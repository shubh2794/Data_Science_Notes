Agent Evaluation

Standard LLM evaluation asks "is this response correct?" Agent evaluation asks something harder: was the whole trajectory good? Did the agent pick the right tools, call them with the right arguments, follow an efficient plan, and know when to stop? Measuring agents means scoring paths, not just endpoints — and tracking cost alongside correctness, because a system that burns a hundred steps to do what should take five is not working.

01 Why agent evaluation is different

An LLM produces text; an agent produces a trajectory — a sequence of reasoning steps, tool calls, observations, and state changes. Standard text metrics cannot see most of what matters.

  • Outputs are actions, not tokens. BLEU, ROUGE, and exact-match score a string; they say nothing about whether the agent called the right tool with the right parameters, or whether a database row was correctly updated.
  • Intermediate steps matter. Two agents can reach the same final answer — one in three clean steps, the other after twenty retries and three hallucinated tool calls. The final-answer score is identical; the systems are not.
  • Evaluation must check multiple dimensions simultaneously: Did the right tools get called? Were the arguments correct? Was the multi-step plan efficient? Did the agent know when to stop — or when to escalate?
  • Non-determinism is structural. The same input can produce different valid trajectories on different runs. Evaluation must distinguish "different but valid" from "wrong."
  • Cost is a first-class metric. An agent that succeeds at 2x the token budget of another is not "just as good" — in production, cost and latency are constraints, not footnotes.

Evaluation is the keystone. Without trajectory-level eval, you cannot tell whether a prompt change, model swap, or tool update made the system better or worse. Every other improvement depends on measuring correctly first.

02 Evaluation sets & hero scenarios

An eval set is a structured collection of test cases, each specifying an input, expected behaviour, and success criteria. Hero scenarios are the highest-priority subset — the cases that must never regress.

Anatomy of an eval case

  • Input state: the starting context — conversation history, available tools, environment state (files, database rows, API stubs).
  • Expected final state: the ground truth — which tool calls should fire (name + arguments), what state changes should occur, what the response should contain.
  • Success criteria: binary (pass/fail on a programmatic check), scored (rubric-based), or ranked (this trajectory is better than that one).

Building and growing eval sets

  • Mine production logs. Real user interactions expose edge cases no one imagined. Filter for failures, escalations, and high-latency runs; convert them to eval cases.
  • Hero scenarios first. Identify the 10–20 representative high-priority use cases that define the system's value. These run on every change.
  • Use LLMs to generate adversarial variants: counterfactual editing (change one detail to flip the correct answer), ambiguous intent blending (combine two plausible interpretations), and edge-case injection (unusual parameter values, missing fields).
  • Living eval sets grow with the system. Every production bug becomes a regression test. Every new capability adds hero scenarios. Static eval sets become stale and misleading within weeks.
eval set lifecycleseed cases → production mining → adversarial generation → regression suite → repeat
Rule of thumb: if the eval set has not changed in a month, it is not testing the system you have today. Treat eval sets as living specification, not a one-time deliverable.

03 Component evaluation

Test individual pieces in isolation before wiring them together. Component-level eval localises failures and keeps debugging tractable.

What to test per component

  • Tool execution correctness. For each tool: does it accept valid inputs and reject invalid ones? Does it handle edge cases (empty lists, missing fields, timeouts) gracefully? Does the output match the contract? This is classic unit testing, applied to the tool layer.
  • Planning quality. Given a task description and available tools, does the planner produce a reasonable strategy? Compare the generated plan against an optimal or reference plan — measuring step count, tool selection, and ordering.
  • Memory retrieval accuracy. Does the agent recall the right context from its memory store? Measure precision and recall of retrieved facts against a labelled set, the same way you would evaluate a RAG pipeline.
  • Learning effectiveness. If the agent uses episodic memory or in-context learning, does performance improve with experience? Compare metrics on the first attempt vs. repeated attempts at similar tasks.

Component eval catches problems cheaply. An end-to-end failure that takes an hour to debug often traces to a tool that fails on empty input — a ten-second unit test.

04 Holistic evaluation

End-to-end scenario testing: give the agent a full task and measure whether the entire job gets done correctly, consistently, and coherently.

Component vs. holistic evaluation radar Compare two agent versions across five evaluation axes

Key dimensions

  • Task completion rate. The binary question: did the agent finish the job? Measure pass@1 (single attempt) and pass@k (best of k attempts) to separate "cannot do it" from "does it unreliably."
  • Consistency. Same input, same output across runs? High variance signals prompt sensitivity or under-constrained behaviour. Run each scenario multiple times and measure agreement.
  • Coherence. Does the agent maintain a logical narrative through the trajectory? Does it contradict earlier steps, forget established facts, or change strategy without cause?
  • Hallucination detection. Does the agent fabricate information — especially tool results it did not actually obtain? Cross-check claims against actual tool outputs in the trace. See Hallucination & Factuality.
  • Robustness. How does performance degrade with typos, ambiguous requests, adversarial prompts, or unexpected tool errors? A system that only works on clean, well-formed inputs is a demo, not a product.
reliability over repeated attemptspass@k = 1 − (1 − p)k
Holistic eval is the final gate, but it is expensive and slow to debug. Use it to catch integration failures that component tests miss — not as a substitute for them.

05 Agent-specific benchmarks

Standardised benchmarks let you compare agents against a shared bar — but the gap between leaderboard position and real-world performance is wide and well-documented.

Custom benchmarks

  • Domain-specific agents (customer support, data analysis, DevOps) need domain-specific eval suites. A code agent benchmark tells you nothing about a support bot's escalation accuracy.
  • Build custom benchmarks the same way you build eval sets: mine production logs, define expected outcomes, automate scoring.

The leaderboard gap

  • Benchmark scores conflate capability with scaffolding — the same model scores differently with different prompt templates, retry strategies, and tool configurations.
  • Agents can overfit to benchmark structure: learning the eval harness, not the task. As soon as the benchmark leaks into training data, scores inflate.
  • Goodhart's law applies: once a benchmark becomes a target, it ceases to be a good measure. Use benchmarks for coarse comparison; use your own eval sets for real decisions.
Benchmarks are maps, not territory. They tell you roughly where you stand. Your own eval suite, built from your production cases, tells you whether the system actually works.

06 Trajectory & cost metrics

Final-answer correctness is necessary but not sufficient. Agents need metrics that see the path, not just the destination.

Trajectory scoring

  • Step reasonableness. Were the intermediate steps logical? Did each action make progress toward the goal, or was the agent wandering? Score by comparing against a reference trajectory or via a judge model.
  • Step efficiency. How many steps did the agent take vs. the optimal? A ratio of actual/optimal steps quantifies waste.
  • Tool call accuracy. Precision: what fraction of tool calls were necessary? Recall: were all needed tools actually called? This catches both over-calling (wasteful) and under-calling (missed steps).
tool call precision and recallprecision = |correct calls| / |total calls made| recall = |correct calls| / |calls needed|

Cost-adjusted metrics

  • Token cost per task: total input + output tokens across all steps. Tracks the monetary cost of a solution.
  • Latency per task: wall-clock time from input to final answer. Includes both LLM inference time and tool execution time.
  • Accuracy per dollar: task success rate divided by average cost. The metric that actually matters in production — it rewards both accuracy and efficiency.
  • Accuracy per second: same idea, with latency as the denominator. For user-facing systems where response time is a constraint.
cost-adjusted successscoreadj = success − λ · (tokens + tool-time) efficiency = success rate / avg cost per task

Reward models over trajectories

  • Train a reward model to score entire trajectories, not just final answers. This enables automated scoring at scale and can feed back into training via preference optimization.
  • The reward model learns from human annotations of trajectory quality: "this run was efficient and correct" vs. "this run succeeded but was wasteful."
  • Trajectory reward models also enable agentic RL — optimising the agent's policy directly on trajectory-level reward.
An eval without a cost axis misleads. Success rate alone rewards brute force. Always report success per unit of budget — per dollar, per second, per step.

07 Evaluation in the development lifecycle

Evaluation is not a one-time gate before launch — it is a continuous feedback loop woven into every stage of development and deployment.

Offline eval in CI/CD

  • Automated eval on every change. Every code change, prompt edit, or model swap triggers the eval suite. Hero scenarios run first (fast, high signal); the full suite runs nightly or on merge.
  • Track metrics over time. Dashboard the key metrics (task completion, cost per task, tool accuracy) with run-over-run comparison. Detect regressions before they reach production.
  • Gate merges on eval results. A PR that drops task completion by 3% should not merge, the same way a PR that breaks unit tests should not merge. CI/CD pipeline integration patterns apply directly here.

Online eval and production

  • Shadow mode. Run the new agent version alongside the old one on real traffic, without serving the new responses. Compare outputs offline. Zero user risk, full signal on real inputs.
  • A/B testing. Split live traffic between old and new agents, measure task success, user satisfaction, cost, and latency. See A/B Testing for statistical rigour.
  • Canary deployments. Route a small fraction of traffic to the new version. Monitor for regressions (error spikes, cost blowouts, latency increases). Promote or roll back based on metrics.
  • Human-in-the-loop review. For novel or high-stakes domains, human reviewers audit a sample of agent runs. Their annotations feed back into the eval set, closing the loop.

The eval flywheel

  • Production failures become eval cases. Eval cases drive improvements. Improvements are validated by eval. The system gets better precisely because eval is continuous.
  • See Monitoring & Drift for detecting when the world changes underneath your agent — new APIs, shifted user behaviour, updated tools.
Treat eval sets as living specification. They define what the agent should do, and they evolve as the system evolves. A frozen eval suite is a frozen understanding of the problem.

08 Pitfalls & what to remember

Pitfalls

  • Overfitting to benchmarks (Goodhart's law). Optimising for SWE-bench until the agent exploits the eval harness rather than solving the problem. Use benchmarks for orientation, not navigation.
  • Testing only happy paths. Eval sets full of clean, well-formed inputs miss the messy reality of production — typos, ambiguous intent, missing context, adversarial users.
  • Ignoring cost and latency. A system that is 2% more accurate but 5x more expensive is a regression in most production settings. Always report cost-adjusted metrics.
  • Static eval sets. An eval suite that has not changed in months is testing yesterday's system. Production logs, new features, and shifting user behaviour all demand new test cases.
  • Not testing tool interactions. The agent may reason perfectly but fail because a tool returns unexpected output, times out, or changes its API. Test the tools independently and in combination.
  • Scoring only the final answer. Two agents can both get the right answer — one efficiently, one through a cascade of retries and hallucinated intermediate steps. Trajectory quality matters.

What to remember

  • Agents need trajectory-level eval, not just output-level. Score the path, not only the destination.
  • Build living eval sets from production logs, hero scenarios, and adversarial generation. Freeze the format, not the content.
  • Test components and end-to-end. Component eval catches bugs cheaply; holistic eval catches integration failures.
  • Track cost-adjusted metrics. Success per dollar and success per second are more informative than success alone.
  • Integrate eval into CI/CD. Automated offline eval on every change, shadow mode and A/B testing in production, human review for high stakes.
