Agent Learning & Improvement

A static agent is a depreciating asset — the world shifts, users change, and yesterday's prompt drifts. Learning is what closes the gap: changing what goes into the model (nonparametric) or changing the model itself (parametric), and wiring both into a feedback loop that turns production traffic into permanent improvement.

Agentic AI Learning Continuous improvement

01 Why agents need to learn

An agent that cannot learn is frozen at the moment it shipped — and the world moves on without it.

  • Environments drift. APIs change return formats, user vocabulary evolves, new edge cases appear. A frozen prompt degrades silently, then fails loudly.
  • Manual updates do not scale. A human rewriting prompts after every failure is a bottleneck; learning automates the feedback loop.
  • Two axes of learning. Nonparametric learning changes what goes into the model — examples, reflections, memory — without touching weights. Parametric learning changes the model itself — fine-tuning, preference optimization, RL.
  • The practical order: start nonparametric (fast, reversible, no training infra), graduate to parametric as data accumulates and the nonparametric ceiling becomes visible.

Key insight: nonparametric and parametric learning are not alternatives — they are stages. Most production agents climb the ladder: exemplar learning first, fine-tuning later, evaluation throughout.

02 Exemplar learning

The simplest form of agent learning: store what worked, retrieve it at runtime, let the model generalize from examples.

  • The triple. Every successful run yields an (input, action-sequence, outcome) triple. Inject the best-matching triples as few-shot examples and the model imitates the demonstrated behaviour.
  • Fixed few-shot — a handful of hand-picked examples hardcoded in the prompt. Easy to start with; breaks when the task distribution widens beyond those few cases.
  • Dynamic few-shot — embed each stored example, embed the current input, retrieve the top-k by cosine similarity from a vector store. Scales to thousands of examples and adapts the prompt to every query.
dynamic exemplar retrievalscore(q, ei) = cos(embed(q), embed(ei)) prompt = instructions ⊕ top-k(score) ⊕ query
  • Granularity matters. Store full task trajectories for end-to-end imitation, or individual sub-task solutions for more composable retrieval. The right grain depends on task diversity.
  • As count grows, retrieval quality dominates. At 50 examples, any retrieval works. At 5,000, poor embeddings or missing metadata bury the best matches. Treat the example store like a RAG pipeline — chunk, embed, index, re-rank.
  • Cold-start: seed the store with synthetic examples (model-generated, human-verified) to bootstrap before real production data arrives.
Remember: exemplar learning is in-context learning with a retrieval front-end — it inherits the strengths (no training) and limits (context window, model ceiling) of both.

03 Reflexion

Act, fail, self-critique, and remember the lesson — a lightweight learning loop that changes nothing but the prompt.

  • The loop. The agent attempts the task, logs the full trial (actions, observations, outcome), then generates a reflection: what went wrong, what to do differently. The reflection is stored in memory and injected into the prompt on the next attempt.
  • No weight changes. The model coaches itself purely through context engineering — reflections are just more text in the window. This makes reflexion fast to deploy and easy to debug.
the reflexion looptrialk = agent(task, reflections1..k−1) rk = reflect(trialk, outcomek) memory ← memory ∪ {rk}
  • Works well for: code debugging (run tests, see failures, reflect, retry), multi-step reasoning (trace the wrong step), web navigation (observe dead ends, avoid them).
  • Improves with iterations — typically 2-4 reflection rounds yield most of the gain; more rounds add cost with diminishing returns.
  • Quality of reflection matters more than quantity. Vague "try harder" reflections teach nothing; grounded reflections that cite specific observations and propose concrete strategy changes are what drive improvement.
  • Limitation: the model cannot learn what it cannot critique. If the failure mode is invisible in the trace (e.g., subtle logical errors the model also cannot detect on review), reflexion will not help.
Key idea: reflexion turns a single-shot agent into an iterative learner without any infrastructure — just the LLM, a memory buffer, and a prompt template. See Agentic Design Patterns for how reflection fits the broader pattern catalogue.

04 Experiential learning

Richer than storing outcomes — store full trajectories and mine them for reusable strategies.

  • Full trajectories. Record (state, action, observation, reward) at every step, not just the final outcome. This preserves the structure of the decision process, not just its result.
  • Experience replay. At planning time, sample relevant past experiences and use them to inform the current decision. Analogous to replay buffers in reinforcement learning, but applied at the prompt level.
  • Episodic memory. Retrieve full episodes — past runs whose initial state resembles the current situation — and present them as context. The agent sees how a similar problem was solved before and adapts the strategy.
experience-informed planningepisodes = retrieve(statenow, memory, k) plan = agent(task, episodes, reflections)
  • Strategy distillation. After accumulating many episodes, extract generalizable patterns: "when the API returns a 429, back off and retry" or "always verify file existence before reading." These become persistent instructions — experience crystallized into rules.
  • Filtering is essential. Not all experiences are worth replaying. Filter by outcome quality, recency, and relevance. Replaying bad trajectories teaches bad habits; replaying stale ones teaches outdated strategies.
  • Storage cost. Full trajectories are large. Compress by keeping only decision points and their outcomes, or by summarizing long observation spans while preserving key facts.
Remember: exemplar learning stores what worked; experiential learning stores how it worked. The richer signal supports better generalization but demands more careful curation.

05 Parametric learning (fine-tuning)

When in-context tricks plateau, change the weights — make the model itself embody the learned behaviour.

  • When to cross the line. Nonparametric learning hits a ceiling: the context window fills up, retrieval noise grows, and the base model's priors resist the demonstrated behaviour. Fine-tuning pushes past this ceiling.
  • Supervised fine-tuning (SFT) on curated agent trajectories: take the best runs, format them as training data, and train the model to reproduce those trajectories. The model internalizes the behaviour that was previously only in-context.
  • Direct preference optimization (DPO) — train on (preferred trajectory, rejected trajectory) pairs. The model learns not just what to do but what not to do, without needing an explicit reward model. See Policy / Preference Optimization.
  • RLVR (reinforcement learning with verifiable rewards) — for tasks with automated verification (code passes tests, math answers match, SQL returns correct results), train directly on the binary reward signal. No human labels needed once the verifier exists.
the fine-tuning progressionSFT: minimize −log πθ(aexpert | s) DPO: maximize log σ( β · ( log πθ(aw) − log πθ(al) ) ) RLVR: maximize 𝔼[ R(τ) · log πθ(τ) ]
  • The promise of specialization. A small, task-specific fine-tuned model can match or beat a large general model on its target domain — at a fraction of the inference cost. This is how production agents escape the "biggest model for everything" trap.
  • PEFT for agents: LoRA and similar methods let you fine-tune cheaply and maintain multiple task-specific adapters on the same base model.
  • Data quality over quantity. 500 high-quality, verified trajectories beat 5,000 noisy ones. Invest in curation: human review of training trajectories, filtering by outcome score, deduplication.
Remember: fine-tuning is powerful but slow and hard to reverse. Use nonparametric learning to find the right behaviour, then fine-tuning to bake it in.

06 Feedback pipelines

Learning needs signal — build the pipeline that turns production traces into prioritized improvements.

  • The production feedback loop: collect traces → detect issues → root-cause analysis → prioritize improvements → refine prompts/tools/examples → redeploy → measure impact → repeat.
  • Automated issue detection. Run an LLM-as-judge over production traces to flag failures, near-misses, and quality drops. Cheaper than human review for the bulk of traffic; catches systematic problems that individual users might not report.
  • Human-in-the-loop for edge cases. Route the hardest failures — where the judge is uncertain or the stakes are high — to human reviewers. Their annotations become both fixes and future training data.
StageWhat happensWho/what does it
CollectLog full traces: inputs, actions, observations, outputs, latency, costInstrumentation / observability

  • Aggregation matters. Individual failures are noisy; patterns across many failures are signal. Cluster failure traces by root cause, not by surface symptom, to avoid fixing the same underlying issue five different ways.
  • Close the loop fast. The lag between a failure in production and a deployed fix is the system's learning rate. Nonparametric fixes (new examples, updated prompts) can deploy in minutes; parametric fixes (fine-tuning) take days.
Remember: without a feedback pipeline, learning is ad-hoc — someone notices a failure, someone else fixes it, and nobody tracks whether the fix worked. The pipeline makes improvement systematic.

07 Experimentation & continuous learning

Ship the improvement, measure it, and let usage feed the next round — the flywheel that turns a good agent into a great one.

The learning ladder Click "Climb" to advance through each learning technique and see performance improve
  • Shadow deployments. Run the new agent alongside the old on the same inputs; compare outputs without exposing users to risk. Catches regressions before they reach production.
  • A/B testing on live traffic. Split users between the current agent and the candidate. Measure task success, user satisfaction, cost, latency. Statistical rigor matters — small sample sizes produce false positives.
  • Bayesian bandits for rapid exploration: allocate more traffic to the variant that is winning, converge faster than fixed-split A/B tests. Useful when you have many prompt variants to compare.
  • In-context learning from production. As the example store and episodic memory grow from real usage, the agent improves without any retraining — the nonparametric flywheel.
  • Offline retraining cycles. Periodically harvest the best production trajectories, curate them, and fine-tune. Each cycle raises the parametric baseline, which makes the nonparametric layer more effective on top.
the improvement flywheelusage → traces → curation → learning → better agent → more usage
  • The goal: compound improvement. Each cycle of the flywheel raises the floor. Nonparametric improvements are fast but bounded; parametric improvements are slow but permanent. Together they compound.
  • Versioning everything. Track prompt versions, example store snapshots, model checkpoints, and eval results together. When something regresses, you need to know what changed.
Remember: experimentation without evaluation is just change. Every deployment — shadow, A/B, or full — must be paired with a clear success metric and an eval that measures it.

08 Pitfalls & what to remember

Pitfalls

  • Learning without evaluation = blind optimization. You cannot improve what you do not measure. Every learning mechanism needs a paired eval that catches regressions.
  • Experience replay without filtering = learning from bad examples. An unfiltered trajectory store teaches the model to repeat its own mistakes. Filter by outcome quality, recency, and relevance.
  • Fine-tuning on too few examples = overfitting. The model memorizes the training trajectories instead of generalizing. Watch for exact reproduction of training examples and poor performance on held-out tasks.
  • Not separating learning from serving. Retrieval over a large example store, reflection generation, or trajectory logging can add latency. Keep the serving path fast; do learning work asynchronously.
  • Stale memory. Old reflections and examples can contradict current reality. Memory needs a forget policy — decay, invalidation, or periodic review.

What to remember

  • The learning ladder: start with exemplar learning (fast, simple) → add reflexion (self-improvement) → build experience replay (richer signal) → graduate to fine-tuning (permanent improvement).
  • Always run evaluation alongside learning. Every improvement must be tested before deployment and monitored after.
  • Build feedback pipelines for continuous, systematic improvement — not ad-hoc fixes.
  • Nonparametric learning finds the behaviour; parametric learning bakes it in. Use both, in that order.
  • The flywheel: usage generates data, data enables learning, learning makes the agent better, a better agent gets more usage.
