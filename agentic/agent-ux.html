Agent UX Design

Building an agent that works is one problem; building one that people want to use is another. This page covers the human side of agentic systems — interaction modalities, the right level of autonomy, trust calibration, and how to design for the inevitable failures.

01 Interaction modalities

Agents meet users through text, GUI, voice, or video — and each modality shapes what the agent can do well.

  • Text-based (chatbots, CLI agents, messaging). The lowest-bandwidth channel is also the most traceable: every turn is logged, copy-pasteable, and searchable. Text scales to multi-step tool use where the user needs to audit intermediate reasoning. IDE integrations and terminal agents live here.
  • Graphical interfaces (dashboards, workflow builders, IDE panels). GUIs give agents visual structure: progress bars, step graphs, side-by-side diffs. Users can click to approve, reject, or reorder sub-tasks instead of typing instructions. Workflow builders expose the agent’s plan as a drag-and-drop graph.
  • Speech / voice (smart assistants, call-centre automation). Voice is hands-free and fast for short commands, but poor for precision editing and hard to audit after the fact. Turn-taking latency is critical: 300 ms feels responsive, 2 s feels broken.
  • Video / avatar (virtual tutors, therapy avatars, embodied agents). Adds facial expression, gesture, and spatial presence for empathy-sensitive domains. The richest channel — and the hardest to get right without falling into the uncanny valley.

Multimodal combinations are increasingly the norm: an IDE agent that shows a text chat alongside a visual diff, or a voice assistant that falls back to a screen for complex output. The design principle is match the modality to the task phase — voice for intake, GUI for review, text for the audit trail.

One sentence: choose the modality that fits the task’s bandwidth, traceability, and precision needs — then design a graceful fallback to a richer channel when the primary one is not enough.

02 The autonomy slider

Not every agent needs full autonomy. The right level depends on stakes, reversibility, and user preference — and it should be adjustable.

The autonomy spectrum Click a stop to see how risk, speed, and human effort change
  • Manual: the human does everything; the agent offers passive information or search results. No autonomy risk, but no speed gain either.
  • Suggest: the agent drafts an action or answer; the human edits and executes. Good for creative tasks where the user wants control but values a starting point.
  • Approve: the agent proposes a concrete action and waits for a yes/no. The human is a gate, not a writer. This is the most common pattern for medium-stakes work: code changes, email sends, data modifications.
  • Monitor: the agent acts on its own but surfaces a log. The human reviews after the fact and can intervene or undo. Works when actions are reversible and speed matters.
  • Autonomous: the agent acts without notifying. Appropriate only for low-stakes, reversible, well-tested tasks: code formatting, routine filing, spam filtering.
matching autonomy to stakesautonomy ≤ f( 1 / stakes, reversibility, model_reliability )

High-stakes domains (medical, financial, legal) should cap at Approve or Monitor. Low-stakes domains (email drafting, code formatting, file organisation) can safely reach Autonomous. The key design decision is to let users adjust the slider: a power user may want Monitor where a new user wants Approve for the same task.

Remember: autonomy is a dial, not a switch. Default to the lowest level that is useful, and let the user turn it up as trust builds. See Agents for how the loop itself is structured.

03 Synchronous vs asynchronous experiences

A chatbot answers in seconds; a research agent works for minutes. The UX patterns for each are fundamentally different.

Synchronous: the conversation

  • Users expect sub-second feedback that something is happening: a typing indicator, streaming tokens, or a progress spinner.
  • Turn-taking must be explicit. The user needs to know when it is their turn and when the agent is still working. Ambiguity here is the top frustration in chat UX.
  • If a sync task takes more than ~15 seconds, convert it to async rather than making the user stare at a spinner. Tell them you will notify them when done.

Asynchronous: the background worker

  • The agent works in the background — running a CI pipeline, researching a topic, processing a batch of emails. The user may close the tab.
  • Progress updates matter more than speed: "3 of 12 sources checked" beats silence. Surface partial results early so the user can course-correct.
  • Notification design is critical: notify on completion, on failure, or when approval is needed. Too many notifications train users to ignore them; too few leave users wondering if the agent is still running.
  • Always provide a status page: current step, elapsed time, estimated completion, and a cancel button.

Many real agents are hybrid: the first response is synchronous ("I will research this for you"), but the work is async, with periodic check-ins. The design challenge is the boundary: when does a conversation become a background job?

Design rule: if the user cannot do anything useful while waiting, it is sync and must be fast. If they can, it is async and must have progress, notifications, and a status page.

04 Context retention & continuity

Users should not have to repeat themselves. Good memory is the difference between a tool and a collaborator.

Session memory vs long-term memory

  • Session memory is the conversation transcript — everything said in this interaction. It degrades with length (see Context Engineering). Compaction and summarisation preserve the important parts.
  • Long-term memory persists across sessions: user preferences, past decisions, known constraints. This is where the agent stops feeling generic and starts feeling like your agent.
  • The two serve different purposes: session memory supports task completion; long-term memory supports personalisation and adaptation.

What users actually want from memory

  • "Remembers my preferences" — I always want TypeScript, I prefer concise answers, I deploy to AWS. These are stable facts, stored once and retrieved often.
  • "Learned from past mistakes" — last time you reformatted my code you broke the imports; do not do that again. This is episodic memory: event-specific lessons that require inference, not just retrieval.
  • Context handoff between agents in a multi-agent system: when one agent hands off to another, the user should not have to re-explain the problem. The handoff must carry the goal, the state, and what has been tried.
memory as retrievalmemory(q) = retrieve( q, store ) → relevant context injected into ct

Every memory store needs a write policy (what gets saved and when) and a forget policy (how stale entries are pruned). Without both, the store grows noisy and retrieval degrades. Users should be able to view, edit, and delete what the agent remembers about them.

Remember: memory is a retrieval problem. The same principles — relevance, recency, deduplication, and bounded store size — apply whether you are retrieving documents or user preferences.

05 Communicating capabilities & limitations

The biggest UX failure is a capable agent that users do not know how to use.

Discoverability

  • Users rarely read documentation. The agent must proactively communicate what it can do at the right moment: "I can help you cancel orders, check delivery status, or update your account."
  • Use contextual suggestions: when a user is on a settings page, offer settings-related actions. When they paste an error log, offer debugging help. The agent’s affordances should feel as obvious as buttons on a toolbar.
  • Progressive disclosure: show three top capabilities first, then "I can also..." for the long tail. Do not overwhelm on first contact.

Communicating confidence and uncertainty

  • When the agent is uncertain, say so: "I am about 70% sure this is right — you may want to verify." Calibrated confidence prevents both over-trust and under-trust.
  • Use visual cues: confidence badges, warning colours, or hedging language. Avoid false precision ("92.3% confident") when the model cannot truly calibrate at that level (see Hallucination & Factuality).
  • When unsure, ask rather than guess. A clarifying question is almost always better than a wrong answer delivered confidently.

Graceful fallback

  • When the agent cannot help, it should: (1) say so clearly, (2) explain why, (3) suggest alternatives — a different phrasing, a human agent, a documentation link.
  • Never fail silently. Never say "I cannot do that" without a next step.
Design rule: the agent should feel like it has a manual built in. At any point, the user should know what it can do, how confident it is, and what to do when it cannot help.

06 Trust in agent interaction

Trust is built through predictable behaviour, transparency, and successful outcomes. The goal is calibrated trust — not maximum trust.

Building trust

  • Predictability: the agent should behave consistently. Same input, same general approach. Surprising behaviour erodes trust faster than a failure does.
  • Transparency: show the agent’s reasoning. Cite sources. Display the plan before executing. Let users expand intermediate steps. This is not just about honesty — it is about debuggability.
  • Successful outcomes: nothing builds trust like working. Ship the easy wins first; earn the right to handle harder tasks by proving reliability on simpler ones.
  • User override: at every step, the user should be able to correct, cancel, or redirect the agent. The feeling of control is trust.

Trust calibration

  • Over-trust leads to automation complacency: the user stops checking the agent’s work, and errors slip through. This is especially dangerous in high-stakes domains where the agent is usually right but occasionally catastrophically wrong.
  • Under-trust leads to underutilisation: the user re-does the agent’s work manually, gaining no benefit. This often happens after a salient early failure, even if the agent is reliable overall.
  • The ideal is a user who verifies proportionally to stakes: spot-checks low-stakes output, carefully reviews high-stakes output, and knows the difference.

Trust repair

  • After a failure, the agent should: (1) acknowledge the error explicitly, (2) explain what went wrong if possible, (3) show what it is doing differently this time.
  • Rebuilding trust takes more evidence than building it in the first place. Budget extra transparency after a failure — show more reasoning, ask for more confirmations, run more checks.
One sentence: the best agent UX produces calibrated trust — users who rely on the agent the right amount, verify when it matters, and are never surprised by the agent’s limitations.

07 Designing for failure

Agents will fail. The question is not whether, but whether the failure is cheap and recoverable or expensive and silent.

Graceful degradation

  • Clear error messages: tell the user what happened, not just that something went wrong. "I could not access your calendar because the connection timed out" beats "Something went wrong."
  • Suggest next steps: retry, try a different approach, escalate to a human, or offer a partial result. Never dead-end the user.
  • Preserve context during handoff: if the agent escalates to a human, pass along the full conversation, the goal, and what was attempted. The user should not have to start over.

Ambiguity handling

  • When the user’s intent is ambiguous, clarify rather than guess. "Did you mean the marketing budget or the engineering budget?" is better than a 50-50 gamble.
  • The exception is when the cost of guessing wrong is very low and the cost of asking is high (e.g., interrupting a voice workflow). In that case, guess and make it easy to correct.

Partial results, undo, and progressive error detail

  • Partial results: if the agent completed 8 of 10 sub-tasks before failing, return the 8. Do not throw away good work because the last step broke.
  • Undo / rollback: for autonomous actions, provide a way to reverse them. If the agent sent an email, offer to send a correction. If it modified a file, keep a backup. Reversibility is what makes autonomy safe.
  • Progressive disclosure of error details: show a simple message first ("The search failed"), with an expandable section for details ("Connection refused at api.example.com:443, retried 3 times, last attempt at 14:32:07"). Developers want the detail; end users want the summary.

Design stance: assume the agent will be wrong and make wrongness cheap — undo for actions, partial results for tasks, context preservation for handoffs, and progressive detail for errors. See also Failure modes in Agents.

08 Pitfalls & what to remember

Pitfalls

  • Over-automating high-stakes tasks: full autonomy on medical, financial, or legal actions. The speed gain is not worth the liability when the agent gets it wrong.
  • Poor discoverability: a powerful agent that users do not know how to use is indistinguishable from a weak one.
  • No feedback mechanism: if users cannot tell the agent it was wrong, the agent cannot improve and users cannot build trust.
  • Ignoring async UX: designing only the happy-path chat flow and neglecting what happens when the agent runs for minutes — no progress, no notifications, no cancel button.
  • Not designing for trust repair: one salient failure with no acknowledgement or explanation can permanently damage adoption.
  • Silent failures: the agent encounters an error, says nothing, and returns a subtly wrong result. The user trusts it because the agent seemed confident.

What to remember

  • Match the modality to the task: text for auditability, GUI for structure, voice for hands-free, video for empathy. Combine when needed.
  • Use the autonomy slider: default low, let users dial up. Match autonomy to stakes and reversibility.
  • Design both sync and async paths: fast feedback for conversations, progress and notifications for background work.
  • Memory is a retrieval problem: session memory for task completion, long-term memory for personalisation. Users should control what is remembered.
  • Communicate capabilities proactively: the agent should feel like it has a built-in manual. Surface confidence, uncertainty, and fallback options.
  • Build calibrated trust: transparency, predictability, user override, and trust repair after failures.
  • Design for failure: clear errors, partial results, undo, context-preserving handoffs, and progressive error detail.
