Agentic Design Patterns

Almost every working agent is an assembly of a few recurring structures — chaining, routing, parallelism, reflection, tool use, planning, delegation. Naming them turns "design an agent" into "pick the cheapest arrangement that clears the bar".

Agentic AI Architecture Patterns

01 Why patterns, and the agency dial

The useful axis is not "agent vs. not an agent" but who decides the control flow. In a workflow, you wrote the graph and the model fills in nodes. In an agent, the model chooses the next step at runtime, in a loop, until it decides it is done.

  • Turning the dial up buys flexibility on open-ended tasks and costs predictability: more calls, higher latency, more places to go wrong, harder debugging.
  • So the default rule is start simple. A single well-prompted call with good context beats a five-agent constellation on most tasks. Add a pattern only when a measured failure demands it.
  • The reason structure is needed at all is compounding: multi-step tasks multiply per-step reliability. A step that works 95% of the time is fine once and hopeless twenty times in a row.
  • Every pattern below is really a way to spend tokens on one of three things: quality (extra passes), reach (external state), or containment (limiting how far an error travels).
reliability compounds multiplicativelyP(task) = ∏i=1..n pi 0.9510 ≈ 0.60 0.9910 ≈ 0.90
One sentence: patterns exist because long tasks decay geometrically — each one either raises pi, shortens n, or inserts a checkpoint that stops the decay.

02 The pattern atlas

Read every pattern along three questions: who picks the next step (you or the model), how many model calls it costs, and where the checkpoint sits — the point at which something is verified before work continues.

  • Fixed-path workflows — prompt chaining, routing, parallelization. You own the graph; the model owns each node. Cheapest and most debuggable.
  • Feedback loops — reflection and the evaluator–optimizer split. A second pass judges the first and sends it back.
  • Open loops — tool use / ReAct, planning, orchestrator–workers. The model chooses its own next action until a stop condition fires.

03 Fixed-path workflows

Three patterns where you write the control flow. They are not glamorous and they solve a surprising share of real tasks.

Prompt chaining — decompose into a fixed sequence

  • Intent: trade one hard call for several easy ones. Structure: call 1 → optional programmatic gate → call 2 → call 3, each step's output being the next step's input.
  • Use when the task splits cleanly into ordered subtasks and you can check the intermediate artifact. Failure modes: errors propagate silently, latency is the sum of all hops, and an over-fine decomposition loses global coherence.
  • Example: draft an outline → validate it has the required headings → write each section against it.

Routing — classify, then dispatch

  • Intent: send each input to the handler built for it, instead of one prompt that hedges across all cases. Structure: a small classifier picks a branch; each branch has its own prompt, tools, and model tier.
  • Use when inputs fall into distinct classes, or when a cheap model can serve most traffic and a strong one only the hard tail. Failure modes: confident misroutes with no fallback, and class boundaries that drift as traffic changes.
  • Example: billing questions to a refund tool-chain, debugging questions to a code-execution agent.

Parallelization — sectioning and voting

  • Sectioning: split independent subtasks across simultaneous calls and merge. Latency becomes the slowest branch rather than the sum, and each branch gets a focused context.
  • Voting: run the same task k times and aggregate by majority or by any-flag. Majority raises accuracy when errors are roughly independent; any-flag raises recall for safety checks at the cost of false positives.
  • Failure modes: cost multiplies by k, and correlated errors — same model, same prompt, same blind spot — make voting an expensive way to repeat yourself.
latency and votingTserial = ∑i ti Tparallel = maxi ti + tmerge P(majority of k correct) = ∑j > k/2 C(k, j) · pj · (1 − p)k − j ⟵ only valid if errors are independent
Chaining spends latency to buy accuracy; parallelization spends tokens to buy latency or reliability; routing spends a small classifier to buy both. None of them give the model control of the graph.

04 Reflection & evaluator–optimizer

Generate → critique → refine. The cheapest quality pattern there is, and the one most often used where it cannot possibly work.

Self-critique

  • The same model reviews its own output against the instructions and rewrites. It reliably catches format violations, omissions, and internal contradictions — errors visible in the text itself.
  • It is much weaker at catching factual errors, because the same weights that produced the mistake are asked to notice it.

Evaluator–optimizer — split the roles

  • Structure: a generator produces a candidate; a separate evaluator scores it against an explicit rubric and returns actionable critique; the generator revises. Loop until the score clears a threshold or the budget runs out.
  • The split matters: a fresh prompt with the rubric and none of the drafting context is a harsher critic than a continuation of the drafting conversation. See LLM-as-a-judge for the biases that follow the evaluator around.
  • Use when the quality signal is real — tests, a compiler, a schema validator, a retrieval check — or when a human would obviously improve the draft on a second read.
  • Failure modes: self-preference (the model likes its own text), endless cosmetic polish, critiques that reshuffle rather than fix, and 2–3× cost for a marginal gain.
  • Example: write a query → run it → feed the error or empty result back → repair.
stop condition — always requiredstop if score ≥ τ or k ≥ kmax or Δscore < ε
Rule of thumb: reflection pays when the critic has information the generator lacked — a tool result, a rubric, a different context. Pure self-review with no new signal usually just adds tokens.

05 Tool use & the ReAct loop

Tools are how a model touches state it did not memorise: search, code execution, databases, APIs, a file system. This is the pattern that turns a text generator into something that can act.

  • Structure: the model emits a structured call, the runtime executes it and returns the result as an observation, and the loop repeats — think → act → observe — until the model answers. That interleaving is the ReAct loop.
  • Where it breaks down decomposes cleanly: picking the right tool, filling the arguments correctly, and actually using what came back. All three fail differently and should be measured separately.
  • Tool design is prompt design. Unambiguous names, a description that says when not to use it, tight schemas with enums instead of free strings, and error messages written for a model to act on.
  • Observation bloat is the quiet killer: raw tool output floods the window and buries the goal. Truncate, summarise, or write results to a file and pass a handle — see context engineering.
  • Example: a question about today's numbers → query the warehouse → read the rows → answer with the figure and the query used.
decompose tool reliabilitypstep = pselect · pargs · puse ⟵ fix the smallest factor first
More tools is not more capability. Past roughly a dozen similar-sounding tools, selection accuracy falls; group them, hide irrelevant ones behind a router, or expose one tool that takes a small program.

06 Planning

Write the plan before doing the work, so that a wrong turn on step 7 does not silently redefine the goal.

  • Plan-then-execute: decompose the goal into an ordered list of subtasks with explicit dependencies and success criteria, then run them. The plan is an artifact you can show a human, cache, and diff against what actually happened.
  • Interleaved re-planning: after each step, compare the observation to the expectation and revise the remaining plan. More robust, more expensive, and the pattern that keeps long tasks from drifting.
  • Use when the horizon is long, steps have dependencies, or the work is expensive enough that a wrong ordering is costly. Skip it when the task is two steps — a plan for a two-step task is pure overhead.
  • Failure modes: plans that read beautifully and cannot be executed; over-decomposition into trivia; sticking to a stale plan after the world changed; and re-planning so often that no step ever completes.
  • Quality here is bounded by the model's reasoning: a plan is a chain of thought that happens to be executable.
re-plan triggerreplan if observation ≠ expectation or stepsused > 1.5 · stepsplanned
A plan is most valuable as a contract: it is the cheapest place to insert a human checkpoint, because approving a plan costs one read and rejecting a finished artifact costs the whole run.

07 Multi-agent shapes

Several models, each with its own context, instructions, and tools. The gain is rarely "more brains" — it is context isolation and parallel exploration.

Orchestrator–workers

  • A lead agent decomposes the task at runtime, spawns workers with narrow briefs, and synthesises their returns. Unlike parallel sectioning, the number and shape of the subtasks is decided by the model, not by you.
  • The real benefit: each worker gets a clean window containing only its slice, so the lead never has to hold every intermediate result at once.
  • Failure modes: vague briefs producing overlapping work, workers that cannot ask clarifying questions, and token cost several times a single-agent run.

Debate and role play

  • k agents argue positions for a few rounds and a judge decides. It helps where disagreement is checkable — a proof step, a numeric answer, a policy that either applies or does not.
  • On subjective tasks it mostly produces expensive consensus: agents converge to agreement quickly, and persona labels ("you are a senior architect") add style more than accuracy.
  • Example: two reviewers argue whether a change is safe, a judge writes the verdict with the strongest argument from each side.
Before you split: most "multi-agent" problems are context problems. If one agent fails because its window is polluted, isolation fixes it — but so does summarising, and that costs one call instead of five.

08 Memory, checkpoints, guardrails

The three patterns that decide whether a demo survives contact with real users. None of them make the agent smarter; all of them make it survivable.

Memory patterns

  • Scratchpad — a running notes field the agent rewrites each turn, holding the goal, what is done, and what is left. Cheap, and the single best defence against drift on long runs.
  • Compaction — when the window fills, summarise the transcript into a compact state and continue. Keep raw artifacts on disk and carry handles, not contents.
  • External store — write durable facts to a retrievable store and fetch by relevance at each step, so memory does not scale with the window. Details in context engineering.

Human-in-the-loop checkpoints

  • Put the gate where reversal is impossible or expensive: before a purchase, a delete, an outbound message, a production write. Everything else can run unattended.
  • Also gate on plan approval and on low confidence — cheap moments where one human answer redirects the entire remaining run.
  • Make the ask answerable in seconds: what will happen, on what, and a default. A checkpoint that requires reading a transcript will be rubber-stamped.

Guardrails

  • Validate inputs (injection screening, scope checks) and outputs (schema, policy, citation presence) with deterministic code wherever a rule can be written as code.
  • Cap the loop on steps, tokens, wall-clock, and spend; require a re-authorisation to continue past a budget. Keep a kill switch that leaves the environment in a recoverable state.
loop budget — every open loop needs onehalt when steps > Smax ∨ tokens > B ∨ elapsed > T ∨ no-progress-turns > m
Guardrails belong outside the model, in the runtime. A rule the model is merely asked to follow is a suggestion; a rule the executor enforces is a guarantee.

Did the pattern actually help?

  • Hold a frozen eval set of real tasks with automatic graders. Run the simpler baseline and the patterned version on the same set, same model, same seeds where possible.
  • Report four numbers together: task success, cost per solved task, p95 latency, and human interventions per 100 runs. A pattern that lifts success 3 points while tripling cost is often a loss.
  • Demand a margin beyond noise — with N tasks the standard error on a success rate is roughly √(p(1−p)/N), so a 2-point gain on 50 tasks means nothing.
  • Watch for the classic confound: the patterned version also got a better prompt. Change one thing.

10 Pitfalls & what to remember

Pitfalls

  • Agency as a default. Reaching for an open loop when a two-step chain would do; the loop is harder to debug and the failure is non-deterministic.
  • Unbounded loops. Any back-edge without a step, token, time, and no-progress budget will eventually spin on a live system.
  • Reflection without signal. Self-critique with no rubric, tool result, or fresh context mostly rewords the draft at double the cost.
  • Voting on correlated errors. Same model, same prompt, k samples — the majority is confidently wrong together.
  • Multi-agent as a first resort. Handoffs lose context; a briefing that is not written down does not exist for the worker.
  • Guardrails living in the prompt. If the executor does not enforce it, it is not a limit.
  • Improving on the eval set. Patterns are easy to tune to your 40 favourite tasks; hold out a set you never look at.

What to remember

  • Control flow is the design decision: you pick the graph (chaining, routing, parallel) or the model does (ReAct, planning, orchestration).
  • Reflection buys quality, tool use buys reach, planning buys coherence over a horizon, delegation buys context isolation, checkpoints buy safety.
  • P(task) = ∏ pi — shorten the horizon, raise each step, or verify in the middle.
  • Start simple, add one pattern at a time, and keep the pattern only if success-per-cost improved beyond noise.
  • Neighbours: the agent loop these patterns arrange, agentic RL for learning the policy instead of prompting it, skills for packaging procedures, reasoning, and context engineering.
The whole page in one line: pick the least agency that clears the bar, put a checkpoint where failure is expensive, and measure cost per solved task — not success alone.
