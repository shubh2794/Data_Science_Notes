Agents

A language model answers; an agent acts. Wrap the model in a loop, give it tools, memory, and an environment to touch, and a one-shot predictor becomes a system that plans, takes actions, reads what happened, and keeps going until the goal is met — or until it is stopped.

Agentic AI Tool use Autonomy

01 What makes it an agent

An agent is an LLM plus a loop, tools, and memory, pointed at a goal — and, crucially, allowed to choose its own next step.

  • The model is the policy. Given what it has seen so far it picks the next action; the scaffold only decides what is allowed.
  • The loop supplies persistence. A chat completion ends after one response; an agent keeps acting until a stop condition fires — final answer, step budget, timeout, or interrupt.
  • Tools supply reach: search, code, files, databases, HTTP — anything the runtime can execute, with the result fed back as an observation.
  • Memory supplies continuity: a transcript within the run, optionally a store across runs.

Autonomy is a dial, not a switch: at one end a single tool call inside a hand-written pipeline, at the other an open loop that decides which tools to call, how often, and when to stop. The more control flow you hand the model, the more flexible the system — and the harder to predict, price, and test.

02 The agent loop (ReAct)

The core pattern: interleave reasoning and acting, so each action is informed by the last observation.

Reason → Act → Observe, until it can answer The agent thinks, calls a tool, reads the result, and repeats

Why interleaving beats either half

  • Reasoning without acting hallucinates its premises — it invents the population figure, then does arithmetic on a fiction.
  • Acting without reasoning fires tools blindly: no hypothesis about the result, so nothing catches a wrong or empty response.
  • The thought is where the agent picks which action and — just as important — decides whether it now has enough to stop.

One iteration

  • Assemble ct: instructions, tool schemas, goal, running transcript.
  • Sample an action — a tool call (name + arguments) or a terminal answer, optionally preceded by reasoning tokens.
  • Execute in the environment; capture output, errors, truncation. Append the observation and repeat.
Remember: the loop body is trivial; the difficulty is entirely in what goes into ct and what the agent may do with it. See Reasoning in LLMs for how the thought half is trained.

03 Tool use and where it runs

Tools are how an agent escapes the limits of its weights — and where most real failures live.

Schemas and the call contract

  • A tool is a name, a description (what it does and when to use it), and a typed argument schema. The model emits a structured call; the runtime validates and executes it.
  • The description does selection work, exactly like a retrieval query. Overlapping descriptions are the commonest cause of wrong-tool calls, so keep the toolset small and orthogonal.
  • Constrained decoding makes arguments syntactically valid by construction; it cannot make them semantically right.

Parallel calls, and errors as observations

Independent actions should not be serialized: several calls emitted in one turn can run concurrently and return together. Recognising independence is a planning judgement — fetching three files is parallel, "read the config, then fetch what it points at" is not.

round-trips, sequential vs batchedTseq = Σi=1..k ( tllm + ttool,i ) Tpar = tllm + maxi ttool,i
  • A failed call should return a readable error — message, offending argument, hint — so the model can correct itself. Cap retries: two informative failures teach more than ten identical ones.
  • Truncate large outputs with an explicit marker and a way to page through the rest; one huge tool result can end a run.
  • Make destructive tools idempotent or confirmation-gated, because retries will happen.

Environments and sandboxes

Calls execute somewhere — a container, a VM, a browser session — and that environment defines the true action space and the blast radius. Sane defaults: disposable filesystem, no ambient credentials, network allow-list, CPU and wall-clock caps. Sandboxing also makes runs reproducible, which is what turns a demo into something you can evaluate and later train on (see Computer Control).

Remember: tool reliability, not model IQ, is usually the binding constraint. Clear schemas, informative errors, bounded outputs, and a sandbox buy more success than a bigger model.

04 Planning, decomposition, reflection

Reacting handles the next step; planning handles the shape of the task; re-planning handles the moment reality disagrees.

Decomposition and re-planning

  • Plan-then-execute drafts ordered sub-goals first; the plan is a cheap artifact — inspectable, editable, cacheable.
  • Good sub-goals are independently checkable, so failure is localised instead of discovered at the end. Over-decomposition is its own failure: twelve steps for a two-step task multiplies cost and error surface.
  • Re-plan on signal, not every turn: a sub-goal failing twice, an observation contradicting an assumption, or a budget that can no longer cover the plan. Re-planning eagerly produces thrash.

Reflection

  • A critic pass reviews the work against the goal and emits a concrete revision, which becomes context for the next attempt.
  • Reflection helps most when grounded in an external signal — a failing test, a schema violation, a diff. Ungrounded self-critique tends to praise its own output.
  • Cap reflection rounds; quality plateaus after one or two, then drifts.
Rule of thumb: plan when the task has structure you can name up front, react when it does not, and always keep a re-plan trigger. Combinations are catalogued in Agentic Design Patterns.

05 Memory and context

The transcript is working memory — and it grows quadratically in cost while getting harder to reason over.

Short-term: the transcript

  • Every thought, call, and observation is appended, so step t re-reads steps 1..t−1. Total prefill scales with the square of the step count.
  • Long transcripts degrade quality before hitting the hard limit: instructions get buried and stale results compete with fresh ones.
context growth over a run|ct| ≈ |c0| + Σi<t ( |ai| + |oi| ) tokensrun = Σt=1..T |ct| = O( T² · ō )

Compaction, long-term, episodic

  • Compaction: near the budget, summarize older turns into a state note — goal, decisions, established facts, files touched, open questions — and continue from that plus recent turns verbatim. Drop what the agent can cheaply re-derive; never drop a constraint stated once (Context Engineering).
  • Externalise state: notes, scratch files, a task list on disk act as unlimited memory, re-read on demand.
  • Semantic memory retrieves durable facts and preferences by relevance — memory as a retrieval problem; episodic memory stores summaries of past runs, which shortcut repeated work but propagate stale conclusions.
  • Every store needs a write policy and a forget policy; unbounded writes turn retrieval into noise.
Remember: context is a working set, not an archive. Keep it small and current; put everything else behind retrieval or on disk.

06 Multi-agent patterns

Several agents help when the task separates — parallel sub-tasks or genuinely different roles. They hurt when it does not.

Orchestrator and workers

A lead agent decomposes the goal, spawns workers with narrow briefs and fresh context windows, then integrates the results. The benefit is context isolation: each worker reads only what its sub-task needs, so a sweep across twenty sources never has to fit in one transcript. The cost is that the orchestrator sees only what workers report — a summary of a summary — so briefs and return formats must be tight.

Roles, review, and voting

  • Separate producer and reviewer roles; the reviewer's fresh context is what makes its critique worth more than self-reflection.
  • Pipelines of specialists (retrieve → draft → verify → format) trade flexibility for predictability and make each stage testable.
  • Run n independent attempts and aggregate — majority vote when answers are verifiable, a judge when they are open-ended (LLM-as-a-Judge). Gains come from diverse errors; identical prompts and shared context correlate the mistakes and the vote just amplifies them.
Default to one agent. Cost scales linearly with agents while accuracy gains flatten fast; add agents only for separable work or an independent reviewer with clean context.

07 Evaluating agents

You are scoring a trajectory, not a response — and the cheapest honest signal is whether the end state is correct.

Outcome first

  • Task success against a programmatic check of the final state: tests pass, the file has the right contents, the record exists. Binary, hard to fake, cheap.
  • Report pass@k beside single-attempt success to separate "cannot do it" from "does it unreliably". Hold out tasks like data — agents overfit a fixed suite fast.
reliability and repeated attemptspass@k = 1 − ( 1 − p )k scoreadj = success − λ · ( tokens + tool-time )

Then the path

  • Efficiency: steps, tokens, wall-clock, money per solved task — succeeding in 90 flailing steps is a different system from succeeding in 6.
  • Process quality: redundant calls, retry storms, malformed arguments, abandoned sub-goals. Classify the losses: the failure distribution tells you what to fix; the aggregate score does not.

08 Failure modes and safety

Long horizons multiply small error rates, and real actions turn mistakes into consequences.

Error compounding

If each step succeeds independently with probability p, an n-step task succeeds with probability pn: at 95% per step, twenty steps land near 36%. This is why verification and recovery matter more than raw capability — a check-and-retry that catches half the failures raises the effective p, and that compounds in your favour.

Why long horizons are hard Per-step reliability compounds — verification and retry bend the curve back

Loops, cost, and prompt injection

  • Repetition loops: the agent re-issues an action that already failed, because the failed attempt sits in context and still looks reasonable. Detect repeated (tool, arguments) pairs and say so explicitly.
  • Stalling and blowout: endless re-planning with no state change. Require observable progress and enforce hard caps on steps, tokens, time, and spend, with a graceful partial-result exit.
  • Any tool output — a page, an email, a file, a comment — is untrusted input that will be read as instructions if it is phrased like instructions.
  • The dangerous combination is untrusted content plus private data plus an outbound channel. Break one leg: fence untrusted text, scope credentials, allow-list egress, gate irreversible actions, apply least privilege, and log every call.

Design stance: assume the agent will be wrong sometimes and make wrongness cheap — reversible actions, sandboxes, confirmation on the irreversible, and a full log.

09 Pitfalls & what to remember

Pitfalls

  • Reaching for an agent when a workflow would do — if you can write the control flow, write it.
  • Tool sprawl: overlapping descriptions wreck selection accuracy long before the context limit does.
  • Swallowed errors and unbounded observations — one silent failure or one enormous result can end a run.
  • Multi-agent by default, and success-rate-only evals that cannot tell competence from brute force.
  • Trusting tool output: retrieved content is data, never instructions.

What to remember

  • Agent = model + loop + tools + memory, with autonomy over control flow — and autonomy is a dial.
  • ReAct interleaves reasoning and acting so each grounds the other; the thought also decides when to stop.
  • Tool quality dominates: schemas, parallelism, readable errors, bounded output, sandboxed execution.
  • Plan when structure exists, react when it does not, re-plan on signal, reflect against grounded feedback.
  • Context is a working set — compact it, externalise it, retrieve into it.
  • Score trajectories and cost, and remember that reliability compounds over long horizons.
