Computer Control

The most general tool an agent can have is a computer itself. A computer-control agent reads a screen, decides where to click and what to type, and drives real GUIs, browsers, and terminals the way a person would — no bespoke API required, and none of the guarantees one would give.

01 The task, and why it is hard

Given a goal in natural language and a stream of observations of a running machine, emit low-level actions — mouse, keyboard, navigation — until the goal is achieved. It is tool use where the tool is the whole desktop.

  • Why bother: most software exposes a UI and no usable API. Legacy line-of-business apps, internal dashboards, spreadsheets, sites behind logins. An agent that can drive the UI reaches all of it with one integration instead of hundreds.
  • What makes it different from ordinary tool use: the interface is not designed for a machine. Affordances are visual, state is implicit, results are asynchronous, and there is no schema, no error code, and no idempotency.
  • The observation is huge and mostly irrelevant. A screenshot is thousands of tokens of which a handful of pixels matter; a raw page can be tens of thousands of tokens of markup around one button.
  • Horizons are long. Real tasks are 15–50 actions. With per-step reliability p, end-to-end success decays as pn, so a 97%-per-step agent finishes a 30-step task barely a third of the time.
  • Actions are real. Unlike a sandboxed reasoning chain, a mis-click sends the email, empties the folder, or completes the purchase.
the control problemat = πθ( g, o≤t, a<t ) P(success) ≈ ∏t=1..n pt g = goal, o = observation, a = action
One idea: computer control converts a language problem into a partially observed sequential control problem. Everything difficult about it — grounding, horizon, recovery, safety — follows from that one change.

02 The perceive–plan–act loop

Capture an observation → decide the next action → execute it → wait for the interface to settle → capture again. Step through a small task below.

What happens on each turn

  • Perceive: screenshot and/or structured tree of the active window, usually downscaled to a fixed resolution so coordinates stay in one frame of reference.
  • Plan: the model updates its state — what has been done, what remains — and picks one action. Verbalising the expected result first is what makes error detection possible on the next turn.
  • Act: the runtime executes the action against the OS or browser. Failures here are ordinary software failures: the element moved, the click landed on an overlay, the page was still loading.
  • Settle and verify: wait for a stable frame, then compare what appeared against what was expected. Without this check, the agent happily continues from a state it never reached.
An agent operating a screen Each step: read the screen, choose a target, act
The loop is trivial; the state estimate is not. The agent must answer "am I where I think I am?" from pixels alone, every single turn — which is why an explicit expectation-then-check habit outperforms a longer plan.

03 Observation spaces

What exactly does the agent receive each turn? Four options, each trading generality against precision and token cost.

Pixels — the screenshot

  • A vision-language model reads the rendered image directly. Universal: it works on canvas apps, remote desktops, video players, and native software with no accessibility support.
  • Cost is set by patchification — the image becomes ⌈W/P⌉ · ⌈H/P⌉ visual tokens — and small text is lost when the screenshot is downscaled to fit.
  • The output must be a coordinate, which is the hardest thing to get right.

Accessibility tree — the semantic skeleton

  • The OS or browser already exposes a tree of elements with roles, names, values, states, and bounding boxes — built for screen readers, reusable by agents.
  • Actions become element references rather than pixels, which removes coordinate error entirely. But coverage is uneven: custom widgets, canvas-drawn UIs, and sloppy apps report almost nothing useful.

DOM / raw markup — precise but enormous

  • On the web the full DOM gives exact selectors and hidden attributes. It is also the most verbose option by an order of magnitude and includes elements that are invisible or off-screen.
  • Practical use always means pruning to interactive, visible nodes and stripping styles and scripts.

Set-of-marks — the hybrid that usually wins

  • Detect the interactive elements (from the tree, the DOM, or an element detector), draw numbered boxes on the screenshot, and pass both the annotated image and the numbered legend.
  • The model then selects an index, not a coordinate — the layout stays visible while the action space becomes discrete and verifiable. This is the standard recipe for browser agents.

04 Action spaces

Three levels of abstraction, and the choice constrains everything downstream: what the model must predict, what can be validated before execution, and how a failure is recovered.

Coordinates — the lowest common denominator

  • click(x, y), double_click, right_click, drag(x₁,y₁ → x₂,y₂), type(text), key("ctrl+s"), scroll(dx, dy), wait(ms), screenshot().
  • Works on anything, including remote desktops and games. Nothing can be validated in advance: (x, y) is either on the button or on the background.

Element references — the reliable middle

  • click(elem=17), fill(elem=3, "text"), select(elem=9, "May"). The runtime resolves the index to a real node and can refuse an invalid, invisible, or disabled target before anything happens.
  • Requires an element list, so it inherits whatever the accessibility tree or detector missed. Indices also change between frames — always re-index after the screen settles.

Code and API calls — skip the UI when you can

  • Let the agent write a short script or call a real endpoint: one deterministic action replaces twenty clicks, and it is testable, loggable, and re-runnable.
  • Hybrid policies do this by default and fall back to the GUI only where no programmatic path exists — the single biggest lever on both cost and reliability.

05 Grounding

Grounding is the mapping from a phrase — "the Search button", "the second row's checkbox" — to a concrete, actionable target on screen. It is the component that most often decides whether a run succeeds.

  • Coordinate regression asks the model to emit (x, y) directly from the image. It is scored by whether the predicted point lands inside the target's bounding box, which makes small controls disproportionately hard.
  • Referring-expression selection instead scores each candidate element against the phrase and picks the best — a ranking problem over a short list, which is far easier than regression over a continuous plane.
  • Resolution is a first-class hyperparameter. Downscale for token cost and you lose the label you needed; keep native resolution and every frame is expensive. Cropping to the relevant region, or a coarse-then-fine second look, is the usual compromise.
  • Ambiguity is common: three buttons say "Open", the label is an icon with no text, the target is off-screen and must be scrolled to first. A good policy resolves by context and position, and scrolls to search rather than guessing.
  • Grounding is a genuinely separate skill from planning. Many systems split them — a strong planner chooses what, a small specialised model chooses where — which is cheaper and measurably more accurate than one model doing both.

06 Training signals

Prompting a general model gets a surprising distance. Going further means training on trajectories — and the scarcity of good trajectories is the field's real bottleneck.

Behaviour cloning from trajectories

  • Collect sequences of (observation, action) from human demonstrations or from a stronger agent, and maximise the log-likelihood of the recorded action given the history. Simple, stable, and it teaches interface conventions no amount of text pretraining conveys.
  • Its known weakness is compounding distribution shift: the policy is only trained on states an expert visits, so its first mistake takes it somewhere it has never seen. Mitigations are the classic ones — collect corrections from the policy's own states, and deliberately include recovery trajectories.
  • Demonstrations are expensive, so pipelines synthesise them: script tasks with known solutions, mine screen recordings and tutorials into pseudo-actions, or replay a strong agent and keep only verified successes.

Reinforcement learning from task success

  • Give a reward only for a verified outcome — a file exists with the right contents, a form submitted, a database row changed — and optimise expected return. Execution-based verification is what makes the reward trustworthy; a model judging its own screenshot is not.
  • Add a step penalty so the policy prefers short routes, and shape lightly with subgoal checks to fight the sparse-reward problem on 30-step tasks. Credit assignment across such horizons is the core difficulty — see agentic RL.
  • Environments must be resettable and parallel: containers or VM snapshots restored between episodes, or the agent's own side effects contaminate the next rollout.
two objectivesBC: maxθ ∑(o,a) ∈ D log πθ( a | g, o≤t ) RL: maxθ 𝔼τ ∼ πθ [ R(τ) ] , R(τ) = 𝟙[verified success] − λ · steps
Clone first, then reinforce. Behaviour cloning teaches the interface cheaply; reinforcement learning teaches recovery and efficiency, which demonstrations almost never contain because experts rarely make the mistakes the policy will.

07 Evaluation, latency & cost

Screenshots make demos look wonderful. Only execution-verified task success on held-out tasks says anything.

Environments and metrics

  • The standard shapes: execution-verified desktop suites (a few hundred real tasks across a browser, file manager, editor, and office apps, each with a scripted checker), self-hosted web environments that clone common site types so runs are reproducible and side effects are contained, mobile UI task sets, and pure grounding datasets that only ask for the location of a named element.
  • Report at minimum: task success rate, steps taken versus a human reference, cost and wall-clock per task, and the failure taxonomy — grounding miss, wrong plan, unrecovered error, timeout, refusal.
  • Read leaderboards carefully. Step budgets, screen resolution, whether the agent got credentials or a code path, and self-reported versus independently re-run numbers all move results by more than most model differences. As of mid-2026, reported end-to-end success on a widely used ~370-task desktop suite ranges from roughly the low 60s to the mid 80s percent depending on harness, against a human baseline near 72% — where the first published systems in 2024 were around 12%.

Latency and cost accounting

  • Every step pays for a fresh observation. At ~1–2k visual tokens per frame plus the growing transcript, a 30-step task easily crosses six figures of input tokens — and the accumulated history, not the current screen, is usually the larger half.
  • Wall-clock is dominated by three terms: model latency, interface settle time, and the retries. Perceived speed improves most from fewer steps, not a faster model — which is the strongest argument for code actions.
  • Standard economies: cache the stable prefix, drop or downscale old screenshots and keep only their summaries, batch independent checks, and let a small model handle grounding while a large one plans.

A 90% agent at 40 steps and five minutes per task can be worth less than a 70% agent at 12 steps — because the failures are cheap to retry and the successes are cheap to produce.

08 Safety & containment

This is the one agent setting where the model's mistakes are indistinguishable from a user's — same clicks, same credentials, same consequences. Safety here is engineering, not prompting.

Irreversible actions

  • Classify actions before granting them: reversible (navigation, scrolling, reading), recoverable (edit a draft, move a file), and irreversible (send, pay, delete, deploy, grant access). Only the last class needs a gate, so the gate stays rare enough to be taken seriously.
  • Practical gates: an explicit confirmation showing what will happen to what, spend and rate caps enforced by the runtime, allow-listed domains and applications, and a preference for dry runs and drafts over direct execution.

Prompt injection through the interface

  • Every pixel and every DOM node is untrusted input. A page, a document, an email, an image, or a hidden element can contain text addressed to the agent — and a policy trained to follow on-screen instructions is exactly the wrong prior.
  • The dangerous combination is access to sensitive data, exposure to untrusted content, and an outbound channel. Remove any one of the three and exfiltration stops being possible.
  • Defences that hold up: keep observations strictly as data in the prompt, never as instructions; require the goal to come only from the user turn; confirm outbound actions (send, upload, post, navigate off the allow-list); and run injection-attempt suites as a standing regression test rather than a one-off audit.

Sandboxing

  • Run in a disposable VM or container with a snapshot to restore, a scoped network, a separate browser profile, and least-privilege credentials — short-lived, per-task, and never the operator's own session.
  • Log every observation and action for replay. Post-hoc debugging of a GUI agent without a frame-by-frame trace is guesswork.
Containment beats correctness. Assume the policy will occasionally do the wrong thing; design so that the worst wrong thing available to it is cheap to undo.

09 Pitfalls & what to remember

Pitfalls

  • Judging by the demo. Cherry-picked recordings hide the tail; only execution-verified success on held-out tasks counts.
  • Not measuring grounding separately. A planning problem and a targeting problem look identical in an end-to-end failure log and need opposite fixes.
  • Clicking where an API exists. Twenty clicks that could have been one call: slower, costlier, and far more failure-prone.
  • No settle-and-verify step. Acting on a stale frame produces the most confusing failures in the whole field.
  • Unbounded loops. Without step, time, and spend caps, a stuck agent will scroll a page forever at full token price.
  • Treating screen text as instructions. The default assumption must be that some of it is hostile.
  • Testing with real credentials. Evaluate in a snapshot-restorable sandbox, always.

What to remember

  • Observation space (pixels · accessibility tree · DOM · set-of-marks) and action space (coordinates · element index · code) are the two design choices that determine everything else.
  • The loop is perceive → plan → act → settle and verify; the missing fourth stage is where most agents quietly fail.
  • Grounding is the dominant per-step error, and per-step error compounds as pn over a 15–50 step horizon.
  • Train by cloning trajectories first, then reinforce against verified task success with a step penalty.
  • Score on success, steps, and cost together — and contain the blast radius before optimising any of them.
  • Neighbours: agents, agent skills for packaging reusable procedures, agentic RL, design patterns, and vision-language models.
The whole page in one line: pick the most structured observation and the highest-level action the environment allows, verify after every step, and sandbox as if the agent will be talked into something — because eventually it will be.
