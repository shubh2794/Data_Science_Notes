Multi-Agent Systems

When a single LLM agent hits a wall — too many tools, too much context, tasks that need independent validation — the answer is not a bigger model but more agents with smaller jobs. Multi-agent systems split work across specialized agents that coordinate, communicate, and compose their outputs. The design space mirrors distributed systems: topologies, message passing, failure handling, and the eternal question of whether the coordination cost is worth the gain.

Agentic AI Multi-Agent Coordination Architecture

01 When one agent isn't enough

The default is a single agent. You add agents the way you add microservices — only when a measured problem demands it, and never because the architecture diagram looks impressive.

  • Tool sprawl. Past roughly a dozen similar-sounding tools, selection accuracy drops. One agent with 40 tools picks the wrong one more often than four agents with 10 each, because the router is now a simple dispatch, not a 40-way classification buried in the prompt.
  • Context pollution. A long research trace fills the window with irrelevant detail before the writing step begins. Splitting into a researcher and a writer gives each a clean context — the real win of multi-agent, not "more brains."
  • Independent validation. A single agent reviewing its own output is weak on factual errors (same weights, same blind spots). A second agent with different instructions and a different context is a genuinely different critic. See LLM-as-a-judge.
  • Separable tasks. If the work decomposes into chunks that can run in parallel with no shared intermediate state, multiple agents reduce wall-clock time from the sum to the maximum of the branches.
  • The microservices analogy. Each agent should be independently testable, reusable across workflows, and have a bounded responsibility. If you would not split it into a separate service, do not split it into a separate agent.
The starting rule: build a single agent first. Add a second only when you can name the specific failure — tool confusion, context overflow, missing validation — that the second agent fixes. Measure cost per solved task before and after.

How agents are wired together determines who talks to whom, who decides, and where the bottleneck sits. Four topologies cover most real systems.

03 The CWD model — Coordinator, Worker, Delegator

A role-based decomposition that assigns every agent in a multi-agent system one of three jobs: coordinate, work, or delegate.

  • Coordinator. Manages the overall workflow: receives the goal, breaks it into tasks, tracks progress, decides when the job is done. Holds the "big picture" context and the success criteria. Analogous to a project manager.
  • Worker. A specialized executor that receives a narrow brief and returns a result. Workers are domain experts — one writes code, another searches the web, a third reviews for security. They should not need to know about each other.
  • Delegator. An intermediary that balances workloads: routes tasks to the best available worker, handles retries when a worker fails, and can reassign on the fly. Separating delegation from coordination lets the coordinator stay focused on the goal.

Information flow

  • Downward flow carries tasks, priorities, constraints, and deadlines — everything a worker needs to start.
  • Upward flow carries progress updates, results, utilization reports, and failure signals — everything the coordinator needs to decide next.
  • Bidirectional flow is essential: a worker that cannot ask a clarifying question will guess, and a coordinator that cannot interrupt a worker will wait for a stale result.

Design principles

  • Separation of concerns — each role has a single responsibility. A coordinator never executes a task; a worker never decides the plan.
  • Hierarchical organization — coordinators can nest: a top-level coordinator delegates to sub-coordinators that each manage a cluster of workers.
  • Dynamic resource allocation — the delegator can spin up new workers, shut down idle ones, or reassign workers between sub-teams at runtime.
  • Fault tolerance through redundancy — critical workers can be duplicated; the delegator routes to whichever responds first or retries on failure.
  • Runtime role reassignment — in advanced systems, a worker can be promoted to coordinator if the original coordinator fails, enabling graceful degradation.
The CWD model is not a framework — it is a vocabulary. When you describe your system in terms of who coordinates, who works, and who delegates, gaps in the design become obvious: "who retries this?" or "who notices the worker is stuck?"

04 Communication patterns

Agents that cannot communicate effectively are just parallel single agents. The communication layer determines latency, coupling, and how much context each agent actually receives.

Synchronous message passing

  • Agent A calls Agent B and blocks until B responds. Simple to reason about, easy to debug, but the caller is idle while waiting. Works well for short, critical handoffs (e.g., "validate this output before I continue").
  • In practice: function calls between agents in the same process, or request/response over HTTP.

Asynchronous message passing

  • Agent A sends a message and continues working. B processes it later and sends a result back (or to a third party). Higher throughput, but harder to debug because ordering is not guaranteed.
  • Message brokers and event buses — middleware like a task queue sits between agents, decoupling senders from receivers. Agents publish events ("research complete") and subscribers react. This is the pattern behind systems that need to scale beyond a handful of agents.
  • Agent-to-agent protocol — a structured envelope that includes sender, recipient, message type (request / response / broadcast / error), payload, and a correlation ID so responses can be matched to requests.

Shared memory / blackboard

  • All agents read from and write to a shared data structure — a "blackboard." No direct messages; agents poll or subscribe to changes. Classic in AI planning (1980s blackboard architectures) and revived in modern artifact-passing systems.
  • Advantage: any agent can see any result without an explicit handoff. Disadvantage: race conditions, stale reads, and "who wrote this?" attribution problems.

Structured message formats

  • Free-text messages between LLM agents are fragile — one agent's verbose output floods another's context. Enforce structure: JSON payloads with typed fields, explicit task IDs, and length limits.
  • The instruction formatting problem: a coordinator's brief to a worker is itself a prompt. All the rules of context engineering apply — be specific, include success criteria, state what not to do.
The choice between sync and async mirrors the choice in distributed systems: sync is simpler until it blocks, async scales until you lose track of what happened when. Start synchronous; move to async only when latency demands it.

05 Task allocation and delegation

Decomposing a goal into tasks and matching tasks to agents is half the problem. Get it wrong and agents duplicate work, starve for input, or produce outputs nobody asked for.

Decomposition strategies

  • Static decomposition. You predefine the task graph — which agents handle which subtasks in which order. Deterministic, testable, but inflexible if the input varies widely.
  • Dynamic decomposition. A coordinator agent analyzes the goal at runtime and generates subtasks. More flexible, but the coordinator can produce vague or overlapping briefs. This is the orchestrator-workers pattern from agentic design patterns.

Assignment mechanisms

  • Direct assignment. The coordinator knows each worker's capabilities and assigns directly. Simple, but the coordinator must maintain an accurate capability registry.
  • Contract net protocol. The coordinator broadcasts a task announcement; workers bid based on their suitability and availability; the coordinator awards the contract to the best bidder. Classic multi-agent protocol (Smith, 1980) that decentralizes capability matching.
  • Auction-based allocation. Tasks are auctioned; workers bid tokens, time estimates, or confidence scores. Useful when tasks have different costs and workers have different strengths.
  • Capability matching. Each worker publishes a capability descriptor (tools available, domains covered, context window size). A router matches task requirements to capabilities, often using embedding similarity or structured metadata.

Load balancing

  • In systems with many workers, a naive round-robin wastes capacity. The delegator (in CWD terms) should track worker utilization and route to the least loaded agent — or the one whose capability best matches, weighted by current queue depth.
  • Timeout-based reassignment: if a worker does not respond within a deadline, the delegator reassigns the task to another worker and discards the late response.
The contract net protocol is from 1980, but the problem it solves — "who should do this?" — is exactly the problem every orchestrator agent re-invents. Name the mechanism you are using; if you cannot name it, you do not have one.

06 Shared state and context management

Context isolation is the primary benefit of multi-agent systems — and also the primary headache. Each agent gets a clean window, but now the results need to travel between windows without losing meaning.

Artifact passing

  • The simplest pattern: Agent A produces an artifact (a document, a code file, a data table) and passes it as input to Agent B. The artifact is the interface — typed, inspectable, and cacheable.
  • Keep artifacts outside the message itself when they are large. Pass a handle (file path, object ID) and let the receiving agent fetch what it needs, rather than stuffing the full content into a prompt.

Shared memory stores

  • A key-value store, vector database, or shared scratchpad that all agents can read and write. Useful for accumulating partial results — e.g., a research agent writes findings, a writing agent reads them, a fact-check agent annotates them.
  • Consistency matters: if two agents write to the same key, you need a policy — last-writer-wins, versioning, or conflict resolution. In practice most LLM multi-agent systems are small enough that explicit ordering avoids the issue.

Context isolation as the feature

  • Each agent sees only what it needs. A security-review agent does not see the marketing copy; a code-generation agent does not see the project-management discussion. This reduces distraction, shrinks token cost, and limits the blast radius of a confused agent.
  • The flip side: information that should cross boundaries must be explicitly routed. A common failure is an agent that lacks context it needed because nobody forwarded it.

Persistence across runs

  • Within a single run, in-memory state suffices. Across runs, agents need durable state: a database, a file system, or a conversation history store. This is especially important for long-running tasks that resume after interruption.
  • State serialization must capture not just data but agent role assignments, the current task graph, and which tasks are complete — enough to reconstruct the system state from scratch.
If your agents share everything, you have one agent with extra overhead. If they share nothing, they cannot collaborate. The art is choosing the minimal interface — the smallest artifact or message — that lets each agent do its job without polluting the others' context.

07 Debate, voting, and adversarial collaboration

Multiple agents arguing, critiquing, and voting can improve output quality — but only when the disagreement carries real information. On subjective tasks, agents converge to polite agreement within two rounds.

Multi-agent debate

  • Structure: k agents independently answer a question, then read each other's answers and revise, for several rounds. A judge (or majority vote) selects the final answer.
  • When it works: factual questions with checkable answers (math, logic, code correctness). Debate surfaces errors because a second agent spots what the first missed, especially when the error is in reasoning rather than knowledge.
  • When it fails: subjective or open-ended tasks. Agents quickly converge because LLMs are trained to be agreeable. Persona labels ("you are a skeptic") add style but rarely sustain genuine disagreement past round two.

Majority voting

  • Run the same task k times (same or different agents) and take the majority answer. Accuracy improves if and only if errors are approximately independent — same model, same prompt, same blind spot makes voting useless.
  • Diversity helps: vary the model, the prompt, or the temperature across samples. The gain from voting is bounded by the correlation between errors.
majority vote accuracy (independent errors)P(correct) = ∑j > k/2 C(k, j) · pj · (1 − p)k − j

Actor-critic

  • One agent acts (generates a draft, writes code, proposes a plan); a second agent critiques against an explicit rubric and returns structured feedback. The actor revises. This is the evaluator-optimizer pattern from design patterns with the roles split across agents.
  • The critic is more effective when it has information the actor lacked: test results, retrieval output, a security checklist, or a different model entirely.

Red-team / blue-team

  • A specialized adversarial pattern: the blue-team agent produces output; the red-team agent actively tries to find flaws, exploits, or failure cases. Used in security review, content safety, and robustness testing.
  • Unlike generic debate, the red-team agent has an explicit adversarial objective, which sustains disagreement. See LLM security for the broader context.
Debate and voting spend tokens on diversity of perspective. The return is high when errors are independent and checkable, and near zero when agents share the same training data, the same biases, and the same inability to verify. Always ask: "does the second opinion carry information the first lacked?"

  • Actor frameworks (Ray, Orleans, Akka) treat each agent as an independent unit of computation with its own state and mailbox. They solve the distributed execution problem but leave the LLM-specific concerns (prompt management, tool routing, context windows) to you.
  • Workflow engines manage the agent graph: which agent runs next, what state it receives, where checkpoints go. LangGraph and similar tools sit here.
  • Convention-over-configuration frameworks like CrewAI trade flexibility for speed of setup — useful for prototyping, limiting when the task does not fit the convention.

Evaluate frameworks on three axes: debuggability (can you see what each agent received and returned?), controllability (can you override a routing decision?), and cost visibility (does it show you token spend per agent?). A framework that hides these is a demo tool, not a production tool.

09 Failure modes and scaling

Multi-agent systems inherit all single-agent failure modes and add new ones: partial failures, coordination overhead, and cost that scales faster than capability.

Partial failures

  • One worker fails (timeout, hallucination, refusal) while others succeed. The coordinator must decide: retry, skip, substitute, or abort. Without an explicit policy, partial failures become silent data loss.
  • Timeout and fallback. Every agent call needs a deadline. When it expires, the delegator either retries with a different worker, falls back to a simpler strategy (e.g., a cached result), or escalates to the coordinator.
  • Poison messages. A malformed output from one agent corrupts the next agent's input. Validate artifacts at every handoff — schema checks, length limits, required fields.

Coordination overhead

  • Every message between agents costs tokens and latency. A system with n agents in a flat topology sends O(n2) messages per round. At $0.01 per message, 10 agents debating for 5 rounds costs 500 messages — before any actual work.
  • The coordination tax: a multi-agent system that spends more tokens on routing, summarizing, and status updates than on the actual task has negative value. Track the ratio.
coordination cost in flat topologymessages per round = n · (n − 1) total messages = n · (n − 1) · r (r = rounds)

Cost scaling

  • Multi-agent runs are expensive by construction: each agent is a full LLM call (or many). A 5-agent system with 3 rounds each is at minimum 15 LLM calls per task, plus coordination overhead.
  • Measure cost per solved task, not just success rate. A multi-agent system that solves 5% more tasks at 10x the cost is usually a loss.

Swarm patterns

  • At large scale (dozens to hundreds of agents), top-down coordination breaks. Swarm patterns use local rules and emergent behavior: each agent follows simple heuristics (respond to nearby signals, share findings with neighbors) and global order emerges without a central coordinator.
  • Swarms are more resilient (no single point of failure) but harder to steer and debug. They work best for search and exploration tasks where the goal is coverage, not precision.

Automated agent design

  • Meta-agents that design agent topologies: given a task description, a meta-agent proposes which agents to create, what roles they play, and how they communicate. Still experimental (as of mid-2025), but the idea is sound — the topology is a hyperparameter, and hyperparameters can be searched.
  • The risk: automated design can produce complex topologies that work on benchmarks and collapse in production. Human review of the generated topology remains essential.
The most common failure mode in multi-agent systems is not a crash — it is coordination overhead exceeding the value of collaboration. If agents spend more tokens talking to each other than doing useful work, collapse back to fewer agents with better prompts.

10 Pitfalls & what to remember

Pitfalls

  • Multi-agent as a first resort. Most "multi-agent" problems are context problems. If one agent fails because its window is polluted, try summarizing before splitting into five agents.
  • Vague briefs. A coordinator that tells a worker "do the research part" has not delegated — it has deferred. The brief must include scope, format, constraints, and success criteria, just like a good prompt.
  • No failure policy. If you cannot answer "what happens when Worker B times out?" before deployment, the system is not production-ready.
  • Persona without purpose. Giving agents names and backstories ("you are Dr. Smith, a senior architect") adds flavor but rarely improves output. Roles should define what tools and context the agent gets, not just a persona label.
  • Debate on subjective tasks. LLMs converge to agreement quickly. Multi-round debate on open-ended questions mostly produces expensive consensus.
  • Ignoring cost. Every agent is a full LLM call. A 5-agent, 3-round debate is 15+ calls minimum. Track cost per solved task, not just accuracy.
  • Shared-everything state. If all agents see all state, you have a single agent with extra overhead and race conditions.

What to remember

  • The case for multi-agent is context isolation, parallel execution, and independent validation — not "more agents = smarter."
  • Choose the topology that matches the task: pipeline for sequential refinement, hub-spoke for fan-out/fan-in, hierarchical for nested sub-problems, flat for genuine debate.
  • The CWD vocabulary — coordinator, worker, delegator — makes gaps visible: who retries? who notices a stuck worker? who decides "done"?
  • Communication is the bottleneck. Structured messages, minimal interfaces, and explicit handoff contracts keep coordination cost below the value of collaboration.
  • Measure cost per solved task. A multi-agent system that solves 5% more tasks at 10x the cost is a regression.
  • Neighbours: the agent loop these systems compose, design patterns for single-agent structure, agent skills for reusable capabilities, context engineering for managing what each agent sees, and LLM security for the trust boundaries multi-agent introduces.
The whole page in one line: add agents only when a measured failure demands it, wire them with the simplest topology that works, keep the communication interface minimal, and always measure cost per solved task — not success alone.
