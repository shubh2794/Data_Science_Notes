Data Warehousing, Lakes & Lakehouses

Analytical storage is built for a different question than application databases: not "fetch this one order" but "sum revenue by region over three years". That single shift — few queries scanning many rows and few columns — explains columnar storage, dimensional models, MPP engines, and partition pruning. Data lakes then relaxed the warehouse's rigidity by storing open files on cheap object storage, and lakehouses put warehouse guarantees (ACID, schema, time travel) back on top of those files.

02 Dimensional modelling: facts, dimensions, and grain

A dimensional model splits the world into events you measure (facts) and context you slice by (dimensions).

  • Declare the grain first. "One row per order line" or "one row per customer per day" — every other design decision follows, and mixing grains in one fact table is the root of most double-counting bugs.
  • Fact tables are long and narrow: foreign keys to dimensions plus numeric measures. They grow with activity and are usually the biggest tables by far.
  • Dimension tables are short and wide: descriptive attributes (product name, category, brand, colour) used in WHERE and GROUP BY. They change slowly — see slowly changing dimensions.
  • Surrogate keys (warehouse-generated integers) decouple facts from source-system ids and let one natural key have several historical versions.

04 Columnar storage: read only what you need

A row store keeps each record's fields together; a column store keeps each column's values together. An analytical query that touches 3 of 40 columns reads ~7% of the bytes in a column store — before compression makes it smaller still.

bytes scanned for a query touching column set Q over N rowsrow store: B ≈ N · ∑c ∈ all columns wc column store: B ≈ N · ∑c ∈ Q wc / rc wc = width of column c, rc = its compression ratio with min/max pruning over row groups (zone maps)B ≈ f · N · ∑c ∈ Q wc / rc f = share of row groups whose [min, max] overlaps the predicate

Pick the columns a query uses, set a date predicate, and compare layouts. Then toggle whether the table is clustered by date — pruning only works when each row group covers a narrow date range.

05 Encodings and compression

A column holds one type with a narrow range of values, so it compresses far better than interleaved rows — often 5–10× overall, and much more on sorted, low-cardinality columns.

  • Late materialisation and vectorised execution: engines evaluate predicates directly on encoded data (compare dictionary codes, skip whole runs) and process batches of thousands of values per CPU instruction loop, stitching full rows together only for the final result.
  • Open file formats carry this design to the lake: Parquet and ORC split a file into row groups/stripes, store each column chunk separately with its own encoding, and keep min/max statistics in a footer so readers can skip whole chunks.

06 MPP: massively parallel processing

  • Shared-nothing MPP: rows are spread across many nodes, each with its own CPU, memory, and (originally) disk. A query plan runs as parallel fragments on every node; partial results are exchanged and combined — the same scatter/shuffle/gather as MapReduce, but pipelined and SQL-planned.
  • Distribution key. Rows are hash-distributed on a column. A join on that column is co-located (no data movement); a join on anything else forces a redistribute or broadcast. Small dimensions are often replicated to every node.
  • Skew in the distribution key (one giant customer) leaves one node doing most of the work — query time is the slowest node's time.
  • Separation of storage and compute is the defining modern shift: data lives in durable object storage; stateless compute clusters cache hot data on local SSD and can be resized, paused, or multiplied independently. Many clusters can read the same data without copying it.

07 Partitioning and clustering

  • Partitioning physically separates data by a column's value (usually a date): …/dt=2026-11-16/. A query with WHERE dt = … never opens other partitions — partition pruning. It is also the natural unit of idempotent loads and retention deletes.
  • Clustering / sort keys order data within partitions so that row groups have tight min/max ranges on frequently filtered columns, enabling the zone-map skipping in the viz above. Multi-column techniques (Z-order, Hilbert curves) interleave several columns' bits so that filters on any of them prune reasonably well.
  • Over-partitioning is the common failure: partitioning by a high-cardinality column (user id, or by hour on a small table) creates millions of tiny files. Per-file overhead (listing, opening, footer reads, planning) then dominates. Aim for files in the hundreds of MB and partitions with at least a few such files.
  • Choose by query pattern: partition on the coarse column almost every query filters on (date); cluster on the next most selective filters (customer, region); leave the rest to columnar scanning.
Diagnostic: after a query, compare "bytes scanned" to table size. If a selective query scans most of the table, pruning failed — the predicate is on an unclustered column, wrapped in a function (WHERE DATE(ts) = … on a table partitioned by ts may not prune), or type-mismatched.

08 Cloud warehouses

  • Managed, elastic, columnar MPP on object storage. You load data and write SQL; the service handles storage layout, statistics, replication, and scaling.
  • Pricing models shape behaviour. Pay-per-bytes-scanned rewards partitioning, clustering, and never running SELECT *; pay-per-compute-time rewards right-sizing clusters and suspending them when idle. Know which one you're on before writing a dashboard that refreshes every minute.
  • Workload isolation: separate compute pools for ELT, BI dashboards, and ad-hoc data science, so a heavy backfill can't starve the CEO's dashboard. Auto-scaling adds clusters under concurrency spikes.
  • Result and materialised-view caching serve repeated queries without rescanning; materialised views are incrementally maintained aggregates — fast, but they cost storage and refresh compute.
  • Semi-structured columns (JSON/variant types) let raw events land without upfront modelling while remaining queryable — blurring the line toward the lake.

09 Data lakes: schema-on-read over open files

A data lake stores data as files in cheap object storage, in open formats, in whatever shape it arrives. Structure is imposed by the reader at query time, not by the writer at load time.

Why plain lakes became swamps

  • No atomic commits. A job writing 500 files that dies at file 300 leaves readers seeing a partial table. Two concurrent writers can interleave files.
  • No updates or deletes. Object storage files are immutable; changing one row means rewriting its files by hand. Privacy-driven deletion requests become multi-day projects.
  • Table = directory listing. Discovering files by listing prefixes is slow at millions of objects, and the "schema" lives in an external catalog that can disagree with the files.
  • Small files from streaming and frequent appends degrade every reader.
  • No governance by default: nobody knows what a folder contains, who owns it, or whether it's current. See Data Quality & Governance.

10 Lakehouses: table formats bring ACID to object storage

The fix was not a new storage system but a metadata layer: a table is defined by a log or tree of metadata files that lists exactly which data files belong to each version. Readers never list directories; writers commit by atomically publishing a new version.

  • ACID on object storage. Atomicity: a version is either published or not. Isolation: snapshot isolation (and serialisable for some operations) via optimistic concurrency — writers read version n, write new files, and try to commit n+1; if someone else committed first, they check for conflicting changes and retry.
  • Time travel. Old versions stay addressable until their files are cleaned up: SELECT … VERSION AS OF 41 or TIMESTAMP AS OF '2026-11-01'. Use it to reproduce a training set exactly, audit a change, or roll back a bad write.
  • Schema evolution (add/rename/reorder columns via metadata, without rewriting files) and, in Iceberg, partition evolution — change from monthly to daily partitioning without rewriting history; queries plan across both layouts.
  • Row-level updates come in two flavours, below. Either way, unreferenced files must be expired (VACUUM, expire-snapshots) to control storage cost — which also ends time travel to those versions.
  • Interoperability layers now let one physical table be read as more than one format, and open catalogs expose these tables to many engines (Spark, Flink, Trino, warehouses) at once.

12 Takeaways

  • Analytics = few columns, many rows. Columnar storage + compression + min/max pruning cut bytes scanned by orders of magnitude.
  • Model dimensionally: declare the grain, keep facts narrow and additive, conform shared dimensions, prefer star over snowflake.
  • Partition coarse, cluster fine, avoid tiny files; check bytes-scanned to confirm pruning.
  • MPP cost is data movement: co-locate or broadcast joins, watch distribution skew; separate storage from compute.
  • Lakes gave flexibility and open formats but lost transactions and governance; lakehouse table formats restore ACID, schema enforcement, upserts, and time travel via an atomically committed metadata layer.
  • Pipelines that feed these stores: ETL Pipelines, Stream Processing; compute that reads them: Apache Spark, SQL; ML-facing layer: Feature Stores; physical substrate: Distributed Storage.
