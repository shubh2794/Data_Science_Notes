ETL Pipelines

Every model, dashboard, and feature table sits at the end of a pipeline that extracts data from source systems, transforms it into a usable shape, and loads it somewhere queryable. The code is rarely hard. What makes pipelines hard is that they run forever, on a schedule, against sources that change — so the properties that matter are operational: idempotency, incrementality, recoverability, and the ability to tell when the output is wrong.

01 ETL vs ELT

The letters are the same; the order decides where the compute lives and whether raw data is kept.

ETL (transform, then load)ELT (load raw, transform in place)
Where transforms runA separate engine (Spark job, custom service) before the targetInside the warehouse/lakehouse, usually as SQL models
Raw data kept?Often not — only the transformed result landsYes — a raw/bronze layer is the replayable source of truth
Reprocessing after a logic bugRe-extract from sources (which may have changed or expired)Re-run the SQL over the retained raw layer
Good fitPII must be masked before landing; heavy non-SQL transforms (parsing, ML scoring); constrained targetsCheap elastic warehouse compute; analysts own the transforms; frequent logic changes
RiskLost history; transform engine is a bottleneckRaw layer becomes a swamp; warehouse bill grows with every re-run
  • Most modern stacks are layered ELT: raw (exact copy of source, append-only) → staged/cleaned (typed, deduplicated, conformed) → marts (business-level facts and dimensions, see Data Warehousing). The same idea is often called bronze/silver/gold.
  • Keep the raw layer. Storage is cheap; the ability to rebuild every downstream table after a bug is priceless.

02 Batch orchestration: DAGs and schedulers

A scheduler runs a directed acyclic graph of tasks: each task starts only when its upstreams succeed. The scheduler — not your code — owns retries, timeouts, concurrency, and history.

ConceptWhat it meansWhy it matters
Task / operatorOne unit of work: run a query, call an extract, trigger a Spark jobThe unit of retry and of logging
DependencyEdge A → B: B waits for AEncodes data dependencies explicitly, not by timing
Logical date / data intervalThe slice of data a run is responsible for (e.g. 2026-11-16 00:00 → 2026-11-17 00:00), distinct from when it actually executesMakes runs reproducible and backfills possible
Retries with backoffRe-attempt a failed task N times, waiting longer each timeAbsorbs transient failures (timeouts, throttling) — only safe if the task is idempotent
Sensor / data-aware triggerWait for an upstream file, partition, or table update rather than a clock timeStops "ran at 2 a.m. on yesterday's half-written data"
SLA / timeoutAlert if a task or the whole DAG hasn't finished by a deadlineLate data is a failure mode even when nothing errors
  • Schedulers in this family (Airflow-style DAG-as-code, asset-oriented orchestrators, and managed cloud equivalents) differ in emphasis — task-centric vs data-asset-centric — but share this vocabulary. Asset-centric tools model "table X depends on table Y" directly and trigger when Y's partition materialises.
  • Keep the orchestrator thin. It should call compute (warehouse SQL, Spark, containers), not perform heavy processing inside its own workers.

03 Idempotency: the property everything else depends on

A pipeline task is idempotent if running it once or many times for the same input interval leaves the target in the same state. Retries, reruns, and backfills are all safe exactly when this holds.

idempotent load for a data interval prun(p) ∘ run(p) = run(p) target state after k ≥ 1 runs = target state after 1 run three standard ways to achieve itoverwrite partition: DELETE WHERE dt = p; INSERT … WHERE dt = p (atomically) merge / upsert: MERGE INTO t USING s ON t.key = s.key WHEN MATCHED UPDATE WHEN NOT MATCHED INSERT write-then-swap: write to t__staging, validate, atomically rename/swap into t
  • The classic bug: INSERT INTO t SELECT … WHERE dt = '{{ logical_date }}'. It works on the first run. On a retry after a partial failure, or a rerun to fix upstream data, it appends a second copy and every downstream sum doubles.
  • Parametrise by the data interval, never by now(). A task that reads "the last 24 hours" relative to wall-clock gives different answers on retry and cannot be backfilled.
  • Atomic publication. Readers should see either the old partition or the new one, never a half-written mix. Lakehouse table formats and warehouse transactions give you this; raw file writes to object storage do not (see Transactions (ACID)).
  • Side effects (sending emails, calling a payment API) are not idempotent by default. Guard them with an idempotency key recorded in a table, or move them out of the pipeline.

04 Backfills and reruns

  • A backfill runs the pipeline for past intervals: a new table needs two years of history, or a logic fix must be applied retroactively. If tasks are interval-parametrised and idempotent, a backfill is just "run for each p in [start, end]".
  • Partition-at-a-time design makes backfills parallel and resumable — 730 independent daily runs, any of which can fail and retry alone — instead of one monolithic job that must restart from scratch.
  • Dependencies across time. Tasks that read their own previous output (running totals, SCD Type 2, sessionisation) must run in order; mark them as depending on the previous interval so the scheduler serialises them.
  • Throttle. A backfill can launch hundreds of concurrent queries against a production source database. Cap concurrency, read from replicas or the raw layer, and schedule outside peak hours.
  • Downstream propagation. Fixing a staging table doesn't fix the marts built from it. Lineage (§10) tells you everything that must be re-run, in topological order.
Operational rule: if you can't confidently answer "what happens if I run yesterday's job again right now?", the pipeline isn't production-ready.

05 Incremental loads

Re-copying an entire source every night stops scaling at some point. Incremental strategies move only what changed — and each one has a characteristic way of missing data.

StrategyHowCatches deletes?Failure mode
Full refreshCopy everything, replace targetYesCost and source load grow with table size; fine for small dimensions
Append-only by key/timeCopy rows with id or created_at beyond the last loaded valueNoMisses updates to existing rows
High-watermark on updated_atCopy rows where updated_at > last watermarkNo (unless soft-deleted)Late-committing transactions, clock skew, and rows updated without touching the column are silently skipped
Change data captureRead the database's change logYesOperational complexity; log retention limits how long a consumer can be down (§06)
high-watermark extraction with a safety overlapextract { r : wm − δ < r.updated_at ≤ wm′ } wm′ = max updated_at observed (or extraction start time) then MERGE on primary key — the overlap δ re-reads a little, and MERGE makes the re-read harmless
  • The overlap δ exists because a transaction can start before the previous extract, commit after it, and carry an updated_at older than the stored watermark. Without overlap + MERGE, that row is lost forever.
  • Periodically reconcile: compare counts or checksums between source and target for a sample of partitions, and schedule an occasional full refresh to repair drift.

06 Change data capture (CDC)

Databases already record every change in a write-ahead or binary log for their own replication. Log-based CDC tails that log and turns it into a stream of change events.

CDC methodMechanismTrade-off
Log-basedRead the transaction log (WAL, binlog, redo log) via a replication slot or equivalentCaptures every insert/update/delete in commit order with low source overhead; needs log access and careful slot management
Trigger-basedDatabase triggers write each change into an audit tableWorks anywhere; adds write latency to every transaction
Query-basedPoll with a high-watermark (§05)Simplest; misses deletes and intermediate states
shape of a change event{ op: c | u | d, key: {id: 42}, before: {…} | null, after: {…} | null, source: {lsn, txid, ts_ms} }
  • Bootstrap = snapshot + stream. Take a consistent snapshot, note the log position at that instant, then apply changes from exactly that position. Getting this hand-off wrong causes duplicates or gaps.
  • Ordering is per key, not global. Changes are usually published to a durable log partitioned by primary key (see Stream Processing), so all events for one row stay in order. Apply them with MERGE using the log sequence number to discard stale replays.
  • The retention trap. A stalled consumer holding a replication slot can make the source database retain log segments until its disk fills — a CDC outage that takes down production. Alert on slot lag.
  • Schema changes in the source (a renamed column) flow straight into the change stream. This is where data contracts (§08) earn their keep.

08 Data contracts

Most pipeline breakages start upstream: a product team renames a column, changes units, or starts emitting nulls, with no idea that a model depends on it. A data contract makes that dependency explicit and enforceable.

  • What a contract specifies: schema (names, types, nullability), semantics (units, enumerations, what a row means), quality expectations (uniqueness, ranges, freshness), delivery SLA, an owner, and a versioning and deprecation policy.
  • Where it's enforced: in the producer's CI (a schema change that breaks the contract fails the build), at ingestion (reject or quarantine non-conforming records), and in a schema registry for event streams.

  • Write–audit–publish. Write the new partition to a staging location or branch, run data tests against it, and only then atomically publish. A failed audit leaves consumers on yesterday's good data instead of today's bad data — fail closed.
  • Distinguish blocking tests (duplicate primary keys, broken joins) from warning tests (a 15% volume dip). Alert fatigue from non-blocking noise is how real failures get ignored.
  • For distribution-level checks on inputs and features, see Data Quality & Governance and Monitoring & Drift.

10 Lineage and observability

  • Lineage is the graph of which datasets (and which columns) are derived from which. Table-level lineage answers "what breaks if this source is late?"; column-level lineage answers "which dashboards use this PII field?" and "which models consume the column being renamed?".
  • Collection: parse SQL to extract input/output tables and columns, emit lineage events from the orchestrator and compute engines on every run, and store them in a catalog. Hand-maintained lineage diagrams are stale within weeks.
  • Impact analysis before a change and root-cause analysis after an incident are the two payoffs: walk the graph downstream to notify consumers, upstream to find the first broken node.

11 Takeaways

  • Prefer layered ELT and keep the raw layer — it makes every bug recoverable.
  • Idempotency first: parametrise by data interval, overwrite partitions or MERGE, publish atomically. Retries and backfills are only safe on top of it.
  • Incremental loads leak at the edges: overlap the watermark and MERGE; use log-based CDC when deletes and every intermediate state matter; watch replication-slot lag.
  • Pick the SCD type per attribute by asking which version a historical fact should report under.
  • Contracts push breakage left to the producer's CI; write–audit–publish stops bad data at the door; lineage tells you what to re-run.
  • Engines: Apache Spark or warehouse SQL (SQL) for transforms; stream processing when batch latency is too high; outputs feed warehouses and feature stores.
