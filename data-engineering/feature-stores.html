Feature Stores

A model needs the same feature computed twice: in bulk over history to build a training set, and one row at a time in milliseconds to serve a prediction. A feature store is the system that keeps those two paths consistent — one definition, an offline store for time-travel queries, an online store for low-latency lookups, and a registry so features are found and reused instead of re-invented. Its central technical problem is time: every training row must see features exactly as they were at prediction time, not as they are now.

01 The problem: every feature lives twice

  • Training needs features for millions of historical (entity, timestamp, label) rows, computed in batch with Spark or warehouse SQL.
  • Serving needs the same features for one entity now, within a latency budget of a few milliseconds, from a service written in a different language by a different team.
  • Without shared infrastructure, the two implementations drift: a different null fill, a timezone boundary, a 7-day window computed as 7×24 hours in one and calendar days in the other. The model then sees inputs at serving time it was never trained on — training/serving skew — and degrades silently.
  • Meanwhile five teams each build their own "customer 30-day spend" with five slightly different definitions.
One line: a feature store turns features from ad-hoc pipeline code into managed, versioned data products with two access paths — historical (point-in-time) and live (low latency) — fed from one definition.

03 Entities, feature views, and timestamps

  • Entity: the thing features describe, with a join key — customer_id, merchant_id, (customer_id, merchant_id) for pair features.
  • Feature view / group: a set of features for one entity sharing a source and a schedule, e.g. customer_spend_stats with spend_7d, spend_30d, txn_count_24h.
  • Event timestamp: the time at which the value became true in the world (end of the aggregation window). This is what point-in-time joins use.
  • Created / ingestion timestamp: when the row was written to the store. It differs from event time when data arrives late or is backfilled, and it matters for reproducing what was actually knowable at serving time (§05).
  • TTL: how far back a value may be used. A spend_7d computed 40 days ago should not be joined to today's label; with TTL = 2 days the join returns null instead, mirroring what the online store would return for a stale entity.

04 Point-in-time-correct joins

For every training row (entity e, prediction time t), join the feature value that was the latest one known at t — never a later one. This is an as-of join, not an equality join.

as-of join with ingestion delay δ and time-to-live TTLx(e, t) = v(e, τ*) τ* = max { τ : τ + δ ≤ t and τ ≥ t − TTL } (null if the set is empty) what a naive join does insteadxnaive(e, t) = v(e, latest τ) — uses values from after t: label leakage

Drag the label (prediction) times and compare the naive "latest value" join with the as-of join. Raise the ingestion delay to model a nightly batch that only lands features hours after the window closes.

  • Implementation: sort both sides by (entity, time) and merge (merge_asof in pandas; ASOF JOIN or a window/QUALIFY ROW_NUMBER() pattern in SQL; range join + rank in Spark). At scale, bucket by entity and time to avoid a cross join.
  • Leakage looks like success. A churn model trained with naive joins sees "days since last login" computed after the customer churned. Offline AUC soars; production performance collapses. The gap between offline and online metrics is often the first symptom (see Model Evaluation).

06 Training/serving skew

KindCauseDetection / fix
Logic skewTwo implementations of a feature (SQL offline, Java online)Single definition compiled to both paths; on-demand transforms shared as one function
Data skewOnline path reads a different source (cache vs warehouse), different null handling, unit or timezone differencesCompare distributions of logged serving features to training features
Freshness skewTraining used values available within minutes; serving sees values a day old (or vice versa)Model δ in the as-of join to match production freshness
Version skewModel trained on feature v2, serving still materialises v1 (or an embedding from a different model)Pin feature versions in the model artifact; registry checks at deploy
  • Log-and-wait is the most robust fix: log the exact feature vector served with each prediction, join it to the label when it arrives, and train on that. Training data then matches serving by construction — at the cost of waiting to accumulate it, and of only having features that were served.
  • Skew metric: for a sample of entities, recompute features offline for the same timestamps they were served and compare. Track mismatch rate per feature; alert above a threshold. Distribution-level checks (PSI, KS) are covered in Monitoring & Drift.

  • Online writes are upserts of the latest value; offline writes are appends with timestamps. A materialisation job that only updates the online store leaves the offline history incomplete — and the next training set can't be point-in-time correct.
  • Streaming backfills. A new streaming feature has no history. Either compute history with a batch job using the same logic (risking logic skew), or replay the event log through the stream job (kappa-style).
  • Idempotent materialisation by (entity, event timestamp) makes reruns safe — the same discipline as ETL idempotency.

Feature staleness: batch interval vs streaming change the schedule and pipeline latency
  • Value of freshness is feature-specific. "Transactions in the last 5 minutes" is meaningless a day late; "country of residence" can be a week old. Set freshness SLAs per feature view and alert on violations.
  • Online latency budget: a recommendation request might allow 50 ms end to end; feature retrieval for a few hundred candidates must fit in a fraction of that. Batch the lookups (one multi-get per request), co-locate the store with the model server, and cap the number of feature views per request.
  • Online store sizing: memory ≈ entities × features × bytes per value × replication. 100 M users × 200 float features × 4 B ≈ 80 GB before overhead and replicas.

09 Feature registry and governance

  • Definitions as code, reviewed and versioned: entity, source, transformation, schedule, TTL, owner, description, tags. The registry is built from the repository, not edited by hand.
  • Discovery and reuse: searchable catalog with descriptions, statistics, freshness, and which models consume each feature. Reuse is where most of the organisational value comes from — the fifth team gets spend_30d for free and consistent.
  • Versioning: changing a feature's logic creates a new version; models pin versions. Breaking changes follow the same rules as data contracts.
  • Lineage: feature → source tables → upstream pipelines, and feature → models. Needed to answer "which models break if this source is late?" and to propagate deletions.
  • Access control and privacy: tag PII-derived features, restrict who can read them, and support deletion requests in both stores. For aggregate features with privacy guarantees, see Differential Privacy; for quality checks, see Data Quality & Governance.

10 Embeddings as features

  • Embeddings of users, items, or text are increasingly the most important features. They behave like features in a store — keyed by entity, materialised in batch or streaming, served online — with extra constraints.
  • Version coupling. An embedding is only meaningful relative to the model that produced it; vectors from encoder v3 and v4 live in different spaces. Store the producing model's version with every vector and never mix versions in one training set or one index.
  • Re-embedding is a backfill. Upgrading the encoder means recomputing every entity's vector, retraining downstream models, and rebuilding ANN indexes — plan it like a migration, with dual-writing during cut-over.
  • Storage and serving. 768 float32 dimensions = 3 KB per entity; 100 M entities ≈ 300 GB. Lower precision (float16, int8) or reduced dimensions cut this substantially. Key-based lookup ("this user's vector") fits the online store; similarity search ("items near this vector") needs a vector index (see Vector Databases).
  • Point-in-time still applies: a user embedding trained on data including future interactions leaks just like a scalar aggregate.

12 Takeaways

  • One definition, two stores: offline (history, point-in-time joins) and online (latest value, ms reads), plus a registry for discovery and versions.
  • Point-in-time correctness is non-negotiable: τ* = max τ with τ + δ ≤ t, within TTL. Naive latest-value joins leak labels and inflate offline metrics.
  • Skew comes from logic, data, freshness, and version differences; log served features and measure mismatch.
  • Choose materialisation by freshness need: batch (hours, cheap), streaming (seconds), on-demand (request-time).
  • Embeddings are features with a model version attached; re-embedding is a coordinated backfill.
