Stream Processing & Kafka

Batch pipelines answer "what happened yesterday?". Stream processing answers "what is happening now?" by computing continuously over unbounded data. The hard part isn't speed — it's time: events arrive late and out of order, so a stream processor must decide when a result is complete enough to emit, keep state safely across failures, and never double-count. A durable, replayable log (Kafka) underneath is what makes all of that tractable.

01 Bounded vs unbounded data

  • Batch processes a bounded dataset: all input exists before the job starts, so "the total for Tuesday" is computed once and is final.
  • Streaming processes an unbounded dataset: input never ends, so every result is computed over some window of it, and the processor must decide when a window's answer is final.
  • Batch is a special case of streaming — a stream that happens to end. Modern engines (Flink, Spark Structured Streaming) use one API for both; the difference is whether the source has an end and how results are triggered.
  • Why bother: fraud scoring, real-time features for models (see Feature Stores), alerting, operational dashboards, CDC replication — anywhere the value of data decays in seconds or minutes.

02 Event time vs processing time

Every event has two timestamps: when it happened (event time, stamped by the producer) and when the processor sees it (processing time). The gap between them is variable and unbounded.

skew(e) = tprocessing(e) − tevent(e) ≥ 0 — varies per event: network delays, retries, phones offline for hours
  • Processing-time windows are trivial to implement (bucket by the wall clock on arrival) but give answers that depend on network weather and change on replay. A backlog drained after an outage piles hours of events into one "minute".
  • Event-time windows assign each event to the window in which it happened, so results are deterministic and replayable — but the processor can never be sure it has seen every event for a window. That uncertainty is what watermarks manage (§04).
  • Out of order is normal. A mobile app batching events, a partitioned log read in parallel, and producer retries all reorder events. Correctness must not depend on arrival order.

04 Watermarks and late data

A watermark is the processor's running assertion: "I believe no more events with event time earlier than W will arrive." It turns an unanswerable question (is this window complete?) into a tunable policy.

bounded-out-of-orderness watermark (the common heuristic)W(now) = max event time seen so far − d window [a, b) fires when W ≥ b event e is late if tevent(e) < W when it arrives parallel sources: the operator's watermark is the minimum over its inputsWop = minᵢ Wᵢ — one idle or slow partition holds everyone back
  • The trade-off is completeness vs latency. A larger delay d waits longer and drops fewer late events; a smaller d emits sooner and drops more. There is no setting that is both instant and complete.
  • Late-data policies: drop (and count — a late-drop metric is essential); allowed lateness, which keeps window state a bit longer and emits updated results; or route late events to a side output for a batch correction job.
  • Idle partitions. Because the watermark is a minimum over inputs, a partition that stops receiving data freezes it and no window ever fires. Engines offer idleness timeouts that exclude quiet partitions.
  • State is bounded by the watermark. Once W passes a window's end (plus allowed lateness), its state can be discarded. Without a watermark, a windowed aggregation's state grows forever — the most common cause of streaming jobs slowly running out of memory.

05 Stateful operators

  • Stateless operators (map, filter, parse) look at one event at a time and scale trivially. Stateful ones — aggregations, windows, joins, deduplication, pattern detection — remember things across events.
  • Keyed state. Streams are partitioned by key so that all events for a key reach the same parallel task, which holds that key's state locally. This is the streaming version of a shuffle, and key skew hurts the same way.
  • State backends: in-memory hash maps for small state; an embedded on-disk key-value store (RocksDB-style LSM) for state far larger than memory, with incremental checkpoints. State of hundreds of GB per job is routine.
  • State TTL. Deduplication ("have I seen this event id?") and per-user features need an expiry, or state grows with every distinct key ever seen.
  • Stream–stream joins must buffer both sides; a time bound (b.t BETWEEN a.t AND a.t + 15 min) plus watermarks lets the engine evict buffered rows. A stream–table join (enrich events with a slowly changing table, often fed by CDC) keeps the table side as state.

06 Kafka as the durable log

Kafka is not a queue that deletes messages once read; it is a partitioned, replicated, append-only log. Consumers track their own position in it, so data can be re-read, by many independent consumers, at their own pace.

07 Delivery semantics and exactly-once

GuaranteeHow it arisesEffect of a crash
At-most-onceCommit offset before processingEvents in flight are lost
At-least-onceCommit offset after processingEvents in flight are re-processed → duplicates downstream
Exactly-once (effectively-once)State, output, and input position commit atomically, or output is idempotentReplays leave results unchanged
  • Exactly-once never means "each event is physically processed once" — after a failure, events are re-processed. It means the observable effect (state and sink contents) is as if each were processed once.
  • The end-to-end recipe: (1) a replayable source with offsets (Kafka); (2) checkpointed state consistent with those offsets (§08); (3) a sink that is either transactional (commit output together with the checkpoint, two-phase commit) or idempotent (upsert by a deterministic key, so a replay overwrites identical values).
  • Inside Kafka: the idempotent producer (sequence numbers per partition) removes retry duplicates; transactions write to several partitions plus the consumer offsets atomically; consumers reading with isolation.level=read_committed skip aborted data.
  • The weakest link decides. A job that writes to a plain HTTP API or sends emails is at-least-once no matter how good the engine is — design the sink for idempotency (see idempotency).

08 Checkpointing: consistent snapshots of a running job

To recover, a job needs a snapshot in which every operator's state reflects exactly the same prefix of the input. Stopping the world to take it would be too slow.

  • Barrier snapshots (a variant of the Chandy–Lamport algorithm): the coordinator injects a numbered barrier into each source partition. When an operator has received barrier n on all inputs, it snapshots its state asynchronously and forwards the barrier. When all sinks acknowledge, checkpoint n is complete and records the source offsets.
  • Aligned checkpoints buffer inputs that delivered the barrier early until the others catch up — exact but slow under backpressure. Unaligned checkpoints include in-flight buffers in the snapshot instead, keeping checkpoint time bounded under load at the cost of bigger snapshots.
  • Recovery = restore every operator's state from checkpoint n, rewind sources to its offsets, and resume. Events after the checkpoint are re-processed; transactional sinks discard their uncommitted output so nothing is duplicated.
  • Micro-batch engines get the same effect more simply: each batch's offsets and state are committed to a checkpoint directory before the next batch starts.
cost of the checkpoint interval Δexpected replay after a failure ≈ rate · (Δ / 2 + restart time) transactional sinks commit once per checkpoint ⇒ end-to-end latency for consumers ≥ Δ
Tuning: short intervals mean little replay and fresh transactional output but more overhead; long intervals the reverse. Seconds to a few minutes is typical; measure checkpoint duration and alert when it approaches the interval.

10 Lambda vs kappa architecture

LambdaKappa
StructureA batch layer recomputes accurate views from all history; a speed layer streams approximate recent results; a serving layer merges themOne streaming pipeline over a replayable log; reprocessing = replay the log through a new version of the job
Code pathsTwo implementations of the same logic, which drift apartOne
Correction of mistakesBatch layer overwrites the speed layer's answersDeploy fixed job, replay from an earlier offset into a new output, switch readers
RequiresBatch + stream infrastructureLong log retention (or tiered storage), exactly-once stream engine
When it still makes senseVery expensive history recomputation that streaming can't express; legacy stacksDefault for new systems
  • Lambda existed because early stream processors were lossy and approximate. Exactly-once engines and durable logs removed that reason; the remaining cost of kappa is retention — replaying a year of events needs a year of log, often in tiered object storage or a lakehouse table that the stream engine can also read.
  • A pragmatic hybrid is common: stream into lakehouse tables (see Data Warehousing) and run batch over the same tables, with one transformation codebase.

12 Takeaways

  • Window by event time, not arrival time, for deterministic and replayable results.
  • Watermarks trade latency for completeness (W = max event time − d); measure late drops, use allowed lateness or side outputs; watermarks also bound state.
  • Kafka is a replayable log: per-partition order, key-based partitioning, offsets owned by consumers, retention as the replay horizon, parallelism capped by partitions.
  • Exactly-once = replayable source + consistent checkpoints + transactional or idempotent sink. The sink is usually the weak link.
  • Prefer kappa (one codebase, replay to fix) over lambda for new systems.
