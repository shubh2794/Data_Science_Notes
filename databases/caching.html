Caching — Keeping Hot Data Close

A cache stores a copy of data somewhere faster or nearer than its source, betting that what was asked for recently will be asked for again. Because real workloads are skewed, a cache holding a few percent of the data can absorb most of the traffic. The hard parts are not the lookup — they are deciding what to evict, keeping copies fresh, and surviving the moment a hot entry expires. Caching is one of the core scalability patterns.

01 Why caches work: locality and skew

  • Temporal locality: an item used now is likely to be used again soon. Spatial locality: its neighbours are likely next (the reason CPUs fetch 64-byte lines, and why memory layout matters).
  • Popularity skew: request frequencies typically follow a power law (Zipf): the item of rank r is requested with probability proportional to 1/rᵅ. With α ≈ 1, the top 1% of items can draw a large share of all requests.
  • Skew is what makes caching cheap: you do not need to hold the dataset, only its head. Uniform access (every key equally likely) is the case where caches fail — hit ratio equals the fraction cached.
P(rank r) = r⁻ᵅ / ∑i=1..N i⁻ᵅ (Zipf popularity; α ≈ 0.6–1.2 in many request logs)

03 Hit ratio, effective latency and origin load

h = hits / (hits + misses)
Teff = h · thit + (1 − h) · (thit + tmiss) (a miss pays the lookup and then the origin)
origin load = (1 − h) · λ
  • With thit = 0.5 ms and tmiss = 20 ms: h = 90% → Teff = 2.5 ms; h = 99% → 0.7 ms. More importantly, origin load drops 10× between 90% and 99%. Think in miss ratio, not hit ratio: 1% vs 10% misses is the number your database feels.
  • This is the danger: a database sized for a 1% miss ratio is undersized by 10× the moment the cache is cold (restart, deploy, failover, a new key space). Plan cache warm-up and treat the cache as load-bearing.
  • Byte hit ratio (bytes served from cache) matters more than request hit ratio for CDNs, where a few huge objects dominate bandwidth.

04 Eviction policies

PolicyEvictsStrength · weakness
FIFOThe oldest inserted itemTrivial, lock-friendly · ignores reuse entirely
LRUThe least recently used itemAdapts to recency; O(1) with a hash map + doubly linked list · one large scan flushes the whole cache
CLOCKAn LRU approximation: a "referenced" bit swept by a handCheap, no list reordering on hit; used by OS page caches
LFUThe least frequently used itemKeeps the stable head under Zipf · stale popularity lingers when tastes shift; needs counter ageing
ARCBalances a recency list and a frequency list, sized adaptively using "ghost" lists of recently evicted keysScan-resistant and self-tuning, no parameter · more bookkeeping
W-TinyLFUAdmits a new item only if its sketched frequency beats the eviction victim'sNear-optimal hit ratios with tiny metadata (count-min sketch)
TTLAnything older than its time-to-liveBounds staleness, not memory — combine it with one of the above
OPT (Belady)The item whose next use is furthest in the futureOptimal but needs the future — the yardstick for the others
  • Online algorithms theory makes this precise: with cache size k, LRU and FIFO are k-competitive against OPT, and no deterministic policy does better in the worst case — see Online Paging & List Update.
  • Redis does approximate LRU/LFU: on eviction it samples a handful of keys and evicts the best candidate among them, avoiding a global list. Its policies (allkeys-lru, allkeys-lfu, volatile-ttl, noeviction, …) decide which keys are eligible.

PatternRead pathWrite pathTrade-off

CPUs use write-back caches with coherence protocols; application caches overwhelmingly use cache-aside with delete-on-write, because deleting is idempotent and safe to retry while updating in place is not.

07 Invalidation and consistency

  • TTL-only: accept bounded staleness (≤ TTL). The simplest correct model when the business tolerates it; add random jitter to TTLs so keys filled together do not expire together.
  • Explicit invalidation: delete on write. The classic race: reader A misses and reads the old value from the DB; writer B updates the DB and deletes the key; A then writes the old value into the cache, where it lives until TTL. Mitigations: short TTLs as a backstop, leases (the cache hands the reader a token that a concurrent delete invalidates), or delayed double-delete.
  • Versioned keys: embed a version or content hash in the key (user:42:v17); writes bump the version, old entries simply age out. Excellent for immutable artefacts — model files, feature snapshots, static assets.
  • Change-data-capture invalidation: tail the database's replication log and invalidate (or update) cache keys from it, so invalidation is driven by committed writes rather than by every code path remembering to do it. This rides on a message log.
  • A cache is a replica without a consensus protocol. It cannot give you transactional guarantees; if a read must be fresh (balances, permissions), read the source.

08 Stampedes and the thundering herd

When a hot key expires, every concurrent request misses at once and all of them recompute or hit the database — a load spike proportional to request rate × recompute time, exactly when the origin is least able to absorb it.

  • Request coalescing (single-flight): the first miss recomputes; the others wait for its result. One origin call per expiry per cache node.
  • Locks / leases: the same idea across processes — only the lease holder recomputes; others get a short wait or the stale value.
  • Stale-while-revalidate: keep serving the expired value while one background refresh runs. Users never see the miss latency.
  • Probabilistic early expiration: each reader independently decides to refresh before expiry, with a probability that rises as expiry approaches and with the cost of recomputation:
refresh early if now − δ · β · ln(u) ≥ expiry (u ~ uniform(0,1) · δ = recompute time · β ≥ 1, default 1)
Origin load around expiries of one hot key TTL = 10 s · bars = origin calls per 250 ms

memcachedRedis (and compatible forks)
Data modelOpaque byte strings by keyStrings, hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLog
ThreadingMulti-threadedCommand execution essentially single-threaded per shard (I/O can be threaded) — scale by sharding
Persistence & replicationNone — pure cacheOptional snapshots / append-only log; primary–replica replication; cluster mode with hash slots
MemorySlab allocator, per-slab LRUConfigurable maxmemory + eviction policy
Use whenSimple, very high-throughput look-aside cachingYou also want counters, rate limiters, leaderboards, queues, locks
  • Partitioning: keys are spread across nodes by consistent hashing or fixed hash slots, so adding a node remaps only a fraction of keys (each remapped key is a miss).
  • Hot keys: one celebrity key can saturate one shard regardless of cluster size. Fixes: a small in-process cache in front (L1 + L2), replicating hot keys to several suffixed copies, or read replicas.
  • Big values (multi-MB) block a single-threaded server and saturate NICs; compress, split, or store the blob in object storage and cache a pointer.
  • Do not let the cache become the system of record by accident: if losing it loses data, it is a database and needs to be operated as one.

11 Takeaways

  • Skew is the reason caches work; under uniform access they barely help.
  • Think in miss ratio: origin load is (1 − h)·λ, and a cold cache multiplies it.
  • Pick eviction for the workload: LRU for recency, LFU (with decay) for stable popularity, ARC / W-TinyLFU when scans and shifts both happen; TTL bounds staleness.
  • Cache-aside + delete-on-write + TTL backstop is the default; know its race and use leases or versioned keys where it matters.
  • Defend hot-key expiry with single-flight, stale-while-revalidate or probabilistic early refresh.
  • In ML, version every cache key by model — features, embeddings and predictions are only valid for the model that produced or consumes them.
