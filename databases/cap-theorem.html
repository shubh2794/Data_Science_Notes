CAP Theorem, PACELC and Quorums

When a network partition separates replicas, a replicated store has to choose between answering every request, and risking stale or conflicting data, and refusing some requests to stay correct. This page gives the precise version of that statement, explains what it does and doesn't say, extends it to normal operation with PACELC, and works through the quorum arithmetic behind "tunable consistency".

01 Intuition: two replicas and a broken link

Put two replicas of a bank balance in two data centres. The link between them goes down. A client in the second data centre asks for the balance just after a client in the first one withdrew money.

  • Option 1, answer: return the local, possibly stale balance. The system stays available but gives up consistency.
  • Option 2, refuse or wait: return an error or block until the link heals. The system stays consistent but gives up availability.
  • There is no third option. The replica cannot learn about a write it never received. That is the whole theorem.
One line: partitions aren't optional, so CAP is really "during a partition, choose C or A". The famous "pick 2 of 3" phrasing is misleading.

02 The precise statement

The formal version was proved in 2002 for an asynchronous network, where messages can be delayed arbitrarily and there are no clocks to bound delays.

TheoremNo read/write register replicated over an asynchronous network can guarantee both (C) linearizability and (A) availability in every execution, including those where the network drops messages between nodes (P).
LetterFormal meaning in the theoremWhat it is not
C = linearizabilityEvery operation appears to take effect atomically at a single instant between its invocation and its response, so all clients see one real-time-ordered history of a single copy.Not the "C" in ACID (invariants), and not serializability of multi-object transactions
A = total availabilityEvery request received by a non-failing node eventually gets a non-error response. There is no time bound, and "the majority side answers" doesn't count.Not "five nines uptime". A system can be CP and still highly available in practice.
P = partition toleranceThe guarantees must hold even when the network loses arbitrarily many messages between groups of nodesNot a feature you can opt out of on a real network

03 Proof sketch

  1. Split the nodes into two non-empty groups G₁ and G₂ and drop every message between them.
  2. A client writes v₁ to a node in G₁. By availability, the write must complete, even though G₂ can't hear about it.
  3. Another client then reads from a node in G₂. By availability, it must answer, and it can only answer with what G₂ knows, the old v₀.
  4. The read started after the write completed, yet it returned the old value. That violates linearizability. ∎

The argument only needs one partition and one read. Any "always answer" design loses linearizability as soon as the network splits.

04 Simulate it: CP vs AP under a partition

A three-replica cluster: A and B on one side, C on the other. Cut the link, pick a mode, and send requests to different sides. In CP mode a request needs a majority (2 of 3). In AP mode every node answers locally, and conflicts are resolved by last-write-wins when the partition heals.

05 What CAP does not say

  • It doesn't classify most systems. A single-leader database with asynchronous followers is neither linearizable (follower reads are stale) nor totally available (writes fail when the leader is cut off). It is "neither C nor A" in the CAP sense, and it is still a perfectly useful design.
  • It says nothing about the time when there's no partition. With a healthy network you can have both C and A. The real day-to-day cost of consistency is latency, which is what PACELC adds.
  • The choice is per operation, not per system. One database can serve linearizable reads for account balances and stale reads for a product catalogue.
  • It's about one model at each extreme. Many weaker guarantees, such as causal consistency, read-your-writes and monotonic reads, can survive partitions. "AP" doesn't have to mean "anything goes".
  • Node crashes are not partitions, although from the outside they look the same: a timeout. That ambiguity is why failure detection is hard (see failover).

06 PACELC: the latency half of the trade-off

PACELCif Partition → choose Availability or Consistency Else (normal operation) → choose Latency or Consistency

Even with a perfect network, a linearizable write has to reach a majority, possibly in other regions, before it's acknowledged. A system that replies after one local replica is faster and weaker.

These labels describe defaults. Most production systems expose knobs that move them along both axes.

07 Quorums: R + W > N

Store each key on N replicas. A write is acknowledged once W replicas confirm it, and a read waits for R replicas and keeps the newest version it sees. If the two sets must overlap, every read contains at least one replica that holds the latest acknowledged write.

Overlap and fault toleranceR + W > N ⇒ |read set ∩ write set| ≥ R + W − N ≥ 1 W > N / 2 ⇒ two write quorums always intersect (no split-brain writes) writes survive N − W failed replicas · reads survive N − R
Quorum calculator worst-case placement: writes hit the leftmost W, reads hit the rightmost R
  • Latency is an order statistic. A request waits for the W-th (or R-th) fastest replica, so a quorum of 2 out of 3 hides one slow node. W = N waits for the slowest replica every time.
  • Common settings: N = 3 with W = R = 2 is the balanced default. W = N, R = 1 gives fast reads and fragile writes. W = 1, R = N is the reverse.
Quorum ≠ linearizable. R + W > N guarantees overlap with the last completed write only. While a write is still propagating, one reader can see the new value and a later reader the old one. Sloppy quorums, last-write-wins with skewed clocks, and failed writes that left partial copies all break the guarantee as well. Read repair before returning, or consensus, closes the gap.

08 The consistency spectrum

Model (strong → weak)GuaranteeAvailable under partition?
Strict serializabilityTransactions serializable and in real-time orderNo
LinearizabilitySingle-object operations look atomic and real-time orderedNo (this is CAP's C)
SequentialOne global order consistent with each client's program order, but not with real timeNo
CausalCausally related operations are seen in order by everyone; concurrent ones may be seen in different ordersYes, if each client sticks to one replica or side
Read-your-writes, monotonic reads, monotonic writesPer-client session guaranteesYes, with sticky sessions
EventualIf writes stop, replicas convergeYes
  • Causal consistency is close to the strongest model that can remain available through partitions, which makes it a sweet spot for geo-replicated apps such as comments, chat and collaborative editing.
  • CRDTs (conflict-free replicated data types such as counters, sets and sequences) make eventual consistency safe by merging concurrent updates deterministically, so nothing is lost the way it is with last-write-wins.

09 Designing with CAP in practice

  • Classify each piece of data by the invariant it protects. Money, inventory, uniqueness, locks and leader election need C. Feeds, counters, likes, caches and recommendations usually tolerate A with bounded staleness.
  • Make staleness visible and bounded. Track replication lag and version vectors, and set an SLO such as "follower reads ≤ 5 s stale". Monitor it like any other SLI.
  • Plan the partition behaviour explicitly: what the minority side returns (an error, cached data, a degraded mode), and how divergent writes are reconciled when it heals (LWW, CRDT merge, or a manual queue).
  • Distributed locks need fencing. A lease holder that pauses for GC can wake up after its lease expired. Hand out monotonically increasing fencing tokens and have storage reject stale ones.
  • ML serving angle: an online feature store is typically AP/EL (stale features are better than a timeout), while a model registry's "current production version" pointer should be CP.

10 Takeaways

  • CAP: during a partition, a replicated register can't be both linearizable and totally available. The C and A are specific formal properties.
  • PACELC: without a partition, the trade-off is latency vs consistency, and that's the cost you pay every day.
  • Quorums: R + W > N gives overlap. W > N/2 prevents split-brain writes. Latency is set by the W-th or R-th fastest replica. Overlap alone is still not linearizability.
  • Pick consistency per operation, and prefer causal and session guarantees or CRDTs where full linearizability isn't required.
