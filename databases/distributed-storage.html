Distributed Storage — HDFS, Object Stores and Erasure Coding

When data outgrows one machine's disks — or must survive that machine dying — it is split into pieces, spread across many nodes, and stored redundantly. This page covers the three storage interfaces (block, file, object), the classic HDFS design, modern object stores, the maths of replication vs erasure coding, columnar formats like Parquet, and how ML training jobs actually read terabytes from all of it.

Data Systems HDFS Object Storage Durability

01 What distributing storage buys — and costs

  • Capacity: petabytes across thousands of commodity disks, growing by adding nodes rather than replacing machines.
  • Aggregate throughput: a file striped across 100 disks can be read at 100 disks' bandwidth — the property that makes parallel compute (MapReduce, Spark, distributed training) possible.
  • Durability and availability: at scale, disk and node failures are daily events, not exceptions. Redundancy plus automatic repair turns them into routine background work.
  • The cost: redundant bytes (storage overhead), repair traffic, metadata that must itself be highly available, and consistency semantics that are weaker or slower than a local filesystem.
One line: distributed storage is the art of choosing an overhead (how many extra bytes) and a repair speed that together make the probability of losing data negligible.

03 HDFS architecture

  • NameNode (metadata): holds the entire namespace — directory tree, file → block list, block → DataNode locations — in RAM, persisted as a checkpoint image plus an edit log. Clients ask it where blocks live, then talk to DataNodes directly; file data never flows through the NameNode.
  • DataNodes (data): store blocks as local files, send heartbeats every few seconds and periodic block reports. A DataNode that stops heart-beating is declared dead and its blocks are re-replicated elsewhere.
  • Blocks are large — 128 MB by default — so a 1 GB file is just 8 blocks. Large blocks keep metadata small and make reads sequential and streaming-friendly; they are wrong for small random reads.
  • Write pipeline: the client streams a block to the first DataNode, which forwards to the second, which forwards to the third; acks flow back. HDFS is write-once, append-only — no in-place edits.
  • High availability: an active and a standby NameNode share the edit log through a quorum of journal nodes; failover is coordinated so only one NameNode is ever active. Federation splits the namespace across several NameNodes.
  • The small-files problem: every file, directory and block is an in-RAM object on the NameNode (a commonly quoted rule of thumb is ~150 bytes each). 100 million 10 KB files cost far more NameNode memory than 10 000 files of 100 MB — and each tiny file becomes its own map task. Compact small files.
  • Data locality: because the NameNode knows block locations, schedulers run compute on the node holding the block — the original "move compute to data" idea behind MapReduce.

04 Rack-aware replication

With the default replication factor 3, HDFS places replicas to survive a whole rack failing (a top-of-rack switch or power feed) while keeping write traffic mostly within racks:

  • Replica 1: on the writer's node if the writer is a DataNode, otherwise a random node.
  • Replica 2: on a node in a different rack.
  • Replica 3: on a different node in the same rack as replica 2.

One cross-rack transfer per block instead of two, yet any single rack can disappear and every block still has a live copy. Try it — place a file, then fail nodes and racks:

05 Object stores

  • Flat namespace: s3://bucket/datasets/2026/part-00017.parquet is one key; the slashes are a naming convention. "Directories" are prefixes, and LIST by prefix is a paginated scan.
  • No rename: "renaming a directory" means copying and deleting every object under the prefix — non-atomic and slow. Job commit protocols that relied on HDFS's atomic rename had to be redesigned; table formats (Iceberg, Delta Lake, Hudi) solve it by committing a new metadata/manifest file instead of moving data.
  • Consistency: the major object stores now provide strong read-after-write consistency for PUTs, overwrites, deletes and LIST. Older eventual-consistency behaviour (a new object missing from a listing) is why many older tools carry workarounds. Concurrent writers to the same key: last writer wins, unless you use conditional writes (if-none-match / if-match on an ETag) where supported.
  • Large objects: uploaded in parts (multipart upload, parallel, resumable) and read with byte-range GETs — which is what lets Parquet readers fetch just a footer or a single column.
  • Request rates scale per prefix (on the order of thousands of requests per second per prefix in a widely used service) and the store partitions hot prefixes automatically over time. Spread high-rate workloads over many prefixes; expect throttling (HTTP 503 "slow down") during sudden ramps.
  • Durability is typically designed for "eleven nines" annually via erasure coding across failure domains (availability zones). Availability — being able to read right now — is a separate, lower number.
  • Cost model: per GB-month, plus per request, plus egress. Millions of tiny GETs can cost more than the storage; lifecycle rules move cold data to cheaper, slower tiers.

06 Replication vs erasure coding

Replication stores r full copies. Erasure coding (Reed–Solomon RS(k, m)) splits data into k fragments and computes m parity fragments; any k of the k + m reconstruct the data.

  • When per-node failure probability within a repair window is small, EC gives more durability for less space (RS(6, 3) loses data only if 4 of 9 fragments fail, ≈ 126·p⁴, vs p³ for 3× replication — EC wins whenever p < ~0.8%). But repair reads k× as much data, degraded reads (a fragment is missing) need decoding, and small files waste space. Hence the common split: replicate hot data, erasure-code warm and cold data. HDFS supports both (EC policies such as RS-6-3 per directory).
  • Correlated failures break the formula. The binomial model assumes independent failures; a rack, power domain or bad firmware batch takes out many at once. That is why fragments must be spread across failure domains — at least k + m racks or zones for the guarantees to mean anything.
  • Repair time is a durability knob: p is the probability of further failures during the repair window, so faster repair (more parallel rebuild bandwidth) shrinks p and adds nines.

07 Columnar files on object storage: Parquet

Object stores are slow per request but fast in bulk; analytical queries read a few columns of many rows. Columnar formats exploit both.

  • Layout: a file is split into row groups (often ~128 MB–1 GB of rows); inside each, every column is stored contiguously as a column chunk made of pages. A footer at the end holds the schema and, per row group and column, statistics (min, max, null count).
  • Projection pushdown: SELECT user_id, label reads just those column chunks via byte-range GETs — often 5–20% of the bytes.
  • Predicate pushdown: WHERE event_date = '2026-11-01' skips every row group whose min/max excludes it. Sorting or clustering data on common filter columns makes the statistics selective. Directory-style partitioning (…/event_date=2026-11-01/) skips whole files.
  • Encoding and compression: values of one type sit together, so dictionary encoding, run-length encoding and general compression (Snappy, Zstandard) work well — 3–10× smaller than row-oriented text formats is common.
  • File sizing: aim for files of roughly 100 MB–1 GB. Thousands of tiny files multiply request overhead and listing time (the object-store version of the small-files problem); one giant file limits parallelism.
  • Table formats layer on top: a metadata log of which Parquet files make up the table, giving atomic commits, snapshots/time travel and schema evolution — the basis of lakehouse warehousing. Query engines and Spark read the same files.

08 How ML training reads from distributed storage

required read bandwidth = GPUs × samples/s per GPU × bytes per sample
e.g. 64 GPUs × 2 000 img/s × 110 KB ≈ 14 GB/s (sustained, for every epoch)
  • Shard the dataset into large sequential files (hundreds of MB each, thousands of shards) instead of millions of individual images. Per-object latency (tens of ms) is fatal for random small reads and fine for streaming big ones.
  • Parallel, prefetched reads: each data-loader worker streams different shards with several concurrent range GETs; decoding and augmentation overlap with GPU compute. A starving GPU (utilisation dips while the loader catches up) is the symptom of an I/O-bound pipeline.
  • Shuffling without random access: shuffle the shard order each epoch, then mix samples in an in-memory shuffle buffer. Larger buffers approach a true shuffle; a tiny buffer over sorted shards leaks ordering into training.
  • Distributed training splits shards across ranks (each rank reads a disjoint subset per epoch), so the total shard count should be a healthy multiple of workers × loader processes — see Distributed Training.
  • Cache locally: multi-epoch jobs read everything repeatedly; staging the dataset to local NVMe (or a node-local cache) after the first epoch turns a network-bound job into a disk-bound one.
  • Tabular data: read Parquet with column projection and row-group filters; for features, the offline store of a feature store is usually exactly such a table. Pin the dataset snapshot / version used for each run so experiments are reproducible (Experiment Tracking).
  • Checkpoints and model artefacts go to object storage too; multi-GB writes use multipart upload, and serving replicas pulling the same weights at once benefit from a caching layer (Caching).

10 Takeaways

  • Block for databases, file for shared POSIX, object for lakes and ML data — object storage is now the default system of record.
  • HDFS = in-RAM NameNode metadata + DataNodes with large replicated blocks, rack-aware placement and data locality; its Achilles' heel is small files.
  • Object stores have a flat namespace, immutable objects, strong read-after-write consistency, no atomic rename, and request-based pricing.
  • Erasure coding beats replication on space and durability but costs repair bandwidth and decode latency; both depend on independent failure domains.
  • Parquet + partitioning + sensible file sizes make object storage fast for analytics; large sequential shards, prefetching and shuffle buffers make it fast for training.
