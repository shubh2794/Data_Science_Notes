Hadoop & MapReduce

The batch paradigm that started "big data": when a dataset no longer fits one machine, ship the computation to the data, express it as two pure functions — map and reduce — and let the framework handle partitioning, sorting, network transfer, and machine failure. Spark replaced the engine, but nearly every idea here (partitioners, shuffles, locality, speculative tasks) survives in it.

01 The problem: computation is cheap, moving data is not

Scanning 10 TB from one disk at ~200 MB/s takes ~14 hours. Spread across 1,000 disks it takes under a minute — if each machine processes the bytes sitting on its own disk.

  • Scale out, not up. Commodity machines are cheap and fail often. At 1,000 nodes with a 3-year mean time between failures, you lose roughly one machine per day — so failure is a normal operating condition, not an exception.
  • Move code, not data. A job's code is kilobytes; its input is terabytes. The scheduler places a task on (or near) the machine holding the input block — data locality.
  • Restrict the programming model to make the hard parts automatic. If user code is a pure function over records, the framework can re-run any piece anywhere, any number of times, and get the same answer. That determinism is what makes parallelism and recovery free.
One line: MapReduce trades expressiveness for automation — you write two side-effect-free functions; the framework owns distribution, the shuffle, retries, and stragglers.

02 The programming model: map, shuffle, reduce

Every job is the same three-phase skeleton. Only the two functions at either end are yours.

the two user functions, as typesmap : (k₁, v₁) → list(k₂, v₂) reduce : (k₂, list(v₂)) → list(k₃, v₃) what the framework does between themshuffle : group all (k₂, v₂) by k₂, sort by k₂, deliver each group to exactly one reducer
PhaseWho runs itWhat happens
Input splitFrameworkInput files are cut into splits (typically one per storage block); one map task per split.
MapUser code, M parallel tasksEach record → zero or more intermediate key/value pairs. Output is buffered in memory, partitioned, sorted, and spilled to local disk.
Combine (optional)User code, on the map sideA mini-reduce over one map task's output, to shrink what crosses the network.

ReduceUser code, R parallel tasksCalled once per distinct key with an iterator of its values; output written to the distributed file system.
  • M and R are independent knobs. M follows the input size (one task per ~128 MB block); R is chosen by you and sets output-file count and reduce parallelism.
  • The only communication between tasks is the shuffle. Map tasks never talk to each other, reduce tasks never talk to each other — which is why any task can be killed and re-run in isolation.

03 Word count, step by step

The canonical first job. map emits (word, 1) for every token; reduce sums the ones. Step through the phases, toggle the combiner, and change the reducer count to see how the partitioner routes keys and how much data crosses the network.

  • Notice that the appears in every split and always lands on the same reducer — that is the shuffle's contract. A hot key like this is also the seed of reduce-side skew (§05).
  • With the combiner on, each mapper ships one record per distinct word instead of one per token. On natural-language text, where a few words dominate (Zipf's law), this routinely cuts shuffle volume by an order of magnitude.

04 Shuffle & sort: the expensive middle

Map and reduce are embarrassingly parallel. The shuffle is the all-to-all exchange between them, and it is where most MapReduce jobs spend their time.

  • Map side. Output goes into a circular in-memory buffer (100 MB by default). When it crosses a threshold (80%), a background thread partitions, sorts by key within each partition, optionally runs the combiner, and spills a file to local disk. Multiple spills are merged into one partitioned, sorted file per map task.
  • Reduce side. Each reducer fetches its partition from all M mappers over HTTP — an M × R mesh of transfers — then merge-sorts the runs so it can stream one key's values at a time.
  • A reducer cannot start reducing until every mapper has finished, because the last mapper might hold values for any key. That barrier is why a single slow map task stalls the whole job.
default partitioner and shuffle costpartition(k) = hash(k) mod R network transfers = M × R bytes shuffled ≈ ∑ⱼ |map-output of task j| (after combining, if any)
Operational rule: the cheapest shuffle byte is the one never emitted. Filter and project inside map, combine where the algebra allows, and compress intermediate output — CPU is cheaper than the network.

05 Combiners and partitioners

Combiner: when is it safe?

  • The framework may run the combiner zero, one, or many times on any subset of a key's values. So the operation must be associative and commutative, and its output type must equal its input type.
  • Safe: sum, count, min, max, set union, top-k. Unsafe as-is: mean, median, distinct-count. The fix for mean is to carry a decomposable state: emit (sum, count), combine component-wise, divide only in the reducer.
why a naive mean combiner is wrongmean(mean(1, 2), mean(3)) = mean(1.5, 3) = 2.25 ≠ mean(1, 2, 3) = 2 decomposable fix(s₁, n₁) ⊕ (s₂, n₂) = (s₁ + s₂, n₁ + n₂) final mean = s / n

Partitioner: who gets which key

  • Hash partitioner (default) balances well when keys are many and roughly uniform. It cannot split a single hot key — all of its values go to one reducer.
  • Total-order partitioner samples the keys to pick R−1 split points so reducer i gets a contiguous key range; concatenating the outputs yields a globally sorted file. This is how the classic sort benchmarks were run.
  • Custom partitioner for joins and secondary sort: partition on a prefix of a composite key (e.g. user id) while sorting on the full key (user id, timestamp).
  • Skew mitigation: salt hot keys (key#0…key#n), aggregate per salt, then aggregate again; or detect heavy hitters by sampling and route them specially.

06 HDFS and data locality

MapReduce's speed came from pairing it with a file system that exposed where every block lived.

ComponentRole
NameNodeHolds the namespace and the block → DataNode map in memory. A single logical master; production clusters run an active/standby pair with a shared edit log.
DataNodeStores blocks on local disks, heartbeats to the NameNode, serves reads directly to clients.
BlockLarge and fixed-size (128 MB default) so seek time is amortised and the metadata stays small.
ReplicationFactor 3 by default. Rack-aware placement: first replica on the writer's node, second on a node in a different rack, third on another node in that second rack — survives a whole-rack loss with only one cross-rack write.
  • Locality levels: node-local (read from local disk) → rack-local (one top-of-rack switch hop) → off-rack (crosses the core network, the scarce resource). Schedulers wait briefly for a local slot before accepting a worse one ("delay scheduling").
  • The small-files problem. Every file and block costs NameNode memory (on the order of 150 bytes per object), and every small file becomes its own tiny map task. Ten million 10 KB files are far worse than one 100 GB file — compact them.
  • HDFS is write-once, append-only: no in-place updates. That constraint resurfaces later as the reason data lakes needed table formats to get updates and deletes (see Data Warehousing).

07 Fault tolerance, stragglers, and speculative execution

  • Task failure: re-run the task elsewhere (up to a retry limit, 4 by default). Because map/reduce are deterministic and inputs are immutable, a re-run produces identical output.
  • Node failure: its completed map tasks are also re-run, because their output lived on that node's local disk, not in HDFS. Completed reduce output is already in HDFS and survives.
  • Stragglers. A job finishes when its slowest task finishes. A failing disk, a noisy neighbour, or a bad NIC can make one task 5–10× slower than its peers, and at scale the chance that some task is slow approaches certainty.
  • Speculative execution launches a backup copy of a lagging task near the end of a phase and takes whichever copy finishes first. It costs extra slots for a large cut in tail latency — but it is harmful for tasks with side effects (writing to an external database), which is another reason to keep tasks pure.

08 YARN: separating resources from the engine

The first Hadoop fused job scheduling and resource management into one JobTracker, which capped clusters at a few thousand nodes and supported only MapReduce. YARN split the two.

DaemonScopeResponsibility
ResourceManagerClusterArbitrates CPU/memory among applications via pluggable schedulers (capacity queues, fair share).
NodeManagerPer machineLaunches and monitors containers (a bounded slice of memory and vcores); reports health.
ApplicationMasterPer jobNegotiates containers from the RM, schedules the job's tasks into them, handles task retries and speculation.
  • Because the AM is per-application, YARN became a generic cluster OS: MapReduce, Spark, Tez, and Flink all ran as YARN applications on the same hardware.
  • Today Kubernetes fills the same role in many shops; the RM/AM split maps onto the Kubernetes scheduler plus a per-job driver or operator.

10 Why it gave way to Spark

MapReduce's rigid two-stage shape and disk-everything durability were the right defaults for 2004 web indexing and the wrong ones for interactive SQL and iterative machine learning.

ConcernMapReduceApache Spark
Between stagesMaterialise to HDFS (3× replicated) between jobs; spill to disk inside a jobPipelines narrow operations in memory; shuffle files on local disk only at wide boundaries
Job shapeExactly map → reduce; multi-step logic = chain of jobsArbitrary DAG of many stages in one job
IterationRe-read input from disk each passcache() the working set once, iterate in memory
RecoveryRe-run the task from its durable inputRecompute lost partitions from lineage; checkpoint long lineages
APILow-level Java classes; SQL bolted on via HiveDataFrames/SQL with a cost-based optimiser; Python, Scala, SQL, R
Latency floorTens of seconds of JVM/task startup per jobLong-lived executors; sub-second tasks
  • For iterative ML, keeping the working set in memory made Spark one to two orders of magnitude faster on the same hardware — the gap that decided the market.
  • What survived: HDFS-style block storage (now mostly cloud object stores), YARN-style resource managers, columnar file formats born in the Hadoop ecosystem, and the whole map → partition → shuffle → reduce vocabulary, which is exactly how a Spark stage boundary works.

11 Takeaways

  • Two pure functions, one framework. Determinism is what makes re-execution, speculation, and parallelism automatic.
  • The shuffle is the cost centre: M × R transfers, sort, and a global barrier. Filter early, combine where associative and commutative, compress.
  • Hash partitioning can't split a hot key — salt it or special-case heavy hitters.
  • Locality + replication (128 MB blocks, 3 replicas, rack-aware) let compute run where data sits and survive routine machine loss.
  • Stragglers set the job time; speculative backups trim the tail at the price of extra slots.
  • Disk materialisation between every step is why Spark replaced it — but the vocabulary carries straight over. For the storage side see Distributed Storage and Sharding & Replication.
