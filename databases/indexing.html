Indexing

An index is a second, redundant copy of some of your data, kept in a shape that answers one kind of question quickly. Every index buys read speed with write cost, disk space and planner complexity. This page covers the main structures (B⁺-tree, hash, LSM-tree, bitmap), how composite and covering indexes behave, and how a query planner decides whether to use any of them.

01 Why indexes exist: the cost of a full scan

Without an index, WHERE email = 'a@b.c' has to read every page of the table. The cost is counted in page I/Os, not rows, because storage moves data in fixed-size pages (usually 4–16 KB).

  • Full scan: cost ∝ P, the number of table pages. That's fine for a 10 MB table and hopeless for a 2 TB one when you only want one row.
  • Index lookup: descend a small structure to find where the matching rows live, then fetch only those pages. Cost ∝ index height + matching rows.
  • What you pay for it: each INSERT/UPDATE/DELETE has to maintain every index on the table. Indexes also take disk, buffer-cache memory and backup time, and every extra one gives the planner more ways to pick a bad plan.
Rough I/O cost of one equality lookupfull scan ≈ P pages B⁺-tree ≈ h + k (h = tree height, k = pages holding the k matches)
One line: an index turns "read everything and filter" into "seek, then read a little". The work moves from read time to write time.

02 The B⁺-tree: the default index

A B⁺-tree is a balanced multiway search tree with one node per disk page. Inner nodes hold only separator keys and child pointers, so a single page fans out to hundreds of children. Leaves hold the keys plus row pointers (or the rows themselves) and are chained left to right, which makes range scans cheap. The structure itself is covered in B-Trees & B⁺-Trees.

Fan-out and heightf ≈ ⌊ page_size / (key_bytes + pointer_bytes) ⌋ · fill h ≈ ⌈ log_f (N / leaf_entries) ⌉ + 1
  • Because f is in the hundreds, h grows extremely slowly. A billion rows fit in 3–4 levels. The inner levels are small enough to stay in the buffer cache, so a point lookup costs about one or two real disk reads.
  • Fill factor: after random inserts nodes settle at about 69% full (≈ ln 2). Bulk-loading sorted data can pack them to about 90–100%.
  • Supports: equality, ranges (<, BETWEEN), prefix LIKE 'abc%', ORDER BY without a sort step, and MIN/MAX. It does not help with LIKE '%abc' or with functions of the column unless you build an expression index.

03 Hash indexes: O(1) equality, nothing else

A hash index maps h(key) → bucket → row pointers. Equality lookups take expected O(1) probes regardless of table size. The hashing details are in Hash Tables.

  • No order, so no ranges. WHERE ts > …, ORDER BY and prefix matches cannot use a hash index (see what hashing cannot do).
  • Growth: on-disk hash indexes have to grow without rehashing everything at once. Linear hashing splits one bucket at a time. Extendible hashing doubles a directory of bucket pointers.
  • In practice a B⁺-tree is usually within a level of a hash index on equality and handles everything else as well, so relational engines default to B-trees. Hash indexing earns its place in in-memory key-value stores, hash joins and the in-memory key directory of log-structured stores.

04 LSM-trees: turn random writes into sequential ones

A log-structured merge tree buffers writes in memory and flushes them as immutable sorted files. Writes are fast and sequential. Reads may have to check several files.

  1. Write: append to the WAL for durability, then insert into the in-memory memtable (a sorted skip list or tree).
  2. Flush: when the memtable fills up, write it out as an immutable sorted SSTable in level 0.
  3. Compaction: background jobs merge-sort SSTables into larger ones at deeper levels and drop overwritten values and tombstones (delete markers).
  4. Read: check the memtable, then each level from newest to oldest. A per-file Bloom filter skips files that definitely don't contain the key, and sparse block indexes locate the block inside a file.

05 Read, write and space amplification

Storage engines are compared by how many bytes they physically move per logical byte. It is generally accepted that no structure minimises all three amplifications at once: improving any two costs you the third.

Definitionswrite amp = bytes written to storage / bytes written by the application read amp = bytes (or pages) read per logical lookup space amp = bytes on disk / bytes of live data
  • B⁺-tree write amp: changing a 100-byte row dirties a whole 8 KB page, which works out to about 80× at the page level, plus the WAL record and possibly a full-page image after a checkpoint. Writes are in-place and random.
  • LSM write amp: each byte is rewritten once per compaction it passes through. Leveled compaction with T = 10 and 4–5 levels commonly measures 10–30×, but those writes are large and sequential, which SSDs and HDDs handle much better than random 8 KB writes.
  • Secondary indexes multiply write amp. A table with 6 indexes does roughly 7 structure updates per insert. Under write-heavy load, the number of indexes is the first knob to check.
  • SSD wear: write amp is also a hardware cost, because flash endurance is rated in total bytes written.

06 Bitmap indexes: low-cardinality analytics

A bitmap index stores one bit-vector per distinct value. Bit i is 1 if row i has that value. A predicate becomes a bitwise operation.

rows(status='open' ∧ region∈{EU,US}) = B_open AND (B_EU OR B_US) size ≈ distinct_values · N bits (before compression)
  • Bitmaps suit columns with few distinct values (status, country, boolean flags), where a B-tree would point at huge, unselective lists of rows. Run-length or roaring-style compression keeps sparse bitmaps small, and AND/OR/COUNT run with SIMD over whole machine words.
  • Poor for OLTP: one update can touch a compressed run that covers many rows, so locking and rewrite costs are high under concurrent writes. They belong in warehouses and columnar engines (see Data Warehousing).
  • Some row stores build bitmaps at query time instead. A "bitmap index scan" collects matching row locations from one or more B-trees into a bitmap, combines them with AND/OR, then visits the heap pages in physical order.

07 Composite indexes and the leftmost-prefix rule

An index on (country, city, signup_date) sorts entries lexicographically: first by country, then by city within each country, then by date. A seek can only use a leading run of equality columns, optionally followed by one range column. That is the leftmost-prefix rule. Toggle the predicates and watch which entries the scan has to touch.

Leftmost-prefix: which part of the index is a contiguous range? green = returned · amber = scanned then filtered · dim = skipped
  • Column order rule of thumb: equality columns first, then the column used for a range or ORDER BY. Among the equality columns, the order matters less than which column sets are actually queried together.
  • An index on (a, b) also serves queries on a alone, so a separate index on a is usually redundant write cost.
  • Skip scan: some engines can use an index whose leading column has no predicate by jumping between its distinct values. This only pays off when that leading column has very few distinct values.

Correlation matters: the same index can be cheap or ruinous depending on how closely the table's physical row order follows the index order. With high correlation, k matches cost about k/rows_per_page sequential pages. With none, they cost about k random pages.

09 Selectivity and how the planner chooses

A cost-based planner estimates the selectivity s of each predicate (the fraction of rows that pass), converts each candidate plan to an abstract cost, and picks the cheapest. Indexes win only when s is small.

Simplified cost model (units of one sequential page read)cost_seq ≈ P · c_seq + N · c_cpu cost_index ≈ h · c_rand + s·N · c_rand (uncorrelated: one random page per match) cost_bitmap ≈ P · (1 − e^(−sN/P)) · c_page + s·N · c_cpu (each heap page visited once, in order)
  • Where selectivity comes from: per-column statistics, namely most-common-value lists, equi-depth histograms and distinct counts, refreshed by ANALYZE. Predicates on different columns are multiplied together under an independence assumption.
  • Correlated columns break that assumption. city='Paris' AND country='FR' is estimated at s_city·s_country, which can be orders of magnitude too low. The planner then picks a nested loop that runs a million times. Multi-column (extended) statistics fix this.
  • c_rand / c_seq encodes the storage. A ratio of about 4 is the classic spinning-disk default, and about 1.1 suits SSDs. On SSDs the index stays the better plan up to much larger selectivities.
Seq scan vs index scan vs bitmap scan drag selectivity; the cheapest plan is highlighted

Use EXPLAIN ANALYZE to compare estimated and actual rows at each node. A gap of 10× or more is the usual root cause of a bad plan, more often than a missing index.

10 Operational practice

  • Index for the workload, not the schema. Start from the slowest frequent queries (from query-stats views or slow logs) and design composite or covering indexes for them. Don't index every foreign key and filter column reflexively.
  • Find unused indexes. Usage counters show indexes that are never scanned. They are pure write and space cost. Check replicas too, because a read replica may depend on an index the primary never uses.
  • Build online. Creating an index on a large live table can block writes. Use the engine's concurrent or online build, and expect it to take longer and possibly fail halfway, leaving an invalid index to drop.
  • Bloat and fragmentation: MVCC updates leave dead entries behind, and random-key inserts split pages. Watch index size compared with live rows, and rebuild or repack when the ratio drifts.
  • Monitor the plan, not just latency. Plans flip when statistics change, for example after a bulk load. Treat a plan regression like a model regression: alert on it and diff it (compare Monitoring & Drift).
  • Vector search is indexing too: approximate-nearest-neighbour indexes trade recall for speed. See Vector Databases.

11 Takeaways

  • B⁺-tree is the general-purpose default: equality, ranges and ordering in about 3–4 levels for a billion rows, with inner levels cached in memory.
  • Hash handles equality only. LSM gives fast sequential writes and pays for them with compaction and multi-file reads. Bitmap suits low-cardinality analytics and is poor for OLTP.
  • Composite indexes follow the leftmost-prefix rule: equality columns first, then at most one range column. Covering indexes avoid table lookups altogether.
  • Every index adds write amplification, and the planner only uses an index when the estimated selectivity is low enough. Bad estimates do more damage than missing indexes.
