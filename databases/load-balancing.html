Load Balancing — Spreading Requests Across Servers

A load balancer sits between clients and a pool of interchangeable backends and decides, request by request, who does the work. Done well it multiplies throughput, hides failures, and keeps tail latency flat; done naively it piles work onto the one slow server. This page covers the layers (L4 vs L7), the algorithms (round robin to power of two choices), consistent hashing, health checks, stickiness, and global traffic steering. It is one of the core patterns of scalability.

01 What a load balancer is for

  • Throughput: turn N servers into one logical service with roughly N× capacity — the horizontal half of scaling.
  • Availability: stop sending traffic to dead or sick backends, so a single failure costs capacity, not correctness.
  • Decoupling: clients see one stable address while backends are added, drained, deployed and autoscaled behind it — the mechanism under rolling, blue/green and canary deployments.
  • Edge duties that naturally live in the same hop: TLS termination, request routing, rate limiting, retries, connection pooling, observability.
One line: the goal is not equal request counts but equal queueing — every backend should be about as busy as every other, relative to its capacity.

02 Layer 4 vs Layer 7

L4 (transport)L7 (application)
SeesIP addresses, ports, TCP/UDP connectionsFull requests: HTTP method, path, headers, cookies, gRPC method
BalancesConnections (a long-lived connection sticks to one backend)Individual requests, even multiplexed over one HTTP/2 connection
Can doVery high packet rates, low added latency, protocol-agnostic, can forward without terminatingPath/host routing, header-based canaries, TLS termination, retries, compression, auth, caching
CostsNo content awareness; poor balance with few long connectionsMust parse and usually terminate TLS — more CPU, more latency, more config
Typical placeNetwork edge, in front of L7 proxies, non-HTTP protocolsAPI gateways, ingress controllers, service-mesh sidecars
  • The HTTP/2 / gRPC trap: clients hold one long connection and multiplex everything over it. An L4 balancer pins that whole stream to one backend, so new replicas receive nothing. Use L7 (per-request) balancing or client-side balancing for gRPC.
  • Large deployments stack them: L4 at the edge (or anycast) spreads connections across a fleet of L7 proxies, which then route requests to services.

03 Static algorithms — no feedback from the backends

Hash-basedbackend = hash(client IP or key) mod NAffinity / cache locality · any change in N remaps almost every key (see §06)

Static rules are cheap and stateless, which matters when the balancer itself is distributed. But they are blind: they keep sending to a server that has slowed down.

04 Dynamic algorithms and the power of two choices

  • Least connections: send to the backend with the fewest outstanding requests. Self-correcting — a slow server accumulates in-flight work and stops being chosen. Needs a global view, which a fleet of independent balancers does not have.
  • Least response time / peak-EWMA: score backends by a decaying average of latency × outstanding requests; reacts to slowdowns that connection counts miss.
  • Herd behaviour: if many balancers all read the same stale "least loaded" signal, they all pick the same backend at once and overload it. Full information, applied synchronously, can be worse than randomness.
  • Power of two choices (P2C): sample two backends at random and send to the less loaded. It needs almost no state, avoids herding (the random sample decorrelates balancers), and its effect on the worst-case load is exponential:
n balls into n bins — maximum load with high probability
one random choice: ≈ ln n / ln ln n best of d ≥ 2 choices: ≈ ln ln n / ln d + O(1)

Going from one choice to two collapses the maximum load from roughly log to log log; going from two to more helps only by a constant factor. That asymmetry is why P2C is the default in many modern proxies and service meshes. The balls-into-bins analysis connects to the greedy-approximation view of online load balancing.

05 Simulation — eight servers, one of them fast, two of them slow

Requests arrive as a Poisson stream; servers process them with random service times. Two servers run at half speed, one at double speed. Pick a policy, push the load, and watch the queues and the p99 latency.

  • Above ρ ≈ 0.5, round robin and random overload the half-speed servers: they receive 1/8 of the traffic but only have 1/16 of the capacity, so their queues grow without bound.
  • Weighted round robin fixes the known imbalance; least connections and P2C fix it without being told the weights — they read the queues.
  • Notice that P2C here can trail weighted round robin: comparing raw queue lengths, an idle slow server looks as attractive as an idle fast one, so short queues still leak work to the slow machines. Production P2C balancers compare a latency-weighted load (e.g. peak-EWMA × outstanding requests) for exactly this reason.

06 Consistent hashing — affinity that survives resizing

When the same key should go to the same backend (a cache shard, a partition, a replica holding a warm KV cache), hash(key) mod N is a disaster on resize: going from N to N+1 moves about N/(N+1) of all keys.

mod-N: keys moved on N → N+1 ≈ K · N/(N+1) consistent hashing: keys moved ≈ K / (N+1)
  • The ring: hash both nodes and keys onto a circle; a key belongs to the first node clockwise. Adding a node steals keys only from its successor; removing one hands its keys to the next.
  • Virtual nodes: with one point per node, arcs are very uneven. Give each node v points; load imbalance shrinks roughly like 1/√v, and weights become "more vnodes for bigger machines".
  • Relatives: rendezvous (highest-random-weight) hashing scores every node per key and picks the max — no ring, O(N) per lookup; Maglev hashing builds a lookup table for O(1) lookups with minimal disruption; consistent hashing with bounded loads caps any node at (1+ε)× the average and spills the overflow clockwise, fixing hot keys.

07 Health checks, outlier detection and retries

  • Active health checks: the balancer probes each backend (TCP connect, HTTP /healthz) every few seconds; after k consecutive failures it is ejected, after j successes re-admitted. The hysteresis stops flapping.
  • Liveness vs readiness: "the process is up" is not "it can serve". A model server that is still loading weights must fail readiness, or it will receive traffic and time out. Deep checks that hit the database can take the whole fleet out when the database blips — keep readiness local.
  • Passive checks / outlier detection: watch real traffic and eject backends whose error rate or latency is an outlier, with a cap on the ejected fraction so a global problem does not empty the pool.
  • Retries amplify load: three layers each retrying three times turn one failure into 27 requests. Use retry budgets (e.g. retries ≤ 10% of requests), exponential backoff with jitter, and only retry idempotent requests.
  • Connection draining: on deploy or scale-in, stop new requests to a backend but let in-flight ones finish before shutdown.

08 Sticky sessions — when affinity helps and when it hurts

MechanismHowTrade-off
Source-IP hashSame client IP → same backendBreaks behind NAT (many users, one IP) and on mobile IP changes
Cookie affinityL7 balancer sets a cookie naming the backendPrecise, but uneven load when a few sessions are heavy
Key / header hashConsistent hash of user ID, tenant ID or prompt prefixGood cache locality; hot keys need bounded-load spill-over
  • Stickiness is usually a sign of state on the server. Prefer moving session state out (shared cache, tokens) and keeping affinity only as a performance hint — the system must still be correct when a sticky backend dies.
  • The legitimate use is cache locality: routing the same key to the same node so its local cache stays warm.

09 Global load balancing — DNS, GeoDNS and anycast

  • DNS load balancing: the name resolves to several addresses, or to the nearest/healthiest region (GeoDNS, latency-based routing). Simple and global, but slow to react: resolvers and clients cache answers for the TTL, and some ignore it. Expect failover in minutes, not seconds.
  • Anycast: many sites announce the same IP; internet routing delivers each packet to the topologically nearest one. Fast failover (routes withdraw), natural DDoS absorption; typical for CDNs and DNS itself. Long-lived TCP flows can break if routes shift.
  • The hierarchy: DNS/anycast picks a region → an L4 tier spreads connections → L7 proxies route requests → a service mesh or client library picks a replica with P2C. Each layer balances at a different granularity and timescale.
  • Data gravity: global routing is easy for stateless serving and hard for writes — sending a user to another region only helps if their data is there too (replication and CAP trade-offs).

10 Load balancing for ML inference

  • Request cost varies wildly. An LLM request with a 20-token prompt and one with a 30 000-token prompt are not the same unit of work. Count outstanding tokens or estimated compute, not requests — least-loaded by request count misleads.
  • Batching backends are most efficient when full; balancing must trade even spreading against letting each GPU accumulate a batch.
  • Cache-aware routing: replicas that already hold a prompt's prefix in their KV cache answer far faster. Routers hash on the prefix (consistent hashing with bounded loads) to reuse it — see LLM Serving.
  • Model and version routing: L7 header rules send a percentage of traffic to a canary model and mirror traffic to a shadow model; the statistics of comparing them are in A/B Testing.
  • Readiness matters more: a replica is not ready until weights are loaded and warm-up inference has run, or the first requests will see multi-second latencies.

11 Takeaways

  • L4 balances connections; L7 balances requests — use L7 (or client-side) for HTTP/2 and gRPC.
  • Static rules are blind to slow servers; least connections and power of two choices read the queues, and P2C does it without herding.
  • Consistent hashing moves only ~K/N keys on resize; add virtual nodes for balance and bounded loads for hot keys.
  • Health checks need hysteresis, readiness must be local, and retries need budgets.
  • Global steering (DNS, anycast) is coarse and slow; the fine-grained balancing happens near the backends.
