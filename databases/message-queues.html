Message Queues — Decoupling Producers from Consumers

A message queue lets one part of a system hand work or events to another without waiting for it. The producer writes a message and moves on; consumers process it when they can. That one indirection buys burst absorption, independent scaling and failure isolation — and costs you a new set of questions: how many times is a message delivered, in what order, and what happens when consumers fall behind. Queues are one of the core scalability patterns.

01 Why put a queue in the middle

  • Load levelling: producers burst, consumers drain at a steady rate. The queue absorbs the difference so the database behind the consumers sees the average, not the peak.
  • Temporal decoupling: the consumer can be down, deploying or slow; messages wait. A synchronous call chain fails if any link fails; a queue-connected chain degrades into latency instead.
  • Independent scaling: add consumers to drain faster without touching producers — the queue depth is the autoscaling signal.
  • Fan-out: one event ("order placed") feeds many independent consumers (billing, email, analytics, a feature pipeline) without the producer knowing they exist.
One line: a queue converts a failure or overload problem into a latency problem — which is only a good deal if you watch the backlog and bound it.

02 Point-to-point vs publish/subscribe

Log-based systems blur the line: a topic is pub/sub across consumer groups, and point-to-point within a group, because each partition is read by one member of the group.

  • Recent Kafka releases add share groups (queue semantics on a topic: consumers can outnumber partitions and ack records individually, at the cost of per-partition ordering), narrowing the gap between the two models.

04 Partitions, ordering and consumer groups

  • A topic is split into partitions; a message goes to partition = hash(key) mod P. All messages with the same key land in the same partition, and a partition is read in order — so ordering is guaranteed per key, never globally.
  • A consumer group divides partitions among its members: each partition is owned by exactly one consumer in the group. Therefore parallelism ≤ number of partitions — the 13th consumer on a 12-partition topic sits idle.
  • Rebalancing: when a consumer joins, leaves or stops heart-beating, partitions are reassigned. During a rebalance consumption pauses, and uncommitted work is redone by the new owner. Cooperative/incremental rebalancing moves only the affected partitions.
  • Hot keys: one very active key pins all its traffic to one partition and one consumer. Partition count cannot fix skew — only a better key (or key salting, giving up per-key ordering) can.

05 Delivery semantics

GuaranteeHow it arisesFailure symptom
At-most-onceAck (commit offset) before processing; or fire-and-forget producerCrash after ack → the message is lost
At-least-onceProcess, then ack; producer retries until acknowledgedCrash after processing, before ack → the message is processed twice
Exactly-once (effectively-once)At-least-once delivery + deduplication or atomic commit of output and offsetHolds only inside the boundary that participates in the protocol
  • No network protocol can guarantee a message is delivered exactly once (the sender cannot distinguish a lost message from a lost ack). What systems offer is exactly-once processing: duplicates still arrive but their effects are applied once.
  • Log systems implement it with idempotent producers (the broker drops retried duplicates using a producer ID and sequence numbers) and transactions that atomically write output records and the consumer's offsets. This covers read-from-log → write-to-log pipelines; the moment you call an external API or database, you are back to at-least-once plus your own idempotency.
  • FIFO managed queues deduplicate by a message-deduplication ID within a fixed window (minutes). Outside the window, duplicates are again your problem.
Rule of thumb: design every consumer as at-least-once + idempotent. It is the only guarantee that survives crossing system boundaries.

06 Idempotency patterns

  • Naturally idempotent operations: "set status = shipped", upserts keyed by ID, writing a file to a deterministic path. Applying twice equals applying once: f(f(x)) = f(x).
  • Idempotency keys: each message carries a unique ID; the consumer records processed IDs in the same transaction as its side effect, and skips IDs it has seen. The dedup table needs a retention policy longer than the maximum redelivery delay.
  • Transactional outbox: the producer cannot atomically write its database and publish a message. Instead it writes the message into an outbox table in the same DB transaction; a relay (or change-data capture) publishes from the outbox. This removes the "DB committed but publish failed" gap.
  • Versioning / fencing: include a monotonically increasing version; consumers ignore anything older than what they have applied. Handles both duplicates and out-of-order redeliveries.

07 Backpressure and consumer lag

  • Consumer lag — the number of messages (or seconds) between the newest produced message and the consumer's position — is the health metric of a queue. Rising lag means arrival rate exceeds service rate; nothing else will tell you sooner.
  • Unbounded queues hide overload until memory or disk runs out, then fail catastrophically. Bound them, and decide explicitly what happens when full: block the producer (backpressure), reject with an error (load shedding), or drop low-priority messages.
  • Flow control: pull-based consumers apply backpressure naturally (they fetch only what they can handle); push-based brokers need a prefetch / credit limit per consumer, or a fast broker will flood a slow consumer.
  • Autoscale on lag, not CPU: a consumer blocked on a slow database shows low CPU and high lag. Remember the partition ceiling: you cannot scale a group past its partition count.
  • Because latency ≈ lag ÷ consume rate (Little's law), a lag SLO can be stated in seconds — "events reach the feature store within 60 s".

08 Retries, poison messages and dead-letter queues

  • Transient failures (timeouts, throttling) deserve retries with exponential backoff and jitter: delay = random(0, min(cap, base · 2ᵃᵗᵗᵉᵐᵖᵗ)). Without jitter, every failed consumer retries in lock-step and re-creates the overload.
  • Poison messages (malformed payloads, a bug triggered by one input) fail every time. Retrying them forever blocks the partition behind them (head-of-line blocking) or burns capacity.
  • Dead-letter queue (DLQ): after k failed attempts, move the message aside with its error and attempt count. The main flow continues; the DLQ is alarmed, inspected and replayed once the bug is fixed. A DLQ nobody watches is a silent data-loss mechanism.
  • Visibility timeouts must exceed the worst-case processing time (or be extended while working); otherwise a slow-but-healthy consumer's message reappears and is processed twice in parallel.
  • Ordered streams and retries conflict: to retry without blocking a partition you must move the message to a retry topic — which breaks per-key ordering. Decide which matters more per use case.

09 Queueing math — why 90% utilisation feels like an outage

Model a consumer as an M/M/1 queue: Poisson arrivals at rate λ, exponential service at rate μ, one server. Everything follows from the utilisation ρ (derivations in Ergodic Averages, MCMC & Queues):

ρ = λ / μ (stable only if ρ < 1)
L = ρ / (1 − ρ) W = 1 / (μ − λ) Wq = ρ / (μ − λ) L = λ · W
  • Waiting time is proportional to ρ/(1 − ρ): 1× service time at ρ = 0.5, 9× at 0.9, 99× at 0.99. The curve is a hockey stick, and the knee is earlier than intuition suggests.
  • Variability matters as much as load. For general arrivals and service (G/G/1), Kingman's approximation: Wq ≈ (ρ / (1 − ρ)) · ((cₐ² + cₛ²) / 2) · (1/μ), where c is the coefficient of variation. Bursty producers (cₐ > 1) or heavy-tailed jobs (cₛ > 1) multiply the wait.
  • With c consumers (M/M/c) the same knee appears at ρ = λ/(cμ) near 1, but pooling makes it sharper and later — one shared queue feeding c consumers beats c separate queues.

10 Queues in ML systems

  • Asynchronous inference: long jobs (document parsing, video, large-batch embedding) go on a work queue; GPU workers pull at their own pace and the client polls or gets a callback. Queue depth drives GPU autoscaling — see Model Deployment.
  • Request batching: an inference server's internal queue is what lets it form batches; the max-wait-before-batch setting is a direct latency↔throughput dial (LLM Serving).
  • Event logs as training data: impressions, clicks and predictions logged to a topic feed both real-time features (stream processing → feature stores) and the offline lake for retraining — one log, two consumers, consistent data.
  • Prediction logging for monitoring: publishing every prediction with its features lets drift monitors consume asynchronously without slowing serving.
  • Pipeline orchestration: ETL stages connected by queues retry independently; idempotent stage outputs make re-runs safe.

11 Takeaways

  • Work queues distribute tasks to one consumer; pub/sub broadcasts events to every subscriber; a log does both via consumer groups.
  • Ordering is per partition (per key), and group parallelism is capped by the partition count.
  • Assume at-least-once and make consumers idempotent; "exactly-once" holds only inside a transactional boundary.
  • Watch lag, bound queues, and back off with jitter; send poison messages to a DLQ that someone actually monitors.
  • Keep consumers below ~70–80% utilisation: queueing delay grows like ρ/(1 − ρ), and burstiness makes it worse.
