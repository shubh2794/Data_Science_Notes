NoSQL — Key-Value, Document, Wide-Column, Graph

"NoSQL" covers non-relational stores that relax parts of the relational model, such as fixed schemas, joins and multi-row transactions, to get horizontal scale, flexible records or a better fit for one data shape. The trade is that you model the data around your queries instead of around entities, and you take on consistency work the database used to do for you.

01 Why non-relational stores exist

  • Scale-out writes. A single relational primary eventually runs out of write throughput or disk. Most NoSQL systems are built to partition data across many machines from day one, and the data model is restricted so that one request touches only one partition.
  • Shape fit. Nested JSON, sparse attributes, time series and highly connected graphs are awkward to express as normalized tables.
  • Operational choices. Tunable consistency, multi-region active-active writes and predictable single-digit-millisecond latency at any size are design goals of some of these systems.
  • What you give up: ad-hoc joins, schema enforcement and (traditionally) multi-key transactions. Many systems have since added some of these back, and relational engines have absorbed JSON columns and horizontal scaling. The line between the camps is blurrier now than the name suggests.
One line: relational design asks "what are the entities?" and NoSQL design asks "what are the queries?". In NoSQL a query you didn't plan for is often slow or impossible.

03 Key-value stores

  • The simplest contract: get(k), put(k, v), delete(k). Because the store never looks inside v, partitioning is trivial: shard = h(k) mod S, or a consistent-hash ring.
  • In-memory stores (Redis-style) add data-structure values such as lists, sets, sorted sets and streams, plus TTLs. They are ideal for caching, rate limits and leaderboards. Durability is optional (snapshots or an append-only file), so treat them as caches unless you've configured otherwise.
  • Embedded LSM stores (RocksDB-style) are the storage engines underneath many databases, including some of the families below. See Indexing for LSM-trees.
  • Limits: a query on anything except the key needs a separately maintained index. Multi-key atomicity is either missing or limited to keys in the same slot or partition.

04 Document stores

A document stores an aggregate, meaning an entity together with the children you always read with it, as one nested record. One read returns the whole aggregate with no join.

  • Schema-on-read: the database accepts any shape. The schema still exists, but in application code, so plan for documents in several historical shapes and migrate lazily or with optional JSON-schema validation.
  • A single-document update is atomic. Multi-document ACID transactions exist in the major document stores today but cost more coordination, especially across shards. Modelling so that one business operation touches one document is still the fast path.

05 Wide-column stores

The key has two parts. The partition key decides which node owns the data. The clustering key sorts rows inside the partition, so "the latest 50 events for sensor 17" is a single sequential read.

Primary key anatomyPRIMARY KEY ((sensor_id, day), ts) → node = token(sensor_id, day) · rows sorted by ts within it
  • Query-first tables: one table per access pattern is normal. The same reading may be written to by_sensor and to by_site.
  • Bound the partition. A partition that grows without limit (all events for one sensor, ever) becomes a hotspot and a compaction problem. Add a time bucket such as day to the partition key.
  • Storage is an LSM-tree, so writes are cheap. Deletes write tombstones, which have to be read past until compaction removes them. Queue-like "insert then delete" workloads are a well-known failure mode.
  • Conflicts are usually resolved per cell by last-write-wins on timestamps, so clock skew can silently drop writes. Compare-and-set costs a consensus round per operation (lightweight transactions).

06 Graph databases

  • Property graph: nodes and edges both carry labels and key-value properties. Queries are pattern matches like (a:User)-[:PAID]->(m:Merchant)<-[:PAID]-(b:User). Common languages are Cypher, Gremlin and the ISO GQL standard. The RDF model (triples queried with SPARQL) is the other main school.
  • Why not SQL joins? A k-hop query in SQL is k self-joins, each an index lookup over the whole edge table. Native graph engines store adjacency directly on each node, so a hop costs time proportional to that node's degree, independent of total graph size.
  • Hard parts: partitioning a graph cuts edges, which turns traversals into network hops, so many graph databases scale up rather than out. Supernodes (a celebrity with 10M followers) make traversals explode.
  • Graph algorithms such as PageRank, community detection and shortest paths are often run in a batch engine instead of the OLTP graph store (see Graph Representations).

07 Modelling by access pattern: picking the partition key

The single most important NoSQL decision is the partition key. A good key spreads both storage and traffic evenly and makes your hot queries hit one partition. Try the candidates on an orders dataset hashed across 8 partitions.

Partition-key chooser: balance vs query fan-out bars = load per partition · table = partitions each query must touch
  1. List the access patterns first, with rough rates: "get a customer's last 20 orders, 5k/s", "fetch an order by id, 2k/s", "today's orders for a dashboard, 1/min".
  2. Choose a key that turns the hottest patterns into single-partition reads. Serve the rest with secondary indexes, a second table or an analytical copy. Rare scatter-gather queries are acceptable.
  3. Check skew under real distributions. Monotonic keys (dates, auto-increment ids) send every new write to one partition. Low-cardinality keys (country) can never use more partitions than they have distinct values.

08 Denormalization: paying at write time

Without joins, you precompute them by copying data to wherever it is read. That moves cost from reads, which happen often, to writes, which happen less often, and adds a consistency problem: the copies can disagree.

Per-write cost with R reads per write, join depth J, copy fan-out Fnormalized ≈ R · J + 1 denormalized ≈ R · 1 + F denormalize when R > (F − 1) / (J − 1)
When does denormalizing pay off? operation cost per write as the read:write ratio grows
  • Keeping copies in sync: transactional multi-item writes where supported, change-data-capture streams that update the derived copies, or an outbox table plus a message queue. All but the first leave a window of staleness. Measure it and monitor it.
  • Prefer copying immutable or slow-changing fields (a product's name at time of purchase is a feature, not a bug). Avoid copying fast-changing counters, and use a separate aggregate for those.

09 Consistency models in practice

GuaranteeWhat a client observesTypical mechanism
Strong / linearizableEvery read sees the latest acknowledged writeRead from the leader, quorum with read repair, or consensus
Read-your-writesYou always see your own updates; others may lagRoute a user's reads to the leader for a while after they write, or pass a version token
Monotonic readsTime never appears to go backwards for one clientPin a client to one replica
CausalIf write B depends on A, nobody sees B without ADependency tracking or version vectors
EventualReplicas converge once writes stop; reads may be stale and out of orderAsync replication, anti-entropy, LWW or CRDT merges
  • Tunable consistency: leaderless stores let each request choose how many replicas must acknowledge (ONE, QUORUM, ALL). R + W > N makes read and write sets overlap. The details and caveats are on CAP Theorem.
  • Some managed key-value stores default to eventually consistent reads and offer strongly consistent reads at roughly twice the read cost, and often not on global secondary indexes. Know your default.

11 Takeaways

  • The four families (key-value, document, wide-column, graph) each restrict the data model in exchange for scale or shape fit.
  • Model by access pattern. The partition key decides balance and query fan-out, so check it against real skew and against monotonic keys.
  • Denormalize when reads outnumber writes by more than about (F−1)/(J−1). Budget for the sync mechanism and the staleness window.
  • Know the default consistency of every read path, and pay for stronger consistency only where an invariant needs it.
