Scalability — Scaling Up, Scaling Out, and Why It Stops

A system is scalable if adding resources buys a proportional increase in the load it can carry, without latency falling apart. This page is the overview for the scaling patterns — load balancing, caching, sharding & replication, queues — and for the three laws that tell you where scaling stops paying: Amdahl, the Universal Scalability Law, and Little's law.

01 What "scalable" actually means

"Scalable" is not a property a system has; it is a question: if load grows along this axis, what do we do, and what does it cost? Answering it needs two vocabularies — how you describe load, and how you describe performance.

  • Load parameters are the numbers that describe demand: requests/s, read:write ratio, concurrent users, data volume, fan-out per request, hot-key skew. A system that handles 10× more users may still die at 10× more writes per user.
  • Performance is throughput (work completed per second) and latency (time per request) — and latency is a distribution, not a number. Report percentiles: p50, p95, p99, p99.9.
  • Scalability is the slope: how throughput changes as you add capacity N, and whether latency percentiles hold steady while it does. Elasticity is the operational version — how fast capacity can follow load up and back down.
One line: a scalable design keeps the cost per unit of load roughly flat as load grows — the laws below explain the three forces (serial work, contention, coherence) that bend that line upward.

02 Vertical vs horizontal scaling

Scale up (vertical)Scale out (horizontal)

  • Real systems do both: scale the stateless tiers out cheaply and keep the stateful core vertical as long as possible, then shard it when a single node runs out. Premature sharding is one of the most expensive mistakes in data systems.
  • Diagonal scaling: pick the instance size with the best price/performance, then scale out in units of that size.

03 Statelessness — the precondition for scaling out

  • A stateless server keeps nothing between requests that another replica would need: any request can go to any instance. That makes replicas interchangeable, so you can add, remove, restart or autoscale them freely.
  • State does not disappear — it moves to a dedicated tier: sessions into a shared cache or signed tokens, durable data into a database, files into object storage, work-in-progress into a queue.
  • The hidden-state traps: local disk caches, in-process rate-limit counters, scheduled jobs that run "on one box", WebSocket connections, and in-memory model warm-up. Each one quietly breaks interchangeability.
  • For ML serving, model weights are read-only state — replicas stay effectively stateless, but cold start (pulling multi-GB weights, compiling kernels) is what limits elasticity. KV caches in LLM serving are per-replica state, which is why routing becomes cache-aware.

04 Amdahl's law — the serial fraction caps the speed-up

If a fraction p of the work parallelises perfectly and 1 − p is inherently serial, then N workers give at most:

S(N) = 1 / ( (1 − p) + p / N ) limN→∞ S(N) = 1 / (1 − p)
  • With p = 0.95 the ceiling is 20×, no matter how many nodes you buy; at 64 nodes you already have 15.4×. The serial 5% — a global lock, a single coordinator, one un-sharded table — owns the result.
  • Gustafson's view is the optimistic counterpart: if the problem grows with the machine (bigger datasets, more users), the scaled speed-up is S(N) = (1 − p) + p·N. Both are right; they answer different questions (fixed work vs fixed time).
  • Amdahl assumes coordination costs nothing beyond the serial part. Real clusters pay extra for every node they add — that is what the USL models. The algorithmic side (work, span, Brent's bound) is in Parallel Scheduling & Scaling Laws.

05 The Universal Scalability Law — contention σ and coherence κ

The USL adds a second penalty to Amdahl: nodes must keep each other consistent, and that cost grows with the number of pairs of nodes. Relative capacity at N nodes is:

C(N) = N / ( 1 + σ·(N − 1) + κ·N·(N − 1) )
N* = √( (1 − σ) / κ ) (peak: adding nodes past N* reduces throughput)
TermPhysical causeEffect on the curve
σ contentionQueueing on a shared resource: a lock, a primary DB, a single partition, one coordinatorThroughput saturates at 1/σ (this is Amdahl with σ = 1 − p)
κ coherence (crosstalk)Pairwise agreement: cache invalidation, distributed locks, gossip, all-reduce, two-phase commitThroughput peaks and then falls — retrograde scaling
Amdahl vs USL — throughput as nodes are added drag σ and κ; the orange marker is your cluster size
ideal linearAmdahl (κ = 0)USL
  • Fitting the USL needs only a handful of load-test points (N, throughput). Fit σ and κ by regression, then read off N* before you buy the hardware. A κ that is non-zero but tiny still sets a peak — it is just far away.
  • Reducing σ means removing shared bottlenecks (partition the hot table, shard the lock). Reducing κ means removing all-to-all chatter (avoid broadcast invalidation, prefer leader-based or partitioned designs, shrink the consistency domain).

06 Little's law, throughput vs latency, and the utilisation knee

For any stable system — a server, a queue, a whole data centre — the average number of requests inside equals arrival rate times average time spent inside:

L = λ · W (L = in-flight requests · λ = throughput · W = mean latency)
  • It is distribution-free and indispensable for sizing: 5 000 req/s at 80 ms mean latency means 400 requests in flight — that is your required concurrency (threads, connections, GPU batch slots) across the fleet.
  • Throughput and latency are not independent. As utilisation ρ = λ / (c·μ) approaches 1, queues form and waiting time explodes. For a single M/M/1 server W = 1 / (μ − λ) — at ρ = 0.5 latency is 2× the service time, at ρ = 0.9 it is 10×, at ρ = 0.99 it is 100×. The derivation and simulation live in Message Queues.
  • This is why capacity plans target 50–70% utilisation at peak, not 100%: the headroom is what keeps p99 flat. "We are only at 85% CPU" is not good news for tail latency.
  • Throughput-oriented systems (batch ETL, training, offline inference) run hot and accept queueing; latency-oriented systems (online serving, search) run cool and buy headroom.

07 Tail latency and fan-out

At scale, the slowest responses dominate. If a request fans out to n servers and waits for all of them, it is slow whenever any leaf is slow:

P(request is slow) = 1 − (1 − q)ⁿ (q = chance one leaf exceeds its p99 → q = 0.01)
Fan-out amplifies the tail one leaf's p99 becomes the request's median
  • With q = 1% and n = 100, 63% of user requests see at least one p99-slow leaf. Tail behaviour of the parts becomes the median behaviour of the whole.
  • Causes of tail latency: GC pauses, noisy neighbours, background compaction, queueing bursts, cold caches, retransmits, and long-tailed service time distributions (see heavy tails).
  • Tail-tolerant techniques: hedged requests (send a duplicate to another replica after the p95 deadline; take the first reply — costs a few % extra load), tied requests (both copies cancel each other once one starts), timeouts with retry budgets, and partial results (answer from 98% of shards).

  • Write the estimate down with its assumptions; the useful output is knowing which assumption, if wrong by 10×, changes the design.

10 Scaling ML systems

  • Online inference scales out like any stateless service, but with GPU-specific twists: batching raises throughput at the price of latency, so autoscale on queue depth or in-flight requests, not CPU. See LLM Serving and Model Acceleration (quantisation shrinks the per-replica cost).
  • Training is a USL textbook case: data-parallel all-reduce is a coherence cost (κ), the parameter server or a slow data loader is contention (σ). Throughput per GPU dropping as you add GPUs is retrograde scaling in action — see Distributed Training.
  • Feature and embedding lookups fan out per request — exactly the tail-latency setting of §07. Feature stores and vector databases are scaled with caching, replication and sharding.
  • Data pipelines are throughput-oriented: scale out with partitioned stream processing and batch ETL, and watch for skewed partitions (a hot key is σ in disguise).

11 Takeaways

  • Describe load and performance precisely — load parameters plus latency percentiles, never averages alone.
  • Scale stateless tiers out; keep stateful cores up until they cannot fit, then partition.
  • Amdahl: serial work caps speed-up at 1/(1−p). USL: coherence κ makes throughput peak at N* = √((1−σ)/κ) and then fall.
  • Little's law L = λW sizes concurrency; utilisation near 1 explodes latency — plan for 50–70%.
  • Fan-out turns rare slowness into common slowness; hedge, time out, and degrade gracefully.
