Sharding & Replication

Two independent techniques for spreading a database across machines. Sharding (partitioning) splits the data so each node holds only part of it, which scales storage and write throughput. Replication copies each part onto several nodes, which gives availability, read scaling and lower latency. Real systems combine them: every shard is replicated. This page covers how to split keys, how to keep the split balanced as the cluster changes, and how replicas stay in sync, fall behind and take over.

One line: shard for size and writes, replicate for survival and reads, and expect to need both before long.

02 Range partitioning

Each shard owns a contiguous key range, for example [a, f), [f, m) and so on. A router or metadata service maps ranges to nodes.

  • Strength: range scans (ts BETWEEN …, "all keys with prefix user42:") hit one or a few shards, and data stays sorted.
  • Weakness: monotonic keys. With timestamps or auto-increment ids as the key, all new writes go to the last range. One shard is busy and the rest sit idle. Fix it by prefixing the key with something well spread ((sensor_id, ts)) or by hashing.
  • Dynamic splitting: a range that grows past a size threshold splits in two, and one half can move to another node. The number of ranges follows the data volume. A new, empty table starts as a single range, so pre-split it before a bulk load.

03 Hash partitioning and the mod-N trap

Hash the key and assign shard = h(k) mod N. Keys spread evenly whatever their distribution, but ranges are lost, because neighbouring keys land on random shards.

Fraction of keys that move when N → N + 1mod-N: P(h mod N ≠ h mod (N+1)) = N / (N + 1) ideal (consistent): 1 / (N + 1)
  • Going from 10 to 11 nodes with mod-N moves about 91% of the data, which is a full reshuffle at the moment you're short of capacity. Only about 9% actually has to move to fill the new node.
  • Fixes, in rising order of sophistication: a fixed number of partitions much larger than the node count (move whole partitions, never re-hash), consistent hashing, rendezvous (highest-random-weight) hashing, and jump consistent hash for numbered buckets (see hashing beyond the table).

04 Consistent hashing with virtual nodes

Map both keys and nodes onto a ring of hash values. A key belongs to the first node clockwise from it. Adding a node takes over only the arc just before it, so about 1/(N+1) of keys move. With one point per node the arcs are very uneven. Giving each node V virtual nodes (tokens) averages that out.

Load spread with V tokens per node (random placement)share of a node ≈ sum of V arc lengths, each ≈ Exp(mean 1/(N·V)) coefficient of variation of load ≈ 1 / √V
Consistent-hash ring more virtual nodes → flatter load · adding a node moves ~1/(N+1) of keys
  • Heterogeneous hardware: give bigger machines more tokens.
  • Trade-off of many tokens: more metadata, and more peers involved in every rebuild and repair. Some systems have lowered their default token counts for this reason and use placement algorithms in place of purely random tokens.
  • Replicas on the ring: store a key on the next R distinct physical nodes clockwise, skipping tokens owned by nodes already chosen, and ideally spread across racks or zones.

  • Throttle data movement. Rebalancing competes with live traffic for disk and network. Moving data at full speed during a capacity crisis can make the crisis worse.
  • Keep a human in the loop for big moves. Automatic rebalancing combined with automatic failure detection can cascade: an overloaded node looks dead, its data moves, and its neighbours become overloaded in turn.
  • Request routing: clients talk to any node that forwards requests, or to a routing tier, or they cache the partition map themselves. The map normally lives in a consensus store.

06 Hotspots and secondary indexes

  • Hash spreading doesn't fix a hot key. A celebrity's timeline, a viral product or a global counter is one key on one shard. Measure the per-key rate, not just the per-shard rate.
  • Key salting: write to key#0 … key#(S−1) at random, which spreads the writes S ways. Reads then have to gather all S sub-keys and merge them. Apply this only to keys detected as hot.
  • Caching absorbs read-hot keys in front of the shard (see Caching). Request coalescing stops many simultaneous misses for the same key from all reaching the database.

07 Leader-follower replication

One leader accepts writes and streams its log (physical WAL or a logical row-change stream) to followers. Followers apply the log in order and can serve reads.

ModeCommit waits forDurability on leader lossLatency and availability
SynchronousAll (or named) followersNo acknowledged write lostSlowest replica sets the latency, and any replica being down blocks writes
Semi-synchronousAt least one followerSurvives one node lossThe usual compromise
AsynchronousNothing (leader only)Recent writes lost (RPO > 0)Fast; followers lag by an unbounded amount
  • Adding a follower: take a consistent snapshot tagged with its log position, copy it over, then stream the log from that position onward. No write downtime is needed.
  • Consensus replication (Raft or Paxos per shard) is leader-follower where commit waits for a majority and leader election is built into the protocol. Many modern distributed databases use it.

08 Replication lag and the anomalies it causes

With asynchronous followers, a read routed to a follower returns the state as of lag seconds ago. Usually that's milliseconds. Under load, during a long-running query or after a network blip it can be minutes. Move the sliders to see who reads stale data.

09 Failover

  1. Detect: missed heartbeats for longer than a timeout. Too short gives false failovers under load spikes or GC pauses. Too long means minutes of write downtime.
  2. Elect: choose the most up-to-date follower, by consensus or by an external coordinator.
  3. Reconfigure: point clients and the other followers at the new leader, and demote the old one if it returns.
  • Lost writes: with asynchronous replication, writes the old leader acknowledged but never shipped are gone. If they are later discarded while other systems (caches, search, ids already handed out) have seen them, you get inconsistencies that are very hard to debug.
  • Split brain: the old leader didn't actually die, it was only partitioned, and it keeps accepting writes. Guard against it with epochs / fencing tokens that storage checks, leader leases that expire before a new leader is allowed to start, or forcibly cutting the old node off.
  • Practise it. A failover path that never runs will fail when it's needed. Run scheduled failover drills and measure the real RTO (time to recover) and RPO (data lost).

10 Multi-leader and leaderless replication

Letting more than one node accept writes gives local write latency in every region and keeps writes working through partitions. The price is write conflicts.

Conflict handlingHowRisk
Last-write-winsKeep the value with the highest timestampSilently drops concurrent writes, and clock skew decides which one
Version vectors + siblingsDetect true concurrency and return every concurrent version for the application to mergeMerge logic is pushed onto the application
CRDTsData types whose merge is commutative, associative and idempotentOnly for data that fits a CRDT; metadata overhead
Avoid conflictsRoute all writes for a given record to its "home" leaderRe-homing on failure reintroduces conflicts
  • Leaderless (Dynamo-style): the client or a coordinator sends each write to all N replicas and waits for W acknowledgements. Reads ask R replicas. With R + W > N the two sets overlap (details and caveats on CAP Theorem).
  • Catching up stale replicas: read repair writes the newest version back to replicas that returned old ones. Anti-entropy compares Merkle trees of key ranges in the background and syncs the ranges that differ. Hinted handoff has a stand-in node hold writes for a down replica and replay them when it returns.

11 Takeaways

  • Range partitioning keeps scans cheap but creates hotspots on monotonic keys. Hash partitioning spreads load but loses ranges. Never use bare mod N, because changing N moves N/(N+1) of the data.
  • Consistent hashing with virtual nodes moves about 1/(N+1) of keys per added node, and load imbalance shrinks like 1/√V.
  • Hot keys need salting or caching. Local secondary indexes mean scatter-gather reads, and global ones mean asynchronous staleness.
  • Leader-follower replication trades durability against latency (sync, semi-sync or async). Lag causes read-your-writes and monotonic-read anomalies, and failover risks lost writes and split brain unless you use fencing.
  • Multi-leader and leaderless replication give write availability and pay for it with conflict resolution: prefer CRDTs or conflict avoidance over last-write-wins.
