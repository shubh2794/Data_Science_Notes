Transactions (ACID)

A transaction groups several reads and writes into one unit that either happens completely or not at all, and is isolated from other transactions running at the same time. This page covers what each ACID letter guarantees and how engines implement it (write-ahead logging, locking, multi-versioning), the anomalies each isolation level allows, and why distributed commits are harder.

02 Atomicity and durability: the write-ahead log

The rule is to log before writing the data page. Every change is first appended to a sequential log. A transaction is committed at the moment its COMMIT record is durable on disk. Data pages can be written back later, in any order.

  • Steal / no-force: the buffer pool may flush pages containing uncommitted changes (steal), and doesn't have to flush pages at commit (no-force). That gives the best performance, but it means recovery needs both redo (committed changes not yet on disk) and undo (uncommitted changes that reached disk).
  • Recovery (ARIES-style): analysis finds the transactions that were active at the crash, redo replays history from the last checkpoint, and undo rolls back the transactions that never committed.
  • Group commit batches many transactions' COMMIT records into one fsync. Durability per transaction stays the same and throughput goes up. "Async commit" modes acknowledge before the fsync and can lose the last few milliseconds of commits on a crash.
  • The same log feeds replication and change-data-capture. Followers replay it (see Sharding & Replication).

03 Isolation anomalies

Full isolation (serializability) costs throughput, so engines offer weaker levels. Each weaker level permits specific anomalies, which are interleavings whose result matches no serial order.

Dirty writeT2 overwrites T1's uncommitted writeRollback becomes undefined. Every real level forbids it.
Dirty readT2 reads T1's uncommitted write, then T1 abortsActing on data that never existed
Non-repeatable (fuzzy) readT1 reads x, T2 updates x and commits, T1 reads x again and gets a different valueA report whose totals don't add up

PhantomT1 queries rows matching a predicate; T2 inserts a matching row; T1's view of the set is now wrongA count that changes inside a transaction; double-booking

*Lock-based repeatable read holds read locks on the rows it has read, which prevents write skew over those rows. It still allows the phantom form of write skew, where the conflict is over rows that don't exist yet.

  • The ANSI SQL definitions are ambiguous. They are phrased in terms of three phenomena and leave out lost update, read skew and write skew. They also don't place snapshot isolation anywhere. As a result, the same level name means different things in different engines.
  • Examples: PostgreSQL's REPEATABLE READ is snapshot isolation and its SERIALIZABLE is serializable snapshot isolation. Oracle's SERIALIZABLE is snapshot isolation. MySQL/InnoDB defaults to REPEATABLE READ with snapshot reads, but locking reads and updates see the latest version, so an application-side read-then-write can still lose an update.
  • Defaults are weak. Most engines default to Read Committed (InnoDB: Repeatable Read). Unless you've asked for more, assume your code is exposed to every anomaly in that row of the table.

05 Serializability, formally

A schedule is conflict-serializable if you can reorder its non-conflicting operations to get a serial schedule. Two operations conflict when they come from different transactions, touch the same item, and at least one of them is a write.

Precedence (serialization) graphedge Tᵢ → Tⱼ if an op of Tᵢ conflicts with and precedes an op of Tⱼ (w→r, r→w, w→w) schedule is conflict-serializable ⇔ the precedence graph is acyclic
  • Write skew shows up in the graph as a cycle of two read→write anti-dependencies: T1 read what T2 later wrote, and T2 read what T1 later wrote. Neither transaction overwrote the other, which is why snapshot isolation doesn't notice.
  • Strict serializability = serializable and consistent with real time: if T1 commits before T2 starts, T1 comes first in the serial order. It is serializability combined with linearizability.

06 Two-phase locking (2PL)

  • Rule: a transaction acquires locks in a growing phase and releases them in a shrinking phase, and it never acquires a lock after releasing one. This alone guarantees conflict-serializability. Strict 2PL holds write locks (and in practice all locks) until commit, which also prevents cascading aborts.
  • Lock modes: shared (S) for reads and exclusive (X) for writes. S is compatible with S. X is compatible with nothing. Readers block writers and writers block readers.
  • Phantoms need predicate locks: lock "all rows where room = 1 and time overlaps 10:00–11:00", including rows that don't exist yet. Engines approximate this with next-key / gap locks on index ranges, and without a suitable index the gap lock can grow to the whole table.
  • Deadlocks are inevitable. The engine keeps a waits-for graph, detects cycles, and aborts a victim. The application must retry.

07 MVCC and snapshot isolation

Instead of overwriting rows, a writer creates a new version tagged with its transaction id. Each transaction reads from a snapshot: the newest version committed before the snapshot was taken.

Visibility rule (simplified)version v is visible to snapshot S ⇔ creator(v) committed before S ∧ ¬(deleter(v) committed before S)
  • Readers never block writers, and writers never block readers. Only write–write conflicts need coordination. This is why MVCC dominates OLTP engines.
  • Snapshot isolation adds first-committer-wins (or first-updater-wins): if two concurrent transactions write the same row, the second to commit is aborted. That prevents lost updates.
  • The costs: old versions pile up and must be garbage-collected (vacuum or purge). A long-running transaction pins old snapshots, so bloat grows and index scans slow down. Alert on transaction age.
  • Serializable snapshot isolation (SSI) keeps snapshot reads but tracks read→write anti-dependencies between concurrent transactions. When it sees two consecutive ones (a "dangerous structure") it aborts a transaction. It is optimistic: no blocking, occasional false-positive aborts.

08 Distributed transactions: two-phase commit

When one transaction spans several shards or systems, each participant can commit locally, but all of them must make the same decision.

  1. Prepare: the coordinator asks every participant to prepare. A participant that votes YES has durably logged enough to commit and has promised it will commit if told to, even after a crash. It keeps holding its locks.
  2. Commit/abort: if every vote is YES, the coordinator logs COMMIT and tells everyone. If any vote is NO or a participant times out, everyone aborts.
  • 2PC blocks. If the coordinator dies after participants voted YES, they are in doubt: they may not commit or abort on their own, so they hold locks until the coordinator recovers. Running the coordinator's decision through a consensus group (Paxos or Raft) removes the single point of failure at the cost of extra round trips.
  • Latency: at least two network round trips plus forced log writes on every participant. Cross-region 2PC is slow.
  • Alternatives: design aggregates so that one operation touches one shard. Use sagas (a sequence of local transactions with compensating actions) and an outbox with idempotent consumers when the steps span services.

09 Operational practice

  • Always write a retry loop for serialization failures and deadlocks (SQLSTATE 40001 / 40P01). The transaction body must be safe to re-run, so keep side effects such as emails and payments outside it or make them idempotent.
  • Keep transactions short. Never wait for user input or a remote API call while holding a transaction open. Long transactions hold locks (2PL) or pin snapshots (MVCC).
  • Fix specific anomalies cheaply: atomic updates (UPDATE … SET n = n + 1) instead of read-modify-write, SELECT … FOR UPDATE to lock what you read, unique or exclusion constraints to stop double-booking, or "materialising the conflict" as a row everyone must lock.
  • Durability is a setting. Check the fsync/sync-commit settings, the disk write cache, and whether commit waits for a replica. Test it by actually cutting power to a staging node.
  • Monitor: abort and retry rates, lock waits, deadlocks per minute, oldest running transaction, MVCC bloat and replication lag. A climbing serialization-failure rate is an early sign of a contention hotspot.

10 Takeaways

  • The WAL gives you atomicity and durability. Commit is the moment the COMMIT record is durable, and recovery redoes committed work and undoes the rest.
  • Isolation levels are lists of permitted anomalies. The same name can mean different things in different engines, so check what yours actually prevents.
  • Snapshot isolation is not serializable: write skew and its phantom form get through. SSI or 2PL closes the gap.
  • 2PL is pessimistic, blocks, and deadlocks. MVCC doesn't block but needs garbage collection. SSI doesn't block but aborts and needs retries.
  • 2PC makes multi-shard commits atomic but blocks when the coordinator fails. Prefer single-shard designs or sagas.
