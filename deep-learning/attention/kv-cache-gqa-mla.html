24 The KV cache: what it stores, and why generation would be impossible without it

The KV cache is the stored keys and values of every token already processed, kept per layer so that each new token computes only its own q, k, v, appends k and v, and attends against the store. Autoregressive generation runs the model once per output token; done naively that is O(n²) work per token and O(n³) for the sequence, and the cache turns the first into O(n) — creating, in the process, the object that governs every inference cost from here on.

the observation the cache rests on, which is a consequence of §15's maskUnder a CAUSAL mask, position j attends only to positions ≤ j. So kⱼ and vⱼ depend only on x₁ … x_j and appending a new token x_{n+1} CANNOT CHANGE any earlier key or value. They are final the moment they are computed. (Without causality this is false, which is why a bidirectional encoder cannot be decoded incrementally at all.) so one decode step, with and without the cacheWITHOUT recompute everything for the whole prefix: Q, K, V for n+1 positions → 3(n+1)·d·(…) MACs scores and gather → 2(n+1)²·d MACs per token: O(n²). Whole sequence: O(n³). WITH compute Q, K, V for the ONE new token, append K and V: projections 2·d² + 2·d·(g·dₖ) MACs ← no n at all (W_Q and W_O, then W_K and W_V) scores q·Kᵀ n·(h·dₖ) = n·d MACs gather A·V n·(h·d_v) = n·d MACs per token: O(n). Whole sequence: O(n²). The cache does not make generation cheap. It makes it POSSIBLE, and it converts a compute problem into a MEMORY problem — which §26 shows is the harder kind on current hardware.

Note what the second block says about the arithmetic. Per generated token, per layer, the model does ≈ 12d² MACs against the weights (four attention projections plus a classic 4d FFN; a SwiGLU FFN makes it somewhat more) and 2nd MACs against the cache. At d = 4096 and n = 8192 those are 2.0e8 and 6.7e7 — the cache term is a quarter of the arithmetic. But the bytes tell a completely different story, and §26 is that story.

Two things the cache is not. It is not an optimisation you can turn off for long sequences to save memory and pay in time — the recompute cost is quadratic per token, so the trade is catastrophic, not marginal. And in its basic form it is not a cache in the usual sense: there are no misses, no eviction policy, and nothing is being re-derived more cheaply (serving systems do add eviction and prefix sharing on top, but that is bookkeeping around the object, not the object itself). It is a materialised intermediate result whose size is dictated by the architecture. Everything in §27 and §28 is an attempt to make that materialised result smaller without changing what it means.

Three readings of that table are worth making explicit.

  • Llama-2 7B at 128k context would need 64 GiB of cache for a single sequence — five times the 12.6 GiB its own weights occupy in bf16 (6.74 B parameters × 2 bytes). This is the observation that made the KV cache an architectural concern rather than an implementation detail: past some context length the cache is bigger than the model. For Llama-2 7B that length is 12.55 GiB / 512 KiB ≈ 25 700 tokens.
  • The cache scales with layers, not with width. Llama-3 70B has nearly nine times the parameters of Llama-3 8B and only 2.5 times the cache, because both use g = 8 and dₖ = 128 and the only difference is 80 layers against 32. Cache cost and parameter cost are genuinely different axes.
  • Batch multiplies it and nothing amortises it. Serving 32 concurrent 8k-token conversations on Llama-3 70B is 32 × 8192 × 320 KiB = 80 GiB of cache, on top of 131.5 GiB of weights. The weights are shared across all 32; the cache is not. That single asymmetry is what makes inference economics what they are.

26 Why the cache binds and the arithmetic does not: arithmetic intensity

At decode, attention does about one multiply–accumulate per byte of cache it reads, while the accelerator can do a hundred or more per byte it fetches from memory; the step is therefore limited by memory bandwidth, not arithmetic, and its time is the time to read the cache. That one ratio — arithmetic intensity — is why the variants aimed at decode (MQA, GQA, MLA, cache quantisation) are about bytes and not about operations. One derivation, one number per configuration, and the question is settled for the decode step.

the arithmetic intensity of one decode step's attention over the cache MACs = n·(h·dₖ) for q·Kᵀ + n·(h·d_v) for A·V = 2·n·h·dₖ bytes = 2·n·(g·dₖ)·b reading K and V out of memory, b = bytes per element intensity I = 2·n·h·dₖ / (2·n·g·dₖ·b) = h / (g·b) MAC per byte ─────────────────────── the sequence length CANCELS. in FLOP per byte, which is how hardware quotes its peak (2 FLOP per MAC): I = 2h / (g·b) — the unit the table below uses Two consequences, both decisive: 1 · I does not depend on n. A longer context does not make the attention step more or less compute-bound; it makes it uniformly bigger. 2 · I does not improve with BATCH. Batching amortises the WEIGHTS — one read of W serves B sequences — but every sequence owns its own cache, so the cache read scales with B exactly as the arithmetic does. The one lever that fixes every other memory-bound operation does not touch this one.

Read the decode-efficiency literature through this one number. I = h/(g·b). Within the formula there are three levers: reduce g (MQA and GQA, §27), reduce b (cache quantisation), or reduce the bytes per token some other way (MLA's low-rank cache, §28). Outside the formula, the remaining options all reduce how much of the cache is read per step rather than the intensity of reading it: cap n with a sliding window (§29), share one cache across several layers, or read only a selected subset of the cache for each query. None of them is about doing less arithmetic — the arithmetic was never the problem.

27 MQA and GQA: fewer key/value heads, and exactly what that costs

§25's formula has one term the architect can shrink without touching the query side: g, the number of key/value heads. Setting it to 1 is multi-query attention; setting it between 1 and h is grouped-query attention. The saving is exact, the quality cost is real and small, and the reason it is small is worth understanding.

Why the quality cost is smaller than the compression suggests

Going from 32 KV heads to 8 removes three-quarters of the cache, and the quality loss is small enough that most recent model families have taken the trade. Three reasons, in decreasing order of confidence:

  • The query side is untouched. §12 established that the binding constraint is the number of independent selections, and that is h, not g. GQA keeps all 32 attention maps; it only makes the things being selected from shared. A group of four query heads reading one key set can still attend to four completely different positions.
  • Heads within a group were already correlated. §12's own measurement showed seeds putting two heads on the same relation. Real models have measurable redundancy between neighbouring heads, and a shared key/value set is a way of paying for it once.
  • It can be added to an existing model cheaply. A trained multi-head checkpoint is converted by mean-pooling the key and value projections within each group — which works better than picking one head's or reinitialising — followed by a short continued-training run at a small fraction of the original pretraining compute. That an averaged initialisation recovers is itself evidence that the heads within a group were doing similar things.
Query heads to key/value heads: the mapping, the cache and the intensity watch the cache and the parameters fall by h/g while the quadratic-MAC line does not move at all
The misreading to avoid. "GQA makes attention cheaper." It makes the cache and the projections cheaper and leaves the quadratic term exactly where it was. During prefill — processing the prompt — the quadratic term is untouched and the only saving is on the K and V projections, which takes the projection term from 4nd² to 2.5nd² at g = h/4: worth a few per cent of a layer at the lengths in §19's table, and less as the prompt grows. Its real value is at decode, where the cost is bytes read per generated token, and there it buys a factor of h/g on the binding resource. Two different phases, two different bottlenecks; a variant that fixes one may do nothing for the other.

28 Multi-head latent attention: compress the cache instead of sharing it

GQA shrinks the cache by making heads share. The other option is to keep every head distinct and store a low-rank latent from which the keys and values are reconstructed. It reaches a smaller cache than GQA at quality reported to match or exceed full multi-head attention, and the trick that keeps the reconstruction off the per-token byte budget is worth seeing.

the construction compress c_t = x_t · W_DKV c_t is d_c wide, d_c ≪ h·dₖ expand k_tᶜ = c_t · W_UK per head, on demand v_t = c_t · W_UV CACHE c_t ONLY. d_c numbers per token per layer, instead of 2·g·dₖ. The keys and values are never stored; they are recomputed from c_t, which costs arithmetic and saves bytes — which §26 says is exactly the right direction. the complication: ROTARY POSITION. A rotation applied to k depends on the position t, so it cannot be folded into a position-independent W_UK. The fix is to carry a small SEPARATE rotary key: decoupled k_tᴿ = RoPE( x_t · W_KR ) dₕᴿ wide, SHARED by all heads cached per token per layer: d_c + dₕᴿ the trick that keeps the expansion off the byte budget at decodeThe score a query head needs is, in the row convention (q, c row vectors): q · kᶜᵀ = q · ( c·W_UK )ᵀ = q · W_UKᵀ · cᵀ = ( q·W_UKᵀ ) · cᵀ └────┬────┘ re-associate: a d_c-wide "absorbed" query So instead of expanding c into a key and then dotting, ABSORB W_UK into the query projection ONCE, and dot the (already-absorbed) query directly against the cached latent c. The same trick absorbs W_UV into W_O on the output side. At decode, MLA therefore never materialises a key or a value: it attends against the latent directly. What it pays is ARITHMETIC — each head now dots a d_c-wide query against a d_c-wide latent, d_c/dₖ = 4 times the work of a 128-wide key — and §26 says arithmetic is the resource that was never binding.

The headline number, checked. The report's abstract says MLA "reduces the KV cache by 93.3%". That figure is not the MLA-against-MHA ratio, and it is not reproducible from the architecture alone. Recomputed against the previous generation's published shape — 95 layers, 64 query heads, GQA with 8 KV heads, dₕ 128, which is 2·8·128·95 = 194 560 elements per token, or 380.0 KiB in bf16 — the new model's 34 560 elements are 67.5 KiB, a reduction of 82.24%. The missing factor is that the report also quantises the deployed cache to 6 bits per element on average: 34 560 × 0.75 = 25 920 bytes = 25.3 KiB, and 1 − 25.3/380.0 = 93.34%. The report does not spell out this derivation; it is the reconstruction that reproduces the headline to four significant figures. So the headline is architecture plus quantisation, against a GQA baseline with a different layer count — not the attention mechanism on its own. The mechanism's own number is 82.2% against that baseline, or 98.2% against an MHA of the same shape. All three are defensible; only one is what the sentence sounds like.
