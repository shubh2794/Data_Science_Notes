Convolutional Networks

Part 1 built the function class and part 2 built the machinery that fits it. Both are architecture-neutral: they know nothing about what the input coordinates mean. This page is the first architecture, and it is the cleanest example in the whole series of a simple idea — put a hard constraint on the weight matrix and the constraint becomes knowledge. A convolution layer is a dense layer whose matrix is forced to be banded (each output sees a small window) and tied (the same weights are reused at every position). Nothing else changes: the same forward pass, the same loss, the same backward pass, the same optimiser. What changes is that the layer now assumes the input lives on a grid, and that assumption is worth several orders of magnitude of parameters and a great deal of sample efficiency — right up to the point where it is false.

Every number on this page was recomputed against an independent implementation before it was printed: every shape, every parameter and multiply-accumulate count, every receptive field (measured by perturbing one input pixel, not just by applying the formula), and the backward pass (audited against central differences). Where a common presentation gets an arithmetic detail wrong, the page teaches the discrepancy rather than repeating it.

01 What a convolution layer is, and the conventions this page never departs from

One sentence, and then the rest of the page is that sentence in detail: a convolution layer is an affine map, exactly like part 1's dense layer, whose weight matrix is constrained to be banded and tied. Banded means an output unit sees only a small contiguous window of the input. Tied means every output unit uses the same window of weights, just slid to a different place. Both constraints are hard — the forbidden weights are not penalised toward zero, they do not exist.

That ratio — ten numbers standing in for two and a half billion — is the whole story, and §02 and §03 make it precise. Everything after that is bookkeeping: how the window is placed (§08), how channels stack (§10), what it costs (§12), how far each output can see (§14), what to do when the plain version is too expensive (§20–§22), and how the gradient flows back through it (§25).

02 Why a dense layer fails on a grid: the arithmetic, done explicitly

The standard motivation for convolution is "too many parameters". That is true and it is the least of the three problems. Do the arithmetic first, then read off all three.

The parameter count, for a real image

Take a 224×224 colour image — the input size the entire ImageNet lineage in §28 uses. Flatten it, as an MLP must, and feed it to a first hidden layer of 1000 units:

flattening a 224 × 224 × 3 image into a 1000-unit dense layerdᵢₙ = 224 · 224 · 3 = 150 528 W₁ is (150 528 × 1000) = 150 528 000 weights + 1 000 biases = 150 529 000 parameters at fp32, 4 bytes each = 602 MB — for ONE layer's weights with Adam (part 2 §22: two moment buffers + the gradient, all fp32) = 2.41 GB of optimiser state and that is the SMALL image. At 512 × 512 × 3dᵢₙ = 786 432 W₁ = 786 432 000 weights into 1000 units. against a convolution layer producing SIXTY-FOUR full-resolution feature maps64 filters, each 3 × 3 × 3, one bias each = 64 · (3·3·3) + 64 = 1 728 + 64 = 1 792 parameters output = 224 × 224 × 64 (same padding) The dense layer that produced the SAME 224·224·64 outputs from the SAME 150 528 inputs would need 150 528 · 3 211 264 ≈ 4.83 × 10¹¹ weights. Ratio of dense to convolutional parameters: 2.70 × 10⁸.

Two hundred and seventy million to one. And the convolution's 1 792 parameters produce more outputs (3 211 264 of them) than the dense layer's 150 million produce (1 000).

The three problems, in increasing order of severity

problem 1 — the obvious one
Memory and compute
602 MB of weights per layer, 2.41 GB of Adam state, and 150 million MACs per example for a layer that has not yet done anything useful. This is the problem everyone quotes and it is the easiest to fix by throwing hardware at it.
problem 2 — the statistical one
Sample efficiency
Each of those 150 million weights is used once per forward pass and must be estimated from data. A convolution's nine weights are used 50 176 times per forward pass, so every training image supplies 50 176 constraints on each of them. That is where the generalisation gap comes from, and no amount of hardware fixes it.
problem 3 — the fatal one
It does not know the pixels are a grid
Part 1 §24 proves it: shuffle every image's pixels by one fixed permutation and an MLP's achievable accuracy is exactly unchanged. Its optimum simply moves to the permuted weights. It must learn from data that pixel 5 and pixel 6 are neighbours and that pixel 5 and pixel 30 000 are not — and it must learn that separately for every pair.

Problem 3 is the one that matters, and it explains why problem 2 is unfixable by scale alone in the small-data regime. Convolution addresses all three at once with a single structural change, and §05–§07 name the three parts of that change.

Parameters, memory and weight reuse: dense against convolutional, on the same layer both bars are computed from the same layer specification; the reuse column is the one that predicts generalisation, and it is the one a parameter count hides
The misreading. "Convolution is a compression trick — it approximates the dense layer with fewer parameters." It is not an approximation of anything. A convolution layer is not a low-rank or sparse estimate of the dense layer it replaces; it is a different hypothesis class, chosen because the functions it can represent are the ones that are plausibly true of images and the ones it cannot represent are the ones that are not. If you want the compression framing, the honest version is part 2 §31's: it is a regulariser, and specifically it is the infinitely strong one of §06.

03 Banded and tied: what the constraint looks like as a matrix

Before any picture of a kernel sliding over an image, it is worth seeing the layer as part 1 would: a matrix. Convolution is a linear operation, so it is a matrix, and everything special about it is visible in that matrix's structure.

The 1-D case, written out

Take a 5-long input, a 3-long kernel (w₀, w₁, w₂), stride 1, no padding. Three outputs. The matrix is:

z = x Mᵀ, or equivalently zᵀ = M xᵀ — the 3 × 5 matrix M of a 1-D convolution layer ⎡ w₀ w₁ w₂ 0 0 ⎤ M = ⎢ 0 w₀ w₁ w₂ 0 ⎥ each row is the row above, shifted right by s ⎣ 0 0 w₀ w₁ w₂ ⎦ the two structural facts, namedBANDED 15 entries, of which 6 are structurally zero. The non-zeros of row i occupy columns i·s … i·s + f − 1 and nowhere else. TIED the 9 non-zero entries take only 3 DISTINCT VALUES. A matrix whose every diagonal is constant is a TOEPLITZ matrix; this is a Toeplitz matrix with its corners cut off. In 2-D the same object is a doubly block Toeplitz matrix — blocks of Toeplitz blocks. and the consequence for the countdense H′·H free parameters conv f free parameters, independent of H and H′ entirely.

The figure in §01 draws exactly this matrix, at whatever size and stride you choose, with one colour per free parameter. Two things are worth watching in it. First, stride removes rows, not columns: increasing s shrinks the output and therefore the matrix's height, while the band width stays f. Second, under valid padding the first and last columns carry fewer non-zeros than the middle ones — that is the border pixels being used less often, which is the entire motivation for padding in §08.

Why this matters more than it looks

Goodfellow's framing, and the best one: a convolutional network is a fully connected network with an infinitely strong prior over its weights. A prior is strong when it concentrates probability mass; it is infinitely strong when it puts zero mass on some parameter values, forbidding them regardless of what the data says. The convolutional prior says two things and both are infinitely strong:

every off-band weight is exactly 0andevery on-band weight equals its neighbour's, shiftedthereforethe layer's function is local and translation-equivariant, and nothing the data says can change that

Two consequences follow immediately, and both are easy to forget. (1) A convolution can underfit for structural reasons. If the true function needs a long-range interaction that no stack of local windows can reach, or if the right feature genuinely differs between the top and the bottom of the image, the prior is wrong and the training error — not just the test error — will be higher than a dense layer's. §29 is about exactly this case. (2) Benchmarks that compare a convnet to a non-convolutional model are comparing priors, not learning algorithms. A model that would be unaffected by shuffling the pixels is solving a strictly harder problem, and image datasets often keep separate leaderboards for the two.

The bridge to part 2. Because a convolution is a matrix, every single thing part 2 says still applies verbatim. The gradient is computed by the same reverse-mode sweep (part 2 §05); the vanishing-gradient analysis (§09) is the same product of Jacobians; the initialisation variance argument (§12) needs only the right fan-in, which §12 here supplies; the optimisers do not know they are optimising a kernel. The only new thing is that the parameter-tying makes the gradient of a shared weight a sum over all the positions that used it, which §25 derives and audits.

04 The operation itself, and the correlation-versus-convolution naming, stated once

There are two operations here and they differ by a flip of the kernel. Almost every framework implements one and calls it the other. This section says which is which, once, and then the page uses the framework convention everywhere and never mentions it again except where it genuinely matters — which is exactly one place, §25.

the two operations, on a 2-D input I and kernel K, indices from 0TRUE CONVOLUTION S(i, j) = (I ∗ K)(i, j) = ∑ₘ ∑ₙ I(i − m, j − n) · K(m, n) CROSS-CORRELATION S(i, j) = (I ⋆ K)(i, j) = ∑ₘ ∑ₙ I(i + m, j + n) · K(m, n) the only differenceI ∗ K = I ⋆ flip(K) where flip(K) reverses BOTH axes: flip(K)(m,n) = K(f−1−m, f−1−n) Convolution FLIPS the kernel; correlation does not. That is the whole of it. what the flip buys, and what it costsbuys commutativity: I ∗ K = K ∗ I. Useful for writing proofs, and it is what makes the convolution theorem (see Frequency Domain) work. costs nothing a network cares about. A LEARNED kernel will simply learn the flipped version of whichever kernel the other convention would learn, and the two networks are exactly as expressive.

So: every deep-learning framework's conv2d computes the cross-correlation and calls it convolution. This page follows that usage. When the flip actually matters — and it does, exactly once, in the backward pass — the page says "true convolution" or "flipped" explicitly.

The scope handover. Classical vision cares about the distinction for a different reason: there the kernel is designed, so a flip is a real change to a real filter, and it interacts with symmetry, separability and the frequency response. That treatment — with the same worked examples on both operations, all five border modes and the verified numerics — is Image Processing §correlation vs convolution. The framing that connects the two pages: a convolution layer is designed filtering with the kernel learned instead, and the flip stops mattering the moment the kernel becomes a variable.

Correlation, convolution, and the flip — one window at a time step the window and watch the products accumulate; the flip toggle changes only which kernel cell multiplies which pixel, and the two output maps differ by exactly the sign when the kernel is antisymmetric
A real trap, not a pedantic one. "The two are the same, so it does not matter." It matters in three specific places. (1) When you port a hand-designed kernel from a signal-processing reference into a network, you must flip it or your edge signs invert. (2) When you compare a learned first-layer filter against a textbook Sobel, they will look mirrored. (3) In the backward pass the flip is forced: §25 shows that the gradient with respect to the input is a true convolution with the kernel even though the forward pass was a correlation, and getting that wrong produces a network that trains to a plausible-looking but wrong solution rather than crashing.

05 Motivation 1 — sparse interactions, and what they cost you

The three motivations are sparse interactions, parameter sharing and equivariance to translation. They are often run together; they are three different things, each with its own arithmetic, and the next three sections take them one at a time. This one is about the band of §03 and nothing else — forget for a moment that the weights are also tied.

the statementDENSE every output unit is a function of EVERY input unit. m inputs, n outputs → m·n parameters, O(m·n) work per example. SPARSE every output unit is a function of at most k input units. m inputs, n outputs → k·n parameters, O(k·n) work per example. and k is tinyFor a 3 × 3 kernel on a 3-channel input, k = 27. For a 224×224×3 image, m = 150 528. The ratio k/m is 1.79 × 10⁻⁴ — four orders of magnitude, and that is BEFORE the weights are tied. Sparsity alone gets you from m·n to k·n; §06's tying then gets you from k·n to k.

Two named quantities fall out of the band, and both are used constantly for the rest of the page.

looking down
The projective field
Fix one input pixel and ask which outputs it can reach. For a single f×f layer at stride 1, that is an f×f block of outputs — 9 for a 3×3 kernel, out of however many outputs there are. Under a dense layer it is all of them.
looking up
The receptive field
Fix one output unit and ask which inputs can reach it. For one layer that is the f×f window. Stacked, it grows — and §14 works out exactly how fast, and measures it rather than asserting it.
the catch
A single layer cannot see far
Sparsity is a restriction. A one-layer 3×3 convolution simply cannot represent any function that depends on two pixels 50 apart. The answer is depth: §14 shows that stacking L layers of 3×3 gives a receptive field of 2L + 1, so the restriction is on each layer, not on the network. This is exactly why convnets are deep.

The sharpest way to feel it: take the two-tap kernel [1, −1], which subtracts each pixel from its left neighbour and so reports vertical edges, and apply it to a 320×280 image. Both descriptions below define exactly the same linear map:

06 Motivation 2 — parameter sharing, and the infinitely strong prior

Sparsity says each output looks at a small window. Sharing says every window is looked at by the same weights. These are independent choices: a layer can be sparse without being shared, and §29 is about the architectures that make exactly that choice.

the three connectivity patterns, in increasing order of constraintFULLY CONNECTED every output sees every input, all weights distinct parameters m · n LOCALLY CONNECTED every output sees a k-window, all weights distinct (unshared conv) parameters k · n CONVOLUTIONAL every output sees a k-window, ALL WINDOWS SHARE ONE SET parameters k — independent of n entirely the runtime does NOT change between the last twoBoth do O(k·n) work per example. Sharing buys STORAGE and STATISTICAL EFFICIENCY, not arithmetic. This is the single most-missed point about convolution and it is why §12's MAC counts are so much less impressive than its parameter counts.

Why sharing is worth so much more than the parameter count suggests

Count the other way round. A dense weight is used once per forward pass, so one training example supplies one constraint on it. A convolutional weight is used once per output position, so one training example supplies H′·W′ constraints on it. On a 224×224 map that is 50 176 constraints per image, per weight. The estimation problem the optimiser faces is not "150 million parameters from 1.2 million images" but "1 792 parameters from 60 billion constraints" — and that difference, not the memory, is why a convnet generalises from data an MLP cannot learn from at all.

One parameter, many uses — and the same weight matrix under the three connectivity patterns the highlighted parameter is a single number; watch how many edges it controls as the pattern changes, and watch the parameter count collapse while the edge count does not

The infinitely strong prior, and the two things it predicts

§03 introduced the framing; here is the payoff. A prior distribution over the weights of a fully connected layer that puts zero probability on every non-convolutional weight vector is equivalent to a convolution layer. The prior says: the weights of one hidden unit must equal those of its neighbour, shifted; and they must be zero outside a small contiguous window. This is not an analogy, it is an exact restatement, and two non-obvious things follow from it.

prediction 1
Convolution can cause underfitting
A prior helps when it is true and hurts when it is false. If a task needs precise spatial information, or needs a genuinely different feature at the top of the image than at the bottom, the convolutional prior is wrong and the training error rises — not just the test error. That is the diagnostic signature: high training error that more capacity does not fix. Faces cropped and aligned to a fixed frame are the standard example, and §29 gives the architectures that relax the prior.
prediction 2
Only compare like with like
A model with no spatial prior would perform identically if you permuted every image's pixels (part 1 §24). It is solving a strictly harder problem. Benchmarks that mix the two are measuring the designer's prior knowledge, not the learning algorithm — which is why several image datasets keep separate permutation-invariant leaderboards.
and the corollary
Sharing is a regulariser with a name
Part 2 §31's map lists parameter sharing as a regularisation strategy alongside L2 and dropout, and this is why: it is the hard-constraint limit of a penalty that ties parameters together. Unlike L2 it costs nothing at inference and unlike dropout it changes the model class rather than the training procedure.

07 Motivation 3 — equivariance to translation, and its boundaries

The third motivation is the one that is stated loosely most often. Here it is precisely, with the caveats that make it almost true rather than true.

the definitionA function h is EQUIVARIANT to a transformation g when h(g(x)) = g(h(x)) "transform then process" and "process then transform" give the same answer. Contrast INVARIANCE, which is the strictly stronger and quite different h(g(x)) = h(x) the claim for convolutionLet Tₐ shift an image by a pixels. For an INFINITE image, or in the interior of a finite one, conv(Tₐ x) = Tₐ conv(x) (stride 1) Move the object; its representation moves the same amount and is otherwise unchanged. A feature map is therefore a MAP OF WHERE things are, not a summary of whether they are there.

Read the consequence carefully, because it is what makes the whole architecture work: a convolutional layer does not learn "there is an edge here" — it learns "this is what an edge looks like" and then reports where. One kernel is a statement about a pattern, applied everywhere at once. That is exactly what makes it reusable across positions and exactly why parameter sharing is legitimate.

The three ways the claim is not quite true

caveat 1
Borders
Equivariance is exact only where the shifted window still lies inside the image. Near the edge, padding invents values that do not shift with the content, so a shift and a convolution do not commute there. The figure measures the interior error (exactly zero) and the border error (not) separately.
caveat 2
Stride
A stride-s layer is equivariant only to shifts that are multiples of s. Shift by one pixel under stride 2 and the output is not a shifted version of anything — the sampling grid moved relative to the content. This is aliasing, and §19 is about it.
caveat 3
Everything that is not a translation
Convolution is not equivariant to rotation, to scale, to reflection or to any affine warp. Nothing in the construction gives you those; they must come from augmentation (part 2 §35), from an architecture that builds them in, or from data. This is the gap §30 and §31 are about.
Shift then convolve, against convolve then shift the difference map is the whole claim: it must be exactly zero in the interior, and the readout prints the interior and border errors separately rather than a single number that would hide the distinction
Equivariance is not invariance, and the difference is the subject of §18. A convolution layer is equivariant; a pooling layer is (approximately) invariant; a global pooling layer is exactly invariant to any permutation of positions, translation included. Which of the two you want depends entirely on the task, and choosing wrongly is a real and common architectural error. §18 states both properties precisely and measures them; §30 is the argument that the whole architecture chooses wrongly.

Why padding exists at all — two reasons, not one

reason 1
The map shrinks
Without padding each layer costs f − 1 pixels. Thirteen 3×3 layers on a 32×32 input leave 32 − 26 = 6 pixels; on a 28×28 input they run out entirely. The shrinkage bounds the depth, which is fatal for an architecture whose whole strategy is depth.
reason 2
The border is under-used
Under valid padding a corner pixel is read by exactly one output and a central pixel by f² of them. The §01 figure draws the per-position count directly. Information at the edge of the frame is systematically down-weighted, and padding restores the balance — partially.
and the cost
Zeros are a signal
Padding does not create information; it creates a detectable border artefact. A network can and does learn to read the ring of zeros as a position cue, which is one of the ways a "translation-equivariant" architecture leaks absolute position. It is a small effect and a real one, and it is why same padding is a compromise rather than a solution.

Shape arithmetic is arithmetic, so it either works or it throws — except in the four cases below, where it works and is wrong. Every one of these costs a real debugging session at least once.

Trap 1 — the floor discards input, silently

The floor is doing exactly what it says: a window that would hang off the end is rejected. But nothing warns you, the shapes are all consistent, the loss goes down, and a strip of the input is simply invisible to the model. Odd input sizes with even strides are where this bites; it is the reason architectures are so fond of powers of two.

Trap 2 — same padding is not always symmetric

when the required total padding is odd, one side gets moren = 8, f = 3, s = 2 → total P = 1 → p = (0, 1) ASYMMETRIC n = 7, f = 4, s = 1 → total P = 3 → p = (1, 2) ASYMMETRIC n = 7, f = 3, s = 1 → total P = 2 → p = (1, 1) symmetric The convention, in both major frameworks: the EXTRA pixel goes on the RIGHT and the BOTTOM. p₀ = ⌊P/2⌋, p₁ = P − p₀.

The consequence is a portability trap. A framework's padding=1 integer argument means symmetric padding and cannot express (0, 1) at all; a framework's padding="same" string can. So a model that used a string policy with an even kernel or an awkward stride cannot be reproduced by an integer padding, and the reimplementation will be off by one pixel in a way that shifts every feature map by half a position and degrades accuracy without ever erroring.

Trap 3 — an even kernel cannot be same with symmetric padding, ever

the two-line proofWith symmetric integer padding p on both sides and stride 1: n′ = n + 2p − f + 1 For n′ = n we need 2p = f − 1. If f is EVEN then f − 1 is ODD, and no integer p satisfies it. Therefore: an even kernel with symmetric padding always changes the size, by an odd number, whatever p you choose.

This is the real reason kernels are odd. It is not that odd kernels are more expressive — a 4×4 kernel has more parameters than a 3×3 one — it is that an odd kernel has a centre, so "the output at position i is a function of the input around position i" is a true statement with no half-pixel offset in it. With an even kernel the output grid sits half a pixel off the input grid, and after several layers those half-pixels accumulate into a real misregistration. §14's start column tracks exactly this quantity.

Trap 4 — several input sizes give the same output size

the floor is not injectivef = 3, s = 2, valid: n = 7 → n′ = 3 n = 8 → n′ = 3 f = 3, s = 2, same: n = 7 → n′ = 4 n = 8 → n′ = 4 Given only n′ = 3, f = 3 and s = 2, the input could have been 7 or 8. why this matters laterA transposed convolution (§23) has to UNDO this map, and it cannot: the information about which n produced n′ is gone. 10 Convolution over volumes: why a filter is three-dimensional

Everything so far has been one channel. Real inputs have three (colour) and real hidden layers have hundreds. The extension is small but it is the point at which most people's mental picture goes wrong, so it is worth being exact: a filter is not 2-D and slid over channels — it is 3-D and slid only over space.

one filter, one output channel — NCHW throughout (§01)input V (Cᵢₙ, H, W) filter K (Cᵢₙ, f, f) ← as deep as the input, ALWAYS bias b a scalar output Z (1, H′, W′) ← ONE map, however many input channels there were Z[p][q] = b + ∑ over c = 0 … Cᵢₙ−1 ∑ over m = 0 … f−1 ∑ over n = 0 … f−1 V[c][p·s + m·d − p₀][q·s + n·d − p₀] · K[c][m][n] read the three sumsm and n slide — the window MOVES over rows and columns c does NOT slide — the sum runs over ALL channels at every position So the channel axis is CONTRACTED AWAY, exactly like the summation axis of a matrix product. That is why one 3-D filter produces one 2-D map: the depth was consumed, not traversed.

Three consequences follow, and each is a common source of confusion:

consequence 1
The output has no depth of its own
A 3×3×3 filter on a 6×6×3 input gives a 4×4 map — a single flat map, not a 4×4×3 volume. Depth in the output comes from having many filters (§11), never from one.
consequence 2
The filter's depth is not a choice
You choose f; Cᵢₙ is dictated by whatever the previous layer emitted. The only free choices in a conv layer are the spatial size, the number of filters, and the geometry. This is why a shape error in a convnet is almost always a channel-count error.
consequence 3
Channels can be mixed selectively
Nothing forces every output channel to see every input channel. Restricting each filter to a subset of the input channels is grouped convolution (§20), and taking the subset to be a single channel is depthwise (§21). Both are just this sum with a shorter range on c.
One 3-D filter on a 3-channel input: three windows, one number the three per-channel partial sums are shown separately and then added; changing the filter's depth-slices changes which channel dominates, and the output map is a single flat map whatever you do
The picture that causes the confusion. "The kernel slides across the image and also across the channels." It does not slide across channels. There is no such thing as a "position" along the channel axis for the window to be at — the sum over c is complete at every spatial position. If a kernel did slide over channels you would have a 3-D convolution, which is a real and different operation (used on video and volumetric scans, §34), and its kernel would be (Cᵢₙ, f_t, f, f) with a fourth sliding axis.

What a filter is, said plainly

A filter is a pattern detector with a single template. Its Cᵢₙ·f·f weights are a small volume of numbers; the layer computes the inner product of that volume with every equally-sized window of the input; and the output map is high where the window resembles the template and low where it does not. A layer with 64 filters is asking 64 independent "does this look like…?" questions at every position simultaneously. The channel axis of a feature map is therefore a list of questions, and the spatial axes are where they were asked — which is why global pooling over space (§17) is a summary of whether, and the spatial map is a record of where.

A bank of filters, and the stack it produces each filter is an independent template; the stack on the right is the layer's output, and the channel you select there is produced by exactly one filter on the left

14 The receptive field, layer by layer — computed, and then measured

A single 3×3 layer can only see 3×3. A network of them can see the whole image. How fast that happens is the single most important design quantity in a convolutional architecture: if the receptive field of the last layer is smaller than the object you are trying to recognise, no amount of training will fix it.

the recursion — three quantities, tracked together, one line eachstart: r₀ = 1 j₀ = 1 c₀ = 0.5 jₗ = jₗ₋₁ · sₗ rₗ = rₗ₋₁ + (fₑ,ₗ − 1) · jₗ₋₁ cₗ = cₗ₋₁ + ((fₑ,ₗ − 1)/2 − p₀,ₗ) · jₗ₋₁ what each one isrₗ RECEPTIVE FIELD. How many input pixels, along one axis, can change this unit's value. This is the number people quote. jₗ JUMP (or effective stride). How far apart, in INPUT pixels, two adjacent units of layer l are. The product of every stride so far — it is why a single stride-2 layer doubles the receptive-field growth of EVERY layer after it, not just its own. cₗ CENTRE of unit 0, in input coordinates. Nobody tracks this and it is why feature maps end up misregistered with their inputs. Half-integer values are the even-kernel offset of §09 trap 3.

The two rules worth memorising

stride 1, kernel f
Growth is additive
Each layer adds f − 1. So L layers of 3×3 give r = 2L + 1: five layers see 11 pixels, ten see 21, twenty see 41. To cover a 224-pixel image at stride 1 you would need 111 layers. Stride-1 stacking alone is far too slow.
with downsampling
Growth becomes multiplicative
A stride-2 layer doubles j, and every subsequent layer's contribution (f−1)·j is doubled with it. Five stride-2 stages multiply j by 32, and the same 3×3 layers now add 64 pixels each. This is why every classification convnet downsamples: not to save compute, but to make the receptive field grow geometrically.
and the trap
Padding does not change r
Padding changes the output size and the centre c, and leaves r and j completely alone. A layer's receptive field is a property of f, s and d only. That is why r can exceed the input size — and routinely does.

15 Effective against theoretical receptive field: the number that is quoted is not the number that matters

§14's r is the set of inputs that can affect an output. It says nothing about how much each of them does. The answer turns out to be: overwhelmingly unequally, in a shape that is Gaussian, and over a radius that is much smaller than r.

the right definition of "how much"The influence of input pixel (i, j) on output unit u is the partial derivative ∂zᵤ / ∂xᵢⱼ which is a real number, not a yes/no. Set ∂L/∂zᵤ = 1 and every other output gradient to 0, run ONE backward pass, and the gradient that arrives at the input IS the influence map. The theoretical receptive field is the SUPPORT of that map; the EFFECTIVE receptive field is the region where it is not negligible. They are very different sets.

Why it is Gaussian, in one paragraph

Consider a stack of L stride-1 layers with kernel f, and forget the non-linearity for a moment. A path from an input pixel to an output unit picks one tap in each layer; the total influence of that pixel is the sum, over all such paths, of the product of the taps along it. The number of paths reaching an offset Δ is the number of ways to write Δ as a sum of L displacements each in {0, …, f−1} — which is a convolution of L uniform distributions. That is a sum of L i.i.d. random variables, so by the central limit theorem the path count is asymptotically Gaussian in Δ, with variance proportional to L. Two consequences follow immediately, and both are counter-intuitive:

consequence 1
The effective field grows like √L
The theoretical field grows linearly, as r = L(f−1) + 1. The standard deviation of the Gaussian grows as √L. So the effective field occupies a fraction ≈ 1/√L of the theoretical one, and that fraction shrinks as you add layers. Doubling the depth does not double what the unit actually looks at.
consequence 2
The corners are almost dead
A Gaussian on a square window puts almost nothing in the corners. Units at the edge of the theoretical field contribute a fraction of a percent. Quoting "receptive field 212" for a network whose effective field is a Gaussian of a few dozen pixels is technically correct and practically misleading.
what changes it
Skips, dilation and downsampling
Residual connections make the effective field smaller relative to the theoretical one, because the identity path concentrates influence at the centre. Dilation (§22) and stride spread it out. This is a large part of why segmentation architectures, which need genuinely large context, use dilation rather than just more layers.
The influence map: measured by backpropagation, not asserted the map is a real gradient, obtained by seeding one output unit with a gradient of one; the dashed square is the theoretical receptive field and the shaded disc is where 95% of the influence mass actually lies
The design mistake this causes. "My network has a receptive field of 212 pixels, so it can use whole-image context." It can in principle and does not in practice. If your task genuinely needs long-range context — segmenting a large object, reading a scene layout — a stack whose effective field is a tight Gaussian will underperform in a way that looks like an optimisation problem and is not. The fixes are architectural: dilation (§22), aggressive downsampling with an upsampling path (§23), or an attention layer, which has a flat influence profile by construction and is a large part of why transformers took vision (§33).

16 The 1×1 convolution: channel mixing, the bottleneck, and the cost it saves

A 1×1 kernel looks like a joke — it multiplies each pixel by a number. It is not, because of the channel axis. A 1×1 convolution is a full dense layer applied independently at every spatial position, and it is one of the two or three most consequential ideas in the whole architecture lineage.

what it actually computesK is (Cₒᵤₜ, Cᵢₙ, 1, 1), so the spatial sums collapse and Z[cₒ][p][q] = b[cₒ] + ∑ᶜ V[c][p][q] · K[cₒ][c] For EACH pixel independently, the Cᵢₙ-vector of that pixel's channel values is multiplied by a (Cᵢₙ × Cₒᵤₜ) matrix. Reshape the map to the (H·W × Cᵢₙ) matrix of pixel vectors, one pixel per ROW, and this is EXACTLY part 1's Z = X W + b W of shape (Cᵢₙ × Cₒᵤₜ) the row-convention dense layer, with the H·W pixels playing the role of the batch. That is not an analogy — it is the same computation.

So a 1×1 convolution does no spatial mixing whatsoever and complete channel mixing. It is the exact complement of a depthwise convolution (§21), which does complete spatial mixing and no channel mixing. Every efficient architecture in §28 is built by alternating those two.

The four things it is used for

use 1
Shrink the channel axis
Pooling reduces H and W and cannot touch C — it operates channel by channel. A 1×1 convolution is the only cheap way to go from 192 channels to 32. This is the original motivation and the one the source deck leads with.
use 2
The bottleneck
Put a cheap 1×1 before an expensive f×f to reduce its input depth, and another after to restore it. The expensive layer now works on a fraction of the channels. The arithmetic below is dramatic and it is the whole design of the deep residual bottleneck block.
use 3
Add non-linearity for free
Even at Cₒᵤₜ = Cᵢₙ, a 1×1 followed by a ReLU adds a layer of depth with almost no cost and no change of resolution. The "network in network" idea: a small MLP applied at every pixel.
use 4
Match shapes for a skip
A residual connection needs its two branches to have the same shape. When a block changes the channel count or the resolution, the shortcut is a 1×1 convolution — with stride if the resolution changed. Look at any residual network's "downsample" module and it is exactly this.

19 Strided convolution instead of pooling — and the aliasing both of them cause

Pooling is not the only way to shrink a map. A stride-2 convolution does the same job in the same layer, with parameters, and it has largely replaced pooling in modern architectures. The two are not equivalent, and both share a defect that neither of them advertises.

Stride is free in parameters and quartic in arithmetic.

The defect they share: subsampling without a low-pass filter is aliasing

Downsampling a signal by 2 without first removing everything above the new Nyquist frequency causes high frequencies to fold onto low ones — the sampling theorem, which is Frequency Domain's material and is not re-derived here. A stride-2 convolution subsamples. A max pool subsamples, and worse: the max operator is non-linear, so it does not even have a frequency response to reason about, and it can create high frequencies before discarding them.

The visible consequence is a specific and famous failure: shift an image by one pixel and a modern classifier's prediction can change. Not because the network is fragile in some vague sense, but because a one-pixel shift moves the content relative to the stride-2 sampling grid, the aliased components change, and the change propagates. The fix that works is exactly the one the sampling theorem prescribes: blur before you subsample. Insert a small fixed low-pass filter — a binomial kernel — between the response and the stride, and shift-consistency improves measurably, usually with accuracy improving too.

Scope. The sampling theorem, the fold rule, the spectrum of a Gaussian and why the binomial kernel is the right small low-pass filter all belong to the Computer Vision series: sampling replicates the spectrum, aliasing and the fold rule, and box, tent and Gaussian. This section takes those results as given and asks only what they imply for a stride argument.

The claim that is almost right. "Strided convolution and pooling are interchangeable." They downsample by the same factor and they are not the same layer. A stride-2 convolution has parameters and can learn which linear combination survives the subsample; a max pool has none and always keeps the largest. Empirically the strided version is at least as good and the parameter-free version is more robust when data is scarce. The real reason architectures moved to stride is simpler: it merges two layers into one and removes a factor of s² from the arithmetic of the layer it replaces.

Grouping was invented for a mundane reason — an early architecture split its channels across two GPUs because one card did not have enough memory — and it turned out to cost nothing in accuracy and sometimes to help. It has since become a first-class design knob.

What it costs: the channel blocking problem

With g groups the network is g independent networks running side by side that never talk to each other. Stack several grouped layers and information in group 1 can never reach group 2, no matter how deep the network gets. Two standard fixes:

fix 1
A 1×1 convolution between groups
A dense 1×1 layer (§16) mixes every channel with every other at a cost with no f² factor. Alternate grouped f×f with dense 1×1 and the blocking is gone. This is exactly the depthwise-separable pattern of §21, at g = Cᵢₙ.
fix 2
Channel shuffle
Permute the channel axis between grouped layers so that each group's outputs are redistributed across all groups. Costs zero parameters and zero arithmetic — it is a reindexing — and restores full connectivity after two layers. The trade is that it is a fixed, not learned, mixing.
and the caveat
Cheap in FLOPs, not always in time
A grouped convolution does 1/g of the arithmetic and issues g smaller matrix products instead of one large one. On hardware that is happiest with large dense products, a layer that is 8× cheaper on paper is frequently not 8× faster. §21's caveat is the same one and is even sharper there.

23 Transposed convolution, the checkerboard, and why "deconvolution" is the wrong word

Everything so far shrinks maps or keeps them the same size. Generation, segmentation and any encoder–decoder need the opposite: a learned layer that makes a map bigger. The operation exists, it is elementary, and it is burdened with the worst name in the field.

What it actually is

the definition, and where the name comes from§03: a convolution layer is multiplication by a sparse, tied matrix M: z = M x M is (H′W′ × HW), so it MAPS DOWN when H′ < H The TRANSPOSED convolution is multiplication by Mᵀ: y = Mᵀ u Mᵀ is (HW × H′W′), so it MAPS UP That is the entire definition. It is not an inverse, it is a TRANSPOSE — the adjoint of the forward operator with respect to the ordinary inner product. why it is exactly the backward pass, and vice versaFrom §25: the gradient of a convolution with respect to its INPUT is ∂L/∂x = Mᵀ (∂L/∂z) which is the transposed convolution applied to the output gradient. So the forward pass of a transposed convolution IS the backward pass of an ordinary one, and its backward pass is an ordinary forward pass. Frameworks implement one routine and call it from both places. the output size, and the ambiguity it inheritsn′ = (n − 1)·s − p₀ − p₁ + fₑ + output_padding Because §09 trap 4 showed the forward map is not injective, this inverse needs to be TOLD which of the possible sizes it should produce — that is what output_padding is for, and forgetting it is the standard reason a decoder's output is one pixel smaller than its encoder's input.
"Deconvolution". A deconvolution is the inverse problem — given y = k ∗ x and k, recover x — which is an ill-posed division in the frequency domain, is the subject of a large classical literature, and has nothing to do with this layer. A transposed convolution does not invert a convolution, does not recover the original input, and does not even try. Two better names are in use: transposed convolution (what it is) and fractionally strided convolution (what it does — a stride of 1/s, achieved by inserting s − 1 zeros between input positions before convolving at stride 1).

The checkerboard artefact, and exactly when it happens

Implement the transposed convolution the natural way — for each input position, add a scaled copy of the kernel into the output at stride s — and the copies overlap. How many copies land on a given output position depends on that position modulo s, and if s does not divide f the count is not constant. Output positions receiving more contributions get systematically larger values, in a periodic pattern with period s. That is the checkerboard, and it has an exact statement:

the overlap count, computedf = 3, s = 2 → contributions per output position: 2, 1, 2, 1, 2, 1, … a period-2 pattern with a 2:1 amplitude ratio. CHECKERBOARD f = 4, s = 2 → contributions: 2, 2, 2, 2, … CLEAN f = 5, s = 2 → contributions: 3, 2, 3, 2, … CHECKERBOARD f = 6, s = 3 → contributions: 2, 2, 2, … CLEAN f = 4, s = 3 → contributions: 2, 1, 1, 2, 1, 1, … CHECKERBOARD THE RULE: the overlap count is uniform ⟺ s divides f.

Two fixes, both standard. (1) Choose f divisible by s — a 4×4 kernel at stride 2 is the reason that combination is so common in generator architectures. (2) Replace the layer entirely with "resize by nearest-neighbour or bilinear interpolation, then apply an ordinary stride-1 convolution". This decouples upsampling from learning, has no overlap to be uneven, and is now the more common choice in image-generation and segmentation decoders. It costs more arithmetic — the convolution runs at the higher resolution — and produces visibly cleaner output.

Note that fix (1) is necessary and not sufficient. Making the overlap uniform removes the structural checkerboard, but a learned kernel can still produce one if the training signal encourages it, and stacking several transposed layers multiplies whatever periodicity survives. The interpolate-then-convolve fix removes the mechanism entirely, which is why it won.

Three consequences that shape how convnets train

consequence 1
Shared weights get summed gradients
A kernel entry's gradient is a sum over H′W′ terms. Its magnitude therefore scales with the map area, which is why the same learning rate behaves differently at different resolutions and why part 2 §12's variance argument needs the fan-in Cᵢₙ·f², not the parameter count.
consequence 2
Padding costs a gradient
Gradient that lands on a padded position is discarded — it flows to a zero that no parameter owns. Border input positions therefore receive systematically less gradient than interior ones, which is the backward-pass shadow of §08's border argument.
consequence 3
The backward pass costs the same twice
Part 2 §01's 1 : 2 : 3 rule holds exactly: the two backward operations each have the same MAC count as the forward one. A training step on a convolution layer costs three forward passes, and the first layer's ∂L/∂V is the only one you can skip.

26 Convolution as one matrix product: im2col, and the Toeplitz view

§03 said a convolution is a matrix. That was a statement about its structure. This section is the practical version: how a convolution is actually executed, which is by rearranging it into a single dense matrix product and calling the same library routine an MLP calls.

im2col — the lowering, in the series row conventionFor every output position (p, q), extract the Cᵢₙ × f × f window it reads and flatten it into a ROW. Stack the rows: P is (H′W′ × Cᵢₙ·f·f) one PATCH per row W is (Cᵢₙ·f·f × Cₒᵤₜ) one FILTER per column Z = P·W + b (H′W′ × Cₒᵤₜ) Reshape Z back to (Cₒᵤₜ, H′, W′) and you are done. That is part 1's X·W + b, with the pixels playing the role of the batch — the same row convention, the same shapes, the same routine. the tradeCOST P holds Cᵢₙf² · H′W′ numbers where V held only CᵢₙHW — a memory blow-up of about f² (NINE times for a 3×3 kernel) for the duration of the layer. Every input value is copied f² times. BUY one large dense matrix product, which runs at 60–90% of a machine's peak throughput, instead of a hand-rolled sliding loop, which does not. The blow-up is worth it and every framework does it, in tiles small enough to stay in cache.

Reading off the counts

The matrix form makes §12's arithmetic obvious rather than derived. The product (H′W′ × Cᵢₙf²)·(Cᵢₙf² × Cₒᵤₜ) costs H′W′ · Cᵢₙf² · Cₒᵤₜ MACs — exactly the count of §12, with no work. The weight matrix has Cᵢₙf²·Cₒᵤₜ entries — exactly the parameter count. And the reuse factor H′W′ is just the number of rows in P, i.e. the number of times each column of W is dotted with something.

The other two ways, and when they win

alternative 1
Direct / implicit GEMM
Build the patch rows on the fly in registers rather than materialising P in memory. Same arithmetic, none of the blow-up. This is what a modern library actually does; im2col is the mental model and the fallback.
alternative 2
The frequency domain
Convolution is pointwise multiplication of transforms — the convolution theorem. Cost drops from O(n²f²) to O(n² log n), independent of f. It wins for large kernels and loses badly for 3×3, where the transform overhead dwarfs nine multiplies. It is why large-kernel layers are less expensive than they look.
alternative 3
Winograd
A minimal-filtering algorithm that trades multiplications for additions on small tiles. For 3×3 kernels it cuts multiplications by a factor of 2.25 and is the standard fast path for exactly that case. It is numerically less stable, which matters in low precision (part 2 §27).
Why this matters beyond implementation. Once you see the layer as P·W, three things follow that are hard to see otherwise. (1) A 1×1 convolution has f = 1, so P is just the activation reshaped and no copying happens at all — which is why 1×1 layers are so cheap in practice as well as in theory (§16). (2) The rank of W is a meaningful quantity, and low-rank factorisation of it is a real compression technique. (3) The doubly block Toeplitz matrix M of §03 and the dense W here are two different matrices doing the same job: M is (H′W′ × HW), huge and sparse and tied; W is (Cᵢₙf² × Cₒᵤₜ), small and dense and free. The tying was moved out of the matrix and into the indexing, which is the whole trick.

27 What a convolutional network actually learns

The most reproducible empirical fact about convnets: the first layer always learns the same thing. Oriented edges at several scales and orientations, and a few colour-opponent blobs — whatever the dataset, whatever the task, whatever the initialisation. That regularity is not a coincidence and it has an explanation that requires no learning at all.

Why the first layer is always oriented edges

Take a large collection of small patches from natural images and compute their covariance. The principal components of that covariance — the directions of maximum variance, computed with no labels, no network and no gradient descent — are localised, oriented, band-pass filters. They look like the first layer of a trained convnet because they are answering the same question: what are the dominant modes of variation in a small window of a natural image? A first layer trained by gradient descent on almost any objective ends up spanning approximately the same subspace, because that is where the signal is.

Two consequences that matter in practice. (1) First layers transfer perfectly. Because they encode a property of natural images rather than of your task, the first layer of a network trained on one dataset is a good first layer for another — which is the foundation of transfer learning and why "freeze the early layers" is a sensible default. (2) A first layer that does not look like this is a diagnostic. Noisy, high-frequency or dead first-layer filters after training mean the learning rate was too high, the initialisation was wrong, or the layer never received usable gradient — see part 2 §14 and §11. Looking at the first layer is a five-second diagnostic that catches real bugs.

30 The critique: what pooling throws away, and the viewpoint problem

Everything up to here has been description. This section is the strongest sustained argument against the design, made from inside the field, and it is worth taking seriously whether or not you accept its proposed fix. The charge sheet has four counts.

What the critique concedes

local feature detectors — correct·replicated across the image — correct·receptive fields growing with depth — correctbutinterleaving them with pooling — wrong

Count 1 — pooling solves the wrong problem

This is the central charge, and §18 has already stated the distinction it turns on. Pooling is designed to produce invariance to small translations. But the invariance we ultimately want is only in the final label. Discarding position throughout the network, a little at a time, destroys the spatial relationships between parts that a later layer would need to check whether the parts are in a plausible configuration. The claim: what you want at every intermediate layer is equivariance — the representation should change in a predictable way with viewpoint, not be blind to it — and invariance should be applied once, at the end, if at all.

Note how much of modern practice has quietly conceded this: max-pooling layers have largely been replaced by strided convolutions and, in the most recent designs, by very few downsampling stages with a single global pool at the end. That is not the same argument arriving at the same conclusion, but it is not unrelated.

Count 2 — the network has no notion of pose

The framing is that vision is inverse graphics. A renderer takes a scene — objects, and a pose matrix for each — and produces pixels. Vision should recover the objects and their poses. In computer graphics the relationship between a whole and its part is a transformation matrix that is viewpoint invariant: the matrix relating a face to its nose is the same whichever way the face is turned. A convolutional network represents none of this. It has activations that say "a nose is present here, strongly", and no representation of the nose's orientation, scale or position relative to the face.

The practical consequence is the one everybody has met: a convnet extrapolates badly to unseen viewpoints, and the standard fix is to show it every viewpoint. That is what augmentation is (part 2 §35) and it is expensive in data. A representation that carried pose explicitly would generalise across viewpoints from far fewer examples.

Count 3 — the parts are detected but their arrangement is not checked

This is the sharpest and most testable count. A network built out of "is feature X present in this region?" detectors, aggregated by pooling, has weak machinery for asking "are these features in the right relative positions?". The prediction: an image with the right parts in the wrong places should still be classified confidently as the object. This is easy to test and it largely holds — scramble a face's features within the frame and a classifier's confidence often stays high. §17's figure already measured the mechanism: a 2×2 max pool discards two bits of within-window position per channel per window, and does it at every stage.

Count 4 — pooling is a crude routing decision

Read max pooling as a routing operation: of the k² units in a window, it decides that exactly one gets to send its value onward, and the choice is made by a fixed rule — take the largest. That is routing without any consideration of what the receiving unit needs. A better scheme would send each lower-level unit's output to whichever higher-level unit is best placed to make use of it, decided dynamically per input. §31 is that scheme.

The arrangement test: right parts, wrong places both images contain exactly the same parts in the same quantities; the two feature vectors are compared, and the similarity after global pooling is the number the critique predicts will be high

31 Capsule networks: routing by agreement, and the loss that goes with it

§30 was the diagnosis. This is the proposed cure, and it is worth a section because it is the most fully worked-out alternative to the convolution-plus-pooling design that anyone has built. It lives here, inside this page's critique, because that is what it is — a critique of the CNN's design, not an independent architecture family with a literature to match. Reading it after §30 is the only way it makes sense.

What a capsule is

the single structural changeA NEURON outputs a SCALAR: "this feature is present, with strength a". A CAPSULE outputs a VECTOR: "this entity is present with probability ‖v‖, and its POSE is the direction of v." The length carries EXISTENCE and the orientation carries INSTANTIATION PARAMETERS — position, scale, rotation, thickness, skew. So the same entity seen from a new viewpoint produces a vector of the SAME LENGTH pointing in a DIFFERENT DIRECTION. That is equivariance, built into the representation rather than hoped for. the squash, which enforces the "length is a probability" reading ‖s‖² s squash(s) = ─────── · ───── 1 + ‖s‖² ‖s‖ ‖s‖ → 0 ⇒ ‖v‖ ≈ ‖s‖² short vectors are crushed toward 0 ‖s‖ → ∞ ⇒ ‖v‖ → 1 long vectors are capped just below 1 The DIRECTION is untouched — squash is a radial rescaling and nothing else. Routing by agreement

This is the replacement for pooling. Each lower-level capsule i makes a prediction for what each higher-level capsule j should be, by applying a learned transformation matrix: û_{j|i} = W_{ij} u_i. Those matrices are the pose relationships of §30 — "given a nose in this pose, here is the face pose it implies". Then the higher-level capsule's output is a weighted average of the predictions made about it, and the weights are set by how well each prediction agrees with the emerging consensus:

After a few iterations the capsules that agree have dominated the average and the ones that do not have been suppressed. CONTRAST WITH MAX POOLING, which is also a routing decision (§30, count 4): max pooling picks the LARGEST value in a window. The choice ignores what the receiving unit needs, and it is made once, statically. routing picks by AGREEMENT with the receiver's current estimate. The choice depends on the input, and is refined over r iterations. Note the softmax is over j, not i: each LOWER capsule distributes its output across the upper capsules, so it must decide where to send itself. It is a competition between PARENTS for a child, not between children for a parent. And r is small — 3 is the value that works; more iterations tend to overfit the routing and make the coefficients collapse to one-hot too early.

Between 0.1 and 0.9 the absent-class term is zero and the present-class term is zero, so there is no gradient — the deliberate flat region is what stops the model from wasting capacity driving lengths to the extremes. why a margin loss and not a softmax cross-entropyBecause ‖vₖ‖ is meant to be an INDEPENDENT probability of the entity existing, not a share of a normalised total. A softmax would force the class capsules to compete for one unit of probability mass, which contradicts the design's intent that several entities can be present at once. λ = 0.5 down-weights the absent classes, of which there are K − 1, so early training is not dominated by pushing nine lengths to zero. the reconstruction regulariserTake the 16-D output vector of the CORRECT class capsule, mask the others to zero, and feed it to a small fully connected decoder (16·K → 512 → 1024 → 784) that must reproduce the input image. Add the squared reconstruction error, SCALED BY 0.0005, to the margin loss. The scale matters and is easy to get wrong: the raw reconstruction error is over 784 pixels and would otherwise dwarf the margin loss entirely.

Three arithmetic and definitional errors that circulate in secondary presentations of this material — all three found while checking this section against the source. Stated so you do not inherit them.
  • T_k = 1 when the class is present, not when it is predicted. Several summaries write "T_k = 1 when the correct label is predicted". That would make the target depend on the model's own output and remove the gradient that pushes a wrong prediction toward the right answer. T_k is the label, full stop.
  • The reconstruction loss is scaled by 0.0005, not 0.00005. A factor of ten. At the smaller value the reconstruction term is essentially switched off and the regularisation it is supposed to provide does not happen — and the network still trains, so nothing tells you.
  • A reported 5% error rate is a re-implementation's number, not the method's. The original result is 0.25% test error on digits with three routing iterations and reconstruction. A 5% figure — twenty times worse — indicates a training problem, and quoting it as the method's performance mis-states the evidence in both directions.

32 Why capsules did not displace convolutional networks — an honest assessment

The critique in §30 is largely correct. The architecture in §31 is a genuine attempt to fix it. It did not take over, and understanding why is more instructive than either dismissing it or over-selling it.

reason 1
The cost is quadratic in capsule count
DigitCaps needs one transformation matrix per (lower, upper) pair: 1 152 × 10 × 8 × 16 = 1 474 560 parameters for a two-layer routing step on 28×28 digits. Scale the lower layer to a real image's worth of capsules and the pairwise matrices dominate everything. Convolution's answer to this — share the transformation across positions — is available and reintroduces exactly the weight-tying the design was trying to escape.
reason 2
Routing is an inner loop that does not vectorise well
Three routing iterations mean three sequential passes over the coupling coefficients, each with a softmax and a dot product per pair, inside every forward pass. Convolution is one dense matrix product (§26) that runs at close to peak throughput. Reported wall-clock costs were an order of magnitude worse for comparable accuracy — and the hardware has moved further toward dense matrix products since, not away.
reason 3
It never scaled past small images
The compelling results were on digits and on small, controlled datasets. Attempts to scale to ImageNet-sized problems did not produce competitive numbers, and the number of researchers who tried was large. That is real evidence, though it is evidence about this instantiation of the idea rather than about the idea.
reason 4
The comparison was against a moving target
Over the same period, ordinary convnets absorbed better normalisation, better optimisers, far better augmentation, and eventually transformer-style blocks (§28). A four-point accuracy gain from a training recipe alone is larger than most architectural claims of the era. Capsules needed to beat a rapidly improving baseline with a much smaller research community behind them.

What survived, and where

The ideas did not vanish; they were absorbed, mostly without the name.

dynamic, input-dependent routing→attention, whose weights are computed from the data exactly as routing coefficients are
vector-valued units carrying pose→the multi-dimensional tokens of a transformer, and equivariant architectures with explicit group structure
equivariance over invariance→the modern preference for few downsampling stages and one global pool at the end, and for dense-prediction backbones that never pool at all

The sharpest way to put it: routing by agreement and attention are the same move — replace a fixed aggregation rule with one computed from the data — and attention won because it is a single matrix product with no inner loop, is trivially parallel, and turned out to need no pose machinery to be useful. Attention and Transformers are where that thread continues.

Why this material has no node of its own. Capsule networks are a critique of the convolutional design before they are an architecture, and they are best understood immediately after §30's charge sheet, by a reader who has just been shown exactly what pooling discards and has watched it measured. Splitting them onto a page of their own would separate the answer from the question and would give a line of work that did not scale the same weight in the graph as convolution itself. The honest place for them is here.

33 Convolutional networks against vision transformers: which prior, and when

The comparison is usually framed as "convolution versus attention". That framing is wrong twice over: the two architectures are more similar than they look, and the thing that actually differs is the strength of the prior, which is a statement about how much data you have.

How similar they really are

a vision transformer, translated into this page's vocabularypatch embedding = a CONVOLUTION with kernel = stride = the patch size. A 16×16 patch embedding on a 224×224 image is exactly conv(f = 16, s = 16), giving a 14×14 map of D channels. Not "like" a convolution — it IS one (§08's formula: (224 − 16)/16 + 1 = 14). the MLP block = two 1×1 CONVOLUTIONS with a non-linearity between them (§16). Identical operation, different name. the attention = the genuinely new part: a mixing matrix over positions that is COMPUTED FROM THE DATA rather than learned as a fixed kernel, and that is dense over all positions rather than banded. so the real difference is exactly one layer, and it is thisCONVOLUTION fixed, banded, tied mixing: the weights do not depend on the input, each output sees a small window, and the same weights are used everywhere. ATTENTION dynamic, dense, untied mixing: the weights ARE a function of the input, every position can see every other, and there is no tying at all — position information must be ADDED explicitly because there is none in the operation.

The decision rule, which is not "which is better". Ask instead: how much data do I have, and is locality true of it? Under roughly a million labelled examples and with images of natural scenes, a convolutional backbone is the right default and will train faster and more reliably. With hundreds of millions of examples, or with a large pretrained model available to fine-tune, the weaker prior wins. And if you are fine-tuning someone else's pretrained model — which is the common case (Fine-tuning & Transfer Learning) — the question is not architectural at all: it is which pretrained model is closest to your data. 34 Convolution beyond images: 1-D, 3-D, and variable size

Nothing in §04–§12 mentioned images. Convolution applies to any input with a known grid topology — a set of coordinates where "nearby" means something and where a pattern can occur at more than one location. That covers considerably more than pictures.

dimensionssingle channelmulti-channel
1-DAn audio waveform. One axis, time, sampled at a fixed rate. Convolving over it makes the model equivariant to shifts in time.Skeleton or sensor data. One channel per joint angle or per sensor; the sliding axis is time and the channel axis is contracted at every step exactly as in §10.
2-DA spectrogram. Rows are frequency and columns are time. Note the standard cheap factorisation, which is §21's idea in another guise: a (1, f, f) spatial convolution followed by an (f, 1, 1) temporal one, instead of a full (f, f, f).

Variable input size, which is a real and under-used advantage

A dense layer's weight matrix has a fixed shape, so an MLP simply cannot accept an input of a different size. A convolution can: the kernel is applied as many times as it fits, and the output grows or shrinks accordingly. The only obstacle is the classifier at the end, which needs a fixed-size vector — and there are three standard answers, all of which appear elsewhere on this page:

global pooling (§17)—one number per channel regardless of the map size; the simplest and now the default
adaptive pooling to a fixed grid—vary the pooling region size with the input so the count of regions is fixed, e.g. always a 3×3 grid of summaries
no classifier at all—emit one feature map per class and let the output be as variable as the input; this is what a segmentation network does (§23)
And the boundary of the idea. Convolution makes sense when a variable-size input contains varying amounts of the same kind of observation — more seconds of audio, more pixels of scene. It makes no sense when the input varies because it contains different kinds of observation. Sliding one kernel over a feature vector whose first three entries are exam grades and whose next two are test scores is meaningless: those coordinates have no adjacency relation, so the prior of §03 is simply false. That is the same test as part 1 §24's shuffle: if permuting the coordinates would not destroy anything, there was no grid to exploit. For genuinely irregular relational structure, the right generalisation is a graph neural network, where the neighbourhood is given explicitly rather than implied by a grid.

Two habits that prevent most of the above

habit 1
Print the shape table, once, and read it
Every layer's input shape, output shape, parameter count and whether its division was exact. It takes ten seconds and catches traps 1, 3 and 4 immediately. §13's figure is that table; the point is to have the real one for your own model.
habit 2
Look at the first-layer filters after training
They should be oriented edges and colour blobs (§27). If they are noise, the learning rate or the initialisation is wrong; if many are uniformly grey, those units are dead (part 2 §11). A five-second visual check that catches problems a loss curve hides for hours.

36 What to remember

the one idea
A constrained dense layer
Banded (each output sees a window) and tied (the same weights everywhere). Nothing else about the layer changes — same forward pass, same loss, same optimiser. The constraint is the prior knowledge, expressed as a hard limit rather than a penalty.
the three motivations
Sparse, shared, equivariant
Sparsity takes m·n parameters to k·n. Sharing takes k·n to k and buys the sample efficiency. Equivariance is what makes sharing legitimate. They are three separate things.
the one formula
⌊(n + p₀ + p₁ − fₑ)/s⌋ + 1
With fₑ = d(f−1)+1. Every shape on this page comes from it, and every off-by-one bug in §09 is the floor or the padding split.
the three counts
They move differently
Parameters do not contain H or W. MACs are parameters × H′W′. Activations are N·Cₒᵤₜ·H′W′ and contain no parameters. Never reason about one from another.
the growth rule
Depth adds, downsampling multiplies
rₗ = rₗ₋₁ + (fₑ−1)·jₗ₋₁ with jₗ = jₗ₋₁·sₗ. Stride-1 stacking is far too slow; downsampling makes the growth geometric; dilation does the same without losing resolution.
and the caveat on it
Effective ≠ theoretical
The influence profile is Gaussian and its width grows like √L while the theoretical field grows like L. Quoting a 212-pixel receptive field says much less than it appears to.
the two complementary primitives
1×1 and depthwise
A 1×1 mixes channels and not space; a depthwise mixes space and not channels. Every efficient architecture alternates them, and the cost ratio 1/Cₒᵤₜ + 1/f² is why.
the distinction that matters most
Equivariance is not invariance
Equivariance preserves information; invariance destroys it. Convolution is equivariant, global pooling is invariant, strided max pooling is neither cleanly. Choose invariance once, at the end, and only if the task wants it.
the calculus
The flip is forced
Forward is a correlation. ∂L/∂K is a valid correlation of the input with the output gradient; ∂L/∂V is a full convolution of the output gradient with the kernel. Verified to 2.86e−09 against central differences across eight geometries.
the execution
It is one matrix product
im2col turns the layer into P·W — part 1's X·W with pixels as the batch — at the price of about f² memory. The MAC count falls straight out of the matrix shapes.
the critique to take seriously
Pooling discards arrangement
A 2×2 max pool throws away two bits of position per channel per window, at every stage. The prediction — right parts in the wrong places still classify as the object — is testable and largely holds. Modern practice has quietly conceded much of this.
the comparison
It is about the prior, not the operation
A patch embedding is a convolution and an MLP block is two 1×1 convolutions. The real difference is a strong fixed local prior against a weak dynamic global one, and which wins is a question about how much data you have.

The mistakes that cost the most

  • Not printing the shape table. Traps 1, 3 and 4 in §09 are all visible in it in ten seconds and invisible in a loss curve for days.
  • Reasoning about speed from a parameter count. Early layers are cheap in parameters and expensive in arithmetic; late layers are the reverse; and a depthwise layer is cheap in both and slow anyway (§12, §21).
  • Comparing a "GFLOPs" figure to a "MACs" figure. They differ by exactly two and both are called FLOPs in print (§12).
  • Believing max pooling gives translation invariance. A one-pixel shift changes over 90% of a stride-2 max pool's outputs on §18's test map. It gives a partial reduction in sensitivity, not invariance.
  • Leaving the bias on a convolution that is followed by a normalisation layer. Not harmful, but inert, and it makes the parameter count disagree with the reference implementation (§24).
  • Using a stride-2 transposed convolution with a 3×3 kernel and then wondering about the checkerboard. The overlap counts are 2, 1, 2, 1 and no amount of training fixes a geometric fact (§23).
  • Adding depth to fix a context problem. The effective field grows like √L; dilation or attention is the fix, not more 3×3 layers (§15, §22).
  • Assuming grouped or depthwise layers make the model faster in proportion to their MAC saving. Measure the wall clock (§20, §21).
  • Forgetting evaluation mode. Still the single most expensive one-line bug in the field (part 2 §29).
  • Taking the "edges, parts, objects" story literally. The first layer is reliable; the rest is partly a selection effect, and the network is more texture-driven than the story suggests (§27).
