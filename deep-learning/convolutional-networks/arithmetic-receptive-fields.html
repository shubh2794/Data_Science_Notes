08 Shape arithmetic: padding, stride, dilation, and the one formula

Everything about where the window goes is one formula. Learn it, learn what each symbol does independently, and the whole family of layer variants in §19–§23 becomes bookkeeping rather than new material.

the output size of one axis — the only shape formula on this page ⎢ n + p₀ + p₁ − fₑ ⎥ n′ = ⎢ ─────────────── ⎥ + 1 where fₑ = d·(f − 1) + 1 ⎣ s ⎦ n input length p₀ padding BEFORE (left / top) f kernel length p₁ padding AFTER (right / bottom) s stride d dilation fₑ the EFFECTIVE kernel: how many input positions the window spans read each symbol as an independent knobf grows the window and shrinks the output by f − 1 p grows the input; +1 output per +1 of TOTAL padding, at stride 1 s subsamples the output positions — the only term that DIVIDES d spreads the SAME f taps over fₑ = d(f−1)+1 positions: a bigger window at no extra parameters and no extra arithmetic (§22) The two axes are independent, so a rectangular kernel is just this formula applied twice with different numbers. This page uses square kernels.

That last pair is a famous and instructive discrepancy. The original large-kernel-stem architecture is universally described as taking a 224×224 input and producing a 55×55 first feature map — and 224 gives 54, not 55. The input that actually produces 55 is 227 (or 224 with two pixels of padding). Every reimplementation quietly picks one fix or the other. It is worth knowing because it is the cleanest example of the general rule: if a published architecture's shapes do not reproduce, the padding is the thing that was left out of the description.

Why padding exists at all — two reasons, not one

reason 1
The map shrinks
Without padding each layer costs f − 1 pixels. Thirteen 3×3 layers on a 32×32 input leave 32 − 26 = 6 pixels; on a 28×28 input they run out entirely. The shrinkage bounds the depth, which is fatal for an architecture whose whole strategy is depth.
reason 2
The border is under-used
Under valid padding a corner pixel is read by exactly one output and a central pixel by f² of them. The §01 figure draws the per-position count directly. Information at the edge of the frame is systematically down-weighted, and padding restores the balance — partially.
and the cost
Zeros are a signal
Padding does not create information; it creates a detectable border artefact. A network can and does learn to read the ring of zeros as a position cue, which is one of the ways a "translation-equivariant" architecture leaks absolute position. It is a small effect and a real one, and it is why same padding is a compromise rather than a solution.
The shape formula, one knob at a time the strip shows exactly where each window lands; the formula below is evaluated term by term with the current numbers, and the counts under the strip are how many times each input position is actually read

09 The off-by-one traps, and which of them are silent

Shape arithmetic is arithmetic, so it either works or it throws — except in the four cases below, where it works and is wrong. Every one of these costs a real debugging session at least once.

Trap 1 — the floor discards input, silently

n = 8, f = 3, s = 2, validn′ = ⌊(8 − 3)/2⌋ + 1 = ⌊2.5⌋ + 1 = 3 windows start at 0, 2, 4 → they cover input positions 0 … 6 INPUT POSITION 7 IS NEVER READ. Not by a padded zero, not partially — the entire last column of the image is discarded, every forward pass, forever. the same layer with "same" paddingn′ = ⌈8/2⌉ = 4, total padding = (4−1)·2 + 3 − 8 = 1 → p = (0, 1) windows start at 0, 2, 4, 6 → they cover 0 … 8, of which 8 is padding. Position 7 IS read. The padding policy changed whether a quarter of your image's last column exists.

The floor is doing exactly what it says: a window that would hang off the end is rejected. But nothing warns you, the shapes are all consistent, the loss goes down, and a strip of the input is simply invisible to the model. Odd input sizes with even strides are where this bites; it is the reason architectures are so fond of powers of two.

Trap 2 — same padding is not always symmetric

when the required total padding is odd, one side gets moren = 8, f = 3, s = 2 → total P = 1 → p = (0, 1) ASYMMETRIC n = 7, f = 4, s = 1 → total P = 3 → p = (1, 2) ASYMMETRIC n = 7, f = 3, s = 1 → total P = 2 → p = (1, 1) symmetric The convention, in both major frameworks: the EXTRA pixel goes on the RIGHT and the BOTTOM. p₀ = ⌊P/2⌋, p₁ = P − p₀.

The consequence is a portability trap. A framework's padding=1 integer argument means symmetric padding and cannot express (0, 1) at all; a framework's padding="same" string can. So a model that used a string policy with an even kernel or an awkward stride cannot be reproduced by an integer padding, and the reimplementation will be off by one pixel in a way that shifts every feature map by half a position and degrades accuracy without ever erroring.

Trap 3 — an even kernel cannot be same with symmetric padding, ever

the two-line proofWith symmetric integer padding p on both sides and stride 1: n′ = n + 2p − f + 1 For n′ = n we need 2p = f − 1. If f is EVEN then f − 1 is ODD, and no integer p satisfies it. Therefore: an even kernel with symmetric padding always changes the size, by an odd number, whatever p you choose.

This is the real reason kernels are odd. It is not that odd kernels are more expressive — a 4×4 kernel has more parameters than a 3×3 one — it is that an odd kernel has a centre, so "the output at position i is a function of the input around position i" is a true statement with no half-pixel offset in it. With an even kernel the output grid sits half a pixel off the input grid, and after several layers those half-pixels accumulate into a real misregistration. §14's start column tracks exactly this quantity.

Trap 4 — several input sizes give the same output size

the floor is not injectivef = 3, s = 2, valid: n = 7 → n′ = 3 n = 8 → n′ = 3 f = 3, s = 2, same: n = 7 → n′ = 4 n = 8 → n′ = 4 Given only n′ = 3, f = 3 and s = 2, the input could have been 7 or 8. why this matters laterA transposed convolution (§23) has to UNDO this map, and it cannot: the information about which n produced n′ is gone. That is why every framework's transposed convolution takes an explicit output_size or output_padding argument, and why an encoder-decoder that forgets to pass it produces a decoder output one pixel smaller than its encoder input.
The four traps, each drawn as the geometry that causes it the counts under the strip are measured by running the layer, not asserted — an input cell with a count of zero is one the network never sees
The habit that prevents all four. Print the shape of every tensor once, at the top of training, and read the list. Not the parameter count — the shapes. Every one of these traps is visible in a shape table within ten seconds and invisible in a loss curve for days. §13's figure is that table.

10 Convolution over volumes: why a filter is three-dimensional

Everything so far has been one channel. Real inputs have three (colour) and real hidden layers have hundreds. The extension is small but it is the point at which most people's mental picture goes wrong, so it is worth being exact: a filter is not 2-D and slid over channels — it is 3-D and slid only over space.

one filter, one output channel — NCHW throughout (§01)input V (Cᵢₙ, H, W) filter K (Cᵢₙ, f, f) ← as deep as the input, ALWAYS bias b a scalar output Z (1, H′, W′) ← ONE map, however many input channels there were Z[p][q] = b + ∑ over c = 0 … Cᵢₙ−1 ∑ over m = 0 … f−1 ∑ over n = 0 … f−1 V[c][p·s + m·d − p₀][q·s + n·d − p₀] · K[c][m][n] read the three sumsm and n slide — the window MOVES over rows and columns c does NOT slide — the sum runs over ALL channels at every position So the channel axis is CONTRACTED AWAY, exactly like the summation axis of a matrix product. That is why one 3-D filter produces one 2-D map: the depth was consumed, not traversed.

Three consequences follow, and each is a common source of confusion:

consequence 1
The output has no depth of its own
A 3×3×3 filter on a 6×6×3 input gives a 4×4 map — a single flat map, not a 4×4×3 volume. Depth in the output comes from having many filters (§11), never from one.
consequence 2
The filter's depth is not a choice
You choose f; Cᵢₙ is dictated by whatever the previous layer emitted. The only free choices in a conv layer are the spatial size, the number of filters, and the geometry. This is why a shape error in a convnet is almost always a channel-count error.
consequence 3
Channels can be mixed selectively
Nothing forces every output channel to see every input channel. Restricting each filter to a subset of the input channels is grouped convolution (§20), and taking the subset to be a single channel is depthwise (§21). Both are just this sum with a shorter range on c.
One 3-D filter on a 3-channel input: three windows, one number the three per-channel partial sums are shown separately and then added; changing the filter's depth-slices changes which channel dominates, and the output map is a single flat map whatever you do
The picture that causes the confusion. "The kernel slides across the image and also across the channels." It does not slide across channels. There is no such thing as a "position" along the channel axis for the window to be at — the sum over c is complete at every spatial position. If a kernel did slide over channels you would have a 3-D convolution, which is a real and different operation (used on video and volumetric scans, §34), and its kernel would be (Cᵢₙ, f_t, f, f) with a fourth sliding axis.

11 Many filters, the feature-map stack, and one layer written out in full

§10 produced one map from one filter. A layer has many filters, and the maps they produce are stacked into the channel axis of the output, where they become the input channels of the next layer. That single sentence is the whole of how depth in a convnet works.

the complete layer — this is the equation the rest of the page counts, differentiates and optimisesinput V (Cᵢₙ, H, W) kernel K (Cₒᵤₜ, Cᵢₙ, f, f) one 3-D filter per output channel bias b (Cₒᵤₜ) output Z (Cₒᵤₜ, H′, W′) Z[cₒ][p][q] = b[cₒ] + ∑ᶜ ∑ₘ ∑ₙ V[c][p·s + m·d − p₀][q·s + n·d − p₀] · K[cₒ][c][m][n] A = g(Z) element-wise, part 1 §11–§13 the same thing in the dense-layer form part 1 wroteZ = X W + b with X the (H′W′ × Cᵢₙff) matrix of extracted PATCHES, one patch per ROW, §26's im2col and W the (Cᵢₙff × Cₒᵤₜ) matrix of flattened filters. Row convention, unchanged from part 1 §09. A convolution layer IS a dense layer; the only question was ever which matrix.
The one bias fact worth stating. There is one bias per output channel, shared across all H′·W′ positions — not one per output unit. A per-position bias is legal (and is what a locally connected layer does, §29) but it destroys translation equivariance, because the layer's response would then depend on absolute position. The only common argument for it: under zero padding the border units receive systematically less input and might want a larger bias. Almost nobody does it.

The shape rule, in one line

input H × W × Cᵢₙconvolved withCₒᵤₜ filters of f × f × Cᵢₙgivesoutput H′ × W′ × Cₒᵤₜ

Written in the source's HWC order because that is how it is usually quoted; the arithmetic is the NCHW one of §01. The two facts to hold on to: the output's depth is the number of filters and nothing else, and each filter's depth is the input's depth and nothing else. Every channel-shape bug is one of those two being violated.

What a filter is, said plainly

A filter is a pattern detector with a single template. Its Cᵢₙ·f·f weights are a small volume of numbers; the layer computes the inner product of that volume with every equally-sized window of the input; and the output map is high where the window resembles the template and low where it does not. A layer with 64 filters is asking 64 independent "does this look like…?" questions at every position simultaneously. The channel axis of a feature map is therefore a list of questions, and the spatial axes are where they were asked — which is why global pooling over space (§17) is a summary of whether, and the spatial map is a record of where.

A bank of filters, and the stack it produces each filter is an independent template; the stack on the right is the layer's output, and the channel you select there is produced by exactly one filter on the left

12 Counting one layer, exactly: parameters, arithmetic, activations

Three counts, three different formulas, three different things they predict. Confusing them is the most common quantitative mistake made about convnets, and the confusion runs in a specific direction: people quote the parameter count and reason about the compute.

the three counts for one convolution layerPARAMETERS Cₒᵤₜ · (Cᵢₙ/g · f · f) + Cₒᵤₜ ← does NOT contain H or W. A conv layer's parameter count is completely independent of the input resolution. A parameter count therefore tells you almost nothing about where the time goes, and §13's figure shows both profiles for a whole network side by side.

The MAC/FLOP factor of two, said once. A multiply–accumulate is one multiply plus one add. Some papers report MACs, some report FLOPs meaning MACs, and some report FLOPs meaning 2 × MACs. A network quoted at "4.1 GFLOPs" and one quoted at "8.2 GFLOPs" may be the same network. This page reports MACs everywhere and says so in every figure. When you compare two published numbers, check the convention before you conclude anything.

Where the fully connected head goes wrong

Classic convnets end with a flatten and two or three dense layers, and that head is where the parameters actually are. For a 16-layer network on 224×224 input the numbers are stark:

a 13-conv-layer network with a 4096–4096–1000 head, counted exactlyall 13 convolution layers 14 714 688 params 15.35 G MACs (10.6% / 99.2%) the three dense layers 123 642 856 params 0.12 G MACs ( 89.4% / 0.8%) ─────────── ────────── total 138 357 544 15.47 G MACs The FIRST dense layer alone — 7·7·512 = 25 088 inputs into 4096 units — is 102 764 544 parameters, 74% of the entire network.

That single layer is why global average pooling (§17) replaced the flatten. Pool the final 7×7×512 map down to 1×1×512 and the head becomes 512 × 1000 + 1000 = 513 000 parameters instead of 123.6 million — a 241-fold reduction in the head, with better accuracy in practice because the flatten's parameters were mostly memorising absolute position.

14 The receptive field, layer by layer — computed, and then measured

A single 3×3 layer can only see 3×3. A network of them can see the whole image. How fast that happens is the single most important design quantity in a convolutional architecture: if the receptive field of the last layer is smaller than the object you are trying to recognise, no amount of training will fix it.

the recursion — three quantities, tracked together, one line eachstart: r₀ = 1 j₀ = 1 c₀ = 0.5 jₗ = jₗ₋₁ · sₗ rₗ = rₗ₋₁ + (fₑ,ₗ − 1) · jₗ₋₁ cₗ = cₗ₋₁ + ((fₑ,ₗ − 1)/2 − p₀,ₗ) · jₗ₋₁ what each one isrₗ RECEPTIVE FIELD. How many input pixels, along one axis, can change this unit's value. This is the number people quote. jₗ JUMP (or effective stride). How far apart, in INPUT pixels, two adjacent units of layer l are. The product of every stride so far — it is why a single stride-2 layer doubles the receptive-field growth of EVERY layer after it, not just its own. cₗ CENTRE of unit 0, in input coordinates. Nobody tracks this and it is why feature maps end up misregistered with their inputs. Half-integer values are the even-kernel offset of §09 trap 3.

The two rules worth memorising

stride 1, kernel f
Growth is additive
Each layer adds f − 1. So L layers of 3×3 give r = 2L + 1: five layers see 11 pixels, ten see 21, twenty see 41. To cover a 224-pixel image at stride 1 you would need 111 layers. Stride-1 stacking alone is far too slow.
with downsampling
Growth becomes multiplicative
A stride-2 layer doubles j, and every subsequent layer's contribution (f−1)·j is doubled with it. Five stride-2 stages multiply j by 32, and the same 3×3 layers now add 64 pixels each. This is why every classification convnet downsamples: not to save compute, but to make the receptive field grow geometrically.
and the trap
Padding does not change r
Padding changes the output size and the centre c, and leaves r and j completely alone. A layer's receptive field is a property of f, s and d only. That is why r can exceed the input size — and routinely does.

The verification matters more than the formula. Every receptive field quoted on this page was checked by direct measurement: run the stack on a zero image, run it again with exactly one input pixel set to one, and record which outputs changed. The width of the set of input pixels that move a given output is the receptive field, by definition, with no formula involved. Across twelve configurations — plain stacks, pooled stacks, strided stacks, dilated stacks, 1×1 stacks and even-kernel stacks — the measured span matched the formula in every case.

Receptive field: the recursion, and a direct perturbation measurement of the same quantity the measured span is obtained by moving a single input impulse and recording which outputs move — the formula is never consulted; the two numbers are printed side by side and must agree

15 Effective against theoretical receptive field: the number that is quoted is not the number that matters

§14's r is the set of inputs that can affect an output. It says nothing about how much each of them does. The answer turns out to be: overwhelmingly unequally, in a shape that is Gaussian, and over a radius that is much smaller than r.

the right definition of "how much"The influence of input pixel (i, j) on output unit u is the partial derivative ∂zᵤ / ∂xᵢⱼ which is a real number, not a yes/no. Set ∂L/∂zᵤ = 1 and every other output gradient to 0, run ONE backward pass, and the gradient that arrives at the input IS the influence map. The theoretical receptive field is the SUPPORT of that map; the EFFECTIVE receptive field is the region where it is not negligible. They are very different sets.

Why it is Gaussian, in one paragraph

Consider a stack of L stride-1 layers with kernel f, and forget the non-linearity for a moment. A path from an input pixel to an output unit picks one tap in each layer; the total influence of that pixel is the sum, over all such paths, of the product of the taps along it. The number of paths reaching an offset Δ is the number of ways to write Δ as a sum of L displacements each in {0, …, f−1} — which is a convolution of L uniform distributions. That is a sum of L i.i.d. random variables, so by the central limit theorem the path count is asymptotically Gaussian in Δ, with variance proportional to L. Two consequences follow immediately, and both are counter-intuitive:

consequence 1
The effective field grows like √L
The theoretical field grows linearly, as r = L(f−1) + 1. The standard deviation of the Gaussian grows as √L. So the effective field occupies a fraction ≈ 1/√L of the theoretical one, and that fraction shrinks as you add layers. Doubling the depth does not double what the unit actually looks at.
consequence 2
The corners are almost dead
A Gaussian on a square window puts almost nothing in the corners. Units at the edge of the theoretical field contribute a fraction of a percent. Quoting "receptive field 212" for a network whose effective field is a Gaussian of a few dozen pixels is technically correct and practically misleading.
what changes it
Skips, dilation and downsampling
Residual connections make the effective field smaller relative to the theoretical one, because the identity path concentrates influence at the centre. Dilation (§22) and stride spread it out. This is a large part of why segmentation architectures, which need genuinely large context, use dilation rather than just more layers.
The influence map: measured by backpropagation, not asserted the map is a real gradient, obtained by seeding one output unit with a gradient of one; the dashed square is the theoretical receptive field and the shaded disc is where 95% of the influence mass actually lies
The design mistake this causes. "My network has a receptive field of 212 pixels, so it can use whole-image context." It can in principle and does not in practice. If your task genuinely needs long-range context — segmenting a large object, reading a scene layout — a stack whose effective field is a tight Gaussian will underperform in a way that looks like an optimisation problem and is not. The fixes are architectural: dilation (§22), aggressive downsampling with an upsampling path (§23), or an attention layer, which has a flat influence profile by construction and is a large part of why transformers took vision (§33).
