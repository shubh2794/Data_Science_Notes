Distributed Training

Frontier models don't fit — or don't train in reasonable time — on one device. Distributed training splits the work across many GPUs, by replicating the model, slicing it, or staging it, often all at once.

Deep Learning Scale Systems

01 Two reasons to distribute

  • Throughput: a huge dataset trains too slowly on one GPU — spread the batch to go faster.
  • Capacity: the model (plus its gradients and optimizer state) doesn't fit in one GPU's memory — split it.
  • The three classic strategies — data, tensor, and pipeline parallelism — address these and combine into "3D parallelism"; sequence/context and expert parallelism add two more axes, and sharded data parallelism (ZeRO/FSDP) removes data parallelism's memory redundancy.

Six axes you can split along

A training step is a computation over a four-dimensional object: a batch of B sequences, each N tokens long, pushed through L layers whose weight matrices are h wide. Every parallelism scheme picks one of those dimensions (or the optimiser state that rides alongside the weights) and cuts it across devices. What you cut decides what you must communicate, how often, and whether that communication can hide behind arithmetic.

03 Data parallelism

  • Every GPU holds a full copy of the model and processes a different slice of the batch.
  • After the backward pass, gradients are all-reduced (averaged) across GPUs so all copies stay in sync.
  • Simple and the most common — but needs the whole model to fit on each GPU.

Why averaging gradients is exactly right

The loss of a minibatch is a mean over its examples, and the gradient is linear, so the gradient of the whole batch is the mean of the per-shard gradients. If D ranks each process b examples, the all-reduced average

data-parallel gradientg = (1/D) · Σᵣ gᵣ , gᵣ = (1/b) · Σ over rank r's examples of ∇ℓ = (1/(D·b)) · Σ over all D·b examples of ∇ℓ

is identical, up to floating-point summation order, to the gradient one device would compute on a batch of D·b. Data parallelism therefore does not approximate anything: it is large-batch training, and all the large-batch caveats (learning-rate scaling, warmup) apply unchanged — see Batch size & the LR coupling. Two things break the identity. Layers whose forward pass depends on batch statistics (BatchNorm) see only b examples per rank unless you synchronise them, and losses normalised per rank (e.g. dividing by that rank's count of non-padding tokens) give a different average from normalising by the global count. The second one is easy to miss: with variable-length sequences, averaging per-rank token means weights each rank equally rather than each token equally.

The effective batch

global batchglobal batch (sequences) = micro-batch per rank × accumulation steps × D worked: micro-batch 4, accumulation 8, D = 32 ranks → 4 × 8 × 32 = 1024 sequences at 4096 tokens each → 1024 × 4096 = 4,194,304 ≈ 4.2 M tokens per optimiser step

Gradient accumulation (the single-device technique of §28 there) composes with data parallelism in one specific way: the all-reduce is only needed on the last micro-batch of each accumulation window. Frameworks suppress synchronisation on the intermediate backward passes (PyTorch's no_sync() context), so with 8 accumulation steps the gradient traffic drops 8×. Forgetting this is a common reason a job with accumulation runs no faster per sample than one without.

Buckets and overlap

DDP does not wait for the whole backward pass and then send one giant tensor. It groups gradients into buckets (PyTorch's default cap is 25 MB) in roughly reverse layer order, and launches an asynchronous all-reduce for each bucket the moment every gradient in it is ready. The last layers' gradients are produced first, so their all-reduce runs while the earlier layers are still computing. With a deep enough network almost all of the communication is hidden; what remains exposed is the final bucket, the one containing the first layers. Larger buckets mean fewer launches (less per-message latency) but a later start; smaller buckets start earlier but pay latency on each. Two further details matter in practice: parameters that receive no gradient in a step (a conditional branch, an unused head) will stall the bucket they belong to unless DDP is told to search for unused parameters, which costs an extra graph traversal every step; and buffers such as BatchNorm running statistics are broadcast from rank 0 at each forward by default.

04 Where the memory goes: sixteen bytes per parameter

Before choosing a strategy, count what has to live on a GPU. For a model trained with Adam in mixed precision the answer is dominated by a number that is easy to remember and routinely underestimated: about 16 bytes for every parameter, before a single activation is stored.

model state, mixed-precision Adam (Ψ parameters)16-bit working weights 2 bytes · Ψ 16-bit gradients 2 bytes · Ψ fp32 master weights 4 bytes · Ψ ┐ fp32 Adam first moment m 4 bytes · Ψ ├ optimiser state K = 12 bytes · Ψ fp32 Adam second moment v 4 bytes · Ψ ┘ ───────────────────────────────────────────── total 16 bytes · Ψ = 2Ψ + 2Ψ + KΨ

The master copy exists because updates of size η·Δ are often below the 16-bit resolution of the weight they are added to, so the running sum must be kept in fp32 (mixed precision explains the rounding). Some stacks keep fp32 parameters and fp32 gradients and cast to 16 bits only for the matmuls; that is 4 + 4 + 8 = 16 bytes as well, split differently. SGD with momentum has K = 8 (master + momentum), and an 8-bit Adam can bring K down to about 6 by quantising the two moments.

Activations are the other half

Model state does not depend on the batch; activations do. For a transformer layer the stored activations scale as b·s·h times a constant that depends on what is kept (§12 derives the exact per-layer count). A 7 B-class model (h = 4096, 32 layers) at batch 1 and 4096 tokens stores about 34·b·s·h = 34 × 16.8 M ≈ 570 MB per layer with a fused attention kernel, or roughly 18 GB for 32 layers — before any checkpointing. Activation memory is why sharding the model state is necessary but not sufficient, and why sequence and context parallelism (§12–§14) exist.

05 ZeRO and FSDP: sharding the model state

  • ZeRO / FSDP: shard the optimizer states, gradients, and parameters across data-parallel GPUs instead of replicating them — huge memory savings with data-parallel simplicity.
  • Gradient accumulation: sum gradients over several micro-batches to simulate a large batch on limited memory.
  • Activation checkpointing: drop activations in the forward pass and recompute them in the backward pass — trade compute for memory.

The last two are single-device techniques (their mechanics are in Neural Network Training §28); they are listed here because every sharded run uses them. The rest of this section is about the first bullet.

The three ZeRO stages as formulas

Plain data parallelism keeps N identical copies of all 16Ψ bytes. The observation behind ZeRO ("ZeRO: Memory Optimizations Toward Training Trillion Parameter Models", arXiv 1910.02054) is that each rank only ever updates a slice of the parameters if the optimiser step is partitioned, so it only needs that slice's optimiser state; and it only needs full weights and full gradients for the layer it is currently computing. Two things follow. First, ZeRO-1 and ZeRO-2 have a floor: they still replicate the 16-bit weights (and ZeRO-1 the gradients), so no number of GPUs gets a 70 B model under 140 GB per rank with ZeRO-2. Only stage 3 divides everything by N; the paper's headline — a trillion parameters on 1024 GPUs at about 16 GB each — is the last row. Second, stages 1 and 2 are close to free in communication (§07 shows they move the same bytes as DDP), so for a model whose weights fit, ZeRO-2 is the usual default and ZeRO-3 is chosen only when it does not.

How ZeRO-3 / FSDP runs a layer

Each rank permanently owns 1/N of every parameter (a flat slice, or a slice of each tensor). To run a layer it must briefly hold the whole thing:

one sharded unit (usually one transformer block), per stepforward : all-gather the unit's weights → compute → free the gathered copy backward: all-gather weights again → compute grads → reduce-scatter grads (each rank keeps its 1/N) step : each rank updates only its own 1/N slice with its own 1/N of the optimiser state

Peak memory is therefore the permanent shard (16Ψ/N) plus the gathered working copy of the units in flight. That working copy is why the unit size matters: wrapping the whole model as one unit gathers every weight at once and loses the saving entirely, while wrapping each transformer block bounds the transient to one or two blocks. It is also why ZeRO-3 cannot rescue a model whose single largest layer does not fit on a GPU — that layer is gathered whole. Splitting within a layer is tensor parallelism's job (§10).

FSDP1 flat parameters against FSDP2 per-parameter sharding

PyTorch's first FSDP ("PyTorch FSDP: Experiences on Scaling Fully Sharded Data Parallel", arXiv 2304.11277) concatenates all parameters of a wrapped unit into one contiguous FlatParameter and shards that 1-D buffer evenly. One all-gather per unit is efficient, but the flattening leaks everywhere: individual parameters become views into a shared buffer, so freezing some of them, giving them different optimiser settings, or mixing dtypes inside a unit is awkward; and the flat shard does not respect tensor boundaries, so checkpoints need a gather or special resharding logic.

FSDP2 (the fully_shard API) instead shards each parameter on its own dimension 0 and represents it as a DTensor with a Shard(0) placement. Every parameter stays a real tensor with its own dtype and requires_grad; a sharded state dict is just the local shards plus placement metadata; and the same DTensor abstraction composes with tensor-parallel placements, which is what makes 2-D (FSDP × TP) layouts straightforward. The cost is that a unit's all-gather must copy several per-parameter shards into and out of a contiguous communication buffer; in practice this is fused and cheap. FSDP2 also drops the caching-allocator stream tricks FSDP1 used to recycle memory, which makes its peak memory more predictable.

06 Offloading to CPU and NVMe: memory you pay for in bandwidth

A server has far more host memory than GPU memory — an 8-GPU training node often has 1–2 TB of DRAM against 640 GB of HBM, and several TB of NVMe. Offloading parks the model states that are touched only once per step in those slower tiers and streams them in and out.

ZeRO-Offload ("ZeRO-Offload: Democratizing Billion-Scale Model Training", arXiv 2101.06840) keeps the 16-bit weights and all forward/backward compute on the GPU and moves the gradients and the whole optimiser (fp32 master, m, v) to the CPU, where a vectorised CPU Adam performs the update. The reasoning is a data-flow argument: the optimiser step is O(Ψ) arithmetic, cheap enough for a CPU, whereas forward and backward are O(Ψ · tokens) and must stay on the accelerator. What crosses PCIe per step is 2Ψ bytes of 16-bit gradients down and 2Ψ bytes of 16-bit updated weights up. The paper reports training 13 B parameters on a single V100 (about 10× what plain PyTorch fits) at 40 TFLOP/s for a 10 B model, and near-linear scaling to 128 GPUs.

ZeRO-Infinity ("ZeRO-Infinity: Breaking the GPU Memory Wall for Extreme Scale Deep Learning", arXiv 2104.07857) extends ZeRO-3 so that the weight shards themselves can live in CPU memory or on NVMe, fetched layer by layer just before use, with partitioned fetches so that every GPU's PCIe link is used in parallel. It reports over 25 PFLOP/s on 512 V100s (about 40% of peak) and model capacities in the tens of trillions of parameters.

If one optimiser step's forward and backward take 5–10 s (large batch with accumulation), this is a 10–20% overhead and a good trade. If the step is short, the CPU update and the PCIe transfer dominate and the GPU sits idle. ZeRO-Offload's one-step delayed parameter update overlaps the CPU step of iteration t with the GPU work of t+1, at the price of the gradient being one step stale; the paper enables it only after the early, unstable phase of training. NVMe is another order of magnitude slower (a few GB/s per drive) and only makes sense when the batch per step is very large or the alternative is not training at all.

Tempting: "Offload makes the model fit, so turn it on."
Better: first try more sharding (ZeRO-3 over more GPUs) or tensor parallelism, which cost NVLink/InfiniBand bandwidth measured in hundreds of GB/s; offload costs PCIe and DRAM bandwidth measured in tens. Offload is the tool for a fixed, small number of GPUs.

07 Communication is the bottleneck: collectives and their cost

Every strategy on this page moves data between GPUs — all-reduce, all-gather, all-to-all, point-to-point — and that traffic, not the arithmetic, is usually what limits scaling. A two-parameter cost model is enough to predict most of it.

  • Real systems combine data, tensor and pipeline parallelism (and often sequence and expert parallelism) plus sharding, and lay each onto the part of the network whose bandwidth matches its traffic (§18–§19).
  • It is a systems problem as much as an ML one: the same model can run at very different efficiency depending on which dimension crosses which link.

The collectives, and what each costs per rank

Every scheme on this page is built from six communication primitives. Their cost is best stated as the bytes each rank must send (and, symmetrically, receive), because on a ring or a switched fabric that is what the per-GPU link bandwidth β bounds. For a buffer of S bytes over n ranks:

The all-reduce row is the important identity: a bandwidth-optimal all-reduce is a reduce-scatter followed by an all-gather, which is why the ring algorithm sends 2·(n−1)/n · S — just under twice the buffer — no matter how many ranks there are. Adding ranks does not make the per-rank traffic grow; it adds 2·(n−1) latency steps of α each (microseconds on NVLink, more across nodes), which is why very large jobs switch to tree or hierarchical algorithms for small messages.

(ZeRO-1 and ZeRO-2 move the same bytes; the difference is that ZeRO-1 still allocates a full-size gradient buffer and discards the parts it does not own after the reduce-scatter.) So stages 1 and 2 add no traffic over DDP; they only change its shape. Only stage 3 costs more, and only by half. A frequently repeated rule of thumb says ZeRO needs far more interconnect than DDP; that holds for stage 3's 1.5× volume and for the fact that its all-gathers sit on the critical path of every layer (they must finish before that layer can compute), not for the total bytes of stages 1–2.

08 The ring all-reduce, step by step

The 2·(n−1)/n · S of §07 is not a convention; it falls out of a specific algorithm. Seeing it run explains both why the bandwidth term does not grow with the number of ranks and why the latency term eventually does.

Arrange the n ranks in a ring and cut every rank's buffer into n chunks. In reduce-scatter step k, rank r sends its partial sum of chunk (r − k) mod n to rank r+1, which adds it to its own copy. After n − 1 steps every chunk has visited every rank once, and rank r holds the complete sum of one chunk. In all-gather the completed chunks travel round the ring once more, overwriting instead of adding, for another n − 1 steps.

ring all-reduce, buffer S bytes, n rankssteps 2·(n−1) (n−1 reduce-scatter + n−1 all-gather) bytes per step S/n per rank, every rank sending and receiving at once bytes sent per rank 2·(n−1)·S/n → 2S as n grows time 2·(n−1)·α + 2·(n−1)/n · S/β

Every link carries traffic in every step, which is why the ring is bandwidth-optimal: no algorithm can have a rank send less than (n−1)/n · S in each half, because each rank must contribute its (n−1)/n share to other ranks' chunks and receive theirs. The cost the ring pays is the step count. Its latency term grows linearly in n.

For a DDP bucket on a large flat ring, the latency term is ten times the bandwidth term. Collective libraries therefore do not use one flat ring at scale. Tree algorithms (NCCL ships a double binary tree alongside the ring) have a latency term logarithmic in n at a modest bandwidth cost. Hierarchical all-reduce exploits the two-tier network: reduce-scatter inside each node over NVLink, all-reduce the resulting 1/g shards across nodes (one ring per local GPU index, running in parallel), then all-gather inside the node. Each GPU then sends only 2·(N−1)/N · S/g bytes across the slow network, where N is the node count and g the GPUs per node. The library picks among these per message size and topology. In practice, message size (bucket size) is the knob you control.

09 DDP in practice: launching, buckets and accumulation

§03 explained why DDP is correct and how bucketing hides communication. This section is the working version: one process per GPU, a launcher that wires them together, and the three settings that decide whether the overlap actually happens.

One process per GPU

Each GPU is driven by its own Python process. A launcher starts them and tells each one who it is through environment variables: RANK (global index), LOCAL_RANK (index within the node, used to pick the device), WORLD_SIZE, and a rendezvous address (MASTER_ADDR/MASTER_PORT, or a rendezvous endpoint). The process group is then created once, the model is wrapped, and every rank gets a disjoint slice of the data.

import os, torch, torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP
from torch.utils.data.distributed import DistributedSampler

dist.init_process_group(backend="nccl")              # reads RANK / WORLD_SIZE / MASTER_* from the launcher
local = int(os.environ["LOCAL_RANK"]); torch.cuda.set_device(local)
model = DDP(build_model().cuda(), device_ids=[local],
            bucket_cap_mb=25)                         # the default; larger = fewer, later all-reduces
sampler = DistributedSampler(dataset, shuffle=True)   # each rank sees 1/WORLD_SIZE of every epoch
loader = DataLoader(dataset, batch_size=micro_bs, sampler=sampler)

for epoch in range(E):
    sampler.set_epoch(epoch)                          # otherwise every epoch reuses the same shuffle
    for i, batch in enumerate(loader):
        last = (i + 1) % accum == 0
        ctx = contextlib.nullcontext() if last else model.no_sync()
        with ctx:                                     # no all-reduce on the first accum−1 micro-batches
            loss = model(batch).loss / accum
            loss.backward()
        if last:
            opt.step(); opt.zero_grad(set_to_none=True)
# one node, 8 GPUs
torchrun --nproc-per-node 8 train.py
# two nodes: run on each, same endpoint
torchrun --nnodes 2 --nproc-per-node 8 --rdzv-backend c10d --rdzv-endpoint head-node:29500 train.py
# the same script under Accelerate (its config file supplies the counts)
accelerate launch --num_processes 8 train.py

With Accelerate the loop is written against an Accelerator. Its accumulate(model) context skips the gradient synchronisation on intermediate micro-batches the same way no_sync() does, and the Transformers Trainer does it for you when gradient_accumulation_steps is set (§20).

10 Model parallelism I — tensor parallelism: the Megatron split

Data parallelism, even fully sharded, needs every layer to fit on one GPU at the moment it runs and keeps per-GPU activations at a full layer's width. Model parallelism splits the model itself. Tensor parallelism does it inside each layer (this section and the next two), and pipeline parallelism does it across layers (§15–§16).

  • Tensor (intra-layer): split a single layer's matrices across GPUs. Each computes part of every layer, then the parts are combined. Heavy, frequent communication, so it needs a fast interconnect.
  • Pipeline (inter-layer): put different layers on different GPUs, and micro-batches flow through the stages like an assembly line. Watch out for the idle "bubble" at the ends.

The MLP: column split, then row split

The construction in "Megatron-LM: Training Multi-Billion Parameter Language Models Using Model Parallelism" (arXiv 1909.08053) rests on one observation about the transformer MLP Z = GeLU(X·A)·B. Split the first matrix A (h × 4h) by columns across t GPUs. Then each GPU computes X·Aᵢ, a slice of the hidden activation, from the full input X. The nonlinearity is applied element-wise, so GeLU(X·Aᵢ) is exactly the corresponding slice of GeLU(X·A) and no communication is needed. Split the second matrix B (4h × h) by rows to match. Each GPU now computes a full-width partial product Zᵢ = GeLU(X·Aᵢ)·Bᵢ, and the output is their sum.

tensor-parallel MLP, t GPUsA = [A₁ A₂ … A_t] (columns, h × 4h/t each) B = [B₁; B₂; … ; B_t] (rows, 4h/t × h each) Z = Σᵢ GeLU(X·Aᵢ)·Bᵢ one all-reduce produces Z on every GPU had we split A by rows: GeLU(X₁A₁ + X₂A₂) ≠ GeLU(X₁A₁) + GeLU(X₂A₂) → a sync before the GeLU

The last line is why the order matters. A row split of A would put a sum inside the nonlinearity and cost a second synchronisation per MLP.

Attention: split by heads

Attention is already parallel over heads. The Q, K and V projections are split by columns so that each GPU owns a/t complete heads. It computes those heads' attention locally with any kernel, then applies its row-slice of the output projection. That again produces a partial sum and one all-reduce. The head count must be divisible by t. With grouped-query attention the key/value head count is the tighter limit, and KV heads are replicated when t exceeds it.

The conjugate operators f and g

the two operators Megatron inserts around each blockf : forward = identity backward = all-reduce of ∂L/∂X (before the column-split matmul) g : forward = all-reduce backward = identity (after the row-split matmul) per transformer layer (attention + MLP): 2 all-reduces forward + 2 all-reduces backward

The backward all-reduce in f is needed because each GPU computes only its share of the input gradient, ∂L/∂X = Σᵢ ∂L/∂(XAᵢ) · Aᵢᵀ. It is a sum over the column slices, so the pieces must be summed exactly as the outputs were in the forward pass. The two operators are conjugates: whatever one does forward, the other does backward.

Embeddings and the loss

The input embedding is split along the vocabulary, and each GPU looks up the tokens in its range, contributing zeros elsewhere. An all-reduce assembles the result. The output layer is the same matrix, split the same way. Gathering b·s·V logits to compute the cross-entropy would be expensive, so Megatron-LM fuses the parallel output GEMM with the loss. Each GPU reduces its logits to per-token partial statistics (its local max and sum of exponentials, and the target logit if it owns it), and only those b·s-sized quantities are communicated. The paper reports 15.1 PetaFLOPs sustained on 512 GPUs for an 8.3 B-parameter model, 76% scaling efficiency against a single-GPU baseline of 39 TeraFLOPs (30% of peak).

13 Context parallelism I — ring attention

Sequence parallelism splits the token-local regions across the tensor-parallel group, but attention itself still sees the whole sequence on every GPU. At 128 K tokens and beyond, one sequence's activations do not fit even with everything in §12. Context parallelism splits the sequence for the whole layer, attention included.

Every operation except attention acts on each token independently, so with the sequence cut into C chunks each rank runs projections, MLP and norms on its own s/C tokens with no communication at all. Attention needs every query to see every earlier key. Ring attention ("Ring Attention with Blockwise Transformers for Near-Infinite Context", arXiv 2310.01889) keeps each rank's queries in place and passes the key/value blocks round a ring. At each of C steps a rank computes attention of its queries against the K/V block it currently holds, while it sends that block on and receives the next one.

Why the result is exact: online softmax

A softmax over keys that arrive in blocks can be accumulated exactly by carrying three running quantities per query row: the running maximum m, the running denominator ℓ, and the unnormalised output o. The same identity underlies fused attention kernels, applied here across devices instead of across on-chip tiles.

absorbing K/V block j into the running state (per query row)Sⱼ = Q·Kⱼᵀ / √d m' = max(m, rowmax(Sⱼ)) ℓ' = e^(m − m')·ℓ + rowsum(e^(Sⱼ − m')) o' = e^(m − m')·o + e^(Sⱼ − m')·Vⱼ after the last block: output = o / ℓ (identical to softmax(QKᵀ/√d)·V)

The backward pass runs the ring again, circulating K/V together with their gradient accumulators. Memory per rank is proportional to s/C: the paper counts six blocks of b·c·h (query, the current K and V, the incoming K and V, and the output), independent of the total sequence length.

When the ring hides its own communication

Per step a rank computes about 4·d·c² FLOPs on a block of c tokens and sends about 4·c·d bytes, so compute hides the transfer when c ≥ F/B, the device's FLOP rate over its link bandwidth. That is the paper's condition. Its Table 2 puts the minimum block at about 1 K tokens for A100s on NVLink (312 TFLOP/s ÷ 300 GB/s ≈ 1,040) and about 25 K over InfiniBand at 12.5 GB/s. It requires each device's sequence to be about six blocks, between roughly 6 K and 10 K tokens on fast interconnects. The paper states the ring allows sequences "up to device count times longer" than prior memory-efficient transformers, without approximation.

The causal-mask imbalance, and the zig-zag fix

With a causal mask, cut the sequence into contiguous chunks. Rank 0's queries attend only to its own keys, while the last rank's queries attend to everything. At most ring steps some ranks have nothing to compute while others do a full block, and the slowest rank sets the pace. The figure measures the result: with contiguous chunks the pass takes 2C − 1 block-times of the busiest rank's work instead of C, for a utilisation of C/(2C−1). That is 57% at C = 4, tending to 50%. The standard fix cuts the sequence into 2C chunks and gives rank r chunks r and 2C−1−r, pairing an early chunk with a late one. Every rank then does the same work at every step. The Llama 3 paper ("The Llama 3 Herd of Models", arXiv 2407.21783) describes exactly this split into 2×CP chunks. Its implementation all-gathers K and V instead of passing them round a ring, which it motivates by easier support for arbitrary attention masks (such as document masks) and by K and V being much smaller than Q under grouped-query attention. Striped attention (arXiv 2311.09431) reaches the same balance by assigning tokens round-robin.

Work counts a full chunk-by-chunk block as 1 and a diagonal block as ½. Utilisation is total work ÷ (C × the sum over steps of the busiest rank's work). 14 Context parallelism II — Ulysses head all-to-all, and which to use

Ring attention keeps the sequence split and moves keys and values. The other design switches which dimension is split: around attention, turn a sequence-sharded tensor into a head-sharded one, run ordinary full-sequence attention on a subset of heads, and switch back.

"DeepSpeed Ulysses: System Optimizations for Enabling Training of Extreme Long Sequence Transformer Models" (arXiv 2309.14509) does this with two all-to-alls per layer. Before attention, each rank holds Q, K and V for N/P tokens and all heads. An all-to-all regroups them so each rank holds all N tokens for a/P heads. Attention is then entirely local, and any kernel works because every head sees its whole sequence. A second all-to-all on the output restores the sequence split for the rest of the layer.

15 Model parallelism II — pipeline parallelism and the bubble

Cut the model by depth into p stages of L/p consecutive layers, one stage per GPU (or per tensor-parallel group). Only the activations at stage boundaries cross the network, point to point, so pipeline parallelism is the cheapest scheme in bandwidth and the natural one to stretch across nodes. The price is idle time.

Naively, stage 1 cannot start until stage 0 has finished the whole batch, so only one GPU works at a time. GPipe ("GPipe: Efficient Training of Giant Neural Networks using Pipeline Parallelism", arXiv 1811.06965) splits the batch into m micro-batches and streams them through, running all forwards and then all backwards. The pipeline still has to fill and drain. Stage p−1 waits p−1 forward slots before its first micro-batch arrives, and stage 0 waits the same at the end of the backward.

The two conventions describe the same schedule: (p−1)/m ÷ (1 + (p−1)/m) = (p−1)/(m+p−1). A quoted "bubble of 37.5%" at p = 4, m = 8 is the second one; the fraction of wall-clock time idle is 27.3%. The remedy is more micro-batches. GPipe reports the bubble as negligible once m ≥ 4p. But m is bounded by the global batch: m = global batch ÷ (micro-batch × data-parallel degree), so adding data parallelism shrinks the m available to each pipeline.

GPipe reports a 557 M-parameter AmoebaNet at 84.4% ImageNet top-1 and a 6 B-parameter, 128-layer multilingual Transformer. It kept memory in check with re-materialisation, storing only stage-boundary activations and recomputing the rest in backward, because an all-forwards-first schedule must hold activations for all m micro-batches at once.

Two practical costs are not in the formula. Stage balance: the slowest stage sets the clock, and the embedding and output layers make the first and last stages heavier than the middle ones, so layer counts per stage are often uneven. And batch-statistics layers and tied weights across stages (input and output embeddings on different GPUs) need their own synchronisation.

The Hugging Face parallelism guide summarises the trade in words. Pipeline parallelism "creates micro-batches" so that GPUs work concurrently, but "it also isn't possible to completely reduce idle time because the last forward pass must also wait for the backward pass to finish". It also notes that models may need rewriting as a sequence of nn.Sequential modules.

16 Pipeline schedules: 1F1B, interleaved, zero bubble

Every schedule after GPipe attacks one of two costs: the activation memory of holding many micro-batches in flight, or the bubble itself.

1F1B: same bubble, bounded memory

The one-forward-one-backward schedule was introduced in PipeDream ("PipeDream: Fast and Efficient Pipeline Parallel DNN Training", arXiv 1806.03377). Its flushed, synchronous form is used by Megatron-LM. After a warm-up of p − 1 − i forwards on stage i, each stage alternates one forward with one backward. A micro-batch's activations are released as soon as its backward runs, so stage 0 never holds more than p micro-batches and later stages fewer, whatever m is. The bubble is unchanged, (p−1)/(m+p−1), but raising m to shrink it no longer costs memory. PipeDream itself was asynchronous and kept several weight versions ("weight stashing") so that a micro-batch's backward used the weights of its forward. Synchronous flushed 1F1B gives the same updates as ordinary training.

Since stage 0 holds p micro-batches of L/p layers each, the peak activation memory on stage 0 is L layers' worth for one micro-batch, the same as without pipelining. Pipelining divides the weights by p but not the first stage's activations.

Interleaved 1F1B: v chunks per device

Megatron-LM's interleaved schedule (arXiv 2104.04473) gives each device v non-contiguous chunks of layers. With p = 4 and v = 2, device 0 holds layers 1–2 and 9–10 of 16. Each forward slot is now 1/v as long, so the fill and drain shrink by v:

interleaved bubblebubble fraction (p − 1) / (v·m + p − 1) (idle ÷ useful: (p − 1) / (v·m)) cost v× as many point-to-point messages; m must be a multiple of p in Megatron's implementation

The paper reports that the interleaved schedule "can improve throughput by 10+% with memory footprint comparable to existing approaches". The whole system trained a 1 T-parameter model at 502 petaFLOP/s on 3072 GPUs, 52% of theoretical peak per GPU.

Zero bubble: split the backward

"Zero Bubble Pipeline Parallelism" (arXiv 2401.10241) observes that the backward is two computations with different dependencies. B computes the gradient with respect to the layer's input, which the previous stage is waiting for. W computes the gradient with respect to the weights, which nobody downstream needs until the optimiser step. Running B promptly and deferring W into what would otherwise be bubble slots fills the drain. With F, B and W each taking one unit, the paper's handcrafted ZB-H1 schedule has a bubble of (p−1)·(F + B − W), one third of 1F1B's (p−1)·(F + B + W), at the same peak memory. ZB-H2 reaches nearly zero with more memory. The paper also bypasses the synchronisation normally done before the optimiser step and adds an automatic scheduler. It reports up to 23% higher throughput than 1F1B under a similar memory limit, and up to 31% when the memory constraint is relaxed.

17 Expert parallelism: all-to-all dispatch and combine

A mixture-of-experts layer replaces one MLP with E expert MLPs and a router that sends each token to its top-k (routing is covered on its own page). Parameters grow with E while FLOPs per token grow only with k, which makes the experts the natural thing to spread across GPUs.

With expert-parallel degree X, each rank holds E/X experts. The rest of the layer (attention, norms, router) is replicated across those same ranks and trained data-parallel on different tokens. Each MoE layer then needs two all-to-alls. Dispatch sends every token's hidden vector to the ranks that own its chosen experts. Combine sends the expert outputs back so each token's weighted sum can be formed where the token lives. Backward repeats both in reverse.

Unlike a ring collective, an all-to-all finishes when its slowest pair finishes, so it is sensitive both to topology and to routing skew: a popular expert makes its rank receive more than T·k/X. That is why EP groups are usually kept inside a fast domain, and why load balance is also a systems property, not only a modelling one.

Capacity factor

Static-shape implementations allocate a fixed buffer per expert. With capacity factor CF, each expert accepts at most

expert capacitycapacity = ⌈ CF · (tokens routed in the group · k) / E ⌉ tokens over capacity are dropped: they skip the expert and pass on through the residual connection

CF = 1 is exactly enough under perfectly uniform routing and drops tokens under any skew. Larger factors drop fewer tokens but pad every buffer, so they waste both all-to-all bandwidth and expert FLOPs. GShard ("GShard: Scaling Giant Models with Conditional Computation and Automatic Sharding", arXiv 2006.16668) used such a per-expert capacity alongside its sharding annotations. It trained a 600 B-parameter multilingual translation MoE on 2048 TPU v3 accelerators in 4 days. Later "dropless" implementations avoid capacity altogether with variable-size grouped matmuls.

Expert parallelism: the dispatch matrix and expert capacity routing is sampled from a skewed preference over experts; raise the skew to see drops and a hot rank

Routing is simulated with a fixed seed. Expert e is preferred with weight 1/(rank + 1)^skew over a shuffled order, each token draws k distinct experts, and tokens are processed in order so the last arrivals at a full expert are the ones dropped. Skew 0 is uniform routing. Bytes are 16-bit hidden vectors for the rank that sends the most off-rank traffic.

Laying out EP with DP and TP

Expert parallelism is carved out of ranks that are otherwise data-parallel (and possibly context-parallel) for the dense layers. With D data-parallel ranks and EP degree X dividing D, there are D/X copies of each expert, and an expert's gradients are all-reduced only among those copies. Tensor parallelism can additionally split each expert's matrices, or it can be kept for attention only. The Transformers expert-parallel path does the latter (§20).

The inference angle. In serving, expert parallelism lets a model whose total parameters exceed a node's memory run with each GPU holding a few experts. The all-to-all latency per generated token then matters more than bandwidth, which is why serving stacks co-locate EP groups on the fastest link available.

18 Composing N-D parallelism: the device mesh

Large runs use several axes at once. The GPU count factors into a product of degrees, the GPUs are arranged as a multi-dimensional grid (a device mesh), and each axis of the grid runs its own collectives within its own groups. The design question is which axis goes on which link.

the bookkeeping identitiesN GPUs = TP × CP × PP × DP (EP is drawn from within DP × CP) global batch = micro-batch × m × DP (TP, CP and PP do not multiply the batch) micro-batches m = global batch ÷ (micro-batch × DP) → feeds the pipeline bubble (p−1)/(m+p−1) constraints TP | heads (KV heads with GQA) · PP ≤ layers · CP | sequence · EP | experts

Rank r sits at coordinate (r ÷ 8, r mod 8), so ranks 0–7 form one TP group on node 0 and ranks 0, 8, 16, … form one DP group, one GPU per node. 19 Choosing degrees for real hardware: a 70 B model on 64 and 512 GPUs

Put the page's formulas together for one model and two cluster sizes. Take a 70 B model (h = 8192, 80 layers, 64 heads), 80 GB GPUs in 8-GPU NVLink nodes with 50 GB/s of InfiniBand per GPU, 4,096-token sequences, a global batch of 4,194,304 tokens (1,024 sequences) and 400 TFLOP/s achieved.

64 GPUs (8 nodes)

Both plans fit. A trades a full re-run of the forward for simplicity; B keeps activations without full recompute and moves an order of magnitude less over InfiniBand, paying about 17% exposed TP time instead. At this size either is defensible, and measuring beats arguing.

The fixed global batch is what changes the answer. At 512 GPUs each GPU gets two sequences per step, so compute per GPU falls 8× while pure FSDP's per-GPU traffic stays at about 3 × the model's 16-bit size. Tensor parallelism divides that traffic by 8, because each DP group now synchronises only a 1/8 slice. Adding a short pipeline trades a 3% bubble for replacing ZeRO-3's per-layer gathers with a once-per-step ZeRO-1 reduce-scatter and all-gather. The planner below evaluates any such layout.

N-D layout planner choose degrees; DP is what is left over. Memory, bubble and communication update from the formulas of §04–§17

Rank order is [TP, CP, PP, DP], innermost first. Model state is 16 bytes per parameter of this GPU's TP × PP shard, sharded over DP per the chosen ZeRO stage. Activations use §12's 34·s·b·h/t (or 2·s·b·h/t) per layer for s/CP local tokens, times L/PP layers, times PP micro-batches in flight on stage 0 under 1F1B. TP communication uses §11's ratio on NVLink if TP fits the domain, otherwise on InfiniBand. DP traffic is 2× (ZeRO-1) or 3× (ZeRO-3) the shard's 16-bit size over InfiniBand once the job spans more than one domain. Compute is 6·Ψ·tokens ÷ GPUs at 400 TFLOP/s. Embedding, logits, all-gather buffers and fragmentation are ignored, so leave headroom.

Tempting: "More GPUs, same recipe: just raise DP."
Better: at a fixed global batch, raising DP lowers the tokens per GPU and the micro-batches per pipeline. Communication stops hiding and the bubble grows. Past some size, the degrees have to be re-chosen, not scaled.

  • DDP "activates automatically when you launch with a multi-process launcher" such as accelerate launch --num_processes 4 train.py. It is configured by TrainingArguments fields: ddp_bucket_cap_mb, ddp_find_unused_parameters (don't combine with gradient checkpointing), ddp_broadcast_buffers, ddp_backend ("nccl" for NVIDIA GPUs) and ddp_timeout. With gradient_accumulation_steps set, the Trainer "skips the all-reduce on intermediate accumulation steps and runs it only on the final micro-batch".
  • FSDP2: set fsdp=True and pass an fsdp_config (or use an Accelerate config with fsdp_version: 2). reshard_after_forward chooses between re-gathering in backward (true, less memory) and keeping parameters gathered (false), the §05 knob. auto_wrap_policy defaults to "TRANSFORMER_BASED_WRAP". With "NO_WRAP" "the entire model is one FSDP unit and you lose the memory benefit of sharding". state_dict_type defaults to "FULL_STATE_DICT"; "SHARDED_STATE_DICT" writes one file per rank and "only load[s] back into FSDP". cpu_ram_efficient_loading loads on rank 0 and broadcasts. activation_checkpointing should be used instead of the Trainer's gradient checkpointing, and setting both raises an error.
  • DeepSpeed: pass a JSON config to TrainingArguments(deepspeed=...), using "auto" for values the Trainer should fill. The docs warn that mismatched manual values make training "continue silently with the wrong values". For ZeRO-3, TrainingArguments must be created before the model is loaded, or "no memory is saved". offload_optimizer takes cpu, and offload_param is ZeRO-3 only. stage3_gather_16bit_weights_on_model_save is required to save a consolidated 16-bit model. Expert parallelism

DistributedConfig(tp_size=WORLD_SIZE, enable_expert_parallel=True) switches an MoE model to the ep_plan in its config. Per the docs, it "automatically enables tensor parallelism for attention layers", expert weights are split "so each device loads only its local experts", the ep_router "routes tokens to experts and an all-reduce operation combines their outputs", and "the number of devices must evenly divide the total number of experts". That is a different mechanism from §17's all-to-all: router scores for non-local experts are masked, and the partial outputs are summed with an all-reduce.

Recorded conflicts and gaps, doc against paper.
  • The DeepSpeed page says each additional ZeRO stage reduces memory "at the cost of more inter-GPU communication". The ZeRO paper's analysis (§07) gives stages 1 and 2 the same volume as DDP (2Ψ); only stage 3 adds traffic (3Ψ). The page's own advice, "use ZeRO-3 only when your model doesn't fit across GPUs with ZeRO-2", is consistent with the paper.
  • The strategy table labels fast inter-node connectivity as "NVLink or NVSwitch". On standard servers those are intra-node links, and cross-node traffic uses InfiniBand or Ethernet (rack-scale NVLink systems excepted). Its two multi-node rows also recommend the same strategies, so it does not by itself distinguish fast from slow networks. §18–§19 do.
  • Expert parallelism is documented with an all-reduce combine rather than the all-to-all dispatch/combine of GShard-style systems (§17).
  • The v5.17.0 documentation has no context-parallelism guide (the page exists only in the main-branch docs), and enable_sequence_parallel is marked not wired up. Nothing about context parallelism in Transformers is stated here for that version.

21 Fault tolerance and checkpointing sharded state

At thousands of GPUs, failure is a routine event, not an exception, and the checkpoint is several times the model's size. How often you save, and in what shape, is part of the parallelism design.

The Llama 3 paper reports 466 job interruptions in a 54-day snapshot of pre-training: 47 planned and 419 unexpected. About 78% of the unexpected ones were attributed to confirmed or suspected hardware issues, with GPU issues the largest category at 58.7%. Automation handled all but three, and the team reports higher than 90% effective training time.

How often to checkpoint

first-order optimum interval (Young, 1974), save cost δ, mean time between failures Mτ* ≈ √(2 · δ · M) lost fraction ≈ δ/τ + τ/(2M) (time spent saving + expected recomputation after a failure) worked: 419 failures in 54 days → M ≈ 54 × 24 / 419 = 3.1 h = 11,100 s δ = 60 s (blocking save) → τ* ≈ √(2·60·11,100) ≈ 1,150 s ≈ 19 min, lost ≈ 5.2% + 5.2% = 10.4% δ = 10 s (async to host) → τ* ≈ 470 s ≈ 8 min, lost ≈ 2.1% + 2.1% = 4.2%

The restart itself (rescheduling, re-initialising NCCL, reloading) adds to every failure, so the real loss is higher. The formula shows the lever: making saves cheap shortens the optimal interval and cuts both terms. Asynchronous checkpointing copies the shards to host memory, which blocks training only briefly, and writes them to storage in the background.

Sharded, not gathered

what a full training checkpoint holds, 70 B, mixed-precision Adam16 bytes × 70e9 = 1.12 TB (fp32 master 280 GB + m 280 GB + v 280 GB + 16-bit weights 140 GB + …) gathered to rank 0 : one host must hold and write 1.12 TB sharded, 64 ranks : 17.5 GB per rank, written in parallel

Sharded checkpoints (FSDP's SHARDED_STATE_DICT, DeepSpeed's per-rank files, PyTorch Distributed Checkpoint) have every rank write its own shard plus metadata about where each piece belongs. The metadata is what makes resharding possible: loading onto a different world size or parallel layout by reading, for each new shard, the byte ranges it needs from the old ones. DeepSpeed calls its version universal checkpointing. The weights-only export for inference is a separate step: gather the 16-bit weights once (DeepSpeed's stage3_gather_16bit_weights_on_model_save, or FSDP's full state dict) at the end.

  • Detect hangs, not only crashes. A dead rank leaves the others blocked inside a collective. A collective timeout (DDP's timeout, the Trainer's ddp_timeout) turns a silent hang into an error that the launcher can act on.
  • Restart automatically. torchrun's elastic mode restarts the worker group on failure (--max-restarts), re-running rendezvous, and the script resumes from the last checkpoint.
  • Save the data position and RNG state with the model. Resuming at the right weights but re-reading already-seen data changes the run.

22 Pitfalls

Most distributed-training bugs do not crash. They make the run slower than it should be, or quietly train a different model.

Correctness

  • Per-rank loss normalisation. Dividing by each rank's own token count and then averaging across ranks weights ranks, not tokens (§03). Normalise by the global count.
  • Forgetting sampler.set_epoch. Every epoch then repeats the same shuffle on every rank.
  • Different random seeds where they must match (initialisation under TP must be consistent across the group, and dropout inside TP regions must differ across ranks in the right places), or the same seed where they must differ (data order across DP ranks).
  • Splitting a fused weight with a plain shard. A gate_up matrix split into contiguous halves gives one rank all of the gate. The shapes are right, so nothing fails (§20).
  • Mismatched DeepSpeed and Trainer values (batch size, accumulation) when not set to "auto". Training continues with the wrong ones.
  • Loading the model before ZeRO-3 is configured. Every rank materialises the full model first and no memory is saved.

Performance

  • Accumulation without no_sync: one all-reduce per micro-batch instead of per step (§09).
  • Tensor parallelism across nodes: the §11 ratio exceeds 1 on InfiniBand for realistic widths.
  • Wrapping the whole model as one FSDP unit: the gathered copy is the whole model and the saving disappears (§05).
  • Too few micro-batches per pipeline after raising DP at a fixed global batch: the bubble grows as (p−1)/(m+p−1) (§15).
  • Contiguous context-parallel chunks with a causal mask: utilisation tends to 50% (§13).
  • Offload as a first resort: PCIe and DRAM bandwidth are an order of magnitude below NVLink (§06).
  • Tiny buckets on large rings: the latency term dominates (§08).
Takeaway: write down the expected communication-to-compute ratio of each axis before launching. A measured step time that disagrees with it by more than the overlap you expect is almost always one of the bugs above.

24 What to remember

Ten statements, each backed by a section above.

  • Data parallel replicates the model, splits the batch and all-reduces gradients. It is exact large-batch training, and its traffic hides behind compute only while each GPU has enough tokens.
  • Training costs about 16 bytes per parameter before activations. A 7 B model does not fit plain DDP on an 80 GB GPU.
  • ZeRO-1/2 are free in bandwidth; ZeRO-3/FSDP costs 1.5× and puts gathers on every layer's critical path, but divides everything by N.
  • All-reduce = reduce-scatter + all-gather, about 2S per rank whatever n is; at scale the latency term, not the bytes, is what breaks flat rings.
  • Tensor parallelism splits matrices column-then-row with two all-reduces per block each way. Its cost ratio does not improve with more tokens, so it lives inside the NVLink domain.
  • Sequence parallelism removes the activations TP leaves replicated, at no extra bandwidth. Selective recompute removes the s² term.
  • Context parallelism splits attention itself: a ring of K/V blocks merged with online softmax, or a head all-to-all. Causal masks need a balanced layout.
  • Pipeline parallelism is cheap in bandwidth and pays a (p−1)/(m+p−1) bubble. 1F1B bounds memory, interleaving and zero-bubble shrink the bubble.
  • Expert parallelism costs two all-to-alls per MoE layer each way, and routing skew is a systems problem, capped by capacity.
  • Compose by bandwidth: [TP, CP, PP, DP] from the fastest link to the slowest, and re-choose the degrees when the GPU count changes at a fixed batch. Scales up Neural Network Training, and is essential for LLMs.
