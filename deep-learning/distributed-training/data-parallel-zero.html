03 Data parallelism

  • Every GPU holds a full copy of the model and processes a different slice of the batch.
  • After the backward pass, gradients are all-reduced (averaged) across GPUs so all copies stay in sync.
  • Simple and the most common — but needs the whole model to fit on each GPU.

Why averaging gradients is exactly right

The loss of a minibatch is a mean over its examples, and the gradient is linear, so the gradient of the whole batch is the mean of the per-shard gradients. If D ranks each process b examples, the all-reduced average

data-parallel gradientg = (1/D) · Σᵣ gᵣ , gᵣ = (1/b) · Σ over rank r's examples of ∇ℓ = (1/(D·b)) · Σ over all D·b examples of ∇ℓ

is identical, up to floating-point summation order, to the gradient one device would compute on a batch of D·b. Data parallelism therefore does not approximate anything: it is large-batch training, and all the large-batch caveats (learning-rate scaling, warmup) apply unchanged — see Batch size & the LR coupling. Two things break the identity. Layers whose forward pass depends on batch statistics (BatchNorm) see only b examples per rank unless you synchronise them, and losses normalised per rank (e.g. dividing by that rank's count of non-padding tokens) give a different average from normalising by the global count. The second one is easy to miss: with variable-length sequences, averaging per-rank token means weights each rank equally rather than each token equally.

The effective batch

global batchglobal batch (sequences) = micro-batch per rank × accumulation steps × D worked: micro-batch 4, accumulation 8, D = 32 ranks → 4 × 8 × 32 = 1024 sequences at 4096 tokens each → 1024 × 4096 = 4,194,304 ≈ 4.2 M tokens per optimiser step

Gradient accumulation (the single-device technique of §28 there) composes with data parallelism in one specific way: the all-reduce is only needed on the last micro-batch of each accumulation window. Frameworks suppress synchronisation on the intermediate backward passes (PyTorch's no_sync() context), so with 8 accumulation steps the gradient traffic drops 8×. Forgetting this is a common reason a job with accumulation runs no faster per sample than one without.

Buckets and overlap

DDP does not wait for the whole backward pass and then send one giant tensor. It groups gradients into buckets (PyTorch's default cap is 25 MB) in roughly reverse layer order, and launches an asynchronous all-reduce for each bucket the moment every gradient in it is ready. The last layers' gradients are produced first, so their all-reduce runs while the earlier layers are still computing. With a deep enough network almost all of the communication is hidden; what remains exposed is the final bucket, the one containing the first layers. Larger buckets mean fewer launches (less per-message latency) but a later start; smaller buckets start earlier but pay latency on each. Two further details matter in practice: parameters that receive no gradient in a step (a conditional branch, an unused head) will stall the bucket they belong to unless DDP is told to search for unused parameters, which costs an extra graph traversal every step; and buffers such as BatchNorm running statistics are broadcast from rank 0 at each forward by default.

04 Where the memory goes: sixteen bytes per parameter

Before choosing a strategy, count what has to live on a GPU. For a model trained with Adam in mixed precision the answer is dominated by a number that is easy to remember and routinely underestimated: about 16 bytes for every parameter, before a single activation is stored.

model state, mixed-precision Adam (Ψ parameters)16-bit working weights 2 bytes · Ψ 16-bit gradients 2 bytes · Ψ fp32 master weights 4 bytes · Ψ ┐ fp32 Adam first moment m 4 bytes · Ψ ├ optimiser state K = 12 bytes · Ψ fp32 Adam second moment v 4 bytes · Ψ ┘ ───────────────────────────────────────────── total 16 bytes · Ψ = 2Ψ + 2Ψ + KΨ

The master copy exists because updates of size η·Δ are often below the 16-bit resolution of the weight they are added to, so the running sum must be kept in fp32 (mixed precision explains the rounding). Some stacks keep fp32 parameters and fp32 gradients and cast to 16 bits only for the matmuls; that is 4 + 4 + 8 = 16 bytes as well, split differently. SGD with momentum has K = 8 (master + momentum), and an 8-bit Adam can bring K down to about 6 by quantising the two moments.

So even a 7 B model cannot be trained with plain data parallelism on an 80 GB accelerator: its model state alone is 112 GB, and plain DDP replicates all of it on every rank. Weights you can serve in 14 GB take 8× that to train. The GB here are 10⁹ bytes; an "80 GB" part reports roughly 80 GiB (about 85 × 10⁹ bytes; the exact figure varies by model), of which the framework, CUDA context and allocator fragmentation claim a few.

Activations are the other half

Model state does not depend on the batch; activations do. For a transformer layer the stored activations scale as b·s·h times a constant that depends on what is kept (§12 derives the exact per-layer count). A 7 B-class model (h = 4096, 32 layers) at batch 1 and 4096 tokens stores about 34·b·s·h = 34 × 16.8 M ≈ 570 MB per layer with a fused attention kernel, or roughly 18 GB for 32 layers — before any checkpointing. Activation memory is why sharding the model state is necessary but not sufficient, and why sequence and context parallelism (§12–§14) exist.

05 ZeRO and FSDP: sharding the model state

  • ZeRO / FSDP: shard the optimizer states, gradients, and parameters across data-parallel GPUs instead of replicating them — huge memory savings with data-parallel simplicity.
  • Gradient accumulation: sum gradients over several micro-batches to simulate a large batch on limited memory.
  • Activation checkpointing: drop activations in the forward pass and recompute them in the backward pass — trade compute for memory.

The last two are single-device techniques (their mechanics are in Neural Network Training §28); they are listed here because every sharded run uses them. The rest of this section is about the first bullet.

The three ZeRO stages as formulas

Plain data parallelism keeps N identical copies of all 16Ψ bytes. The observation behind ZeRO ("ZeRO: Memory Optimizations Toward Training Trillion Parameter Models", arXiv 1910.02054) is that each rank only ever updates a slice of the parameters if the optimiser step is partitioned, so it only needs that slice's optimiser state; and it only needs full weights and full gradients for the layer it is currently computing. Partitioning each state in turn gives three stages:

Two things follow. First, ZeRO-1 and ZeRO-2 have a floor: they still replicate the 16-bit weights (and ZeRO-1 the gradients), so no number of GPUs gets a 70 B model under 140 GB per rank with ZeRO-2. Only stage 3 divides everything by N; the paper's headline — a trillion parameters on 1024 GPUs at about 16 GB each — is the last row. Second, stages 1 and 2 are close to free in communication (§07 shows they move the same bytes as DDP), so for a model whose weights fit, ZeRO-2 is the usual default and ZeRO-3 is chosen only when it does not.

How ZeRO-3 / FSDP runs a layer

Each rank permanently owns 1/N of every parameter (a flat slice, or a slice of each tensor). To run a layer it must briefly hold the whole thing:

one sharded unit (usually one transformer block), per stepforward : all-gather the unit's weights → compute → free the gathered copy backward: all-gather weights again → compute grads → reduce-scatter grads (each rank keeps its 1/N) step : each rank updates only its own 1/N slice with its own 1/N of the optimiser state

Peak memory is therefore the permanent shard (16Ψ/N) plus the gathered working copy of the units in flight. That working copy is why the unit size matters: wrapping the whole model as one unit gathers every weight at once and loses the saving entirely, while wrapping each transformer block bounds the transient to one or two blocks. It is also why ZeRO-3 cannot rescue a model whose single largest layer does not fit on a GPU — that layer is gathered whole. Splitting within a layer is tensor parallelism's job (§10).

FSDP1 flat parameters against FSDP2 per-parameter sharding

PyTorch's first FSDP ("PyTorch FSDP: Experiences on Scaling Fully Sharded Data Parallel", arXiv 2304.11277) concatenates all parameters of a wrapped unit into one contiguous FlatParameter and shards that 1-D buffer evenly. One all-gather per unit is efficient, but the flattening leaks everywhere: individual parameters become views into a shared buffer, so freezing some of them, giving them different optimiser settings, or mixing dtypes inside a unit is awkward; and the flat shard does not respect tensor boundaries, so checkpoints need a gather or special resharding logic.

FSDP2 (the fully_shard API) instead shards each parameter on its own dimension 0 and represents it as a DTensor with a Shard(0) placement. Every parameter stays a real tensor with its own dtype and requires_grad; a sharded state dict is just the local shards plus placement metadata; and the same DTensor abstraction composes with tensor-parallel placements, which is what makes 2-D (FSDP × TP) layouts straightforward. The cost is that a unit's all-gather must copy several per-parameter shards into and out of a contiguous communication buffer; in practice this is fused and cheap. FSDP2 also drops the caching-allocator stream tricks FSDP1 used to recycle memory, which makes its peak memory more predictable.

Worked hybrid case: 70 B on 16 nodes × 8 GPUs. Full sharding over 128 ranks gives 1120 / 128 = 8.75 GB of model state per GPU but runs every per-layer all-gather over InfiniBand. Hybrid sharding over the 8 GPUs of each node gives 1120 / 8 = 140 GB — does not fit. Sharding over groups of 16 (two nodes) gives 70 GB, which still leaves no room for activations on 80 GB parts. So for 70 B the hybrid group has to span at least 4 nodes (1120 / 32 = 35 GB), and the choice is between that and adding tensor parallelism inside the node (§19).

06 Offloading to CPU and NVMe: memory you pay for in bandwidth

A server has far more host memory than GPU memory — an 8-GPU training node often has 1–2 TB of DRAM against 640 GB of HBM, and several TB of NVMe. Offloading parks the model states that are touched only once per step in those slower tiers and streams them in and out.

ZeRO-Offload ("ZeRO-Offload: Democratizing Billion-Scale Model Training", arXiv 2101.06840) keeps the 16-bit weights and all forward/backward compute on the GPU and moves the gradients and the whole optimiser (fp32 master, m, v) to the CPU, where a vectorised CPU Adam performs the update. The reasoning is a data-flow argument: the optimiser step is O(Ψ) arithmetic, cheap enough for a CPU, whereas forward and backward are O(Ψ · tokens) and must stay on the accelerator. What crosses PCIe per step is 2Ψ bytes of 16-bit gradients down and 2Ψ bytes of 16-bit updated weights up. The paper reports training 13 B parameters on a single V100 (about 10× what plain PyTorch fits) at 40 TFLOP/s for a 10 B model, and near-linear scaling to 128 GPUs.

ZeRO-Infinity ("ZeRO-Infinity: Breaking the GPU Memory Wall for Extreme Scale Deep Learning", arXiv 2104.07857) extends ZeRO-3 so that the weight shards themselves can live in CPU memory or on NVMe, fetched layer by layer just before use, with partitioned fetches so that every GPU's PCIe link is used in parallel. It reports over 25 PFLOP/s on 512 V100s (about 40% of peak) and model capacities in the tens of trillions of parameters.

Worked: what offload costs a 7 B model on one GPU

7 B, single GPU, optimiser + gradients offloadedGPU keeps 2Ψ = 14 GB of 16-bit weights (+ activations) CPU keeps 2Ψ + 12Ψ = 98 GB (16-bit gradients + fp32 master, m, v) PCIe per step 2Ψ down + 2Ψ up = 28 GB at ~25 GB/s 28 / 25 ≈ 1.1 s of transfer per optimiser step (PCIe 4.0 x16, achievable rate) CPU Adam must read and write ≈ 16 bytes × 7 × 10⁹ ≈ 112 GB of state per step; at ~100 GB/s of DRAM bandwidth that is on the order of 1 s

If one optimiser step's forward and backward take 5–10 s (large batch with accumulation), this is a 10–20% overhead and a good trade. If the step is short, the CPU update and the PCIe transfer dominate and the GPU sits idle. ZeRO-Offload's one-step delayed parameter update overlaps the CPU step of iteration t with the GPU work of t+1, at the price of the gradient being one step stale; the paper enables it only after the early, unstable phase of training. NVMe is another order of magnitude slower (a few GB/s per drive) and only makes sense when the batch per step is very large or the alternative is not training at all.

Tempting: "Offload makes the model fit, so turn it on."
Better: first try more sharding (ZeRO-3 over more GPUs) or tensor parallelism, which cost NVLink/InfiniBand bandwidth measured in hundreds of GB/s; offload costs PCIe and DRAM bandwidth measured in tens. Offload is the tool for a fixed, small number of GPUs.
