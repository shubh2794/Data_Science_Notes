01 What this page is for, and what it deliberately leaves to the theory page

Almost every failed deep-learning project fails in engineering, not in mathematics: a label column shifted by one row, a validation set that shares patients with the training set, a GPU at 30 % utilisation because images are decoded in the main process, a model evaluated in training mode. The frameworks make the right thing easy only if you know what the right thing is. This page is that knowledge, organised in the order a project meets it.

02 Tensors: shape, dtype, device — and broadcasting, where silent bugs live

A tensor is an n-dimensional array with three attributes that matter more than its values. Shape decides which operations are legal. Dtype decides memory, speed and numerical range. Device decides where the arithmetic happens — and an operation between tensors on two devices is an error, not an implicit copy.

shape
Axis conventions are a contract
Images: PyTorch is (N, C, H, W), Keras/TensorFlow default (N, H, W, C). Sequences: (N, T, D) with batch_first=True in PyTorch RNNs, (T, N, D) otherwise. Axis 0 is almost always the batch — which is why one stray reduction over axis 0 averages your examples together.
dtype
float32 by default; ints for labels
Classification targets are int64 class indices for CrossEntropyLoss (or one-hot floats for Keras' categorical_crossentropy, int for sparse_categorical_crossentropy). NumPy defaults to float64; a torch.from_numpy of it gives a double tensor that errors against float32 weights.
device
Move the model once, the batch every step
model.to(device) moves parameters in place; x.to(device) returns a new tensor. Keras places tensors for you. Every .cpu(), .item() or print of a GPU tensor forces a synchronisation — do it every step and you serialize the GPU.
memory of a tensorbytes = numel × bytes-per-element numel = ∏ᵢ shapeᵢ float32 = 4 B · bfloat16/float16 = 2 B · int8/uint8 = 1 B · int64 = 8 B

Worked number. One batch of 256 RGB images at 224×224: numel = 256·3·224·224 = 38 535 168. As uint8 straight from JPEG decode that is 38.5 MB; as float32 after normalisation it is 154.1 MB. This is why pipelines keep images as uint8 until the last moment (ideally until they are already on the GPU) and why the host→device copy of a float32 batch can itself be a bottleneck.

Broadcasting

Element-wise operations between tensors of different shapes follow one rule, identical in NumPy, PyTorch, TensorFlow and JAX:

the broadcasting rule1 Right-align the two shapes; pad the shorter one on the LEFT with 1s. 2 Compare each axis pair (a, b): a = b → keep it a = 1 or b = 1 → the size-1 axis is (virtually) repeated to match otherwise → error 3 Result shape = element-wise max. Nothing is copied in memory.

The rule is convenient and also the source of the most common silent bug in hand-written losses: predictions of shape (N, 1) minus targets of shape (N,) broadcast to an (N, N) matrix — every prediction against every target — and the mean of that is a perfectly finite, perfectly wrong number. The model trains, the loss decreases, and it converges to predicting the mean. Try the presets below.

Broadcasting checker type two shapes (comma-separated) or pick a preset — amber axes are stretched, red ones are incompatible

Habit that bites: reading a shape bug off the error message. Better: the dangerous shape bugs raise no error at all (broadcasting). Assert shapes at every boundary you write yourself — assert pred.shape == y.shape in a custom loss costs nothing.

03 Automatic differentiation: the tape, reverse mode, and switching it off

Neither framework differentiates your code symbolically. As the forward pass runs, every operation on a tensor that requires a gradient is recorded — onto a tape (TensorFlow's GradientTape) or as a graph of backward functions hanging off each result (PyTorch's grad_fn). Calling backward replays that record in reverse, multiplying each local Jacobian-transpose into the upstream gradient. Why reverse mode is the right direction for a scalar loss is derived on the theory page; here is how it behaves in code.

what each recorded op stores and does on the way backforward: y = f(x) — save whatever f's backward will need (x, or y, or a mask) backward: x̄ = (∂y/∂x)ᵀ · ȳ — a vector–Jacobian product; ȳ = ∂L/∂y arrives from above leaves: w.grad ← w.grad + w̄ (ACCUMULATES — it is += , not =)

The last line is the one that matters in practice. PyTorch adds into .grad; nothing clears it but you. Forgetting optimizer.zero_grad() means step t uses the sum of all gradients so far — training still "works" for a few steps, then diverges. The same accumulation is what makes gradient accumulation over micro-batches a two-line change (theory).

Define-by-run: watch the tape being written, then replayed backwards L = (relu(w·x + b) − t)² with x = 2, b = 1, t = 5 — step forward to record, keep stepping to run backward()

PyTorch — autograd

w = torch.tensor(3.0, requires_grad=True)
x, b, t = torch.tensor(2.0), torch.tensor(1.0), 5.0
L = (torch.relu(w * x + b) - t) ** 2
L.grad_fn             # <PowBackward0>: the tape's last entry
L.backward()          # replay in reverse
w.grad                # tensor(8.)   = 2(y-t)·1·x

with torch.no_grad():            # nothing recorded (eval, EMA,
    w -= 0.1 * w.grad            #  manual updates)
w.grad = None                    # what zero_grad() does

feat = encoder(img).detach()     # cut the graph: a constant now
torch.inference_mode()           # stricter, faster no_grad

04 Eager versus graph execution: tf.function, torch.compile, and the static graphs of the past

Eager execution runs each operation the moment Python reaches it: debuggable with print and a debugger, but the framework sees one op at a time and pays Python's overhead on every one. Graph execution first captures the whole computation, then optimises it as a unit — fusing element-wise kernels, removing intermediates, planning memory — and runs it without the interpreter. Modern frameworks are eager by default and let you compile the hot path.

history · TF 1.x
Build a graph, then run a session
You declared placeholders and ops symbolically, then called sess.run(fetches, feed_dict). Fast and deployable, but a Python if could not see a tensor's value, errors surfaced far from their cause, and debugging meant inspecting a graph. Define-by-run frameworks (Chainer, then PyTorch, 2015–17) won on ergonomics; TF 2 (2019) went eager by default.
TensorFlow · tf.function
Trace Python into a graph
The decorated function runs once in tracing mode; ops are recorded into a graph (AutoGraph rewrites Python if/for over tensors into graph control flow). Later calls with the same input signature reuse the graph. Keras' fit() wraps its train step in one for you; jit_compile=True adds XLA fusion.
PyTorch 2 · torch.compile
Capture bytecode, fall back when it cannot
TorchDynamo intercepts Python bytecode and extracts FX graphs; TorchInductor generates fused kernels (Triton on GPU). Code it cannot capture — data-dependent Python, prints, unsupported libraries — causes a graph break: that piece runs eagerly and compilation resumes after it. Correctness is kept; speed is lost at each break.

PyTorch

model = MyNet().to(device)
cmodel = torch.compile(model)      # lazy: compiles on first call
# mode="reduce-overhead" (CUDA graphs, small batches)
# mode="max-autotune"   (longer compile, faster kernels)
out = cmodel(x)                    # first call: slow (compiling)

# see why it is not faster:
#   TORCH_LOGS="graph_breaks" python train.py

TensorFlow backend

@tf.function(jit_compile=True)     # trace once, XLA-fuse
def train_step(x, y): ...

# Keras: fit() already runs a compiled step
model.compile(optimizer="adam", loss=..., jit_compile="auto")
model.compile(..., run_eagerly=True)   # for debugging only

05 Declaring a model: Sequential, Functional, subclassing, and nn.Module

A model is a container of parameters plus a forward function. Keras offers three levels of flexibility; PyTorch offers one mechanism — subclass nn.Module — with nn.Sequential as a shortcut. The trade is the usual one: the more declarative the definition, the more the framework can check, plot and serialise for you; the more imperative, the more arbitrary the forward logic can be.

Keras · Sequential — a plain stack

model = keras.Sequential([
    keras.Input(shape=(28, 28, 1)),
    keras.layers.Conv2D(32, 3, activation="relu"),
    keras.layers.MaxPooling2D(),
    keras.layers.Flatten(),
    keras.layers.Dropout(0.3),
    keras.layers.Dense(10),            # logits
])
model.summary()

Keras · Functional — a DAG of layers

img  = keras.Input(shape=(64, 64, 3), name="img")
meta = keras.Input(shape=(8,), name="meta")
h = keras.layers.Conv2D(32, 3, activation="relu")(img)
h = keras.layers.GlobalAveragePooling2D()(h)
h = keras.layers.Concatenate()([h, meta])     # two inputs
price = keras.layers.Dense(1, name="price")(h)    # two
kind  = keras.layers.Dense(5, name="kind")(h)     # outputs
model = keras.Model([img, meta], [price, kind])

Keras · subclassing — imperative call()

class Net(keras.Model):
    def __init__(self, **kw):
        super().__init__(**kw)
        self.body = keras.layers.Dense(64, activation="relu")
        self.drop = keras.layers.Dropout(0.3)
        self.head = keras.layers.Dense(10)
    def call(self, x, training=False):
        return self.head(self.drop(self.body(x), training=training))

PyTorch · nn.Module

class Net(nn.Module):
    def __init__(self):
        super().__init__()
        self.body = nn.Linear(784, 64)   # in_features required
        self.drop = nn.Dropout(0.3)
        self.head = nn.Linear(64, 10)
    def forward(self, x):                # mode via model.train()/.eval()
        return self.head(self.drop(F.relu(self.body(x))))

Dropout and BatchNorm behave differently

logits vs probabilities
Put the softmax in the loss, not the model
nn.CrossEntropyLoss expects raw logits and applies log-softmax internally. In Keras use SparseCategoricalCrossentropy(from_logits=True) with a linear last layer. A softmax in both places trains slowly and saturates; the fused form is also the numerically stable one (why).
registration
Only attributes are parameters
Layers kept in a plain Python list are invisible to model.parameters() and to .to(device). Use nn.ModuleList/nn.ModuleDict (Keras tracks lists of layers automatically).

06 Input pipelines: shuffling, batching, on-the-fly augmentation, and the input-bound GPU

The GPU can only be as busy as the pipeline that feeds it. Reading files, decoding JPEGs, tokenising and random augmentation all run on the CPU; if one batch takes longer to prepare than to train on, the GPU sits idle for the difference, however fast it is. The cure is overlap: prepare batch k+1 (and k+2…) on other cores while the GPU trains on batch k.

steady-state throughputsynchronous (load, then train): time per batch = t_load + t_gpu overlapped with W workers + prefetch: time per batch = max( t_load / W , t_gpu ) GPU utilisation = t_gpu / time per batch workers needed ≈ ⌈ t_load / t_gpu ⌉

Worked number. Decode + augment takes t_load = 30 ms per batch, the training step t_gpu = 12 ms. Synchronously: 42 ms per batch, 23.8 batches/s, GPU busy 12/42 = 29 %. With prefetch and W = 1 worker: max(30, 12) = 30 ms, 40 %. With W = 3: max(10, 12) = 12 ms, 83 batches/s, 100 % — the GPU is now the bottleneck, which is what you want. Adding a fourth worker buys nothing.

Pipeline timeline: CPU workers preparing batches, GPU consuming them red gaps on the GPU lane are idle time; switch to prefetch, then add workers until they close

07 The canonical training loop, written out — and what fit() does for you

The mathematics of one step is on the theory page. Here are the lines of code, with the parts people forget. Write this loop by hand at least once; then you know exactly what the high-level fit() is doing and where to hook in when it is not enough.

model = Net().to(device)
opt   = torch.optim.AdamW(model.parameters(), lr=3e-4, weight_decay=0.01)
sched = torch.optim.lr_scheduler.OneCycleLR(opt, max_lr=3e-3,
            total_steps=EPOCHS * len(train_dl))
loss_fn = nn.CrossEntropyLoss()

for epoch in range(EPOCHS):
    model.train()                               # 1 dropout on, BN uses batch stats
    for x, y in train_dl:
        x, y = x.to(device, non_blocking=True), y.to(device, non_blocking=True)
        opt.zero_grad(set_to_none=True)         # 2 clear the ACCUMULATED grads
        with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
            loss = loss_fn(model(x), y)         # 3 forward (mixed precision)
        loss.backward()                         # 4 backward
        torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)  # 5 optional
        opt.step()                              # 6 update
        sched.step()                            # 7 per-STEP schedule
    model.eval()                                # 8 dropout off, BN running stats
    with torch.no_grad():                       # 9 no tape, less memory
        val = sum(loss_fn(model(x.to(device)), y.to(device)).item() * len(y)
                  for x, y in val_dl) / len(val_dl.dataset)   # 10 weight by size
    log(epoch, val); maybe_checkpoint(model, opt, sched, epoch, val)

The Keras equivalent is three calls — and a customised step, when you need one (GAN losses, gradient penalties, multiple optimisers), overrides only train_step and keeps everything else fit() provides:

Keras 3 · custom train_step (TF backend)

class Custom(keras.Model):
    def train_step(self, data):
        x, y = data
        with tf.GradientTape() as tape:
            y_pred = self(x, training=True)
            loss = self.compute_loss(y=y, y_pred=y_pred)
        grads = tape.gradient(loss, self.trainable_variables)
        self.optimizer.apply(grads, self.trainable_variables)
        for m in self.metrics:
            if m.name == "loss": m.update_state(loss)
            else: m.update_state(y, y_pred)
        return {m.name: m.result() for m in self.metrics}

08 Callbacks: checkpointing, early stopping, schedules, and logging

A callback is code that runs at a named point of the loop — start/end of a batch, an epoch, training — with access to the model and the latest metrics. Four of them belong in nearly every run.

callbacks = [
    keras.callbacks.ModelCheckpoint("best.keras", monitor="val_loss",
                                    save_best_only=True),
    keras.callbacks.EarlyStopping(monitor="val_loss", patience=8,
                                  restore_best_weights=True),
    keras.callbacks.ReduceLROnPlateau(monitor="val_loss", factor=0.5, patience=3),
    keras.callbacks.TensorBoard(log_dir="runs/exp1"),   # or CSVLogger("log.csv")
]
model.fit(train_ds, validation_data=val_ds, epochs=100, callbacks=callbacks)
checkpoint
Save the best, and enough to resume
"Best by validation metric" is the model you ship. A resumable checkpoint also needs optimizer state (Adam's moments), scheduler step, epoch, grad-scaler and RNG states — weights alone restart the optimiser cold. Keep the last one too, for pre-empted jobs.
early stopping
Patience, and restore the best
Stop after patience epochs without improvement — and restore the best weights, not the last (which are by construction worse). Why this is a regulariser: theory. With one-cycle or cosine schedules, early stopping cuts the schedule short; prefer fixing the epoch count from a previous run.
LR schedule
Step-level vs epoch-level
ReduceLROnPlateau reacts to validation (epoch-level). One-cycle and warmup+cosine are step-level and are usually passed to the optimiser as a LearningRateSchedule (Keras) or stepped per batch (PyTorch).
logging
Log more than the loss
Training and validation loss and metric, learning rate, gradient norm, throughput (samples/s), and a few prediction examples. TensorBoard, CSV, or an experiment tracker; the aim is that any run can be compared with any other a month later.

In a hand-written PyTorch loop the same four are a dozen lines:

best, bad = float("inf"), 0
for epoch in range(EPOCHS):
    train_one_epoch(...); val = evaluate(...)
    writer.add_scalar("val/loss", val, epoch)           # torch.utils.tensorboard
    writer.add_scalar("lr", opt.param_groups[0]["lr"], epoch)
    if val < best - 1e-4:
        best, bad = val, 0
        torch.save({"model": model.state_dict(), "opt": opt.state_dict(),
                    "sched": sched.state_dict(), "epoch": epoch}, "best.pt")
    else:
        bad += 1
        if bad >= PATIENCE: break
model.load_state_dict(torch.load("best.pt", weights_only=True)["model"])

09 The universal workflow: task and metric, baseline, overfit, regularise, tune

The order matters more than any individual step. Each stage answers one question, and skipping ahead means you cannot tell which question an experiment is answering. The strategic side — how to split data, which error to attack next — is on ML Strategy; this is the hands-on sequence.

StageDoDone when
1 · Define the taskInput, target, task type (binary, multi-class, multi-label, regression, ranking, segmentation). Choose the success metric the stakeholder actually cares about — accuracy on balanced classes, PR-AUC / F1 on rare positives, MAE for forecasting. Look at the data by eye.You can state what a wrong prediction costs.
2 · Evaluation protocolHold-out, K-fold for small data, or a time-based split for anything temporal. Split by entity (patient, user, document) when examples are correlated. Freeze the test set. See Model Evaluation.No example, entity or future time step is on both sides.
3 · BaselineThe common-sense score: majority class; "tomorrow = today" for time series; a linear model or gradient-boosted trees on hand features. Your network must beat it.You have a number to beat.
4 · OverfitA model with enough capacity to drive training loss near zero. First on one batch (§15), then on the full training set until validation gets worse — that is where the regime boundary is.Train loss ≪ validation loss; the model can express the task.
5 · RegulariseMore data / augmentation first, then weight decay, dropout, a smaller model, early stopping (the map).Validation stops improving with each change.
6 · TuneLR first (§10), then batch size, weight decay, architecture width/depth. Random or Bayesian search over the validation set (Hyperparameter Tuning). Then retrain on train+val and touch the test set once.Budget spent; one final test number.
sanity numbers to know before the first runcross-entropy of a uniform guess over C classes = ln C (C = 10 → 2.303, C = 2 → 0.693) cross-entropy of predicting the class prior p = −∑ₖ pₖ ln pₖ accuracy of the majority-class baseline = max_k pₖ (95 % on a 95/5 split — and useless)

The first logged loss should be close to ln C. Much higher means the output layer's initial logits are large (over-confident at random) — shrink the final layer's init or set its bias to the log prior. A model whose training loss stays at ln C is predicting nothing; one that plateaus at the prior entropy has learnt only the class frequencies.

10 The learning-rate finder in practice

One short mock training run — a few hundred mini-batches with the learning rate growing exponentially from ~10⁻⁷ to ~10 — tells you the useful range in a minute (Smith 2015). Why the curve has a cliff, and a ground-truth comparison, are on the theory page. Here: how to run it and how to read the suggestion it prints.

the sweeplrₖ = lr_start · (lr_end / lr_start)^(k/(N−1)), k = 0 … N−1 (a straight line on a log axis) smoothed loss: sₖ = β·sₖ₋₁ + (1−β)·Lₖ, reported sₖ / (1 − βᵏ⁺¹) (bias-corrected EWMA) stop when sₖ > 4 · min_{j≤k} sⱼ (it has diverged)
LR finder on a simulated run, with the usual suggestions marked change the model state and the smoothing; re-run for a fresh noise draw — see which suggestion is stable

PyTorch (hand-rolled, 15 lines)

def lr_find(model, dl, opt, loss_fn, lo=1e-7, hi=10, n=100, beta=0.98):
    state = copy.deepcopy(model.state_dict())     # restore afterwards
    mult, avg, best, out = (hi / lo) ** (1 / (n - 1)), 0.0, float("inf"), []
    for k, (x, y) in zip(range(n), itertools.cycle(dl)):
        lr = lo * mult ** k
        for g in opt.param_groups: g["lr"] = lr
        opt.zero_grad(); loss = loss_fn(model(x), y); loss.backward(); opt.step()
        avg = beta * avg + (1 - beta) * loss.item()
        s = avg / (1 - beta ** (k + 1)); out.append((lr, s))
        if s > 4 * best: break
        best = min(best, s)
    model.load_state_dict(state)
    return out

11 The one-cycle policy: learning rate up, then far down — momentum the other way

One-cycle (Smith 2018) is the default schedule of the fast-training recipe: warm the learning rate up from max_lr/div to max_lr over the first ~25–30 % of steps, then anneal it down to a tiny value. Momentum moves inversely — high while the LR is low, low while the LR is high — because a large step and high momentum together overshoot. The high-LR middle acts as a regulariser and explores; the long low tail settles into a minimum. The general theory of schedules and warmup is here.

PyTorch OneCycleLR (two-phase, default)lr_init = max_lr / div_factor lr_min = lr_init / final_div_factor phase 1 (t ≤ s₁ = pct_start·T): lr: lr_init → max_lr momentum: m_max → m_base phase 2 (t > s₁): lr: max_lr → lr_min momentum: m_base → m_max cosine anneal from a to b over progress p ∈ [0, 1]: b + (a − b)·(1 + cos πp)/2 defaults — PyTorch: div 25, final_div 1e4, pct_start 0.3, momentum 0.85–0.95 fastai fit_one_cycle: div 25, div_final 1e5, pct_start 0.25, moms (0.95, 0.85, 0.95)

Worked number. max_lr = 10⁻², T = 1 000 steps, defaults: the run starts at 4×10⁻⁴, peaks at 10⁻² at step 300, and ends at 4×10⁻⁸ — five and a half orders of magnitude below the peak. With Adam-family optimisers the "momentum" being cycled is β₁.

One-cycle schedule: learning rate (top) and momentum (bottom) over a run drag the sliders — the dashed line marks the end of the warm-up phase

12 Fine-tuning a pretrained model: freeze, discriminative learning rates, progressive unfreezing

Starting from pretrained weights is the single largest practical gain on small and medium datasets. The mechanics are in Fine-Tuning & Transfer Learning; the recipe is: protect the pretrained body while the freshly initialised head is still random, then let every layer adapt — but the early, general layers more gently than the late, task-specific ones.

discriminative learning rates over G layer groupslr_g = lr_low · (lr_high / lr_low)^(g/(G−1)), g = 0 (input side) … G−1 (head) example: slice(1e-6, 1e-4) over 3 groups → 1e-6, 1e-5, 1e-4 (geometric spacing) ULMFiT's variant (Howard & Ruder 2018): each group ÷ 2.6 relative to the one above
  1. Freeze the body; train only the new head for 1–3 epochs at the finder's LR. A random head sends large, random gradients into the body otherwise and wrecks the features you paid for.
  2. Unfreeze (all at once, or progressively: last group first, one more group each epoch — ULMFiT's gradual unfreezing, most useful for text and for very small datasets).
  3. Re-run the LR finder — the curve now looks like the "pretrained" option in §10 — and train with discriminative LRs, one-cycle, fewer epochs.
  4. Keep BatchNorm layers in the frozen body in eval mode (their running statistics are part of what was pretrained), or at least keep their affine parameters trainable; Keras freezes BN statistics automatically when trainable=False.

13 The rest of the fast-training recipe: mixed precision, progressive resizing, test-time augmentation

Three cheap wins that are one line each in a good library. None changes the model; each changes how efficiently it is trained or how its predictions are formed.

mixed precision
≈2× throughput, ≈½ activation memory
Matmuls and convolutions in bf16/fp16 on tensor cores, a float32 master copy of the weights, reductions and softmax kept in float32. On hardware with bfloat16 (A100, H100, recent TPUs) prefer it — same exponent range as float32, so no loss scaling. With float16, a dynamic loss scaler is required. Numerics: theory.
progressive resizing
Small images first, then large
Train most epochs at, say, 128 px, then a few at 224 px. Early epochs are ~3× cheaper, and the size change acts as augmentation. The convolutional body is resolution-agnostic; only the pooling before the head must be global. Re-run the LR finder after the switch.
test-time augmentation
Average over augmented copies
At inference, predict on K augmented versions (flips, crops) and average the probabilities: p̂(x) = (1/K) ∑ₖ p(tₖ(x)). Typically a small but free-at-training-time accuracy gain for K× inference cost. Use only label-preserving transforms (no horizontal flip for text-in-images or left/right-sensitive tasks).

PyTorch

# bfloat16: autocast only

16 Reproducibility: seeds, determinism, and what bit-exact costs

Randomness enters at weight initialisation, data shuffling, augmentation, dropout — and, less obviously, in GPU kernels whose floating-point reductions run in a nondeterministic order (atomic adds), so two runs with identical seeds can differ in the last bits and then diverge. There are two levels to aim for: seeded (runs are statistically comparable) and deterministic (bit-identical on the same hardware and library versions).

PyTorch

import os, random, numpy as np, torch
os.environ["CUBLAS_WORKSPACE_CONFIG"] = ":4096:8"   # before CUDA init
def seed_all(s):
    random.seed(s); np.random.seed(s); torch.manual_seed(s)  # + all GPUs
seed_all(42)
torch.use_deterministic_algorithms(True)   # error on nondeterministic ops
torch.backends.cudnn.benchmark = False     # no per-shape algorithm search

g = torch.Generator().manual_seed(42)
def worker_init(i):                        # numpy/random are not reseeded
    s = torch.initial_seed() % 2**32       #   per worker by default
    np.random.seed(s); random.seed(s)
dl = DataLoader(ds, shuffle=True, num_workers=4,
                generator=g, worker_init_fn=worker_init)

the price
Determinism is slower
Deterministic kernels can be markedly slower, and cudnn.benchmark = False gives up per-shape autotuning. Use it for debugging and regression tests; for research claims, prefer several seeds and report mean ± spread.
seed variance is real
One run is an anecdote
Seed-to-seed spread of a fine-tuned model's validation score can be as large as the "improvement" being claimed. Compare configurations over 3–5 seeds before believing a difference.
record everything else
Code, data, environment
Commit hash, dataset version / hash, the exact config, library versions, GPU type. A seed without these reproduces nothing.

19 What to remember

  • Print shape, dtype and device of every new tensor you create; assert shapes in custom losses. Broadcasting turns shape bugs into silent wrong answers (§02).
  • Gradients accumulate. zero_grad every step; .item() when logging; no_grad/inference_mode for evaluation (§03).
  • Eager to develop, compile to run. Watch for retracing and graph breaks; time after warm-up (§04).
  • Functional API for any DAG in Keras; nn.Module in PyTorch. Logits out of the model, softmax inside the loss; model.eval() for validation (§05).
  • Measure the loader alone. Parallel decoding + prefetch + pinned memory; augment after cache (§06).
  • Follow the workflow: metric and split → baseline → overfit one batch → overfit the set → regularise → tune → test once (§09, §15).
  • LR finder → one-cycle; for pretrained models freeze, then discriminative LRs; mixed precision always on modern GPUs (§10–§13).
  • Look at your data — the final batch, the highest-loss examples — before touching the model (§15).
  • Seed everything, record everything; deterministic mode for debugging, multiple seeds for claims (§16).
  • Checkpoints resume; exports serve. state_dict/.keras for the first; torch.export/ONNX/SavedModel, with preprocessing, for the second (§17).
