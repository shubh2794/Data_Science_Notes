GPU Programming & Kernel Optimization

The hardware/kernel layer of deep learning: how GPUs execute model operations, how kernels are written and fused, how FlashAttention tiles attention into SRAM, and how mixed precision trades mantissa bits for throughput. Every framework call eventually becomes a kernel launch — understanding that layer is how you go from "it runs" to "it runs fast."

Deep Learning Systems CUDA Performance GPU

01 GPU architecture primer

  • A GPU is an array of Streaming Multiprocessors (SMs), each containing many cores. An H100 has 132 SMs with 128 CUDA cores each — 16,896 cores total. The cores are simple: no branch prediction, no out-of-order execution, no deep cache hierarchy per core. Throughput comes from running thousands of threads, not from making one thread fast.
  • Throughput-oriented vs latency-oriented. A CPU optimises for one thread's time-to-completion — deep caches, branch prediction, speculative execution. A GPU optimises for total work per second — when one group of threads stalls on a memory access, the hardware instantly switches to another group that is ready. The individual thread is slow; the aggregate is fast.
  • Memory hierarchy is the key to performance. Data lives at multiple levels, each trading size for speed:
levelscopetypical size (H100)bandwidthlatency
Registersper thread~256 KB / SMhighest~1 cycle
Shared memory / L1per SM (block)228 KB / SM~19 TB/s aggregate~20-30 cycles
L2 cacheall SMs50 MB~12 TB/s~200 cycles
HBM (global memory)entire GPU80 GB3.35 TB/s~400-600 cycles
  • The goal of kernel optimization is to keep data in the faster levels as long as possible. A naive kernel that reads from and writes to HBM for every operation wastes most of its time waiting for memory. A well-written kernel loads data into shared memory or registers, does all its work there, and writes back once.
  • HBM bandwidth (3.35 TB/s on H100) sounds enormous, but tensor core peak throughput (990 TFLOPS for FP16) can consume data far faster — the arithmetic intensity (FLOPs per byte loaded) must be high enough to keep the cores fed.

One sentence: a GPU trades single-thread speed for massive parallelism, and performance depends on how well you manage the memory hierarchy — registers are free, HBM is expensive.

02 Threads, warps & blocks

  • Thread: the smallest unit of execution. Each thread has its own registers and program counter, but executes the same instruction as the other threads in its warp.
  • Warp: 32 threads executed in lockstep (SIMT — Single Instruction, Multiple Threads). All 32 threads in a warp execute the same instruction at the same time. This is the actual unit of scheduling on the hardware.
  • Block (thread block): a group of warps (typically 128-1024 threads). Threads within a block can synchronise via barriers and share data through shared memory. A block is assigned to exactly one SM and cannot migrate.
  • Grid: a grid of blocks, launched by a single kernel call. Blocks within a grid are independent — they cannot synchronise with each other (except at kernel boundaries). This is what makes GPUs scalable: more SMs means more blocks can run simultaneously.

Thread divergence

  • When threads in a warp take different branches of an if/else, the warp must execute both paths — threads not on the active path are masked off. This is warp divergence, and it serialises what should be parallel. The penalty is proportional to how many paths the warp takes.
  • Rule: structure data so that neighbouring threads (same warp) take the same branch. If thread 0-15 go left and 16-31 go right, that is two paths in one warp. If threads 0-31 all go left and threads 32-63 all go right, each warp is non-divergent.

Occupancy

  • Occupancy = active warps / maximum warps per SM. Each SM can hold a fixed number of warps (e.g. 64 on H100). Occupancy is limited by whichever resource the kernel uses most: registers per thread, shared memory per block, or threads per block.
  • Higher occupancy gives the scheduler more warps to switch between, hiding memory latency. But occupancy is not everything — a kernel at 50% occupancy with good memory access patterns can outperform one at 100% occupancy with poor patterns.
occupancy O = active warps per SM / max warps per SM threads → warps warps per block = ⌈threads per block / 32⌉
Takeaway: the warp is the real unit of execution. Keep threads in a warp doing the same thing (no divergence) and accessing consecutive memory (coalesced). Occupancy hides latency but is not the only thing that matters.

03 Writing kernels

A spectrum of abstraction levels, from "just call PyTorch" to "manage every warp by hand." The right level depends on how much performance you need and how much time you can afford.

leveltooleffortspeedcontrol
1PyTorch eagerlowest — Python APIslowest — one kernel per op, Python overheadnone — whatever CUDA ops PyTorch ships
2torch.compileone line — model = torch.compile(model)fast — auto-generates fused Triton kernelslimited — can inspect/override generated code
3Tritonmedium — Python-like, block-level programmingfaster — explicit tiling, auto-tuning of block sizesblock-level: you pick tile shapes, the compiler handles warps
4CUDA C/C++highest — manage threads, warps, shared memoryfastest (ceiling) — full hardware controltotal — register allocation, warp shuffles, async copies

The practical workflow

  • Start with torch.compile. It is free performance: fuses elementwise ops, eliminates Python overhead, and often matches hand-tuned Triton for standard models. Inspect what it generates with TORCH_LOGS="output_code".
  • Move to Triton when you need a specific fusion pattern torch.compile does not find, or when you need a custom operation (e.g. a novel attention variant). Triton operates on blocks of data: you write "load a 128-element tile, compute, store" and the compiler maps tiles to warps.
  • Move to CUDA only for the innermost, highest-impact kernels — things like FlashAttention, custom GEMM tiles, or hardware-specific tricks (warp shuffles, tensor core MMA intrinsics, async memory copies). The development cost is 10-100x higher than Triton.

Triton example sketch

# Triton: fused add + ReLU on a 1-D tensor
@triton.jit
def add_relu_kernel(x_ptr, y_ptr, out_ptr, N, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < N
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    out = tl.maximum(x + y, 0.0)       # fused: add + relu, no HBM round-trip
    tl.store(out_ptr + offs, out, mask=mask)
# launch with auto-tuned BLOCK sizes: 256, 512, 1024, …
Takeaway: torch.compile is the default. Triton when you need custom fusions. CUDA when you need every last FLOP. Most practitioners never need to leave level 2.

04 Memory coalescing

  • HBM is accessed in 128-byte transactions (a cache line). When all 32 threads in a warp access consecutive 4-byte addresses, one transaction serves the entire warp — this is coalesced access.
  • If threads access addresses that are strided or scattered, the hardware must issue multiple transactions for the same warp — each fetching 128 bytes but using only a few of them. The ratio of useful bytes to total bytes fetched is the memory efficiency.
  • Impact: coalesced access can be 10-100x faster than fully random access. It is the single most important memory-level optimization.

Row-major vs column-major

  • A matrix stored row-major has consecutive elements along each row. If threads in a warp each process one row (reading across columns), access is coalesced. If they each process one column (reading down rows), access is strided by the row width — catastrophically uncoalesced.
  • Transposing a matrix or swapping loop orders often converts uncoalesced access to coalesced. The same kernel, same math, but 10x faster because of memory layout.

Shared memory bank conflicts

  • Shared memory is divided into 32 banks. If multiple threads in a warp access different addresses that map to the same bank, the accesses serialise — a bank conflict. Solution: pad the shared memory array by one element per row, changing the stride so threads hit different banks.
coalesced (ideal) thread i reads address base + i × sizeof(element) → 1 transaction for 32 threads strided (bad) thread i reads address base + i × stride, stride ≫ element size → up to 32 transactions bank index bank(addr) = (addr / 4) mod 32 conflict when two threads hit the same bank
Takeaway: make neighbouring threads access neighbouring memory. When they do not, change the data layout until they do — or tile through shared memory where you control the access pattern.

05 Kernel fusion

Every separate kernel reads its input from HBM and writes its output back to HBM. For elementwise chains — add, ReLU, LayerNorm, dropout — the actual compute is trivial; the cost is the memory round-trips. Fusion eliminates them.

  • Unfused: LayerNorm(x) → write to HBM → Dropout(x) → write to HBM → x + residual → write to HBM. Three kernel launches, three round-trips through the memory hierarchy. Each round-trip costs ~240 ns of latency plus bandwidth.
  • Fused: one kernel does LayerNorm + Dropout + residual add. Input loaded once from HBM into registers/shared memory, all three operations applied, result written back once. Saves 2 HBM round-trips — often 2-3x faster for elementwise-dominated regions.
  • torch.compile does this automatically for pointwise and reduction patterns. It traces the computation graph, identifies fusible subgraphs, and generates Triton kernels. This is the main source of its speedup.
  • When to fuse manually: when the fusion pattern involves custom logic torch.compile cannot trace (dynamic shapes, non-standard control flow), or when you want a specific tiling strategy the auto-fuser does not discover.
  • Trade-off: fused kernels are less reusable and harder to debug. A fused LayerNorm+Dropout+Add kernel cannot be reused where only LayerNorm is needed. Fusion also increases register pressure, which can lower occupancy.
unfused cost K ops → K kernel launches, each reads + writes N elements from HBM total HBM traffic ≈ 2 × K × N × bytes per element fused cost 1 kernel launch, reads N elements once, writes N elements once total HBM traffic ≈ 2 × N × bytes per element (K× reduction)
Takeaway: fusion is not about saving FLOPs — it is about saving memory bandwidth. The compute is cheap; the data movement is expensive. torch.compile handles the common cases; write custom fusions only when profiling shows the bottleneck.

06 FlashAttention

Standard attention materialises the N×N score matrix in HBM. FlashAttention tiles the computation so the full matrix never exists — just small blocks in SRAM. See also Sparse, Linear & Flash Attention for the broader attention efficiency landscape.

The problem

  • Standard attention: S = Q KT (N×N), then P = softmax(S), then O = P V. The N×N matrix S must be materialised in HBM: for N=8192 in FP16, that is 128 MB per head per layer. At 32 heads and 80 layers, the attention matrices alone dwarf the model weights.
  • Worse, the softmax over each row of S requires reading the entire row to compute the max and sum — a reduction that standard implementations perform by writing S to HBM, reading it back for the softmax, then writing P to HBM, and reading it back for the P×V multiply. Four HBM passes over the N×N matrix.

The solution: tiling + online softmax

  • FlashAttention never materialises S or P. Instead, it processes tiles of Q (Br rows) against tiles of K,V (Bc columns) entirely in SRAM (shared memory).
  • Online softmax: the key insight. Normal softmax needs the global max across the row. Online softmax maintains a running max and running sum as each K-tile is processed. When a new tile has a larger max, the previous partial results are rescaled. At the end of all tiles, the softmax is exact — no approximation.
  • IO complexity: standard attention performs O(N2 d) HBM accesses (read/write the N×N matrix, each element d-related). FlashAttention performs O(N2 d2 / M) HBM accesses, where M is the SRAM size. Since M is typically much larger than d2 (SRAM ~200KB, d2 for d=128 is 16K elements = 32KB in FP16), this is a significant reduction.
  • Result: 2-4x wall-clock speedup on training, with exact results (not an approximation). Memory usage drops from O(N2) to O(N) — enabling much longer sequences without running out of memory.
standard IO HBM accesses = O( N² · d ) (materialise N×N matrix) flash IO HBM accesses = O( N² · d² / M ) M = SRAM size per SM online softmax mnew = max(mold, max(Stile)) ℓnew = e(m_old − m_new) · ℓold + ∑ e(S_tile − m_new) Onew = (ℓold / ℓnew) · e(m_old − m_new) · Oold + (1 / ℓnew) · e(S_tile − m_new) · Vtile

FlashAttention-2 and FlashAttention-3

  • FlashAttention-2: parallelises across the sequence length dimension (outer loop over Q tiles, inner loop over K/V tiles — the reverse of FA1). Reduces non-matmul FLOPs by keeping rescaling in registers. Result: ~2x faster than FA1, reaching 50-73% of theoretical FLOP utilization.
  • FlashAttention-3: targets H100 and later GPUs. Exploits FP8 tensor cores (E4M3 for Q/K/V, accumulate in FP32), asynchronous warp-specialised pipelining (one warp group issues loads while another computes), and block quantisation for FP8 to maintain accuracy. Result: further 1.5-2x speedup on Hopper GPUs.
Takeaway: FlashAttention is not an approximation — it computes exact attention while being faster and using less memory. The trick is tiling + online softmax, which turns an HBM-bound operation into a compute-bound one. It is now the default attention implementation in all major frameworks.

07 Mixed precision training

Every number in a neural network is a floating-point bit pattern. Fewer bits = less memory, faster computation — but the numbers must still be large enough to represent the values that matter. See also Training: Precision & Memory.

The formats

formatbitsexponentmantissarangeprecisionuse
FP3232823±3.4 × 1038~7 decimal digitsmaster weights, accumulation
FP1616510±65,504~3.3 digitsforward/backward (needs loss scaling)
BF161687±3.4 × 1038~2.4 digitsforward/backward (no loss scaling needed)
FP8 E4M3843±448~1.3 digitsforward pass on H100+
FP8 E5M2852±57,344~0.9 digitsbackward pass (wider range for gradients)

Why BF16 is preferred over FP16

  • FP16 has only 5 exponent bits — its max representable value is 65,504. Gradients or activations that exceed this overflow to infinity. Loss scaling is mandatory: multiply the loss by a large factor (e.g. 1024) before the backward pass to keep small gradients representable, then divide the gradients after. If the scale is too large, gradients overflow; too small, they underflow.
  • BF16 has the same 8-bit exponent as FP32 — same range, just less mantissa precision (7 bits vs 23). No loss scaling needed. The reduced precision rarely matters for training because gradient noise already dwarfs mantissa error. BF16 is the standard on all modern GPUs (A100+).

Loss scaling (for FP16)

  • Forward pass in FP16. Loss is computed. Loss is multiplied by a scale factor S (initially large, e.g. 216). Backward pass runs in FP16 with the scaled loss. After backward, gradients are divided by S in FP32, then the optimizer step is in FP32.
  • Dynamic loss scaling: start with a large S. If any gradient is inf/nan, skip the step and halve S. If N consecutive steps have no overflow, double S. This finds the highest scale that does not overflow — maximising the dynamic range used.

The mixed-precision recipe

  • Master weights in FP32 (the optimizer updates these).
  • Forward and backward in BF16 (or FP16 with loss scaling). Saves memory and doubles throughput on tensor cores.
  • Gradient accumulation and optimizer step in FP32 (to avoid rounding errors accumulating over many steps).
  • AMP (Automatic Mixed Precision): the framework decides which ops run in which precision. Matmuls and convolutions → BF16/FP16. Reductions (softmax, LayerNorm, loss) → FP32. This is what torch.amp.autocast does.
FP16 loss scaling L̃ = S · L → backward yields S · ∂L/∂θ in FP16 ∂L/∂θ = (S · ∂L/∂θ) / S (divide in FP32 before optimizer step) tensor core throughput H100: FP32 = 67 TFLOPS, FP16/BF16 = 990 TFLOPS, FP8 = 1,979 TFLOPS
Takeaway: use BF16 by default — same range as FP32, no loss scaling needed, 2x throughput. Keep master weights and reductions in FP32. FP8 on H100+ for another 2x, but requires per-tensor or per-block scaling.

08 Tensor cores & matrix ops

  • Tensor cores are specialised matrix-multiply-accumulate (MMA) units. One instruction computes a small tile — e.g. a 16×16×16 FP16 multiply-add with FP32 accumulation. This is the entire reason low-precision training is fast: tensor cores, not CUDA cores.
  • Throughput difference: H100 FP16 tensor cores deliver 990 TFLOPS. FP32 CUDA cores deliver 67 TFLOPS. That is ~15x more throughput for operations that fit the tensor core format — which is any matrix multiplication.
  • Dimension alignment: to use tensor cores, matrix dimensions must be multiples of 8 (for FP16) or 16 (for FP8). If your hidden dim is 768 (divisible by 8) — tensor cores engage. If it is 769, the runtime pads or falls back to CUDA cores. All standard Transformer dimensions (512, 768, 1024, 2048, 4096, …) are designed for this.

cuBLAS and GEMM

  • cuBLAS is NVIDIA's optimized BLAS library. It automatically uses tensor cores for GEMMs when dimensions and dtypes qualify. When you call torch.matmul, it ultimately dispatches to cuBLAS.
  • A GEMM (General Matrix Multiply) C = α·A·B + β·C is tiled: the output matrix is partitioned into tiles, each computed by a thread block. Within each block, tiles of A and B are loaded into shared memory and multiplied using tensor core MMA instructions. The key tuning parameters are tile sizes (M_tile × N_tile × K_tile), pipeline depth, and swizzle patterns for shared memory.
  • WMMA (Warp Matrix Multiply-Accumulate): a warp-level API for tensor cores. Each warp declares fragment types, loads tiles, calls mma_sync, and stores the result. Lower-level than cuBLAS but useful for custom kernels that need matrix multiply as a building block (like FlashAttention).
tensor core op Dm×n = Am×k · Bk×n + Cm×n A, B in FP16/BF16/FP8; C, D in FP32 accumulate alignment rule M, N, K must be multiples of 8 (FP16) or 16 (FP8) arithmetic intensity I = 2MNK / (2(MK + KN) × bytes) ≈ N/2 (for square N×N × N×N)
Takeaway: tensor cores are where the FLOPs live. If your operation is not a matrix multiply (or cannot be cast as one), you are limited to CUDA core throughput — 15x slower. Design dimensions to be multiples of 8, and let cuBLAS handle the dispatch.

09 Profiling & optimization

Optimise what you measure, not what you guess. GPU profiling has two levels: timeline (macro) and per-kernel (micro).

Timeline profiling: Nsight Systems

  • Shows what the CPU and GPU are doing over time: kernel launches, memory copies, CPU-side Python, idle gaps. Answers the question "where is the GPU waiting?"
  • Common findings: CPU bottleneck (Python data loading or preprocessing holds up kernel launches), kernel launch overhead (many tiny kernels with gaps between them), lack of CPU/GPU overlap (the CPU blocks waiting for the GPU instead of queuing the next batch).

Per-kernel profiling: Nsight Compute

  • Runs a single kernel in isolation and measures everything: occupancy, memory throughput (bytes/sec achieved vs peak), compute throughput (FLOPS achieved vs peak), instruction mix, warp stall reasons.
  • Key metrics:
    • Achieved occupancy — fraction of max warps actively running.
    • Memory bandwidth utilization — fraction of peak HBM bandwidth used.
    • Compute utilization — fraction of peak FLOPS used.
    • Arithmetic intensity — FLOPs per byte of memory traffic.

The roofline model

  • A kernel is either compute-bound (limited by FLOPS) or memory-bound (limited by bandwidth). The roofline model plots achievable FLOPS as a function of arithmetic intensity:
roofline achievable FLOPS = min( peak FLOPS, peak bandwidth × arithmetic intensity ) arithmetic intensity I = total FLOPs / total bytes transferred (FLOPs per byte) ridge point I* = peak FLOPS / peak bandwidth (H100: 990 TFLOPS / 3.35 TB/s ≈ 295 FLOP/byte)
  • If I < I*, the kernel is memory-bound — optimise by reducing data movement (fusion, tiling, compression). If I > I*, it is compute-bound — optimise by reducing FLOPs or using faster instructions (tensor cores, FP8).
  • Most operations in deep learning are memory-bound. LayerNorm, activations, dropout, residual adds — all have arithmetic intensity near 1. Only large matmuls (GEMM with large M, N, K) are compute-bound. This is why fusion (§05) matters so much: it reduces the memory-bound operations.
Takeaway: profile before optimising. Use Nsight Systems for the big picture (where is time spent?), Nsight Compute for the kernel under a microscope. The roofline model tells you which bottleneck to attack.

10 Pitfalls & recap

Common pitfalls

  • Premature CUDA optimization. Writing a CUDA kernel when torch.compile would have fused the operation automatically. Try the easy thing first — it is often 90% of the way there.
  • Ignoring memory coalescing. A tensor transposed in the wrong place turns coalesced reads into strided reads. A 10x slowdown for a one-line bug.
  • Not using tensor cores. Hidden dimension is 769 instead of 768? Tensor cores disengage, throughput drops 15x. Always align to multiples of 8.
  • FP16 without loss scaling. Gradients overflow silently, training diverges after thousands of steps. Use BF16 (no scaling needed) or dynamic loss scaling with FP16.
  • Over-fusing. A mega-kernel that fuses 20 operations is fast but impossible to debug when it produces wrong results. Fuse incrementally, test each step.
  • Not profiling before optimizing. Spending a week optimizing a kernel that accounts for 2% of runtime. Nsight Systems first — find the actual bottleneck.
  • Benchmarking without warmup. The first kernel launch is slow (compilation, memory allocation). Always run warmup iterations before timing.

Recap

  • GPU = hierarchy. Threads → warps (32 threads, lockstep) → blocks (share memory) → SMs → the GPU. The warp is the real execution unit.
  • Memory hierarchy matters most. Registers → shared/L1 → L2 → HBM. Every kernel optimization is ultimately about keeping data in the faster levels.
  • Kernel fusion eliminates HBM round-trips between elementwise ops. torch.compile handles most cases automatically.
  • FlashAttention tiles the N×N attention matrix into SRAM blocks with online softmax — exact, faster, and O(N) memory.
  • Mixed precision doubles (BF16) or quadruples (FP8) throughput on tensor cores. BF16 is the default; FP8 for H100+.
  • Profile first. Nsight Systems for the timeline, Nsight Compute for the kernel, roofline to classify the bottleneck.
