Mixture of Experts

Scale a model's parameters by 10–100× while keeping per-token compute almost flat: replace the dense feed-forward layer with many expert FFNs, and route each token to just a few of them.

Deep Learning Sparse models LLM scaling

01 The core idea: conditional computation

Decouple how many parameters a model has from how many it uses per token.

A dense Transformer runs every token through every weight. Doubling the parameters doubles the compute. MoE breaks that link with conditional computation: maintain a large pool of N expert sub-networks, but for each token activate only the top k of them (often k=1 or 2).

  • Capacity grows with the total number of experts N.
  • Compute per token grows only with the active experts k.
  • So you can scale total parameters enormously while training/inference FLOPs stay roughly fixed.
One sentence: a learned router sends each token to a small subset of specialist FFNs, so the model is huge in parameters but cheap per token.

02 Experts & the router

An MoE layer swaps one FFN for many, plus a tiny network that decides who handles what.

The experts

Each expert is just an ordinary feed-forward network — the same 2-layer MLP that normally sits in a Transformer block, only now there are N copies. They're all trained on the same data but, because routing sends them different tokens, they specialize on their own.

The gating / router network

A single linear layer scores the token against each expert:

g(x) = x · W_router ∈ ℝᴺ (one logit per expert)

It acts as a dynamic controller — implicitly clustering tokens and dispatching each cluster to the expert best suited to it. Typically only the FFN sub-layer becomes MoE; attention stays dense.

03 Gating & top-k routing

Softmax the router logits, keep the top k, drop the rest. Drag the controls to watch tokens get dispatched — and the experts load up unevenly.

Token routing through the gate Each token routes to its top-k experts · watch the per-expert load bars and the imbalance readout
p(x) = softmax(g(x)) G(x) = keep top-k of p(x), zero the rest (renormalized over the k)

Noisy top-k gating (Shazeer et al., 2017) adds tunable Gaussian noise to the logits before the top-k cut during training — it encourages exploration and helps spread load, then is turned off at inference.

04 The combined output

Run only the selected experts, then blend their outputs by the gate weights.

y(x) = Σ_(i ∈ top-k) Gᵢ(x) · Eᵢ(x)
  • E_i(x) — expert i's FFN output for this token.
  • G_i(x) — the gate weight (renormalized softmax probability) for expert i.
  • The sum runs over only the k selected experts, so just k FFNs actually execute — the whole point.

The top-k selection is non-differentiable, so gradients reach the experts through the kept gate weights (a straight-through-style path): chosen experts and the router both get trained, idle experts get no signal that step.

05 Top-1 vs top-2, and sparsity

How many experts per token, and how sparse the whole layer is.

  • Top-1 (Switch Transformer): each token → a single expert. Minimal compute and communication, but needs a stronger balancing loss to avoid collapse.
  • Top-2 (GShard, Mixtral): each token → two experts. More stable (the token gets two views) and more expressive, at ~2× the expert compute.

Sparsity is the key scaling knob — total experts divided by active experts:

sparsity = N_total / k_active

06 The load-balancing problem

Left alone, routers collapse — a few popular experts hog every token while the rest starve.

It's a "rich-get-richer" loop: an over-chosen expert trains faster, so it gets chosen even more, while neglected experts never specialize and their capacity is wasted. You saw this as the imbalance (CV) readout in the viz above. Three standard fixes:

1 · Auxiliary load-balancing loss (Switch Transformer)

L_balance = λ · N · Σ_i f_i · P_i f_i = fraction of tokens routed to expert i P_i = average router probability for expert i perfect balance: f_i = P_i = 1/N

Added to the main loss with a small weight λ (≈0.01–0.1), it pushes utilization toward uniform.

2 · Expert capacity & token dropping

C = (T / N) · α α = capacity factor (≈1.0–1.5)

Each expert accepts at most C tokens per batch; overflow tokens are dropped (passed through via the residual) or rerouted. The capacity factor α>1 leaves slack for imperfect balance.

3 · Noisy gating & loss-free routing

Noise in the router (above) softens the winner-take-all dynamics. Newer models like DeepSeek-V3 go auxiliary-loss-free: they nudge per-expert router biases dynamically to balance load without a competing loss term.

07 Active vs total parameters

The headline number and the one that actually sets your compute are different.

Mixtral 8×7B: ~47B total params · ~13B active per token (top-2 of 8) → roughly 3.6× cheaper per token than a dense 47B model
  • Latency & FLOPs depend on active params, not total — that's the win.
  • Memory depends on total params: every expert must be resident in accelerator memory even though only k run per token. This is MoE's primary constraint.
  • Throughput beats a dense model of equal total size, because per-token work is far smaller.
MoE trades memory for compute: you pay to store all experts, but only compute a few. Great when you're compute/latency-bound, costly when you're VRAM-bound.

09 Expert specialization

No one tells the experts what to specialize in — it emerges from sparse routing.

  • Self-organization: with no explicit supervision, each expert ends up seeing a narrower slice of the data distribution, converges faster, and interferes less with the others.
  • What they cluster on: probing studies find experts organizing by language, domain, or token type — especially visible in multilingual and instruction-tuned models.
  • Shared experts: some designs (DeepSeek-MoE) keep one expert always active to capture universal knowledge, letting the routed experts focus purely on specialization.
  • Fine-grained experts: many smaller experts give finer specialization and less memory each, at the cost of more routing decisions to balance.
The theory: high-dimensional input naturally clusters, and a non-linear expert per cluster learns a sharper local boundary than one dense network spanning all clusters.

10 Trade-offs & limitations

Sparsity isn't free — it moves the cost around.

  • Memory residency (primary): all experts must sit in VRAM; you can't grow N indefinitely on fixed hardware. Mitigations: expert parallelism (shard experts across devices), quantization (QMoE).
  • Training instability: uneven selection gives noisy gradients and risks routing collapse; needs balancing loss + capacity tuning.
  • Communication overhead: distributed MoE needs all-to-all token exchange to reach the device holding each expert — a real bottleneck, sensitive to routing skew.
  • Latency variability: a "straggler" expert that gets too many tokens slows the whole batch; latency is less predictable than a dense model's.
  • Non-differentiable routing: top-k is a hard selection; gradients flow only through chosen experts, a biased-but-lower-variance signal.

11 Takeaways

  • MoE = conditional computation. Many expert FFNs, a router picks top-k per token: huge parameter count, small per-token compute.
  • Output is the gate-weighted sum over only the selected experts: y = Σ G_i(x)·E_i(x).
  • Load balancing is the central engineering problem — auxiliary loss, expert capacity, noisy/loss-free routing keep experts evenly used.
  • Active ≠ total params. Compute scales with active (Mixtral ~13B); memory scales with total (~47B).
  • Sparsity is a scaling knob — more total experts lowers loss at fixed active compute, until routing/communication costs bite.
  • Experts are FFNs (Feedforward / MLP) dropped into a Transformer block in place of the dense FFN.
