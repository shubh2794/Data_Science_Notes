36 The model as an implementation defines it: a configuration, a base model, a head, and a preprocessor

Everything above this section is the architecture as mathematics. From here to §51 the page follows the same Transformer into a real implementation at inference time: how it is described, stored, loaded and placed; which attention kernel actually runs; how the KV cache is managed; what the generate loop does to the logits; how perplexity is measured; and how a chat is turned into tokens. The first fact is structural: an implementation splits a model into three objects that travel separately — a configuration (the hyper-parameters §22 counted, and nothing else), a model built from it (a base model plus zero or more task heads), and a preprocessor (a tokenizer, and for chat models a template; for vision models an image processor) that turns raw input into the integer ids §20 embeds.

Base model against head: why the split exists

Every head in the table reads the same (n × d) output, so one pretrained base model serves every task, and swapping the task means swapping one small matrix. The head that ships with a generative checkpoint is the d × V LM head; asking for a sequence classifier on the same checkpoint loads the base model's weights and creates a d × num_labels matrix that has no pretrained values — 4 096 × 2 = 8 192 fresh numbers for a binary classifier on the 8B model, initialised randomly and reported as "newly initialised" at load time. That warning is the expected signal that fine-tuning is required, not an error. The mechanics that make the swap work are naming conventions: every parameter has a dotted path (model.layers.0.self_attn.q_proj.weight), the base model lives under one fixed prefix (model.), and a loader that sees a checkpoint with the prefix and a module without it — or the reverse — strips or adds the prefix. Weight tying (§21) is declared rather than copied: the head's weight is recorded as an alias of the embedding's, so it is stored once on disk and a device placer never puts the two copies on different devices.

Backbones: the same split for vision, read at several depths

Detection and segmentation models use a backbone (feature extractor), a neck (combines feature maps) and a head (predicts boxes or masks), and the backbone is exposed as a base model whose output is not only its last layer but a chosen set of stages. Asking a hierarchical vision Transformer for its first stage returns a map of shape (1, 96, 56, 56) on a 224 × 224 input: the patch embedding strides by 4, so 224/4 = 56 positions per side, and 96 is that stage's channel width. Later stages halve the grid and double the channels (28 × 28 × 192, 14 × 14 × 384, 7 × 7 × 768), which is exactly the multi-scale pyramid a detection neck expects. The patch embedding and the encoder stack are Vision Transformers' subject; the point here is only that "backbone" is the base-model / head split with more than one read-out depth.

Changing a component without rewriting the model

Because the configuration fully determines the modules, a model can be modified by replacing one module class before the weights are loaded. The standard example splits a fused qkv projection into three so that a low-rank adapter can be attached to q and v only: a load-time hook chunks each (3d × d) fused weight into three (d × d) pieces as the checkpoint streams in. With rank 16 on the two projections of a 12-layer, d = 768 vision encoder that adds 12 × 2 × 16 × (768 + 768) = 589 824 trainable parameters to a 94 274 096-parameter model — 0.63%, which is Parameter-Efficient Fine-Tuning's subject. The order matters: swapping the class after loading leaves the three new projections randomly initialised, because the hook runs only while the checkpoint is read. The model still runs and produces fluent-looking nonsense — another bug that does not crash (§35).

The conventions that make loading and placement possible

  • Modules are built on the meta device (§38): a tensor with a shape and no storage. Any initial value written in a constructor is therefore discarded; initialisation lives in a separate routine that runs only for parameters the checkpoint did not supply.
  • The block class is declared unsplittable, so an automatic device placer never cuts a residual block — and its residual addition — across two devices (§38).
  • One rotary module per model, not per layer: the angle table θᵢ = base^(−2i/dₖ) of §06 is built once and the cos/sin are passed down; one copy per attention layer duplicates buffers 32 times and invites the per-layer drift §06's pairing warning describes.
  • No hard-coded −1e9 in a masked fill: fp16's largest finite value is 65 504 (§28), so −1e9 overflows to −∞ in fp16 while being nowhere near the smallest fp32 value — the same constant means different things in different dtypes. §35's query-axis mask test is the consequence.
  • No positional container names: a sequential container names its children mlp.0, mlp.2, and every conversion map (§39), tying declaration and parallelism plan that refers to them breaks when a layer is inserted.
  • Remote code is code: a model whose architecture is not in the library ships its own Python and runs it at load time. Pin the exact revision you reviewed; a moving branch can change what executes.

37 How a checkpoint is laid out on disk: sharded tensors, an index, a configuration and a tokenizer

A trained model on disk is a directory, not a file. The weights are split into shards of a bounded size, an index maps every parameter name to its shard, and beside them sit the configuration of §36, the generation defaults of §46, and the tokenizer and chat template of §50. Each file exists because of a specific failure it prevents, and the byte counts follow from §36's arithmetic.

Sharding, worked

A shard cap bounds the size of any single file, which matters for downloads that resume, for file systems and hosts with per-file limits, and for the loader, which can read shards in parallel. The rule is greedy: walk the parameters in order, append each tensor to the current shard, and start a new shard when the next tensor would push it over the cap; a single tensor larger than the cap gets a shard of its own. For §36's 8B model in bf16 the total is 16 060 522 496 bytes. Under a 5 GB cap that is ⌈16.06 / 5⌉ = 4 shards at best, and the greedy walk gives exactly four (the embedding and the first blocks, two shards of middle blocks, the last blocks and the 1.05 GB head); the four-shard layout is what such checkpoints were commonly published with. Under the 50 GB default the current library version saves with, the same model is one file, and a 70B-class model in bf16 (137.95 GB, §22's row times two bytes) is three. The index's total_size is the sum of the tensors' bytes — the number to compare with a device's memory before anything is loaded, and the figure below computes it from the configuration exactly as a loader would.

38 Loading: the stored dtype, an empty skeleton on the meta device, and a device map that fills the fastest memory first

Loading a checkpoint is three decisions: in what dtype to hold the weights, how to avoid holding them twice while they are read, and on which device each block should live. Each has a default that is right most of the time and a failure mode that costs memory or speed without raising an error.

The dtype: load what was stored

A model trained in bf16 carries no information in an fp32 copy of its weights — upcasting pads each mantissa with zeros (§28) — and costs twice the memory: 32.12 GB instead of 16.06 GB for the 8B model. Current library versions therefore default to the dtype recorded in the configuration (or, failing that, the dtype of the first floating-point tensor in the checkpoint), and an explicit dtype overrides it. Older versions defaulted to fp32, and older guides still say so; the safe habit is to state the dtype explicitly (dtype="auto" or torch.bfloat16). The one reason to change dtype at load time is hardware: fp16 on a device without bf16 support, which brings back §28's overflow risk for the largest activations.

the two loaders, and their peak memoryNAIVE 1 build the model: every parameter allocated and randomly initialised M bytes 2 read the checkpoint into a separate dictionary of tensors + M bytes 3 copy the dictionary into the parameters, free the dictionary peak ≈ 2M (8B in bf16: ≈ 32.1 GB for a 16.1 GB model) read shard by shard, freeing each after its copy: peak ≈ M + the largest shard — one reason checkpoints are sharded (8B, 5 GB shards: ≈ 21 GB) and the random initialisation of step 1 is pure waste: every value is overwritten META DEVICE 1 build the model on the "meta" device: shapes and dtypes, NO storage 0 bytes 2 for each tensor in the (memory-mapped) shards: allocate it on its target device in its target dtype and copy the bytes in; free the source view 3 initialise only what the checkpoint did not contain (a new head, §36); re-establish tied weights peak ≈ M (+ the largest tensor group a conversion needs at once, §39)

Placement: fill the fastest memory first, never cut a block

When the model does not fit on one device, an automatic device map assigns modules in order — embedding, blocks, final norm, head — to the fastest device until its budget is spent, then to the next: GPU(s), then CPU memory, then disk. The unit it moves is the block: the block class is declared unsplittable (§36), because cutting a block would put a residual addition's two operands on two devices. Parameters placed on the CPU or disk are not computed there; they are streamed to the GPU for every forward pass and discarded. That is why offloading makes a model runnable but not fast, and the arithmetic is decisive.

by hand — a 70B-class model (137.95 GB in bf16) on one 80 GB GPU with a 70 GB budgetper block: 855.6 M parameters × 2 B = 1.711 GB (§22: 68 452.4 M in 80 blocks) embedding: 32 000 × 8 192 × 2 B = 0.524 GB placed first GPU blocks: ⌊ (70 − 0.524) / 1.711 ⌋ = 40 blocks → 68.98 GB on the GPU CPU: the other 40 blocks + final norm + head = 68.98 GB one decode step must read EVERY weight once (§47): GPU-resident part at 3.35 TB/s: 68.98 GB / 3.35 TB/s ≈ 21 ms CPU part over PCIe at ~25 GB/s: 68.98 GB / 25 GB/s ≈ 2.8 s ← about 130× the GPU part if that half were on an NVMe disk at ~3 GB/s: ≈ 23 s per token (transfer rates are representative assumptions, not measurements; the ratio is the point)

So a device map that spills half a model to the CPU generates at roughly one token every three seconds, not at half the GPU speed. The remedies are the ones that shrink the model rather than move it — fewer bytes per weight (quantisation), or more GPU memory through tensor or pipeline parallelism — and the device map is best read as a way to run something that does not fit, for evaluation or debugging. Two further details keep loading fast: shards are read by a small pool of threads (the work is I/O-bound, so a handful suffices; changing dtype during the copy makes it CPU-bound), and every tensor is written once, directly into its destination, so there is no second pass. The figure in §37 runs the placement for any configuration and budget.

39 Dynamic weight loading: when the checkpoint's layout is not the model's, and the conversion runs as the bytes arrive

The tensors on disk are named and shaped the way the model was trained or published; the tensors in memory are named and shaped the way the kernels want them. The two differ more often than not — fused projections, experts stacked into one 3-D tensor, a different RoPE pairing, legacy names — and a modern loader closes the gap with a list of small, reversible tensor operations applied to each group of checkpoint tensors as it is read, so that saving applies the inverses and reproduces the original files.

Worked: an 8-expert layer, from 24 tensors to two

A mixture-of-experts checkpoint commonly stores each expert's three SwiGLU matrices separately — for 8 experts that is 24 tensors per layer — while a grouped-matmul kernel (§43) wants all experts' gate and up projections in one tensor and all down projections in another. Two converters do it: stack the gate matrices and the up matrices across experts, then concatenate the two stacks along the output axis.

The RoPE permutation: §06's warning, turned into a load step

§06 showed that "adjacent" pairing (2i, 2i+1) and "rotate-half" pairing (i, i + dₖ/2) are different functions of q, and that running a checkpoint under the wrong one does not crash. A converter fixes it at load time by permuting the output rows of W_Q and W_K within each head so that the coordinates a checkpoint rotated together land in the positions the other convention rotates together. With dₖ = 8 the adjacent pairs are (0,1), (2,3), (4,5), (6,7) and the rotate-half pairs are (0,4), (1,5), (2,6), (3,7); the permutation that moves old row 2i to new row i and old row 2i+1 to new row i + 4 is [0, 2, 4, 6, 1, 3, 5, 7] (new position j takes old row perm[j]). Check pair 1 under rotate-half: new rows 1 and 5 hold old rows 2 and 3 — an adjacent pair, as required. Because q·k sums over the same coordinates in both conventions, permuting both W_Q and W_K identically leaves every unrotated score unchanged and makes every rotated score identical to the original model's; V is never touched (§06). The same permutation applied to only one of W_Q, W_K is a silent bug, and the §17-style check that catches it is one forward pass compared against a reference implementation.

Sharding while loading, and the packed-weight trap

With tensor parallelism each device holds a slice of every matrix (Distributed Training owns the scheme), and a dynamic loader slices each tensor as it is materialised, so a device never holds more than its share. Fused tensors need care. A gate_up projection of width 2·d_ff is laid out [G₀ G₁ G₂ G₃ | U₀ U₁ U₂ U₃]; split naively in two, device 0 gets all of the gate and device 1 all of the up projection, and silu(gate) ⊙ up would multiply the wrong halves. The correct split interleaves: device 0 gets [G₀ G₁ | U₀ U₁], device 1 gets [G₂ G₃ | U₂ U₃]. At d_ff = 14 336 and two devices that is 7 168 gate columns and 7 168 up columns each. The shapes of the right and the wrong split are identical, so this is a bug that does not crash — caught only by comparing outputs against an unsharded run.

40 Heterogeneous stacks: when the blocks are not identical, and every per-layer quantity must be computed per layer

§01 said the stack is L identical blocks, and §22's accounting multiplied by L. Several recent checkpoints break that on purpose: architecture search on a trained model shrinks the FFN of some layers, cuts the key/value heads of others, or removes a sub-layer entirely where the model can do without it — a 253B model derived from a 405B one and a 49B model from a 70B one are published examples. A configuration then needs a global value plus a sparse list of per-layer overrides, and every formula that multiplied by L becomes a sum over layers.

Two further kinds of heterogeneity are common enough to have their own fields. Layer types: many recent decoders interleave sliding-window layers (§45, window 4 096 for example) with full-attention layers — one to one in some models, several sliding layers per full one in others — so part of the cache is capped and the rest grows; a per-layer cache that ignores the type allocates the full length everywhere. Sub-configurations: a vision–language model has a vision configuration and a text configuration, each with its own attention backend (§41) and cache. The general rule the whole section reduces to: anything the model sizes per layer, compute per layer, and treat a global attribute as a default, not a fact.

What differs is which intermediate arrays exist in device memory, how many times they cross the memory hierarchy, and what shape of mask the kernel can accept. Masks: one semantics, four formats — and the float-mask trap

The mask is the same object everywhere (§18): which key each query may read. But an eager kernel adds it to the scores, so it must be 0 where allowed and −∞ where not; SDPA accepts that or a boolean; a flash kernel takes a causal flag and sequence offsets; flex attention takes a block mask built from a Boolean function. Handing an additive kernel the 1 / 0 convention of a 2-D padding mask is the classic mistake, and it does not crash:

by hand — a causal mask in the wrong convention, n = 5intended "1 = attend, 0 = masked" what an ADDITIVE kernel does with it k0 k1 k2 k3 k4 q0 1 0 0 0 0 adds +1 to allowed scores and +0 to FORBIDDEN ones: q1 1 1 0 0 0 every future key stays visible; the "mask" is a +1 bias q2 1 1 1 0 0 on the past. Flex attention's block mask is also what makes structured sparsity cheap. How a backend is chosen in practice. The default is the framework's fused SDPA, because it runs everywhere and dispatches to a flash-style kernel when no explicit mask has to be passed (plain causal attention without padding). A dedicated FlashAttention build is chosen for long contexts on supported GPUs and in half precision; it is also what makes padding-free "packed" batches cheap, since sequence offsets replace a padding mask. Flex attention is chosen when the mask is structured but unusual. Eager is chosen when attention weights must be returned — the other kernels never form them — or when a score modification has no fused form. A multimodal model may set one backend per sub-model (a vision encoder that needs fp32, which flash kernels do not support, beside a text decoder on FlashAttention), and a backend registered under a new name must come with a mask formatter of the same name, or mask creation is silently skipped: the attention function receives no mask, and the padding and window constraints it would have carried are lost unless the function re-derives them.

42 Paged attention: the KV cache in fixed-size pages, a block table per sequence, and what it does to fragmentation

A server generating for many users at once does not know how long each answer will be. Reserving a contiguous cache of the maximum length for every request wastes most of it; growing each cache by reallocation fragments memory. Paged attention borrows the operating system's answer: cut the cache into fixed-size blocks of B tokens, give each sequence a block table mapping its logical blocks to physical ones anywhere in a shared pool, and teach the attention kernel to gather keys and values through the table.

The measurement that motivated the design found that earlier serving systems stored actual token states in only 20.4–38.2% of the KV-cache memory they held — 60–80% lost to reservation and fragmentation — against under 4% waste with paging; the resulting larger batches gave 2–4× higher throughput at the same latency. The block size is a trade: too small and the gather through the table costs more per token; too large and the partly filled last block wastes more and fewer blocks can be shared. 16 tokens is one widely used default (the paper's system uses it); other implementations choose blocks of hundreds of tokens. The kernel side is a change of indirection only — the scores are the same numbers — which is why paged variants of eager, SDPA and FlashAttention can all exist (§41). 43 Experts backends: the same routed FFN, computed by a loop, by duplicated weights, or by one grouped matrix multiply

In a mixture-of-experts layer a router picks k of E expert FFNs for each token and mixes their outputs with the routing weights. Every implementation computes that same function. What differs is how the k · T token–expert pairs of a batch of T tokens become matrix multiplies — and the three standard answers trade launches against memory in opposite directions, which is why a good implementation switches between them between prefill and decode.

Hence the switch: a grouped matmul for prefill, where T is large and copying weights per token is ruinous, and a batched matmul for decode, where T is the batch size, the copy is small, and one fixed-shape launch per layer is what a compiled, graph-captured decode step wants. One widely used library does exactly this on GPUs when the grouped backend is selected, switching back when generation ends; on CPUs it keeps the grouped form throughout, which its documentation reports as the most efficient at every input size. Vendor kernels go further — fusing the router dispatch, the gated up-projection, the activation and the down-projection into one kernel, or running the experts in fp8 or fp4 with per-block scales — and are Model Acceleration's.
