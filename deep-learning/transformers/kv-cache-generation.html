44 The KV cache as an implementation holds it: a list of layers, an update call, and the shapes of one decode step

The attention page proved why the cache is exact — under a causal mask an old key or value never changes — and counted its bytes. Growing, rolling back, and reusing

  • Growing. The simplest layer appends by concatenation, which allocates a new tensor of length t + 1 and frees the old one every step; for one moment both exist, so the transient peak is one layer's cache on top of the whole cache. The fixed-size layers of §45 write into a pre-allocated slot instead.
  • Rolling back. Speculative decoding appends several drafted tokens and then rejects some of them, so the cache must be cropped back to the last accepted position — for full-attention layers simply a shorter view. A sliding-window layer (§45) has already discarded the oldest entries it would need, so it can roll back only if it was told in advance to keep them; the cheap default cannot.
  • Reusing a prefix. A long system prompt shared by many requests can be run once, its cache kept, and a copy handed to each request, which then prefills only its own suffix. For a 1 000-token shared prefix and a 30-token question the prefill runs over 30 tokens instead of 1 030 — 34× fewer prefill operations. The same idea across calls to a hosted model is prompt caching, whose economics are Context Engineering's; the paged pool of §42 makes the sharing copy-free.
  • Multi-turn chat. Keeping the cache between turns works only if the new prompt's token prefix is identical to what was cached. A chat template (§50) that re-renders history differently — dropping a reasoning block from the previous answer, say — produces a different prefix, and a cache reused against it is silently wrong. The safe rule: reuse a cache only after checking that the re-tokenised history begins with exactly the cached ids.
  • Only at inference. Training computes every position in one pass (§24) and needs no cache; turning it on during training wastes memory and can interfere with gradient checkpointing.

Reading the table

Static trades memory for a fixed shape. A decode step whose tensors never change shape can be compiled once and replayed as a captured graph, which removes per-step launch overhead — the dominant cost of a small model's decode — and that, not memory, is why the static cache exists; compilation itself is Model Acceleration's. Offloading trades speed for memory, and the bandwidth arithmetic above says how much: the transfer is overlapped with other layers' compute, so it is nearly free while the cache is small and dominates once a layer's cache takes longer to move than the layer takes to compute — at 32k tokens, 128 MiB per layer at ~25 GB/s is about 5 ms, against roughly 0.13 ms to read that layer's 0.44 GB of weights from GPU memory. It is a fallback for running out of memory, not a speed setting. A sliding window is free only for models trained with it: imposing a window on a full-attention model deletes context it was trained to read. Quantisation is modelled on the KIVI paper's asymmetric scheme (which quantises keys per channel and values per token; one common implementation quantises both per channel), with a full-precision residual of the most recent tokens (128 by default in one common implementation) because the newest keys and values are the ones attended to most sharply; its cost is dequantisation work every step, so it pays only when memory, not speed, is the limit. The per-layer rule of §40 applies to all of them: a model with mixed sliding and full layers needs a cache that knows which layer is which.

46 The generate loop: prefill, then one step at a time through a pipeline of logits processors

§29 reshaped one distribution and §30 ran three rules on the page's model. A production generate loop is those rules embedded in a fixed sequence of steps, with a pipeline of logits processors between the model's raw logits and the choice of token. Each processor is a small function (input_ids, logits) → logits; they run in a fixed order, and the order matters because several of them are not invariant to the others.

Two things the numbers show. First, the n-gram ban is absolute and the repetition penalty is not: "cat" went to zero, while "the" — seen twice — lost only a few points and is still the likeliest token. Second, and less often noticed, the repetition penalty is not invariant to shifting the logits, though the softmax is. Subtract 3 from every raw logit — the same distribution — and "the" becomes −1.0, which the penalty multiplies to −1.2; its probability after the penalty is then 0.407, higher than the 0.399 it had with no penalty at all, because the unseen "mat" (−1.8) was left alone. The penalty's strength therefore depends on an arbitrary offset of the model's logits, and one value of θ is not comparable across models. The figure steps through every stage for any setting.

47 Stopping criteria, streaming, and what one step costs: time to first token against time per token

A generate loop needs a rule for when to stop and, in an interactive setting, a way to show text before it has stopped. Both look trivial and both have edge cases that come from the same fact: the model emits token ids, and the things people care about — a stop phrase, a printable character — are defined on text.

Streaming: hold back what cannot be printed yet

A streamer receives each new id and must emit text. Decoding ids one at a time is wrong in two ways. Byte-level tokens can split a character: é is the two UTF-8 bytes C3 A9, and a byte-level vocabulary may emit them as two tokens; decoding the first alone yields a replacement character. Word-piece and space conventions make a token's text depend on its neighbours. So a streamer decodes the whole pending tail, prints only the part that ends at a safe boundary — a completed character, or conventionally a space or newline — and keeps the rest pending. The printed text is then exactly the final decoded text, delivered early; the latency the user perceives is the time to the first printable chunk, not the time to the last token.

These two numbers explain most of inference engineering. Prefill is arithmetic-bound, so it benefits from fused kernels (§41) and larger batches of prompt tokens. Decode is bandwidth-bound, so it benefits from fewer bytes per weight (quantisation), fewer bytes per cached token (GQA, §45's strategies), batching many users onto one read of the weights (§42), and producing several tokens per read of the weights — Speculative Decoding's idea. More arithmetic throughput alone does almost nothing for decode.

48 Decoding rules beyond greedy, beam and sampling: contrastive search, contrasting layers, diverse beams and constraints

§30's three rules optimise the next token, the sequence's probability, or nothing. Each of the rules below adds one more term to the choice — similarity to the context, disagreement between layers, disagreement between beams, or a hard requirement on the output — and each is worked by hand here. In current library versions several of them are distributed as community-maintained "custom generation" methods loaded by name rather than built into the core loop; the mechanisms are what matter.

Contrastive search takes B: less probable, and new.

The rule targets the failure §29's table called "the mode of a language model is repetitive": greedy and beam search fall into loops because a repeated phrase makes itself more probable. Sampling escapes loops by adding randomness and pays in coherence; contrastive search stays deterministic and penalises only candidates whose representation duplicates the context. Its cost is the k candidate rows per step — cheap in a bandwidth-bound decode (§47), where k extra rows share one read of the weights — and a penalty that depends on the geometry of the hidden states, which works best when those are not all mutually similar (the proposal paired it with a training objective that spreads them out). DoLa: contrast the final layer with an earlier one

Decoding by contrasting layers reads the next-token distribution at two depths — the final layer N and a "premature" layer M, obtained exactly as §33's logit lens obtains it, by applying the final norm and the output head to layer M's residual stream — and prefers tokens whose probability grew between the two. The motivation is that factual content is added in later layers while shallow, surface-level predictions are already present early, so the growth isolates the later layers' contribution; the reported effect is a 12–17 point absolute improvement on a truthfulness benchmark for one family of 7B–65B models.

Diverse (group) beam search, and constrained beam search

A beam's B hypotheses tend to differ only in their last few tokens. Diverse beam search splits the beams into G groups decoded in turn at each step, and subtracts from a later group's scores a penalty λ times the number of times each token was already chosen by earlier groups at that step (a Hamming diversity term). Constrained beam search goes the other way: it forces given words or phrases into the output by tracking, per hypothesis, how much of each constraint is satisfied, and reserving part of the beam for hypotheses at each level of progress so that a constraint-satisfying but initially improbable path is not pruned. Both run the model exactly as ordinary beam search does; they change only which B of the B·V candidates survive.

by hand — two groups of one beam each, one step, diversity strength λlog p: a −0.51 b −1.20 c −2.30 group 1 chooses a. group 2 scores a − λ·1, b, c: λ = 0.5: a −1.01 b −1.20 → a again (no diversity yet) λ = 1.0: a −1.51 b −1.20 → b the groups diverge once λ exceeds the log-probability gap, here 1.20 − 0.51 = 0.69.

49 Perplexity of a fixed-context model: disjoint chunks against a strided sliding window, worked token by token

Perplexity is the exponentiated mean negative log-likelihood of a text under the model — the same quantity as §24's loss, read back as "the effective number of equally likely choices per token". For a model with a trained context of n_ctx tokens the exact definition cannot be evaluated on a longer text, and the approximation chosen changes the number by more than many of the differences it is used to report.

The same effect at real scale: a 774M-parameter decoder with a 1 024-token context scores a standard Wikipedia test set at a perplexity of 19.44 with disjoint 1 024-token chunks — close to the 19.93 its authors reported — and at 16.44 with windows sliding by 512, the same model and the same text. A 15% difference in the headline number from the evaluation loop alone is the reason a reported perplexity is meaningless without its stride and context. Two further rules. Perplexity is per token, so two models with different tokenizers are not comparable on it; the tokenizer-free form is bits per byte, (N_tokens / N_bytes) · ln PPL / ln 2 — for PPL 16.44 at an assumed 4 bytes per token that is 2.80 / 4 / 0.693 ≈ 1.01 bits per byte. It is defined for causal models only: a masked (bidirectional) model does not define p(xₜ | x<t), and its "pseudo-perplexity" is a different quantity. The loss from which it is computed is the one-hot cross-entropy, never a label-smoothed one (§25).

50 Chat templates: a conversation is one token sequence, and the model only knows the format it was trained on

A chat model is still the decoder of §18: it continues a sequence of tokens. What makes it a chat model is fine-tuning on conversations serialised in one specific format — role markers, message delimiters, special control tokens — and a chat template is the program, shipped with the tokenizer, that serialises a list of {role, content} messages into exactly that format. Two models fine-tuned from the same base can use different formats; given the wrong one, a model still produces text, usually noticeably worse.

The four switches that decide the string

  • The generation prompt. Ending the string with the opening of an assistant turn (<|im_start|>assistant\n) tells the model that what comes next is its reply. Without it the model may continue the user's message instead. Some formats have no assistant header, and the switch does nothing.
  • Continuing the final message. The opposite: leave the last (assistant) message open, without its end-of-turn token, so generation continues it — "prefilling" a reply that starts with {"name": " to force a JSON answer. It cannot be combined with the generation prompt, which would open a new turn.
  • Special tokens, once. A template usually emits the begin-of-sequence token itself. Tokenising its output with the tokenizer's default "add special tokens" adds a second one — a sequence starting <s><s> that the model never saw in training. Nothing fails; quality drops. Render and tokenise in one step, or tokenise without adding special tokens.
  • The end-of-turn token is a stop token. A format whose assistant turns end in <|eot_id|> or <|im_end|> must have that id in the stopping set of §47, or the model writes the end of its turn and then keeps going — often by writing the user's next message itself.

Tools, and where the template stops

Tool use extends the same scheme. Tools are passed to the template as JSON schemas (name, description, typed parameters) and rendered into the system block in whatever form the model was trained on — some templates render them as function signatures. An assistant message may carry tool_calls (a list of {name, arguments}) instead of content; the tool's result comes back as a message with role tool; the template renders each in the model's trained delimiters, for example <tool_call>{"name": "multiply", "arguments": {"a": 5, "b": 6}}</tool_call> and a tool turn whose content is 30. For training, the same template is applied without the generation prompt, and usually only the assistant tokens contribute to the loss (§24's per-position mask). Templates are small programs (Jinja) stored as a file beside the tokenizer; whitespace is significant, which is why they are written with whitespace-trimming syntax, and a newline the model never saw after a role marker is enough to change its behaviour. One safety note: many tokenizers recognise a control token's literal text anywhere in their input, so user-supplied text containing <|im_end|> can close a turn from inside a message unless the application escapes it. What to put in the messages — prompting, retrieval, tool schemas as a design problem, the context budget — is Context Engineering's; this section owns only how the list becomes tokens.

A chat template renderer: the exact string a message list becomes, with control tokens marked pick a format and toggle the switches — control tokens are drawn as boxes because each is one vocabulary entry; the counters are computed from the rendered string, and the double-BOS check fires when the tokenizer would add a second begin-of-sequence token

51 Getting the most out of a large model: fewer bytes per weight, an attention kernel that never forms n², and an architecture built for decoding

Deploying a large decoder comes down to three levers, and this page has already derived each of them; this section puts them in one place with the numbers, and points to where each is taken further. Lower precision shrinks the weights that every decode step must read (§47). A fused attention kernel removes the n² array (§41). Architectural choices made at training time — relative positions that survive long inputs, and fewer key/value heads — shrink the cache and extend the usable context.

The architectural lever has two halves, and both are derived above rather than here. Positions: relative schemes put position where tokens meet — RoPE (§06–§07) and ALiBi (§08) — and §09 measured what each does past the training length; ALiBi degrades least out of the box, RoPE degrades gently and is the one that context-length extension rescales. The cache: the attention page's MQA/GQA section derives the saving exactly, §45 shows what each allocation strategy then does with it, and §42 how a server packs many such caches into one pool. None of these can be retrofitted by a flag — a model trained with full multi-head attention and learned positions keeps them — which is why they are decisions for §31's stage of design, not for deployment.

The claim to soften. "Using the KV cache gives identical results." Identical in exact arithmetic; in floating point, close. With the cache, the last token's attention is computed as a (1 × t) product instead of one row of a (t × t) product, and matmul kernels sum in different orders for different shapes, so logits can differ in the last bits and a greedy decode can, rarely, take a different branch at a near-tie. The same is true of switching attention backends (§41). A test that compares generations across these switches should compare logits with a tolerance, not strings.
