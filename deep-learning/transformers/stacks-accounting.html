18 The stacks: encoder-only and decoder-only are the same block with a different mask

Stack L of the blocks of §02 and there are two things to decide: what each position is allowed to see, and where the loss is read. Those two decisions are the entire difference between an encoder and a decoder. The block does not change; the mask does.

Why the mask composes through depth

A single causal attention layer lets position i read 0 … i. Stacking two does not widen that: at layer 2, position i reads layer-1 outputs at 0 … i, each of which depended only on positions up to itself, so the union is still 0 … i. The set of positions that can influence position i is therefore {0, …, i} at any depth — the figure computes that reachability set explicitly by propagating a Boolean matrix through L layers and shows it is the lower triangle at every depth. The same computation for the encoder gives the full square after one layer; there is nothing left to reach after that, which is why encoder depth is about refining representations, not widening context. For the prefix-LM the reachable set of a suffix position is the whole prefix plus its own causal past, and of a prefix position the whole prefix — the figure draws that too. Padding is orthogonal to all three: a padded key is masked out (−∞ on its column) in every stack, and as the attention page's masking section explained, never on its row.

19 The encoder–decoder stack: cross-attention wiring, shapes and cost

The 2017 architecture had two stacks: an encoder over the source and a decoder over the target, joined by a third kind of attention in which the decoder's queries read the encoder's keys and values. This section writes that wiring exactly, counts it, and says what it buys over the single-stack alternatives.

the decoder block of an encoder–decoder model — THREE sub-layers, not twoencoder Hₑ = EncoderStack(X_src) (n_src × d), computed ONCE per source decoder block, pre-norm form, on the target stream X (n_tgt × d): X₁ = X + SelfAttn( N₁(X) ) causal, over the target — the "self" of the attention page X₂ = X₁ + CrossAttn( N₂(X₁) , Hₑ ) queries from the target, keys and values from Hₑ Y = X₂ + FFN( N₃(X₂) ) CrossAttn(U, Hₑ): Q = U·W_Q (n_tgt × h·dₖ) K = Hₑ·W_K, V = Hₑ·W_V (n_src × …) A = softmax( Q Kᵀ/√dₖ + padding mask on SOURCE keys ) (n_tgt × n_src) Z = A·V, concat, ·W_O (n_tgt × d) no causal mask here: every target position may read every source position. the score matrix is RECTANGULAR, n_tgt × n_src — the one place in the architecture where the two axes of an attention matrix index different sequences. the count — what the third sub-layer addsparameters per decoder block attention 4d² (self) + 4d² (cross) + FFN 8d² = 16d² against a decoder-only block's 12d²: cross-attention is +33% MACs per decoded token, cross-attention: Q projection d·d every step K, V projections 2·n_src·d·d ONCE per source (cached across every step and, with one W_K, W_V per layer, once per layer) scores + blend 2·n_src·d every step, against the cached source so decoding one token reads the WHOLE source in O(n_src·d) per layer, and the source is never re-encoded: the encoder's cost is paid once per input.

What the second stack buys, and what it costs

Against a decoder-only model given the source as a prefix, the encoder–decoder has three real differences. First, the source is read bidirectionally — every source position's representation sees the whole source — while a causal prefix reads it left to right; for inputs whose meaning depends on later parts (most sentences) this is a genuine representational advantage, and it is the usual explanation for why the family has stayed competitive on translation and summarisation at equal parameter count. Second, the source is encoded once and its keys and values cached, so a long input costs its encoding once and then O(n_src) per output token, the same as a KV cache; a decoder-only model pays the same after the prefill, so this is a wash. Third, the source and target live in separate streams: the decoder's residual stream carries only the target, and the source enters only through cross-attention, which means the decoder's depth is spent on generation and none of its positions is "wasted" on re-representing the input. The costs are the third sub-layer's parameters, a second set of hyper-parameters (encoder depth against decoder depth), and — arguably the one that mattered most at scale — a training objective that supervises only the target positions, against a decoder-only objective that supervises every position of every document. §34 puts the three families side by side with the counts.

Where this wiring is used now. Translation and summarisation models of the T5 and BART families; speech and vision–language systems in which a non-text encoder feeds a text decoder; and, in a different guise, the retrieval-augmented designs that read retrieved passages through cross-attention rather than by placing them in the prompt. The pure-text large decoders dropped the second stack for the training-objective reason above. Encoder vs Decoder Models is the decision guide; this section is the wiring it points at.

20 Embedding in: the token table, the √d_model scale, and what it is for

The first thing the model does is look a row up in a table, E[token], multiply it by √d_model, and add the position vector P[i]. The factor exists to make the token term and the position term comparable in size — a sinusoidal row has norm √(d/2), an embedding row initialised at variance 1/d has norm about 1 — and whether it is needed depends entirely on how the table was initialised. It is the one detail of the input that is routinely copied without being understood, and this section says what it is for.

the input, and the two scales that have to matchx⁰ᵢ = √d · E[tokenᵢ] + P[i] E (V × d), P (n_max × d) or RoPE and no P at all sinusoidal P: entries in [−1, 1], half of them sin and half cos ⇒ ‖P[i]‖ ≈ √(d/2) E initialised like a weight matrix, N(0, 1/d) per entry (the 2017 convention, so that a TIED output projection has the right scale — §21): ‖E[t]‖ ≈ 1 without the factor: ‖E[t]‖ ≈ 1 against ‖P[i]‖ ≈ √(d/2) = 16 at d = 512 the position term is 16× the token term; the token is nearly invisible with the factor: ‖√d·E[t]‖ ≈ √d = 22.6 against 16 comparable, token slightly larger the OTHER convention, in which the factor must NOT be appliedE initialised N(0, 0.02²) per entry, P LEARNED and initialised similarly small (0.01 in the original 2019 decoder code): ‖E[t]‖ ≈ 0.02·√d = 0.55 at d = 768, ‖P[i]‖ about half (the figure uses 0.02 for both, which makes them equal) — already matched, and the norms are small on purpose: the first block's norm will rescale them. Multiplying by √d here does no harm to the ratio but changes the absolute scale the tied output head sees (§21). The rule is not "always scale"; it is "make the token and position terms the same size, and know what the output head expects".

The figure measures the two norms and the cosine of x⁰ with each of its two components under each convention. It also shows the consequence for the attention scores of the first layer: with the position term dominating, the first block's queries and keys are functions of position almost alone, and the score matrix is nearly the same for every input — a banded pattern that depends on |i − j| and not on the tokens. The model can recover from this (the first block's W_Q, W_K can learn to ignore the position directions), but it starts with a handicap it need not have, and on a small budget it may never fully recover. This is the first of §35's bugs that does not crash.

The two components of x⁰ under each convention, and what the first layer's scores look like the norms are the whole story — pick a table initialisation and toggle the √d factor; when the position term dominates, the first-layer score matrix stops depending on the tokens

21 Unembedding out: the vocabulary projection, weight tying, and what it costs in a small model

The last thing the model does is turn a d-vector into V logits. That is one matrix, (d × V), and in a small model it is a third of the parameters and a third of the arithmetic. Tying it to the input table halves that count and makes an assumption about geometry that the initialisation has to honour.

That is a reasonable prior for a small model. Most 7B+ decoders untie — the extra V·d is cheap at that scale and separating the roles is reported to help a little — but not all: some very large models keep the tie. requires: an initialisation in which ‖E[t]‖ makes ⟨hᵢ, E[t]⟩ the right size — the same fact §20 needed, seen from the other end.

What the initial loss says about the head

A model at initialisation should be roughly uniform over the vocabulary, so its loss should be about ln V — 10.8 for a 50k vocabulary. Push random tokens through DL.tfInit under the conventions of §20 and read the loss: the untied head with unit-variance logits gives about ln V + ½, the expected cross-entropy of a Gaussian logit vector; the tied head with the N(0, 0.02²) table gives ln V almost exactly; the tied head with the N(0, 1/d) table and the √d factor gives noticeably more than ln V, and the reason is instructive — the residual stream still contains the input embedding at the top, the final norm scales it to norm √d, and tying makes ⟨hᵢ, E[tokenᵢ]⟩ ≈ √d: the untrained model confidently predicts its own input token, which is the wrong answer for next-token prediction. And the tied head with a unit-variance table and no factor gives a loss in the hundreds: the logits are √d too large. The figure runs all four and prints them; the one in the hundreds is the bug, the one a few nats above ln V is a known cost of tying that training removes in the first steps.

Reading the table

  • The block count is the model. From 125M to 70B the block share of parameters goes from 68% to 99%; the embedding is a fixed cost that becomes invisible. This is why "non-embedding parameters" is the count scaling laws are written in (Large Language Models), and why §23's 6·N·D rule is usually stated with N the non-embedding count.
  • The 70B row's attention is smaller than its shape suggests. With g = 8 key/value heads for h = 64 query heads, the attention block is (2 + 2·8/64)·d² = 2.25·d² rather than 4d²: 151M per block instead of 268M. The figure lets you set g = h and watch 9.4 billion parameters appear.
  • Untied heads cost exactly one more V·d. 131M in the 7B model, 262M in the 70B — 2% and 0.4%. Once that share is this small, tying no longer pays much for its assumption (§21), which is one reading of why most large decoders untie.
  • Learned positions are the smallest line and the most consequential. 1.6M parameters in the 125M model — 1.3% — and the reason its context is fixed at n_max for ever (§05).

From the count to bytes: on disk, in memory, and beside the cache

A parameter count becomes a memory requirement by one multiplication, and that product is the first number an implementation checks. The 7B-class row is 6 738 415 616 parameters: 26.95 GB in fp32, 13.48 GB in bf16, about 3.8 GB at 4 bits with group scales; the 70B-class row is 137.95 GB in bf16, more than one 80 GB device holds. How those bytes are split into files and indexed is §37, how they are placed on devices without being held twice is §38, and why the layout on disk can differ from the layout above is §39. At inference a second memory term sits beside the weights and, unlike them, grows with every token and every concurrent sequence: the KV cache, 2·L·g·dₖ values per token — which is why the g column of the table matters more at deployment than its share of the parameters suggests (§45).

23 Training compute: the 6·N·D rule derived from the MAC count, and exactly what it leaves out

The rule of thumb says training a model of N parameters on D tokens costs 6·N·D floating-point operations. It is true, it is a MAC count in disguise, and it omits one term that this page can put a number on. Derive it from the forward pass of §01 and the backward pass of the training page.

forward: one MAC per weight per token, plus the attention termevery weight matrix W (a × b) is applied as x·W once per token: a·b MACs = one MAC per parameter ⇒ forward weight MACs per token = N_weights ≈ N_non-embedding + V·d (the head is a matmul too; the input lookup is not — it costs nothing) the attention matrices are not weights: Q·Kᵀ and A·V cost 2·n·(h·dₖ) MACs per token per layer (causal kernels skip half: n·(h·dₖ), plus a little) ⇒ forward MACs per token = N_weights + L·n·d (causal, h·dₖ = d) backward: twice the forward, so training is three forwards — in MACs — and 6 in FLOPsfor each y = x·W : ∂L/∂W = xᵀ·(∂L/∂y) and ∂L/∂x = (∂L/∂y)·Wᵀ two matmuls, same size ⇒ backward MACs = 2 × forward MACs (the training page's backprop-cost section counted the same factor for an MLP) ⇒ training MACs per token = 3·N_weights + 3·L·n·d ⇒ training FLOPs per token = 6·N_weights + 6·L·n·d (1 MAC = 2 FLOPs) ⇒ training FLOPs = 6·N·D + 6·L·n·d·D the rule keeps the first term. The second is the attention term, and its size RELATIVE to the weight term is L·n·d / N_weights ≈ n / (12·d) for a standard block (12d² per layer): d = 768, n = 2048: 0.22 d = 4096, n = 4096: 0.083 d = 8192, n = 4096: 0.042 d = 4096, n = 32768: 0.67 — at long context the "negligible" term is two-fifths of the total.

Three things the derivation makes exact

First, which N: the rule wants the parameters that are multiplied, so the input embedding is excluded (a lookup) and the output head is included (a matmul) — for a tied model that means N_non-embedding + V·d, which is why quoting the rule with the total count is slightly wrong in both directions and nearly right at scale. Second, MACs against FLOPs: the 6 is 3 in MACs; a hardware peak is quoted in FLOP/s, and a MAC count from the attention page's cost section or DL.attnMacs must be doubled before it is divided into a peak — this is the factor-of-two slip the box below names, and the figure prints both units on every bar. Third, where the crossover is: the attention term equals the weight term at n ≈ 12·d, which the attention page's crossover section derived per layer as n* = 2d + nmat·d_ff/2; this section only reads that result at the model level. Everything else the rule omits — the norms, the softmax, the activation functions, the optimiser's own arithmetic — is a few percent. Activation recomputation, if it is used to save memory, is not a few percent: it repeats the forward pass during the backward pass and turns the 6 into 8. And Distributed Training owns what happens when the count has to be split across machines.

The unit slip to avoid. "The 7B model does 7 GFLOPs per token in the forward pass." It does 7 GMACs, which is 14 GFLOPs, and 42 GFLOPs per token in training. Every count on this page and on the attention page is a MAC count unless it says FLOPs; the conversion is a factor of two and it is the difference between a training-time estimate that is right and one that is off by half.
