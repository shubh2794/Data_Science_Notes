01 What algorithm analysis is

Algorithm analysis is the prediction of the resources an algorithm consumes — almost always time, sometimes space — expressed as a function of the size of its input, computed on a high-level description of the algorithm in an abstract machine model, and reported only up to constant factors. It is not benchmarking. Nothing is executed, no hardware is named, and the answer is a function, not a number.

the object being computedT(n) = the number of primitive steps the algorithm executes on the worst input of size n what is actually reportedT(n) = Θ(g(n)) for the simplest g that tracks T's rate of growth the formal content of that report∃ c₁, c₂ > 0 and n₀ > 0 such that 0 ≤ c₁·g(n) ≤ T(n) ≤ c₂·g(n) for all n ≥ n₀

The three questions, in order

  • Is it correct? An algorithm that is fast and wrong has no cost worth measuring. Correctness is proved — by a loop invariant for iteration (§04), by induction on subproblem size for recursion (§13), by an exchange argument for a greedy method, by optimal substructure for dynamic programming. It is not established by a test suite, because a test suite reports on the inputs you thought of.
  • What does it cost, as a function of n? This page.
  • Can we do better? Sometimes the answer is provably no — a lower bound such as the Ω(n log n) decision-tree bound on comparison sorting (sketched in §09, and applied throughout Sorting & Searching) is a statement about every possible algorithm in a model, not about one algorithm, and it is what tells you to stop optimising or to change the model.

Four commitments hidden in that definition

  • A function of input size, not a single number. "This sort takes 4 ms" is a fact about one input on one machine on one day. "This sort takes Θ(n²) comparisons in the worst case" is a fact about the algorithm. The first does not compose, does not extrapolate, and does not survive a hardware refresh; the second does all three.
  • Size has to be defined per problem. For sorting it is the number of elements. For multiplying two integers it is the number of bits, because that is what the work scales with — an algorithm that is linear in the value of its input is exponential in its size. For a graph it takes two numbers, |V| and |E|. State the measure before you state the bound; a great many confused complexity claims are really disagreements about n.
  • Up to constant factors, deliberately. The constants are hardware, compiler, language and mood. Discarding them is what makes the result portable — and it is also the single largest source of analysis that is technically true and practically useless, which §11 and §23 are about.
  • Worst case unless stated otherwise. A bound over all inputs of size n is a guarantee. An average needs a distribution over inputs, and that distribution is an assumption you must be prepared to defend (§05, §06).

What "resources" covers

  • Time, counted as primitive operations, is the default and occupies most of this page.
  • Space — how much memory beyond the input the procedure needs at its peak, including the recursion stack, which is the part people forget. §21.
  • Other scarce things, when they dominate: disk or network transfers in an external-memory or distributed setting, cache misses on a modern CPU, comparisons when a comparison is a human judgement, samples when data is what costs money. The machinery is identical; only the unit being counted changes.
The one-line version. Analysis replaces the question "how long did it take?" — which is a measurement — with "how does the cost grow?" — which is a property of the algorithm, provable on paper, and the only form of the question whose answer is still true next year.

02 Why you cannot settle this by timing it

The obvious alternative is an experiment: implement the thing, run it on some inputs, plot seconds against n. That is a real and useful activity — §22 builds a disciplined version of it — but as a substitute for analysis it fails in three specific ways, and there is a fourth failure that is worse than all of them.

The three standard limitations

  • Results are not comparable across environments. Two timings mean nothing next to each other unless the hardware, the operating system, the language runtime, the compiler flags and the background load are the same. Wall-clock time also measures whatever else the machine was doing; CPU time is fairer and still not reproducible to better than a few percent.
  • You can only test the inputs you thought of. An experiment reports on a finite sample of inputs. The input that matters is frequently the one nobody generated — the already-sorted array, the adversarial hash key set, the graph that is one long path. Worst-case analysis covers all inputs of size n by construction; a benchmark covers the ones in the harness.
  • You must build it first. This is the expensive one. The whole point of analysis is to choose between designs before committing weeks to one. Implementing an approach in order to discover it is quadratic is a very costly way to learn something a page of arithmetic would have told you.

The failure that actually bites: exponential time is invisible at small n

Take the Fibonacci numbers, defined by F₀ = 0, F₁ = 1, Fₙ = Fₙ₋₁ + Fₙ₋₂. The recursive definition transcribes into code in three lines, and for n up to about 30 it returns instantly. Every experiment you would plausibly run says it is fine. It is not fine.

the direct transcriptionfib1(n): if n ≤ 1: return n; else: return fib1(n−1) + fib1(n−2) its cost recurrenceT(n) = T(n−1) + T(n−2) + Θ(1) ⇒ T(n) ≥ Fₙ and Fₙ itself grows geometricallyFₙ = Θ(φⁿ), φ = (1 + √5)/2 ≈ 1.618 so T(n) = Ω(1.618ⁿ) ≈ Ω(2^(0.694·n))
  • The cost recurrence is the Fibonacci recurrence. T satisfies the same relation the values do, plus a constant, so T(n) ≥ Fₙ. Computing F₂₀₀ that way costs at least F₂₀₀ ≈ 2.81 × 10⁴¹ ≈ 2¹³⁷·⁷ elementary steps. A machine doing 10¹³ steps per second — far beyond a laptop — needs about 2⁹⁴·⁵ ≈ 2.8 × 10²⁸ seconds, some 60 billion times the current age of the universe.
  • Hardware cannot rescue it. Suppose machines got 1.6× faster every year — the rule of thumb of the Moore-and-Dennard era, roughly the rate single-thread performance actually improved from the 1980s to about 2005. Since the cost grows as 1.618ⁿ and 1.6 ≈ φ, a year of that progress buys you about one more Fibonacci number: log(1.6)/log(φ) = 0.98 of an index. That is the curse of exponential time stated as sharply as it can be stated, and no benchmark at n = 30 will ever reveal it. Two honest caveats: the 1.6× figure is an historical rule of thumb, not a law, and single-core performance has grown only a few percent per year since clock scaling stopped — so the real picture is worse than this bullet paints it, not better.
  • The fix is structural, not a micro-optimisation. Keeping the last two values and looping upward computes Fₙ with n − 1 additions: from exponential to linear, without touching the hardware. That reuse of already-computed subproblems is dynamic programming, in its smallest possible instance.
  • A caveat that is itself an analysis lesson. "Linear in n" here counts additions as O(1), but Fₙ has Θ(n) bits, so each addition really costs Θ(n) bit operations and the loop is Θ(n²) bit operations. Still polynomial, still exponentially better than the recursion — but it shows that what you declared to be one step silently changed the answer. That declaration is the subject of §03.
The stance this page takes. Analysis first, to choose the design and to know what to expect; measurement second, to check that the implementation obeys the analysis and to pin the constants that the analysis threw away. Measurement instead of analysis cannot see past the largest n you tested, and the interesting n is always larger than that.

03 The RAM model, and what counts as one step

Before anything can be counted, you must say what a "step" is. The standard answer is the random-access machine — the RAM model, and in its precise form, where a machine word holds Θ(log n) bits, the word RAM: one processor, instructions executed one after another with no concurrency, and each instruction from a fixed repertoire costing a constant amount of time. Every bound on this page is a bound in that model, and the model's edges are where the surprises live.

The repertoire

  • Arithmetic: add, subtract, multiply, divide, remainder, floor, ceiling — each O(1).
  • Data movement: load, store, copy — each O(1). In particular indexing an array is one step, independent of n: the address is computed as base + i·sizeof(element), which is the defining privilege of contiguous storage.
  • Control: conditional and unconditional branch, subroutine call and return — each O(1). Note the split: calling a subroutine is one step; executing it is whatever it costs.
  • Data types: integer and floating point, with a bounded word size — typically c·log n bits for a constant c ≥ 1. The lower limit c ≥ 1 is needed so a single word can hold an index into the input; the upper limit "constant c" is needed so you cannot cheat by packing the entire input into one word and operating on it in one step.

What the model deliberately excludes, and why the exclusions matter

  • No instruction may do unbounded work. A machine with a one-instruction SORT would sort in O(1), which is why the repertoire is pinned to things real processors actually have. The guide is realism, not convenience.
  • Exponentiation is a grey area. Computing x^y for real x, y takes many instructions and is not O(1). But 2ᵏ for small integer k is a left shift, one instruction — so it is treated as constant when k fits in a word, and not otherwise. Grey areas like this are to be avoided in analysis, not exploited.
  • No memory hierarchy. The model has no caches, no TLB, no virtual memory, no prefetcher. Every memory access costs the same. Real machines disagree by roughly a factor of fifty: on a current x86 core an L1 hit resolves in about 4–5 cycles, an L3 hit in about 40, and a DRAM access in the region of 200 (quoted figures range from about 100 to 400 depending on the part and the access pattern). That gap is the usual reason a linear scan of an array outruns an asymptotically identical walk of a linked list. The RAM model cannot see the difference, and §23 is about what to do when it is the difference that matters.
  • No concurrency. One processor, one instruction at a time. Parallel and distributed costs need different models entirely.
  • It nonetheless predicts real performance well enough to be worth using. That is the empirical justification for all of the above — an engineering claim, not a theorem: RAM-model analyses are, in practice, good predictors of how code scales, while being poor predictors of how long it takes. §22's doubling test is how you check the first half of that sentence on a particular implementation, and §23 catalogues the cases where even the scaling prediction comes out wrong.

Primitive operations, concretely

When analysing code rather than pseudocode, it helps to name the operations you are willing to call constant-time. A conventional list: assigning a name to an object; looking up the object a name refers to; one arithmetic operation; one comparison; one indexed access into an array; calling a function (excluding its body); returning from a function. The assumption underneath the list is that these all cost roughly the same, so the count of primitive operations is proportional to the running time. That assumption is what lets a count stand in for a clock.

the chain the whole subject rests onalgorithm → count of primitive operations f(n) → running time ≈ k·f(n) → Θ(g(n)) the assumption at the second arroweach primitive operation costs a bounded number of machine instructions ⇒ k is a constant

Choosing what to count

  • Pick the operation that dominates. For searching and sorting, count comparisons — they are what the algorithm is really doing, and everything else is bookkeeping proportional to them. For numerical and matrix work, count arithmetic operations, usually splitting them into additive (add, subtract, increment) and multiplicative (multiply, divide, modulus), because multiplications historically cost more and some algorithms are judged by trading multiplications for additions.
  • Bookkeeping is ignored on purpose. Loop-counter increments and index arithmetic are proportional to the dominant operation, so including them changes a constant factor and never the growth class.
  • Counting the wrong thing gives the wrong answer. If one "comparison" is a disk read and another is a register compare, they are not the same unit, and a bound stated in comparisons is meaningless. Declare the unit; keep it honest.
Model discipline. Every cost claim is relative to a model. "Counting sort is linear" is true in a model where you may use a key as an array index, and false in the comparison model where you may only ask "is a < b?" — and neither statement contradicts the other, because they are claims about different machines. A great many arguments about whether a bound is "really" true turn out, on inspection, to be arguments about which model is in force rather than about any mathematics.

04 Counting steps exactly: insertion sort, line by line

Asymptotic notation is a simplification, and you cannot simplify what you have not first written down exactly. So the honest starting point is a table: every line, the constant it costs, and the number of times it runs. Insertion sort is the canonical vehicle because its inner loop runs a different number of times for each outer iteration, which is exactly the feature that makes the analysis non-trivial.

insertion sort, with the line numbers the analysis refers toINSERTION-SORT(A) 1 for j = 2 to A.length 2 key = A[j] 3 // insert A[j] into the sorted sequence A[1 .. j−1] 4 i = j − 1 5 while i > 0 and A[i] > key 6 A[i+1] = A[i] 7 i = i − 1 8 A[i+1] = key

First: the loop invariant, because a cost for a wrong procedure is worthless

The proof obligation for a loop is a loop invariant — a property that holds at the top of every iteration and that, at exit, hands you the theorem you wanted. It is induction with a stopping rule: initialization is the base case, maintenance is the inductive step, and termination is where you cash in.

invariant for the for loop of lines 1–8At the start of each iteration, the subarray A[1 .. j−1] holds the elements originally in A[1 .. j−1], in sorted order.
  • Initialization. Before the first iteration j = 2, so A[1 .. 1] is a single element — trivially sorted, and trivially the element that was originally there. The invariant holds.
  • Maintenance. The body moves A[j−1], A[j−2], … one position right (lines 4–7) until it finds the slot where key belongs, then writes it there (line 8). Nothing is lost — each shifted value is written before it is overwritten — and nothing enters from outside the subarray. So A[1 .. j] now holds the original elements of A[1 .. j] in sorted order, which is the invariant with j incremented.
  • Termination. The loop exits when j > n, and since j rises by one each time, it exits with j = n + 1. Substituting into the invariant: A[1 .. n] holds the original elements in sorted order. That is the entire array, so the algorithm is correct.
  • The subtlety worth noticing. The maintenance step above is informal about the inner while; a fully formal treatment states a second invariant for lines 5–7 ("A[i+2 .. j] holds values all greater than key, in their original relative order") and proves that one too. Invariants nest exactly the way loops do.

Now the count

Let tⱼ be the number of times the while test on line 5 executes for that value of j. A loop test runs one more time than its body whenever the loop is left by the test failing — the last evaluation is the one that fails — which is the case for both loops here; a loop left by a break, a return or an exception is the exception to the rule, and then you must count the exits separately. Multiplying each line's constant by its execution count and summing gives the running time exactly, with no approximation yet:

exact running time, no simplificationT(n) = c₁·n + c₂·(n−1) + c₄·(n−1) + c₅·∑ⱼ₌₂ⁿ tⱼ + c₆·∑ⱼ₌₂ⁿ (tⱼ−1) + c₇·∑ⱼ₌₂ⁿ (tⱼ−1) + c₈·(n−1) line 1 runs n times, not n−1the test that fails and ends the loop counts too line 3 is a commentcost 0 — comments are not executable statements

Best case: an already-sorted array

If A is already sorted then A[i] ≤ key the very first time line 5 is tested, so tⱼ = 1 for every j, and lines 6–7 never run at all.

tⱼ = 1 for all jT(n) = c₁n + c₂(n−1) + c₄(n−1) + c₅(n−1) + c₈(n−1) = (c₁ + c₂ + c₄ + c₅ + c₈)·n − (c₂ + c₄ + c₅ + c₈) = a·n + b — a linear function of n, so T(n) = Θ(n)

Worst case: a reverse-sorted array

Now every element must be compared against the whole sorted prefix, so tⱼ = j. Two summation identities close the form:

the two sums needed∑ⱼ₌₂ⁿ j = n(n+1)/2 − 1 ∑ⱼ₌₂ⁿ (j−1) = n(n−1)/2 substitutingT(n) = c₁n + c₂(n−1) + c₄(n−1) + c₅·(n(n+1)/2 − 1) + (c₆ + c₇)·n(n−1)/2 + c₈(n−1) collected by power of nT(n) = (c₅/2 + c₆/2 + c₇/2)·n² + (c₁ + c₂ + c₄ + c₅/2 − c₆/2 − c₇/2 + c₈)·n − (c₂ + c₄ + c₅ + c₈) = a·n² + b·n + c — a quadratic function of n, so T(n) = Θ(n²)
  • The shape survives; the constants do not matter. Whatever the cᵢ are, the answer is some quadratic with a positive leading coefficient. Since every such quadratic is Θ(n²) (§09), the entire table of constants was scaffolding — necessary to build the result, discarded once it stands.
  • The counts are not independent. ∑(tⱼ − 1) is the number of shifts, and a shift happens exactly once per pair of elements that start out in the wrong relative order. So shifts = inversions of the input, a purely combinatorial quantity. That identity is the whole average-case analysis in embryo (§06) and it is what the figure below checks by counting inversions a second, independent way.
  • Tests are not comparisons. Line 5's test is i > 0 and A[i] > key with short-circuit evaluation, so when the loop stops because i ran off the front, no element comparison happens. The number of element comparisons is therefore ∑tⱼ minus the number of j for which key is a new minimum. Both are counted separately below, and they differ. Being sloppy about which one you mean is how off-by-n errors get into published analyses.

Why bother with the exact table at all, when the answer is going to be Θ(n²)? Because the table is where you find out which sum you are actually taking, and the sums are where the real content is. Skipping to "two nested loops, so n²" gets insertion sort right by luck and gets the next algorithm wrong — §12 has a triple-nested loop that is Θ(n²) and a single loop that is Θ(n²).

05 Best case, worst case, average case — and why worst case is quoted

An algorithm's cost is not a function of n alone; it is a function of the particular input. Fixing n still leaves a whole set of inputs, and the algorithm spends a different amount of time on each. Best, worst and average are three different ways of collapsing that set to one number, and they answer three different questions.

The three collapses

  • Best case — the minimum over inputs of size n. B(n) = min { cost(x) : |x| = n }. Usually uninteresting and often constant: the best case of a search is that the target is the first thing you look at, which is one comparison no matter how large the array. A best case is only worth quoting when it is reachable in practice — insertion sort's Θ(n) on nearly-sorted data is a genuine reason to use it as the base case inside a bigger sort.
  • Worst case — the maximum over inputs of size n. W(n) = max { cost(x) : |x| = n }. A guarantee: the algorithm will never take longer, on any input, ever.
  • Average case — the expectation over a distribution on inputs of size n. Partition the inputs into m groups that each take the same time, let pᵢ be the probability of landing in group i and tᵢ its cost.
average case, in generalA(n) = ∑ᵢ₌₁ᵐ pᵢ · tᵢ when all m groups are equally likelyA(n) = (1/m) · ∑ᵢ₌₁ᵐ tᵢ and alwaysB(n) ≤ A(n) ≤ W(n)

Three reasons the worst case is the default

  • It is a bound, not a guess. Knowing W(n) means you never have to hope. Every other summary leaves open the possibility that today's input is the bad one, and in a system with an adversary — a public API, a user-supplied regular expression, attacker-chosen hash keys — "the bad input is unlikely" is not a security property.
  • The worst case is often the common case. The worst case for a search is that the item is absent, and searching for absent items is exactly what a cache, a validator or a spell-checker spends its life doing.
  • The average is frequently no better. For insertion sort, the average number of comparisons is about half the worst case — n²/4 against n²/2 — which is a factor of two, not a change of class. Doing the harder analysis bought a constant.

What an average-case claim actually assumes

  • A distribution over inputs has to be named. "All n! permutations equally likely" is the usual choice and is frequently false — real data arrives partly sorted, partly duplicated, clustered by time. An average-case bound under an assumption your data violates is worse than no bound, because it looks like a guarantee.
  • The groups must be genuinely uniform in cost. If two inputs in the same group take different times, the group has to be split. Getting this partition right is most of the work in an average-case proof.
  • Randomization changes who is being averaged over. If the algorithm flips coins — a random pivot, a random hash seed — the expectation is over its own coin flips and holds for every input. That is a far stronger and far more defensible statement than an expectation over an assumed input distribution, and it is why randomized quicksort is trusted while "quicksort on random data" is not.
  • Expectation is not concentration. An expected cost of O(n log n) says nothing on its own about the spread. The useful randomized results come with a tail bound as well.

Cases are not the same thing as the notation

This is one of the two or three most common confusions in the subject, so it is worth stating flatly: O, Ω and Θ are about bounding functions; best, worst and average are about which function you chose to bound. They are orthogonal. You can say "insertion sort's best-case time is Θ(n)", "its worst-case time is Θ(n²)", and "its running time on any input is O(n²)" — the last one is a valid blanket statement because O bounds every case at once. What is meaningless is "the running time is at least O(n²)": O is already an upper bound, so "at least an upper bound" constrains nothing. The intended sentence is almost always Ω(n²).

06 The average case, carried all the way through

An average-case analysis computes the expected cost of an algorithm over a named probability distribution on its inputs. Done here for insertion sort under the standard assumption — every one of the n! orderings of n distinct keys equally likely — it yields a closed form for the expected number of comparisons, exactly, not to within a constant. Average-case claims are usually asserted rather than derived, which is how the folklore "insertion sort does about n²/4 comparisons" circulates without anyone saying what it is an approximation to. It is worth doing once, exactly, because the derivation is short, the exact answer is prettier than the approximation, and having a closed form means a measurement can check it.

The informal argument

When A[j] is inserted into the sorted prefix A[1 .. j−1], on average half of that prefix is smaller than it and half is larger, so the scan stops about halfway: tⱼ ≈ j/2. Summing, ∑ⱼ₌₂ⁿ j/2 ≈ n²/4. That is where the folklore number comes from, and it is right about the growth class — quadratic — which is all it was ever meant to establish.

The exact argument

Assume the input is a uniformly random permutation of n distinct keys. Two facts finish it. First, the number of shifts is the number of inversions, and each of the C(n,2) = n(n−1)/2 pairs is inverted with probability exactly 1/2, so by linearity of expectation the expected number of shifts is n(n−1)/4 — no independence needed, which is the whole charm of linearity. Second, each pass makes one extra comparison, the failing one that stops the scan, unless the scan ran off the front of the array — and it runs off the front exactly when A[j] is smaller than all of A[1 .. j−1], which for a random permutation has probability 1/j.

  • The harmonic number is the fingerprint of "probability 1/j". Hₙ = ln n + γ + O(1/n) with γ ≈ 0.5772. It shows up here, in the expected number of times a running maximum is updated, in the coupon-collector bound, and in the analysis of randomized quicksort — every time an event has probability 1/j at step j.
  • The exact form beats the folklore by a whole linear term. n(n−1)/4 + n − Hₙ exceeds n²/4 by exactly (3/4)·n − Hₙ. That term is lower-order — Θ(n) against Θ(n²), so it never dominates and the two agree asymptotically — but it is far from negligible at the sizes anyone actually sorts with insertion sort: it is 17% of the truth at n = 8, 10% at n = 20, and still 6% at n = 40, which the figure shows directly.
  • Worst / average = 2, asymptotically. [n(n−1)/2] / [n(n−1)/4] = 2. Randomising the input buys a factor of two here and nothing more — contrast quicksort, where the same move converts Θ(n²) into Θ(n log n) and therefore changes the class.

07 Asymptotic notation, formally

The three main symbols are sets of functions, each defined by an explicit quantifier pattern: there exist constants such that, beyond some threshold, an inequality holds. Everything people find slippery about big-O — why n = O(n²) is true, why "at least O(n²)" is nonsense, why the base of a logarithm is invisible — falls straight out of these three lines once you read them literally.

the three definitions, verbatimΘ(g(n)) = { f(n) : ∃ c₁ > 0, c₂ > 0, n₀ > 0 such that 0 ≤ c₁·g(n) ≤ f(n) ≤ c₂·g(n) for all n ≥ n₀ } O(g(n)) = { f(n) : ∃ c > 0, n₀ > 0 such that 0 ≤ f(n) ≤ c·g(n) for all n ≥ n₀ } Ω(g(n)) = { f(n) : ∃ c > 0, n₀ > 0 such that 0 ≤ c·g(n) ≤ f(n) for all n ≥ n₀ }

Reading the definitions out loud

  • O is an upper bound to within a constant factor. Past n₀, f never rises above some fixed multiple of g. It says nothing about how far below it might sit — which is exactly why n = O(n²) is a true statement and a useless one.
  • Ω is a lower bound to within a constant factor. Past n₀, f never drops below some fixed multiple of g.
  • Θ is both at once — f is squeezed between two multiples of the same g, so g is an asymptotically tight bound. Formally Θ(g) = O(g) ∩ Ω(g), and that intersection is a theorem, not a definition: f = Θ(g) if and only if f = O(g) and f = Ω(g).
  • The constants are existentially quantified, so any witness will do. You do not have to find the best c or the smallest n₀; you have to exhibit one pair that works. Proofs in this area are therefore constructive and usually short.
  • The leading 0 ≤ matters, and it constrains both functions. It forces f to be asymptotically non-negative — non-negative for all sufficiently large n — which is no loss, since a "running time" that goes negative is not a running time. It constrains g too, by implication: if g dipped below zero infinitely often, no f could satisfy the inequalities and the set Θ(g) would simply be empty. So the standing convention is that every function written inside one of these symbols is asymptotically non-negative.

The equals sign is an abuse of notation, and a useful one

  • Strictly, f(n) ∈ O(g(n)). Conventionally, nearly everyone writes f(n) = O(g(n)). Keep the set reading in your head: the "equation" is one-directional, so n = O(n²) is fine and O(n²) = n is not.
  • Asymptotic notation on the right-hand side of a formula means "some anonymous function in that set". So 2n² + 3n + 1 = 2n² + Θ(n) asserts that there is some h(n) ∈ Θ(n) making the two sides equal — here h(n) = 3n + 1. Chained equations are read left to right, each step introducing a new anonymous function, which is what makes 2n² + 3n + 1 = 2n² + Θ(n) = Θ(n²) legitimate.
  • On the left-hand side it means "for every function in that set". 2n² + Θ(n) = Θ(n²) claims: whatever function you pick out of Θ(n), the sum lands in Θ(n²). That asymmetry is the whole convention, and it is why the notation composes in proofs.

What the definitions buy. Portability. A Θ claim is invariant under every transformation that multiplies cost by a constant — a faster CPU, a better compiler, rewriting in C, unrolling a loop. That invariance is not a happy accident; it is precisely what the ∃c quantifier was put there to achieve.

08 Little-o, little-omega, and the comparison analogy

O and Ω allow the bound to be tight; o and ω forbid it. The change in the definition is one quantifier — ∃c becomes ∀c — and that single swap turns "no bigger than" into "strictly, eventually negligible".

little-oh: the bound holds for EVERY constanto(g(n)) = { f(n) : ∀ c > 0 ∃ n₀ > 0 such that 0 ≤ f(n) < c·g(n) for all n ≥ n₀ } little-omegaω(g(n)) = { f(n) : ∀ c > 0 ∃ n₀ > 0 such that 0 ≤ c·g(n) < f(n) for all n ≥ n₀ } equivalently, by dualityf(n) ∈ ω(g(n)) ⇔ g(n) ∈ o(f(n)) the limit characterisations (when the limit exists)f = o(g) ⇔ lim (n→∞) f(n)/g(n) = 0 f = ω(g) ⇒ lim (n→∞) f(n)/g(n) = ∞

Where the quantifier swap bites

  • 2n = O(n²) and also 2n = o(n²) — the bound is loose, and o records that it is loose.
  • 2n² = O(n²) but 2n² ≠ o(n²) — pick c = 1 and the required 2n² < n² fails for every n. In O you get to choose c after seeing f; in o an adversary chooses c and you must still satisfy it.
  • n²/2 = ω(n) but n²/2 ≠ ω(n²), by the mirror-image argument.
  • In running-time talk, o is the honest way to say "strictly better". "Sub-quadratic" means o(n²); "sub-linear" means o(n); an algorithm that is O(n²) may be quadratic, while one that is o(n²) provably is not.

The analogy with comparing numbers

The analogy is not decorative — the relational properties really do carry over. Transitivity holds for all five. Reflexivity holds for O, Ω and Θ (but not for o or ω, just as a < a is false). Symmetry holds for Θ alone. And transpose symmetry — f = O(g) ⇔ g = Ω(f), and f = o(g) ⇔ g = ω(f) — is the formal statement that upper and lower bounds are the same fact seen from either side.

Where the analogy breaks: there is no trichotomy

  • For real numbers, exactly one of a < b, a = b, a > b is true. For functions, none of the five relations need hold. Two functions can simply be incomparable.
  • The standard witness is f(n) = n against g(n) = n^(1 + sin n). The exponent oscillates forever over the whole interval [0, 2], so g is repeatedly far below n and repeatedly far above it. Neither f = O(g) nor f = Ω(g) holds, and therefore neither does Θ, o or ω.
  • Why you should care about a pathological example. It is the reason "algorithm A is not O(f), therefore it is Ω(f)" is invalid reasoning, and the reason theorems in this area carry hypotheses like "asymptotically positive" or "monotonic" — they are there to rule out exactly this. The Master theorem's case gaps (§17) are another instance of the same phenomenon.
Practical translation. O = "I promise it is no worse than". Θ = "I know exactly what class it is in". Ω = "I promise it is at least this bad", which for a problem rather than an algorithm is the strongest kind of result there is. o and ω = "strictly", used when the difference between loose and tight is the point.

Logarithms: why the base never appears in a bound

  • Change of base is multiplication by a constant. log_b n = (log_c n)/(log_c b), and 1/log_c b is a constant once b and c are fixed. So O(log₂ n) = O(log₁₀ n) = O(ln n), and writing the base inside a big-O is at best noise. Outside a big-O — in an exact count such as "the tree has log₂ n levels" — the base is essential.
  • Powers of a log are a different animal from a log of a power. logᵏ n means (log n)ᵏ; log nᵏ = k·log n = Θ(log n). The first is polylogarithmic and grows; the second is just log n with a constant in front.
  • Every polynomial beats every polylogarithm. logᵇ n = o(n^a) for all constants a > 0, b. So log¹⁰⁰ n is eventually smaller than n^0.01 — eventually being the operative word, and astronomically far out.
  • Every exponential beats every polynomial. n^b = o(aⁿ) for all constants a > 1, b. This is the formal content of the "polynomial vs exponential" line that §02's Fibonacci story dramatised.
  • Factorials sit above exponentials. By Stirling, n! = √(2πn)·(n/e)ⁿ·(1 + Θ(1/n)), from which n! = o(nⁿ), n! = ω(2ⁿ), and — the one that matters for the sorting lower bound — log(n!) = Θ(n log n).

What log(n!) is for: the decision-tree lower bound

That last identity is not decoration; it is the one place on this page where the algebra produces a statement about every possible algorithm rather than about one. The argument is called the decision-tree lower bound, and it is worth seeing once in full because the shape recurs: model the algorithm as a tree, count the leaves the tree must have, and conclude something about its height.

  • The model. A comparison sort learns about its input only by asking "is aᵢ ≤ aⱼ?". Fix n and any such algorithm, and draw its decision tree: internal nodes are comparisons, the two edges out of a node are the two answers, and a leaf is reached when the algorithm halts and outputs a permutation.
  • The leaf count. Every one of the n! input orderings needs its own leaf — two different orderings that reached the same leaf would receive the same output permutation, and at most one of those can be sorted. So the tree has at least n! reachable leaves.
  • The height. A binary tree of height h has at most 2ʰ leaves, so 2ʰ ≥ n!, i.e. h ≥ log₂(n!). The height is the worst-case number of comparisons, because the longest root-to-leaf path is the input that asks the most questions.
the boundworst-case comparisons ≥ log₂(n!) = Θ(n log n), for every comparison sort a concrete instancen = 12: 12! = 479 001 600, log₂(12!) = 28.84 ⇒ at least 29 comparisons, by any comparison sort whatsoever and the bound is not loosemergesort achieves O(n log n), so the bound is TIGHT — Θ(n log n) is the true complexity of the problem
  • The bound is about a model, not about reality. Counting sort and radix sort run in linear time and do not contradict it, because they never perform a comparison — they use a key as an index, which the decision-tree model does not permit. A lower bound is always a statement of the form "in this model, nothing does better", which is why §03's model discipline is not pedantry.
  • The distinction to keep. An upper bound is a claim about an algorithm you can exhibit; a lower bound is a claim about every algorithm, including the ones nobody has invented. That is why lower bounds are rare, hard, and the ones worth memorising. Sorting & Searching is where this one is put to work.

  • The geometric sum is the single most important identity on this page. If the work per level of a recursion falls off geometrically, the whole tree costs a constant times the root. If it grows geometrically, the whole tree costs a constant times the bottom level. If it is flat, the total is the per-level work times the number of levels.   • A bounded sum of a growing sequence is at most n times its largest term — ∑ₖ₌₁ⁿ f(k) ≤ n·f(n) for non-decreasing f. Crude, instant, and correct; often enough to settle an upper bound before you invest in the exact sum.

Three mistakes this algebra is designed to prevent

  • Summing a variable number of terms with a constant bound. "Each iteration is O(1) and there are n iterations, so O(n)" is valid. "Each iteration is O(i) where i is the loop index, so O(n)" is not — you must sum, and ∑i = Θ(n²). This is among the most common errors in loop analysis, and the one §12's figure is built to expose.
  • Cancelling asymptotics. O(n²) − O(n²) is not 0; both anonymous functions are unknown, and the difference can be anything up to Θ(n²). The notation supports adding and multiplying, not subtracting or dividing.
  • Hiding a cost inside a library call. sum(A[0:j+1]) looks like one operation and costs Θ(j). Whether an operation is primitive is a fact about the implementation, not about how short the source line is — §12's worked example turns on exactly this.

10 The growth hierarchy, in wall-clock terms

Almost every bound you will meet is one of about nine functions. Knowing their order by heart is most of practical analysis; knowing what each one means in seconds at a realistic input size is what turns the ordering into engineering judgement.

the hierarchy — each is o(·) of the next1 ≺ log log n ≺ log n ≺ log² n ≺ √n ≺ n ≺ n log n ≺ n² ≺ n³ ≺ 2ⁿ ≺ n! ≺ nⁿ the two dividing lines that mattersublinear | you cannot even read the input polynomial | exponential — tractable | not

What each class feels like

  • Θ(1) constant. The cost does not depend on n at all — array indexing, a hash lookup on average, a stack push. "Constant" does not mean "small": a constant-time operation can still be a disk seek.
  • Θ(log n) logarithmic. The signature of repeatedly discarding a constant fraction. Solve n/2ᵏ = 1 and you get k = log₂ n. Binary search, balanced-tree descent, and the height of a heap all live here. Doubling the input adds one step.
  • Θ(n) linear. You look at each item a constant number of times. This is the floor for any algorithm that must read its whole input, which makes Ω(n) a trivial lower bound for a great many problems.
  • Θ(n log n) linearithmic. "Sort it, or divide and conquer it." Provably optimal for comparison sorting, and in practice barely distinguishable from linear — at n = 10⁶ the log factor is only 20.
  • Θ(n²) quadratic. Every pair. Fine to n ≈ 10⁴, painful at 10⁵, hopeless at 10⁶. The most common accidental complexity in real code, usually from a linear operation inside a linear loop.
  • Θ(n³) cubic. Every triple — naive matrix multiplication, Floyd–Warshall. Practical only for small n, and the reason sub-cubic matrix multiplication is a celebrated research thread.
  • Θ(2ⁿ) exponential and Θ(n!) factorial. Every subset; every ordering. These are not slow algorithms, they are enumerations. At the table's rate of 10⁹ operations per second, 2ⁿ costs about a second at n = 30, 18 minutes at n = 40 and a fortnight at n = 50 — so the practical wall is somewhere around n = 40, and every further element doubles whatever you were willing to wait. n! hits the same wall much sooner: half a second at n = 12, six seconds at n = 13, twenty minutes at n = 15. Both walls move by only a handful of n for any plausible speedup, which is the point of §02.
Growth classes, and what they cost in wall-clock time the log axis is the only way to see all nine at once

The table assumes a machine executing 10⁹ primitive operations per second and simply divides the operation count by that rate; every cell is evaluated from the same function objects the curves are drawn from, so the picture and the numbers cannot drift apart. The interesting column is n = 1 000 000: logarithmic finishes in 20 nanoseconds and linear in a millisecond, n log n takes 20 ms — a twentieth of a second, faster than you can blink — n² takes 1 000 s, about a quarter of an hour, and n³ takes 10⁹ s, which is 31.7 years. Switch the axis to linear and the log-scale intuition collapses: the vertical range is then set by n!, so at n = 32 the factorial curve is the only thing visible and every other function — 2ⁿ included — lies flat on the axis. A linear axis can only ever show you one class at a time, which is why growth comparisons are drawn on a log or log-log scale.

Two ways to read the hierarchy that are worth internalising

  • How much bigger an input can you handle in the same time budget? Doubling the time budget lets a linear algorithm handle 2n, a quadratic one √2·n ≈ 1.41n, and an exponential one n + 1. Hardware progress is a multiplicative gift, and exponential algorithms convert multiplication into addition.
  • What happens when you buy a machine 256 times faster? An algorithm costing 400n microseconds goes from problem size m to 256m. One costing 2n² goes to 16m. One costing 2ⁿ goes to m + 8. The asymptotically better algorithm does not merely win; it wins by more on better hardware, which is the opposite of what intuition suggests.
The rule of thumb. Anything up to O(n log n) with a sane constant is efficient. O(n²) is a design decision you should be able to defend with an input-size bound. O(2ⁿ) is a decision to enumerate, and needs either a small n, aggressive pruning, or the approximation machinery of NP-Completeness & Approximation.

11 Constants, and where the crossover actually is

Asymptotics are a statement about the limit, and the limit may be nowhere near your data. An algorithm that is asymptotically better is better for all n past some crossover point n* — and the definitions in §07 are completely silent about where n* is. It can be 5, or it can be larger than any input that will ever exist.

The two-sided lesson

  • The constant can make an asymptotically superior algorithm useless. A running time of 10¹⁰⁰·n is honestly O(n) and honestly better than 10·n log n — for n beyond roughly 2^(10⁹⁹), a number vastly exceeding the count of atoms in the observable universe. That algorithm is a theorem, not a program. Galactic algorithms of exactly this shape exist for matrix multiplication.
  • And yet the constant almost never saves the worse class. A factor of 100 in the constant is worth a factor of 100 in n for a linear algorithm, and only a factor of 10 for a quadratic one — the ratio n²/(n log n) = n/log n grows without bound, so every finite constant is eventually overwhelmed. The question is never "does it win?" but "does it win before my largest input?".
  • The productive move is to measure n*, not to argue about it. Which is what the figure does.
Where does the O(n log n) algorithm overtake the O(n²) one? n* is located by scanning, and moves as you change the constants

At the defaults — a = 100 against b = 1, a hundredfold constant handicap — the scan puts the crossover just under n = 1 000, and the shaded region to its left is where the quadratic algorithm is genuinely the right choice. The probe table makes the same point in numbers: at n = 100 the quadratic algorithm does about a sixth of the work, and by n = 10 000 it is doing roughly seven times as much. Raise a to 500 and the crossover moves out past n = 6 000; raise b to 5 as well and it snaps back below n = 1 000. Nothing about the asymptotic classes changed in any of those moves — only n* did, which is precisely the information the classes discard.

What practitioners do about it

  • Hybrid algorithms. Production sorts run an O(n log n) method down to a small subarray and then switch to insertion sort, because below the crossover the quadratic method with its tiny constant and excellent cache behaviour is faster. The cutoff is a tuned constant, found by measurement, and the tuned values differ by a factor of three across implementations of the same idea: the GNU C++ library's introsort finishes partitions of 16 or fewer with insertion sort; a widely used Java dual-pivot quicksort uses a threshold of 47; and the Timsort family sorts its minimum runs — typically 32 to 64 elements — with binary insertion sort. That spread is itself the lesson: the crossover of this figure is real, but where it sits depends on the machine, the element type and the comparison cost, so it is measured rather than derived.
  • Known input bounds change the answer. If n ≤ 50 always, the asymptotically worse algorithm may be the correct engineering choice — simpler, less memory, fewer branches. Say so explicitly in the code, with the bound written down, so the decision does not silently rot when the input grows.
  • Do not confuse this with an excuse. "Constants matter" is true and is also the most commonly abused sentence in the subject. It justifies choosing insertion sort for n = 20. It does not justify a quadratic scan over a table that grows with your user count.
Discipline. Quote the class, then quote the crossover you measured. A bound without a crossover is a half-finished sentence, and §22's doubling test is how you finish it.

Three-way set disjointness, two ways

Given three sets of n distinct values, is there any value in all three? The obvious triple loop tests every triple: Θ(n³). The improved version tests a == b first and only enters the third loop when they match. The code still has three nested loops. But if A and B each contain distinct values, at most n of the n² pairs can satisfy a == b, so the innermost loop is entered at most n times and contributes at most n·n work. Notice what the picture separates and what it does not: the two quadratic prefix-average routines are parallel lines, offset by a constant factor of two, while the guarded and unguarded triple loops diverge, because they differ in class rather than in constant. Parallel on log-log means "same class, different constant"; converging or diverging means "different class". The readout confirms every measured count equals its closed form at n = 64.

The takeaway for reading code. Do not count indentation. Count total inner-loop iterations, and price every call by what it does rather than by how it looks. 13 Recurrences: what they are and where they come from

A recurrence is an equation that defines a function in terms of its own value on smaller inputs. A recursive algorithm's running time satisfies one automatically: the time on an input of size n is the time to split, plus the time of the recursive calls, plus the time to combine. Solving the recurrence — turning it into a closed form or an asymptotic bound — is the entire cost analysis of a recursive algorithm.

Deriving mergesort's recurrence, carefully

  • Divide. Compute the midpoint. One arithmetic operation: D(n) = Θ(1).
  • Conquer. Two subproblems, each of half the size: 2·T(n/2).
  • Combine. Merge two sorted halves into one sorted array. Each step of the merge writes exactly one element and advances one input pointer, so the merge does Θ(n) work: C(n) = Θ(n).
  • Assemble. D(n) + C(n) = Θ(1) + Θ(n) = Θ(n), giving T(n) = 2·T(n/2) + Θ(n), whose solution is Θ(n log n) — by recursion tree in §15, by Master theorem in §16, and provable by substitution in §14.

Three conventions that look like cheating and are not

  • The base case is usually omitted. Writing T(n) = 2T(n/2) + Θ(n) without saying T(1) = Θ(1) is standard, because every recurrence in this subject has a constant base case and stating it adds nothing. It matters only when you do a formal induction (§14), where the base case of the proof is a separate thing from the base case of the recurrence.
  • Floors and ceilings are dropped. The honest recurrence for mergesort is T(n) = T(floor(n/2)) + T(ceil(n/2)) + Θ(n), since n/2 need not be an integer. Replacing both by n/2 does not change the asymptotic solution — a fact that is proved once, in the proof of the Master theorem, and then used silently forever.
  • The recursion is assumed to reach the base case. Which requires the subproblem to shrink strictly, and the base case to be reachable. Both are termination obligations, and both are where real recursive bugs live.

Three methods solve these, and they are complementary: substitution (§14) proves a bound you have already guessed, recursion trees (§15) generate the guess, and the Master theorem (§16) is a lookup table for the common case. The usual workflow is tree → guess → substitution → proof, with the Master theorem short-circuiting the whole thing when it applies.

14 The substitution method

Two steps: guess the form of the solution, then prove it by induction, substituting the inductive hypothesis for the recursive terms. It is the only one of the three methods that produces an actual proof, and the only one that works on recurrences of any shape. Its weakness is that you must already have the guess.

A proof carried all the way through

Take T(n) = 2·T(floor(n/2)) + n, and guess T(n) = O(n log n). By the definition in §07 that means proving T(n) ≤ c·n·log₂ n for some constant c > 0 and all n past some threshold. Assume it holds for all positive m < n — in particular for m = floor(n/2) — and substitute:

inductive stepT(n) ≤ 2·( c·floor(n/2)·log₂(floor(n/2)) ) + n ≤ c·n·log₂(n/2) + n (drop the floor, which only shrinks both factors) = c·n·log₂ n − c·n·log₂ 2 + n = c·n·log₂ n − c·n + n ≤ c·n·log₂ n whenever c ≥ 1

The inductive step is done, and it told us how large c has to be: any c ≥ 1.

The base case is where it nearly falls over

  • Suppose the recurrence's base case is T(1) = 1. Then the claim at n = 1 reads T(1) ≤ c·1·log₂ 1 = 0, which is false. The induction has no base.
  • The repair uses the definition, not a bigger constant. Asymptotic notation only requires the bound for n ≥ n₀, and we get to choose n₀. For n > 3 the recurrence never refers to T(1) directly, so take n₀ = 2 and use n = 2 and n = 3 as the base cases of the proof. From T(1) = 1 the recurrence gives T(2) = 2·T(1) + 2 = 4 and T(3) = 2·T(1) + 3 = 5. Both are satisfied by T(2) ≤ 2c·log₂ 2 = 2c and T(3) ≤ 3c·log₂ 3 ≈ 4.75c as soon as c ≥ 2.
  • Combining the two constraints, c = 2 and n₀ = 2 is a complete witness and the proof is finished. Note the distinction that trips people: the base case of the recurrence (n = 1) and the base cases of the induction (n = 2, 3) are different objects, and you are free to move the second.

The subtlety: a hypothesis that is too weak

Consider T(n) = T(floor(n/2)) + T(ceil(n/2)) + 1. The answer is O(n). Guess T(n) ≤ c·n and substitute:

the attemptT(n) ≤ c·floor(n/2) + c·ceil(n/2) + 1 = c·n + 1 — and c·n + 1 is NOT ≤ c·n, for any c. The proof fails. the counterintuitive fix: guess something SMALLERT(n) ≤ c·n − d, with d ≥ 0 a second constant T(n) ≤ (c·floor(n/2) − d) + (c·ceil(n/2) − d) + 1 = c·n − 2d + 1 ≤ c·n − d whenever d ≥ 1
  • Why strengthening the claim makes it provable. In an induction you must use your own hypothesis on the subproblems. A weaker hypothesis gives you weaker material to work with, so it can genuinely be harder to prove a weaker bound. Here the recurrence has two recursive terms, so subtracting d once in the statement buys you 2d back in the step — a surplus of d, which absorbs the stray +1.
  • Do not respond by guessing bigger. O(n²) would go through easily and would be a weaker, correct, useless theorem. When the algebra misses by a lower-order term, subtract a lower-order term.
  • The same trick on a different recurrence. For T(n) = 4T(n/3) + n the true answer is Θ(n^(log₃ 4)), and the naive hypothesis T(n) ≤ c·n^(log₃ 4) also fails by a lower-order term; T(n) ≤ c·n^(log₃ 4) − d·n repairs it.

The pitfall: proving O(n) for something that is not

A famously seductive wrong proof for T(n) = 2T(floor(n/2)) + n: guess T(n) ≤ c·n, then write T(n) ≤ 2·c·floor(n/2) + n ≤ c·n + n = O(n) — and declare victory. It is wrong. The inductive hypothesis to be re-established is the exact statement T(n) ≤ c·n, and c·n + n is not ≤ c·n. Writing O(n) at the end of the chain hides a constant that grows by one at every level of the recursion, and n levels of that is exactly the missing log n factor. In substitution you must re-derive the hypothesis with its own constants, symbol for symbol.

Two more tools

  • Change of variables. T(n) = 2·T(√n) + log₂ n looks unlike anything. Set m = log₂ n, so √n = 2^(m/2), and define S(m) = T(2^m). The recurrence becomes S(m) = 2·S(m/2) + m — the mergesort recurrence — with solution S(m) = O(m log m). Substituting back, T(n) = O(log n · log log n).
  • Bracketing to find the guess. Prove a loose lower bound and a loose upper bound, then squeeze. For T(n) = 2T(n/2) + n, Ω(n) is immediate from the + n term and O(n²) is easy; tighten from both ends until they meet at Θ(n log n). And if the recurrence resembles one you know — T(n) = 2T(floor(n/2) + 17) + n, say — guess the same answer. The +17 cannot matter once n is large, and substitution confirms it.
When to reach for substitution. When the Master theorem does not apply — unequal splits, subtractive recurrences, a variable number of subproblems — or when you need an actual proof rather than a bound to quote. It is the general method; the other two are shortcuts.

15 The recursion-tree method

Draw the recursion as a tree: each node is one subproblem, labelled with the non-recursive work it does. Sum across each level, then sum the levels. Drawn carefully it is a proof; drawn quickly it is the fastest way to manufacture the guess that substitution then verifies.

The three quantities to write down

for T(n) = a·T(n/b) + f(n)subproblem size at depth i: n / bⁱ number of nodes at depth i: aⁱ work at depth i: aⁱ · f(n / bⁱ) the tree bottoms out when n/bⁱ = 1depth = log_b n, so there are log_b n + 1 levels number of leavesa^(log_b n) = n^(log_b a) ← the identity that makes n^(log_b a) the number to beat totalT(n) = ∑ᵢ₌₀^(log_b n − 1) aⁱ·f(n/bⁱ) + Θ(n^(log_b a))

That leaf-count identity is worth a moment: a^(log_b n) = n^(log_b a) because taking log_b of both sides gives log_b n · log_b a either way. It is why the quantity n^(log_b a) — the cost of the bottom of the tree — is the yardstick the Master theorem compares everything against.

A tree summed by hand: T(n) = 3T(n/4) + c·n²

  • Each level has 3× more nodes than the one above, and each node is 1/4 the size, so its n² work is 1/16 as large. Level i therefore costs 3ⁱ·c·(n/4ⁱ)² = (3/16)ⁱ·c·n².
  • The per-level costs form a geometric series with ratio 3/16 < 1 — decreasing fast. Bounding the finite sum by the infinite one (§09) gives ∑(3/16)ⁱ·cn² < cn²/(1 − 3/16) = (16/13)·cn².
  • The bottom level has 3^(log₄ n) = n^(log₄ 3) ≈ n^0.79 leaves, each costing Θ(1), so the leaves contribute Θ(n^0.79) — asymptotically negligible against n².
  • Conclusion: T(n) = O(n²), dominated by the root. The guess is then confirmed by substitution: assume T(m) ≤ d·m² for m < n, substitute to get T(n) ≤ 3·d·(n/4)² + cn² = (3/16)·d·n² + cn² ≤ d·n² whenever d ≥ (16/13)c.
Recursion tree for T(n) = a·T(n/b) + n^k — per-level work, summed watch which level dominates as a/b^k crosses 1

At the defaults a = 3, b = 4, k = 2 the per-level ratio is a/b^k = 3/16 = 0.1875, the bars shrink by a factor of more than five each level, and the readout reports the root alone as over 80% of the total with the leaves at a tenth of a percent: the work is top-heavy, and T(n) = Θ(f(n)). Now move the sliders and watch the ratio do all the work:

  • a = 2, b = 2, k = 1 (mergesort) gives a/b^k = 1 exactly. Every bar is the same length — each level costs n — and with log_b n + 1 levels the total is Θ(n log n). The equal-bar picture is case 2 of the Master theorem.
  • a = 4, b = 2, k = 1 gives a/b^k = 2 > 1: the bars grow downward, the bottom level swamps everything, and the total is Θ of the leaf count n^(log_b a) = n².
  • Set k = 0 with a = 1 and you get binary search: one node per level, constant work, log_b n + 1 levels, total Θ(log n).
The one thing to remember. The per-level ratio is a/b^k. Less than 1 → geometric decay → the root dominates. Equal to 1 → flat → multiply by the number of levels. Greater than 1 → geometric growth → the leaves dominate. Those three sentences are the Master theorem, and §16 adds the fine print — which, as §17 shows, is exactly where a good many real recurrences fall.

16 The Master theorem

A cookbook for the recurrence that divide-and-conquer produces — also called the master method, and you will meet both names for the same result. It answers one question — does the root, the leaves, or every level equally, dominate the tree? — by comparing f(n) against n^(log_b a), and it converts §15's three geometric outcomes into three memorisable cases. It is a sufficient condition in each case, never a necessary one: when no case applies the theorem says nothing at all, which is not the same as saying the recurrence has no solution (§17).

Master theoremLet a ≥ 1 and b > 1 be CONSTANTS, f(n) an asymptotically non-negative function, and T(n) = a·T(n/b) + f(n) (n/b read as floor(n/b) or ceil(n/b) — it makes no difference) 1. If f(n) = O(n^(log_b a − ε)) for some constant ε > 0, then T(n) = Θ(n^(log_b a)). ← the LEAVES dominate 2. If f(n) = Θ(n^(log_b a)), then T(n) = Θ(n^(log_b a) · log n). ← EVERY LEVEL costs the same 3. If f(n) = Ω(n^(log_b a + ε)) for some constant ε > 0, AND a·f(n/b) ≤ c·f(n) for some constant c < 1 and all large n, (the REGULARITY condition) then T(n) = Θ(f(n)). ← the ROOT dominates

Why n^(log_b a) is the thing to compare against

It is the number of leaves. Each level multiplies the node count by a, there are log_b n levels, so the bottom has a^(log_b n) nodes — and by the identity of §15, a^(log_b n) = n^(log_b a). So n^(log_b a) is exactly what the recursion costs if the combine step were free. The theorem asks whether the real combine cost f(n) beats that, ties with it, or loses to it.

Three cases worked with actual numbers

  • Case 1 — Strassen's matrix multiplication: T(n) = 7T(n/2) + Θ(n²). Here a = 7, b = 2, so log₂ 7 ≈ 2.807 and the yardstick is n^2.807. Is f(n) = n² polynomially smaller? Take ε = 0.8: n^(2.807 − 0.8) = n^2.007, and n² = O(n^2.007). Yes. So T(n) = Θ(n^2.807) — the recursion, not the combine, is the whole cost, and Strassen's contribution was to reduce a from 8 to 7.
  • Case 2 — mergesort: T(n) = 2T(n/2) + Θ(n). log₂ 2 = 1, the yardstick is n¹ = n, and f(n) = Θ(n) matches it exactly. So T(n) = Θ(n log n). In the tree picture every level costs n and there are log₂ n + 1 of them — the flat-bar picture from §15.
  • Case 3 — with the regularity check done properly: T(n) = 3T(n/4) + n log n. log₄ 3 ≈ 0.7925. Is n log n polynomially larger? Take ε = 0.2, so the bar is n^0.9925, and n log n ≥ n ≥ n^0.9925 for n ≥ 1. Yes. Now regularity: a·f(n/b) = 3·(n/4)·log(n/4) ≤ (3/4)·n log n = c·f(n) with c = 3/4 < 1. Satisfied. So T(n) = Θ(n log n).

What the regularity condition is for

  • It says the work really does shrink as you descend. a·f(n/b) ≤ c·f(n) with c < 1 means one level down costs a constant fraction of the level above — which is exactly what makes the per-level series geometric and therefore summable to Θ of its first term.
  • For a pure power f(n) = n^k it is automatic when case 3's polynomial condition holds: a·f(n/b) = a·(n/b)^k = (a/b^k)·f(n) exactly, so c = a/b^k, which is below 1 precisely when b^k > a, i.e. when k > log_b a. So for every pure polynomial f you will meet, regularity is free and you may check it in one line. The one-line check needs a footnote when f carries a log factor. For f(n) = n^k·log^p n with p ≥ 0, log(n/b) ≤ log n and c = a/b^k still works. For p < 0 the log factor moves the wrong way and a/b^k itself may fail at every finite n — but a·f(n/b)/f(n) → a/b^k, so any constant strictly between a/b^k and 1 is a valid c for all large n, and regularity holds anyway.
  • It can fail for pathological f. An f that oscillates — dipping low at n and spiking at n/b — can be polynomially larger than n^(log_b a) and still violate a·f(n/b) ≤ c·f(n). Then case 3 does not apply even though its first condition does, and the theorem is silent. This is the trichotomy failure of §08 reappearing in applied form.
Master-theorem case classifier — f(n) = n^k·log^p n against n^(log_b a) the last two presets are the recurrences the theorem cannot solve

At the default preset the two curves lie on top of each other — f(n) = n and n^(log₂ 2) = n are the same function — and the classifier reports case 2 with T(n) = Θ(n log n). Step the a slider up one at a time with b = 2, k = 1 held: at a = 1 the root wins (case 3, Θ(n)), at a = 2 they tie (case 2), and from a = 3 onward the leaves win (case 1, Θ(n^(log₂ a))) — the entire theorem traversed with one control. The classic-recurrence table is produced by the same classifier the sliders drive, so the two cannot disagree with each other.

Read the case label carefully — the classifier knows more than the theorem above it. The p slider puts a factor of log^p n into f, and when p ≠ 0 with k = log_b a the classifier reports "case 2 (extended — NOT the basic theorem)". That is deliberate. The three cases stated above do not cover 2T(n/2) + n log n; the standard p > −1 extension does, and the figure implements the extension. So the preset labelled gap of the basic theorem is reported as solvable, with T(n) = Θ(n log² n) — solvable by the extension, a genuine gap for the three cases. §17 derives both, and the second gap preset — p = −1, where even the extension fails — is reported as no case applies.
A decision procedure you can run in your head. Compute log_b a. Compare it with the exponent of n in f. Smaller exponent in f → leaves win, answer n^(log_b a). Equal → tie, multiply by log n. Larger → root wins, answer f(n). Only then worry about whether the gap is polynomial and whether regularity holds — which, for a pure power f(n) = n^k, it automatically does.

17 What the Master theorem cannot solve

The three cases do not tile the space of possibilities. There are gaps between them, a condition in case 3 that can fail, and whole families of recurrences that are not of the required shape at all. Knowing where the cookbook ends is as useful as knowing what is in it, because the failure mode is quietly applying a case that does not hold.

Gap 1 — smaller, but not polynomially smaller

Case 1 needs f(n) = O(n^(log_b a − ε)) for a constant ε > 0. A function can be asymptotically below n^(log_b a) and still fail that, if the gap is only logarithmic.

the standard witnessT(n) = 2·T(n/2) + n / log n the comparisonn^(log₂ 2) = n, and f(n)/n = 1/log n → 0, so f is smaller but n/log n is NOT O(n^(1−ε)) for any constant ε > 0 — 1/log n beats no power of n no case applies; the true answer, by summing the tree directlyT(n) = Θ(n · log log n)

The tree argument: every level costs 2ⁱ·(n/2ⁱ)/log(n/2ⁱ) = n/(log n − i), so the total is n·∑ᵢ₌₀^(log n − 1) 1/(log n − i) = n·H_(log n) = Θ(n log log n) — a harmonic sum in disguise, which the cookbook has no way to notice.

Gap 2 — larger, but not polynomially larger

the other standard witnessT(n) = 2·T(n/2) + n log n the comparisonn^(log₂ 2) = n, f(n)/n = log n → ∞, so f is larger but log n is NOT Ω(n^ε) for any constant ε > 0 — §09: every polynomial beats every polylog the basic theorem is silent; the standard EXTENSION covers itif f(n) = Θ(n^(log_b a) · log^p n) with p > −1, then T(n) = Θ(n^(log_b a) · log^(p+1) n) so hereT(n) = Θ(n · log² n)
  • The extension subsumes case 2, which is just p = 0. It is worth memorising in the general form, because n log n and n log² n combine steps are common.
  • It has its own boundary. At p = −1 the extension fails too — and p = −1 is precisely the n / log n case above, whose answer Θ(n log log n) is not of the form n log^q n at all. The classifier's last two presets are exactly these two frontiers.

The more general tool: Akra–Bazzi

For recurrences with several unequal splits, T(n) = ∑ᵢ₌₁ᵏ aᵢ·T(bᵢ·n) + f(n), there is a genuine generalisation. The hypotheses are worth stating rather than waving at, because they are what makes the p below exist and be unique: the aᵢ are positive constants, each bᵢ is a constant with 0 < bᵢ < 1, the argument may be perturbed by a floor, a ceil or anything else of size O(n / log² n) without changing the answer, and f must satisfy a polynomial-growth condition — informally, f(n) and f(bᵢ·n) stay within constant factors of each other, which every n^k·log^p n does and an oscillating f need not. Then find p from the balance equation and integrate:

Akra–Bazzifind p such that ∑ᵢ aᵢ·bᵢ^p = 1 then T(n) = Θ( n^p · ( 1 + ∫₁ⁿ f(u)/u^(p+1) du ) ) applied to the median-of-medians recurrence T(n) = T(n/5) + T(7n/10) + n(1/5)^p + (7/10)^p = 1 ⇒ p ≈ 0.8398 ∫₁ⁿ u / u^(p+1) du = ∫₁ⁿ u^(−p) du = (n^(1−p) − 1)/(1 − p) = Θ(n^(1−p)) T(n) = Θ( n^p · n^(1−p) ) = Θ(n) sanity check on the balance equation1/5 + 7/10 = 0.9 < 1, so the subproblems together are smaller than the whole ⇒ linear time is possible
  • Why p exists and is unique. Define g(p) = ∑ᵢ aᵢ·bᵢ^p. Since every bᵢ < 1, each term aᵢ·bᵢ^p is a strictly decreasing function of p; the sum is therefore strictly decreasing, runs to +∞ as p → −∞ and to 0 as p → +∞, and so crosses 1 exactly once. No search heuristics, no case analysis — one root, found numerically. For the median-of-medians equation, g(0) = 2 > 1 and g(1) = 0.9 < 1, so the root sits in (0, 1): it is p ≈ 0.8398.
  • The intuition behind the balance equation. ∑aᵢbᵢ = 0.9 < 1 means each level of recursion handles only 90% as much total data as the level above, so the per-level work decays geometrically and the root dominates — linear time. If the sum were exactly 1 you would get Θ(n log n), and above 1 the leaves would take over. It is the Master theorem's three cases again, in a form that tolerates unequal splits.
  • It is why median-of-medians works. Choosing the pivot costs a recursive call on n/5, and the partition leaves at most 7n/10; the two fractions must sum to less than 1 for the whole construction to be linear, and 0.9 is the margin the constant 5 buys.
Practical order of attack. Try the Master theorem; it settles most divide-and-conquer recurrences in seconds. If a gap or the wrong shape blocks it, draw the recursion tree — the tree always works, it just takes longer — and confirm the guess by substitution. Reach for Akra–Bazzi only when the splits are genuinely unequal.

18 Amortized analysis, and how it differs from the average case

Amortized analysis averages the cost of an operation over a sequence of operations, in the worst case, with no probability anywhere. It exists because multiplying "worst case per operation" by "number of operations" often gives an answer that no execution can actually achieve — the expensive operations are expensive because of work the cheap ones did not have to do, so they cannot all be expensive at once.

the definitionif every sequence of n operations costs at most T(n) in total, then the amortized cost per operation is T(n)/n the guarantee this gives∑ᵢ₌₁ⁿ (actual cost of operation i) ≤ n · (amortized cost) for EVERY sequence what it does NOT giveany bound at all on one individual operation

The motivating over-count

Take a stack supporting PUSH, POP and MULTIPOP(S, k), which pops min(k, s) items. A single MULTIPOP can cost Θ(n), so the naive bound for n operations is n operations × O(n) each = O(n²). That bound is correct and unachievable. Every item popped must first have been pushed, and there are at most n pushes in the sequence, so the total number of pops — including those inside MULTIPOP — is at most n. The whole sequence costs O(n), and the amortized cost per operation is O(1).

  • Amortized is a worst-case statement. It is not "usually cheap" — it is "provably cheap in total, no matter what an adversary asks for". That is why it is a legitimate guarantee and average case, in an adversarial setting, is not.
  • It is still a statement about a sequence. "This append is O(1) amortized" does not mean this append will be fast. It means that if you do n of them, the total is O(n).
  • Where that distinction bites. In a real-time system, a garbage collector, an audio callback, or any latency-sensitive path, the tail is what matters, and an O(1)-amortized structure with an O(n) worst-case operation will produce a visible stall exactly when it resizes. The engineering responses are to pre-size the structure, to use an incremental variant that spreads the copy over many operations, or to accept the tail and measure it.
  • The bookkeeping is fictional. Credits and potentials exist in the proof, not in the code. Nothing in a dynamic array stores a "credit" field; the accounting is a device for reasoning about a program that is unaware of it.
One sentence to keep. Average case answers "what usually happens?" and needs a distribution. Amortized answers "what does a whole run cost?" and needs none. Confusing them turns a guarantee into a hope.

19 The three methods: aggregate, accounting, potential

Three techniques, increasing in power and in setup cost, that all prove the same kind of statement. The example that shows off all three at once is a k-bit binary counter incremented n times from zero, where the cost of an increment is the number of bits it flips.

the procedure being analysedINCREMENT(A) 1 i = 0 2 while i < A.length and A[i] == 1 3 A[i] = 0 // clear a run of trailing 1s — each is a flip 4 i = i + 1 5 if i < A.length 6 A[i] = 1 // set the first 0 — one more flip the naive boundone INCREMENT flips up to k bits ⇒ n INCREMENTs cost O(n·k) — correct, and not tight

Method 1 — aggregate analysis: bound the total, then divide

  • The observation. Not every bit flips on every increment. Bit A[0] flips every time; A[1] every second time; A[2] every fourth. In general A[i] flips floor(n/2ⁱ) times.
  • The sum. A geometric series, bounded by its infinite version: total flips < n·∑ᵢ₌₀^∞ 1/2ⁱ = 2n.
  • The conclusion. n increments cost O(n), so the amortized cost is O(n)/n = O(1) — and the constant is 2, independent of k.
  • Its limitation. Aggregate analysis assigns the same amortized cost to every operation. When a structure has several operation types with genuinely different costs, that is too blunt.
the aggregate sumtotal flips = ∑ᵢ₌₀^(k−1) floor(n/2ⁱ) < n·∑ᵢ₌₀^∞ (1/2)ⁱ = 2n amortized cost = 2n/n = 2 = O(1)

Method 2 — the accounting method: charge more, bank the surplus

  • The device. Assign each operation an amortized charge that may differ from its actual cost. Overcharge stores credit on specific objects in the structure; undercharge spends credit already there.
  • The obligation. The credit balance must never go negative — equivalently ∑ĉᵢ ≥ ∑cᵢ for every prefix of every sequence. Violate that and the "amortized" total stops being an upper bound on the real total.
  • For the counter: charge 2 to set a bit from 0 to 1. One unit pays for the flip; one is left on that bit as credit. Clearing a bit back to 0 is then charged 0, paid for by the credit sitting on it. Since INCREMENT sets at most one bit, its amortized cost is at most 2. The number of 1s is never negative, so neither is the credit. Amortized O(1).
  • For the stack: charge PUSH 2, POP 0, MULTIPOP 0. Each pushed item carries a credit that pays for its own eventual pop, however that pop happens. Different operations, different amortized costs — the thing aggregate analysis cannot express.

the definitionΦ maps each state Dᵢ of the structure to a real number ĉᵢ = cᵢ + Φ(Dᵢ) − Φ(Dᵢ₋₁) — amortized = actual + change in potential summing, and telescoping∑ᵢ₌₁ⁿ ĉᵢ = ∑ᵢ₌₁ⁿ cᵢ + Φ(Dₙ) − Φ(D₀) so the amortized total bounds the actual total wheneverΦ(Dₙ) ≥ Φ(D₀); in practice one shows Φ(D₀) = 0 and Φ(Dᵢ) ≥ 0 for all i
  • The intuition. Φ is stored energy. An operation that leaves the structure in a more "loaded" state pays extra now and raises the potential; an expensive operation is paid for by the potential it releases.
  • For the counter, take Φ = bᵢ, the number of 1s. If the i-th increment clears tᵢ bits, its actual cost is at most tᵢ + 1, and the number of 1s changes by at most 1 − tᵢ. So ĉᵢ ≤ (tᵢ + 1) + (1 − tᵢ) = 2. The tᵢ cancels — which is the whole trick, and the reason the bound is independent of how long the run of trailing 1s was.
  • It handles a non-zero starting state, which the others do not. Rearranging the telescoped sum gives ∑cᵢ = ∑ĉᵢ − Φ(Dₙ) + Φ(D₀) ≤ 2n − bₙ + b₀. So a counter starting at an arbitrary value with b₀ ones still costs O(n) for n increments as long as b₀ = O(n) — a strictly stronger theorem than the aggregate argument can reach.
  • Choosing Φ is the creative step. Different potentials give different (valid) amortized costs; the right one measures exactly the "debt" the structure is carrying toward its next expensive operation. §20 constructs one from that principle rather than guessing.

The second half of that sentence is the content of "the amortized cost is independent of k"; the first half is why the naive O(n·k) bound was loose in the first place.

Which method to reach for. Aggregate when one operation type dominates and the total is easy to bound. Accounting when different operations should carry different charges and there is an obvious object to park credit on. Potential when the structure's state is what determines the coming cost, when you need a non-empty starting state, or when the other two get tangled — it is the most mechanical of the three once Φ is chosen.

20 The dynamic array, worked three ways

The case study that justifies the whole chapter, because it is under every list, vector and ArrayList you have ever used. A table stores items in a contiguous block; when it fills, a bigger block is allocated and everything is copied. A single insert can cost Θ(n). A sequence of n inserts costs Θ(n) in total.

Aggregate: the geometric series again

split the total into the cheap part and the expansions∑ᵢ₌₁ⁿ cᵢ ≤ n + ∑ⱼ₌₀^(floor(log₂ n)) 2ʲ < n + 2n = 3n soamortized cost ≤ 3n/n = 3 = O(1)

Every insert pays 1 for placing its own item — that is the n. The copies happen only at sizes 1, 2, 4, …, and those sum to less than 2n because a geometric series is dominated by its last term. The deep point: the sum of all previous doublings is smaller than the current one. Everything about amortized array growth is that sentence.

Accounting: why the charge is exactly 3

Charge each insert 3 credits. One pays to place the item now. One is banked on the item itself, to pay for moving it at the next expansion. One is banked on an item in the older half of the table, which already spent its own moving credit in the previous expansion. When the table of size m fills, it holds m/2 items that arrived before the last expansion and m/2 that arrived after; the later m/2 arrivals have deposited exactly m/2 credits on themselves and m/2 on the older items, so every one of the m items has a credit to pay for its own copy. The bank is never overdrawn, and 3 is exactly enough.

Potential: designing Φ instead of guessing it

Build the function from its requirements rather than pulling it out of the air. It must be 0 right after an expansion (nothing owed — the table is half full and has just been paid for) and must have grown to num by the time the table is full (enough stored energy to pay for copying every item). Right after an expansion num = size/2; right before the next one num = size. A linear function meeting both is immediate:

the potentialΦ(T) = 2·T.num − T.size check the two design constraintsjust after an expansion, num = size/2 ⇒ Φ = 0 ✓ just before one, num = size ⇒ Φ = num ✓ the table is always at least half full ⇒ Φ ≥ 0 ✓ no expansion: cᵢ = 1, sizeᵢ = sizeᵢ₋₁ĉᵢ = 1 + (2·numᵢ − sizeᵢ) − (2·(numᵢ−1) − sizeᵢ) = 1 + 2 = 3 expansion: cᵢ = numᵢ, sizeᵢ = 2·sizeᵢ₋₁ = 2·(numᵢ − 1)ĉᵢ = numᵢ + (2·numᵢ − 2(numᵢ−1)) − (2(numᵢ−1) − (numᵢ−1)) = numᵢ + 2 − (numᵢ − 1) = 3

Both branches give exactly 3 — the expensive case and the cheap case have the same amortized cost, which is what a well-chosen potential buys you. The numᵢ terms cancel, exactly as the tᵢ terms did for the counter.

Read the running mean carefully — it is a sawtooth, not a flat line. That also corrects the natural misreading of the readout. At n = 64 the measured amortized cost is 127/64 = 1.98, and the tempting conclusion is that the 3 of the accounting argument is simply generous. It is not: n = 64 is the most flattering place to stop, because the table has just filled exactly and no capacity is being paid for twice. Nudge the slider one step to n = 72 and the measured cost is 2.76; stop at n = 65 — one append after the expansion that copies 64 items — and it is 2.95. The bound of 3 is very nearly tight, and where you stop counting decides which impression you get. That is worth internalising as a general hazard of amortized measurement: a partial sequence is not a sequence, and an amortized figure quoted at a lucky stopping point is an advertisement, not a bound.

Now move the growth factor. Drop it to 1.1 and the spikes become frequent and small while the amortized cost climbs to about 12; raise it to 4 and it falls to about 1.33, but the table now wastes up to three quarters of its space immediately after every resize. That is the real trade-off — time ≈ g/(g−1) per append against wasted space ≈ 1 − 1/g — and the conventional choice of 2 is a point on that curve, not a law: 1.5 is common in implementations that want the allocator to be able to reuse the previously freed blocks, and at least one widely used dynamic array grows by only about 1.125 plus a small constant, trading ~9 elementary insertions per append for very low memory slack. The readout prints the g/(g−1) prediction beside the measurement. The two agree only in the limit, and the gap you see is the sawtooth again, not an error in either. At g = 1.5, n = 64 the measurement reads 3.97 against a prediction of 3 — because with that factor the capacities run 1, 2, 3, 4, 6, 9, 13, 19, 28, 42, 63, 94 and append number 64 is exactly the expansion out of capacity 63, so the run ends by paying for 63 copies it has had no appends to amortise against. Move to n = 128 and the same setting reads 3.22. One genuinely different effect is also visible at small sizes: a rule stated as a factor cannot grow a 1-slot table at all (floor(1 × 1.5) = 1), so the figure — like every real implementation — falls back on max(size + 1, floor(size·g)), which means the first few expansions add a single slot and the geometric argument has not started yet. Real containers handle this with a minimum initial capacity instead.

The potential is a sawtooth: it climbs by 2 per append, reaching num when the table is exactly full, and the expansion spends almost all of it. Precisely: at the instant the table of size m has just been reallocated to 2m and the m old items copied, Φ = 2m − 2m = 0 — which is the design constraint it was built to satisfy — and then the new item is placed in the same operation, so the value you see plotted immediately after every expansion is Φ = 2, not 0. Deletion, and the trap of shrinking at half

  • The obvious policy is wrong. Double when full, halve when the table drops below half full. Fill a table to exactly n/2, then run insert, delete, delete, insert, insert, …: each insert triggers an expansion and each pair of deletes triggers a contraction, both costing Θ(n), Θ(n) times. Total Θ(n²), amortized Θ(n) — the guarantee is destroyed.
  • The diagnosis. After an expansion the table sits exactly at the contraction threshold, so there is no slack: nothing has been "paid in" before the next resize is demanded. The structure has no hysteresis.
  • The fix. Double when full, but halve only when the table falls below one quarter full. After any resize the load factor is 1/2, so Θ(n) operations must occur before either threshold can be reached again. The load factor stays in [1/4, 1], wasted space is bounded by a constant fraction, and both insert and delete are O(1) amortized.
  • The potential generalises accordingly. Take Φ = 2·num − size when the load factor is at least 1/2, and Φ = size/2 − num when it is below — zero at load factor 1/2 in both branches, rising to num at load factor 1 and at load factor 1/4. The design principle is unchanged: potential measures distance from the comfortable state.
Where this shows up in practice. Every growable array; the hash table's rehash on load factor (see Data Structures); the two-stack queue, where each element is moved between stacks at most once; the disjoint-set forest with path compression; and the reserve/with_capacity call you make when the amortized guarantee is not good enough because the tail is what you are optimising.

21 Space complexity, including the stack you forgot

The same machinery, counting memory words instead of steps. The distinction that matters is between total space (input included) and auxiliary space (everything the algorithm allocates on top of the input) — and the item most often left out of the second is the recursion stack, which is invisible in the source and entirely real at run time.

the two quantitiesS_total(n) = input + auxiliary S_aux(n) = everything beyond the input "in place" meansS_aux(n) = O(1) — a constant number of extra words, independent of n the stack is part of S_auxstack space = (maximum recursion depth) × (size of one frame) and space is bounded by timeS(n) = O(T(n)) — a step can write only O(1) words, so you cannot use more memory than steps

Where the space goes

  • Explicit allocations. Mergesort's merge buffer is Θ(n); a DP table over two sequences is Θ(mn); a hash table's array is Θ(capacity).
  • The recursion stack. Each live call holds its parameters, locals and return address. Depth d therefore costs Θ(d) words at minimum, and it is the maximum depth ever reached, not the number of calls, that matters.
  • Hidden copies. A slice, a defensive copy, a string concatenation, an iterator that materialises its source — each can be Θ(n) in a place the source makes look free. The same trap as §12's hidden loops, in the space column.
  • Output space is usually excluded by convention. If the algorithm must produce n values, requiring Θ(n) for the answer is not interesting; say whether you are counting it.

Counting the stack by hand, at n = 8

"Depth, not node count" is the sentence everyone repeats and nobody checks. Check it on two call trees small enough to draw.

  • Mergesort on 8 elements. The call tree has 1 + 2 + 4 + 8 = 15 nodes and its height is log₂ 8 = 3. At any instant the live frames are one root-to-leaf path, so the stack holds at most 4 frames (levels 0 through 3). The merge buffer, by contrast, is Θ(n) = 8 words no matter how the recursion is scheduled — which is why the table below says the buffer, not the stack, is what dominates mergesort's auxiliary space: Θ(n) swamps Θ(log n).
  • Naive Fibonacci at n = 5. fib1(5) makes 15 calls in total — count them: the tree has 15 nodes — but the deepest chain is 5 → 4 → 3 → 2 → 1, so the stack never holds more than 5 frames. Fifteen nodes, five frames. At n = 200 that becomes Θ(φ²⁰⁰) nodes and 200 frames: the program does not run out of memory, it runs out of time. Node count is the time bound; the longest root-to-leaf path is the space bound.
  • The counter-case, so the rule is not over-learned. A breadth-first traversal has no recursion stack at all, and its queue can hold Θ(V) vertices at once — the widest level, not the deepest path. Depth-first and breadth-first trade exactly this: depth for width.

  • Quicksort's stack bound is a real engineering fix, not a nicety. Recurse on the smaller partition and loop on the larger — tail-call elimination done by hand — and the depth is O(log n) even in the worst case, because the smaller side is at most half. Without it, a sorted input gives depth n and a crash rather than a slow sort.
  • Languages differ on whether the stack is your problem. A guaranteed tail-call optimisation turns tail recursion into a loop with O(1) stack; without it, recursion depth is a hard limit set by the runtime. Trading one for the other

  • Spend space to save time. Memoization (Dynamic Programming), precomputed tables, hash indexes, prefix sums — all buy repeated queries with one-off storage.
  • Spend time to save space. Recompute instead of caching; stream instead of materialising; use the rolling-array trick that reduces a DP table from Θ(mn) to Θ(min(m, n)) when only the answer, not the reconstruction, is needed.
  • Sometimes space is time. A structure that fits in cache can be an order of magnitude faster than an asymptotically identical one that does not, which is why halving a node's size is a legitimate optimisation even though it changes nothing asymptotically. §23.
Reporting discipline. Quote both: "Θ(n log n) time, Θ(n) auxiliary space" is a complete answer; "Θ(n log n)" alone is half of one. And when you claim "in place", say whether the recursion stack is included — for most recursive algorithms, honestly, it is not O(1).

Doing it with a real clock, without fooling yourself

  • Warm up first. On a JIT runtime the first runs measure the compiler. Discard them.
  • Repeat and take the minimum or the median, not the mean. Noise from other processes is essentially one-sided — it makes a run slower, not faster — so the minimum is the best estimate of the true cost, and the median is the robust compromise. The mean is dragged around by a single scheduling hiccup.
  • Make n big enough that the timer is not the measurement. If one run takes a microsecond and the clock ticks in microseconds, you are plotting the clock.
  • Pin the input class. Sorted, reversed, random and adversarial inputs can differ by an entire growth class. Measure the case you are claiming a bound for, and say which one it was.
  • Expect the exponent to be wrong near a memory boundary. An algorithm that is Θ(n) in operations can measure as super-linear exactly where the working set outgrows a cache level, because the cost per operation jumps. That is not a failure of the doubling test; it is the test detecting something the RAM model cannot express.
  • Check the residual. Fit c·n^b, then look at T(n)/(c·n^b) across the range. If it drifts systematically, the power law is the wrong model — usually because a log factor is present.
What a doubling test can and cannot conclude. It can say "this implementation behaves like n^2.0 over the range I measured" — a strong, checkable claim. It cannot say "this algorithm is Θ(n²)", because it never saw the input that triggers the worst case and never saw n past the largest one tested. Analysis supplies the universal quantifier; measurement supplies the constant and the reality check.

23 Where asymptotics mislead

Every simplification that makes asymptotic analysis portable also makes it blind to something. The blindness is not a defect to be apologised for — it is the price of a result that survives a hardware change — but you need to know what was traded away, because in four common situations the discarded information is the thing that decides the outcome.

1. The constant, and the crossover

Covered in §11 and worth restating as a failure mode: a Θ claim tells you which algorithm wins eventually, and eventually can be past every input you will ever see. Galactic algorithms — asymptotically superior methods whose constants put the crossover beyond the size of the observable universe — are the extreme case, and the fast-matrix-multiplication literature is full of them. Quote the class; measure the crossover.

2. The memory hierarchy, which the RAM model denies exists

  • The model says every memory access costs 1. A real machine charges, in CPU cycles, roughly 4–5 for an L1 hit, ~10 for L2, ~40 for L3 and ~200 for DRAM (published figures for the last range from about 100 to 400 depending on the part, the access pattern and whether the row is already open). So a DRAM access costs on the order of 50 times an L1 hit, and two algorithms with identical operation counts can differ by more than an order of magnitude in time. Note that this is latency; a prefetchable streaming access can hide most of it, which is exactly why access pattern, not access count, is the thing that matters.
  • The canonical demonstration is traversing a matrix. Row-major order walks consecutive addresses and every cache line fetched is fully used; column-major order touches one word per line and evicts it before returning. Same Θ(n²), same instruction count, and an order of magnitude apart in wall-clock time at sizes that exceed cache.
  • It is why an array beats a linked list at equal asymptotics. A linear scan of contiguous storage prefetches perfectly; chasing pointers around the heap does not. Both are Θ(n). One is much faster.
  • The honest response is a different model. The external-memory model counts block transfers rather than operations and gets a different — and more predictive — answer for exactly these problems; cache-oblivious algorithms are designed to be good in it without knowing the block size. That is not a patch on the RAM model, it is the admission that the unit being counted has to match what is actually scarce (§03).

3. Small n, and the input you actually get

  • Asymptotics say nothing about small inputs, by construction — every statement begins "for all n ≥ n₀". If n is always 12, the analysis is not wrong, it is silent.
  • Real data is not the worst case, and is not uniform either. Log timestamps arrive nearly sorted, which is why real-world sorts detect existing runs and why insertion sort's Θ(n) best case earns its place inside them. Neither the worst-case nor the uniform-average model describes that input.
  • Branch prediction, SIMD and instruction-level parallelism all reward predictable, straight-line work. A branch-free routine doing twice the operations can beat a branchy one doing half, because a mispredicted branch costs more than the arithmetic saved.
  • Vectorised and parallel execution changes the unit again. The array-programming model wins by doing the same number of operations far more cheaply per operation — invisible to the RAM model, decisive in practice.

4. The wrong n: pseudo-polynomial bounds

0/1 knapsack, by dynamic programmingrunning time = Θ(n · W) — n items, capacity W that looks polynomial, but W is a VALUE, not a sizewriting W takes log₂ W bits, so the input size is Θ(n log W) and n · W = n · 2^(log₂ W) is EXPONENTIAL in the input size
  • The bound is honest and the adjective matters. Θ(nW) is genuinely fast when W is small, and useless when W is a 64-bit number. An algorithm polynomial in the numeric value of its input but not in its length is called pseudo-polynomial, and 0/1 knapsack remains NP-hard despite having one. (The corresponding vocabulary: a problem that is NP-hard but admits a pseudo-polynomial algorithm is called weakly NP-hard; one that stays NP-hard even when the numbers are written in unary is strongly NP-hard, and for those no pseudo-polynomial algorithm can exist unless P = NP.)
  • Put numbers on it. With n = 100 items and capacity W = 10⁹, the DP table has n·W = 10¹¹ cells — days of work and far more memory than you have. The input, meanwhile, is about 100 × 30 = 3 000 bits — about 375 bytes. A 375-byte input that takes 10¹¹ steps is the whole phenomenon in one line. Halve nothing and instead double W to 2 × 10⁹ — one extra bit of input — and the running time doubles. That is the definition of exponential in the input size.
  • The same trap in miniature, stated carefully: the naive primality test that trial-divides by every candidate up to √N costs O(√N) in the value and therefore O(2^(b/2)) in the number of bits b — exponential in the input length, which is why it is useless on a 2048-bit number. What that does not establish is that primality is hard. It is not: Miller–Rabin decides primality in polynomial time with an arbitrarily small error probability, and a deterministic polynomial-time primality test has been known since 2002, so primality lies in P. Cryptosystems of the RSA family in fact require primality testing to be easy — that is how the keys are generated. What no one knows how to do in polynomial time is factoring a composite, and it is that asymmetry — easy to certify prime, easy to multiply, apparently hard to invert — that the cryptography rests on. The units lesson survives intact; the security claim it was attached to does not follow from it.
  • The defence is §01's rule. Say what n measures before quoting a bound. Most confusion here is a units error, not a mathematical one.
How to hold both ideas at once. Asymptotic analysis is the right tool for choosing an algorithm and the wrong tool for predicting a runtime. Use it to eliminate the designs that cannot work at your scale — which it does decisively and cheaply — and then measure the survivors on the real inputs on the real machine.
