01 What algorithm analysis is

Algorithm analysis is the prediction of the resources an algorithm consumes — almost always time, sometimes space — expressed as a function of the size of its input, computed on a high-level description of the algorithm in an abstract machine model, and reported only up to constant factors. It is not benchmarking. Nothing is executed, no hardware is named, and the answer is a function, not a number.

the object being computedT(n) = the number of primitive steps the algorithm executes on the worst input of size n what is actually reportedT(n) = Θ(g(n)) for the simplest g that tracks T's rate of growth the formal content of that report∃ c₁, c₂ > 0 and n₀ > 0 such that 0 ≤ c₁·g(n) ≤ T(n) ≤ c₂·g(n) for all n ≥ n₀

The three questions, in order

  • Is it correct? An algorithm that is fast and wrong has no cost worth measuring. Correctness is proved — by a loop invariant for iteration (§04), by induction on subproblem size for recursion (§13), by an exchange argument for a greedy method, by optimal substructure for dynamic programming. It is not established by a test suite, because a test suite reports on the inputs you thought of.
  • What does it cost, as a function of n? This page.
  • Can we do better? Sometimes the answer is provably no — a lower bound such as the Ω(n log n) decision-tree bound on comparison sorting (sketched in §09, and applied throughout Sorting & Searching) is a statement about every possible algorithm in a model, not about one algorithm, and it is what tells you to stop optimising or to change the model.

Four commitments hidden in that definition

  • A function of input size, not a single number. "This sort takes 4 ms" is a fact about one input on one machine on one day. "This sort takes Θ(n²) comparisons in the worst case" is a fact about the algorithm. The first does not compose, does not extrapolate, and does not survive a hardware refresh; the second does all three.
  • Size has to be defined per problem. For sorting it is the number of elements. For multiplying two integers it is the number of bits, because that is what the work scales with — an algorithm that is linear in the value of its input is exponential in its size. For a graph it takes two numbers, |V| and |E|. State the measure before you state the bound; a great many confused complexity claims are really disagreements about n.
  • Up to constant factors, deliberately. The constants are hardware, compiler, language and mood. Discarding them is what makes the result portable — and it is also the single largest source of analysis that is technically true and practically useless, which §11 and §23 are about.
  • Worst case unless stated otherwise. A bound over all inputs of size n is a guarantee. An average needs a distribution over inputs, and that distribution is an assumption you must be prepared to defend (§05, §06).

What "resources" covers

  • Time, counted as primitive operations, is the default and occupies most of this page.
  • Space — how much memory beyond the input the procedure needs at its peak, including the recursion stack, which is the part people forget. §21.
  • Other scarce things, when they dominate: disk or network transfers in an external-memory or distributed setting, cache misses on a modern CPU, comparisons when a comparison is a human judgement, samples when data is what costs money. The machinery is identical; only the unit being counted changes.
The one-line version. Analysis replaces the question "how long did it take?" — which is a measurement — with "how does the cost grow?" — which is a property of the algorithm, provable on paper, and the only form of the question whose answer is still true next year.

The notes, in 5 parts

Analysis is a pipeline: fix a machine model and count, compress the count into a growth rate, solve the recurrences that recursive code produces, charge occasional expensive operations against cheap ones, and finally check the answer against memory and measurement. The five parts follow that pipeline in order.

Where this language gets used next in the series. Recursion, Divide & Conquer generates the recurrences §13–§17 solve. Sorting & Searching puts §09's decision-tree bound to work — the one result in this vocabulary that constrains every possible algorithm rather than one — and shows which sorts sit at it, which sit above it, and which escape it by leaving the comparison model. Dynamic Programming is the systematic version of §12's "stop recomputing what you already know", and its running time is always (number of states) × (work per transition), which is a §12 loop count. And NP-Completeness & Approximation is what happens when the analysis says the answer is exponential and no amount of cleverness changes it.
Where it goes sideways, out of this domain. The cost language is what model acceleration argues in and what the vectorised array model exploits by attacking the constant rather than the class. The recurrence machinery of §15–§16 is where the FFT's Θ(n log n) comes from. Memoized recursion reappears as value iteration and as the Viterbi algorithm. The average-vs-worst distinction of §05 is the same argument as reporting a mean instead of a tail quantile, and the "measure, do not assume" discipline of §22 is model evaluation applied to running time.
