Recursion, Divide & Conquer

A procedure that solves a problem by calling itself on a smaller instance of the same problem, and the design paradigm built on top of that trick: split the input, solve the pieces recursively, glue the answers together. Recursion is the control structure — base case, recursive case, and a measure that has to shrink. Divide and conquer is what you do with it: a family of algorithms whose cost is a recurrence, and whose speed comes from the fact that the recurrence's solution can be much smaller than the obvious loop's. Sorting in n log n, multiplying integers in n^1.585, searching a sorted array in log n, and enumerating an exponential search space while visiting only a sliver of it — all of them are this one idea, differently parameterised.

01 What recursion is

A recursive procedure is one that is defined in terms of itself: it solves an instance of a problem by invoking itself on one or more smaller instances of the same problem, and combining what comes back. Three parts are mandatory and there is no fourth. A base case — at least one input small enough to answer outright, with no recursive call. A recursive case — a rule that expresses the answer for a general input in terms of the answers for smaller ones. And progress — a guarantee that every recursive call moves strictly closer to a base case. Drop any one of the three and you do not have a slower program, you have a program that never finishes.

Why a definition that mentions itself is not circular

The obvious objection to factorial(n) = n · factorial(n − 1) is that it defines the thing using the thing. It does not, because the right-hand side never mentions factorial at the same argument — it mentions it at a strictly smaller one. The definition is therefore not circular but inductive: the value at n is pinned down by the value at n − 1, which is pinned down by the value at n − 2, and the chain is finite because n is a non-negative integer and decreases by one each step. Every legitimate recursion has this structure. The base case supplies the ground floor, the recursive case supplies the staircase, and the "progress" requirement is the promise that you are walking down the staircase rather than pacing on one step.

This is why recursion and mathematical induction are the same idea seen from two directions. Induction proves a statement about n from the statement about n − 1; recursion computes a value at n from the value at n − 1. The base case of the recursion is the base case of the induction, and — as §03 makes precise — the correctness proof of a recursive routine is always an induction whose inductive step is the recursive case, read as an implication instead of as an instruction.

What recursion is not

  • Not a performance technique. Recursion buys expressiveness, not speed. A recursive procedure whose recursion tree has the same shape as a loop's iteration sequence does exactly the same work plus a per-call overhead. The speed in this page comes from divide and conquer — the observation that solving two half-size problems can be cheaper than solving one full-size one — and that is a statement about the recurrence, not about the calling convention.
  • Not restricted to functions. A data structure is recursive when its definition refers to smaller instances of itself: a list is empty or a node followed by a list; a binary tree is empty or a root with two subtrees. Recursive algorithms feel natural on recursive data precisely because the code's case analysis mirrors the type's case analysis, which is why tree traversals are three lines recursively and a page iteratively.
  • Not always self-recursion. Mutual recursion — even(n) calls odd(n − 1) calls even(n − 1) — is recursion too. The measure that must shrink is defined over the whole group of functions, not over any one of them.
  • Not free. Each pending call occupies a frame on the call stack, so the peak depth of the recursion is a space cost the source code never mentions. §05 and §06 are about exactly that, and it is the single most commonly forgotten term in the analysis of a recursive algorithm.

The two halves of this page

Sections 01–11 are the mechanics: how a recursion terminates, how it is proved correct, how deep it goes, what that costs, what shapes it comes in, when to prefer a loop, and how to turn one into the other. Sections 12–28 are the paradigm: divide and conquer, the recurrence it generates, and the classic algorithms that instantiate it — mergesort, binary search, maximum subarray, Karatsuba, Strassen, closest pair, the fast Fourier transform — followed by backtracking and branch and bound, which are recursion over a search tree rather than over a shrinking array, and by the randomized variants where the split point is chosen by a coin flip. Sections 29 and 30 are a catalogue of the specific ways all of this goes wrong, and a one-screen summary. The recurrence mathematics is not here: it is in Algorithm Analysis, §13–§17, and this page states recurrences and cites their solutions rather than re-deriving them.

The one-line version. Recursion is "assume the smaller case is already solved, and say what you would do with it". Divide and conquer is that assumption applied to halves — which is what turns a linear scan into a logarithmic number of levels, and a quadratic loop into n log n.

31 Pitfalls

Every entry below is a specific failure this page has an argument against, ordered roughly from the ones that produce wrong answers to the ones that only produce slow ones. The wrong-answer group is first because it is the group that passes a casual test.

PitfallWhat actually happensThe fix
A base case that does not cover every size the divide step can produceCorrect at n = 1, undefined or wrong at n = 0. Survives every test whose inputs never generate an empty piece.Enumerate the sizes the split can emit — for a halving split that is 0 and 1 — and handle all of them. Prefer if n <= base over if n == base (§03).
A recursive call that does not shrink the measureInfinite recursion, then a stack overflow — often only on one input size, such as a range of exactly two. The classic is recursing on [mid, hi] rather than [mid+1, hi].Write the measure next to the call as a number that must strictly decrease, and check the smallest cases by hand (§02).
Forgetting the case that straddles the splitA fast, elegant, wrong algorithm: it returns the best answer that lies wholly inside one piece. Maximum subarray, closest pair and Karatsuba's carry are all this failure.Before writing the combine, ask what the split cuts through, and handle it explicitly (§12, §16, §20).
Initialising a running maximum to 0 rather than −∞Silently changes the problem to "…or the empty solution", which returns 0 on all-negative input. Correct-looking on every input containing a positive number.Initialise from the first element, or to −∞, and keep an all-negative case in the tests (§16, §17).
A pessimistic bound in branch and boundPrunes a subtree that contained the optimum. The search still terminates and still returns an answer — just not the best one.Prove the bound is never worse than the true best completion. A loose optimistic bound is slow; a pessimistic one is incorrect (§26).
Treating an alpha-beta result as exact outside its windowA value returned after a cutoff is only a bound. Stored in a transposition table as exact, it is later reused as the position's value, and the program misjudges positions it has already searched.Store the bound type — exact, lower or upper — with every entry, and use a bound only when it alone settles the current window (§28).
Failing to undo a mutation in backtrackingState leaks from one branch into its siblings. Produces missing solutions, spurious ones, or both, depending on the leak.Write the undo on the line immediately after the recursive call, every time — or copy the state into each child and pay for it (§23).
Caching results that depend on state the key does not captureMemoization returns a stale answer. Slower code would have been the better outcome.Memoize only functions of their arguments. If hidden state exists, put it in the key or do not cache (§11).
Computing the midpoint as (lo + hi) / 2Overflows in a fixed-width integer type for large ranges, giving a negative index. Invisible until the array is huge.lo + (hi − lo) / 2, which cannot overflow when lo ≤ hi (§15).
Confusing the node count with the depthTwo opposite mistakes: fearing a stack overflow from a bushy shallow recursion, or ignoring the Θ(n) stack of a thin deep one. The second one crashes in production.Breadth is time, depth is space. Solve the depth recurrence separately — it maximises over children where the time recurrence sums (§04, §05).
Relying on tail-call eliminationConstant-stack in one language, one compiler or one optimisation level; linear-stack and an overflow in another. The debug build fails and the release build does not.Rely on it only where the language defines it. Otherwise write the loop (§09).
Passing slices instead of index boundsEvery call copies its subarray, adding Θ(n) per level. Binary search becomes Θ(n); mergesort's constant doubles. The algorithm looks right and the complexity is wrong.Recurse on (array, lo, hi) and expose a clean wrapper that supplies the initial bounds (§03).
Treating overlapping subproblems as divide and conquerExponential time on a problem with a polynomial algorithm — naive Fibonacci, naive edit distance, naive coin change.Count the distinct subproblems. If the call tree is much larger, memoize or tabulate (§11, Dynamic Programming).
Allocating the merge buffer inside every callA constant-factor space and time cost, plus allocator pressure, plus cache pollution. The asymptotics are unchanged, which is why it goes unnoticed.Allocate once at the top and pass it down (§05, §14).
No cutoff to a simple method at small sizesMost of the invocations are leaves, so most of the overhead is spent on subproblems of size one and two.Stop recursing below a threshold and finish with insertion sort or a direct method — then tune the threshold by timing, not by counting comparisons (§22).
Quoting quicksort as Θ(n log n)It is Θ(n log n) expected, with a Θ(n²) worst case that randomization makes improbable but does not remove.Say "expected". And cap the stack with the recurse-on-the-smaller-side rule, which is a deterministic guarantee rather than a probabilistic one (§06, §29).
Assuming reversed input is the worst caseTrue for insertion sort, false for mergesort — reversed input is one of its best cases, because every merge has one run entirely above the other.Derive the worst case from the algorithm's structure rather than from analogy, and measure it (§14).
Reading the Master theorem's cases as ordinary inequalitiesRecurrences such as T(n) = 2T(n/2) + n/log n look like case 1 or 3 and are in neither: the separation must be polynomial.Check for a fixed ε > 0, and fall back to a recursion tree when there is none (§13, Algorithm Analysis, §17).
Confusing the number of pieces with the number recursed intob is how the instance is cut; a is how many pieces you solve. Binary search has b = 2 and a = 1, and calling it a = 2 predicts Θ(n).Count the recursive calls, not the pieces (§12).
Pushing children in the natural order in an explicit-stack conversionA stack reverses them, so a left-to-right traversal comes out right-to-left. Plausible output, wrong order, no error.Push children in reverse, and validate the converted version against the recursive one on small inputs — which is exactly what §10's figure does (§10).
The two habits that prevent most of this. First, write the measure and the base cases before the recursive case; the wrong-answer failures above are almost all failures of one or the other. Second, keep the obvious slow version and compare against it — exhaustive search, the recursive original, the unoptimised merge. Several of this page's figures do exactly that, and it is the cheapest correctness check available for an algorithm whose whole point is that it is not obvious.

Which paradigm is this?

  • Subproblems are disjoint pieces of the input, and the combine is cheap → divide and conquer. Write the recurrence first.
  • Subproblems overlap → dynamic programming. Count the distinct states; the running time is states × transition cost.
  • Subproblems are choices, and most of them are dead ends → backtracking. The running time is the size of the pruned tree, and it must be measured.
  • Choices plus an objective, and a cheap optimistic estimate exists → branch and bound. The bound must never be pessimistic.
  • Choices alternate between two opponents → minimax with alpha-beta. The answer is fixed by the tree; the node count is decided by move ordering.
  • The answer for a prefix extends in O(1) → a single scan. Do not recurse at all.
  • One subproblem can be proved irrelevant → the a = 1 family: binary search, quickselect, exponentiation by squaring. This is where the logarithms and the linear-time selections come from.

Numbers this page measured

  • Naive fib(n): 2·F(n+1) − 1 invocations, height n, only n + 1 distinct subproblems. At n = 20, 21,891 invocations against 39 for the memoized version.
  • Mergesort at n = 8: 17 comparisons and 24 element moves on the worked input, 12 on both sorted and reverse-sorted input; the exact worst case n·ceil(log₂n) − 2^ceil(log₂n) + 1 is 17 at n = 8 and 49 at n = 16. Over all 40,320 permutations of eight distinct keys the count is 16 most often (38.1%), 17 a quarter of the time (25.4%), and never outside 12…17.
  • Maximum subarray: divide and conquer, exhaustive search and the linear scan all return A[7..10] with sum 43 on the sixteen-value example; the recursion's crossing scans make n inspections per level.
  • Karatsuba: 9 single-digit multiplications against schoolbook's 16 on 1234 × 5678; measured exponents 1.585 and 2.000 at 128 digits.
  • Strassen at a cutoff of 8: total scalar operations first favour it at n = 16 (7,872 against 7,936); at n = 64, 436,416 against 520,192. With no cutoff it loses on total operations throughout the measured range.
  • n-queens at n = 8: 2,057 nodes explored, 13,664 squares pruned, 92 solutions, against 8⁸ = 16,777,216 unpruned row assignments.
  • Randomized quicksort: measured mean comparisons track 2(n+1)Hₙ − 4n to within a couple of percent at the default 40 runs per size — the largest gap over the seven sizes is about 2.5%, and it shrinks as the runs-per-size slider is raised, which is what sampling error is supposed to do. Quickselect for the median measures about 3.4n at n = 1000, inside the 4n bound and close to the known 2(1 + ln 2)·n ≈ 3.39n.
