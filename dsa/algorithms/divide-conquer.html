Recursion, Divide & Conquer

A procedure that solves a problem by calling itself on a smaller instance of the same problem, and the design paradigm built on top of that trick: split the input, solve the pieces recursively, glue the answers together. Recursion is the control structure — base case, recursive case, and a measure that has to shrink. Divide and conquer is what you do with it: a family of algorithms whose cost is a recurrence, and whose speed comes from the fact that the recurrence's solution can be much smaller than the obvious loop's. Sorting in n log n, multiplying integers in n^1.585, searching a sorted array in log n, and enumerating an exponential search space while visiting only a sliver of it — all of them are this one idea, differently parameterised.

01 What recursion is

A recursive procedure is one that is defined in terms of itself: it solves an instance of a problem by invoking itself on one or more smaller instances of the same problem, and combining what comes back. Three parts are mandatory and there is no fourth. A base case — at least one input small enough to answer outright, with no recursive call. A recursive case — a rule that expresses the answer for a general input in terms of the answers for smaller ones. And progress — a guarantee that every recursive call moves strictly closer to a base case. Drop any one of the three and you do not have a slower program, you have a program that never finishes.

the shape, as a definitionf(x) = base(x) if x is small enough f(x) = combine( f(x₁), …, f(x_k) ) otherwise, with every xᵢ < x the shape, as codesolve(x): if is_base(x): return answer_for(x) ← no call here, ever pieces = split(x) ← every piece strictly smaller return combine([ solve(p) for p in pieces ]) the canonical one-linerfactorial(n) = 1 if n = 0 factorial(n) = n · factorial(n − 1) if n ≥ 1

Why a definition that mentions itself is not circular

The obvious objection to factorial(n) = n · factorial(n − 1) is that it defines the thing using the thing. It does not, because the right-hand side never mentions factorial at the same argument — it mentions it at a strictly smaller one. The definition is therefore not circular but inductive: the value at n is pinned down by the value at n − 1, which is pinned down by the value at n − 2, and the chain is finite because n is a non-negative integer and decreases by one each step. Every legitimate recursion has this structure. The base case supplies the ground floor, the recursive case supplies the staircase, and the "progress" requirement is the promise that you are walking down the staircase rather than pacing on one step.

This is why recursion and mathematical induction are the same idea seen from two directions. Induction proves a statement about n from the statement about n − 1; recursion computes a value at n from the value at n − 1. The base case of the recursion is the base case of the induction, and — as §03 makes precise — the correctness proof of a recursive routine is always an induction whose inductive step is the recursive case, read as an implication instead of as an instruction.

What recursion is not

  • Not a performance technique. Recursion buys expressiveness, not speed. A recursive procedure whose recursion tree has the same shape as a loop's iteration sequence does exactly the same work plus a per-call overhead. The speed in this page comes from divide and conquer — the observation that solving two half-size problems can be cheaper than solving one full-size one — and that is a statement about the recurrence, not about the calling convention.
  • Not restricted to functions. A data structure is recursive when its definition refers to smaller instances of itself: a list is empty or a node followed by a list; a binary tree is empty or a root with two subtrees. Recursive algorithms feel natural on recursive data precisely because the code's case analysis mirrors the type's case analysis, which is why tree traversals are three lines recursively and a page iteratively.
  • Not always self-recursion. Mutual recursion — even(n) calls odd(n − 1) calls even(n − 1) — is recursion too. The measure that must shrink is defined over the whole group of functions, not over any one of them.
  • Not free. Each pending call occupies a frame on the call stack, so the peak depth of the recursion is a space cost the source code never mentions. §05 and §06 are about exactly that, and it is the single most commonly forgotten term in the analysis of a recursive algorithm.

02 Why a recursion terminates: the well-founded measure

"Every call is on a smaller input" is the informal version. The formal version — and the one that catches real bugs — is: exhibit a function from the arguments to a well-founded set, show it strictly decreases at every recursive call, and show that below some threshold the base case fires. A set is well-founded when it has no infinite strictly decreasing chain; the non-negative integers are the standard choice, which is why the measure is almost always "some non-negative integer derived from the arguments".

the obligation, stated onceμ : arguments → ℕ such that for every recursive call solve(x) → solve(x′): μ(x′) < μ(x) strictly, every time and μ(x) ≤ B ⇒ x is handled by a base case four worked measuresfactorial(n) μ = n decreases by 1, base at n = 0 binary_search(A, lo, hi) μ = hi − lo + 1 at least halves, base at μ ≤ 0 mergesort(A, lo, hi) μ = hi − lo + 1 halves, base at μ ≤ 1 gcd(a, b) μ = b b → a mod b < b, base at b = 0 ← NOT a, and NOT a + b; see below why "strictly" is the whole rulea chain μ(x₀) > μ(x₁) > μ(x₂) > … in ℕ has length ≤ μ(x₀) + 1 ⇒ the recursion depth is bounded by μ(x₀) + 1, so it must stop

That last line is worth reading twice, because it is doing double duty. It proves termination — an infinite descent in ℕ is impossible — and it simultaneously bounds the recursion depth, which §05 turns into the space cost. The measure you write to prove the thing halts is usually the same measure you differentiate to get the depth.

The three ways progress fails, in increasing order of sneakiness

  • No base case at all. f(n): return f(n) is the degenerate example and nobody writes it deliberately, but its realistic cousin is a base case guarding a condition that the recursive case can step over — if n == 0: return 1 paired with return n · f(n − 2), which terminates for even n and recurses forever through the negatives for odd n. The base case must be a net the descent cannot slip through, which usually means writing if n <= 0 rather than if n == 0.
  • A call that does not shrink the measure. The classic is an off-by-one in a range-halving recursion. In binary search over [lo, hi] with mid = floor((lo + hi) / 2), the right recursive call must be on [mid + 1, hi]. Write [mid, hi] instead and consider lo = 3, hi = 4: mid = 3, and the "smaller" call is on [3, 4] — the identical range, forever. The measure hi − lo + 1 went from 2 to 2. It never decreased, so there was never a proof, and the bug is invisible on every input that happens to terminate earlier.
  • A measure that decreases but has no floor. Recursing on a float that you halve each time never reaches zero in exact arithmetic (and in floating point it reaches a denormal and then zero, which is termination by accident rather than by design). ℕ is well-founded; the non-negative reals under > are not.

When the measure is not just "n"

Sometimes no single argument shrinks, and the measure has to be built. Three standard constructions cover nearly everything. A sum: merge(A, B) recurses on merge(A′, B) or on merge(A, B′) depending on which front element is smaller, so neither list shrinks on every call — but |A| + |B| drops by exactly one every time, and that sum is the measure. A different argument from the obvious one: the Euclidean algorithm's gcd(a, b) → gcd(b, a mod b) is the cautionary case. The first argument does not shrink — if a < b then a mod b = a, the call is gcd(b, a), and the first argument has gone up. Nor does the sum: a + b becomes b + a, which is the same number, so a + b is non-increasing but not strictly decreasing and is therefore not a valid measure. The measure that does work is the second argument on its own: it goes from b to a mod b, and a mod b < b holds for every b > 0 — including the very first call — so μ = b strictly decreases at every step and the base case b = 0 is reached. The lesson is the general one: the plausible measure and the correct one are often different, and only the one you can actually prove strictly decreases counts. A lexicographic pair: the Ackermann function A(m, n) recurses on A(m − 1, …) and on A(m, n − 1), so neither argument alone shrinks, but the pair (m, n) decreases in the lexicographic order on ℕ×ℕ, which is well-founded. Remaining choices: in a backtracking search (§23) the natural measure is the number of unassigned variables, which drops by one at every level regardless of what the search does with the values — which is why a backtracking recursion always terminates even though its cost may be astronomical.

Practical habit. Write the measure in a comment next to the recursive call, as a number that must go down. Two minutes of that catches the [mid, hi] bug, the n == 0-versus-n <= 0 bug, and the "I recursed on the same list I was handed" bug — which between them account for most of the infinite recursions anyone actually ships.

03 Proving a recursion correct: induction on subproblem size

Iterative code is proved with a loop invariant — a property true before the loop, preserved by each pass, and strong enough at exit (Algorithm Analysis, §04). Recursive code is proved with strong induction on the measure: assume the recursive calls return correct answers for every smaller input, and show that the combine step then produces the correct answer for this one. The assumption is called the inductive hypothesis, and the discipline of the method is that you are allowed to assume it without thinking about how the smaller call works — which is exactly the mental leverage recursion provides.

the proof obligation, in three linesBASE for every x with μ(x) ≤ B, the base case returns the right answer STEP assume solve(x′) is correct for every x′ with μ(x′) < μ(x); show combine(solve(x₁), …, solve(x_k)) is correct for x CONCLUDE by strong induction on μ, solve is correct for every input the three places a proof actually breaks1. a base case that is right for n = 1 but wrong for n = 0 (the empty input) 2. a combine step that is right only when the pieces are non-empty 3. pieces that do not cover the original problem — a case that falls between them

Worked: mergesort, in four sentences

Base. A subarray of length 1 is sorted, trivially and by definition; a subarray of length 0 is also sorted, which matters because a careless split can hand you one. Step. Assume both recursive calls return sorted permutations of their halves. merge repeatedly takes the smaller of the two front elements, so it outputs a non-decreasing sequence, and it outputs every element exactly once, so it outputs a permutation — hence the result is a sorted permutation of the concatenation of the halves, which is the original subarray. Conclude. By induction on the subarray length, mergesort sorts. Notice that the only real work was proving merge correct, and merge is a loop — so it gets a loop invariant of its own ("the output holds the smallest k elements of the two inputs, in order, and the two cursors point at the smallest unconsumed element of each half"). This layering is typical: induction on the outside, invariant on the inside.

Why the empty case is where the bodies are buried

Failure shape number one in recursive code is a base case that is correct at n = 1 and wrong at n = 0, because the recursive case never happens to produce an empty piece on the inputs anyone tested. Maximum subarray (§16) is a sharp example: the problem is defined over non-empty subarrays, so "the maximum subarray sum of an empty array" is not zero, it is undefined — and an implementation that returns 0 for the empty case silently returns 0 on an all-negative array, which is wrong, because the true answer is the largest single element. Similarly, a recursive maximum over A[lo..hi] with base case lo == hi is correct; the same routine with base case lo > hi returning −∞ is also correct; and a routine that reaches lo > hi while believing its base case is lo == hi runs off the end. Enumerate the sizes your recursive case can produce, and make sure the base case covers all of them. For a halving split of a length-2 array that is sizes 1 and 1; for a halving split of a length-1 array under a careless mid it can be 0 and 1, and the 0 is the one that bites.

Strong induction, not ordinary induction

The hypothesis has to be "correct for all smaller inputs", not "correct for the input one smaller", because divide and conquer recurses on inputs of size n/2, not n − 1. Strong induction over a well-founded measure covers both and costs nothing extra — the principle is the same one that makes §02's descent argument work. In practice this means: state the hypothesis over the measure, never over the literal argument, and the proof survives a change of split.

The habit that makes recursion easy. Do not trace the recursion. Tracing is for debugging, not for design. Write down what the function promises for an arbitrary input, assume the promise holds for the smaller calls, and check that the combine step keeps the promise. If you cannot state the promise in one sentence, the subproblem is wrong — and there are two standard repairs. Strengthen it, returning more information than was asked for: that is what §17 does to make maximum subarray linear, and what a Fibonacci routine that returns the pair (F(n−1), F(n)) does to make Fibonacci linear. Or cache it, which is §11's memoization — a different fix for a different disease, and §11 says which is which.

04 The call tree, and the two numbers it holds

Every execution of a recursive procedure has a call tree: one node per invocation, with an edge from each call to the calls it makes. It is the single most useful picture in this subject because two different costs live in the same drawing. The number of nodes is the time cost — every call does at least constant non-recursive work. The height is the space cost — the deepest chain of simultaneously-live calls, which is the peak of the call stack. They are wildly different numbers for the same routine, and confusing them produces two opposite mistakes.

Deriving the call count, and checking it

Let C(n) be the number of invocations made by one top-level call to fib(n), counting that call itself. Then C(0) = C(1) = 1 and C(n) = 1 + C(n−1) + C(n−2). Guess C(n) = 2·F(n+1) − 1 and verify by induction: the base cases give 2·F(1) − 1 = 1 and 2·F(2) − 1 = 1, both correct; and the step gives 1 + (2F(n) − 1) + (2F(n−1) − 1) = 2(F(n) + F(n−1)) − 1 = 2·F(n+1) − 1. Running the sequence out by hand — C(2) = 3, C(3) = 5, C(4) = 9, C(5) = 15, C(6) = 25, C(7) = 41, C(8) = 67 — matches 2F(n+1) − 1 at every index. That gap is the inefficiency — the tree is broad because the same subproblem is recomputed in many places, and the table underneath reports how many times each argument was re-entered.

The two mistakes this picture prevents

  • "It branches twice, so it will blow the stack." No: branching costs time, not stack. Only one branch is live at a time — the left call completes and its frames are popped before the right call is made — so the stack holds one root-to-node path, never the whole tree. fib(40) makes 2·F(41) − 1 = 331,160,281 calls and never exceeds 40 frames.
  • "It is only linear recursion, so it is cheap." Also no: a single-call recursion of depth n is Θ(n) stack, and on an input of ten million elements that is ten million live frames, which no default thread stack survives. A recursive traversal of a linked list is the standard casualty.
  • The general rule. Breadth is time; depth is space. A shallow, bushy recursion is a time problem you fix with memoization (§11) or a better recurrence. A deep, thin recursion is a space problem you fix with tail-call elimination (§09) or an explicit stack (§10). They are different diseases with different cures.

05 Recursion depth, and the space nobody budgeted for

The auxiliary space of a recursive algorithm is peak call-stack depth × frame size, plus whatever each frame allocates on the heap. The source code never writes this down — there is no allocate anywhere in mergesort — which is precisely why it gets omitted from the analysis. Compute the depth as a recurrence of its own, exactly the way you compute the time, and the space bound falls out.

the depth recurrenceD(n) = 1 + max over the recursive calls of D(size of that call) … because only ONE child is live at a time, so the depths do not add the time recurrence, for contrastT(n) = ∑ over the recursive calls of T(size of that call) + f(n) … because ALL children run, so the times DO add the space bound it givesauxiliary space = D(n) · (frame size) + (per-frame heap allocations, summed over live frames)

The contrast between those first two lines is the whole section. Time sums over children because every child eventually runs; space maximises over children because the first child's frames are gone by the time the second child's are pushed. A binary recursion therefore has exponential time and linear depth; a halving recursion has linear time and logarithmic depth. The depth recurrence is almost always trivial to solve — D(n) = D(n − 1) + 1 gives n, D(n) = D(n/2) + 1 gives log₂ n — which is a mercy, because the time recurrence usually is not (Algorithm Analysis, §13–§17).

Read them together: binary sum and naive Fibonacci both branch twice per call, yet binary sum's depth is logarithmic and Fibonacci's is linear, because the branching factor tells you nothing about the depth — the rate at which the measure shrinks does. Halving gives log n levels; subtracting one gives n levels. And binary search, which also halves, has a depth in the same class as binary sum — floor(log₂ n) + 2 against ceil(log₂ n) + 1, which the table shows as 7 against 6 at the default n = 32 and as equal at, say, n = 48 — while making a logarithmic rather than a linear number of calls, because it discards one half instead of recursing into it. The one-frame gap is not a deep fact: it is the empty-range call at the very bottom of the half-open binary search, and it disappears if you make the base case hi − lo == 1.

The catch: linear sum and binary sum cost the same time and different space

Both add n numbers and both make Θ(n) calls — binary sum makes exactly 2n − 1 of them for every n ≥ 1, which the table reports and which is the node count of a binary tree with n leaves in which every internal node has two children. So on time they are equivalent. On space they are not: linear sum holds n + 1 frames at its peak, binary sum holds about log₂ n + 1. For n = 10⁷ that is the difference between 10⁷ + 1 live frames and ceil(log₂ 10⁷) + 1 = 25. Same asymptotic time, exponentially different space — and if you only ever wrote down the time recurrence you would never see it.

Heap allocation inside frames adds up differently again

Mergesort's merge needs a scratch buffer. If the buffer is allocated inside each call, then the live frames at depth d hold buffers of sizes n, n/2, n/4, …, summing to under 2n — so the peak auxiliary space is Θ(n), not Θ(n log n), because the sibling's buffer is already freed when yours is allocated. This is the same "maximise, do not sum" logic as the depth recurrence, applied to the heap. Allocate one buffer of size n once at the top and pass it down, and the constant drops from something like 2 to exactly 1, which is one of the few micro-optimisations in sorting that is worth the trouble. (Algorithm Analysis, §21, sets out the general accounting.)

Report both numbers, always. "Mergesort is Θ(n log n)" is half an answer. The full one is Θ(n log n) time, Θ(n) auxiliary space for the merge buffer, and Θ(log n) stack depth. Quicksort's full answer is Θ(n log n) expected time, O(1) auxiliary — and Θ(n) stack in the worst case unless you recurse on the smaller side first, which caps it at O(log n). That last clause is an algorithmic decision that costs one line and changes the space class.

06 Depth limits, and what actually happens when you exceed them

A thread's call stack is a fixed, contiguous reservation made when the thread is created, not a growable heap allocation. When the recursion pushes past it, the program does not slow down — it fails, and how it fails depends on whether the runtime guards the boundary itself or leaves it to the hardware. Knowing which is the difference between a clean exception and a segmentation fault with no useful message.

the budgetmaximum depth ≈ (stack reservation) / (bytes per frame) an order-of-magnitude sum, with the assumption stated8 MiB reservation ÷ 64 bytes per frame ≈ 131,000 frames 8 MiB reservation ÷ 256 bytes per frame ≈ 32,700 frames so the classes behave completely differentlydepth Θ(log n): n = 10¹⁸ needs ≈ 60 frames → never a problem depth Θ(√n): n = 10⁹ needs ≈ 31,600 frames → marginal depth Θ(n): n = 10⁷ needs 10,000,000 frames → guaranteed overflow

Treat those byte counts as the arithmetic they are, not as measurements: frame size depends on the number of parameters and locals, on whether the compiler keeps a frame pointer, on register spilling, and on optimisation level, and it varies by a large factor across routines on the same machine. The reservation itself is a per-platform, per-thread configuration — commonly a few megabytes for a process's initial thread, and frequently much smaller for threads created by a thread library, which is why a recursion that works in main can overflow in a worker pool. Check the actual value on your platform rather than trusting a number from a page; the shell on a typical Unix reports it as a stack-size resource limit, and thread APIs let it be set explicitly at thread creation.

Two different failure mechanisms, and they look nothing alike

  • A language-level depth counter. Some runtimes count nested calls and raise a catchable error at a configurable limit — a limit set deliberately low (often around a thousand) so that the error fires while the real stack still has room, turning an unrecoverable crash into an exception with a traceback. The important and frequently-missed consequence: raising that limit does not enlarge the stack. It removes the guard rail. Push it far enough and the next failure is the hardware one below, with none of the diagnostics.
  • A guard page fault. With no language-level counter, the stack is bounded by an unmapped page placed immediately past the reservation. Touching it traps, and the process receives a fault. Some runtimes catch that fault and convert it into an error object; others simply die. Either way, the failure happens at whatever call happened to cross the line, which may be nowhere near the recursion that was actually too deep — so the stack trace points at the victim rather than the culprit.

The four honest fixes, in the order to try them

  1. Make the recursion shallower. Recursing on halves instead of on n − 1 takes the depth from n to log₂ n and ends the conversation. Where the algorithm allows it — sums, maxima, reductions, tree builds — this is not a workaround, it is a better algorithm, and §05's figure is the evidence.
  2. Recurse on the smaller piece, loop on the larger. If a routine makes two calls and then returns, convert the second into a loop (§09) and make the recursive one the smaller side. The live depth is then bounded by log₂ n because each surviving frame corresponds to at least halving the remaining size. Quicksort's O(log n) stack guarantee is exactly this, and it is the standard way an in-place divide-and-conquer sort becomes safe on adversarial input.
  3. Convert to an explicit stack (§10). The state then lives on the heap, which is far larger and growable, and you push only the few values you actually need rather than a whole frame. This is what iterative depth-first search is.
  4. Enlarge the stack — last, because it is a constant-factor fix to a growth-rate problem. Doubling the reservation doubles the n a linear-depth recursion survives, which buys one factor of two and then you are back.
Rule of thumb worth memorising. A recursion whose depth is O(log n) is safe for any n that fits in memory — a logarithm of anything addressable is under a hundred. A recursion whose depth is Θ(n) is safe only while n is small and bounded by something you control, and "the input is a user-supplied list" is not that. The dangerous middle case is Θ(n) depth in the worst case only — an unbalanced binary search tree, quicksort on sorted input — which works in every test and fails on the one adversarial input in production.

07 Three shapes: linear, binary, multiple recursion

Classify a recursion by how many recursive calls a single activation can make. At most one is linear recursion; at most two is binary recursion; more than two is multiple recursion. The classification is not cosmetic — it fixes the branching factor of the call tree, which together with how fast the measure shrinks determines the entire time cost, while the depth is determined by the shrink rate alone.

Linear recursion is a loop wearing a hat

A linear recursion visits a sequence of states, one per level, and does constant work at each — which is precisely what a while loop does. So the only real differences are the per-call overhead and the Θ(depth) stack, both of which favour the loop. Linear recursion earns its keep when the state is awkward to carry explicitly, or when the work happens on the way back up. That last case is the interesting one: reverse_print(list) recurses to the end and prints on return, producing the reversed order for free, and the only iterative equivalent is to push everything onto a stack first — that is, to rebuild the call stack by hand. When you need the return path, recursion is not syntactic sugar, it is the data structure.

Binary recursion splits either the work or the case analysis

Two distinct things wear the same shape. In divide and conquer (§12 onward) the two calls are on disjoint halves of the input, so the sizes add up to n and the tree has log₂ n levels. In case analysis — Towers of Hanoi, naive Fibonacci, a binary-tree traversal — the two calls are on subproblems that are only one step smaller, so the tree has n levels and 2ⁿ-ish nodes. Identical code shape, completely different cost, and telling them apart is just asking what the measure does: halved, or decremented?

Towers of Hanoi — a binary recursion whose measure decrements, stepped one move at a time moves and invocations are counted by the instrumented routine, not asserted

The rule is the familiar one — move n disks from the source peg to the target peg, one at a time, never placing a larger disk on a smaller one. The recursion is three lines and needs no cleverness: move the top n − 1 to the spare peg, move disk n, move the n − 1 back on top of it. Its cost follows immediately.

Multiple recursion is where the fan-out is data, not syntax

A directory walk calls itself once per subdirectory, so the branching factor is whatever the file system says. A permutation enumerator calls itself once per remaining element, so the branching factor shrinks by one per level and the node count is ∑ n!/(n−k)! (§25). A puzzle solver calls itself once per legal move. In all of these the call tree is a search tree rather than a divide-and-conquer tree: the children are not pieces of the input but choices, and the payoff comes from not having to explore all of them (§23, §26). Multiple recursion is also where the depth analysis is easiest and the time analysis is hardest — depth is the number of decisions, which is usually obvious; the node count depends on how much the pruning removes, which usually is not.

Two independent knobs. Branching factor a and shrink rule together give the cost: a calls on inputs of size n/b give n^(log_b a) leaves; a calls on inputs of size n − 1 give aⁿ leaves. That is the difference between Θ(n) and Θ(2ⁿ) for the same "two calls per activation", and it is the single most useful thing to check first when you meet an unfamiliar recursion.

08 Recursion versus iteration, honestly

Anything computable by one is computable by the other — that is a theorem, not an opinion, and §10 gives the mechanical construction. So the choice is never about power. It is about which one makes the invariant visible, and about a measurable constant-factor and space cost that recursion pays and iteration does not.

The constant factor is real, and it is a constant factor

A call costs more than a jump: arguments have to be placed where the callee expects them, the return address recorded, a frame established, callee-saved registers preserved, and all of it undone on return. How much more is a property of the platform, the calling convention and the optimiser — it varies by an order of magnitude between a small leaf function in a compiled language with the call inlined away, and a dynamically-dispatched call in an interpreter that allocates a frame object per invocation. No number here would survive the machine it was measured on, so none is given. What is portable is the shape of the conclusion: recursion multiplies the running time by a constant and adds Θ(depth) space, and therefore cannot change the complexity class. If a recursive formulation is asymptotically better than the iterative one you had, that is because the algorithm is better, not because it recurses.

Where recursion is genuinely the better engineering choice

  • The data is recursive. Traversing a tree iteratively means maintaining an explicit stack, which is the call stack rewritten by hand with more opportunities for error. Three-line recursive traversals are correct by inspection.
  • The work happens on the way back. Post-order computations — a subtree's height, a directory's total size, an expression's value — need the children's answers before the parent's, and the return path delivers them in exactly the right order for free.
  • The case analysis branches. Backtracking (§23) needs to undo a choice and try the next one. In recursive form "undo" is just returning; the state was in the frame and disappears. Iteratively, undo is code you write and get wrong.
  • The recursion is shallow. O(log n) depth means at most a few dozen frames for any realistic n, so the space objection evaporates and only the constant factor remains.

Where iteration wins outright

  • Linear depth on unbounded input. A recursion over a list of user-supplied length is a latent crash (§06). Rewrite it as a loop.
  • The recursion is tail-recursive and the language does not promise to eliminate it (§09). You get all the cost and none of the benefit.
  • The hot inner loop. When a routine runs billions of times, a constant factor is the whole budget — which is where the divide-and-conquer sorts switch to insertion sort at small sizes (§22), a decision that is entirely about constants.
The rule that settles most cases. Ask what the depth is. O(log n): write it recursively and stop worrying. Θ(n) on input you control and know is small: recursion is fine. Θ(n) on input you do not control: iterate, or use an explicit stack. Then ask whether subproblems repeat — if they do, no amount of choosing between loops and calls will help, and §11 is the actual fix.

09 Tail recursion, and which languages actually eliminate it

A call is in tail position when its result is returned immediately, with no further computation in the caller afterwards. A recursion is tail-recursive when every recursive call is in tail position. The significance is a fact about frames: if nothing in the caller's frame will ever be read again, the callee can reuse that frame instead of pushing a new one — turning Θ(depth) stack into O(1), and the recursion into a jump. Whether that reuse happens is a property of the implementation, not of your code, and this is the single most confidently misremembered fact in the subject.

tail position — the frame is dead after the callgcd(a, b): if b = 0: return a return gcd(b, a mod b) ← nothing happens after; the frame is garbage NOT tail position — one multiply is still pendingfactorial(n): if n = 0: return 1 return n · factorial(n − 1) ← the caller must survive to do the "n ·" the standard fix: an accumulator parameterfactorial(n, acc = 1): if n = 0: return acc return factorial(n − 1, n · acc) ← the multiply moved BEFORE the call and the loop it is isomorphic toacc = 1 while n ≠ 0: acc = n · acc; n = n − 1 return acc

Two structural consequences fall straight out of the definition. First, a tail recursion is necessarily a linear recursion: if two recursive calls were made, the first cannot be the last thing the function does. Second, a tail recursion is always rewritable as a loop with no auxiliary storage, by the purely mechanical transformation shown above — replace the recursive call with an assignment of the new arguments to the existing parameters, and wrap the body in a loop. Binary search, gcd, and a search for a value in a list are all tail-recursive and all become loops this way; the loop version of binary search in Arrays & Strings, §16, is exactly this transformation applied.

What the accumulator trick really does

Non-tail-recursive code leaves work pending in every frame — the n · in factorial, the two writes after the call in a recursive list reversal. The stack is therefore not merely storing "where to return to"; it is storing a queue of deferred operations, and its depth is how many of them are outstanding. Adding an accumulator performs each operation before descending instead of after returning, which empties that queue and leaves nothing for the frame to hold. Note the price: the order of the deferred operations reverses. factorial multiplies from n down rather than from 1 up — harmless for multiplication, which is associative and commutative, but a real semantic change for a non-associative combine, and the reason a naive accumulator rewrite of a string-building recursion produces the string backwards.

The three errors this table is meant to head off

  • "Tail recursion is efficient." Tail position is a syntactic property of your code; the efficiency is a property of the compiler. Writing a tail call in a language that does not eliminate it buys nothing whatsoever — the frame is still pushed, the depth is still linear, and you have paid the readability cost of the accumulator for no return.
  • "My recursion is tail-recursive." Check what happens after the call returns. A pending arithmetic operation, a pending write, an exception handler or a resource-cleanup block wrapping the call, or a debug trace on the return path — any of these puts the call out of tail position, and the last two do so invisibly, because a try or a scoped destructor means the frame must survive the call in order to run the cleanup.
  • "So it never overflows." Only for the tail calls. Portable advice. If the language guarantees proper tail calls, use them freely and write loops as recursions. If it does not, treat a tail-recursive formulation as a design sketch — it tells you the loop exists and what its state variables are — and then write the loop. For recursions that are not tail-recursive and are too deep anyway, §10 is the general answer.

10 Converting any recursion to iteration with an explicit stack

Every recursion can be rewritten as a loop over a stack you allocate yourself, mechanically, with no cleverness and no change to the algorithm. The call stack is a stack; replace it with one of yours. What changes is only where the memory comes from — heap instead of thread reservation — and what is stored — the few values you actually need instead of a whole frame. A conversion that popped there would lose every move, and a conversion with no stage field could not tell iteration 2's visit to that record from iteration 4's. The stage tag is the return address, and there is no version of this that does without one — except in the special case below.

What you gain, and what you do not

  • Gain: capacity. The heap is typically orders of magnitude larger than a thread's stack reservation and can grow. A depth that overflows as a recursion is routine as an explicit stack. This is the reason production graph code writes depth-first search iteratively.
  • Gain: a smaller record. A real frame carries a return address, saved registers, alignment padding and every local the function declares. Your record carries the four values you chose. The saving is a constant factor, but on a deep recursion a constant factor on the space is the difference between fitting and not.
  • Gain: control. You can inspect the stack, bound it, serialise it, resume it, or run several searches interleaved. None of that is possible with the call stack.
  • Not gained: asymptotic space. The peak is the same Θ(depth). Converting a linear-depth recursion to an explicit stack moves ten million records from the stack to the heap; it does not make them go away. If the depth itself is the problem, change the algorithm (§06, fix 1 or 2).
  • Lost: legibility. The stage tags are a hand-rolled program counter, and they are easy to get wrong in a way that produces a plausible-looking wrong order. Convert only when you need to, and keep the recursive version alongside as the specification — as the figure does, by running both and comparing.

The special case that needs no stage tag

When the work between recursive calls is nothing — a pre-order traversal, a flood fill, a plain depth-first search — the record is just the subproblem and the loop collapses to "pop one, do its work, push its children". That is why iterative DFS is six lines while iterative post-order traversal, which must do work after the children, needs either a stage tag or a second stack. The amount of machinery you need is exactly the amount of state that has to survive a call, which is the same quantity that decides whether a recursion is tail-recursive (§09). One idea, two consequences: nothing pending means a loop; something pending means a stack. Note also that pushing children in the natural left-to-right order makes the stack process them right to left, so a faithful pre-order conversion pushes the children reversed — a one-line detail that silently produces a mirrored traversal when it is forgotten. The stack and queue mechanics themselves are set out in Linked Structures, Stacks & Queues, §12–§13.

The equivalence, stated once. Recursion and "iteration plus a stack" are interchangeable in both directions, and the conversion is mechanical enough to be done by a compiler. So arguments about which is "more powerful" are empty; the real questions are where the memory lives, how much of it there is, and which version you can read six months from now.

11 Overlapping subproblems, and the memo that fixes them

Divide and conquer is fast when the subproblems it generates are disjoint — mergesort's two halves share no element, so solving both costs what solving the whole costs, once. When the subproblems overlap, the same subproblem is solved many times over, the call tree becomes exponentially larger than the set of distinct subproblems, and the fix is not a better split but a table: remember each answer the first time and look it up thereafter.

At n = 20 that is 21,891 invocations against 39; at n = 26 it is 392,835 against 51. The ratio is what grows, and it grows like φⁿ/n.

When does memoization apply?

Exactly when two conditions hold. Overlapping subproblems: the recursion reaches the same subproblem along more than one path, so there is something to cache. Optimal substructure (or, for a plain computation, referential transparency): the answer to a subproblem depends only on its arguments, so a cached answer is still valid when it is reused. The second is what fails when a recursion's result depends on mutable state the arguments do not capture — cache that and you get a wrong answer rather than a slow one, which is worse. Mergesort passes the second test and fails the first: its subproblems never repeat, so a memo would be pure overhead.

Two things memoization does not fix

  • The stack depth. Memoized Fibonacci still descends n frames before the first value comes back, so it still overflows at large n. Converting top-down memoization into bottom-up tabulation — fill the table from the base cases upward with a loop — removes the recursion entirely and with it the stack, which is one of the two reasons tabulation is usually preferred in production.
  • The table's own space. Θ(number of distinct subproblems) memory is now a real cost, and for a two-dimensional state space it is the dominant one. Recovering it needs the rolling-window trick, which only works once the dependency structure is explicit — another argument for tabulation.
Named here, developed elsewhere. Recursion with a memo is dynamic programming, top-down. The state definition, the choice between memoization and tabulation, the space-reduction tricks and the reconstruction of the solution itself all belong to that page; what belongs here is the diagnosis — if the call tree is far larger than the set of distinct subproblems, you do not have a divide-and-conquer problem, you have a dynamic-programming problem — and the observation that the two paradigms are distinguished by exactly one question: do the subproblems overlap? The same distinction shows up far outside this domain: the value-iteration recursion of reinforcement learning and the Viterbi recursion are both "recursion over overlapping subproblems", tabulated.

12 The divide-and-conquer template

Divide and conquer is the design paradigm in which a problem of size n is broken into a subproblems, each of size about n/b with b > 1, solved recursively, and reassembled. Three steps, always in this order: divide the instance into subproblems of the same type; conquer them by recursion, falling back to a direct method once they are small enough; combine the subsolutions into a solution of the original. It is a special case of recursion, distinguished by b > 1 — the input shrinks by a factor rather than by a constant — which is precisely what makes the number of levels logarithmic instead of linear.

the templateDC(P): if size(P) ≤ n₀: return direct_solve(P) ← the cutoff, §22 P₁, …, P_a = divide(P) ← a pieces, each about size(P)/b S₁, …, S_a = DC(P₁), …, DC(P_a) ← conquer return combine(S₁, …, S_a) the three design parametersa = how many subproblems are actually SOLVED (not how many pieces exist) b = the factor the size shrinks by (b > 1, or it is not divide and conquer) f(n) = cost of divide + combine at this level, excluding the recursive calls the cost, immediatelyT(n) = a·T(n/b) + f(n)

Why a and b are separate numbers

They are routinely conflated and they measure different things. b says how the instance is cut up; a says how many of the resulting pieces you have to recurse into. Binary search cuts into two (b = 2) and recurses into one (a = 1), because the comparison at the midpoint proves the answer cannot be in the other half — the whole algorithm is that a < b. Mergesort cuts into two and recurses into both (a = b = 2). Karatsuba cuts each operand into two halves, which would naively need four products, and arranges by algebra to need only three (a = 3, b = 2) — and since a > b its leaves outnumber n, which is why its exponent exceeds 1. Reducing a while holding b fixed is the single most productive move in this entire paradigm, and §18 and §19 are two famous instances of making it.

The four questions that turn a problem into a divide-and-conquer algorithm

  1. What is a subproblem of the same type? Usually a contiguous subrange, a subset of the coordinates, half the bits of a number, or a sub-rectangle of a matrix. If the smaller instance is not the same problem, recursion does not apply and you are doing something else.
  2. Do the pieces cover every case? This is the step people skip, and it is where maximum subarray is instructive: splitting an array in half leaves a third possibility — a solution that straddles the split — which neither recursive call can see. Missing it gives a routine that is fast, elegant and wrong. Whenever the split is geometric rather than logical, ask what lives on the boundary (§16, §20).
  3. How expensive is the combine? This is f(n) and it decides everything. A constant-time combine with a = b = 2 gives Θ(n); a linear combine gives Θ(n log n); a quadratic combine gives Θ(n²) and the recursion has bought nothing.
  4. What is the base case, and at what size? Correctness needs a base case that covers every size the divide step can produce, including zero and one (§03). Performance needs a base case that fires well above size 1, because below some threshold the direct method is simply faster (§22).

Three neighbours it is easy to confuse it with

  • Decrease and conquer reduces to one subproblem that is smaller by a constant — T(n) = T(n − 1) + f(n). Insertion sort, selection sort and factorial live here. The level count is n, so it never produces a logarithm, and calling it divide and conquer obscures exactly the property that matters.
  • Dynamic programming also recurses on subproblems, but they overlap, so the recursion tree revisits them and a table is required (§11). Divide and conquer's subproblems are disjoint, which is why no table is needed and why its space cost is just the stack.
  • Backtracking also recurses, but on choices rather than on pieces of the input; the subproblems do not partition anything, and the payoff comes from pruning rather than from a shrinking measure (§23).
The paradigm in one sentence. If a subproblems of size n/b plus f(n) glue is cheaper than solving the whole thing directly, recurse — and the comparison that decides "cheaper" is between f(n) and n^(log_b a), which is the entire content of §13.

14 Mergesort, the canonical instance

Mergesort is divide and conquer with a trivial divide and all the intelligence in the combine. Split the array at the midpoint — an index calculation, no work. Sort both halves recursively. Then merge the two sorted halves into one sorted whole in linear time, which is possible only because they are sorted: the smallest remaining element of the union is always at the front of one of the two runs, so one comparison decides the next output.

Reversed input is not mergesort's worst case

This is the observation the figure exists to make, and it separates mergesort from the quadratic sorts in a way that is easy to state and easy to get wrong. For insertion sort, reversed input is exactly the worst case: every element travels the whole way. For mergesort, reversed input is a best case, tied with already-sorted input, because in every single merge one run lies entirely above the other, so one cursor exhausts immediately and the tail is as long as possible. The genuine worst case is an input constructed so that the two runs interleave at every merge, which the adversarial preset does at n = 8 — and it reaches the known exact worst case n·ceil(log₂ n) − 2^ceil(log₂ n) + 1, which is 8·3 − 8 + 1 = 17. At n = 16 that formula gives 16·4 − 16 + 1 = 49, and the sixteen-value preset happens to attain it too, so the figure measures both rather than asserting them. The matching lower bound ∑ min(p, q) — 12 at n = 8, 32 at n = 16 — is computed from the recursion's own merge sizes and printed alongside; only the n = 8 end of it is exhibited by a preset, the sorted and reversed inputs. The practical upshot: mergesort's comparison count varies by less than a factor of two between its best and worst inputs — 12 against 17 at n = 8, 32 against 49 at n = 16. The best case for a balanced split is (n/2)·log₂ n and the worst is n·log₂ n − n + 1, so the ratio climbs towards 2 as n grows and never reaches it. That bounded spread is the strongest form of the "no bad inputs" guarantee any comparison sort offers.

The four properties that make mergesort the reference sort

  • Θ(n log n) in every case, not just on average. The recursion tree's shape is fixed by the index arithmetic and does not depend on the data at all, so there is no input that degrades it — unlike quicksort, whose tree shape is data-dependent and whose worst case is quadratic.
  • Stable, provided the merge breaks ties toward the left run — the ≤ rather than < in the comparison. Equal elements keep their original relative order, which matters whenever you sort by one key after having sorted by another.
  • Sequential access only. The merge reads both runs front to back and writes the output front to back, so it works on data that cannot be randomly accessed — linked lists, files, streams. This is why external sorting of data too large for memory is mergesort, and why sorting a linked list in O(n log n) with O(1) extra space is mergesort with pointer splicing instead of copying.
  • The cost: Θ(n) auxiliary space for the merge buffer. The merge cannot be done in place in linear time by any simple method; in-place merge algorithms exist but carry constants that erase the benefit. Allocate one buffer of size n at the top and pass it down rather than allocating per call (§05).
Lower bound met. The decision-tree argument in Algorithm Analysis, §09, says every comparison sort needs Ω(n log n) comparisons in the worst case. Mergesort's worst case is Θ(n log n). So mergesort is asymptotically optimal among comparison sorts, and no amount of cleverness inside the comparison model will beat it by more than a constant. The full comparison of the sorts that sit at this bound, above it, and outside the model entirely is in Sorting & Searching.

15 Binary search: divide and conquer with a = 1

Binary search is the degenerate and most important case of the paradigm: divide into two, and then throw one half away. Because a = 1, the recursion tree is not a tree but a path — one node per level, log₂ n levels, constant work each — and the total is Θ(log n). Every other algorithm on this page pays for its logarithm by multiplying it against n; binary search gets the logarithm alone, and it gets it by proving that half the search space cannot contain the answer rather than by examining it.

Reading the tie case through the Master theorem is a useful sanity exercise, because the intuition "one call per level, constant work, so it is the number of levels" and the formal classification have to agree — and they do, with n^(log₂ 1) = n⁰ = 1. The same reading immediately tells you what goes wrong if the "constant work" is not constant — but the two ways it can fail are different, and they are routinely conflated. If the per-level work grows with the subproblem size, say f(m) = Θ(m) because each call rebuilds or copies its half-range, the recurrence is T(n) = T(n/2) + Θ(n), which lands in the root-dominates case and costs Θ(n) — the geometric series n + n/2 + n/4 + …, not log n terms of size n. That is the "passing slices instead of index bounds" pitfall of §29, and it destroys the whole point of the algorithm. If instead the per-level work is a constant that merely happens to be large — comparing whole strings of length L, where the cost is Θ(L) and does not shrink as the range does — then f is constant in the recurrence's variable and the answer is Θ(L log n): the tie case again, with the constant carried along. Only work that scales with the subproblem size belongs in f(n), and mistaking the second case for the first is the commonest way to misread a recurrence.

Where the logarithm actually comes from, and what it costs up front

Nothing about halving is magic on its own; you may halve a sorted range because sortedness lets one comparison eliminate everything on one side. The precondition is the price. Sorting costs Θ(n log n), so a single lookup in an unsorted array is faster by linear scan — Θ(n) beats Θ(n log n) + Θ(log n) — and binary search only pays off across many queries: q lookups cost Θ(n log n + q log n) sorted against Θ(q·n) unsorted, so the crossover is around q ≈ log n queries. This "sort once, query many" trade is the same shape as the presorting step in closest pair (§20), and it is one of the standard reasons to sort at all.

Two things the divide-and-conquer framing makes obvious

  • The depth is the whole cost, so the boundary conditions are the whole difficulty. With one node per level there is no combine step to get wrong and no subtle interaction between the halves — which is why binary search bugs are always index bugs: an inclusive-versus-exclusive hi, a mid that fails to shrink the range (§02), or a midpoint computed as (lo + hi) / 2 in a fixed-width integer type, where the sum can overflow and lo + (hi − lo) / 2 cannot. The boundary-variant versions — first index ≥ x, last index ≤ x, the insertion point — and their invariants are worked through in Arrays & Strings, §16.
  • a = 1 is a design target, not an accident. Any time you can prove that a subproblem cannot contain the answer, you may drop it, and the exponent log_b a falls. Branch and bound (§26) is this idea applied to a search tree, where the "proof" is a bound rather than a comparison; and quickselect (§28) is it applied to selection, where the partition proves the target is on one side, turning quicksort's 2T(n/2) into T(n/2) and its n log n into n.
A logarithm is a promise about levels. Whenever a cost comes out as log n, the reason is always the same: something halves, and there are only log₂ n halvings available before you reach 1. Balanced trees, heaps, skip lists, exponentiation by squaring and binary search all collect their logarithm from this one fact, and all of them pay for it with a structural precondition that has to be established and maintained.

16 The maximum-subarray problem, and the case that lives on the boundary

Given an array of numbers, some negative, find a contiguous non-empty subarray whose sum is largest. The brute force is Θ(n²): there are n(n+1)/2 subarrays and each sum is obtainable in O(1) from the previous one. Divide and conquer gets it to Θ(n log n), and does so by confronting the one thing a geometric split always introduces — a third case that neither half can see.

the three-way case analysis, which is the entire algorithmsplit A[lo..hi] at mid = floor((lo + hi)/2). Why the crossing scan is two independent maximisations

This is the step that makes the algorithm work and it is worth being explicit about. A crossing subarray is pinned: it must contain both A[mid] and A[mid+1]. So it is determined by its left endpoint i ≤ mid and its right endpoint j > mid, and its sum is the sum of the left piece plus the sum of the right piece — two quantities that depend on disjoint variables. Maximising a sum of two independent terms is maximising each term, so instead of trying all (mid − lo + 1) × (hi − mid) pairs you make two linear passes. If the two endpoints had interacted, the crossing case would have cost Θ(n²) and the whole design would have been pointless — which is exactly what happens for problems where the boundary case does not decompose.

Worked by hand, on the array the figure uses

Take the sixteen values A = [13, −3, −25, 20, −3, −16, −23, 18, 20, −7, 12, −5, −22, 15, −4, 7] at indices 0…15, so mid = 7. Walk left from index 7, accumulating: 18, −5, −21, −24, −4, −29, −32, −19 — the largest is 18, at i* = 7. Walk right from index 8: 20, 13, 25, 20, −2, 13, 9, 16 — the largest is 25, at j* = 10. So the best crossing subarray is A[7..10] = [18, 20, −7, 12] with sum 18 + 25 = 43. Meanwhile the left half's own best is 20 (the single element at index 3) and the right half's own best is 25 (A[8..10]). The winner is max(20, 25, 43) = 43 — the crossing case, which is the entire point: the answer to this instance is invisible to both recursive calls, and an implementation that forgot case (3) would confidently return 25.

Three different algorithms agreeing on both the sum and the index range is a far stronger check than any one of them returning a plausible number, and the all-negative preset is there because it is the case that breaks careless implementations of all three.

The empty-subarray trap, stated precisely

The problem says non-empty. If the empty subarray were allowed its sum would be 0, and the answer on an all-negative array would always be 0 — a different and much less useful problem. Implementations go wrong in three specific places. A base case that returns 0 for a zero-length range is fine only if the range can never be the whole input; initialising the running best to 0 rather than −∞ silently converts the problem into the empty-allowed version; and the crossing scan must take at least one element from each side, so its two running-best values must start at −∞ and be updated after adding the first element, not before. The all-negative preset makes each of these produce a visibly wrong answer, which is why it is worth keeping as a test rather than as a footnote.

The transferable lesson. Whenever you split an instance geometrically — an array at an index, a plane at a line, a matrix into quadrants — ask what the split cuts through. Maximum subarray cuts through subarrays; closest pair (§20) cuts through pairs; a divide-and-conquer inversion count cuts through inversions. In every case the algorithm's real content is the linear-time handling of the boundary case, and the recursion is the easy part.

17 When a linear scan beats the split

Maximum subarray has a Θ(n) solution — one pass, constant space — which is asymptotically better than the Θ(n log n) divide and conquer of §16. It is worth working through for two reasons: it is the right algorithm for this problem, and the reason it exists is a reason that generalises. Divide and conquer is a default, not an optimum, and the thing that beats it here is a strengthened induction on prefixes rather than on halves.

Why the first recurrence is true

A subarray ending at j either starts at j — in which case its sum is A[j] — or it starts earlier, in which case it is a subarray ending at j − 1 extended by A[j], and the best such is the best one ending at j − 1 plus A[j]. Those two cases are exhaustive, so the maximum is the larger of them. The practical reading is the memorable one: if the running sum so far is negative, it can only hurt, so drop it and start again at j. Note that the choice is between A[j] and best_ending_here(j−1) + A[j], not between A[j] and 0 — which is the same non-empty requirement as §16, in its other disguise, and the reason the base case is A[0] rather than 0.

The general principle: strengthen the subproblem

The naive prefix subproblem "the best subarray of A[0..j]" fails because knowing it tells you nothing about how to extend to j + 1 — the new best might start anywhere. Carrying a second quantity, the best subarray ending at j, makes the extension a constant-time calculation. That move — return more than you were asked for, so that the recursion composes — is the same one that turns naive Fibonacci into a linear recursion by having fib_pair(n) return the consecutive pair (F(n−1), F(n)), from which the caller gets F(n+1) by one addition (a different repair from §11's memo: strengthening removes the repeated subproblems instead of caching them), and the same one that turns a recursive tree-balance check from Θ(n²) into Θ(n) by returning the height alongside the verdict. Whenever a recursion recomputes something its caller already had, the fix is usually to widen the return value rather than to add a cache.

So when is divide and conquer the wrong tool?

  • When the problem has a prefix or suffix recurrence. If the answer for A[0..j] can be maintained in O(1) as j advances, a scan is linear and unbeatable. Running maxima, prefix sums, and most one-dimensional sliding-window problems are of this kind — see Arrays & Strings, §14.
  • When the combine is as expensive as the whole problem. T(n) = 2T(n/2) + Θ(n²) solves to Θ(n²) — the recursion contributed nothing but overhead.
  • When the subproblems overlap. Then it is dynamic programming (§11), and forcing a divide-and-conquer framing produces an exponential algorithm.
  • When n is small. The constants matter more than the exponent, which §22 quantifies.

What the split buys that the scan does not

The scan is the better algorithm for this problem and a worse one for its relatives, because a left-to-right pass needs a left-to-right direction to sweep along. The split does not. Strengthen a recursive call to return four numbers instead of one — the range's total, the best sum of a prefix of it, the best sum of a suffix of it, and the best sum anywhere inside it — and two adjacent ranges compose in O(1).

the four-value combine, which is §16's case analysis in closed formtotal = total_L + total_R prefix = max( prefix_L, total_L + prefix_R ) suffix = max( suffix_R, total_R + suffix_L ) best = max( best_L, best_R, suffix_L + prefix_R ) ← the CROSSING case again what that composability is worthstore the four numbers at every node of a segment tree over the array ⇒ maximum-subarray over ANY subrange, and point updates, in O(log n) each — a query the linear scan cannot answer without rescanning

The same strengthening, done post-order instead of left-to-right, solves the maximum-sum path problems on trees: each node returns the best path ending at it and the best path anywhere in its subtree, and the parent combines them. One caution against a tempting over-generalisation: the two-dimensional maximum-subrectangle problem is not a case where the scan fails. Its standard Θ(n³) algorithm fixes a pair of rows, collapses the rows between them into a single array of column sums, and runs exactly the linear scan of this section on that array. There the scan generalises and the split is the awkward one.

Both algorithms are worth knowing, for different reasons. The linear scan is what you ship: one pass, constant space, no stack. The divide-and-conquer version is what teaches the boundary-case discipline, and it is the one whose return value generalises — into the segment tree above, onto trees, and into any setting where two neighbouring answers have to be glued rather than swept. Notice that the crossing case of §16 survives into the last line of the combine: the boundary treatment is not scaffolding you throw away, it is the part that makes the structure composable.

18 Karatsuba multiplication: where the fourth product went

Multiplying two n-digit integers by the method taught in school costs Θ(n²) single-digit multiplications, and for as long as anyone had thought about it that looked like the answer — it was conjectured outright, in the middle of the twentieth century, that Ω(n²) was a lower bound. It is not. Split each operand in half and the schoolbook method becomes a divide and conquer with a = 4 — which is still Θ(n²), so the recursion has bought nothing. The insight is an algebraic identity that computes the middle coefficient from the two products you already have plus one more, reducing a from 4 to 3, and that single change moves the exponent from 2 to log₂ 3 ≈ 1.585.

split each n-digit operand at the halfway point, base Bx = x₁·B^(n/2) + x₀ y = y₁·B^(n/2) + y₀ (each half has n/2 digits) expanding the product gives three coefficients, four productsx·y = x₁y₁·Bⁿ + (x₁y₀ + x₀y₁)·B^(n/2) + x₀y₀ ────┬─── ────────┬──────── ──┬── call it P the middle call it Q ⇒ T(n) = 4·T(n/2) + Θ(n) = Θ(n²) ← no better than schoolbook the identity: the middle is one product minus two you already have(x₁ + x₀)·(y₁ + y₀) = x₁y₁ + x₁y₀ + x₀y₁ + x₀y₀ = P + middle + Q ⇒ middle = (x₁ + x₀)·(y₁ + y₀) − P − Q so three products sufficeP = x₁·y₁ Q = x₀·y₀ R = (x₁ + x₀)·(y₁ + y₀) x·y = P·Bⁿ + (R − P − Q)·B^(n/2) + Q ⇒ T(n) = 3·T(n/2) + Θ(n) = Θ(n^(log₂ 3)) = Θ(n^1.58496…)

Carried through with real digits: 1234 × 5678

Take B = 10, n = 4, so the halves are two digits each: x₁ = 12, x₀ = 34, y₁ = 56, y₀ = 78. The three products are P = 12 × 56 = 672, Q = 34 × 78 = 2652, and R = (12 + 34) × (56 + 78) = 46 × 134 = 6164. The middle coefficient is R − P − Q = 6164 − 672 − 2652 = 2840. Assembling, 672 × 10⁴ + 2840 × 10² + 2652 = 6,720,000 + 284,000 + 2,652 = 7,006,652, which is 1234 × 5678. Schoolbook's four products would have been 12×56 = 672, 12×78 = 936, 34×56 = 1904, 34×78 = 2652, whose middle is 936 + 1904 = 2840 — the same middle coefficient, reached with one fewer multiplication. That is the entire trick, and the figure lays the two side by side.

The carry, which is where implementations go wrong

One detail the algebra hides: x₁ + x₀ and y₁ + y₀ can each be as large as 2(B^(n/2) − 1), which needs n/2 + 1 digits, not n/2. So the third recursive call is not quite on half-size operands. Left unhandled this quietly changes the recursion and can break a fixed-width implementation; handled naively it makes the recurrence T(n) = 2T(n/2) + T(n/2 + 1) + Θ(n), which still solves to Θ(n^log₂ 3) but is awkward to prove. The clean fix is to peel the overflow digit off explicitly: write x₁ + x₀ = c_x·B^(n/2) + r_x with c_x ∈ {0, 1}, do the same for y, and expand (c_x·B^(n/2) + r_x)(c_y·B^(n/2) + r_y) — only the r_x · r_y term is a genuine half-size multiplication, and everything else is a shift or a conditional add. The figure's implementation does exactly this, which is why its measured multiplication count is exactly 3^log₂ n, with no fudge.

Three products instead of four — the worked example, and the measured cost as n grows counts are single-digit multiplications, tallied inside the real recursive routines

In counts mode the figure runs both recursions on random operands at each size and reports the tallies. The schoolbook split lands on n² exactly and Karatsuba on 3^log₂ n = n^log₂ 3 exactly, and the measured slope between consecutive sizes — log₂ (count(2n) / count(n)) — comes out at 2.000 and 1.585 respectively, which is the exponent read straight off the data rather than taken from the recurrence. Every product is also checked against exact arithmetic, so the figure is verifying that it multiplied correctly as well as cheaply.

What this is and is not worth in practice

  • It is a real asymptotic win, and it is used: big-integer libraries switch from schoolbook to Karatsuba above a threshold typically in the range of a few dozen machine words, and to still-faster methods above a much larger one. The exact thresholds are implementation- and platform-specific and are set by measurement, not by the exponents.
  • The constant is worse. Karatsuba replaces one multiplication by several additions, subtractions and shifts, all of which are linear-time but not free. Below the threshold the extra additions dominate and schoolbook wins — the same cutoff story as §22, with the same resolution.
  • It is not the end of the line. Splitting into three parts with five products gives n^(log₃ 5) ≈ n^1.465, and the pattern generalises to a family of methods whose exponents approach 1. Beyond those, multiplication via the fast Fourier transform (§21) reaches O(n log n log log n) and better, which is what the largest computations actually use.
  • The size measure is bits or digits, not value. "Multiplying two numbers" is O(1) when they fit in a machine word; this entire discussion is about numbers that do not, where n is the length of the representation. Getting that wrong is the classic input-size confusion flagged in Algorithm Analysis, §01.
The move to remember. When a divide and conquer produces a subproblems and the combine is cheap, look for algebraic structure that lets one subproblem be computed from the others. Karatsuba reduces 4 to 3; Strassen reduces 8 to 7; Toom–Cook reduces 9 to 5. Each is the same manoeuvre — trade multiplications for additions, which are asymptotically cheaper — and each pays off precisely because log_b a is in an exponent.

19 Strassen's algorithm, and what it actually buys

The same manoeuvre, one dimension up. Multiplying two n × n matrices by the definition costs Θ(n³). Partition each into four n/2 × n/2 blocks and the block formulas need eight block products — T(n) = 8T(n/2) + Θ(n²) = Θ(n³), no gain. Reading the crossover honestly

Switch the plot to multiplications only and Strassen uses strictly fewer at every size strictly above the cutoff — the ratio measured at a cutoff of 8 is 1.143× at n = 16, 1.306× at n = 32 and 1.493× at n = 64. That is not an approach to a limit but an exact identity: the naive recursion does n³ scalar multiplications whatever the cutoff, Strassen does 7^k · n₀³ with k = log₂(n/n₀) levels above the cutoff, so the ratio is exactly (8/7)^k — 8/7 = 1.1429, (8/7)² = 1.3061, (8/7)³ = 1.4927, which is what the table prints to three places. At n equal to the cutoff the two are the same routine and the counts tie exactly, which is the boundary the table makes visible and which is easy to state wrongly as a strict win. Switch back to total scalar operations and the picture changes completely, because the eighteen additions are not free. With the recursion taken all the way down to single scalars — cutoff 1 — the measurement says Strassen loses on total operation count at every size the figure can reach: at n = 64 it is 798,967 operations against the naive 520,192. Raise the cutoff and the additions collapse, because they are incurred once per level and the number of levels drops: at a cutoff of 8 the measured totals cross at n = 16 (7,872 against 7,936 — a margin under one percent), and by n = 64 Strassen's total is 436,416 against 520,192. The cutoff is not a tuning detail, it is what makes the algorithm work at all, and every number in this paragraph is read off the figure's counters rather than computed from the recurrence.

And then a caution that the figure cannot show: an operation count is not a running time. Modern processors execute a multiply and an add at comparable cost and frequently fuse them, so a method that trades one multiply for three adds can lose even when its operation count wins. Real matrix multiplication is limited by memory traffic rather than arithmetic, and the naive triple loop — properly blocked for cache — reaches a very large fraction of a machine's peak throughput, while Strassen's extra temporary matrices cost bandwidth and allocation. Reported practical crossovers therefore vary widely with the implementation and the hardware, and the only defensible statement is that they are determined by measurement on the target machine, not by comparing exponents. The same caveat, at greater length, is the subject of Algorithm Analysis, §23.

Three further costs that do not appear in the recurrence

  • Memory. The naive block recursion needs little scratch space; Strassen materialises ten operand matrices and seven products per level. Implementations work hard to reuse buffers, and the space overhead is a real part of why it is reserved for large n.
  • Numerical behaviour. With floating-point entries, Strassen satisfies a weaker error bound than the definitional algorithm. The naive method's error is bounded entry by entry relative to the magnitudes that produced that entry; Strassen's additions mix entries from across the matrix before multiplying, so its guarantee is in terms of matrix norms rather than per-entry, and an entry that should be small can carry error proportional to the largest entries anywhere in the operands. For well-scaled inputs this is usually acceptable; for matrices with wildly differing magnitudes it is not, and this — more than speed — is why numerical libraries are conservative about it.
  • Non-power-of-two sizes. The recursion assumes even dimensions at every level. Real implementations pad to the next suitable size or peel off a border row and column, and the bookkeeping is a meaningful fraction of the code.
What it actually buys. Asymptotically, a genuinely smaller exponent — the first proof that n³ is not a law of nature, which reframed the whole question of how fast matrix multiplication can be. Practically, a worthwhile speed-up on large, well-conditioned, dense problems in implementations that cut over to a tuned base case early, and nothing at all below that cutoff. The relevance of the constant-factor story to real numerical workloads is picked up in vectorised array computing and model acceleration, where the same arithmetic is the bottleneck.

20 Closest pair of points: the boundary case with a counting argument

Given n points in the plane, find the two whose distance is smallest. Checking all pairs is Θ(n²). Divide and conquer reaches Θ(n log n), and it is the most instructive algorithm on this page, because the boundary case does not decompose the way maximum subarray's did. Splitting the plane leaves a strip of candidates that could, for all the recursion knows, contain every point — so getting a linear combine requires a genuine geometric argument about how many points can be packed into a small box.

the splitsort the points by x once, up front. Split at the median x into L and R. recursively find the closest pair in L (distance δ_L) and in R (distance δ_R) δ = min(δ_L, δ_R) the boundary casea closer pair, if one exists, has one point in L and one in R, and BOTH must lie within δ of the dividing line — call that vertical band the STRIP the counting argument that makes the strip cheapwalk the strip in increasing y, and from each p look only FORWARD — a closer pair below p was already considered when its lower point was the one walking. Divide that box into eight δ/2-by-δ/2 squares (4 across × 2 down). The dividing line falls on a square boundary, so each square lies wholly in L or wholly in R, and its diagonal is δ/√2 ≈ 0.707·δ < δ, so it holds AT MOST ONE point — two points in one square would be a same-side pair closer than δ, which the recursive calls have already ruled out. ⇒ the box holds at most 8 points INCLUDING p ⇒ at most 7 forward partners. so the strip scan is linear, andT(n) = 2·T(n/2) + Θ(n) ⇒ Θ(n log n) [with the y-order maintained by merging] T(n) = 2·T(n/2) + Θ(n log n) ⇒ Θ(n log² n) [if the strip is re-sorted at every level]

Why "at most 7" is the whole algorithm

Without that bound, the strip scan is quadratic in the strip's size and the strip can be everything. The bound holds because δ is already known to be a lower bound on the distance between any two points on the same side — that is what the recursive calls established — so points cannot be packed densely within either half. Two points in the same δ/2 × δ/2 square would be within δ/√2 ≈ 0.707·δ of each other, contradicting the recursion's result. The constant 8 is not tight, and it is not claimed to be attained: it is an upper bound obtained by a deliberately crude packing count, and different presentations quote 7, 8 or a slightly larger number depending on whether the box is taken above p or centred on it, whether the squares are closed or half-open, and whether the strip is 2δ or 2δ-plus-endpoints wide. What matters for the complexity is only that the number is a constant independent of n, which is what turns the strip scan into O(n). The figure therefore measures the maximum number of forward partners actually examined for any strip point rather than asserting a value — it is 2 at the default layout, and never exceeds 3 anywhere in the two sliders' full range, comfortably under the 7 the argument permits. A measured constant well below a proved bound is the expected outcome, not a discrepancy.

The presorting trick, and why it is worth a section of its own

The strip must be traversed in increasing y. Sorting it inside the recursion costs Θ(n log n) per level and gives Θ(n log² n) overall — already better than quadratic, and the version worth writing first. To reach Θ(n log n), sort by y once, before the recursion starts, and have each call return its points in y order so the parent obtains its own y-ordered list by merging the two children's lists in linear time — mergesort's combine step, reused. This is a general and reusable move: when a recursive step needs a sorted order, maintain the order through the recursion instead of re-establishing it, and the same idea gives the Θ(n log n) divide-and-conquer inversion count.

What the default state shows, and why it is the normal case

At the default layout the top-level strip holds only a handful of points and the winning pair is not a crossing pair at all — the answer was already found inside one half. That is not a badly chosen example, it is what usually happens, and it is worth being explicit about. δ at the top level is the global minimum over both halves, so by the time the top-level strip is built δ is tiny compared with the spread of the points, and a band of width 2δ catches almost nothing. Move the layout slider through the presets and you will see the top-level strip population stay in the low single digits — one or two points at most layouts, four at the default, and never more than five anywhere in the sliders' range. The same is true of whether the answer crosses at all: over all 348 combinations of the two sliders, the winning pair is a top-level crossing pair in just 6 of them. The strip work that matters happens deep in the recursion, where δ is still large relative to the local point spacing. The packing argument is what guarantees the strip cannot be expensive; the geometry is what usually makes it cheap.

What generalises, and what does not

  • The packing argument generalises to higher dimensions, with a constant that grows exponentially in the dimension. The same counting runs verbatim: a candidate partner of p lies in a d-dimensional box of side 2δ around it, subdivide that into cubes of side δ/2 — there are 4^d of them — and each holds at most one point because its diagonal is δ·√d/4, which is below δ for every d < 16. So the candidate count is bounded by a constant of the order of 4^d (smaller with a more careful count, but exponential in d either way), which is fine at d = 2 or 3 and useless by the time d is a few dozen. That exponential constant is the geometric side of the same phenomenon that makes nearest-neighbour search hard in high dimensions.
  • The recursion needs no assumption about the point distribution. This is a worst-case Θ(n log n) bound, not an average-case one; adversarial point sets do not degrade it, unlike the grid-bucketing heuristics that are often faster in practice.
  • The same shape appears without geometry. Counting inversions, computing a sequence's longest ascending run across a split, and any "combine needs a sorted view" problem use the identical presort-and-merge structure.
The pattern this page has now shown three times. Split the instance; the recursion handles everything that lies strictly inside a piece; the algorithm's real content is a linear-time treatment of whatever the split cut through — the crossing subarray in §16, the strip here, and the carry digits in §18. When you cannot make that boundary treatment linear, the recursion buys nothing, and that is the usual reason a promising divide and conquer does not work out.

21 The fast Fourier transform, sketched

The FFT is the most consequential divide and conquer ever written, and its structure is the one you already know: T(n) = 2T(n/2) + Θ(n), hence Θ(n log n). What makes it different from mergesort is what is being halved. The input is not split into a left half and a right half of the data; it is split into the even-indexed and odd-indexed entries, and the reason that works is an algebraic coincidence about roots of unity. The full development belongs to the frequency domain; what belongs here is why it is a divide and conquer at all.

the problem, stated as polynomial evaluationgiven coefficients a₀ … a₍ₙ₋₁₎ of A(x) = a₀ + a₁x + … + a₍ₙ₋₁₎x^(n−1), evaluate A at the n complex n-th roots of unity ωⁿ = 1, ω = e^(2πi/n) the split: by parity of the index, not by positionA(x) = A_even(x²) + x·A_odd(x²) where A_even collects a₀, a₂, a₄, … and A_odd collects a₁, a₃, a₅, … each has n/2 coefficients the coincidence that makes it payas x ranges over the n n-th roots of unity, x² ranges over only n/2 DISTINCT values — the (n/2)-th roots of unity — because (ω^(k + n/2))² = (ω^k)² ⇒ the two half-size subproblems are themselves FFTs of size n/2, not new problems the combine, one "butterfly" per output pairA(ω^k) = A_even(ω²ᵏ) + ω^k · A_odd(ω²ᵏ) A(ω^(k + n/2)) = A_even(ω²ᵏ) − ω^k · A_odd(ω²ᵏ) ← same two terms, opposite sign ⇒ Θ(n) work to combine, and T(n) = 2T(n/2) + Θ(n) = Θ(n log n)

Worked by hand at n = 4, which is the whole algorithm in eight lines

Take the coefficients a = [1, 2, 3, 4], so A(x) = 1 + 2x + 3x² + 4x³, and n = 4, ω = e^(2πi/4) = i. Split by parity: A_even = [1, 3], meaning 1 + 3x, and A_odd = [2, 4], meaning 2 + 4x. Each is evaluated at the two square roots of unity {1, −1} — which is where the halving happened, because the four points {1, i, −1, −i} squared give only {1, −1}.

Four outputs from two size-2 transforms plus four arithmetic operations, and the two size-2 transforms are themselves butterflies over size-1 transforms — which are the coefficients themselves. Count: n/2 = 2 complex multiplications and n = 4 additions per level, log₂ n = 2 levels. The structure is the same at every size; only the twiddle factors ω^k change.

The structural point, in one paragraph

Every divide and conquer needs its subproblems to be instances of the same problem. Splitting a polynomial's coefficients by parity would normally fail that test, because you would then need A_even and A_odd evaluated at n points, which is no smaller than what you started with. The halving comes entirely from the squaring: the n evaluation points collapse to n/2 when squared, so each half really is a size-n/2 instance. The roots of unity are not decoration; they are what makes the recursion close. That is why the FFT is stated over them and why the naive "evaluate at any n points" version is still quadratic.

Why anyone cares: convolution

Multiplying two degree-n polynomials — equivalently, convolving two length-n sequences — costs Θ(n²) in the coefficient representation and Θ(n) in the point-value representation, because evaluation is pointwise. So: transform both operands to point-value form, multiply pointwise, transform back. Each transform is Θ(n log n) and the middle step is Θ(n), giving Θ(n log n) convolution. One step of that chain has a size requirement that is easy to omit and fatal to omit. The product of two degree-n polynomials has degree 2n, so it has 2n + 1 coefficients, and a polynomial is determined by its values at as many points as it has coefficients. Evaluating at only n points therefore does not determine the answer: the transform of length n computes the product modulo xⁿ − 1, which wraps the high coefficients round onto the low ones — the cyclic convolution rather than the one you wanted. The fix is to zero-pad both operands to a length of at least 2n + 1 (in practice the next power of two above that) before transforming. Skipping the padding produces an answer that is plausible, wrong, and correct in its low half, which is the worst combination for debugging. That single chain is why the FFT matters: it is the reason large-integer multiplication beats Karatsuba at scale (§18), the reason convolution is tractable in image processing, and the reason spectral methods exist at all. The inverse transform is the same algorithm with ω replaced by ω⁻¹ and a division by n, which is itself a small miracle of the same algebra.

Three practical notes

  • Powers of two. The recursion as stated needs n to be a power of two; real implementations either pad to one or use mixed-radix variants that split by other small factors, with the same n log n behaviour for smooth n and a fallback for large prime lengths.
  • In place, and the bit-reversal permutation. The classic iterative formulation does the butterflies bottom-up over an array permuted by reversing the bits of each index — the very same reordering the recursion performs implicitly when it separates evens from odds at every level. That equivalence is a good exercise in the recursion-to-iteration conversion of §10.
  • Finite fields. The whole argument needs only an element of multiplicative order n, not complex numbers — so the same algorithm runs exactly, without floating point, in a modular arithmetic where such an element exists. That is what large-integer libraries actually use, because it removes the rounding analysis entirely.
Why it is here. As a divide and conquer it is unremarkable: a = 2, b = 2, linear combine, the same recurrence as mergesort and the same n log n answer. What is remarkable is the change of representation — coefficients to values and back — which turns a quadratic operation into a linear one, and the algebraic structure that makes the halving legal. The transform itself, the sampling theory around it, and its use in filtering are in Frequency-Domain Image Processing.

22 When divide and conquer does not pay

The recurrence tells you the growth rate and says nothing about the constant, and there are four distinct situations in which the constant decides the outcome. Three of them are cures — small inputs, an expensive combine, and call overhead — and the fourth is a widely-repeated claim that points the wrong way, so it is worth getting right.

1. Small n: the cutoff, and why every real implementation has one

At the bottom of a divide-and-conquer recursion the subproblems are tiny, and a method with a worse growth rate but a smaller constant wins there. Mergesort and quicksort both stop recursing below a threshold and finish with insertion sort, which is Θ(k²) but has an inner loop of two array accesses and a comparison. This is not an optimisation bolted on afterwards; it removes the majority of the recursive calls, because a binary recursion's nodes are concentrated at the bottom — half of all invocations are leaves, three quarters are in the bottom two levels — so cutting off at size k eliminates roughly a (1 − 1/k) fraction of them.

Mergesort with an insertion-sort cutoff — comparisons, element moves and invocations, all measured the weight on a recursive call is a declared model parameter; the three counts are not

Read the three measured curves before the weighted one. Invocations fall off a cliff as the cutoff rises — that is the whole benefit, and it is enormous. Comparisons and element moves are flat and then rise, because insertion sort's quadratic behaviour starts to show once the blocks get big. So the measured comparison count alone is minimised at the smallest cutoffs — at the default settings cutoffs 1 and 2 are tied, and element moves bottom out at 4 — and anyone who tunes a cutoff by counting comparisons alone will conclude, wrongly, that there should be barely any cutoff at all. The weighted total adds w comparison-units per recursive call — w is a model parameter you are choosing, not something this page measured — and as you raise it the minimum slides to larger cutoffs — 4 at w = 0, 8 at the default w = 8, 16 at w = 24. That is exactly why real implementations, where a call costs far more than a comparison and insertion sort's tight inner loop is friendly to the branch predictor and the cache, settle on thresholds several times larger than the comparison count alone would suggest — the ones you meet in production sorts are typically somewhere between about 7 and 64, and they differ between libraries because they were each measured on different hardware. The defensible procedure is to time it on the target machine (Algorithm Analysis, §22); the figure's purpose is to show that the shape of the trade is real and where each term comes from.

2. The combine dominates

If f(n) is as large as the whole problem, the recursion contributes nothing. T(n) = 2T(n/2) + Θ(n²) solves to Θ(n²): you have paid for the recursion and kept the original growth rate. The warning sign is a combine step that needs to look at all pairs, sort from scratch, or re-derive information the recursive calls already had — which is precisely what the presorting trick of §20 exists to prevent. Before writing the code, compute n^(log_b a) and compare it with f(n); if f wins by a polynomial factor the answer is Θ(f(n)) and the recursion is decoration.

3. A linear-time alternative exists

Maximum subarray in Θ(n log n) is a fine algorithm and the wrong one, because the linear scan of §17 exists. The same applies to finding a maximum, a sum, a running statistic, or anything else with a prefix recurrence. Divide and conquer's floor is Ω(n) for the combines alone, so it can never beat a single pass; if one pass suffices, take it. The honest use of the divide-and-conquer version is as a generalisation — it survives into two dimensions, onto trees, and into range-query structures, where no left-to-right scan exists.

4. Cache effects — which cut the other way

It is often said that recursion is bad for the memory hierarchy. For divide and conquer on arrays and matrices, the opposite is closer to the truth, and this is worth stating carefully because the mistaken version is common. As the recursion descends, the subproblems get smaller until they fit in cache, and everything below that point runs entirely out of cache without the algorithm having been told the cache size. That property has a name — cache-obliviousness — and it is why recursive blocked matrix multiplication and recursive mergesort often outperform naively written loop nests on real hardware: the loop nest streams the whole array repeatedly, while the recursion automatically works on a resident block. The genuine memory-hierarchy costs of divide and conquer are different ones: call overhead at the leaves (fixed by the cutoff of point 1), and auxiliary allocation — mergesort's buffer, Strassen's temporaries — which consumes bandwidth and can evict useful data. Neither is "recursion has bad locality".

The checklist before committing to a divide and conquer. Is there a one-pass algorithm? — if so, stop. Is f(n) polynomially larger than n^(log_b a)? — if so, the recursion buys nothing. Do the subproblems overlap? — if so, you want dynamic programming. Is n ever large enough for the asymptotics to matter? — if not, write the simple quadratic one. If all four answers are favourable, write it — and then add a cutoff, because you will need one.

23 Backtracking: recursion over a tree of choices

Backtracking is a systematic search of a space of partial solutions, built one decision at a time, in which a partial solution that cannot possibly be completed is abandoned immediately and the search returns to the last decision point to try the next alternative. It is recursion whose tree is a decision tree rather than a partition of the input: the children of a node are the choices available at that point, not pieces of the data. That tree has a standard name — the state-space tree — whose root is the empty partial solution, whose internal nodes are partial solutions, and whose leaves are complete solutions and dead ends; backtracking is depth-first traversal of the state-space tree with the subtrees below dead ends never generated. Nothing shrinks in the divide-and-conquer sense; what shrinks is the number of decisions left to make, which is what guarantees termination.

Why the undo step is free in recursive form

The line that makes backtracking work is "undo e". In a recursive formulation, most of the undoing happens automatically: anything stored in local variables disappears when the frame is popped, so the state the caller sees is the state it had. Only mutations to a shared structure — a board, a partial assignment, a visited set — have to be undone explicitly, and that is the one place backtracking code reliably goes wrong. Two implementation styles: mutate and undo, which is fast and needs a matching undo for every mutation, or copy the state into each child, which cannot be got wrong and costs a copy per node. The mutate-and-undo style is standard, and the discipline is to write the undo on the line immediately after the recursive call, every time, before writing anything else.

Where the speed comes from: the prune, not the recursion

A backtracking search that never prunes is exhaustive enumeration, and its cost is the full size of the search space — which is exponential. Every bit of the speed-up comes from abandoning a subtree without exploring it, and the value of a prune is the entire subtree it removes, which for a prune near the root is almost everything. Two kinds are worth distinguishing. A feasibility prune rejects a partial solution that violates a constraint — no completion can repair it, so the whole subtree is provably empty. A bound prune rejects a partial solution that could be completed but cannot beat the best complete solution already found; that is branch and bound (§26), and it needs an optimisation objective, whereas a feasibility prune does not.

The design decisions that actually change the running time

  • Test constraints as early as possible. Checking validity when the solution is complete is generate-and-test, and explores the whole space. Checking after every single decision — incrementally, against the choices already made — is what makes the tree small. The difference is not a constant factor.
  • Order the variables. Choosing next the variable with the fewest remaining legal values fails fastest and therefore prunes highest in the tree. This one heuristic is often worth more than any amount of micro-optimisation.
  • Order the values. Trying the most promising value first finds a solution sooner, which matters when you only want one — and, in branch and bound, gives a good incumbent early, which makes every later bound prune more effective.
  • Exploit symmetry. If the problem has symmetries, exploring one representative of each symmetry class divides the work by the size of the symmetry group. For the eight-queens problem the board's eight symmetries reduce 92 solutions to 12 essentially different ones.
  • Keep incremental state. Maintaining sets of used rows and used diagonals turns an O(k) safety check at depth k into O(1). This is a constant-factor change, but on an exponential tree the constants are what you can actually control.
Where backtracking sits. It is the standard approach to constraint satisfaction — puzzles, scheduling, graph colouring, satisfiability — to enumeration problems (§25), and to path-finding in an implicit graph such as a maze, where the "choices" are the directions you can move and the "undo" is stepping back. It is also the honest answer for problems with no known polynomial algorithm: you cannot avoid the exponent, so you attack the constant and the pruning, and you stop when the answer is good enough.

The diagonal test, and a 4×4 board traced to its first backtrack

Two queens at (c₁, r₁) and (c₂, r₂) share a diagonal exactly when they are the same number of steps apart horizontally and vertically, that is when |r₁ − r₂| = |c₁ − c₂|. Both diagonal directions are covered by the absolute values, which is why one line suffices where a naive treatment writes two. Now trace a 4×4 board, columns and rows numbered from 0, with the search trying rows in increasing order. It places a queen at (0, 0). In column 1, row 0 shares a row and rows 1 fails the diagonal test — |1 − 0| = 1 = |1 − 0| — so the first legal square is (1, 2). Now look at column 2: row 0 shares a row with (0, 0); row 2 shares a row with (1, 2); row 1 is diagonal to (1, 2) because |1 − 2| = 1 = |2 − 1|; and row 3 is diagonal to (1, 2) for the same reason, |3 − 2| = 1 = |2 − 1|. Every square in column 2 is attacked, so the entire subtree below the partial solution [0, 2] is empty and is abandoned without being explored — that is the prune, and the four rejected squares are all the evidence the search needs to discard every completion of a two-queen prefix.

The recursion then backtracks: it undoes the queen in column 1 and tries its next row. (1, 3) is legal, column 2 accepts row 1, and column 3 is then entirely attacked — rows 0 and 3 by row conflicts, row 1 by a row conflict with column 2, and row 2 by the diagonal |2 − 1| = 1 = |3 − 2|. Backtrack again; column 2 has no further legal rows (row 2 is diagonal to (0, 0), since |2 − 0| = 2 = |2 − 0|, and row 3 shares a row with column 1); backtrack again; column 1 is exhausted; backtrack to column 0 and try row 1. From there the search runs straight down — (1, 3), then (2, 0), then (3, 2) — and records the first solution, rows [1, 3, 0, 2]. A handful of rejected squares and a few backtracks have eliminated the entire branch in which column 0's queen sits in row 0 — a quarter of the 256 row assignments — without ever completing one of them; the figure below counts exactly how many attempts, prunes and backtracks the whole search performs.

So the constraint-checking recursion visits about one node for every eight thousand placements the unconstrained enumeration would consider. That ratio is not a constant; it grows with n, which is why pruning is the only thing that makes an exponential search practical at all — and why the search is still exponential, so that the ratio growing is not the same as the problem becoming easy.

Two honest qualifications

  • Pruning does not change the complexity class. The number of nodes explored still grows faster than any polynomial in n on this problem; better pruning multiplies the tractable range by a modest factor, it does not make the search polynomial. The measured node counts over the range the slider covers are 17, 54, 153, 552, 2057, which is a factor of 3.2, 2.8, 3.6 and 3.7 from one n to the next — call it roughly three-and-a-half per unit increase in n, with the ratio itself drifting upward rather than settling, which is what an exponential with a growing base looks like. The figure stops at n = 8 for exactly that reason.
  • Counting solutions and finding one are different problems. Finding a single solution for large n is easy — explicit constructions are known that place n non-attacking queens directly for every n ≥ 4, with no search at all. What is hard, and what the figure measures, is enumerating all of them. Conflating the two makes the exponential look avoidable when it is not.
The general shape. A backtracking search is characterised by three numbers: the depth (here n, one decision per column), the branching factor (here at most n, and far less after pruning), and the node count, which is the only one you cannot predict from the problem statement and the only one that determines the running time. Measure it. A pruning idea that sounds clever and does not reduce the measured node count is not an optimisation.

25 Subsets, permutations, and the size of the search space

Before pruning can be assessed, the unpruned space has to be counted. Two implementation notes that matter more than they look

  • Emit, do not accumulate. Building a list of all 2ⁿ subsets costs Θ(n·2ⁿ) memory; yielding each one as it is produced costs Θ(n). For any n large enough for the time to matter, the memory matters first, so the generator form is not a stylistic preference.
  • Subsets have a non-recursive form. Each subset corresponds to an n-bit integer, so counting from 0 to 2ⁿ − 1 and reading the bits enumerates all of them with no recursion and no stack — and consecutive integers differ in few bits, which a Gray-code ordering sharpens to exactly one bit per step, making each subset an incremental edit of the last. That is the natural fit for search problems where evaluating a subset is expensive but updating an evaluation is cheap.
The estimate to make before writing the search. Count the leaves: is it 2ⁿ, n!, kⁿ, or something else? Multiply by the work per leaf. If the product is beyond reach, no amount of code quality will rescue it, and the real options are pruning (§23, §26), an approximation, a dynamic-programming reformulation if the subproblems overlap, or accepting a heuristic answer. Writing the search first and discovering this afterwards is the expensive order, and it is the failure Algorithm Analysis, §02, opens with.

26 Branch and bound: pruning with a number instead of a rule

Backtracking prunes a subtree when it is infeasible. Branch and bound prunes a subtree when it is feasible but provably not good enough. It applies to optimisation rather than to satisfaction, and it needs one extra ingredient: a function that, given a partial solution, computes an optimistic bound on the best objective value any completion of it could achieve. If that optimistic bound is no better than the best complete solution already in hand, the entire subtree can be discarded, because even in the best case it contains nothing worth having.

the two ingredientsINCUMBENT the best complete solution found so far (its value: best) BOUND(p) an OPTIMISTIC estimate of the best value reachable from partial p — for a maximisation, bound(p) ≥ true best completion of p — for a minimisation, bound(p) ≤ true best completion of p the prunemaximising: if bound(p) ≤ best: discard the whole subtree below p minimising: if bound(p) ≥ best: discard the whole subtree below p the one property the bound MUST haveit must never be pessimistic — never worse than the true best completion — or the prune discards a subtree that contained the optimum, and the answer is WRONG (a bound that is optimistic but loose is merely slow; one that is pessimistic is incorrect) the tensiontighter bound → prunes more subtrees → fewer nodes, but more work per node looser bound → cheap per node → more nodes the right choice is measured, not argued

Worked in miniature: the 0/1 knapsack, with the arithmetic done

Items have weights and values; choose a subset of maximum total value subject to a weight capacity. Branch on one item at a time — take it or leave it, the subset tree of §25. For a partial choice, an optimistic bound is the value already committed plus the value obtained by filling the remaining capacity fractionally with the remaining items in decreasing value-per-weight order. That relaxation allows something the real problem does not — cutting an item in half — so its optimum is at least the true optimum of any completion, which is exactly the "never pessimistic" requirement. It is also computable in linear time after one sort. Here is the whole thing on three items.

Two lessons are visible in six lines. The leave-A-out prune is the real thing: one bound computation, evaluated before any of that subtree existed, disposes of half the search space and provably loses nothing. The leave-B node is the honest other half of the story — its bound of 17.5 exceeds the incumbent by half a unit, so the search must descend into a subtree that turns out to contain nothing, and no amount of correct reasoning about bounds prevents that. A bound prunes only when it is tight enough to fall below the incumbent; being valid is necessary and not sufficient. With items sorted by density and a decent incumbent found early by taking greedily, the fractional bound prunes enormously; with a weak bound, such as "the remaining capacity times the best density in the whole instance", the same search degenerates towards enumerating all 2ⁿ subsets.

Three things that decide how well it works

  • Getting a good incumbent early. The prune compares against best, so until a good complete solution exists nothing prunes. Running a fast greedy heuristic first, or exploring the most promising branch first (depth-first with a value-ordering heuristic), pays for itself immediately.
  • The order in which nodes are expanded. Depth-first uses O(depth) memory and finds complete solutions quickly. Best-first — expand the node with the most promising bound, using a priority queue — explores the fewest nodes in theory but can hold exponentially many of them in memory. Real solvers use hybrids for exactly this reason: node count and memory are in direct tension.
  • The bound's tightness versus its cost. A bound that takes ten times as long but halves the tree is a win only if the tree was more than ten times bigger than the per-node work. This is a measurement, and it is why solver development is dominated by benchmarking rather than by proofs.

What it does and does not promise

Branch and bound is exact: when it terminates, the incumbent is optimal, and this follows from the never-pessimistic property — every discarded subtree provably contained nothing better. That distinguishes it from a heuristic search, which returns something good with no guarantee. What it does not promise is a running time: the worst case is still the whole tree — an instance on which every bound exceeds the incumbent explores every node — and for the problems branch and bound is aimed at, no algorithm with a better than exponential worst case is known, which is a statement about the state of knowledge and not a proved lower bound. In practice a good bound turns "impossible" into "minutes" on real instances while leaving contrived worst cases untouched — which is the honest description of essentially every practical exact method for a hard problem.

Same idea, different clothes. Alpha-beta pruning in game-tree search is branch and bound with two bounds, one per player. A best-first search guided by an admissible heuristic — never overestimating the remaining cost — is the same "optimistic estimate" requirement, and "admissible" is precisely "never pessimistic". Constraint propagation in a solver is a feasibility prune made stronger by deducing consequences before branching. The common structure is always: recursion over choices, plus a cheap argument that a whole region contains nothing you want.

Las Vegas, not Monte Carlo

The standard vocabulary for randomized algorithms splits them in two, and randomized quicksort is squarely on one side of the line. A Las Vegas algorithm is always correct and its running time is the random variable: it flips coins, it may be lucky or unlucky, and when it stops the answer is right. A Monte Carlo algorithm has a running time you can bound outright and its answer is the random variable: it may be wrong, with a probability you control. Randomized quicksort, randomized quickselect (§28) and randomized incremental geometry are all Las Vegas — a bad run costs you time, never correctness, which is why the figure below can verify every single output and still find something interesting to plot. Primality tests of the repeated-witness kind and the sketching algorithms used on data streams are Monte Carlo. The distinction matters because it decides what "it failed" can mean: for a Las Vegas algorithm, only "it took too long", and a Monte Carlo algorithm can always be built from it by simply stopping early and returning whatever you have.

Why that indicator argument is the whole proof

Two elements are compared only against a pivot, and only while they are still in the same subarray. Once a pivot lands strictly between them, they are separated forever and never meet. So the pair (zᵢ, zⱼ) is compared exactly when the first pivot drawn from the value range zᵢ … zⱼ is one of the two endpoints — probability 2/(j − i + 1) — and never compared otherwise. Summing that over all pairs gives the harmonic sum above, and it is worth noticing that no recurrence was solved: linearity of expectation turns a question about a random recursion tree into a sum of n(n−1)/2 little probabilities — which need not be independent, because linearity of expectation does not require independence, and that is precisely why the argument is so short.

At n = 3 the whole thing fits on a page and the two routes have to agree. By enumeration: the first pivot is equally likely to be the smallest, middle or largest of the three. A pivot of 3 elements always costs 2 comparisons. If it is the smallest or the largest (probability 2/3) one side is empty and the other has 2 elements, costing 1 more — total 3. If it is the middle (probability 1/3) both sides are singletons and cost nothing — total 2. So E = (2/3)·3 + (1/3)·2 = 2 + 2/3 = 8/3 ≈ 2.667. What randomization does and does not guarantee

  • It moves the randomness from the input to the algorithm. A deterministic pivot rule has bad inputs — first-element pivot is quadratic on already-sorted data, which is the single most common real input. A randomized pivot has no bad inputs at all: the expectation is over the algorithm's own coin flips, so the same input can be run twice and give different costs, and no adversary who knows your code can construct a slow case, only an adversary who can see your random numbers.
  • The worst case is still quadratic. Randomization changes its probability, not its existence. The probability of a genuinely quadratic run falls off very fast in n — the exactly-worst run, in which every pivot is an extreme, has probability on the order of 2ⁿ⁻¹/n!, which for n in the thousands is smaller than any number you have a use for — but it is not zero, and for small n it is not even small. The "less likely than the machine failing" line you will hear is folklore rather than a theorem, and it is only about large n. What is a theorem is the concentration: the probability that the comparison count exceeds a constant multiple of n log n is polynomially small in n. Either way, describing quicksort as "n log n" without the word expected is the most common misstatement about it.
  • Balance is cheap to buy. A pivot anywhere in the middle half of the values splits at worst 1:3, and T(n) = T(n/4) + T(3n/4) + Θ(n) is still Θ(n log n). Half of all pivots are that good, so on average every other level of the recursion is a good split — which is the intuitive form of the proof and the reason the constant is only about 1.39 times the perfectly-balanced one.
  • The depth still needs guarding. Expected depth is Θ(log n), but a bad run can be deep, so the "recurse on the smaller side, loop on the larger" rule of §06 is applied anyway: it caps the stack at O(log n) deterministically, regardless of how the pivots fall.
Randomization as a design tool. The same move — replace a structural assumption with a random choice and analyse the expectation — appears throughout: randomized incremental construction in computational geometry, hash functions chosen from a family to defeat adversarial keys, sampling-based selection, and randomized algorithms for problems where no efficient deterministic method is known. The analysis technique is always the one used above: define indicator variables for the events you can price, and sum their expectations.

The geometric-series intuition, made explicit

Each round costs Θ(n) for the partition and then works on a strictly smaller array. If every round shrank the array by a constant factor c < 1, the total would be n + cn + c²n + … = n/(1 − c) — a constant multiple of n, not n log n, because the sizes form a geometric series rather than a sum of log n equal terms. That single observation is the whole difference between selection and sorting: quicksort's two calls make the level sizes sum to n at every level, so the levels do not shrink and you pay n per level for log n levels; quickselect's one call makes the total work itself geometric. Discarding half the problem is worth a whole logarithmic factor.

Why the magic number five

The deterministic version picks its pivot by splitting the input into groups of five, taking each group's median, and recursively selecting the median of those medians. That pivot is guaranteed to be greater than at least about 3n/10 elements and less than at least about 3n/10, so each recursive call handles at most about 7n/10 — and the pivot-finding call handles n/5. The recurrence works because 1/5 + 7/10 = 9/10 < 1; with groups of three the arithmetic becomes 1/3 + 2/3 = 1, the fractions no longer sum to less than one, and the recurrence solves to Θ(n log n) instead. Among odd group sizes, five is the smallest that makes the sum of the fractions strictly less than one for this algorithm, and that strict inequality is the entire proof. Read that as a statement about the recurrence and not as a lower bound: it says the straightforward groups-of-three version of this particular routine is Θ(n log n), not that no linear-time selection algorithm can use groups of three — more elaborate arrangements that do are known. Odd sizes are preferred only because an odd group has an unambiguous median; the constant is what rules out larger groups, since the cost of finding each group's median grows while the guaranteed split improves only marginally. The solution of that recurrence, which lies outside the Master theorem, is worked through in Algorithm Analysis, §17.

Which one to use

  • Randomized selection in practice, essentially always. Its constant is small — switch the figure in §27 to selection mode and the measured mean comparisons for finding a median are about 3.4·n at n = 1000, against the 4n bound the good-pivot argument proves — and its code is a loop around a partition.
  • Median-of-medians when a worst-case guarantee is required, or as the fallback in a hybrid that starts randomized and switches if it is taking too long. Its constant is large enough that it is rarely the fastest choice on real data; its value is the theorem.
  • Neither, if you need many order statistics. Sorting once costs Θ(n log n) and then every query is O(1) — the same "sort once, query many" trade as §15.
The result worth remembering. The median can be found in Θ(n) time in the worst case, without sorting and without any assumption about the data. That is genuinely surprising — it says finding the middle element is strictly easier than arranging all of them — and it is the reason the Ω(n log n) comparison lower bound applies to sorting and not to every question you might ask about order. The wider family of order-statistic problems is taken up in Sorting & Searching.

Every entry below is a specific failure this page has an argument against, ordered roughly from the ones that produce wrong answers to the ones that only produce slow ones. The wrong-answer group is first because it is the group that passes a casual test.

Confusing the number of pieces with the number recursed intob is how the instance is cut; a is how many pieces you solve. Binary search has b = 2 and a = 1, and calling it a = 2 predicts Θ(n).Count the recursive calls, not the pieces (§12).

The two habits that prevent most of this. First, write the measure and the base cases before the recursive case; the wrong-answer failures above are almost all failures of one or the other. Second, keep the obvious slow version and compare against it — exhaustive search, the recursive original, the unoptimised merge. Several of this page's figures do exactly that, and it is the cheapest correctness check available for an algorithm whose whole point is that it is not obvious.

Which paradigm is this?

  • Subproblems are disjoint pieces of the input, and the combine is cheap → divide and conquer. Write the recurrence first.
  • Subproblems overlap → dynamic programming. Count the distinct states; the running time is states × transition cost.
  • Subproblems are choices, and most of them are dead ends → backtracking. The running time is the size of the pruned tree, and it must be measured.
  • Choices plus an objective, and a cheap optimistic estimate exists → branch and bound. The bound must never be pessimistic.
  • The answer for a prefix extends in O(1) → a single scan. Do not recurse at all.
  • One subproblem can be proved irrelevant → the a = 1 family: binary search, quickselect, exponentiation by squaring. This is where the logarithms and the linear-time selections come from.

Numbers this page measured

  • Naive fib(n): 2·F(n+1) − 1 invocations, height n, only n + 1 distinct subproblems. At n = 20, 21,891 invocations against 39 for the memoized version.
  • Mergesort at n = 8: 17 comparisons and 24 element moves on the worked input, 12 on both sorted and reverse-sorted input; the exact worst case n·ceil(log₂n) − 2^ceil(log₂n) + 1 is 17 at n = 8 and 49 at n = 16. Over all 40,320 permutations of eight distinct keys the count is 16 most often (38.1%), 17 a quarter of the time (25.4%), and never outside 12…17.
  • Maximum subarray: divide and conquer, exhaustive search and the linear scan all return A[7..10] with sum 43 on the sixteen-value example; the recursion's crossing scans make n inspections per level.
  • Karatsuba: 9 single-digit multiplications against schoolbook's 16 on 1234 × 5678; measured exponents 1.585 and 2.000 at 128 digits.
  • Strassen at a cutoff of 8: total scalar operations first favour it at n = 16 (7,872 against 7,936); at n = 64, 436,416 against 520,192. With no cutoff it loses on total operations throughout the measured range.
  • n-queens at n = 8: 2,057 nodes explored, 13,664 squares pruned, 92 solutions, against 8⁸ = 16,777,216 unpruned row assignments.
  • Randomized quicksort: measured mean comparisons track 2(n+1)Hₙ − 4n to within a couple of percent at the default 40 runs per size — the largest gap over the seven sizes is about 2.5%, and it shrinks as the runs-per-size slider is raised, which is what sampling error is supposed to do. Quickselect for the median measures about 3.4n at n = 1000, inside the 4n bound and close to the known 2(1 + ln 2)·n ≈ 3.39n.
