23 Backtracking: recursion over a tree of choices

Backtracking is a systematic search of a space of partial solutions, built one decision at a time, in which a partial solution that cannot possibly be completed is abandoned immediately and the search returns to the last decision point to try the next alternative. It is recursion whose tree is a decision tree rather than a partition of the input: the children of a node are the choices available at that point, not pieces of the data. That tree has a standard name — the state-space tree — whose root is the empty partial solution, whose internal nodes are partial solutions, and whose leaves are complete solutions and dead ends; backtracking is depth-first traversal of the state-space tree with the subtrees below dead ends never generated. Nothing shrinks in the divide-and-conquer sense; what shrinks is the number of decisions left to make, which is what guarantees termination.

the templatesearch(partial): if partial is a complete solution: record it; return if partial cannot be extended to any solution: return ← THE PRUNE for each candidate extension e of partial: apply e to partial ← make the choice search(partial) ← recurse undo e ← UNMAKE the choice, and try the next the two costs, which are entirely differentdepth = the number of decisions — usually small and obvious nodes = the size of the explored tree — depends on the prune, and is the whole story the termination measureμ = number of unassigned variables, which drops by exactly one per level ⇒ backtracking ALWAYS terminates; it is the running time that is in doubt

Why the undo step is free in recursive form

The line that makes backtracking work is "undo e". In a recursive formulation, most of the undoing happens automatically: anything stored in local variables disappears when the frame is popped, so the state the caller sees is the state it had. Only mutations to a shared structure — a board, a partial assignment, a visited set — have to be undone explicitly, and that is the one place backtracking code reliably goes wrong. Two implementation styles: mutate and undo, which is fast and needs a matching undo for every mutation, or copy the state into each child, which cannot be got wrong and costs a copy per node. The mutate-and-undo style is standard, and the discipline is to write the undo on the line immediately after the recursive call, every time, before writing anything else.

Where the speed comes from: the prune, not the recursion

A backtracking search that never prunes is exhaustive enumeration, and its cost is the full size of the search space — which is exponential. Every bit of the speed-up comes from abandoning a subtree without exploring it, and the value of a prune is the entire subtree it removes, which for a prune near the root is almost everything. Two kinds are worth distinguishing. A feasibility prune rejects a partial solution that violates a constraint — no completion can repair it, so the whole subtree is provably empty. A bound prune rejects a partial solution that could be completed but cannot beat the best complete solution already found; that is branch and bound (§26), and it needs an optimisation objective, whereas a feasibility prune does not.

The design decisions that actually change the running time

  • Test constraints as early as possible. Checking validity when the solution is complete is generate-and-test, and explores the whole space. Checking after every single decision — incrementally, against the choices already made — is what makes the tree small. The difference is not a constant factor.
  • Order the variables. Choosing next the variable with the fewest remaining legal values fails fastest and therefore prunes highest in the tree. This one heuristic is often worth more than any amount of micro-optimisation.
  • Order the values. Trying the most promising value first finds a solution sooner, which matters when you only want one — and, in branch and bound, gives a good incumbent early, which makes every later bound prune more effective.
  • Exploit symmetry. If the problem has symmetries, exploring one representative of each symmetry class divides the work by the size of the symmetry group. For the eight-queens problem the board's eight symmetries reduce 92 solutions to 12 essentially different ones.
  • Keep incremental state. Maintaining sets of used rows and used diagonals turns an O(k) safety check at depth k into O(1). This is a constant-factor change, but on an exponential tree the constants are what you can actually control.
Where backtracking sits. It is the standard approach to constraint satisfaction — puzzles, scheduling, graph colouring, satisfiability — to enumeration problems (§25), and to path-finding in an implicit graph such as a maze, where the "choices" are the directions you can move and the "undo" is stepping back. It is also the honest answer for problems with no known polynomial algorithm: you cannot avoid the exponent, so you attack the constant and the pruning, and you stop when the answer is good enough.

24 n-queens, and how much the prune is worth

Place n queens on an n × n board so that no two attack each other — no shared row, column or diagonal. The problem is the standard demonstration of backtracking because each of its three constraints eliminates a different and easily-counted part of the search space, so the value of each pruning idea can be measured exactly.

three ways to describe the same search spaceevery square independently C(n², n) placements — n = 8: 4,426,165,368 one queen per column, any row nⁿ — n = 8: 16,777,216 one queen per column, distinct rows n! — n = 8: 40,320 what backtracking actually visits measured by the figure — n = 8: 2,057 nodes the representation that bakes in two constraints for freecol[c] = the row of the queen in column c ← one queen per column, automatically enforce col[c] ≠ col[k] ← no shared row enforce |col[c] − col[k]| ≠ |c − k| ← no shared diagonal: equal row-difference and column-difference IS the definition of a diagonal the recursionplace(c): if c = n: record a solution; return for r = 0 … n−1: if safe(c, r): col[c] = r; place(c + 1) ← recurse only when legal else: PRUNE — the entire subtree below (c, r) is skipped

The diagonal test, and a 4×4 board traced to its first backtrack

Two queens at (c₁, r₁) and (c₂, r₂) share a diagonal exactly when they are the same number of steps apart horizontally and vertically, that is when |r₁ − r₂| = |c₁ − c₂|. Both diagonal directions are covered by the absolute values, which is why one line suffices where a naive treatment writes two. Now trace a 4×4 board, columns and rows numbered from 0, with the search trying rows in increasing order. It places a queen at (0, 0). In column 1, row 0 shares a row and rows 1 fails the diagonal test — |1 − 0| = 1 = |1 − 0| — so the first legal square is (1, 2). Now look at column 2: row 0 shares a row with (0, 0); row 2 shares a row with (1, 2); row 1 is diagonal to (1, 2) because |1 − 2| = 1 = |2 − 1|; and row 3 is diagonal to (1, 2) for the same reason, |3 − 2| = 1 = |2 − 1|. Every square in column 2 is attacked, so the entire subtree below the partial solution [0, 2] is empty and is abandoned without being explored — that is the prune, and the four rejected squares are all the evidence the search needs to discard every completion of a two-queen prefix.

The recursion then backtracks: it undoes the queen in column 1 and tries its next row. (1, 3) is legal, column 2 accepts row 1, and column 3 is then entirely attacked — rows 0 and 3 by row conflicts, row 1 by a row conflict with column 2, and row 2 by the diagonal |2 − 1| = 1 = |3 − 2|. Backtrack again; column 2 has no further legal rows (row 2 is diagonal to (0, 0), since |2 − 0| = 2 = |2 − 0|, and row 3 shares a row with column 1); backtrack again; column 1 is exhausted; backtrack to column 0 and try row 1. From there the search runs straight down — (1, 3), then (2, 0), then (3, 2) — and records the first solution, rows [1, 3, 0, 2]. A handful of rejected squares and a few backtracks have eliminated the entire branch in which column 0's queen sits in row 0 — a quarter of the 256 row assignments — without ever completing one of them; the figure below counts exactly how many attempts, prunes and backtracks the whole search performs.

n-queens by backtracking — every attempt, every prune and every backtrack, counted green ring = a legal placement, red cross = a pruned attempt, and the subtree it removed

At the default n = 4 the whole search is 78 events long and you can watch every one of them: 17 recursive calls, 44 squares rejected by the safety test, 16 placements each later undone, and 2 solutions — out of 4⁴ = 256 row assignments, so about one node explored per fifteen assignments. Now push the slider, and the table becomes the pruning argument as arithmetic. At n = 8 the measured search explores 2,057 nodes and rejects 13,664 individual placements to find all 92 solutions — against a space of 8⁸ = 16,777,216 row assignments, or 8! = 40,320 once distinct rows are forced. So the constraint-checking recursion visits about one node for every eight thousand placements the unconstrained enumeration would consider. That ratio is not a constant; it grows with n, which is why pruning is the only thing that makes an exponential search practical at all — and why the search is still exponential, so that the ratio growing is not the same as the problem becoming easy.

Two honest qualifications

  • Pruning does not change the complexity class. The number of nodes explored still grows faster than any polynomial in n on this problem; better pruning multiplies the tractable range by a modest factor, it does not make the search polynomial. The measured node counts over the range the slider covers are 17, 54, 153, 552, 2057, which is a factor of 3.2, 2.8, 3.6 and 3.7 from one n to the next — call it roughly three-and-a-half per unit increase in n, with the ratio itself drifting upward rather than settling, which is what an exponential with a growing base looks like. The figure stops at n = 8 for exactly that reason.
  • Counting solutions and finding one are different problems. Finding a single solution for large n is easy — explicit constructions are known that place n non-attacking queens directly for every n ≥ 4, with no search at all. What is hard, and what the figure measures, is enumerating all of them. Conflating the two makes the exponential look avoidable when it is not.
The general shape. A backtracking search is characterised by three numbers: the depth (here n, one decision per column), the branching factor (here at most n, and far less after pruning), and the node count, which is the only one you cannot predict from the problem statement and the only one that determines the running time. Measure it. A pruning idea that sounds clever and does not reduce the measured node count is not an optimisation.

25 Subsets, permutations, and the size of the search space

Before pruning can be assessed, the unpruned space has to be counted. Two recursions cover most enumeration problems, and their sizes are the two numbers every exponential-search estimate is built from: 2ⁿ subsets of an n-element set and n! permutations. Both are generated by multiple recursion, and in both cases the tree is larger than the set of answers — which is the quantity that actually costs you time.

subsets — one binary decision per elementsubsets(i, chosen): if i = n: emit chosen; return subsets(i+1, chosen) ← leave element i out subsets(i+1, chosen ∪ {i}) ← take element i in results = 2ⁿ tree nodes = 1 + 2 + 4 + … + 2ⁿ = 2ⁿ⁺¹ − 1 depth = n + 1 permutations — choose which element comes nextperms(prefix, remaining): if remaining is empty: emit prefix; return for each e in remaining: perms(prefix + e, remaining − {e}) results = n! nodes at level k = n!/(n−k)! tree nodes = ∑ (k = 0 … n) n!/(n−k)! = ∑ (j = 0 … n) n!/j! = floor(e·n!) for n ≥ 1 depth = n + 1, and e = 2.71828… so the tree is about 2.72× the number of answers the numbers, to calibrate intuitionn: 10 20 30 50 2ⁿ: 1,024 1,048,576 1.07×10⁹ 1.13×10¹⁵ n!: 3,628,800 2.43×10¹⁸ 2.65×10³² 3.04×10⁶⁴

That last block is the point of the section. An exponential and a factorial are not the same kind of hopeless. Enumerating all subsets of 30 items is about a billion operations — a few seconds, entirely feasible. Enumerating all permutations of 30 items is 2.65 × 10³², which is not feasible on any machine that will ever exist. Subset enumeration stays tractable to around n = 25–30; permutation enumeration stops being tractable somewhere around n = 12, where 12! ≈ 4.8 × 10⁸. Knowing which of the two your search space is tells you immediately whether pruning might save you or whether you need a different algorithm entirely.

The enumeration trees, drawn and counted — results at the leaves, cost at every node above about eighty nodes the tree stops fitting and the figure reports nodes per level instead

At the default — subsets of a four-element set — the tree is drawn in full: 31 nodes producing 16 results, five levels deep, with the closed forms 2ⁿ⁺¹ − 1 and 2ⁿ confirmed level by level. Every node in the drawing is an invocation the real generator made, and the counts underneath are read off a counter threaded through it, then compared with the closed forms. The gap between leaves and nodes is the overhead the enumeration pays for its own bookkeeping: for subsets it is a factor of just under two — (2ⁿ⁺¹ − 1)/2ⁿ → 2 — and for permutations a factor approaching e ≈ 2.718. Neither factor grows with n, which is the reassuring part: enumeration is optimal up to a constant, and if the answer set really is exponential there is nothing to fix at this level. The only leverage is to avoid enumerating the whole set, which is what §23's pruning and §26's bounding do.

Two implementation notes that matter more than they look

  • Emit, do not accumulate. Building a list of all 2ⁿ subsets costs Θ(n·2ⁿ) memory; yielding each one as it is produced costs Θ(n). For any n large enough for the time to matter, the memory matters first, so the generator form is not a stylistic preference.
  • Subsets have a non-recursive form. Each subset corresponds to an n-bit integer, so counting from 0 to 2ⁿ − 1 and reading the bits enumerates all of them with no recursion and no stack — and consecutive integers differ in few bits, which a Gray-code ordering sharpens to exactly one bit per step, making each subset an incremental edit of the last. That is the natural fit for search problems where evaluating a subset is expensive but updating an evaluation is cheap.
The estimate to make before writing the search. Count the leaves: is it 2ⁿ, n!, kⁿ, or something else? Multiply by the work per leaf. If the product is beyond reach, no amount of code quality will rescue it, and the real options are pruning (§23, §26), an approximation, a dynamic-programming reformulation if the subproblems overlap, or accepting a heuristic answer. Writing the search first and discovering this afterwards is the expensive order, and it is the failure Algorithm Analysis, §02, opens with.

26 Branch and bound: pruning with a number instead of a rule

Backtracking prunes a subtree when it is infeasible. Branch and bound prunes a subtree when it is feasible but provably not good enough. It applies to optimisation rather than to satisfaction, and it needs one extra ingredient: a function that, given a partial solution, computes an optimistic bound on the best objective value any completion of it could achieve. If that optimistic bound is no better than the best complete solution already in hand, the entire subtree can be discarded, because even in the best case it contains nothing worth having.

the two ingredientsINCUMBENT the best complete solution found so far (its value: best) BOUND(p) an OPTIMISTIC estimate of the best value reachable from partial p — for a maximisation, bound(p) ≥ true best completion of p — for a minimisation, bound(p) ≤ true best completion of p the prunemaximising: if bound(p) ≤ best: discard the whole subtree below p minimising: if bound(p) ≥ best: discard the whole subtree below p the one property the bound MUST haveit must never be pessimistic — never worse than the true best completion — or the prune discards a subtree that contained the optimum, and the answer is WRONG (a bound that is optimistic but loose is merely slow; one that is pessimistic is incorrect) the tensiontighter bound → prunes more subtrees → fewer nodes, but more work per node looser bound → cheap per node → more nodes the right choice is measured, not argued

Worked in miniature: the 0/1 knapsack, with the arithmetic done

Items have weights and values; choose a subset of maximum total value subject to a weight capacity. Branch on one item at a time — take it or leave it, the subset tree of §25. For a partial choice, an optimistic bound is the value already committed plus the value obtained by filling the remaining capacity fractionally with the remaining items in decreasing value-per-weight order. That relaxation allows something the real problem does not — cutting an item in half — so its optimum is at least the true optimum of any completion, which is exactly the "never pessimistic" requirement. It is also computable in linear time after one sort. Here is the whole thing on three items.

the instancecapacity W = 10 weight value density A 5 10 2.00 ← sort by density, descending B 4 7 1.75 C 6 9 1.50 true optimum (by inspection of all 8 subsets): {A, B}, weight 9, value 17 — {A,C} weighs 11 and {A,B,C} weighs 15, both infeasible; {B,C} weighs 10, value 16 the incumbent, from a greedy pass before any branchingtake A (5 left), take B (1 left), C does not fit ⇒ best = 17 the root bound — fractional fillA whole (10) + B whole (7) + 1/6 of C (1.5) = 18.5 ≥ 17 ✓ never pessimistic branch on A, and watch one subtree dieLEAVE A OUT: capacity 10, items {B, C} bound = 7 + 9 = 16 (B and C together weigh exactly 10) 16 ≤ best = 17 ⇒ PRUNE — 4 of the 8 leaves never generated, and correctly so: the best in that subtree really is 16 TAKE A: committed 10, capacity 5, items {B, C} bound = 10 + 7 + (1/6)·9 = 18.5 > 17 ⇒ explore ├ take B: value 17, capacity 1, C does not fit ⇒ 17, ties the incumbent └ leave B: value 10, capacity 5, bound = 10 + (5/6)·9 = 17.5 > 17 ⇒ explore, C does not fit, leaf value 10 ← a bound too LOOSE to prune

Two lessons are visible in six lines. The leave-A-out prune is the real thing: one bound computation, evaluated before any of that subtree existed, disposes of half the search space and provably loses nothing. The leave-B node is the honest other half of the story — its bound of 17.5 exceeds the incumbent by half a unit, so the search must descend into a subtree that turns out to contain nothing, and no amount of correct reasoning about bounds prevents that. A bound prunes only when it is tight enough to fall below the incumbent; being valid is necessary and not sufficient. With items sorted by density and a decent incumbent found early by taking greedily, the fractional bound prunes enormously; with a weak bound, such as "the remaining capacity times the best density in the whole instance", the same search degenerates towards enumerating all 2ⁿ subsets.

Three things that decide how well it works

  • Getting a good incumbent early. The prune compares against best, so until a good complete solution exists nothing prunes. Running a fast greedy heuristic first, or exploring the most promising branch first (depth-first with a value-ordering heuristic), pays for itself immediately.
  • The order in which nodes are expanded. Depth-first uses O(depth) memory and finds complete solutions quickly. Best-first — expand the node with the most promising bound, using a priority queue — explores the fewest nodes in theory but can hold exponentially many of them in memory. Real solvers use hybrids for exactly this reason: node count and memory are in direct tension.
  • The bound's tightness versus its cost. A bound that takes ten times as long but halves the tree is a win only if the tree was more than ten times bigger than the per-node work. This is a measurement, and it is why solver development is dominated by benchmarking rather than by proofs.

What it does and does not promise

Branch and bound is exact: when it terminates, the incumbent is optimal, and this follows from the never-pessimistic property — every discarded subtree provably contained nothing better. That distinguishes it from a heuristic search, which returns something good with no guarantee. What it does not promise is a running time: the worst case is still the whole tree — an instance on which every bound exceeds the incumbent explores every node — and for the problems branch and bound is aimed at, no algorithm with a better than exponential worst case is known, which is a statement about the state of knowledge and not a proved lower bound. In practice a good bound turns "impossible" into "minutes" on real instances while leaving contrived worst cases untouched — which is the honest description of essentially every practical exact method for a hard problem.

Same idea, different clothes. Alpha-beta pruning in game-tree search (§28) is branch and bound with two bounds, one per player. A best-first search guided by an admissible heuristic — never overestimating the remaining cost — is the same "optimistic estimate" requirement, and "admissible" is precisely "never pessimistic". Constraint propagation in a solver is a feasibility prune made stronger by deducing consequences before branching. The common structure is always: recursion over choices, plus a cheap argument that a whole region contains nothing you want.

27 Game trees and minimax: backtracking against an opponent

In a two-player, zero-sum game of perfect information — each player sees the whole position, moves alternate, and one player's gain is exactly the other's loss — the value of a position under best play by both sides is defined by a recursion, and computing it is a depth-first search of the tree of moves. The game tree has positions as nodes and legal moves as edges; its leaves are finished games, each labelled with a payoff to the first player, conventionally called MAX. The opponent, MIN, wants that payoff as small as possible. Nothing about the search is new — it is §23's state-space tree, walked depth-first — but the rule for combining children is: at a node where MAX moves the value is the largest child value, and where MIN moves it is the smallest.

the minimax valueV(p) = utility(p) if p is a finished game V(p) = max over children c of V(c) if MAX is to move at p V(p) = min over children c of V(c) if MIN is to move at p the same thing as one function — negamaxscore every position from the point of view of the side to move; then N(p) = max over children c of −N(c) since max(x, y) = −min(−x, −y) what the value guaranteesMAX has a strategy that achieves at least V(root) against EVERY MIN strategy, and MIN has one that holds MAX to at most V(root) against every MAX strategy — finite game, perfect information: V(root) is the game's value (backward induction) the cost, for branching factor b and depth dtime = nodes of the tree = 1 + b + b² + … + bᵈ = (bᵈ⁺¹ − 1)/(b − 1) = Θ(bᵈ) space = Θ(d) frames, plus O(b) per frame if a move list is materialised — it is a DFS

Why the recursion is right, and why it is also useless as it stands

Correctness is induction on height, exactly as in §03. A leaf's value is its payoff by definition. At an internal MAX node, assume every child's value is correct — the payoff reached from that child when both sides play optimally thereafter; then MAX, choosing a move, can do no better than the best of those and can always achieve it, so the maximum is correct. The MIN case is the mirror image. The argument quietly assumes the opponent is optimal; against a weaker opponent minimax is still safe — it guarantees the value — but not necessarily the move that exploits the mistake.

Now the cost. Tic-tac-toe has at most 9! = 362,880 move sequences, and fewer actual games because many end early; exhaustive minimax over that is instant, and it proves the game a draw. Chess has an average branching factor in the region of thirty-five and games of eighty plies or more, so bᵈ is beyond any computation that will ever be run. For every interesting game, the exact minimax value is out of reach, and the recursion has to be cut off.

Depth-limited search and the evaluation function

The standard cut is to stop at a fixed depth d and replace the missing subtree by an evaluation function eval(p): a fast heuristic estimate of V(p), typically a weighted sum of features — material, mobility, king safety — tuned by hand or learned. The recursion is unchanged except for its base case, which now reads "if p is finished or the depth budget is spent, return eval(p)". What is computed is then the exact minimax value of the truncated tree with eval at its leaves, which is only as good as eval is at the frontier. Three standard refinements address where that goes wrong.

  • The horizon effect. A search to depth d cannot see a loss at depth d + 1, and a program will make pointless delaying moves that push an inevitable loss just past its horizon, where the evaluation cannot see it. No fixed depth cures this; it only moves the horizon.
  • Quiescence search. Evaluate only quiet positions. At the depth limit, if the position is in the middle of an exchange — a capture is pending — keep searching the forcing moves until it settles, then evaluate. This targets the cases where a static estimate is most wrong, at a cost confined to a narrow part of the tree.
  • Iterative deepening. Search to depth 1, then 2, then 3, … until the time runs out, and play the best move of the last completed iteration. The repeated work is small: the nodes of all shallower searches total about 1/(b − 1) of the last one's, so the overhead is a constant factor, b/(b − 1) — at most 2, and about 1.03 at b = 35. In return the search is anytime (it always has an answer), and each iteration's results tell the next one which moves to try first — which is exactly what §28 needs.
Where it sits. Minimax is backtracking (§23) with a different combine step, and like backtracking it is exact on the tree it searches and exponential in that tree's depth. The whole engineering problem of game search is therefore the one §23 and §26 already named: visit fewer nodes without changing the answer. For games where no good evaluation function is known, the modern alternative samples playouts instead of evaluating statically, and a learned value estimate can stand in for eval — the bridge to reinforcement learning, whose Bellman backup is minimax's max over a single agent.

28 Alpha-beta pruning: the (α, β) window, and why move order is everything

Alpha-beta computes exactly the minimax value while skipping subtrees that provably cannot affect it. It is §26's branch and bound with two incumbents, one per player: α is the best value MAX is already guaranteed along the current path, β the best value MIN is already guaranteed. A node whose value is certain to fall outside the window (α, β) is irrelevant — one of the players has a better option earlier on the path and will never allow play to reach it — so the rest of its children need not be searched.

the algorithmalphabeta(p, depth, α, β, maximising): if depth = 0 or p is finished: return eval(p) if maximising: v = −∞ for each child c: v = max(v, alphabeta(c, depth−1, α, β, false)) α = max(α, v) if α ≥ β: break ← β-cutoff: MIN above will never let play get here return v else: v = +∞ for each child c: v = min(v, alphabeta(c, depth−1, α, β, true)) β = min(β, v) if α ≥ β: break ← α-cutoff: MAX above already has something better return v root call: alphabeta(root, d, −∞, +∞, true) the window invariant — what a call returns, given (α, β) with α < βif α < V(p) < β: returns exactly V(p) if V(p) ≤ α: returns some v with V(p) ≤ v ≤ α ("fails low": an upper bound) if V(p) ≥ β: returns some v with β ≤ v ≤ V(p) ("fails high": a lower bound) ⇒ with the full window (−∞, +∞) the first case always holds, so the root value is EXACT

A worked example, nine leaves

MAX at the root, three MIN children, three leaves each: [4, 9, 6], [2, 7, 5], [10, 3, 1]. Minimax gives the MIN nodes 4, 2, 1 and the root 4, after evaluating all nine leaves. Alpha-beta searches the first child completely — it has to, to learn that it is worth 4 — and the root's α becomes 4. The second child is entered with the window (4, +∞); its first leaf is 2, so this MIN node is worth at most 2, and β = 2 ≤ α = 4: MAX already has 4 available and will never choose a move MIN can hold to 2 or less, so the leaves 7 and 5 are cut. The third child sees 10 (its value is now at most 10, no cut), then 3 (at most 3 ≤ 4, cut), and the leaf 1 is skipped. Six leaves evaluated instead of nine, and the root value 4 is the same. Had the third child's leaves come in the order [1, 3, 10], the first leaf would have cut immediately: five leaves. Nothing about the tree changed except the order in which children were tried.

Why the invariant holds

Induction on height again. At a MAX node, v only ever increases and α tracks max(α, v). If the loop finishes without a cut, every child was searched with a window at least as wide as (α, β) restricted to above the running v, and by the inductive hypothesis each child returned either its exact value or a bound on the side that cannot raise v, so v is exact whenever it lies in the window and an upper bound when it does not. If the loop breaks, v ≥ β and the true value is at least v — a lower bound, which is exactly the "fails high" case, and the MIN parent, holding β, will discard it. The MIN case is symmetric. The point to take away is that a returned value is only guaranteed to be exact inside the window it was searched with; outside it, it is a bound, and that distinction is what a transposition table must record (below).

With best move first the measured leaf count equals b^⌈d/2⌉ + b^⌊d/2⌋ − 1 exactly, on every tree and every shape in the menu — 11 of 27 leaves at b = 3, depth 3, and 17 of 81 at depth 4. Move ordering: from bᵈ to about b^(d/2)

the three regimes, leaves evaluated at depth dworst ordering bᵈ — no cut ever fires: plain minimax perfect ordering b^⌈d/2⌉ + b^⌊d/2⌋ − 1 = Θ(b^(d/2)) — the minimal tree random ordering roughly b^(3d/4) for moderate b — an empirical and asymptotic estimate what the minimal tree means in practiceeffective branching factor b → √b (35 → about 6 in chess) same time budget ⇒ search about TWICE as deep

Where does b^(d/2) come from? To establish a node's value, a search must prove two things: that it is at least v and at most v. Proving "a MAX node is at least v" needs only one child worth at least v — the best one, if it is tried first. Proving "a MIN node is at least v" needs all its children to be at least v. So a proof of a lower bound branches fully at every other level and singly at the others: about b^⌈d/2⌉ leaves. The upper-bound proof is the same with the roles swapped: about b^⌊d/2⌋. The two share one leaf — the end of the principal variation — hence the −1. Perfect ordering makes alpha-beta examine exactly the union of those two proof trees, and on a uniform tree no algorithm that must establish the exact minimax value can examine fewer leaves, which is why this bound is also a lower bound for the problem.

Perfect ordering needs the answer in advance — the figure's "oracle" computes full minimax first, which is cheating — so real programs approximate it, and most of the practical strength of a game-search program is in its move ordering:

  • The previous iteration's best move first. Iterative deepening (§27) makes this almost free, and it is usually right.
  • Forcing moves first. Captures, ordered by the most valuable victim and least valuable attacker, and checks — they are the moves most likely to cause a cut.
  • Killer and history heuristics. A move that caused a cutoff in a sibling position at the same depth, or that has caused many cutoffs anywhere, is tried early; it is a cheap statistical guess that good refutations recur.
  • Narrower windows. Searching with a window around an expected value (an aspiration window), or with a zero-width window just to test "is this move better than the current best?", cuts more; if the test fails, re-search with a wider window. Both rely on the fail-low / fail-high contract above.

Transposition tables: the game tree is really a graph

Different move orders often reach the same position — move A then B versus B then A — so the "tree" is a directed acyclic graph with many paths to each node, and searching each copy separately is §11's overlapping-subproblems waste in a new setting. The fix is §11's fix: a memo, here called a transposition table, a hash table from position to what was learned about it. Positions are hashed incrementally: give every (piece, square) pair a random 64-bit key and let a position's hash be the XOR of the keys of its pieces, so a move updates the hash with two or three XORs in O(1) rather than rehashing the board. Two things make it more than plain memoization. First, an entry records the depth it was searched to, and is reused only for a search no deeper. Second, because alpha-beta returns exact values only inside its window, an entry records whether its value is exact, a lower bound, or an upper bound, and a bound is used only when it alone decides the current window. The table also stores the best move found, which is the best available ordering hint the next time the position is searched. The table is finite, so entries are overwritten by a replacement policy, and a rare hash collision can return information about the wrong position — accepted in practice because 64-bit keys make it very rare and the consequence is a slightly wrong evaluation, not a crash.

The whole picture. Minimax defines the answer; alpha-beta computes the same answer from far fewer nodes, and how many fewer is decided almost entirely by move ordering — between bᵈ and b^(d/2), which at practical depths is the difference between a weak program and a strong one. Iterative deepening supplies the ordering, the transposition table removes the duplicated subtrees and remembers the best moves, and quiescence search patches the evaluation at the horizon. Every one of those is an idea from earlier on this page — backtracking, bounds, memoization — assembled for an adversary.
