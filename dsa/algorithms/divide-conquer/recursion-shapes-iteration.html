07 Three shapes: linear, binary, multiple recursion

Classify a recursion by how many recursive calls a single activation can make. At most one is linear recursion; at most two is binary recursion; more than two is multiple recursion. The classification is not cosmetic — it fixes the branching factor of the call tree, which together with how fast the measure shrinks determines the entire time cost, while the depth is determined by the shrink rate alone.

Linear recursion is a loop wearing a hat

A linear recursion visits a sequence of states, one per level, and does constant work at each — which is precisely what a while loop does. So the only real differences are the per-call overhead and the Θ(depth) stack, both of which favour the loop. Linear recursion earns its keep when the state is awkward to carry explicitly, or when the work happens on the way back up. That last case is the interesting one: reverse_print(list) recurses to the end and prints on return, producing the reversed order for free, and the only iterative equivalent is to push everything onto a stack first — that is, to rebuild the call stack by hand. When you need the return path, recursion is not syntactic sugar, it is the data structure.

Binary recursion splits either the work or the case analysis

Two distinct things wear the same shape. In divide and conquer (§12 onward) the two calls are on disjoint halves of the input, so the sizes add up to n and the tree has log₂ n levels. In case analysis — Towers of Hanoi, naive Fibonacci, a binary-tree traversal — the two calls are on subproblems that are only one step smaller, so the tree has n levels and 2ⁿ-ish nodes. Identical code shape, completely different cost, and telling them apart is just asking what the measure does: halved, or decremented?

Towers of Hanoi — a binary recursion whose measure decrements, stepped one move at a time moves and invocations are counted by the instrumented routine, not asserted

The rule is the familiar one — move n disks from the source peg to the target peg, one at a time, never placing a larger disk on a smaller one. The recursion is three lines and needs no cleverness: move the top n − 1 to the spare peg, move disk n, move the n − 1 back on top of it. Its cost follows immediately.

the routinehanoi(n, from, to, via): if n = 0: return hanoi(n − 1, from, via, to) ← clear the way move disk n: from → to ← the one unit of real work hanoi(n − 1, via, to, from) ← rebuild on top movesM(n) = 2·M(n−1) + 1, M(0) = 0 ⇒ M(n) = 2ⁿ − 1 invocationsC(n) = 2·C(n−1) + 1, C(0) = 1 ⇒ C(n) = 2ⁿ⁺¹ − 1 depthD(n) = D(n−1) + 1, D(0) = 1 ⇒ D(n) = n + 1

At the default n = 4 the figure measures 15 moves and 31 invocations at a peak depth of 5 — and 2⁴ − 1 = 15, 2⁵ − 1 = 31, 4 + 1 = 5, all three of which the readout checks against the counter. The two recurrences differ by exactly the +1 in the base case: there are 2ⁿ − 1 internal nodes doing the moving and 2ⁿ leaves doing nothing, for 2ⁿ⁺¹ − 1 nodes total. That gap between a move count and an invocation count is the wasted half of this recursion, and it is why a base case of n = 1 (move the disk directly) rather than n = 0 halves the number of calls without changing a single move.

Multiple recursion is where the fan-out is data, not syntax

A directory walk calls itself once per subdirectory, so the branching factor is whatever the file system says. A permutation enumerator calls itself once per remaining element, so the branching factor shrinks by one per level and the node count is ∑ n!/(n−k)! (§25). A puzzle solver calls itself once per legal move. In all of these the call tree is a search tree rather than a divide-and-conquer tree: the children are not pieces of the input but choices, and the payoff comes from not having to explore all of them (§23, §26). Multiple recursion is also where the depth analysis is easiest and the time analysis is hardest — depth is the number of decisions, which is usually obvious; the node count depends on how much the pruning removes, which usually is not.

Two independent knobs. Branching factor a and shrink rule together give the cost: a calls on inputs of size n/b give n^(log_b a) leaves; a calls on inputs of size n − 1 give aⁿ leaves. That is the difference between Θ(n) and Θ(2ⁿ) for the same "two calls per activation", and it is the single most useful thing to check first when you meet an unfamiliar recursion.

08 Recursion versus iteration, honestly

Anything computable by one is computable by the other — that is a theorem, not an opinion, and §10 gives the mechanical construction. So the choice is never about power. It is about which one makes the invariant visible, and about a measurable constant-factor and space cost that recursion pays and iteration does not.

The constant factor is real, and it is a constant factor

A call costs more than a jump: arguments have to be placed where the callee expects them, the return address recorded, a frame established, callee-saved registers preserved, and all of it undone on return. How much more is a property of the platform, the calling convention and the optimiser — it varies by an order of magnitude between a small leaf function in a compiled language with the call inlined away, and a dynamically-dispatched call in an interpreter that allocates a frame object per invocation. No number here would survive the machine it was measured on, so none is given. What is portable is the shape of the conclusion: recursion multiplies the running time by a constant and adds Θ(depth) space, and therefore cannot change the complexity class. If a recursive formulation is asymptotically better than the iterative one you had, that is because the algorithm is better, not because it recurses.

Where recursion is genuinely the better engineering choice

  • The data is recursive. Traversing a tree iteratively means maintaining an explicit stack, which is the call stack rewritten by hand with more opportunities for error. Three-line recursive traversals are correct by inspection.
  • The work happens on the way back. Post-order computations — a subtree's height, a directory's total size, an expression's value — need the children's answers before the parent's, and the return path delivers them in exactly the right order for free.
  • The case analysis branches. Backtracking (§23) needs to undo a choice and try the next one. In recursive form "undo" is just returning; the state was in the frame and disappears. Iteratively, undo is code you write and get wrong.
  • The recursion is shallow. O(log n) depth means at most a few dozen frames for any realistic n, so the space objection evaporates and only the constant factor remains.

Where iteration wins outright

  • Linear depth on unbounded input. A recursion over a list of user-supplied length is a latent crash (§06). Rewrite it as a loop.
  • The recursion is tail-recursive and the language does not promise to eliminate it (§09). You get all the cost and none of the benefit.
  • The hot inner loop. When a routine runs billions of times, a constant factor is the whole budget — which is where the divide-and-conquer sorts switch to insertion sort at small sizes (§22), a decision that is entirely about constants.
The rule that settles most cases. Ask what the depth is. O(log n): write it recursively and stop worrying. Θ(n) on input you control and know is small: recursion is fine. Θ(n) on input you do not control: iterate, or use an explicit stack. Then ask whether subproblems repeat — if they do, no amount of choosing between loops and calls will help, and §11 is the actual fix.

09 Tail recursion, and which languages actually eliminate it

A call is in tail position when its result is returned immediately, with no further computation in the caller afterwards. A recursion is tail-recursive when every recursive call is in tail position. The significance is a fact about frames: if nothing in the caller's frame will ever be read again, the callee can reuse that frame instead of pushing a new one — turning Θ(depth) stack into O(1), and the recursion into a jump. Whether that reuse happens is a property of the implementation, not of your code, and this is the single most confidently misremembered fact in the subject.

tail position — the frame is dead after the callgcd(a, b): if b = 0: return a return gcd(b, a mod b) ← nothing happens after; the frame is garbage NOT tail position — one multiply is still pendingfactorial(n): if n = 0: return 1 return n · factorial(n − 1) ← the caller must survive to do the "n ·" the standard fix: an accumulator parameterfactorial(n, acc = 1): if n = 0: return acc return factorial(n − 1, n · acc) ← the multiply moved BEFORE the call and the loop it is isomorphic toacc = 1 while n ≠ 0: acc = n · acc; n = n − 1 return acc

Two structural consequences fall straight out of the definition. First, a tail recursion is necessarily a linear recursion: if two recursive calls were made, the first cannot be the last thing the function does. Second, a tail recursion is always rewritable as a loop with no auxiliary storage, by the purely mechanical transformation shown above — replace the recursive call with an assignment of the new arguments to the existing parameters, and wrap the body in a loop. Binary search, gcd, and a search for a value in a list are all tail-recursive and all become loops this way; the loop version of binary search in Arrays & Strings, §16, is exactly this transformation applied.

What the accumulator trick really does

Non-tail-recursive code leaves work pending in every frame — the n · in factorial, the two writes after the call in a recursive list reversal. The stack is therefore not merely storing "where to return to"; it is storing a queue of deferred operations, and its depth is how many of them are outstanding. Adding an accumulator performs each operation before descending instead of after returning, which empties that queue and leaves nothing for the frame to hold. Note the price: the order of the deferred operations reverses. factorial multiplies from n down rather than from 1 up — harmless for multiplication, which is associative and commutative, but a real semantic change for a non-associative combine, and the reason a naive accumulator rewrite of a string-building recursion produces the string backwards.

There is also a language-level depth limit in the mix (§06), so a "constant-stack" tail recursion still dies at a thousand levels.

The three errors this table is meant to head off

  • "Tail recursion is efficient." Tail position is a syntactic property of your code; the efficiency is a property of the compiler. Writing a tail call in a language that does not eliminate it buys nothing whatsoever — the frame is still pushed, the depth is still linear, and you have paid the readability cost of the accumulator for no return.
  • "My recursion is tail-recursive." Check what happens after the call returns. A pending arithmetic operation, a pending write, an exception handler or a resource-cleanup block wrapping the call, or a debug trace on the return path — any of these puts the call out of tail position, and the last two do so invisibly, because a try or a scoped destructor means the frame must survive the call in order to run the cleanup.
  • "So it never overflows." Only for the tail calls. A routine that is tail-recursive in one branch and not in another has its depth set by the non-tail branch — which is exactly how quicksort behaves, and exactly why the "recurse on the smaller side, loop on the larger" rule of §06 is the reliable fix rather than hoping the compiler noticed.
Portable advice. If the language guarantees proper tail calls, use them freely and write loops as recursions. If it does not, treat a tail-recursive formulation as a design sketch — it tells you the loop exists and what its state variables are — and then write the loop. For recursions that are not tail-recursive and are too deep anyway, §10 is the general answer.

10 Converting any recursion to iteration with an explicit stack

Every recursion can be rewritten as a loop over a stack you allocate yourself, mechanically, with no cleverness and no change to the algorithm. The call stack is a stack; replace it with one of yours. What changes is only where the memory comes from — heap instead of thread reservation — and what is stored — the few values you actually need instead of a whole frame. The algorithm, the order of operations, and the asymptotic cost are all identical, which the figure below verifies by comparing the two output sequences element by element.

The routine being converted is the Hanoi recursion of §07, chosen because it has two recursive calls with real work between them — the case that actually needs the stage tag. Each record holds (n, from, to, via, stage). Stage 0 means "I have done nothing yet": push the child for the first call. Stage 1 means "the first call returned": emit the move, and push the child for the second call. Stage 2 means "both calls returned": pop. Watch the stack in the figure and you are watching the call stack of §07, drawn out where you can see it — and the readout reports that the emitted move sequence is identical to the one the recursive version produces, which is the claim that the conversion is faithful.

Read iteration 4 carefully, because it is the one the stage tag exists for. The record for n = 1 is not popped when its first child returns; it is resumed, does its unit of real work, and pushes a second child. A conversion that popped there would lose every move, and a conversion with no stage field could not tell iteration 2's visit to that record from iteration 4's. The stage tag is the return address, and there is no version of this that does without one — except in the special case below.

What you gain, and what you do not

  • Gain: capacity. The heap is typically orders of magnitude larger than a thread's stack reservation and can grow. A depth that overflows as a recursion is routine as an explicit stack. This is the reason production graph code writes depth-first search iteratively.
  • Gain: a smaller record. A real frame carries a return address, saved registers, alignment padding and every local the function declares. Your record carries the four values you chose. The saving is a constant factor, but on a deep recursion a constant factor on the space is the difference between fitting and not.
  • Gain: control. You can inspect the stack, bound it, serialise it, resume it, or run several searches interleaved. None of that is possible with the call stack.
  • Not gained: asymptotic space. The peak is the same Θ(depth). Converting a linear-depth recursion to an explicit stack moves ten million records from the stack to the heap; it does not make them go away. If the depth itself is the problem, change the algorithm (§06, fix 1 or 2).
  • Lost: legibility. The stage tags are a hand-rolled program counter, and they are easy to get wrong in a way that produces a plausible-looking wrong order. Convert only when you need to, and keep the recursive version alongside as the specification — as the figure does, by running both and comparing.

The special case that needs no stage tag

When the work between recursive calls is nothing — a pre-order traversal, a flood fill, a plain depth-first search — the record is just the subproblem and the loop collapses to "pop one, do its work, push its children". That is why iterative DFS is six lines while iterative post-order traversal, which must do work after the children, needs either a stage tag or a second stack. The amount of machinery you need is exactly the amount of state that has to survive a call, which is the same quantity that decides whether a recursion is tail-recursive (§09). One idea, two consequences: nothing pending means a loop; something pending means a stack. Note also that pushing children in the natural left-to-right order makes the stack process them right to left, so a faithful pre-order conversion pushes the children reversed — a one-line detail that silently produces a mirrored traversal when it is forgotten. The stack and queue mechanics themselves are set out in Linked Structures, Stacks & Queues, §13–§13.

The equivalence, stated once. Recursion and "iteration plus a stack" are interchangeable in both directions, and the conversion is mechanical enough to be done by a compiler. So arguments about which is "more powerful" are empty; the real questions are where the memory lives, how much of it there is, and which version you can read six months from now.

11 Overlapping subproblems, and the memo that fixes them

Divide and conquer is fast when the subproblems it generates are disjoint — mergesort's two halves share no element, so solving both costs what solving the whole costs, once. When the subproblems overlap, the same subproblem is solved many times over, the call tree becomes exponentially larger than the set of distinct subproblems, and the fix is not a better split but a table: remember each answer the first time and look it up thereafter.

the diagnosticcount the NODES of the call tree vs count the DISTINCT arguments naive fib(n): nodes = 2·F(n+1) − 1 = Θ(φⁿ) distinct = n + 1 ⇒ a gap of Θ(φⁿ / n), which is the wasted work, exactly the fix, top-downmemo = {} fib(n): if n in memo: return memo[n] v = n if n ≤ 1 else fib(n−1) + fib(n−2) memo[n] = v; return v the new costinvocations = 2n − 1 for n ≥ 1, each doing O(1) work time Θ(n) table Θ(n) stack depth Θ(n) ← still linear, still a risk
Naive versus memoized recursion — invocations measured on both, same routine, one dictionary apart log axis; the naive curve is measured only as far as it is cheap to measure

Both curves are measurements of the same instrumented routine, differing only in whether a dictionary is consulted first. The memoized count lands on 2n − 1 exactly — one call per distinct argument that computes, plus one per edge that hits the table — and the readout checks it. The naive count lands on 2·F(n+1) − 1. At n = 20 that is 21,891 invocations against 39; at n = 26 it is 392,835 against 51. The ratio is what grows, and it grows like φⁿ/n.

When does memoization apply?

Exactly when two conditions hold. Overlapping subproblems: the recursion reaches the same subproblem along more than one path, so there is something to cache. Optimal substructure (or, for a plain computation, referential transparency): the answer to a subproblem depends only on its arguments, so a cached answer is still valid when it is reused. The second is what fails when a recursion's result depends on mutable state the arguments do not capture — cache that and you get a wrong answer rather than a slow one, which is worse. Mergesort passes the second test and fails the first: its subproblems never repeat, so a memo would be pure overhead.

Two things memoization does not fix

  • The stack depth. Memoized Fibonacci still descends n frames before the first value comes back, so it still overflows at large n. Converting top-down memoization into bottom-up tabulation — fill the table from the base cases upward with a loop — removes the recursion entirely and with it the stack, which is one of the two reasons tabulation is usually preferred in production.
  • The table's own space. Θ(number of distinct subproblems) memory is now a real cost, and for a two-dimensional state space it is the dominant one. Recovering it needs the rolling-window trick, which only works once the dependency structure is explicit — another argument for tabulation.
Named here, developed elsewhere. Recursion with a memo is dynamic programming, top-down. The state definition, the choice between memoization and tabulation, the space-reduction tricks and the reconstruction of the solution itself all belong to that page; what belongs here is the diagnosis — if the call tree is far larger than the set of distinct subproblems, you do not have a divide-and-conquer problem, you have a dynamic-programming problem — and the observation that the two paradigms are distinguished by exactly one question: do the subproblems overlap? The same distinction shows up far outside this domain: the value-iteration recursion of reinforcement learning and the Viterbi recursion are both "recursion over overlapping subproblems", tabulated.
