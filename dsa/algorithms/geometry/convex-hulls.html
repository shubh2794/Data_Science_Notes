11 Convex hulls: definition, output, and why they matter

The convex hull of a finite point set S is the smallest convex set containing it — equivalently, the intersection of all half-planes containing S — and it is a convex polygon whose vertices are points of S. Computing it means listing those vertices in boundary order; with h the number of hull vertices, the output has size h, anywhere from 3 (or fewer, for degenerate input) to n.

three equivalent definitionsconv(S) = { Σ λᵢ pᵢ : λᵢ ≥ 0, Σ λᵢ = 1 } all convex combinations = ∩ { H : H a closed half-plane, S ⊆ H } the half-plane intersection = the convex polygon whose vertices are the EXTREME points of S p ∈ S is EXTREME ⟺ p is not a convex combination of the other points of S ⟺ some line through p has all of S ∖ {p} strictly on one side the output convention this page useshull vertices in COUNTER-CLOCKWISE order, each listed once; STRICT: points in the interior of a hull edge are NOT vertices (orient = 0 is not a turn); certificate of correctness: every consecutive triple turns strictly left, AND every input point is on or to the left of every hull edge — O(nh) to check

The certificate is worth stating separately because it is how the hull figure below checks each algorithm without trusting any of them: a counter-clockwise polygon whose every turn is strictly left is convex, and if every input point is on the inner side of every edge, the polygon contains the input; its vertices are input points, so it is the hull. Every algorithm in §12–§15 produces a list that passes this test, and the figure prints the result.

Hulls are the first computation in a surprising range of tasks: the diameter of a point set (the farthest pair is a pair of hull vertices, found in O(h) by rotating calipers); collision detection between convex shapes, where a hull is the standard bounding volume tighter than a box; linear separability of two classes (their hulls are disjoint), which is the geometric content of the hard-margin support-vector machine; and the lower envelope of lines, which is a hull in the dual plane and is how the "convex hull trick" speeds up certain dynamic programs. The hull is also the 2-D face of linear programming: the optimum of a linear objective over a polytope is attained at a vertex.

12 Graham scan and the polar-sort invariant

Sort the points by angle around a point known to be on the hull, then walk them in that order with a stack, popping the top whenever the last two stack entries and the next point fail to make a left turn. The sort costs O(n log n); the scan is O(n) amortised, because each point is pushed once and popped at most once.

the algorithma ← the lowest point (leftmost among ties) — certainly a hull vertex sort the others by angle around a, counter-clockwise; compare p, q by orient(a, p, q): p first if > 0; if = 0, nearer first stack ← [a] for each p in sorted order: while |stack| ≥ 2 and orient(second-from-top, top, p) ≤ 0: pop push p return stack — the hull, counter-clockwise the invariant (loop over the sorted points)after processing p₁ … pᵢ, the stack holds, bottom to top, the vertices of conv{a, p₁, …, pᵢ} in counter-clockwise order, starting at a and ending at pᵢ — i.e. every consecutive triple on the stack turns strictly left. costsort O(n log n) comparisons, each ONE orientation test scan pushes = n − 1, pops ≤ n − 2 ⇒ ≤ 2n − 3 loop iterations ⇒ O(n) (aggregate amortisation) TOTAL O(n log n) — dominated by the sort

Why the invariant holds

Before pᵢ arrives, the stack is the hull of the points so far, and pᵢ is the most counter-clockwise point yet seen around a, so it is certainly a vertex of the new hull — it is extreme in the direction perpendicular to the ray a → pᵢ. The old hull vertices that remain are exactly those that still turn left on the way to pᵢ: if orient(sₖ₋₁, sₖ, pᵢ) ≤ 0, then sₖ lies inside or on triangle a sₖ₋₁ pᵢ and is not extreme any more, so popping it is right; and because the stack's own turns are all left, once one triple turns left every triple below it does too, so the while-loop can stop at the first left turn. Push pᵢ, and the invariant holds for i. At the end the stack is the hull of all points.

Two details make the proof go through. The sort is valid with orientation alone because every point lies in the closed upper half-plane of a (that is what choosing the lowest point buys): within a half-plane, "counter-clockwise from" is a total order. And the tie-break "nearer first" for points collinear with a puts the farther one later, so the scan pops the nearer one when the farther arrives (orientation 0 ⇒ pop). Step through the figure and count: the readout below it shows that pops never exceed pushes, which is the whole amortised argument.

13 Andrew's monotone chain: the same scan without angles

Sort the points lexicographically by (x, y) and run Graham's stack scan twice — left to right for the lower hull, right to left for the upper hull — then concatenate. It has Graham's O(n log n) bound and its amortised scan, but the sort is by coordinates rather than by angle, which removes the anchor, the polar comparator and its half-plane precondition. It is the variant most implementations use.

the algorithmsort points by (x, y) lower ← [] for p in sorted: while |lower| ≥ 2 and orient(lower[−2], lower[−1], p) ≤ 0: pop; push p upper ← [] for p in reversed(sorted): while |upper| ≥ 2 and orient(upper[−2], upper[−1], p) ≤ 0: pop; push p hull ← lower minus its last point ++ upper minus its last point — counter-clockwise why two passesthe leftmost and rightmost points (first and last in (x, y) order) are hull vertices and split the hull into an x-MONOTONE lower chain and an x-monotone upper chain; along a monotone chain the sorted order IS the boundary order, so a single stack scan builds it. Each pass: ≤ 2n stack steps.

Select "monotone chain" in the figure above: the lower hull grows left to right, turns green when finished, and the upper hull is then built right to left. Compare the counts in the table with Graham's. Graham's orientation count includes one test per sort comparison, because its polar comparator is an orientation test; the monotone chain's sort compares plain coordinates, so all of its orientation tests are in its two scans, and its total is the smaller. Both are dominated by n log n sorting work, and the sort-comparison column of the table measures it.

The lexicographic tie-break on y is what handles vertical alignment: points with the same x are ordered bottom to top, so the leftmost column's lowest point starts the lower chain and its highest point ends the upper chain. Without the tie-break, two points with equal x can appear in either order and the chains can come out non-monotone. The same one line is also what makes the algorithm correct on the lattice distribution, where whole columns share an x.

14 Jarvis march: gift wrapping in O(nh)

Start at a point certainly on the hull; repeatedly find the next hull vertex as the point that every other point lies to the left of — one linear scan of orientation tests — until you return to the start. Each of the h steps costs Θ(n), so the total is Θ(nh): faster than n log n when the hull is small, quadratic when every point is on it.

the algorithms ← leftmost point (lowest among ties); cur ← s repeat: output cur cand ← any point ≠ cur for each r ≠ cur: if orient(cur, cand, r) < 0 or (= 0 and r farther from cur than cand): cand ← r cur ← cand until cur = s cost, and when it winsper hull vertex n − 2 orientation tests ⇒ total ≈ n·h h = O(1) (points in a triangle, a few outliers) Θ(n) — beats Graham h = Θ(log n) Θ(n log n) — ties h = Θ(n) (points in convex position) Θ(n²) — loses badly uniform in a square: E[h] = Θ(log n); uniform in a disk: E[h] = Θ(n^(1/3))

The figure makes the trade visible. Choose "Jarvis march" and "convex position": every point is a hull vertex, h = n, and the orientation count in the table grows as n² while Graham's grows as n log n. Switch to "uniform in a square" and the hull has only about a dozen vertices; Jarvis's count is then h·n, a fixed multiple of n, and the gap to the sort-based algorithms stops growing with n — at the sizes the figure allows the sort-based algorithms still win on count, and Jarvis's advantage appears only when h is smaller than log n, which needs far larger inputs or a hull known in advance to be tiny. "Uniform in a disk" sits in between, with a hull whose expected size grows like the cube root of n.

Jarvis march is the simplest output-sensitive hull algorithm: its cost depends on the output size h. The best possible output-sensitive bound is O(n log h), and it is achieved by combining the two ideas on this page: guess m, split the points into groups of m, hull each group with Graham in O(m log m), and then gift-wrap over the group hulls, finding each next vertex by a binary search per group in O((n/m) log m); if h steps do not close the hull, square m and repeat. The guesses m = 2^(2^t) make the total a geometric series summing to O(n log h). That bound is optimal: the lower bound of §16 generalises to Ω(n log h).

15 Quickhull, briefly

Quickhull is quicksort for hulls: split the points by the line through the leftmost and rightmost points, find the point farthest from that line (a hull vertex), discard everything inside the triangle it forms, and recurse on the two outer sides. Its expected behaviour on typical input is O(n log n) and it is often the fastest in practice, but its worst case is Θ(n²).

the recursionA, B ← leftmost, rightmost points (both on the hull) hull ← A ++ FIND(A, B, points right of A→B) ++ B ++ FIND(B, A, points right of B→A) FIND(a, b, S): if S empty: return [] f ← point of S farthest from line ab — largest |orient(a, b, ·)|; ties toward a return FIND(a, f, points of S right of a→f) ++ [f] ++ FIND(f, b, points of S right of f→b) (points inside triangle a f b are discarded for good) costeach level of recursion: O(|S|) orientation tests BALANCED splits, or a constant fraction discarded per level ⇒ O(n log n) UNBALANCED — every point in convex position, few discarded ⇒ Θ(n²) in the worst case the recurrence is quicksort's: T(n) = T(n₁) + T(n₂) + O(n), n₁ + n₂ ≤ n − 1

The table under the hull figure includes quickhull on the same points. Counted in orientation tests it is not the cheapest here — this implementation tests each surviving point against both new edges, and Graham's count includes its whole sort — and on convex-position input, where no point is ever discarded, its count grows fastest after Jarvis's. Its practical speed comes from elsewhere: on large, spread-out inputs the first few farthest-point triangles discard most points after a handful of sequential, cache-friendly passes, and nothing is sorted. The farthest-point choice is the "pivot" and the discarded triangle is its payoff; the tie-break toward a in the code is the degenerate case of §17 — without it, a point in the middle of a hull edge parallel to ab could be chosen as the "farthest" point and appear as a spurious vertex. Quickhull generalises directly to three and more dimensions, which is its main practical importance.

16 The Ω(n log n) lower bound, by reduction from sorting

Any algorithm that outputs the convex hull in boundary order can be used to sort, with only linear extra work — so it cannot be faster than sorting. This is the geometric counterpart of the reductions in NP-Completeness: there, a reduction transfers hardness from a problem believed hard; here it transfers a proved lower bound.

the reduction: SORTING ≤ HULL in O(n) extra timeinput: distinct reals x₁, …, xₙ map: pᵢ = (xᵢ, xᵢ²) — every point lies on the parabola y = x² fact: the parabola is strictly convex, so EVERY pᵢ is a hull vertex (h = n) and the counter-clockwise boundary order is the order of increasing x recover: find the leftmost hull vertex (O(n)), read the cycle from there ⇒ x's in sorted order ⇒ T_hull(n) + O(n) ≥ T_sort(n) what the bound says, preciselySORTING needs Ω(n log n) comparisons (decision-tree counting, n! leaves), and Ω(n log n) operations in the algebraic decision-tree model (arithmetic and sign tests on the inputs, not floor or hashing). The map is algebraic (squaring), so the bound transfers to hulls in that same model: any algorithm that REPORTS THE HULL IN ORDER needs Ω(n log n) in the worst case. Stronger: merely identifying WHICH points are hull vertices (unordered) is also Ω(n log n), and the output-sensitive bound is Ω(n log h).

The argument, from Sorting & Searching, is that a comparison sort must distinguish n! input orders and a binary decision tree with that many leaves has depth at least log₂ n! = Θ(n log n). The parabola map feeds exactly those inputs to the hull algorithm, and the hull's boundary order encodes the permutation. So Graham scan and the monotone chain are optimal in the worst case, and no clever geometric idea can beat them on points in convex position — which is what the "convex position" distribution in the hull figure is.

  • This does not contradict Jarvis's O(nh). On the parabola input h = n, and O(n·n) is well above n log n. Output-sensitive bounds escape the worst-case lower bound only on inputs whose hull is small.
  • It is a statement about a model. For integer coordinates in a bounded range, sorting can be done faster than n log n with radix sort, and the monotone chain then runs in the time of that sort plus O(n). The lower bound constrains algorithms that only compare and compute polynomials.
  • The same trick proves other bounds. Element uniqueness reduces to closest pair (a zero distance), so closest pair is Ω(n log n) in the algebraic model too — which is why §18's linear-time randomized algorithm must, and does, use the floor function.

17 Collinear and duplicate points

Every hull algorithm needs a decision about orient = 0 — whether a point in the middle of a hull edge is a vertex — and a guarantee that duplicates and all-collinear inputs do not break the loop. The strict convention (collinear points are not vertices) is the simpler one to get right, and it is what every routine on this page implements.

the choices, per algorithm STRICT hull (drop collinear) INCLUSIVE hull (keep them) Graham pop on orient ≤ 0; pop on orient < 0; and REVERSE the last run of ties in the sort: nearer first points collinear with the anchor (they must come far → near) monotone chain pop on orient ≤ 0 pop on orient < 0 Jarvis on orient = 0 take the FARTHER point on orient = 0 take the NEARER point quickhull farthest-point ties broken along the collect points ON each final edge separately edge, toward its start duplicates orient = 0 with a zero vector ⇒ popped / skipped by every rule above all collinear output the two extreme points (a degenerate "hull" of 2 vertices)

Select the "5 × 5 lattice" distribution in the hull figure: it draws points from a 5×5 grid with replacement, so the input has many exact duplicates and every hull edge is a row or column of collinear lattice points. All four algorithms still return the same vertex set and pass the certificate, because every one of them uses the same strict convention. The dangerous combination is to mix conventions — a Graham scan that pops on < 0 but sorts collinear ties nearer-first leaves the final edge's collinear points in the wrong order and produces a polygon that doubles back on itself — or to decide collinearity in floating point, which by §02 is exactly where float predicates fail. With integer coordinates and the exact orientation test, orient = 0 is a trustworthy answer and the degeneracies are just cases.

The lesson generalises beyond hulls: every zero-valued predicate is a branch, and the implementation must take a definite side on it that is consistent across all the places it occurs. Symbolic perturbation (§02) is a systematic way to choose those sides; for the hull, the strict convention above is the whole of it.
