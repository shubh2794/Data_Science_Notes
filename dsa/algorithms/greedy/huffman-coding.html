12 Prefix codes: variable-length codewords, the binary trie, and the cost of a tree

A binary character code assigns each symbol of an alphabet a string of bits, its codeword; a message is coded by concatenating codewords. A fixed-length code uses ceil(log₂ |C|) bits for every symbol. A variable-length code can do better by giving frequent symbols short codewords — provided the receiver can still tell where one codeword ends and the next begins. A prefix code (better: prefix-free) is one in which no codeword is a prefix of another; that single property makes decoding unambiguous and left-to-right, and it is the class within which Huffman's algorithm is optimal.

Why prefix codes lose nothing

Restricting to prefix codes looks like a sacrifice — perhaps some cleverer uniquely-decodable code, one that needs lookahead to parse, could be shorter. It cannot. Every uniquely-decodable code with codeword lengths ℓ₁, …, ℓₙ satisfies the Kraft inequality ∑ 2^(−ℓᵢ) ≤ 1, and conversely for any lengths satisfying it there is a prefix code with exactly those lengths — build the trie by assigning the shortest codewords first, and the inequality guarantees room. So the set of achievable length profiles is the same for both classes, and since the cost depends only on the lengths, the best prefix code is as short as the best uniquely-decodable code. This is the "no loss of generality" that lets §13 search only over trees. (The inequality for prefix codes is a one-line argument: each codeword of length ℓ "owns" a fraction 2^(−ℓ) of the infinite binary strings — those beginning with it — and prefix-freeness makes those fractions disjoint.)

Where the trie lives

The code tree is a binary trie — the structure of Balanced Trees, §23, with the bit alphabet {0, 1} and the symbols stored only at leaves. Encoding is a table lookup (symbol → codeword string, built once by a walk of the tree); decoding is a trie walk, one node per bit. In practice the tree is not stored at all: a canonical Huffman code (§16) is determined by the codeword lengths alone, so a compressor transmits the lengths and the receiver rebuilds the same trie. The tree's role is in the construction and the proof, where the fact that merging two subtrees under a new root adds 1 to every depth below it is what makes the cost recurrence (§14) work.

13 Huffman's algorithm: merge the two lightest, with a priority queue

Start with each symbol as a one-node tree weighted by its frequency; repeatedly remove the two lightest trees, join them under a new root whose weight is their sum, and put the new tree back; after |C| − 1 merges one tree remains, and it is an optimal prefix code. The greedy choice is "the two lightest", the data structure that finds them is a min-priority queue, and the cost is |C| − 1 rounds of two extractMins and one insert, after the |C| inserts that fill the queue.

Reading the trace

Three things in the trace are the algorithm. First, the weights only ever go up: each merged node weighs at least as much as either child, so the two lightest trees at any moment are found at the front of the queue and a merged node never needs to be reconsidered. Second, the sum of the merge weights is the cost of the tree: a symbol of frequency f at depth d takes part in exactly d merges (one per ancestor), contributing f to each, so ∑ merges = ∑ f · d = B(T). Huffman's algorithm minimises each merge's cost in turn — it is greedy on the merge weights — and the two lemmas of §14 show that this local minimisation is globally optimal. Third, ties are broken arbitrarily and the choice matters for the tree but not the cost: the figure's queue orders equal weights by creation time, another implementation might not, and §15 says exactly what is and is not unique.

14 Why Huffman's algorithm is optimal: the greedy-choice lemma and the substructure lemma

The proof is the two-property pattern of §02 made exact. Lemma 1 (greedy choice): there is an optimal tree in which the two least frequent symbols are sibling leaves at maximum depth — so merging them first is safe. Lemma 2 (optimal substructure): an optimal tree for the alphabet with those two symbols replaced by their merged node, expanded back, is optimal for the original alphabet — so what remains after the merge is the same problem, smaller. Together, by induction on the alphabet size, the algorithm's tree is optimal.

LEMMA 1 (greedy choice). Hypothesis: alphabet C, frequencies freq; x and y the two symbols of lowest frequency.there exists an optimal prefix code for C in which x and y have codewords of the same length differing only in the last bit (= they are sibling leaves of maximum depth in the tree). proof — two exchangeslet T be any optimal tree; let a, b be sibling leaves of maximum depth in T (a full tree has such a pair), with freq(a) ≤ freq(b), and freq(x) ≤ freq(y). then freq(x) ≤ freq(a) and freq(y) ≤ freq(b) (x, y are the two smallest overall). If x = b then freq(a) = freq(b) = freq(x) = freq(y) and the lemma is trivial, so assume x ≠ b. swap the leaves a and x, giving T': B(T) − B(T') = freq(x)·d(x) + freq(a)·d(a) − freq(x)·d(a) − freq(a)·d(x) = (freq(a) − freq(x)) · (d(a) − d(x)) ≥ 0 both factors are ≥ 0: a is a deepest leaf, x is a lightest symbol. What the proof says about the "cost of a merge"

Lemma 2's identity B(T) = B(T') + freq(x) + freq(y) is the reason Huffman's algorithm can be described as "greedy on merge cost". Every full tree on C can be built by a sequence of |C| − 1 merges, and its cost is the sum of the merge weights, whatever order the merges are done in (the trace in §13 shows the sum coming to 224). The algorithm chooses, at each step, the cheapest possible merge. That is exactly the shape of §01's template, and it is exactly the shape that is usually wrong — minimising each step's cost does not in general minimise the sum — so it is worth seeing where the proof does the real work: Lemma 1 says the cheapest merge is compatible with some optimum, not merely cheap, and that is what the two-swap exchange establishes. The lemma is the greedy-choice property; the identity is optimal substructure; the theorem is the induction that needs both.

The proof also shows what Huffman's algorithm does not claim. It is optimal among prefix codes that assign one codeword per symbol for a known, fixed frequency table. It says nothing about codes over blocks of symbols (which can approach the entropy more closely, §15), about adaptive codes that change as the message is read, about arithmetic coding (which is not a symbol-by-symbol prefix code and can beat Huffman's per-symbol overhead), or about what happens when the frequencies used to build the code differ from the message's actual frequencies. Each of those is a different problem, and "Huffman is optimal" is a true sentence only with its hypotheses attached.

15 How good is optimal? The entropy bound H ≤ L < H + 1, ties, and what is and is not unique

Huffman's code is the best prefix code for its frequency table, but "best" is relative to a limit. The entropy of the symbol distribution, H = −∑ pᵢ log₂ pᵢ bits per symbol, is a lower bound on the average length L of every uniquely-decodable symbol code, and the optimal prefix code always lands within one bit of it: H ≤ L < H + 1. On the six-symbol instance H = 2.220 and L = 2.240: Huffman is 0.02 bits per symbol above the floor. On a two-symbol alphabet with probabilities 0.99, 0.01, H = 0.081 and L = 1: the bound's slack of nearly a full bit is real, and it is where block coding and arithmetic coding earn their place.

Ties, and what is unique

  • The cost B(T) is unique; the tree is not. Whenever two candidate merges tie in weight, either choice leads to an optimal tree, and the trees can have different shapes with different individual codeword lengths. Frequencies 1, 1, 2, 2: merging the 1s gives node 2; the queue is then {2, 2, 2} and the next merge may pair the new node with a leaf (depths 3, 3, 2, 1, cost 3 + 3 + 4 + 2 = 12) or the two leaves (depths 2, 2, 2, 2, cost 2 + 2 + 4 + 4 = 12). Same cost, different lengths, different trees. The multiset of lengths is not unique either — {3, 3, 2, 1} versus {2, 2, 2, 2} — only the average is.
  • Equal frequencies give a fixed-length code when |C| is a power of two and an almost-fixed one otherwise: four equal symbols get lengths 2, 2, 2, 2 (L = 2 = H); five equal symbols get 2, 2, 2, 3, 3 (L = 2.4, H = log₂ 5 = 2.32).
  • One symbol: the algorithm returns a single leaf, depth 0 — codeword length 0, L = 0 = H. That is the mathematically correct answer (a message over one symbol carries no information) and a practical nuisance: a decoder needs to know the message length. Implementations assign the lone symbol a 1-bit codeword, which is not optimal but is decodable; the figure shows the length-0 answer and says so.
  • Two symbols: always lengths 1, 1, L = 1 regardless of the probabilities — the source of the H + 1 slack: a symbol with p = 0.99 "deserves" log₂(1/0.99) = 0.0145 bits and gets a whole one. Coding pairs of symbols (an alphabet of four, with probabilities .9801, .0099, .0099, .0001) brings the per-symbol average down toward H; coding blocks of k independent symbols gives H ≤ Lₖ / k < H + 1/k, which is how block codes approach the entropy.
  • Left/right assignment is a convention. Swapping the two children of any internal node changes every codeword below it and nothing about the lengths; §16's canonical codes remove this freedom deliberately.

16 Huffman codes in practice: canonical codes, transmitting the table, and what real compressors actually do

A textbook Huffman coder is a component, not a compressor. Real systems answer three questions the algorithm leaves open — how does the decoder learn the code?, where do the frequencies come from?, and what redundancy is the code blind to? — and the answers explain both why Huffman coding is everywhere and why it is almost never the whole story.

Canonical Huffman codes: send the lengths, not the tree

Since the cost depends only on the length assigned to each symbol — B = ∑ freq(c) · ℓ(c) (§15) — every tree realising the same per-symbol lengths costs the same, and a compressor can throw the tree away and keep only the lengths. A canonical code assigns codewords from the lengths by a fixed rule: sort symbols by (length, symbol order); give the first symbol the all-zeros codeword of its length; each subsequent codeword is the previous one plus 1, shifted left when the length increases. Decoder and encoder run the same rule on the same lengths and agree on every codeword, so the transmitted "table" is one small integer per symbol, and decoding can use length-indexed arithmetic instead of a trie walk. This is the form in which Huffman codes appear in the DEFLATE format (the code lengths are themselves compressed by a second, small Huffman code) and in JPEG's baseline entropy coder (a table of counts per length plus the symbol order).

Static, two-pass, and adaptive

The frequencies must come from somewhere. A static code uses a fixed table agreed in advance (an English-text table, say) — no header, but suboptimal for anything else. A two-pass (semi-static) coder scans the input to count, builds the code, transmits the lengths, then encodes: optimal for the input's own distribution, at the cost of the header and a second pass. An adaptive coder starts from a flat code and updates the tree as symbols arrive, encoder and decoder making identical updates, so no table is sent and the code tracks a drifting distribution; the price is per-symbol tree maintenance. Which one a format uses is a design choice about latency, header cost and the stationarity of the data, not about the algorithm.

What Huffman coding is blind to, and what real formats pair it with

  • It sees single symbols only. A file of ABABAB… has two equally frequent symbols and Huffman gives it 1 bit per symbol — no compression at all — although it is perfectly predictable. Repetition and context are captured by a modelling stage: run-length encoding for long runs (a run of k identical bytes stored as the byte and the count), dictionary matching (LZ77-style back-references "copy 12 bytes from 340 bytes back"), or a context model. Huffman coding then codes the output of that stage — literals, match lengths, distances — where it is doing what it is good at: turning a skewed symbol distribution into near-entropy bits.
  • DEFLATE (the format inside zip, gzip and PNG) is exactly that pairing: LZ77 matching followed by Huffman coding of literals/lengths and of distances, with canonical codes described by transmitted lengths. Baseline JPEG Huffman-codes the quantised transform coefficients (a Huffman symbol per (zero-run, magnitude-category) pair, with the magnitude bits appended raw); the standard also defines an arithmetic-coding option that is rarely used for compatibility reasons.
  • Its per-symbol overhead is real — the < 1 bit of §15 — and for very skewed distributions it dominates. Arithmetic coding and its table-driven descendants (asymmetric numeral systems, ANS) code a whole message as one number and reach the entropy to within a constant per message rather than per symbol. Modern general-purpose compressors mix the two: one widely used format uses a finite-state ANS coder for its main streams and a Huffman coder for literals, choosing each for speed; modern image and video codecs generally use arithmetic or ANS coders. The general statement that is safe: Huffman coding remains the fast, simple entropy coder in many formats, usually behind a modelling stage, and is increasingly replaced by ANS/arithmetic coding where the last few percent of size matter more than the last few percent of speed.
  • Any lossless compressor makes some inputs longer. A pigeonhole count: there are fewer short strings than long ones, so a scheme that shortens some inputs must lengthen others. Huffman coding on data whose symbols are already uniform (encrypted, already-compressed) gains nothing and pays the header.
The one-line version. Huffman's algorithm is the optimal symbol-by-symbol prefix code for a known distribution, built greedily in O(|C| log |C|) with a priority queue; in practice it is transmitted as canonical lengths, placed after a modelling stage that captures repetition, and competes with arithmetic/ANS coders that avoid its up-to-one-bit-per-symbol overhead.
