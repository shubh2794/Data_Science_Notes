Number-Theoretic Algorithms

Every algorithm earlier in this series treated a number as a unit: one comparison, one addition, one array index, each costing O(1). That model breaks when the numbers are the input. A 2048-bit RSA modulus does not fit in a machine word, and an algorithm that loops "up to n" on it would not finish before the sun burns out. Number-theoretic algorithms are measured in the length of the number, β bits, and the good ones are polynomial in β: Euclid's gcd in O(β) divisions, a modular inverse by extended Euclid, aᵇ mod n in at most 2β multiplications by repeated squaring, and a primality test that makes a handful of such exponentiations. The page builds that toolkit from the division theorem up: divisibility and gcd, Euclid and its Fibonacci worst case, Bézout coefficients, the groups Zₙ and Zₙ*, Euler's φ, Fermat's and Euler's theorems, repeated squaring, and the Chinese remainder theorem. It then applies the toolkit: Fermat and Miller–Rabin primality testing, the density of primes and how to generate a large one, RSA with its correctness proof and its textbook pitfalls, and Pollard's rho for factoring. Every step count, liar count and multiplication count on the page is measured by running the real routine, on BigInt values wherever they can exceed 2⁵³.

01 Why integers get their own page: the input size is the number of bits

A number n is written with β = ⌊log₂ n⌋ + 1 bits, and β, not n, is its input size. An algorithm that runs in time polynomial in n is therefore exponential in its input: "loop from 2 to √n" is 2^(β/2) iterations. The whole subject is about replacing loops over values with loops over bits. Deciding whether a 1024-bit number is prime by trial division means up to 2⁵¹¹ divisions. Miller–Rabin decides it with a few thousand multiplications of 1024-bit numbers. The gap between those two is the gap between exponential and polynomial, and it is what makes public-key cryptography possible: the legitimate user runs polynomial algorithms, and the attacker is left with an exponential or sub-exponential one.

02 The cost of arithmetic on big integers

Adding two β-bit numbers costs O(β) bit operations, and multiplying or dividing them costs O(β²) with the schoolbook method. Every algorithm on this page is a short sequence of these operations, so its running time is (number of arithmetic operations) × (cost of one). Euclid makes O(β) divisions; repeated squaring makes O(β) multiplications. Both are therefore O(β³) bit operations at worst, and a careful count brings Euclid down to O(β²).

The derivation of Karatsuba's recurrence and its measured digit-multiplication counts are in Recursion, Divide & Conquer, and this page does not repeat them. The point here is how the costs compose. A modular exponentiation with a β-bit exponent does about 1.5β modular multiplications on average (§13), each O(β²), so O(β³) in total. With a 2048-bit modulus, that is about 1.5 · 2048 ≈ 3 000 modular multiplications, each about 2 · 32² word multiplications for the product and its reduction: roughly 6 million in all. That is a few milliseconds, where a loop to √n would take 2¹⁰²⁴ steps. Division is the operation to watch. A general division by a β-bit divisor costs as much as a multiplication, so libraries avoid it inside loops. Montgomery multiplication replaces "reduce mod n" by shifts and a multiplication by a precomputed constant. Barrett reduction replaces the division by a multiplication with a precomputed reciprocal.

03 Divisibility, primes, and the division theorem

Everything on the page rests on one fact: for any integer a and any positive n there is exactly one way to write a = q·n + r with 0 ≤ r < n. The remainder r is "a mod n", and modular arithmetic is arithmetic on remainders. Divisibility is the case r = 0, and primes are the numbers whose only divisors are 1 and themselves.

Two small facts do most of the work later. Euclid's lemma: if a prime p divides a product ab, it divides a or b. §04 proves it from Bézout's identity. With it comes the fundamental theorem of arithmetic: every integer n > 1 is a product of primes in exactly one way, up to order. Existence is induction: either n is prime, or it splits into two smaller factors. Uniqueness is Euclid's lemma applied to two factorisations. The theorem says a lot about structure and little about computation. It guarantees the factorisation exists, and §22 shows how slowly anyone knows how to find it.

Negative operands differ between languages. The mathematical a mod n is always in [0, n). C, C++, Java, JavaScript and Go truncate the quotient towards zero, so -7 % 3 is -1. Python and Ruby floor the quotient, so -7 % 3 is 2. Code that reduces a possibly negative value (a Bézout coefficient, a rolling hash after a subtraction) must normalise with ((a % n) + n) % n, or the "residue" is negative and every later comparison is wrong. The routines on this page do so everywhere.

04 The greatest common divisor, and why it is a linear combination

gcd(a, b) is the largest integer dividing both a and b. The key characterisation is algebraic: gcd(a, b) is the smallest positive number of the form a·x + b·y with integers x, y. Every property on this page, including the existence of modular inverses, follows from that one statement.

the theoremfor integers a, b not both 0: gcd(a, b) = min { a·x + b·y : x, y ∈ Z, a·x + b·y > 0 } proof: let s = a·x + b·y be the smallest positive such combination. Divide: a = q·s + r, 0 ≤ r < s. r = a − q·(a·x + b·y) = a·(1 − q·x) + b·(−q·y) is again a combination, and r < s, so r = 0: s | a. Likewise s | b. so s is a common divisor, and s ≤ gcd. Conversely gcd divides a and b, so it divides a·x + b·y = s: gcd ≤ s. ∎ consequences used later(1) d | a and d | b ⟹ d | gcd(a, b) every common divisor divides the gcd, not just ≤ it (2) gcd(a·n, b·n) = n·gcd(a, b) for n ≥ 1 (3) n | a·b and gcd(a, n) = 1 ⟹ n | b 1 = a·x + n·y, so b = a·b·x + n·b·y is divisible by n (4) EUCLID'S LEMMA: p prime, p | a·b ⟹ p | a or p | b — (3) with n = p (5) gcd(a, n) = 1 and gcd(b, n) = 1 ⟹ gcd(a·b, n) = 1 — units are closed under multiplication (§09) (6) gcd(a, b) · lcm(a, b) = |a·b| (7) gcd(a, b) = gcd(b, a) = gcd(−a, b) = gcd(a, b + k·a), gcd(a, 0) = |a|

Property (7) is the one Euclid's algorithm uses: adding a multiple of one argument to the other does not change the gcd, because any common divisor of a and b divides b + ka, and conversely. Taking k = −⌊b/a⌋ turns the second argument into b mod a, which is smaller. The theorem above also shows why the gcd is computable by something smarter than listing divisors. It is the generator of the set {ax + by}, and Euclid's algorithm finds that generator by the same repeated division as the proof, run on concrete numbers. Factoring a and b and intersecting the prime lists would also give the gcd, and §22 explains why nobody does it that way.

05 Euclid's algorithm: gcd(a, b) = gcd(b, a mod b)

Replace (a, b) by (b, a mod b) until b is 0; the other number is the gcd. Each step preserves the gcd, and the second argument strictly decreases, so the algorithm terminates, and it terminates quickly: the remainders fall at least as fast as Fibonacci numbers rise.

06 How many steps: the halving argument, Lamé's theorem, and the bit cost

Two consecutive division steps at least halve the remainder, so Euclid takes at most about 2·log₂ b steps. Lamé's theorem sharpens this: the pair that needs the most steps for its size is a pair of consecutive Fibonacci numbers, so the step count is at most 1 + log_φ b ≈ 1.44·log₂ b, which is less than 5 times the number of decimal digits of b.

The bit cost: better than steps × division

A naive bound multiplies O(β) steps by O(β²) per division to get O(β³). The true cost is O(β²), because the divisions are cheap exactly when there are many of them. Long division of rᵢ₋₁ by rᵢ costs O(log₂ rᵢ · (log₂ qᵢ + 1)) bit operations, where qᵢ is the quotient. Since rᵢ ≤ b, the total is at most O(log b · Σ(log₂ qᵢ + 1)). The product of the quotients is at most a, because rᵢ₋₁ ≥ qᵢ·rᵢ telescopes, so Σ log₂ qᵢ ≤ log₂ a. That gives O(log a · log b) = O(β²). This is the same cost as one schoolbook multiplication, and it is why the extended gcd is the standard way to compute a modular inverse (§11).

What the assumption is. Lamé's bound is a worst case over all inputs and needs no assumption. The 0.843·ln b average assumes the inputs are uniformly random below a bound. The O(β²) bit cost assumes schoolbook division. With fast multiplication, a recursive "half-gcd" algorithm reaches O(M(β) log β), where M(β) is the cost of one multiplication. Big-number libraries switch to it above a few thousand bits.

07 Binary gcd: no division at all

Binary gcd replaces division by the three cheapest operations a machine has: test the low bit, shift right, subtract. It uses the same invariant idea as Euclid, with rules chosen so that every step removes at least one bit.

the rulesgcd(a, 0) = a gcd(2a, 2b) = 2·gcd(a, b) both even: pull out a common factor 2 (count it in a shift k) gcd(2a, b) = gcd(a, b) b odd 2 is not a common divisor, so drop it gcd(a, b) = gcd(|a − b|, min(a, b)) both odd: the difference is EVEN, so the next step shifts it result = 2ᵏ · (the odd gcd) costeach subtraction of two odd numbers yields an even number, which the next step halves ⟹ every one or two operations shrink a + b by at least one bit: O(β) shifts and subtractions, O(β) bits each ⟹ O(β²) bit operations same asymptotic cost as Euclid, with no division instruction — the win is a constant factor on hardware where division is slow

The Euclid figure of §05 runs binary gcd on the same pair and prints its shift and subtraction counts beside Euclid's divisions, with an agreement check. For small numbers, Euclid takes fewer steps. Binary gcd takes more steps, but each is a single-cycle instruction. It wins in hardware, on microcontrollers without a divider, and in constant-time cryptographic code, where the data-dependent timing of a division instruction can leak the secret. Its extended version exists as well, and is the usual way to compute a modular inverse on hardware without a divider.

08 Extended Euclid: computing the Bézout coefficients

§04 proved that gcd(a, b) = a·x + b·y for some integers x, y. Extended Euclid finds them at no extra asymptotic cost, by carrying the coefficients back up the recursion. With x in hand, a modular inverse is one call away.

Bézout coefficients are never unique. Adding b/d to x and subtracting a/d from y gives another pair. Extended Euclid returns the one inside the bound above.

Why this matters beyond gcds. Extended Euclid is the inverse operation of modular arithmetic (§11). It solves linear Diophantine equations ax + by = c, which have a solution exactly when gcd(a, b) | c. It provides the CRT coefficients (§14) and computes RSA's private exponent (§19). The polynomial version, run on polynomials over a field, decodes Reed–Solomon codes and computes inverses in the finite fields behind AES and elliptic-curve cryptography.

09 Modular arithmetic: the groups Zₙ and Zₙ*

Arithmetic mod n works on the n residue classes {0, 1, …, n − 1}, and addition and multiplication are well defined on them: reducing before or after an operation gives the same class. Under addition the classes form the group Zₙ. Under multiplication, only the classes coprime to n have inverses, and they form the group Zₙ*, of size φ(n). These two groups are the arena for everything that follows. Their sizes, and the sizes of their subgroups, are what make Fermat's theorem, Miller–Rabin and RSA work.

Closure of Zₙ* is property (5) of §04: a product of two numbers coprime to n is coprime to n. Inverses exist by Bézout, as §11 makes concrete. The elements left out, the non-units that share a factor with n, can never be multiplied to 1. If d = gcd(a, n) > 1, every multiple a·x mod n is itself a multiple of d. This is the one place where modular arithmetic differs from ordinary arithmetic, and algorithms that divide mod n must check it. A useful by-product is that finding a non-unit factors n: gcd(a, n) is then a non-trivial divisor. Pollard's rho (§22) is a method for stumbling on one.

10 Euler's φ: how many residues are invertible

φ(n) counts the integers in [1, n] coprime to n, which is the size of Zₙ*. It is easy to compute from the factorisation of n and, as far as anyone knows, hard to compute without it. RSA depends on exactly that asymmetry.

For an RSA modulus N = pq, knowing φ(N) is as good as knowing the factors. From φ(N) = N − (p + q) + 1 you get p + q, and with pq = N, p and q are the roots of z² − (p + q)z + N. Computing φ for an RSA modulus is therefore exactly as hard as factoring it. This is the first of several places where "compute a group's size" and "factor the modulus" turn out to be the same problem.

11 Modular inverses and linear congruences

a has an inverse mod n if and only if gcd(a, n) = 1, and extended Euclid computes it in O(β²) bit operations. More generally, a·x ≡ b (mod n) has a solution exactly when d = gcd(a, n) divides b, and then it has exactly d solutions mod n, spaced n/d apart.

Why exactly d solutions: divide everything by d. The congruence becomes (a/d)·x ≡ b/d (mod n/d) with a/d now coprime to n/d, so it has exactly one solution mod n/d. That one class splits into d classes mod n. When n is prime every non-zero a is invertible and the congruence behaves exactly like a linear equation over the rationals. That is why so much cryptography, coding theory and hashing works mod a prime: Zₚ is a field, and algebra works in it without exceptions.

Inverses in bulk. To invert k residues mod the same n, one extended Euclid call suffices. Form the prefix products a₁, a₁a₂, …, a₁⋯aₖ, invert the last, and walk backwards: aₖ⁻¹ = (a₁⋯aₖ)⁻¹ · (a₁⋯aₖ₋₁), and so on. That is 3(k − 1) multiplications and one inversion instead of k inversions. Elliptic-curve libraries use this trick, often called batch inversion, to normalise many points at once.

15 What the CRT is used for

The CRT splits one problem mod n into independent problems mod its coprime factors. That turns big-number arithmetic into small-number arithmetic, turns proofs about composite moduli into proofs about prime powers, and makes RSA decryption about four times faster.

  • RSA-CRT decryption. The key holder knows p and q, so instead of c^d mod N it computes m_p = c^(d mod (p−1)) mod p and m_q = c^(d mod (q−1)) mod q and recombines them: m = m_q + q·((q⁻¹ mod p)·(m_p − m_q) mod p). This mixed-radix form of the reconstruction needs one precomputed inverse. Each half-size exponentiation has half as many bits in the exponent and a modulus half as wide. With schoolbook arithmetic each multiplication costs a quarter as much, so each half costs about ⅛ of the full exponentiation, and the two together about ¼. That gives the roughly 4× speed-up every RSA library uses. The toy RSA figure of §19 counts both.
  • Multi-modular (residue number) arithmetic. To compute an integer result whose size you can bound (a determinant, a resultant, the exact solution of an integer linear system), compute it mod many word-sized primes, independently and in parallel, and reconstruct with the CRT. No intermediate number is ever larger than a word. Exact linear algebra in computer algebra systems works this way, and so do fast multiplication by number-theoretic transform, which multiplies mod three or so NTT-friendly primes and recombines, and residue-number-system hardware for DSP.
  • Structure theorems. Zₙ* ≅ Z*_{p₁^e₁} × … × Z*_{pₖ^eₖ}, so φ is multiplicative (§10). An element's order is the lcm of its orders in the factors. x² ≡ 1 has 2ᵏ solutions mod a product of k distinct odd primes, one choice of ±1 per factor. That count is where Miller–Rabin's non-trivial square roots of 1 come from (§17), and it makes square roots mod N as hard as factoring N.
  • Scheduling and cycles. Two periodic events with coprime periods m and n coincide exactly once every mn steps. The CRT grid's walk is this statement. Calendars, gear trains and interleaved hash probes are all cases of it.
  • Secret sharing and error correction. Split a secret into its residues mod several coprime moduli, so that any large enough subset of residues reconstructs it and a smaller subset does not. This is the CRT twin of polynomial secret sharing. Redundant residue number systems add extra moduli so that a corrupted residue can be detected and corrected.
A fault in one CRT half leaks the key. If a glitch corrupts m_p but not m_q while signing, the faulty signature s' is still correct mod q and wrong mod p. Then gcd(s'^e − m, N) = q, and one faulty signature factors the modulus. Implementations verify sᵉ ≡ m before releasing a signature. This is a direct consequence of the CRT's independence of the components: the property that makes the method fast also makes it fragile.

Miller–Rabin looks inside the Fermat exponentiation. It computes a^(n−1) by repeated squaring from a^d, where n − 1 = 2ˢ·d, and checks that the last value before reaching 1 is −1, as it must be mod a prime. For every odd composite n > 9, at most a quarter of the bases pass. So t independent random bases wrongly accept a composite with probability at most 4⁻ᵗ, and a prime is never rejected. This is a one-sided Monte Carlo algorithm in the sense of Online & Randomized Algorithms. That page's amplification argument applies unchanged.

18 How many primes there are, and how to generate a large one

By the prime number theorem, about 1 in every ln n integers near n is prime. A random β-bit odd number is prime with probability about 2/(β·ln 2). To get a 1024-bit prime, draw random odd 1024-bit numbers and test each: about 355 draws on average, most of them rejected by a small-prime sieve before any exponentiation is done.

The output distribution matters. "Pick a random start and take the next prime" is faster but biased. It favours primes that follow long prime gaps, so some primes are much more likely than others. For RSA the bias has not been shown to be exploitable, and some libraries use incremental search from a random start for speed. The uniform method above is simpler to reason about. What has broken real keys is bad randomness. Devices that generated keys right after boot, with little entropy, produced many RSA moduli that share a prime factor with some other key. A single gcd of the two moduli then factors both (§21). A generator is only as good as its random source.

Why the method is fast enough. The density of primes falls only like 1/β, so the number of candidates grows linearly with the key size, while each test is polynomial. Had primes been exponentially rare, like the fraction 2^(−β/2) of numbers that are perfect squares, random generation would be hopeless, and so would RSA. The prime number theorem is an analytic result, but here it is doing algorithmic work: it bounds the expected running time of the generator.

21 Why RSA is believed secure, and why textbook RSA is not

Anyone who can factor N can compute λ(N) and then d, so RSA is at most as hard as factoring. Nobody has proved it is as hard. Its security is a belief, grounded in decades of failed attempts to factor fast. Factoring itself is almost certainly not NP-complete. Separately, "textbook" RSA, the bare map m ↦ mᵉ, is insecure in several simple ways, and real systems never use it unpadded.

The NP ∩ co-NP argument is the one in NP-Completeness & Approximation: if any problem in NP ∩ co-NP were NP-complete, NP would equal co-NP. So cryptography does not rest on P ≠ NP in the way it is sometimes described. It rests on a narrower and stronger assumption, that one particular problem, which is probably not NP-hard, is nevertheless hard on average for moduli built from random primes. NP-hardness would not help anyway, because it is a worst-case notion. A cryptosystem needs instances that are hard on average, and a random RSA modulus is believed to be one.

Textbook-RSA pitfalls (conceptual, no recipes)

  • It is deterministic. The same m always gives the same c. Anyone can encrypt guesses with the public key and compare. If the message space is small (yes/no, a PIN, a salary band), textbook RSA hides nothing. Randomised padding fixes this: OAEP for encryption, PSS for signatures.
  • It is malleable. (m₁·m₂)ᵉ = m₁ᵉ·m₂ᵉ, so from c an attacker can make a valid encryption of m·r for any r without knowing m. Unpadded signatures can be combined the same way. Padding with structure checks breaks the multiplicative relation.
  • Small e with a small message. If mᵉ < N, no reduction happens and m is the ordinary integer e-th root of c. If one message is sent to e recipients with the same small e, the CRT combines the ciphertexts into mᵉ mod the product of the moduli, which again needs no reduction. e = 65537 with proper padding avoids both.
  • Shared moduli, shared primes. Two users who share N with different e can each derive the other's d, since knowing one's own d factors N (above). If the same message goes to both, Bézout on e₁, e₂ recovers it without any d. Keys generated with poor randomness that share one prime are broken by a single gcd (§18).
  • A small private exponent. Choosing a short d to speed up decryption is unsafe. Below about N^0.25, and in practice higher, d can be recovered from (N, e) alone. Use CRT for speed instead (§15).
  • Side channels and faults. A non-constant-time exponentiation leaks d through timing (§13). A fault in one CRT half leaks a factor (§15). Padding-check error messages that differ let an attacker decrypt by adaptive queries. These attacks target the implementation, not the mathematics.

22 Integer factorisation: trial division and Pollard's rho

Trial division finds a factor p in about p/2 steps. Pollard's rho finds it in about √p steps, by the birthday paradox, using almost no memory. For N = p·q with balanced factors that is N^(1/4) instead of N^(1/2): a large improvement, and still exponential in β. It is the right tool for the small factors of ordinary numbers and useless against an RSA modulus.

The rest of the factoring toolbox, in one paragraph. Pollard's p − 1 method finds p quickly when p − 1 has only small prime factors, which is why RSA primes were once required to be "strong", though random large primes are now considered fine. The elliptic-curve method is the p − 1 idea with a random group order, and its running time depends on the size of the smallest factor. It finds 30–60-digit factors of huge numbers. 24 Pitfalls

  • Calling a loop to n "linear". For numeric input the size is β = log₂ n. O(n) and O(√n) are exponential in it (§01).
  • Computing aᵇ and then reducing. The unreduced power has b·log₂ a bits. Reduce after every multiplication (§13).
  • Overflow in a·b mod n. Two 63-bit residues multiply to 126 bits. Use a 128-bit product, Montgomery form or a big-integer type. In JavaScript, Number loses exactness above 2⁵³, which is why this page uses BigInt.
  • Negative remainders. % in C, Java and JavaScript keeps the sign of the dividend. Normalise with ((a % n) + n) % n before using a residue, especially a Bézout coefficient (§03, §08).
  • Dividing mod n without checking the gcd. a⁻¹ mod n exists only when gcd(a, n) = 1. A linear congruence can have 0, 1 or several solutions (§11).
  • Trusting the Fermat test. Carmichael numbers pass it for every coprime base, and repetition does not help (§16). Use Miller–Rabin.
  • Fixed Miller–Rabin bases on adversarial input. The deterministic sets are proved only below their bounds. Above them, an attacker can build composites that pass any fixed list. Use random bases, or a proven set within its range (§17).
  • Quoting 4⁻ᵗ as the chance a random candidate is composite. It is a worst-case bound per composite. For random candidates the true error is far smaller (§17).
  • Assuming CRT moduli are coprime. Without coprimality, a solution may not exist, and when it does it is unique only mod the lcm (§14).
  • Textbook RSA. No padding makes encryption deterministic and malleable. A small e with a small message, a shared modulus, a small d and a variable-time exponentiation are each fatal (§21).
  • Weak randomness in key generation. Moduli that share a prime are broken by one gcd (§18).
  • Believing RSA's security is "because factoring is NP-complete". Factoring is in NP ∩ co-NP and believed not NP-complete. The assumption is average-case hardness of this one problem (§21).
  • Pollard's rho with c = 0 or c = −2. These maps have special structure, and the random-map heuristic fails. When gcd returns N, retry with another c rather than giving up (§22).
