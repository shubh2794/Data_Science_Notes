06 Paging: the model, and the policies worth knowing

A fast memory holds k pages and a slow memory holds all of them. Each request names a page: if it is in the cache the request is a hit and costs nothing, and if not it is a fault, costs 1, and the page must be brought in, evicting another if the cache is full. The eviction rule is the whole algorithm. The same model covers CPU caches (lines), virtual memory (pages), database buffer pools (blocks), web and CDN caches (objects), and the key-value cache in front of any slow service. The only differences are the unit and the cost of a miss.

the paging problemcache of k slots; request sequence σ = p₁, p₂, …, pₙ of page ids cost = number of FAULTS (requests for a page not in the cache) DEMAND paging: a page is loaded only when it is requested, and at most one page is evicted per fault (every algorithm can be made demand-paging without increasing its cost, so this loses nothing) the policies this page simulatesLRU evict the page whose last request is OLDEST deterministic, k-competitive (§08) FIFO evict the page that was LOADED earliest (hits do not refresh it) deterministic, k-competitive, anomalous (§09) LFU evict the page with the FEWEST requests since it was loaded deterministic, NOT competitive FWF flush-when-full: on a fault with a full cache, evict EVERYTHING deterministic, k-competitive (!) CLOCK FIFO with a reference bit: a referenced page gets a second chance deterministic, k-competitive; the practical LRU MARKER mark pages on request; evict a uniformly random UNMARKED page; when all are marked, unmark all (a new phase) randomised, 2H_k-competitive (§10) OPT Belady: evict the page whose next request is FURTHEST in the future offline — needs σ; optimal (§07)

Two families that organise the zoo

Marking algorithms. Divide the sequence into phases. A phase begins with a request and ends just before the request that would make it contain k + 1 distinct pages. Mark a page when it is requested and clear all marks at the start of each phase. A marking algorithm never evicts a marked page. LRU is a marking algorithm: a page requested in the current phase is among the k most recently used distinct pages, so it is never least recently used while unmarked pages remain. FWF is the crudest marking algorithm. The randomized marker is the marking algorithm that picks which unmarked page to evict by coin flip. Every marking algorithm faults at most k times per phase, and that single fact gives k-competitiveness (§08). Conservative algorithms. On any consecutive stretch of requests with at most k distinct pages, the algorithm faults at most k times. LRU, FIFO and CLOCK are conservative. FIFO is not a marking algorithm, since it can evict a page requested moments ago, but it is conservative, and conservativeness also gives k-competitiveness.

Why LFU fails, precisely

LFU looks sensible: keep what is popular. It fails because counts never forget. Request pages 1, …, k − 1 each M times. Then alternate two fresh pages x, y, x, y, … for 2M requests. Each of x and y arrives with count 1, below every stale page, and is the only candidate for eviction when the other arrives. LFU faults on every one of the 2M alternating requests. OPT evicts one stale page once and then faults on nothing, so it pays k + 1 in total. LFU's cost grows with M while OPT's stays fixed, so no constant c works. The "phases" pattern in the §08 figure, a working set that drifts, shows the same failure on a less contrived input: LFU keeps the old working set because of its high counts and faults on almost everything new. This is why production caches either decay their counts or combine frequency with recency (§24).

The cost model is a simplification, and it is the right one. Every fault costs the same. Real systems have different miss costs (a CDN object of 1 KB against one of 1 GB), different object sizes (the generalised caching problem), and write-backs (evicting a dirty page costs twice). Each generalisation has its own competitive theory, and the ratios mostly keep their shape: k for deterministic algorithms, O(log k) for randomized ones. The unit-cost model is where the ideas are cleanest, and it is the one this page proves things in.

07 Belady's rule: evicting the page needed furthest in the future is optimal offline

If the whole request sequence is known, the fewest faults come from a simple greedy rule: on each fault, evict the page whose next request lies furthest in the future, or a page never requested again if there is one. The proof is an exchange argument of exactly the kind in the greedy chapter. No online algorithm can run this rule, because it needs the future. Its value is as the yardstick: every competitive ratio on this page is measured against it, and every figure computes it by simulation on the same sequence.

the rule (furthest in future, FF)on a fault for page p with a full cache: evict argmax over q in cache of next(q) where next(q) = the index of q's next request after now (= ∞ if q is never requested again) cost: with the next-use indices precomputed in one right-to-left pass, O(k) per fault naively, O(log k) with a heap the theorem, and the exchange lemma that proves itTHEOREM FF incurs the minimum number of faults over all eviction schedules. LEMMA Let S be any schedule that makes the same decisions as FF on the first j requests. Then there is a schedule S' that makes the same decisions as FF on the first j + 1 requests, and faults(S') ≤ faults(S). Induction on j, starting from an optimal S, turns it into FF with no increase in faults.

The exchange, step by step

At request j + 1 both schedules have the same cache. If the request is a hit, or both evict the same page, set S' = S for this step. Otherwise FF evicts e and S evicts some f ≠ e. Let S' evict e instead. From then on the two caches differ in exactly one page: S holds e where S' holds f. S' copies S's decisions exactly until the first time this difference matters, and at that moment makes the caches identical without paying more than S. There are three possibilities. (a) A request for f arrives. S faults and S' hits. If S evicts e to make room, the caches are now equal and S' has saved a fault. If S evicts some other page g, then S' evicts g and loads e in its place. That is one load against S's one fault, and the caches are now identical at equal cost. The load is not on demand, but any schedule can be converted to a demand-paging one without adding faults (§06). (b) S evicts e of its own accord, to serve some other page. S' evicts f in the same step, and the caches become identical at the same cost. (c) A request for e arrives before any request for f. This is the case that cannot happen: FF chose e because its next request is furthest away, so f is requested first, or neither is ever requested again, in which case the difference never matters. In every case S' pays no more than S and agrees with FF for one more step.

This is the "greedy stays ahead / exchange" template of Greedy Algorithms, with one feature worth noting. The exchange is done locally in time: the argument never compares whole schedules, only the stretch from step j + 1 to the first request that separates e from f. The same shape of proof shows that earliest-deadline-first minimises maximum lateness in that chapter's §08.

What Belady's rule is used for in practice

  • As the ceiling in trace studies. Given a recorded trace of a real workload, FF gives the best hit rate any cache of size k could have had. A new policy is judged by how much of the gap between LRU and FF it closes. Every row of §08's figure prints its ratio to FF for this reason.
  • As a training target. Learned cache-replacement policies in CPUs and CDNs are often trained to imitate FF's decisions on past traces. The model's features predict "how far in the future is this object's next request", which is exactly the quantity FF sorts by.
  • When the future really is known. Compilers allocating registers over a basic block, schedulers that know a job's full I/O plan, and out-of-core matrix algorithms with a fixed access pattern can all run FF exactly. Register spilling in a straight-line block is often done with this rule, sometimes known by its compiler-community name.
A caution about "OPT" in sizes and costs. FF is optimal for the unit-cost, unit-size problem only. When pages have different sizes, or different miss costs, offline optimal caching becomes NP-hard, since it contains a knapsack-like choice of which set of objects to keep (NP-Completeness, §14). Evicting "the one needed furthest in future" can then be arbitrarily bad, for example evicting a small object needed soon rather than a huge one needed slightly sooner. The CDN literature compares against approximations of the offline optimum for this reason, not against FF.

08 LRU and FIFO are k-competitive, and no deterministic policy is better

Every marking or conservative policy (LRU, FIFO, CLOCK, even flush-when-full) faults at most k times for each fault that Belady's rule must make, plus a constant. There is a sequence on which every deterministic policy faults k times as often as Belady. So k is the exact deterministic competitive ratio of paging. The upper bound depends on the right way to split the sequence, and the lower bound is an adversary who always asks for the one page you do not hold.

upper bound: phasessplit σ into PHASES: phase 1 starts at p₁; each phase is the longest stretch with at most k DISTINCT pages; the next phase starts at the request that would be the (k+1)-th distinct page. Three consequences worth stating separately

  • The ratio does not tell LRU and FIFO apart, but workloads do. Both are k-competitive, and on the cyclic loop both fault on every request. On a skewed workload LRU usually wins, because a hit refreshes a popular page under LRU but not under FIFO. On a drifting working set, compare their bars: FIFO keeps evicting the hot pages of the current working set just because they were loaded early.
  • The cyclic loop is not exotic. It is what a program that scans an array one page larger than the cache does, and LRU is exactly wrong for it: the page it evicts is always the next one needed. Databases deal with this by giving sequential scans their own small ring of buffers so they cannot flush the main pool. The "hot set + one-shot scans" pattern shows scan pages ("s" in the timeline) pushing the hot set out of LRU.
  • Resource augmentation is the practical reading. "LRU with twice the memory is within 2 of optimal" is a guarantee engineers can use, and it matches the observation that LRU's miss rate approaches the optimum as caches grow. When sizing a cache, compare LRU at size k with FF at size k/2. That comparison is at most 2, whatever the workload.
Why CLOCK is what systems actually run. Exact LRU moves an entry to the head of a list on every hit. That is a pointer update under a lock on the hot path of every memory access. CLOCK sets a single reference bit on a hit, often in hardware, and pays for eviction only on a miss, by sweeping a hand past pages whose bit is set and clearing it. It is conservative, so it keeps the k guarantee, and on real workloads it behaves close to LRU. Its bar in the figure shows this. Operating-system page replacement and PostgreSQL's buffer manager both use CLOCK-style sweeps rather than exact LRU (§24). The doubly linked list that exact LRU needs is described in Linked Lists, Stacks & Queues.

09 Belady's anomaly: under FIFO, a bigger cache can fault more

On the request string 1 2 3 4 1 2 5 1 2 3 4 5, FIFO with 3 frames faults 9 times and FIFO with 4 frames faults 10 times. LRU and Belady's rule can never do this: their cache contents at size k are always a subset of their contents at size k + 1, so more memory can only help. The anomaly is a curiosity with a clear lesson. A policy's decisions at one size need not be consistent with its decisions at another, and a property that holds for some policies (more memory never hurts) is not automatically true of all.

the stack (inclusion) propertya policy is a STACK ALGORITHM if for every σ, every time t and every k: Cache_k(t) ⊆ Cache_{k+1}(t) — the k-frame contents are a subset of the (k+1)-frame contents ⟹ faults(k+1) ≤ faults(k) for every σ: whenever the k+1 cache misses, so did the k cache LRU: stack algorithm — Cache_k = the k most recently used distinct pages, which are among the k+1 most recent OPT: stack algorithm — Cache_k = the k pages ranked "soonest next use" among those loaded FIFO: NOT a stack algorithm — "loaded earliest" depends on the fault history, which differs between sizes

The stack property also has a practical payoff. For a stack algorithm, one pass over a trace gives the fault count for every cache size at once. Keep the pages in a recency stack, and for each request record its depth in the stack (its stack distance). The request is a hit in a cache of size k exactly when its depth is at most k. So the histogram of stack distances is the whole miss-ratio curve. This is how cache designers produce the "hit rate against cache size" curves used for sizing. It is not possible for FIFO, because FIFO's contents at different sizes aren't nested.

Faults against cache size: FIFO can rise, LRU and Belady cannot each point is a full simulation at that cache size; a red point is a size at which adding a frame increased the faults. "found by search" is the first anomalous string in a seeded family of random strings, found and verified at page load

Why the anomaly does not contradict FIFO's k-competitiveness

The competitive bound compares FIFO at size k with OPT at size k. It says nothing about FIFO at size k against FIFO at size k + 1. The anomaly needs a string on which FIFO's larger cache keeps exactly the wrong pages, and such strings are uncommon: the seeded search behind the "found" option tries thousands of random strings before one shows it. How large can the anomaly get? It was long conjectured that FIFO's faults at size k + 1 could never exceed twice its faults at size k. That conjecture was later disproved: with enough frames and a long enough constructed string, the ratio is unbounded. It is still a curiosity. The engineering point is the one above: stack algorithms allow single-pass miss-ratio curves and FIFO does not.

Where FIFO is nonetheless the right choice. FIFO is making a comeback in large web caches. On a hit it does nothing at all: no pointer move, no lock, no reference bit. That makes it the cheapest policy to run at millions of requests per second. Recent designs put a small FIFO queue in front of a larger one, promoting an object only if it is hit again while in the small queue. That filters out the one-hit wonders that make up most CDN traffic and matches or beats LRU's hit rate (§24). The anomaly is real, but on real traces it rarely shows up.

10 The randomized marker algorithm: 2H_k ≈ 2 ln k, against a lower bound of H_k

Mark each page when it is requested, and on a fault evict an unmarked page chosen uniformly at random. When every cached page is marked, clear the marks and start a new phase. Against an oblivious adversary, the expected number of faults is at most 2H_k times optimal, where H_k = 1 + 1/2 + … + 1/k ≈ ln k. So randomization improves paging from k to O(log k). For a thousand-slot cache the guarantee is 2H_k ≈ 15 instead of 1 000, against a floor of H_k ≈ 7.5. The analysis counts, phase by phase, how many pages are new to the phase and how likely a stale page is to have been evicted before it is requested again.

the marker algorithmon request p: if p is cached: mark p else (fault): if every cached page is marked: unmark ALL of them — a new phase begins evict a UNIFORMLY RANDOM unmarked page; load p; mark p (a marking algorithm, so ≤ k faults per phase deterministically — the randomness is in WHICH unmarked page goes) the analysis, per phase iNEW pages of phase i: requested in phase i but not in phase i − 1. Let mᵢ be their number. STALE pages of phase i: requested in phase i − 1 and again in phase i. There are k − mᵢ of them. each new page faults once: mᵢ faults the j-th distinct stale page requested faults only if it was evicted earlier in the phase. At that moment at most mᵢ of the k − j + 1 not-yet-requested stale slots have been used up, each equally likely, so P(fault) ≤ mᵢ / (k − j + 1) E[faults in phase i] ≤ mᵢ + Σⱼ₌₁^(k−mᵢ) mᵢ/(k − j + 1) = mᵢ·(1 + H_k − H_{mᵢ}) ≤ mᵢ·H_k OPT: phases i−1 and i together request k + mᵢ distinct pages, so OPT faults ≥ mᵢ over each such pair; summing over the odd pairs and the even pairs: OPT ≥ ½ Σᵢ mᵢ ⟹ E[MARKER] ≤ H_k · Σ mᵢ ≤ 2H_k · OPT. Marker is within a factor 2 of that. More careful algorithms (partitioning, equitable) achieve EXACTLY H_k.

Why the cyclic loop is harmless to the marker

On the loop 0, 1, …, k, 0, 1, …, each phase requests k distinct pages and then the page that starts the next phase. Only one page per phase is new (mᵢ = 1), and the others are stale. LRU evicts exactly the next page needed, every time. The marker evicts a random unmarked page, and the j-th stale page it meets has been evicted with probability about 1/(k − j + 1). Summing gives H_k faults per phase against OPT's one. The sequence is the same, but the deterministic policy is being steered by an adversary who can predict it, and the randomized one is not.

Randomized eviction in real systems. Some processor caches use pseudo-random replacement within a set: it needs no per-line state, and it has no pathological cyclic case. Redis's approximate LRU samples a handful of keys at random and evicts the least recently used among the sample. That is a randomized policy chosen for memory efficiency, and its behaviour approaches true LRU as the sample size grows. Neither is the marker algorithm exactly, but both rely on its lesson: an eviction the workload can't predict can't be systematically exploited by the workload.

11 List update: move-to-front is 2-competitive, by a potential function

Keep n items in a linked list. Accessing the item at position i costs i, and after the access the item may be moved forward for free. Move-to-front (MTF) moves every accessed item to the head. Against any offline algorithm, even one that sees the whole sequence and rearranges the list at will, MTF pays at most twice as much, minus the number of requests. The proof uses the potential method from Algorithm Analysis, with the number of inversions between MTF's list and the offline algorithm's list as the potential. It is the classic example of amortized analysis applied to an online algorithm.

the cost modelaccess the item at position i (1-based) cost i FREE exchange: move the just-accessed item any distance forward cost 0 PAID exchange: swap any two adjacent items cost 1 MTF move the accessed item to the front (free exchanges only) TRANSPOSE swap the accessed item with its predecessor FREQUENCY COUNT (FC) keep the list sorted by access count so far the theoremfor ANY algorithm A (online or offline) and ANY sequence σ of m requests, both starting from the same list: C_MTF(σ) ≤ 2·C_A(σ) + P_A(σ) − F_A(σ) − m C = access cost, P_A = A's paid exchanges, F_A = A's free exchanges. For an A that never pays: C_MTF ≤ 2·C_A − m. ⟹ MTF is 2-competitive. No deterministic algorithm beats 2 − 2/(n + 1); TRANSPOSE and FC are not competitive at all. the potential-function proof, one request at a timeΦ = number of INVERSIONS between MTF's list and A's list (pairs ordered one way in MTF, the other way in A); Φ ≥ 0. request x; x at position k in MTF, position i in A. v = number of items before x in MTF but after x in A — moving x to the front REMOVES these v inversions (k − 1 − v) items are before x in both lists — moving x to the front CREATES these k − 1 − v inversions and since they are before x in A, k − 1 − v ≤ i − 1. amortised cost of MTF's step = k + ΔΦ = k + (k − 1 − v) − v = 2(k − v) − 1 ≤ 2i − 1 (using k − v ≤ i) A's own free exchange moves x forward in A: each removes at most one inversion, ΔΦ ≤ 0 — only helps. A's paid exchange changes one pair: ΔΦ ≤ +1 — charged to A's P_A. sum over the m requests: C_MTF + Φ_end − Φ₀ ≤ 2·C_A − m + P_A and Φ₀ = 0 when both start alike.

What each pattern shows

  • Locality is what MTF exploits. On bursts of repeats MTF beats even the best static list, because after the first access of a burst every repeat costs 1. The static list can't adapt to a burst. This is why self-organising lists appear inside compressors: move-to-front coding turns the locality in the output of the Burrows–Wheeler transform into a stream of small integers that entropy-code well.
  • Transpose can be trapped. Alternate requests for the last two items. Transpose swaps them with each other at the tail on every request and pays n each time. MTF brings both to the front and pays 1 or 2. The ratio of transpose to the optimum grows with n, and with longer adversarial sequences it is unbounded. Frequency count is caught by the reverse trick: a burst of requests for an item that was cold earlier leaves it deep in the list for a long time.
  • Cyclic access is MTF's worst case. Requesting n − 1, n − 2, …, 0 repeatedly makes every MTF access cost n. The static list pays about (n + 1)/2 on average. The ratio approaches 2, and the theorem says it can go no higher.
Why the proof uses a potential and not a phase argument. For paging the phases give a clean block structure. For list update there is none: MTF's cost on a request depends on the entire history of the list. The potential function records exactly the part of that history that matters, which is how differently the two lists are ordered, and makes every step's amortized cost bounded. It's the same move as the dynamic-array proof in Algorithm Analysis, §20. There, the potential banks credit before a doubling. Here, it banks credit whenever MTF's list agrees with A's more than the costs would suggest. The doubly linked list is what makes MTF's move constant-time once the item is found.

12 Online load balancing and bipartite matching, briefly

Two more online problems show the same pattern: a greedy rule with a clean guarantee, an adversary showing the guarantee is tight, and, for matching, a randomized rule that beats every deterministic one against an oblivious adversary. Greedy list scheduling is (2 − 1/m)-competitive for makespan on m machines. Greedy matching is ½-competitive, and the randomized RANKING algorithm is (1 − 1/e)-competitive, which is optimal.

online makespan minimisation (list scheduling)jobs with sizes p₁, p₂, … arrive one by one; assign each IMMEDIATELY and IRREVOCABLY to one of m machines; cost = makespan = the largest machine load. GREEDY: put each job on the currently least-loaded machine. let job j be the one that finishes last, starting at load s: s ≤ (Σᵢ pᵢ − pⱼ)/m (s was the minimum load) makespan = s + pⱼ ≤ Σ pᵢ/m + (1 − 1/m)·pⱼ ≤ OPT + (1 − 1/m)·OPT = (2 − 1/m)·OPT using OPT ≥ Σ pᵢ/m (average load) and OPT ≥ pⱼ (some machine runs the largest job) TIGHT for greedy: m(m − 1) jobs of size 1, then one job of size m. Greedy: (m − 1) + m. OPT: m. online bipartite matchingoffline vertices U are known; online vertices V arrive one at a time with their edges to U, and each must be matched immediately to a free neighbour, or left unmatched forever. GREEDY (match to any free neighbour): a maximal matching, so ≥ ½·OPT — ½-competitive; no deterministic rule does better RANKING: draw a uniformly random ORDER of U once, up front; match each arrival to its free neighbour of best rank E[RANKING] ≥ (1 − 1/e)·OPT ≈ 0.632·OPT against an OBLIVIOUS adversary, and no randomised algorithm does better.

The load-balancing bound is the same argument as the list-scheduling 2-approximation in Greedy Algorithms, and it works online because it never used the order of the jobs. Only the last job's size and the average load enter the proof. Sorting the jobs first (longest first) improves the offline guarantee to 4/3, but that needs the whole input, which is exactly what an online algorithm lacks. The deterministic online lower bound for this problem is about 1.88 for large m, and the best known algorithms reach about 1.92 by keeping some machines deliberately lightly loaded. So greedy's 2 − 1/m is close to the truth.

Matching is the problem behind ad allocation. Advertisers are the offline side, search queries arrive online, and each query must be shown an ad immediately. Deterministic greedy can be tricked. Give the first arrival two neighbours, let greedy pick either one, and have the adversary send the next arrival to the one it picked. That arrival goes unmatched, and repeating the construction on a larger graph holds greedy to half the optimum. RANKING hides its preferences in a random order drawn once, so the adversary can't aim the next arrival at the vertex it will choose. The weighted, budgeted version (each advertiser has a daily budget) has the same 1 − 1/e ratio for an algorithm that discounts bids by how much of the budget has been spent. The trade-off function that achieves it is the same geometric shape as ski rental's optimal distribution (§05).

A single idea connects §04–§12. Every deterministic online rule is steered by an adversary who can predict it, and every randomized one is protected by what the adversary can't see. The guarantees come from charging arguments (phases, potentials, the last job) that are independent of the order of the input. The lower bounds come from an adversary, or from Yao's principle with a well-chosen input distribution. Everything from here on changes the viewpoint: randomness stops being a defence against an adversary and becomes a tool for analysis and for design.
