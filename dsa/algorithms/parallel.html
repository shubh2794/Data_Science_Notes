Parallel Algorithms

Every algorithm in this series so far has been priced on one processor: a single sequence of steps, one after the other, whose length is the running time. Parallel algorithms are priced on many processors at once, and the price has two numbers instead of one. The work T₁ is the total number of steps, exactly the serial cost; the span T∞ is the length of the longest chain of steps that must happen one after another, the time an unlimited number of processors would still need. Their ratio, the parallelism, is the most speedup the algorithm can ever show, and a greedy scheduler achieves close to it: T_p ≤ T₁/p + T∞. This page builds that theory on the fork-join model (spawn, sync, parallel for), draws the computation DAG of real programs and schedules it on p processors, sets Amdahl's and Gustafson's laws beside it, shows why races make results depend on timing, and then works the classic parallel algorithms: reduction, the work-efficient prefix sum and what it unlocks, merge sort with a parallel merge, matrix multiplication by loops, by divide and conquer and on a systolic array, and level-synchronous BFS. The thread that runs through all of it is that span, not work, is what decides the speedup. Every work, span and step count on the page is measured by running the real routine under a tracer.

01 Why parallelism, and why "divide by p" is not the analysis

For about thirty years a program got faster every year without anyone touching it, because the clock got faster; that stopped in the mid-2000s, and since then the extra transistors each generation brings have been spent on more cores, wider vector units and more GPU lanes instead. Speed now comes from doing several things at once, and it has to be earned by the algorithm. The reason the clock stopped is power. Dynamic power in a chip scales roughly as capacitance × voltage² × frequency, and for decades each shrink let voltage fall along with feature size, so frequency could rise at constant power density. Once voltage could no longer fall — leakage current grows sharply as the threshold voltage drops — a higher clock meant a hotter chip, and a chip can only shed so many watts per square centimetre. Transistor counts kept doubling, so designers used them the only way that does not raise the clock: replicate the core.

The naive consequence is "with p cores, divide the running time by p". That is almost never what happens, and the reasons are the content of this page. First, not every step can run alongside every other: a step that needs another step's result must wait for it, so the dependency structure of the computation caps the speedup no matter how many processors there are. Second, someone has to decide which processor runs which step, and a bad schedule wastes processors even when the dependencies allow them to be used. Third, processors share memory, so two steps that each look correct can produce a wrong answer together if they touch the same location without coordination, and the coordination itself costs time. Fourth, some of every real program is serial, and that part does not shrink at all.

Work tells you whether the algorithm is efficient at all — a parallel algorithm whose work is asymptotically larger than the best serial one loses on a small machine before it has a chance to win on a large one. Span tells you how far parallelism can take it. The two are computed by the same recurrence machinery as the serial analysis of Algorithm Analysis, with one change: where the serial recurrence adds the costs of two recursive calls, the span recurrence takes their maximum when the calls run in parallel. That single change is why a divide-and-conquer algorithm from Recursion, Divide & Conquer is the natural shape for a parallel algorithm: its subproblems are independent by construction.

What "processor" means here. The theory is stated for p identical processors sharing one memory, each executing one unit-cost instruction per time step. Real cores are close enough for the asymptotics; GPU lanes and SIMD units are processors that must execute the same instruction in lockstep (§23); a cluster adds communication costs the model leaves out (§21). Every bound on the page names the model it is proved in.

02 The PRAM model, briefly

The parallel random-access machine is the parallel analogue of the RAM model: p processors, a shared memory, and a global clock; at every tick each processor performs one instruction, and the variants differ only in what happens when two processors touch the same memory cell in the same tick. It was the dominant model of parallel algorithms theory for two decades, and it is where the step counts of this page's scan and reduction were first worked out. Its weakness is that the algorithm must say, for every tick, exactly what every processor does — it is a model of a machine, not of a program.

the three standard variants, weakest to strongestEREW exclusive read, exclusive write no two processors touch the same cell in one step CREW concurrent read, exclusive write many may read one cell; only one may write it CRCW concurrent read, concurrent write many may write one cell; a rule picks the result: COMMON all writers must write the same value ARBITRARY one writer, unspecified which, succeeds PRIORITY the lowest-numbered writer succeeds power: EREW ≤ CREW ≤ CRCW, and a p-processor CRCW step can be simulated on EREW in O(log p) steps

The variants genuinely differ. On a COMMON CRCW machine with n processors, the OR of n bits takes one step: every processor holding a 1 writes 1 into a cell initialised to 0. The maximum of n numbers takes O(1) steps with n² processors: processor (i, j) compares a[i] with a[j] and, if a[i] < a[j], writes "not the max" into cell i. On CREW or EREW both problems need Ω(log n) steps, because each step can combine information from only a constant number of cells into one. That log n gap is exactly the O(log p) simulation overhead in the formula block.

The PRAM also introduced the idea that runs through the rest of the page. Summing n numbers on an EREW PRAM with n/2 processors takes ⌈log₂ n⌉ steps: add pairs, then pairs of pairs, up a balanced tree. But n/2 processors are wasteful — most sit idle after the first step. With only p = n / log n processors, have each first add up a block of log n elements serially (log n steps), then run the tree on the p partial sums (log p ≤ log n steps). The time is still O(log n), and now the total operations, p × time = O(n), match the serial algorithm. An algorithm whose processor-time product matches the best serial work is called work-efficient (or work-optimal), and the principle that one can trade processors for time this way is Brent's, from 1974 — §07 proves it in its modern form.

Why the page moves on. A PRAM algorithm is written for a fixed p and a lockstep clock; real machines have neither. The number of available cores changes with the load, cores run at different speeds, and nothing synchronises them every instruction. The next section's model describes the algorithm's logical parallelism once, independently of p, and leaves the mapping onto processors to a scheduler with a provable guarantee. Where this page quotes a PRAM step count it says so; everything else is fork-join.

03 Fork-join: spawn, sync and parallel for

In the fork-join (dynamic multithreading) model a program is an ordinary serial program with three extra keywords — spawn ("this call may run in parallel with what follows"), sync ("wait for everything I spawned"), and parallel for ("these iterations are independent") — and nothing else. The keywords express permission, not obligation: the program says what may run concurrently, and a runtime scheduler decides what actually does. This is the model of Cilk, OpenMP tasks, Intel TBB, Java's fork/join pool, Rust's rayon, .NET's task library and Go's goroutines with wait groups, and it is the model every bound after this section is stated in.

the three keywords, and the running exampleP-FIB(n) if n < 2: return n x = spawn P-FIB(n − 1) ▸ the child MAY run in parallel with the parent's next line y = P-FIB(n − 2) ▸ the parent keeps going — it does not wait here sync ▸ wait until every child spawned by THIS call has returned return x + y parallel for i = 1 to n: body(i) ≡ recursively split [1, n] in half, spawn one half, run the other, sync → spawning n iterations has span Θ(log n), not Θ(1) and not Θ(n) (§11)

Three properties make the model the practical one. It is processor-oblivious: the program never mentions p, so the same binary runs on two cores or two hundred. It has a serial projection: delete the keywords and you get a correct serial program computing the same result — provided the program is free of determinacy races (§12). That is what makes it debuggable: every question about what the program computes is a question about a serial program. It composes: a parallel library routine called from inside a parallel loop just adds more spawns to the same pool; nothing oversubscribes the machine, because the scheduler, not the program, maps work to threads.

The trade is that spawn is cheap but not free — a well-engineered runtime makes it a few times the cost of a function call — so real code stops spawning below a grain size and runs the base case serially. The analysis on this page counts every spawn as a unit strand, which makes the constants honest about the overhead while leaving the asymptotics unchanged; §24 returns to what the grain size does in practice.

Fork-join against threads. Creating an OS thread per spawn would work in principle and fail in practice: thread creation costs tens of microseconds, and P-FIB(30) spawns over a million children. The runtime instead keeps one worker thread per core and treats each spawn as a small task pushed onto that worker's deque (§08). "Thread" in this page's prose means a logical strand of the computation, never an OS thread.

04 The computation DAG

Running a fork-join program on an input unfolds it into a directed acyclic graph: each vertex is a strand — a maximal run of instructions with no spawn, sync or return inside it — and each edge says "this strand must finish before that one starts". The DAG is a property of the program and the input, not of the machine, and every parallel cost on this page is a measurement of it.

the four kinds of edgeCONTINUATION u → u' the next strand in the same procedure instance SPAWN u → v u spawned a child whose first strand is v CALL u → v an ordinary call: v runs, the caller waits (it is a spawn followed at once by a sync) RETURN v → w the child's last strand must finish before the parent's strand after sync two strands are LOGICALLY IN SERIES if a directed path joins them, LOGICALLY IN PARALLEL otherwise. a strand is READY when all its predecessors are done.

This page's figures build the DAG by running the program under a tracer. The tracer offers two operations, work(k) (append k unit strands in series) and par(f, g, …) (run each branch starting from the current point, then join their ends), and each algorithm is written against them once. One tracer records every strand as a vertex, so a figure can draw it and schedule it; a second keeps only two numbers — total work and the current path length — and composes them by the rules of §05. The load-time audit in the cheat sheet checks that the two agree on every small program.

A useful way to read the DAG is as the serial execution with the sequencing relaxed. The serial projection runs the strands in one order, a depth-first walk of the spawn tree. Every other order that respects the edges computes the same result for a race-free program, and a parallel execution is just such an order in which several strands occupy the same time step. The DAG therefore contains exactly two things a scheduler needs: how much there is to do, and what must wait for what.

Unit strands, and why it costs nothing to assume them. A real strand is a run of instructions of some length. Split it into that many unit-time vertices joined in series and nothing about the work, span or schedule changes except that every vertex now costs one step — which is the convention this page uses throughout. Where the text says "strand", read "unit-time vertex of the DAG".

05 Work, span and parallelism

The work T₁ is the number of vertices in the DAG — the time on one processor. The span T∞ is the number of vertices on a longest directed path, the critical path — the time on unboundedly many processors, since even they must execute that chain one step at a time. The parallelism T₁/T∞ is the average amount of work available per step along the critical path, and it is the largest speedup the program can ever show.

Parallelism is the right summary number because it is scale-free: it says how many processors the program can keep busy on average. A program with parallelism 50 can use 8 cores well and 50 cores poorly; one with parallelism 5 000 can use a GPU's worth. The rule of thumb practitioners use — aim for parallelism at least ten times the processor count, called parallel slackness — comes directly from Brent's bound in §07: when T₁/T∞ ≫ p, the T∞ term is negligible and the speedup is nearly p.

Span is not the height of the spawn tree. It is the longest path through the DAG, and that path can run down through spawns, along long serial stretches, and back up through returns. The serial merge is the example: the spawn tree has height log n, but the span is Θ(n) because the merge at the root is a chain of n strands. Always compute span from the recurrence, not from the recursion depth.

06 The work law, the span law and speedup

Two lower bounds hold for every schedule on p processors, whatever the scheduler does. The work law: T_p ≥ T₁/p, because p processors execute at most p strands per step and there are T₁ strands. The span law: T_p ≥ T∞, because the critical path's strands must execute one per step in order, and a machine with p processors can do no better than one with unboundedly many.

The two laws together say T_p ≥ max(T₁/p, T∞), and they pull in opposite directions as p grows: the work term falls like 1/p while the span term is a floor that does not move. Plot speedup against p and it rises along the diagonal S = p until p approaches the parallelism, then flattens toward it. Nothing a scheduler, a compiler or a faster memory system does can lift the curve above that floor; only reducing the span — changing the algorithm — can.

The laws also define what a good parallel algorithm is. Keep the work within a constant factor of the best serial algorithm (work-efficiency: otherwise the parallel version is slower than the serial one on small machines, and the extra work is energy spent for nothing), and make the span as small as possible, ideally polylogarithmic. The algorithms of §14–§22 are all judged by that pair.

Model assumptions behind both laws. Identical processors, unit-time strands, no cost for communication, scheduling or memory contention. Relax any of them and the laws still hold as lower bounds — real overheads only make T_p larger — but the matching upper bounds of the next section need them.

07 Greedy scheduling and Brent's bound

A scheduler is greedy if it never leaves a processor idle while a strand is ready: at each step it runs min(p, number of ready strands) of them. Every greedy scheduler, however it breaks ties, achieves T_p ≤ T₁/p + T∞. Since the laws say T_p ≥ max(T₁/p, T∞) and a + b ≤ 2·max(a, b), a greedy schedule is always within a factor of 2 of the best possible one.

The bound's history is worth one sentence. The original 1974 result was about PRAM computations with a known number of operations at each level: a computation of m operations and t levels runs on p processors in at most t + (m − t)/p steps — the sharper form above. The greedy-scheduler version for arbitrary DAGs is the same argument restated for a dynamic setting, and the reason fork-join programs can be written without mentioning p: the program fixes T₁ and T∞, and any greedy runtime converts them into a running time on whatever p turns up.

What the bound assumes. Unit-time strands (§04 makes this free), identical processors, and a scheduler that knows instantly which strands are ready and can hand them out at no cost. That last assumption is the unrealistic one — a centralised ready queue is a bottleneck on a many-core machine — and the next section is about the schedulers that give up exact greediness to remove it while keeping the bound in expectation.

08 Work stealing: the scheduler real runtimes use

In a work-stealing scheduler each worker keeps its own double-ended queue of ready tasks and works on the bottom of it like a serial program's call stack; only when its deque is empty does it become a thief, pick another worker uniformly at random, and steal the task at the top of that worker's deque. Randomised work stealing runs a fork-join computation in expected time T₁/p + O(T∞) — Brent's bound up to the constant on the span term — with no central queue at all.

the protocolon spawn of child C: push the CONTINUATION of the parent onto the bottom of my deque; run C now ("work-first": the child runs immediately, exactly as in the serial order) on return / sync: pop the bottom of my deque and resume it, if it is still there deque empty: choose a victim uniformly at random; steal the TOP of its deque; repeat on failure the guarantees, for fully strict fork-join computationstime E[T_p] = T₁/p + O(T∞) and the same with high probability, up to a log(1/ε) term steals E[#steal attempts] = O(p · T∞) — communication is proportional to the SPAN, not the work space S_p ≤ p · S₁ — each worker's stack is at most one serial stack deep

Why stealing from the top? The top of a deque holds the oldest continuation, which in a divide-and-conquer program is the one closest to the root of the spawn tree — the one with the most work still under it. A single steal therefore transfers a large piece of the computation, and the thief then runs it locally, pushing and popping its own deque without contention for a long time. Owners touch the bottom and thieves touch the top, so the common case needs no lock; only when the deque is nearly empty do the two ends meet, and that race is resolved with one atomic compare-and-swap. The upshot is that almost all of the T₁ work runs at serial speed with no synchronisation, and the coordination cost scales with T∞ — the same quantity that already bounds the running time.

The space bound is the other half of why the model is practical. A breadth-first scheduler that ran every ready task as soon as possible would, for P-FIB, materialise exponentially many live frames; work-first stealing keeps each worker on a depth-first path, so the total memory is at most p times what the serial program uses. p processors cost at most p stacks, and never more.

Where the model and the runtime part ways. The bound counts steal attempts as unit-time operations and ignores cache effects. In reality a stolen task's data is in another core's cache, so each steal costs a burst of cache misses — the reason grain size matters (§24) and the reason work stealing is paired with locality-aware tweaks such as stealing from a nearby core first. The asymptotics survive; the constants are where the engineering goes.

09 Amdahl's law and Gustafson's law

Amdahl's law is the span law for the crudest possible DAG: a fraction f of the serial running time cannot be parallelised at all, and the rest parallelises perfectly. Then T_p = f·T₁ + (1 − f)·T₁/p, and the speedup can never exceed 1/f however many processors you add. Gustafson's law asks a different question — not "how much faster is this problem?" but "how much bigger a problem can I solve in the same time?" — and gets a speedup that grows linearly in p.

Amdahl — fixed problem size (strong scaling)f = serial fraction of the ONE-processor running time S_p = T₁ / T_p = 1 / ( f + (1 − f)/p ) → 1/f as p → ∞ f = 0.05: S₁₆ = 1 / (0.05 + 0.95/16) ≈ 9.14 and never more than 20, even at a million cores Gustafson — problem grows with p (weak scaling)f = serial fraction of the p-PROCESSOR running time; the parallel part grows in proportion to p scaled speedup S_p = f + p·(1 − f) = p − f·(p − 1) — linear in p, slope 1 − f f = 0.05: S₁₆ = 16 − 0.05 · 15 = 15.25

The two laws do not contradict each other; they measure different things, and the difference is entirely in what f is a fraction of. Amdahl fixes the problem, so as p grows the parallel part shrinks and the serial part becomes an ever larger share of the time until it is all that is left. Gustafson fixes the time and lets the problem grow, which is how large machines are actually used: a weather model on a bigger computer runs at finer resolution, not faster; a larger GPU cluster trains a larger model. The serial part — reading the configuration, setting up, a final reduction — stays the same size while the parallel part grows with p, so its share of the work falls.

Amdahl is a special case of the span law, and a pessimistic one. In work/span terms, Amdahl's program has T∞ = f·T₁ + 1: the serial part is on the critical path and the parallel part adds one step. The span law gives S_p ≤ T₁/T∞ ≈ 1/f — the same ceiling. Real algorithms rarely have a fixed serial fraction; their span grows with n more slowly than their work, so their parallelism rises with problem size. That is Gustafson's observation in algorithmic form, and it is why work and span are the more useful pair of numbers.

10 Strong scaling and weak scaling

A scaling study is a graph of speedup or efficiency against p, and it comes in two kinds that answer the two laws' questions. Strong scaling fixes the total problem and asks how the time falls; weak scaling fixes the problem per processor and asks whether the time stays flat.

The work/span analysis predicts both from one pair of recurrences. For the parallel reduction, T₁ = Θ(n) and T∞ = Θ(log n). Strong scaling at fixed n: speedup rises until p ≈ n / log n and then flattens. Weak scaling with n = p·m: T_p ≈ m + log(p·m), so the time creeps up only logarithmically — near-perfect weak scaling. For merge sort with a serial merge, T∞ = Θ(n), so weak scaling is impossible: the time grows linearly in n = p·m whatever p is. Parallelism that does not grow with the problem is the signature of an algorithm that cannot scale.

Reporting a scaling result honestly. The baseline T₁ should be the best serial program, not the parallel program run on one core — the parallel version carries spawn overhead and extra work, and using it as the baseline inflates the speedup. Say which kind of scaling was measured, the problem size, and the efficiency, not just the speedup; an 80× speedup on 1 000 cores is 8 % efficiency.

11 Analysing parallel recursion: span recurrences and parallel loops

A parallel algorithm is analysed by writing two recurrences from its code: the work recurrence, which is the ordinary serial recurrence, and the span recurrence, which is the same except that calls spawned in parallel contribute the maximum of their spans rather than the sum. Both are then solved with the methods of the master theorem and the recursion tree.

The parallel loop deserves its line. A parallel for over n iterations cannot spawn all n in one step: a spawn creates one child. The runtime therefore splits the range recursively — spawn one half, recurse on the other — which creates a balanced binary tree of spawns of height ⌈log₂ n⌉. That Θ(log n) is invisible in the PRAM, where n processors start together by fiat, and it is the reason several fork-join spans on this page carry one more log factor than their PRAM step counts (§14, §15). It is also why a loop's span is Θ(log n) plus the longest iteration, not the average: one expensive iteration is on the critical path.

12 Race conditions and determinacy races

A determinacy race occurs when two logically parallel strands access the same memory location and at least one of them writes it. The result then depends on the order the scheduler happened to pick, so a program that computes the right answer a thousand times can compute the wrong one on the thousand-and-first, and its serial projection — which always runs one fixed order — will never show the bug.

Two properties make determinacy races the right thing to reason about. First, a program with no determinacy races is deterministic: every schedule computes what the serial projection computes, so testing the serial program tests the parallel one. Second, determinacy races can be detected — a race detector runs the program once, serially, and tracks for every memory location which logically-parallel strands have touched it, reporting any conflicting pair. Because the check is about the DAG, not the schedule, one run on one input finds every race that input can exhibit, whatever the timing. The fork-join model's discipline — share only what you read, give each parallel strand its own output location — is what makes the check tractable; the algorithms from §14 on are all written that way. Races that are intended, such as a benign "any writer wins" flag or a lock-free data structure, are a different discipline (data-race-free programming with atomics), and the rest of this page avoids them.

The loop that is almost always a race. A parallel for whose body updates something indexed by a value that is not the loop variable — count[key[i]] += 1, y[i] += A[i][j]·x[j] with i parallel over the inner j, total += a[i]. Each is correct serially and wrong in parallel. The fix is almost never a lock; it is a different algorithm — a reduction (§21), a scan (§16), or a per-strand private copy combined at the end.

13 What coordination costs: atomics, locks, reducers and false sharing

Every way of making concurrent updates to shared memory correct also makes them serial. A lock or an atomic operation on one location lets exactly one strand update it at a time, so n updates to one location have span Θ(n) however they are scheduled — the synchronisation has put them back on a single critical path. The cure is to avoid the shared location, not to protect it.

the options for "many strands contribute to one value" correctness span of n updates cost per update unsynchronised WRONG — one load + one store lock around the update correct Θ(n) (serialised) lock/unlock + contention, waits, convoying atomic fetch-and-add / CAS correct Θ(n) on one cache line tens of cycles uncontended; hundreds when the line bounces between cores REDUCER / private copies correct Θ(log p) combine + Θ(n/p) one private update; one combine per strand + tree combine REDUCTION algorithm (§21) correct Θ(log n) Θ(1)

A reducer (or reduction hyperobject, or a thread-local accumulator) is the fork-join runtime's version of the last two rows: the shared variable is given a private view per strand, each strand updates its own view with no synchronisation, and when strands join their views are combined with the associative operator. Because the combine follows the DAG, a reducer over an associative operation gives the same answer as the serial program — even for non-commutative operations like list append — and has no determinacy race. It is the right tool whenever a loop body naturally "adds to a total".

False sharing is the coordination cost that the program never asked for. Caches move data in lines, typically 64 bytes, and a coherence protocol lets only one core hold a line in the writable state at a time. If two strands write different variables that happen to sit in the same line — adjacent elements of a per-thread counter array is the classic case — the line ping-pongs between their caches on every write, and the two strands run as if they shared a lock, though there is no race and the answer is correct. The fix is layout: pad per-thread data to a cache line, or accumulate in a local variable and write once at the end. False sharing is invisible to the work/span model, which has no caches; it is the most common reason a race-free parallel loop with ample parallelism shows no speedup.

Why not just lock? Locks are also a source of bugs the model cannot see: deadlock, when two strands each hold a lock the other needs; priority inversion; and convoying, when a descheduled lock holder stalls every waiter. A lock also makes the program's result depend on who acquires first whenever the protected operation is not commutative — a lock prevents a data race but not a determinacy race. The fork-join style of this page, where each output location has exactly one writer and combination happens at joins, needs no locks at all.

14 Prefix sums (scan), and the naive parallel scan

The prefix sum, or scan, of x₀, x₁, …, x_{n−1} under an associative operator ⊕ is the sequence of running totals. Serially it is a single loop of n − 1 additions, each depending on the one before — a chain with span n − 1, apparently the least parallel computation there is. It turns out to be parallelisable to logarithmic span with linear work, and it is the most useful parallel primitive after reduction: an enormous range of apparently serial computations are scans in disguise (§16).

The naive scan has the right span on a PRAM and the wrong work. It performs Θ(n log n) additions where the serial loop needs n − 1, so on p processors its time is Θ((n log n)/p + log n) against the serial Θ(n): it only beats the serial loop when p > log n, and on a machine with fewer processors than that it is strictly slower. That is the definition of not work-efficient, and it is exactly the kind of algorithm §06 warned against. Its virtue is that each round is perfectly regular — every element does the same thing — which is why it is still used within a GPU warp, where 32 lanes execute in lockstep anyway and idle lanes cost nothing extra.

Double buffering is part of the algorithm. The round must read the old x[i − 2ᵈ], not a value another strand has already updated in this round. Writing in place is a determinacy race in the sense of §12: whether x[i − 2ᵈ] has been overwritten depends on the schedule. The x' buffer makes each round's reads and writes disjoint.

15 The work-efficient scan: up-sweep and down-sweep

The work-efficient scan does 2(n − 1) additions — twice the serial count, a constant factor — in 2·log₂ n parallel rounds. It runs a reduction up a balanced binary tree (the up-sweep), keeping the partial sums at internal nodes, and then pushes prefixes back down the same tree (the down-sweep): each node passes its incoming prefix to its left child unchanged and passes "prefix ⊕ left child's sum" to its right child.

Why is it correct? After the up-sweep, the cell for each tree node holds the sum of that node's leaves. The down-sweep maintains the invariant "the cell for node v holds the sum of all leaves to the left of v's subtree": true at the root, whose prefix is empty; and preserved going down, because a left child has the same leaves to its left as its parent, and a right child has those plus the whole left sibling. At the leaves the invariant is the definition of the exclusive scan. Getting the inclusive scan costs one more parallel step, yᵢ = scanᵢ ⊕ xᵢ.

For more than a handful of processors, block it. With p ≪ n the best practical scan is three phases: each processor scans its own block of n/p elements serially; the p block totals are scanned (by the tree, or serially if p is small); each processor adds its block's offset to its elements. Work ≈ 2n, time Θ(n/p + log p). This is Brent's trade from §02 again, and it is how library scans on CPUs and GPUs are organised, with the in-block step itself a warp-level scan on a GPU.

16 What scan unlocks: compaction, partition, radix sort and more

A scan turns "each element needs to know where it goes" into a parallel computation: if each element computes a count of how many slots it will occupy, the exclusive scan of those counts is exactly each element's output offset. That one idea parallelises filtering, partitioning, sorting by digits, allocating variable-sized outputs, and building sparse structures — all at Θ(n) work and Θ(log n) span.

The radix-sort line is why scan matters for sorting on GPUs: LSD radix sort needs each pass to be a stable distribution by one digit, and a split by scan is stable by construction, because the offsets preserve the input order within each bucket. With r-bit digits instead of single bits, each pass becomes a histogram and a scan over 2ʳ buckets per block, which is the structure of the fastest known GPU sorts. The quicksort line is the same partition step with a pivot comparison as the predicate: the recursion depth is Θ(log n) in expectation and each level's partition has span Θ(log n), so the expected span is Θ(log² n).

The pattern generalises well beyond sorting. Segmented scan — a scan that restarts at flagged segment boundaries, itself a scan under a cleverly defined associative operator on (flag, value) pairs — runs many independent scans in one pass, which is how sparse matrix–vector products and per-row operations are parallelised over irregular data. Allocation: when each of n tasks produces a variable number of outputs, a scan of the output counts gives each task its slice of one shared output buffer, with no locking. Linear recurrences yᵢ = aᵢ·y_{i−1} + bᵢ are a scan under the associative composition of affine maps, which is how state-space sequence models evaluate a length-n recurrence in logarithmic span during training.

Recognising a scan. If a serial loop carries one accumulator from iteration to iteration, and the update is "combine the accumulator with something from this iteration" under an operation you can show is associative — addition, max, min, matrix product, composition of affine or linear maps, the carry logic of binary addition — the loop is a scan and has logarithmic span. If the update does something non-associative with the accumulator (a data-dependent branch that changes which operation applies, say), it may not be.

17 Parallel merge sort: the naive version and its Θ(n) span

The obvious parallel merge sort spawns the two recursive sorts and merges serially. Its work is the serial Θ(n log n), but its span is Θ(n), because the merge at the top is a serial chain of n steps — so its parallelism is only Θ(log n), and even on a million elements it cannot keep more than a couple of dozen processors busy.

19 Parallel matrix multiplication: loops, divide and conquer, Strassen

Matrix multiplication has so much parallelism that the question is only how to expose it. 20 Systolic arrays: algorithms built as machines

A systolic array is a grid of identical, very simple processors, each connected only to its neighbours, through which data is pumped in a fixed rhythm: every step, each cell reads from its neighbours, does one small operation, and passes values on. There is no shared memory, no scheduler and no long wire — the algorithm is the wiring and the timing. The canonical example is matrix multiplication on an n × n grid, which finishes in 3n − 2 steps; set against this page's work/span accounting it shows exactly what the model leaves out and what a hardware schedule pays for it.

A greedy scheduler with n² processors and a shared memory could finish in at most 2n steps; the systolic array takes 3n − 2, within a factor of 1.5, and in exchange it needs no shared memory at all. Every operand is read from memory exactly once — 2n² values enter at the edges — and is then reused n times as it marches through the grid, so the machine performs n² multiply-adds per step while fetching only 2n values. That ratio of computation to communication, which the PRAM and work/span models treat as free, is what actually limits a dense linear-algebra kernel (§19's closing remark about cache blocking is the same concern in software). Utilisation for a single product tends to ⅓ because cells idle while the skewed wavefront fills and drains the grid; streaming many products through back to back overlaps one product's drain with the next one's fill and drives utilisation towards 1 — throughput, not latency, is what the design optimises.

Other algorithms as machines

The same recipe — a local recurrence, a regular dependence pattern, and a skewed schedule that makes every dependency a one-step move between neighbours — turns many classical loops into arrays. A linear array of n cells computes a matrix–vector product in 2n − 1 steps, and the same array computes convolutions and FIR filters. Any grid dynamic program whose cell reads only its up, left and up-left neighbours — edit distance, LCS, the alignment scores of Dynamic Programming, §15 — can be computed by a linear array sweeping anti-diagonal wavefronts, m + n − 1 steps for an m × n table, which is how special-purpose sequence-alignment hardware works. Odd-even transposition sort is a linear systolic array: n cells, each holding one key and compare-exchanging with a neighbour on alternate steps, sorting in n rounds. The design discipline is the opposite of this page's fork-join model — the schedule is fixed at design time rather than discovered at run time by work stealing — and it pays off exactly when the computation is regular enough to fix.

The modern echo. The matrix units at the heart of machine-learning accelerators are systolic arrays of this kind — hundreds of cells on a side, usually weight-stationary (each cell holds one weight and the activations and partial sums flow past) so that a layer's weights are loaded once and reused for a whole stream of inputs; Neural Network Hardware steps both dataflows cycle by cycle.

21 Map, reduce and the MapReduce view

Two patterns cover a surprising share of parallel programs. A map applies the same function to every element independently — work Θ(n) times the function's work, span Θ(log n) plus the function's span — and is embarrassingly parallel. A reduce combines all elements with an associative operator by a balanced tree — work Θ(n), span Θ(log n). MapReduce is the observation that many large-scale data computations are a map, a regrouping by key, and a reduce per key.

Floating-point addition is the reduction that bites in practice. It is not associative: (1 + 10¹⁶) − 10¹⁶ is 0 in double precision while 1 + (10¹⁶ − 10¹⁶) is 1. A parallel sum therefore generally gives a slightly different answer from the serial loop, and a runtime that combines partial sums in whatever order threads finish gives a different answer from run to run. The tree order is usually more accurate than the serial loop — its rounding error grows like O(log n) rather than O(n) — but reproducibility needs a fixed reduction tree. The vectorised reductions of NumPy's axis reductions use pairwise summation for exactly this reason.

MapReduce and its successors are the same algebra at cluster scale, where the model must be extended with the cost the work/span model leaves out: moving data between machines. The shuffle is an all-to-all exchange and usually dominates; a combiner — running the reducer locally on each mapper's output before the shuffle — is only legal because ⊕ is associative and commutative, and it can shrink the shuffle by orders of magnitude. Dataflow engines generalise the one-shot map-shuffle-reduce into a DAG of such stages kept in memory, which is precisely a computation DAG in the sense of §04 whose vertices are whole partitions of data rather than single instructions.

The same reduction at the heart of distributed training. Data-parallel training computes a gradient on each worker's shard and needs their sum on every worker — an all-reduce. A tree all-reduce has Θ(log p) latency; the ring all-reduce used in practice sends each worker's data in p chunks around a ring, reaching bandwidth-optimal 2(p − 1)/p times the gradient size per worker, independent of p. Distributed Training works through that trade-off, and its data-parallel section is this page's reduction running across GPUs.

22 Parallel BFS, level by level

Breadth-first search parallelises naturally by levels: all vertices at distance d form the frontier, and expanding the whole frontier at once produces the frontier at distance d + 1. With a parallel loop over the frontier's edges and a scan to compact the next frontier, the work stays O(V + E) and the span is O(D · log V), where D is the number of levels — the eccentricity of the source.

level-synchronous BFSdist[s] = 0; F = [s]; d = 0 while F is not empty: parallel for each u in F, parallel for each edge (u, v): if dist[v] = ∞ and CAS(dist[v], ∞, d + 1): ▸ exactly one discoverer wins; no duplicates mark v as "in next frontier" F = compact(marked vertices) ▸ scan-based compaction, §16 d = d + 1 work O(V + E) ▸ every vertex enters F once; every edge is examined from each side once span O(D · log V) ▸ D rounds, each a parallel loop plus a scan, Θ(log V) span per round

The shape of the input decides whether this is fast. On a road network, D is in the thousands and each frontier is small, so there is little parallelism per round and many rounds — BFS on high-diameter graphs parallelises poorly. On a social or web graph, D is typically under 20 and the middle frontiers contain most of the graph, so each round has enormous parallelism. That second case inspired direction-optimising BFS: when the frontier is large, it is cheaper for each unvisited vertex to check whether any neighbour is in the frontier (stopping at the first) than for each frontier vertex to push along every edge. The serial algorithm, its queue invariant and the distance proof are in Graph Representations & Traversal; the parallel version keeps the invariant level by level rather than vertex by vertex.

The atomic is a correctness device, not a race. Two frontier vertices can discover the same v in the same round. With a plain write, both would add v to the next frontier, and duplicate entries would inflate the work beyond O(V + E). The compare-and-swap makes exactly one discoverer win. Distances are still deterministic — every writer writes the same d + 1 — but the BFS parent of v is whichever discoverer won, and varies from run to run.

The stragglers problem, in this page's terms. At the end of a parallel stage the slowest task is on the critical path, so one machine that is 3× slower than the rest makes the whole stage 3× slower whatever p is. That is the span law applied to a DAG whose vertex costs are not uniform, and the standard fix — launch a backup copy of a slow task and take whichever finishes first — spends extra work to shorten the span.
