14 Prefix sums (scan), and the naive parallel scan

The prefix sum, or scan, of x₀, x₁, …, x_{n−1} under an associative operator ⊕ is the sequence of running totals. Serially it is a single loop of n − 1 additions, each depending on the one before — a chain with span n − 1, apparently the least parallel computation there is. It turns out to be parallelisable to logarithmic span with linear work, and it is the most useful parallel primitive after reduction: an enormous range of apparently serial computations are scans in disguise (§16).

The naive scan has the right span on a PRAM and the wrong work. It performs Θ(n log n) additions where the serial loop needs n − 1, so on p processors its time is Θ((n log n)/p + log n) against the serial Θ(n): it only beats the serial loop when p > log n, and on a machine with fewer processors than that it is strictly slower. That is the definition of not work-efficient, and it is exactly the kind of algorithm §06 warned against. Its virtue is that each round is perfectly regular — every element does the same thing — which is why it is still used within a GPU warp, where 32 lanes execute in lockstep anyway and idle lanes cost nothing extra.

Double buffering is part of the algorithm. The round must read the old x[i − 2ᵈ], not a value another strand has already updated in this round. Writing in place is a determinacy race in the sense of §12: whether x[i − 2ᵈ] has been overwritten depends on the schedule. The x' buffer makes each round's reads and writes disjoint.

15 The work-efficient scan: up-sweep and down-sweep

The work-efficient scan does 2(n − 1) additions — twice the serial count, a constant factor — in 2·log₂ n parallel rounds. It runs a reduction up a balanced binary tree (the up-sweep), keeping the partial sums at internal nodes, and then pushes prefixes back down the same tree (the down-sweep): each node passes its incoming prefix to its left child unchanged and passes "prefix ⊕ left child's sum" to its right child.

Step through the figure and watch both phases. In the up-sweep each round halves the number of active additions — n/2, n/4, …, 1 — so the total is n − 1, exactly the additions of a reduction tree. The clear step saves the total and zeroes the root. The down-sweep reverses the pattern, and each round's teal arrows copy a parent prefix down to a left child while the amber arrows add the left child's saved subtree sum into the right child. Switch to the naive algorithm to compare: fewer rounds, but every round touches almost every element, and the addition counter runs away from n − 1.

Why is it correct? After the up-sweep, the cell for each tree node holds the sum of that node's leaves. The down-sweep maintains the invariant "the cell for node v holds the sum of all leaves to the left of v's subtree": true at the root, whose prefix is empty; and preserved going down, because a left child has the same leaves to its left as its parent, and a right child has those plus the whole left sibling. At the leaves the invariant is the definition of the exclusive scan. Getting the inclusive scan costs one more parallel step, yᵢ = scanᵢ ⊕ xᵢ.

For more than a handful of processors, block it. With p ≪ n the best practical scan is three phases: each processor scans its own block of n/p elements serially; the p block totals are scanned (by the tree, or serially if p is small); each processor adds its block's offset to its elements. Work ≈ 2n, time Θ(n/p + log p). This is Brent's trade from §02 again, and it is how library scans on CPUs and GPUs are organised, with the in-block step itself a warp-level scan on a GPU.

16 What scan unlocks: compaction, partition, radix sort and more

A scan turns "each element needs to know where it goes" into a parallel computation: if each element computes a count of how many slots it will occupy, the exclusive scan of those counts is exactly each element's output offset. That one idea parallelises filtering, partitioning, sorting by digits, allocating variable-sized outputs, and building sparse structures — all at Θ(n) work and Θ(log n) span.

stream compaction — keep the elements satisfying a predicate, in orderinput x = [ 5, 8, 2, 9, 4, 7, 6, 1 ] keep if even flags f = [ 0, 1, 1, 0, 1, 0, 1, 0 ] parallel map Θ(n) work, Θ(log n) span offsets s = exclusive-scan(f) = [ 0, 0, 1, 2, 2, 3, 3, 4 ] scan Θ(n) work, Θ(log n) span scatter if fᵢ = 1: out[sᵢ] = xᵢ parallel map out = [8, 2, 4, 6] size s_{n−1} + f_{n−1} = 4 no two writes collide, so no race parallel partition and one pass of radix sortSPLIT by a bit (or by "< pivot"): zeros go first, in order: position = exclusive-scan(1 − b)ᵢ ones go after them, in order: position = (#zeros) + exclusive-scan(b)ᵢ → a STABLE partition in Θ(n) work, Θ(log n) span LSD radix sort on k-bit keys = k stable splits → Θ(k·n) work, Θ(k·log n) span QUICKSORT with a parallel partition: Θ(n log n) expected work, Θ(log² n) expected span

The radix-sort line is why scan matters for sorting on GPUs: LSD radix sort needs each pass to be a stable distribution by one digit, and a split by scan is stable by construction, because the offsets preserve the input order within each bucket. With r-bit digits instead of single bits, each pass becomes a histogram and a scan over 2ʳ buckets per block, which is the structure of the fastest known GPU sorts. The quicksort line is the same partition step with a pivot comparison as the predicate: the recursion depth is Θ(log n) in expectation and each level's partition has span Θ(log n), so the expected span is Θ(log² n).

The pattern generalises well beyond sorting. Segmented scan — a scan that restarts at flagged segment boundaries, itself a scan under a cleverly defined associative operator on (flag, value) pairs — runs many independent scans in one pass, which is how sparse matrix–vector products and per-row operations are parallelised over irregular data. Allocation: when each of n tasks produces a variable number of outputs, a scan of the output counts gives each task its slice of one shared output buffer, with no locking. Linear recurrences yᵢ = aᵢ·y_{i−1} + bᵢ are a scan under the associative composition of affine maps, which is how state-space sequence models evaluate a length-n recurrence in logarithmic span during training.

Recognising a scan. If a serial loop carries one accumulator from iteration to iteration, and the update is "combine the accumulator with something from this iteration" under an operation you can show is associative — addition, max, min, matrix product, composition of affine or linear maps, the carry logic of binary addition — the loop is a scan and has logarithmic span. If the update does something non-associative with the accumulator (a data-dependent branch that changes which operation applies, say), it may not be.
