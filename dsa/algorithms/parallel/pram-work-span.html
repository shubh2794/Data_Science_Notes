02 The PRAM model, briefly

The parallel random-access machine is the parallel analogue of the RAM model: p processors, a shared memory, and a global clock; at every tick each processor performs one instruction, and the variants differ only in what happens when two processors touch the same memory cell in the same tick. It was the dominant model of parallel algorithms theory for two decades, and it is where the step counts of this page's scan and reduction were first worked out. Its weakness is that the algorithm must say, for every tick, exactly what every processor does — it is a model of a machine, not of a program.

the three standard variants, weakest to strongestEREW exclusive read, exclusive write no two processors touch the same cell in one step CREW concurrent read, exclusive write many may read one cell; only one may write it CRCW concurrent read, concurrent write many may write one cell; a rule picks the result: COMMON all writers must write the same value ARBITRARY one writer, unspecified which, succeeds PRIORITY the lowest-numbered writer succeeds power: EREW ≤ CREW ≤ CRCW, and a p-processor CRCW step can be simulated on EREW in O(log p) steps

The variants genuinely differ. On a COMMON CRCW machine with n processors, the OR of n bits takes one step: every processor holding a 1 writes 1 into a cell initialised to 0. The maximum of n numbers takes O(1) steps with n² processors: processor (i, j) compares a[i] with a[j] and, if a[i] < a[j], writes "not the max" into cell i. On CREW or EREW both problems need Ω(log n) steps, because each step can combine information from only a constant number of cells into one. That log n gap is exactly the O(log p) simulation overhead in the formula block.

The PRAM also introduced the idea that runs through the rest of the page. Summing n numbers on an EREW PRAM with n/2 processors takes ⌈log₂ n⌉ steps: add pairs, then pairs of pairs, up a balanced tree. But n/2 processors are wasteful — most sit idle after the first step. With only p = n / log n processors, have each first add up a block of log n elements serially (log n steps), then run the tree on the p partial sums (log p ≤ log n steps). The time is still O(log n), and now the total operations, p × time = O(n), match the serial algorithm. An algorithm whose processor-time product matches the best serial work is called work-efficient (or work-optimal), and the principle that one can trade processors for time this way is Brent's, from 1974 — §07 proves it in its modern form.

Why the page moves on. A PRAM algorithm is written for a fixed p and a lockstep clock; real machines have neither. The number of available cores changes with the load, cores run at different speeds, and nothing synchronises them every instruction. The next section's model describes the algorithm's logical parallelism once, independently of p, and leaves the mapping onto processors to a scheduler with a provable guarantee. Where this page quotes a PRAM step count it says so; everything else is fork-join.

03 Fork-join: spawn, sync and parallel for

In the fork-join (dynamic multithreading) model a program is an ordinary serial program with three extra keywords — spawn ("this call may run in parallel with what follows"), sync ("wait for everything I spawned"), and parallel for ("these iterations are independent") — and nothing else. The keywords express permission, not obligation: the program says what may run concurrently, and a runtime scheduler decides what actually does. This is the model of Cilk, OpenMP tasks, Intel TBB, Java's fork/join pool, Rust's rayon, .NET's task library and Go's goroutines with wait groups, and it is the model every bound after this section is stated in.

the three keywords, and the running exampleP-FIB(n) if n < 2: return n x = spawn P-FIB(n − 1) ▸ the child MAY run in parallel with the parent's next line y = P-FIB(n − 2) ▸ the parent keeps going — it does not wait here sync ▸ wait until every child spawned by THIS call has returned return x + y parallel for i = 1 to n: body(i) ≡ recursively split [1, n] in half, spawn one half, run the other, sync → spawning n iterations has span Θ(log n), not Θ(1) and not Θ(n) (§11)

Three properties make the model the practical one. It is processor-oblivious: the program never mentions p, so the same binary runs on two cores or two hundred. It has a serial projection: delete the keywords and you get a correct serial program computing the same result — provided the program is free of determinacy races (§12). That is what makes it debuggable: every question about what the program computes is a question about a serial program. It composes: a parallel library routine called from inside a parallel loop just adds more spawns to the same pool; nothing oversubscribes the machine, because the scheduler, not the program, maps work to threads.

The trade is that spawn is cheap but not free — a well-engineered runtime makes it a few times the cost of a function call — so real code stops spawning below a grain size and runs the base case serially. The analysis on this page counts every spawn as a unit strand, which makes the constants honest about the overhead while leaving the asymptotics unchanged; §24 returns to what the grain size does in practice.

Fork-join against threads. Creating an OS thread per spawn would work in principle and fail in practice: thread creation costs tens of microseconds, and P-FIB(30) spawns over a million children. The runtime instead keeps one worker thread per core and treats each spawn as a small task pushed onto that worker's deque (§08). "Thread" in this page's prose means a logical strand of the computation, never an OS thread.

04 The computation DAG

Running a fork-join program on an input unfolds it into a directed acyclic graph: each vertex is a strand — a maximal run of instructions with no spawn, sync or return inside it — and each edge says "this strand must finish before that one starts". The DAG is a property of the program and the input, not of the machine, and every parallel cost on this page is a measurement of it.

the four kinds of edgeCONTINUATION u → u' the next strand in the same procedure instance SPAWN u → v u spawned a child whose first strand is v CALL u → v an ordinary call: v runs, the caller waits (it is a spawn followed at once by a sync) RETURN v → w the child's last strand must finish before the parent's strand after sync two strands are LOGICALLY IN SERIES if a directed path joins them, LOGICALLY IN PARALLEL otherwise. a strand is READY when all its predecessors are done.

This page's figures build the DAG by running the program under a tracer. The tracer offers two operations, work(k) (append k unit strands in series) and par(f, g, …) (run each branch starting from the current point, then join their ends), and each algorithm is written against them once. One tracer records every strand as a vertex, so a figure can draw it and schedule it; a second keeps only two numbers — total work and the current path length — and composes them by the rules of §05. The load-time audit in the cheat sheet checks that the two agree on every small program.

A useful way to read the DAG is as the serial execution with the sequencing relaxed. The serial projection runs the strands in one order, a depth-first walk of the spawn tree. Every other order that respects the edges computes the same result for a race-free program, and a parallel execution is just such an order in which several strands occupy the same time step. The DAG therefore contains exactly two things a scheduler needs: how much there is to do, and what must wait for what.

Unit strands, and why it costs nothing to assume them. A real strand is a run of instructions of some length. Split it into that many unit-time vertices joined in series and nothing about the work, span or schedule changes except that every vertex now costs one step — which is the convention this page uses throughout. Where the text says "strand", read "unit-time vertex of the DAG".

05 Work, span and parallelism

The work T₁ is the number of vertices in the DAG — the time on one processor. The span T∞ is the number of vertices on a longest directed path, the critical path — the time on unboundedly many processors, since even they must execute that chain one step at a time. The parallelism T₁/T∞ is the average amount of work available per step along the critical path, and it is the largest speedup the program can ever show.

the composition rules — one rule for work, two for span WORK SPAN A then B (series) T₁(A) + T₁(B) T∞(A) + T∞(B) A ∥ B (parallel) T₁(A) + T₁(B) max(T∞(A), T∞(B)) work ALWAYS adds. span adds in series and takes the MAX in parallel. applied to P-FIB, counting each strand as one stepT₁(n) = T₁(n − 1) + T₁(n − 2) + Θ(1) = Θ(F(n)) = Θ(φⁿ), φ = (1 + √5)/2 ≈ 1.618 T∞(n) = max(T∞(n − 1), T∞(n − 2)) + Θ(1) = T∞(n − 1) + Θ(1) = Θ(n) parallelism T₁/T∞ = Θ(φⁿ / n) — enormous: far more than any machine has cores

The figure draws the DAG of a small program with time running left to right: each vertex sits at its depth, the length of the longest path reaching it, which is the earliest step it could run with unlimited processors. The critical path is traced back from the deepest vertex. P-FIB's DAG is the call tree of the naive Fibonacci recursion with a spawn strand going in and a combine strand coming out of each internal call, so its width grows like the Fibonacci numbers while its depth grows by two per level. The serial loop is a single chain: work and span are equal and the parallelism is exactly 1. The reduction is a balanced tree going out and a balanced tree coming back, depth logarithmic in n. Merge sort with a serial merge is the instructive one: the recursion fans out beautifully, then the final merge is a chain of length n that nothing can shorten — the critical path runs straight through it.

Parallelism is the right summary number because it is scale-free: it says how many processors the program can keep busy on average. A program with parallelism 50 can use 8 cores well and 50 cores poorly; one with parallelism 5 000 can use a GPU's worth. The rule of thumb practitioners use — aim for parallelism at least ten times the processor count, called parallel slackness — comes directly from Brent's bound in §07: when T₁/T∞ ≫ p, the T∞ term is negligible and the speedup is nearly p.

Span is not the height of the spawn tree. It is the longest path through the DAG, and that path can run down through spawns, along long serial stretches, and back up through returns. The serial merge is the example: the spawn tree has height log n, but the span is Θ(n) because the merge at the root is a chain of n strands. Always compute span from the recurrence, not from the recursion depth.

06 The work law, the span law and speedup

Two lower bounds hold for every schedule on p processors, whatever the scheduler does. The work law: T_p ≥ T₁/p, because p processors execute at most p strands per step and there are T₁ strands. The span law: T_p ≥ T∞, because the critical path's strands must execute one per step in order, and a machine with p processors can do no better than one with unboundedly many.

the two laws and what they imply for speedupWORK LAW T_p ≥ T₁ / p ⟹ speedup S_p = T₁ / T_p ≤ p SPAN LAW T_p ≥ T∞ ⟹ speedup S_p = T₁ / T_p ≤ T₁ / T∞ (the parallelism) S_p = Θ(p) LINEAR speedup S_p = p PERFECT linear speedup S_p > p SUPERLINEAR — impossible in this model; in practice a sign that the baseline was slow or that p caches held a working set that one cache could not (§24) efficiency E_p = S_p / p ∈ (0, 1] slackness (T₁/T∞) / p — how many times more parallelism than processors; ≫ 1 is what you want

The two laws together say T_p ≥ max(T₁/p, T∞), and they pull in opposite directions as p grows: the work term falls like 1/p while the span term is a floor that does not move. Plot speedup against p and it rises along the diagonal S = p until p approaches the parallelism, then flattens toward it. Nothing a scheduler, a compiler or a faster memory system does can lift the curve above that floor; only reducing the span — changing the algorithm — can.

The laws also define what a good parallel algorithm is. Keep the work within a constant factor of the best serial algorithm (work-efficiency: otherwise the parallel version is slower than the serial one on small machines, and the extra work is energy spent for nothing), and make the span as small as possible, ideally polylogarithmic. The algorithms of §14–§22 are all judged by that pair.

Model assumptions behind both laws. Identical processors, unit-time strands, no cost for communication, scheduling or memory contention. Relax any of them and the laws still hold as lower bounds — real overheads only make T_p larger — but the matching upper bounds of the next section need them.
