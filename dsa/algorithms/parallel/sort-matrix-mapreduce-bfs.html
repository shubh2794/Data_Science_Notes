17 Parallel merge sort: the naive version and its Θ(n) span

The obvious parallel merge sort spawns the two recursive sorts and merges serially. Its work is the serial Θ(n log n), but its span is Θ(n), because the merge at the top is a serial chain of n steps — so its parallelism is only Θ(log n), and even on a million elements it cannot keep more than a couple of dozen processors busy.

naive parallel merge sortMERGE-SORT′(A, lo, hi) if hi − lo ≤ 1: return mid = ⌊(lo + hi)/2⌋ spawn MERGE-SORT′(A, lo, mid) MERGE-SORT′(A, mid, hi) sync MERGE(A, lo, mid, hi) ▸ the serial two-finger merge — Θ(n), on the critical path T₁(n) = 2·T₁(n/2) + Θ(n) = Θ(n log n) T∞(n) = T∞(n/2) + Θ(n) = Θ(n) ▸ n + n/2 + n/4 + … ≤ 2n parallelism T₁/T∞ = Θ(log n) ▸ for n = 10⁶, about 20

The recurrence shows exactly where the span goes: at every level of the recursion, one merge sits on the critical path, and the merges at the top dominate — the root's merge alone is half the span. Parallelising the recursion without parallelising the combine step is the most common way a divide-and-conquer algorithm fails to scale, because the combine step is where the serial merge sort does all of its work. The schedule figure of §07 shows the consequence: select the serial-merge sort and the measured T_p flattens against the span floor after a few processors, while the processors sit idle through the final merge.

This is the general lesson of the page. Speedup is limited by span, and span is limited by the least parallel step on the critical path. A divide-and-conquer algorithm has a parallel span only if its divide and combine steps do. For merge sort, the divide step is trivial and the combine step is the whole problem — so the next section parallelises the merge itself.

18 Parallel merge by binary-search splitting, and a Θ(log³ n)-span sort

To merge two sorted arrays in parallel, take the median x of the longer one, binary-search for where x would go in the shorter one, and place x at the output position that those two indices determine. Everything smaller than x from both arrays belongs to the left of it and everything larger to the right, so the two remaining merges are independent — spawn them. The merge then has Θ(n) work and Θ(log² n) span, and the sort built on it has Θ(n log n) work and Θ(log³ n) span.

the parallel mergeP-MERGE(T[p₁..r₁], T[p₂..r₂], A, p₃) ▸ merge two sorted runs into A starting at p₃ n₁ = r₁ − p₁ + 1, n₂ = r₂ − p₂ + 1 if n₁ < n₂: swap the runs ▸ make the first run the longer one if n₁ = 0: return ▸ both empty q₁ = ⌊(p₁ + r₁)/2⌋ ▸ median of the longer run q₂ = BINARY-SEARCH(T[q₁], T, p₂, r₂) ▸ first index in run 2 with T[q₁] ≤ T[q₂] q₃ = p₃ + (q₁ − p₁) + (q₂ − p₂) ▸ exactly this many elements precede T[q₁] A[q₃] = T[q₁] spawn P-MERGE(T[p₁..q₁−1], T[p₂..q₂−1], A, p₃) P-MERGE(T[q₁+1..r₁], T[q₂..r₂], A, q₃ + 1) sync why each recursive merge is at most 3n/4, and the span it givesn = n₁ + n₂ with n₁ ≥ n₂, so n₂ ≤ n/2. Both trees in the figures above can show this. In the DAG explorer (§05), set the parallel-merge sort beside the serial-merge sort at the same n: the DAG is wider and its critical path is much shorter, at the price of more strands — the binary searches are extra work, a constant factor at these sizes. In the growth figure (§11), the two sorts' work curves nearly coincide while their span curves separate: one a straight line of slope 1 on the log–log plot, the other bending over. The measured span divided by log³ n is still drifting at n = 4 096 because the lower-order log² n terms are the same size as the leading term there; divided by log² n it is still rising. That is what a Θ(log³ n) function with a small leading constant looks like at modest sizes.

Assumptions behind the bound. Fork-join model with unit-cost strands; the temporary T allocated in constant time (or initialised in parallel at Θ(log n) span, which is dominated by the merge); comparisons in constant time. The Θ(log³ n) is not the best possible — Cole's pipelined merge sort reaches Θ(log n) span with Θ(n log n) work on a CREW PRAM, and practical parallel sorts (sample sort, parallel radix sort via §16) use a different structure altogether — but it is the natural fork-join version of merge sort, and the analysis technique carries over to any divide-and-conquer algorithm with a splittable combine step.

19 Parallel matrix multiplication: loops, divide and conquer, Strassen

Matrix multiplication has so much parallelism that the question is only how to expose it. Parallelising the two outer loops gives Θ(n³) work and Θ(n) span, because each output entry's inner product is still a serial loop. Recursing on quadrants, with the eight sub-products spawned in parallel and summed by a parallel addition, cuts the span to Θ(log² n) at the same work.

parallel loopsP-MATRIX-MULTIPLY(A, B, C) ▸ n × n parallel for i = 1 to n: parallel for j = 1 to n: for k = 1 to n: ▸ serial — every iteration writes C[i][j] C[i][j] += A[i][k] · B[k][j] T₁ = Θ(n³) T∞ = Θ(log n) + Θ(log n) + Θ(n) = Θ(n) parallelism Θ(n²) divide and conquer with a temporaryP-MM-RECURSIVE(C, A, B, n) ▸ writes C = A·B if n = 1: C₁₁ = A₁₁ · B₁₁; return allocate T (n × n) ▸ O(1) assumed spawn C₁₁ = A₁₁B₁₁, C₁₂ = A₁₁B₁₂, C₂₁ = A₂₁B₁₁, C₂₂ = A₂₁B₁₂ spawn T₁₁ = A₁₂B₂₁, T₁₂ = A₁₂B₂₂, T₂₁ = A₂₂B₂₁ T₂₂ = A₂₂B₂₂ ▸ the eighth runs in the parent sync parallel for i, j: C[i][j] += T[i][j] ▸ Θ(n²) work, Θ(log n) span T₁(n) = 8·T₁(n/2) + Θ(n²) = Θ(n³) ▸ master theorem, case 1 T∞(n) = T∞(n/2) + Θ(log n) = Θ(log² n) ▸ all eight products are in parallel parallelism Θ(n³ / log² n) the variantsno temporary: do the 4 C-products, sync, then accumulate the other 4 into C T∞(n) = 2·T∞(n/2) + Θ(1) = Θ(n) ▸ saves Θ(n²) memory per level; parallelism back to Θ(n²) inner product as a parallel REDUCTION instead of a serial loop T∞ = Θ(log n) ▸ same work, but Θ(n³) partial sums to combine STRASSEN: 7 products of n/2 × n/2 plus Θ(n²) additions, all parallel T₁(n) = 7·T₁(n/2) + Θ(n²) = Θ(n^(log₂ 7)) ≈ Θ(n^2.81) T∞(n) = T∞(n/2) + Θ(log n) = Θ(log² n) ▸ parallelism Θ(n^2.81 / log² n)

The variants are a textbook example of the work/span/space trade-off. The temporary matrix buys a span of Θ(log² n) by letting the two halves of each output quadrant be computed at the same time, at the cost of Θ(n²) extra memory at the top level and a parallel addition pass. Dropping it saves the memory but puts the two halves in series, and the span recurrence gains a factor of 2 in front — enough to change Θ(log² n) into Θ(n). Since n² is already an enormous parallelism for any real matrix, production libraries usually take the memory-light choice, and spend the saved effort on cache blocking instead: a matrix multiplication's real bottleneck is moving data, not a shortage of parallelism. Strassen's algorithm parallelises exactly as the eight-product version does, because its seven products are independent and its additions are parallel loops.

Select the two matrix multiplications in the growth figure of §11. The measured work of both is Θ(n³) — the divide-and-conquer version's extra additions are a lower-order Θ(n²) per level — while the spans separate: the loop version's grows linearly, the recursive version's by only a few steps each time n doubles. The DAG explorer draws the loop version's DAG for small n: n² independent serial chains of length n, fanned out by two levels of loop-splitting.

Why the inner loop stays serial in the loop version. Parallelising for k naively is the race of §12: every iteration writes C[i][j]. Making it parallel correctly means turning it into a reduction (the "inner product as a parallel reduction" variant), which is legal but rarely worth it — the outer loops already supply n²-way parallelism, and the reduction adds combining work and destroys the inner loop's sequential memory access.

20 Systolic arrays: algorithms built as machines

A systolic array is a grid of identical, very simple processors, each connected only to its neighbours, through which data is pumped in a fixed rhythm: every step, each cell reads from its neighbours, does one small operation, and passes values on. There is no shared memory, no scheduler and no long wire — the algorithm is the wiring and the timing. The canonical example is matrix multiplication on an n × n grid, which finishes in 3n − 2 steps; set against this page's work/span accounting it shows exactly what the model leaves out and what a hardware schedule pays for it.

matrix multiplication, output-stationary — cell (i, j) owns C[i][j]row i of A enters the grid from the left, delayed i steps; column j of B enters from the top, delayed j steps A values move one cell RIGHT per step, B values one cell DOWN per step at step t (t = 0, 1, …) cell (i, j) holds A[i][k] and B[k][j] with k = t − i − j, and if 0 ≤ k < n: C[i][j] += A[i][k] · B[k][j] cell (i, j) is busy for steps i + j … i + j + n − 1; the last cell, (n − 1, n − 1), finishes at step 3n − 3 ⇒ 3n − 2 steps measured by stepping the schedule (every C checked against the triple loop)n = 3: 7 steps, 27 MACs, at most 7 of 9 cells busy in one step n = 8: 22 steps, 512 MACs, at most 48 of 64 busy; utilisation n³ / (n² · (3n − 2)) = 0.364 → ⅓ as n grows k products streamed back to back: k·n + 2(n − 1) steps ⇒ utilisation 0.90 at k = 16, 0.97 at k = 64 (n = 8) in the work/span language of §05–§07work T₁ = n³ multiply-adds span T∞ = n each C[i][j] is a chain of n dependent additions — the loop version of §19 p = n² cells: work law T_p ≥ n; Brent T_p ≤ T₁/p + T∞ = 2n; the systolic schedule 3n − 2 the extra 2(n − 1) steps are the SKEW: a value needs i + j steps to walk from the edge to cell (i, j)

The comparison with §07 is the point of the example. A greedy scheduler with n² processors and a shared memory could finish in at most 2n steps; the systolic array takes 3n − 2, within a factor of 1.5, and in exchange it needs no shared memory at all. Every operand is read from memory exactly once — 2n² values enter at the edges — and is then reused n times as it marches through the grid, so the machine performs n² multiply-adds per step while fetching only 2n values. That ratio of computation to communication, which the PRAM and work/span models treat as free, is what actually limits a dense linear-algebra kernel (§19's closing remark about cache blocking is the same concern in software). Utilisation for a single product tends to ⅓ because cells idle while the skewed wavefront fills and drains the grid; streaming many products through back to back overlaps one product's drain with the next one's fill and drives utilisation towards 1 — throughput, not latency, is what the design optimises.

Other algorithms as machines

The same recipe — a local recurrence, a regular dependence pattern, and a skewed schedule that makes every dependency a one-step move between neighbours — turns many classical loops into arrays. A linear array of n cells computes a matrix–vector product in 2n − 1 steps, and the same array computes convolutions and FIR filters. Any grid dynamic program whose cell reads only its up, left and up-left neighbours — edit distance, LCS, the alignment scores of Dynamic Programming, §15 — can be computed by a linear array sweeping anti-diagonal wavefronts, m + n − 1 steps for an m × n table, which is how special-purpose sequence-alignment hardware works. Odd-even transposition sort is a linear systolic array: n cells, each holding one key and compare-exchanging with a neighbour on alternate steps, sorting in n rounds. The design discipline is the opposite of this page's fork-join model — the schedule is fixed at design time rather than discovered at run time by work stealing — and it pays off exactly when the computation is regular enough to fix.

The modern echo. The matrix units at the heart of machine-learning accelerators are systolic arrays of this kind — hundreds of cells on a side, usually weight-stationary (each cell holds one weight and the activations and partial sums flow past) so that a layer's weights are loaded once and reused for a whole stream of inputs; Neural Network Hardware steps both dataflows cycle by cycle.

21 Map, reduce and the MapReduce view

Two patterns cover a surprising share of parallel programs. A map applies the same function to every element independently — work Θ(n) times the function's work, span Θ(log n) plus the function's span — and is embarrassingly parallel. A reduce combines all elements with an associative operator by a balanced tree — work Θ(n), span Θ(log n). MapReduce is the observation that many large-scale data computations are a map, a regrouping by key, and a reduce per key.

reduction, and the condition it needsREDUCE(x, lo, hi, ⊕) if hi − lo = 1: return x[lo] mid = ⌊(lo + hi)/2⌋ a = spawn REDUCE(x, lo, mid, ⊕); b = REDUCE(x, mid, hi, ⊕); sync return a ⊕ b T₁(n) = 2T₁(n/2) + Θ(1) = Θ(n) T∞(n) = T∞(n/2) + Θ(1) = Θ(log n) REQUIRES ⊕ ASSOCIATIVE — the tree regroups the terms. Commutativity is needed only if the runtime may also REORDER them (unordered combining of per-thread partials does). MapReduce, as three parallel primitivesMAP each input record → zero or more (key, value) pairs parallel map SHUFFLE group all values with the same key together a parallel sort or hash partition (in memory: a scan-based split, §16) REDUCE for each key, combine its values with an associative ⊕ one reduction per key, all in parallel word count: map: document → (word, 1) per word; reduce: ⊕ = + work Θ(total input + shuffle), span ≈ span(map) + span(shuffle) + max over keys of span(reduce)

Floating-point addition is the reduction that bites in practice. It is not associative: (1 + 10¹⁶) − 10¹⁶ is 0 in double precision while 1 + (10¹⁶ − 10¹⁶) is 1. A parallel sum therefore generally gives a slightly different answer from the serial loop, and a runtime that combines partial sums in whatever order threads finish gives a different answer from run to run. The tree order is usually more accurate than the serial loop — its rounding error grows like O(log n) rather than O(n) — but reproducibility needs a fixed reduction tree. The vectorised reductions of NumPy's axis reductions use pairwise summation for exactly this reason.

MapReduce and its successors are the same algebra at cluster scale, where the model must be extended with the cost the work/span model leaves out: moving data between machines. The shuffle is an all-to-all exchange and usually dominates; a combiner — running the reducer locally on each mapper's output before the shuffle — is only legal because ⊕ is associative and commutative, and it can shrink the shuffle by orders of magnitude. Dataflow engines generalise the one-shot map-shuffle-reduce into a DAG of such stages kept in memory, which is precisely a computation DAG in the sense of §04 whose vertices are whole partitions of data rather than single instructions.

The same reduction at the heart of distributed training. Data-parallel training computes a gradient on each worker's shard and needs their sum on every worker — an all-reduce. A tree all-reduce has Θ(log p) latency; the ring all-reduce used in practice sends each worker's data in p chunks around a ring, reaching bandwidth-optimal 2(p − 1)/p times the gradient size per worker, independent of p. Distributed Training works through that trade-off, and its data-parallel section is this page's reduction running across GPUs.

22 Parallel BFS, level by level

Breadth-first search parallelises naturally by levels: all vertices at distance d form the frontier, and expanding the whole frontier at once produces the frontier at distance d + 1. With a parallel loop over the frontier's edges and a scan to compact the next frontier, the work stays O(V + E) and the span is O(D · log V), where D is the number of levels — the eccentricity of the source.

level-synchronous BFSdist[s] = 0; F = [s]; d = 0 while F is not empty: parallel for each u in F, parallel for each edge (u, v): if dist[v] = ∞ and CAS(dist[v], ∞, d + 1): ▸ exactly one discoverer wins; no duplicates mark v as "in next frontier" F = compact(marked vertices) ▸ scan-based compaction, §16 d = d + 1 work O(V + E) ▸ every vertex enters F once; every edge is examined from each side once span O(D · log V) ▸ D rounds, each a parallel loop plus a scan, Θ(log V) span per round

The shape of the input decides whether this is fast. On a road network, D is in the thousands and each frontier is small, so there is little parallelism per round and many rounds — BFS on high-diameter graphs parallelises poorly. On a social or web graph, D is typically under 20 and the middle frontiers contain most of the graph, so each round has enormous parallelism. That second case inspired direction-optimising BFS: when the frontier is large, it is cheaper for each unvisited vertex to check whether any neighbour is in the frontier (stopping at the first) than for each frontier vertex to push along every edge. The serial algorithm, its queue invariant and the distance proof are in Graph Representations & Traversal; the parallel version keeps the invariant level by level rather than vertex by vertex.

The atomic is a correctness device, not a race. Two frontier vertices can discover the same v in the same round. With a plain write, both would add v to the next frontier, and duplicate entries would inflate the work beyond O(V + E). The compare-and-swap makes exactly one discoverer win. Distances are still deterministic — every writer writes the same d + 1 — but the BFS parent of v is whichever discoverer won, and varies from run to run.
