02 Relaxation and the shortest-path optimality conditions

Relaxing an edge (u, v) asks whether the best known way to reach u, extended by that edge, beats the best known way to reach v — and if it does, lowers v's estimate to match and records u as its predecessor. That test is the whole of the single-source machinery: every algorithm from §04 to §15 initialises one estimate per vertex and then performs relaxations in some order, and nothing else ever changes an estimate. The reason this is enough is a short list of properties that hold for any sequence of relaxations whatsoever: estimates never drop below the truth, an estimate that reaches the truth stays there, and relaxing the edges of a shortest path in order — with anything at all happening in between — drives the estimate at its end to the true distance. Each correctness proof on this page is one of those properties applied to one schedule.

The proofs, each a few lines

Triangle inequality. If v is unreachable the right side is what it is and the left is ∞ only if u is unreachable too, so take both reachable. A shortest s ⇝ u path followed by the edge (u, v) is a walk from s to v of weight δ(s, u) + w(u, v); with no negative cycle reachable, any walk contains a simple path of no greater weight (cut out each cycle — its weight is ≥ 0), and δ(s, v) is the minimum over paths, so δ(s, v) ≤ δ(s, u) + w(u, v). Upper bound. Induction over the sequence of relaxations. After initialisation d[s] = 0 = δ(s, s) (no negative cycle reachable means no negative cycle through s, so the empty path is shortest) and every other d[v] = ∞ ≥ δ(s, v). A relaxation of (u, v) that changes anything sets d[v] = d[u] + w(u, v) ≥ δ(s, u) + w(u, v) ≥ δ(s, v), the first step by the induction hypothesis on u and the second by the triangle inequality. The second half follows: relaxation only ever lowers an estimate, and it cannot go below δ, so an estimate that equals δ is stuck. No path. δ(s, v) = ∞, and d[v] ≥ δ(s, v) by the upper-bound property. Convergence. Suppose d[u] = δ(s, u) before (u, v) is relaxed. It still equals δ(s, u) at the moment of relaxation, by the upper-bound property. Afterwards d[v] ≤ d[u] + w(u, v) = δ(s, u) + w(u, v) = δ(s, v) — the last equality because the s ⇝ u part of a shortest s ⇝ u → v path is itself a shortest path (Dynamic Programming, §02: splice a shorter one in and the whole gets shorter). Combined with d[v] ≥ δ(s, v) that is equality, and it persists. Path relaxation. Induction on i: after the i-th listed relaxation, d[vᵢ] = δ(s, vᵢ). For i = 0 this is d[s] = 0 from initialisation, never changed thereafter. For the step, every prefix of a shortest path is a shortest path, so s ⇝ vᵢ₋₁ → vᵢ is one; d[vᵢ₋₁] = δ(s, vᵢ₋₁) holds before (vᵢ₋₁, vᵢ) is relaxed by the hypothesis, and the convergence property gives d[vᵢ] = δ(s, vᵢ) afterwards, whatever other relaxations intervened. Predecessor subgraph. Two facts. First, G_π never contains a cycle: if relaxing (vₖ₋₁, vₖ) closed a cycle ⟨v₀, …, vₖ = v₀⟩ of π-pointers, then just before it, for each earlier edge on the cycle, d[vᵢ] ≥ d[vᵢ₋₁] + w(vᵢ₋₁, vᵢ) — equality held when π[vᵢ] was set and d[vᵢ₋₁] can only have dropped since — while for the closing edge d[vₖ] > d[vₖ₋₁] + w strictly; summing around the cycle, the d terms cancel and leave 0 > w(cycle), a negative cycle reachable from s, which was excluded. So G_π is a forest in which every vertex has at most one parent, connected through s — a tree. Second, once every d[v] = δ(s, v), take the π-path ⟨s = v₀, …, vₖ = v⟩; the same inequality d[vᵢ] ≥ d[vᵢ₋₁] + w now reads w(vᵢ₋₁, vᵢ) ≤ δ(s, vᵢ) − δ(s, vᵢ₋₁), and summing telescopes to w(path) ≤ δ(s, v) − 0. A path cannot weigh less than δ, so it weighs exactly δ: the π-path is a shortest path.

What the properties buy: correctness is a statement about order

Put the path-relaxation property next to the upper-bound property and the shape of every proof to come is visible. To show that an algorithm computes δ(s, v) it suffices to show that its schedule relaxes the edges of some shortest s ⇝ v path in path order; the estimates it happens to produce in between are irrelevant, because none of them can overshoot below the truth and the listed relaxations force the truth regardless. Bellman-Ford's proof (§08) is exactly this: a shortest path has at most V − 1 edges, and a schedule that relaxes every edge in each of V − 1 rounds relaxes the path's i-th edge no later than round i. The DAG algorithm's proof (§09) is the same with "round" replaced by "topological position". Dijkstra's proof (§05) is subtler because its schedule relaxes each edge once, so the order must be right the first time — which is what non-negative weights guarantee and what the figure of §05 breaks. The properties also say what a wrong answer must look like: since d[v] ≥ δ(s, v) always, an algorithm can only fail by leaving an estimate too high, never too low — it can miss a shortcut but never invent one. That is why an independent check against brute force is a check that every d[v] came down far enough.

Vocabulary that the rest of the page uses without comment

An estimate d[v] is tight when d[v] = δ(s, v). An edge (u, v) is tense when d[v] > d[u] + w(u, v) — relaxing it would improve something — and a set of estimates is a fixed point of relaxation when no edge is tense; §08 and §10 use the fact that the estimates are all tight if and only if d[s] = 0 and no edge is tense (one direction is the triangle inequality applied to δ; the other is the telescoping argument above run along a shortest path). A vertex is settled or finalised when the algorithm promises never to lower it again — Dijkstra's S — and tentative otherwise. An algorithm that settles one vertex per step and never revisits it is label-setting — Dijkstra and its relatives A* and Dial's buckets, which settle in key order and need w ≥ 0 for the promise to hold (§05), and the DAG pass, which settles in topological order and needs no condition on the weights (§09); an algorithm that allows any estimate to fall again until no edge is tense is label-correcting — Bellman-Ford, its queue-driven variant SPFA, and Dijkstra with re-insertion of improved vertices (§05) — and its guarantee is a fixed point rather than a settled set, which is why it tolerates negative edges on cyclic graphs and pays for it in rounds. The shortest-paths tree is a rooted tree containing every reachable vertex in which the unique root-to-v path is a shortest path; when several shortest paths exist there are several such trees, the algorithms return one of them, and which one depends on the schedule and on tie-breaking — the figure's four schedules all produce the same π here only because this graph's shortest paths are unique.

03 Negative edges and negative cycles: what δ means then

A negative edge is an edge whose weight is below zero; a negative cycle is a cycle whose weights sum to less than zero; and the shortest-path weight δ(s, v) is well defined — ∞ if v is unreachable, otherwise a finite minimum attained by a simple path — exactly when no negative cycle is reachable from s on the way to v. Negative edges by themselves change nothing in the definition and only some things in the algorithms: Bellman-Ford (§07), the DAG pass (§09) and Johnson's reweighting (§14) handle them as written, and Dijkstra (§04) does not. A negative cycle changes the definition: walks around it get arbitrarily cheap, the minimum over walks does not exist, and the honest value of δ is −∞ for every vertex the cycle can reach. This section fixes what each case means, why restricting to simple paths does not rescue the negative-cycle case, why Dijkstra's hypothesis is the sign of the edges and not the absence of cycles, and why the obvious repair — shift every weight up until none is negative — is wrong, while a less obvious one is right.

the casesno negative cycle reachable from s: δ(s, v) = min over PATHS = min over WALKS, attained by a simple path with ≤ V − 1 edges — any walk contains a simple path of no greater weight: cut out each cycle, whose weight is ≥ 0 a negative cycle C reachable from s, and v reachable from C: inf over walks = −∞ (go round C once more: −|w(C)| cheaper each time) — define δ(s, v) = −∞; vertices NOT reachable from any such C keep a finite δ, which Bellman-Ford still computes correctly (§07) an undirected edge of negative weight = a directed 2-cycle u → v → u of weight 2·w(u, v) < 0: every undirected negative edge is a negative cycle the add-a-constant fallacy — three vertices s, a, tedges s→t (1), s→a (2), a→t (−2). δ(s, t) = 0 by s→a→t (the direct edge costs 1) add c = 2 to every edge: s→t (3), s→a (4), a→t (0). now s→a→t = 4 and s→t = 3: Dijkstra on the shifted graph returns s→t, original weight 1 ≠ 0 why: a path with k edges gains k·c, so the shift favours paths with FEWER edges — it changes which path is shortest whenever the true shortest path has more edges than a rival (the same happens for c = 3 or c = 10: the shifted answer is always s→t — measured by running the routine on the shifted instances) the reweighting that does work — potentials (Johnson, §14)choose any function h : V → ℝ and set w′(u, v) = w(u, v) + h(u) − h(v) for ANY s ⇝ v path p: w′(p) = w(p) + h(s) − h(v) — the correction depends on the endpoints only (the h terms telescope), so every s ⇝ v path shifts by the SAME amount hence p is shortest under w′ ⇔ p is shortest under w; and a cycle keeps its weight exactly (h(s) − h(s) = 0), so negative cycles are neither created nor destroyed if h satisfies h(v) ≤ h(u) + w(u, v) for every edge — for instance h = δ from a new source joined to every vertex by a 0-edge — then every w′ ≥ 0 and Dijkstra applies on the three-vertex graph: h = ⟨0, 0, −2⟩ gives w′ = s→t 3, s→a 2, a→t 0; Dijkstra returns d′ = ⟨0, 2, 2⟩ and d′(v) − h(s) + h(v) = ⟨0, 2, 0⟩ = δ

Why "shortest simple path" does not rescue the negative-cycle case

Faced with a negative cycle, the tempting redefinition is "the shortest path that visits no vertex twice". That is a well-posed problem — the minimum over finitely many simple paths exists — but it is not one any algorithm on this page solves, and there is strong evidence that no efficient algorithm solves it: the shortest simple path problem with arbitrary weights is NP-hard. The reduction is short. Given any directed graph, give every edge weight −1; a simple path from s to t of weight −(V − 1) uses V − 1 edges, hence visits every vertex — it is a Hamiltonian path — and conversely; so an algorithm for shortest simple paths would decide Hamiltonian path, which is NP-complete. Equivalently, shortest simple path with negated weights is longest simple path, and Dynamic Programming, §02 shows on four vertices exactly why the latter lacks optimal substructure: subpaths compete for vertices. The evidential status should be stated as it is: NP-hardness means a polynomial algorithm would give one for every problem in NP, which is widely believed impossible but not proved. What is proved is the equivalence, and it is enough to explain why the algorithms here compute δ over walks and report −∞ rather than searching for the cheapest cycle-free route. Every efficient shortest-path algorithm rests on optimal substructure, and optimal substructure for paths holds only when cutting a cycle out of a walk never makes it more expensive — which is precisely "no negative cycles".

Why Dijkstra's hypothesis is w ≥ 0, not "no negative cycle"

The two conditions are different in both directions of strength. "No negative cycle reachable" is what makes δ well defined and is all Bellman-Ford needs (§07). "Every edge non-negative" is stronger — it implies the first, since a cycle of non-negative edges is non-negative — and it is what Dijkstra needs, because Dijkstra's argument is not about the definition of δ but about its schedule: it finalises the closest tentative vertex on the grounds that no path leaving through a farther vertex can come back cheaper, and "cannot come back cheaper" is the statement that extending a path never lowers its weight, which is w ≥ 0 edge by edge. The graph of §05's figure has a single negative edge, no cycle at all (it is a DAG), a perfectly well-defined δ — and Dijkstra gets it wrong, because the negative edge lets a longer-looking route end up shorter after a vertex has already been finalised. So the hypotheses line up as: DAG (any weights, §09) and no-negative-cycle (any weights, Bellman-Ford) concern the definition; w ≥ 0 concerns Dijkstra's greedy step, and the Greedy Algorithms page's §20 names it as the greedy-choice lemma's hypothesis. A special case is worth knowing because it is a common exercise and a common misconception: if the only negative edges leave s, and no cycle through s is negative (so that δ is finite), Dijkstra is still correct — every simple path from s uses at most one such edge, as its first, and thereafter only grows, so the finalisation argument of §05 survives — but a negative edge anywhere else can break it, and there is no cheap patch for "just one negative edge" in general (§05 says what the patches cost).

Where negative weights come from, and what to do about each

Negative weights are not exotic. Log-probabilities: multiplying probabilities along a path becomes adding −log p ≥ 0, so the most probable path is a shortest path with non-negative weights and Dijkstra is fine; the Viterbi decoding of the DP page is this on a DAG. Gains and losses: an edge that pays out (a currency conversion at a favourable rate, a job that earns rather than costs) is negative, and a negative cycle is an arbitrage — a sequence of conversions that ends with more than it started with; Bellman-Ford's negative-cycle test (§07) is the arbitrage detector, run on weights −log(rate). Constraints: a system of inequalities xⱼ − xᵢ ≤ bₖ is a shortest-path problem whose edge weights are the bₖ, of either sign, and whose infeasibility is a negative cycle (§10). Reweighting: when a negative-weight instance has no negative cycle and must be solved many times or for all pairs, one Bellman-Ford computes potentials and thereafter every query is a Dijkstra (§14). The decision procedure of §28 begins with the sign of the weights for this reason, and the pitfalls of §29 include the constant-shift fallacy above because it is attempted every year: it is not that the shift makes the weights positive — it does — but that it adds a per-edge toll that penalises long paths, and nothing about shortest paths is invariant under a per-edge toll. Potentials add a per-endpoint toll instead, which every s ⇝ v path pays equally, and that is the entire difference between the fallacy and the theorem.

The summary the later sections assume. Weights all non-negative: every algorithm on the page applies; Dijkstra is the default. Some negative edges, no negative cycle reachable: δ is well defined, Bellman-Ford or Johnson, or one pass if the graph is a DAG; Dijkstra is wrong and no constant shift repairs it. A negative cycle reachable: δ = −∞ on everything the cycle reaches, Bellman-Ford reports the cycle (§07), and "shortest simple path" is a different problem with no known efficient algorithm. Undirected graphs with a negative edge are in the last case automatically.

04 Dijkstra's algorithm, stepped

Dijkstra's algorithm computes single-source shortest paths in a graph whose edge weights are all non-negative by maintaining a set S of finalised vertices and, repeatedly, moving into S the vertex outside it with the smallest estimate and relaxing that vertex's outgoing edges. The estimate of a vertex at the moment it enters S is its true distance — that is the invariant, and §05 proves it — so each vertex is finalised once, each edge is examined once — when its tail is finalised — and the work is V extract-mins plus E relaxations, each relaxation possibly lowering a key in whatever priority queue holds the tentative vertices. It is breadth-first search with the FIFO queue replaced by a min-priority queue keyed on d, and with "assign the distance on discovery" replaced by "relax, and allow the distance to be lowered again until finalisation".

What the counter reports

Run under a counter, the routine performs 6 extractions — one per vertex, V — and examines 10 edges, the sum of the out-degrees, which equals E here because every vertex is reachable and every edge is examined exactly once, from its tail's extraction. Reading the algorithm as BFS with a different frontier

Three differences from BFS, and only three. The queue is ordered by tentative distance rather than by arrival, so the vertex that leaves it next is the closest one known rather than the oldest; the discovery step is a relaxation, which may fire more than once per vertex (vertex 3 above fired three times) rather than an assignment that fires once; and a vertex is finished when it is extracted, not when it is discovered. With all weights equal, tentative distances are the BFS layer number times the weight, no relaxation ever lowers an estimate after discovery, and the three differences collapse: Dijkstra on unit weights is BFS, at the cost of a log V per queue operation it does not need — which is why Graph Representations & Traversal, §28 says to check for equal weights before reaching for a heap, and why §11 below recovers BFS's linear time for weights in {0, 1} and for small integers. Prim's algorithm (§19) is the same loop once more, keyed by the weight of the single edge into the tree instead of the total path length, and §20 shows on one graph that the two keys grow different trees.

05 Why Dijkstra is right, and exactly where it needs w ≥ 0

Dijkstra's algorithm is correct because the vertex it extracts always already has its true distance: at the moment u leaves the queue, d[u] = δ(s, u). The proof is by contradiction on the first extraction for which that fails, and it uses non-negative weights in exactly one inequality — the claim that a vertex on the way to u along a true shortest path cannot be farther from s than u is. Everything else in the proof is the relaxation properties of §02. This section gives the proof with that step marked, then breaks it: a three-vertex graph with one negative edge on which Dijkstra finalises a vertex too early, the four-vertex extension on which the error propagates whichever implementation variant is used, and a slider that finds the exact weight at which the answer first goes wrong.

The counterexample, worked

Three vertices s, a, b and edges s→a (2), s→b (1), a→b (−3). The true distances: δ(s, a) = 2 and δ(s, b) = min(1, 2 − 3) = −1, by the path s→a→b. Dijkstra: extract s and relax, giving d[a] = 2, d[b] = 1; extract b (key 1, the smaller) and finalise it — this is the wrong step, since d[b] = 1 ≠ δ(s, b) = −1; it is the first failure, y = a is the first vertex of the true shortest path outside S, and step (2) fails because δ(s, a) = 2 > δ(s, b) = −1: the shortest path to b leaves S through a vertex farther than b. Then extract a (key 2) and meet the edge a→b, which now points into S. Two implementations diverge here, and both are wrong. The variant this page's routine uses — skip edges into S, which is what a heap-based implementation must do since b is no longer in the queue — returns d[b] = 1. The relax-anyway variant, which relaxes every out-edge regardless of whether its head is finalised, updates d[b] to −1, which is the right number by accident: b has already been extracted, so nothing downstream of b is ever recomputed. Add a fourth vertex c with b→c (1) to see the accident fail: δ(s, c) = 0, and both variants report d[c] = 2, because b→c was relaxed while d[b] was still 1 and is never relaxed again. Measured on the four-vertex graph with the negative edge at −3: the skipping variant is wrong on b and c, the relax-anyway variant is wrong on c; neither is fixable without re-examining a finalised vertex.

The figure's slider moves the weight of a→b from +2 down to −5. For weights 2, 1, 0, −1 Dijkstra agrees with brute force at every vertex; the first weight at which it disagrees is −2, and at −1 it still agrees only because 2 + (−1) = 1 ties the direct edge rather than beating it — the same "ties are harmless, strict improvements after finalisation are not" boundary as in the proof, where step (2) needs ≤ and a weight of exactly zero on the y ⇝ u stretch preserves it. So the hypothesis of the theorem can be weakened only to "no path can get strictly shorter by continuing past a finalised vertex", which for general graphs is the same as w ≥ 0.

Zero-weight edges, and edges into S

Zero weights are harmless. The proof needs the y ⇝ u stretch to weigh at least zero, and it does; the only visible effect is ties — several tentative vertices at the same key — and the theorem holds for every tie-break, since the argument never says which of two equal-key vertices is extracted. A zero-weight cycle is likewise fine: δ remains finite, and the algorithm never traverses the cycle because every vertex on it is extracted once. What is not harmless is a negative edge into S, in any implementation that never re-extracts. The finalised vertex is wrong forever in the skipping variant, wrong for its successors in the relax-anyway variant, and the damage is invisible to the algorithm: nothing in Dijkstra's state records that a finalised vertex was improved, so no error is raised. A defensive implementation can detect the situation cheaply — if a relaxation would lower the key of a vertex in S, a negative edge has been found — and either abort with a diagnosis or fall back to Bellman-Ford; that check costs one comparison per edge and is worth having in a library routine that cannot trust its input.

What can be salvaged with a few negative edges

Dijkstra cannot be patched for negative edges in general, but three special cases are genuinely solvable with it, and all three have the same shape: partition every shortest path into non-negative stretches and use Dijkstra on the stretches. Negative edges only out of s, and no negative cycle: unchanged Dijkstra is correct, because a simple path from s uses one such edge, its first, and the y ⇝ u stretch in step (2) never contains it (§03). One negative edge (p, q), no negative cycle: a shortest path uses it at most once, so δ(s, t) = min( δ₀(s, t), δ₀(s, p) + w(p, q) + δ₀(q, t) ) where δ₀ is computed in the graph without that edge — two Dijkstra runs, from s and from q; on the figure's graph with w(a→b) = −3: δ₀ from s without that edge is ⟨0, 2, 1, 2⟩, δ₀ from b is ⟨∞, ∞, 0, 1⟩, and min(δ₀(s, ·), δ₀(s, a) − 3 + δ₀(b, ·)) = min(⟨0, 2, 1, 2⟩, ⟨∞, ∞, −1, 0⟩) = ⟨0, 2, −1, 0⟩, matching brute force; the figure's readout re-derives this patch at every slider weight and flags its agreement. k negative edges, no negative cycle: alternate k + 1 times between a Dijkstra pass over the non-negative edges (started from the current estimates, all tentative vertices in the queue — the multi-source form, whose correctness argument is the theorem above with "d[s] = 0" replaced by "the initial estimates are upper bounds") and a single relaxation of each negative edge; after phase i every vertex whose shortest path uses at most i negative edges is correct, by the path-relaxation property, so k + 1 phases cost O(k · (V + E) log V) — cheaper than Bellman-Ford's O(VE) when k is small, and requiring that the negative edges be known. The general alternative — allow a finalised vertex to be re-inserted when it improves, turning Dijkstra into a label-correcting algorithm — is correct when no negative cycle exists but loses the bound: on adversarial instances the number of re-extractions is known to grow exponentially in V, so it is not a safe default. When the negative edges are many or unknown, the answer is Bellman-Ford (§07), a DAG pass if the graph is acyclic (§09), or Johnson's potentials if many queries follow (§14).

06 Dijkstra's cost: array, binary heap, Fibonacci heap, lazy deletion — measured

Dijkstra's running time is V extract-mins plus at most E decrease-keys plus Θ(V + E) bookkeeping, and every published bound for it is that formula with one priority queue's costs substituted in: Θ(V²) for an unsorted array, O((V + E) log V) for a binary heap with decrease-key, O(E log E) plus Θ(V) initialisation — equal to O((V + E) log E), and the same thing as the index-map bound since log E ≤ 2 log V — for a binary heap with lazy deletion, and O(E + V log V) amortised for a Fibonacci heap. There is no single "Dijkstra bound"; there is a bound per queue, and the right queue depends on the density E/V. This section derives each, says which wins where and why, and then measures the three that are implemented on this page across V at two densities — which turns up a fact the bounds hide: the number of decrease-keys that actually happen is far smaller than E.

Why the array is right for dense graphs

The array implementation keeps d[] as the queue: extract-min is a linear scan for the smallest tentative entry, V steps, done V times — Θ(V²) — and a decrease-key is a single assignment into d[v], so relaxing all E edges costs Θ(E) and disappears into the V². A heap makes extraction cheap, log V, but makes every decrease-key cost log V too, and when there are Θ(V²) edges that is Θ(V² log V) of decrease-key work — more than the array's whole run. The array is the correct structure whenever E is within a log V factor of V²; it is also the simplest to write, has no pointers, and scans a contiguous block of memory, and is often assumed to be faster in practice on dense graphs; the measurement below shows that assumption depends on how many relaxations actually succeed. The d-ary heap of Heaps & Priority Queues, §17 interpolates: with d = max(2, ⌈E/V⌉) its bound is O(E · log V / log(E/V)), which is the binary heap's O(E log V) for sparse graphs and falls to O(E) — the array's order on a dense graph — once E = V^{1+ε} for a constant ε.

The binary heap with decrease-key, and the one with lazy deletion

A heap that supports decrease-key must be able to find a vertex's entry — an index map pos[v] updated on every swap, which Heaps & Priority Queues, §16 builds — and every successful relaxation becomes pos lookup, key overwrite, sift-up. The queue holds at most V entries, so every operation is O(log V), and the total is O((V + E) log V): V extractions and up to E decrease-keys. The lazy variant drops the index map entirely, which is the form most library-based implementations take because the library's heap has no decrease-key. Instead of lowering an entry's key it pushes a new pair (d[v], v) and leaves the old pair where it is; when a pair is popped, the algorithm checks whether it is stale — whether its key is larger than the current d[v], or v has already been finalised — and if so discards it and pops again. The check is what makes the duplicates harmless: a stale pair can never be the one that finalises v, because the fresher pair with the smaller key was pushed later and will be popped first (same key or smaller), and after v is finalised every remaining pair for it is discarded on sight. The cost is that the heap can hold up to V + D pairs — one per successful relaxation — so each operation is O(log(V + E)) = O(log V), and the pops number V + D rather than V: the bound is O((V + E) log E), the same order as with decrease-key, with a larger heap and no index map. On the six-vertex instance of §04 the lazy routine pushed 9 pairs after the initial one, popped 10, discarded 4 as stale, and held at most 5 pairs at once; the index-map heap did 6 extractions and 9 decrease-keys on a heap that never exceeded 6 entries.

The Fibonacci heap: the bound that is best and the structure that rarely wins

A Fibonacci heap makes decrease-key O(1) amortised by cutting the decreased node out of its tree and adding it to the root list rather than sifting it up, and pays for that during extract-min, which consolidates the root list in O(log V) amortised; Heaps & Priority Queues, §21 gives the potential-function argument, and Algorithm Analysis, §18 the meaning of "amortised": the bound is on the total over the whole run, and an individual extract-min may take Θ(V). Substituted into the formula it gives O(E + V log V), which is asymptotically the best known for Dijkstra with arbitrary real non-negative weights, and which is a genuine improvement over the binary heap's O(E log V) only when E is well above V. In practice it rarely wins the race it wins on paper, for reasons that page's §23 spells out and that the measurement below makes concrete: its constants are large (four pointers, a mark and a degree per node, and a consolidation step on every extraction), its nodes are scattered in memory where a binary heap is one array, and — decisively — the operation it makes cheap is the one that seldom happens. The bound charges E decrease-keys; on the dense random graphs below the measured number is a few percent of E (708 of 16,384 at V = 256), and even on the sparse ones it is well under half (301 of 768).

That is also why the "crossover density" the readout reports comes in three versions, all measured at V = 128 by sweeping E/V² from 0.02 to 1. On the bound's own accounting — V² + E against (V + E)·⌈log₂ V⌉ + E, every relaxation charged a decrease-key — the array wins from the first sampled density above the algebraic threshold, 0.15 (E = 2,458), upward — the threshold itself is E > V²/log₂ V − V ≈ 2,213, density ≈ 0.135, and 0.12 is the last sampled point below it. Charging the heap's measured operations at their worst case ⌈log₂ 128⌉ = 7 levels each, the array never catches up: at full density (E = 16,256) the heap's 494 operations cost at most 3,458 levels plus 8,128 relaxations, against the array's 16,384 scans plus the same relaxations. And counting the sift steps the heap actually took, the heap did 9,760 elementary steps to the array's 24,512 at full density — the array is at a 2.5× disadvantage on the very graphs the worst case says it should win. Only 366 of the 16,256 edges produced a decrease-key. None of this contradicts the bounds, which are worst-case statements over all inputs; it says that the input family on which the array's advantage materialises is one where relaxations succeed constantly, and random weights are not it. Adversarial weightings exist (make every later-discovered route cheaper), and dense graphs with structured weights — a complete graph with Euclidean distances, say — sit between the two. The recommendation stands as the bounds give it, with this caveat attached: a binary heap for anything sparse or of unknown density; the array for dense graphs when it is measured to win on the actual inputs, not assumed to.
