Sorting & Searching

Sorting is rearranging a sequence so that its keys are in order; searching is locating a key in a sequence. They are one subject because order is what makes searching cheap: an unsorted array can only be scanned, a sorted one can be halved. This page treats sorting as a subject — every sort's invariant, exact cost, stability, adaptivity, memory and practical behaviour, measured on the real routine rather than asserted — and searching as a practice: the loop that is actually correct, the two bugs everyone writes, the boundary variants that answer the questions people really ask, and the structures that take over when an array no longer fits the problem. The Θ(n log n) comparison bound is proved and then escaped; quicksort's partition schemes are traced index by index; every displayed number is a measurement that has been recomputed a second way.

01 What sorting is

To sort a sequence a₀, a₁, …, aₙ₋₁ is to find a permutation π of the indices such that the keys are monotone along it: key(aπ(0)) ≤ key(aπ(1)) ≤ … ≤ key(aπ(n−1)). Two words in that sentence carry the whole subject. Permutation: the output contains exactly the input's elements, each once — a sort that drops, invents or duplicates an element is not a slow sort, it is not a sort. Monotone under ≤: the ordering has to be a total preorder — reflexive, transitive, and total (any two keys are comparable) — but it need not be antisymmetric, which is exactly why two different records can have equal keys, why "stable" is a meaningful word, and why the order of equal keys in the output is a property the sort either guarantees or does not.

the specificationinput: a[0 .. n), a key function, and a total preorder ≤ on keys output: a permutation of the same elements with key(a[i]) ≤ key(a[i+1]) for all 0 ≤ i < n − 1 the comparison modelthe algorithm learns about keys ONLY by asking "is key(x) ≤ key(y)?" it may move, copy and index elements freely, but it never inspects a key's bits cost = number of such questions (plus moves, counted separately on this page) the vocabulary, onceSTABLE equal keys keep their input order: i < j and key(aᵢ) = key(aⱼ) ⇒ aᵢ precedes aⱼ in the output IN-PLACE O(1) extra words beyond the input — by convention an O(log n) recursion stack is still "in place" ADAPTIVE cost falls with a measure of existing order (inversions, runs, …), not only with n ONLINE can absorb elements one at a time without restarting INTERNAL the whole input fits in random-access memory; EXTERNAL it does not, and access is by block

Why the comparison model is the right first model

An algorithm that only compares keys works for every key type that has an order — integers, strings, dates, records under a user-supplied comparator — and its cost can be counted exactly, as a number of questions asked. That generality is what lets one theorem (§10) bound every such algorithm at once: with only yes/no answers to work with, distinguishing among n! possible input orders needs log₂(n!) questions. The model's limits are equally sharp. An algorithm that reads a key's bits — uses it as an array index, splits it into digits — is not a comparison sort, is not bound by the theorem, and can run in linear time under hypotheses the theorem never mentions (§22–§24). The first question to ask of any sort is therefore which model it lives in; everything about its cost follows from the answer.

What the vocabulary buys

  • Stability is what makes "sort by department, then within department by name" expressible as two successive sorts (§25). It is also the property that lets a radix sort work at all (§23). Of the sorts on this page, insertion, bubble, odd-even transposition, mergesort, counting and radix are stable as written; selection, cycle sort, shellsort, quicksort and heapsort are not, and §05 shows the exact three-element input on which selection sort breaks it.
  • In-place is a memory property, not a speed property. Mergesort's Θ(n) buffer is the price of a sequential access pattern that is, in cache terms, an asset (§12, §21). Quicksort is fast because its inner loop is a tight sequential scan against one register-resident value — not because it uses no buffer.
  • Adaptive is a statement about a specific measure of disorder. Insertion sort is adaptive in the number of inversions (§04); natural mergesort in the number of runs (§12); a sort that is adaptive in one measure can be oblivious in another, so the claim always needs its measure attached.
  • Online matters when the input is a stream. Insertion sort is the only elementary sort that is naturally online (a heap-based priority queue is the other online route, at O(log n) per arrival) — the sorted prefix is always a finished answer for what has arrived so far — which is one reason it is the finishing step inside most hybrids (§19, §26).

02 Why sorting matters: what order makes cheap

Sorting is rarely the goal. It is the preprocessing step that converts a quadratic problem into a linear or logarithmic one, and the pattern is always the same: pay Θ(n log n) once, then exploit the fact that related keys are now adjacent, or that any key can be located by halving. Most of the classical "sort, then …" algorithms are two lines long once the sort is done, and the sort is where all the cost sits.

Order as a data structure

A sorted array is a data structure in its own right — the simplest and densest ordered dictionary there is. It supports membership, predecessor, successor, rank and range queries in O(log n) each (§28–§29), it uses no memory beyond the elements, and its access pattern is as cache-friendly as a search can be. What it does not support is cheap update: inserting into a sorted array shifts Θ(n) elements (Arrays & Strings, §05). That one weakness is the reason balanced search trees, skip lists and B-trees exist: they are sorted arrays that gave up density to buy logarithmic insertion (§30). The decision between "sort once and search" and "maintain an ordered structure" is the decision between a read-mostly and a write-heavy workload, and it recurs in every index a database builds.

What sorting costs, honestly

The Θ(n log n) comparison count is only the first term. A sort also moves elements, and when the elements are large records the moves dominate — which is why records are sorted through an index or a key array rather than bodily (§25). It touches memory in a pattern that is sequential for mergesort and the partition scans of quicksort, and scattered for heapsort, and on a modern machine that difference is worth more than the constant in front of the comparison count (§21). And it has a worst case that may or may not match its average: mergesort and heapsort are Θ(n log n) on every input, quicksort is Θ(n²) on inputs that a naive implementation meets every day (§18). "Which sort is fastest" is therefore never a question with a single answer; it is the question this page's comparison table (§21) is built to make precise.

The one-line version. Sorting is the general-purpose way to make "related things adjacent" and "any thing findable by halving" true at once, for n log n, and nearly every fast algorithm on a sequence begins by buying those two properties.

32 Pitfalls

Every one of these is a claim that is true of one variant, one model or one input class and gets repeated about the whole family. The section number is where the correct statement lives.

The claimWhat is actually trueWhere
"Quicksort is quadratic on equal keys"Lomuto's partition is; Hoare's is n log n on all-equal input; three-way partitioning is linear. It is a property of the partition scheme, not of quicksort. Measured factor between the schemes on 1 024 equal keys: 256×.§17
"Insertion sort is O(n + inversions)"In moves, always; in comparisons, for the linear-scan version. Binary insertion cuts the comparisons to O(n log n) and leaves the moves — and the running time — at Θ(n + I).§04
"Mergesort makes n·log₂n comparisons"Its worst case is n·ceil(log₂n) − 2^ceil(log₂n) + 1 for the top-down split; the average is about n·log₂n − 1.25n; the best is about half; and bottom-up at a non-power of two can exceed the top-down worst case.§12
"Counting sort is linear"Θ(n + k) — linear iff the key range k is O(n). Radix sort is Θ(D(n + k)) and needs a stable digit sort and a key width of O(log n) to be linear. Bucket sort is expected-linear only under a distribution hypothesis and is quadratic without it.§22–§24
"Sorting is Ω(n log n)"Comparison sorting is, in the worst case and on average. The bound says nothing about integer keys, and the linear-time sorts do not contradict it — they leave the model.§10
"Binary search is O(log n)"On a sorted array with O(1) random access. On a linked list it is Θ(n); on an array sorted by a different key it is wrong without an error.§28
"Selection sort is stable" / "shellsort is stable" / "quicksort can be made stable easily"Selection sort's swap breaks stability on three elements; shellsort's long-gap passes break it; quicksort's partition breaks it and the fix costs a buffer. Insertion, bubble, mergesort, counting and radix are stable; heapsort is not.§05, §07, §13
"Quicksort is fast because it is in place"It is fast because its inner loop is a sequential scan against a register-resident pivot, with one branch that can be made branchless. Being in place is a memory property with no bearing on speed; mergesort's buffer gives it the best access pattern of the three.§13, §19, §21
"Mergesort's extra memory makes it slow"Its access pattern is purely sequential, which is why it is the external sort and the cache-friendly sort. Its cost relative to quicksort is the copy, not the buffer.§11, §31
"Radix sort is always faster than comparison sorting for integers"Only when the key width in digits is smaller than log n comparison levels, and only if its scattered writes do not cost more than they save. 64-bit keys at n = 1000 are level; 32-bit keys at a million are a clear win.§23
"Binary search is always faster than linear search"Below a small, platform-dependent n, a linear scan wins on wall-clock time — predictable branches, prefetching, vectorisation — despite more comparisons. Library searches and merges switch to scanning at that size.§27
"Recursing on the smaller part first makes quicksort safe"It bounds the stack to floor(log₂n) + 1. The running time on sorted input with a bad pivot is still n(n − 1)/2; only the pivot rule or a depth limit fixes that.§18
"Median-of-three fixes the worst case"It fixes sorted and reversed input and improves the average by about 14%. It has its own killer — the organ-pipe input costs it Θ(n²), measured at depth 255 for n = 1024. Only a random pivot or a depth limit removes the ordering worst case — and neither helps Lomuto on equal keys; that needs §17's partition.§16
"The cutoff is 16" (or any number)The cutoff is a measured constant of the implementation. Here the Hoare hybrid's optimum is 8–16 and the Lomuto hybrid gains nothing; libraries choose theirs by benchmark, and quoting one as a fact about the algorithm is a category error.§19, §26
"Sort, then binary search, is always better than a hash table"For equality lookups a hash table is expected O(1). The sorted array wins on predecessor, range, rank and ordered iteration — the queries hashing cannot do — and on memory.§30
"The pivot goes at index j" (Hoare)Hoare's partition returns a split point, not the pivot's index; the pivot may be on either side. Recursing on [lo, j) and [j + 1, hi) loses an element; the correct calls are [lo, j + 1) and [j + 1, hi).§15
"Interpolation search is O(log log n)"On uniformly distributed keys. On exponentially spaced keys it is linear — measured at 13 596 probes for n = 65 536 against binary search's 13.8.§29
"lower_bound stops when it finds x"It cannot: finding a copy proves nothing about the first. Every boundary search runs to lo = hi, always floor(log₂n) + 1 probes or fewer, no early exit.§29

Where it goes sideways, out of this domain. Sorting is the preprocessing step of nearest-neighbour search, of the sweep-line algorithms in computational geometry, and of every vector database's candidate ranking; the Ω(n log n) argument is the first lower bound most readers meet and the template for every information-theoretic bound after it. Radix sort's digit passes are the same idea as the bucketed histograms and argsorts of array computing, the sort-then-scan idioms of §02 are the daily work of SQL's ORDER BY, GROUP BY and merge joins, and the external merge of §31 is the shape of every shuffle stage in a distributed data engine.
