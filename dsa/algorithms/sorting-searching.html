Sorting & Searching

Sorting is rearranging a sequence so that its keys are in order; searching is locating a key in a sequence. They are one subject because order is what makes searching cheap: an unsorted array can only be scanned, a sorted one can be halved. This page treats sorting as a subject — every sort's invariant, exact cost, stability, adaptivity, memory and practical behaviour, measured on the real routine rather than asserted — and searching as a practice: the loop that is actually correct, the two bugs everyone writes, the boundary variants that answer the questions people really ask, and the structures that take over when an array no longer fits the problem. The Θ(n log n) comparison bound is proved and then escaped; quicksort's partition schemes are traced index by index; every displayed number is a measurement that has been recomputed a second way.

01 What sorting is

To sort a sequence a₀, a₁, …, aₙ₋₁ is to find a permutation π of the indices such that the keys are monotone along it: key(aπ(0)) ≤ key(aπ(1)) ≤ … ≤ key(aπ(n−1)). Two words in that sentence carry the whole subject. Permutation: the output contains exactly the input's elements, each once — a sort that drops, invents or duplicates an element is not a slow sort, it is not a sort. Monotone under ≤: the ordering has to be a total preorder — reflexive, transitive, and total (any two keys are comparable) — but it need not be antisymmetric, which is exactly why two different records can have equal keys, why "stable" is a meaningful word, and why the order of equal keys in the output is a property the sort either guarantees or does not.

Why the comparison model is the right first model

An algorithm that only compares keys works for every key type that has an order — integers, strings, dates, records under a user-supplied comparator — and its cost can be counted exactly, as a number of questions asked. That generality is what lets one theorem (§08) bound every such algorithm at once: with only yes/no answers to work with, distinguishing among n! possible input orders needs log₂(n!) questions. The model's limits are equally sharp. An algorithm that reads a key's bits — uses it as an array index, splits it into digits — is not a comparison sort, is not bound by the theorem, and can run in linear time under hypotheses the theorem never mentions (§20–§22). The first question to ask of any sort is therefore which model it lives in; everything about its cost follows from the answer.

What the vocabulary buys

  • Stability is what makes "sort by department, then within department by name" expressible as two successive sorts (§23). It is also the property that lets a radix sort work at all (§21). Of the sorts on this page, insertion, bubble, mergesort, counting and radix are stable as written; selection, shellsort, quicksort and heapsort are not, and §05 shows the exact three-element input on which selection sort breaks it.
  • In-place is a memory property, not a speed property. Mergesort's Θ(n) buffer is the price of a sequential access pattern that is, in cache terms, an asset (§10, §19). Quicksort is fast because its inner loop is a tight sequential scan against one register-resident value — not because it uses no buffer.
  • Adaptive is a statement about a specific measure of disorder. Insertion sort is adaptive in the number of inversions (§04); natural mergesort in the number of runs (§10); a sort that is adaptive in one measure can be oblivious in another, so the claim always needs its measure attached.
  • Online matters when the input is a stream. Insertion sort is the only elementary sort that is naturally online (a heap-based priority queue is the other online route, at O(log n) per arrival) — the sorted prefix is always a finished answer for what has arrived so far — which is one reason it is the finishing step inside most hybrids (§17, §24).

02 Why sorting matters: what order makes cheap

Sorting is rarely the goal. It is the preprocessing step that converts a quadratic problem into a linear or logarithmic one, and the pattern is always the same: pay Θ(n log n) once, then exploit the fact that related keys are now adjacent, or that any key can be located by halving. Most of the classical "sort, then …" algorithms are two lines long once the sort is done, and the sort is where all the cost sits.

Order as a data structure

A sorted array is a data structure in its own right — the simplest and densest ordered dictionary there is. It supports membership, predecessor, successor, rank and range queries in O(log n) each (§26–§27), it uses no memory beyond the elements, and its access pattern is as cache-friendly as a search can be. What it does not support is cheap update: inserting into a sorted array shifts Θ(n) elements (Arrays & Strings, §05). That one weakness is the reason balanced search trees, skip lists and B-trees exist: they are sorted arrays that gave up density to buy logarithmic insertion (§28). The decision between "sort once and search" and "maintain an ordered structure" is the decision between a read-mostly and a write-heavy workload, and it recurs in every index a database builds.

What sorting costs, honestly

The Θ(n log n) comparison count is only the first term. A sort also moves elements, and when the elements are large records the moves dominate — which is why records are sorted through an index or a key array rather than bodily (§23). It touches memory in a pattern that is sequential for mergesort and the partition scans of quicksort, and scattered for heapsort, and on a modern machine that difference is worth more than the constant in front of the comparison count (§19). And it has a worst case that may or may not match its average: mergesort and heapsort are Θ(n log n) on every input, quicksort is Θ(n²) on inputs that a naive implementation meets every day (§16). "Which sort is fastest" is therefore never a question with a single answer; it is the question this page's comparison table (§19) is built to make precise.

The one-line version. Sorting is the general-purpose way to make "related things adjacent" and "any thing findable by halving" true at once, for n log n, and nearly every fast algorithm on a sequence begins by buying those two properties.

03 The loop-invariant discipline, on insertion sort

Insertion sort is how a hand sorts cards: keep the left part of the array sorted, take the next unsorted element, and slide it leftward past every larger element until it sits in place. It is the first sort to learn not because it is fast but because its correctness proof is the template for every other loop on this page — a property that holds before the loop, is preserved by each pass, and at exit says exactly what you wanted.

Two things in that trace are worth naming. First, every shift removes exactly one inversion — v passes one larger element — so the number of shifts equals the number of inversions, no matter what order the input is in. Second, an insertion ends in one of two ways: a failing comparison (an element that is not greater than v stops it) or the front of the array (j = 0, no comparison made). Why the invariant is the proof, and why it is also the design

Notice what the invariant does not say. It does not say a[0..i) contains the i smallest elements of the array — it does not, and the trace shows it (after i = 3 the prefix is [2, 4, 5, 6] while 1 is still to come). That weaker statement is exactly what selection sort's invariant does say (§05), and the difference is the difference between the two algorithms: selection sort's prefix is final, insertion sort's is merely ordered. Reading the invariant tells you what the loop has committed to, and therefore what it can and cannot exploit. Insertion sort has committed to nothing about the unsorted suffix, which is why it can be online — new elements simply extend the suffix — and why its cost depends on how far each element has to travel rather than on n alone.

The habit. Before analysing any sort on this page, write its invariant in one sentence. Every cost bound below is derived by asking "how much work does one pass do to restore the invariant?", and every subtle bug — the ≤ that breaks stability, the partition that loses an element, the merge that reads past a run — is a pass that fails to restore it.

04 Insertion sort's cost: inversions, adaptivity, and the binary-insertion trap

§03 showed that every shift removes exactly one inversion. That single fact gives insertion sort's cost exactly, on every input, in terms of one number: I, the count of pairs that are out of order. Comparisons lie between I and I + n − 1; moves are 2(n − 1) + I; and since I ranges from 0 (sorted) to n(n − 1)/2 (reversed), the best, worst and average cases are all read off the distribution of I.

The average-case derivation is worth reading because it is the pattern for every average case on this page: fix the probability model (each of the n! permutations equally likely), decompose the cost into a sum over one element at a time, and use linearity of expectation so that each term can be computed in isolation. It saves comparisons, not time: the running time is still Θ(n + I) in moves, and Θ(n²) on a random input.

What "adaptive" means here, precisely

Insertion sort is adaptive in the inversion measure (inversions, runs and the longest sorted subsequence are the standard presortedness measures, and "adaptive" is always relative to one of them): its cost is Θ(n + I), so an input with O(n) inversions — a few misplaced elements, a sorted array with a block appended, the output of a quicksort that stopped at small subarrays (§17) — is sorted in linear time. It is not adaptive in every measure of order. An array consisting of the sorted second half followed by the sorted first half has only two runs (natural mergesort sorts it in one merge, §10) but n²/4 inversions, and insertion sort is quadratic on it. The measure matters; "insertion sort is fast on nearly sorted input" is true only when "nearly sorted" means "few inversions".

Why it survives inside every fast sort. On tiny arrays the constant matters more than the exponent, and insertion sort's constant is the smallest of any sort: no recursion, no buffer, one tight loop over contiguous memory that the branch predictor learns quickly. That is why quicksort (§17), mergesort hybrids and every library sort (§24) hand subarrays below some cutoff to insertion sort, and why the cutoff is measured rather than derived — it is the point where c₁·n² crosses c₂·n log n for two constants nobody can compute from first principles. The measured sweep in §17 finds it between 8 and 16 elements for the Hoare-partition quicksort on this page — and finds that the Lomuto version gains nothing from it, which is its own lesson about constants.

05 Selection sort, and why it is not stable

Selection sort turns the invariant around: instead of keeping a prefix ordered, keep a prefix final. At the top of iteration i, a[0..i) holds the i smallest elements, in order, in their final positions. Each pass scans the entire unsorted suffix for its minimum and swaps it into position i. The scan cannot be shortened by any property of the input — to know the minimum you must look at every candidate — so the comparison count is the same on every input, and it is quadratic.

The instability, on three elements

Stability fails the moment a swap carries an element past an equal one. Take two records with key 2, tagged 2a and 2b by input order, and a 1 after them: [2a, 2b, 1]. Pass 0 finds the minimum, 1, at index 2 and swaps it with index 0 — and the element that was at index 0, 2a, lands at index 2, behind 2b. Pass 1 compares 2b with 2a, finds neither smaller, swaps nothing. Output: [1, 2b, 2a]. The two equal keys have exchanged their relative order, on a three-element input, with one swap. The figure in §03 tests this live on 300 random arrays of tagged records: selection sort violates stability on 300 of 300 runs at n = 40 with five distinct keys; insertion, binary insertion and bubble sort on none; shellsort on all 300, for the reason §07 gives.

the tracestart [2a, 2b, 1] pass 0 min of a[0..3) is 1 at index 2; swap a[0] ↔ a[2] → [1, 2b, 2a] 2a jumped over 2b pass 1 min of a[1..3) is 2b at index 1 (2a is not < 2b); no swap → [1, 2b, 2a] output [1, 2b, 2a] — sorted, NOT stable a stable variant exists, at a priceinstead of swapping, ROTATE a[i..m] right by one (shift the block, drop the minimum at i): stable, but Θ(n²) moves — the one property selection sort had over insertion sort, its O(n) moves, is exactly what stability costs

When the minimal move count matters

Selection sort's only genuine advantage is that it writes to the array at most 3(n − 1) times. Where a write is expensive — flash memory with limited erase cycles, records so large that a move dominates a comparison by orders of magnitude, a sort performed by physically moving objects — that can be decisive, and selection sort or its cycle-sort relative (which achieves the theoretical minimum number of writes) is the right tool. Everywhere else it is dominated: insertion sort does no more comparisons on any input, far fewer on most, is stable, is online, and is adaptive. The sort's real legacy is its idea: "repeatedly extract the minimum of what remains" is heapsort with a linear-time extract. Replace the Θ(n) scan with a heap's O(log n) extract-min and the same invariant gives O(n log n) — which is precisely how Heaps & Priority Queues, §12, introduces heapsort.

06 Bubble sort, the early-exit flag, and why it is dominated

Bubble sort sweeps left to right, swapping any adjacent pair that is out of order; after pass k the k largest elements have "bubbled" to their final places at the right end. Its invariant is selection sort's, mirrored: after k passes, a[n−k..n) holds the k largest keys in final position. It is the sort everyone learns first and the one nobody should use, and the reason is not the exponent — insertion sort has the same one — but a constant that is worse in every column.

The asymmetry in the last block is the whole indictment. A large element out of place is fixed in one pass, because the sweep carries it rightward as far as it needs to go. A small element out of place moves exactly one position left per pass — the sweep goes the other way — so a single misplaced minimum at the far end forces n − 1 full passes and n(n − 1)/2 comparisons to perform n − 1 swaps. Insertion sort on the same input does 2n − 3 comparisons (n − 2 failing tests, then one scan of n − 1 for the misplaced minimum). The early-exit flag rescues only the already-sorted case and inputs whose disorder happens to be "large elements too far left"; it does nothing for the reverse, and on a random permutation the measured comparison count is about twice insertion sort's for the same number of inversions removed, because insertion sort stops each scan at the first non-greater element while bubble sort's pass always runs to the end.

Cocktail shaker and the other patches

Alternating the sweep direction (cocktail shaker sort) fixes the small-element asymmetry — a pass in each direction moves a misplaced element to its place whichever way it must go — and tracking the position of the last swap lets each pass stop early at the boundary of the already-final suffix. Both are real improvements and both leave the algorithm dominated by insertion sort: the same I swaps, at least as many comparisons, no online property, and an inner loop that swaps (three moves) where insertion sort shifts (one move). The reason bubble sort persists in curricula is that it is the easiest sort to see, which is a virtue of a first example and not of an algorithm. Use §03's figure to watch it once, then never write it.

The one thing it teaches well. "One adjacent swap removes exactly one inversion" is a genuinely useful lemma — it proves that any sort restricted to adjacent swaps needs at least I swaps, hence Θ(n²) on average, and it is why shellsort (§07) exists: to beat the quadratic bound you must exchange elements that are far apart.

07 Shellsort: gap sequences, and what is and is not known

Every sort in §03–§06 moves elements one position at a time, and §06's lemma says that costs I exchanges, which on random input is n²/4. Shellsort's idea is to let elements jump. For a decreasing sequence of gaps h ending in 1, insertion-sort each of the h interleaved subsequences a[k], a[k+h], a[k+2h], …; the array is then "h-sorted", and a later, smaller gap inherits a nearly ordered input. The final pass with h = 1 is plain insertion sort, but by then few inversions remain. The algorithm is four lines; its analysis is one of the oldest open problems in the subject.

the algorithmfor each gap h in the sequence (largest first, last = 1): for i = h .. n − 1: v = a[i]; j = i while j ≥ h and a[j − h] > v: a[j] = a[j − h]; j = j − h a[j] = v the two facts that make it work1. after the h pass the array is h-SORTED: every subsequence with stride h is in order 2. an array that is h-sorted and is then k-sorted STAYS h-sorted (the earlier work is not undone) ⇒ each pass inherits the order of all previous passes; the final h = 1 pass sees few inversions what is known, by gap sequence — WORST-case bounds, each proved for its own sequence onlyfloor(n/2ᵏ): n/2, n/4, …, 1 Θ(n²) the original sequence; all gaps even until 1, so evens and odds never mix 2ᵏ − 1: 1, 3, 7, 15, 31, … Θ(n^(3/2)) (3ᵏ − 1)/2: 1, 4, 13, 40, 121, … Θ(n^(3/2)) — the sequence §03's figure and this section's default use 2ᵃ·3ᵇ: 1, 2, 3, 4, 6, 8, 9, … Θ(n log² n) best proved asymptotic bound; too many gaps to be fast in practice 1, 4, 10, 23, 57, 132, 301, 701, … empirically the fastest known small-n sequence; no proved bound ANY sequence: Ω(n · (log n / log log n)²) — a lower bound for every gap sequence, so shellsort is NOT O(n log n) what is NOT knownthe average-case running time for essentially any useful sequence; whether any sequence achieves the lower bound; the best sequence

Fact 2 is the non-obvious one and the reason the method works at all: a pass with a smaller gap does not destroy the order created by a larger one. The proof is a short exchange argument and is the only piece of theory the practitioner needs. Sketch: suppose the array is h-sorted and a k-pass then moves elements; a k-pass is an insertion sort on each k-chain, and an insertion sort only ever exchanges an adjacent pair of its chain that is out of order. Consider any two positions i < i + h after the k-pass, and the elements a, b that were exchanged to put them there: they came from positions i − k, i + h − k (or the same positions), which were h-ordered before the pass, and an exchange that repairs a k-inversion between two elements cannot create an h-inversion, because the two elements it moves are each moving toward a position whose h-partner was already on the correct side of both. Chase the two interleavings of the chains and every case reduces to that. Where it is used, and why it is not stable

Shellsort is the sort of choice when code size matters more than the last factor of two — embedded systems, bootstrap loaders, anywhere a recursive n log n sort is unwelcome — because it is insertion sort with one extra loop, uses no stack and no buffer, and is respectable up to tens of thousands of elements. It is not stable: an h-pass with h > 1 moves an element past elements it is never compared with, so two equal keys in different strided subsequences can cross. The §01 vocabulary check for it therefore reads: in-place yes, stable no, adaptive somewhat (it is insertion sort at the end), online no. Its real intellectual contribution is the observation that a sequence of passes that each leave a partial order intact can add up to a full sort — the same design as LSD radix sort's digit passes (§21), where the "partial order" preserved is the ordering by lower digits and the tool that preserves it is stability.

08 The Ω(n log n) lower bound: decision trees, worst case and average case

Every sort so far is Θ(n²) or worse than n log n; the sorts from §09 on are Θ(n log n). Before improving further it is worth knowing that no comparison sort can do better than log₂(n!) ≈ n log₂ n − 1.44n comparisons in the worst case — nor in the average case. What the theorem does and does not say

  • It is about a model. Counting sort (§20), radix sort (§21) and bucket sort (§22) run in linear time without contradiction, because they never ask "is aᵢ ≤ aⱼ" — they read the key's value as a number and use it as an index. The bound says nothing about them, and it says nothing about sorting integers in general. It says: if all you may do is compare, this is the floor.
  • It is about comparisons, not time. A sort that makes n log n comparisons but moves n² elements is quadratic. The bound is a lower bound on one resource; upper bounds have to account for all of them (§19).
  • It is a worst-case AND average-case statement, and the two are separate theorems with separate proofs. The worst-case bound follows from the height of a tree with n! leaves; the average-case bound from its mean leaf depth. Both are log₂(n!). A common misreading is that "some inputs must be slow but most could be fast" — they cannot: at most a vanishing fraction of the n! inputs can sit at depth much below log₂(n!) − c, since a tree has at most 2ᵈ leaves at depth d.
  • It is tight. Mergesort and heapsort achieve O(n log n) in the worst case, so Θ(n log n) is the true worst-case complexity of comparison sorting — the bound is not a gap in our knowledge but a closed question. The remaining gap between log₂(n!) and the best sort is a linear term, and closing that is what merge-insertion and its descendants do, at a cost in moves that makes them impractical.

09 Mergesort as a sort: the merge invariant, stability, and the buffer

Mergesort is the first sort on this page that meets the bound of §08, and it does so because of one linear-time primitive: merging two sorted runs into one sorted run in p + q − 1 comparisons at most. Sorted input is the precondition that makes it cheap — the smallest unconsumed element of the union is always at the front of one of the two runs, so one comparison decides the next output element. Everything mergesort is (stable, Θ(n log n) in every case, sequential, buffer-hungry) is a property of this loop. The recursion that calls it, and the recurrence T(n) = 2T(n/2) + Θ(n), are in Recursion, Divide & Conquer, §14; this section is about the merge.

The buffer, and what "in place" would cost

The merge above needs Θ(m) extra space, and mergesort therefore needs a buffer of n elements — allocated once, at the top, and threaded through the recursion, because allocating per call turns a constant into a log n factor of allocator traffic and, worse, a fresh cache-cold buffer at every level. That buffer is the standard objection to mergesort and the objection is weaker than it looks. Merging in place in linear time is possible in principle — stable in-place merge algorithms with O(m) moves and comparisons exist — but their constants are large enough that a simple in-place merge is usually implemented by rotations, which cost O(m log m) per merge and make the whole sort O(n log² n); and the linear-time constructions are so involved that they are essentially never used. The honest statement is: mergesort with a buffer is Θ(n log n) and stable; mergesort without one is either slower by a logarithmic factor or impractically complex; and when memory is the constraint the answer is heapsort or quicksort, not an in-place merge. The linked-list version (§10) is the exception that proves the rule — there the "buffer" is the pointers you already have.

Sequential access is the asset. The merge reads two runs front to back and writes one run front to back: three sequential streams, which is the best case for prefetching and for a cache line. That is why mergesort — not quicksort, not heapsort — is the algorithm of external sorting (§29) and of every library sort that has to be stable (§24). "It needs a buffer" and "its access pattern is ideal" are the same fact seen from two sides.

Mergesort on a linked list: O(1) extra space, honestly

On a singly linked list the merge needs no buffer at all: the two runs are already chains of nodes, and merging them is re-linking next pointers — each step detaches the smaller front node and appends it to the output chain. Splitting is the only cost that changes: finding the middle of a list takes a Θ(n) walk (the runner technique of Linked Structures, Stacks & Queues, §09), which adds a linear term per level and leaves the total at Θ(n log n). The bottom-up schedule avoids even that: walk the list once, merging runs of length 1 into 2, then 2 into 4, and so on, with no midpoint search at all. The result is the one classical case of a stable n log n sort in O(1) extra space — because the "extra space" is the n pointers the list already carries — and it is why mergesort is the sort for linked lists, where quicksort's random-access partition and heapsort's index arithmetic are unavailable. The cache cost is the usual one for linked structures: every node visit is a potential miss, so the constant is far worse than the array version's.

Which variant, when

  • Top-down is the reference implementation: simplest to prove, O(log n) stack, the exact counts above. Its one avoidable inefficiency is copying: alternating the roles of the array and the buffer level by level (merging from one into the other) halves the moves from 2n to n per level.
  • Bottom-up removes the recursion, which matters where a stack is unwelcome, and is the natural form for linked lists and for external sorting (§29). Pad the input to a power of two conceptually — or accept the lopsided tree's slightly larger worst case.
  • Natural buys adaptivity in the run measure: presorted, reverse-sorted-then-fixed, and "sorted with a block appended" inputs all sort in near-linear time. The price is a run-detection pass and unbalanced merges on random input. Library sorts (§24) take this idea and add a minimum run length built by insertion sort, so that the balanced and the adaptive behaviours are both kept.
  • The stability of all three rests on the same character: ≤ in the merge. Nothing else in mergesort can reorder equal keys, because no element ever moves past another except through a merge.

11 Quicksort: the idea, and the partition invariant

Mergesort does no work to divide and all its work to combine. Quicksort is the mirror image: choose a pivot, rearrange the array so that everything smaller is to the pivot's left and everything larger to its right, then sort the two sides recursively — and there is no combine step at all, because a sorted left part, the pivot, and a sorted right part are already a sorted whole. All the intelligence is in the partition, a single linear pass, and everything about quicksort — its speed, its instability, its quadratic worst case, its sensitivity to equal keys — is a property of how that pass is written and which pivot it is given.

Why a fixed proportional split is still n log n

The 1-to-9 line is the one to internalise, because it is why quicksort works in practice at all. The recursion tree of a 1:9 split has its shallowest leaf at depth log₁₀ n and its deepest at log n / log(10/9) ≈ 22·log₁₀ n; every level costs at most n, so the total is at most n · log n / log(10/9) = O(n log n). The base of the logarithm — the constant — depends on how lopsided the split is, but the split does not have to be even, or anywhere near even, for the exponent to be right. A random pivot lands in the middle 80% of the sorted order with probability 0.8, so four out of five partitions are at least 1:9, and the occasional bad one is absorbed: an unlucky level of cost n followed by a lucky one costs n + n = 2n for the same progress a single lucky level would have made. That is the intuition; §16 makes it a theorem with an exact expectation.

What every partition scheme must and must not do

  • It must shrink both sides. The Lomuto scheme (§12) places the pivot at its final index q and excludes it from both recursive calls, so each side has at most n − 1 elements. The Hoare scheme (§13) does not fix the pivot; its guarantee is subtler — the returned index is strictly less than hi − 1 — and using its return value with Lomuto's recursion — excluding A[j] from both calls — silently leaves one element unsorted at every level (§13 lists the bug).
  • It must be linear and sequential. Every scheme here scans with one or two indices moving monotonically, comparing each element to a pivot value held in a register. That inner loop — increment, compare, occasionally swap — is why quicksort is fast: it is the tightest loop of any n log n sort, it touches memory in order, and its one branch is well predicted on random data. "In place" is a side effect, not the cause.
  • It need not be stable, and none of the simple ones are. A swap that moves an element across the unexamined middle can carry it past an equal key. Making quicksort stable requires either an O(n) buffer (at which point mergesort is the better choice) or a stable in-place partition with a logarithmic overhead; in practice a stable sort is a merge sort (§24).
  • Its behaviour on equal keys is not specified by the contract. The postcondition "≤ p on the left, ≥ p on the right" lets equal keys go either way, and the three schemes make three different choices with three different costs on duplicate-heavy input — §15 measures a factor of 250 between them at n = 1024.

13 The Hoare partition, on the same array

The original partition scans from both ends toward the middle: the left index advances past elements smaller than the pivot, the right index retreats past elements larger, and when both have stopped on a misplaced pair the two are swapped. It does far fewer swaps than Lomuto on random input — one third as many inside the scans, roughly 40–60% fewer overall once each partition's pivot-placement swap is counted (measured 1.6–1.9× fewer at n = 1024–4096) — its scans stop on keys equal to the pivot — which is what saves it on duplicates — and it does not leave the pivot at a known index, which changes the recursion and is the source of most Hoare-partition bugs.

That costs Hoare a few extra comparisons per level — the n + 2 against n − 1, plus one element more in a subproblem — and the measured totals in §16 show the price: about 1.65× Lomuto's comparisons at n = 64, falling to 1.28× at n = 4096 as the shared 2n·ln n term dominates. The two bugs this scheme invites

  • Recursing on (lo, j) and (j + 1, hi) as if j were the pivot's index. It is not; A[j] is merely the last element of the left part. Excluding it from both calls leaves A[j] where it is, never placed: the output is a permutation of the right multiset in the wrong order — swaps cannot lose elements, so the bug shows up as an unsorted result, not a crash. The correct calls are [lo, j + 1) and [j + 1, hi).
  • Taking the pivot from the middle or the end without moving it to A[lo]. The termination argument — the pivot stops both scans — needs the pivot value to be in the range on the correct side of where the scans start. With p = A[hi − 1] and the loop above, neither scan runs off — the pivot value still stops both — but the guarantee j < hi − 1 is lost: on [1, 2] the partition returns j = 1 = hi − 1, the left call is the whole range again, and the recursion never terminates. Choose the pivot however you like (§14), then swap it to lo before the loop.

14 Choosing the pivot: first, random, median-of-three, ninther

The partition's cost is fixed at Θ(n); the pivot decides how much progress that cost buys. A pivot at rank k splits the range k − 1 : n − k, and the sum over the recursion of these split costs is the running time. The first or last element is the worst possible rule on the most common inputs; the median of three sample elements is the standard cheap improvement; a random element gives an expected guarantee on every input; and no deterministic rule that looks at o(n) elements is safe against an adversary who knows it.

Deterministic rules have killers; random rules have bad luck

For every deterministic pivot rule that inspects a bounded number of positions there is an input that makes it quadratic, and such inputs can be constructed mechanically — an adversary answers each comparison in whichever way keeps the pivot extreme, assigning actual values only when forced, and the resulting array defeats that specific implementation. Median-of-three "killers" for the standard library quicksorts of the 1990s were built exactly this way, and they were a denial-of-service vector against any service that sorted user-supplied data. A random pivot has no killer ordering: on distinct keys its cost is a random variable whose expectation is 2n·ln n on every input (duplicate-heavy input is a different matter — with Lomuto it stays quadratic whatever the pivot, §15), and whose probability of exceeding that by any fixed factor shrinks as n grows (§16). The residual risk is a bad random draw, not a bad input, and the two are different in kind: an adversary can choose the input and cannot choose the draw. Where determinism is required — reproducibility, or no access to randomness — the answer is not a cleverer pivot but a guaranteed fallback: introsort's depth limit (§17).

Practical summary. Use median-of-three (or the ninther on large ranges) for its constant-factor gain, and either a random component or a depth-limited fallback for its guarantee. Never the first or last element alone: sorted input is not rare, it is the single most common input a sort receives.

Why the average is trustworthy, and what "expected" means here

The theorem's hypothesis is that the pivot's rank is uniform at every call, which a random pivot guarantees on every input, and which a fixed rule guarantees only when the input is a random permutation. That is the difference between an average-case bound and an expected-time bound, and Algorithm Analysis, §06, is about exactly this distinction: the first is a statement about typical inputs and says nothing about yours; the second is a statement about the algorithm's own coin flips and holds for every input. Beyond the expectation, the distribution is concentrated — the probability that randomized quicksort's count deviates from its mean by any fixed fraction goes to zero as n grows, and the figure's Monte Carlo means sit within a few percent of the exact value at a few dozen runs — so in practice the expectation is the running time, on every input. The expectation argument in its general form, with the sampling framework that makes "2/(j − i + 1)" precise, is Recursion, Divide & Conquer, §27.

17 Practical quicksort: the small-subarray cutoff and introsort

Two engineering additions turn the textbook quicksort into the one libraries ship. The cutoff: stop partitioning ranges below some small size and finish with insertion sort, because on a dozen elements the partition's overhead exceeds the quadratic sort's total. Introsort: track the recursion depth and, if it exceeds 2·floor(log₂n), hand the current range to heapsort — which converts quicksort's Θ(n²) worst case into a guaranteed O(n log n) at no measurable cost on ordinary inputs.

What else a production quicksort does

  • Equal-key handling. A Hoare-style scan that stops on equal keys, usually with equal keys collected at the two ends during the scan and swapped into the middle afterwards, so that duplicate-heavy input is O(n log d) (§15) without paying two comparisons per key on distinct input.
  • Pivot by size. Median-of-three on small ranges, the ninther on large ones (§14), and, in the pattern-defeating variants, a check for whether the partition did any work at all — a partition that swapped nothing on an already-ordered range is a strong hint that the range is sorted, and a quick insertion-sort attempt with a bounded budget can finish it in linear time.
  • Adversary defence. Either a random element in the pivot choice, or — the common choice, since randomness costs time and reproducibility — a depth limit with heapsort, exactly the introsort rule above. On detecting a bad partition some variants also shuffle part of the range, which breaks the pattern that produced it.
  • Branch-free partitioning. On modern processors the partition's one data-dependent branch is the dominant cost on random input, since it is mispredicted half the time; block-based partitions that buffer the indices of misplaced elements and swap them in bulk remove the branch and are measurably faster. This is the clearest case of an algorithm being optimised for the machine rather than for the operation count, and it is the reason "quicksort is fast because it is in place" is the wrong explanation — it is fast because its inner loop can be made branchless and sequential.
Where this leaves quicksort. With a good pivot, three-way or equal-stopping partition, a cutoff, and a depth limit, quicksort is an in-place O(n log n) sort with the smallest constant of any comparison sort on random data, no worst-case input, and a sequential access pattern. What it still is not is stable — and that is the one property that keeps mergesort (§10, §24) in every standard library beside it.

18 Heapsort's contract, and where it is taught

Heapsort is selection sort (§05) with the Θ(n) scan for the maximum replaced by a heap's O(log n) extract: build a max-heap over the array in place in Θ(n), then n − 1 times swap the root to the end of the live region and sift the new root down. It is the one comparison sort that is simultaneously O(n log n) in the worst case and O(1) in extra space, which makes it the guaranteed fallback inside introsort (§17) and the right answer whenever memory is the binding constraint. It is not stable, and its access pattern is the worst of the three n log n sorts.

Where it wins and where it loses

  • Wins: a guaranteed bound with no memory — introsort's fallback, embedded and real-time systems, sorting in a fixed buffer. And the partial sort: the k largest of n in O(n + k log n) by stopping after k extractions, which no other sort here does cheaply.
  • Loses: to quicksort by a constant of about 1.5 in comparisons (1.76 against 1.17–1.27 in §19) and far more in wall-clock time on large arrays, because every sift-down is a chain of cache misses; to mergesort on stability and on sequential access. The heaps page's §15 has the measured ratios.

19 The n log n sorts head to head: comparisons, moves, memory, stability, worst case

The columns the counter cannot measure

  • Worst case. Mergesort and heapsort are Θ(n log n) on every input by the shape of their recursion or their heap; quicksort is Θ(n²) unless a depth limit or a random pivot is present, and then it is O(n log n) guaranteed or expected respectively (§16, §17). A service that sorts adversarial input must not run an unguarded quicksort.
  • Stability. Mergesort only. That single fact decides the default sort of every language runtime that promises stability (§24) and every multi-key sort (§23).
  • Memory. Heapsort O(1); quicksort O(log n) stack with smaller-first; mergesort Θ(n), or O(1) on a linked list.
  • Access pattern. This is the column that decides wall-clock time and that no operation count captures. Mergesort streams; quicksort's partition streams from both ends; heapsort jumps across the array at every level of every sift. On arrays larger than the cache, the same "1.76 versus 0.90" comparison ratio between heapsort and mergesort becomes a much larger running-time ratio, because heapsort's comparisons each wait on memory while mergesort's arrive in prefetched lines. The principled version of this argument — why an operation count is a model of running time and where the model breaks — is Algorithm Analysis, §22–§23.
  • Branch prediction. Quicksort's partition branch is unpredictable on random data, which is why the branchless block partition of §17 exists; mergesort's merge has the same problem and the same fix (branchless merges select with arithmetic rather than a jump). Heapsort's comparisons are data-dependent at every step and cannot be made branchless as easily.
The decision, in one line each. Need stability, or the input is a linked list or a stream, or the data does not fit in memory → mergesort. Need the best typical speed in place and can tolerate an expected or depth-limited bound → quicksort (as introsort). Need a hard bound in O(1) space, or the k largest, or a fallback → heapsort. Keys are small integers or fixed-width strings → none of them; read §20–§22.

20 Escaping the bound: counting sort

The lower bound of §08 binds algorithms that only compare. Counting sort never compares two keys: it assumes the keys are integers in a known range 0..k−1, counts how many times each value occurs, converts the counts to prefix sums — which are exactly the final positions — and places each element by indexing. Its cost is Θ(n + k), linear whenever k = O(n), and it is stable, which is the property radix sort (§21) will need from it.

Where it applies, and where it quietly does not

  • Small integer keys with satellite data — sorting records by a byte-sized category, a grade, a month, a small enumeration. The output array carries the whole record, which is why stability and the backwards pass matter: they are what keep records with the same key in their original order.
  • Not for keys that merely look small. 32-bit integers have k = 4·10⁹; a count array of that size is neither linear nor allocatable for n in the thousands. Radix sort (§21) is what turns wide keys into a sequence of narrow ones.
  • Not in place, and not comparison-based. It needs a caller that can hand it an integer key function; it cannot sort under an arbitrary comparator. This is exactly the boundary the lower bound draws — leave the comparison model, gain linearity, lose generality.
  • The counting pass alone is useful. A histogram is Θ(n + k) and answers "how many keys in [a, b]" in O(1) after the prefix pass, which is the prefix-sum trick of Arrays & Strings, §14, applied to a key distribution.

21 Radix sort: LSD and MSD, the stability requirement, and the word-size hypothesis

Radix sort sorts wide keys by sorting on one narrow digit at a time. Least-significant-digit first: sort the whole array by the last digit, then by the next, and so on, using a stable sort for each pass — after the pass on digit d the array is sorted by its low d + 1 digits. With counting sort as the digit sort, d digits of k possible values cost Θ(d·(n + k)). Whether that beats n log n depends on how many digits a key has relative to log n, and on nothing else.

MSD radix sort, and why it is the different algorithm

Most-significant-digit first is the recursive version: bucket the keys by their leading digit, then sort each bucket recursively on the next digit. It is not a sequence of stable passes over the whole array — each bucket is an independent subproblem, exactly as in quicksort with a k-way partition — and it has two properties LSD lacks. It stops early: a bucket of one element is finished, so keys that are distinguished by their first few digits never have their remaining digits examined, and on keys with long common prefixes or highly variable lengths (strings, most obviously) it inspects only the characters it must. And it works on variable-length keys, since a key that has run out of digits simply sorts first in its bucket. Its cost is that it creates k buckets at every recursive call — on the seven-key example the readout counts 30 bucket arrays for 11 placements — which for a large radix and small buckets is pure overhead; production versions switch to insertion sort on small buckets for the same reason quicksort does (§17). LSD is the algorithm for fixed-width integer keys; MSD, or its three-way-quicksort hybrid for strings, is the algorithm for text.

And it is not stable by construction in the way LSD is: stability within a bucket is whatever the recursive call preserves, so an MSD sort that finishes small buckets with insertion sort is stable and one that finishes them with quicksort is not.

When radix beats comparison sorting, honestly

  • Key width against log n. A 32-bit key over a million elements is 4 byte-passes against 20 comparison levels; a 64-bit key over a thousand elements is 8 passes against 10 levels. The formula b/log n passes says which regime you are in, and "radix sort is faster for integers" is true only in the first.
  • Memory traffic. Each radix pass reads the whole array and writes it to another buffer with scattered writes (one per bucket); a comparison sort's passes are sequential or nearly so. On data larger than the cache, a radix pass can cost several times what its operation count suggests, and the byte-per-pass choice is often tuned to keep the 2ʳ counters in cache rather than to minimise passes.
  • What it cannot do. Sort under a user-supplied comparator; sort floating-point keys without a bit-level transform; sort in place (the standard version needs a second array); or be adaptive — its cost is D·(n + k) on sorted input too.

22 Bucket sort and its distribution hypothesis

Bucket sort is the third way out of the comparison model, and it rests on the strongest hypothesis of the three. Assume the keys are real numbers drawn uniformly and independently from [0, 1); split the interval into n equal buckets, drop each key into its bucket by one multiplication, insertion-sort each bucket, and concatenate. Under the hypothesis, every bucket holds a constant number of keys on average and the whole thing is expected-linear. Without it, one bucket can hold everything and the cost is insertion sort's — quadratic.

Where it fits

Bucket sort is the right tool when the keys are known to be spread evenly over a known range — the output of a hash function, uniformly generated identifiers, measurements with a flat distribution — and when the range is continuous or too wide for counting sort. It generalises counting sort (which is bucket sort with one bucket per key value and no within-bucket sort) and it is the one-pass ancestor of MSD radix sort (§21), which is bucket sort applied recursively with the digit as the bucket index. In practice its most common appearance is not as a sort at all but as the distribution step of a sample sort or an external sort (§29): partition the data into ranges by sampled splitters so that the ranges are roughly equal, then sort each range independently, in parallel or in memory. The analysis above is exactly the analysis of why that works — and of why it fails when the splitters are chosen without looking at the data.

The three escapes, side by side. Counting sort: integer keys in a small range, Θ(n + k), no hypothesis about the input's order or distribution. Radix sort: integer keys of bounded width, Θ(D·(n + k)), linear iff the width is O(log n), needs a stable digit sort. Bucket sort: real keys, expected Θ(n) iff the distribution is known and spreads the keys, quadratic otherwise. Each replaces the comparison model's one weak hypothesis — "keys are comparable" — with a stronger one, and each is only as fast as its hypothesis is true.

23 Sorting records: keys versus satellite data, indirect sorting, and multiple keys via stability

Real sorts rarely sort numbers. They sort records — rows, objects, structs — by one field, and carry the rest along. That changes three things: a move now costs the size of the record, not a word; the key may be expensive to compute or compare; and "sort by A, then by B" becomes a question about stability. Each has a standard answer, and all three are about separating the ordering from the moving.

Why the key function belongs outside the comparator

A comparison sort calls its comparator about n·log₂n times — 20 million times for a million records. If the comparator computes something from each record on every call (lower-cases a string, parses a number out of a field, walks a pointer), that computation is done twenty times per record instead of once. The decorate-sort-undecorate pattern computes key(r) exactly once per record, stores it beside the record, sorts the pairs by the precomputed key, and discards the keys afterwards. It costs Θ(n) extra memory and one pass, and it is the reason every library sort accepts a key function as well as, or instead of, a comparator: the library applies the pattern for you. The second thing the pattern buys is stability for free — if the decoration is (key, original index), no two decorations are equal and the sort's own stability is irrelevant, which is the standard way to get a stable result out of an unstable sort.

Indirect sorting, and the cost of reading the answer

When records are large, sorting an index array is cheaper by the ratio of record size to word size in every move, and the comparison count is unchanged. The result is a permutation, not a sorted array: idx[0] is the position of the smallest record, and reading the records in sorted order means jumping through memory in that order — a scattered access pattern, one cache miss per record if the records are large. Whether that matters depends on how many times the sorted order is read. Read once, the index is the right answer. Read many times, apply the permutation in one pass — cycle by cycle, in place, or into a fresh array — and pay the scatter once. Database engines make this decision constantly: a sort by key produces row identifiers, and the "materialise the rows in order" step is a separate, and often more expensive, operation.

Multi-key sorting: the stability theorem in daily use

"Sort employees by department, and within each department by name" is one of two things. Written as a single lexicographic comparator it is one sort of any kind. Written as two sorts — first by name, then stably by department — it is correct for exactly the reason LSD radix sort is: the second sort orders records with different departments, and for records with the same department leaves them in the order the first sort produced, which was by name. Swap the order of the two passes, or use an unstable sort for the second, and the result is sorted by department with names in arbitrary order. The multi-pass form is what makes interactive "click a column header to sort by it" interfaces behave as users expect: each click is a stable sort by the clicked column, and the previously chosen columns survive as tie-breakers. It is also why the default sort of every runtime that offers one is stable (§24) — not because stability is elegant but because this idiom is everywhere.

The rule. Compute keys once, move indices rather than records when records are large, and use stability — yours or the decoration index's — whenever a sort is followed by another sort. Every one of these is a constant-factor concern, and every one of them routinely outweighs the difference between two n log n algorithms.

24 What library sorts actually do: hybrids, run detection, guaranteed fallbacks

No standard library ships a textbook quicksort or a textbook mergesort. Each ships a hybrid: an n log n algorithm for the bulk of the work, insertion sort below a cutoff, a mechanism that recognises existing order and finishes it in linear time, and a hard worst-case guarantee. The designs cluster into two families, and which family a library chose is decided by one question — whether the sort is required to be stable.

the two families — described as techniques, not as any one implementationSTABLE, MERGE-BASED ("natural merge with a minimum run") · scan for existing ascending runs; reverse strictly descending ones in place so they count too · a run shorter than a minimum length (a few dozen elements) is extended to it by binary insertion sort · merge runs from a stack, keeping the pending run lengths roughly geometric so the merge tree stays balanced · during a merge, when one run keeps winning, switch to "galloping": exponential search (§27) for how far it wins result: Θ(n) on sorted or reverse-sorted input, O(n log r) for r runs, O(n log n) worst, stable, Θ(n) buffer at most UNSTABLE, PARTITION-BASED ("introspective / pattern-defeating quicksort") · median-of-three or ninther pivots by range size, insertion sort below a cutoff of roughly a dozen to a few dozen elements · a partition that handles equal keys — either three-way, or a Hoare-style scan that stops on equals · a check after each partition: if nothing moved, the range may already be sorted — try a bounded insertion sort · a recursion-depth limit of about 2·log₂n, past which the range goes to heapsort; some variants also break a detected pattern by swapping a few elements result: O(n) on several common patterns, O(n log n) guaranteed, in place, NOT stable

What this means for the reader of a sort's documentation

  • "Stable" is the property to check first. As a matter of general practice at the time of writing: the default list sort in Python is stable and merge-based; the sort of object arrays in Java is stable and merge-based, while its sort of primitive arrays is a dual-pivot quicksort, stability being meaningless for primitives; the C++ standard's sort is not required to be stable and is typically an introsort, with stable_sort a separate merge-based function; JavaScript's array sort has been required to be stable since the 2019 language standard; Rust and Go each offer a stable sort and an explicitly named unstable one. The unstable variants exist because they are faster and in place; the stable ones exist because §23's idioms need them. Check, do not assume.
  • Adaptivity is now standard. Both families sort already-sorted, reverse-sorted and "sorted with an appended tail" inputs in linear or near-linear time. Pre-checking for sortedness before calling a library sort is redundant, and pre-shuffling to "avoid the worst case" is actively harmful — it destroys the order the sort would have exploited, and the worst case is already handled by the fallback.
  • The worst-case guarantee is real. Depth-limited quicksorts are O(n log n) on every input, including adversarial ones; merge-based sorts always were. An unguarded quicksort with a quadratic worst case is not something a maintained library ships, and §14's killer inputs are a concern only for hand-written sorts.
  • The cutoff and the minimum run are tuning constants, set by measurement on the implementer's hardware. Typical values are in the range this page measured — around a dozen elements for the quicksort cutoff (§17), a few dozen for the minimum run — and they are not part of any interface. Quoting them as facts about "the algorithm" is a mistake; they are facts about a build.
  • Key functions and comparators are both accepted, and the library applies decorate-sort-undecorate (§23) for the former. Prefer the key function: it is called n times, the comparator n log n.

Why the merge family won stability and the partition family won speed

A merge is naturally stable and naturally sequential, and detecting runs is a natural extension of a bottom-up merge; the whole stable family is §10 made adaptive plus §04's insertion sort for the small pieces. A partition is naturally in place and naturally branch-predictable when written carefully, and the depth limit is the cheapest possible worst-case insurance; the whole unstable family is §17 with equal-key handling from §15 and pattern detection bolted on. The two families do not compete on the same axis, and the reason both exist in every runtime is that no known sort is at once stable, in place, and O(n log n) with a small constant. When a library offers only one sort, it is usually — not always: C's qsort promises nothing — the stable one; a stable sort can be used where an unstable one is wanted, at some cost, but not the other way round.

Practical rule. Use the library sort. Pass a key function. Ask for the stable variant when the sort is followed by another sort or when equal keys have meaning. Reach for anything on this page by hand only when the library's contract is wrong for the problem — a linked list, an external file, a fixed memory budget, a key type that permits a radix pass, or a partial result such as the k smallest.

25 Searching: linear search, and when it wins

Searching is locating a key, and the simplest search is the only one that works on unordered data: look at every element until the key turns up, or the elements run out. It is Θ(n) in the worst case and on average, it needs no precondition, no extra memory and no structure, and on small arrays it is faster than anything cleverer for reasons the operation count does not show. The sections that follow are about what it costs to do better — sorting first, or maintaining a structure — and linear search is the baseline every one of them has to beat.

Why the linear scan wins on small arrays

A linear scan over a few dozen contiguous elements is a loop with a predictable branch and a sequential memory pattern — the processor prefetches the next line, the branch predictor learns "not yet", and the compiler may vectorise the comparison so that several elements are tested per instruction. A binary search over the same elements makes a handful of unpredictable branches, each of which is mispredicted about half the time, and each probe lands on an address the previous one did not predict. For small n the constant costs of the four or five mispredictions exceed the cost of scanning everything, and the linear scan is faster in wall-clock time despite doing several times the comparisons. Where the crossover sits depends on the element size, the key type and the machine, and this page does not quote a number for it — it is measured per platform, and the honest statement is only its direction: below some small n, scan; above it, halve. Library implementations of binary search and of the merge step in stable sorts (§24) routinely switch to a linear scan when the range shrinks below such a threshold, for exactly this reason. The same argument, with the same conclusion, is why insertion sort finishes every fast sort (§04, §17).

What linear search is really for

  • One-off lookups in unsorted data. A single query does not justify a Θ(n log n) sort or the memory of a hash table; q queries do once q exceeds roughly log n (§02).
  • Queries that are not equality. "The first element satisfying a predicate", "the element with the maximum score", "any element in a range" — over unsorted data all of these are a scan, and a scan with a predicate is the only general tool.
  • The bottom of every hybrid. The last few elements of a binary search, a bucket in a hash table, a leaf in a B-tree: each ends in a short linear scan, because at that size nothing beats it.
The baseline, stated once. A search that does not exploit order or hashing costs Θ(n) per query. Every faster search on this page pays for its speed with a precondition — sortedness, a hash function, a tree — and the precondition's cost is part of the search's cost.

26 Binary search: the loop, the invariant, the two bugs, and one convention

On a sorted array one comparison against the middle element eliminates half the candidates, and repeating that gives floor(log₂n) + 1 probes in the worst case. That much everyone knows; what makes binary search famous is how often it is written wrong. The loop below is correct; its invariant is the reason; and the two ways it is usually broken — a range that fails to shrink, and a midpoint that overflows — are each one character. This page uses the half-open convention [lo, hi) throughout: lo is the first candidate, hi is one past the last, and the range is empty exactly when lo = hi.

The two bugs

  • Bug 1 — the range that does not shrink. Write lo = mid instead of lo = mid + 1. On most ranges nothing goes wrong — from [3, 5), mid = 3 + floor(2/2) = 4, and if A[4] < x then lo = 4 still shrinks the range to [4, 5) — which is exactly why the bug survives testing. Take [3, 4): mid = 3; if A[3] < x then lo = mid = 3, and the range [3, 4) is unchanged forever. The measure hi − lo failed to decrease on a range of size 1, which is the last size any test reaches, and the loop spins. The same bug in the closed convention is hi = mid (instead of mid − 1) on a ONE-element range, or lo = mid on a two-element one — with mid = lo + floor((hi − lo)/2), mid equals lo on both sizes and equals hi only on size 1. The cure is the termination argument above: check that both branches strictly shrink the range at every size, including 1 and 2.
  • Bug 2 — the midpoint that overflows. (lo + hi) / 2 is wrong whenever lo + hi can exceed the integer type's range — in a 32-bit index over an array of more than about a billion elements the sum wraps negative, mid is negative, and the read is out of bounds. lo + (hi − lo) / 2 computes the same value and cannot overflow, because hi − lo ≤ hi. In languages with arbitrary-precision integers the bug is unreachable, but the habit is worth keeping: the form that is correct everywhere costs nothing.

The convention, and why one is chosen

Closed [lo, hi] and half-open [lo, hi) are both correct when written consistently: closed initialises hi = n − 1, loops while lo ≤ hi, and updates with hi = mid − 1; half-open initialises hi = n, loops while lo < hi, and updates with hi = mid. Arrays & Strings, §16, writes the closed form. This page commits to the half-open form for three reasons: the empty range is representable without a negative index (lo = hi, never hi = −1); the terminating value of lo is directly the insertion point and the boundary variants (§27) need no adjustment; and hi − lo is the number of candidates, which makes the termination argument a sentence. Mixing the two — hi = n with lo ≤ hi, or hi = mid with hi = n − 1 — is the third bug, and it is the one that reads out of bounds or misses the last element only on some inputs. Pick one, and write every search the same way.

Exponential search: when the array is unbounded or the answer is near the front

If the array's length is unknown, or infinite in effect (a stream that can be probed at any index), or the answer is expected close to the start, probe indices 1, 2, 4, 8, … until the key is exceeded, then binary-search the last interval [2ᵏ⁻¹, 2ᵏ] (closed at the top — the probe that stopped the doubling may itself be the key). The cost is O(log i) where i is the answer's position — about 2·log₂i probes, one for the doubling and one for the search — which is better than log₂n whenever i ≪ n and never worse by more than a factor of two. Its main use is inside merging: when one run keeps winning a merge, the merge switches to galloping — an exponential search along the winning run for how far it wins — and copies that stretch in one move instead of one element per comparison. This is what makes the merge-based library sorts of §24 near-linear on inputs made of a few long runs.

28 Searching beyond arrays: what a search tree, a hash table and a skip list each buy

A sorted array answers every ordered query in O(log n) and costs Θ(n) per insertion. That trade is right for read-mostly data and wrong for everything else, and the three classical alternatives each move the cost somewhere different. A balanced search tree keeps every operation logarithmic; a hash table makes equality lookup and insertion expected constant and gives up order entirely; a skip list is a sorted linked list with logarithmic shortcuts, whose guarantees are probabilistic and whose code is short.

  • The binary search tree is binary search made into a structure: each node is a midpoint, its subtrees are the two halves, and an insertion is a search that ends by hanging a new leaf where the search failed. Unbalanced, it degenerates to a linked list on sorted insertions — exactly the sorted-input failure of first-pivot quicksort, and for the same reason: a quicksort's recursion tree with first-element pivots is the BST built by inserting the elements in order. Balancing (rotations, colour or height invariants) restores O(log n) for every operation, and the B-tree generalisation with wide nodes is what every database index uses because it matches the block size of the storage. The structure and its balancing belong to Trees, BSTs & Graph Algorithms.
  • The hash table abandons order to buy constant time. It answers "is x here" and "insert x" in O(1) expected under a uniformity hypothesis on the hash function, and it cannot answer "what is the smallest key above x", "how many keys are in [a, b]", or "give me the keys in order" without a full scan — Hash Tables, §26, is precisely the list of what hashing cannot do, and every item on it is a query this page's sorted array answers in a logarithm. The rule is therefore a single question: does anything ask about the order or relationship of two keys? No → hash. Yes → something sorted.
  • The skip list is a sorted linked list in which each node is promoted to a higher "express" level with probability ½, so that a search starts at the top level, skips forward in large steps, and drops a level whenever the next key is too big — a randomised binary search over a list. It supports every ordered query of a balanced tree with expected logarithmic cost and no rotations, at the price that its bounds hold in expectation over its own coin flips rather than in the worst case. It is the structure of choice when concurrent insertion matters, because its local pointer updates are far easier to make lock-free than a tree's rotations.
Sorting's place in this picture. A sorted array is the static ordered dictionary — build it once with a sort, query it with §26–§27, rebuild it when the data changes. The dynamic structures exist because rebuilding costs Θ(n log n) and a single insertion should not. When updates are batched — a nightly load, a bulk import — the static answer wins again: sort the batch, merge it into the array in Θ(n) (§09), and keep the density and the sequential access that no tree can offer.

29 External sorting and the k-way merge

When the data does not fit in memory the cost model changes: the unit of work is no longer a comparison but a block transfer between disk and memory, and an algorithm is judged by how many times it reads and writes the whole file. Mergesort is the only n log n sort whose access pattern is purely sequential single-direction streams (a partition scans sequentially too, but from both ends of one range), and its external form — sort memory-sized runs, then merge them k at a time with a heap — reads the file only 1 + ceil(log_k(runs)) times. With realistic memory sizes that is two passes for anything that fits on a disk.

Why mergesort and not quicksort

Quicksort's partition is also sequential, and a partition-based external sort (distribution sort: choose k − 1 splitters, scatter the file into k ranges, recurse) exists and achieves the same bound — it is the external form of bucket sort (§22), and its splitters are chosen by sampling for exactly the reason §22 gives. Mergesort is preferred in practice because its runs are formed from whatever fits in memory with no dependence on the data's distribution, because a merge pass's output is written strictly sequentially while a distribution pass's output is written to k streams at once, and because the run-formation phase can produce runs longer than memory by replacement selection — keep a heap of M records, output the minimum that is still ≥ the last record written, and refill from the input — which on random data yields runs of average length 2M and on nearly-sorted data yields runs that are essentially the whole file. Heapsort, whose every step is a random access, is not a candidate at all outside memory, and inside memory it is the run-formation sort of choice only because it is the heap that replacement selection already needs.

The same picture, one level up

  • Distributed sorting is external sorting with machines for blocks: each node sorts its shard, a sample of the data picks splitters, every node scatters its shard by splitter range, and every node merges what it receives. The transfer count is the network cost, and the analysis above applies with "block" replaced by "message".
  • Cache-aware sorting is external sorting one level down: a sort that fits the working set of each phase into the cache — runs of cache size, then k-way merges with k chosen so the buffers fit — beats a cache-oblivious n log n sort on large in-memory arrays by the same argument, with cache lines as blocks. The memory hierarchy is the reason mergesort's "extra buffer" is an asset rather than a cost.
  • Merge joins in a database are the merge step alone: two inputs sorted on the join key, one sequential pass, and the sort that produced them is the external sort above. When one input is already sorted (an index scan), only the other is sorted; when both are, the join is linear.
The rule at every scale. When the cost is moving data between two levels of memory rather than comparing it, the winning algorithm is the one whose passes are sequential and whose pass count is logarithmic in the ratio of the two levels' sizes. That is mergesort, at every level from registers to a cluster.

"Quicksort is fast because it is in place"It is fast because its inner loop is a sequential scan against a register-resident pivot, with one branch that can be made branchless. Being in place is a memory property with no bearing on speed; mergesort's buffer gives it the best access pattern of the three.§11, §17, §19
"Mergesort's extra memory makes it slow"Its access pattern is purely sequential, which is why it is the external sort and the cache-friendly sort. Its cost relative to quicksort is the copy, not the buffer.§09, §29
"Radix sort is always faster than comparison sorting for integers"Only when the key width in digits is smaller than log n comparison levels, and only if its scattered writes do not cost more than they save. 64-bit keys at n = 1000 are level; 32-bit keys at a million are a clear win.§21
"Binary search is always faster than linear search"Below a small, platform-dependent n, a linear scan wins on wall-clock time — predictable branches, prefetching, vectorisation — despite more comparisons. Library searches and merges switch to scanning at that size.§25
"Recursing on the smaller part first makes quicksort safe"It bounds the stack to floor(log₂n) + 1. The running time on sorted input with a bad pivot is still n(n − 1)/2; only the pivot rule or a depth limit fixes that.§16
"Median-of-three fixes the worst case"It fixes sorted and reversed input and improves the average by about 14%. It has its own killer — the organ-pipe input costs it Θ(n²), measured at depth 255 for n = 1024. Only a random pivot or a depth limit removes the ordering worst case — and neither helps Lomuto on equal keys; that needs §15's partition.§14
"The cutoff is 16" (or any number)The cutoff is a measured constant of the implementation. Here the Hoare hybrid's optimum is 8–16 and the Lomuto hybrid gains nothing; libraries choose theirs by benchmark, and quoting one as a fact about the algorithm is a category error.§17, §24
"Sort, then binary search, is always better than a hash table"For equality lookups a hash table is expected O(1). The sorted array wins on predecessor, range, rank and ordered iteration — the queries hashing cannot do — and on memory.§28
"The pivot goes at index j" (Hoare)Hoare's partition returns a split point, not the pivot's index; the pivot may be on either side. Recursing on [lo, j) and [j + 1, hi) loses an element; the correct calls are [lo, j + 1) and [j + 1, hi).§13
"Interpolation search is O(log log n)"On uniformly distributed keys. On exponentially spaced keys it is linear — measured at 13 596 probes for n = 65 536 against binary search's 13.8.§27
"lower_bound stops when it finds x"It cannot: finding a copy proves nothing about the first. Every boundary search runs to lo = hi, always floor(log₂n) + 1 probes or fewer, no early exit.§27
