27 Searching: linear search, and when it wins

Searching is locating a key, and the simplest search is the only one that works on unordered data: look at every element until the key turns up, or the elements run out. It is Θ(n) in the worst case and on average, it needs no precondition, no extra memory and no structure, and on small arrays it is faster than anything cleverer for reasons the operation count does not show. The sections that follow are about what it costs to do better — sorting first, or maintaining a structure — and linear search is the baseline every one of them has to beat.

Why the linear scan wins on small arrays

A linear scan over a few dozen contiguous elements is a loop with a predictable branch and a sequential memory pattern — the processor prefetches the next line, the branch predictor learns "not yet", and the compiler may vectorise the comparison so that several elements are tested per instruction. A binary search over the same elements makes a handful of unpredictable branches, each of which is mispredicted about half the time, and each probe lands on an address the previous one did not predict. For small n the constant costs of the four or five mispredictions exceed the cost of scanning everything, and the linear scan is faster in wall-clock time despite doing several times the comparisons. Where the crossover sits depends on the element size, the key type and the machine, and this page does not quote a number for it — it is measured per platform, and the honest statement is only its direction: below some small n, scan; above it, halve. Library implementations of binary search and of the merge step in stable sorts (§26) routinely switch to a linear scan when the range shrinks below such a threshold, for exactly this reason. The same argument, with the same conclusion, is why insertion sort finishes every fast sort (§04, §19).

What linear search is really for

  • One-off lookups in unsorted data. A single query does not justify a Θ(n log n) sort or the memory of a hash table; q queries do once q exceeds roughly log n (§02).
  • Queries that are not equality. "The first element satisfying a predicate", "the element with the maximum score", "any element in a range" — over unsorted data all of these are a scan, and a scan with a predicate is the only general tool.
  • The bottom of every hybrid. The last few elements of a binary search, a bucket in a hash table, a leaf in a B-tree: each ends in a short linear scan, because at that size nothing beats it.
The baseline, stated once. A search that does not exploit order or hashing costs Θ(n) per query. Every faster search on this page pays for its speed with a precondition — sortedness, a hash function, a tree — and the precondition's cost is part of the search's cost.

28 Binary search: the loop, the invariant, the two bugs, and one convention

On a sorted array one comparison against the middle element eliminates half the candidates, and repeating that gives floor(log₂n) + 1 probes in the worst case. That much everyone knows; what makes binary search famous is how often it is written wrong. The loop below is correct; its invariant is the reason; and the two ways it is usually broken — a range that fails to shrink, and a midpoint that overflows — are each one character. This page uses the half-open convention [lo, hi) throughout: lo is the first candidate, hi is one past the last, and the range is empty exactly when lo = hi.

the loop — half-open [lo, hi), membershiplo = 0; hi = n ← n candidates: indices 0 .. n − 1 while lo < hi: mid = lo + floor((hi − lo) / 2) ← never (lo + hi)/2: see bug 2 if A[mid] < x: lo = mid + 1 ← A[mid] and everything left of it are too small elif A[mid] > x: hi = mid ← A[mid] and everything right of it are too big else: return mid return NOT FOUND ← lo = hi: no candidates remain; lo is the insertion point the invariantif x occurs in A at all, it occurs in A[lo .. hi) — true initially ([0, n) is everything), preserved by each branch, and at exit with lo = hi it says x occurs in an EMPTY range: absent termination and costlo ≤ mid < hi always (floor of the half of a positive length), so lo = mid + 1 > lo and hi = mid < hi: the range STRICTLY shrinks range sizes: n → at most floor(n/2) → … → 1 → 0: at most floor(log₂n) + 1 probes (n = 0: 0 probes; n = 1: 1; n = 2: 2; n = 3: 2) successful search averages about log₂n − 1 probes; unsuccessful about log₂n: the keys that are NOT there cost the most THEOREM (the precondition, stated). The default replays the successful trace — index 7 in 3 probes — and the readout runs a linear scan on the same input as an independent check of the answer. The absent-key presets are where the loop earns its keep: each ends with lo = hi, the invariant then says "if 40 is anywhere, it is in an empty range", and lo is left pointing at the insertion point — a fact the boundary variants of §29 turn into the primary result rather than a by-product.

The two bugs

  • Bug 1 — the range that does not shrink. Write lo = mid instead of lo = mid + 1. On most ranges nothing goes wrong — from [3, 5), mid = 3 + floor(2/2) = 4, and if A[4] < x then lo = 4 still shrinks the range to [4, 5) — which is exactly why the bug survives testing. Take [3, 4): mid = 3; if A[3] < x then lo = mid = 3, and the range [3, 4) is unchanged forever. The measure hi − lo failed to decrease on a range of size 1, which is the last size any test reaches, and the loop spins. The same bug in the closed convention is hi = mid (instead of mid − 1) on a ONE-element range, or lo = mid on a two-element one — with mid = lo + floor((hi − lo)/2), mid equals lo on both sizes and equals hi only on size 1. The cure is the termination argument above: check that both branches strictly shrink the range at every size, including 1 and 2.
  • Bug 2 — the midpoint that overflows. (lo + hi) / 2 is wrong whenever lo + hi can exceed the integer type's range — in a 32-bit index over an array of more than about a billion elements the sum wraps negative, mid is negative, and the read is out of bounds. lo + (hi − lo) / 2 computes the same value and cannot overflow, because hi − lo ≤ hi. In languages with arbitrary-precision integers the bug is unreachable, but the habit is worth keeping: the form that is correct everywhere costs nothing.

The convention, and why one is chosen

Closed [lo, hi] and half-open [lo, hi) are both correct when written consistently: closed initialises hi = n − 1, loops while lo ≤ hi, and updates with hi = mid − 1; half-open initialises hi = n, loops while lo < hi, and updates with hi = mid. Arrays & Strings, §16, writes the closed form. This page commits to the half-open form for three reasons: the empty range is representable without a negative index (lo = hi, never hi = −1); the terminating value of lo is directly the insertion point and the boundary variants (§29) need no adjustment; and hi − lo is the number of candidates, which makes the termination argument a sentence. Mixing the two — hi = n with lo ≤ hi, or hi = mid with hi = n − 1 — is the third bug, and it is the one that reads out of bounds or misses the last element only on some inputs. Pick one, and write every search the same way.

29 The variants that answer real questions: first and last occurrence, lower and upper bound, predicates, exponential and interpolation search

"Is x present?" is rarely the question. The questions are "where would x go?", "how many copies of x are there?", "what is the first element at least x?", "what is the largest k such that some property holds?" — and all of them are one loop, the boundary form of binary search, which does not stop when it sees x but continues until it has located the exact edge between the elements that satisfy a predicate and the ones that do not. Membership is a special case of it; the boundary form is the one to memorise.

the boundary form — the first index in [0, n] at which a MONOTONE predicate becomes truelo = 0; hi = n while lo < hi: mid = lo + floor((hi − lo) / 2) if P(A[mid]) is false: lo = mid + 1 ← mid and everything left of it fail else: hi = mid ← mid could be the first success: keep it return lo ← in 0 .. n; n means "no element satisfies P" invariant: every index < lo fails P; every index ≥ hi satisfies P; the answer is in [lo, hi] hypothesis: P is MONOTONE on the array — false, false, …, false, true, true, …, true. Sortedness makes "A[i] ≥ x" monotone. cost: always floor(log₂n) + 1 probes or fewer, and never an early exit — the loop must reach lo = hi to know it has the FIRST true the two named instanceslower_bound(x) = first i with A[i] ≥ x (P = "A[i] ≥ x") = the insertion point that keeps x BEFORE its equals upper_bound(x) = first i with A[i] > x (P = "A[i] > x") = the insertion point that keeps x AFTER its equals count of x = upper_bound(x) − lower_bound(x) first occurrence = lower_bound(x), valid iff lower_bound(x) < n and A[lower_bound(x)] = x last occurrence = upper_bound(x) − 1, valid under the same test membership = lower_bound(x) < n and A[lower_bound(x)] = x — the membership loop of §28 is this plus an early exit "binary search on the answer" — the same loop over a VIRTUAL arrayany monotone predicate on the integers 0 .. n can be searched: "can the job be finished with capacity k?", "is the k-th power ≤ N?", "does a bound of k suffice?" — P(k) is computed, not read; cost = (log₂ of the range) × (cost of one evaluation of P) the array is never built. The only requirement is monotonicity, and it must be PROVED, not assumed.

The default replays the lower_bound(2) trace: index 1 in 4 probes, with upper_bound(2) = 4 computed alongside, so the count is 3 and both are confirmed by a linear scan. Notice that lower_bound did not stop at probe 2, when it first saw a 2 — it had found a 2, not the first one, and continued left until the range was empty. That is the difference between the membership loop and the boundary loop, and it is why the boundary loop's cost is the same on every input: no early exit exists, because no single probe can prove that it has found the edge.

Exponential search: when the array is unbounded or the answer is near the front

If the array's length is unknown, or infinite in effect (a stream that can be probed at any index), or the answer is expected close to the start, probe indices 1, 2, 4, 8, … until the key is exceeded, then binary-search the last interval [2ᵏ⁻¹, 2ᵏ] (closed at the top — the probe that stopped the doubling may itself be the key). The cost is O(log i) where i is the answer's position — about 2·log₂i probes, one for the doubling and one for the search — which is better than log₂n whenever i ≪ n and never worse by more than a factor of two. Its main use is inside merging: when one run keeps winning a merge, the merge switches to galloping — an exponential search along the winning run for how far it wins — and copies that stretch in one move instead of one element per comparison. This is what makes the merge-based library sorts of §26 near-linear on inputs made of a few long runs.

Linear, binary, exponential and interpolation search — mean probes for a present key, measured from n = 16 to 65 536, on uniform and on skewed keys log–log: the reference curves are log₂n and log₂log₂n; switch the key distribution to watch interpolation search lose its hypothesis and its logarithm

On uniform keys at n = 65 536 the mean cost of finding a present key is 33 648 probes by linear scan, 14.86 by binary search, 29.43 by exponential search from the front, and 3.70 by interpolation search — against log₂n = 16 and log₂log₂n = 4.00, so interpolation search on the input it was designed for is four times cheaper than binary search, and the worst single search over the four hundred sampled needed 8 probes. Switch the keys to the skewed distribution and interpolation search averages 241 probes at the same n, with a worst of 3 436; on exponentially spaced keys it averages 13 596 — a linear scan with extra arithmetic — while binary search, which never looked at the values, is essentially unchanged at 13.8 against 14.86 — the small difference is that exponentially spaced integer keys collapse into duplicates at the low end, which lets the membership loop exit early. Every search's result is cross-checked against the target it was given. The lesson is §24's in a different costume: an algorithm that exploits a distribution is only as fast as the distribution is true, and a binary search that exploits only the order is the safe default.

What to write, in order of preference. The boundary loop with a monotone predicate, from which membership, insertion point, count, first and last occurrence and "search on the answer" all follow; exponential search when the answer is near the front or the end is unknown; interpolation search only when the keys are known to be near-uniform and the probes are expensive enough (a disk, a network) for log log n against log n to matter.

30 Searching beyond arrays: what a search tree, a hash table and a skip list each buy

A sorted array answers every ordered query in O(log n) and costs Θ(n) per insertion. That trade is right for read-mostly data and wrong for everything else, and the three classical alternatives each move the cost somewhere different. A balanced search tree keeps every operation logarithmic; a hash table makes equality lookup and insertion expected constant and gives up order entirely; a skip list is a sorted linked list with logarithmic shortcuts, whose guarantees are probabilistic and whose code is short.

  • The binary search tree is binary search made into a structure: each node is a midpoint, its subtrees are the two halves, and an insertion is a search that ends by hanging a new leaf where the search failed. Unbalanced, it degenerates to a linked list on sorted insertions — exactly the sorted-input failure of first-pivot quicksort, and for the same reason: a quicksort's recursion tree with first-element pivots is the BST built by inserting the elements in order. Balancing (rotations, colour or height invariants) restores O(log n) for every operation, and the B-tree generalisation with wide nodes is what every database index uses because it matches the block size of the storage. The structure and its balancing belong to Trees, BSTs & Graph Algorithms.
  • The hash table abandons order to buy constant time. It answers "is x here" and "insert x" in O(1) expected under a uniformity hypothesis on the hash function, and it cannot answer "what is the smallest key above x", "how many keys are in [a, b]", or "give me the keys in order" without a full scan — Hash Tables, §26, is precisely the list of what hashing cannot do, and every item on it is a query this page's sorted array answers in a logarithm. The rule is therefore a single question: does anything ask about the order or relationship of two keys? No → hash. Yes → something sorted.
  • The skip list is a sorted linked list in which each node is promoted to a higher "express" level with probability ½, so that a search starts at the top level, skips forward in large steps, and drops a level whenever the next key is too big — a randomised binary search over a list. It supports every ordered query of a balanced tree with expected logarithmic cost and no rotations, at the price that its bounds hold in expectation over its own coin flips rather than in the worst case. It is the structure of choice when concurrent insertion matters, because its local pointer updates are far easier to make lock-free than a tree's rotations.
Sorting's place in this picture. A sorted array is the static ordered dictionary — build it once with a sort, query it with §28–§29, rebuild it when the data changes. The dynamic structures exist because rebuilding costs Θ(n log n) and a single insertion should not. When updates are batched — a nightly load, a bulk import — the static answer wins again: sort the batch, merge it into the array in Θ(n) (§11), and keep the density and the sequential access that no tree can offer.

31 External sorting and the k-way merge

When the data does not fit in memory the cost model changes: the unit of work is no longer a comparison but a block transfer between disk and memory, and an algorithm is judged by how many times it reads and writes the whole file. Mergesort is the only n log n sort whose access pattern is purely sequential single-direction streams (a partition scans sequentially too, but from both ends of one range), and its external form — sort memory-sized runs, then merge them k at a time with a heap — reads the file only 1 + ceil(log_k(runs)) times. With realistic memory sizes that is two passes for anything that fits on a disk.

the two phasesRUN FORMATION read M records at a time (M = what fits in memory), sort them in memory with any §11–§21 sort, write each sorted run ⇒ R = ceil(N / M) runs, one read and one write of the whole file MERGING merge k runs at once: keep the front record of each run in a min-heap of size k; repeatedly pop the minimum, write it, and push the next record from the run it came from ⇒ each pass reduces the number of runs by a factor of k; ceil(log_k R) passes, each one read + one write of the file THEOREM (cost in block transfers). Worked: replacement selection with M = 3, and where the 2M comes from

Input stream 12, 5, 31, 8, 27, 3, 19, 44, 1, 26, memory for three records. Load the first three into a min-heap. Repeatedly emit the minimum, read the next record, and — this is the whole trick — put it in the heap if it is ≥ the record just written (it can still join the current run) or freeze it for the next run if it is smaller. Frozen records are tagged with the next run number, so the heap orders by (run, key) and the current run is always drained first:

Why mergesort and not quicksort

Quicksort's partition is also sequential, and a partition-based external sort (distribution sort: choose k − 1 splitters, scatter the file into k ranges, recurse) exists and achieves the same bound — it is the external form of bucket sort (§24), and its splitters are chosen by sampling for exactly the reason §24 gives. Mergesort is preferred in practice because its runs are formed from whatever fits in memory with no dependence on the data's distribution, because a merge pass's output is written strictly sequentially while a distribution pass's output is written to k streams at once, and because the run-formation phase can produce runs longer than memory by replacement selection — keep a heap of M records, output the minimum that is still ≥ the last record written, and refill from the input — which on random data yields runs of average length 2M and on nearly-sorted data yields runs that are essentially the whole file. Heapsort, whose every step is a random access, is not a candidate at all outside memory, and inside memory it is the run-formation sort of choice only because it is the heap that replacement selection already needs.

The same picture, one level up

  • Distributed sorting is external sorting with machines for blocks: each node sorts its shard, a sample of the data picks splitters, every node scatters its shard by splitter range, and every node merges what it receives. The transfer count is the network cost, and the analysis above applies with "block" replaced by "message".
  • Cache-aware sorting is external sorting one level down: a sort that fits the working set of each phase into the cache — runs of cache size, then k-way merges with k chosen so the buffers fit — beats a cache-oblivious n log n sort on large in-memory arrays by the same argument, with cache lines as blocks. The memory hierarchy is the reason mergesort's "extra buffer" is an asset rather than a cost.
  • Merge joins in a database are the merge step alone: two inputs sorted on the join key, one sequential pass, and the sort that produced them is the external sort above. When one input is already sorted (an index scan), only the other is sorted; when both are, the join is linear.
The rule at every scale. When the cost is moving data between two levels of memory rather than comparing it, the winning algorithm is the one whose passes are sequential and whose pass count is logarithmic in the ratio of the two levels' sizes. That is mergesort, at every level from registers to a cluster.
