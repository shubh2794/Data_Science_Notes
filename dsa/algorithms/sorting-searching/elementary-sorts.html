03 The loop-invariant discipline, on insertion sort

Insertion sort is how a hand sorts cards: keep the left part of the array sorted, take the next unsorted element, and slide it leftward past every larger element until it sits in place. It is the first sort to learn not because it is fast but because its correctness proof is the template for every other loop on this page — a property that holds before the loop, is preserved by each pass, and at exit says exactly what you wanted.

the algorithmfor i = 1 .. n − 1: v = a[i]; j = i while j > 0 and a[j−1] > v: ← strict >: an equal key is NOT passed, so the sort is stable a[j] = a[j−1]; j = j − 1 a[j] = v the loop invariantat the top of the outer loop, for each i: a[0 .. i) is SORTED and is a PERMUTATION of the original a[0 .. i) the three obligationsINITIALIZATION i = 1: a[0 .. 1) is one element — sorted, and trivially the original a[0..1) MAINTENANCE the inner loop shifts a[j−1] right while it exceeds v, then drops v at j; elements a[0..j) are ≤ v (the shift stopped), a[j+1..i] were > v and are in order ⇒ a[0..i] sorted nothing was created or lost: v was held aside and put back ⇒ still a permutation TERMINATION the loop ends with i = n, so a[0 .. n) is sorted and a permutation of the input — the specification

Worked: the invariant checked after every pass

Two things in that trace are worth naming. First, every shift removes exactly one inversion — v passes one larger element — so the number of shifts equals the number of inversions, no matter what order the input is in. Second, an insertion ends in one of two ways: a failing comparison (an element that is not greater than v stops it) or the front of the array (j = 0, no comparison made). So the comparison count is I + (n − 1) − z where z counts the insertions that ran to the front; the figure below computes I and z directly from the input and checks that identity against the counter on every run.

Selection sort under the same controls does 276 comparisons on every input, which is the whole of §05 in one number.

Why the invariant is the proof, and why it is also the design

Notice what the invariant does not say. It does not say a[0..i) contains the i smallest elements of the array — it does not, and the trace shows it (after i = 3 the prefix is [2, 4, 5, 6] while 1 is still to come). That weaker statement is exactly what selection sort's invariant does say (§05), and the difference is the difference between the two algorithms: selection sort's prefix is final, insertion sort's is merely ordered. Reading the invariant tells you what the loop has committed to, and therefore what it can and cannot exploit. Insertion sort has committed to nothing about the unsorted suffix, which is why it can be online — new elements simply extend the suffix — and why its cost depends on how far each element has to travel rather than on n alone.

The habit. Before analysing any sort on this page, write its invariant in one sentence. Every cost bound below is derived by asking "how much work does one pass do to restore the invariant?", and every subtle bug — the ≤ that breaks stability, the partition that loses an element, the merge that reads past a run — is a pass that fails to restore it.

04 Insertion sort's cost: inversions, adaptivity, and the binary-insertion trap

§03 showed that every shift removes exactly one inversion. That single fact gives insertion sort's cost exactly, on every input, in terms of one number: I, the count of pairs that are out of order. Comparisons lie between I and I + n − 1; moves are 2(n − 1) + I; and since I ranges from 0 (sorted) to n(n − 1)/2 (reversed), the best, worst and average cases are all read off the distribution of I.

The average-case derivation is worth reading because it is the pattern for every average case on this page: fix the probability model (each of the n! permutations equally likely), decompose the cost into a sum over one element at a time, and use linearity of expectation so that each term can be computed in isolation. It rests on a hypothesis — uniformly random permutation, distinct keys — and it is only as true as that hypothesis. On inputs with structure the formula says nothing; the exact identity above still holds and the count is whatever I is.

The violet dots are the point of the figure: binary insertion sort, which finds the insertion point by binary search instead of a linear scan, makes about 1 550–1 720 comparisons whatever the disorder, under its bound ∑ ceil(log₂(i + 1)) = 1 793 — and its moves are identical to linear insertion's, because it still has to shift every element the inserted key passes. It saves comparisons, not time: the running time is still Θ(n + I) in moves, and Θ(n²) on a random input.

What "adaptive" means here, precisely

Insertion sort is adaptive in the inversion measure (inversions, runs and the longest sorted subsequence are the standard presortedness measures, and "adaptive" is always relative to one of them): its cost is Θ(n + I), so an input with O(n) inversions — a few misplaced elements, a sorted array with a block appended, the output of a quicksort that stopped at small subarrays (§19) — is sorted in linear time. It is not adaptive in every measure of order. An array consisting of the sorted second half followed by the sorted first half has only two runs (natural mergesort sorts it in one merge, §12) but n²/4 inversions, and insertion sort is quadratic on it. The measure matters; "insertion sort is fast on nearly sorted input" is true only when "nearly sorted" means "few inversions".

Why it survives inside every fast sort. On tiny arrays the constant matters more than the exponent, and insertion sort's constant is the smallest of any sort: no recursion, no buffer, one tight loop over contiguous memory that the branch predictor learns quickly. That is why quicksort (§19), mergesort hybrids and every library sort (§26) hand subarrays below some cutoff to insertion sort, and why the cutoff is measured rather than derived — it is the point where c₁·n² crosses c₂·n log n for two constants nobody can compute from first principles. The measured sweep in §19 finds it between 8 and 16 elements for the Hoare-partition quicksort on this page — and finds that the Lomuto version gains nothing from it, which is its own lesson about constants.

05 Selection sort, and why it is not stable

Selection sort turns the invariant around: instead of keeping a prefix ordered, keep a prefix final. At the top of iteration i, a[0..i) holds the i smallest elements, in order, in their final positions. Each pass scans the entire unsorted suffix for its minimum and swaps it into position i. The scan cannot be shortened by any property of the input — to know the minimum you must look at every candidate — so the comparison count is the same on every input, and it is quadratic.

Hypothesis: none — any input.comparisons = ∑ᵢ₌₀ⁿ⁻² (n − 1 − i) = n(n − 1)/2 best = worst = average swaps ≤ n − 1; moves ≤ 3(n − 1) the smallest move count of any comparison sort in this section measured (§03's figure, n = 24)random, sorted, reversed, nearly sorted: 276 comparisons every time; swaps 22 · 0 · 12 · 3

The instability, on three elements

Stability fails the moment a swap carries an element past an equal one. Take two records with key 2, tagged 2a and 2b by input order, and a 1 after them: [2a, 2b, 1]. Pass 0 finds the minimum, 1, at index 2 and swaps it with index 0 — and the element that was at index 0, 2a, lands at index 2, behind 2b. Pass 1 compares 2b with 2a, finds neither smaller, swaps nothing. Output: [1, 2b, 2a]. The two equal keys have exchanged their relative order, on a three-element input, with one swap. The figure in §03 tests this live on 300 random arrays of tagged records: selection sort violates stability on 300 of 300 runs at n = 40 with five distinct keys; insertion, binary insertion and bubble sort on none; shellsort on all 300, for the reason §07 gives.

the tracestart [2a, 2b, 1] pass 0 min of a[0..3) is 1 at index 2; swap a[0] ↔ a[2] → [1, 2b, 2a] 2a jumped over 2b pass 1 min of a[1..3) is 2b at index 1 (2a is not < 2b); no swap → [1, 2b, 2a] output [1, 2b, 2a] — sorted, NOT stable a stable variant exists, at a priceinstead of swapping, ROTATE a[i..m] right by one (shift the block, drop the minimum at i): stable, but Θ(n²) moves — the one property selection sort had over insertion sort, its O(n) moves, is exactly what stability costs

When the minimal move count matters

Selection sort's only genuine advantage is that it writes to the array at most 3(n − 1) times. Where a write is expensive — flash memory with limited erase cycles, records so large that a move dominates a comparison by orders of magnitude, a sort performed by physically moving objects — that can be decisive, and selection sort or its cycle-sort relative (which achieves the theoretical minimum number of writes, §08) is the right tool. Everywhere else it is dominated: insertion sort does no more comparisons on any input, far fewer on most, is stable, is online, and is adaptive. The sort's real legacy is its idea: "repeatedly extract the minimum of what remains" is heapsort with a linear-time extract. Replace the Θ(n) scan with a heap's O(log n) extract-min and the same invariant gives O(n log n) — which is precisely how Heaps & Priority Queues, §12, introduces heapsort.

06 Bubble sort, the early-exit flag, and why it is dominated

Bubble sort sweeps left to right, swapping any adjacent pair that is out of order; after pass k the k largest elements have "bubbled" to their final places at the right end. Its invariant is selection sort's, mirrored: after k passes, a[n−k..n) holds the k largest keys in final position. It is the sort everyone learns first and the one nobody should use, and the reason is not the exponent — insertion sort has the same one — but a constant that is worse in every column.

the algorithm, with the flagfor pass = 0 .. n − 2: swapped = false for j = 0 .. n − 2 − pass: if a[j] > a[j+1]: swap a[j], a[j+1]; swapped = true if not swapped: break ← the early exit: a pass with no swap proves the array sorted THEOREM (cost). Hypothesis: adjacent swaps only.swaps = I exactly — an adjacent swap of an out-of-order pair removes exactly one inversion and creates none comparisons = ∑ over the passes actually run of (n − 1 − pass) ≤ n(n − 1)/2 passes = min(n − 1, 1 + max over elements of the distance it must travel LEFT) ← each pass moves an element at most one step left; the +1 is the swap-free pass that proves the array sorted, skipped when the loop bound n − 1 is reached first measured, n = 64sorted: 1 pass, 63 comparisons, 0 swaps ← the flag's best case, Θ(n) reversed: 63 passes, 2016 comparisons, 2016 swaps, 6048 moves largest key first: 2 passes, 125 comparisons, 63 swaps ← a large key travels right in ONE pass smallest key last: 63 passes, 2016 comparisons, 63 swaps ← a small key travels left ONE STEP per pass random (mean of 1000): 1975 comparisons, 1006 swaps vs insertion sort's 1065 comparisons, 1132 moves on the same inputs

The asymmetry in the last block is the whole indictment. A large element out of place is fixed in one pass, because the sweep carries it rightward as far as it needs to go. A small element out of place moves exactly one position left per pass — the sweep goes the other way — so a single misplaced minimum at the far end forces n − 1 full passes and n(n − 1)/2 comparisons to perform n − 1 swaps. Insertion sort on the same input does 2n − 3 comparisons (n − 2 failing tests, then one scan of n − 1 for the misplaced minimum). The early-exit flag rescues only the already-sorted case and inputs whose disorder happens to be "large elements too far left"; it does nothing for the reverse, and on a random permutation the measured comparison count is about twice insertion sort's for the same number of inversions removed, because insertion sort stops each scan at the first non-greater element while bubble sort's pass always runs to the end.

Cocktail shaker and the other patches

Alternating the sweep direction (cocktail shaker sort) fixes the small-element asymmetry — a pass in each direction moves a misplaced element to its place whichever way it must go — and tracking the position of the last swap lets each pass stop early at the boundary of the already-final suffix. Both are real improvements and both leave the algorithm dominated by insertion sort: the same I swaps, at least as many comparisons, no online property, and an inner loop that swaps (three moves) where insertion sort shifts (one move). The reason bubble sort persists in curricula is that it is the easiest sort to see, which is a virtue of a first example and not of an algorithm. Use §03's figure to watch it once, then never write it.

The one thing it teaches well. "One adjacent swap removes exactly one inversion" is a genuinely useful lemma — it proves that any sort restricted to adjacent swaps needs at least I swaps, hence Θ(n²) on average, and it is why shellsort (§07) exists: to beat the quadratic bound you must exchange elements that are far apart.

07 Shellsort: gap sequences, and what is and is not known

Every sort in §03–§06 moves elements one position at a time, and §06's lemma says that costs I exchanges, which on random input is n²/4. Shellsort's idea is to let elements jump. For a decreasing sequence of gaps h ending in 1, insertion-sort each of the h interleaved subsequences a[k], a[k+h], a[k+2h], …; the array is then "h-sorted", and a later, smaller gap inherits a nearly ordered input. The final pass with h = 1 is plain insertion sort, but by then few inversions remain. The algorithm is four lines; its analysis is one of the oldest open problems in the subject.

the algorithmfor each gap h in the sequence (largest first, last = 1): for i = h .. n − 1: v = a[i]; j = i while j ≥ h and a[j − h] > v: a[j] = a[j − h]; j = j − h a[j] = v the two facts that make it work1. after the h pass the array is h-SORTED: every subsequence with stride h is in order 2. an array that is h-sorted and is then k-sorted STAYS h-sorted (the earlier work is not undone) ⇒ each pass inherits the order of all previous passes; the final h = 1 pass sees few inversions what is known, by gap sequence — WORST-case bounds, each proved for its own sequence onlyfloor(n/2ᵏ): n/2, n/4, …, 1 Θ(n²) the original sequence; all gaps even until 1, so evens and odds never mix 2ᵏ − 1: 1, 3, 7, 15, 31, … Θ(n^(3/2)) (3ᵏ − 1)/2: 1, 4, 13, 40, 121, … Θ(n^(3/2)) — the sequence §03's figure and this section's default use 2ᵃ·3ᵇ: 1, 2, 3, 4, 6, 8, 9, … Θ(n log² n) best proved asymptotic bound; too many gaps to be fast in practice 1, 4, 10, 23, 57, 132, 301, 701, … empirically the fastest known small-n sequence; no proved bound ANY sequence: Ω(n · (log n / log log n)²) — a lower bound for every gap sequence, so shellsort is NOT O(n log n) what is NOT knownthe average-case running time for essentially any useful sequence; whether any sequence achieves the lower bound; the best sequence

Fact 2 is the non-obvious one and the reason the method works at all: a pass with a smaller gap does not destroy the order created by a larger one. The proof is a short exchange argument and is the only piece of theory the practitioner needs. Sketch: suppose the array is h-sorted and a k-pass then moves elements; a k-pass is an insertion sort on each k-chain, and an insertion sort only ever exchanges an adjacent pair of its chain that is out of order. Consider any two positions i < i + h after the k-pass, and the elements a, b that were exchanged to put them there: they came from positions i − k, i + h − k (or the same positions), which were h-ordered before the pass, and an exchange that repairs a k-inversion between two elements cannot create an h-inversion, because the two elements it moves are each moving toward a position whose h-partner was already on the correct side of both. Chase the two interleavings of the chains and every case reduces to that. Everything else about shellsort is empirical, and the figure treats it as such — it measures comparison counts across n for four gap sequences and reports the fitted exponent of each, which is a description of the measurements and not a theorem.

Where it is used, and why it is not stable

Shellsort is the sort of choice when code size matters more than the last factor of two — embedded systems, bootstrap loaders, anywhere a recursive n log n sort is unwelcome — because it is insertion sort with one extra loop, uses no stack and no buffer, and is respectable up to tens of thousands of elements. It is not stable: an h-pass with h > 1 moves an element past elements it is never compared with, so two equal keys in different strided subsequences can cross. The §01 vocabulary check for it therefore reads: in-place yes, stable no, adaptive somewhat (it is insertion sort at the end), online no. Its real intellectual contribution is the observation that a sequence of passes that each leave a partial order intact can add up to a full sort — the same design as LSD radix sort's digit passes (§23), where the "partial order" preserved is the ordering by lower digits and the tool that preserves it is stability.

08 Cycle sort: the fewest writes, by rotating the permutation's cycles

Every sort so far was priced in comparisons, with moves as a second column. Cycle sort optimises the second column to its floor. It writes each element directly into its final slot, at most once, so the number of array writes equals the number of slots that do not already hold their final key — the least any sort can do. It pays for this with Θ(n²) comparisons on every input, which is the right trade only when a write costs far more than a read.

the algorithm — a[0..cs) is final at the top of each outer iterationfor cs = 0 .. n − 2: item = a[cs]; pos = cs + #{ i > cs : a[i] < item } ← item's final slot: count the smaller keys still unplaced if pos = cs: continue ← already home: NO write while a[pos] = item: pos = pos + 1 ← skip slots already holding an equal key (duplicates) swap item ↔ a[pos] ← ONE write: item lands in its final slot; pick up the evicted key while pos ≠ cs: ← carry the evicted key to ITS slot, and so on round the cycle pos = cs + #{ i > cs : a[i] < item }; skip equals; swap item ↔ a[pos] the cycle view — distinct keyslet dest(i) be the final slot of the key now at i; dest is a permutation, and splits into disjoint CYCLES a cycle of length L (i → dest(i) → dest(dest(i)) → … → i) is rotated with exactly L writes; a fixed point (L = 1) costs 0 writes = ∑ over cycles with L ≥ 2 of L = n − (number of fixed points) ← each element written at most once swaps ≥ n − (number of cycles, fixed points included) ← a swap can raise the cycle count by at most 1 THEOREM (cost). Hypothesis: comparison model; any input.writes = #{ i : a[i] ≠ sorted[i] } — the minimum: a slot holding the wrong key must be written at least once comparisons ≥ n(n − 1)/2 — every cs scans the whole suffix once, and again for each further write in its cycle extra space O(1); NOT stable (an element can be carried past an equal key); NOT adaptive in comparisons

Worked: [4, 2, 7, 1, 3, 6, 5, 0]

The keys are 0 … 7, so every key's final slot is its own value and the cycles can be read straight off the array: slot 0 holds 4, slot 4 holds 3, slot 3 holds 1, slot 1 holds 2, slot 2 holds 7, slot 7 holds 0 — the cycle (0 4 3 1 2 7) — and slots 5 and 6 hold each other's keys, the cycle (5 6). The routine starts at cs = 0, picks up 4, counts four smaller keys to its right and writes 4 into slot 4; it now holds the evicted 3, writes it into slot 3, then 1 into slot 1, 2 into slot 2, 7 into slot 7, and finally 0 into slot 0, closing the cycle after 6 writes. Iterations cs = 1 … 4 find their keys already home and write nothing; cs = 5 rotates (5 6) with 2 writes. Measured: 8 writes in 2 cycles and 73 comparisons. Selection sort on the same array makes 6 swaps — exactly n − (cycles) = 8 − 2, the swap minimum, because each of its swaps splits one element off a cycle — but 6 swaps are 12 writes. The difference is the whole point: a cycle of length L costs L writes when it is rotated and 2(L − 1) when it is undone by swaps.

Cycle sort: the cycles it rotates, and its array writes against selection and insertion sort each arc is one write, from the slot the key came from to its final slot; colours are cycles; the bars count writes through a proxy on the array, so every routine is measured the same way

At the default — ten random keys — the permutation has three cycles and no fixed point, and cycle sort makes 10 writes and 111 comparisons; selection sort makes 7 swaps (n − 3), 14 writes; insertion sort 36. On reverse sorted input every cycle has length 2 and the two write counts coincide (10 and 10): rotation saves nothing on a transposition. On nearly sorted input cycle sort writes 2 slots and still makes 53 comparisons — it is adaptive in writes and not at all in comparisons.

Duplicates, and where the write count matters

With repeated keys the count "smaller keys to the right" names the first slot of a run of equal keys, and without the skip loop the algorithm would write an item on top of an equal one, evict it, and carry the same value round forever. Skipping slots that already hold an equal key restores termination and keeps the optimality: the write count is then the number of slots whose key differs from the sorted array's, which a run over 20 000 random arrays with and without duplicates confirmed exactly, and which the figure checks on every input. The cost model that makes this worth Θ(n²) comparisons is memory with asymmetric or wearing writes — flash and EEPROM, whose cells tolerate a limited number of program/erase cycles and are slower to write than to read — or records so large that a write dominates any comparison. Everywhere else the comparisons make it the slowest sort on this page. Its loop has a second life that is far more common than the sort: applying a known permutation in place — the last step of an indirect sort (§25) — is exactly this cycle-following, with the destination read from the permutation instead of found by counting, and so costs Θ(n).

09 Odd-even transposition sort: n parallel rounds, and the 0-1 principle

Bubble sort's inner loop is a chain — each compare-exchange may move the element the next one reads — so it cannot be run in parallel as written. Odd-even transposition sort reorders the same adjacent compare-exchanges into rounds of disjoint pairs: even rounds compare (0,1), (2,3), …, odd rounds (1,2), (3,4), …. Every pair in a round is independent, so a round is one parallel step, and n rounds always sort. It does Θ(n²) work but has span n; on a line of processors that can talk only to their neighbours, nothing simpler sorts.

Why n rounds suffice

By the 0-1 principle it is enough to sort every string of 0s and 1s, and there the argument is about the 1s marching right. A 1 moves one step right whenever it is compared with a 0 on its right, and the rounds alternate, so a 1 that is not blocked moves at every round. The rightmost 1 is never blocked: it starts moving at round 1 or 2 and then moves every round. The j-th 1 from the right can be held up only by the (j − 1)-th, and an induction shows it moves at every round from round j + 1 at the latest; it has at most n − j steps to travel, so it is home by round n. An exhaustive run over all n! permutations and all 2ⁿ 0-1 inputs for n ≤ 9 found the bound tight: for every n ≥ 3 some input needs all n rounds (the reversed array is one), and the worst 0-1 input needs exactly as many rounds as the worst permutation — the principle, observed.

The algorithm is a sorting network: its compare schedule is fixed in advance, which is what makes it suitable for hardware and for lockstep SIMD lanes, where a data-dependent branch is expensive. Its depth n and n(n − 1)/2 comparators are far from optimal. Bitonic sort and odd-even merge sort are the practical networks, with depth O(log² n) and O(n log² n) comparators — not work-efficient against n log n, but with a span that is polylogarithmic, which is why they appear in GPU and vector-register sorting kernels; a network of depth O(log n) exists, with constants that keep it theoretical. In the work/span language of Parallel Algorithms, §05, odd-even transposition is Θ(n²) work over span n, and on a linear array of n cells passing values only to neighbours it is the simplest example of the rhythmic, neighbour-only computation that page's §20 calls a systolic array.

What the two sections share. Cycle sort and odd-even transposition are both quadratic in comparisons and both still worth knowing, because each optimises a resource the comparison count ignores: cycle sort the number of writes, odd-even transposition the number of parallel rounds under neighbour-only communication. "Which sort is best" is always "best in which cost" — the question §21's table makes precise for the n log n sorts.
