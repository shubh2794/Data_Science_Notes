20 Heapsort's contract, and where it is taught

Heapsort is selection sort (§05) with the Θ(n) scan for the maximum replaced by a heap's O(log n) extract: build a max-heap over the array in place in Θ(n), then n − 1 times swap the root to the end of the live region and sift the new root down. It is the one comparison sort that is simultaneously O(n log n) in the worst case and O(1) in extra space, which makes it the guaranteed fallback inside introsort (§19) and the right answer whenever memory is the binding constraint. It is not stable, and its access pattern is the worst of the three n log n sorts.

the contract, in one block — proved and traced in Heaps & Priority Queuestime O(n log n) worst case, every input; about 2·n·log₂n comparisons for the classic sift-down (two per level), measured 1.76·n·log₂n at n = 8192 on random input; the bottom-up sift-down variant brings the average to ≈ n·log₂n best case Ω(n log n) on every input of DISTINCT keys — sorted input is NOT a best case (it costs slightly more than random); all-equal keys are the exception: Θ(n), since nothing ever sinks space O(1) beyond the array — no buffer, no recursion stable NO — the root-to-end swap carries a key past its equals access scattered: each sift-down touches indices i, 2i + 1, 4i + 3, … — one cache line per level, no prefetching

Everything in that block is established elsewhere and this page only quotes it. The algorithm itself, with a hand trace of build-heap and of the sort phase, is Heaps & Priority Queues, §12. The worst-case bound, the best-case statement for distinct keys, the average measured across input shapes, and the comparison against n·log₂n are its §13. The bottom-up variant that walks the path of larger children first and searches back up — halving the comparisons — is its §14; and the case for and against heapsort in context, cache behaviour included, is its §15. §21 below measures it alongside mergesort and quicksort with the same counter so that the three appear on one chart, and the number it reads at n = 8192 — 1.76 — is the same one that page reports.

Where it wins and where it loses

  • Wins: a guaranteed bound with no memory — introsort's fallback, embedded and real-time systems, sorting in a fixed buffer. And the partial sort: the k largest of n in O(n + k log n) by stopping after k extractions, which no other sort here does cheaply.
  • Loses: to quicksort by a constant of about 1.5 in comparisons (1.76 against 1.17–1.27 in §21) and far more in wall-clock time on large arrays, because every sift-down is a chain of cache misses; to mergesort on stability and on sequential access. The heaps page's §17 has the measured ratios.

21 The n log n sorts head to head: comparisons, moves, memory, stability, worst case

By §10 all three are within a constant of optimal in comparisons, so the comparison between them is a comparison of constants and of everything the comparison count does not capture. Measured on the same inputs with the same counter, mergesort makes the fewest comparisons, quicksort the fewest moves, and heapsort the most of both — and the columns the counter cannot measure, memory and stability and worst case and access pattern, are the ones that decide which is used where.

On random permutations at n = 8192 the comparison counts per n·log₂n are mergesort 0.90, quicksort with Hoare's partition, median-of-three and a cutoff of 12: 1.27, quicksort with Lomuto and a random pivot: 1.17, and heapsort 1.76. Switch the measure to moves and the order inverts: mergesort 2.00 (every level copies the array into the buffer and back), the Hoare quicksort 0.88, the Lomuto one 1.70 (Lomuto swaps far more, §15), heapsort 1.20. Mergesort's comparison count sits below n·log₂n — it is the closest of the three to the log₂(n!) floor — and its moves are the highest, a trade the alternating-buffer implementation halves. Under the sorted input mergesort drops to 0.50 (its best case, §12), the Hoare quicksort with median-of-three to 0.88, and heapsort rises to 1.83, since a sorted array is a heap in reverse and every extracted key has to sink the full height. Under four distinct keys the Lomuto/random-pivot quicksort explodes to 78.96·n·log₂n — §17's degradation, visible here as a line that leaves the chart — while the Hoare configuration is unaffected at 0.91.

The columns the counter cannot measure

  • Worst case. Mergesort and heapsort are Θ(n log n) on every input by the shape of their recursion or their heap; quicksort is Θ(n²) unless a depth limit or a random pivot is present, and then it is O(n log n) guaranteed or expected respectively (§18, §19). A service that sorts adversarial input must not run an unguarded quicksort.
  • Stability. Mergesort only. That single fact decides the default sort of every language runtime that promises stability (§26) and every multi-key sort (§25).
  • Memory. Heapsort O(1); quicksort O(log n) stack with smaller-first; mergesort Θ(n), or O(1) on a linked list.
  • Access pattern. This is the column that decides wall-clock time and that no operation count captures. Mergesort streams; quicksort's partition streams from both ends; heapsort jumps across the array at every level of every sift. On arrays larger than the cache, the same "1.76 versus 0.90" comparison ratio between heapsort and mergesort becomes a much larger running-time ratio, because heapsort's comparisons each wait on memory while mergesort's arrive in prefetched lines. The principled version of this argument — why an operation count is a model of running time and where the model breaks — is Algorithm Analysis, §22–§23.
  • Branch prediction. Quicksort's partition branch is unpredictable on random data, which is why the branchless block partition of §19 exists; mergesort's merge has the same problem and the same fix (branchless merges select with arithmetic rather than a jump). Heapsort's comparisons are data-dependent at every step and cannot be made branchless as easily.
The decision, in one line each. Need stability, or the input is a linked list or a stream, or the data does not fit in memory → mergesort. Need the best typical speed in place and can tolerate an expected or depth-limited bound → quicksort (as introsort). Need a hard bound in O(1) space, or the k largest, or a fallback → heapsort. Keys are small integers or fixed-width strings → none of them; read §22–§24.

22 Escaping the bound: counting sort

The lower bound of §10 binds algorithms that only compare. Counting sort never compares two keys: it assumes the keys are integers in a known range 0..k−1, counts how many times each value occurs, converts the counts to prefix sums — which are exactly the final positions — and places each element by indexing. Its cost is Θ(n + k), linear whenever k = O(n), and it is stable, which is the property radix sort (§23) will need from it.

With k = n² it is quadratic; with k = 2⁶⁴ it does not run at all. The hypothesis IS the algorithm. THEOREM (stability). Hypothesis: the placement loop runs from j = n − 1 DOWN to 0.after the prefix pass, C[v] − 1 is the LAST slot for value v; the backwards scan meets the last v in the input first and puts it there, then the second-to-last v one slot lower, … — so equal keys keep their input order. The readout confirms the trace — 21 steps, zero comparisons, output sorted and stable — and the two other presets show the cost not changing: an already-sorted input and an all-equal input both take exactly 21 steps, because nothing in counting sort depends on the order of the input, only on n and k. That obliviousness is the flip side of linearity: a comparison sort can be adaptive because it looks at the order; counting sort cannot be, because it never does.

Where it applies, and where it quietly does not

  • Small integer keys with satellite data — sorting records by a byte-sized category, a grade, a month, a small enumeration. The output array carries the whole record, which is why stability and the backwards pass matter: they are what keep records with the same key in their original order.
  • Not for keys that merely look small. 32-bit integers have k = 4·10⁹; a count array of that size is neither linear nor allocatable for n in the thousands. Radix sort (§23) is what turns wide keys into a sequence of narrow ones.
  • Not in place, and not comparison-based. It needs a caller that can hand it an integer key function; it cannot sort under an arbitrary comparator. This is exactly the boundary the lower bound draws — leave the comparison model, gain linearity, lose generality.
  • The counting pass alone is useful. A histogram is Θ(n + k) and answers "how many keys in [a, b]" in O(1) after the prefix pass, which is the prefix-sum trick of Arrays & Strings, §14, applied to a key distribution.

23 Radix sort: LSD and MSD, the stability requirement, and the word-size hypothesis

Radix sort sorts wide keys by sorting on one narrow digit at a time. Least-significant-digit first: sort the whole array by the last digit, then by the next, and so on, using a stable sort for each pass — after the pass on digit d the array is sorted by its low d + 1 digits. With counting sort as the digit sort, d digits of k possible values cost Θ(d·(n + k)). Whether that beats n log n depends on how many digits a key has relative to log n, and on nothing else.

Hypothesis: every digit pass is STABLE.invariant after pass d: A is sorted by the low d + 1 digits proof of the step: keys that differ in digit d are ordered by the pass; keys with the SAME digit d keep the order the previous passes gave them — which was by the low d digits — because the pass is stable. Together: sorted by d + 1 digits. with an UNSTABLE digit sort the second clause fails and the output is garbage: this is the one place stability is load-bearing THEOREM (cost). Hypothesis: D digits, radix k, counting sort per pass.time Θ(D·(n + k)) space Θ(n + k) comparisons between keys: 0 for b-bit keys split into digits of r bits: D = ceil(b/r), k = 2ʳ, time Θ((b/r)·(n + 2ʳ)) the optimal digit width is r ≈ log₂n: then 2ʳ ≈ n and the time is Θ(b·n / log n) — linear iff b = O(log n) i.e. radix sort is linear when the keys are no wider than the WORD it takes to count to n. MSD radix sort, and why it is the different algorithm

Most-significant-digit first is the recursive version: bucket the keys by their leading digit, then sort each bucket recursively on the next digit. It is not a sequence of stable passes over the whole array — each bucket is an independent subproblem, exactly as in quicksort with a k-way partition — and it has two properties LSD lacks. It stops early: a bucket of one element is finished, so keys that are distinguished by their first few digits never have their remaining digits examined, and on keys with long common prefixes or highly variable lengths (strings, most obviously) it inspects only the characters it must. And it works on variable-length keys, since a key that has run out of digits simply sorts first in its bucket. Its cost is that it creates k buckets at every recursive call — on the seven-key example the readout counts 30 bucket arrays for 11 placements — which for a large radix and small buckets is pure overhead; production versions switch to insertion sort on small buckets for the same reason quicksort does (§19). LSD is the algorithm for fixed-width integer keys; MSD, or its three-way-quicksort hybrid for strings, is the algorithm for text.

Two things the trace shows. MSD stops early on any prefix that is already unique — the three keys 657, 720, 839 were placed once and never looked at again, which is why MSD wins on long keys with distinguishing prefixes (strings) and loses on short dense keys where nearly every bucket recurses. And it is not stable by construction in the way LSD is: stability within a bucket is whatever the recursive call preserves, so an MSD sort that finishes small buckets with insertion sort is stable and one that finishes them with quicksort is not.

When radix beats comparison sorting, honestly

  • Key width against log n. A 32-bit key over a million elements is 4 byte-passes against 20 comparison levels; a 64-bit key over a thousand elements is 8 passes against 10 levels. The formula b/log n passes says which regime you are in, and "radix sort is faster for integers" is true only in the first.
  • Memory traffic. Each radix pass reads the whole array and writes it to another buffer with scattered writes (one per bucket); a comparison sort's passes are sequential or nearly so. On data larger than the cache, a radix pass can cost several times what its operation count suggests, and the byte-per-pass choice is often tuned to keep the 2ʳ counters in cache rather than to minimise passes.
  • What it cannot do. Sort under a user-supplied comparator; sort floating-point keys without a bit-level transform; sort in place (the standard version needs a second array); or be adaptive — its cost is D·(n + k) on sorted input too.

24 Bucket sort and its distribution hypothesis

Bucket sort is the third way out of the comparison model, and it rests on the strongest hypothesis of the three. Assume the keys are real numbers drawn uniformly and independently from [0, 1); split the interval into n equal buckets, drop each key into its bucket by one multiplication, insertion-sort each bucket, and concatenate. Under the hypothesis, every bucket holds a constant number of keys on average and the whole thing is expected-linear. Without it, one bucket can hold everything and the cost is insertion sort's — quadratic.

the algorithmB[0..n) = n empty lists for each key x: append x to B[floor(n · x)] ← the key's VALUE picks the bucket: not a comparison for i = 0 .. n − 1: insertion_sort(B[i]) concatenate B[0], B[1], …, B[n − 1] THEOREM (expected cost). Hypothesis: keys independent and UNIFORM on [0, 1).let nᵢ = number of keys in bucket i; the insertion sorts cost ∑ O(nᵢ²); everything else is Θ(n) nᵢ ~ Binomial(n, 1/n): E[nᵢ] = 1, Var[nᵢ] = 1 − 1/n, so E[nᵢ²] = Var + E² = 2 − 1/n E[T(n)] = Θ(n) + ∑ᵢ O(E[nᵢ²]) = Θ(n) + n · O(2 − 1/n) = Θ(n) the same conclusion holds for ANY input distribution with ∑ E[nᵢ²] = O(n) — i.e. one under which no bucket is expected to be crowded without the hypothesisall keys in one bucket ⇒ one insertion sort of n keys ⇒ Θ(n²) worst case the fix, when the distribution is known but not uniform: choose bucket boundaries at the distribution's quantiles, not at equal widths

At n = 256 the uniform keys fill the buckets to a maximum of 5, with ∑nᵢ² = 550 against the theorem's expectation of n·(2 − 1/n) = 511, and the insertion sorts make 134 comparisons in total — a small fraction of the n·log₂n = 2 048 a comparison sort would need. Cube the same keys and the distribution piles up near zero: the largest bucket holds 36, ∑nᵢ² rises to 1 910, and the comparisons to 496, 3.7× the uniform cost. At n = 4096 the ratio is 11.4×, and it keeps growing with n, because the crowded bucket's cost is quadratic in its size while the uniform case stays linear. The hypothesis is not a technicality: it is the entire difference between a linear and a quadratic algorithm.

Where it fits

Bucket sort is the right tool when the keys are known to be spread evenly over a known range — the output of a hash function, uniformly generated identifiers, measurements with a flat distribution — and when the range is continuous or too wide for counting sort. It generalises counting sort (which is bucket sort with one bucket per key value and no within-bucket sort) and it is the one-pass ancestor of MSD radix sort (§23), which is bucket sort applied recursively with the digit as the bucket index. In practice its most common appearance is not as a sort at all but as the distribution step of a sample sort or an external sort (§31): partition the data into ranges by sampled splitters so that the ranges are roughly equal, then sort each range independently, in parallel or in memory. The analysis above is exactly the analysis of why that works — and of why it fails when the splitters are chosen without looking at the data.

The three escapes, side by side. Counting sort: integer keys in a small range, Θ(n + k), no hypothesis about the input's order or distribution. Radix sort: integer keys of bounded width, Θ(D·(n + k)), linear iff the width is O(log n), needs a stable digit sort. Bucket sort: real keys, expected Θ(n) iff the distribution is known and spreads the keys, quadratic otherwise. Each replaces the comparison model's one weak hypothesis — "keys are comparable" — with a stronger one, and each is only as fast as its hypothesis is true.

25 Sorting records: keys versus satellite data, indirect sorting, and multiple keys via stability

Real sorts rarely sort numbers. They sort records — rows, objects, structs — by one field, and carry the rest along. That changes three things: a move now costs the size of the record, not a word; the key may be expensive to compute or compare; and "sort by A, then by B" becomes a question about stability. Each has a standard answer, and all three are about separating the ordering from the moving.

the vocabularyKEY the field(s) the order is defined on SATELLITE DATA everything else in the record, carried along unexamined KEY FUNCTION key(record) — computed per record, possibly expensive (a string, a parsed date, a lower-cased name) COMPARATOR cmp(r₁, r₂) — a full comparison of two records, possibly expensive, called Θ(n log n) times three ways to sort records, by what movesDIRECT sort the records in the array: moves cost sizeof(record) each; n·log₂n·(size) bytes of traffic INDIRECT sort an array of INDICES (or pointers) by key(records[i]): moves cost one word; the records never move; reading the result in order is then a scattered walk — or one final Θ(n) permutation pass DECORATE-SORT-UNDECORATE build (key(r), i, r) triples once, sort the triples, strip the keys: the key function is called n times instead of Θ(n log n); the index i breaks ties and makes ANY sort stable on the triples multiple keys, two waysONE PASS, LEXICOGRAPHIC COMPARATOR cmp = (by A, then by B, then by C): any sort, one call, stability irrelevant SEVERAL PASSES, STABLE SORT sort by C, then STABLY by B, then STABLY by A: correct only if each later pass is stable — the same theorem as radix sort's (§23), with the fields as the digits, most significant LAST

Why the key function belongs outside the comparator

A comparison sort calls its comparator about n·log₂n times — 20 million times for a million records. If the comparator computes something from each record on every call (lower-cases a string, parses a number out of a field, walks a pointer), that computation is done twenty times per record instead of once. The decorate-sort-undecorate pattern computes key(r) exactly once per record, stores it beside the record, sorts the pairs by the precomputed key, and discards the keys afterwards. It costs Θ(n) extra memory and one pass, and it is the reason every library sort accepts a key function as well as, or instead of, a comparator: the library applies the pattern for you. The second thing the pattern buys is stability for free — if the decoration is (key, original index), no two decorations are equal and the sort's own stability is irrelevant, which is the standard way to get a stable result out of an unstable sort.

Indirect sorting, and the cost of reading the answer

When records are large, sorting an index array is cheaper by the ratio of record size to word size in every move, and the comparison count is unchanged. The result is a permutation, not a sorted array: idx[0] is the position of the smallest record, and reading the records in sorted order means jumping through memory in that order — a scattered access pattern, one cache miss per record if the records are large. Whether that matters depends on how many times the sorted order is read. Read once, the index is the right answer. Read many times, apply the permutation in one pass — cycle by cycle, in place, or into a fresh array — and pay the scatter once. Database engines make this decision constantly: a sort by key produces row identifiers, and the "materialise the rows in order" step is a separate, and often more expensive, operation.

Multi-key sorting: the stability theorem in daily use

"Sort employees by department, and within each department by name" is one of two things. Written as a single lexicographic comparator it is one sort of any kind. Written as two sorts — first by name, then stably by department — it is correct for exactly the reason LSD radix sort is: the second sort orders records with different departments, and for records with the same department leaves them in the order the first sort produced, which was by name. Swap the order of the two passes, or use an unstable sort for the second, and the result is sorted by department with names in arbitrary order. The multi-pass form is what makes interactive "click a column header to sort by it" interfaces behave as users expect: each click is a stable sort by the clicked column, and the previously chosen columns survive as tie-breakers. It is also why the default sort of every runtime that offers one is stable (§26) — not because stability is elegant but because this idiom is everywhere.

The rule. Compute keys once, move indices rather than records when records are large, and use stability — yours or the decoration index's — whenever a sort is followed by another sort. Every one of these is a constant-factor concern, and every one of them routinely outweighs the difference between two n log n algorithms.

26 What library sorts actually do: hybrids, run detection, guaranteed fallbacks

No standard library ships a textbook quicksort or a textbook mergesort. Each ships a hybrid: an n log n algorithm for the bulk of the work, insertion sort below a cutoff, a mechanism that recognises existing order and finishes it in linear time, and a hard worst-case guarantee. The designs cluster into two families, and which family a library chose is decided by one question — whether the sort is required to be stable.

the two families — described as techniques, not as any one implementationSTABLE, MERGE-BASED ("natural merge with a minimum run") · scan for existing ascending runs; reverse strictly descending ones in place so they count too · a run shorter than a minimum length (a few dozen elements) is extended to it by binary insertion sort · merge runs from a stack, keeping the pending run lengths roughly geometric so the merge tree stays balanced · during a merge, when one run keeps winning, switch to "galloping": exponential search (§29) for how far it wins result: Θ(n) on sorted or reverse-sorted input, O(n log r) for r runs, O(n log n) worst, stable, Θ(n) buffer at most UNSTABLE, PARTITION-BASED ("introspective / pattern-defeating quicksort") · median-of-three or ninther pivots by range size, insertion sort below a cutoff of roughly a dozen to a few dozen elements · a partition that handles equal keys — either three-way, or a Hoare-style scan that stops on equals · a check after each partition: if nothing moved, the range may already be sorted — try a bounded insertion sort · a recursion-depth limit of about 2·log₂n, past which the range goes to heapsort; some variants also break a detected pattern by swapping a few elements result: O(n) on several common patterns, O(n log n) guaranteed, in place, NOT stable

What this means for the reader of a sort's documentation

  • "Stable" is the property to check first. As a matter of general practice at the time of writing: the default list sort in Python is stable and merge-based; the sort of object arrays in Java is stable and merge-based, while its sort of primitive arrays is a dual-pivot quicksort, stability being meaningless for primitives; the C++ standard's sort is not required to be stable and is typically an introsort, with stable_sort a separate merge-based function; JavaScript's array sort has been required to be stable since the 2019 language standard; Rust and Go each offer a stable sort and an explicitly named unstable one. The unstable variants exist because they are faster and in place; the stable ones exist because §25's idioms need them. Check, do not assume.
  • Adaptivity is now standard. Both families sort already-sorted, reverse-sorted and "sorted with an appended tail" inputs in linear or near-linear time. Pre-checking for sortedness before calling a library sort is redundant, and pre-shuffling to "avoid the worst case" is actively harmful — it destroys the order the sort would have exploited, and the worst case is already handled by the fallback.
  • The worst-case guarantee is real. Depth-limited quicksorts are O(n log n) on every input, including adversarial ones; merge-based sorts always were. An unguarded quicksort with a quadratic worst case is not something a maintained library ships, and §16's killer inputs are a concern only for hand-written sorts.
  • The cutoff and the minimum run are tuning constants, set by measurement on the implementer's hardware. Typical values are in the range this page measured — around a dozen elements for the quicksort cutoff (§19), a few dozen for the minimum run — and they are not part of any interface. Quoting them as facts about "the algorithm" is a mistake; they are facts about a build.
  • Key functions and comparators are both accepted, and the library applies decorate-sort-undecorate (§25) for the former. Prefer the key function: it is called n times, the comparator n log n.

Why the merge family won stability and the partition family won speed

A merge is naturally stable and naturally sequential, and detecting runs is a natural extension of a bottom-up merge; the whole stable family is §12 made adaptive plus §04's insertion sort for the small pieces. A partition is naturally in place and naturally branch-predictable when written carefully, and the depth limit is the cheapest possible worst-case insurance; the whole unstable family is §19 with equal-key handling from §17 and pattern detection bolted on. The two families do not compete on the same axis, and the reason both exist in every runtime is that no known sort is at once stable, in place, and O(n log n) with a small constant. When a library offers only one sort, it is usually — not always: C's qsort promises nothing — the stable one; a stable sort can be used where an unstable one is wanted, at some cost, but not the other way round.

Practical rule. Use the library sort. Pass a key function. Ask for the stable variant when the sort is followed by another sort or when equal keys have meaning. Reach for anything on this page by hand only when the library's contract is wrong for the problem — a linked list, an external file, a fixed memory budget, a key type that permits a radix pass, or a partial result such as the k smallest.
