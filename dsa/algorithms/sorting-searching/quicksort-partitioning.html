13 Quicksort: the idea, and the partition invariant

Mergesort does no work to divide and all its work to combine. Quicksort is the mirror image: choose a pivot, rearrange the array so that everything smaller is to the pivot's left and everything larger to its right, then sort the two sides recursively — and there is no combine step at all, because a sorted left part, the pivot, and a sorted right part are already a sorted whole. All the intelligence is in the partition, a single linear pass, and everything about quicksort — its speed, its instability, its quadratic worst case, its sensitivity to equal keys — is a property of how that pass is written and which pivot it is given.

Why a fixed proportional split is still n log n

The 1-to-9 line is the one to internalise, because it is why quicksort works in practice at all. The recursion tree of a 1:9 split has its shallowest leaf at depth log₁₀ n and its deepest at log n / log(10/9) ≈ 22·log₁₀ n; every level costs at most n, so the total is at most n · log n / log(10/9) = O(n log n). The base of the logarithm — the constant — depends on how lopsided the split is, but the split does not have to be even, or anywhere near even, for the exponent to be right. A random pivot lands in the middle 80% of the sorted order with probability 0.8, so four out of five partitions are at least 1:9, and the occasional bad one is absorbed: an unlucky level of cost n followed by a lucky one costs n + n = 2n for the same progress a single lucky level would have made. That is the intuition; §18 makes it a theorem with an exact expectation.

What every partition scheme must and must not do

  • It must shrink both sides. The Lomuto scheme (§14) places the pivot at its final index q and excludes it from both recursive calls, so each side has at most n − 1 elements. The Hoare scheme (§15) does not fix the pivot; its guarantee is subtler — the returned index is strictly less than hi − 1 — and using its return value with Lomuto's recursion — excluding A[j] from both calls — silently leaves one element unsorted at every level (§15 lists the bug).
  • It must be linear and sequential. Every scheme here scans with one or two indices moving monotonically, comparing each element to a pivot value held in a register. That inner loop — increment, compare, occasionally swap — is why quicksort is fast: it is the tightest loop of any n log n sort, it touches memory in order, and its one branch is well predicted on random data. "In place" is a side effect, not the cause.
  • It need not be stable, and none of the simple ones are. A swap that moves an element across the unexamined middle can carry it past an equal key. Making quicksort stable requires either an O(n) buffer (at which point mergesort is the better choice) or a stable in-place partition with a logarithmic overhead; in practice a stable sort is a merge sort (§26).
  • Its behaviour on equal keys is not specified by the contract. The postcondition "≤ p on the left, ≥ p on the right" lets equal keys go either way, and the three schemes make three different choices with three different costs on duplicate-heavy input — §17 measures a factor of 250 between them at n = 1024.

14 The Lomuto partition, traced index by index

The Lomuto scheme uses one scanning index and one boundary index, takes the last element as its pivot, and grows a "≤ pivot" region from the left. It is the easiest partition to prove correct — its loop invariant is three adjacent regions — and it makes exactly n − 1 comparisons on every input. It is also the one that degenerates on equal keys (§17).

The two other presets are §17's subject: on eight equal keys Lomuto's "≤" sends every element to the small region, returns q = 7, and leaves a left part of size 7 and an empty right part — the degenerate split — while Hoare's two scans stop on every equal key and return j = 3, the balanced split.

Two things the trace makes visible

  • Every swap moves a large element to the far end of the large region, out of order. That is the instability: at j = 3 the 8 jumped over the 7. Nothing in the scheme can be tuned to prevent it.
  • The number of swaps is the number of small elements found after the first large one — here 2 real swaps plus the pivot's — and on sorted input with the last element as pivot it is zero: the loop compares n − 1 times, swaps nothing, returns hi − 1, and the recursion continues on n − 1 elements. That is the quadratic worst case in its most common disguise (§18).

15 The Hoare partition, on the same array

The original partition scans from both ends toward the middle: the left index advances past elements smaller than the pivot, the right index retreats past elements larger, and when both have stopped on a misplaced pair the two are swapped. It does far fewer swaps than Lomuto on random input — one third as many inside the scans, roughly 40–60% fewer overall once each partition's pivot-placement swap is counted (measured 1.6–1.9× fewer at n = 1024–4096) — its scans stop on keys equal to the pivot — which is what saves it on duplicates — and it does not leave the pivot at a known index, which changes the recursion and is the source of most Hoare-partition bugs.

the loop (pivot VALUE taken from A[lo])hoare(A, lo, hi): p = A[lo]; i = lo − 1; j = hi loop: repeat j = j − 1 until A[j] ≤ p ← the right scan stops on ≤ (equal keys included) repeat i = i + 1 until A[i] ≥ p ← the left scan stops on ≥ if i < j: swap A[i], A[j] else: return j the invariant and the postconditionA[lo .. i] ≤ p and A[j .. hi) ≥ p after each swap; the scans never run off the range because p itself stops each of them on return: A[lo .. j] ≤ p ≤ A[j + 1 .. hi) with lo ≤ j < hi − 1 the pivot is somewhere in A[lo .. j] — NOT necessarily at j, and NOT excluded from the recursion recursion: quicksort(A, lo, j + 1); quicksort(A, j + 1, hi) ← j + 1, and NOT (lo, j) and (j + 1, hi) with the pivot removed the costcomparisons per partition: n + 1 or n + 2 in this formulation (each scan overshoots by one; measured: both values occur) swaps: about one third of Lomuto's INSIDE the scan (≈ n/6 against ≈ n/2 per partition) — only misplaced PAIRS are exchanged; with the pivot-placement swap added, 1.6–1.9× fewer in total at practical n

The figure in §14 steps both traces in parallel. The essential difference is visible in the last frame: Lomuto's pivot is at index 3 and excluded from both recursive calls; Hoare's is at index 7, inside the right part, and will be compared again in the next level. That costs Hoare a few extra comparisons per level — the n + 2 against n − 1, plus one element more in a subproblem — and the measured totals in §18 show the price: about 1.65× Lomuto's comparisons at n = 64, falling to 1.28× at n = 4096 as the shared 2n·ln n term dominates. What it buys is roughly half the swaps (a third, inside the scan) and, far more importantly, the balanced split on equal keys (§17). A common refinement returns the pivot to a fixed position after the crossing so that it can be excluded — that variant has the swap count of Hoare and the recursion of Lomuto, and is what most careful implementations actually use.

The two bugs this scheme invites

  • Recursing on (lo, j) and (j + 1, hi) as if j were the pivot's index. It is not; A[j] is merely the last element of the left part. Excluding it from both calls leaves A[j] where it is, never placed: the output is a permutation of the right multiset in the wrong order — swaps cannot lose elements, so the bug shows up as an unsorted result, not a crash. The correct calls are [lo, j + 1) and [j + 1, hi).
  • Taking the pivot from the middle or the end without moving it to A[lo]. The termination argument — the pivot stops both scans — needs the pivot value to be in the range on the correct side of where the scans start. With p = A[hi − 1] and the loop above, neither scan runs off — the pivot value still stops both — but the guarantee j < hi − 1 is lost: on [1, 2] the partition returns j = 1 = hi − 1, the left call is the whole range again, and the recursion never terminates. Choose the pivot however you like (§16), then swap it to lo before the loop.

16 Choosing the pivot: first, random, median-of-three, ninther

The partition's cost is fixed at Θ(n); the pivot decides how much progress that cost buys. A pivot at rank k splits the range k − 1 : n − k, and the sum over the recursion of these split costs is the running time. The first or last element is the worst possible rule on the most common inputs; the median of three sample elements is the standard cheap improvement; a random element gives an expected guarantee on every input; and no deterministic rule that looks at o(n) elements is safe against an adversary who knows it.

On random input all five rules land within 10 988–11 854 of each other: the pivot rule is not about the average case, it is about which inputs are allowed to be the worst case.

Deterministic rules have killers; random rules have bad luck

For every deterministic pivot rule that inspects a bounded number of positions there is an input that makes it quadratic, and such inputs can be constructed mechanically — an adversary answers each comparison in whichever way keeps the pivot extreme, assigning actual values only when forced, and the resulting array defeats that specific implementation. Median-of-three "killers" for the standard library quicksorts of the 1990s were built exactly this way, and they were a denial-of-service vector against any service that sorted user-supplied data. A random pivot has no killer ordering: on distinct keys its cost is a random variable whose expectation is 2n·ln n on every input (duplicate-heavy input is a different matter — with Lomuto it stays quadratic whatever the pivot, §17), and whose probability of exceeding that by any fixed factor shrinks as n grows (§18). The residual risk is a bad random draw, not a bad input, and the two are different in kind: an adversary can choose the input and cannot choose the draw. Where determinism is required — reproducibility, or no access to randomness — the answer is not a cleverer pivot but a guaranteed fallback: introsort's depth limit (§19).

Practical summary. Use median-of-three (or the ninther on large ranges) for its constant-factor gain, and either a random component or a depth-limited fallback for its guarantee. Never the first or last element alone: sorted input is not rare, it is the single most common input a sort receives.

17 Equal keys, and three-way partitioning

"Quicksort is quadratic on equal keys" is the most repeated half-truth about the algorithm. It is true of the Lomuto scheme, false of Hoare's, and the opposite of true for a three-way partition, which sorts an all-equal array in linear time. The behaviour is scheme-dependent because the partition contract (§13) does not say where equal keys go, and each scheme answers that question differently.

On a random permutation of distinct keys the order reverses — 11 083, 15 893, 15 302 — because Hoare's overshoot and three-way's second comparison per key are pure overhead when no key is ever equal. That is the trade, and it is why production quicksorts use a partition that detects equal keys cheaply (a Hoare-style scan that stops on equals, with equal keys gathered to the ends and swapped into the middle afterwards) rather than paying two comparisons per element up front. The point stands regardless of formulation: a sort that will meet duplicate-heavy data — and most real data is — must not use a partition that sends equal keys to one side.

Why it matters beyond correctness. Sorting by a low-cardinality key — a status code, a country, a category — is one of the most common sorts there is, and it is exactly the case where d ≪ n. Three-way quicksort's O(n log d) makes it, in that regime, ahead of any n log n sort by a factor of log n / log d in comparisons — a count, not a time; with 16 categories and a million rows that is a factor of five. The same observation, in the non-comparison model, is counting sort (§22).

18 Quicksort analysed: the exact average, the worst case, the recursion depth

With a uniformly random pivot and distinct keys, quicksort's expected comparison count is not "about n log n" but an exact expression: 2(n + 1)·Hₙ − 4n ≈ 2n·ln n − 2.85n, where Hₙ is the harmonic number. The derivation is two lines once the right recurrence is written, the same expression falls out of a completely different argument about pairs, and the figure below checks both against a Monte Carlo measurement. The worst case is n(n − 1)/2 and is chosen, not suffered: it happens when the pivot rule and the input conspire — or, with Lomuto, whenever the keys are mostly equal (§17), and §16 and §19 are the two ways to stop them.

Why the average is trustworthy, and what "expected" means here

The theorem's hypothesis is that the pivot's rank is uniform at every call, which a random pivot guarantees on every input, and which a fixed rule guarantees only when the input is a random permutation. That is the difference between an average-case bound and an expected-time bound, and Algorithm Analysis, §06, is about exactly this distinction: the first is a statement about typical inputs and says nothing about yours; the second is a statement about the algorithm's own coin flips and holds for every input. Beyond the expectation, the distribution is concentrated — the probability that randomized quicksort's count deviates from its mean by any fixed fraction goes to zero as n grows, and the figure's Monte Carlo means sit within a few percent of the exact value at a few dozen runs — so in practice the expectation is the running time, on every input. The expectation argument in its general form, with the sampling framework that makes "2/(j − i + 1)" precise, is Recursion, Divide & Conquer, §29.

19 Practical quicksort: the small-subarray cutoff and introsort

Two engineering additions turn the textbook quicksort into the one libraries ship. The cutoff: stop partitioning ranges below some small size and finish with insertion sort, because on a dozen elements the partition's overhead exceeds the quadratic sort's total. Introsort: track the recursion depth and, if it exceeds 2·floor(log₂n), hand the current range to heapsort — which converts quicksort's Θ(n²) worst case into a guaranteed O(n log n) at no measurable cost on ordinary inputs.

The cutoff pays for the overhead of the partition it replaces, so its value depends on which partition that is. The lesson is the general one from §04: the crossover is an empirical constant of the implementation and the machine, it lies in the range where the literature has always put it, and the exact value matters little — for the Hoare hybrid, any cutoff between 8 and 16 captures nearly all the gain. What else a production quicksort does

  • Equal-key handling. A Hoare-style scan that stops on equal keys, usually with equal keys collected at the two ends during the scan and swapped into the middle afterwards, so that duplicate-heavy input is O(n log d) (§17) without paying two comparisons per key on distinct input.
  • Pivot by size. Median-of-three on small ranges, the ninther on large ones (§16), and, in the pattern-defeating variants, a check for whether the partition did any work at all — a partition that swapped nothing on an already-ordered range is a strong hint that the range is sorted, and a quick insertion-sort attempt with a bounded budget can finish it in linear time.
  • Adversary defence. Either a random element in the pivot choice, or — the common choice, since randomness costs time and reproducibility — a depth limit with heapsort, exactly the introsort rule above. On detecting a bad partition some variants also shuffle part of the range, which breaks the pattern that produced it.
  • Branch-free partitioning. On modern processors the partition's one data-dependent branch is the dominant cost on random input, since it is mispredicted half the time; block-based partitions that buffer the indices of misplaced elements and swap them in bulk remove the branch and are measurably faster. This is the clearest case of an algorithm being optimised for the machine rather than for the operation count, and it is the reason "quicksort is fast because it is in place" is the wrong explanation — it is fast because its inner loop can be made branchless and sequential.
Where this leaves quicksort. With a good pivot, three-way or equal-stopping partition, a cutoff, and a depth limit, quicksort is an in-place O(n log n) sort with the smallest constant of any comparison sort on random data, no worst-case input, and a sequential access pattern. What it still is not is stable — and that is the one property that keeps mergesort (§12, §26) in every standard library beside it.
