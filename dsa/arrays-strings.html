01 Memory layout and why indexing is free

An array is n equal-sized cells laid end to end. Nothing records where element i lives — the machine computes it.

address arithmeticaddr(a[i]) = base + i · sizeof(element) ← one multiply-add ⇒ O(1), independent of n row-major 2-Daddr(a[i][j]) = base + (i · ncols + j) · sizeof(element)
  • Uniform width is the precondition — hence one element type per array, or equal-sized pointers to boxed objects.
  • Reads are O(1); structural edits are not. Inserting or deleting at i shifts the n − i elements behind it ⇒ Θ(n). Only the end is cheap.
  • Contiguity buys locality: a scan walks consecutive cache lines, beating an equally-asymptotic linked list by a constant Big-O hides.

02 Dynamic arrays and amortized doubling

A growable list is a fixed array plus size and capacity; when it fills it reallocates and copies. The design question is how much bigger.

  • Grow by a constant c slots: n/c resizes copying 1c, 2c, 3c … ⇒ Θ(n²/c) total, i.e. Θ(n) per append.
  • Grow by a factor g > 1: copy costs form a geometric series summing to a constant multiple of n ⇒ O(1) amortized.
doubling: resizes at 1, 2, 4, …, 2ᵏ ≤ ncopies = 1 + 2 + ⋯ + 2ᵏ = 2ᵏ⁺¹ − 1 < 2n total < n writes + 2n copies = 3n ⇒ O(1) amortized factor gcopies ≈ n/g + n/g² + ⋯ = n/(g − 1)

Credits, and hysteresis on shrink

  • Charge each append 3 credits: one writes its cell, two are banked. At a doubling each element of the newer half holds two credits — enough to copy itself and one older element, so the bank never runs dry.
  • Halving capacity at half-full lets alternating append/pop resize every step; shrink only at ¼ full, down to half capacity.
Amortized ≠ worst case. The append that triggers a resize still stalls for Θ(n) — reserve capacity when latency matters.

03 Two pointers and the sliding window

Both replace a nested double loop with indices that only move forward, so the total is O(n) even though a loop sits inside a loop.

Converging pointers on sorted data

Compare a[lo] + a[hi] with the target. Too small ⇒ every remaining candidate is ≤ a[hi], so lo has no partner and is discarded; too large ⇒ discard hi. That discard argument is the proof.

invariantif a valid pair exists, both indices lie in [lo, hi] progresshi − lo strictly decreases ⇒ ≤ n steps · O(n) time · O(1) space
Two pointers: find a pair summing to the target On a sorted array, move the pointers inward by comparing the sum to the target

The sliding window

  • Extend r by one, then while the window is illegal (sum too big, a repeat, too many distinct keys) advance l.
  • Invariant: after the shrink loop, a[l..r] is the longest legal window ending at r, so the best over all r is global.
  • Not quadratic: l only increases, advancing ≤ n times overall ⇒ amortized O(n). Fixed windows roll the aggregate instead of recomputing.
Preconditions: converging pointers need sorted input (see Sorting & Searching); windows need a monotone constraint. Negatives break "shrink to fix the sum".

04 Prefix sums and difference arrays

One O(n) pass turns every range-sum question into a single subtraction.

build Θ(n) · query Θ(1)P[0] = 0, P[i] = P[i−1] + a[i−1] sum(a[l..r]) = P[r+1] − P[l] range update, point queryd[l] += v, d[r+1] −= v ⇒ a = prefix-sum(d)
  • The tradeoff: a plain array is O(1) update / O(n) query; prefix sums invert it. Needing both fast means a Fenwick or segment tree, O(log n) each — Trees & Graphs.
  • With a hash map, count subarrays summing to k: (i, j] qualifies iff P[j] − P[i] = k, so sweep j and look up prefixes equal to P[j] − k ⇒ O(n), the rescue for negative values.
  • 2-D by inclusion–exclusion: P[r₂][c₂] − P[r₁][c₂] − P[r₂][c₁] + P[r₁][c₁], four lookups.
Takeaway: the array world's memoization — pay Θ(n) once so q queries cost Θ(q), not Θ(q·n).

05 Rewriting in place

"O(1) extra space" is nearly always one of four moves.

  • Write pointer. Scan with r; copy to a[w] and bump w only for kept elements. Invariant: a[0..w) holds exactly the kept elements, in order.
  • Reversal. Swap a[i] ↔ a[n−1−i] for i < ⌊n/2⌋. Rotating left by k is three reversals — whole array, then each piece ⇒ Θ(n) time, Θ(1) space.
  • Three-way partition. Pointers low / mid / high order three distinct key values in one pass — the partition that makes quicksort duplicate-proof.
  • Array as hash table. Values in 1..n: put each at its home index, or mark "seen" by negating a[|v|−1] — Θ(n) · Θ(1), but it mutates the input.
Takeaway: in-place is a space claim, not a speed claim — name the move and its invariant.

06 Strings are arrays with two extra rules

A character array plus immutability and a variable-width encoding — both change the complexity of code that looks linear.

concatenating in a loop copies a growing prefix1 + 2 + ⋯ + n = n(n+1)/2 ⇒ Θ(n²) collect the pieces, join onceΘ(n)
  • With immutable strings s += t copies both operands into a fresh buffer; a builder (fragments joined once, or a geometrically-growing buffer) makes the build one linear pass.
  • UTF-8 uses 1–4 bytes per code point, so byte index ≠ character index and slicing bytes can split a character; UTF-16 needs surrogate pairs, so "length" differs across languages.
  • One code point is still not one perceived character — accents and emoji sequences form a grapheme cluster, so reversing by code point can corrupt text. See Python.
Takeaway: ask does an edit copy? and is indexing constant-time in this encoding?

07 Substring search: naive, KMP, rolling hash

Find pattern P (length m) in text T (length n). The classic answers differ in how much they remember about comparisons already made.

  • Naive. Every offset, up to m comparisons ⇒ Θ((n−m+1)·m), written O(n·m). Worst on repetitive text (aaaa…a vs aaab): each offset matches m−1 characters, then discards what it learned.
  • KMP. Precompute π[i], the longest proper prefix of P[0..i] that is also a suffix. After a mismatch with q matched, slide so π[q−1] stay aligned; the text pointer never moves back.
  • Why it is linear: match length rises by ≤ 1 per text character and each fallback strictly decreases it, so fallbacks ≤ increments ⇒ scan Θ(n), table Θ(m).
  • Rabin-Karp. Compare a rolling hash per window, verify on a hit: expected Θ(n + m), worst Θ(n·m) under adversarial collisions. Its edge is many patterns at once.

08 Frequency counting

Many string problems reduce to one sentence: two multisets are equal iff their counts are equal.

  • Anagram test: tally one string up and the other down in a fixed count array (26, 256, or a map for Unicode); anagrams iff every count returns to zero ⇒ Θ(n) time, Θ(k) space. Sorting both costs Θ(n log n).
  • Grouping needs a canonical key — sorted characters, or the count vector as a tuple — then bucketing in a hash map.
  • All anagrams of P in T: a length-m window plus one matches counter of how many symbols have the right count keeps each move O(1) ⇒ Θ(n), not Θ(n·k).
Takeaway: the counter is the invariant — state what the map means at every step and the update rule writes itself.

10 Pitfalls and an interview checklist

Array bugs cluster in a few places.

  • Off-by-one: prefer half-open ranges [l, r) — length is r − l, empty is l == r.
  • Hidden linear costs: list membership, insert(0, x), front deletion and slicing are Θ(n) or Θ(k); one inside a loop makes the solution quadratic — a set or deque fixes it (Python).
  • Quadratic string building from += in a loop; mutating while iterating, which skips elements; overflow in (lo + hi) / 2 — write lo + (hi − lo) / 2.
  • Unstated preconditions: pair-sum needs sorted input, windows need monotonicity, index-as-hash needs values in 1..n and a mutable input.
  • Views versus copies: a slice may alias the source buffer; vectorised operations are still Θ(n) — they cut the constant, not the class. See NumPy.
  • Edge cases: empty input, one element, all equal, pattern longer than text, target absent.
Checklist: state the assumptions (sorted? mutable? alphabet?) · name the pattern · write the invariant · argue termination · give time and space separately, flagging worst-case versus amortized — see Big-O Complexity.
