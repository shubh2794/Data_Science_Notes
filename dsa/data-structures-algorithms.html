Data Structures & Algorithms

The CS Core Arrays, trees, graphs, sorting and searching, dynamic programming — and the Big-O language that lets you compare them before writing a line of code.

01 Structure decides cost

A data structure is how you arrange data in memory; an algorithm is the procedure that walks it. Choose the structure well and the algorithm becomes cheap — choose poorly and the identical task costs orders of magnitude more.

  • The layout dictates what is fast. A contiguous array gives O(1) lookup by index but O(n) middle insertion; a balanced tree gives O(log n) ordered search; a hash table gives expected O(1) membership and no order at all.
  • Same answer, different work. "Is x in this collection?" costs O(n) by scanning, O(log n) by binary search on sorted data, and O(1) expected in a hash set. The result is identical; the cost is not.
  • There is no free structure. Every one trades something: ordering for speed, memory for lookups, insert cost for query cost. Naming the trade is the skill.
  • Compare by growth, not by stopwatch. Machines differ; growth rates do not. That is the whole point of Big-O Complexity, which underpins every claim on the pages below.
The same question, three structuresarray · index access O(1) · middle insert O(n) · search O(n) balanced BST · ordered search O(log n) · in-order walk O(n) hash table · membership O(1) expected · O(n) worst case · no ordering
Takeaway: most "make it faster" problems are really "pick a better structure" problems. The algorithm is often forced once the layout is chosen.

03 The problem-solving method

Strong solutions are rarely invented in one leap. They come from a fixed sequence that turns a vague prompt into a bounded, testable algorithm.

  • 1 · Understand. Restate the problem, fix the input and output types, and settle the edge cases now: empty input, one element, duplicates, negatives, overflow, already-sorted. Work one small example by hand.
  • 2 · Brute force. Say the obvious exhaustive solution out loud and state its complexity. It establishes correctness, gives a baseline to beat, and often contains the redundancy the fast solution removes.
  • 3 · Identify the pattern. Ask what the brute force wastes. Re-scanning a window? Re-sorting? Recomputing the same subproblem? Each waste maps to a known pattern in the table below.
  • 4 · Optimize deliberately. Apply the pattern, then re-derive the cost — number of operations times cost per operation — including the space the speed-up buys with.
  • 5 · Verify. Trace the example again, check the edge cases, and state the loop invariant or recurrence that makes it correct. "It passed my example" is not an argument.
Complexity of a solutiontime = (number of operations) × (cost per operation) DP: cost = (# states) × (work per transition) always quote both: time and auxiliary space · and say which case (best / average / worst)
Takeaway: narrate the brute force before optimizing. Jumping straight to a clever answer hides the reasoning that shows the clever answer is correct.

06 Where this shows up in ML and data work

These are not interview artefacts. The same structures decide whether a pipeline runs in seconds or hours.

  • Vectorization is a layout argument. Array code that operates on contiguous blocks beats element-wise loops because of memory locality, not because the asymptotics changed — the theme of NumPy and pandas.
  • Nearest-neighbour search is exact O(n·d) per query by brute force. Approximate indexes trade a little recall for logarithmic-ish search by building navigable proximity graphs or partitioned trees — see Vector Databases and k-Nearest Neighbors.
  • Tokenizers are string algorithms. Sub-word vocabularies are built with priority queues over merge counts and queried through prefix structures — see Tokenization.
  • Models are graphs. A computation graph is topologically sorted before the backward pass, and Graph Neural Networks run message passing over adjacency directly.
  • Trees and tables inside models: decision trees are recursive partitions, and query engines pick between hash joins and sort-merge joins for exactly the reasons in the cheat sheet above — see SQL.
  • Caching and deduplication — feature stores, embedding caches, memoized pipelines — are hash tables and dynamic programming under other names.
Takeaway: the payoff is diagnostic. When a job is slow, this vocabulary tells you whether you have an O(n²) join, a cache miss, or a genuinely hard problem — three very different fixes.

07 Pitfalls and preparation checklist

The recurring failures are analytical, not syntactic — an unstated assumption, a forgotten space cost, an untested boundary.

Common mistakes

  • Quoting time and ignoring space. A recursion carries O(depth) stack; a memo table is real memory.
  • Treating expected as guaranteed. Hash operations are O(1) expected, O(n) worst; quicksort is O(n log n) average, O(n²) worst.
  • Hidden costs inside a loop: string concatenation, list insertion at the front, or a membership test against a list rather than a set — each quietly multiplies the outer bound by n.
  • Skipping boundaries: empty input, a single element, all-equal values, and already-sorted input break more solutions than large inputs do.
  • Optimizing before correctness. A correct O(n²) beats a fast wrong answer, and it is the thing you optimize from.

Before you call it done

  • Can you state the loop invariant or the recurrence that makes it correct?
  • Can you state time and auxiliary space, and say which case each refers to?
  • Have you traced one small example end to end, plus the empty and single-element cases?
  • What are the input limits, and does your bound survive them?
  • What would you improve given more time — and what would it cost in space?
Takeaway: the goal is not to recall solutions but to run the method — understand, brute force, spot the pattern, optimize, verify — while saying the invariant and the cost out loud.
