Arrays & Strings

One decision — put the elements next to each other in memory — and every cost on this page follows from it. Contiguity turns an index into arithmetic, so reading any element is one step; it also means there is no gap to insert into, so making room is a shift of everything after the hole. 01 What an array is

An array is a fixed-size block of consecutive memory cells, all of the same width, holding elements that are addressed by an integer offset from the start of the block. Three words do all the work in that sentence — consecutive, same width, offset — and together they buy the one property that defines the structure: the address of element i can be computed, in a fixed number of arithmetic operations, without looking at any other element.

the defining identity — the whole structure in one lineaddress(A[i]) = base + i × itemsize wherebase = the machine address of the first cell itemsize = the number of bytes every cell occupies — the same for all cells i = the index, an integer offset, counted from 0 consequencereading or writing A[i] costs one multiply, one add and one memory access — O(1), for every i

Why each of the three words is load-bearing

  • Consecutive. If the cells were scattered, the address of cell i would have to be stored somewhere and looked up, and looking it up is itself an access problem — the regress that linked structures solve by following one pointer at a time, at a cost of i dereferences to reach element i. Contiguity replaces a lookup with a calculation.
  • Same width. The multiplication i × itemsize is only valid if every cell before i is exactly itemsize bytes wide. This is the constraint people forget, and it is why an array of objects of different sizes is not an array of those objects at all — it is an array of references to them, each reference being a fixed-width machine address (§04). A language that lets you write A[i] for heterogeneous contents has only two ways to keep the formula valid: store a fixed-width reference in each cell and put the object elsewhere (§04, and by far the commonest answer), or pad every cell to one fixed width large enough for a type tag plus the largest inline payload — the tagged-slot layout used by value types and by some dynamic-language runtimes that pack small values into a machine word. What it cannot do is lay variable-width objects end to end and still index them by arithmetic.
  • Offset, counted from 0. Zero-based indexing is not a stylistic preference; it is what makes the formula have no correction term. With 1-based indices the address becomes base + (i − 1) × itemsize, which is the same thing with an extra subtraction on every single access. Languages that index from 1 either pay that subtraction or bias the stored base pointer by one cell to absorb it.

What the definition does not say

  • Nothing about the contents being ordered. An array is not a sorted sequence. Order is something an algorithm may impose on it (and then exploit — see §16); the structure itself promises only positions.
  • Nothing about the size being known at compile time. Fixed-size means fixed once created. The block may be allocated at run time with a length computed at run time; what it may not do is grow, because the memory immediately after the block belongs to someone else. Growth is faked by allocating a new block and copying — which is the whole of §06.
  • Nothing about bounds being checked. The address formula happily computes an address for i = −5 or i = n + 1000. Whether that address is rejected, silently read, or used to corrupt something is a language decision layered on top of the structure, not a property of it. The structure's contract is arithmetic, not safety.

The motivation, stated as a cost argument

Every container has to answer the question "where is element i?". There are only two families of answer. Compute it — which requires that positions be predictable, which requires uniform cells laid consecutively; or store it — which requires a reference per element and a traversal to reach the reference. The first family is arrays and everything built directly in them: strings, matrices, hash tables, binary heaps, ring buffers, the tape a tokenizer scans. The second is linked nodes and everything built from them: lists, most trees, adjacency lists. The entire rest of this series is a series of positions taken between those two answers, and this page is the first of them because the contiguous block is what the others are measured against.

Address arithmetic: one multiply, one add, at any index move the index — the step count for the array does not move with it

The two bars are the argument. The indexed access is two arithmetic operations at every index — the bar never grows, because the formula never consults the elements it skips. The pointer walk is one dereference per element skipped, so its bar is the index itself. At i = 11 the contest is 2 against 11; at i = 10⁶ it is 2 against a million. Notice also what the byte offset row does when you change itemsize: the index arithmetic is unchanged, only the scale factor moves. That is why the same index formula serves an array of bytes and an array of 64-bit pointers without modification, and why itemsize has to be a property of the array's element type rather than of any individual element.

The one-line version. An array is the data structure you get when you decide that position shall be computable. Everything it is good at, and everything it is bad at, is downstream of that decision.

02 The memory model: words, lines, and why contiguity is the whole story

The RAM model that prices every bound in this series says that one memory access costs O(1), uniformly, wherever the address points. That is the right model for deriving asymptotics and the wrong model for predicting a runtime, and the gap between the two is where arrays earn most of their practical advantage. This section sets out just enough of the real machine to make the rest of the page's performance claims meaningful.

The layers, and the numbers that matter

  • A byte is the unit of address. Consecutive addresses differ by one byte; the address formula of §01 is arithmetic on byte counts.
  • A word is the unit the processor computes on — 8 bytes on a current 64-bit machine. A pointer is one word. An index into any array that fits in memory is one word. The word-RAM assumption that a word holds Θ(log n) bits is exactly the assumption that an index fits in a register.
  • A cache line is the unit of transfer, and it is the one most people never think about. Memory does not move between DRAM and the processor one byte or one word at a time; it moves in aligned blocks, typically 64 bytes on x86 and 64 or 128 bytes on ARM. Touching one byte fetches the whole line containing it.
  • A page is the unit of virtual-memory mapping, typically 4 KB, and the unit at which a translation lookaside buffer miss is paid. It matters for very large strided traversals; the cache line matters for almost everything else.
  • The latency spread. On a current mainstream core an L1 hit resolves in roughly 4–5 cycles, an L2 hit in roughly 12–15, an L3 hit in roughly 40, and a DRAM access somewhere in the region of 200 cycles (published figures vary from about 100 to 400 with the part, the frequency and the access pattern). That is a factor of forty to fifty between the cheapest and the most expensive "one memory access", all of which the RAM model prices identically.

What contiguity does with a cache line

An array of 4-byte integers packs 16 elements into one 64-byte line. A sequential scan therefore pays one memory transaction per sixteen elements and gets fifteen of them free — and because the access pattern is a constant stride, the hardware prefetcher recognises it and starts fetching the next line before it is asked for, which can hide the latency of even the paid one. The same n elements held as separately allocated nodes, each carrying a value and a pointer, occupy n lines in the worst case and are reached in an order the prefetcher cannot predict. Both traversals are Θ(n). They are not remotely the same speed.

The name for the property the array has and the node chain does not is locality of reference: the tendency of a program to touch addresses that are near ones it has recently touched (spatial locality) or to touch the same address again soon (temporal locality). Caches are a bet that programs have both. A contiguous array traversed in order is the best possible spatial locality — every byte fetched is used — and that is the single sentence behind most of this page's constant factors.

Three consequences that recur for the rest of this page

  • Traversal order is a performance decision, not a stylistic one. Walking a matrix along its storage direction touches each line once; walking across it can touch a fresh line on every element. §09 measures exactly that, under a stated cache model.
  • A "linear scan beats the clever structure" result is usually this effect. For small n — and "small" can mean a few hundred elements — scanning a packed array often beats a hash table or a balanced tree whose asymptotics are strictly better, because the array does one or two memory transactions and the tree does one per level, each a cache miss. The crossover is real, it is machine-specific, and the only way to find it is to measure.
  • Space is a time cost. Every extra byte per element is a fraction of a line wasted and a proportional increase in transactions. This is why a compact array of numbers (§04) is not merely more memory-efficient than an array of boxed references; it is faster by the same factor, on the same algorithm.
Model discipline, restated. Every asymptotic bound on this page is a bound in the RAM model, where all accesses cost the same. Every claim about one structure being faster in practice than another with the same bound is a claim about this section — line transfers, not step counts. Keep the two ledgers separate and both are useful; mix them and you will find yourself defending an O(1) access that takes 200 cycles.

03 The array ADT versus the array implementation

There are two different things called "array" and conflating them causes most of the confusion about what arrays cost. One is an abstract data type — a named set of operations with a stated contract. The other is a layout in memory — the contiguous block of §01. The ADT says what you may ask for; the layout says what each request costs. Keeping them apart is the habit that lets you read a library's complexity table and know what it is telling you.

The array ADT, minimally

the operations, and the contract each carriescreate(n) allocate n cells; n ≥ 0 (a zero-length array is legal); size fixed from here on length() the number of cells O(1) get(i) the value in cell i; requires 0 ≤ i < n O(1) set(i, v) write v into cell i; requires 0 ≤ i < n O(1) clear(v) write v into every cell Θ(n) iterate() visit cell 0, 1, …, n−1 in order Θ(n)

That is the whole interface. The hardware offers exactly three of these — allocate, read a cell, write a cell — and everything else on the list is a convenience written in terms of them. Notice what is absent: no insert, no delete, no search, no sort, no resize, no concatenation. Those are operations of richer sequence types, and their absence here is the point: the array ADT is deliberately impoverished so that every operation it offers is constant time. A structure whose interface contains nothing expensive is a structure you can reason about at a glance.

Why an impoverished interface is a feature

  • It makes the cost of the richer type visible. When a list type offers insert(k, v) and the array does not, the difference is not a missing feature — it is a shift loop, priced at Θ(n − k) in §05. Starting from the poor interface forces you to see the loop.
  • It makes the storage exactly the data. A fixed array of n elements occupies n × itemsize bytes and not a byte more. A growable list holds spare capacity — commonly up to twice what is needed — which is the price of amortized append (§06). When the count is known in advance and never changes, paying it is waste: a preallocated block of 100 000 numbers is 100 000 cells, where a doubling list that reached the same length may hold capacity for 200 000.
  • It is what every other structure in this series is built out of. A binary heap is an array plus index arithmetic. A hash table is an array plus a function from keys to indices. A ring buffer is an array plus two indices modulo n. A dense matrix is an array plus a stride. None of them need more than the six operations above from the layer beneath.

All three satisfy the ADT. All three are O(1) access in the RAM model. They differ by a constant factor of memory traffic that §02 says can reach an order of magnitude, and they differ in whether the elements are near each other, which is what decides whether a traversal runs at cache speed or at DRAM speed. This is the general shape of the ADT/implementation distinction and it will recur in every part of this series: the interface fixes what you can ask, the asymptotics are often identical across implementations, and the choice is then decided by constants, by space, or by which operations are hot.

How to read a complexity table. When a language's documentation says indexing is O(1) and insertion is O(n), it is describing the implementation, not the ADT — and the numbers only mean something once you know which of the three rows above it is. A list in a dynamic language is row two plus dynamic growth; an ndarray of a numeric type is row one; a "2-D list" is row three. Those are three different memory models wearing the same subscript syntax.

04 Referential arrays versus compact arrays

§01 required every cell to be the same width. Real collections routinely hold things that are not the same width — strings of different lengths, objects of different classes, integers of unbounded magnitude. The universal resolution is to store a fixed-width reference in the cell and the variable-width object elsewhere. That keeps the address formula intact and quietly changes almost every constant on the page.

The two layouts

  • Compact. The cell is the datum. An array of 4-byte integers holds the integers' bits; a string holds the characters' code units. itemsize is the element's own size, the block is exactly n × itemsize bytes, and one memory access gets you a value.
  • Referential. The cell holds a machine address — one word, 8 bytes on a 64-bit machine — and the object lives wherever the allocator put it. itemsize is 8 regardless of what is being stored, so the block is 8n bytes plus the objects, and getting a value costs two memory accesses: read the slot, then follow it.
bytes for n elements, compactn × itemsize (4n for 32-bit ints) bytes for n elements, referential8n + n × sizeof(boxed element) (often 8n + 16n to 8n + 28n) a worked case: one million 64-bit integerscompact: 1 000 000 × 8 B = 8 MB, one contiguous block referential: 1 000 000 × 8 B of pointers + a boxed integer object each, typically 16–28 B apiece ⇒ roughly 24–36 MB, scattered so the same data, same asymptotics≈ 3–4.5× the memory and ≈ 2× the memory accesses per element read why the box is never smalla heap object carries a header — a type/class word and usually a size or refcount word — and is padded to the allocator's alignment, so 16 B is about the floor for a boxed 32-bit int

Three consequences worth naming

  • Aliasing becomes possible. Two cells may hold the same address, so two entries of a referential array can be the same object. Copying the array copies the references, not the objects — which is exactly right for immutable elements and a trap for mutable ones. §10 is about the bug this causes.
  • Element access is a dependent load. The second access cannot begin until the first returns, so the processor cannot overlap them. On a cache-resident array this costs a few cycles; on a large scattered one it can cost two DRAM round trips per element, which is the practical reason numerical code insists on compact storage — the ndarray is a compact array with a dtype, and that is most of why it is fast.
  • The compact form requires a declared element type. You cannot pack elements end to end without knowing their width, and you cannot know the width without knowing the type. This is why compact arrays in dynamically typed languages always come with a type code attached, and why a general-purpose list cannot be compact.

Pointers built out of indices

The relationship also runs the other way: if you have arrays but no pointers, you can synthesise pointers from indices, and this is worth seeing once because it demystifies what a pointer is. Represent a collection of records with one array per field — key[], next[], prev[] — and let the "pointer" to a record simply be a common index x into all three. Then x.next is next[x], a null pointer is any index the arrays cannot legally take (0, if the arrays are 1-based, or −1 if 0-based), and a linked list is a chain of array indices. The alternative single-array representation packs each record into a contiguous run A[j .. k], makes the "pointer" the start index j, and reaches a field by adding its fixed offset — which is precisely §01's address formula applied at the granularity of records rather than machine bytes. A pointer really is nothing more than an index into one enormous array called memory.

The decision rule. Use compact storage when the elements are numbers of a known width and the workload traverses them; use referential storage when the elements are large, heterogeneous, shared, or immutable enough that copying references is the right semantics. The asymptotics are identical either way, so the choice is made entirely on §02's ledger — bytes moved and dependent loads — plus the aliasing semantics you want.

05 What indexing buys, and what insertion costs

The contiguity that makes get(i) one step is the same contiguity that makes insert(k, v) a loop. There is no slack between cell k and cell k+1 — that is what "consecutive" means — so making room means moving every element from k to the end one position right, and closing a hole means moving every element after it one position left. Nothing is being decided cleverly here; the cost is a direct consequence of the layout, and it is the price paid for the O(1) access.

insert v at index k into n live elements (room already available)for j = n down to k+1: A[j] = A[j−1] // shift right, rightmost first A[k] = v; n = n + 1 element movesn − k worst case k = 0 ⇒ n, best case k = n ⇒ 0 delete the element at index kfor j = k to n−2: A[j] = A[j+1] // shift left, leftmost first A[n−1] = null; n = n − 1 element movesn − 1 − k worst case k = 0 ⇒ n−1, best case k = n−1 ⇒ 0 average over a uniformly random position(1/(n+1)) · ∑ₖ₌₀ⁿ (n − k) = (1/(n+1)) · n(n+1)/2 = n/2 = Θ(n)

Two details that are easy to get wrong

  • The shift direction matters. An insert must copy the rightmost element first; going left to right would overwrite each element with its predecessor before the element had been read, smearing A[k] across the tail. A delete must go the other way, leftmost first. Both loops are one line and both have exactly one correct direction — a classic source of silent corruption when the loop is written from memory.
  • The average is Θ(n), not a constant. "Inserting in the middle is only half as expensive" is true and irrelevant: n/2 is still linear. The only positions that are genuinely cheap are the ones at or near the end, which is why the end of an array is a privileged place and why every array-backed stack, queue and buffer is designed so that the mutation happens there.
  • A real implementation does not write that loop. For a compact array the whole shift is one block move of a contiguous byte range — the memmove primitive, which is specified to behave correctly when source and destination overlap and therefore handles the direction question of the previous bullet for you. A tuned memmove copies a cache line or a vector register at a time and can move an order of magnitude more bytes per cycle than a scalar element loop. It does not change the asymptotics: the work is still proportional to n − k bytes moved, and the constant, while small, is not zero. This is the standard shape of the distinction — a Θ(n) operation with an excellent constant is still Θ(n), and a loop that performs n of them is still quadratic.

Read the table as a single sentence: arrays are fast to read anywhere and fast to modify only at the end. That is the contract. Every structure in the rest of this series exists because some workload could not live with it — a linked list buys O(1) insertion at a known position by giving up computed access; a hash table buys expected-constant insertion and lookup by giving up order; a balanced tree buys logarithmic everything by giving up the contiguous block entirely.

The move that removes the shift. When deletions are frequent and order does not matter, deleting at index k can be done in O(1): overwrite A[k] with A[n−1] and decrement the count. This "swap with the last" trick is everywhere in simulation and game code, and it is a perfect example of paying with a property you did not need — you give up the relative order of the elements and get a linear operation for a constant one.

06 Dynamic arrays: growing a thing that cannot grow

A block of memory cannot be extended in place — the bytes after it belong to something else. So a growable array is a lie told convincingly: the structure holds a block with spare capacity, tracks how much of it is live, and when the spare runs out allocates a larger block, copies everything across, and frees the old one. A single append can therefore cost Θ(n). The result that makes the structure usable is that a sequence of n appends costs Θ(n) in total, so each append is O(1) amortized.

Where the derivation lives

This is the case study of amortized analysis, and it is worked three separate ways — the aggregate method, the accounting method with its three-credit charge, and a potential function Φ = 2·num − size built from its design constraints rather than guessed — in the dynamic-array section of Algorithm Analysis, together with instrumented figures showing the per-append spikes and the running mean. Two results from there are worth carrying here because they change how you use the structure, and neither is obvious from the O(1):

  • Amortized is not average-case, and the difference is what is being averaged over. An average-case bound averages over a probability distribution on inputs — it is a statement about what usually happens, and a sufficiently unlucky input can beat it. An amortized bound averages over a sequence of operations on one structure, with no probability anywhere: it is a worst-case guarantee on the total, so no input at all can make n appends cost more than 3n. The two are often confused because both produce a divided-by-n number. Say which denominator you mean and the confusion cannot survive.
  • The per-operation latency is not amortized. An amortized bound is a statement about a sequence. The individual append that triggers a reallocation genuinely copies n elements and genuinely takes linear time, and in a latency-sensitive loop that shows up as a periodic spike exactly when the structure doubles. If you need a worst-case bound per operation, a dynamic array does not give you one; you either preallocate the final capacity or use a structure that resizes incrementally.
  • Shrinking has to be hysteretic. If the array halves its block as soon as it is half empty, an adversary alternating append and delete at the boundary forces a reallocation on every operation and the amortized cost degrades to Θ(n). The standard fix is to shrink only when the array falls to one quarter full, and to shrink to half: a structure holding num = size/4 that reallocates to size/2 comes out exactly half full, so it needs size/4 further appends to fill up again and size/8 further deletions to fall to the next shrink threshold — Θ(n) cheap operations before the next resize in either direction. The general principle — after any resize, leave enough slack in both directions that a linear number of cheap operations must pass before the next one — reappears for every structure that resizes, notably hash tables.

Why the geometric rule is not negotiable

The tempting alternative is to grow by a fixed number of cells — "add 1000 each time" — which wastes less memory. It is asymptotically catastrophic. With a fixed increment c, reaching n elements requires m = n/c reallocations at sizes c, 2c, 3c, …, mc, and the copying cost is the sum of those sizes:

arithmetic growth — increment c per resizetotal copies = c + 2c + 3c + ⋯ + mc = c·m(m+1)/2, with m = n/c = (n/c)·(n/c + 1)·c/2 = Θ(n²/c) = Ω(n²) for any constant c geometric growth — factor g > 1 per resizetotal copies ≈ 1 + g + g² + ⋯ + g^(K−1) = (g^K − 1)/(g − 1) ≈ n/(g − 1) = Θ(n) the structural reasona geometric series is dominated by its LAST term; an arithmetic one is not

An increment of 1000 does not rescue it — it divides a quadratic by 1000 and leaves it quadratic, which is invisible at n = 10⁴ and fatal at n = 10⁷. The property that matters is that the amount of new space is proportional to the current size, so that the work done by each expansion is paid for by a number of cheap appends proportional to that same size. Any rule with that property gives O(1) amortized; no rule without it does.

What to take away. Appending to a dynamic array is constant time in the only sense that matters for throughput, and linear time in the sense that matters for a latency budget. Both statements are true simultaneously, they are not in tension, and confusing them is the single commonest misreading of an amortized bound.

07 Choosing the growth factor

Doubling is a convention, not a theorem. The amortized O(1) holds for any constant factor g > 1, so the factor is a free parameter and choosing it is a genuine engineering trade: a larger g means fewer copies and more wasted space; a smaller g means less waste and more copying. The left one drops steeply as g rises from 1.1 — where at n = 1000 the counter records about 11.9 elementary writes per append — and then flattens hard: by g = 1.5 it is about 3.1, by g = 2 about 2.02, and by g = 4 about 1.34. Past 2 you are buying a fraction of one write per append for another 25 percentage points of memory. The right panel climbs the other way — jaggedly, because where the run happens to stop decides how much slack is live at the end — from a measured mean of about 4% at g = 1.1 to roughly 25% at g = 2 and 38% at g = 4, beneath a dashed worst case of 1 − 1/g that reaches three quarters. The knee is in the region of roughly 1.5 to 2, and the reason the conventional answer is 2 rather than 3 or 4 is that the left curve has already done nearly all of its falling by then.

Real containers are spread across a wider band than that knee suggests, because they weigh the two panels differently. Factors of 2 (several systems languages' vectors, and the growth of small slices in others) and 1.5 (several standard library list types, and one widely used C++ standard library implementation) are the commonest, but implementations that care more about memory than about copies go lower — around 1.25 for large blocks in one mainstream runtime, and about 1.125 for the list type of one widely used dynamic language, whose rule adds size/8 plus a small constant. All of those are geometric, so all of them are O(1) amortized; they differ only in where on this figure's two curves they choose to stand. The right reading of the figure is therefore "anything from about 1.1 to about 2 is a defensible engineering choice", not "the answer is 2".

Two effects visible in the figure that are not in the formula

  • The measured curve sits above the closed form, sometimes by a lot, and the gap is not an error. At g = 2, n = 1000 the measurement is 2.023 against a prediction of 2.000; at g = 3 it is 2.09 against a prediction of 1.50, which looks like a failure and is not. g/(g−1) is the limit of the running mean, and the running mean is a sawtooth — it jumps when a copy is charged and decays as cheap appends dilute it. Where you stop counting decides which part of the tooth you read. Stopping just after an expansion reads high; stopping just as the block fills exactly reads low. This is a general hazard of amortized measurement, treated at length in the amortized-analysis case study: a partial sequence is not a sequence.
  • The first few expansions are not geometric at all. A rule stated as a factor cannot grow a one-slot block — floor(1 × 1.5) = 1 — so the simulation, like every real implementation, uses max(size + 1, floor(size × g)). At small g the first several expansions therefore add a single cell each and the geometric argument has not started. Real containers avoid the region entirely by starting from a minimum capacity of four or eight.

Why an allocator might prefer 1.5

There is a second, subtler argument for a factor below 2 that has nothing to do with the slack percentage. It rests on three assumptions that have to be stated, because the argument is false without them: that the allocator hands out blocks at consecutive addresses, that it coalesces adjacent freed blocks back into one usable run, and that the old block is released only after the new one has been allocated and copied into (which is what a growable array has to do).

Under those assumptions, follow the arena. With doubling, the capacities are 1, 2, 4, 8, …; at the moment the block of 8 is requested, the block of 4 is still live and only 1 + 2 = 3 bytes of coalesced free space sit below it. Even counting the live block, the whole history is 1 + 2 + 4 = 7 < 8 — so no doubling request can ever be satisfied from the space its predecessors occupied, however the timing works out, and the arena grows monotonically. With g = 1.5 the capacities run 1, 2, 3, 4, 6, 9, 13, … and the sums catch up: when the block of 9 is requested the live block is the one of 6, the blocks of 1, 2, 3 and 4 have all been released, and they coalesce into a contiguous run of 10 ≥ 9 — so the new block can be carved out of the hole its own predecessors left.

the condition, in the limit, for the freed run to cover the next requestfreed after k expansions ≈ g⁰ + g¹ + ⋯ + g^(k−2) = (g^(k−1) − 1)/(g − 1) require it to reach the next request g^kg^(k−1)/(g − 1) ≥ g^k ⇔ 1/(g − 1) ≥ g ⇔ g² − g − 1 ≤ 0 the root of g² − g − 1 = 0g = (1 + √5)/2 = φ ≈ 1.618 sog < φ ⇒ the freed run eventually overtakes the next request, and space is reused g ≥ φ ⇒ it never does, and every expansion consumes fresh arena

Whether any of this matters depends entirely on the allocator, and modern size-class allocators — which round requests to fixed buckets and never coalesce across buckets — make the argument largely moot. It is the argument usually offered for preferring 1.5 to 2, and it is worth knowing for that reason and because it is a clean example of a constant-factor consideration that no asymptotic analysis can see. It is not, however, a proof that 1.5 was chosen for this reason in any particular implementation; treat that as folklore unless you have read the commit that made the choice.

Preallocation beats every factor. If you know the final length, ask for it up front. That turns the whole discussion off: no expansions, no copies, no slack, exactly n cells and exactly n writes. The growth factor is a policy for when you do not know — which is most of the time, which is why the policy exists.

08 Multidimensional arrays: rows, columns, and strides

Memory is one-dimensional. A matrix is not. So a two-dimensional array is always a convention for flattening — a rule that turns a pair of subscripts (i, j) into a single offset. There are exactly two sensible rules, they differ only in which subscript varies fastest along the block, and the choice is invisible to correctness and enormous to performance.

row-major: the last subscript varies fastest — rows are contiguousoffset(i, j) = i × ncols + j address = base + offset × itemsize column-major: the first subscript varies fastest — columns are contiguousoffset(i, j) = j × nrows + i the general d-dimensional form, in terms of stridesoffset(i₁, i₂, …, i_d) = i₁·s₁ + i₂·s₂ + ⋯ + i_d·s_d row-major strides for shape (n₁, n₂, …, n_d)s_d = 1, s_k = n_(k+1) × n_(k+2) × ⋯ × n_d (each stride is the size of one slice below it) costd multiplies and d−1 adds — O(d), independent of every nₖ. Still O(1) for fixed d.

A worked offset

Take a 3 × 5 array of 4-byte values with base = 4096. Row-major strides are s₁ = 5, s₂ = 1. Then element (2, 3) — third row, fourth column, counting from zero — sits at offset 2 × 5 + 3 = 13, so at address 4096 + 13 × 4 = 4148. Under column-major the strides are s₁ = 1, s₂ = 3, the same element sits at offset 3 × 3 + 2 = 11, and its address is 4096 + 44 = 4140. The same logical element, two different addresses, because the flattening rule is different. Nothing about the matrix changed; the convention did. This is why passing a buffer between two libraries that disagree about the convention transposes your data silently, and why every serious array library records the strides explicitly rather than assuming them.

Strides make views free

Once the offset is a dot product of subscripts with strides, several operations become pure bookkeeping on the stride vector, touching no data at all:

  • Transpose — swap the two strides and the two dimension lengths. O(1). The transposed view is row-major read as column-major; no element is moved, which is precisely why a transposed view then traverses badly (§09).
  • A row slice — keep the row stride, advance the base by i × s₁ × itemsize. O(1), and the result is itself contiguous.
  • A column slice — keep the base, take stride s₁ with length nrows. O(1), and the result is not contiguous: a column of a row-major matrix is a strided walk with a gap of ncols − 1 elements between consecutive entries.
  • Every other step, reversal, broadcasting a length-1 axis — all expressible as changes to strides and lengths. The ndarray is exactly this idea made into a type, and "is this array contiguous?" is a question its users learn to ask because the answer decides whether an operation copies.

The other layout: an array of arrays

Instead of one flat block, hold an array of nrows references, each pointing at its own row block. A[i][j] then means "read the reference in slot i, then index into that block at j" — two address computations and two dependent memory accesses. The consequences are a clean list of trade-offs:

The flat block is what numerical and image code uses; the array of rows is what a general-purpose language gives you when you write a list of lists, and it is why a "2-D list" and a real 2-D array have such different performance despite identical subscript syntax. Higher dimensions extend both schemes without any new idea — a 3-D array is a flat block with three strides, or an array of arrays of arrays, and the same table applies one level deeper.

The matrix ADT sits on top of either. A matrix is a 2-D array plus the operations that make it a matrix: scalar multiply, add and subtract (all elementwise, all Θ(nrows × ncols)), transpose, and the multiply that costs Θ(n³) by the schoolbook method and less by divide-and-conquer methods such as Strassen's. The storage decision above is invisible in that interface and decisive in its constants — which is the §03 lesson again, in the place where it costs the most.

09 Traversal order and the cache, measured

Traversal order is the sequence of addresses a loop nest actually visits, and for a multidimensional array it is decided by which subscript sits in the inner loop. A nest whose inner subscript is the fastest-varying one — j for a row-major array — walks the block from front to back, one offset at a time. A nest that puts the other subscript inside walks it in jumps of one full row. Both visit exactly the same n² cells, do exactly the same arithmetic and produce exactly the same output, so no complexity analysis can tell them apart; measured on a machine they can differ by close to an order of magnitude. This is the canonical demonstration that asymptotics and running time are different questions, and it is worth doing once with the misses actually counted rather than asserted.

At the default settings — n = 8, eight elements per line, a four-line cache — the row-major sweep records 8 misses and 56 hits: it enters each of the eight lines once and then reads the other seven elements of that line for free. Select the column-major traversal and the same sweep records 64 misses and 0 hits, one per access — its tape turns solid red. That is a factor of eight, which is not a coincidence: it is L, the line size, because the bad order throws away exactly the L − 1 elements that came along for the ride with every fetch. Raise the line size and the ratio rises with it; raise C until the whole matrix fits and the gap collapses, because at that point the cache is big enough that even the bad order revisits resident lines.

Read the controls as an experiment, not a demo

  • The gap is governed by the working set, not by the order as such. A column sweep of a row-major matrix touches one element from every line in the array before it returns to the first — a working set of n²/L lines. If the cache holds that many, every miss is compulsory and both orders take ceil(n²/L). Push C to 8 with n = 4 and L = 4 and you can watch the two bars meet. On a real machine the same collapse happens for small matrices and is the reason a micro-benchmark on a 64 × 64 matrix can show no effect at all while a 4096 × 4096 one shows a factor of ten.
  • The fix is to change the order, not the algorithm. Swapping the loop nest so the inner variable indexes the fastest-varying subscript costs nothing and is the single highest-leverage change available in array code. Where the algorithm genuinely needs both orders — matrix multiply reads one operand along rows and the other along columns — the standard answer is blocking: process the matrices in tiles small enough that a tile's working set fits in cache, so each loaded line is fully used before it is evicted. The asymptotic count of multiplications is unchanged; only the miss count moves.
  • The model here is deliberately simple, and its errors do not all point the same way. The formula block above states the model exactly — fully associative, LRU, C lines of L elements, initially empty — and every number the figure prints is a count under that model, not a prediction about a machine. Three ways a real cache departs from it, with the direction of each departure named honestly:
    • Set associativity widens the gap. A real cache maps an address to one of a few ways in a fixed set. A column sweep whose stride is a large power of two can land on the same set every time, so the column's working set thrashes a handful of ways instead of the whole cache — conflict misses the fully associative model cannot produce. The column side gets worse; the row side is untouched. The figure understates the gap here.
    • Address translation widens the gap for large arrays. Each step of a column sweep advances by one row. Once a row is as large as a page, every access lands on a new page and the translation lookaside buffer misses as well as the cache. The row-major sweep pays one TLB miss per page; the column sweep can pay one per access. None of this is in a model that counts only cache lines.
    • Prefetching does not straightforwardly widen it, and can narrow it. This is the claim to be careful with. First, a prefetch does not remove a line transfer — the line is still fetched from memory; the prefetcher only issues the request early enough to hide the latency. The miss counts this figure reports are therefore unchanged by prefetching; what changes is time, which is a different ledger. Second, and more to the point, the hardware prefetchers on mainstream cores track constant strides, not just unit strides — and a column sweep of a row-major matrix is a perfectly constant stride. When the row is small enough that the stride stays inside the prefetcher's window (typically a few hundred bytes) and does not cross a page boundary — most prefetchers will not prefetch across one — the column sweep gets prefetched too, and the measured time gap narrows relative to what a pure miss count predicts. For large matrices, where the row stride exceeds those limits, prefetching helps only the row-major side and the gap widens. So the honest statement is: the direction of the prefetching correction depends on the row length, and the figure's miss counts are not a proxy for it either way.

What the figure does license, then, is the narrow claim and not the broad one. Under the stated model, at the stated parameters, the bad order pays L times the line transfers of the good one, and that ratio is a theorem about the model. Whether a particular machine shows a factor of eight, or three, or none at all is an empirical question about associativity, prefetchers, page size and the size of the matrix, and the only way to settle it is to measure on that machine. The reason to trust the qualitative conclusion anyway is that the mechanism — a fetched line whose other L − 1 elements are discarded before they are used — is real on every cache ever built.

Why this belongs on a page about arrays. Contiguity is not merely a way to compute addresses; it is a promise about which elements arrive together. An algorithm that consumes elements in storage order collects on that promise and one that does not throws it away. Every later structure in this series can be judged on the same axis, and it is most of the reason a flat array with a worse asymptotic bound so often beats a pointer structure with a better one.

10 Slices, views, copies — and the aliasing bug

A slice is a contiguous run of an array named as if it were an array itself. Because the run is contiguous, it can be described by three numbers — base, length, stride — and therefore there are two entirely reasonable things a language can mean by A[2:6]: a view that shares the original storage, or a copy that owns new storage. They have different costs and, far more dangerously, different semantics under mutation.

a slice as a triple, with no data touchedview(A, lo, hi) = (base + lo × itemsize, length = hi − lo, stride = 1) costview: O(1) time, O(1) extra space, writes are visible through the original copy: Θ(hi − lo) time and space, writes are private a strided sliceview(A, lo, hi, step) = (base + lo × itemsize, length = ceil((hi − lo)/step), stride = step)

Three layers of "copy", and which one a language gives you

  • No copy — a view. The slice is a window onto the same bytes. Free to make, and every write through either name is seen through the other. This is what array libraries built for numerical work do, because copying a 100 MB sub-matrix to read one row would be absurd.
  • A shallow copy. A new block of cells is allocated and the cell contents are copied. For a compact array of numbers that is a full copy and there is nothing more to say. For a referential array the cells contain addresses, so what is copied is the addresses — the new array points at the very same objects. The containers are independent; the elements are shared.
  • A deep copy. The cells and, recursively, the objects they refer to are duplicated. This is the only one that gives complete independence, it is the most expensive, and it is the one a language almost never gives you by default.

The bug, in its standard form

The classic failure is building a grid of rows by replicating a row. Replication in a referential array copies the reference n times, so all n "rows" are one row under n names. Writing one cell appears to write a whole column:

what was intendedgrid = n copies of a fresh row of zeros what replication actually buildsgrid[0] = grid[1] = … = grid[n−1] = the SAME row object sogrid[0][2] = 7 ⇒ grid[i][2] == 7 for every i the fix — construct a distinct row per indexgrid[i] = a new row of zeros, allocated once per i

The same mechanism produces the subtler version: appending a mutable element to a list and then mutating it afterwards changes what the list holds, because the list holds the object rather than a snapshot of it. Both bugs feel like the container misbehaving; both are the container behaving exactly as documented, on a mental model in which cells hold values rather than addresses.

A defensive checklist

  • Know which of the three you got. Whether slicing yields a view or a copy is a documented property of the type you are using, and the two are indistinguishable until someone writes through one of them. If a function receives a slice and mutates it, the answer decides whether the caller's data changed.
  • Views keep the whole buffer alive. A 12-element view of a 100-million-element array holds a reference to the whole allocation, so the memory cannot be released. Extracting a small window from a large array and retaining it is a genuine leak pattern; the cure is an explicit copy at the point of extraction.
  • Sharing is only safe when the elements are immutable. This is the argument for immutable strings (§11) stated from the other side: if a value cannot change, sharing it can never surprise anyone, and every copy can safely be a reference copy.
  • Mutating a container while iterating over it is a separate hazard with the same flavour. Deleting during a forward scan shifts the tail left under the cursor and silently skips an element. Iterate over a copy, build a new array, or walk backwards.
The general rule. An array cell holds a fixed-width thing. Whether that thing is the value or the address of the value is the single most consequential fact about the type you are using, and almost every surprising behaviour of arrays and lists in a high-level language reduces to it.

11 What a string is: an array with two extra rules

A string is a compact array of character codes. That is the whole definition, and everything distinctive about strings follows from two decisions layered on top of it: the elements are drawn from an encoding rather than being plain integers, and in most modern languages the array is immutable. The first decision breaks the assumption that one character is one cell; the second turns an innocuous loop into a quadratic one.

Rule one: encodings, and why "length" is ambiguous

  • Fixed-width encodings keep §01 intact. ASCII or Latin-1 at one byte per character, or UTF-32 at four, make itemsize a constant, so s[i] is one address computation and the i-th cell is the i-th character. Simple, and wasteful for text that is mostly ASCII.
  • Variable-width encodings break it. In UTF-8 a code point occupies one to four bytes; in UTF-16 one or two 16-bit units. The cells are still uniform — they are bytes, or 16-bit units — but a cell is no longer a character. Indexing by code point then costs Θ(i), because you must decode forward from the start, and the O(1) promise of §01 quietly applies to a different unit than the one you meant.
  • So "the length of a string" has at least four answers — bytes, code units, code points, and user-perceived characters (grapheme clusters, where an accent or a skin-tone modifier joins the preceding character). They coincide for ASCII and diverge for everything else, and a great many text bugs are a disagreement about which one a piece of code is counting. Languages pick different defaults; libraries that slice by byte offset can cut a code point in half.
  • Implementations cheat productively. A common strategy is to store an all-ASCII string as one byte per character and widen only when a non-ASCII character appears, so the common case keeps constant-time indexing and the general case still works. The lesson is the §03 one: the interface says "a sequence of characters", and what it costs depends entirely on the layout underneath.

Rule two: immutability, and the loop everyone writes once

If a string cannot be modified, then s = s + ch cannot append. It must allocate a new block of length |s| + 1 and copy every character of s into it. Doing that in a loop to build a string of length n copies 1 + 2 + ⋯ + n characters:

The parabola sits exactly on its dashed closed form n(n+1)/2 at every point, which is the check that the counter is counting what the algebra describes. The green line is Θ(n) with a small constant — roughly three copies per character, one to place it, about one more for the array's amortized doubling (§06), and one for the final join. On the logarithmic axis the two become straight lines of slope 2 and slope 1, which is the cleanest possible statement that one is quadratic and the other linear. The asymmetry is brutal and grows without bound: at n = 200 the measured ratio is 30.7×, at n = 400 it is 61.2× — it roughly doubles when n does, because a quadratic divided by a linear is a linear.

Why immutability is chosen anyway

  • Sharing becomes free and safe. An immutable string can be handed to any number of holders, stored as a dictionary key, cached, interned, or shared between threads without a lock, because no holder can invalidate another's view. That is the §10 aliasing problem simply not existing.
  • Hashes and lengths can be cached. A value that cannot change can have its hash computed once and stored, which is what makes strings cheap dictionary keys.
  • Substrings can be views. If nobody can write, a substring can share the parent's buffer. (This is a real technique with a real cost — it keeps the parent alive, §10 again — so implementations differ on whether they do it.)
  • The escape hatch is a mutable builder. Every language that makes strings immutable provides a growable buffer for the times you need to accumulate: build there, convert once at the end. That is exactly the green line in the figure, and it is the only correct habit for assembling text in a loop.
A warning about the warning. Some runtimes special-case s += ch when they can prove there is exactly one reference to s, mutating the buffer in place and turning the quadratic loop linear. That optimisation is fragile — one extra reference anywhere and the quadratic behaviour returns — and it is not guaranteed across implementations. Do not write code whose complexity class depends on an optimiser noticing something. Collect and join.

12 The two-pointer pattern and its invariant

A family of linear-time array algorithms that all have the same shape: maintain two indices, move them in a disciplined way that never backtracks, and carry an invariant strong enough that when the indices meet the answer is decided. The pattern is worth naming because it converts a great many naive double loops from Θ(n²) to Θ(n) with O(1) extra space, and because the conversion is only valid when the invariant holds — which is what makes it a technique rather than a trick.

The two configurations

  • Converging pointers — one array; lo starts at 0, hi at n − 1, and they move toward each other until they meet or cross. Reversal, palindrome testing, the sorted two-sum and the container-of-most-water problem all live here. Termination is free: the gap hi − lo strictly decreases every iteration.
  • Chasing pointers — one array; a read index sweeps it while a write index trails behind, marking the end of the part already processed. Removing duplicates from a sorted array in place, stable partitioning by a predicate, and compacting out deleted entries all live here. Termination is free again: read increases every iteration and write ≤ read always.
  • Parallel pointers — two sequences, one index into each, both moving only forward, with the choice of which to advance made by comparing the two elements they point at. The merge step of mergesort is the canonical instance, and so are the sorted-set intersection, union and difference routines. It is worth separating from the first two because the termination argument is different: neither index is bounded by the other, and the loop ends when either sequence is exhausted, so the body needs an explicit drain of whatever remains. Total movement is still at most n₁ + n₂, which is why merging is linear.

A hand-worked trace: a pair summing to 17

Take the sorted array A = [1, 3, 4, 6, 8, 10, 13, 15] and target 17. Start with lo = 0, hi = 7 and compare the sum against the target at every step:

step 1A[0] + A[7] = 1 + 15 = 16 < 17 → 1 is too small to pair with even the largest element ⇒ lo = 1 step 2A[1] + A[7] = 3 + 15 = 18 > 17 → 15 is too large to pair with even the smallest survivor ⇒ hi = 6 step 3A[1] + A[6] = 3 + 13 = 16 < 17 → 3 is eliminated ⇒ lo = 2 step 4A[2] + A[6] = 4 + 13 = 17 = 17 → found, at indices (2, 6) cost4 sum evaluations, against the 8·7/2 = 28 pairs a double loop would test

The elimination argument is the whole proof. When the sum is too small, A[lo] has just been paired with the largest remaining element and still fell short; since every other candidate partner is smaller, A[lo] can be in no solution at all and may be discarded forever. The mirror argument discards A[hi] when the sum is too large. Each step therefore removes one element from consideration permanently, which is simultaneously the correctness proof (nothing that could be part of an answer is ever discarded) and the running-time proof (at most n − 1 steps before the pointers meet).

That argument has a standard shape, and it is worth naming because every correctness proof on this page uses it. A loop invariant is a statement about the program's variables that is true before the loop starts, is preserved by one iteration of the body, and — combined with the loop's exit condition — implies the thing you wanted. The three obligations have names: initialization (it holds on entry), maintenance (each iteration preserves it), and termination (when the loop stops, the invariant plus the exit condition give the result). Discharging all three is a proof; skipping the third is how an algorithm ends up correct on every test case and wrong on the empty input.

Switch to reverse for the other flavour, where the shading means something different — the cells outside [lo, hi] are finished rather than excluded — and where the invariant becomes "the two ends already hold their final mirrored values". Both routines are one pass and both use no extra memory beyond the two indices, which is the pattern's characteristic signature.

When the pattern applies, and when it does not

  • It needs a monotone consequence of moving a pointer. Two-sum works because the array is sorted, so moving lo right can only increase the sum and moving hi left can only decrease it. If no such monotonicity exists, advancing a pointer can skip an answer and the method is simply incorrect — no amount of care in the implementation repairs that.
  • Sorting first may still be worth it. Given an unsorted array, sorting for Θ(n log n) and then running two pointers for Θ(n) beats the Θ(n²) double loop for all but tiny n. A hash table solves the same problem in Θ(n) expected time without sorting, at the price of Θ(n) extra space and no worst-case guarantee — a good miniature of the recurring space-for-time trade.
  • Three pointers is the same idea one level up. The classic three-sum is a loop over the first element wrapping a two-pointer scan over the rest: Θ(n²) instead of Θ(n³). The three-way partition of §15 is a three-pointer routine in its own right.
  • Do not confuse the three forward-moving shapes. Converging pointers shrink one range from both ends. Parallel pointers walk two different sequences and the object of interest is the merged output. A sliding window's two indices walk the same sequence, both forward, and the object of interest is the region between them. All three share the "each index moves at most n times" accounting and nothing else, and it is that accounting — not any resemblance in the code — that makes all of them linear.

13 The sliding window, fixed and variable

A window is a contiguous range A[l … r] carried across the array together with a summary of its contents — a sum, a count, a character multiset, a maximum. The pattern works when the summary can be updated incrementally: O(1) to admit the element entering on the right, O(1) to evict the one leaving on the left. Then a question about all Θ(n²) contiguous sub-ranges collapses into one pass.

Fixed width: the easy case

With a window of fixed width k, both edges advance in lockstep. Compute the summary once for A[0 … k−1] in Θ(k), then slide: sum += A[r] − A[l−1]. Each of the n − k + 1 positions costs O(1), so the whole sweep is Θ(n) against the Θ(nk) of recomputing each window from scratch. This is the same algebraic move that Rabin-Karp's rolling hash makes on a window of characters and that a moving average makes on a time series; the summary just has to admit an inverse for the departing element.

Variable width: the interesting case

When the window's width is the thing being optimised, the right edge advances unconditionally in the outer loop and the left edge advances only as far as a feasibility condition requires. The structure looks quadratic — a while inside a for — and is not, for an amortization reason identical in spirit to the one behind amortized append:

That is the same accounting as amortized append and not a coincidence.

On pwwkew the doubled w forces a two-step eviction at r = 2, and the best window is wke — also 3, but reached differently, and a useful reminder that the answer is a length, not a unique substring. The sum variant inverts the logic: it shrinks greedily whenever the window is already good enough, so that the recorded length is always minimal for the current right edge, giving 2 for [4, 3].

Three things that go wrong

  • Applying it where the condition is not monotone. "Longest window with no repeat" works because removing elements can never create a repeat, so shrinking always moves toward feasibility. If a condition can be broken by shrinking, the left edge has no safe direction and the pattern does not apply — a window over an array containing negative numbers breaks "shortest window with sum ≥ target" for exactly this reason, and that problem needs prefix sums plus a search structure instead.
  • A summary that cannot evict in O(1). Maintaining the window's maximum with a plain variable is wrong: when the maximum leaves on the left, there is no way to recover the new maximum without rescanning. The fix is a monotone deque holding indices in decreasing value order, which keeps the answer at the front and still amortizes to O(1) because each index is pushed and popped once.
  • Recording the answer at the wrong moment. For a longest window, record after the shrink loop restores feasibility. For a shortest window, record inside the shrink loop, before the eviction that would break feasibility. Swapping those two placements produces code that runs, terminates, and returns the wrong number.
The shared accounting. Two pointers and sliding windows are both instances of one argument: an index that only moves forward can move at most n times, however deeply nested the loop that moves it appears to be. That is the same aggregate reasoning that gives amortized bounds, and it reappears verbatim in KMP's proof that its backtracking loop runs O(n) times in total.

14 Prefix sums and difference arrays

A prefix-sum array is a precomputed table of cumulative totals: P[i] is the sum of the first i elements, so that the sum of any contiguous range is the difference of two of its entries. One linear pass converts every future range-sum query from Θ(length) into O(1). It is the smallest interesting example of a precomputation trade — spend Θ(n) once, save on every query afterwards — and the first tool to reach for when a problem mentions "sum over a subarray".

the table, with the convention that makes the arithmetic painlessP[0] = 0, P[i+1] = P[i] + A[i] for i = 0 … n−1 so P has n+1 entries, and P[i] = A[0] + A[1] + ⋯ + A[i−1] the querysum(A[l … r]) = P[r+1] − P[l] one subtraction, O(1) why it telescopesP[r+1] − P[l] = (A[0]+⋯+A[r]) − (A[0]+⋯+A[l−1]) = A[l] + ⋯ + A[r] cost of q queriesprefix: Θ(n) + Θ(q) direct: Θ(q·n) in the worst case

Use the n+1-entry convention. Defining P[i] as the sum of the first i elements — rather than the sum up to and including index i — makes P[0] = 0 a real entry and removes the special case at l = 0 entirely. The alternative convention forces a conditional in every query, and that conditional is where the off-by-one lives.

Build once, subtract forever — with both answers computed and compared the bars are measured arithmetic operations over q random queries

Note the half-cell offset between the two rows: it is drawn that way because P indexes the boundaries between elements, not the elements, which is the mental model that makes the r+1 stop being a fiddly correction and start being obvious. The query bracket spans from the boundary before A[l] to the boundary after A[r]. Drag q and watch the bars separate: the prefix cost is a fixed build plus one operation per query, so it is essentially flat, while direct summation grows in proportion to q × (average range length). Both answers are computed on every draw and compared — the readout says so explicitly — because a range-query identity that is off by one is exactly the kind of thing that is right in the caption and wrong in the code.

The inverse trick: difference arrays for range updates

Prefix sums make range queries cheap on a static array. The dual construction makes range updates cheap when all the queries come at the end. To add v to every element of A[l … r], do not touch the range — record the change at its two boundaries in a difference array D, and reconstruct A by taking the prefix sums of D once, at the end.

the update, O(1) instead of Θ(r − l + 1)add v to A[l … r] ⇒ D[l] = D[l] + v; D[r+1] = D[r+1] − v the size of D — the fencepost againD has n+1 entries, so that D[r+1] is a legal write when r = n−1; the last entry is never read back the reconstruction, once, at the endA[i] = D[0] + D[1] + ⋯ + D[i] — a single prefix-sum pass, Θ(n) u updates then one readoutΘ(u + n) instead of Θ(u · n)

A hand-worked example. Start with A = [0, 0, 0, 0, 0, 0] and apply two updates: add 5 to A[1 … 3], then add 2 to A[2 … 4]. The difference array takes four writes in total — D[1] += 5, D[4] −= 5, D[2] += 2, D[5] −= 2 — leaving D = [0, 5, 2, 0, −5, −2]. Its running total is [0, 5, 7, 7, 2, 0]. Check it by hand: index 1 got only the first update (5 ✓); index 2 and 3 got both (7 ✓); index 4 got only the second (2 ✓); indices 0 and 5 got neither (0 ✓). Two range updates that between them touch six cells cost four writes — and because each update is two writes regardless of its width, the saving grows without bound with the range length: the same two updates over ranges of a thousand cells would still be four writes. The +v at l switches the contribution on and the −v at r+1 switches it off; the prefix sum is what integrates the switches back into values.

Where the idea generalises

  • Two dimensions. Build S[i][j] = the sum of the rectangle from (0,0) to (i−1, j−1), in one pass with S[i+1][j+1] = A[i][j] + S[i][j+1] + S[i+1][j] − S[i][j]. Any axis-aligned rectangle sum is then four table lookups by inclusion–exclusion — for the rectangle spanning rows l … r and columns k … c, it is S[r+1][c+1] − S[l][c+1] − S[r+1][k] + S[l][k]. The subtracted corner is added back because it was removed twice. This is the integral image that makes box filters and Haar-feature detectors constant-time per window regardless of window size.
  • Other operators. Any associative operation with an inverse works the same way — products (watch for zeros), XOR (its own inverse, which makes it especially clean), counts. Operators with no inverse, minimum and maximum being the usual culprits, cannot use the subtraction trick and need a sparse table or segment tree instead, which is exactly the point at which a flat array stops being enough.
  • Numerical caution. With floating-point elements the subtraction P[r+1] − P[l] subtracts two large nearly equal numbers and can lose most of its significant digits when the range is short and the prefix is long. For exact integer work this never arises; for accumulating floats it is a real concern and the reason numerical libraries offer compensated summation.
  • It is the base case of a bigger idea. "Store the answers to overlapping subproblems so you never recompute one" is the definition of dynamic programming, and a prefix-sum table is the smallest instance in which the recurrence, the table and the O(1) transition are all visible at once.

15 In-place rearrangement: reverse, rotate, partition

An operation is in place when it uses O(1) extra space beyond the input — a handful of index variables and one temporary, no second array. For arrays this is a class of algorithms worth knowing individually, because they are the primitives that larger routines are assembled from, and because "in place" is the property that decides whether an operation on a large array is possible at all rather than merely fast.

Reverse: the base primitive

Converging pointers, swap, close in. floor(n/2) swaps, Θ(n) time, O(1) space, and the invariant of §12. Everything below is built from it.

Rotate: three reversals

Rotating an array left by k looks like it needs a scratch buffer of k elements. It does not — and the reason is a small identity worth carrying: reversing two halves separately and then reversing the whole thing swaps the halves.

rotate A left by k, in placereverse(A[0 … k−1]); reverse(A[k … n−1]); reverse(A[0 … n−1]) why, in symbols, writing Xᴿ for the reversal of XA = X Y ⇒ after the first two: Xᴿ Yᴿ ⇒ after the third: (Xᴿ Yᴿ)ᴿ = Y X costfloor(k/2) + floor((n−k)/2) + floor(n/2) swaps ≈ n swaps = Θ(n) time, O(1) space

Worked by hand on A = [1, 2, 3, 4, 5, 6, 7] with k = 3. Reverse the first three: [3, 2, 1, 4, 5, 6, 7]. Reverse the rest: [3, 2, 1, 7, 6, 5, 4]. Reverse everything: [4, 5, 6, 7, 1, 2, 3] — the original rotated left by three, using 1 + 2 + 3 = 6 swaps and one temporary. The alternative cycle (juggling) algorithm moves each element directly to its destination by following the permutation's cycles, of which there are exactly gcd(n, k); it performs n element moves rather than about 2n, which is fewer writes, but it jumps through memory with stride k and therefore often loses to the three reversals on a real machine for exactly the reason §09 gives. Two algorithms, the same asymptotics, and the winner decided by the memory hierarchy.

Partition: two-way and three-way

Partitioning rearranges an array so that everything satisfying a predicate precedes everything that does not. The two-way version is one chasing-pointer pass — a write index trailing a read index, swapping whenever read finds a qualifying element — and it is the engine inside quicksort and quickselect. The three-way version, the Dutch national flag problem, is the one to know: it splits the array into three regions in a single pass, which is what makes quicksort robust on inputs with many duplicate keys.

three-way partition — one pass, three pointerslo = 0; i = 0; hi = n−1 while i ≤ hi: if A[i] < pivot: swap(A[lo], A[i]); lo = lo + 1; i = i + 1 elif A[i] == pivot: i = i + 1 else: swap(A[i], A[hi]); hi = hi − 1 // i does NOT advance invariant, maintained at the top of every iterationA[0 … lo−1] < pivot · A[lo … i−1] == pivot · A[hi+1 … n−1] > pivot · A[i … hi] unexamined terminationi + (n−1−hi) increases by one every iteration and is bounded by n ⇒ ≤ n iterations
Three-way partition, stepped — the four regions form as you advance the readout re-checks the output independently — sortedness and multiset

The single most error-prone line is the third branch: after swapping a 2 to the back, i must not advance, because the value that came back from position hi has never been examined. Advancing it there produces code that passes on many inputs and fails on some — try the exactly reversed preset, which is where the bug shows up soonest. The all equal to the pivot preset is the one that explains why three-way partitioning exists at all: the counter records zero swaps — its ten tests are the nine element dispatches plus the loop's final i > hi check — and the routine returns immediately with the whole array classified as "equal", so a quicksort built on it recurses on nothing.

What a two-way partition does on the same input depends on which two-way partition it is, and this is worth stating precisely because "quicksort is quadratic on duplicates" is repeated far more often than it is qualified:

  • The one-directional scheme — a single read index with a write index trailing it, testing A[read] ≤ pivot and swapping on success — sends every equal key to the low side. On an array of identical keys the split is n − 1 against 0, the recursion depth is n, and the total work is Θ(n²). This is the scheme most often written from memory, and it is the one the folklore is about.
  • The two-index scheme — pointers advancing from both ends that stop on a key equal to the pivot rather than scanning past it — swaps equal keys across the middle and splits an all-equal array almost exactly in half, giving Θ(n log n). The stopping-on-equal rule looks like wasted work on a single partition and is precisely what buys the balance; a version that scans past equal keys to "save a swap" reintroduces the quadratic case.
  • Three-way partitioning fixes it for both, and does more than fix it: by removing the entire equal-block from the recursion it makes an array with k distinct values sort in O(n log k) rather than O(n log n), which for something like a column of boolean or categorical values is a different complexity class rather than a constant-factor improvement.

What in-place buys, and what it costs

  • It buys feasibility at scale. An out-of-place operation on an array that is half of available memory cannot run at all. An in-place one can. This, not speed, is usually the reason it matters.
  • It buys locality. In-place routines touch one buffer instead of two, which halves the number of cache lines in flight — §09's ledger again.
  • It costs stability, sometimes. The swap-based two-way partition is not stable: equal elements can be reordered. A stable partition in Θ(n) time requires Θ(n) extra space, and doing it in O(1) space costs Θ(n log n) time. Where relative order carries meaning — sorting records by one field after another — that trade is the whole decision.
  • It costs the original. An in-place routine destroys its input by definition. If the caller needs the original as well, the copy you avoided inside has to be made outside, and nothing was saved.
  • Recursion is not free space. A routine that recurses is not O(1) space, however carefully its body avoids allocation: the call stack is auxiliary space, and it is Θ(depth). Quicksort is called "in place" by convention and still needs Θ(log n) stack when its recursion is balanced — a point the space section of Algorithm Analysis makes at length.

16 Binary search, and what it needs from the array

Binary search is the payoff for having both properties at once: an ordered sequence and constant-time access to any position. Either alone is not enough — you cannot halve a sorted linked list usefully, because finding its middle costs a traversal, and you cannot halve an unsorted array at all. It is therefore the clearest single demonstration of what contiguity is for, which is why it appears here; the family of variants and their proofs belong to Sorting & Searching.

Notice also that the successful search took three probes and the failing one four — a successful search is on average cheaper, because it can stop early, and the worst case belongs to the keys that are not there.

The three details that are always the bug

  • The midpoint must not overflow. (lo + hi)/2 is wrong in fixed-width integer arithmetic: for large arrays the sum exceeds the integer range before the division happens. lo + (hi − lo)/2 computes the same value and cannot overflow, because hi − lo is never larger than hi. This bug survived in widely used library code and in a canonical textbook for two decades, which is the best available evidence that binary search is harder to write than it looks.
  • The loop must shrink the range on every iteration. With lo ≤ hi and the mid ± 1 updates above, it does. The variants that write while lo < hi with hi = mid must take care that mid is never equal to lo when the range has two elements, or the loop spins forever. Pick one formulation, prove it terminates, and use only that one.
  • "Found it" is usually not the question. The genuinely useful variants return a boundary: the first index whose value is ≥ x (lower bound), or the first whose value is > x (upper bound). Those compose into counting occurrences, into range extraction, and into insertion-point queries, and they return a meaningful answer when x is absent — which plain membership does not. Write the boundary version; derive membership from it.

What it costs on an array, honestly

The Θ(log n) is a count of comparisons, and on a large array each comparison is a jump to an unrelated address — a probable cache miss, per §02. Twenty comparisons on a million-element array may therefore be twenty DRAM round trips, while a linear scan of a few hundred contiguous elements is a handful of line fetches with prefetching on top. That is why B-trees exist — they widen the node so that each expensive fetch resolves many comparisons at once — and why "binary search is always better than scanning" is false for small n. It is the same family of constant-factor argument that makes library sorts hand small subarrays to insertion sort rather than recursing further, though that threshold is driven as much by call overhead and branch prediction as by the cache. The asymptotic claim is unaffected and remains the right basis for the decision at scale; the constant is where the surprises are.

A linear scan has one classical trick worth naming because it belongs to the same "arrays are arithmetic" family. A scanning loop normally tests two things per step — have I run off the end? and is this the element? — and the first test is pure overhead, since it succeeds every time but once. Write the sought value into one spare cell past the live data, a sentinel, and the search is now guaranteed to terminate on a value match, so the bounds test can be deleted from the loop entirely; whether the scan found a real element or the sentinel is decided once, afterwards, by comparing the final index against n. The same idea appears everywhere a boundary can be turned into a value: a sentinel node that removes the null check from a linked-list loop, a sentinel row of +∞ that removes the exhausted-run check from a merge. It buys a constant factor and nothing asymptotic, it costs one cell of slack and the right to write into it, and it is the reason a container that owns one spare slot is sometimes easier to write loops against than one that does not.

The other precondition, easy to forget. Binary search requires the array to be sorted by the key you are searching on. If the array is maintained sorted, every insertion costs Θ(n) for the shift of §05 — so a sorted array is an excellent read-mostly structure and a poor write-heavy one. That single sentence is the reason balanced search trees exist: they keep the ordering and the logarithmic search while making insertion logarithmic too, by giving up the contiguous block.

17 The string-matching problem, and the obvious algorithm

Given a text T[0 … n−1] and a pattern P[0 … m−1] over a finite alphabet Σ, report every valid shift — every s with 0 ≤ s ≤ n − m such that T[s … s+m−1] = P[0 … m−1]. The problem is the search box in an editor, the grep in a pipeline, the motif hunt in a genome. It is also the cleanest available illustration of one idea: an algorithm that remembers what it has already seen can be asymptotically faster than one that does not.

the naive matcher — try every alignment, compare until something disagreesfor s = 0 to n − m: j = 0 while j < m and T[s+j] == P[j]: j = j + 1 if j == m: report a match at shift s costO((n − m + 1)·m) character comparisons, and the bound is tight the pair that attains itT = aaaa…a (n of them), P = aa…ab (m−1 a's then a b) every alignment matches m−1 characters and then fails ⇒ exactly (n−m+1)·m comparisons with m = n/2 that isΘ(n²) preprocessing · extra spacenone · O(1)

On the default pair the counter records 21 character comparisons over 10 alignments to find the single occurrence at shift 3. Switch to the adversarial preset and the count jumps to the theoretical maximum — (10 − 4 + 1) × 4 = 28, which the readout confirms against the counter — because every alignment matches three characters before the fourth fails. That is the signature of the inefficiency: the matcher does substantial work at each alignment, learns something real from it, and then deletes what it learned.

The information being thrown away

Suppose P = aaab and the alignment at shift s has matched aaa before failing. Those three matched characters are a fact about the text: T[s] = T[s+1] = T[s+2] = a. The naive matcher now retries at s+1 and compares T[s+1] against P[0] = a — a comparison whose answer it already knows. The whole family of fast matchers is different answers to one question: what can be deduced about future alignments from the characters already matched at this one?

  • Rabin-Karp (§18) does not answer it at all; it instead makes each alignment cheaper by testing a fingerprint of the window in O(1) before looking at any character. Same worst case, much better typical case.
  • KMP (§19) answers it exactly, by precomputing from the pattern alone how far the pattern may slide after a mismatch at each position, without ever re-examining a text character. Linear worst case.
  • Boyer-Moore (§20) answers a different question — it compares from the right end of the pattern, so a mismatch can prove that a whole block of alignments is impossible and the matcher can skip text characters entirely. Sublinear in practice, quadratic in the worst case in its simplified form.
  • The finite automaton approach compiles the pattern into a state machine over Σ whose transition on the next text character is a single table lookup. Matching is then Θ(n) with one comparison-free step per character; the cost has moved to building a table of O(m·|Σ|) entries. KMP is best understood as that automaton with the table replaced by an m-entry array and an amortized fall-back loop — the same matching behaviour at Θ(m) preprocessing instead of O(m·|Σ|).
In defence of the naive matcher. It is genuinely the right choice when m is small, the alphabet is large, and the text is not adversarial — which describes most searches in ordinary prose. On text whose characters are independent and uniform over a d-symbol alphabet, the chance that an alignment survives k comparisons is d^(−k), so the expected number of comparisons at one alignment is at most ∑ₖ₌₀^∞ d^(−k) = 1/(1 − 1/d) = d/(d − 1) — at most 2, with equality only at d = 2, and falling toward 1 as the alphabet widens (1.04 for 26 letters). The bound is an over-estimate because the real sum stops at m terms. So the expected total is O(n) with a constant under 2, and the quadratic worst case needs a highly repetitive text and a highly repetitive pattern. Know it exists, do not assume you are in it — and note that the uniform-independent hypothesis is false of natural language, which is why the empirical constant is not exactly d/(d−1).

18 Rabin-Karp and the rolling hash

The idea is to replace a character-by-character comparison with a single number comparison. Treat each length-m window of the text as a number in radix d = |Σ|, and compare that number against the pattern's. Two things make it work: the number of the next window can be computed from the current one in O(1), and the numbers can be kept small by working modulo a prime. The result is an algorithm whose comparisons are arithmetic, and which only touches characters when the arithmetic says it might be worth it.

Without it, t_s is an m-digit number and arithmetic on it is not constant time — the whole argument collapses, because "one operation" would be an operation on an m-digit integer. Choosing a prime q with d·q comfortably inside a machine word keeps every operation single-precision. The price is that the fingerprint is no longer decisive in one direction:

At q = 13 the pattern's fingerprint is 7, and two of the fifteen windows carry that fingerprint: the genuine occurrence at shift 6 (31415) and a collision at shift 12 (67399, and 67399 = 13 × 5184 + 7). The spurious hit is not a bug — it is the designed behaviour, and the verification step is what makes the algorithm correct despite it. Raise the modulus to 997 and the collision disappears entirely; drop it to 7 and hits multiply, until at a small enough modulus the fingerprint filters nothing and the algorithm degenerates into the naive matcher with extra arithmetic. The readout also checks the whole point of the roll: every one of the fifteen fingerprints is recomputed from scratch by Horner's rule and compared with the rolled value, and they agree.

What it is actually good for

  • The worst case is no better than naive — Θ((n−m+1)·m), achieved when every window collides, as it does with P = aᵐ in T = aⁿ where every window is a genuine match. The gain is in the expected case, where the fingerprint rejects almost every window at O(1) and the total is O(n + m).
  • It generalises where the others do not. Because the test is a hash rather than a comparison, the method extends directly to multiple patterns at once — hash every pattern of the same length into a set and test each window against the set — and to two-dimensional pattern matching, where a rectangle's fingerprint rolls in both directions. Neither generalisation is available to KMP.
  • It is the engine behind content-defined chunking and near-duplicate detection. Rolling hashes over sliding windows are what backup systems, rsync-style delta transfer and document-similarity pipelines use to find shared content without comparing everything to everything.
  • It is a Monte-Carlo algorithm made Las Vegas by the verification step. Skip the verification and you have a fast algorithm that is occasionally wrong; keep it and you have an algorithm that is always right and only occasionally slow. That is a pattern worth recognising — it recurs wherever hashing is used to avoid work.
A practical warning. If the modulus and radix are fixed and publicly known, an adversary can construct an input that collides on every window and force the quadratic case deliberately. The defence is the same one hash tables use: choose q at random at run time, so no fixed input is bad for every execution. This is the cheapest available lesson in why randomisation is a security property and not only a performance one.

19 KMP: the prefix function, and never backing up in the text

The Knuth-Morris-Pratt matcher achieves Θ(n) matching with Θ(m) preprocessing and Θ(m) extra space, and it does so by never moving the text pointer backwards. Its entire content is one precomputed array, the prefix function, which answers a question about the pattern's self-similarity: after matching q characters and then failing, what is the longest prefix of the pattern that is still alive?

You will meet this array under at least four names and they are the same object. Prefix function and partial match table describe what it contains; failure function and failure link describe what it is used for — where to fall back when a match fails. A second naming hazard is worse: the array is published both 0-indexed, as here, where pi[q] is a property of the prefix ending at q, and 1-shifted, where entry q says where to resume after a mismatch at position q and the first entry is often −1. The two differ by one everywhere and produce a matcher that is subtly wrong if you mix a table from one convention with a loop from the other. Whenever you read a KMP implementation, establish which convention its table uses before reading anything else.

What the array is used for

Matching keeps a single number q: how many characters of the pattern currently match the text ending at the character just read. Read the next text character T[i]. If it extends the match — if P[q] = T[i] — increment q and move on. If it does not, do not move the text pointer; instead shrink q to pi[q−1] and try again. Shrinking to pi[q−1] is exactly the claim that the longest still-viable prefix is the longest prefix that is also a suffix of what was already matched — and that claim is what the prefix function computes.

Why both loops are linear, although both are nested

The proof is an aggregate amortized argument, and it is the same argument twice.

  • Construction. k starts at 0, increases by at most 1 per iteration of the outer for — so its total increase over the whole run is at most m − 1. Every iteration of the inner while sets k = pi[k−1] < k, a strict decrease, and k never goes below 0. A quantity that rises by at most m − 1 in total and falls by at least 1 per inner iteration can be decreased at most m − 1 times. So the inner loop runs O(m) times in total across the entire construction, not per outer step, and the whole thing is Θ(m).
  • Matching. Identical, with q in place of k and n in place of m: q rises by at most one per text character, so at most n in total, and each fall-back strictly decreases it. Matching is Θ(n), so the algorithm as a whole is Θ(n + m).
  • The bank-account reading. Each text character deposits one credit when it advances q; each fall-back withdraws at least one. The account is never overdrawn because q ≥ 0, so total withdrawals cannot exceed total deposits. This is precisely the accounting method used for amortized append, and recognising it in both places is worth more than either result on its own.
The property with operational consequences. KMP never moves the text pointer backwards, so it can run on a stream: characters arriving from a socket or a pipe can be consumed once, in order, and discarded immediately, with only the O(m) table and the single integer q retained. No window of text is buffered at all — that is the precise form of the advantage, and it is stronger than "it reads the text once", which every linear matcher does. Boyer-Moore is not disqualified from streaming — you can give it a ring buffer of the last m characters, which is the same O(m) space — but its skipping cannot buy anything there, because a stream must still be read byte by byte even over the stretches the matcher declines to examine. On a memory-mapped file or an in-memory buffer, where a skip really is a pointer addition, it can. When the text does not fit in memory or does not exist yet, that structural difference decides the choice regardless of which is faster on a benchmark.

20 Boyer-Moore: reading backwards to skip forwards

Boyer-Moore is a matcher that aligns the pattern against a window of the text, compares the two from the pattern's last character backwards, and on a mismatch consults a table built from the pattern to decide how far right the whole window may jump. Everything distinctive about it follows from the direction of that scan. The matchers so far all read every character of the text at least once, so Θ(n) looks like a floor; it is not, because a mismatch discovered at the far right end of a window carries information about every alignment that window overlaps, and the pattern can be advanced past all of them without ever looking at the characters it skipped.

The two heuristics

  • Looking-glass. Align P with the window and compare P[m−1] against the text first, then work leftwards. This does not save anything by itself — it exists to set up the second heuristic, by making mismatches happen at text positions far to the right of the current alignment.
  • Character jump (the bad-character rule). When T[i] mismatches P[k], look at where T[i] occurs in the pattern at all. If it occurs nowhere, no alignment that covers position i can succeed, so the pattern may be slid entirely past i — a jump of up to m positions, with m − 1 text characters never examined. If it does occur, slide so that its last (rightmost) occurrence lines up with T[i].

A hand-worked run

Take T = abacaabadcabacabaabb and P = abacab. The table is last(a) = 4, last(b) = 5, last(c) = 3, and last(d) = −1. The first alignment compares T[5] = a against P[5] = b and fails; since last(a) = 4 < 5, the pattern slides right by one so that the pattern's rightmost a sits under T[5]. A few comparisons later the scan reaches T[8] = d, which occurs nowhere in the pattern — last(d) = −1 — and the pattern jumps clear past it, skipping five text positions without a single comparison. That single jump is the algorithm's entire value proposition. Run the same pair through the race in §21: Boyer-Moore takes 20 measured character comparisons against the naive matcher's 35 and KMP's 27, on a twenty-character text.

The good-suffix rule, and the worst case

The version above is the simplified Boyer-Moore, and its worst case is no better than naive: O(n·m), attained by T = aⁿ with P = b·a^(m−1), where every alignment matches the whole tail of the pattern and fails on the single leading b, and the bad-character rule can only shift by one. The full algorithm adds a second rule and takes the larger of the two shifts:

  • The good-suffix rule. When the scan has matched a suffix S of the pattern before failing, slide so that another occurrence of S in the pattern lines up with the matched text — or, if no other occurrence exists, so that the longest prefix of P that is also a suffix of S lines up. That second clause is the prefix function of §19 in a different costume; the two ideas are the same idea, applied from opposite ends.
  • With both rules the bound improves, but only under a hypothesis that is usually left out. Taking the larger of the two shifts gives O(n + m + |Σ|) when the pattern does not occur in the text — and the tight constant for that case is known: at most 3n character comparisons, which is attained. When the pattern does occur, and especially when it is periodic (a prefix of some string repeated, like abab), the two rules are not enough: T = aⁿ with P = aᵐ makes every alignment match in full, and the algorithm is back to Θ(n·m). The repair is a third rule that remembers the block already known to match at the previous alignment and declines to re-compare it; with that added, the linear bound holds whether the pattern occurs or not. So there are three different algorithms wearing this name — bad-character only, plus good-suffix, plus the memory rule — with three different worst cases, and "Boyer-Moore is linear" is true of exactly one of them. Establish which one you are looking at before quoting a bound for it.
  • On ordinary prose it examines only a fraction of the characters, and the fraction is measurable rather than folkloric. A number near 0.24 comparisons per text character for a five-character pattern in English circulates widely, and it is the right order of magnitude — but it is an empirical observation about one corpus, one pattern length and one alphabet, not a theorem, so it is worth reproducing rather than repeating. Running the simplified matcher on this page's own English-prose preset (§21, 1 590 characters) under the same counter that produces every other number here gives 0.270 comparisons per text character for the five-character pattern plain — against the naive matcher's 1.031 on the same text — so the circulating figure survives contact with a measurement. The quantity depends on three things: alphabet size (it rises toward and past 1 as the alphabet narrows — the binary preset in the same figure records 1.800, worse than naive's 1.788), pattern length (the maximum jump is m, so the same corpus with the eight-character pattern alphabet drops to 0.195), and how often the pattern actually occurs (each hit costs a full m-character verification and a shift of only m). Quote it with those three conditions attached or do not quote it — and notice that a single number "0.24" with none of them attached is exactly the kind of claim this page's own rule about machine-measured costs exists to prevent.

Where it loses

  • Small alphabets. With two or four symbols, every character occurs somewhere in the pattern, so last(c) is almost never −1 and the jumps are short. The race figure's binary preset shows Boyer-Moore doing more comparisons than the naive matcher — the heuristic has overhead and nothing to spend it on.
  • Short patterns. The maximum jump is m, so a two-character pattern can never skip much. The method wants a long pattern in a large alphabet, which is exactly the text-editor search it was invented for.
  • Streams. The scan runs right to left inside a window and then jumps forward, so it needs random access within the window and the ability to move the window forward cheaply. Neither is impossible on a stream — an m-character ring buffer supplies the first, and the second is a matter of reading and discarding — but the skipping stops paying, because the bytes the matcher declined to examine still have to be pulled off the stream one at a time. Where a skip is a pointer addition, as in a memory-mapped file, it pays in full. This is KMP's structural advantage stated exactly, and it is not visible in any comparison count.
  • Occurrence-dense texts. Every hit costs a full m-character verification and a shift of only m, so a pattern that occurs on a large fraction of alignments erases the method's advantage even before the periodic worst case is reached. The method wants a rare pattern, which is also the case in which it is most worth running at all.

Choosing, in one paragraph. Default to the naive matcher for short patterns in ordinary text — it is a few lines, it has no preprocessing, and in wall-clock terms it is often the fastest despite doing the most comparisons, because its inner loop is a straight-line scan that a compiler or a library routine can vectorise while the jumps of the other three cannot be. That is a claim about constants and about one machine, so treat it as a default to measure against rather than as a result. Reach for Boyer-Moore when the pattern is long and the alphabet is wide, which is the text-search case. Reach for KMP when a worst-case guarantee is contractual or the text arrives as a stream. Reach for Rabin-Karp when the problem is really "find any of these many patterns" or "find this rectangle", where its fingerprint generalises and nothing else does. And when the same text will be searched many times, stop matching against the text altogether and build an index over it — a trie, a suffix array or a suffix tree — which moves the cost to a one-off preprocessing of T rather than of P, and answers each subsequent query in time proportional to the pattern alone.

22 Half-open ranges, fenceposts, and bounds

Almost every off-by-one error on this page's material is a disagreement about what a range means. The convention that removes most of them is the half-open range [lo, hi) — include the low end, exclude the high one — and it is worth spelling out why, because the reasons are structural rather than stylistic and they explain several conventions that otherwise look arbitrary.

Why half-open

  • Length is a subtraction. [lo, hi) holds hi − lo elements, with no +1 correction. Closed ranges need hi − lo + 1, and that +1 is forgotten roughly as often as it is written.
  • The empty range is expressible. [i, i) is empty and legal. A closed range cannot express emptiness without an out-of-band convention like hi < lo, which every loop then has to test for separately.
  • Adjacent ranges join without arithmetic. [a, b) and [b, c) tile [a, c) exactly, with no gap and no overlap, and the shared endpoint is written once. This is what makes recursive splitting — mergesort, quicksort, binary search — read cleanly: the midpoint appears in exactly one of the two halves and nobody has to remember which.
  • It matches zero-based indexing. With indices 0 … n−1, the whole array is [0, n) — the bound is the length, so the same number serves as both, and for i in [0, n) needs no adjustment anywhere.
  • It is why the prefix-sum table has n+1 entries. §14's P indexes the fenceposts between elements, and there are n + 1 fenceposts around n elements. Once the table is understood as a table of boundaries rather than of elements, P[r+1] − P[l] stops being a formula to memorise.

What the index formula will happily compute

The address arithmetic of §01 has no opinion about whether an index is in range. base + i × itemsize is a valid computation for i = −5 and for i = n + 10⁶; it produces an address, and that address points at something — another variable, a chunk of the allocator's bookkeeping, a return address on the stack, or memory the process does not own. What happens next is a language decision layered on top of the structure, and the three available policies have very different consequences:

  • Unchecked. The read or write proceeds. Reading gives garbage; writing corrupts whatever was there, and the symptom appears arbitrarily far from the cause. This is the classical buffer overrun, and it is not a subtle bug class — it is the direct consequence of a structure whose access mechanism is arithmetic and whose bounds are not part of that arithmetic.
  • Checked. Every access compares the index against the length and raises on failure. The cost is one compare-and-branch — a handful of cycles, almost always predicted correctly, and frequently hoisted out of a loop entirely by a compiler that can prove the index stays in range. The usual claim that bounds checking is expensive is, for ordinary loop-carried access patterns, largely false; where it genuinely costs, it costs because it blocks vectorisation, not because of the branch.
  • Wrapped. Negative indices count from the end, or indices are taken modulo the length. Convenient, and it converts a class of errors into silently wrong answers rather than failures — an index that is accidentally −1 reads the last element instead of complaining. A ring buffer's deliberate mod capacity is the legitimate case; an accidental one is worse than a crash.

The practical rule follows from the three: validate at the boundary of your code, not at every access inside it. Check once where an index enters — from a parse, a user, a network message — and then let the internal loops run over ranges you have already proved correct. That is also the reason the array ADT of §03 states preconditions (0 ≤ i < n) rather than return codes: the contract belongs to the caller, and a structure that checks defensively on every operation is paying for a guarantee the caller should already be able to make.

A small habit with a large return. When you write a loop over an array, say out loud what the range is in half-open form and what the invariant at the top of the body is. Most fencepost bugs do not survive being stated. The ones that do are usually a range that was closed on one side and half-open on the other — which is exactly what happens when two people, or two libraries, each picked a convention and neither wrote it down.

Order is not one thing

  • Code-unit order is not alphabetical order. Comparing by numeric code puts every uppercase Latin letter before every lowercase one, so "Zebra" < "apple". That is a total order, it is fast, it is stable across machines, and it is the right choice for an index or a binary-search key — and it is the wrong thing to show a human.
  • Human order is locale-dependent and not a simple comparison. Collation rules handle case, accents, ligatures and language-specific orderings, and they can be non-lexicographic in ways that break the assumptions of a comparison sort's shortcuts. Treat display ordering and index ordering as two different problems with two different keys; conflating them produces search indexes that disagree with the list the user is looking at.
  • Normalisation comes before comparison. In a variable-width encoding the same visible text can have several byte representations. Two strings that look identical may compare unequal, which turns up as a lookup that "should" hit and does not. The discipline is to normalise once, at the boundary, and compare normalised forms — the same "validate at the edge" rule as §22.

The radix d should exceed the alphabet size so that distinct strings give distinct polynomials before the modulus is applied; the modulus q should be prime and large enough that collisions are rare; and if an adversary can choose the keys, d or q must be randomised per run, or the table can be made to degenerate to a single bucket.
  • Prefix hashes give O(1) substring fingerprints. Precompute the polynomial hash of every prefix of a string, exactly as §14 precomputes prefix sums, and the hash of any substring is recoverable with one subtraction and one multiplication by a stored power. That single trick answers "do these two substrings match?" in constant time after linear preprocessing, and it is the engine behind a large family of string algorithms.
  • Short strings are the awkward case. Hashing a three-character key costs about as much as comparing it, so for very short keys a sorted array with binary search, or a trie, can beat a hash table outright — the same small-n constant-factor argument as §16, in a different costume.
The recurring point. A cost model is a claim about what one step costs. For arrays of numbers, "one comparison" really is one step and the standard bounds mean what they say. For strings, one comparison is a loop — so the honest statement of a string-sorting bound names two parameters, the number of keys and their shared structure, and any single-parameter version of it is hiding the one that the data controls.

24 Where arrays sit underneath everything else

Almost every structure in the rest of this series is an array plus a rule for what an index means. Recognising that is not a curiosity; it is how you predict a structure's constants, its memory behaviour and its failure modes before reading a line of its implementation. Here is the inventory.

And outside this domain

  • The numerical array type. A NumPy-style ndarray is precisely §04's compact array plus §08's strides plus §10's view semantics, with the entire performance story of the library resting on the three of them. "Is this operation a view or a copy?" and "is this array contiguous?" are the two questions its users learn to ask, and both are questions from this page.
  • Embeddings are a matrix with an integer index. A token embedding table is a |vocab| × d array, and an embedding lookup is one row slice — §01's address arithmetic, on a row-major block. The whole reason tokenization maps text to integers before anything else happens is that integers are what arrays index.
  • Attention is array layout. The reason attention implementations are rewritten in tiled form is §09's argument at GPU scale — the arithmetic is unchanged, the traffic between memory levels is not, and that traffic is what decides the runtime.
  • Vector indexes are arrays with a search structure over them. A vector database stores a compact matrix of embeddings and builds an index above it; the contiguity of the base array is what makes a brute-force scan competitive at small scale and what the index has to beat at large scale.
  • The integral image. The 2-D prefix sum of §14 is how classical feature detectors evaluate box sums over any window in constant time — one of the cleanest cases of a whole method being enabled by a precomputed array.
  • Sequence models run the same recurrences. The forward and Viterbi algorithms of an HMM or CRF fill a states-by-time table exactly the way a DP table is filled, and the table is an array whose index is a state-time pair.
The reason this inventory matters. When a structure is an array underneath, it inherits the array's constants: contiguous traversal is fast, random access is one computation, growth is amortized, and inserting in the middle is linear. When it is not — when it is nodes and pointers — it inherits the opposite. Asking "what is this made of?" predicts more about real performance than reading its asymptotic table, because the table is usually the same for both.
