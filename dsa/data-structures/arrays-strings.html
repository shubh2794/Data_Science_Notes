Arrays & Strings

One decision — put the elements next to each other in memory — and every cost on this page follows from it. Contiguity turns an index into arithmetic, so reading any element is one step; it also means there is no gap to insert into, so making room is a shift of everything after the hole. That single trade produces dynamic arrays and their amortized constant append, row-major layout and the cache behaviour it dictates, immutable strings and the quadratic loop that catches everyone once, the two-pointer and sliding-window patterns, prefix sums, and the string matchers that get from O(nm) to Θ(n) by never re-reading a character of the text — and past them, the automata, regular expressions, compressors and suffix arrays that reuse the same few ideas.

01 What an array is

An array is a fixed-size block of consecutive memory cells, all of the same width, holding elements that are addressed by an integer offset from the start of the block. Three words do all the work in that sentence — consecutive, same width, offset — and together they buy the one property that defines the structure: the address of element i can be computed, in a fixed number of arithmetic operations, without looking at any other element.

the defining identity — the whole structure in one lineaddress(A[i]) = base + i × itemsize wherebase = the machine address of the first cell itemsize = the number of bytes every cell occupies — the same for all cells i = the index, an integer offset, counted from 0 consequencereading or writing A[i] costs one multiply, one add and one memory access — O(1), for every i

Why each of the three words is load-bearing

  • Consecutive. If the cells were scattered, the address of cell i would have to be stored somewhere and looked up, and looking it up is itself an access problem — the regress that linked structures solve by following one pointer at a time, at a cost of i dereferences to reach element i. Contiguity replaces a lookup with a calculation.
  • Same width. The multiplication i × itemsize is only valid if every cell before i is exactly itemsize bytes wide. This is the constraint people forget, and it is why an array of objects of different sizes is not an array of those objects at all — it is an array of references to them, each reference being a fixed-width machine address (§04). A language that lets you write A[i] for heterogeneous contents has only two ways to keep the formula valid: store a fixed-width reference in each cell and put the object elsewhere (§04, and by far the commonest answer), or pad every cell to one fixed width large enough for a type tag plus the largest inline payload — the tagged-slot layout used by value types and by some dynamic-language runtimes that pack small values into a machine word. What it cannot do is lay variable-width objects end to end and still index them by arithmetic.
  • Offset, counted from 0. Zero-based indexing is not a stylistic preference; it is what makes the formula have no correction term. With 1-based indices the address becomes base + (i − 1) × itemsize, which is the same thing with an extra subtraction on every single access. Languages that index from 1 either pay that subtraction or bias the stored base pointer by one cell to absorb it.

What the definition does not say

  • Nothing about the contents being ordered. An array is not a sorted sequence. Order is something an algorithm may impose on it (and then exploit — see §16); the structure itself promises only positions.
  • Nothing about the size being known at compile time. Fixed-size means fixed once created. The block may be allocated at run time with a length computed at run time; what it may not do is grow, because the memory immediately after the block belongs to someone else. Growth is faked by allocating a new block and copying — which is the whole of §06.
  • Nothing about bounds being checked. The address formula happily computes an address for i = −5 or i = n + 1000. Whether that address is rejected, silently read, or used to corrupt something is a language decision layered on top of the structure, not a property of it. The structure's contract is arithmetic, not safety.

The motivation, stated as a cost argument

Every container has to answer the question "where is element i?". There are only two families of answer. Compute it — which requires that positions be predictable, which requires uniform cells laid consecutively; or store it — which requires a reference per element and a traversal to reach the reference. The first family is arrays and everything built directly in them: strings, matrices, hash tables, binary heaps, ring buffers, the tape a tokenizer scans. The second is linked nodes and everything built from them: lists, most trees, adjacency lists. The entire rest of this series is a series of positions taken between those two answers, and this page is the first of them because the contiguous block is what the others are measured against.

Address arithmetic: one multiply, one add, at any index move the index — the step count for the array does not move with it

The two bars are the argument. The indexed access is two arithmetic operations at every index — the bar never grows, because the formula never consults the elements it skips. The pointer walk is one dereference per element skipped, so its bar is the index itself. At i = 11 the contest is 2 against 11; at i = 10⁶ it is 2 against a million. Notice also what the byte offset row does when you change itemsize: the index arithmetic is unchanged, only the scale factor moves. That is why the same index formula serves an array of bytes and an array of 64-bit pointers without modification, and why itemsize has to be a property of the array's element type rather than of any individual element.

The one-line version. An array is the data structure you get when you decide that position shall be computable. Everything it is good at, and everything it is bad at, is downstream of that decision.

27 Half-open ranges, fenceposts, and bounds

Almost every off-by-one error on this page's material is a disagreement about what a range means. The convention that removes most of them is the half-open range [lo, hi) — include the low end, exclude the high one — and it is worth spelling out why, because the reasons are structural rather than stylistic and they explain several conventions that otherwise look arbitrary.

Why half-open

  • Length is a subtraction. [lo, hi) holds hi − lo elements, with no +1 correction. Closed ranges need hi − lo + 1, and that +1 is forgotten roughly as often as it is written.
  • The empty range is expressible. [i, i) is empty and legal. A closed range cannot express emptiness without an out-of-band convention like hi < lo, which every loop then has to test for separately.
  • Adjacent ranges join without arithmetic. [a, b) and [b, c) tile [a, c) exactly, with no gap and no overlap, and the shared endpoint is written once. This is what makes recursive splitting — mergesort, quicksort, binary search — read cleanly: the midpoint appears in exactly one of the two halves and nobody has to remember which.
  • It matches zero-based indexing. With indices 0 … n−1, the whole array is [0, n) — the bound is the length, so the same number serves as both, and for i in [0, n) needs no adjustment anywhere.
  • It is why the prefix-sum table has n+1 entries. §14's P indexes the fenceposts between elements, and there are n + 1 fenceposts around n elements. Once the table is understood as a table of boundaries rather than of elements, P[r+1] − P[l] stops being a formula to memorise.
the fencepost count, which is the whole family of errors in one linen elements ⇒ n + 1 boundaries ⇒ n − 1 gaps between adjacent elements counts under each conventionhalf-open [lo, hi): hi − lo elements closed [lo, hi]: hi − lo + 1 elements splitting a half-open range at m[lo, hi) = [lo, m) ∪ [m, hi) — m appears in exactly one part, automatically splitting a closed range at m[lo, hi] = [lo, m−1] ∪ [m, hi] or [lo, m] ∪ [m+1, hi] — you must choose, every time

What the index formula will happily compute

The address arithmetic of §01 has no opinion about whether an index is in range. base + i × itemsize is a valid computation for i = −5 and for i = n + 10⁶; it produces an address, and that address points at something — another variable, a chunk of the allocator's bookkeeping, a return address on the stack, or memory the process does not own. What happens next is a language decision layered on top of the structure, and the three available policies have very different consequences:

  • Unchecked. The read or write proceeds. Reading gives garbage; writing corrupts whatever was there, and the symptom appears arbitrarily far from the cause. This is the classical buffer overrun, and it is not a subtle bug class — it is the direct consequence of a structure whose access mechanism is arithmetic and whose bounds are not part of that arithmetic.
  • Checked. Every access compares the index against the length and raises on failure. The cost is one compare-and-branch — a handful of cycles, almost always predicted correctly, and frequently hoisted out of a loop entirely by a compiler that can prove the index stays in range. The usual claim that bounds checking is expensive is, for ordinary loop-carried access patterns, largely false; where it genuinely costs, it costs because it blocks vectorisation, not because of the branch.
  • Wrapped. Negative indices count from the end, or indices are taken modulo the length. Convenient, and it converts a class of errors into silently wrong answers rather than failures — an index that is accidentally −1 reads the last element instead of complaining. A ring buffer's deliberate mod capacity is the legitimate case; an accidental one is worse than a crash.

The practical rule follows from the three: validate at the boundary of your code, not at every access inside it. Check once where an index enters — from a parse, a user, a network message — and then let the internal loops run over ranges you have already proved correct. That is also the reason the array ADT of §03 states preconditions (0 ≤ i < n) rather than return codes: the contract belongs to the caller, and a structure that checks defensively on every operation is paying for a guarantee the caller should already be able to make.

A small habit with a large return. When you write a loop over an array, say out loud what the range is in half-open form and what the invariant at the top of the body is. Most fencepost bugs do not survive being stated. The ones that do are usually a range that was closed on one side and half-open on the other — which is exactly what happens when two people, or two libraries, each picked a convention and neither wrote it down.

28 Comparing, ordering and hashing strings

Sorting and searching bounds are always quoted in comparisons, and the whole framework assumes a comparison is one step. For strings that assumption is false: comparing two strings costs one character comparison per character of their shared prefix, plus one more. So Θ(k log k) comparisons to sort k strings conceals a factor that the data controls, and this section is about making that factor visible.

The three bars carry essentially the same number of string comparisons — 311, 296 and 303 at the default k = 64, a spread of five per cent, all sitting under mergesort's worst-case bound of 321, which the readout checks — and character counts of 381, 2 721 and 7 635, a spread of twenty-fold. This is the clearest available demonstration that "count the dominant operation" (the discipline of the cost model) is only safe once you have confirmed that the dominant operation costs O(1). When it does not, the bound is still true and no longer tells you what you wanted to know. It is also the argument for the alternatives: a trie sorts or searches strings in time proportional to total key length with no comparisons at all, and radix-style string sorts exploit the same structure by bucketing on one character position at a time.

Order is not one thing

  • Code-unit order is not alphabetical order. Comparing by numeric code puts every uppercase Latin letter before every lowercase one, so "Zebra" < "apple". That is a total order, it is fast, it is stable across machines, and it is the right choice for an index or a binary-search key — and it is the wrong thing to show a human.
  • Human order is locale-dependent and not a simple comparison. Collation rules handle case, accents, ligatures and language-specific orderings, and they can be non-lexicographic in ways that break the assumptions of a comparison sort's shortcuts. Treat display ordering and index ordering as two different problems with two different keys; conflating them produces search indexes that disagree with the list the user is looking at.
  • Normalisation comes before comparison. In a variable-width encoding the same visible text can have several byte representations. Two strings that look identical may compare unequal, which turns up as a lookup that "should" hit and does not. The discipline is to normalise once, at the boundary, and compare normalised forms — the same "validate at the edge" rule as §27.

Hashing a string, and its relation to the rolling hash

Using strings as keys in a hash table requires a hash function over a sequence of characters, and the standard construction is the same polynomial evaluation that Rabin-Karp uses — which is not a coincidence, because it is the same problem: reduce a string to a number in a way that rarely collides.

  • The same three design decisions appear as in §18. The radix d should exceed the alphabet size so that distinct strings give distinct polynomials before the modulus is applied; the modulus q should be prime and large enough that collisions are rare; and if an adversary can choose the keys, d or q must be randomised per run, or the table can be made to degenerate to a single bucket.
  • Prefix hashes give O(1) substring fingerprints. Precompute the polynomial hash of every prefix of a string, exactly as §14 precomputes prefix sums, and the hash of any substring is recoverable with one subtraction and one multiplication by a stored power. That single trick answers "do these two substrings match?" in constant time after linear preprocessing, and it is the engine behind a large family of string algorithms.
  • Short strings are the awkward case. Hashing a three-character key costs about as much as comparing it, so for very short keys a sorted array with binary search, or a trie, can beat a hash table outright — the same small-n constant-factor argument as §16, in a different costume.
The recurring point. A cost model is a claim about what one step costs. For arrays of numbers, "one comparison" really is one step and the standard bounds mean what they say. For strings, one comparison is a loop — so the honest statement of a string-sorting bound names two parameters, the number of keys and their shared structure, and any single-parameter version of it is hiding the one that the data controls.

29 Where arrays sit underneath everything else

Almost every structure in the rest of this series is an array plus a rule for what an index means. Recognising that is not a curiosity; it is how you predict a structure's constants, its memory behaviour and its failure modes before reading a line of its implementation. Here is the inventory.

And outside this domain

  • The numerical array type. A NumPy-style ndarray is precisely §04's compact array plus §08's strides plus §10's view semantics, with the entire performance story of the library resting on the three of them. "Is this operation a view or a copy?" and "is this array contiguous?" are the two questions its users learn to ask, and both are questions from this page.
  • Embeddings are a matrix with an integer index. A token embedding table is a |vocab| × d array, and an embedding lookup is one row slice — §01's address arithmetic, on a row-major block. The whole reason tokenization maps text to integers before anything else happens is that integers are what arrays index.
  • Attention is array layout. The reason attention implementations are rewritten in tiled form is §09's argument at GPU scale — the arithmetic is unchanged, the traffic between memory levels is not, and that traffic is what decides the runtime.
  • Vector indexes are arrays with a search structure over them. A vector database stores a compact matrix of embeddings and builds an index above it; the contiguity of the base array is what makes a brute-force scan competitive at small scale and what the index has to beat at large scale.
  • The integral image. The 2-D prefix sum of §14 is how classical feature detectors evaluate box sums over any window in constant time — one of the cleanest cases of a whole method being enabled by a precomputed array.
  • Sequence models run the same recurrences. The forward and Viterbi algorithms of an HMM or CRF fill a states-by-time table exactly the way a DP table is filled, and the table is an array whose index is a state-time pair.
The reason this inventory matters. When a structure is an array underneath, it inherits the array's constants: contiguous traversal is fast, random access is one computation, growth is amortized, and inserting in the middle is linear. When it is not — when it is nodes and pointers — it inherits the opposite. Asking "what is this made of?" predicts more about real performance than reading its asymptotic table, because the table is usually the same for both.
