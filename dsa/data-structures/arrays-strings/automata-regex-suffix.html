22 The string-matching automaton: one transition per character

The string-matching automaton for a pattern P of length m is a deterministic finite automaton with states 0, 1, …, m, where being in state q means "the longest prefix of P that ends at the character just read has length q". State m means a full occurrence has just ended. Matching reads each text character once, does one table lookup, and does nothing else: no comparisons, no fall-back loop, no amortization. §17 promised this machine and §21's table priced it; this section builds it, and shows that KMP is the same machine with its table left uncomputed.

the transition function — the whole automaton is this one tableδ(q, c) = the length of the longest prefix of P that is a suffix of P[0 … q) · c in wordsappend c to the part of the pattern already matched, and ask how much of P is still alive at the end the matcherq = 0 for i = 0 … n−1: q = δ(q, T[i]); if q == m: report a match at shift i − m + 1 the invariant after reading T[0 … i]q = the length of the longest prefix of P that is a suffix of T[0 … i] cost of matchingexactly n transitions, each one array lookup — Θ(n), and Θ(1) per character, not merely on average

Why the table only needs P, not the text

The invariant speaks about the whole text read so far, T[0 … i], but δ is indexed by a state and a character only. The step that makes that legitimate is a small lemma, and it is worth proving because it is the entire reason finite automata can match strings at all.

the lemmaif q = the longest prefix of P that is a suffix of x, then for any character c, the longest prefix of P that is a suffix of x·c = the longest prefix of P that is a suffix of P[0 … q)·c prooflet P[0 … k) be a suffix of x·c. If k = 0 there is nothing to show. Otherwise P[0 … k−1) is a suffix of x and a prefix of P, so k − 1 ≤ q by the choice of q. Then P[0 … k−1) is a suffix of P[0 … q) as well — both are suffixes of x and it is the shorter — so P[0 … k) is a suffix of P[0 … q)·c. The converse holds because P[0 … q) is itself a suffix of x. The two sets of candidates are equal. ∎ consequenceeverything the matcher needs to remember about an unbounded text fits in one integer 0 … m

Building the table in O(m·|Σ|)

Computing each entry straight from the definition — try every k from q+1 down, compare k characters — costs O(m) candidates times O(m) characters per entry, O(m³·|Σ|) in all. The fast construction observes that a mismatch in state q sends the automaton to exactly where it would be if it had been fed P[1 … q) — the matched text minus its first character — and then c. Call that restart state X. It can be carried along the construction, one transition per row, using rows already built:

the construction — one row copied, one entry overridden, per staterow 0: δ(0, c) = 1 if c = P[0], else 0 X = 0 for q = 1 … m: for every c in Σ: δ(q, c) = δ(X, c) // a mismatch behaves exactly as state X would if q < m: δ(q, P[q]) = q + 1; X = δ(X, P[q]) // the one forward edge; advance X cost(m + 1)·|Σ| entries written, O(1) each ⇒ Θ(m·|Σ|) time and space worked out for P = ababaca, Σ = {a, b, c}state q: 0 1 2 3 4 5 6 7 δ(q, a): 1 1 3 1 5 1 7 1 δ(q, b): 0 2 0 4 0 4 0 2 δ(q, c): 0 0 0 0 0 6 0 0 the restart state used for row q is X = pi[q − 1]rows 1 … 7 copy rows 0, 0, 1, 2, 3, 0, 1 — which is the prefix function of §19, 0 0 1 2 3 0 1

On the default pair the counters record 24 table entries written — (7 + 1) × 3, the construction bound with equality — and 17 transitions for a 17-character text, finding the occurrences at shifts 2 and 8. KMP on the same pair performs 19 character comparisons: close to n, because this text does not make it fall back often. The difference that matters is not the total but its distribution. Step to index 5: the automaton goes 5 → 4 in one lookup, δ(5, b) = 4, where KMP compares P[5] = c against the b, falls back to q = pi[4] = 3, and compares again before it can consume the character. The readout also rebuilds every entry from the definition by brute force and confirms that the lazy KMP recurrence below produces the same table.

KMP is this automaton with the transitions computed on demand

Look at what the construction's row copy says: in state q, on any character other than P[q], behave exactly as state pi[q−1] would. Written as a recurrence, that is the whole of KMP's fall-back loop:

the transition function, defined through the prefix functionδ(q, c) = q + 1 if q < m and P[q] = c δ(q, c) = 0 if q = 0 and P[0] ≠ c δ(q, c) = δ(pi[q−1], c) otherwise (state m uses pi[m−1] too) the automatonevaluates the recurrence for every (q, c) in advance — (m+1)·|Σ| entries, one lookup per text character KMPstores only pi (m entries) and unwinds the recurrence each time it is needed — the while loop of §19 what each gives upautomaton: space and preprocessing grow with |Σ| KMP: one character may cost several fall-backs
  • Per-character delay. KMP's total is Θ(n) by the amortized argument of §19, but a single character can trigger a chain of fall-backs; the longest possible chain grows logarithmically in m. The automaton's delay is exactly one step for every character, which is what "real-time" means and what matters when each character must be answered before the next one arrives.
  • The alphabet is the price. For bytes, |Σ| = 256 and the table is 256·(m + 1) entries — tolerable for a short pattern searched against a great deal of text, absurd for Unicode code points. But almost every entry is 0: besides the m forward edges, a pattern has at most about m non-zero backward edges, so a sparse row (store the non-zero entries, default to 0) recovers O(m) space while keeping transitions cheap.
  • Why it matters beyond one pattern. A single table-driven loop of the form q = δ(q, T[i]) is the execution model for every regular language, not just "contains P". The next section generalises the pattern to a regular expression, and the machine that falls out is the same loop over a bigger table — or, when the table would be too big, over a set of states.
The one-line relation. The automaton precomputes, for every state and every character, where KMP's fall-back chain would end. KMP is the automaton with Θ(m·|Σ|) of table traded for Θ(m) of table plus an amortized loop — the same matching behaviour, bought with a different resource.

23 Regular expressions: NFAs, set simulation, and catastrophic backtracking

A regular expression describes a set of strings built from single characters with three operators — concatenation, alternation and repetition — and matching one against a text can always be done in O(m·n) time by simulating a nondeterministic automaton, yet many library engines take exponential time on short inputs. The gap between those two facts is an implementation choice, and it is one of the most consequential in everyday software.

the grammar of regular expressions, and the set each form denotesa one character L = { a } r s concatenation L = { xy : x ∈ L(r), y ∈ L(s) } r | s alternation L = L(r) ∪ L(s) r* Kleene star — zero or more copies L = { x₁x₂⋯xₖ : k ≥ 0, every xᵢ ∈ L(r) } precedence, tightest firststar, then concatenation, then alternation: ab*|c means (a(b*))|c sugar that adds no powerr+ = r r* r? = (r | empty) [abc] = (a|b|c) . = any character what the three operators add over a plain patternchoice (|) and unbounded repetition (*) — a fixed string is the special case with neither

Thompson's construction: one small fragment per operator

The automaton of §22 was deterministic because a plain pattern never makes the matcher choose. A regex does: in (ab|a)c after reading a, both branches are alive. The clean response is to allow the automaton to be in several states at once — a nondeterministic finite automaton (NFA), with ε-transitions that move without consuming a character. The regex then compiles recursively, each operator wrapping the fragments of its operands:

the fragments — each has one start state and one accepting statea s ──a──▶ e (2 new states) r s r's accept ──ε──▶ s's start (0 new states) r | s new s ──ε──▶ r's start and s's start; both accepts ──ε──▶ new e (2 new states) r* new s ──ε──▶ r's start and e; r's accept ──ε──▶ r's start and e (2 new states) size, for a regex of m symbols and operatorsat most 2m states, every state has at most two outgoing edges ⇒ O(m) states and O(m) edges

Simulating the NFA: carry the set, not a choice

An NFA accepts if some sequence of choices reaches the accepting state. Rather than guessing, the simulation keeps the set of every state some choice could have reached, and advances the whole set on each character:

set simulationS = ε-closure({start}) for each text character c: S = ε-closure({ e : some s ∈ S has an edge s ──c──▶ e }) accept iff the accepting state ∈ S at the end the invariantafter reading x, S = exactly the states reachable from start along some path spelling x cost per charactereach state enters S at most once (mark it on entry), each has ≤ 2 edges ⇒ O(m) totalO(m·n) time, O(m) space — for EVERY regex and EVERY text; nothing is ever re-read

Subset construction, and why it is done lazily

Each set S the simulation visits could be treated as one state of a DFA; precompute all of them and matching becomes §22's one-lookup-per-character loop. That is the subset construction, and its catch is that an NFA with k states has 2ᵏ subsets, and some regexes need nearly all of them. The standard witness is (a|b)*a(a|b)⋯(a|b) with k trailing copies — "the (k+1)-th character from the end is a" — where the DFA must remember the last k + 1 characters, all 2^(k+1) possibilities of them. The figure's readout builds the subsets for that family and prints the counts. Practical engines therefore build DFA states lazily: compute a set only when the text first leads there, cache it, and fall back to set simulation if the cache overflows. At most one new state per text character is ever created, so the worst case stays O(m·n) while ordinary inputs run at table-lookup speed.

Backtracking, and how it goes exponential

Many widely used regex libraries do not simulate the NFA; they backtrack. At each choice they commit to the first alternative, carry on, and on failure return to the most recent choice and try the next one — a depth-first search over paths through the NFA. On most inputs that is fast. On some it explores an exponential number of paths that all fail:

(a|a)*b against aⁿ, which contains no bevery a can be consumed by the left branch or the right one: 2ⁿ distinct ways to consume the prefix, and the b fails after every one of them ⇒ Ω(2ⁿ) steps before answering "no" (a+)+b against aⁿthe inner a+ and the outer + can split aⁿ into any composition of n: 2^(n−1) of them, all failing why set simulation cannot do thistwo paths that reach the SAME state at the SAME text position have identical futures. The set merges them; the depth-first search explores both. There are only (states × positions) = O(m·n) distinct (state, position) pairs, so any engine that visits each pair at most once is O(m·n). the fix, in the same termsa backtracker that memoises failed (state, position) pairs is also O(m·n) — at O(m·n) memory
Steps to reject aⁿ, as n grows: a backtracking matcher against NFA set simulation log scale — a straight line is exponential; tick the box to make the input match and watch the backtracker recover

For (a|a)*b the backtracker's count doubles with every extra a — the line on a log axis is straight — and it exceeds the figure's two-million-call budget at n = 18, where the figure stops running it rather than hang your browser. The NFA simulation over the same 10-state Thompson automaton grows by a fixed eight state visits per character and ends at 182 for n = 22. a*a*a*b is the instructive middle case: three adjacent stars can split aⁿ in Θ(n²) ways, and the readout's fitted exponent for the backtracker lands between 2 and 3 — polynomial, not exponential, and still far worse than linear. Tick the box and every pattern that was exponential becomes linear for the backtracker too, because its first path now succeeds: catastrophic backtracking is a property of failing, or nearly matching, inputs, which is why it survives testing and appears in production when someone sends a long almost-valid string. Both engines are run on every n and the readout checks that they agree on every answer.

Why backtracking engines exist anyway, and what grep-style tools do

  • Backreferences are not regular. A pattern like (a+)b\1, "the same group again", which matches exactly aⁿbaⁿ, cannot be recognised by any finite automaton, and matching regexes with backreferences is NP-hard in general. Engines that support them backtrack because nothing polynomial is known to work. The price is that every pattern pays the backtracking risk, including ones that use no backreference at all.
  • The defence in practice. Use an automaton-based engine for untrusted patterns or untrusted text; if you must backtrack, prefer possessive or atomic groups, cap the step count, or rewrite (a+)+ as a+. A pattern with nested quantifiers over overlapping alternatives is the shape to look for in review.
  • Line-oriented search tools compile the regex to an NFA, build DFA states lazily as described above, and search rather than match by allowing the start state back into the set at every position (equivalently, prefixing the regex with Σ*). Before any of that they extract a required literal — a string every match must contain — and scan for it with a fast single-pattern matcher such as Boyer-Moore, running the automaton only on lines where the literal occurs. Most lines are discarded at the cost of a skip-search.
The design lesson. An automaton simulation is a breadth-first search over (state, position) pairs with duplicates merged; a backtracker is a depth-first search over paths without merging. The same distinction — merge equal subproblems or re-solve them — is the entire difference between dynamic programming and naive recursion, and it gives the same exponential-to-polynomial collapse.

24 Beyond regular languages: why parentheses need a stack

A finite automaton has a fixed number of states, so it can remember only a bounded amount about the text it has read — and "are these parentheses balanced?" needs unbounded memory. The repair is exactly one extra structure, a stack, and the languages that a finite control plus a stack can recognise are the context-free languages that every programming-language parser handles.

the pigeonhole argument that no DFA recognises balanced parenthesessuppose a DFA with k states accepts exactly the balanced strings. Feed it (⁰, (¹, (², …, (ᵏ — k + 1 prefixes, k states, so two of them, (ⁱ and (ʲ with i < j, leave it in the SAME state. From that state, reading )ⁱ must accept (because (ⁱ)ⁱ is balanced) and must reject (because (ʲ)ⁱ is not). A DFA's future depends only on its state — contradiction. ∎ what the argument really showsany language that must distinguish unboundedly many prefixes needs unbounded memory the ladder, with the machine each rung needsregular finite automaton a*b, identifiers, number literals context-free finite automaton + one stack balanced brackets, arithmetic, program syntax beyond more (two stacks = a Turing machine) aⁿbⁿcⁿ, "declared before use"

From a counter to a stack to a grammar

  • One kind of bracket needs only a counter — increment on (, decrement on ), reject if it goes negative or ends non-zero. The counter is unbounded, which is precisely what a DFA lacks.
  • Several kinds need a stack. ([)] has balanced counts and is still wrong; the closer must match the most recent unmatched opener, which is last-in first-out by definition. The algorithm and its measured run are on the balanced-delimiters section of the next page.
  • A grammar names the structure. A context-free grammar gives each syntactic category a rule in terms of the others, recursively. The standard grammar for arithmetic encodes precedence in its layering:
a grammar for arithmetic — one rule per precedence levelexpr → term ( ('+' | '−') term )* term → factor ( ('×' | '/') factor )* factor → number | '(' expr ')' recursive descent — one function per rule, the call stack IS the parser's stackparse_expr(): v = parse_term(); while next is + or −: op = take(); v = v op parse_term(); return v parse_term(): v = parse_factor(); while next is × or /: op = take(); v = v op parse_factor(); return v parse_factor(): if next is '(': take(); v = parse_expr(); expect(')'); return v else return take_number() costeach token is taken once and each call either takes a token or returns ⇒ O(n) for a grammar like this one recursion depththe nesting depth of the parentheses — deep enough input overflows the call stack

The regex figure of §23 runs on exactly such a parser: alt → cat ('|' cat)*, cat → rep*, rep → atom ('*' | '+' | '?')*, atom → letter | '(' alt ')'. The irony is structural — the syntax of regular expressions contains nested parentheses, so it is itself not a regular language, and parsing it needs the stack that the languages it describes never do. Grammars that are not deterministic in this one-token-lookahead way still parse in polynomial time: the general algorithm fills a table of "which rule derives which substring" by dynamic programming in O(n³). Converting infix arithmetic to postfix with an explicit operator stack, the non-recursive route to the same result, is on the next page.

The practical rule. If a format nests — brackets, tags, quoted strings containing escapes of quotes — a regex will match the easy cases and fail on the nested ones, often silently. Use a regex to split the text into tokens (a regular job) and a stack or a recursive-descent parser to assemble the tokens (a context-free one). That division is how essentially every compiler front end is built.

25 Compressing strings: runs, back-references, dictionaries

A lossless compressor maps each string to a shorter code from which the original can be rebuilt exactly, and it works by finding structure — runs, repeats, skewed symbol frequencies — that a fixed-width encoding wastes bits on. The three schemes here each exploit one kind of structure, and one counting argument says why none of them, or anything else, can win on every input.

no lossless scheme shrinks every input — the counting argumentthere are 2ⁿ bit strings of length n, but only 2⁰ + 2¹ + ⋯ + 2^(n−1) = 2ⁿ − 1 strings shorter than n. An injective (decodable) map cannot send 2ⁿ inputs into 2ⁿ − 1 outputs ⇒ some input does not shrink. and most inputs barely shrinkoutputs of length ≤ n − k number 2^(n−k+1) − 1, so fewer than a fraction 2^(1−k) of inputs save k bits or more the entropy limit, informallyfor symbols drawn independently with probabilities p₁ … p_s, H = −∑ pᵢ log₂ pᵢ bits per symbol no lossless code averages fewer than H bits per symbol; good codes approach it the two extremesuniform over s symbols: H = log₂ s — nothing to gain beyond fixed-width one certain symbol: H = 0

Run-length encoding

Replace each maximal run of one symbol by the pair (count, symbol). aaaabbbcca becomes (4,a)(3,b)(2,c)(1,a): eight fields for ten symbols. It wins when runs are long — bilevel images, where a scan line is long stretches of white; sparse bitmaps; sensor data that holds a value — and it doubles the size of a string with no repeats, since abcd becomes four pairs. The usual repair is an escape: emit literals as themselves and only encode runs above some length, so the worst case is a small overhead instead of a factor of two. Its real role today is as a stage: after a transform that creates runs, RLE is what collects them.

LZ77: say "the same as d characters back, for ℓ characters"

the encoder — a window of the last W characters already emittedat position i, find the longest match of s[i …] that starts inside the window s[i−W … i) emit the triple (offset, length, next): go back offset, copy length characters, then append next advance i by length + 1 the decoder — the whole thingfor each (d, ℓ, c): repeat ℓ times: out.append(out[len(out) − d]); out.append(c) worked, W = 8abcabcabcabcx → (0,0,a) (0,0,b) (0,0,c) (3,9,x) the overlap, which is not a bug(3, 9, x) copies 9 characters from only 3 back: the copy reads characters it has just written. Copied one at a time, left to right, it reproduces abc three times — a run is one triple. aaaaaaaaaa → (0,0,a) (1,8,a) — LZ77 subsumes run-length encoding

The asymmetry is the design. Decoding is a copy loop with no search, as fast as memory allows; encoding must find the longest match in the window, which naively costs O(W·ℓ) per position and in practice is done with a hash table keyed by the next three or so characters, chaining back to earlier positions with the same prefix. The window bounds the memory both sides need — and bounds what the scheme can see: a repeat further back than W is invisible.

LZW: a dictionary that both sides build identically

LZW emits only dictionary codes, never raw characters. The dictionary starts with every single symbol (agreed in advance), and grows by one entry per emitted code — the phrase just emitted extended by the next character. The decoder never receives the dictionary; it rebuilds the same one from the codes, one step behind.

the encoderw = "" for each character c: if w·c is in the dictionary: w = w·c else: emit code(w); add w·c as the next code; w = c at the end, emit code(w) the decoderprev = dict[first code]; output prev for each later code k: entry = dict[k] if k is already defined = prev · prev[0] if k is the code about to be defined ← the special case output entry; add prev · entry[0]; prev = entry why the special case can happen, and why it is always prev·prev[0]the encoder may use an entry in the very step after creating it, before the decoder has it. That entry is w·c, and its first character c starts the next phrase, which is w·c itself — so c = w[0]. It arises exactly on inputs of the shape c·K·c·K·c (hence the name KwKwK), e.g. every run of one symbol. worked, dictionary a = 0, b = 1abababab → 0 1 2 4 1 — code 4 (aba) is emitted the step after it is created

On the default input LZW emits 16 codes for 24 characters, but the codes must widen from three bits to five as the dictionary grows, so the saving is only 66 bits against the 72-bit baseline — short inputs are where adaptive dictionaries do worst, because the dictionary is still learning. Run-length and LZ77 both expand this input (160% and 163%): it has almost no runs, and a triple costs more than the three-bit symbol it replaces until matches get long. Switch to the 72-character repetition and all of that turns around — LZ77 reaches 66% of the baseline and LZW 70%, as matches and phrases lengthen. Switch to 72 random characters over four symbols and every scheme loses to plain 2-bit symbols (LZW 138%, LZ77 208%), with a zeroth-order entropy of 1.970 bits per symbol saying there was nothing to find: the counting argument, made concrete. The run of a's shows the extremes — run-length collapses it to one pair, and the LZW decoder meets five codes it has not yet defined, each resolved by the prev · prev[0] rule. Every scheme's output is decoded and compared with the input: all round-trips are checked, not assumed.

Where Huffman coding fits

  • A different kind of structure. Huffman coding assigns each symbol a prefix-free bit string whose length depends on its frequency — frequent symbols short, rare ones long — and is optimal among such symbol-by-symbol codes, averaging within one bit of the entropy (derived there). It sees no context: TOBEORNOT repeated a thousand times has the same symbol frequencies as a random shuffle of the same letters, and Huffman codes both identically.
  • Dictionary methods exploit repetition of longer strings, which is where most real redundancy lives — words, markup, repeated records. They are "universal": for long outputs of a stationary source they approach its entropy rate without being told the statistics.
  • So practical formats combine them. The common general-purpose format is LZ77 followed by Huffman coding of its literals, lengths and offsets: the first stage turns repetition into short references, the second squeezes the skewed distribution of what remains. Stronger compressors replace the symbol coder with arithmetic coding, which can spend a fractional number of bits per symbol and so gets arbitrarily close to H.
Compression is prediction. A code that spends −log₂ p bits on a symbol it predicted with probability p is optimal, so a better compressor is exactly a better model of what comes next. That is why the same entropy that bounds compression is the language-modelling loss, and why a byte-level merge vocabulary in tokenization looks so much like an LZW dictionary: both grow by adding the most useful concatenation of units already present.

26 Suffix arrays: preprocess the text instead of the pattern

A suffix array is the list of the starting positions of every suffix of a text T, sorted into lexicographic order of the suffixes. Every occurrence of a pattern is a prefix of some suffix, and in sorted order all suffixes that start with P are adjacent — so after one O(n log n) preprocessing of the text, each query is a binary search. It is the index that §21 recommends when one text will be searched many times, and it is one integer per character.

the definition, worked for T = bananarank SA[rank] suffix LCP with the previous suffix 0 5 a — 1 3 ana 1 (a) 2 1 anana 3 (ana) 3 0 banana 0 4 4 na 0 5 2 nana 2 (na) spacen integers for SA, n more for LCP — against the 10–20 bytes per character or more that a suffix tree typically needs

Construction by prefix doubling

Sorting the suffixes with a generic comparison sort costs O(n log n) comparisons, but each comparison is a string comparison costing up to O(n) characters — the hidden factor that §28 is about — so O(n² log n) in the worst case. Prefix doubling removes that factor by never comparing more than two integers:

the idea — sort by the first 2ᵏ characters, using the ranks from the first 2^(k−1)rank₀[i] = T[i] (sort by one character) key_k(i) = ( rank_(k−1)[i], rank_(k−1)[i + 2^(k−1)] ) (−1 past the end) sort positions by key_k, then give equal keys equal ranks ⇒ rank_k orders suffixes by their first 2ᵏ characters why it is correctthe first 2ᵏ characters of suffix i are its first 2^(k−1) followed by the first 2^(k−1) of suffix i + 2^(k−1) roundsstop when all ranks are distinct — at most ⌈log₂ n⌉ rounds costcomparison sort per round: O(n log n) ⇒ O(n log² n); radix sort on the integer pairs: O(n) ⇒ O(n log n) for the recordlinear-time constructions exist; prefix doubling is the one short enough to write from memory

Searching, and the LCP array

  • Pattern search. Binary search over SA for the first suffix ≥ P and the first suffix that does not start with P; the occurrences are exactly the ranks in between. Each probe compares P with a suffix in O(m), so a query is O(m log n), plus the number of occurrences to list them — independent of how the text was laid out, as with §16's binary search on any sorted array. Precomputing the longest common prefixes between the suffixes that a binary search can visit lets each step resume where the last left off, and cuts this to O(m + log n).
  • The LCP array stores, for each rank, the length of the longest common prefix with the previous suffix in sorted order. It can be built in O(n) by visiting suffixes in text order and noting that the LCP drops by at most one from suffix i to suffix i + 1 — the same kind of "a quantity that rises boundedly and falls by at least one" argument as §19.
  • What the pair answers. The longest repeated substring is the maximum LCP entry (ana in banana, LCP 3). The number of distinct substrings is n(n+1)/2 − ∑ LCP — for banana, 21 − 6 = 15, because each suffix contributes its prefixes except those it shares with its predecessor. Together SA and LCP simulate a suffix tree for most queries, which is why they have largely replaced it in practice: genome indexes, full-text search, and the block-sorting transform behind several compressors are all suffix arrays underneath.
Which side to preprocess. Every matcher from §17 to §22 preprocesses the pattern and then pays Ω(n) per search; a suffix array preprocesses the text once and pays O(m log n) per search. When patterns are many and the text is fixed — a genome, a code base, a document collection — the second trade wins by the ratio of n to log n, which for a billion characters is about thirty million.
