02 The memory model: words, lines, and why contiguity is the whole story

The RAM model that prices every bound in this series says that one memory access costs O(1), uniformly, wherever the address points. That is the right model for deriving asymptotics and the wrong model for predicting a runtime, and the gap between the two is where arrays earn most of their practical advantage. This section sets out just enough of the real machine to make the rest of the page's performance claims meaningful.

The layers, and the numbers that matter

  • A byte is the unit of address. Consecutive addresses differ by one byte; the address formula of §01 is arithmetic on byte counts.
  • A word is the unit the processor computes on — 8 bytes on a current 64-bit machine. A pointer is one word. An index into any array that fits in memory is one word. The word-RAM assumption that a word holds Θ(log n) bits is exactly the assumption that an index fits in a register.
  • A cache line is the unit of transfer, and it is the one most people never think about. Memory does not move between DRAM and the processor one byte or one word at a time; it moves in aligned blocks, typically 64 bytes on x86 and 64 or 128 bytes on ARM. Touching one byte fetches the whole line containing it.
  • A page is the unit of virtual-memory mapping, typically 4 KB, and the unit at which a translation lookaside buffer miss is paid. It matters for very large strided traversals; the cache line matters for almost everything else.
  • The latency spread. On a current mainstream core an L1 hit resolves in roughly 4–5 cycles, an L2 hit in roughly 12–15, an L3 hit in roughly 40, and a DRAM access somewhere in the region of 200 cycles (published figures vary from about 100 to 400 with the part, the frequency and the access pattern). That is a factor of forty to fifty between the cheapest and the most expensive "one memory access", all of which the RAM model prices identically.

What contiguity does with a cache line

An array of 4-byte integers packs 16 elements into one 64-byte line. A sequential scan therefore pays one memory transaction per sixteen elements and gets fifteen of them free — and because the access pattern is a constant stride, the hardware prefetcher recognises it and starts fetching the next line before it is asked for, which can hide the latency of even the paid one. The same n elements held as separately allocated nodes, each carrying a value and a pointer, occupy n lines in the worst case and are reached in an order the prefetcher cannot predict. Both traversals are Θ(n). They are not remotely the same speed.

the quantity the RAM model cannot seeline transfers for a sequential scan of n elements = ceil(n × itemsize / linesize) 4-byte elements, 64-byte lines= ceil(n / 16) — sixteen elements per transaction the same n elements as scattered nodes= up to n transactions, one per node, with no usable stride to prefetch so the ratio of memory traffic, same asymptotic classup to linesize / itemsize = 16×, on top of the bytes the links themselves cost what the links cost, which depends on the payload4-byte payload + one 8-byte link, rounded to the allocator's 16-byte grain ⇒ ≈ 4× the bytes 8-byte payload + one 8-byte link ⇒ ≈ 2× the bytes a 64-byte record + one link ⇒ ≈ 1.13× the bytes

The name for the property the array has and the node chain does not is locality of reference: the tendency of a program to touch addresses that are near ones it has recently touched (spatial locality) or to touch the same address again soon (temporal locality). Caches are a bet that programs have both. A contiguous array traversed in order is the best possible spatial locality — every byte fetched is used — and that is the single sentence behind most of this page's constant factors.

Three consequences that recur for the rest of this page

  • Traversal order is a performance decision, not a stylistic one. Walking a matrix along its storage direction touches each line once; walking across it can touch a fresh line on every element. §09 measures exactly that, under a stated cache model.
  • A "linear scan beats the clever structure" result is usually this effect. For small n — and "small" can mean a few hundred elements — scanning a packed array often beats a hash table or a balanced tree whose asymptotics are strictly better, because the array does one or two memory transactions and the tree does one per level, each a cache miss. The crossover is real, it is machine-specific, and the only way to find it is to measure.
  • Space is a time cost. Every extra byte per element is a fraction of a line wasted and a proportional increase in transactions. This is why a compact array of numbers (§04) is not merely more memory-efficient than an array of boxed references; it is faster by the same factor, on the same algorithm.
Model discipline, restated. Every asymptotic bound on this page is a bound in the RAM model, where all accesses cost the same. Every claim about one structure being faster in practice than another with the same bound is a claim about this section — line transfers, not step counts. Keep the two ledgers separate and both are useful; mix them and you will find yourself defending an O(1) access that takes 200 cycles.

03 The array ADT versus the array implementation

There are two different things called "array" and conflating them causes most of the confusion about what arrays cost. One is an abstract data type — a named set of operations with a stated contract. The other is a layout in memory — the contiguous block of §01. The ADT says what you may ask for; the layout says what each request costs. Keeping them apart is the habit that lets you read a library's complexity table and know what it is telling you.

The array ADT, minimally

the operations, and the contract each carriescreate(n) allocate n cells; n ≥ 0 (a zero-length array is legal); size fixed from here on length() the number of cells O(1) get(i) the value in cell i; requires 0 ≤ i < n O(1) set(i, v) write v into cell i; requires 0 ≤ i < n O(1) clear(v) write v into every cell Θ(n) iterate() visit cell 0, 1, …, n−1 in order Θ(n)

That is the whole interface. The hardware offers exactly three of these — allocate, read a cell, write a cell — and everything else on the list is a convenience written in terms of them. Notice what is absent: no insert, no delete, no search, no sort, no resize, no concatenation. Those are operations of richer sequence types, and their absence here is the point: the array ADT is deliberately impoverished so that every operation it offers is constant time. A structure whose interface contains nothing expensive is a structure you can reason about at a glance.

Why an impoverished interface is a feature

  • It makes the cost of the richer type visible. When a list type offers insert(k, v) and the array does not, the difference is not a missing feature — it is a shift loop, priced at Θ(n − k) in §05. Starting from the poor interface forces you to see the loop.
  • It makes the storage exactly the data. A fixed array of n elements occupies n × itemsize bytes and not a byte more. A growable list holds spare capacity — commonly up to twice what is needed — which is the price of amortized append (§06). When the count is known in advance and never changes, paying it is waste: a preallocated block of 100 000 numbers is 100 000 cells, where a doubling list that reached the same length may hold capacity for 200 000.
  • It is what every other structure in this series is built out of. A binary heap is an array plus index arithmetic. A hash table is an array plus a function from keys to indices. A ring buffer is an array plus two indices modulo n. A dense matrix is an array plus a stride. None of them need more than the six operations above from the layer beneath.

All three satisfy the ADT. All three are O(1) access in the RAM model. They differ by a constant factor of memory traffic that §02 says can reach an order of magnitude, and they differ in whether the elements are near each other, which is what decides whether a traversal runs at cache speed or at DRAM speed. This is the general shape of the ADT/implementation distinction and it will recur in every part of this series: the interface fixes what you can ask, the asymptotics are often identical across implementations, and the choice is then decided by constants, by space, or by which operations are hot.

How to read a complexity table. When a language's documentation says indexing is O(1) and insertion is O(n), it is describing the implementation, not the ADT — and the numbers only mean something once you know which of the three rows above it is. A list in a dynamic language is row two plus dynamic growth; an ndarray of a numeric type is row one; a "2-D list" is row three. Those are three different memory models wearing the same subscript syntax.

04 Referential arrays versus compact arrays

§01 required every cell to be the same width. Real collections routinely hold things that are not the same width — strings of different lengths, objects of different classes, integers of unbounded magnitude. The universal resolution is to store a fixed-width reference in the cell and the variable-width object elsewhere. That keeps the address formula intact and quietly changes almost every constant on the page.

The two layouts

  • Compact. The cell is the datum. An array of 4-byte integers holds the integers' bits; a string holds the characters' code units. itemsize is the element's own size, the block is exactly n × itemsize bytes, and one memory access gets you a value.
  • Referential. The cell holds a machine address — one word, 8 bytes on a 64-bit machine — and the object lives wherever the allocator put it. itemsize is 8 regardless of what is being stored, so the block is 8n bytes plus the objects, and getting a value costs two memory accesses: read the slot, then follow it.
bytes for n elements, compactn × itemsize (4n for 32-bit ints) bytes for n elements, referential8n + n × sizeof(boxed element) (often 8n + 16n to 8n + 28n) a worked case: one million 64-bit integerscompact: 1 000 000 × 8 B = 8 MB, one contiguous block referential: 1 000 000 × 8 B of pointers + a boxed integer object each, typically 16–28 B apiece ⇒ roughly 24–36 MB, scattered so the same data, same asymptotics≈ 3–4.5× the memory and ≈ 2× the memory accesses per element read why the box is never smalla heap object carries a header — a type/class word and usually a size or refcount word — and is padded to the allocator's alignment, so 16 B is about the floor for a boxed 32-bit int

Three consequences worth naming

  • Aliasing becomes possible. Two cells may hold the same address, so two entries of a referential array can be the same object. Copying the array copies the references, not the objects — which is exactly right for immutable elements and a trap for mutable ones. §10 is about the bug this causes.
  • Element access is a dependent load. The second access cannot begin until the first returns, so the processor cannot overlap them. On a cache-resident array this costs a few cycles; on a large scattered one it can cost two DRAM round trips per element, which is the practical reason numerical code insists on compact storage — the ndarray is a compact array with a dtype, and that is most of why it is fast.
  • The compact form requires a declared element type. You cannot pack elements end to end without knowing their width, and you cannot know the width without knowing the type. This is why compact arrays in dynamically typed languages always come with a type code attached, and why a general-purpose list cannot be compact.

Pointers built out of indices

The relationship also runs the other way: if you have arrays but no pointers, you can synthesise pointers from indices, and this is worth seeing once because it demystifies what a pointer is. Represent a collection of records with one array per field — key[], next[], prev[] — and let the "pointer" to a record simply be a common index x into all three. Then x.next is next[x], a null pointer is any index the arrays cannot legally take (0, if the arrays are 1-based, or −1 if 0-based), and a linked list is a chain of array indices. The alternative single-array representation packs each record into a contiguous run A[j .. k], makes the "pointer" the start index j, and reaches a field by adding its fixed offset — which is precisely §01's address formula applied at the granularity of records rather than machine bytes. A pointer really is nothing more than an index into one enormous array called memory.

The decision rule. Use compact storage when the elements are numbers of a known width and the workload traverses them; use referential storage when the elements are large, heterogeneous, shared, or immutable enough that copying references is the right semantics. The asymptotics are identical either way, so the choice is made entirely on §02's ledger — bytes moved and dependent loads — plus the aliasing semantics you want.

05 What indexing buys, and what insertion costs

The contiguity that makes get(i) one step is the same contiguity that makes insert(k, v) a loop. There is no slack between cell k and cell k+1 — that is what "consecutive" means — so making room means moving every element from k to the end one position right, and closing a hole means moving every element after it one position left. Nothing is being decided cleverly here; the cost is a direct consequence of the layout, and it is the price paid for the O(1) access.

insert v at index k into n live elements (room already available)for j = n down to k+1: A[j] = A[j−1] // shift right, rightmost first A[k] = v; n = n + 1 element movesn − k worst case k = 0 ⇒ n, best case k = n ⇒ 0 delete the element at index kfor j = k to n−2: A[j] = A[j+1] // shift left, leftmost first A[n−1] = null; n = n − 1 element movesn − 1 − k worst case k = 0 ⇒ n−1, best case k = n−1 ⇒ 0 average over a uniformly random position(1/(n+1)) · ∑ₖ₌₀ⁿ (n − k) = (1/(n+1)) · n(n+1)/2 = n/2 = Θ(n)

Two details that are easy to get wrong

  • The shift direction matters. An insert must copy the rightmost element first; going left to right would overwrite each element with its predecessor before the element had been read, smearing A[k] across the tail. A delete must go the other way, leftmost first. Both loops are one line and both have exactly one correct direction — a classic source of silent corruption when the loop is written from memory.
  • The average is Θ(n), not a constant. "Inserting in the middle is only half as expensive" is true and irrelevant: n/2 is still linear. The only positions that are genuinely cheap are the ones at or near the end, which is why the end of an array is a privileged place and why every array-backed stack, queue and buffer is designed so that the mutation happens there.
  • A real implementation does not write that loop. For a compact array the whole shift is one block move of a contiguous byte range — the memmove primitive, which is specified to behave correctly when source and destination overlap and therefore handles the direction question of the previous bullet for you. A tuned memmove copies a cache line or a vector register at a time and can move an order of magnitude more bytes per cycle than a scalar element loop. It does not change the asymptotics: the work is still proportional to n − k bytes moved, and the constant, while small, is not zero. This is the standard shape of the distinction — a Θ(n) operation with an excellent constant is still Θ(n), and a loop that performs n of them is still quadratic.
The cost of making room, measured at every position the bars are counter output, the dashed line is the closed form

The bar chart is a straight line falling to zero, and that shape is the cost model: inserting at the front moves everything, inserting at the back moves nothing, and every position in between interpolates. Switch to delete and the line is the same shape shifted down by one, because a deletion at index k moves the n − 1 − k elements strictly after it. The dashed closed form is drawn from the formula and the bars from the counter; they lie on top of each other at every position, which is the check. The violet line is the measured mean over all positions — 6.0 for an insert into 12 elements, which is n/2, and the reason "insert in the middle" is not a fix for anything.

Read the table as a single sentence: arrays are fast to read anywhere and fast to modify only at the end. That is the contract. Every structure in the rest of this series exists because some workload could not live with it — a linked list buys O(1) insertion at a known position by giving up computed access; a hash table buys expected-constant insertion and lookup by giving up order; a balanced tree buys logarithmic everything by giving up the contiguous block entirely.

The move that removes the shift. When deletions are frequent and order does not matter, deleting at index k can be done in O(1): overwrite A[k] with A[n−1] and decrement the count. This "swap with the last" trick is everywhere in simulation and game code, and it is a perfect example of paying with a property you did not need — you give up the relative order of the elements and get a linear operation for a constant one.

06 Dynamic arrays: growing a thing that cannot grow

A block of memory cannot be extended in place — the bytes after it belong to something else. So a growable array is a lie told convincingly: the structure holds a block with spare capacity, tracks how much of it is live, and when the spare runs out allocates a larger block, copies everything across, and frees the old one. A single append can therefore cost Θ(n). The result that makes the structure usable is that a sequence of n appends costs Θ(n) in total, so each append is O(1) amortized.

The shape in that column of costs is the whole phenomenon: the expensive steps get more expensive without bound, and they get rarer at exactly the same rate, so their product stays flat. Notice too that the running mean is highest immediately after an expansion and lowest just before one — the sawtooth that §07's measurement runs into.

Where the derivation lives

This is the case study of amortized analysis, and it is worked three separate ways — the aggregate method, the accounting method with its three-credit charge, and a potential function Φ = 2·num − size built from its design constraints rather than guessed — in the dynamic-array section of Algorithm Analysis, together with instrumented figures showing the per-append spikes and the running mean. Two results from there are worth carrying here because they change how you use the structure, and neither is obvious from the O(1):

  • Amortized is not average-case, and the difference is what is being averaged over. An average-case bound averages over a probability distribution on inputs — it is a statement about what usually happens, and a sufficiently unlucky input can beat it. An amortized bound averages over a sequence of operations on one structure, with no probability anywhere: it is a worst-case guarantee on the total, so no input at all can make n appends cost more than 3n. The two are often confused because both produce a divided-by-n number. Say which denominator you mean and the confusion cannot survive.
  • The per-operation latency is not amortized. An amortized bound is a statement about a sequence. The individual append that triggers a reallocation genuinely copies n elements and genuinely takes linear time, and in a latency-sensitive loop that shows up as a periodic spike exactly when the structure doubles. If you need a worst-case bound per operation, a dynamic array does not give you one; you either preallocate the final capacity or use a structure that resizes incrementally.
  • Shrinking has to be hysteretic. If the array halves its block as soon as it is half empty, an adversary alternating append and delete at the boundary forces a reallocation on every operation and the amortized cost degrades to Θ(n). The standard fix is to shrink only when the array falls to one quarter full, and to shrink to half: a structure holding num = size/4 that reallocates to size/2 comes out exactly half full, so it needs size/4 further appends to fill up again and size/8 further deletions to fall to the next shrink threshold — Θ(n) cheap operations before the next resize in either direction. The general principle — after any resize, leave enough slack in both directions that a linear number of cheap operations must pass before the next one — reappears for every structure that resizes, notably hash tables.

Why the geometric rule is not negotiable

The tempting alternative is to grow by a fixed number of cells — "add 1000 each time" — which wastes less memory. It is asymptotically catastrophic. With a fixed increment c, reaching n elements requires m = n/c reallocations at sizes c, 2c, 3c, …, mc, and the copying cost is the sum of those sizes:

arithmetic growth — increment c per resizetotal copies = c + 2c + 3c + ⋯ + mc = c·m(m+1)/2, with m = n/c = (n/c)·(n/c + 1)·c/2 = Θ(n²/c) = Ω(n²) for any constant c geometric growth — factor g > 1 per resizetotal copies ≈ 1 + g + g² + ⋯ + g^(K−1) = (g^K − 1)/(g − 1) ≈ n/(g − 1) = Θ(n) the structural reasona geometric series is dominated by its LAST term; an arithmetic one is not

An increment of 1000 does not rescue it — it divides a quadratic by 1000 and leaves it quadratic, which is invisible at n = 10⁴ and fatal at n = 10⁷. The property that matters is that the amount of new space is proportional to the current size, so that the work done by each expansion is paid for by a number of cheap appends proportional to that same size. Any rule with that property gives O(1) amortized; no rule without it does.

What to take away. Appending to a dynamic array is constant time in the only sense that matters for throughput, and linear time in the sense that matters for a latency budget. Both statements are true simultaneously, they are not in tension, and confusing them is the single commonest misreading of an amortized bound.

07 Choosing the growth factor

Doubling is a convention, not a theorem. The amortized O(1) holds for any constant factor g > 1, so the factor is a free parameter and choosing it is a genuine engineering trade: a larger g means fewer copies and more wasted space; a smaller g means less waste and more copying. Both sides of that sentence have closed forms, and the figure below measures both.

The two panels move in opposite directions and that opposition is the entire content of the decision. The left one drops steeply as g rises from 1.1 — where at n = 1000 the counter records about 11.9 elementary writes per append — and then flattens hard: by g = 1.5 it is about 3.1, by g = 2 about 2.02, and by g = 4 about 1.34. Past 2 you are buying a fraction of one write per append for another 25 percentage points of memory. The right panel climbs the other way — jaggedly, because where the run happens to stop decides how much slack is live at the end — from a measured mean of about 4% at g = 1.1 to roughly 25% at g = 2 and 38% at g = 4, beneath a dashed worst case of 1 − 1/g that reaches three quarters. The knee is in the region of roughly 1.5 to 2, and the reason the conventional answer is 2 rather than 3 or 4 is that the left curve has already done nearly all of its falling by then.

Real containers are spread across a wider band than that knee suggests, because they weigh the two panels differently. Factors of 2 (several systems languages' vectors, and the growth of small slices in others) and 1.5 (several standard library list types, and one widely used C++ standard library implementation) are the commonest, but implementations that care more about memory than about copies go lower — around 1.25 for large blocks in one mainstream runtime, and about 1.125 for the list type of one widely used dynamic language, whose rule adds size/8 plus a small constant. All of those are geometric, so all of them are O(1) amortized; they differ only in where on this figure's two curves they choose to stand. The right reading of the figure is therefore "anything from about 1.1 to about 2 is a defensible engineering choice", not "the answer is 2".

Two effects visible in the figure that are not in the formula

  • The measured curve sits above the closed form, sometimes by a lot, and the gap is not an error. At g = 2, n = 1000 the measurement is 2.023 against a prediction of 2.000; at g = 3 it is 2.09 against a prediction of 1.50, which looks like a failure and is not. g/(g−1) is the limit of the running mean, and the running mean is a sawtooth — it jumps when a copy is charged and decays as cheap appends dilute it. Where you stop counting decides which part of the tooth you read. Stopping just after an expansion reads high; stopping just as the block fills exactly reads low. This is a general hazard of amortized measurement, treated at length in the amortized-analysis case study: a partial sequence is not a sequence.
  • The first few expansions are not geometric at all. A rule stated as a factor cannot grow a one-slot block — floor(1 × 1.5) = 1 — so the simulation, like every real implementation, uses max(size + 1, floor(size × g)). At small g the first several expansions therefore add a single cell each and the geometric argument has not started. Real containers avoid the region entirely by starting from a minimum capacity of four or eight.

Why an allocator might prefer 1.5

There is a second, subtler argument for a factor below 2 that has nothing to do with the slack percentage. It rests on three assumptions that have to be stated, because the argument is false without them: that the allocator hands out blocks at consecutive addresses, that it coalesces adjacent freed blocks back into one usable run, and that the old block is released only after the new one has been allocated and copied into (which is what a growable array has to do).

Under those assumptions, follow the arena. With doubling, the capacities are 1, 2, 4, 8, …; at the moment the block of 8 is requested, the block of 4 is still live and only 1 + 2 = 3 bytes of coalesced free space sit below it. Even counting the live block, the whole history is 1 + 2 + 4 = 7 < 8 — so no doubling request can ever be satisfied from the space its predecessors occupied, however the timing works out, and the arena grows monotonically. With g = 1.5 the capacities run 1, 2, 3, 4, 6, 9, 13, … and the sums catch up: when the block of 9 is requested the live block is the one of 6, the blocks of 1, 2, 3 and 4 have all been released, and they coalesce into a contiguous run of 10 ≥ 9 — so the new block can be carved out of the hole its own predecessors left.

the condition, in the limit, for the freed run to cover the next requestfreed after k expansions ≈ g⁰ + g¹ + ⋯ + g^(k−2) = (g^(k−1) − 1)/(g − 1) require it to reach the next request g^kg^(k−1)/(g − 1) ≥ g^k ⇔ 1/(g − 1) ≥ g ⇔ g² − g − 1 ≤ 0 the root of g² − g − 1 = 0g = (1 + √5)/2 = φ ≈ 1.618 sog < φ ⇒ the freed run eventually overtakes the next request, and space is reused g ≥ φ ⇒ it never does, and every expansion consumes fresh arena

Whether any of this matters depends entirely on the allocator, and modern size-class allocators — which round requests to fixed buckets and never coalesce across buckets — make the argument largely moot. It is the argument usually offered for preferring 1.5 to 2, and it is worth knowing for that reason and because it is a clean example of a constant-factor consideration that no asymptotic analysis can see. It is not, however, a proof that 1.5 was chosen for this reason in any particular implementation; treat that as folklore unless you have read the commit that made the choice.

Preallocation beats every factor. If you know the final length, ask for it up front. That turns the whole discussion off: no expansions, no copies, no slack, exactly n cells and exactly n writes. The growth factor is a policy for when you do not know — which is most of the time, which is why the policy exists.
