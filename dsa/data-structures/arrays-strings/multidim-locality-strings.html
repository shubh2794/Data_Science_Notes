08 Multidimensional arrays: rows, columns, and strides

Memory is one-dimensional. A matrix is not. So a two-dimensional array is always a convention for flattening — a rule that turns a pair of subscripts (i, j) into a single offset. There are exactly two sensible rules, they differ only in which subscript varies fastest along the block, and the choice is invisible to correctness and enormous to performance.

row-major: the last subscript varies fastest — rows are contiguousoffset(i, j) = i × ncols + j address = base + offset × itemsize column-major: the first subscript varies fastest — columns are contiguousoffset(i, j) = j × nrows + i the general d-dimensional form, in terms of stridesoffset(i₁, i₂, …, i_d) = i₁·s₁ + i₂·s₂ + ⋯ + i_d·s_d row-major strides for shape (n₁, n₂, …, n_d)s_d = 1, s_k = n_(k+1) × n_(k+2) × ⋯ × n_d (each stride is the size of one slice below it) costd multiplies and d−1 adds — O(d), independent of every nₖ. Still O(1) for fixed d.

A worked offset

Take a 3 × 5 array of 4-byte values with base = 4096. Row-major strides are s₁ = 5, s₂ = 1. Then element (2, 3) — third row, fourth column, counting from zero — sits at offset 2 × 5 + 3 = 13, so at address 4096 + 13 × 4 = 4148. Under column-major the strides are s₁ = 1, s₂ = 3, the same element sits at offset 3 × 3 + 2 = 11, and its address is 4096 + 44 = 4140. The same logical element, two different addresses, because the flattening rule is different. Nothing about the matrix changed; the convention did. This is why passing a buffer between two libraries that disagree about the convention transposes your data silently, and why every serious array library records the strides explicitly rather than assuming them.

Strides make views free

Once the offset is a dot product of subscripts with strides, several operations become pure bookkeeping on the stride vector, touching no data at all:

  • Transpose — swap the two strides and the two dimension lengths. O(1). The transposed view is row-major read as column-major; no element is moved, which is precisely why a transposed view then traverses badly (§09).
  • A row slice — keep the row stride, advance the base by i × s₁ × itemsize. O(1), and the result is itself contiguous.
  • A column slice — keep the base, take stride s₁ with length nrows. O(1), and the result is not contiguous: a column of a row-major matrix is a strided walk with a gap of ncols − 1 elements between consecutive entries.
  • Every other step, reversal, broadcasting a length-1 axis — all expressible as changes to strides and lengths. The ndarray is exactly this idea made into a type, and "is this array contiguous?" is a question its users learn to ask because the answer decides whether an operation copies.

The other layout: an array of arrays

Instead of one flat block, hold an array of nrows references, each pointing at its own row block. A[i][j] then means "read the reference in slot i, then index into that block at j" — two address computations and two dependent memory accesses. The consequences are a clean list of trade-offs:

The flat block is what numerical and image code uses; the array of rows is what a general-purpose language gives you when you write a list of lists, and it is why a "2-D list" and a real 2-D array have such different performance despite identical subscript syntax. Higher dimensions extend both schemes without any new idea — a 3-D array is a flat block with three strides, or an array of arrays of arrays, and the same table applies one level deeper.

The matrix ADT sits on top of either. A matrix is a 2-D array plus the operations that make it a matrix: scalar multiply, add and subtract (all elementwise, all Θ(nrows × ncols)), transpose, and the multiply that costs Θ(n³) by the schoolbook method and less by divide-and-conquer methods such as Strassen's. The storage decision above is invisible in that interface and decisive in its constants — which is the §03 lesson again, in the place where it costs the most.

09 Traversal order and the cache, measured

Traversal order is the sequence of addresses a loop nest actually visits, and for a multidimensional array it is decided by which subscript sits in the inner loop. A nest whose inner subscript is the fastest-varying one — j for a row-major array — walks the block from front to back, one offset at a time. A nest that puts the other subscript inside walks it in jumps of one full row. Both visit exactly the same n² cells, do exactly the same arithmetic and produce exactly the same output, so no complexity analysis can tell them apart; measured on a machine they can differ by close to an order of magnitude. This is the canonical demonstration that asymptotics and running time are different questions, and it is worth doing once with the misses actually counted rather than asserted.

the two loops over a row-major n × n arrayfor i = 0 … n−1: for j = 0 … n−1: visit A[i][j] // consecutive offsets: 0, 1, 2, 3, … for j = 0 … n−1: for i = 0 … n−1: visit A[i][j] // offsets jump by n each step the cache model used below, stated so the numbers mean somethingfully associative, LRU replacement, C lines, L elements per line, initially empty a miss fetches the whole line containing the element; a hit costs nothing row-major sweep — each line is entered once, used L times, never revisitedmisses = ceil(n² / L) column-major sweep — when the working set of one column exceeds the cachemisses = n² (every access fetches a line and evicts it before it is reused)

At the default settings — n = 8, eight elements per line, a four-line cache — the row-major sweep records 8 misses and 56 hits: it enters each of the eight lines once and then reads the other seven elements of that line for free. Select the column-major traversal and the same sweep records 64 misses and 0 hits, one per access — its tape turns solid red. That is a factor of eight, which is not a coincidence: it is L, the line size, because the bad order throws away exactly the L − 1 elements that came along for the ride with every fetch. Raise the line size and the ratio rises with it; raise C until the whole matrix fits and the gap collapses, because at that point the cache is big enough that even the bad order revisits resident lines.

Read the controls as an experiment, not a demo

  • The gap is governed by the working set, not by the order as such. A column sweep of a row-major matrix touches one element from every line in the array before it returns to the first — a working set of n²/L lines. If the cache holds that many, every miss is compulsory and both orders take ceil(n²/L). Push C to 8 with n = 4 and L = 4 and you can watch the two bars meet. On a real machine the same collapse happens for small matrices and is the reason a micro-benchmark on a 64 × 64 matrix can show no effect at all while a 4096 × 4096 one shows a factor of ten.
  • The fix is to change the order, not the algorithm. Swapping the loop nest so the inner variable indexes the fastest-varying subscript costs nothing and is the single highest-leverage change available in array code. Where the algorithm genuinely needs both orders — matrix multiply reads one operand along rows and the other along columns — the standard answer is blocking: process the matrices in tiles small enough that a tile's working set fits in cache, so each loaded line is fully used before it is evicted. The asymptotic count of multiplications is unchanged; only the miss count moves.
  • The model here is deliberately simple, and its errors do not all point the same way. The formula block above states the model exactly — fully associative, LRU, C lines of L elements, initially empty — and every number the figure prints is a count under that model, not a prediction about a machine. Three ways a real cache departs from it, with the direction of each departure named honestly:
    • Set associativity widens the gap. A real cache maps an address to one of a few ways in a fixed set. A column sweep whose stride is a large power of two can land on the same set every time, so the column's working set thrashes a handful of ways instead of the whole cache — conflict misses the fully associative model cannot produce. The column side gets worse; the row side is untouched. The figure understates the gap here.
    • Address translation widens the gap for large arrays. Each step of a column sweep advances by one row. Once a row is as large as a page, every access lands on a new page and the translation lookaside buffer misses as well as the cache. The row-major sweep pays one TLB miss per page; the column sweep can pay one per access. None of this is in a model that counts only cache lines.
    • Prefetching does not straightforwardly widen it, and can narrow it. This is the claim to be careful with. First, a prefetch does not remove a line transfer — the line is still fetched from memory; the prefetcher only issues the request early enough to hide the latency. The miss counts this figure reports are therefore unchanged by prefetching; what changes is time, which is a different ledger. Second, and more to the point, the hardware prefetchers on mainstream cores track constant strides, not just unit strides — and a column sweep of a row-major matrix is a perfectly constant stride. When the row is small enough that the stride stays inside the prefetcher's window (typically a few hundred bytes) and does not cross a page boundary — most prefetchers will not prefetch across one — the column sweep gets prefetched too, and the measured time gap narrows relative to what a pure miss count predicts. For large matrices, where the row stride exceeds those limits, prefetching helps only the row-major side and the gap widens. So the honest statement is: the direction of the prefetching correction depends on the row length, and the figure's miss counts are not a proxy for it either way.

What the figure does license, then, is the narrow claim and not the broad one. Under the stated model, at the stated parameters, the bad order pays L times the line transfers of the good one, and that ratio is a theorem about the model. Whether a particular machine shows a factor of eight, or three, or none at all is an empirical question about associativity, prefetchers, page size and the size of the matrix, and the only way to settle it is to measure on that machine. The reason to trust the qualitative conclusion anyway is that the mechanism — a fetched line whose other L − 1 elements are discarded before they are used — is real on every cache ever built.

Why this belongs on a page about arrays. Contiguity is not merely a way to compute addresses; it is a promise about which elements arrive together. An algorithm that consumes elements in storage order collects on that promise and one that does not throws it away. Every later structure in this series can be judged on the same axis, and it is most of the reason a flat array with a worse asymptotic bound so often beats a pointer structure with a better one.

10 Slices, views, copies — and the aliasing bug

A slice is a contiguous run of an array named as if it were an array itself. Because the run is contiguous, it can be described by three numbers — base, length, stride — and therefore there are two entirely reasonable things a language can mean by A[2:6]: a view that shares the original storage, or a copy that owns new storage. They have different costs and, far more dangerously, different semantics under mutation.

a slice as a triple, with no data touchedview(A, lo, hi) = (base + lo × itemsize, length = hi − lo, stride = 1) costview: O(1) time, O(1) extra space, writes are visible through the original copy: Θ(hi − lo) time and space, writes are private a strided sliceview(A, lo, hi, step) = (base + lo × itemsize, length = ceil((hi − lo)/step), stride = step)

Three layers of "copy", and which one a language gives you

  • No copy — a view. The slice is a window onto the same bytes. Free to make, and every write through either name is seen through the other. This is what array libraries built for numerical work do, because copying a 100 MB sub-matrix to read one row would be absurd.
  • A shallow copy. A new block of cells is allocated and the cell contents are copied. For a compact array of numbers that is a full copy and there is nothing more to say. For a referential array the cells contain addresses, so what is copied is the addresses — the new array points at the very same objects. The containers are independent; the elements are shared.
  • A deep copy. The cells and, recursively, the objects they refer to are duplicated. This is the only one that gives complete independence, it is the most expensive, and it is the one a language almost never gives you by default.

The bug, in its standard form

The classic failure is building a grid of rows by replicating a row. Replication in a referential array copies the reference n times, so all n "rows" are one row under n names. Writing one cell appears to write a whole column:

what was intendedgrid = n copies of a fresh row of zeros what replication actually buildsgrid[0] = grid[1] = … = grid[n−1] = the SAME row object sogrid[0][2] = 7 ⇒ grid[i][2] == 7 for every i the fix — construct a distinct row per indexgrid[i] = a new row of zeros, allocated once per i

The same mechanism produces the subtler version: appending a mutable element to a list and then mutating it afterwards changes what the list holds, because the list holds the object rather than a snapshot of it. Both bugs feel like the container misbehaving; both are the container behaving exactly as documented, on a mental model in which cells hold values rather than addresses.

A defensive checklist

  • Know which of the three you got. Whether slicing yields a view or a copy is a documented property of the type you are using, and the two are indistinguishable until someone writes through one of them. If a function receives a slice and mutates it, the answer decides whether the caller's data changed.
  • Views keep the whole buffer alive. A 12-element view of a 100-million-element array holds a reference to the whole allocation, so the memory cannot be released. Extracting a small window from a large array and retaining it is a genuine leak pattern; the cure is an explicit copy at the point of extraction.
  • Sharing is only safe when the elements are immutable. This is the argument for immutable strings (§11) stated from the other side: if a value cannot change, sharing it can never surprise anyone, and every copy can safely be a reference copy.
  • Mutating a container while iterating over it is a separate hazard with the same flavour. Deleting during a forward scan shifts the tail left under the cursor and silently skips an element. Iterate over a copy, build a new array, or walk backwards.
The general rule. An array cell holds a fixed-width thing. Whether that thing is the value or the address of the value is the single most consequential fact about the type you are using, and almost every surprising behaviour of arrays and lists in a high-level language reduces to it.

11 What a string is: an array with two extra rules

A string is a compact array of character codes. That is the whole definition, and everything distinctive about strings follows from two decisions layered on top of it: the elements are drawn from an encoding rather than being plain integers, and in most modern languages the array is immutable. The first decision breaks the assumption that one character is one cell; the second turns an innocuous loop into a quadratic one.

Rule one: encodings, and why "length" is ambiguous

  • Fixed-width encodings keep §01 intact. ASCII or Latin-1 at one byte per character, or UTF-32 at four, make itemsize a constant, so s[i] is one address computation and the i-th cell is the i-th character. Simple, and wasteful for text that is mostly ASCII.
  • Variable-width encodings break it. In UTF-8 a code point occupies one to four bytes; in UTF-16 one or two 16-bit units. The cells are still uniform — they are bytes, or 16-bit units — but a cell is no longer a character. Indexing by code point then costs Θ(i), because you must decode forward from the start, and the O(1) promise of §01 quietly applies to a different unit than the one you meant.
  • So "the length of a string" has at least four answers — bytes, code units, code points, and user-perceived characters (grapheme clusters, where an accent or a skin-tone modifier joins the preceding character). They coincide for ASCII and diverge for everything else, and a great many text bugs are a disagreement about which one a piece of code is counting. Languages pick different defaults; libraries that slice by byte offset can cut a code point in half.
  • Implementations cheat productively. A common strategy is to store an all-ASCII string as one byte per character and widen only when a non-ASCII character appears, so the common case keeps constant-time indexing and the general case still works. The lesson is the §03 one: the interface says "a sequence of characters", and what it costs depends entirely on the layout underneath.

Rule two: immutability, and the loop everyone writes once

If a string cannot be modified, then s = s + ch cannot append. It must allocate a new block of length |s| + 1 and copy every character of s into it. Doing that in a loop to build a string of length n copies 1 + 2 + ⋯ + n characters:

The parabola sits exactly on its dashed closed form n(n+1)/2 at every point, which is the check that the counter is counting what the algebra describes. The green line is Θ(n) with a small constant — roughly three copies per character, one to place it, about one more for the array's amortized doubling (§06), and one for the final join. On the logarithmic axis the two become straight lines of slope 2 and slope 1, which is the cleanest possible statement that one is quadratic and the other linear. The asymmetry is brutal and grows without bound: at n = 200 the measured ratio is 30.7×, at n = 400 it is 61.2× — it roughly doubles when n does, because a quadratic divided by a linear is a linear.

Why immutability is chosen anyway

  • Sharing becomes free and safe. An immutable string can be handed to any number of holders, stored as a dictionary key, cached, interned, or shared between threads without a lock, because no holder can invalidate another's view. That is the §10 aliasing problem simply not existing.
  • Hashes and lengths can be cached. A value that cannot change can have its hash computed once and stored, which is what makes strings cheap dictionary keys.
  • Substrings can be views. If nobody can write, a substring can share the parent's buffer. (This is a real technique with a real cost — it keeps the parent alive, §10 again — so implementations differ on whether they do it.)
  • The escape hatch is a mutable builder. Every language that makes strings immutable provides a growable buffer for the times you need to accumulate: build there, convert once at the end. That is exactly the green line in the figure, and it is the only correct habit for assembling text in a loop.
A warning about the warning. Some runtimes special-case s += ch when they can prove there is exactly one reference to s, mutating the buffer in place and turning the quadratic loop linear. That optimisation is fragile — one extra reference anywhere and the quadratic behaviour returns — and it is not guaranteed across implementations. Do not write code whose complexity class depends on an optimiser noticing something. Collect and join.
