Balanced & Multiway Trees

A binary search tree answers every question in O(h), and nothing in its definition stops h from reaching n − 1: feed it sorted keys and it collapses into a list. A balanced tree is a search tree with one more invariant — a rule about shape, colour, fan-out or randomness — chosen so that the invariant forces h = O(log n) and can be restored after any update for O(log n) work. This page is the catalogue of those rules and the proofs that they work: rotations, the one primitive that reshapes a tree without disturbing its order; AVL trees, whose height bound comes out of the Fibonacci numbers; red-black trees and the black-height lemma; 2-3-4 trees and B-trees, which buy perfect depth balance by letting a node hold many keys — and which are what a disk, a database index and a cache line actually want; splay trees, balanced only on average, with the potential-function proof; skip lists, balanced only in expectation, with the coin-flip analysis; and the digital and implicit trees — tries, segment trees, Fenwick trees — whose depth is bounded by something other than n. Every height on the page is measured on a tree that was built and checked, and every bound is derived, not quoted.

01 What a balanced tree is

A balanced search tree is a search tree together with a structural invariant that (i) implies a height of O(log n) for every tree satisfying it, and (ii) can be re-established after any insertion or deletion with O(log n) work. Both halves are needed. An invariant that bounds height but costs Θ(n) to restore — "the tree is perfectly balanced", say — makes updates as slow as rebuilding; an invariant that is cheap to keep but does not bound height — "every node is a valid BST node" — is the plain search tree, and its height is whatever the input made it. The structures on this page are the invariants that satisfy both conditions, and the page is organised by what kind of promise each invariant makes: a worst-case bound on every operation, an amortised bound over a sequence, or an expected bound over the structure's own coin flips.

Why the height lemma is always a counting argument

Every worst-case bound on this page is proved the same way, and it is worth seeing the shape once before meeting it four times. To show that an invariant forces h ≤ c·log n + d, you do not bound the height directly; you bound the smallest tree the invariant allows at a given height. Let N(h) be the minimum number of nodes in a tree of height h that satisfies the invariant. If the invariant is any good, N(h) grows exponentially — N(h) ≥ b·aʰ for some a > 1 — because it forbids the thin shapes. Then any tree of height h has n ≥ N(h) ≥ b·aʰ, so h ≤ log_a(n/b) = log_a n − log_a b, and c = 1/log₂ a. For AVL trees N(h) = N(h−1) + N(h−2) + 1, a Fibonacci recurrence with a = φ ≈ 1.618 and c = 1/log₂ φ ≈ 1.4405. For red-black trees the count is by black-height: N ≥ 2^bh − 1 and h ≤ 2·bh, giving a = √2 and c = 2. For B-trees the count is by fan-out: N ≥ 2·tʰ − 1 keys, a = t, c = 1/log₂ t. The constant c is the whole difference between the families' worst cases — 1.44, 2, and 1/log₂ t — and the sections below derive each one exactly rather than stopping at "O(log n)", because the exact constant is what decides AVL versus red-black in §12 and what makes a B-tree's height 3 or 4 on a billion keys in §16.

Three promises, and why the difference matters

  • Worst case (AVL, red-black, B-tree): every operation on every tree that satisfies the invariant costs O(log n). This is the promise a real-time system, a kernel scheduler or a database needs — no single operation can stall — and it is the most expensive to keep, because the invariant must be restored before the operation returns.
  • Amortised (splay trees, and the deletion side of some others): any sequence of m operations costs O(m log n) in total, so the average per operation is O(log n) — but one operation in the sequence may cost Θ(n). The accounting is the potential method of Algorithm Analysis §19, and §20 instantiates it. What you buy for the weaker promise is simplicity (no balance information stored per node) and an adaptivity no worst-case structure has: frequently accessed keys drift to the top.
  • Expected (skip lists, treaps): the bound holds on average over the structure's own random choices, for every input. This is different from the "random insertion order" hypothesis of the plain BST, where the randomness is assumed to be in the input and an adversary who controls the input breaks it; here the adversary controls the input and still cannot force a bad shape, because the shape does not depend on the input. A bad run of coins can produce a bad shape, but with probability that vanishes polynomially in n (§22).
The one sentence to carry through the page. A balanced tree is an invariant plus a repair procedure; the invariant is chosen so that a counting argument bounds the height, the repair is chosen so that it touches only the path just walked. Everything else — rotations, colours, splits, coin flips — is a particular way of making that sentence true.

02 Rotations: the one primitive, proved order-preserving, O(1)

A rotation is a local restructuring of a binary search tree that changes the depth of two of its three subtrees by one level while leaving the inorder sequence of keys unchanged. It is the only shape-changing operation that AVL trees, red-black trees, splay trees and treaps use, and everything they do reduces to "walk a path, then rotate at a few nodes on it". A rotation touches two nodes and rewires three pointers (six with parent pointers), so it costs O(1); the proof that it preserves the search-tree invariant is a two-line inspection of where the three subtrees end up, and it is the proof that every balancing algorithm inherits.

Where rotations happen, and why that keeps the repair O(log n)

In every rotation-based structure the rotations are performed at nodes on the path the update just walked — the insertion path, or the path from the deleted node's position up to the root. That path has h + 1 nodes, and each rotation is O(1), so even if every node on the path were rotated the repair would cost O(h) = O(log n), which is the second half of the definition in §01. The structures then differ in how many rotations they actually need: AVL insertion needs at most one restructuring (one or two rotations), AVL deletion can need one at every level; red-black insertion at most two rotations and deletion at most three; a splay needs a rotation at every node of the path by design. Those counts are measured in §07, §10 and §19. A rotation also disturbs any per-node summary — height, subtree size, colour, maximum endpoint — of exactly the two rotated nodes, and only those, which is why augmentation and balancing coexist: §28.

Rotations are not "rebalancing". A rotation on its own does not know anything about balance; it is a pure change of shape that preserves order. The choice of where to rotate, and in which direction, is what each structure's invariant supplies. The same primitive serves a height rule (AVL), a colour rule (red-black), a priority rule (treap) and no rule at all (splay).

03 AVL trees: the height-balance invariant and the balance factor

An AVL tree is a binary search tree in which, at every node, the heights of the left and right subtrees differ by at most one. That single inequality, checked at every node, is the invariant; the balance factor bf(x) = height(x.left) − height(x.right) is the number that records it, and the invariant says bf(x) ∈ {−1, 0, +1} everywhere. It is the oldest balancing invariant (1962) and the most rigid: an AVL tree is never more than about 44% taller than a perfect tree of the same size (§04), which makes it the structure with the fastest lookups among the worst-case families, and the one that pays for that with the most work on deletion (§06).

Why "height", and why "one"

The choice of height rather than size is what makes the repair local. A rotation changes the heights of exactly two nodes by exactly one, and it can be shown (it is the case analysis of §05) that a rotation or double rotation at the lowest unbalanced node always brings that node's bf back into range. A size-based rule — "neither subtree holds more than a fraction α of the nodes", the weight-balanced tree — also works and also uses rotations, but its analysis is heavier and its constant is worse for the strictest settings; it is mentioned in §30 and not developed here. The choice of "one" rather than "zero" is what makes the invariant maintainable at all: a tree in which every node had bf = 0 would be perfect, and perfect trees exist only for n = 2ᵏ − 1, so inserting into one would necessarily break it and restoring it would cost Θ(n). Allowing a difference of one gives just enough slack that some valid tree exists for every n and that the repair after an update is confined to the update's path. Allowing two or more would still work and would reduce rotations, at the price of a worse constant in the height bound: the bound's 1.4405 is the price of "one", and it is the best constant any of the worst-case BINARY families achieves (a multiway tree beats it by having more than two children).

A useful way to see the invariant is as a rule about the minimum a subtree must contain given its height, which is exactly how §04 proves the bound. If a node has height h, one of its subtrees has height h − 1 and the other has height at least h − 2; so the node holds at least 1 + N(h−1) + N(h−2) nodes, where N(·) is the minimum for that height. The inequality "differs by at most one" is the "h − 2" in that sentence, and it is why the Fibonacci numbers appear.

A vocabulary note. Some treatments define balance factor as height(right) − height(left), so that the signs flip; some count height in nodes so that a leaf has height 1. Neither changes anything except which of the mirror-image cases is called "left". This page uses left − right, edges, height(∅) = −1, consistent with the tree page's conventions.

04 The AVL height bound, derived: h < 1.4405·log₂(n + 2) − 1.3277

The bound is the counting argument of §01 carried out exactly. Let N(h) be the minimum number of nodes in an AVL tree of height h. The root of such a tree has one subtree of height h − 1 (someone must reach the bottom) and, by the invariant, the other of height at least h − 2; to be minimal, it is exactly h − 2 and both subtrees are themselves minimal. That is a Fibonacci recurrence with an extra +1, its solution is a shifted Fibonacci number minus one, and the height bound follows by inverting the closed form.

Reading the bound: what the 1.44 means and when it bites

The constant 1/log₂ φ ≈ 1.44 is the worst-case ratio of AVL height to perfect height, and it is approached only by the Fibonacci trees — the "thinnest" AVL trees, which are thin in a very specific way: every node's shorter side is one level shorter, all the way down. A tree built by inserting random keys does not look like that: the figure in §07 measures AVL heights of 13.2 on average at n = 4 096 against the bound's 15.96 and the perfect 12, so in practice an AVL tree sits within about one level of perfect. The bound matters because it is a guarantee: nothing an adversary inserts or deletes can push the height past it, which is the promise a plain BST cannot make and a red-black tree makes only with the constant 2. The difference between 1.44 and 2 is the whole of the AVL-versus-red-black trade of §12: a stricter invariant, a shorter tree, more rotations to keep it.

The statement to check when you quote it. "AVL height is about 1.44 log n" is loose in three ways: the argument is n + 2, not n; there is an additive constant that depends on whether height counts edges (−1.33) or nodes (−0.33); and it is a strict upper bound, not an approximation — typical heights are near log₂ n. The exact form is the one to write.

05 AVL insertion: the four cases, and why one restructuring always suffices

Insertion into an AVL tree is a plain BST insertion — a failed search, then a new leaf — followed by a walk back up the search path recomputing heights. The new leaf can raise the height of every subtree on the path by one, which can push some node's balance factor from ±1 to ±2. The lowest such node, call it z, is fixed by a single rotation or a single double rotation, and — the fact that makes AVL insertion cheap — after that fix, the subtree at z's position has exactly the height it had before the insertion, so no ancestor of z is out of balance and the walk can stop.

The iterative version, and what to store

The recursive form recomputes the height at every node of the path on the way back up, which is O(h) and harmless. An iterative implementation with parent pointers can stop earlier: walking up from the new leaf, if a node's balance factor becomes 0 after the update, its subtree's height did not change (it was ±1 before, and the insertion filled in the shorter side), so nothing above it can be affected and the walk ends; if it becomes ±1, the height grew by one and the walk continues; if it becomes ±2, rotate and stop. Storing only the balance factor (two bits, often packed into a pointer's spare bits) rather than the height is the space-frugal choice and needs exactly this case analysis, since a balance factor cannot be recomputed from the children's balance factors alone; storing the height (one small integer) makes every update a recomputation and is what this page's code does. Either way the per-node overhead is one word or less — larger only than a red-black tree's single bit and the splay tree's zero.

06 AVL deletion: the same cases, but the repair can cascade to the root

Deletion is the three-case BST deletion — splice out a node with fewer than two children, or replace a two-child node's key by its successor's and splice out the successor — followed by the same walk up the path with the same rebalance. The difference is in what a rotation achieves. After an insertion, the rotation returns the subtree to its pre-insertion height and the walk stops. After a deletion, the rotation can leave the subtree one level shorter than it was, which is exactly the situation that caused the rotation one level down — so the parent may now be out of balance too, and the repair may continue all the way to the root — though not at every level: a restructuring ancestor must be two levels above the previous one, so at most floor(h/2) restructurings (up to h rotations if all are doubles), every other level at worst — which is exactly what the cascade figure shows.

08 Red-black trees: the five properties, black-height, and the height lemma proved

A red-black tree is a binary search tree in which every node carries one bit, its colour, subject to five properties whose joint effect is that no root-to-leaf path is more than twice as long as any other. Where the AVL invariant is a rule about heights, the red-black invariant is a rule about counts of black nodes on paths — an approximate balance that is looser than AVL's (height up to 2·log₂(n+1) rather than 1.44·log₂(n+2)) but cheaper to maintain: an insertion needs at most two rotations and a deletion at most three, with the rest of the repair being recolouring, which never changes shape. The properties are stated over a tree whose empty subtrees are represented by a single shared black sentinel, nil, which is what makes "every leaf is black" a sentence rather than a special case.

Why colour rather than height

The red-black invariant looks less natural than AVL's until you see what it encodes. Property 5 says that if you erase the red nodes — merge each red node into its black parent — every leaf ends up at the same depth: the black nodes form a perfectly balanced tree of variable fan-out, and the red nodes are the "extra" keys that let a black node hold two or three keys instead of one. That tree is the 2-3-4 tree of §11, and the red-black tree is its binary encoding: a way to get perfect depth balance on the multiway tree while storing plain binary nodes with one extra bit. Property 4 bounds how many extra keys a black node can absorb (at most two reds hang from one black, so a multiway node has at most 3 keys), and that is what keeps the encoding's binary height within twice the multiway height. Seen this way the repair rules of §09 and §10 stop being a list of cases to memorise and become "split an overfull multiway node" and "borrow from or merge with a sibling", the operations of §13.

10 Red-black deletion: the "doubly black" node, four cases, at most three rotations

11 A red-black tree is a 2-3-4 tree in disguise — the isomorphism, and the left-leaning variant

Take any red-black tree and merge every red node into its black parent. Because a red node's children are black (property 4), each black node absorbs at most two reds, giving a node with one, two or three keys and two, three or four children — a 2-3-4 tree. Because every root-to-nil path has the same number of black nodes (property 5), every leaf of the merged tree is at the same depth — the defining property of a 2-3-4 tree (§13). The correspondence goes both ways, up to the choice of which key of a 3-node is the black one, and it explains every red-black rule as a multiway rule: insertion case 1 is splitting a 4-node, cases 2 and 3 are rearranging within a node, the deletion cases are transfer from a sibling and fuse with a sibling.

13 Multiway search trees: 2-3 and 2-3-4 trees, and the split / transfer / fuse repairs

A multiway search tree is a tree in which a node with d children holds d − 1 keys in sorted order, the i-th key separating the i-th subtree from the (i+1)-th. A binary search tree is the case d = 2 everywhere. Allowing d to vary between 2 and some maximum is what makes a new kind of balance possible: instead of keeping heights within one of each other, keep every leaf at exactly the same depth and absorb the irregularity of the input in the widths of the nodes. A 2-3 tree allows 2- and 3-nodes; a 2-3-4 tree allows 4-nodes as well; a B-tree of minimum degree t allows t to 2t children. The operations are the same in all three, and the 2-3-4 tree is the one to learn them on because it is small enough to draw and is exactly the B-tree with t = 2.

Top-down versus bottom-up, and the 2-3 tree

The description above repairs after the insertion, walking back up the path (bottom-up). A 2-3-4 tree can also be maintained top-down: on the way down during an insertion, split every 4-node you pass through (pushing its middle key into the parent, which cannot be a 4-node because it was split a moment ago), so that when you reach the bottom the leaf-level node has room and no upward pass is needed. This is the form that maps most directly onto the red-black insertion cases — a top-down case 1 at every 4-node — and it is the form the B-tree insertion of §15 uses, where a single downward pass matters because every node visited is a disk read. The 2-3 tree, which forbids 4-nodes, has the same bounds with slightly different arithmetic (log₃(n+1) ≤ h ≤ log₂(n+1)); it cannot be maintained top-down in the same way (a 3-node cannot be split pre-emptively without creating a 2-node that might immediately need a key), and it is the tree encoded by the left-leaning red-black variant of §11. Both are drawn, inserted into and deleted from by the B-tree figures of §15 with t = 2; there is no separate implementation on this page because there is no separate structure.

What the multiway idea really changes. In a binary balanced tree the repair is a rotation, a change of shape. In a multiway tree the repair is a change of width — split, transfer, fuse — and the shape (every leaf at the same depth) never changes except uniformly at the root. That is why B-trees are so natural on disk: the shape is trivially balanced, and the width is chosen to fill a block.

16 The I/O model: why the fan-out follows the block size, and what a search really costs

A B-tree is analysed in a different cost model from every other structure on this page. In the external-memory (I/O) model the cost of an algorithm is the number of blocks of B bytes transferred between a slow, large memory (disk, or main memory seen from a cache) and a fast, small one; CPU work within a block that is already in fast memory is free. A B-tree node is sized to be exactly one block, so a search costs h + 1 block transfers, and the design question becomes: given B, how large can t be? The answer — t in the hundreds — is what makes the height 3 or 4 on a billion keys.

What the model gets right, and what it hides

The model predicts the B-tree's dominance on disk correctly: the height of the tree is the number of dependent reads, and a search on a billion keys that costs four reads on a B-tree costs thirty on any binary tree. It also predicts, less obviously, that the same argument applies one level up the hierarchy — main memory seen from a processor cache is a slow memory with 64-byte blocks — which is why in-memory B-trees with small t beat red-black trees on lookups (§18). What the model hides is the CPU cost inside a node: a scan over 255 keys is 255 comparisons, a binary search over them about 8, and on an in-memory B-tree that difference is the whole running time; it also hides write amplification (a one-key change rewrites a whole block), the cost of keeping a node's keys sorted on insertion (a shift of up to 2t entries), and concurrency (a split locks three blocks). Real systems answer these with binary search within nodes, unsorted-then-sorted leaf layouts, copy-on-write pages and latch-crabbing protocols; the data-structure view here is the invariant they all preserve.

The claim that is backwards. "B-trees are for disk." B-trees are for any memory hierarchy with a block size larger than a node — which is every memory hierarchy. They were designed for disks, where the ratio of block size to key size is thousands; they pay off in RAM, where the ratio is a handful, for the same reason at smaller scale. §18 makes the in-memory case.

17 B⁺-trees: records only in the leaves, leaves chained, and the range scan — the database index

The B-tree of §14 stores a key's record (or a pointer to it) in whatever node holds the key, internal or leaf. 18 B-trees in memory: the cache line is the block

The I/O argument of §16 does not care whether the slow memory is a disk or DRAM. A processor reads main memory in 64-byte lines through a cache hierarchy, and a pointer-chasing search — one node per line, one dependent load per level — costs one cache miss per level of a binary tree: roughly 20 misses on a million keys, each a hundred nanoseconds or so during which the processor can do little else. A B-tree whose node is a few cache lines with a small t (8 to 32) reduces the levels to 4–7 and does the within-node work on data that is already in the cache. That is the reasoning behind the ordered-map implementations of at least one modern systems language and the recommendation of experienced library designers, quoted on the BST page: the tree that wins in memory is the one designed for disk, scaled down.

When the binary tree still wins

The B-tree's in-memory advantage is a constant factor from locality, and constant factors have conditions. If the map is small enough to sit in the fastest cache entirely, every node is a hit and the binary tree's simpler per-node work can win. If the elements are large or expensive to move (big keys, non-movable objects), the B-tree's shifts and splits cost more than a rotation's pointer swaps, and an intrusive red-black tree — where the node lives inside the object and nothing is ever copied — is the better fit; that is the design of the kernel data structures mentioned in §31. If stable references to elements are required across insertions, a binary node never moves and a B-tree entry does. And if the workload is dominated by inserting and deleting under concurrent access, the binary tree's O(1)-rotation repair touches a bounded number of nodes and is easier to lock. The honest summary is the one measured in §30: same asymptotics, and the winner is chosen by memory layout, element size and concurrency.

19 Splay trees: no invariant at all — move every accessed node to the root

A splay tree is a binary search tree with no balance information and one rule: after every access — search, insert or delete — the node accessed is rotated up to the root by a specific sequence of double rotations called splaying. Nothing bounds the height; a splay tree can be a chain, and a single access can cost Θ(n). What the rule buys is a guarantee on sequences: any m operations on a tree that never exceeds n nodes cost O(m log n) in total, so the amortised cost per operation is O(log n) — the same bound as AVL and red-black, with zero bytes of overhead per node and with an adaptivity they lack, since recently and frequently accessed keys end up near the top. The rule's details matter: rotating the node up one level at a time ("move to root") does not give the bound; the pairwise steps below do.

What "amortised" does not promise. A splay tree cannot be used where a single operation's latency matters — a real-time scheduler, a lock held during the operation, a request with a deadline — because that one operation may be Θ(n). It is the right structure when the total time of a long sequence is what counts and the access pattern is skewed toward a working set — caches, symbol tables in compilers, the internals of some garbage collectors — and it is the structure of choice when per-node memory must be zero.

21 Skip lists: balance by coin flip — the structure, search, insert and delete

A skip list is a sorted linked list with express lanes: level 0 holds every key in order; level 1 holds a random subset of them, each promoted with probability p; level 2 a random subset of level 1; and so on, with a head node of −∞ that reaches every level. Every key is a tower whose height was decided by coin flips at insertion time and never changes. A search starts at the top of the head and, at each level, moves right as far as it can without passing the key, then drops one level; at level 0 it lands on the key or on its predecessor. The structure is not a tree, but it behaves like one — the level-i list is the set of nodes within i levels of the ROOT of a randomised balanced tree, counting from the top — the higher the level, the sparser the list — and it gets the balanced tree's bounds in expectation over its own coins, with insertions and deletions that are nothing but linked-list splices.

22 The probabilistic analysis: expected height, expected search cost, expected space — and what "expected" means here

The skip list's bounds are expectations over the coin flips, and the distinction from the random-input BST of the BST page is the whole reason to use one. 23 Tries: search by digit rather than by comparison — O(L) lookups, and the space problem

A trie is a tree in which the keys are strings, each edge is labelled with one character, and a key is stored not in a node but as a path: the string spelled out by the edges from the root to a node marked as terminal. A search reads the query one character at a time and follows the matching child; it costs O(L) for a key of length L, with a constant that depends on how children are found, and it does not depend on n, the number of keys, at all — a trie holding a million words answers "is x here?" in the same number of steps as one holding ten. It is the natural structure for anything indexed by a prefix: autocomplete, longest-prefix routing, dictionary lookups in tokenisers. Its cost is space: a naive trie node holding an array of pointers for every possible character is large, and most of those pointers are null.

24 Compressed tries, Patricia, ternary search tries — and where tries are used

The trie's waste is in its chains: a node with a single child and no key of its own carries no branching information and exists only to spell one character. A compressed trie (radix tree) collapses every such chain into one edge labelled with the whole substring, so that every remaining node is either terminal or has at least two children — which bounds the node count by 2n − 1 for n keys regardless of key length. A Patricia trie takes this to the bit level and stores at each node only the index of the bit to test, with the keys themselves kept in the leaves; it is the routing-table structure. A ternary search trie keeps one character per node but replaces the array of children by a small BST of siblings, trading the O(1) child lookup for space proportional to the characters actually stored.

Digital search versus comparison search

Everything else on this page compares whole keys; tries compare digits of keys, and that changes the accounting. A comparison-based balanced tree over strings costs O(log n) comparisons, each of which may take up to L character steps, so O(L·log n) in the worst case — though in practice a comparison stops at the first differing character, which for random strings is after O(1) characters. A trie costs O(L) character steps total, because each character is examined once and decides one branch. For keys that share long prefixes — URLs, file paths, IP addresses, sorted identifiers — the trie's advantage is real; for short random keys the balanced tree's comparisons are cheap and the trie's space overhead is not repaid. The digital view also explains radix sort: sorting strings by their trie order, one digit at a time, is the same walk performed on all keys at once, and its O(n·L) bound is the trie's O(L) per key.

25 Segment trees: range queries and point updates in O(log n), and the associativity hypothesis

26 Lazy propagation: range updates in O(log n), by leaving the work as a tag

A range update — "add c to every element in [l, r]" — touches r − l + 1 leaves if done naively, which is O(n). Lazy propagation applies the update to the same O(log n) canonical nodes a query would use, and instead of descending into them it records a pending tag on each: "everything below me still owes an add of c". A node's stored value is kept correct for its whole range (an add of c over a range of length w adds c·w to a sum), and the tag is pushed down to the two children only when some later operation needs to enter the node. 27 Fenwick (binary indexed) trees: prefix sums in O(log n) with one array and the lowbit trick

A Fenwick tree is an array t[1 … n] in which entry t[i] holds the sum of the input over the range (i − lowbit(i), i], where lowbit(i) = i & (−i) is the value of i's lowest set bit. That one rule makes a prefix sum a walk that strips low bits — i → i − lowbit(i) → … — and a point update a walk that adds them — i → i + lowbit(i) → … — each O(log n) steps, with no tree stored: the "tree" is the pattern of which entries cover which ranges, implicit in the binary representation of the indices. It is a prefix-sum array that can be updated, in exactly n words of space, and it is the structure to reach for whenever the question is a prefix or range sum (or any invertible group operation) over a changing array. What it gives up relative to the segment tree is generality: no min or max over arbitrary ranges, because a range is computed as a difference of two prefixes.

28 Augmenting a balanced tree: keeping subtree sizes and interval maxima correct through rotations — the augmentation theorem

The BST page attached a subtree size to every node and got rank and select in O(h); on a plain BST that h is unbounded, so the augmentation is only as good as the balance. Combining the two raises one question: does balancing break the augmentation? Rotations move subtrees between nodes, and any field that summarises a subtree must be recomputed. The augmentation theorem says that as long as the field at a node can be computed in O(1) from the node itself and the fields of its two children, insertion and deletion in a red-black or AVL tree maintain it with no change to the O(log n) bound — because a rotation invalidates the field at exactly two nodes, and everything else that changes lies on the one path just walked.

29 Treaps: a random binary search tree by construction, whatever the input order

A treap is a binary tree in which every node holds a key and a randomly drawn priority, arranged so that the keys satisfy the search-tree order and the priorities satisfy the heap order (every node's priority is less than its children's). For a given set of (key, priority) pairs with distinct priorities there is exactly one such tree — the one obtained by inserting the keys in increasing order of priority into a plain BST. Since the priorities are random, that insertion order is a random permutation, and the treap is a randomly built BST regardless of the order the keys actually arrived in: expected depth ≈ 2·ln n, expected height ≈ 4.31·ln n, and — unlike the plain BST — no input can defeat it. It is the tree-shaped counterpart of the skip list: randomness supplied by the structure, an expected bound, and a very short implementation.

31 In practice: what ordered maps, databases, file systems and runtimes actually use

The list below is general practice as documented by the implementations themselves, stated with the conditions that matter; version details change, and the point is the pattern, not any one product's constant. Three patterns account for nearly everything: red-black for per-node-allocated in-memory maps and intrusive kernel structures, B⁺-trees for anything page-based, and skip lists where concurrency or simplicity wins. AVL trees, the oldest structure on the page, are the rarest in libraries and the commonest in textbooks.

  • Language libraries. The C++ standard library's map/set, Java's TreeMap/TreeSet, and .NET's SortedDictionary/SortedSet are red-black trees in the common implementations, chosen for the O(1)-rotation update bound and the one-bit overhead. Java's HashMap converts a bucket with many collisions into a red-black tree. Java's ConcurrentSkipListMap is a lock-free skip list — the concurrent ordered map. Rust's BTreeMap is an in-memory B-tree with a fixed B = 6, i.e. 5 to 11 keys per node, chosen explicitly for cache efficiency over a binary tree's one-allocation-per-key layout. Python and Go ship no tree-based ordered map; the widely used Python sorted-container package is a list of sorted lists.
  • Operating-system kernels. The Linux kernel provides an intrusive red-black tree used across subsystems — the process scheduler's run queue has long been a red-black tree ordered by virtual runtime (the fairness-scheduler design, retained by its successor), and memory regions, timers and I/O schedulers use the same structure. Radix trees (and their successors) index page caches and address spaces; the routing tables of network stacks are Patricia-style tries for longest-prefix match. The choice is driven by intrusive nodes (no allocation on insert) and by bounded rotation counts under locks.
  • Databases. The default index type of the major relational engines is a B⁺-tree with the node sized to the storage page — 8 KB in one widely used engine, 16 KB in another — with leaf pages linked for range scans and the upper levels resident in the buffer pool; a typical index over millions of rows is three or four levels deep. Clustered indexes store the rows in the leaves. Hash indexes exist but serve equality only. Log-structured storage engines keep their in-memory write buffer as a skip list precisely so that one writer and many readers can proceed without locking, then flush it as a sorted file.
  • File systems. Modern file systems keep directories, extents and metadata in B-trees or B⁺-trees (one prominent Linux file system is named for it, and keeps every object in copy-on-write B-trees; others use B⁺-trees for directories and extent maps), for the same page-sized-node reason as databases. Older designs used hashed directory trees with a B-tree-like index.
  • In-memory data stores. The sorted-set type of a widely used in-memory store is a skip list with p = ¼ and a 32-level cap, paired with a hash table for O(1) membership — the "same comparisons, a third fewer pointers" trade of §22, and simple range-by-rank via per-pointer span counts, which is the skip-list version of the size augmentation of §28.
  • Tries, segment trees, Fenwick trees. Tries live in tokenisers (a subword vocabulary looked up by longest match — Tokenization), autocomplete services, spell-checkers, IP routers and some key-value stores' in-memory indexes. Segment and Fenwick trees are the standard tools for range-query problems in competitive programming and in numerical and geometric libraries (order statistics on streams, 2-D dominance counting, range-minimum queries), and rarely appear as library types because they are twenty lines to write for the case at hand.

Four systems claims, each with its condition

  • "Red-black trees are faster than AVL trees." On random workloads the two are within a few percent in every count (§12). Red-black wins the worst-case rotation count on deletion, which is what a library and a kernel care about; AVL wins the worst-case height, which matters for lookup-heavy workloads on adversarial input. Neither claim is unconditional.
  • "B-trees are for disk." They are for any level of a memory hierarchy whose block is larger than a key — which includes the cache line. In-memory B-trees beat red-black trees on lookups and iteration for small keys; red-black wins when elements must not move or the structure is intrusive (§18).
  • "Skip lists are simpler than balanced trees." Simpler to implement concurrently, because an update is a few pointer splices at scattered positions and readers can tolerate a half-finished tower; as a single-threaded structure the code is about as long as a treap's, and the guarantee is expected, not worst case.
  • "A database index is a B-tree." A B⁺-tree (§17): records in the leaves, separators above, leaves chained. The differences decide the cost of range scans, the height of the tree and the behaviour of deletes.

32 Pitfalls

  • Quoting a bound without its convention. "AVL height ≤ 1.44 log n": the true statement is h < 1.4405·log₂(n+2) − 1.3277 in edges, or − 0.3277 in nodes. "Red-black height ≤ 2 log(n+1)": that is to the nil leaves with n the internal nodes; to the deepest key it is one less. "B-tree height ≤ log_t(n)": it is log_t((n+1)/2), in keys, with t the minimum degree. Each mis-statement is off by a constant that a test at n = 1, 2, 4 exposes (§04, §08, §14).
  • "O(1) rotations per operation" for AVL trees. True of insertion; false of deletion, which may restructure at up to floor(h/2) levels (§06). "O(1) rotations" is a red-black property (≤ 2 insert, ≤ 3 delete).
  • Treating a splay tree's bound as a per-operation bound. It is amortised over a sequence starting from an empty tree; one operation can be Θ(n), and a splay tree read by concurrent threads is a splay tree being written by concurrent threads (§20).
  • Treating a skip list's or treap's bound as a worst-case bound. It is an expectation over the structure's coins — robust against any input, but a bad run of coins is possible with polynomially small probability; a seeded or predictable random source restores the adversary (§22, §29).
  • Rotating without recomputing the fields. Height, size, max-high, colour: a rotation invalidates them at exactly the two rotated nodes, and they must be recomputed in the right order (the node that went down first). Forgetting this is the classic augmentation bug, and it does not show up until a query lands on the stale node (§28).
  • Storing the balance factor and updating it as if it were a height. The factor cannot be recomputed from the children's factors; it needs the case analysis of §05. Store the height if in doubt.
  • B-tree deletion that fixes underflow bottom-up. Correct, but it revisits nodes — on disk, twice the reads. The one-pass discipline (ensure ≥ t keys before descending) is what the bounds of §15–16 assume.
  • Confusing B-tree and B⁺-tree. Where records live, whether separators are copies, whether a search can stop early, whether leaves are chained: all four differ, and the database documentation means the B⁺-tree (§17).
  • Sorted bulk insertion into a B-tree with split-on-the-way-down. Leaves every node minimally full — 33–50% utilisation in the figure of §14. Bulk-load from sorted input instead, or special-case appends.
  • A segment tree over a non-associative or non-identity operation. Mean, median, "second largest" cannot be combined from two halves without storing more (a pair, a small list). Subtraction is not associative. Lazy tags must compose (§25–26).
  • A Fenwick tree for min or max. Range queries subtract prefixes; without an inverse there is no subtraction. Prefix minima work only if the array never increases. Use a segment tree (§27).
  • Fenwick index 0. lowbit(0) = 0 — the update loop never advances and the query loop never terminates properly. Shift the input to 1-based (§27).
  • A trie with array children over a large alphabet. One node per prefix at hundreds of bytes each; the naive Unicode trie is a memory bomb. Use map children, a ternary search trie or a compressed trie, and measure (§23–24).
  • Forgetting the empty string in a trie. It is the root's terminal flag; a trie "of all keys" that cannot store it is subtly wrong for tokenisers and routers that use it as a default.
  • Assuming a balanced tree's inorder iteration is cheap per element. It is O(1) amortised (each edge walked twice) but a pointer chase per element; a B-tree walks a node's keys contiguously, and a sorted array walks memory. For iteration-heavy workloads the layout matters more than the balance rule (§18).
