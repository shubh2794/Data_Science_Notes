Balanced & Multiway Trees

A binary search tree answers every question in O(h), and nothing in its definition stops h from reaching n − 1: feed it sorted keys and it collapses into a list. A balanced tree is a search tree with one more invariant — a rule about shape, colour, fan-out or randomness — chosen so that the invariant forces h = O(log n) and can be restored after any update for O(log n) work. This page is the catalogue of those rules and the proofs that they work: rotations, the one primitive that reshapes a tree without disturbing its order; AVL trees, whose height bound comes out of the Fibonacci numbers; red-black trees and the black-height lemma; 2-3-4 trees and B-trees, which buy perfect depth balance by letting a node hold many keys — and which are what a disk, a database index and a cache line actually want; splay trees, balanced only on average, with the potential-function proof; skip lists, balanced only in expectation, with the coin-flip analysis; and the digital and implicit trees — tries, segment trees, Fenwick trees — whose depth is bounded by something other than n. Every height on the page is measured on a tree that was built and checked, and every bound is derived, not quoted.

01 What a balanced tree is

A balanced search tree is a search tree together with a structural invariant that (i) implies a height of O(log n) for every tree satisfying it, and (ii) can be re-established after any insertion or deletion with O(log n) work. Both halves are needed. An invariant that bounds height but costs Θ(n) to restore — "the tree is perfectly balanced", say — makes updates as slow as rebuilding; an invariant that is cheap to keep but does not bound height — "every node is a valid BST node" — is the plain search tree, and its height is whatever the input made it. The structures on this page are the invariants that satisfy both conditions, and the page is organised by what kind of promise each invariant makes: a worst-case bound on every operation, an amortised bound over a sequence, or an expected bound over the structure's own coin flips.

Why the height lemma is always a counting argument

Every worst-case bound on this page is proved the same way, and it is worth seeing the shape once before meeting it four times. To show that an invariant forces h ≤ c·log n + d, you do not bound the height directly; you bound the smallest tree the invariant allows at a given height. Let N(h) be the minimum number of nodes in a tree of height h that satisfies the invariant. If the invariant is any good, N(h) grows exponentially — N(h) ≥ b·aʰ for some a > 1 — because it forbids the thin shapes. Then any tree of height h has n ≥ N(h) ≥ b·aʰ, so h ≤ log_a(n/b) = log_a n − log_a b, and c = 1/log₂ a. For AVL trees N(h) = N(h−1) + N(h−2) + 1, a Fibonacci recurrence with a = φ ≈ 1.618 and c = 1/log₂ φ ≈ 1.4405. For red-black trees the count is by black-height: N ≥ 2^bh − 1 and h ≤ 2·bh, giving a = √2 and c = 2. For B-trees the count is by fan-out: N ≥ 2·tʰ − 1 keys, a = t, c = 1/log₂ t. The constant c is the whole difference between the families' worst cases — 1.44, 2, and 1/log₂ t — and the sections below derive each one exactly rather than stopping at "O(log n)", because the exact constant is what decides AVL versus red-black in §12 and what makes a B-tree's height 3 or 4 on a billion keys in §16.

A balanced tree is not much shallower than a lucky plain tree; it is shallower than an unlucky one by a factor that grows without bound.

Three promises, and why the difference matters

  • Worst case (AVL, red-black, B-tree): every operation on every tree that satisfies the invariant costs O(log n). This is the promise a real-time system, a kernel scheduler or a database needs — no single operation can stall — and it is the most expensive to keep, because the invariant must be restored before the operation returns.
  • Amortised (splay trees, and the deletion side of some others): any sequence of m operations costs O(m log n) in total, so the average per operation is O(log n) — but one operation in the sequence may cost Θ(n). The accounting is the potential method of Algorithm Analysis §19, and §20 instantiates it. What you buy for the weaker promise is simplicity (no balance information stored per node) and an adaptivity no worst-case structure has: frequently accessed keys drift to the top.
  • Expected (skip lists, treaps): the bound holds on average over the structure's own random choices, for every input. This is different from the "random insertion order" hypothesis of the plain BST, where the randomness is assumed to be in the input and an adversary who controls the input breaks it; here the adversary controls the input and still cannot force a bad shape, because the shape does not depend on the input. A bad run of coins can produce a bad shape, but with probability that vanishes polynomially in n (§22).
The one sentence to carry through the page. A balanced tree is an invariant plus a repair procedure; the invariant is chosen so that a counting argument bounds the height, the repair is chosen so that it touches only the path just walked. Everything else — rotations, colours, splits, coin flips — is a particular way of making that sentence true.

33 In practice: what ordered maps, databases, file systems and runtimes actually use

The list below is general practice as documented by the implementations themselves, stated with the conditions that matter; version details change, and the point is the pattern, not any one product's constant. Three patterns account for nearly everything: red-black for per-node-allocated in-memory maps and intrusive kernel structures, B⁺-trees for anything page-based, and skip lists where concurrency or simplicity wins. AVL trees, the oldest structure on the page, are the rarest in libraries and the commonest in textbooks.

  • Language libraries. The C++ standard library's map/set, Java's TreeMap/TreeSet, and .NET's SortedDictionary/SortedSet are red-black trees in the common implementations, chosen for the O(1)-rotation update bound and the one-bit overhead. Java's HashMap converts a bucket with many collisions into a red-black tree. Java's ConcurrentSkipListMap is a lock-free skip list — the concurrent ordered map. Rust's BTreeMap is an in-memory B-tree with a fixed B = 6, i.e. 5 to 11 keys per node, chosen explicitly for cache efficiency over a binary tree's one-allocation-per-key layout. Python and Go ship no tree-based ordered map; the widely used Python sorted-container package is a list of sorted lists.
  • Operating-system kernels. The Linux kernel provides an intrusive red-black tree used across subsystems — the process scheduler's run queue has long been a red-black tree ordered by virtual runtime (the fairness-scheduler design, retained by its successor), and memory regions, timers and I/O schedulers use the same structure. Radix trees (and their successors) index page caches and address spaces; the routing tables of network stacks are Patricia-style tries for longest-prefix match. The choice is driven by intrusive nodes (no allocation on insert) and by bounded rotation counts under locks.
  • Databases. The default index type of the major relational engines is a B⁺-tree with the node sized to the storage page — 8 KB in one widely used engine, 16 KB in another — with leaf pages linked for range scans and the upper levels resident in the buffer pool; a typical index over millions of rows is three or four levels deep. Clustered indexes store the rows in the leaves. Hash indexes exist but serve equality only. Log-structured storage engines keep their in-memory write buffer as a skip list precisely so that one writer and many readers can proceed without locking, then flush it as a sorted file.
  • File systems. Modern file systems keep directories, extents and metadata in B-trees or B⁺-trees (one prominent Linux file system is named for it, and keeps every object in copy-on-write B-trees; others use B⁺-trees for directories and extent maps), for the same page-sized-node reason as databases. Older designs used hashed directory trees with a B-tree-like index.
  • In-memory data stores. The sorted-set type of a widely used in-memory store is a skip list with p = ¼ and a 32-level cap, paired with a hash table for O(1) membership — the "same comparisons, a third fewer pointers" trade of §22, and simple range-by-rank via per-pointer span counts, which is the skip-list version of the size augmentation of §28.
  • Tries, segment trees, Fenwick trees. Tries live in tokenisers (a subword vocabulary looked up by longest match — Tokenization), autocomplete services, spell-checkers, IP routers and some key-value stores' in-memory indexes. Segment and Fenwick trees are the standard tools for range-query problems in competitive programming and in numerical and geometric libraries (order statistics on streams, 2-D dominance counting, range-minimum queries), and rarely appear as library types because they are twenty lines to write for the case at hand.

Four systems claims, each with its condition

  • "Red-black trees are faster than AVL trees." On random workloads the two are within a few percent in every count (§12). Red-black wins the worst-case rotation count on deletion, which is what a library and a kernel care about; AVL wins the worst-case height, which matters for lookup-heavy workloads on adversarial input. Neither claim is unconditional.
  • "B-trees are for disk." They are for any level of a memory hierarchy whose block is larger than a key — which includes the cache line. In-memory B-trees beat red-black trees on lookups and iteration for small keys; red-black wins when elements must not move or the structure is intrusive (§18).
  • "Skip lists are simpler than balanced trees." Simpler to implement concurrently, because an update is a few pointer splices at scattered positions and readers can tolerate a half-finished tower; as a single-threaded structure the code is about as long as a treap's, and the guarantee is expected, not worst case.
  • "A database index is a B-tree." A B⁺-tree (§17): records in the leaves, separators above, leaves chained. The differences decide the cost of range scans, the height of the tree and the behaviour of deletes.

34 Pitfalls

  • Quoting a bound without its convention. "AVL height ≤ 1.44 log n": the true statement is h < 1.4405·log₂(n+2) − 1.3277 in edges, or − 0.3277 in nodes. "Red-black height ≤ 2 log(n+1)": that is to the nil leaves with n the internal nodes; to the deepest key it is one less. "B-tree height ≤ log_t(n)": it is log_t((n+1)/2), in keys, with t the minimum degree. Each mis-statement is off by a constant that a test at n = 1, 2, 4 exposes (§04, §08, §14).
  • "O(1) rotations per operation" for AVL trees. True of insertion; false of deletion, which may restructure at up to floor(h/2) levels (§06). "O(1) rotations" is a red-black property (≤ 2 insert, ≤ 3 delete).
  • Treating a splay tree's bound as a per-operation bound. It is amortised over a sequence starting from an empty tree; one operation can be Θ(n), and a splay tree read by concurrent threads is a splay tree being written by concurrent threads (§20).
  • Treating a skip list's or treap's bound as a worst-case bound. It is an expectation over the structure's coins — robust against any input, but a bad run of coins is possible with polynomially small probability; a seeded or predictable random source restores the adversary (§22, §31).
  • Rotating without recomputing the fields. Height, size, max-high, colour: a rotation invalidates them at exactly the two rotated nodes, and they must be recomputed in the right order (the node that went down first). Forgetting this is the classic augmentation bug, and it does not show up until a query lands on the stale node (§28).
  • Augmenting with a positional field. Storing each node's rank or depth looks like the direct route to a rank query, and makes a single insertion rewrite Θ(n) fields. Store a subtree summary (size) and derive the position on the walk; step 3 of the method exists to catch exactly this (§29). The interval-tree equivalent is keying on the high endpoint, or omitting the max field — either one breaks one of the two cases of the one-way proof (§30).
  • Storing the balance factor and updating it as if it were a height. The factor cannot be recomputed from the children's factors; it needs the case analysis of §05. Store the height if in doubt.
  • B-tree deletion that fixes underflow bottom-up. Correct, but it revisits nodes — on disk, twice the reads. The one-pass discipline (ensure ≥ t keys before descending) is what the bounds of §15–16 assume.
  • Confusing B-tree and B⁺-tree. Where records live, whether separators are copies, whether a search can stop early, whether leaves are chained: all four differ, and the database documentation means the B⁺-tree (§17).
  • Sorted bulk insertion into a B-tree with split-on-the-way-down. Leaves every node minimally full — 33–50% utilisation in the figure of §14. Bulk-load from sorted input instead, or special-case appends.
  • A segment tree over a non-associative or non-identity operation. Mean, median, "second largest" cannot be combined from two halves without storing more (a pair, a small list). Subtraction is not associative. Lazy tags must compose (§25–26).
  • A Fenwick tree for min or max. Range queries subtract prefixes; without an inverse there is no subtraction. Prefix minima work only if the array never increases. Use a segment tree (§27).
  • Fenwick index 0. lowbit(0) = 0 — the update loop never advances and the query loop never terminates properly. Shift the input to 1-based (§27).
  • A trie with array children over a large alphabet. One node per prefix at hundreds of bytes each; the naive Unicode trie is a memory bomb. Use map children, a ternary search trie or a compressed trie, and measure (§23–24).
  • Forgetting the empty string in a trie. It is the root's terminal flag; a trie "of all keys" that cannot store it is subtly wrong for tokenisers and routers that use it as a default.
  • Assuming a balanced tree's inorder iteration is cheap per element. It is O(1) amortised (each edge walked twice) but a pointer chase per element; a B-tree walks a node's keys contiguously, and a sorted array walks memory. For iteration-heavy workloads the layout matters more than the balance rule (§18).
