28 Augmenting a balanced tree: keeping subtree sizes and interval maxima correct through rotations — the augmentation theorem

The BST page attached a subtree size to every node and got rank and select in O(h); on a plain BST that h is unbounded, so the augmentation is only as good as the balance. Combining the two raises one question: does balancing break the augmentation? Rotations move subtrees between nodes, and any field that summarises a subtree must be recomputed. The augmentation theorem says that as long as the field at a node can be computed in O(1) from the node itself and the fields of its two children, insertion and deletion in a red-black or AVL tree maintain it with no change to the O(log n) bound — because a rotation invalidates the field at exactly two nodes, and everything else that changes lies on the one path just walked.

THE AUGMENTATION THEOREMlet f be a field with f(x) = F( x's own data, f(x.left), f(x.right) ) computable in O(1). Then insert and delete in a red-black tree (or AVL tree) can maintain f at every node in O(log n) time, without changing the asymptotic cost. proof: a change at node x affects f only at x's ancestors — at most h + 1 nodes, each recomputed in O(1) bottom-up: O(log n). a rotation at x with child y changes the subtrees of exactly x and y; recompute f(x) first (x is now the child), then f(y): O(1) per rotation. Red-black: ≤ 3 rotations per update; AVL: ≤ h. Total O(log n). ∎ the rotation, with fields — right rotation at x, y = x.left rises (§02's picture)after the pointer swaps: f(x) ← F(x, f(β), f(γ)) — x's children are now β and γ; then f(y) ← F(y, f(α), f(x)) — y's children are now α and the new x. ORDER MATTERS: x before y. nothing outside the rotated pair changes: α, β, γ keep their fields, and y's new subtree holds exactly the nodes x's old subtree held, so f(y_new) = f(x_old) for any f that depends only on the SET of nodes below (size, max, sum) — a useful check. order-statistic tree: f = sizesize(x) = 1 + size(x.left) + size(x.right). select(i) and rank(k) as on the BST page, now O(log n) guaranteed. Under a rotation: size(x) = 1 + size(β) + size(γ), then size(y) = 1 + size(α) + size(x). interval tree: keys are the intervals' low endpoints; f = max high endpoint in the subtreemax(x) = max( x.high, max(x.left), max(x.right) ) with max(∅) = −∞. overlap search for query [a, b]: x ← root; while x ≠ ∅ and x does not overlap [a, b]: if x.left ≠ ∅ and max(x.left) ≥ a: x ← x.left else x ← x.right. Returns an overlapping interval or ∅ in O(log n). why one path suffices: going LEFT when max(left) ≥ a: if the left subtree holds no overlap, then the interval achieving max(left) ends at ≥ a and so must START after b, and by the BST order on lows every interval in the right subtree starts after b too — no overlap anywhere. Going RIGHT when max(left) < a: every left interval ends before a, so nothing on the left can overlap. ∎ what does NOT qualifya field that depends on the node's position in the whole tree (its rank, its depth) or on nodes outside its subtree — such a field changes at Θ(n) nodes under one rotation. Store subtree summaries, derive positions by walking. the same idea elsewhere on this pagea B-tree node can store the number of keys in each child's subtree (order statistics on a B-tree); a skip-list node can store the "width" of each forward pointer (rank in O(log n) expected); a splay tree's Φ uses sizes but does not store them.

29 Augmenting data structures as a method — four steps, and the order-statistic tree built with them

Most practical data structures are not invented; they are an existing structure with one extra field per node and one or two new operations that read it. §28 proved the one fact that makes this safe on a balanced tree — a field that summarises a subtree survives rotations at O(1) per rotated node. This section turns that fact into a procedure and runs it once in full. The procedure has four steps, and skipping the third is the classic way to end up with a structure whose new query is fast and whose updates are silently wrong.

the four steps1. CHOOSE the base structure — one whose existing operations already do most of the work (here: a red-black or AVL tree, for O(log n) height) 2. CHOOSE the extra information — the smallest field that makes the new query cheap 3. VERIFY it is maintainable — the base operations (insert, delete, and every rotation) can keep it correct without changing their bounds 4. DEVELOP the new operations — the queries that read the field the test for step 3 (§28's theorem, restated as a checklist)is f(x) a function of x's own data and f(x.left), f(x.right) only, computable in O(1)? yes ⇒ insert/delete maintain it in O(log n), rotations in O(1) each no ⇒ stop: the field is positional, and one rotation can change it at Θ(n) nodes order-statistic tree — steps 1 to 3base: red-black tree field: x.size = 1 + size(x.left) + size(x.right), size(nil) = 0 maintainable: insert — +1 on every node of the descent path O(log n) delete — −1 on every node from the spliced node up O(log n) rotation — recompute the two rotated nodes' sizes O(1) step 4: OS-SELECT(x, i) — the node of rank i in x's subtreer = size(x.left) + 1 ← x's rank within its own subtree if i = r: return x if i < r: return OS-SELECT(x.left, i) else: return OS-SELECT(x.right, i − r) ← skip x and its r − 1 smaller keys step 4: OS-RANK(T, x) — the rank of a given NODE, walking up with parent pointersr = size(x.left) + 1; y = x while y ≠ T.root: if y = y.parent.right: r = r + size(y.parent.left) + 1 y = y.parent return r invariant at the top of each iteration: r = rank of x within the subtree rooted at y costeach call moves one level down (select) or up (rank): O(h) = O(log n) on a balanced tree

Why the size field, and not the rank itself

Step 2 has an obvious wrong answer: store each node's rank directly, and OS-SELECT becomes a plain search by rank. But rank is positional — it depends on every key smaller than this one, anywhere in the tree — so inserting a new minimum changes the rank of all n nodes, and step 3 fails with a Θ(n) update. The subtree size carries the same information relative to the subtree, which is exactly what the recursion needs: at node x, size(x.left) + 1 is x's rank among its own descendants, and the rank in the whole tree is recovered by adding, on the way up or down, the sizes of the left subtrees that are passed over. Store what is local to the subtree; derive what is global by walking. That is the design rule behind nearly every augmentation.

OS-RANK's invariant, proved

Initialisation: before the loop y = x, and x's rank in its own subtree is the number of keys in its left subtree plus one — which is how r starts. Maintenance: moving from y to its parent p adds the keys of p's subtree that precede everything in y's subtree. If y is a left child there are none — p and its right subtree all come after — so r is unchanged. If y is a right child, p and all of p.left precede y's subtree, which is size(p.left) + 1 more keys. Termination: the loop stops at the root, whose subtree is the whole tree, so r is the rank in T. The walk is one level per iteration, so it is O(h). OS-SELECT is the same argument run downwards, and the BST page's key-based rank(k) is OS-RANK run top-down from a key instead of bottom-up from a node.

A trace, on the tree of §28's figure

The nine intervals of the figure above, keyed by low endpoint, have the lows 3, 5, 7, 10, 15, 17, 20, 25, 26. The AVL build puts 15 at the root with a left subtree of size 4 — {3, 5, 7, 10} — so the root's own rank is 5. OS-SELECT(root, 4): r = 5, and 4 < 5, so go left looking for rank 4; at 7, whose left subtree {3, 5} has size 2, r = 3 and 4 > 3, so go right looking for rank 4 − 3 = 1; at 10 the left subtree is empty, r = 1, found. Three nodes visited, which is what the figure's select(4) query reports. Running OS-RANK from that node back up: at 10, r = 1; it is the right child of 7, so add size({3, 5}) + 1 = 3 to get 4; 7 is the left child of 15, so nothing is added; 15 is the root; the answer is 4. Select and rank are inverses, and each is one root-to-leaf path.

What the order-statistic tree is used for

  • Rank and percentile queries on a changing set — a leaderboard's "what place is this score?", the median or 99th percentile of a sliding set of latencies — each in O(log n) with insert and delete also O(log n). A sorted array answers the query in O(1) but pays Θ(n) per update; a heap cannot answer it at all.
  • Counting inversions online. Insert the elements one at a time; before inserting aⱼ, the number of earlier elements larger than it is j − 1 − rank(aⱼ). Summed, that counts inversions in O(n log n) — the same bound as the mergesort method, but on a stream.
  • Range counting. "How many keys lie in [a, b]?" is rank(b) − rank(a), adjusted by one if a is present — two walks, no enumeration.
  • Sequences with insert-anywhere. Drop the keys and let the in-order position be the key; OS-SELECT(i) finds position i, and inserting before it is a descent by sizes. That is a list with O(log n) indexing, insertion and deletion — the rope of text editors, and the implicit treap of §31.
The method, applied beyond sizes. Change step 2 and the same four steps give a different structure: subtree sums of a value give prefix sums over a dynamic sorted set; subtree min/max of a secondary attribute answer "the cheapest item with key in this range"; and subtree maximum endpoint gives the interval tree, developed next. In every case steps 3 and 4 are the whole job, and step 3 is a one-line check against §28's theorem.

30 Interval trees: the max-endpoint field, and why the overlap search may go one way only

An interval tree stores a dynamic set of closed intervals [low, high] and answers "find an interval in the set that overlaps [a, b]" in O(log n), alongside O(log n) insert and delete. It is the four-step method with a less obvious step 2. Keying the tree by low endpoint is natural, but low endpoints alone cannot rule out a subtree: an interval that starts early may end late. The field that fixes this is the largest high endpoint anywhere in the subtree — one number that says how far to the right the subtree's intervals can reach.

steps 1 to 3base: red-black (or AVL) tree, keyed on x.low ← in-order = intervals by start field: x.max = max( x.high, x.left.max, x.right.max ), nil.max = −∞ maintainable: a function of x and its two children in O(1) ⇒ §28's theorem applies overlap, as a test[p, q] and [a, b] overlap ⇔ p ≤ b and a ≤ q they are disjoint ⇔ q < a (entirely to the left) or b < p (entirely to the right) step 4: INTERVAL-SEARCH(T, [a, b])x = T.root while x ≠ nil and [x.low, x.high] does not overlap [a, b]: if x.left ≠ nil and x.left.max ≥ a: x = x.left else: x = x.right return x ← an overlapping interval, or nil if there is none cost: one root-to-leaf path, O(h) = O(log n) all overlaps, not just onesearch both subtrees wherever each could hold an overlap: left if x.left.max ≥ a; right if x.low ≤ b (right-subtree lows are ≥ x.low) cost: O(min(n, k·log n)) for k reported intervals — output-sensitive

Why going one way is always safe

The loop inspects one node and then discards an entire subtree, so the whole correctness question is: when it discards a side, could that side have held an overlap? There are two cases, and they are not symmetric.

  • It goes right because x.left.max < a (or the left is empty). Every interval on the left ends at most at x.left.max, which is before a, so every one of them lies entirely to the left of the query. Nothing on the left can overlap; discarding it is safe.
  • It goes left because x.left.max ≥ a. This is the subtle case — the search commits to the left without knowing that the left contains an overlap. Suppose it does not. Let [p, q] be the left interval that achieves the maximum, so q = x.left.max ≥ a. It does not overlap [a, b], and it does not end before a, so it must start after the query: b < p. Now use the search-tree order: every interval in the right subtree has a low endpoint at least x.low, which is at least p, which is greater than b — so every right interval also starts after the query ends, and none of them overlaps either. If the left side has no overlap, the right side has none; going left can therefore never lose an answer.

Put together: at each step, either the side discarded provably holds no overlap, or the side kept holds one whenever any exists at all. By induction down the path, the search returns an overlapping interval exactly when one exists — and when it returns nil, that is a proof of absence, not a failure to look. The argument uses both halves of the design: the max field in the first case, and the ordering by low endpoint in the second. Key the tree on anything else and the second case collapses; drop the max field and the first case has no test to run.

The same two cases, on §28's figure

The default query of the figure in §28, [11, 14], shows each case once. At the root [15, 18] there is no overlap; the left max is 12 ≥ 11, so it goes left — the second case, trusting that the right side is empty if the left is. At [7, 10], no overlap; the left max is 8 < 11, so it goes right — the first case, discarding intervals that all end before 11. At [10, 12] it finds the overlap. The query [23, 24] is the case where the answer is nil: the walk ends at a missing child after four visits, and the figure's full scan confirms that none of the nine intervals overlaps it — the one-path argument, checked against brute force.

Where interval trees are used, and the alternatives

  • Scheduling and calendars: "does this booking collide with any existing one?" is one overlap query; insert on accept, delete on cancel.
  • Genomics and time-series: which annotated regions overlap a read, which events overlap a window — usually the all-overlaps version.
  • Geometry: a rectangle-overlap sweep keeps the active rectangles' vertical extents in an interval tree as a line sweeps across the plane, reporting all k intersecting pairs in O((n + k) log n) time.
  • Static sets can use a different design — a tree centred on median points, with the intervals that straddle each centre stored in two sorted lists — which answers stabbing and overlap queries in O(log n + k). For range aggregates over a fixed index space, the segment tree of §25 is the right tool; it is a different structure despite the similar name.
What the two structures teach. The order-statistic tree's field is the obvious one; the interval tree's is not, and the payoff for finding it is a query that looks as if it must search both sides and provably never needs to. In both, steps 1 and 3 came free from the balanced tree and §28 — the design work was entirely in choosing a subtree summary that lets one comparison discard half the tree.

31 Treaps: a random binary search tree by construction, whatever the input order

A treap is a binary tree in which every node holds a key and a randomly drawn priority, arranged so that the keys satisfy the search-tree order and the priorities satisfy the heap order (every node's priority is less than its children's). For a given set of (key, priority) pairs with distinct priorities there is exactly one such tree — the one obtained by inserting the keys in increasing order of priority into a plain BST. Since the priorities are random, that insertion order is a random permutation, and the treap is a randomly built BST regardless of the order the keys actually arrived in: expected depth ≈ 2·ln n, expected height ≈ 4.31·ln n, and — unlike the plain BST — no input can defeat it. It is the tree-shaped counterpart of the skip list: randomness supplied by the structure, an expected bound, and a very short implementation.

the invariantsBST order on keys; MIN-HEAP order on priorities: p(x) < p(x.left), p(x.right). priorities drawn uniformly at random at insertion, independent of the key. uniqueness, and why the shape is randomthe node with the smallest priority must be the root (heap order); its key splits the rest into left and right by BST order; recurse. ⇒ one tree per (key, priority) set. the same tree results from inserting keys into a plain BST in priority order (each inserted key becomes an ancestor of all later ones on its side: exactly the heap-order relation). Random priorities ⇒ random insertion order ⇒ the random-BST theorem applies. operationsinsert(k): BST insert as a leaf with a fresh priority; while p(k) < p(parent): rotate k up. Expected number of rotations < 2 (the expected number of ancestors that end up below it is O(1)). delete(k): rotate k down — with the child of smaller priority — until it is a leaf; remove. Expected rotations O(1), the reverse of the insertion. split(T, k): insert k with priority −∞ (it becomes the root); its subtrees are the two halves. join(T₁, T₂): a root with priority +∞ over them, then delete it. Both O(log n) expected — the treap's special talent. bounds — expected over the priorities, for every inputE[depth of a key] = O(log n) (≈ 2 ln n); E[height] = O(log n) (≈ 4.31 ln n, slowly converging); E[rotations per insert or delete] = O(1); worst case Θ(n) with vanishing probability. implicit treaps and persistencekey = position in a sequence (stored implicitly via subtree sizes): a sequence with O(log n) expected insert-anywhere, delete-anywhere, cut and paste — via split and join. Path-copying gives a persistent version cheaply because updates touch O(log n) expected nodes. against the skip listsame promise (expected), same randomness source; the treap is a tree (rotations, no extra pointers per level, O(1) rotations per update) — the skip list is easier to make concurrent. Both are shorter to implement than red-black.
Treap heights over 100 builds from SORTED input against plain BSTs from random input: the same distribution — and the rotations per insertion, measured n = 1 024; both invariants (key order and heap order) re-verified on every treap; the plain BSTs are the random-order trees of the BST page

The treaps were built from the keys 1 … 1024 in sorted order — the input that turns a plain BST into a chain of height 1 023 — and their heights average 21.3 (maximum 28) over 100 seeds; plain BSTs built from 100 random permutations average 20.8 (maximum 25). The two histograms overlap almost completely, which is the theorem: the treap's shape distribution is the random-BST distribution, and the input order has nothing to do with it. Insertions performed a mean of 0.99 rotations each on this sorted input and 1.95 on the random workload of §32 — both below the expected-fewer-than-two of the analysis — and deletions 0.96. The expected height ≈ 4.31·ln 1024 = 29.9 is an asymptotic statement that the BST page already flagged as slow to converge; at this size the measured 21 is the number to compare against an AVL tree's 11 or a red-black tree's 11–12 on the same keys (§07): the price of "expected" over "worst case" is about a factor of two in height.
