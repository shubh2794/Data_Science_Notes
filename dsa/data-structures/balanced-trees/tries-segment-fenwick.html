23 Tries: search by digit rather than by comparison — O(L) lookups, and the space problem

A trie is a tree in which the keys are strings, each edge is labelled with one character, and a key is stored not in a node but as a path: the string spelled out by the edges from the root to a node marked as terminal. A search reads the query one character at a time and follows the matching child; it costs O(L) for a key of length L, with a constant that depends on how children are found, and it does not depend on n, the number of keys, at all — a trie holding a million words answers "is x here?" in the same number of steps as one holding ten. It is the natural structure for anything indexed by a prefix: autocomplete, longest-prefix routing, dictionary lookups in tokenisers. Its cost is space: a naive trie node holding an array of pointers for every possible character is large, and most of those pointers are null.

The default query, prefix tre, follows 3 edges to the node for tre and then enumerates its subtree to find tree — 2 more node visits, the output size plus the branch — while never looking at the other 19 nodes; the search for card follows 4 edges and succeeds, the search for ca follows 2 and lands on a node that exists but is not terminal (present as a prefix, absent as a key), and tram fails at its third character. The space panel is a model, with its assumptions stated on the figure: array children at 26 pointers of 8 bytes (plus a flag byte) per node cost 5 016 bytes for 24 nodes, a map of children at 16 bytes per node plus 16 per edge costs 752, and a ternary search trie at 32 bytes per stored character costs 736 — a factor of nearly 7 between the naive layout and the frugal ones, for a trie that stores 43 characters of 15 words. Switch to the compressed view: chains such as t-r-e-e collapse into labelled edges and the node count drops from 24 to 20, every remaining node being either terminal or a branch point.

The claim to keep precise. "Trie lookup is O(L)" is true and is the point; "tries are memory-cheap" is false for the array-of-children layout that makes the O(L) constant smallest. The honest statement is a trade: pointer-array nodes for speed on small alphabets, maps or ternary nodes for space, compression for both, and always a per-node cost that is a multiple of the alphabet or of the branching, not of n.

24 Compressed tries, Patricia, ternary search tries — and where tries are used

The trie's waste is in its chains: a node with a single child and no key of its own carries no branching information and exists only to spell one character. A compressed trie (radix tree) collapses every such chain into one edge labelled with the whole substring, so that every remaining node is either terminal or has at least two children — which bounds the node count by 2n − 1 for n keys regardless of key length. A Patricia trie takes this to the bit level and stores at each node only the index of the bit to test, with the keys themselves kept in the leaves; it is the routing-table structure. A ternary search trie keeps one character per node but replaces the array of children by a small BST of siblings, trading the O(1) child lookup for space proportional to the characters actually stored.

Digital search versus comparison search

Everything else on this page compares whole keys; tries compare digits of keys, and that changes the accounting. A comparison-based balanced tree over strings costs O(log n) comparisons, each of which may take up to L character steps, so O(L·log n) in the worst case — though in practice a comparison stops at the first differing character, which for random strings is after O(1) characters. A trie costs O(L) character steps total, because each character is examined once and decides one branch. For keys that share long prefixes — URLs, file paths, IP addresses, sorted identifiers — the trie's advantage is real; for short random keys the balanced tree's comparisons are cheap and the trie's space overhead is not repaid. The digital view also explains radix sort: sorting strings by their trie order, one digit at a time, is the same walk performed on all keys at once, and its O(n·L) bound is the trie's O(L) per key.

25 Segment trees: range queries and point updates in O(log n), and the associativity hypothesis

A segment tree over an array a[0 … n−1] is a binary tree whose root covers the whole index range, whose two children cover the two halves, and so on down to leaves that cover single indices; each node stores the combination — sum, minimum, maximum, gcd, any associative operation — of the array values in its range. A range query [l, r] is answered by combining the values of the O(log n) nodes whose ranges tile [l, r] exactly; a point update changes one leaf and recomputes its O(log n) ancestors. It is the answer to "prefix sums, but the array changes" — a prefix-sum array answers range sums in O(1) but costs O(n) to update — and, unlike a search tree, its shape is fixed by n: balance is automatic because the tree is built over index positions, not over keys.

the structure — a perfect-shaped tree over the index range, stored implicitlynode v covers [lo, hi]; its children cover [lo, m] and [m+1, hi] with m = floor((lo + hi)/2); leaves cover [i, i]. Root = node 1 covering [0, n−1]; children of v are 2v and 2v + 1 (the heap page's index arithmetic, 1-based). height = ceil(log₂ n); nodes = 2n − 1 (one per leaf plus one per internal node); array size 2·2^ceil(log₂ n) ≤ 4n suffices for the implicit layout at any n, power of two or not. t[v] = op( t[2v], t[2v+1] ) for internal v; t[leaf i] = a[i]. op must be ASSOCIATIVE, with an identity e for empty ranges (sum: 0; min: +∞; max: −∞; gcd: 0). build — O(n)build(v, lo, hi): if lo = hi: t[v] ← a[lo] else build both halves; t[v] ← op(t[2v], t[2v+1]). One visit per node: 2n − 1 visits. query [l, r] — the canonical decompositionquery(v, lo, hi): if [lo, hi] ⊆ [l, r]: return t[v] (a CANONICAL node) otherwise recurse into whichever halves intersect [l, r] and combine. LEMMA: at most 2 canonical nodes per level, so ≤ 2·ceil(log₂ n) canonical nodes and ≤ 4·ceil(log₂ n) nodes visited. proof: if at some level three canonical nodes were used, the middle one and one neighbour would both be fully inside [l, r] and be siblings — but two canonical siblings would have been answered by their parent. So at most two per level, at the two boundaries of the range. ∎ point update — O(log n)update(i, x): walk from the root to leaf i (one child per level), set the leaf, then recompute t[v] = op(children) at each ancestor on the way back. ceil(log₂ n) + 1 visits. the hypotheses, and what fails without themASSOCIATIVITY: the query combines canonical nodes left to right, (a∘b)∘c must equal a∘(b∘c) — sum, min, max, gcd, matrix product, "merge of sorted lists" all qualify; subtraction and mean do not (mean needs (sum, count) as the stored pair). NOT needed: commutativity (keep the left-to-right order) or invertibility (no subtraction of a prefix is ever done) — which is what a segment tree has over a Fenwick tree (§27). RANGE update needs one more idea — lazy propagation, §26 — and it needs the updates to COMPOSE (two "add c" tags combine into one). cost summarybuild O(n); query O(log n); point update O(log n); space O(n) — 2n − 1 values (≤ 4n slots in the implicit array). Versus a prefix-sum array: query O(1), update O(n). Versus a plain scan: query O(n), update O(1).

Over a = [5, 3, 7, 1, 4, 6, 2, 8] the default query [1, 6] decomposes into 4 canonical nodes — [1,1] = 3, [2,3] = 8, [4,5] = 10, [6,6] = 2 — whose sum 23 matches the plain scan of a[1..6]; the recursion visited 9 nodes against the bound 4·log₂ 8 = 12, and the canonical count is within 2·log₂ 8 = 6. Notice which nodes are canonical: two leaves at the deepest level (the range's two ends, where it does not align with the tree's halving) and two nodes one level up, [2,3] and [4,5], which are cousins, not siblings — never two siblings, which is the lemma. Setting a[3] to another value recomputes the 4 nodes on the leaf's path to the root and nothing else, and the query re-run afterwards still agrees with the scan. Switch to 11 values: the tree is no longer perfect — the halving produces ranges of unequal size — but the recursion, the bound (4·ceil(log₂ 11) = 16) and the check all hold unchanged, which is why the recursive [lo, hi] formulation is preferred over layouts that assume a power of two.

26 Lazy propagation: range updates in O(log n), by leaving the work as a tag

A range update — "add c to every element in [l, r]" — touches r − l + 1 leaves if done naively, which is O(n). Lazy propagation applies the update to the same O(log n) canonical nodes a query would use, and instead of descending into them it records a pending tag on each: "everything below me still owes an add of c". A node's stored value is kept correct for its whole range (an add of c over a range of length w adds c·w to a sum), and the tag is pushed down to the two children only when some later operation needs to enter the node. The hypothesis is that tags compose: two pending adds combine into one add, so a node never holds more than one tag.

the fieldst[v] = the aggregate of v's range WITH all tags at v and above already applied; lazy[v] = an update pending for v's CHILDREN (not yet applied to them). lazy[v] = 0 (the identity update) means nothing pending. push(v): before entering v's children, hand the tag downif lazy[v] ≠ 0: for each child c with range length w_c: t[c] += lazy[v] · w_c; lazy[c] += lazy[v]; then lazy[v] = 0. — O(1); the children's stored values are now correct for their ranges range add [l, r] += dupdate(v, lo, hi): if [lo, hi] ∩ [l, r] = ∅: return. if [lo, hi] ⊆ [l, r]: t[v] += d · (hi − lo + 1); lazy[v] += d; return. (TAG it — do not descend) push(v); recurse into both children; t[v] = t[2v] + t[2v+1]. range query with tags presentquery(v, lo, hi): disjoint → identity. contained → t[v] (correct, because every tag above v was pushed on the way down). otherwise push(v), recurse, combine. why the bound survivesan update tags the same ≤ 2·ceil(log₂ n) canonical nodes a query would combine, and pushes on the ≤ 2·ceil(log₂ n) split nodes above them: O(log n). A push is O(1). A query does the same walk. So range update, range query: both O(log n). the composition hypothesistags must form a monoid acting on aggregates: apply(tag₂, apply(tag₁, x)) = apply(tag₂ ∘ tag₁, x), and apply(tag, aggregate of a range) must be computable from the aggregate (+ range size). works: range add with sum / min / max; range assign ("set to c") with sum / min / max; range multiply-then-add (store the pair (m, a), compose as (m₂m₁, m₂a₁ + a₂)); range XOR with XOR-sum (needs parity of the length). does not work directly: "set each element to its square" (not computable from the sum); updates whose effect on the aggregate needs the individual elements. costrange update O(log n); range query O(log n); space: one tag per node, 2n − 1 extra values. 27 Fenwick (binary indexed) trees: prefix sums in O(log n) with one array and the lowbit trick

A Fenwick tree is an array t[1 … n] in which entry t[i] holds the sum of the input over the range (i − lowbit(i), i], where lowbit(i) = i & (−i) is the value of i's lowest set bit. That one rule makes a prefix sum a walk that strips low bits — i → i − lowbit(i) → … — and a point update a walk that adds them — i → i + lowbit(i) → … — each O(log n) steps, with no tree stored: the "tree" is the pattern of which entries cover which ranges, implicit in the binary representation of the indices. It is a prefix-sum array that can be updated, in exactly n words of space, and it is the structure to reach for whenever the question is a prefix or range sum (or any invertible group operation) over a changing array. What it gives up relative to the segment tree is generality: no min or max over arbitrary ranges, because a range is computed as a difference of two prefixes.

indexing — 1-based, on purposet[1 … n]; t[0] is UNUSED (lowbit(0) = 0 would loop forever). Input a[1 … n] (shift a 0-based array by one). lowbit(i) = i & (−i) — in two's complement, −i flips the bits above the lowest set bit and keeps it, so the AND isolates it: lowbit(12 = 1100₂) = 4, lowbit(11 = 1011₂) = 1, lowbit(8) = 8. the responsibility of t[i]t[i] = ∑ a[j] for j ∈ (i − lowbit(i), i] — a range of length lowbit(i) ending at i. Odd i: just a[i]. i = 2ᵏ: the whole prefix a[1 … i]. the implicit tree: the parent of i in the QUERY walk is i − lowbit(i); in the UPDATE walk it is i + lowbit(i). Segment tree or Fenwick? If the operation has an inverse and the updates are to single points, the Fenwick tree is smaller, faster and shorter to write. If you need min, max, gcd, or range updates, or a non-commutative combine, use the segment tree; it is the general tool, and the Fenwick tree is the special case that happens to fit in one array.
