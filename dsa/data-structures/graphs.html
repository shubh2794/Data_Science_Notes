Graph Representations & Traversal

Every structure before this one imposed a shape on its data: a line (arrays, lists), a hierarchy (trees), a partial order (heaps), or no shape at all (hash tables). A graph imposes none and records all of them: it is a set of things and a set of pairwise relationships, and that is the whole definition. Road networks, dependency graphs, social networks, the web, state spaces, version histories, knowledge bases and neural-network computation graphs are all the same object with different labels on the vertices. This page is about two questions that come before any graph algorithm. How is a graph stored — the adjacency matrix, adjacency lists and maps, the edge list, and the compressed sparse row layout that real systems use — and what does each make cheap? And how is a graph walked — breadth-first, which discovers vertices in order of their distance in edges and proves it, and depth-first, whose discovery and finishing times induce a nesting structure so rigid that cycle detection, topological ordering, strongly connected components and articulation points all fall out of a single pass. Every cost on the page is measured on a graph that was built and traversed, every hand example was traced by a script, and every algorithm's output is cross-checked against a brute-force method on hundreds of random graphs.

01 What a graph is

A graph G = (V, E) is a finite set V of vertices together with a set E of edges, each edge being a pair of vertices. If the pairs are unordered — {u, v} — the graph is undirected and the edge can be crossed either way; if they are ordered — (u, v), from u to v — the graph is directed (a digraph) and the edge is an arrow. That is the entire definition. Everything else on this page — degrees, paths, cycles, connectivity, trees, representations, traversals — is vocabulary for talking about the pairs, and the reason the vocabulary is worth learning is that an enormous range of problems are, once the labels are stripped off, questions about pairs: can I get from here to there, how far is it, what must happen before what, which things are mutually reachable, which single failure would cut the system in two. Write V and E for the sets and, by the usual abuse, for their sizes; the notation n = |V|, m = |E| is also common and the page uses both.

Why the pairs are the point

A vertex is a thing; an edge is a fact about two things. That asymmetry is why graphs are the general-purpose model. A list says "these things come in this order"; a tree says "this thing is part of that thing"; a graph says only "these two are related", and lets the relation be anything: is adjacent to, links to, depends on, follows, is one move away from, is the parent commit of, was cited by. The definition does not care what the vertices are, and neither do the algorithms — which is what makes one BFS routine solve a maze, a word ladder, a network-hop count and a social distance query without modification. The price of that generality is that a graph carries no built-in way to be walked. An array has index i + 1; a tree has "left child"; a graph has only "the neighbours of v", and the traversals of §10–§16 are precisely the disciplines for turning that one primitive into a systematic visit of everything.

Undirected against directed, and the two degrees

The undirected/directed distinction is not cosmetic: it changes the theorems. In an undirected graph reachability is symmetric, so "connected" is one notion; in a directed graph u may reach v without v reaching u, and "connected" splits into strongly and weakly connected. A DFS of an undirected graph produces only two kinds of edge; of a directed graph, four (§17). Cycle detection has to exclude the edge you arrived on in the undirected case but not in the directed one (§18). Every one of the four recurring mistakes on this page is a theorem for one kind of graph quoted for the other, so each section says which kind it is about. The degree bookkeeping differs too: an undirected vertex has one degree, a directed vertex an in-degree and an out-degree, and the handshake lemma reads ∑ deg = 2E for one and ∑ in = ∑ out = E for the other. The figure measures both on a random graph by walking every adjacency list and counting entries — the count is 2E or E because the list representation stores each undirected edge twice and each directed edge once, which is the first thing to know about that representation (§05).

Why density decides everything

The single number that governs every choice on this page is the ratio of E to V². Since E ≤ V(V−1)/2, a bound of O(V + E) is never worse than O(V²), and on a sparse graph it is smaller by a factor of about V / (1 + E/V) — a quarter of a million times, for a million-vertex road network with three million edges. The adjacency matrix (§04) costs Θ(V²) regardless; the adjacency list (§05) costs Θ(V + E); and every traversal inherits the cost of the representation it runs on, so BFS and DFS are Θ(V + E) with adjacency lists and Θ(V²) with a matrix, and neither statement is complete without its qualifier. The crossover, measured in §08, sits near a density of a quarter for a byte-per-cell matrix against a pointer-based list — and near 3% for a bit-per-cell matrix — so "sparse" in practice means "well below that", which nearly every real graph is.

The one sentence to carry through the page. A graph is a set of pairs; a representation is a way of answering "what are the neighbours of v" and "is (u, v) an edge"; a traversal is a discipline for asking the first question of every vertex exactly once; and every bound on the page is Θ(V + E) because that is what asking it once for every vertex, with adjacency lists, costs.

Three modelling decisions, and what each commits you to

  • Direction. If the relation is symmetric (friendship, adjacency, "shares a border") use an undirected graph and get the simpler theory: one notion of connectivity, two edge classes, cycle detection by "grey neighbour that is not the arrival edge". If it is asymmetric (follows, depends on, links to, can move to) use a directed graph and accept that reachability is one-way, that "connected" needs a qualifier, and that DFS produces four edge classes. Modelling a symmetric relation as two arrows is legal and doubles E; modelling an asymmetric one as undirected loses information you cannot recover.
  • Weight. If "how far" means "how many edges", the graph is unweighted and BFS answers it exactly (§12). If it means a sum of lengths, times or costs, the graph is weighted, BFS is wrong (it counts hops, not weight), and the algorithms of the hand-off in §28 apply. A weighted graph with all weights equal is an unweighted graph.
  • Explicit or implicit. A road network is stored; a puzzle's state space is not — it is defined by a successor function and generated as the traversal reaches it. Every traversal on this page works on either, because they only ever ask for the neighbours of the current vertex; the representation sections (§04–§08) are about the explicit case, and §09 is about the implicit one.

Two claims about real graphs, stated at the level the evidence supports

Real graphs are sparse. A road junction meets a handful of roads; a person has hundreds of contacts out of billions of people; a source file imports tens of modules out of thousands; a web page links to tens of others out of billions. In every case E is a small multiple of V, not a fraction of V², which is the regime where adjacency lists and CSR win and the matrix is unusable. The exception is a graph that was built from a pairwise computation — a full similarity or correlation matrix — and such graphs are usually thresholded back to sparse before any traversal. Real graphs have short paths. The "six degrees of separation" phrase is folklore that predates any large measurement; what has actually been measured is that on one very large social network in 2016 the average shortest path between accounts was reported at about 4.6 friendship links (the company phrased it as "3.57 degrees", counting the intermediaries). That is one platform, one year and one definition of the edge, not a law about humanity, but it illustrates the general finding that large sparse social graphs have small average distances — which is why BFS layers on such graphs grow very fast and why the frontier, not the depth, is what exhausts memory (§25).

What graph databases store. Systems that call themselves "native" graph stores describe their design as index-free adjacency: each vertex record holds direct references to its incident edges, so following an edge is a pointer dereference rather than an index lookup, and a traversal's cost depends on the part of the graph it touches rather than on the whole graph's size. That is an adjacency-list layout (§05) persisted to disk, and it is a design claim by those systems rather than a theorem — a relational table of (source, target) rows with an index on source is a perfectly good adjacency list too, at the cost of one index probe per hop.

Reading the table

Two rows matter more than the rest. neighbours(v) is the traversal primitive: BFS and DFS ask it once per vertex, so their total cost is ∑v cost(neighbours(v)) + Θ(V). With adjacency lists that sum is ∑ deg(v) = 2E (or E directed) and the traversal is Θ(V + E); with a matrix every call costs V and the traversal is Θ(V²) however few edges exist. That is the single most important line on the page, and §12 measures it. hasEdge(u, v) is the other primitive, and the matrix is the only structure that answers it in constant time in the worst case; the adjacency map gets expected constant time by making each vertex's neighbour collection a hash set, and the plain list has to scan. Which of the two questions your algorithm asks decides the representation before density does: a traversal-heavy workload wants lists or CSR; an algorithm that repeatedly tests specific pairs — a triangle counter, a clique finder, Floyd–Warshall — is happier with a matrix or a map. The "addVertex" row is the matrix's other weakness — a new vertex means a new row and column, so the whole V × V block is reallocated — and the "wins when" row is the summary the rest of the page justifies.

04 The adjacency matrix: V² cells, O(1) edge queries, and the algebra it unlocks

Number the vertices 0 … V−1 and keep a V × V table A with A[u][v] = 1 if (u, v) ∈ E and 0 otherwise. For an undirected graph the table is symmetric, A[u][v] = A[v][u], and each edge occupies two cells; for a directed graph a cell is set only in the direction of the arrow. The matrix is a two-dimensional array — one contiguous block of V² cells with row-major addressing — and it inherits both of that array's properties: any cell in constant time, and space proportional to the whole grid whether or not the grid is used.

When the matrix is the right answer

The reflex "matrices waste space, use lists" is right for sparse graphs and wrong as a rule. The matrix wins in four situations, and they are common enough to name. Dense graphs. Once E is a constant fraction of V², the list representation's per-entry overhead (a pointer or an integer per neighbour, a header per vertex) exceeds one byte or one bit per cell; the crossover is measured in §08 at a density near 0.25 for a byte matrix against integer lists and near 0.03 for a bit matrix. A complete graph, a distance table, a full similarity matrix, a tournament — these are matrices already. Worst-case O(1) edge queries. An adjacency map gives expected constant time via hashing; the matrix gives it unconditionally and with one memory access, which matters for algorithms whose inner loop is "is (u, v) an edge" — clique and triangle enumeration, Floyd–Warshall, any dynamic programme over vertex pairs. Bit-parallel operations. A bit matrix stores a row as V/64 machine words, so "the neighbours of u that are also neighbours of v" is V/64 AND instructions, "does u have any neighbour in set S" is an AND and a test, and a whole BFS layer expansion can be done a word at a time. Nothing list-based competes on dense instances. Algebraic questions. Counting walks, triangles, spectral properties, the transitive closure, and every graph-as-linear-operator method (including the normalised-adjacency propagation of graph neural networks) are matrix statements; even when the matrix is stored sparsely, the reasoning is matrix reasoning.

Where it is the wrong answer, and by how much

The measure of the mismatch is the ratio V² / (V + E). For the §08 example of a million vertices and ten million edges it is 10¹² / (1.1 × 10⁷) ≈ 90 000: a bit matrix would be 125 GB against about a hundred megabytes for lists, and a byte matrix a terabyte. Beyond storage, a neighbour query on a sparse row reads V cells to find an average of 2E/V = 20 neighbours, so every traversal pays a V/20 = 50 000-fold overhead in cell reads over the list version. The other, subtler failure is addVertex: a structure that gains vertices over time — a growing social graph, a streaming citation index — cannot afford to reallocate a V × V block for each new one, whereas a list representation appends one empty list. Finally, the matrix cannot hold parallel edges without switching from flags to counts, and it cannot hold per-edge data (an edge label, an object) without becoming a matrix of pointers, at which point it is a sparser and slower adjacency map.

The bound to attach to every traversal. "BFS is Θ(V + E)" is true with adjacency lists and false with a matrix, where it is Θ(V²). The algorithm did not change; the cost of neighbours(v) did. Whenever this page (or any other) states a traversal bound, the representation is part of the statement.

05 Adjacency lists — and the adjacency map and set that fix their one weak query

Keep, for each vertex v, a collection adj[v] of the vertices adjacent to it — its out-neighbours if the graph is directed, all its neighbours if not. The outer structure is an array of V collections, indexed by vertex number (or a hash map from vertex key to collection, if vertices are not numbered); the inner collections can be linked lists, dynamic arrays, hash sets or hash maps, and that inner choice is what distinguishes the "adjacency list" from the "adjacency map". Space is Θ(V + E) whatever the inner type: V headers plus one entry per adjacency, and there are 2E adjacencies in an undirected graph (each edge appears in two lists) and E in a directed one.

Why this is the default

Three things make the adjacency list the representation every graph library reaches for first. It is proportional to the graph: a million vertices with ten million edges is tens of megabytes (§08), and a vertex with no edges costs one empty header. Its neighbour query is proportional to the answer: Θ(deg u) to produce deg u neighbours, so a full traversal costs the sum of the degrees, which is the handshake lemma's 2E, plus V for visiting each vertex — the origin of every Θ(V + E) on the page. And it grows: a new vertex is a new empty collection, a new edge is an append. What it does badly is the edge query, which is a scan, and deletion, which is a scan followed by a shift. The adjacency map exists for workloads where those two matter — a simulation that keeps adding and removing edges, an algorithm that tests specific pairs — and buys expected constant time for both at the cost of a heavier structure and an unordered, slower neighbour iteration. The choice between them is a choice between "I mostly walk" (list) and "I mostly probe and edit" (map), and is independent of density.

Details that bite

  • An undirected edge is two entries. addEdge(u, v) must append to both adj[u] and adj[v]; forgetting one gives a directed graph that quietly fails symmetric queries. Every undirected count on this page — scans, entries, CSR length — is 2E for this reason, and the figures check it.
  • Order of neighbours is part of the behaviour. The traversals of §11 and §15 visit neighbours in list order; a different insertion order gives a different (still correct) BFS tree, DFS tree, edge classification and topological order. Reproducible results need a fixed order — sort the lists, or store edges in a canonical sequence. This page's hand examples use insertion order in the order the edge strings are written.
  • The in-neighbours are not there. A directed adjacency list answers "where can u go" and not "who can reach u". Kahn's algorithm (§20) needs in-degrees; the two-pass SCC algorithm (§22) needs the whole reverse graph. Both are Θ(V + E) to build from the forward lists, once.
  • Vertex removal is the expensive operation. Removing v means finding v in every list that mentions it. Without in-neighbour lists that is a scan of all E entries; a common dodge is to mark v deleted and have traversals skip it — a tombstone, exactly as in open-addressed hash tables, with the same compaction obligation.
  • Self-loops and parallel edges are representable. A self-loop {u, u} is an entry u in adj[u] (twice, if the undirected convention of "each edge contributes two entries" is kept, so that ∑ deg stays 2E); parallel edges are repeated entries. Both are fine for BFS and DFS — they cost an extra scan and never change a distance — but an undirected cycle detector that skips "the parent vertex" instead of "the arrival edge" is blind to a doubled edge (§18), and the matrix cannot hold either without becoming a count matrix.
  • Pointer lists lose the cache. A linked list of neighbour nodes is a pointer chase per neighbour; a dynamic array of neighbour ids is contiguous within one vertex's list but the lists themselves are scattered on the heap. The cache-line model prices this at one line fetch per list header and one per few entries; CSR (§07) is the layout that removes the scatter.

06 The edge list: the minimal representation, and the one that some algorithms actually want

Store the graph as a single array of E pairs (u, v) — optionally with a weight — and nothing per vertex. This is what a graph looks like on disk, in a file of "source, target" rows, in a database table, and in the argument to every graph constructor on this page (GR.graph(n, edges) builds the adjacency lists from an edge list in one pass). It answers the two ADT queries badly — hasEdge and neighbours are both scans of all E pairs — but it answers "give me every edge" perfectly, and there are algorithms for which that is the only question.

A representation for the edges, not for the vertices

The edge list is the honest form of the definition E ⊆ V × V — a set of pairs and nothing else — and its costs follow from that honesty: any question about a vertex requires looking at every pair, because nothing groups the pairs by vertex. That is why it appears at the bottom of every column of §03's table except space and "iterate all edges". Yet two of the most important weighted-graph algorithms are naturally loops over edges rather than over vertices: Kruskal's minimum spanning tree processes edges in sorted weight order and never asks who is adjacent to whom, and Bellman–Ford relaxes every edge V − 1 times and is agnostic to their grouping. For those, the edge list is not a compromise but the right structure, and converting to adjacency lists would be wasted work. The other role of the edge list is as the interchange format: a file of pairs, a table of rows, a stream of events. Every explicit representation on this page is built from one in Θ(V + E), and the conversion to CSR in §07 is a single counting sort of the pairs by their source vertex — the sorted edge list is the CSR targets array.

An easy mistake in the other direction. An algorithm described as "for each edge" on an adjacency-list graph costs Θ(V + E) too — iterate every vertex, then its list — but visits each undirected edge twice, once from each end. Code that does work per edge (relaxation, union) must either accept the double visit or skip the copy with u < v; code that counts edges by this loop gets 2E.

07 Compressed sparse row: the adjacency list flattened into two arrays, and why systems use it

Concatenate all the adjacency lists, in vertex order, into one integer array targets of length 2E (undirected) or E (directed), and keep a second array offsets of length V + 1 with offsets[u] the index where u's neighbours begin. The neighbours of u are then the contiguous slice targets[offsets[u] … offsets[u+1]), its degree is offsets[u+1] − offsets[u], and the whole graph is two flat arrays with no pointers at all. This is the layout under nearly every high-performance graph system, sparse-matrix library and GPU graph kernel, and the reason is not asymptotic — CSR has exactly the adjacency list's Θ(V + E) bounds — but the memory model: contiguous integers are the thing a cache and a prefetcher are built for.

What CSR costs, and what it buys

The price is immutability. Inserting an edge into u's slice means shifting every later slice and incrementing every later offset — Θ(V + E) — so CSR is built once from an edge list and then read. Systems that need updates keep them in a side structure (a small adjacency map of recent insertions, a deletion bitmap) and periodically rebuild; a purely dynamic workload should stay on adjacency lists or maps. What CSR buys is everything the memory hierarchy rewards. A pointer-based adjacency list scatters each vertex's neighbours somewhere on the heap, so a traversal is a cache miss per list header and often per neighbour node; the cache model of the linked-structures page prices those misses and they dominate the instruction count. In CSR the neighbours of u are adjacent integers, a slice of 16 fits in one 64-byte line, the hardware prefetcher streams the next lines, and a BFS that processes vertices in numeric order walks targets almost sequentially. The offsets array is V + 1 integers with no per-vertex header, so the constant in Θ(V + E) is as small as the representation allows, and a parallel weights array keeps per-edge data equally contiguous. This is also the sparse-matrix format of numerical libraries — the graph's adjacency matrix, stored row by row with only the non-zeros — which is why "sparse matrix–vector multiply" and "one round of message passing" are the same loop.

CSR is not "just an adjacency list"

  • Same bounds, different constants. Every Θ(·) in §03's table matches the adjacency list's; the difference is a factor in wall-clock time from cache behaviour, and it is a factor that is large on big graphs and invisible on small ones. Do not cite CSR for an asymptotic win.
  • Static. No in-place insertion or deletion; no vertex addition. A graph that changes is not a CSR graph, or is CSR plus a delta structure.
  • Directed needs two. CSR stores out-neighbours; in-neighbours (for Kahn's algorithm, for the reverse graph in §22, for "who links to me") need a second pair of arrays — the transpose, built by the same counting sort on the swapped pairs.
  • Vertex order is a tuning knob. Because locality depends on numbering, systems renumber vertices so that neighbours have nearby ids (a BFS order from a well-chosen root is a common choice); the graph is unchanged, the traversal is faster. This has no analogue in the pointer representations.

Reading the crossover correctly

  • It is a space crossover. Time has its own: a matrix traversal reads V² cells however sparse the graph, and §12 measures the list-versus-matrix operation counts to show the traversal crossover sits somewhere else entirely — the matrix reads V cells per vertex, the list reads deg entries, so a traversal ties only on the complete graph (V + 2E = V² at density 1) and the matrix never wins a traversal on operation count; its wins are elsewhere (§04).
  • It moves with the constants. 64-bit ids push the list lines up and the crossover left (matrix wins sooner); per-edge weights stored in the matrix push its line up by the weight's size; a linked-list inner structure with 16-byte nodes makes lists three to four times bigger. The model's numbers are one honest configuration, not a universal constant.
  • Most real graphs sit far left of it. A density of 0.03 is an average degree of 0.03 · V — 30 000 neighbours per vertex in a million-vertex graph. Social, web, citation and dependency graphs have average degrees in the tens or hundreds (road networks, a handful) and are two to five orders of magnitude sparser than even the bit-matrix crossover.
  • Undirected: edge list < CSR < lists, always, in this model. The edge list has no per-vertex cost at all and stores each undirected edge once; CSR stores it twice but has only 4 bytes of per-vertex cost; lists pay 24. Directed, CSR stores each edge once too and beats the edge list as soon as E > V + 1 — 44 MB against 80 MB in the table above. The gap between CSR and lists is entirely header overhead, and it is the pointer-scatter that CSR also removes.

09 Implicit graphs: grids, state spaces, and graphs that are never stored

A traversal never needs the whole graph; it needs neighbours(v) for the vertices it reaches. So a graph can be given as a function rather than a structure — a rule that computes the neighbours of any vertex on demand — and every algorithm on this page runs on it unchanged. A grid is the simplest case: the vertex (x, y) has neighbours (x±1, y) and (x, y±1) minus the walls, and no adjacency list is ever built. A puzzle's state space is the important case: vertices are configurations, edges are legal moves, the graph may have 10²⁰ vertices, and BFS from the start configuration finds the fewest-moves solution by generating only the states it actually reaches.

Grids, mazes, images, and the four-versus-eight question

A maze is a grid graph; solving it is BFS from the entrance with parent pointers (§13) to recover the route. An image is a grid graph whose "walls" are decided by a pixel predicate — flood fill in a paint program is exactly this traversal with the predicate "same colour as the seed", and the connected components of §19 on a thresholded image are its blobs. The one modelling choice is adjacency: 4-neighbour (orthogonal moves only) or 8-neighbour (diagonals allowed), and it changes the answers — a diagonal wall blocks a 4-connected fill and not an 8-connected one, and distances in edges differ. Neither is "correct"; the application decides, and it should be stated. With 8-neighbour adjacency and a diagonal step counted as one edge, BFS distance is the Chebyshev distance on an open grid; with 4-neighbour adjacency it is the Manhattan distance. Both are distances in edges — BFS never knows that a diagonal is longer — which is the first place the weighted-graph tools of §28 earn their keep.

State spaces: where BFS finds the fewest moves

A sliding-tile puzzle, a Rubik's cube, a river-crossing riddle, a word ladder (change one letter at a time through dictionary words), a robot's configuration space, a program's reachable states in a model checker: each is a graph whose vertices are states and whose edges are single moves, and in each the question is "what is the shortest sequence of moves from here to there". That is δ(start, goal) in edges, so BFS (§11) answers it exactly, with the parent pointers reconstructing the move sequence. The graph is never stored — the 8-puzzle has 9!/2 = 181 440 reachable states, the 15-puzzle about 10¹³, and a chess position graph is beyond counting — and the traversal generates states from a successor function and remembers the visited ones in a hash set keyed by a compact state encoding. The cost is then governed by the branching factor and the depth: a BFS to depth d with b moves per state touches on the order of bd states, and its queue at depth d holds the whole layer. That layer is what runs out of memory first, long before time does, and it is the reason the memory comparison of §25 matters and the reason heuristic search exists: A*, the hand-off in §28, is BFS with a priority on "estimated total distance" that lets it ignore most of the layer.

Two implicit-graph traps. Without a visited set, any state space with cycles (nearly all of them: a move and its undo) makes BFS and DFS run forever, and a visited set keyed by a state's object identity rather than its value is no visited set at all — hash the encoded state. And an implicit graph has no V to iterate, so the "outer loop over all vertices" that gives DFS its forest and Kahn's algorithm its sources (§15, §20) does not exist; only single-source traversals from a known start make sense.

10 What a traversal is: the visited set, the frontier, and the two disciplines

A traversal (or search) is a procedure that, starting from a source vertex, visits every vertex reachable from it exactly once and examines every edge leaving a visited vertex, using only the neighbours(v) query. All traversals share the same skeleton: keep a set of visited vertices (so that no vertex is processed twice and the procedure terminates on graphs with cycles) and a collection of discovered-but-not-yet-expanded vertices, the frontier; repeatedly take a vertex from the frontier, mark it, and add its unvisited neighbours to the frontier. The single design decision is which frontier vertex to take next, and two answers give the two traversals of this page: the oldest (a queue) gives breadth-first search, the newest (a stack) gives depth-first search.

The three colours

It is convenient — and, for DFS's edge classification, necessary — to refine "visited" into three states. A vertex is white before it is discovered, grey from the moment it enters the frontier until it has been expanded (all its neighbours examined), and black afterwards. The grey vertices are exactly the frontier. In BFS the greys are the queue contents, which at any moment span at most two consecutive distances (§12's key lemma); in DFS the greys are the stack contents, which at any moment form a single path from the root down to the current vertex, and the whole classification of edges in §17 comes from asking what colour the far end of an edge is when the edge is examined: white means a tree edge, grey means an edge back to the current path, black means an edge to something already finished. The colouring costs nothing extra — it is the same visited flag with one more value — and every figure on the page draws it: white as the default node fill, grey as amber, black as blue.

What a traversal computes, beyond a visit

  • Reachability. The visited set at the end is exactly the set of vertices reachable from s (invariants 2 and 3). "Can I get from s to t?" is one traversal, stopped early if t is found.
  • A spanning tree of the reached region (invariant 4), via the parent pointers. For BFS it is a shortest-path tree from s (§12); for DFS it is the tree whose ancestor relation the parenthesis theorem describes (§16).
  • A vertex order — the order of takes (the BFS order, the DFS preorder) or of finishes (the DFS postorder). The reverse DFS postorder is a topological order of a DAG (§20).
  • An edge classification in DFS (§17), from which cycles (§18), strongly connected components (§22) and articulation points (§24) follow.
  • Distances in edges in BFS (§12), and hence bipartiteness (§14) and shortest-path reconstruction (§13).

Where the two traversals come from

Both are the tree traversals of the tree page generalised to a graph, with the visited set added because a graph may have more than one path to a vertex. Level-order traversal of a tree, with its queue, is BFS on the tree from the root; preorder traversal, with its recursion or explicit stack, is DFS. On a tree the visited set is redundant (there is one path to everything) and the two searches produce the level order and the preorder respectively; on a graph the visited set is what stops a cycle from being walked forever, and the "already visited" edges it rejects are the non-tree edges whose classification carries all the structural information. The queue and the stack themselves are the linked-structures page's; this page assumes their O(1) operations and does not re-teach them.

Why the choice of frontier is everything. The generic skeleton with a bag (take any element) still visits everything reachable in Θ(V + E). What the bag's discipline adds is order, and order is what the applications use: the queue's order is by distance, the stack's order is by nesting. Every result in §11–§24 is a theorem about one of those two orders.

What the trace shows

  • The layers are the distances, and the queue is the layer boundary. BFS is often described as "process layer k, then layer k + 1"; the queue implements that without ever storing the layer index, because vertices of layer k + 1 are appended behind the remaining vertices of layer k. An explicit two-list version ("current layer, next layer") is equivalent and is what a bit-parallel or parallel BFS uses.
  • A vertex's distance is fixed at discovery. dist[v] is assigned once, when v turns grey, and never changes — there is no relaxation. That is why BFS is right for unit weights and wrong for general ones: with weights, the first discovery is not necessarily the cheapest.
  • Non-tree edges are wasted scans, and there are E − (Vr − 1) of them. G1 has 10 edges, 7 are tree edges, 3 are not; each non-tree edge is scanned twice and rejected twice. On a dense graph almost every scan is a rejection, and the E term dominates the V term.
  • The queue is short on this graph, and that is not typical. The queue peaks at 2 because G1 is nearly a path. On a star it holds V − 1; on a random graph it holds a whole layer, which can be most of the graph (§25). The queue's maximum length is the BFS memory bound, and it is a property of the graph's shape, not of V.

12 BFS computes shortest paths in edges: the proof, the BFS tree, and the Θ(V + E) accounting

The claim to prove is that on termination dist[v] = δ(s, v) for every vertex, where δ(s, v) is the length in edges of a shortest path from s to v (∞ if none). The proof is in three steps: an easy inequality in one direction, a structural lemma about the queue, and a minimal-counterexample argument that closes the gap. It holds for directed and undirected graphs alike, and it is exactly the statement that fails the moment edges carry unequal weights.

What the proof used, and what it did not

Every step leaned on one fact: a vertex's distance is assigned as dist[parent] + 1 at discovery and the queue keeps discoveries in non-decreasing order, so by the time u is dequeued, everything closer than u has been dequeued and everything at u's distance is at most one behind it. That is a property of unit edge lengths: with a weight w(u, v) the candidate distance dist[u] + w can be beaten later by a path through a vertex dequeued after u, the "grey" case of the proof breaks, and the fix — take the vertex of smallest tentative distance rather than the oldest, and allow a tentative distance to be lowered — is Dijkstra's algorithm, the first item of §28's hand-off. Nothing in the proof cared whether the graph was directed; the undirected case simply has each edge available in both directions, which is why the same routine and the same theorem serve both. And nothing cared about the representation, which is why the cost line has to say "with adjacency lists" separately: the theorem is about the order, the bound is about neighbours(u).

Path reconstruction, and the direction of the pointers

The parent pointers point towards the source, so following them from a target yields the path backwards: g → f → d → b → a for G1, reversed to a b d f g, four edges, equal to dist[g]. This is the cheapest possible representation of a whole shortest-path tree — one integer per vertex — and it is why BFS (and Dijkstra after it) never store paths explicitly. The recursion above is the same shape as printing a linked list in reverse; the iterative version needs a reversal or a stack. A subtle point: the path is a shortest path from s to g, and its prefix a b d is a shortest path to d (every prefix of a shortest path is a shortest path — otherwise a shorter prefix would give a shorter whole), and its suffix d f g is likewise a shortest d-to-g path — every subpath of a shortest path is a shortest path between its own endpoints (splice in a shorter one and the whole gets shorter), the optimal substructure that Dijkstra and Bellman–Ford later rest on. What is not guaranteed is the tree path between two vertices on different branches: d to h through the BFS tree climbs to a and back down, five edges, where the graph offers d f e h in three.

Multi-source BFS and the super-source

Seeding the queue with several sources at distance 0 is not a trick but the same algorithm on a slightly different graph: add a virtual vertex σ with an edge to every source, run BFS from σ, and subtract one from every distance. Lemma 3 and the theorem of §12 apply verbatim, so the result is the distance to the nearest source, in one pass. The applications are all "how far is the closest X": the distance transform in image processing (every pixel's distance to the nearest edge pixel), evacuation planning (nearest exit), facility problems (nearest depot), and the partition of a graph into regions by nearest source, which falls out by recording, alongside dist, the source from which each vertex was reached. Running |S| separate searches and taking the minimum gives the same numbers at |S| times the cost.

14 Bipartiteness by 2-colouring: BFS parity, and the odd cycle it produces when it fails

An undirected graph is bipartite if its vertices can be split into two sides with every edge joining the two sides — equivalently, if it can be properly 2-coloured — and a graph is bipartite if and only if it contains no odd cycle. BFS decides this in one pass: colour each vertex by the parity of its distance from the source, and check every edge. The proof of the "if and only if" is short, and it is constructive in the useful direction: when the check fails, the failing edge together with the BFS tree yields an odd cycle as a certificate.

Why this is stated for undirected graphs, and what it is used for

Bipartiteness is a property of the undirected structure: an edge either joins the two sides or it does not, and direction plays no role. Run the 2-colouring on a directed graph and it answers the question about the underlying undirected graph, which is usually what is meant but should be said. The theorem's uses are broad. Matching: the bipartite matching and assignment algorithms (the flow hand-off in §28) require the two sides as input, and this check produces them. Consistency: any constraint of the form "these two must differ" over a set of items is an edge, and the items are consistently assignable to two classes iff the graph is bipartite — the odd cycle is the minimal inconsistent subset. Parity structure: in a bipartite graph every cycle is even, every walk between the same two vertices has the same parity, and the adjacency matrix has a symmetric spectrum; several graph algorithms have simpler special cases on bipartite input. And the certificate is the point of the constructive proof: an algorithm that says "not bipartite" is less useful than one that says "not bipartite, and here is the odd cycle", because the cycle can be shown to a user, used to localise a bug in a constraint set, or fed to the next stage.

Odd cycle, not just any cycle. A bipartite graph can have plenty of cycles — every even cycle, every grid, every tree-plus-even-chords. "Contains a cycle" is §18's question and has nothing to do with bipartiteness; "contains an odd cycle" is this section's, and the two checks are different passes with different witnesses.

Recursive or explicit stack — which, and when it matters

The recursive version is the definition and the one every proof is written against; its stack is the call stack, one frame per grey vertex holding the position in that vertex's adjacency list. The explicit-stack version keeps that position in an array of iterators and is otherwise identical — the figure runs both and reports that they agree on every timestamp — and it exists because the call stack is small: a few thousand to a few hundred thousand frames depending on the runtime, while a DFS on a path-shaped graph of 10⁶ vertices needs a depth of 10⁶. §26 takes this up. What must not be done is the shortcut that replaces "iterate lazily" by "push every white neighbour now": it is a correct traversal (it visits everything reachable) but the vertex order, the tree and the timestamps differ from true DFS, a vertex may be pushed once per incoming edge, and none of the theorems of §16–§24 apply to its output.

DFS against BFS on the same graph

  • Same work, different order. Both scan every adjacency entry once; both are Θ(V + E). BFS's order is by distance; DFS's is by nesting. BFS from a on G1 discovers b c d e f h g; DFS discovers b d c e f g h and goes eight deep where BFS never went past a layer of two.
  • Different trees. The BFS tree of G1 has g at depth 4; the DFS tree has it at depth 6. Only the BFS tree's depths mean anything (they are distances); the DFS tree's depths are an artefact of list order.
  • Different non-tree edges. BFS's non-tree edges join adjacent or equal layers and are otherwise structureless; DFS's non-tree edges are classified (§17) and each class says something.
  • Different memory profile. BFS holds a layer; DFS holds a path. Which is worse depends on the graph's shape, measured in §25.
DFS on a tree is preorder; on a graph it is preorder plus a memory. The visited set is the only addition, and it is what turns the non-tree edges — which a tree does not have — into the classified edges the rest of this page is built on. The traversals themselves are the tree page's; what is new here is what the rejected edges tell you.

Why the theorems matter more than the algorithm

The DFS procedure is six lines; its value is that those six lines produce timestamps with a provable structure, and that structure is what later algorithms consume. Topological sort (§20) needs only "for every edge (u, v) of a DAG, f[v] < f[u]", which the parenthesis theorem and the edge classification deliver. The two-pass SCC algorithm (§22) needs "the component containing the vertex with the largest f is a source component of the condensation", which the white-path theorem delivers. Articulation points (§24) need "every non-tree edge goes to an ancestor", the undirected special case of §17. None of these consult the DFS tree's parent pointers directly; all consult the timestamps, because the timestamps encode the tree and more. That is also why the naive stack variant of §15 is not DFS: it produces a visit order without the nesting, and none of the corollaries survive.

The four cases at a leaf. A vertex c with no white neighbours at discovery has f[c] = d[c] + 1 (G2: 3/4); its interval contains nothing, so it is nobody's ancestor; it is nested in every ancestor's interval and disjoint from everyone else's. The theorem's trichotomy holds with the "descendant" cases empty — the edge case is not an exception, it is the base of the induction that the recursion embodies.

What each class tells you

  • Tree edges are the DFS forest. Their number is V minus the number of trees, which for an undirected graph is the number of connected components (§19). Everything the forest "knows" — ancestry, depth, the recursion structure — is in these edges.
  • Back edges are cycles. Each one closes a cycle with a tree path, and — the converse, proved in §18 — a graph has a cycle only if DFS finds a back edge. For a DAG the class is empty; for an undirected graph it is the set of edges you could delete to leave a spanning forest, and its size is the cyclomatic number E − V + c.
  • Forward edges are redundant for reachability (a tree path already goes there) but not for distance: a forward edge is a shortcut, and BFS would have used it. Their presence distinguishes "reachable" from "reachable in the tree's number of steps".
  • Cross edges connect what the DFS explored separately, and they always point from later-discovered to earlier-discovered (d[u] > d[v]). They are the class that can join two different DFS trees. Note that an edge between strongly connected components may be a tree, forward or cross edge — never a back edge, since a back edge closes a cycle with the tree path and so lies inside one component — G2's a→d is a forward edge from {a, b, c} to {d, e}, and g→d a cross edge from {f, g, h} — and it is the decreasing-finish-time order of §22, not the classification, that keeps the second pass from following them.

Why direction changes the count from four to two

In a directed graph an edge (u, v) is examined once, from u, and v's colour at that instant is unconstrained by u's: v may have been finished long before u was discovered (cross), or discovered after u and finished through another route (forward). In an undirected graph the edge is available from both ends, and that symmetry forces the earlier-discovered endpoint to still be grey when the later one is discovered — the later one is on its list and must be dealt with before it finishes. So the later endpoint is always a descendant of the earlier, and "descendant" leaves only tree (discovered through this edge) or back (discovered through another route, this edge examined from below). The two "impossible" classes are impossible because an undirected graph cannot have a vertex finished before its neighbour is discovered. The practical consequence is the one that bites in §18: an undirected cycle detector needs only to look for grey neighbours, but it must not count the arrival edge as one.

Classification depends on the DFS, not only on the graph. Change the adjacency order or the starting vertex and an edge that was forward may become cross or tree. What is invariant is the existence of a back edge (it is equivalent to the existence of a cycle, §18) and the counts derived from the forest size; the labels on individual edges are properties of one particular search.

Why the directed proof needs the white-path theorem and the undirected one needs the exclusion

In the directed case the danger is a cycle whose edges are examined in an unhelpful order — could DFS traverse a cycle's vertices in separate subtrees and classify the closing edge as cross? The white-path theorem says no: the first vertex of the cycle to be discovered sees the whole rest of the cycle as a white path and swallows it into its subtree, so the closing edge lands on an ancestor. That is the argument, and it identifies which edge is the witness: the cycle's edge into its first-discovered vertex is always classified back. The cycle's other edges may be tree, forward or even cross edges — r→p tree, p→q cross (if q's subtree was explored from r first), q→r back is a three-cycle in which the cross edge is on the cycle — so "no cycle through this cross edge" is not a valid inference; only "no back edge anywhere, hence no cycle anywhere" is. In the undirected case the theorem of §17 already says every non-tree edge is a back edge, so any non-tree edge is a cycle and the only work is to recognise the tree edge to the parent when it is seen a second time from the child — which is what the exclusion does. Exclude by edge identity, not by parent vertex, and the detector is correct on multigraphs too; on a simple graph the two exclusions coincide, which is why the bug hides until a multigraph arrives.

Three cycle questions, three different answers. "Is there a cycle" is this section (any back edge). "Is there an odd cycle" is §14 (a same-colour edge in the BFS parity colouring). "Is there a cycle through vertex v" is neither: it is whether v lies in a strongly connected component of size ≥ 2 or has a self-loop (§22, directed), or whether v has two incident edges in the same biconnected block (§24, undirected).

Three notions of connectivity, and which this section is about

This section is the undirected case, where one traversal from s settles the matter because paths run both ways. The directed analogues are two different questions with two different algorithms: weak components — the components of the graph with arrows erased — by exactly this section's algorithm on the undirected version; and strong components — maximal sets in which every vertex reaches every other — by the two-pass or low-link algorithms of §22–§23. The word "connected" without a qualifier means the undirected notion, and it is a mistake to apply it to a digraph without saying which of the other two is meant.

When to use which. A static graph, one question: traverse (this section), Θ(V + E), no extra structure. Edges arriving over time with "are these connected yet?" queries between arrivals: union-find, near-linear total, and it is also the inner loop of Kruskal's algorithm — which is why the structure is built on the MST part rather than here (§27). Edges also leaving: neither; that is dynamic connectivity, a harder problem with its own structures.

20 Topological sort: reverse finishing order with its proof, Kahn's in-degree algorithm, and both on one DAG

A topological order of a directed graph is a linear ordering of its vertices in which every edge (u, v) has u before v. Which order do you get, and does it matter

DFS's order has a property Kahn's does not: it comes with finishing times. Any topological order places a vertex before its whole downstream closure — that is the definition — but only the DFS version attaches a timestamp to every vertex, which is what the SCC algorithm of §22 consumes, and only the DFS version still means something on a graph that turns out to be cyclic: reverse postorder then orders the condensation of §22, where Kahn's simply stops short. Kahn's order has a different property: it is level-like, emitting all initial sources first and generally keeping vertices close to their "earliest possible time", and it is the one to use when the choice among ready vertices should be controlled — by priority, by a tie-breaking rule, by "smallest label first" — because the ready set is an explicit queue you can replace with any container. Kahn's is also the one that detects a cycle by counting (fewer than V emitted) and can report the cyclic remainder, whereas DFS detects it by a back edge and can report the cycle itself. If all you need is some valid order, either will do, and neither is faster.

"Topological sort" is not a sort. It costs Θ(V + E), not Θ(V log V), because the order is not a comparison sort — it is a traversal order. The name is historical; sorting vertices by their finishing times with a comparison sort would give the same result with an unnecessary logarithm.

Applications: what is actually a DAG

  • Build systems and package managers. Targets and their dependencies; the build order is a topological order, and a "circular dependency" error is Kahn's algorithm stopping short. Parallel builds schedule every ready vertex at once — the level structure of Kahn's algorithm, processed a whole queue at a time, is exactly the set of targets that can run concurrently.
  • Spreadsheets and reactive systems. Cells that reference cells; recalculation proceeds in topological order so that every formula sees up-to-date inputs, and a cycle is the "circular reference" the spreadsheet refuses.
  • Course prerequisites, project scheduling, task graphs. The classic framing. With durations on the vertices, the longest path in the DAG (computed in one pass over a topological order) is the critical path — the minimum time to complete everything with unlimited parallelism.
  • Compilers. Evaluation order of expressions with shared sub-expressions; instruction scheduling on a dependency DAG; the order of module initialisation; dead-code elimination by reachability from the roots.
  • Computation graphs. A neural network's forward pass is a DAG evaluated in topological order; backpropagation is the same DAG in reverse topological order — the chain rule applied along edges after every downstream gradient is known. Autodiff frameworks record the DAG and sort it.
  • Dynamic programming over a DAG. Any DP whose subproblem dependencies form a DAG can be tabulated in topological order (which is what "bottom-up" means), or memoised, which is DFS finishing order in disguise — memoisation versus tabulation. Shortest and longest paths in a DAG, with any weights, are one relaxation pass along a topological order: Θ(V + E), the first item on the weighted-graph list of §28.
  • Version-control history. A commit DAG's topological order is the "log" order that shows every commit after its parents; the merge base of two branches is a lowest common ancestor in that DAG, found by a two-colour traversal from both.
The DAG is the shape of "before". Whenever a problem says "must precede", "depends on", "is computed from", it has handed you a directed graph, and the first thing to check is that it is acyclic — because if it is not, no order exists and the problem as stated has no solution. Topological sort is simultaneously the check and the answer.

Why the reverse graph, and why decreasing finishing time

Pass 1 is a DFS whose only output is the finishing order, and the lemma says that order sorts the components topologically in the condensation: the component that finishes last is a source component (nothing enters it from another component). A DFS of G from a vertex of a source component would leak — it reaches everything downstream. A DFS of Gᵀ from the same vertex cannot leak, because in Gᵀ the source component is a sink. That is the whole trick: the finishing order finds a source of the condensation, the reversal turns it into a sink, and a DFS confined to a sink component collects exactly that component. Removing it and repeating (which is what the decreasing-f outer loop does, with black vertices as "removed") peels the condensation one sink at a time. The order in which pass 2 emits components is therefore a topological order of the condensation — sources of GSCC first — which is often the by-product you actually wanted, since "process each component after everything that can reach it" is the typical next step.

Connected, strongly connected, weakly connected. G2 is one weak component (erase arrows: connected), three strong components, and not strongly connected. 23 The single-pass low-link algorithm: the same components in one DFS, with an explicit stack of the current path's components

The two-pass algorithm is the easiest to prove; the single-pass algorithm (Tarjan's) is the one most libraries ship, because it needs no reverse graph and one traversal instead of two. Its idea: during a single DFS of G, keep every discovered-but-not-yet-assigned vertex on an auxiliary stack, and compute for each vertex u a low-link value — the smallest discovery index reachable from u's subtree by following tree edges down and at most one non-tree edge to a vertex still on the stack. When a vertex's low-link equals its own index, it is the root of a component, and everything above it on the auxiliary stack is that component.

Reading the low-link values

The value low[u] answers "how far back up the current path can u's subtree reach with one jump", and the test low[u] = idx[u] answers "not past u itself". In G2, d's only edge goes to e, which is on the stack with index 3, so low[d] = 3 < 4: d can climb to e and is not a root. e inherits low[d] = 3, which equals its own index — nothing in e's subtree reaches above e — so e is a root, and the stack above and including e is d, e: the component {d, e}, popped as a unit while a, b stay below on the stack awaiting their own root. Note the edge g→d late in the search: by then d has been popped and is no longer on the stack, so the edge is ignored — it is a cross edge into a completed component, and following it would wrongly merge {f, g, h} with {d, e}. That "ignore if not on the stack" test is the single line that most hand-written versions get wrong, and it is why the algorithm's correctness check against brute force is worth running.

Which to use. When the reverse graph is available anyway (CSR with both directions, a database with in-links), the two-pass algorithm's clarity wins. When the graph is implicit, or only out-edges are cheap, or the constant matters, the low-link algorithm wins. When the component order matters, note that they disagree — sources-first versus sinks-first — and both orders are topological orders of the condensation in opposite directions.

An articulation point (cut vertex) of a connected undirected graph is a vertex whose removal disconnects it; a bridge is an edge whose removal does. A graph with at least three vertices and no articulation point is biconnected: every pair of vertices lies on a common cycle, so no single failure separates them. The same idea, three times

The low value of this section, the low-link of §23 and the test in both are one idea: how far back up the DFS path can this subtree reach with a single non-tree edge? In a directed graph the answer identifies component roots (a subtree that cannot reach above its root is a closed component); in an undirected graph it identifies separators (a subtree that cannot reach above its parent is cut off by that parent). The bookkeeping differs — the directed version must ignore edges into completed components, the undirected version must ignore the arrival edge — but the recursion is the same postorder minimum, and the cost is the same single traversal. The undirected version extends in the obvious way to output the blocks themselves (the blocks and cut vertices together form the block-cut tree, which is what reliability analyses actually work on): push edges on a stack as they are examined, and when a child w with low[w] ≥ d[u] finishes, pop edges down to (u, w) — those edges are one biconnected component.

Using low[w] > d[u] for cut vertices (that is the bridge test; a vertex on a cycle through its parent has low[w] = d[u] and is still a cut vertex if it is the only route) — and forgetting the root's separate rule, which makes the root a cut vertex whenever low[child] ≥ d[root] = 1, i.e. always. The path example and the biconnected example together catch both.

The practical rules

  • State spaces: BFS for the optimal solution, DFS only with a depth bound. BFS's memory is the width of the layer at the solution depth, exponential in the depth but bounded by it; unbounded DFS may descend the wrong way forever. Iterative deepening — DFS to depth 1, then 2, then 3 … — gives BFS's order with DFS's memory at a constant-factor cost in time, and is the standard compromise.
  • Structure: DFS. Anything that needs the parenthesis theorem needs DFS's timestamps, and BFS cannot supply them. Topological sort has Kahn's BFS-like alternative and components and undirected cycle witnesses work with either search (§14, §19); SCCs and articulation points do not.
  • Distance: BFS, and only for unit weights. The moment edges carry unequal weights, neither search is the tool; the priority-queue frontier of §28 is.
  • Big graphs: mind the frontier you are holding. A web-scale BFS holds a layer that can be most of the graph; a road-network DFS holds a path that can be most of the graph. Both can be Θ(V), and the pointer-heavy version of either is what runs out of memory first. CSR (§07) and a bit-vector visited set are the mitigations.
The one-line comparison. BFS is a search by distance and holds a layer; DFS is a search by nesting and holds a path. Time is the same; memory is the shape's choice; the theorems are the order's.

Where the depth comes from, and why it is not rare

It is tempting to think a million-deep recursion needs a contrived input. It does not. A linked list is a path; a file system with a deep directory chain, a long-running commit history with no branches, a chain of dependent tasks, a road that runs across a country, a polymer, a time series modelled as a graph — all are paths or nearly so. A grid is worse in a subtler way: with any fixed neighbour order, DFS explores a grid as a space-filling snake, and a 1 000 × 1 000 image is a million-deep recursion. Random sparse graphs, as the figure of §25 shows, have DFS trees whose depth is a large constant fraction of V. Only genuinely tree-like, well-balanced inputs keep the depth logarithmic, and a graph algorithm rarely gets to assume its input is balanced. The rule is therefore simple: a DFS that may be run on a large graph is written with an explicit stack, and the recursive version is kept for the proofs and for small inputs.

Tail calls do not help. DFS is not tail-recursive — after the call on v returns, u must continue its loop and then finish — so no tail-call optimisation removes the frame. The recursion page explains which shapes can be eliminated and which cannot; DFS is squarely in the "cannot" class, which is why the conversion has to be done by hand.

27 Union-find, named: the dynamic-connectivity structure that belongs to the MST part

Twice on this page a second algorithm answered a connectivity question by processing edges one at a time — the union-find check in §19's figure, and the "incremental" column of §19's discussion — and both times the structure was used without being built. Union-find (the disjoint-set forest) maintains a partition of V under two operations: find(x), which returns a canonical representative of x's set, and union(x, y), which merges two sets. Feeding it the edges of a graph one by one makes it answer "are u and v connected yet?" between insertions, which a traversal cannot do without re-running. Its construction, the two heuristics and the inverse-Ackermann amortised analysis are the business of the Algorithms series' shortest-paths-and-MST part, where it is Kruskal's inner loop; this section says only what it is, what it costs, and why it is not this page's.

The reason the structure is not built here is that this page's questions are all static — the graph is given and traversed — and for a static graph the traversal of §19 is simpler, exact and linear. Union-find earns its place when the edge set is being discovered, and the canonical place that happens is Kruskal's algorithm: sort the edges by weight, walk them in order, and accept each one whose endpoints are not yet connected. That loop makes E find-queries and V − 1 unions, and the near-constant amortised cost per operation is exactly what makes the algorithm O(E log E) — dominated by the sort — rather than O(E · V). Traversal or union-find? Static graph, one pass: traverse. Edges arriving with queries in between, or an algorithm that selects edges one at a time (Kruskal, percolation, image segmentation by merging): union-find. Edges leaving: neither.

Arbitrage, constraint systems, the correctness backstop. O(V · E). SHORTEST PATHS IN A DAG — one relaxation pass in topological order (§20), any weights, no cycles to worry about. Θ(V + E): the cheapest shortest-path algorithm there is, and the longest-path / critical-path computation is the same pass with max. ALL PAIRS — Floyd–Warshall on the matrix, Θ(V³), the recurrence dk[i][j] = min(dk−1[i][j], dk−1[i][k] + dk−1[k][j]); its boolean form is the transitive closure this page used to check SCCs (§22). Or V runs of Dijkstra for sparse graphs. SINGLE TARGET with a heuristic — A*: Dijkstra with the key dist + h(v), h an admissible (never over-estimating) estimate of the remaining distance; explores far fewer states on the implicit graphs of §09. Route planning, puzzle solving, motion planning. MINIMUM SPANNING TREE — the cheapest edge set connecting everything: Kruskal (sorted edges + union-find, §27) or Prim (BFS with a priority queue keyed by the edge weight to the tree — Dijkstra's skeleton with a different key). Network design, clustering (cut the MST's heaviest edges), approximation algorithms. MAXIMUM FLOW / MINIMUM CUT — how much can be pushed from s to t through capacitated edges, and the bottleneck that limits it: augmenting paths found by BFS on the residual graph (Edmonds–Karp), or push–relabel. Bipartite matching (§14 supplies the sides), assignment, scheduling, image segmentation, network reliability. where they areall of the above — with proofs, traces and measured costs — belong to the Algorithms series part Shortest Paths, MST & Flow, reached from the hub's map. This page's contribution is the graph they run on and the traversals they are built from.

Why the hand-off is here and not earlier

Every weighted algorithm above is one of this page's traversals with a different frontier. Dijkstra is BFS with the queue replaced by a heap and the assignment dist[v] = dist[u] + 1 replaced by the relaxation dist[v] = min(dist[v], dist[u] + w); Prim is the same loop keyed by a different quantity; DAG shortest paths is a topological sort followed by one relaxation sweep; Bellman–Ford is the edge-list loop that §12 used as a brute-force check, run with real weights; Edmonds–Karp is BFS on a graph derived from the original. Reading them without this page means learning the traversal and the weight logic at once; reading them after it means learning only the weight logic. The single conceptual step is the one the §12 proof isolated — with unit weights the frontier's arrival order is the distance order, and with general weights it is not, so the frontier must be ordered explicitly and distances must be allowed to improve.

Before reaching for any of them. If the weights are all equal, it is BFS. If the graph is a DAG, it is one topological pass. If only one path is needed and a good estimate of remaining distance exists, it is A*. Dijkstra is the general non-negative case, Bellman–Ford the general case with negatives, and each costs more than the one before; the cheapest applicable algorithm is decided by the graph's properties, which this page's tools — unit weights?, acyclic? (§18), connected? (§19) — establish first.

What transfers, and what does not

What transfers is the representation and the cost model. A GNN library's "sparse tensor" is CSR (or the COO edge list of §06, converted); its "scatter-add over edges" is the adjacency scan; its memory is Θ(V·d + E·d) per layer and its time the same, so a graph with a few hubs of enormous degree costs what the handshake lemma says it costs. The neighbourhood a k-layer network can see is exactly the set BFS reaches in k layers, and on a sparse random graph with small distances (§02) that set is most of the graph within a handful of layers — the "over-smoothing" problem of deep GNNs is, in this page's terms, the observation that BFS layers on such graphs grow to cover everything, so that every vertex aggregates nearly the same set. What does not transfer is the notion of "shortest path": a message-passing network does not compute distances, and an attention weight on an edge is not a length. The weighted-graph tools of §28 are a different toolbox, and the ML pages that need real path lengths (route prediction, graph-distance features) call them as pre-processing rather than learning them.

The same object under every name. "Sparse tensor", "adjacency structure", "triple store", "proximity index", "computation graph", "factor graph" — each is an adjacency representation from §04–§07 with a specialised access pattern, and each one's cost is a §12-style aggregate over the adjacency lists. Read the representation first and the model second.

30 Pitfalls

  • "BFS/DFS is Θ(V + E)" without naming the representation. With adjacency lists, yes; with a matrix it is Θ(V²) at any density, because neighbours(v) scans a row. §12's figure shows both at V = 64.
  • "BFS gives shortest paths." Shortest in edge count, from the source, one per vertex. With weights it is wrong (§28); between two non-source vertices the BFS-tree path is not generally shortest (§13).
  • Four edge classes on an undirected graph. Undirected DFS has tree and back edges only (§17). Seeing the arrival edge a second time produces a spurious back edge (the tree edge seen from the child) or a spurious forward edge (a back edge seen from the ancestor's side); a "cross" label means an undirected edge was stored in only one adjacency list — the graph is secretly directed.
  • Cycle detection that excludes the parent vertex. Correct on simple graphs, blind to parallel edges. Exclude the arrival edge (§18's fourth case).
  • "A graph is a DAG iff DFS finds no back edge" applied to an undirected graph. A back edge in an undirected graph means a cycle, but the statement "DAG" is directed; an undirected graph with no cycles is a forest, and the test is E = V − c (§18, §19).
  • Assuming the topological order is unique, or that the two algorithms agree. D has 40 valid orders; DFS gives h a c f b d e g, Kahn a h b c d f e g. Unique iff a Hamiltonian path (§21).
  • Emitting reverse finishing order without checking for a back edge. On a cyclic graph the DFS still finishes, and the "order" it produces violates some edge. Check, or use Kahn's count (§20).
  • The naive stack DFS. "Push all white neighbours" is a traversal, not DFS: no valid finishing times, a vertex pushed up to in(v) times, and none of §16–§24 applies (§15, §26).
  • Recursive DFS on a big graph. Stack overflow on a path, a grid, or most random sparse graphs at V in the hundreds of thousands. Use the explicit-stack version, which reproduces the same timestamps (§26).
  • "BFS uses more memory than DFS." BFS holds a layer, DFS holds a path; the star and the path graph are each other's worst cases, and a random sparse graph is bad for both (§25).
  • Forgetting the outer loop. A single BFS/DFS from s reaches s's component only. Components, topological sort, SCCs and the DFS forest need the loop over all vertices (§10, §19).
  • "Connected" on a digraph. Say weakly or strongly. G2 is weakly connected with three strong components (§22).
  • Following edges into completed components in the low-link SCC algorithm. The onStack test is what stops g→d from merging {f, g, h} with {d, e} (§23).
  • Using > for cut vertices or forgetting the root rule. Cut vertex: low[w] ≥ d[u]; bridge: low[w] > d[u]; root: two or more tree children (§24).
  • Multi-source BFS as several BFS runs. One run with all sources enqueued at distance 0 gives the nearest-source distances at Θ(V + E), not |S| times that (§13).
  • Bipartite check on a directed graph without saying so. It answers for the underlying undirected graph; direction is irrelevant to 2-colourability (§14).
  • Matrix "always worse". Dense graphs, worst-case O(1) edge queries, bit-parallel neighbourhood operations and algebraic methods all favour it; the space crossover is near density 1/4 (byte) or 1/32 (bit) (§04, §08).
  • Treating CSR as a mutable adjacency list. It is static: an insertion is a rebuild. Its benefit is cache behaviour, not asymptotics (§07).
  • The implicit-graph visited set keyed by object identity. Two generations of the same state are different objects; hash the encoded state, or the search loops (§09).
  • Counting edges with the adjacency-list loop. "For each vertex, for each neighbour" counts every undirected edge twice: 2E, the number every scan counter on this page reports (§05, §06).
