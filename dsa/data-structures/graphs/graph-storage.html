03 The graph ADT: the operations, and which representation makes each cheap

A graph abstract data type has a small, stable set of them, and the four representations of §04–§07 are four different trade-offs across that set. Reading the table

Two rows matter more than the rest. neighbours(v) is the traversal primitive: BFS and DFS ask it once per vertex, so their total cost is ∑v cost(neighbours(v)) + Θ(V). With adjacency lists that sum is ∑ deg(v) = 2E (or E directed) and the traversal is Θ(V + E); with a matrix every call costs V and the traversal is Θ(V²) however few edges exist. That is the single most important line on the page, and §12 measures it. hasEdge(u, v) is the other primitive, and the matrix is the only structure that answers it in constant time in the worst case; the adjacency map gets expected constant time by making each vertex's neighbour collection a hash set, and the plain list has to scan. Which of the two questions your algorithm asks decides the representation before density does: a traversal-heavy workload wants lists or CSR; an algorithm that repeatedly tests specific pairs — a triangle counter, a clique finder, Floyd–Warshall — is happier with a matrix or a map. The "addVertex" row is the matrix's other weakness — a new vertex means a new row and column, so the whole V × V block is reallocated — and the "wins when" row is the summary the rest of the page justifies.

04 The adjacency matrix: V² cells, O(1) edge queries, and the algebra it unlocks

Number the vertices 0 … V−1 and keep a V × V table A with A[u][v] = 1 if (u, v) ∈ E and 0 otherwise. For an undirected graph the table is symmetric, A[u][v] = A[v][u], and each edge occupies two cells; for a directed graph a cell is set only in the direction of the arrow. The matrix is a two-dimensional array — one contiguous block of V² cells with row-major addressing — and it inherits both of that array's properties: any cell in constant time, and space proportional to the whole grid whether or not the grid is used.

When the matrix is the right answer

The reflex "matrices waste space, use lists" is right for sparse graphs and wrong as a rule. The matrix wins in four situations, and they are common enough to name. Dense graphs. Once E is a constant fraction of V², the list representation's per-entry overhead (a pointer or an integer per neighbour, a header per vertex) exceeds one byte or one bit per cell; the crossover is measured in §08 at a density near 0.25 for a byte matrix against integer lists and near 0.03 for a bit matrix. A complete graph, a distance table, a full similarity matrix, a tournament — these are matrices already. Worst-case O(1) edge queries. An adjacency map gives expected constant time via hashing; the matrix gives it unconditionally and with one memory access, which matters for algorithms whose inner loop is "is (u, v) an edge" — clique and triangle enumeration, Floyd–Warshall, any dynamic programme over vertex pairs. Bit-parallel operations. A bit matrix stores a row as V/64 machine words, so "the neighbours of u that are also neighbours of v" is V/64 AND instructions, "does u have any neighbour in set S" is an AND and a test, and a whole BFS layer expansion can be done a word at a time. Nothing list-based competes on dense instances. Algebraic questions. Counting walks, triangles, spectral properties, the transitive closure, and every graph-as-linear-operator method (including the normalised-adjacency propagation of graph neural networks) are matrix statements; even when the matrix is stored sparsely, the reasoning is matrix reasoning.

Where it is the wrong answer, and by how much

The measure of the mismatch is the ratio V² / (V + E). For the §08 example of a million vertices and ten million edges it is 10¹² / (1.1 × 10⁷) ≈ 90 000: a bit matrix would be 125 GB against about a hundred megabytes for lists, and a byte matrix a terabyte. Beyond storage, a neighbour query on a sparse row reads V cells to find an average of 2E/V = 20 neighbours, so every traversal pays a V/20 = 50 000-fold overhead in cell reads over the list version. The other, subtler failure is addVertex: a structure that gains vertices over time — a growing social graph, a streaming citation index — cannot afford to reallocate a V × V block for each new one, whereas a list representation appends one empty list. Finally, the matrix cannot hold parallel edges without switching from flags to counts, and it cannot hold per-edge data (an edge label, an object) without becoming a matrix of pointers, at which point it is a sparser and slower adjacency map.

The bound to attach to every traversal. "BFS is Θ(V + E)" is true with adjacency lists and false with a matrix, where it is Θ(V²). The algorithm did not change; the cost of neighbours(v) did. Whenever this page (or any other) states a traversal bound, the representation is part of the statement.

05 Adjacency lists — and the adjacency map and set that fix their one weak query

Keep, for each vertex v, a collection adj[v] of the vertices adjacent to it — its out-neighbours if the graph is directed, all its neighbours if not. The outer structure is an array of V collections, indexed by vertex number (or a hash map from vertex key to collection, if vertices are not numbered); the inner collections can be linked lists, dynamic arrays, hash sets or hash maps, and that inner choice is what distinguishes the "adjacency list" from the "adjacency map". Space is Θ(V + E) whatever the inner type: V headers plus one entry per adjacency, and there are 2E adjacencies in an undirected graph (each edge appears in two lists) and E in a directed one.

Why this is the default

Three things make the adjacency list the representation every graph library reaches for first. It is proportional to the graph: a million vertices with ten million edges is tens of megabytes (§08), and a vertex with no edges costs one empty header. Its neighbour query is proportional to the answer: Θ(deg u) to produce deg u neighbours, so a full traversal costs the sum of the degrees, which is the handshake lemma's 2E, plus V for visiting each vertex — the origin of every Θ(V + E) on the page. And it grows: a new vertex is a new empty collection, a new edge is an append. What it does badly is the edge query, which is a scan, and deletion, which is a scan followed by a shift. The adjacency map exists for workloads where those two matter — a simulation that keeps adding and removing edges, an algorithm that tests specific pairs — and buys expected constant time for both at the cost of a heavier structure and an unordered, slower neighbour iteration. The choice between them is a choice between "I mostly walk" (list) and "I mostly probe and edit" (map), and is independent of density.

Details that bite

  • An undirected edge is two entries. addEdge(u, v) must append to both adj[u] and adj[v]; forgetting one gives a directed graph that quietly fails symmetric queries. Every undirected count on this page — scans, entries, CSR length — is 2E for this reason, and the figures check it.
  • Order of neighbours is part of the behaviour. The traversals of §11 and §15 visit neighbours in list order; a different insertion order gives a different (still correct) BFS tree, DFS tree, edge classification and topological order. Reproducible results need a fixed order — sort the lists, or store edges in a canonical sequence. This page's hand examples use insertion order in the order the edge strings are written.
  • The in-neighbours are not there. A directed adjacency list answers "where can u go" and not "who can reach u". Kahn's algorithm (§20) needs in-degrees; the two-pass SCC algorithm (§22) needs the whole reverse graph. Both are Θ(V + E) to build from the forward lists, once.
  • Vertex removal is the expensive operation. Removing v means finding v in every list that mentions it. Without in-neighbour lists that is a scan of all E entries; a common dodge is to mark v deleted and have traversals skip it — a tombstone, exactly as in open-addressed hash tables, with the same compaction obligation.
  • Self-loops and parallel edges are representable. A self-loop {u, u} is an entry u in adj[u] (twice, if the undirected convention of "each edge contributes two entries" is kept, so that ∑ deg stays 2E); parallel edges are repeated entries. Both are fine for BFS and DFS — they cost an extra scan and never change a distance — but an undirected cycle detector that skips "the parent vertex" instead of "the arrival edge" is blind to a doubled edge (§18), and the matrix cannot hold either without becoming a count matrix.
  • Pointer lists lose the cache. A linked list of neighbour nodes is a pointer chase per neighbour; a dynamic array of neighbour ids is contiguous within one vertex's list but the lists themselves are scattered on the heap. The cache-line model prices this at one line fetch per list header and one per few entries; CSR (§07) is the layout that removes the scatter.

06 The edge list: the minimal representation, and the one that some algorithms actually want

Store the graph as a single array of E pairs (u, v) — optionally with a weight — and nothing per vertex. This is what a graph looks like on disk, in a file of "source, target" rows, in a database table, and in the argument to every graph constructor on this page (GR.graph(n, edges) builds the adjacency lists from an edge list in one pass). It answers the two ADT queries badly — hasEdge and neighbours are both scans of all E pairs — but it answers "give me every edge" perfectly, and there are algorithms for which that is the only question.

costsspace E pairs: Θ(E), 8 bytes per edge as two 32-bit ids — the smallest constant of any representation (§08); no header per vertex, so V isolated vertices cost nothing (and are not even recorded — V must be stored separately) edges() Θ(E), contiguous addEdge O(1) append removeEdge O(E) to find, O(1) to swap-delete once found hasEdge(u, v) O(E) scan neighbours(u) O(E) scan degree(u) O(E) — a BFS that used these directly would be O(V · E) what it is forKruskal's MST: SORT the edges by weight and take each one that joins two components (a union-find query) — it never asks for a neighbour, only for the edges in order (the hand-off in §27–§28) Bellman–Ford: V − 1 rounds of "relax every edge" — again a loop over E pairs, no adjacency needed; the figures of §11 and §13 use exactly this loop, with unit weights, as one of their two brute-force checks on BFS loading, storing, streaming, shuffling, sampling edges; building any other representation: sort by source (counting sort, Θ(V + E)) and the sorted edge list IS the CSR targets array (§07)

A representation for the edges, not for the vertices

The edge list is the honest form of the definition E ⊆ V × V — a set of pairs and nothing else — and its costs follow from that honesty: any question about a vertex requires looking at every pair, because nothing groups the pairs by vertex. That is why it appears at the bottom of every column of §03's table except space and "iterate all edges". Yet two of the most important weighted-graph algorithms are naturally loops over edges rather than over vertices: Kruskal's minimum spanning tree processes edges in sorted weight order and never asks who is adjacent to whom, and Bellman–Ford relaxes every edge V − 1 times and is agnostic to their grouping. For those, the edge list is not a compromise but the right structure, and converting to adjacency lists would be wasted work. The other role of the edge list is as the interchange format: a file of pairs, a table of rows, a stream of events. Every explicit representation on this page is built from one in Θ(V + E), and the conversion to CSR in §07 is a single counting sort of the pairs by their source vertex — the sorted edge list is the CSR targets array.

An easy mistake in the other direction. An algorithm described as "for each edge" on an adjacency-list graph costs Θ(V + E) too — iterate every vertex, then its list — but visits each undirected edge twice, once from each end. Code that does work per edge (relaxation, union) must either accept the double visit or skip the copy with u < v; code that counts edges by this loop gets 2E.

07 Compressed sparse row: the adjacency list flattened into two arrays, and why systems use it

Concatenate all the adjacency lists, in vertex order, into one integer array targets of length 2E (undirected) or E (directed), and keep a second array offsets of length V + 1 with offsets[u] the index where u's neighbours begin. The neighbours of u are then the contiguous slice targets[offsets[u] … offsets[u+1]), its degree is offsets[u+1] − offsets[u], and the whole graph is two flat arrays with no pointers at all. This is the layout under nearly every high-performance graph system, sparse-matrix library and GPU graph kernel, and the reason is not asymptotic — CSR has exactly the adjacency list's Θ(V + E) bounds — but the memory model: contiguous integers are the thing a cache and a prefetcher are built for.

What CSR costs, and what it buys

The price is immutability. Inserting an edge into u's slice means shifting every later slice and incrementing every later offset — Θ(V + E) — so CSR is built once from an edge list and then read. Systems that need updates keep them in a side structure (a small adjacency map of recent insertions, a deletion bitmap) and periodically rebuild; a purely dynamic workload should stay on adjacency lists or maps. What CSR buys is everything the memory hierarchy rewards. A pointer-based adjacency list scatters each vertex's neighbours somewhere on the heap, so a traversal is a cache miss per list header and often per neighbour node; the cache model of the linked-structures page prices those misses and they dominate the instruction count. In CSR the neighbours of u are adjacent integers, a slice of 16 fits in one 64-byte line, the hardware prefetcher streams the next lines, and a BFS that processes vertices in numeric order walks targets almost sequentially. The offsets array is V + 1 integers with no per-vertex header, so the constant in Θ(V + E) is as small as the representation allows, and a parallel weights array keeps per-edge data equally contiguous. This is also the sparse-matrix format of numerical libraries — the graph's adjacency matrix, stored row by row with only the non-zeros — which is why "sparse matrix–vector multiply" and "one round of message passing" are the same loop.

CSR is not "just an adjacency list"

  • Same bounds, different constants. Every Θ(·) in §03's table matches the adjacency list's; the difference is a factor in wall-clock time from cache behaviour, and it is a factor that is large on big graphs and invisible on small ones. Do not cite CSR for an asymptotic win.
  • Static. No in-place insertion or deletion; no vertex addition. A graph that changes is not a CSR graph, or is CSR plus a delta structure.
  • Directed needs two. CSR stores out-neighbours; in-neighbours (for Kahn's algorithm, for the reverse graph in §22, for "who links to me") need a second pair of arrays — the transpose, built by the same counting sort on the swapped pairs.
  • Vertex order is a tuning knob. Because locality depends on numbering, systems renumber vertices so that neighbours have nearby ids (a BFS order from a well-chosen root is a common choice); the graph is unchanged, the traversal is faster. This has no analogue in the pointer representations.

08 The representation costs measured, and the density at which a matrix wins

Asymptotically the matter is settled — Θ(V²) against Θ(V + E) — but the interesting question is where a matrix becomes the smaller structure, and that depends on constants that have to be written down. This section states a byte model, applies it across the whole density range, and finds the crossover; the figure computes every number from the model rather than asserting it.

At the default V = 1 000 the two matrix lines are flat — 1 000 000 bytes and 125 000 bytes, independent of E — and the three list-like lines rise linearly with E from a floor set by their per-vertex cost (the adjacency list's 24 000 bytes of headers is the highest floor, the edge list's zero the lowest). The byte matrix becomes the smaller structure at about E ≥ 122 000 (the figure's scan steps by 124; the model's exact threshold is 122 001), a density of 0.244 of the 499 500 possible edges; the bit matrix at about E ≥ 12 600 (exactly 12 626), density 0.025. Move V to 10 000 and both crossovers approach their limits of 1/4 and 1/32; move it to 100 and the bit matrix, at 1 250 bytes, is smaller than a hundred 24-byte headers before a single edge is stored — small dense graphs are matrix graphs. The panel's second block is the million-vertex case above: the difference between 1 000 GB and 84 MB is a factor of about 12 000 — V² bytes against 4·(V + 1 + 2E) bytes — and it is why "sparse" is the assumption that every large-graph system makes.

Reading the crossover correctly

  • It is a space crossover. Time has its own: a matrix traversal reads V² cells however sparse the graph, and §12 measures the list-versus-matrix operation counts to show the traversal crossover sits somewhere else entirely — the matrix reads V cells per vertex, the list reads deg entries, so a traversal ties only on the complete graph (V + 2E = V² at density 1) and the matrix never wins a traversal on operation count; its wins are elsewhere (§04).
  • It moves with the constants. 64-bit ids push the list lines up and the crossover left (matrix wins sooner); per-edge weights stored in the matrix push its line up by the weight's size; a linked-list inner structure with 16-byte nodes makes lists three to four times bigger. The model's numbers are one honest configuration, not a universal constant.
  • Most real graphs sit far left of it. A density of 0.03 is an average degree of 0.03 · V — 30 000 neighbours per vertex in a million-vertex graph. Social, web, citation and dependency graphs have average degrees in the tens or hundreds (road networks, a handful) and are two to five orders of magnitude sparser than even the bit-matrix crossover.
  • Undirected: edge list < CSR < lists, always, in this model. The edge list has no per-vertex cost at all and stores each undirected edge once; CSR stores it twice but has only 4 bytes of per-vertex cost; lists pay 24. Directed, CSR stores each edge once too and beats the edge list as soon as E > V + 1 — 44 MB against 80 MB in the table above. The gap between CSR and lists is entirely header overhead, and it is the pointer-scatter that CSR also removes.

09 Implicit graphs: grids, state spaces, and graphs that are never stored

A traversal never needs the whole graph; it needs neighbours(v) for the vertices it reaches. So a graph can be given as a function rather than a structure — a rule that computes the neighbours of any vertex on demand — and every algorithm on this page runs on it unchanged. A grid is the simplest case: the vertex (x, y) has neighbours (x±1, y) and (x, y±1) minus the walls, and no adjacency list is ever built. A puzzle's state space is the important case: vertices are configurations, edges are legal moves, the graph may have 10²⁰ vertices, and BFS from the start configuration finds the fewest-moves solution by generating only the states it actually reaches.

Grids, mazes, images, and the four-versus-eight question

A maze is a grid graph; solving it is BFS from the entrance with parent pointers (§13) to recover the route. An image is a grid graph whose "walls" are decided by a pixel predicate — flood fill in a paint program is exactly this traversal with the predicate "same colour as the seed", and the connected components of §19 on a thresholded image are its blobs. The one modelling choice is adjacency: 4-neighbour (orthogonal moves only) or 8-neighbour (diagonals allowed), and it changes the answers — a diagonal wall blocks a 4-connected fill and not an 8-connected one, and distances in edges differ. Neither is "correct"; the application decides, and it should be stated. With 8-neighbour adjacency and a diagonal step counted as one edge, BFS distance is the Chebyshev distance on an open grid; with 4-neighbour adjacency it is the Manhattan distance. Both are distances in edges — BFS never knows that a diagonal is longer — which is the first place the weighted-graph tools of §28 earn their keep.

State spaces: where BFS finds the fewest moves

A sliding-tile puzzle, a Rubik's cube, a river-crossing riddle, a word ladder (change one letter at a time through dictionary words), a robot's configuration space, a program's reachable states in a model checker: each is a graph whose vertices are states and whose edges are single moves, and in each the question is "what is the shortest sequence of moves from here to there". That is δ(start, goal) in edges, so BFS (§11) answers it exactly, with the parent pointers reconstructing the move sequence. The graph is never stored — the 8-puzzle has 9!/2 = 181 440 reachable states, the 15-puzzle about 10¹³, and a chess position graph is beyond counting — and the traversal generates states from a successor function and remembers the visited ones in a hash set keyed by a compact state encoding. The cost is then governed by the branching factor and the depth: a BFS to depth d with b moves per state touches on the order of bd states, and its queue at depth d holds the whole layer. That layer is what runs out of memory first, long before time does, and it is the reason the memory comparison of §25 matters and the reason heuristic search exists: A*, the hand-off in §28, is BFS with a priority on "estimated total distance" that lets it ignore most of the layer.

Two implicit-graph traps. Without a visited set, any state space with cycles (nearly all of them: a move and its undo) makes BFS and DFS run forever, and a visited set keyed by a state's object identity rather than its value is no visited set at all — hash the encoded state. And an implicit graph has no V to iterate, so the "outer loop over all vertices" that gives DFS its forest and Kahn's algorithm its sources (§15, §20) does not exist; only single-source traversals from a known start make sense.
