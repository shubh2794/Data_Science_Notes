20 Topological sort: reverse finishing order with its proof, Kahn's in-degree algorithm, and both on one DAG

A topological order of a directed graph is a linear ordering of its vertices in which every edge (u, v) has u before v. Such an order exists if and only if the graph is a DAG — a cycle would need each of its vertices before the next, around to itself — and every "schedule these tasks respecting their prerequisites" problem is the problem of finding one. There are two standard algorithms, both Θ(V + E), and they produce different valid orders: DFS emits vertices in decreasing finishing time, Kahn's algorithm emits them in the order their prerequisites are exhausted. Each is proved below and both are run on the same DAG.

Which order do you get, and does it matter

DFS's order has a property Kahn's does not: it comes with finishing times. Any topological order places a vertex before its whole downstream closure — that is the definition — but only the DFS version attaches a timestamp to every vertex, which is what the SCC algorithm of §22 consumes, and only the DFS version still means something on a graph that turns out to be cyclic: reverse postorder then orders the condensation of §22, where Kahn's simply stops short. Kahn's order has a different property: it is level-like, emitting all initial sources first and generally keeping vertices close to their "earliest possible time", and it is the one to use when the choice among ready vertices should be controlled — by priority, by a tie-breaking rule, by "smallest label first" — because the ready set is an explicit queue you can replace with any container. Kahn's is also the one that detects a cycle by counting (fewer than V emitted) and can report the cyclic remainder, whereas DFS detects it by a back edge and can report the cycle itself. If all you need is some valid order, either will do, and neither is faster.

"Topological sort" is not a sort. It costs Θ(V + E), not Θ(V log V), because the order is not a comparison sort — it is a traversal order. The name is historical; sorting vertices by their finishing times with a comparison sort would give the same result with an unnecessary logarithm.

21 How many topological orders, when there is exactly one, and what they are used for

A DAG almost never has a unique topological order — any two vertices with no path between them can be swapped — and the number of valid orders can be astronomically large: V! for a graph with no edges, 1 for a path. The exact count is #P-hard in general (it is the number of linear extensions of a partial order), but for small graphs it can be computed by a dynamic programme over subsets, which is how the figures verify their "40". The uniqueness question, by contrast, has a clean answer, and the applications are the reason the whole topic exists.

(⇐) if consecutive vertices are always adjacent, the order is forced: v₁ must precede v₂, which must precede v₃, … . Applications: what is actually a DAG

  • Build systems and package managers. Targets and their dependencies; the build order is a topological order, and a "circular dependency" error is Kahn's algorithm stopping short. Parallel builds schedule every ready vertex at once — the level structure of Kahn's algorithm, processed a whole queue at a time, is exactly the set of targets that can run concurrently.
  • Spreadsheets and reactive systems. Cells that reference cells; recalculation proceeds in topological order so that every formula sees up-to-date inputs, and a cycle is the "circular reference" the spreadsheet refuses.
  • Course prerequisites, project scheduling, task graphs. The classic framing. With durations on the vertices, the longest path in the DAG (computed in one pass over a topological order) is the critical path — the minimum time to complete everything with unlimited parallelism.
  • Compilers. Evaluation order of expressions with shared sub-expressions; instruction scheduling on a dependency DAG; the order of module initialisation; dead-code elimination by reachability from the roots.
  • Computation graphs. A neural network's forward pass is a DAG evaluated in topological order; backpropagation is the same DAG in reverse topological order — the chain rule applied along edges after every downstream gradient is known. Autodiff frameworks record the DAG and sort it.
  • Dynamic programming over a DAG. Any DP whose subproblem dependencies form a DAG can be tabulated in topological order (which is what "bottom-up" means), or memoised, which is DFS finishing order in disguise — memoisation versus tabulation. Shortest and longest paths in a DAG, with any weights, are one relaxation pass along a topological order: Θ(V + E), the first item on the weighted-graph list of §28.
  • Version-control history. A commit DAG's topological order is the "log" order that shows every commit after its parents; the merge base of two branches is a lowest common ancestor in that DAG, found by a two-colour traversal from both.
The DAG is the shape of "before". Whenever a problem says "must precede", "depends on", "is computed from", it has handed you a directed graph, and the first thing to check is that it is acyclic — because if it is not, no order exists and the problem as stated has no solution. Topological sort is simultaneously the check and the answer.

22 Strongly connected components: the two-pass reverse-graph algorithm, its proof, and the condensation DAG

A strongly connected component (SCC) of a directed graph is a maximal set of vertices in which every vertex can reach every other. The SCCs partition V, and contracting each to a single vertex gives the condensation, which is always a DAG. The two-pass algorithm computes the partition in Θ(V + E) with two depth-first searches: one on G to obtain finishing times, one on the reverse graph Gᵀ in decreasing order of those times, each tree of the second search being one component. Why that works is a short argument about which component finishes last, and the figure runs both passes on G2.

Why the reverse graph, and why decreasing finishing time

Pass 1 is a DFS whose only output is the finishing order, and the lemma says that order sorts the components topologically in the condensation: the component that finishes last is a source component (nothing enters it from another component). A DFS of G from a vertex of a source component would leak — it reaches everything downstream. A DFS of Gᵀ from the same vertex cannot leak, because in Gᵀ the source component is a sink. That is the whole trick: the finishing order finds a source of the condensation, the reversal turns it into a sink, and a DFS confined to a sink component collects exactly that component. Removing it and repeating (which is what the decreasing-f outer loop does, with black vertices as "removed") peels the condensation one sink at a time. The order in which pass 2 emits components is therefore a topological order of the condensation — sources of GSCC first — which is often the by-product you actually wanted, since "process each component after everything that can reach it" is the typical next step.

Connected, strongly connected, weakly connected. G2 is one weak component (erase arrows: connected), three strong components, and not strongly connected. "The graph is connected" is meaningless for a digraph until one of the other two words is chosen, and the two algorithms — §19's on the undirected shadow, this section's on the digraph — answer different questions with different answers on the same input.

23 The single-pass low-link algorithm: the same components in one DFS, with an explicit stack of the current path's components

The two-pass algorithm is the easiest to prove; the single-pass algorithm (Tarjan's) is the one most libraries ship, because it needs no reverse graph and one traversal instead of two. Its idea: during a single DFS of G, keep every discovered-but-not-yet-assigned vertex on an auxiliary stack, and compute for each vertex u a low-link value — the smallest discovery index reachable from u's subtree by following tree edges down and at most one non-tree edge to a vertex still on the stack. When a vertex's low-link equals its own index, it is the root of a component, and everything above it on the auxiliary stack is that component.

Reading the low-link values

The value low[u] answers "how far back up the current path can u's subtree reach with one jump", and the test low[u] = idx[u] answers "not past u itself". In G2, d's only edge goes to e, which is on the stack with index 3, so low[d] = 3 < 4: d can climb to e and is not a root. e inherits low[d] = 3, which equals its own index — nothing in e's subtree reaches above e — so e is a root, and the stack above and including e is d, e: the component {d, e}, popped as a unit while a, b stay below on the stack awaiting their own root. Note the edge g→d late in the search: by then d has been popped and is no longer on the stack, so the edge is ignored — it is a cross edge into a completed component, and following it would wrongly merge {f, g, h} with {d, e}. That "ignore if not on the stack" test is the single line that most hand-written versions get wrong, and it is why the algorithm's correctness check against brute force is worth running.

Which to use. When the reverse graph is available anyway (CSR with both directions, a database with in-links), the two-pass algorithm's clarity wins. When the graph is implicit, or only out-edges are cheap, or the constant matters, the low-link algorithm wins. When the component order matters, note that they disagree — sources-first versus sinks-first — and both orders are topological orders of the condensation in opposite directions.

24 Articulation points and bridges: the low-link idea on an undirected graph, in one DFS

An articulation point (cut vertex) of a connected undirected graph is a vertex whose removal disconnects it; a bridge is an edge whose removal does. A graph with at least three vertices and no articulation point is biconnected: every pair of vertices lies on a common cycle, so no single failure separates them. These are the reliability questions — which router, which road, which server is a single point of failure — and the brute-force answer (remove each vertex or edge, recount components) costs Θ(V·(V + E)) or Θ(E·(V + E)). One DFS with a low value per vertex answers both in Θ(V + E), using the fact from §17 that an undirected DFS has only tree and back edges.

The same idea, three times

The low value of this section, the low-link of §23 and the test in both are one idea: how far back up the DFS path can this subtree reach with a single non-tree edge? In a directed graph the answer identifies component roots (a subtree that cannot reach above its root is a closed component); in an undirected graph it identifies separators (a subtree that cannot reach above its parent is cut off by that parent). The bookkeeping differs — the directed version must ignore edges into completed components, the undirected version must ignore the arrival edge — but the recursion is the same postorder minimum, and the cost is the same single traversal. The undirected version extends in the obvious way to output the blocks themselves (the blocks and cut vertices together form the block-cut tree, which is what reliability analyses actually work on): push edges on a stack as they are examined, and when a child w with low[w] ≥ d[u] finishes, pop edges down to (u, w) — those edges are one biconnected component.

Two errors that pass small tests. Using low[w] > d[u] for cut vertices (that is the bridge test; a vertex on a cycle through its parent has low[w] = d[u] and is still a cut vertex if it is the only route) — and forgetting the root's separate rule, which makes the root a cut vertex whenever low[child] ≥ d[root] = 1, i.e. always. The path example and the biconnected example together catch both.
