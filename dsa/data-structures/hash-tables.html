Hash Tables

One decision — compute the slot from the key instead of searching for it — and everything here follows. An array can reach slot i in constant time but only if you already know i; a hash table manufactures i out of the key itself, turning a search into an arithmetic expression. The price is that the manufacturing is not injective: distinct keys are guaranteed to land on the same slot, so most of this page is about what you do next. That question has exactly two families of answer — hang a list off the slot, or go find another slot — and each answer comes with its own expected-cost theorem, its own hypothesis, its own failure mode as the table fills, and its own opinion about what deletion means. The bounds here are expected, not worst-case, and the difference is not decoration: it is a probabilistic promise whose small print says who gets to choose the keys.

01 What a hash table is

A hash table is an implementation of the map abstract type in which the storage location of a key is computed from the key by a function, rather than found by searching. There is an array of m slots — the bucket array — and a hash function h that maps every possible key to an index in 0 … m−1. To store, look up or remove the entry for key k, you evaluate h(k) and go straight there. That is the entire idea, and the entire difficulty is contained in one word of it: function. A function from a large set to a small one cannot be injective, so different keys will arrive at the same slot, and a hash table is really a hash function plus a stated policy for what happens when they do.

Why each word of the definition is load-bearing

  • Computed, not searched. This is the whole inversion. A sorted array with binary search finds a key by narrowing an interval: O(log n) comparisons, each of which looks at data. A hash table performs no comparisons at all to decide where to look; it performs arithmetic on the key and then goes there. Comparisons reappear only to confirm that the entry sitting in the slot is really the one you wanted — which is why a hash table needs both a hash function and an equality test, and why the two must agree (§29).
  • A total function. h must be defined for every key in the universe and must return the same slot every time it is asked about the same key, for the lifetime of that key's membership in the table. Determinism is not a nicety; it is the only reason get can find what put stored. Every practical disaster in §29 is a violation of it: a key whose hash depends on a field that was later mutated, a hash that incorporates a memory address that the garbage collector moved, a hash seeded per-process being written to a file and read back in another process.
  • Into 0 … m−1. The range is the table, so the function's codomain is a property of the table, not of the key type. That is why the hash of a key is almost always built in two stages — a table-independent hash code and a table-dependent compression — which §04 separates properly, because nearly every real design decision lives at the seam between them.
  • Plus a collision policy. Without one, the structure is not a map. The two families, chaining and open addressing, are not interchangeable implementation details: they have different memory behaviour, different deletion semantics, different tolerable load factors, and different theorems. Half of this page is the consequence of that choice.

The motivation, as a cost argument against the alternatives

A map has to answer "where is the entry for key k?", and before hashing there were two honest answers. Scan: keep entries in a contiguous array or a chain of nodes in arbitrary order and compare against each — O(1) insert, Θ(n) lookup, trivially correct, fine up to a few dozen entries and useless beyond. Order: keep the entries sorted by key, and binary-search — Θ(log n) lookup, but insertion into a sorted array costs Θ(n) element moves, which pushes you toward a balanced search tree at Θ(log n) for everything. Hashing proposes a third answer that is not on that spectrum at all: do not look for the key, calculate where it must be. The gain is a bound with no log n in it. The losses are precise and worth naming up front — the bound is expected rather than guaranteed, the entries are stored in an order nobody chose, and every operation that depends on order — minimum, successor, range scan — becomes a full Θ(n) scan, and sorted iteration becomes a Θ(n log n) sort, instead of being free. §26 takes that trade seriously; the intervening sections earn the gain.

The one-sentence summary to carry through the page. A hash table buys O(1) expected time by replacing search with arithmetic, and every remaining section is either about making the arithmetic spread keys well, or about paying for the fact that it cannot spread them perfectly.

02 The map ADT, and what it does not promise

A map (equivalently dictionary, associative array, symbol table) is an abstract type holding a set of (key, value) pairs in which keys are unique. It is defined by behaviour, not by storage: any structure supporting the operations below is a map, and a hash table is one implementation among several. Keeping the ADT and the implementation apart is the discipline that makes the rest of the page legible — the ADT says what must be true, the implementation says what it costs, and a great many arguments about hash tables are really arguments about which of the two is being discussed.

What the ADT promises

  • Uniqueness of keys, enforced on put. A second put with an equal key overwrites rather than appends. This is the single behavioural difference between a map and a multimap, and it is why put cannot be implemented as "insert without looking" — it must first search, which is why insertion into a hash table costs a lookup and is not cheaper than one.
  • Values are opaque. The map never inspects a value; it neither compares, orders nor hashes it. Only keys are hashed. A set is exactly this ADT with the value omitted, which is why every hash-table technique on this page applies unchanged to hash sets.
  • Total lookup. get is defined for every key, answering "absent" when there is no entry. This matters more than it sounds: the unsuccessful search is a first-class case, it is usually the more frequent one in real workloads, and it has its own cost theorem in every scheme here — one that is consistently worse than the successful case, because an unsuccessful search cannot stop early.

What the ADT conspicuously does not promise

  • Any order. iterate() visits the entries in whatever order the implementation finds convenient. For a hash table, that order is a function of the hash values and the insertion history, so it can change when the table resizes, and — with a per-process random seed (§25) — between two runs of the same program on the same data. Code that depends on iteration order is depending on an implementation accident. If order is part of the requirement, the requirement is for a sorted map (key order — a balanced tree) or an insertion-ordered map (arrival order — a hash table with an auxiliary linked list threaded through the entries). Those are two different ADTs, and a plain hash table is neither.
  • Any relationship between keys. No minimum, no maximum, no successor, no "all keys between a and b". A map's keys form a set, not an ordered set, and this is precisely the structure a hash table destroys in exchange for its speed (§26).
  • Worst-case bounds. The ADT says nothing about cost at all. The O(1) people attach to it is a property of one implementation, holds in expectation, and rests on a hypothesis that an adversary can deliberately falsify.

Where the keys' own contract comes in

A hash table imposes two obligations on the key type that the ADT alone does not, and both are routine sources of bugs that present as "the entry vanished". First, h must be consistent with equality: if k equals k′ then h(k) must equal h(k′). The converse need not hold and cannot — that is what a collision is — but this direction is mandatory, because two equal keys that hash apart will be stored in two different slots and the map will contain a duplicate, silently violating its own invariant. Second, keys must be immutable while in the table, or at least the parts of them that h and equality read must be. Mutating a key after insertion moves its correct slot without moving the entry, and the entry becomes unreachable through the front door while remaining visible to iteration — the most confusing failure mode in this whole subject, because the entry is simultaneously present and absent depending on which operation you ask. Languages that only allow immutable types as hash keys are enforcing exactly this, and the restriction is not arbitrary conservatism.

03 Direct addressing, and exactly where it fails

Start from the case where hashing is unnecessary. If the key universe U is small and the keys are integers 0 … |U|−1, allocate an array of |U| slots and use the key itself as the index. This is a direct-address table, and it is the ideal hash table: h(k) = k, no collisions ever, Θ(1) worst-case for every operation with no probabilistic hypothesis anywhere. It is worth building the idea from here because the whole of hashing is what you do when the one assumption behind it — that |U| is affordable — is false.

The failure is about space, and only about space

It is worth being exact, because the argument is often stated loosely as "direct addressing doesn't scale". Time does not degrade at all — a direct-address table of a billion slots answers a lookup in one array access, same as a table of ten. What fails is that the array must be allocated, and its size is set by the universe rather than by the data. The example in the formula block is the canonical one: nine-digit identifiers give a universe of 10⁹, and a table of that many machine words costs gigabytes whether it holds a thousand entries or none. The memory is not merely wasted, it is actively harmful — it must be allocated, it must be initialised to NIL, and a traversal of the occupied entries has to walk all 10⁹ slots to find the thousand, so iterate() degrades from Θ(n) to Θ(|U|). Direct addressing turns a space problem into a time problem for exactly one operation, and that operation is the one that touches every slot.

Where direct addressing is still the right answer

  • Small, dense universes. Counting bytes (|U| = 256), bucketing ages, indexing by weekday, tallying the 26 letters of an alphabet, the bad-character table of a Boyer-Moore matcher: all of these are direct-address tables, and using a hash table for them would be strictly slower and larger. If |U| is a few thousand and occupancy is above a few per cent, stop here — you have a perfect hash function for free and it is the identity.
  • Bit vectors, when there is no value. If the map is really a set of small integers, each slot needs one bit rather than one word, and a universe of 10⁶ costs 125 KB rather than 8 MB. That is a 64-fold improvement which moves the affordability threshold by a factor of 64 — not by enough to rescue the 9-digit case, but enough to rescue many.
  • As the second level of something else. Index arithmetic on a dense small range is what makes perfect hashing's inner tables work, what makes counting sort and radix sort work, and what makes a direct-mapped cache work. The technique does not disappear; it becomes a component.

The intermediate case that motivates everything after

Between "universe small enough to index directly" and "universe astronomically large" there is no interesting middle ground, and that is the real point. Universes in practice are either tiny (a byte, a weekday) or enormous (every string, every 64-bit integer, every tuple) — there is almost never a universe of size 3n. So the decision is binary: if the universe is tiny, index it; otherwise the table must be sized by n, which forces m ≪ |U|, which forces h to be non-injective, which forces a collision policy. Everything from §09 onward is the consequence of this single unavoidable step. The hash function's job, viewed this way, is to simulate the direct-address table's distinct-slot-per-key property as closely as a function into a smaller range can — and the collision policy's job is to handle the gap that remains.

A useful reframing. A hash table is a direct-address table on a compressed universe. The compression is lossy, the loss is called a collision, and the load factor n/m measures how hard the compression is being pushed. Hold that picture and the rest of the page organises itself.

04 The two halves: hash code, then compression

In practice h is never written as a single function. It is the composition of a hash code, which maps an arbitrary key to a fixed-width integer and knows nothing about the table, and a compression function, which maps that integer into 0 … m−1 and knows nothing about the key. The split is not bureaucratic. It puts every key-type-specific decision on one side of a seam and every table-specific decision on the other, so a table can be resized without re-deciding how to hash a string, and a new key type can be supported without touching the table. It also localises blame: collisions are inevitable at the compression step, but a bad hash table is almost always one whose hash code was weak and whose compression then faithfully preserved the weakness.

What the hash code must achieve

The hash code's job is to turn "different key" into "different integer" as reliably as a deterministic function into 2^w values can, and to do so in a way that destroys the structure in the input. Real key sets are not random: identifiers in a program are i, j, n, tmp, ptr, pt, pts; file paths share long prefixes; timestamps are consecutive; record identifiers are consecutive and often a multiple of something. A code that preserves any of that structure hands it to the compression step, which will convert it into a systematic collision pattern. Three properties are wanted, and they are not the same property:

  • Determinism. Same key, same code, always, within one process's lifetime. This is a correctness requirement, not a quality one.
  • Uniformity. Over the key distribution you actually face, the codes should look spread out. Note the qualifier — uniformity is a joint property of the function and the input distribution, and is therefore not a property you can test once and rely on forever.
  • The avalanche property. Flipping one bit of the input should change roughly half the output bits, unpredictably. This is much stronger than uniformity and it is what makes a code robust to near-keys: "pt" and "pts", or ids 1000 and 1001, should not merely differ in their codes, they should differ everywhere in their codes. The reason it matters for tables specifically is that compression usually keeps a few bits of the code, and a code that concentrates its differences in the bits compression throws away is worthless. The low bits option in the figure of §01 keeps exactly those bits, so it is the setting that punishes a code with poor downward diffusion.

What the compression function must achieve, and the failure it must avoid

Compression must fold a wide integer into m values as evenly as possible, and its characteristic failure is preserving a periodicity. If the codes happen to be spaced d apart and m shares a factor with d, the folded values collapse onto a sublattice of the table and a large fraction of slots become unreachable. The clean worked case: codes 200, 205, 210, …, 595 — 80 values spaced 5 apart — compressed by c mod 100 land on only 20 distinct slots, four keys to a slot, so every code collides with exactly three others; compressed by c mod 101 they land on 80 distinct slots and collide not at all. Nothing changed but one in the divisor. That is the entire argument for choosing m prime, made precise in §07, and it is also the argument for randomising the compression when the codes are not under your control, which is §22.

Where the responsibility actually lands

A recurring practical confusion is which half to blame when a table performs badly. The test is cheap and worth naming: count the distinct hash codes, then count the distinct slots. If the codes themselves are already colliding — ten keys producing four codes — the key type's hash code is broken, and no table size will rescue it, because compression cannot separate integers that are already equal. If the codes are distinct and the slots are not, the fold is the problem, and the fixes are a different m, a different compression, or more slots. The figure in §01 prints both counts for exactly this reason. Its two settings are the two diagnoses side by side: the default polynomial code keeps all ten codes distinct and loses three keys to the fold — a compression collision — while the sum-of-characters code collapses ten keys to three codes before the table is even consulted, which is a code failure that no table can repair.

A widespread real-world design. Some library implementations counter a weak low-entropy hash code by mixing the code's high bits down into its low bits before masking — a cheap "finalisation" step applied by the table to whatever code the key type supplied. That is a table-side repair of a code-side weakness, and it is an admission that the seam described here leaks in one specific direction: the compression step is entitled to assume the code is good, and real codes often are not.

05 What makes a hash function good

"Good" is measurable, but only against a stated purpose, and hash functions are used for at least three purposes with incompatible requirements: filling a table evenly, fingerprinting data for equality or integrity, and resisting an adversary. A function that excels at one can be useless at another, and most confusion about hash functions comes from importing a criterion from the wrong column. This section fixes the criteria for the table-addressing job specifically — the job this page is about — and names the others so they can be told apart.

The three jobs, and why their criteria differ

  • Table addressing — this page. The output range is tiny (m slots), collisions are handled rather than fatal, and the function runs on the critical path of every single operation, so speed dominates. A function that collides once in a thousand on your keys is fine; the collision policy absorbs it. What is not fine is a systematic pattern, because a pattern makes many keys collide at once rather than a few at random.
  • Fingerprinting — deduplication, content addressing, change detection, the rolling hash of a substring matcher. Here the output range is large (64 to 256 bits), there is no collision policy, and a collision is a wrong answer rather than a slow one. The criterion is the birthday bound: with a b-bit fingerprint you can afford about 2^(b/2) items before a collision becomes likely, so 64 bits is comfortable at millions of items and uncomfortable at billions.
  • Adversarial resistance — any table whose keys come from outside the program. The criterion is not statistical at all: it is that no efficient adversary can produce colliding keys, which no fixed fast hash provides. The two real answers are a keyed hash with a per-process secret, and universal hashing, and they are the same answer wearing different clothes (§25).

The measurements that tell you whether a hash is spreading

Two numbers are worth computing on a real key set, and they catch different failures. The chi-square statistic on the bucket counts catches a global bias: sum (nⱼ − n/m)²/(n/m) over the slots, and compare against m − 1, which is the expectation under a uniform spread. A value near m means the spread is indistinguishable from random; a value several times m means the function is clumping. The longest chain catches a local one, and it carries a subtlety that is easy to get backwards: even a perfect random hash does not give a flat table. Throwing n keys into n slots leaves the busiest slot holding Θ(log n / log log n) keys in expectation. Be careful with that expression: it is a growth rate, not a value, and evaluating it literally gives 3.0 at n = 100 and 5.3 at n = 10⁶, while the expected maximum computed from the bucket distribution itself is 4.2 and 8.8 — the suppressed constants are not small at any n you will meet. So an observed maximum chain of 9 in a million-entry table is not evidence of a bad hash, it is what a good one produces; evidence of a bad hash looks like a maximum chain of 500. §11 and §12 compute those expected maxima and measure them. §10's figure measures both against their predictions, so the baseline is visible rather than assumed.

Cost is part of quality, and it is often the deciding part

The cheapest possible table hash for a machine word is a multiply and a shift; the strongest commonly used one costs tens of nanoseconds per key. Between them lie one or two orders of magnitude, and since every operation pays this cost, the choice can dominate the table's performance more than the collision policy does. The right way to think about it is a budget: a lookup costs (hash cost) + (probes) × (probe cost), and probes cost roughly a cache miss each at any interesting table size. A stronger hash is worth its cycles precisely when it removes probes — and past the point where the spread is already near-uniform it removes none, so additional strength buys only adversary resistance. That is a real thing to buy, and §25 explains when. It is not a speed improvement.

The claim to be suspicious of. "This hash function is good" is not a complete sentence. Good for which job, on which key distribution, against which adversary, at what cost per key? A function that is excellent for a symbol table of identifiers may be a poor fingerprint and is almost certainly not adversary-resistant.

06 The uniformity hypotheses — three different assumptions

Every expected-cost result on this page is conditional, and the conditions are not the same condition. Three distinct hypotheses circulate, they license different theorems, and the commonest error in this entire subject is proving a bound under one and quoting it under another. They are set out here, together, before any of them is used, so that each theorem later can name its own and be held to it.

H1: simple uniform hashing

The assumption is that h scatters keys like independent uniform draws: slot j is as likely as slot j′ for any key, and knowing where k landed tells you nothing about where k′ will land. It is a hypothesis about the pair (hash function, key distribution), and it is therefore not checkable in general — you rarely know the key distribution, and even when you do the keys may not be drawn independently. What it buys is the balls-in-bins model in full: the count nⱼ of keys in slot j is Binomial(n, 1/m), its expectation is exactly α = n/m, and every chaining result follows from that one fact by linearity of expectation. Note carefully what H1 does not say: it says nothing about probe sequences, so it cannot by itself justify a single open-addressing bound.

H2: uniform hashing

Open addressing needs more, because a key does not have a slot, it has an ordered list of slots to try. H2 upgrades the assumption from "one uniform draw per key" to "one uniform permutation of all m slots per key". This is a genuinely stronger statement — it implies H1 by looking only at the first probe, and it additionally promises that after i failed probes the next one is uniform over the m − i slots not yet examined, which is exactly the step the proof in §18 takes. The awkward truth is that H2 is false for every scheme anyone actually uses. Linear probing has m possible probe sequences, quadratic probing has m, double hashing has about m²; uniform hashing demands m!, which is astronomically more. So the probe theorems are a model, and the right way to read them is: this is how a perfectly randomised scheme would behave, and real schemes are compared against it. Double hashing comes close; linear probing does not, and has its own separate theorems because of it.

H3: universality — the one you can actually guarantee

The third is different in kind. H1 and H2 are assumptions about the world, unverifiable and falsifiable by an adversary who picks your keys. H3 is a property of a family of hash functions that can be proved once and for all, and it moves the randomness from the keys to the algorithm: pick h at random from the family when the table is created, and the collision probability bound holds for every fixed key set, including one chosen by an adversary who knows the family but not your draw. It is weaker than H1 in an important way — it only constrains pairs of keys, saying nothing about triples or about the shape of the whole distribution — and yet, remarkably, pairwise is all the chaining analysis ever uses, so H3 recovers the chaining bounds with no assumption about the keys at all. That is the content of §22, and it is the single most important idea on this page.

How to read every bound that follows

From here on, each cost claim is stated in the form (quantity, value, hypothesis), and the hypothesis is never omitted. The discipline matters because the six probe-cost formulas in §18 look interchangeable and are not. They come in three groups of two — a successful and an unsuccessful figure each. Two are theorems under H2; two hold under a different model specific to linear probing, in which the initial positions are uniform but the sequence is a fixed scan; and two are approximations under a secondary-clustering model for quadratic probing, not theorems at all. Quoting the uniform-hashing formula for linear probing understates linear probing's cost at high load by a factor that the figure there measures at over five. Use the wrong one and you will conclude that a 90%-full linear-probing table costs 10 probes on an unsuccessful search when it costs about 50.

07 The division method, and why m should be prime

The simplest compression is the remainder: h(k) = k mod m. One instruction on most machines, no tuning constants, defined for every key once the key is an integer. Its entire behaviour is governed by number theory rather than by intuition, and the governing fact is short enough to state exactly: the remainder map preserves any arithmetic structure in the keys whose step shares a factor with m. Choosing m prime is not a superstition or a rule of thumb — it is the choice that makes that shared factor impossible for every step except multiples of m itself.

Why "prime, and not near a power of two"

The primality half is the gcd argument above. The second half — avoid primes just above or below 2^p — guards against a different pattern. If the hash code is built by a polynomial in radix 2^b (which is what every byte-at-a-time string code is), then codes that differ by a shift or a character permutation differ by multiples of quantities close to powers of two, and a modulus close to a power of two folds those differences into a narrow band of slots. The specific pathological case is m = 2^p − 1 with a radix-2^p code: then 2^p ≡ 1 (mod m), so every positional weight in the polynomial collapses to 1 and the code reduces to the sum of the characters, making every anagram of a key collide with it. That is not a mild bias; it is an exact, constructible collision family, and it is the cleanest argument available that the modulus and the hash code must be chosen with knowledge of each other.

The honest case for powers of two

Despite all of the above, a great many high-performance tables use m = 2^p and mask instead of dividing, and it is worth saying why rather than treating it as a mistake. An integer division or remainder costs on the order of ten to forty cycles depending on the core generation, against one cycle for a bitwise AND; at small table sizes that difference is comparable to the entire rest of the lookup. The trade those implementations make is explicit: pay for a strong mixing step in the hash code, then mask. If the code has good avalanche, its low bits are as good as any other bits and the gcd argument has nothing to bite on, because the key's arithmetic structure was destroyed before compression saw it. The rule that emerges is a conditional, and it is the accurate form of the folklore: with a weak or identity-like hash code, use a prime modulus; with a strong avalanching code, a power of two and a mask is faster and equally good. 08 The multiplication method

The second classical construction multiplies rather than divides: scale the key by an irrational-looking constant, throw away the integer part, and read the slot off the fraction that remains. Its practical attraction is the mirror image of the division method's — here the value of m is not critical, so m can be a power of two and the whole computation becomes a multiply and a shift, with no division anywhere. The structure it destroys is different too: where the remainder rotates an arithmetic progression into a stride, multiplication scatters a progression across the table in a pattern with a provable spacing property.

Each step adds A mod 1 to the fraction and wraps, so the successive slots advance by 16 × 0.618 ≈ 9.9, landing about ten slots further on each time, modulo 16. That is the golden ratio doing its one trick, and it is worth stating what is and is not special about it. The three-distance property is not: for every irrational A, the first N points cut the unit interval into gaps of at most three distinct lengths. What the golden ratio adds is that those gaps stay close to equal. Because its continued fraction is all ones it is the worst-approximable irrational, so the sequence never settles into a short cycle and never clumps, and the ratio of the longest gap to the shortest never exceeds φ² ≈ 2.618 at any prefix length — a bound no other constant improves on. An A that is a good rational approximation, by contrast, still gives three gap lengths, but one of them is enormous and the table has a hole in it.

What the method does and does not buy

  • It buys freedom in m. This is the headline. Table sizes can be powers of two, so resizing is a doubling and compression is a shift — which removes the awkward business of keeping a table of primes around and dividing on every lookup.
  • It buys good behaviour on consecutive keys specifically. Sequential integer keys are extremely common — row ids, timestamps, counters — and this is exactly the pattern k mod 2^p handles worst for open addressing.
  • It does not buy adversary resistance. A is a fixed published constant, so an adversary can solve for keys that all land in one slot just as easily as with k mod m. Nothing with a fixed hash function resists an adversary; that requires §22.
  • It does not buy uniformity for all key distributions. The method is a heuristic, not a theorem. Keys whose low bits carry all the entropy, or keys that are themselves multiples of something near 2^w/s, can still clump. The constant matters: at A = 1/2 or 1/3 exactly, k·A mod 1 takes only two or three values and the whole table collapses to that many slots; at an A merely close to such a rational the collapse is not total but the points cluster in a few tight bands for a long initial run of k, which for the consecutive-key case that motivated the method is just as bad.

The modern descendant, and one honest caveat

The integer form above — multiply by an odd constant, take the high bits of the product — is the skeleton of nearly every fast mixing function in use today. Contemporary mixers iterate it: multiply by a large odd constant, exclusive-or the value with a shifted copy of itself, repeat two or three times, then take the top bits. The multiply provides diffusion from low bits upward, the shift-xor provides it downward, and alternating them gives avalanche in both directions, which a single multiply does not. The caveat worth stating plainly: taking the high bits of the product is not optional. A multiply moves entropy from the low bits of the input toward the high bits of the product, so the low bits of k·s depend only on the low bits of k — masking the product's low bits gives you back a disguised version of the division-by-power-of-two failure of §07. This is a good example of the fourth recurring error in systems reasoning: a plausible-sounding simplification that is exactly backwards.

09 Collisions are guaranteed — pigeonhole and the birthday bound

Two separate results say that collisions must be designed for rather than hoped away, and they say different things. The pigeonhole principle says collisions exist — for any fixed h, some slot receives many keys of the universe, and an adversary who knows h can find them. The birthday bound says collisions arrive early — even with a perfectly random hash and a table far larger than the number of keys, the first collision shows up after about √m insertions, not after m/2. The first result kills the hope of a collision-free fixed hash; the second kills the intuition that a sparse table is a collision-free one.

Pigeonhole: why no fixed hash function is safe

The counting argument is immediate — a function from a big set to a small one must repeat — but the useful version is the quantified one. With a universe of size |U| and m slots, some slot is the image of at least ceil(|U|/m) universe keys. For realistic universes this number is astronomically larger than any n you will ever store, which means that for any fixed hash function there exists a set of n keys that all land in one slot, turning every operation into a linear scan. This is not a hypothetical: it is the mechanism of a hash-flooding denial of service, in which an attacker submits form fields or JSON keys chosen to collide, and a server that expected O(n) total work does Θ(n²) instead (§25). The important structural point is that no analysis of the hash function fixes this, because the adversary gets to see the function and choose afterwards. The only repair is to make the function unknown to the adversary — randomly chosen per table or per process — which is exactly what universal hashing formalises.

The birthday bound: why sparse tables still collide

Assume the ideal — a perfectly random hash, hypothesis H1 in full. Insert keys one at a time. When the (i+1)-th key arrives, i slots are already spoken for, so it avoids all of them with probability (1 − i/m); multiplying over i = 1 … n−1 makes all n keys distinct with probability ∏(1 − i/m), which the bound 1 + x ≤ e^x compresses to e^(−n(n−1)/2m). Setting that to 1/2 gives n ≈ 1.1774·√m. The number to remember is √m, not m: a table of a million slots holding a mere twelve hundred keys — a load factor of 0.0012 — is already more likely than not to contain a collision. The pairs are what matter, and n keys make n(n−1)/2 pairs, so the pair count reaches m when n reaches roughly √(2m). Everything surprising about the birthday paradox is contained in the fact that people count keys and the mathematics counts pairs.

When does the first collision arrive? a Monte Carlo run of the real insertion process, against the exact expectation and the square-root approximation

Three independent numbers are printed and they agree: the simulated mean from running the real insertion loop until a slot repeats; the exact expectation ∑ₖ Pr[first k distinct] summed term by term with no approximation; and the closed form √(πm/2) + 2/3. Agreement of a Monte Carlo with an exact sum confirms the simulation; agreement of the exact sum with the closed form confirms the approximation. The histogram carries the part the mean hides — the distribution is broad and right-skewed, so "about √m" describes a typical run and individual runs vary by a factor of two either way. Push m to its maximum and watch the mean grow like √m, not like m: quadrupling the slots only doubles the wait.

The two results do not say the same thing

It is worth separating them, because they are often blurred into a single "collisions happen" and they have different consequences. Pigeonhole is adversarial and worst-case: it concerns a chosen key set, it applies with probability 1, and it is defeated only by randomising the hash function. The birthday bound is probabilistic and typical-case: it concerns random keys, it says nothing about an adversary, and it is not defeated by anything — randomising the hash does not make random keys collide any less. For table design the birthday bound is reassuring rather than alarming, because a collision in a hash table merely costs a probe; it is the fingerprinting job of §05, where a collision is a wrong answer, that has to size its output by 2^(b/2) and take the bound as a hard constraint.

10 Chaining: put the collisions in a list

The first collision policy is the obvious one. If two keys want slot j, let them both have it: slot j holds not an entry but a bucket — a container of all entries whose key hashes to j. The container is classically a singly linked list, whose node mechanics are exactly those set out in Linked Lists, Stacks & Queues, and which is where the name comes from. The scheme's virtues are that it is short, that it is correct without any special cases, that deletion is genuinely easy, and that n may exceed m without the structure breaking. Its cost is one pointer indirection per bucket and one allocation per entry.

The unsuccessful-search theorem, proved

Search for a key k that is not present. Under H1, k is equally likely to hash to any slot, so the bucket it lands in is a uniformly chosen one, and the search must walk that bucket to its end — an unsuccessful search cannot stop early, because any of the remaining entries could still be the one. The expected number of entries examined is therefore E[n_h(k)] = α, by definition of the mean bucket length. Adding the O(1) to compute the hash and index the array gives Θ(1 + α). The 1 + is not cosmetic: at α = 0 the cost is one hash computation and one array access, not zero, and writing the bound as Θ(α) would wrongly claim an empty table costs nothing.

What chaining buys, itemised

  • Deletion is trivial and complete. Unlink the node and it is gone — no marker, no residue, no effect on any other key's search path. This single property is the reason chaining is the default recommendation whenever deletion is a normal part of the workload, and §19 shows in detail what open addressing has to do instead.
  • α > 1 is legal. The table degrades smoothly rather than failing: at α = 4 a search examines about four entries. There is no wall. Open addressing has a hard wall at α = 1 and a soft one well before it.
  • The bucket can be any map. Nothing requires a list. A bucket that grows past a threshold can be replaced by a balanced tree, converting the worst case for that bucket from Θ(nⱼ) to O(log nⱼ) — which is what "treeified buckets" means in §25, and it is a defence against adversarial collisions rather than an optimisation of the common case.
  • Insert is O(1) worst case — if you skip the uniqueness check. Prepending a node is two writes. But a map must not store a duplicate key, so a correct put searches the bucket first and therefore costs what a search costs. Implementations that advertise O(1) worst-case insertion are describing a multimap, or are assuming the caller has already checked.

What it costs, in memory and in cache

Every entry carries at least one link, and every entry is a separate allocation, so chaining pays the node overhead derived in Linked Lists §03 — a link word per entry, allocator grain rounding, and nodes that may land anywhere in the heap. A bucket walk is a pointer chase, so a chain of length 3 can mean three cache misses where an open-addressed table would have made one. This is the real reason open addressing is preferred in performance-critical libraries despite its harder deletion story: at low load factors an open-addressed lookup touches one or two cache lines and a chained one touches two or three, and at modern memory latencies that ratio is the whole performance difference. The asymptotics are identical; the constant is not.

11 The load factor α — what it controls and what it does not

α = n/m is the single number that summarises how hard a table is being pushed, and it appears in every cost formula on this page. The two families have qualitatively different relationships with α

For chaining, cost is linear in α: doubling the load doubles the mean bucket walk, and there is no value of α at which anything special happens. For open addressing, cost is hyperbolic in α: the 1/(1−α) term is nearly flat until the table is about two-thirds full and then climbs without bound. The numbers make the asymmetry concrete — under uniform hashing (H2), which is the hypothesis that 1/(1−α) belongs to and which only double hashing comes close to satisfying — an unsuccessful search costs 2 probes at α = 0.5, 10 at 0.9, 100 at 0.99, and at α = 1 it does not terminate until it has scanned all m slots. Linear probing's own theorem is worse at every one of those loads (2.5, 50.5, 5 000.5), and quoting the 1/(1−α) row for it is the error §18 is built around. Chaining at those same loads costs 0.5, 0.9 and 0.99 entries examined. This is why the two families have different conventional thresholds (§25) and why "keep the load factor below 0.75" is meaningless advice until you say which family it is about.

Why α says nothing about the longest bucket

This is the single most useful corrective in the section. Set m = n, so α = 1 and the mean bucket length is exactly 1. The maximum bucket length is not 1, and it does not stay bounded: under H1 it is Θ(log n / log log n) with high probability. The asymptotic shape is what that statement pins down; the actual expected maximum, computed from the bucket distribution rather than from the asymptotic form, is about 4.2 at a hundred entries, 5.5 at a thousand, 8.8 at a million and 11.6 at a billion. Slowly growing, but growing, and unbounded — and note that the bare log n / log log n expression evaluates to about 5.3 at a million, so it captures the growth rate and not the value, which is exactly what Θ claims and no more. The consequence for engineering is that a hash table's tail latency is not governed by its load factor. If your service has a p99.9 latency budget, the mean-cost theorems on this page do not speak to it; the maximum-load result does, and it says the tail creeps upward with n no matter how much memory you spend on slots. The figure in §12 measures the maximum alongside the mean so the gap between them is visible rather than theoretical.

Choosing a target

  • Chaining tolerates a high α. Thresholds near 0.75 to 1 are common, and analyses support holding α below about 0.9; past that the linear growth is still gentle but the memory saved is small compared with the node overhead you are already paying.
  • Open addressing needs a low one. Linear probing degrades fastest and is usually held below about 0.5; other probing schemes tolerate somewhat more, and implementations using thresholds around two-thirds are common. §18 measures where each curve turns up so the choice can be made from the graph rather than from a remembered constant.
  • The threshold is a memory-versus-time dial, and it is not linear on either axis. Going from α = 0.9 to 0.45 doubles the memory and, for linear probing, cuts the expected unsuccessful probe count from 50.5 to 2.15. Going from 0.45 to 0.225 doubles the memory again and takes it to 1.33 — a saving of 0.8 probes against the first halving's 48.3. Almost all of the benefit is in the first halving.
  • α must be maintained, not merely chosen. A table that is sized once and then filled has a load factor that rises to whatever the data dictates. Keeping α bounded requires resizing, which is §20.

12 What chaining really costs, measured

The two theorems of §10 predict means. The distribution, not the mean

Throwing n keys independently into m slots makes each bucket's occupancy a Binomial(n, 1/m) variable, which for large m and fixed α is Poisson with parameter α. That single fact explains several things at once that are otherwise folklore. At α = 1 — the setting that sounds like "perfectly packed" — about e⁻¹ ≈ 37% of slots are empty and about 26% hold two or more keys. The array is not neatly one-per-slot and never will be; it is patchy, and the patchiness is intrinsic to randomness rather than a defect in the hash function. This is why a chained table sized m = n wastes about a third of its slot array, and it is a large part of why open addressing, which cannot tolerate that waste in the same way, runs at lower load factors.

Raise α and both grow, at different rates, and the ratio between them is the tail-latency risk that the Θ(1 + α) bound is silent about. Reading the maximum correctly

The maximum bucket is the quantity most often misread as evidence about the hash function, in both directions. A longest bucket of 9 in a table of a million entries at α = 1 is exactly what a perfect hash function produces — the expected maximum computed from the bucket distribution is 8.79 — and the figure prints the measured and the predicted maximum side by side so they can be compared at whatever n and m you choose. Concluding "the hash is bad" from such an observation is a mistake; so is concluding "the hash is fine" from a mean that looks right while the maximum is 500. The correct test is the comparison the figure makes: measure the maximum, compute what a uniform hash would give at this n and m, and look at the ratio. A factor of two is noise; a factor of fifty is a broken hash function or an adversary, and the two are distinguished only by asking where the keys came from.

13 Open addressing: go and find another slot

The second collision policy refuses the auxiliary structure entirely. Every entry lives in the bucket array itself, one entry per slot. If a key's first slot is taken, the key does not get a list — it gets a probe sequence, an ordered list of alternative slots to try, determined by the key. Insertion walks the sequence until it finds an empty slot; search walks the same sequence until it finds the key or an empty slot. That last clause is the entire design: an empty slot means "not here", and it is the only thing that stops a search. Everything difficult about open addressing, and all of §19, is a consequence of that one sentence.

Why the probe sequence must be a permutation

If the sequence repeats a slot or omits one, a key can be turned away from a table that still has empty slots. That is not merely inefficient, it is a correctness failure of the container: put reports "full" when it is not. Every scheme in the next three sections is therefore judged first on whether it generates a permutation and only then on how fast it is. Linear probing generates a permutation unconditionally, double hashing whenever gcd(h₂(k), m) = 1; plain quadratic probing does not, and §15 is largely about what to do about that. Note the subtlety in the insert loop above: it also stops when it finds the key itself, which is what enforces the map's uniqueness invariant, and it must do that before deciding the key is absent — a probe sequence that found an occupied non-matching slot has learned nothing and must continue.

What open addressing buys

  • No per-entry allocation and no link words. The entire structure is one array. For an 8-byte key and an 8-byte value at α = 0.5, open addressing uses 32 bytes per stored entry; chaining uses 16 bytes of array slot plus a node of key, value, link and allocator overhead — typically 40 or more bytes per entry, plus a second dereference to reach any of it.
  • Locality. A linear-probing lookup reads consecutive slots, which is the best possible access pattern for a cache: a probe sequence of four may be four reads inside one 64-byte cache line, costing one memory transaction rather than four. This is the property that outweighs everything else in practice at low load factors, and it is specific to linear probing — double hashing's probes are scattered and pay a miss each, which is a real and often-forgotten cost of its better probe count.
  • Predictable memory. No allocator on the hot path means no allocation failure mid-insert, no fragmentation, and a footprint you can compute from m alone. That matters in embedded and real-time settings more than any asymptotic argument.

What it costs

  • A hard ceiling at α = 1, and a soft one well below. Cost is hyperbolic in α, so the table must be resized earlier and kept emptier than a chained one. The memory saved per entry is partly given back as unused slots.
  • Deletion is genuinely hard. This is the dominant practical objection, and it is not a small implementation wrinkle — it changes the cost model. Once a table uses deletion markers, the probe-count theorems of §18 no longer apply, because search cost stops depending on α and starts depending on the history of insertions and deletions. A table that has churned can be slow while looking almost empty.
  • Clustering. Occupied slots are not independent: they gang up into runs, and the runs make themselves longer. §14 makes that mechanism visible and §17 compares its severity across the three schemes.
The rule of thumb, with its condition attached. Open addressing wins when entries are small, deletions are rare or absent, and the load factor is kept modest; chaining wins when entries are large, deletions are frequent, or the load factor must be allowed to climb. The two are not ranked — they are suited to different workloads, and the deletion question decides it more often than the speed question does.

14 Linear probing and primary clustering

The simplest probe sequence is "try the next slot": h(k,i) = (h′(k) + i) mod m. It is a permutation for every m and every h′ with no conditions at all, it needs no second hash function, and its memory access pattern is a forward scan, which is the fastest thing a processor can do. It also has the worst clustering behaviour of any scheme here, for a reason that is precise and worth understanding rather than memorising: an empty slot preceded by a run of i occupied slots is (i+1)/m likely to be filled next, so long runs grow faster than short ones and the distribution of run lengths becomes heavy-tailed.

Why the two linear-probing formulas are different from everything else

The formulas quoted above are not the uniform-hashing formulas of §18, and substituting one for the other is the classic error this page is most at risk of. Uniform hashing assumes each key gets an independent random permutation; linear probing gives each key a fixed scan from a random start, so the occupancies of adjacent slots are strongly positively correlated and the independence the uniform-hashing proof uses is simply absent. The consequence is quantitative and large: at α = 0.9 uniform hashing predicts 10 probes for an unsuccessful search and linear probing costs about 50. The successful-search figures are much closer (2.56 against 5.5), because a successful search stops at the key rather than at the end of a run. Both formulas are asymptotic in m, and the approach to them is slow: the figure in §18 measures 42.9 probes at m = 1009 against the predicted 50.5, and 50.1 at m = 8009. The figure in §18 uses tables of several thousand slots for exactly this reason.

What rescues linear probing in practice

Given all of that, linear probing remains extremely widely used, and the reason is the one asymptotics cannot see. Its probes are sequential memory reads. A run of eight 16-byte entries occupies two cache lines, so eight probes can cost two memory transactions where double hashing's eight scattered probes cost eight. If a probe is counted as "a memory access" the comparison favours double hashing; if it is counted as "a cache miss" — which is what actually takes time — linear probing wins at moderate load and keeps winning until the runs get long. The engineering conclusion is a conditional, not a ranking: linear probing below about α = 0.5 is usually the fastest scheme in wall-clock terms, and above about 0.7 it degrades faster than anything else on this page. (That is a statement about time, not probes — the one place this page steps outside §01's probe-count cost model, and it rests on the cache argument above, not on the formulas.) Two further repairs change the picture again — Robin Hood reordering, which evens out the run occupancy without changing the probe pattern, and a strong hash, which is what keeps the starting slots genuinely uniform in the first place.

15 Quadratic probing, secondary clustering, and the half-table condition

Quadratic probing keeps linear probing's single hash function but accelerates away from the home slot: h(k,i) = (h′(k) + c₁·i + c₂·i²) mod m. The acceleration is what defeats primary clustering — two keys with different home slots separate after one step instead of queueing — and it costs two things. Keys with the same home slot still follow an identical sequence, which is secondary clustering; and, in the plain form c₁ = 0, c₂ = 1, the probe sequence is not a permutation of the table. For m an odd prime it reaches exactly ceil(m/2) slots and no more. A prime is the guaranteed case, not the best one: for composite m the reachable count is erratic — a few composites do slightly better (i² mod 6 takes four values, i² mod 10 six) but many do far worse (i² mod 16 takes only four values, not eight; i² mod 12 also four) — which is why plain quadratic probing is quoted with a prime modulus or not at all. Either way the scheme carries a load-factor condition that the other two do not.

What the half-table condition actually says — and what it does not

This is a boundary worth stating carefully, because it is routinely reported as both stronger and weaker than it is. The theorem is a guarantee, not a description of typical behaviour: below α = 1/2, insertion cannot fail; at or above it, insertion may fail, and whether it does depends on which slots happen to be occupied. Those are different claims and both halves matter. The figure of §14 demonstrates the failure concretely: eleven slots, ten keys all with home slot 4, and the plain quadratic sequence reaches only the six slots {4, 5, 8, 2, 9, 7} — that is ceil(11/2) = 6, exactly as the theorem predicts — so the seventh key onward is refused while five slots sit empty. But the same scheme fed random keys fails far less readily, because a failure needs every one of the ceil(m/2) reachable slots to be occupied simultaneously, which random occupancy makes very unlikely until the table is nearly full. The sweep in §17 measures the failure count directly at each load factor, so the gap between "not guaranteed" and "actually fails" is a number rather than an impression.

Secondary clustering, and why it is the milder disease

Secondary clustering is the residue that quadratic probing cannot remove: two keys that land on the same home slot are condemned to the same probe sequence, so they collide at every step, not just the first. Compare the two mechanisms directly. Primary clustering merges keys with different home slots into shared runs, so the number of keys competing for a slot grows with the size of the run, which grows with the table's history. Secondary clustering only affects keys with identical home slots, and the number of those is governed by the hash function and the load factor, not by the table's shape. That is why the damage is bounded in a way primary clustering's is not: under a good hash, only about α keys share any given home slot on average, whereas a primary cluster can be tens of slots long. The measured probe counts in §18 put numbers on "milder": at α = 0.9 an unsuccessful search costs about 50 probes under linear probing and about 11 under quadratic.

The practical verdict

Quadratic probing occupies an awkward middle position and is, in current practice, the least used of the three. It needs only one hash function (cheaper than double hashing), it removes primary clustering (better than linear probing), and it keeps some locality for the first few probes since the offsets 1, 4, 9 are small. Against that: the reachability condition forces a low load factor or a non-obvious variant, the parameters c₁, c₂ and m are coupled and easy to choose wrongly, and its probes scatter after the first few, so it loses linear probing's cache advantage without gaining double hashing's probe-count advantage. If you want the middle ground in practice, the modern answer is usually Robin Hood linear probing rather than a quadratic sequence.

16 Double hashing and the coprimality requirement

Double hashing makes the step depend on the key as well as the start: h(k,i) = (h₁(k) + i·h₂(k)) mod m. Two keys now differ in where they begin and in how far they jump, so two keys that collide on their first probe almost certainly diverge on the second — there is neither primary nor secondary clustering. It generates about m² distinct probe sequences against the other schemes' m, which is why its measured behaviour tracks the idealised uniform-hashing model so closely. The price is a second hash computation per key, scattered memory accesses, and one hard requirement that is easy to violate and fails silently: h₂(k) must be coprime with m.

Where double hashing stands

  • It is the closest practical approximation to uniform hashing. With Θ(m²) sequences instead of m, its measured probe counts sit almost exactly on the 1/(1−α) and (1/α)·ln(1/(1−α)) curves, which §18 verifies. Neither of the other two schemes does.
  • It tolerates a higher load factor than the others. Because the curve it follows is the gentlest of the three, it remains usable at loads where linear probing has collapsed.
  • It pays for that in cache behaviour. Each probe is a jump of h₂(k) slots, which at any realistic table size is a different cache line and often a different page. Five probes means five misses. Linear probing's five probes may mean one. Counting probes ranks double hashing first; counting memory transactions often does not.
  • It costs a second hash. Usually cheap — the second hash can be derived from spare bits of the first, provided the derivation is guaranteed to produce a value coprime with m, which forcing the low bit to 1 does for a power-of-two table.

The consequence for cost, stated carefully

It is tempting to convert cluster lengths directly into probe counts, and the conversion is not quite that simple. A search's cost is not the length of the run it lands in; it is the distance from its home slot to the end of the run, which is on average about half the run for a uniformly placed home — and because longer runs are also more likely to be landed in, the expected cost involves the second moment of the run-length distribution, not the mean. That is the technical reason linear probing's unsuccessful-search cost contains 1/(1−α)² where uniform hashing has 1/(1−α): squaring is what a second moment does. It is also why the long tail of the run distribution matters so much more than its mean, and why the three schemes' probe counts diverge faster than their mean run lengths do.

How to hold the three groups apart

  • Match the hypothesis to the scheme, not to the formula you remember. If the scheme is double hashing, Group A is the right family and the measurement confirms it. If the scheme is linear probing, Group A is wrong and Group B is right. If the scheme is quadratic probing, Group C is right and is an approximation rather than a theorem.
  • Unsuccessful is always worse than successful, in every group. An unsuccessful search runs to an empty slot; a successful one stops at its key. Any formula pair in which the unsuccessful figure is the smaller one has been transcribed the wrong way round — the two Group B formulas are the pair most often swapped, because they differ only by a squared denominator.
  • An insertion costs what an unsuccessful search costs. Insertion must first establish that the key is absent, so it walks the same sequence to the same empty slot. This is why a table's build cost is governed by the unsuccessful formula, and why filling a linear-probing table to α = 0.9 is so expensive.
  • All of them assume no deletion markers. Every formula here is derived for a table built by insertions alone. §19 explains why a table that has seen deletions obeys none of them.

19 Deletion, the broken probe chain, and the tombstone

In a chained table, deletion unlinks a node and the structure is exactly as it would have been had the key never arrived. In an open-addressed table, you cannot simply empty the slot. A search stops at the first empty slot it meets, so emptying a slot in the middle of a probe path tells every key beyond it on that path that it is absent. The entry is still there, still occupying memory, and permanently unreachable. This is the single sharpest edge in the whole subject, it is easy to write and impossible to notice in testing until the table is dense enough for probe paths to be long, and the standard repair — a tombstone (the textbook name for the technique is lazy deletion) — fixes correctness at the cost of a cost model.

Why the tombstone changes the cost model, not just the cost

Every probe-count theorem in §18 is derived for a table built by insertions alone, where a slot is empty if and only if no key is stored there. Once tombstones exist, that equivalence breaks, and the quantity governing search cost is α_eff = (occupied + tombstones)/m. Two facts follow and both are unpleasant. First, α_eff is monotone non-decreasing between rebuilds: an insertion can consume a tombstone, but a deletion always creates one, so a workload with equal inserts and deletes drifts upward and never recovers. Second, the load factor you can measure — n/m — stops predicting anything. A cache holding a steady thousand entries in a table of ten thousand slots reports α = 0.1 and, after a few hundred thousand insert/delete cycles, can be probing dozens of slots per lookup because the other nine thousand are tombstones. The symptom is a table that gets slower over time at constant size, which is a mystery until you know to look for it.

The repairs, and what each costs

  • Rehash on a tombstone threshold. Track tombstones and rebuild the table when α_eff exceeds a bound, even if n has not grown — often into a table of the same size. This is the standard fix, it costs a Θ(m) pass, and it amortises exactly as a resize does (§20). The threshold must be on α_eff, not on n/m; a table that only resizes when n grows will never clean itself.
  • Backward-shift deletion, for linear probing only. Instead of a marker, shift subsequent entries in the run backwards into the hole, stopping when a key is reached whose home slot would be passed. This restores the no-tombstone invariant exactly and keeps the table's statistics identical to a never-deleted one — the cleanest solution available, at the cost of a deletion that is O(run length) rather than O(1), and of code that is genuinely fiddly to get right. It does not generalise to quadratic or double probing, because there is no "subsequent entry in the run" when probes jump.
  • Use chaining. The honest option. If a workload deletes heavily, the whole tombstone apparatus — the third slot state, the remembered-tombstone insert rule, the α_eff accounting, the cleanup threshold — is machinery that a chained table does not need. This is the single most common reason to choose chaining.

The two additions that are specific to hash tables

  • Tombstones must be counted in the resize trigger.   • The new size is not always 2m. A prime-modulus table must jump to the next prime at least 2m, which is why implementations of that style carry a table of primes. What amortization does not buy

The tallest spike in the figure is the cost of the last rehash, and it is Θ(m). Amortized O(1) says the total is linear; it says nothing about any individual operation, and the individual operation that triggers a rehash of a million-entry table will take milliseconds. For a batch program that is invisible. For an interactive system, a game loop, an audio callback or anything with a latency budget, it is a stall — and it arrives at the least convenient moment, since the table rehashes precisely when it is busiest. That is the entire motivation for §21. It is also a general lesson worth carrying beyond hash tables: amortized analysis is a statement about throughput, and it is silent about tail latency by construction.

The stop-the-world rehash of §20 is cheap on average and terrible at the tail. Why k has a lower bound, and what happens below it

This is the detail most often left out, and it is the one that decides whether the scheme works. Migration must finish before the new table itself needs to grow, or the structure ends up with three live tables and then four. Between two resizes the table absorbs about (1 − 1/g)·α_max·m′ = (g−1)·α_max·m new insertions; migration must move about α_max·m entries in that time, and each insertion moves k. Dividing, the α_max cancels and the requirement is simply k ≥ 1/(g−1) — the load-factor threshold does not enter it at all, which is worth noticing because it is often quoted as though it did. With doubling that is k ≥ 1, and the awkward part is that it is an equality: at k = 1 the migration finishes at exactly the moment the next resize fires, with no margin for the rounding, the deletions and the resizes-of-a-resize that a real implementation has. Count the same budget in slots scanned rather than entries moved — which is what the cursor actually does, since it must walk the empty slots too — and the requirement becomes k ≥ 1/((g−1)·α_max) = 1.33. So moving two per operation is safe and moving one is not, and "one per operation" is exactly the value a first implementation reaches for. The failure it produces is slow and confusing: the table appears to work, memory use creeps, and lookups get gradually slower because they are searching an ever-growing stack of half-migrated tables.

Lazy variants, and where each is used

  • Migrate on touch. Instead of a cursor, move an entry only when an operation happens to find it in the old table. Simple and self-tuning for skewed workloads, but entries that are never touched are never migrated, so the old table can persist indefinitely — and the memory it holds with it. Usually combined with a cursor to guarantee completion.
  • Generational / two-table lookup. Formalise the pair as a permanent design: a small "new" table absorbing writes and a large "old" one being drained. Lookups check both. This is the same idea as the memory-table-plus-file layering in a log-structured store, and it has the same trade — cheap writes, more expensive reads.
  • Chunked rehash on a background thread. Moves the work off the critical path entirely, at the price of needing every operation to be safe against concurrent migration. This is a concurrency problem rather than a data-structure one, and it is where most of the difficulty of concurrent hash tables lives.
  • Don't resize at all. If the maximum entry count is known ahead of time, size the table once, for that count at the target load factor, and the entire section is unnecessary. This is the correct answer far more often than it is used, and it is the only one that removes the Θ(m) rehash stall entirely. It does not, of course, touch the Θ(n) adversarial worst case of §09 — a probe path is bounded by the table's contents, not by its size policy.

Why pairwise is enough

Universality is a strictly weaker property than simple uniform hashing: it constrains only pairs of keys, and says nothing about whether three keys land independently or whether the induced distribution on slots is anywhere near uniform. It would be reasonable to expect that to be too weak to recover the chaining bounds — and it is not, for a specific and instructive reason. Look back at the proof in §10: the only probabilistic fact it ever uses is E[Xᵢⱼ] = Pr[h(kᵢ) = h(kⱼ)] = 1/m for a pair, and then linearity of expectation does all the rest. Linearity of expectation does not require independence. So replacing the equality = 1/m by the inequality ≤ 1/m carries the entire argument through unchanged, with = becoming ≤ in the conclusion. That is why the pairwise definition is the right one: it is exactly as strong as the analysis needs and no stronger, which makes it cheap to satisfy.

What universal hashing does and does not promise

  • It does not make the worst case go away. A particular draw can still be unlucky, and a table can still degrade. What changes is who chooses: bad performance now requires the algorithm's own coin flips to come up badly, which happens with small probability and independently of the input, rather than requiring an adversary to have a bad day.
  • It guarantees nothing if the draw is reused or leaked. The parameters must be drawn fresh — per process at least, and per table ideally — and must not be recoverable from observable behaviour. An attacker who can time lookups precisely enough can in principle learn about the hash, and the practical form of this arms race is §25.
  • The stronger relatives, and a distinction worth keeping. A family is k-independent (k-wise independent) if any k distinct keys are mapped independently and uniformly. Strongly 2-universal is the exact-uniform pairwise version, Pr[h(k)=i ∧ h(k′)=j] = 1/m², and is the same thing as 2-independence. Plain universal — sometimes written 2-universal, which is why the two get confused — is strictly weaker: it bounds only the collision probability and says nothing about the marginals. The family above is on the weak side of that line, and precisely so: (a·k + b) mod p alone is 2-independent over {0…p−1} when a ranges over all of {0…p−1} (with a ≠ 0, as the family above is defined, step 2 of the proof shows it is uniform over distinct pairs only — a pair can never land on the same residue), but the second fold mod m destroys it, because m does not divide p and so the m slots do not receive equal numbers of residues. What survives the fold is universality — the ≤ 1/m collision bound proved above — and that is all the chaining analysis needed. Some analyses — notably of linear probing — genuinely need more than pairwise independence: 5-independence is known to suffice for linear probing's expected constant cost, and some 2-independent families provably make it fail (expected cost Θ(log n) on adversarial key sets) — a real caveat on applying this section's guarantee to §14's scheme rather than to chaining.
  • It costs almost nothing. One integer multiplication, one addition and two remainders. The multiply-shift relative — odd a, take the top p bits of a·k mod 2^w — is a multiply and a shift, and is universal up to a factor of two (collision probability ≤ 2/m, "almost-universal") rather than ≤ 1/m. The same machinery is the MAD compression of §04, which is why that construction looked arbitrary there and does not here.

23 Perfect hashing: O(1) worst case, for a static key set

Every bound on this page has been an expectation, and the worst case has been Θ(n) throughout. There is one setting in which that can be fixed completely: when the key set is static — fixed, known in advance, never inserted into again. Reserved words in a compiler, opcodes in an interpreter, country codes, the field names of a wire format, the vertices of a fixed graph. For such a set you can afford to search for a hash function that collides on none of your keys, and then every lookup is one probe, guaranteed, with no hypothesis at all. The construction that makes this affordable in O(n) space is two-level, and it is a small masterpiece.

Why the squares are affordable

The construction looks as though it should explode. Each bucket's secondary table is quadratic in its own occupancy, and §12 established that the largest bucket at α = 1 holds Θ(log n / log log n) keys — so the biggest secondary table has tens of slots. The reason the total stays linear is that ∑nⱼ² counts something concrete: it is n plus twice the number of colliding pairs, and under a universal family the expected number of colliding pairs at m = n is only (n−1)/2. Most buckets hold zero or one key and contribute zero or one to the sum; the rare bucket holding five contributes 25, and there are few enough of those that the total still averages under 2n. Squaring a distribution that is overwhelmingly zeros and ones is cheap; it is only expensive if the distribution has mass in the tail, and Poisson(1) does not.

The two randomised searches, and the Markov argument that bounds them

Both levels use the same trick: compute the expectation, then use Markov's inequality — for a non-negative random variable, Pr[X ≥ t] ≤ E[X]/t — to argue that the realised value exceeds twice its expectation less than half the time, so redrawing succeeds after an expected two attempts. At the second level, the expected number of collisions in a table of size nⱼ² is under 1/2, so a draw is collision-free with probability over 1/2. At the first level, E[∑nⱼ²] < 2n, so Pr[∑nⱼ² ≥ 4n] < 1/2 and a draw gives linear total space with probability over 1/2. Both searches are Las Vegas: the answer is always correct and only the running time is random, which is exactly the property you want when the result is going to be baked into a program and used for years. Construction is therefore O(n) in expectation, and since it happens once, offline, even a much worse construction time would be acceptable.

Where this actually shows up

  • Compiler and interpreter keyword tables. The set of reserved words is fixed at language-design time, and generators that emit a perfect hash function for such a set are a standard build-time tool. The payoff is not only speed but determinism: no probe loop, no load factor, no resize, no adversary.
  • Minimal perfect hashing. A refinement that maps n keys onto exactly n slots with no gaps, giving an ideal-density lookup table. Modern constructions reach a few bits of auxiliary storage per key. This is the machinery behind compact static dictionaries, immutable key-value bundles shipped inside binaries, and index structures over fixed vocabularies.
  • The conceptual payoff. Perfect hashing is the proof that the Θ(n) worst case elsewhere on this page is not intrinsic to hashing — it is the price of supporting insertion. Once the key set stops changing, the price disappears. That framing is worth keeping: the dynamic-versus-static distinction buys more here than almost anywhere else in data structures.

24 Robin Hood, cuckoo and hopscotch

The three classical probe schemes all share one assumption: once an entry is placed, it stays where it was placed. Insertion is the only thing that searches, and it searches only for an empty slot. Dropping that assumption — allowing an insertion to move entries already in the table — produces a family of schemes with strikingly better worst-case behaviour, because moving entries is how you convert a long probe path for one key into two short ones for two keys. All three below are variations on that single idea, and all three trade a more expensive insertion for a cheaper and much more predictable lookup.

Robin Hood, and the early exit that is its real prize

The swapping rule is easy to state and its consequence is not obvious. Standard linear probing gives a lucky key a PSL of 0 and an unlucky one a PSL of 40; Robin Hood redistributes so that both sit near the mean. The mean is unchanged — for linear probing the set of occupied slots, and hence the total displacement, is the same whatever order the keys arrive in and whichever key gets which slot inside a cluster — so this is purely a variance reduction. But it produces a second property for free that is worth more than the first, and it is worth stating the property exactly, because the usual short form of it is wrong. The invariant is that home slots are non-decreasing along a run, not that PSLs are: homes 5, 5, 7 sitting at slots 5, 6, 7 is a state Robin Hood reaches by its own rules, and its PSLs read 0, 1, 0. What the home-slot ordering buys is the early exit. Arriving at slot j with probe count d, the resident's PSL is j − home(resident) and ours would be d = j − home(ours), so resident's PSL smaller is exactly resident's home later than ours — and since homes only increase from here, every remaining slot in the run belongs to a key homed after us. Our key is not there, and the search stops. That makes an unsuccessful search cost about what a successful one costs, which none of the three classical probe schemes manages (all three of §18's groups have unsuccessful cost above successful), and unsuccessful searches are the frequent case in most real workloads. Robin Hood is the reason a linear-probing table can be run at a high load factor and still have a usable tail latency.

Cuckoo hashing, and the shape of its failure

Cuckoo hashing gives a genuine O(1) worst-case lookup for a dynamic key set: at most two probes, always, because a key can only ever be in two places. Hopscotch shares that property (at most H probes, by its neighbourhood invariant), and perfect hashing gives it for a static set; none of the three classical probe schemes does. That makes it the natural choice when lookups must be bounded rather than merely fast on average — hardware tables, packet-forwarding lookups, anything with a fixed cycle budget. Deletion is also clean: empty the slot, no tombstone, because a key's two homes are fixed and a search never depends on what lies between them. The cost is concentrated entirely in insertion, whose behaviour changes character at a threshold: below it, the eviction chain is short with high probability; above it, the chain diverges and the insertion must be abandoned and the whole table rehashed with fresh functions. For two tables and one slot each the threshold sits near α = 0.5; using more hash functions or letting each slot hold several entries raises it substantially, and practical variants run comfortably above 0.9. The trade to remember is that cuckoo hashing moves all of the uncertainty from lookup to insertion, and then bounds it with a rebuild.

Hopscotch, and why bitmaps beat probes

Hopscotch starts from the observation that a probe is expensive mainly because it may be a cache miss, so the right thing to bound is not the number of probes but the address range they cover. It guarantees every key sits within H slots of its home and stores, alongside each home slot, a bitmap of which of those H positions actually hold keys homed there. A lookup reads the bitmap and probes only the marked slots — typically one or two, all inside the same cache line or two. The clever part is insertion: when the neighbourhood is full, find any empty slot further away and then walk it backwards, repeatedly swapping it with a key that can legally move forward into it, until the empty slot has been dragged into range. That backward walk is the same idea as Robin Hood's swapping, applied to a different invariant. Hopscotch is also unusually friendly to concurrency, since the neighbourhood is a small, lockable region.

What to take from all three

The classical schemes optimise the mean and accept a long tail. These three all spend extra work at insertion time to buy a short tail, and they are the right frame for understanding modern high-performance tables, which mix these ideas with layout tricks — storing a one-byte hash fingerprint per slot in a separate metadata array so a group of slots can be filtered with a single SIMD comparison before any key is touched, and probing group by group rather than slot by slot. The general pattern is the same one the cache discussion of §13 set up: once a probe costs a cache miss, the winning design is the one that answers the question with the fewest cache lines, not the fewest probes, and metadata bytes are cheap because hundreds of them fit in a line.

25 Hash tables in practice

Library implementations diverge from the textbook in a few consistent ways, and each divergence is a response to a specific problem this page has raised. This section names the patterns that recur across widely used implementations. Where a specific numeric constant is quoted it is a documented property of a particular implementation and not a general law, and it is flagged as such — the general practice is what transfers, not the number.

Randomised seeds and hash flooding

§09's pigeonhole argument is not a theoretical concern; it was weaponised. A server that builds a hash table out of attacker-controlled strings — query parameters, form fields, JSON object keys, HTTP headers — can be handed a few thousand keys chosen to collide under its language's published hash function, turning an O(n) parse into a Θ(n²) one and consuming a CPU core with a single small request. The class of attack is called hash flooding, and it was demonstrated broadly enough that most major language runtimes changed their default string hash in response. The standard defence has two parts, and they are the applied form of §22: a keyed hash function — one taking a secret key as an input, so the function an attacker would have to invert is not the one published — and a per-process random seed for that key, so the secret differs on every run. A short keyed pseudorandom function designed for exactly this purpose, cheap enough to run on every key, is the usual choice; some runtimes expose an environment variable to pin the seed for reproducibility, and pinning it re-opens the hole. Two practical consequences follow. Iteration order can differ between runs of the same program on the same data, so relying on it is a latent bug. And a hash value computed in one process must never be persisted and reused in another, because the seed will differ.

Treeified buckets

A second, independent defence for chained tables: if a bucket's chain grows past a threshold, replace the chain with a balanced search tree, converting that bucket's worst case from Θ(nⱼ) to O(log nⱼ). One widely used implementation converts a chain to a red-black tree at length 8 and converts back at length 6 — the gap between the two thresholds is hysteresis, exactly as in §20's shrink rule, and it exists to stop a bucket oscillating between representations. The choice of 8 is justified in that implementation's own documentation by the Poisson calculation of §12: under its default load factor, a chain reaching length 8 by chance has probability about 6 × 10⁻⁸, so a bucket that long is evidence of a broken hash function or an attack rather than of bad luck. That is the right way to read the feature — it is a safety net that should never trigger, not an optimisation of the common path. The same implementation also requires the table to be reasonably large before treeifying, preferring to resize first, since at small table sizes a long chain is more likely to mean "too few slots" than "adversarial keys".

Open addressing versus chaining in real libraries

Both are in wide use and the split tracks the trade this page has developed. Implementations that expect frequent deletion, arbitrary user-defined hash functions of unknown quality, and large stored values tend toward chaining, where deletion is exact and a bad bucket can be treeified. Implementations chasing throughput on small entries tend toward open addressing, and the current state of the art in that camp shares a recognisable shape: a single flat array of slots, a separate byte-per-slot metadata array holding a few bits of each key's hash, and probing that examines a whole group of slots at once — 8 or 16, depending on the SIMD width available — by comparing the group's metadata bytes against the sought key's fingerprint in one vector instruction. Only slots whose fingerprint matches are then touched at all, so a group of sixteen candidate slots is filtered with a single instruction and usually zero key comparisons. Designs of this family are reported to run at load factors around 7/8 without the cliff that §18's curves would predict for naive linear probing, because the metadata array is so dense that scanning many groups still touches few cache lines. Implementations of essentially this design now sit under the default hash map of several major languages.

Probe sequences in practice, and one instructive choice

One widely used interpreter's dictionary takes a different route from any of §14–§16: its probe sequence is generated by a recurrence that mixes in successive bits of the key's full hash value, shifting a "perturbation" register right by a few bits at each step. The effect is a sequence that is scattered like double hashing at first, depends on the whole hash rather than just its low bits, and — once the perturbation is exhausted — degenerates into a sequence that provably visits every slot. That last property is the same permutation requirement of §13, arrived at by a different route. It is a good example of the general shape of real implementations: they are not one of the three textbook schemes, they are engineered hybrids, and the textbook schemes are the vocabulary in which their choices are legible.

The practical checklist

  • Do not rely on iteration order. It is unspecified, it changes on resize, and with a randomised seed it changes between runs.
  • Do not persist hash values across processes unless the hash is explicitly documented as stable. Seeds are randomised; so are algorithms, between versions.
  • Do not use attacker-controlled keys with a non-keyed hash. If you are writing the hash yourself, this is your problem, not the library's.
  • Size the table up front when you can. Constructing with a capacity hint removes every rehash, and the hint should be the expected n divided by the target load factor, not n — passing n to an implementation with a 0.75 threshold still triggers a resize.
  • Make keys immutable, and make the hash agree with equality. The two obligations of §02 are where most real bugs live.

26 What a hash table cannot do

The defining move of hashing is to compute a location from a key in a way that deliberately destroys any relationship between keys. Keys that are adjacent, similar or ordered end up in unrelated slots — that is the uniformity the whole analysis depends on. The cost is total and permanent: a hash table has no idea which of two keys is larger, and every operation that needs that information degrades to a full scan. This section lists those operations and names what to use instead, because "use a hash map" is the default answer to far more problems than it should be.

The replacements, and when each is right

  • Balanced binary search trees. The general answer. Ordered iteration, successor, range queries and rank all in logarithmic time, at the price of a logarithmic lookup and worse cache behaviour. When a workload mixes point lookups with range scans, this is usually the right structure even though every individual point lookup is slower.
  • Sorted arrays with binary search. The right answer for a static ordered set: no per-node overhead, perfect locality, and Θ(log n) lookup with a much better constant than a tree. The mirror image of perfect hashing — both are the static specialisation of a dynamic structure, and both are better than it.
  • Tries, for string keys with shared structure. A trie answers "all keys with this prefix" — which a hash table cannot answer at all — and does so in time proportional to the prefix length plus the number of results. It also finds a key in time proportional to the key's length with no hashing and no comparisons. When keys are strings and prefix queries matter, a trie beats a hash table outright, and Arrays & Strings §23 makes the cost argument for short keys.
  • Locality-sensitive hashing, for "nearby". If the requirement is similar rather than equal, the answer is not to abandon hashing but to invert its defining property: an LSH family is designed so that similar inputs collide often. That is the exact opposite of the uniformity this page has spent twenty-five sections pursuing, and it is worth noticing that the same machinery reversed solves a different problem.
  • Both, when the workload genuinely needs both. A hash table for point lookups plus a tree or sorted index for ordered queries, kept consistent. The memory doubles and every write touches two structures; that is the honest price of two access patterns, and it is what a database's "add an index" does.

Three more limits, less often stated

  • No worst-case guarantee, ever, for a dynamic key set. Every scheme here is Θ(n) in the worst case. If a system has a hard per-operation latency bound, a hash table cannot meet it — perfect hashing can, but only for a static set, and cuckoo hashing can for lookups only, moving the unboundedness into insertion. This is a real constraint in real-time and hardware contexts and it is the reason those contexts so often use structures that look primitive.
  • Memory overhead is structural, not incidental. A table must be kept below its load-factor threshold, so a chained table at α = 0.75 has a third more slots than entries plus a link per entry, and an open-addressed one at α = 0.5 has twice as many slots as entries. A sorted array has none of that. If memory is the binding constraint and the key set is static, hashing is often the wrong tool.
  • Iteration is proportional to m, not n. Walking a hash table means walking the slot array, including the empty slots. At α = 0.1 that is ten times more work than the entries justify, and it is why repeatedly iterating a large sparse table is unexpectedly slow. Chaining can avoid it by threading a list through the entries — which is also, not coincidentally, how an insertion-ordered map is implemented.

27 Bloom filters: the lossy cousin

A hash table stores the keys. A Bloom filter stores only the evidence that keys were inserted: an array of m bits, with k independent hash functions setting k bits per key. It answers "is k in the set?" with either definitely not or probably yes — one-sided error, no false negatives, tunable false positives — in constant time and a handful of bits per element, with no key material stored at all. It is the right structure whenever a negative answer is common and cheap to act on, and a positive answer can afford to be checked against something slower.

Why k has an optimum, in words

More hash functions means more bits must coincide for a false positive, which pushes the error down. More hash functions also means more bits get set per insertion, which fills the array faster and pushes the error up. The two effects cross, and the crossing point is where exactly half the bits are set — a memorable and checkable diagnostic, since an implementation whose bit array is 90% ones is either over-filled or using too many hash functions, and one at 10% is wasting space. Note the shape of the trade: at the optimum the error is 2^(−k*), so each additional 1.44 bits per element halves the false-positive rate. The improvement is exponential in space, which is why very small filters are already useful — eight bits per element buys about 2%, and no amount of cleverness with a real hash table gets near that, because a hash table must store the key.

More hashing is not monotonically better — twice as many hash functions as the optimum is about as bad as a third as many.

What a Bloom filter cannot do, and the variants that patch each gap

  • It cannot delete. Clearing a bit would clear it for every other key that set it, creating false negatives and destroying the one-sided guarantee. Counting Bloom filters replace each bit with a small counter, incremented on insert and decremented on delete, at typically four times the space — and they can still overflow, which reintroduces a small error.
  • It cannot enumerate, and it cannot return the key. There is nothing to return; the keys were never stored. A filter is a membership oracle, not a container, and it is always paired with the real store behind it.
  • It cannot be resized without the original keys. Its m is fixed at construction, and growing it means re-inserting everything — which you cannot do from the filter itself. Scalable variants chain filters of growing size; the error budget is split across them.
  • Its error is not a bound on any single query. ε is the probability over a random absent key. A specific unlucky key is a false positive every time it is queried, deterministically, for the life of the filter — which matters when queries are repeated, and is a real source of confusion in caches.
  • Cuckoo and quotient filters are the modern alternatives: they support deletion, are more cache-friendly (one or two lookups rather than k scattered bit probes), and at low error rates use less space. The Bloom filter remains the one to understand first because its analysis is transparent and its guarantee is the cleanest.

Where it earns its place

The pattern is always the same: a cheap filter in front of an expensive lookup, where most lookups miss. A storage engine keeps a filter per on-disk table so that a key absent from that table costs a few bit tests instead of a disk read. A web cache keeps a filter of "things we have seen once" so that single-access items are never cached. A crawler keeps a filter of visited URLs, storing ten bits per URL instead of two hundred bytes. A distributed join ships a filter instead of a key list, turning a network round trip into a local test. In every case the false positives are harmless because a positive answer only triggers the real, exact check — the filter never decides anything on its own, and a design in which it does is a design that has misunderstood it.

28 Hashing beyond the table

The bucket array is one application of a much more general move: replace an object by a short, well-spread summary of it, and reason about the summary instead. Once that move is visible, it turns up everywhere — in algorithms that never allocate a table, in systems that hash to choose a machine rather than a slot, and in machine learning where hashing is used to bound a dimension. This section collects the recurrences, because recognising them is worth more than any individual technique.

Inside algorithms

  • Memoization. A top-down dynamic program is a recursion plus a map from state to result, and that map is almost always a hash table. The state is a tuple, the tuple is hashed, and the whole "overlapping subproblems" saving is realised by an O(1) expected lookup. Where the state space is small and dense, the table degenerates to the direct-address array of §03 — which is exactly what a bottom-up table is, and the clearest statement of the relationship between the two DP styles.
  • Deduplication and "have I seen this?" The commonest use of a hash set. A visited-set in a graph traversal, a duplicate-line filter, a cycle check. Note the alternative when memory is the constraint and a small error is tolerable: a Bloom filter.
  • Two-sum and its family. A whole class of array problems drops from Θ(n²) to Θ(n) by storing what has been seen in a hash map and querying it for the complement — the same move as the prefix-sum trick, with a map replacing the arithmetic. Grouping anagrams by a canonical key, counting distinct elements in a sliding window, and finding the longest substring without repeats are all the same pattern.
  • Rolling hashes and string matching. Rabin-Karp hashes every window of a text and compares hashes instead of characters; the polynomial hash there is the same construction as the string hash code of §04, and the reason it can be updated in O(1) per shift is a property of the polynomial that the table never needs.
  • Transposition tables. A game-tree search hashes a board position to a 64-bit key and caches the evaluation. Here the table is deliberately lossy — collisions are accepted rather than resolved, because the cost of a rare wrong evaluation is lower than the cost of storing full positions. That is a design nobody would tolerate in a map, and it is correct in its own setting.

Inside systems

  • Sharding and consistent hashing. Hash the key, take the result modulo the number of servers, and you have a distributed dictionary — until the server count changes, at which point every key moves, for exactly the reason a table resize re-places every entry. Consistent hashing repairs it by mapping both keys and servers onto a circle and assigning each key to the next server clockwise, so adding a server moves only the keys in one arc. Concretely: a ring of 100 positions, servers at A = 7, B = 31, C = 58, D = 84, and eighteen keys hashed to 1, 8, 16, 24, 29, 30, 33, 47, 50, 60, 69, 70, 74, 75, 77, 80, 81, 91; each key goes to the next server clockwise, so B owns 8 … 30 (five keys), C owns 33, 47, 50, D owns 60 … 81 (eight), and A wraps round to take 91 and 1. Add a fifth server E = 45: it takes over exactly the arc (31, 45], which holds one key, 33, and one key moves — the expectation is n/5 ≈ 3.6, and the arc here happens to be a thin one. The naive mod 4 → mod 5 remap moves fourteen of the same eighteen. It is the distributed-systems answer to the rehash problem of §20, and the analogy is exact.
  • Content addressing and integrity. Name a blob by the hash of its bytes and you get deduplication, cheap equality, and tamper evidence for free. The criterion here is the birthday bound of §09 and, when an adversary is present, collision resistance, which is a cryptographic property that none of the fast hash functions on this page has.
  • Caches. A processor's set-associative cache is a hash table with h(address) = some address bits, buckets of fixed capacity, and an eviction policy in place of growth. The cache model used throughout the series is itself a hashing structure, which is a pleasing circularity.
  • Cardinality and similarity sketches. HyperLogLog estimates the number of distinct items from the maximum count of leading zeros in their hashes, in a few kilobytes for billions of items; MinHash estimates the overlap of two sets from the minimum hash value in each. Neither is the pair-collision (birthday) mathematics of §09: both use the order statistics of random hash values — the longest run of leading zeros, the minimum value — to infer something about the set that produced them.

Inside machine learning

  • The hashing trick. To turn an unbounded vocabulary of features into a fixed-length vector, hash each feature name to an index in 0 … d−1 and accumulate there. No vocabulary is stored, new features need no retraining of the encoder, and memory is fixed in advance. The price is exactly the price of this page: collisions, here meaning two unrelated features sharing a weight. A signed variant multiplies each contribution by ±1 derived from a second hash, so colliding features cancel in expectation rather than reinforcing. This is the technique that makes very high-dimensional linear models practical on streaming text.
  • Locality-sensitive hashing for nearest neighbours. k-NN at scale cannot compare a query against every point, and LSH inverts the uniformity goal of §05: the family is built so that similar vectors collide with high probability. Candidates come from the colliding bucket and are then checked exactly — the same filter-then-verify shape as a Bloom filter.
  • Embedding tables and hash embeddings. Very large categorical vocabularies are often mapped into a smaller embedding table by hashing, sometimes with several hash functions per item whose embeddings are combined, so that collisions are unlikely to be shared across all of them. It is double hashing's idea — two independent functions make a coincidence much less likely — applied to a learned table rather than a slot array.
  • Random projection. Reducing dimension by multiplying with a random matrix is the continuous analogue of the same move: replace an object by a short random summary that preserves what you care about, here distances rather than equality. The dimensionality reduction page takes that idea from the other end.
The unifying sentence. Every one of these replaces an expensive object by a cheap, well-spread summary and then reasons about summaries. What differs between them is only what a collision costs — a probe in a hash table, a wrong evaluation in a transposition table, a shared weight in a feature vector, a broken integrity guarantee in content addressing — and that cost is what decides how many bits the summary needs.

29 Pitfalls

Ordered roughly by how much damage they do before anyone notices. The first three are correctness bugs that present as data loss; the rest are performance failures that present as a system that used to be fast.

Correctness

  • Mutating a key after inserting it. The entry's correct slot moves; the entry does not. It becomes unreachable through get while remaining visible to iteration and still counted by size(). The map now contains an entry it cannot find, and inserting the "same" key again produces a duplicate. There is no way for the table to detect this, which is why languages that permit only immutable keys are not being pedantic.
  • A hash function inconsistent with equality. If a == b but hash(a) ≠ hash(b), the two land in different buckets and the uniqueness invariant of §02 is violated silently. This is the standard failure of overriding an equality method and forgetting the hash method, or of adding a field to a record's equality without adding it to the hash. The reverse — equal hashes for unequal keys — is a collision and is fine.
  • Deleting from an open-addressed table by writing EMPTY. §19 in full. Some keys stored past the hole become unreachable; which keys depends on the probe paths, so the bug is data-dependent, intermittent, and invisible in a test that deletes from a sparse table. Write a tombstone or use backward-shift deletion.
  • Forgetting the mod m in a probe loop. j = j + 1 instead of j = (j + 1) % m reads past the end of the array — out of bounds in a language that checks, silently wrong in one that does not, and in either case the search terminates early for every key whose probe path would have wrapped. The hand trace in §14 exercises exactly this case with key 21.
  • A double-hashing step that is not coprime with m. §16. The probe sequence visits m/gcd(h₂, m) slots and can refuse an insertion into a table that is 25% full. Nothing warns you; the symptom is an occasional "table full" or an infinite loop.
  • Unbounded probe loops. Every probe loop must terminate after m probes, whatever its scheme, and must treat that as a real outcome rather than an impossible one. A loop written as while (slot is occupied) hangs the process the first time a table genuinely fills.
  • Inserting into the first tombstone before finishing the search. §19's insert rule. Placing the key at the first tombstone without checking the rest of the probe path can duplicate a key that already exists further along. Remember the tombstone, keep probing, and only place after the path proves the key absent.

Performance

  • Never rebuilding a churned table. A resize trigger on n/m alone never fires under a balanced insert/delete workload, so tombstones accumulate without limit. The §21 figure measures a 127-fold slowdown at a load factor that never moves off 0.30. Trigger on α_eff.
  • A power-of-two modulus with a weak hash code. §07. Masking keeps the low bits, and an identity-like code puts no entropy there, so keys in arithmetic progression collapse onto m/gcd(stride, m) slots. Either use a prime modulus or add an avalanche step; the failure is using neither.
  • Quoting the uniform-hashing formula for linear probing. §18. It understates the unsuccessful cost by a factor of about five at α = 0.9 and leads directly to running the table at a load factor it cannot sustain.
  • Sizing a table to n rather than n / α_target. A capacity hint of exactly n to an implementation with a 0.75 threshold still triggers a resize before the last element arrives, which is the one thing the hint was meant to prevent.
  • Shrinking at the same threshold you grow at. Without hysteresis, an alternating insert/delete at the boundary resizes on every operation, turning amortized O(1) into Θ(n) per operation. §20, and the same trap as the dynamic array's.
  • An expensive hash on a small key. If the key is a 32-bit integer and the hash costs forty cycles, the hash dominates everything and a sorted array with binary search may well be faster. §05's budget argument: a stronger hash is worth its cycles only when it removes probes.
  • Recomputing a string's hash on every operation. Hashing a length-L key is Θ(L), so a loop doing map.contains(s) then map.get(s) hashes twice, and a rehash without a cached code re-hashes every key from scratch. Cache the code with the entry — the whole point of the seam in §04.
  • Iterating a large sparse table repeatedly. Iteration is Θ(m), not Θ(n). A table that grew to a million slots and then had most entries deleted still costs a million slot reads per pass.

Reasoning

  • Treating O(1) as a guarantee. It is an expectation, under a hypothesis about the keys, and it counts probes rather than instructions. The worst case is Θ(n) and the tail is governed by the maximum bucket, which grows with n forever (§12).
  • Assuming a low load factor means few collisions. The birthday bound: the first collision arrives after about √m insertions, at a load factor of about 1/√m. A million-slot table collides at twelve hundred entries.
  • Assuming a long chain means a bad hash. At α = 1 a perfect hash gives a longest bucket of about 5.5 at a thousand entries and 8.8 at a million. Compare against the prediction, not against 1.
  • Depending on iteration order. It is unspecified, it changes on resize, and with a randomised seed it changes between runs of the same binary on the same input (§25).
  • Using a non-keyed hash on attacker-controlled keys. §09's pigeonhole argument is constructive. This is a denial-of-service vulnerability, not a performance note.
