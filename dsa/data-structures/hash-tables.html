Hash Tables

One decision — compute the slot from the key instead of searching for it — and everything here follows. An array can reach slot i in constant time but only if you already know i; a hash table manufactures i out of the key itself, turning a search into an arithmetic expression. The price is that the manufacturing is not injective: distinct keys are guaranteed to land on the same slot, so most of this page is about what you do next. That question has exactly two families of answer — hang a list off the slot, or go find another slot — and each answer comes with its own expected-cost theorem, its own hypothesis, its own failure mode as the table fills, and its own opinion about what deletion means. The bounds here are expected, not worst-case, and the difference is not decoration: it is a probabilistic promise whose small print says who gets to choose the keys.

01 What a hash table is

A hash table is an implementation of the map abstract type in which the storage location of a key is computed from the key by a function, rather than found by searching. There is an array of m slots — the bucket array — and a hash function h that maps every possible key to an index in 0 … m−1. To store, look up or remove the entry for key k, you evaluate h(k) and go straight there. That is the entire idea, and the entire difficulty is contained in one word of it: function. A function from a large set to a small one cannot be injective, so different keys will arrive at the same slot, and a hash table is really a hash function plus a stated policy for what happens when they do.

Why each word of the definition is load-bearing

  • Computed, not searched. This is the whole inversion. A sorted array with binary search finds a key by narrowing an interval: O(log n) comparisons, each of which looks at data. A hash table performs no comparisons at all to decide where to look; it performs arithmetic on the key and then goes there. Comparisons reappear only to confirm that the entry sitting in the slot is really the one you wanted — which is why a hash table needs both a hash function and an equality test, and why the two must agree (§29).
  • A total function. h must be defined for every key in the universe and must return the same slot every time it is asked about the same key, for the lifetime of that key's membership in the table. Determinism is not a nicety; it is the only reason get can find what put stored. Every practical disaster in §29 is a violation of it: a key whose hash depends on a field that was later mutated, a hash that incorporates a memory address that the garbage collector moved, a hash seeded per-process being written to a file and read back in another process.
  • Into 0 … m−1. The range is the table, so the function's codomain is a property of the table, not of the key type. That is why the hash of a key is almost always built in two stages — a table-independent hash code and a table-dependent compression — which §04 separates properly, because nearly every real design decision lives at the seam between them.
  • Plus a collision policy. Without one, the structure is not a map. The two families, chaining and open addressing, are not interchangeable implementation details: they have different memory behaviour, different deletion semantics, different tolerable load factors, and different theorems. Half of this page is the consequence of that choice.

The motivation, as a cost argument against the alternatives

A map has to answer "where is the entry for key k?", and before hashing there were two honest answers. Scan: keep entries in a contiguous array or a chain of nodes in arbitrary order and compare against each — O(1) insert, Θ(n) lookup, trivially correct, fine up to a few dozen entries and useless beyond. Order: keep the entries sorted by key, and binary-search — Θ(log n) lookup, but insertion into a sorted array costs Θ(n) element moves, which pushes you toward a balanced search tree at Θ(log n) for everything. Hashing proposes a third answer that is not on that spectrum at all: do not look for the key, calculate where it must be. The gain is a bound with no log n in it. The losses are precise and worth naming up front — the bound is expected rather than guaranteed, the entries are stored in an order nobody chose, and every operation that depends on order — minimum, successor, range scan — becomes a full Θ(n) scan, and sorted iteration becomes a Θ(n log n) sort, instead of being free. §26 takes that trade seriously; the intervening sections earn the gain.

Key → hash code → slot, on real keys the collisions appear at the compression step, not at the hash code — change m and watch which keys merge

The figure separates the two stages that are usually said in one breath. The middle column — the hash code — is a property of the key alone, and at the default settings all ten of these keys produce ten distinct codes. The right-hand column then folds those ten integers into m = 13 slots and seven survive as distinct, so three collisions were manufactured entirely by the compression step. That is the honest picture of what a hash function does: the first half tries to destroy the structure in the key, and the second half throws information away on purpose, because it has to. Now switch the hash code control to sum of characters and watch the middle column collapse to three distinct values — stop, tops, pots, opts, spot and post are anagrams, and a code that only adds characters cannot tell anagrams apart. No table size and no compression function can separate integers that are already equal, and the readout says so. That is the §04 blame test running live: count the distinct codes, then count the distinct slots, and whichever number collapsed is the half at fault.

The one-sentence summary to carry through the page. A hash table buys O(1) expected time by replacing search with arithmetic, and every remaining section is either about making the arithmetic spread keys well, or about paying for the fact that it cannot spread them perfectly.

The notes, in 5 parts

29 Pitfalls

Ordered roughly by how much damage they do before anyone notices. The first three are correctness bugs that present as data loss; the rest are performance failures that present as a system that used to be fast.

Correctness

  • Mutating a key after inserting it. The entry's correct slot moves; the entry does not. It becomes unreachable through get while remaining visible to iteration and still counted by size(). The map now contains an entry it cannot find, and inserting the "same" key again produces a duplicate. There is no way for the table to detect this, which is why languages that permit only immutable keys are not being pedantic.
  • A hash function inconsistent with equality. If a == b but hash(a) ≠ hash(b), the two land in different buckets and the uniqueness invariant of §02 is violated silently. This is the standard failure of overriding an equality method and forgetting the hash method, or of adding a field to a record's equality without adding it to the hash. The reverse — equal hashes for unequal keys — is a collision and is fine.
  • Deleting from an open-addressed table by writing EMPTY. §19 in full. Some keys stored past the hole become unreachable; which keys depends on the probe paths, so the bug is data-dependent, intermittent, and invisible in a test that deletes from a sparse table. Write a tombstone or use backward-shift deletion.
  • Forgetting the mod m in a probe loop. j = j + 1 instead of j = (j + 1) % m reads past the end of the array — out of bounds in a language that checks, silently wrong in one that does not, and in either case the search terminates early for every key whose probe path would have wrapped. The hand trace in §14 exercises exactly this case with key 21.
  • A double-hashing step that is not coprime with m. §16. The probe sequence visits m/gcd(h₂, m) slots and can refuse an insertion into a table that is 25% full. Nothing warns you; the symptom is an occasional "table full" or an infinite loop.
  • Unbounded probe loops. Every probe loop must terminate after m probes, whatever its scheme, and must treat that as a real outcome rather than an impossible one. A loop written as while (slot is occupied) hangs the process the first time a table genuinely fills.
  • Inserting into the first tombstone before finishing the search. §19's insert rule. Placing the key at the first tombstone without checking the rest of the probe path can duplicate a key that already exists further along. Remember the tombstone, keep probing, and only place after the path proves the key absent.

Performance

  • Never rebuilding a churned table. A resize trigger on n/m alone never fires under a balanced insert/delete workload, so tombstones accumulate without limit. The §21 figure measures a 127-fold slowdown at a load factor that never moves off 0.30. Trigger on α_eff.
  • A power-of-two modulus with a weak hash code. §07. Masking keeps the low bits, and an identity-like code puts no entropy there, so keys in arithmetic progression collapse onto m/gcd(stride, m) slots. Either use a prime modulus or add an avalanche step; the failure is using neither.
  • Quoting the uniform-hashing formula for linear probing. §18. It understates the unsuccessful cost by a factor of about five at α = 0.9 and leads directly to running the table at a load factor it cannot sustain.
  • Sizing a table to n rather than n / α_target. A capacity hint of exactly n to an implementation with a 0.75 threshold still triggers a resize before the last element arrives, which is the one thing the hint was meant to prevent.
  • Shrinking at the same threshold you grow at. Without hysteresis, an alternating insert/delete at the boundary resizes on every operation, turning amortized O(1) into Θ(n) per operation. §20, and the same trap as the dynamic array's.
  • An expensive hash on a small key. If the key is a 32-bit integer and the hash costs forty cycles, the hash dominates everything and a sorted array with binary search may well be faster. §05's budget argument: a stronger hash is worth its cycles only when it removes probes.
  • Recomputing a string's hash on every operation. Hashing a length-L key is Θ(L), so a loop doing map.contains(s) then map.get(s) hashes twice, and a rehash without a cached code re-hashes every key from scratch. Cache the code with the entry — the whole point of the seam in §04.
  • Iterating a large sparse table repeatedly. Iteration is Θ(m), not Θ(n). A table that grew to a million slots and then had most entries deleted still costs a million slot reads per pass.

Reasoning

  • Treating O(1) as a guarantee. It is an expectation, under a hypothesis about the keys, and it counts probes rather than instructions. The worst case is Θ(n) and the tail is governed by the maximum bucket, which grows with n forever (§12).
  • Assuming a low load factor means few collisions. The birthday bound: the first collision arrives after about √m insertions, at a load factor of about 1/√m. A million-slot table collides at twelve hundred entries.
  • Assuming a long chain means a bad hash. At α = 1 a perfect hash gives a longest bucket of about 5.5 at a thousand entries and 8.8 at a million. Compare against the prediction, not against 1.
  • Depending on iteration order. It is unspecified, it changes on resize, and with a randomised seed it changes between runs of the same binary on the same input (§25).
  • Using a non-keyed hash on attacker-controlled keys. §09's pigeonhole argument is constructive. This is a denial-of-service vulnerability, not a performance note.

Where it goes sideways, out of the domain. The cost language is derived in Algorithm Analysis, whose amortized analysis underwrites §20 and whose best/worst/average distinction is the difference between this page's expected bounds and its worst-case ones. The memoization table of Dynamic Programming is a hash table, and the bottom-up version of the same algorithm is the direct-address table of §03. Outside the domain, the hashing trick bounds the feature dimension of linear models, locality-sensitive hashing is what makes k-nearest-neighbour search scale, and the same summarise-then-compare move reappears as random projection in dimensionality reduction.
