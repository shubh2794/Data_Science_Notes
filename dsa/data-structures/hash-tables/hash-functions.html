02 The map ADT, and what it does not promise

A map (equivalently dictionary, associative array, symbol table) is an abstract type holding a set of (key, value) pairs in which keys are unique. It is defined by behaviour, not by storage: any structure supporting the operations below is a map, and a hash table is one implementation among several. Keeping the ADT and the implementation apart is the discipline that makes the rest of the page legible — the ADT says what must be true, the implementation says what it costs, and a great many arguments about hash tables are really arguments about which of the two is being discussed.

the core operationsget(k) → the value stored under k, or "absent" put(k, v) → associate v with k; REPLACE any existing value for k remove(k) → delete the entry for k, if present contains(k) → is there an entry for k? size() → the number of entries the traversal operation, and the reason it is listed separatelyiterate() → visit every (k, v) exactly once, IN NO SPECIFIED ORDER the uniqueness invariant, which put must maintainat all times: k ≠ k′ ⇒ the map holds at most one entry for each what "k ≠ k′" means, and why it is the map's business and not the table'sequality is supplied by the key type; the map never invents it the three standard implementations, for comparisonunsorted list get Θ(n) put Θ(n) ordered iteration Θ(n log n) balanced tree get Θ(log n) put Θ(log n) ordered iteration Θ(n) hash table get O(1) exp. put O(1) exp. ordered iteration Θ(n log n)

What the ADT promises

  • Uniqueness of keys, enforced on put. A second put with an equal key overwrites rather than appends. This is the single behavioural difference between a map and a multimap, and it is why put cannot be implemented as "insert without looking" — it must first search, which is why insertion into a hash table costs a lookup and is not cheaper than one.
  • Values are opaque. The map never inspects a value; it neither compares, orders nor hashes it. Only keys are hashed. A set is exactly this ADT with the value omitted, which is why every hash-table technique on this page applies unchanged to hash sets.
  • Total lookup. get is defined for every key, answering "absent" when there is no entry. This matters more than it sounds: the unsuccessful search is a first-class case, it is usually the more frequent one in real workloads, and it has its own cost theorem in every scheme here — one that is consistently worse than the successful case, because an unsuccessful search cannot stop early.

What the ADT conspicuously does not promise

  • Any order. iterate() visits the entries in whatever order the implementation finds convenient. For a hash table, that order is a function of the hash values and the insertion history, so it can change when the table resizes, and — with a per-process random seed (§25) — between two runs of the same program on the same data. Code that depends on iteration order is depending on an implementation accident. If order is part of the requirement, the requirement is for a sorted map (key order — a balanced tree) or an insertion-ordered map (arrival order — a hash table with an auxiliary linked list threaded through the entries). Those are two different ADTs, and a plain hash table is neither.
  • Any relationship between keys. No minimum, no maximum, no successor, no "all keys between a and b". A map's keys form a set, not an ordered set, and this is precisely the structure a hash table destroys in exchange for its speed (§26).
  • Worst-case bounds. The ADT says nothing about cost at all. The O(1) people attach to it is a property of one implementation, holds in expectation, and rests on a hypothesis that an adversary can deliberately falsify.

Where the keys' own contract comes in

A hash table imposes two obligations on the key type that the ADT alone does not, and both are routine sources of bugs that present as "the entry vanished". First, h must be consistent with equality: if k equals k′ then h(k) must equal h(k′). The converse need not hold and cannot — that is what a collision is — but this direction is mandatory, because two equal keys that hash apart will be stored in two different slots and the map will contain a duplicate, silently violating its own invariant. Second, keys must be immutable while in the table, or at least the parts of them that h and equality read must be. Mutating a key after insertion moves its correct slot without moving the entry, and the entry becomes unreachable through the front door while remaining visible to iteration — the most confusing failure mode in this whole subject, because the entry is simultaneously present and absent depending on which operation you ask. Languages that only allow immutable types as hash keys are enforcing exactly this, and the restriction is not arbitrary conservatism.

03 Direct addressing, and exactly where it fails

Start from the case where hashing is unnecessary. If the key universe U is small and the keys are integers 0 … |U|−1, allocate an array of |U| slots and use the key itself as the index. This is a direct-address table, and it is the ideal hash table: h(k) = k, no collisions ever, Θ(1) worst-case for every operation with no probabilistic hypothesis anywhere. It is worth building the idea from here because the whole of hashing is what you do when the one assumption behind it — that |U| is affordable — is false.

the direct-address tableT[0 … |U|−1], T[k] = the entry with key k, or NIL get(k) = T[k] put(k,v) = (T[k] ← (k,v)) remove(k) = (T[k] ← NIL) the cost, with no small print of any kindevery operation: Θ(1) WORST case — no expectation, no hypothesis, no adversary the cost that kills itspace = Θ(|U|), regardless of how many keys n are actually present the ratio that decides whether it is acceptableoccupancy = n / |U| worked: 9-digit identifiers, 1000 of them actually in use|U| = 10⁹ slots × 8 bytes per reference = 8 GB, to hold 1000 entries occupancy = 1000 / 10⁹ = 10⁻⁶ — one slot in a million carries anything what hashing changes, in one linereplace the table of size |U| by a table of size m ≈ n, and h(k) = k by h : U → {0…m−1} space Θ(|U|) → Θ(m) = Θ(n), at the cost of h no longer being injective

The failure is about space, and only about space

It is worth being exact, because the argument is often stated loosely as "direct addressing doesn't scale". Time does not degrade at all — a direct-address table of a billion slots answers a lookup in one array access, same as a table of ten. What fails is that the array must be allocated, and its size is set by the universe rather than by the data. The example in the formula block is the canonical one: nine-digit identifiers give a universe of 10⁹, and a table of that many machine words costs gigabytes whether it holds a thousand entries or none. The memory is not merely wasted, it is actively harmful — it must be allocated, it must be initialised to NIL, and a traversal of the occupied entries has to walk all 10⁹ slots to find the thousand, so iterate() degrades from Θ(n) to Θ(|U|). Direct addressing turns a space problem into a time problem for exactly one operation, and that operation is the one that touches every slot.

Where direct addressing is still the right answer

  • Small, dense universes. Counting bytes (|U| = 256), bucketing ages, indexing by weekday, tallying the 26 letters of an alphabet, the bad-character table of a Boyer-Moore matcher: all of these are direct-address tables, and using a hash table for them would be strictly slower and larger. If |U| is a few thousand and occupancy is above a few per cent, stop here — you have a perfect hash function for free and it is the identity.
  • Bit vectors, when there is no value. If the map is really a set of small integers, each slot needs one bit rather than one word, and a universe of 10⁶ costs 125 KB rather than 8 MB. That is a 64-fold improvement which moves the affordability threshold by a factor of 64 — not by enough to rescue the 9-digit case, but enough to rescue many.
  • As the second level of something else. Index arithmetic on a dense small range is what makes perfect hashing's inner tables work, what makes counting sort and radix sort work, and what makes a direct-mapped cache work. The technique does not disappear; it becomes a component.

The intermediate case that motivates everything after

Between "universe small enough to index directly" and "universe astronomically large" there is no interesting middle ground, and that is the real point. Universes in practice are either tiny (a byte, a weekday) or enormous (every string, every 64-bit integer, every tuple) — there is almost never a universe of size 3n. So the decision is binary: if the universe is tiny, index it; otherwise the table must be sized by n, which forces m ≪ |U|, which forces h to be non-injective, which forces a collision policy. Everything from §09 onward is the consequence of this single unavoidable step. The hash function's job, viewed this way, is to simulate the direct-address table's distinct-slot-per-key property as closely as a function into a smaller range can — and the collision policy's job is to handle the gap that remains.

A useful reframing. A hash table is a direct-address table on a compressed universe. The compression is lossy, the loss is called a collision, and the load factor n/m measures how hard the compression is being pushed. Hold that picture and the rest of the page organises itself.

04 The two halves: hash code, then compression

In practice h is never written as a single function. It is the composition of a hash code, which maps an arbitrary key to a fixed-width integer and knows nothing about the table, and a compression function, which maps that integer into 0 … m−1 and knows nothing about the key. The split is not bureaucratic. It puts every key-type-specific decision on one side of a seam and every table-specific decision on the other, so a table can be resized without re-deciding how to hash a string, and a new key type can be supported without touching the table. It also localises blame: collisions are inevitable at the compression step, but a bad hash table is almost always one whose hash code was weak and whose compression then faithfully preserved the weakness.

What the hash code must achieve

The hash code's job is to turn "different key" into "different integer" as reliably as a deterministic function into 2^w values can, and to do so in a way that destroys the structure in the input. Real key sets are not random: identifiers in a program are i, j, n, tmp, ptr, pt, pts; file paths share long prefixes; timestamps are consecutive; record identifiers are consecutive and often a multiple of something. A code that preserves any of that structure hands it to the compression step, which will convert it into a systematic collision pattern. Three properties are wanted, and they are not the same property:

  • Determinism. Same key, same code, always, within one process's lifetime. This is a correctness requirement, not a quality one.
  • Uniformity. Over the key distribution you actually face, the codes should look spread out. Note the qualifier — uniformity is a joint property of the function and the input distribution, and is therefore not a property you can test once and rely on forever.
  • The avalanche property. Flipping one bit of the input should change roughly half the output bits, unpredictably. This is much stronger than uniformity and it is what makes a code robust to near-keys: "pt" and "pts", or ids 1000 and 1001, should not merely differ in their codes, they should differ everywhere in their codes. The reason it matters for tables specifically is that compression usually keeps a few bits of the code, and a code that concentrates its differences in the bits compression throws away is worthless. The low bits option in the figure of §01 keeps exactly those bits, so it is the setting that punishes a code with poor downward diffusion.

What the compression function must achieve, and the failure it must avoid

Compression must fold a wide integer into m values as evenly as possible, and its characteristic failure is preserving a periodicity. If the codes happen to be spaced d apart and m shares a factor with d, the folded values collapse onto a sublattice of the table and a large fraction of slots become unreachable. The clean worked case: codes 200, 205, 210, …, 595 — 80 values spaced 5 apart — compressed by c mod 100 land on only 20 distinct slots, four keys to a slot, so every code collides with exactly three others; compressed by c mod 101 they land on 80 distinct slots and collide not at all. Nothing changed but one in the divisor. That is the entire argument for choosing m prime, made precise in §07, and it is also the argument for randomising the compression when the codes are not under your control, which is §22.

Where the responsibility actually lands

A recurring practical confusion is which half to blame when a table performs badly. The test is cheap and worth naming: count the distinct hash codes, then count the distinct slots. If the codes themselves are already colliding — ten keys producing four codes — the key type's hash code is broken, and no table size will rescue it, because compression cannot separate integers that are already equal. If the codes are distinct and the slots are not, the fold is the problem, and the fixes are a different m, a different compression, or more slots. The figure in §01 prints both counts for exactly this reason. Its two settings are the two diagnoses side by side: the default polynomial code keeps all ten codes distinct and loses three keys to the fold — a compression collision — while the sum-of-characters code collapses ten keys to three codes before the table is even consulted, which is a code failure that no table can repair.

A widespread real-world design. Some library implementations counter a weak low-entropy hash code by mixing the code's high bits down into its low bits before masking — a cheap "finalisation" step applied by the table to whatever code the key type supplied. That is a table-side repair of a code-side weakness, and it is an admission that the seam described here leaks in one specific direction: the compression step is entitled to assume the code is good, and real codes often are not.

05 What makes a hash function good

"Good" is measurable, but only against a stated purpose, and hash functions are used for at least three purposes with incompatible requirements: filling a table evenly, fingerprinting data for equality or integrity, and resisting an adversary. A function that excels at one can be useless at another, and most confusion about hash functions comes from importing a criterion from the wrong column. This section fixes the criteria for the table-addressing job specifically — the job this page is about — and names the others so they can be told apart.

the four requirements for a TABLE hash, in priority order1. deterministic same key ⇒ same value, for the table's lifetime (correctness) 2. consistent with = k = k′ ⇒ h(k) = h(k′) (correctness) 3. spreading the induced load on the m slots is near even (performance) 4. cheap O(1) for fixed-width keys, Θ(L) for length-L keys (performance) the measurable form of "spreading" — the chi-square statistic on the bucket countsX² = ∑ⱼ (nⱼ − n/m)² / (n/m) expected ≈ m − 1 for a uniform spread X² ≫ m ⇒ clumped; X² ≪ m ⇒ suspiciously even (a red flag for a non-random test set) the OTHER measurable form — the longest chainn keys, m = n slots, ideal random hash ⇒ E[longest chain] = Θ(log n / log log n) which is NOT O(1) — the worst slot grows, slowly, forever the avalanche criterion, stated numericallyflip one input bit ⇒ each output bit flips with probability ≈ 1/2, near-independently the tension, which cannot be resolved, only chosenstronger mixing ⇒ better spread and more adversary resistance ⇒ more cycles per key

The three jobs, and why their criteria differ

  • Table addressing — this page. The output range is tiny (m slots), collisions are handled rather than fatal, and the function runs on the critical path of every single operation, so speed dominates. A function that collides once in a thousand on your keys is fine; the collision policy absorbs it. What is not fine is a systematic pattern, because a pattern makes many keys collide at once rather than a few at random.
  • Fingerprinting — deduplication, content addressing, change detection, the rolling hash of a substring matcher. Here the output range is large (64 to 256 bits), there is no collision policy, and a collision is a wrong answer rather than a slow one. The criterion is the birthday bound: with a b-bit fingerprint you can afford about 2^(b/2) items before a collision becomes likely, so 64 bits is comfortable at millions of items and uncomfortable at billions.
  • Adversarial resistance — any table whose keys come from outside the program. The criterion is not statistical at all: it is that no efficient adversary can produce colliding keys, which no fixed fast hash provides. The two real answers are a keyed hash with a per-process secret, and universal hashing, and they are the same answer wearing different clothes (§25).

The measurements that tell you whether a hash is spreading

Two numbers are worth computing on a real key set, and they catch different failures. The chi-square statistic on the bucket counts catches a global bias: sum (nⱼ − n/m)²/(n/m) over the slots, and compare against m − 1, which is the expectation under a uniform spread. A value near m means the spread is indistinguishable from random; a value several times m means the function is clumping. The longest chain catches a local one, and it carries a subtlety that is easy to get backwards: even a perfect random hash does not give a flat table. Throwing n keys into n slots leaves the busiest slot holding Θ(log n / log log n) keys in expectation. Be careful with that expression: it is a growth rate, not a value, and evaluating it literally gives 3.0 at n = 100 and 5.3 at n = 10⁶, while the expected maximum computed from the bucket distribution itself is 4.2 and 8.8 — the suppressed constants are not small at any n you will meet. So an observed maximum chain of 9 in a million-entry table is not evidence of a bad hash, it is what a good one produces; evidence of a bad hash looks like a maximum chain of 500. §11 and §12 compute those expected maxima and measure them. §10's figure measures both against their predictions, so the baseline is visible rather than assumed.

Cost is part of quality, and it is often the deciding part

The cheapest possible table hash for a machine word is a multiply and a shift; the strongest commonly used one costs tens of nanoseconds per key. Between them lie one or two orders of magnitude, and since every operation pays this cost, the choice can dominate the table's performance more than the collision policy does. The right way to think about it is a budget: a lookup costs (hash cost) + (probes) × (probe cost), and probes cost roughly a cache miss each at any interesting table size. A stronger hash is worth its cycles precisely when it removes probes — and past the point where the spread is already near-uniform it removes none, so additional strength buys only adversary resistance. That is a real thing to buy, and §25 explains when. It is not a speed improvement.

The claim to be suspicious of. "This hash function is good" is not a complete sentence. Good for which job, on which key distribution, against which adversary, at what cost per key? A function that is excellent for a symbol table of identifiers may be a poor fingerprint and is almost certainly not adversary-resistant.

06 The uniformity hypotheses — three different assumptions

Every expected-cost result on this page is conditional, and the conditions are not the same condition. Three distinct hypotheses circulate, they license different theorems, and the commonest error in this entire subject is proving a bound under one and quoting it under another. They are set out here, together, before any of them is used, so that each theorem later can name its own and be held to it.

H1 — SIMPLE UNIFORM HASHING (the chaining hypothesis)each key is equally likely to hash to any of the m slots, independently of where every other key hashed a statement about ONE value h(k) per key — licenses the chaining theorems of §10 H2 — UNIFORM HASHING (the open-addressing hypothesis)each key's PROBE SEQUENCE ⟨h(k,0), h(k,1), …, h(k,m−1)⟩ is equally likely to be any of the m! permutations of ⟨0, 1, …, m−1⟩ a statement about a whole permutation per key — licenses the probe theorems of §18 H3 — UNIVERSAL HASHING (a property of a FAMILY, and provable rather than assumed)a family H is universal iff for all k ≠ k′: Pr[h(k) = h(k′)] ≤ 1/m probability over the random CHOICE of h ∈ H — not over the keys, which may be adversarial the strict logical relationsH2 ⇒ H1 (a uniformly random permutation has a uniformly random first element) H1 ⇏ H2 (linear probing satisfies H1 for its first probe and violates H2 badly) H3 is weaker than H1 — pairwise only — and yet suffices for the chaining bounds, §22 and the fact that ruins the neat pictureNONE of linear, quadratic or double probing satisfies H2 each generates at most m² distinct probe sequences; H2 demands m! of them

H1: simple uniform hashing

The assumption is that h scatters keys like independent uniform draws: slot j is as likely as slot j′ for any key, and knowing where k landed tells you nothing about where k′ will land. It is a hypothesis about the pair (hash function, key distribution), and it is therefore not checkable in general — you rarely know the key distribution, and even when you do the keys may not be drawn independently. What it buys is the balls-in-bins model in full: the count nⱼ of keys in slot j is Binomial(n, 1/m), its expectation is exactly α = n/m, and every chaining result follows from that one fact by linearity of expectation. Note carefully what H1 does not say: it says nothing about probe sequences, so it cannot by itself justify a single open-addressing bound.

H2: uniform hashing

Open addressing needs more, because a key does not have a slot, it has an ordered list of slots to try. H2 upgrades the assumption from "one uniform draw per key" to "one uniform permutation of all m slots per key". This is a genuinely stronger statement — it implies H1 by looking only at the first probe, and it additionally promises that after i failed probes the next one is uniform over the m − i slots not yet examined, which is exactly the step the proof in §18 takes. The awkward truth is that H2 is false for every scheme anyone actually uses. Linear probing has m possible probe sequences, quadratic probing has m, double hashing has about m²; uniform hashing demands m!, which is astronomically more. So the probe theorems are a model, and the right way to read them is: this is how a perfectly randomised scheme would behave, and real schemes are compared against it. Double hashing comes close; linear probing does not, and has its own separate theorems because of it.

H3: universality — the one you can actually guarantee

The third is different in kind. H1 and H2 are assumptions about the world, unverifiable and falsifiable by an adversary who picks your keys. H3 is a property of a family of hash functions that can be proved once and for all, and it moves the randomness from the keys to the algorithm: pick h at random from the family when the table is created, and the collision probability bound holds for every fixed key set, including one chosen by an adversary who knows the family but not your draw. It is weaker than H1 in an important way — it only constrains pairs of keys, saying nothing about triples or about the shape of the whole distribution — and yet, remarkably, pairwise is all the chaining analysis ever uses, so H3 recovers the chaining bounds with no assumption about the keys at all. That is the content of §22, and it is the single most important idea on this page.

How to read every bound that follows

From here on, each cost claim is stated in the form (quantity, value, hypothesis), and the hypothesis is never omitted. The discipline matters because the six probe-cost formulas in §18 look interchangeable and are not. They come in three groups of two — a successful and an unsuccessful figure each. Two are theorems under H2; two hold under a different model specific to linear probing, in which the initial positions are uniform but the sequence is a fixed scan; and two are approximations under a secondary-clustering model for quadratic probing, not theorems at all. Quoting the uniform-hashing formula for linear probing understates linear probing's cost at high load by a factor that the figure there measures at over five. Use the wrong one and you will conclude that a 90%-full linear-probing table costs 10 probes on an unsuccessful search when it costs about 50.

07 The division method, and why m should be prime

The simplest compression is the remainder: h(k) = k mod m. One instruction on most machines, no tuning constants, defined for every key once the key is an integer. Its entire behaviour is governed by number theory rather than by intuition, and the governing fact is short enough to state exactly: the remainder map preserves any arithmetic structure in the keys whose step shares a factor with m. Choosing m prime is not a superstition or a rule of thumb — it is the choice that makes that shared factor impossible for every step except multiples of m itself.

One in the divisor, and the table goes from two usable slots to seventeen. Notice also what the prime case looks like: the slots are not consecutive, they walk the table in a stride of 8, which is the behaviour you want — the progression's structure is still there, it has simply been rotated into a stride that visits everything. That distinction matters again in §14, because a stride of 8 produces scattered singletons while a stride of 1 produces one long cluster, and linear probing cares about the difference enormously even though chaining does not care at all.

Why "prime, and not near a power of two"

The primality half is the gcd argument above. The second half — avoid primes just above or below 2^p — guards against a different pattern. If the hash code is built by a polynomial in radix 2^b (which is what every byte-at-a-time string code is), then codes that differ by a shift or a character permutation differ by multiples of quantities close to powers of two, and a modulus close to a power of two folds those differences into a narrow band of slots. The specific pathological case is m = 2^p − 1 with a radix-2^p code: then 2^p ≡ 1 (mod m), so every positional weight in the polynomial collapses to 1 and the code reduces to the sum of the characters, making every anagram of a key collide with it. That is not a mild bias; it is an exact, constructible collision family, and it is the cleanest argument available that the modulus and the hash code must be chosen with knowledge of each other.

The honest case for powers of two

Despite all of the above, a great many high-performance tables use m = 2^p and mask instead of dividing, and it is worth saying why rather than treating it as a mistake. An integer division or remainder costs on the order of ten to forty cycles depending on the core generation, against one cycle for a bitwise AND; at small table sizes that difference is comparable to the entire rest of the lookup. The trade those implementations make is explicit: pay for a strong mixing step in the hash code, then mask. If the code has good avalanche, its low bits are as good as any other bits and the gcd argument has nothing to bite on, because the key's arithmetic structure was destroyed before compression saw it. The rule that emerges is a conditional, and it is the accurate form of the folklore: with a weak or identity-like hash code, use a prime modulus; with a strong avalanching code, a power of two and a mask is faster and equally good. What is never safe is a weak code and a power-of-two mask, which is the configuration the figure below shows collapsing.

At the default setting — 64 identifiers spaced 8 apart, no mixing — the three panels show the gcd theorem playing out exactly. The power-of-two table puts all 64 keys on 64/gcd(8,64) = 8 slots, eight keys deep, leaving seven-eighths of the array untouched. The composite modulus 66 does better but not well: gcd(8,66) = 2, so only 33 of its 66 slots are reachable, and with 64 keys crowded onto them 31 of the 33 hold two keys and two hold one. The prime 67 shares no factor with 8, reaches all 64 keys' worth of distinct slots, and its longest bucket is 1. The readout checks the three measured counts against min(n, m/gcd(8, m)) computed independently, and they agree. Note what this shows and does not: being composite is not itself the problem, sharing a factor with the stride is — switch the pattern to ids spaced 100 apart and the power-of-two table improves from 8 slots to 16, because gcd(100,64) = 4 rather than 8, while 66 is unchanged at 33 since gcd(100,66) = 2 just as gcd(8,66) was. Neither is repaired; only the prime is immune to every stride that is not a multiple of it, which is the whole of its advantage and the reason the rule is stated as "prime" rather than "not a power of two". Now tick mix the code first and all three moduli become indistinguishable, because the avalanche step destroyed the stride before compression ever saw it — which is the conditional rule stated above, demonstrated rather than asserted. Switch to unstructured random ids and the three moduli agree with or without mixing: the choice of m only matters when the keys have structure, and the whole difficulty is that real keys usually do and you usually cannot see it.

08 The multiplication method

The second classical construction multiplies rather than divides: scale the key by an irrational-looking constant, throw away the integer part, and read the slot off the fraction that remains. Its practical attraction is the mirror image of the division method's — here the value of m is not critical, so m can be a power of two and the whole computation becomes a multiply and a shift, with no division anywhere. The structure it destroys is different too: where the remainder rotates an arithmetic progression into a stride, multiplication scatters a progression across the table in a pattern with a provable spacing property.

Each step adds A mod 1 to the fraction and wraps, so the successive slots advance by 16 × 0.618 ≈ 9.9, landing about ten slots further on each time, modulo 16. That is the golden ratio doing its one trick, and it is worth stating what is and is not special about it. The three-distance property is not: for every irrational A, the first N points cut the unit interval into gaps of at most three distinct lengths. What the golden ratio adds is that those gaps stay close to equal. Because its continued fraction is all ones it is the worst-approximable irrational, so the sequence never settles into a short cycle and never clumps, and the ratio of the longest gap to the shortest never exceeds φ² ≈ 2.618 at any prefix length — a bound no other constant improves on. An A that is a good rational approximation, by contrast, still gives three gap lengths, but one of them is enormous and the table has a hole in it.

What the method does and does not buy

  • It buys freedom in m. This is the headline. Table sizes can be powers of two, so resizing is a doubling and compression is a shift — which removes the awkward business of keeping a table of primes around and dividing on every lookup.
  • It buys good behaviour on consecutive keys specifically. Sequential integer keys are extremely common — row ids, timestamps, counters — and this is exactly the pattern k mod 2^p handles worst for open addressing.
  • It does not buy adversary resistance. A is a fixed published constant, so an adversary can solve for keys that all land in one slot just as easily as with k mod m. Nothing with a fixed hash function resists an adversary; that requires §22.
  • It does not buy uniformity for all key distributions. The method is a heuristic, not a theorem. Keys whose low bits carry all the entropy, or keys that are themselves multiples of something near 2^w/s, can still clump. The constant matters: at A = 1/2 or 1/3 exactly, k·A mod 1 takes only two or three values and the whole table collapses to that many slots; at an A merely close to such a rational the collapse is not total but the points cluster in a few tight bands for a long initial run of k, which for the consecutive-key case that motivated the method is just as bad.

The modern descendant, and one honest caveat

The integer form above — multiply by an odd constant, take the high bits of the product — is the skeleton of nearly every fast mixing function in use today. Contemporary mixers iterate it: multiply by a large odd constant, exclusive-or the value with a shifted copy of itself, repeat two or three times, then take the top bits. The multiply provides diffusion from low bits upward, the shift-xor provides it downward, and alternating them gives avalanche in both directions, which a single multiply does not. The caveat worth stating plainly: taking the high bits of the product is not optional. A multiply moves entropy from the low bits of the input toward the high bits of the product, so the low bits of k·s depend only on the low bits of k — masking the product's low bits gives you back a disguised version of the division-by-power-of-two failure of §07. This is a good example of the fourth recurring error in systems reasoning: a plausible-sounding simplification that is exactly backwards.
