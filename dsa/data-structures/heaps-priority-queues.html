Heaps & Priority Queues

One decision — maintain a partial order instead of a total one — and everything here follows. A sorted array knows the rank of every element and pays Θ(n) to admit a new one; an unsorted array admits in O(1) and pays Θ(n) to find the smallest. A heap refuses both bargains. It promises only that every node beats its children, which is exactly enough to know the minimum and nothing more, and that single relaxation buys O(log n) for both insertion and extraction. The structure lives in a plain array with no pointers at all: the tree is an interpretation of the indices, the shape is forced to be complete so the array has no holes, and the two repair moves — sift up, sift down — walk a root-to-leaf path whose length is exactly floor(log₂ n). From there the page builds outward: a linear-time construction whose proof is a single geometric sum, heapsort as the heap applied to sorting, handles that make decreaseKey possible, wider branching, and the mergeable heaps that end at the Fibonacci heap, whose O(1) amortized decreaseKey is a potential-function argument and whose name is a theorem.

01 What a heap is

A binary heap is a complete binary tree in which every node's key is at least as good as the keys of its children, stored in an array by reading the tree level by level. Three clauses, and each one does work. Complete fixes the shape: every level is full except possibly the last, and the last is filled from the left with no gaps. Every node beats its children is the heap property, and it is deliberately weaker than "sorted": it says nothing about how two siblings compare, or how an uncle compares with a nephew. Level order in an array is the representation, and it is the reason a heap needs no pointers: the completeness clause guarantees that level order leaves no holes, so the parent and the children of the node at index i can be computed from i rather than stored.

Why each clause of the definition is load-bearing

  • "Every node beats its children" — and only that. A total order would let you answer "what is the k-th smallest?" for any k; the heap property answers it only for k = 1. That is the whole design bargain: by promising less, the structure can be repaired after a change by touching a single root-to-leaf path, instead of shifting everything that sits between the old and new positions. The cost of a repair is bounded by the tree's height, and the height is logarithmic because of the next clause.
  • "Complete" is what keeps the height at floor(log₂ n). A binary tree of n nodes can be a chain of height n−1. The heap property alone would permit that: a chain 9 → 7 → 5 → 3 satisfies "every node beats its children". Completeness forbids it by forcing every level to be full before the next one opens, so 2ʰ nodes fit on level h and n nodes need only floor(log₂ n)+1 levels. Balanced search trees earn the same height with rotations and extra bookkeeping; a heap gets it for free by refusing to be anything but complete.
  • "Level order in an array" is what removes the pointers. Completeness and level order together mean that the nodes of the tree are exactly the indices 0 … n−1, with the root at 0, its children at 1 and 2, theirs at 3 4 5 6, and so on: node i's children are always at 2i+1 and 2i+2. A search tree cannot do this — insertions land where the keys dictate, so the shape is not predictable and each node must carry links. A heap chooses the shape first (the next free slot, always) and moves keys to fit it. The array is a contiguous block, and everything that page says about constant-time indexing and about growth by doubling applies to the heap's storage unchanged.
  • "At least as good" rather than "greater than". Equal keys are allowed and are common — priorities tie constantly. The heap property is non-strict, and every routine on this page uses a strict comparison to decide whether to move, which is what stops equal keys from being swapped endlessly. Equal keys also mean the heap is not a stable structure: two entries with the same priority come out in an order the heap does not specify, and §24 shows the standard fix.

The motivation, as a cost argument against the alternatives

The job is a priority queue: admit items with keys, and repeatedly hand back the one with the smallest (or largest) key. Linked Lists, Stacks & Queues §26 names it as the third removal discipline — not the newest item, not the oldest, but the best — and sets out the two honest list-based answers. An unsorted list admits in O(1) and must scan all n to extract: Θ(n). A sorted list extracts in O(1) and must walk to the insertion point to admit: Θ(n). Over n insertions and n extractions both are Θ(n²) in the worst case, and neither can be fixed by cleverness, because both maintain a total order or none at all. The heap's proposal is the middle position that the list implementations cannot reach: maintain a partial order — just enough that the minimum is known — and pay O(log n) to restore it after either operation. Over n inserts and n extracts that is O(n log n), which is also what sorting costs, and that is no coincidence: a priority queue emptied in order is a sort, and a heap-based one is heapsort (§12). The losses are equally precise. The heap cannot find an arbitrary key without a linear scan, cannot iterate in sorted order without dismantling itself, and gives no successor or predecessor; §29 takes those seriously. And an array heap cannot be merged with another in less than linear time, which is the gap the mergeable heaps of §18 onward exist to close.

The one-sentence summary to carry through the page. A heap is a complete binary tree stored in an array, ordered only along parent–child edges; that is exactly enough to keep the extreme key at index 0, and every operation is a walk along one root-to-leaf path of length floor(log₂ n).

02 The array encoding: index arithmetic, 0-based and 1-based

A heap's tree is not stored, it is computed, and the computation is three integer formulas. There are two conventions in use — root at index 1, which makes the formulas prettier, and root at index 0, which is what every array language actually gives you — and they differ by exactly the shift j = i + 1. This page uses 0-based throughout, because the array on the page is a real 0-based array and an off-by-one in a heap is not a cosmetic bug: a wrong parent formula silently produces a structure that is almost a heap, and the first symptom is a wrong answer from extractMin several operations later.

Why the formulas work

Number the nodes of a complete binary tree in level order, 1-based. Level d holds nodes 2ᵈ … 2ᵈ⁺¹−1, i.e. 2ᵈ of them, and the k-th node of level d (counting k from 0) has number 2ᵈ + k. Its two children are the (2k)-th and (2k+1)-th nodes of level d+1 — every node on level d contributes two consecutive children on level d+1, in order — so their numbers are 2ᵈ⁺¹ + 2k = 2(2ᵈ + k) and 2ᵈ⁺¹ + 2k + 1 = 2(2ᵈ + k) + 1. That is left(j) = 2j and right(j) = 2j + 1, and inverting either gives parent(j) = floor(j/2). The 0-based forms follow by the shift above. The argument depends on completeness at exactly one point: "every node on level d contributes two children on level d+1" is true of every level except the last, and on the last level the missing children are precisely the indices ≥ n, which the leaf test catches. A tree with a hole in the middle of a level would break the numbering, which is why the shape clause of the definition cannot be relaxed.

Why the page chooses 0-based, and what it costs

The classical convention wastes a[0] (or uses it as a sentinel, as one traditional implementation does, storing +∞ there so that sift-up needs no "am I at the root?" test). The 0-based convention wastes nothing and matches the array the language hands you, at the price of a subtraction in parent. That subtraction is why the classic pitfall is parent(i) = i/2 in 0-based code: it is right for every odd i (1/2 = 0 ✓, 3/2 = 1 ✓) and wrong for every even i ≥ 2 (2/2 = 1, but 2's parent is floor(1/2) = 0; 4/2 = 2, but 4's parent is floor(3/2) = 1). Worse, it hides: used only in sift-up, the wrong path 4 → 2 → 1 → 0 still passes through the root's children, and an exhaustive run over every insertion order of up to six keys never produces an invalid heap. The first broken heap needs seven keys — index 6's "parent" 3 is a cousin, not an ancestor — so a test suite of small cases passes and production fails. 03 The height is exactly floor(log₂ n), and the other counts the proofs need

Every bound on this page is "a constant times the height", so the height must be pinned down precisely, not just as Θ(log n). For a complete binary tree of n ≥ 1 nodes it is exactly floor(log₂ n): not "about", not "at most", and the derivation is two inequalities. The same argument yields the three other counts that the build-heap proof (§10) and the sift bounds (§06, §07) rest on: the number of leaves, the index of the last internal node, and the number of nodes at each height.

Why the counts are what the proofs need

The sift bounds need the height because a sift is a walk along one path. Sift-up starts at the last index and climbs at most its depth, floor(log₂ n) edges; sift-down starts at the root and descends at most the height, floor(log₂ n) edges. The build-heap proof needs the per-height count because it charges each internal node for a sift-down that costs O(its height), and then sums: ∑ over h of (nodes of height h) × h ≤ ∑ ceil(n/2ʰ⁺¹) × h, which is where the geometric series in §10 comes from. The leaf count is why the build loop starts at floor(n/2) − 1: everything from floor(n/2) onward is a leaf, and a leaf is a one-node heap that needs no work. Getting that start index wrong by one in either direction is harmless in one direction (sifting a leaf does nothing but one bounds check) and a silent bug in the other (skipping the last internal node leaves one parent–child pair unchecked).

04 The priority queue ADT, and what it does not promise

A priority queue is an abstract type holding a collection of entries, each with a key drawn from an ordered set, that can always hand back an entry with the extreme key. It is defined by behaviour, not storage: a heap is one implementation, a sorted list is another, a Fibonacci heap is a third, and keeping the ADT separate from the structure is what lets the page compare them honestly. The distinction that matters most is between the four core operations that every implementation supports, and the three extended ones — decreaseKey, delete, merge — that separate the implementations from one another and that graph algorithms lean on.

What the ADT promises

  • An extreme entry, not a sorted view. findMin and extractMin are the only order-dependent queries. There is no "second smallest", no "all entries with key below k", no ordered iteration. Every implementation that supports those cheaply is doing more than a priority queue, and paying for it — see §29.
  • Ties are unspecified. Two entries with equal keys may come out in either order. Most heap implementations break ties in a way that depends on the history of the structure, which means a priority queue used as a FIFO among equal priorities will usually look right and occasionally reorder. §24 gives the standard fix, a sequence number as a secondary key.
  • Values are opaque; keys are compared and nothing else. A heap never hashes a key, never tests equality, never asks for a successor. It needs exactly one thing from the key type: a comparison that is a total preorder. A comparison that is not transitive — floating-point NaN, a "compare by length, then by whatever" that forgets the "then" — breaks the heap silently: the heap property becomes unsatisfiable and extractMin starts returning non-minima with no error.
  • decreaseKey moves in one direction. Lowering a key in a min-PQ can only move the entry toward the root; raising it can only move it away. An implementation that supports the general "changeKey" does so by sifting in whichever direction is needed, and the two directions have different costs on some structures (a Fibonacci heap's decreaseKey is O(1) amortized; its increaseKey is not, and is implemented as delete-then-insert).

What the extended operations are for, and why they are separate

The core four are what a scheduler or an event-driven simulation needs: jobs arrive with priorities, the highest runs next; events are scheduled at times, the earliest fires next, and firing it may schedule more. Nothing there ever changes the priority of a waiting entry. The extended operations exist because graph algorithms do. Dijkstra's shortest paths and Prim's minimum spanning tree both keep every unvisited vertex in a min-PQ keyed by its best-known distance, and every relaxation of an edge lowers a key: that is decreaseKey, called once per edge in the worst case, up to E times, against only V extractMins. Which operation dominates decides which structure wins, and §23 works through that arithmetic. Merge exists for a different reason: some algorithms build many small priority queues and combine them, and an array-based heap simply cannot combine two arrays in less than linear time, which is why the mergeable heaps from §18 onward abandon the array. The bare ADT does not require any of the three, and the most widely used library priority queues (§24) implement none of them in logarithmic time — at most a linear-time remove — which is why the lazy-deletion workaround in that section is as important in practice as the operations themselves.

The comparison with the other two removal disciplines — LIFO and FIFO — is made properly in Linked Lists, Stacks & Queues §26, which also makes the point this page will not contradict: a stack and a queue can each be simulated by a priority queue (key = a counter, decreasing or increasing), so the priority queue is the general structure and the other two are the special cases where the key is arrival time. The reverse is false: no fixed-key discipline recovers "by value".

05 The three naive implementations, and the sorts they secretly are

Before the heap there are three honest ways to build a priority queue out of things already on the shelf, and each is worth knowing for two reasons: one of them is the right choice in a specific setting, and all three, when used to sort, turn out to be sorting algorithms you already know. The bounded case — priorities drawn from a small fixed set — has a fourth implementation that beats everything on this page, because it is not really a priority queue at all.

Why the two lists cost what they cost

The unsorted list maintains no order, so insertion is free and every query must look at everything — and it must look at everything because any element could be the minimum. The sorted list maintains a total order, so every query is free and every insertion must find and open the right slot, which on average is halfway along. The pair is the clearest illustration of why the heap's partial order is the right target: total order costs Θ(n) per insert to maintain and answers questions nobody asked; no order costs Θ(n) per query. A partial order that only orders each node against its parent can be restored along one path, and the tree's height makes that path short. Everything in §06 and §07 is the mechanics of "restore along one path". The linked and array variants of each list differ only in constants: a linked unsorted list appends and unlinks in O(1) but scans through pointers, an array appends in amortized O(1) and scans contiguously; a sorted linked list splices in O(1) once the position is found, a sorted array must shift.

Where the naive versions are the right answer

The unsorted list wins when insertions vastly outnumber extractions — a log that is occasionally asked for its worst entry — and it wins outright, not on constant factors, whenever decreaseKey with a handle dominates: lowering a key is one field write, and there is no order to repair. That single fact is why Dijkstra's algorithm on a dense graph is best run with an unsorted array as its priority queue: V extractMins at Θ(V) each plus E decreaseKeys at O(1) each is Θ(V² + E), which for E near V² beats the binary heap's O((V + E) log V). Linked Lists §26 makes that point and this page does not re-derive it; §23 puts it in the full table. The sorted list wins when arrivals are nearly in order — a simulation that mostly schedules events in the near future inserts near the front and walks a short way — and the bounded array-of-queues wins whenever it applies, because O(p) with p a small constant is O(1), and it gives FIFO order among equal priorities without any of the tie-breaking machinery of §24. A process scheduler with 32 priority levels is the canonical case, and it is not an approximation of a heap: it is a better structure for that problem.

The sorting correspondence, made exact

Phase one inserts all n elements; phase two extracts n times, and the extracted sequence is sorted. With an unsorted list, phase one is n appends (Θ(n)) and phase two scans n, then n−1, then n−2 … elements to find each minimum: ∑ (m − 1) = n(n−1)/2 comparisons, Θ(n²), regardless of the input — that is selection sort, and its indifference to input order is inherited. With a sorted list, phase two is n pops (Θ(n)) and phase one inserts element i into a sorted prefix of length i−1, walking past everything larger: that is insertion sort, and its best case — every walk of length 0 or 1 — is Θ(n). Which input order that is depends on which end the walk starts from: a min-first list walked from the front is Θ(1) per insert on descending input and Θ(n) per insert on ascending input, its worst; an array insertion sort scanning back from the tail is the reverse. The heap does both phases in O(n log n); heapsort is exactly this scheme with the priority queue kept inside the array being sorted, and §12 shows the trick that makes it in-place. What the correspondence teaches is that "which priority queue" and "which sort" are the same decision seen from two sides, and that a priority queue's cost profile can be read off the sort it induces.

06 Sift-up: insertion, and its bound of floor(log₂ n) comparisons

Insertion has two halves, and the order matters. First the shape is restored: the new key goes into the one slot that keeps the tree complete, which is index n — the next free cell of the array. Then the order is restored: the new key may be better than its parent, in which case they swap, and the check repeats one level up until the key is no better than its parent or has reached the root. That climb is sift-up. It touches one root-to-leaf path from the bottom, so it costs at most the depth of the last index — which by §03 is floor(log₂ n) for the new size n.

Why the climb is correct, and why it stops

Before the append, the whole array is a heap. Appending at index n creates a tree that is still complete (the new node is the leftmost free position on the bottom level, or the first node of a new level) and satisfies the heap property at every edge except possibly the one from the new leaf to its parent — a leaf has no children to violate anything below it. That is the invariant with i = n. Each iteration either finds a[i] ≤ a[parent(i)], in which case the one possibly-bad edge is in fact fine and the whole array is a heap, or swaps. After the swap the risen key sits at parent(i) and is greater than the key it displaced, which was already greater than its other child and everything below; and the displaced key now at i is smaller than the risen key above it, so the edge (parent(i), i) is fine. The only edge that can now be wrong is the one above parent(i), which is the invariant with i replaced by parent(i). Termination: i strictly decreases and the loop stops at 0. The subtlety is the strict comparison: with a[i] ≥ a[parent(i)] as the swap condition, equal keys would swap uselessly all the way to the root, still correct but wasteful and — for the tie-breaking discussion in §24 — a different ordering among equals.

The bound is on the depth of the last index, and it is exact

The new key starts at index n − 1 (after the increment) and can only move to its parent, so the number of swaps is at most the number of edges between that index and the root, which is its depth, floor(log₂((n−1)+1)) = floor(log₂ n). Each iteration performs exactly one comparison, and the loop runs one more time than it swaps unless it exits by hitting i = 0, so comparisons ≤ floor(log₂ n) as well. The bound is attained: insert a key larger than everything present and it climbs the full path. 07 Sift-down: extraction, and its bound of 2·floor(log₂ n) comparisons

Extraction is insertion run backwards, with one twist. The entry to remove is at the root; the slot that must disappear to keep the tree complete is the last one, index n − 1. So the last key is moved to the root, the size is decremented, and the moved key — which is almost certainly too small to be a root — is sifted down: at each node it is compared with its children, and if the better child beats it they swap and the check repeats one level down. The twist is that a node has two children and the key must swap with the better of them, which costs a comparison of its own. That is why sift-down's bound is 2·floor(log₂ n) comparisons against sift-up's floor(log₂ n), and why the comparison count is the number to watch in heapsort.

Why the extra comparison is unavoidable, and why it is the constant that matters

Suppose the sinking key is k and the children are x (left) and y (right), with k smaller than both. Something must rise to the parent's slot, and whatever rises becomes the parent of the child that stays. If x rises and x < y, the new parent x has child y > x: the heap property is broken at an edge the routine has already left behind and will never revisit. So the routine must rise the larger child, and knowing which is larger costs one comparison before the comparison against k. Two per level, then. The consequence is quantitative and it shapes heapsort: a sift-down from the root of an n-heap costs up to 2·floor(log₂ n) comparisons, and heapsort performs n − 1 of them on shrinking heaps, so its comparison count is about 2n·log₂ n rather than n·log₂ n — roughly twice mergesort's — and the bottom-up variant in §14 exists precisely to get that 2 back down toward 1.

The precondition is the point

Sift-down does not require the array to be a heap. It requires only that the two subtrees under i already are, and it then makes the subtree at i a heap. That local contract is what lets the same routine serve three callers: extractMax (i = 0, the subtrees are the old root's children, both intact), build-heap (§09, called on every internal node in reverse order so that the precondition is always met by induction), and heapsort's inner loop. The proof of the invariant mirrors sift-up's. At the start the two child subtrees are heaps and the only suspect edges are the two from i. If a[i] beats both children, all edges are fine and the subtree is a heap. Otherwise swapping with the larger child makes the risen key ≥ both children (it beat one and was compared with the other) and ≥ everything beneath them (they were roots of heaps), so the edges from i are now fine — and the sunk key at `best` sits above a subtree that is still a heap, so the only suspect edges are the two from `best`. That is the invariant one level down, and the height strictly decreases, so the loop terminates at a leaf at the latest.

08 The two invariants side by side, and the "exactly one violation" principle

Both repair routines rest on the same idea, and it is worth stating once in general because every later structure on the page — d-ary heaps, index heaps, even the Fibonacci heap's cut — reuses it. A heap with exactly one misplaced key can be repaired by moving that key along a single path. If the key is too good for its position it moves toward the root; if it is too poor it moves toward the leaves; and in either case each step fixes the edge it is on and can only break the next edge along the same path, so the violation travels along the path rather than spreading.

Why the violation travels instead of spreading

Take sift-down. Before a swap at node i the suspect edges are (i, left) and (i, right). After swapping a[i] with the larger child c, three edges are affected: (parent(i), i), which now holds a larger key at i than before and so cannot have become worse — a[parent(i)] was ≥ the old a[i]'s children by the hypothesis that the edge above i was fine and the subtrees below were heaps; (i, other child), which is fine because the risen key was the larger of the two; and the edges (c, c's children), which are the new suspects because the sunk key may be smaller than c's children. Two suspect edges in, two suspect edges out, one level lower. The argument for sift-up is the mirror image with one suspect edge. The reason the argument needs the whole rest of the tree to be a heap is that the swap consults only the immediate neighbourhood; if some far-away edge were also broken, the local repair would leave it broken, and the routine would report success on a structure that is not a heap. That is exactly why build-heap (§09) processes nodes in reverse level order — so that when it reaches i, everything below i is already repaired and the precondition holds.

The delete-at-handle case, which needs both directions

Deleting the entry at index i by overwriting it with the last key and shrinking the heap is the one operation where the direction is not known in advance. The last key came from the bottom level, so intuition says "it is small, sift down" — and usually that is right. But the last key can be larger than i's parent: in a max-heap [50, 10, 40, 1, 2, 30, 35], deleting the 1 at index 3 moves the 35 from index 6 into index 3, where its parent is 10, and the 35 must sift up. An implementation that only sifts down after an arbitrary delete is wrong in a way that surfaces rarely, which is the worst kind of wrong; §30 lists it, and §16 shows the correct routine. The "exactly one violation" principle says why the fix is cheap: after the overwrite the array is a heap except at node i, and at most one of the two sifts will move anything.

Why "last internal node first" and not "first internal node first"

Run the loop the other way — i from 0 up to floor(n/2) − 1 — and it is wrong, not merely slower. Sift-down at node 0 assumes the subtrees at 1 and 2 are heaps; on an arbitrary array they are not, so the routine compares the root against two children that are not the maxima of their subtrees, and the key it promotes may be smaller than something deeper down. The "exactly one violation" principle of §08 is what fails: sift-down only repairs a structure that is a heap everywhere except at its start node, and the reverse loop is the order that makes that true when each call begins. The forward loop is an easy bug to write and a hard one to notice, because on many inputs it happens to produce a heap; the input [1, 2, 3] happens to survive it (the root promotes 3 and the result [3, 2, 1] is a heap), but [1, 3, 2, 4] does not: at i = 0 the root sees children 3 and 2 and promotes 3, the 1 sinks to index 1 and then past the 4 at index 3, leaving [3, 4, 2, 1]; at i = 1 the loop finds 4 above 1 and is satisfied; and the root 3 is left sitting below its child 4, because the forward loop never revisits index 0.

10 The Θ(n) proof: sum over heights, and why the geometric series saves it

The crude bound is n/2 calls to sift-down at O(log n) each, O(n log n). It is correct and it is loose, because it charges every node the height of the tree when sift-down from node i only descends the height of i's subtree, and most nodes have tiny subtrees. Half the nodes are leaves (height 0, never called). A quarter have height 1. An eighth have height 2. Charging each node its own height and summing gives a series whose terms shrink geometrically while the heights grow only linearly — and that series converges to a constant, so the total is a constant times n.

Where the 2 comes from, and what it does not include

The constant 2 is the value of the series ∑ h/2ʰ, and it enters twice in a way that is easy to double-count: once because at most n/2ʰ⁺¹ nodes have height h — the "+1" in the exponent halves everything — and once because a sift-down step costs two comparisons. Written out: n·∑ (2h)/2ʰ⁺¹ = n·∑ h/2ʰ = 2n. That is comparisons. For swaps the per-level cost is 1, and the same sum gives n·∑ h/2ʰ⁺¹ = n, so swaps are under n. What the bound leaves out is the ceiling's slack and the fact that a node with a single child costs one comparison rather than two; both push the true count below 2n, and the measured 14 on the ten-element example against the bound of 20 is that slack. Why this matters beyond heapsort

For heapsort the linear build is a nicety: the sorting phase is Θ(n log n) regardless, and a linear build shaves a lower-order term. For everything else the linear build is the whole point. "Heapify a list, then pop k times" is O(n + k log n), which for small k is linear — the k-smallest selection of §25. Dijkstra's initialisation, an event queue seeded from a file, a batch of jobs scheduled at once: each starts with n keys known in advance, and building in Θ(n) rather than O(n log n) is a factor of log n on the setup cost. The lesson generalises past heaps, too: whenever an algorithm does work at every node of a tree proportional to that node's height, the total is linear — not n log n — and the reason is always this series. The same sum bounds the total work of merging adjacent runs bottom-up, of building a segment tree, and of the "small heaps first" phase of several external-memory algorithms; recognising it saves a log factor each time.

11 Why n repeated insertions is Θ(n log n) in the worst case, and when it matters

The other way to build a heap — start empty and insert each key, the construction the literature calls Williams' method — is what you do when the keys arrive one at a time, and it is the construction most library priority queues perform if you push n items in a loop. Its worst case is Θ(n log n): insert the keys in ascending order into a max-heap and every new key is the largest so far, so every sift-up climbs to the root, and the total is ∑ depth(i) = ∑ floor(log₂(i+1)), which is n·log₂n − O(n). Its average case, over random insertion orders, is linear — a known and slightly surprising result: about 1.28n swaps and 2.28n comparisons. So the two constructions differ by a log factor in the worst case and by a constant factor of about 1.2 on random input, and both facts are needed to choose correctly.

Reading the two results together

The worst-case statement is a statement about input order, and the order that triggers it — sorted ascending into a max-heap, or sorted descending into a min-heap — is not exotic. Timestamps arrive in increasing order; a min-heap of event times fed by a clock is the benign direction, but a max-heap of scores fed by a monotone process is the malign one. So "repeated insertion is linear on average" is true and should not be taken as "repeated insertion is fine": it is fine for random input and it is a log factor worse on the one input shape that real systems produce constantly. Bottom-up construction has no bad input: it is under 2n comparisons for every permutation, and its worst shape (ascending, every node falling the full height) costs about 2n comparisons and n swaps against the 1.88n / 0.74n average. When all the keys are available, build bottom-up, and the choice is not close. When they are not — when they arrive over time — repeated insertion is what you have, and the average-case constant says it is not expensive.

The two heaps differ, and it matters exactly once

The three-element example shows that the two constructions produce different heaps from the same input, and it is worth being clear that this is not a bug in either: a heap is not a canonical form. There are many valid heaps on a given multiset, and which one you get depends on the operation history. The one place this bites is testing: an assertion that "heapify(x) equals repeated-push(x)" fails, and an assertion that a heap's array equals some expected array is brittle across implementations. The right test is the property — every parent beats its children — which every figure on this page re-checks after every run, and which is the only thing the ADT promises.

12 Heapsort: the heap applied to sorting, in place

A priority queue emptied in order is a sort, and heapsort is that idea with one trick that makes it need no extra memory: the heap and the sorted output share the array. Build a max-heap over all n slots. The largest key is now at index 0 and belongs at index n − 1, so swap them — and notice that the swap has done two things at once: it has placed the maximum in its final position, and it has moved the last key to the root, which is exactly the first half of extractMax. Shrink the heap by one so the placed key is outside it, sift the root down, and repeat. After n − 1 rounds the heap is a single key, which is the smallest, and it is already at index 0. The array is sorted ascending, and at no moment did the algorithm hold more than a constant number of keys outside it.

Why the swap is the whole trick

An extractMax on a heap of size m does three things: remembers a[0], moves a[m−1] to a[0], and shrinks. Heapsort observes that the slot a[m−1] just vacated is exactly where the remembered maximum belongs in the final order — the largest of the m smallest keys is the m-th smallest overall, whose sorted position is index m−1. So instead of remembering the maximum somewhere else, it swaps it into the vacated slot. The heap loses one slot at its right end and the sorted suffix gains one at its left end, and the two regions are always adjacent with no gap between them, which is what "in place" means here: O(1) extra space, not counting the input. The same trick does not work for a min-heap sorted ascending (the minimum belongs at the left end, where the heap's root is), which is why heapsort ascending uses a max-heap; to sort descending, use a min-heap.

Where the cost goes

The build is Θ(n) and is never the dominant term. The sort phase is n − 1 sift-downs from the root of heaps of sizes n−1, n−2, …, 1, each costing up to 2·floor(log₂ size) comparisons, so ∑ 2·floor(log₂ k) ≈ 2n·log₂n comparisons in the worst case and — this is the part that surprises — also in the typical case, because the key moved to the root came from the bottom level and is almost always small, so it almost always falls nearly the full height. That is why classic heapsort performs about twice the comparisons of mergesort and why the bottom-up variant of §14 exists. It is also why heapsort is not adaptive: the sort phase does not know or care whether the input was sorted, because by the time it starts, the build has scrambled the input into a heap either way. §13 makes those claims precise and measures them.

Why the best case is not better than the worst

The intuition to dislodge is "sorted input should be easy". For insertion sort it is: the walk stops immediately. For heapsort the sorting phase never sees the input; it sees a heap, and a heap built from sorted input looks like any other heap. The key that each round moves to the root is the last key of the current heap, which sits on the bottom level, and in a heap the bottom level holds keys that are, on average, among the smallest: a key at depth d has d ancestors all larger than it. So the moved key nearly always sinks nearly the whole way, and the round costs about 2·log₂(size) comparisons no matter how the input was ordered. The formal best-case result is more delicate than this picture and its proof is not reproduced here; what it establishes is that the cheapest possible input costs about half the worst case, still Θ(n log n), and that input is a specially constructed heap rather than anything sorted. Why "not stable" is structural, not incidental

A stable sort keeps equal keys in their input order. Heapsort moves keys along root-to-leaf paths that depend on the shape of the heap, not on the input order, and the three-element example in the formula block is the whole proof: two equal keys 2a and 2b (a before b in the input), and a smaller key 1, form a valid max-heap in input order — yet the first round takes the root, which is 2a, and places it at the far end, after 2b. No tie-breaking rule inside sift-down repairs this without extra information, because the routine cannot see input order; the fix is the one every unstable sort uses, augment the key with the original index, and it costs space. When stability matters, mergesort or a library's stable sort is the answer, and heapsort's role is elsewhere: as the guaranteed-Θ(n log n) fallback inside introsort when quicksort's recursion goes too deep, and as the in-place sort when memory is the constraint.

14 The bottom-up variant: one comparison per level on the way down

Classic sift-down pays two comparisons per level — which child is larger, then does it beat the sinking key — and the second one is almost always wasted during heapsort, because the sinking key came from the bottom of the heap and is going back there. The bottom-up variant refuses to ask the second question until it has to. Walk the path of larger children all the way to a leaf, one comparison per level; then climb back up that path comparing the sinking key until it fits; then shift the path up by one and drop the key in. The descent costs log₂n, the climb usually costs only a few steps, and the total comparisons per extraction fall from about 2·log₂n toward log₂n + O(1).

Where the saving comes from, and where it does not

Count comparisons for one extraction on a heap of height h. Classic: up to 2h. Bottom-up: h on the descent, plus the climb. The climb is a search for the insertion point of v along a sorted path of h+1 values, done linearly from the bottom, and for a key that belongs near the bottom it costs one or two comparisons. That is the average case, n·log₂n + O(n), a genuine halving. The worst case is the climb going all the way back up — v belonging at or near the root — which costs 2h again, and an adversary can arrange it for a constant fraction of extractions, hence 1.5·n·log₂n + O(n); the number of such extractions is limited because a key that belongs near the root is large, and large keys are extracted early. The variant does not reduce data movement: the path values all shift by one, which is the same number of writes the classic version makes in swaps (fewer, in fact, if the classic version does three-assignment swaps). And it does not help the build phase, where sift-down starts from an arbitrary internal node with a key that may belong anywhere in its subtree; the build stays as in §09.

What the measurement shows, and a caution about reading it

In the second view of the figure in §13, the variant's comparison count sits at about 1.03·n·log₂n on random input at n = 8192 against the classic 1.76 — a 42% reduction in comparisons. Whether that is a 42% reduction in time depends on what a comparison costs relative to a memory access, and for keys that are cheap to compare and heaps that do not fit in cache, it is not: both variants touch the same cells in the same order, and the cost of heapsort at scale is dominated by the cache misses of the scattered access pattern (§28), not by the comparisons. The variant matters most when comparisons are expensive — long strings, records compared by several fields, a comparator that calls out to something — and that is where it is used. The lesson is the one Algorithm Analysis makes in general: a comparison count is a model, and the model's currency has to be the expensive one for the count to predict time.

15 Heapsort against mergesort and quicksort: where it wins, and why it usually loses

Three algorithms share the Θ(n log n) class and they are chosen for three different reasons. Mergesort is the stable one and the one whose access pattern is sequential. Quicksort is the fast one on average, with a quadratic worst case that randomisation makes negligible in practice. Heapsort is the guaranteed one: Θ(n log n) on every input with O(1) extra space, no randomness, no recursion. That combination is rare and valuable, and it is also why heapsort is rarely the sort you call directly and often the sort that runs underneath.

Why quicksort usually beats it, despite a worse worst case

Quicksort's partition scans two pointers inward through a contiguous range: every access is the next cell or the previous one, the hardware prefetcher predicts it, and a cache line fetched for one key serves the next fifteen. Heapsort's sift-down jumps from index i to 2i+1 or 2i+2, then to roughly 4i, then 8i: after the first three or four levels every access is a different cache line, and none of them is predictable. §28 measures the gaps. At n small enough for the whole array to sit in cache the two are close and heapsort's guarantee is nearly free; at n large enough that the heap spans many pages, the cache-miss count is what the clock measures, and quicksort's sequential scans are the reason its lower comparison count turns into a larger time advantage than the comparison ratio alone would predict. Mergesort makes the same argument from the other side: its merge is also sequential, and a well-implemented mergesort is often faster than heapsort even before stability is considered.

Introsort, the compromise that is usually what "sort" means

The standard resolution is to not choose. Introsort runs quicksort, tracks the recursion depth, and if the depth exceeds a small multiple of log₂n — evidence that the pivots have been bad and the quadratic case is being approached — switches the remaining subproblem to heapsort, whose bound does not depend on pivots. The typical input never triggers the switch and gets quicksort's speed; the adversarial input triggers it and gets heapsort's guarantee. Heapsort's O(1) extra space is what makes it the natural fallback: the switch happens in the middle of a recursion that has already budgeted only O(log n) stack, and a fallback that needed Θ(n) extra memory would violate that. 16 Handles: decreaseKey and delete on an array heap, via the inverse map

The heap knows where its minimum is and nothing else. To lower the key of an arbitrary entry — the operation Dijkstra's algorithm performs once per edge — it must first find the entry, and a scan is Θ(n), which would make the whole exercise pointless. The fix is to make the heap adaptable: keep, alongside the array, an inverse map from each entry's handle (the caller's name for it: a vertex id, a task id, a locator object) to its current index, and update that map every time a swap moves an entry. Then decreaseKey is a map read, a key overwrite, and a sift-up; delete is a map read, a move-in of the last entry, and a sift in whichever direction the "exactly one violation" principle of §08 demands. Why the inverse map costs nothing asymptotically and everything in practice

A swap on a plain heap is three assignments; on an index heap it is two such exchanges (key and item) plus two map writes, and the map is either an array indexed by a dense integer handle (a vertex number — the common case in graph algorithms, and O(1) with no hashing) or a hash table keyed by an arbitrary handle (O(1) expected, with a constant that is not small). The asymptotic cost of every operation is unchanged, O(log n), because the map adds O(1) per swap. The practical cost is that every heap operation now touches a second array with an unrelated access pattern, which roughly doubles the cache traffic of a structure whose cache behaviour was already its weak point (§28). That is the reason library priority queues almost never offer decreaseKey (§24): the map would be paid for by every user, and most users never change a key. The users who do — Dijkstra, Prim, A*, event simulations that reschedule — either write the index heap themselves, or use the lazy-deletion trick that avoids the map entirely at the cost of a larger heap.

Why delete needs both directions

The entry moved into the vacated slot is the last entry of the heap, and its key can be anything relative to the vacated slot's neighbourhood: smaller than the parent (then it must rise) or larger than a child (then it must fall), and — because the vacated slot was in a valid heap — never both. The second worked example is the case implementations get wrong: the moved-in 4 came from the bottom level, "so it must be small, so sift down" — but it landed under a 20, and the correct move is up. The test is one comparison against the parent, and the cost of omitting it is a heap that passes every extractMin test on small inputs and returns a wrong minimum on the input where a delete happens to land a small key under a large parent. A delete of the root is just extractMin, and a delete of the last entry needs no sift at all; the general routine handles both as special cases of "compare, then sift the right way".

Where the trade really lives

The theorem is a worst-case statement and it is worth being precise about that, because the figure below measures both a worst-shape workload and a typical one and they disagree. In the worst shape — every insert and every decreaseKey climbs the full height — insert and decreaseKey cost log_d n comparisons each and shrink as d grows, extract costs about d·log_d n and grows, and the total for a workload with many key changes per extraction is minimised at a d that rises with that ratio: the textbook picture. In a typical workload, a random key inserted at the bottom beats its parent with probability about 1/2 and its grandparent with about 1/4 whatever d is, so a climb is short at every d and insert and decreaseKey cost about the same small constant for every width; extract still costs d·log_d n, so extract decides, and d = 3 or 4 wins the comparison count regardless of the ratio. The moral is not that d-ary heaps are useless — it is that their advantage is a worst-case guarantee on the insert side, and a cache-line effect on the extract side, rather than a typical-case comparison saving.

The d-ary heap and the graph algorithms

Dijkstra's algorithm with a binary heap runs in O((V + E) log V). With a d-ary heap tuned to d = E/V the bound becomes O(E·log_(E/V) V), which for dense graphs (E = Θ(V²)) is O(E) — matching the unsorted-array implementation that Linked Lists §26 identifies as the dense-graph winner — and for sparse graphs (E = Θ(V)) is O(V log V), matching the binary heap. It interpolates. What it cannot do is beat O(E + V log V), the Fibonacci heap's bound in §23, on graphs in between; and in practice it is usually the simplest of the three structures to make fast, because it is still one array. Algorithm Analysis's point about constants and crossovers applies with full force: the d that minimises comparisons, the d that minimises cache misses, and the d that minimises wall-clock time are three different numbers, and only the last one matters.

18 Mergeable heaps, and the binomial heap as the bridge to Fibonacci

An array heap cannot be merged with another in less than linear time: the two arrays must become one array, and building a heap over their concatenation is Θ(n) at best. Every structure that merges faster gives up the implicit array for linked nodes and gives up the single complete tree for a collection of trees. The binomial heap is the cleanest of these, and it is worth understanding on its own terms because the Fibonacci heap of §19 is a binomial heap that has been allowed to become lazy: the same trees, the same linking rule, with the tidying deferred until an extractMin forces it.

Why "at most one tree per degree" is the whole design

The uniqueness rule is what keeps the root list short — log n trees — so that finding the minimum among the roots is cheap, and it is what makes merge a mechanical procedure: two heaps with unique degrees combine like two binary numbers, and the carry is a LINK. Everything else follows from the shape of Bₖ. Because Bₖ's root has k children which are themselves B₀ … Bₖ₋₁, removing the root of any tree leaves a valid binomial heap in one step, with no sift-down at all; the "repair" after extractMin is just a merge. And because a tree of degree k has 2ᵏ nodes, degree is bounded by log₂n, which is the fact the Fibonacci heap will have to work to recover once it lets trees lose children. The binomial heap is what you get if you insist that every operation be O(log n) worst case and that merge be among them; it is not faster than a binary heap on any operation except merge, and its constant factors are larger because every node carries pointers.

The step from binomial to Fibonacci, in one sentence

A binomial heap consolidates on every insert and merge, so that the root list is always tidy; a Fibonacci heap never consolidates on insert or merge — it just appends to the root list in O(1) — and pays for the mess all at once when extractMin has to scan the roots anyway, using the same LINK primitive to restore "at most one tree per degree" then. That deferral is what turns insert and merge into O(1) amortized. The second change, which is what makes decreaseKey O(1) amortized, is to allow a node to be cut out of its tree and dropped into the root list rather than sifted up, with a marking rule that limits how far the trees can degrade from binomial shape. The next four sections take those two ideas in turn and end with the theorem that gives the structure its name. Algorithm Analysis supplies the potential method the accounting rests on, and Linked Lists §08 supplies the circular doubly linked lists that make every splice O(1).

19 Fibonacci heaps: the structure, the potential Φ, and the lazy operations

A Fibonacci heap is a collection of min-heap-ordered trees of arbitrary shape, linked into a circular doubly linked root list, with a pointer to the root holding the minimum. Each node carries its key, its parent, one child pointer into a circular doubly linked list of its children, its degree (number of children), and a one-bit mark recording whether it has lost a child since it last became somebody's child. The design principle is do as little as possible, as late as possible: insert and merge just splice root lists in O(1) and do no tidying; the tidying is deferred to extractMin, which has to scan the roots anyway. The accounting that makes the deferral honest is the potential method, with a potential that counts exactly the two kinds of untidiness the lazy operations create.

Why inserting lazily is safe

A binomial heap inserts by merging a one-node tree and immediately carrying: O(log n) worst case, O(1) amortized by the binary-counter argument. A Fibonacci heap skips the carrying. After k inserts into an empty heap there are k one-node trees in the root list, which is ugly, and the potential records the ugliness: Φ = k. The next extractMin will have to look at all k roots — its actual cost is Θ(k) — but consolidating them links them into O(log k) trees and the potential drops by nearly k, so the amortized cost of that extractMin is only O(log k). The k inserts each paid one unit in advance, the extractMin spent them. That is the whole logic of the structure, and the figure in §20 shows exactly this sequence: seven lazy inserts, Φ = 7, one extractMin, Φ = 2. Merge is the same story with two root lists instead of one: the splice is O(1), the potential is additive, and whatever mess the two heaps brought with them is paid for by the extractMin that eventually tidies it.

What the structure gives up

The trees have no fixed shape and no array; every node is a separate allocation with four pointers, a degree and a mark, so the constant factors are large and the memory traffic is worse than an index heap's. There is no search: as with every heap, decreaseKey and delete need a handle, and here the handle is the node pointer itself, which the caller must keep. The bounds are amortized: a single extractMin can cost Θ(n) actual time (right after n inserts), which rules the structure out wherever a per-operation worst case matters — real-time schedulers, interactive latency budgets. And the O(1) is for decreaseKey only; increaseKey is delete-then-insert, O(log n) amortized. All of this is why §23 will conclude that the Fibonacci heap is the structure that proves the O(E + V log V) bound for Dijkstra and rarely the structure that runs it. None of this makes the analysis less worth knowing: it is the cleanest worked example of the potential method on the site, and the reasoning transfers to every lazy structure.

21 decreaseKey in O(1) amortized: cut, don't sift, and cascade

In a binary heap, lowering a key means sifting it up: O(log n) comparisons along a path. A Fibonacci heap refuses to walk the path. If the decreased key is now smaller than its parent, the node is simply cut out of its tree and dropped into the root list, where it is a root and the heap order is trivially satisfied. That is O(1). The catch is that cutting children out of trees makes them thin, and a thin tree of degree k with few nodes would break the D(n) = O(log n) bound that extractMin depends on. The mark is the damage limiter: a node may lose one child and be marked; when it loses a second, it is cut too — a cascading cut that may run up several ancestors — so that no non-root node ever has lost more than one child. The cascade can be long, but every marked node it cuts had paid two units of potential in advance.

Why cutting preserves heap order and why the cascade is bounded

A cut node becomes a root, and a root has no parent to be ordered against, so the only edge the decrease could have broken — the one above x — is removed rather than repaired; every other edge is untouched. The subtree under x moves with it and was already ordered. That is why there is no comparison at all beyond the one against the parent: the structure handles a decrease by forgetting the relationship instead of fixing it. The cascade's length is unbounded in the worst case for a single call (a chain of marked ancestors of any length can be built), and that is exactly what the potential absorbs: each marked node on the chain contributed 2 units when it was marked, the cut consumes them, and the total over any sequence is what the O(1) amortized bound describes. The figure's example is built to hit the bound with equality — c = 3 cascading-cut calls, two of which cut and one of which marks, ΔΦ = +1 = 4 − c — so the inequality in the theorem can be seen to be tight, not slack.

Where the marking rule enters, precisely

Lemma 1 is the only place the marks are used, and it uses them in one clause: "since then, yᵢ has lost at most one child". Without cascading cuts a child could lose all its children and keep its place, degree(yᵢ) could be 0 for every i, and a node of degree k could have exactly k+1 descendants — no exponential bound, D(n) could be n − 1, and extractMin would be O(n) amortized. With a rule that cut a node after losing its j-th child instead of its second, the recurrence would become sₖ ≥ j + ∑ᵢ₌ⱼ..ₖ sᵢ₋ⱼ, still exponential with a smaller base for every fixed j — the "2" is the tightest choice that keeps the constant small, not the only one that works. And the reason the mark is cleared when a node becomes a root (in CUT) or a child (in LINK) is that Lemma 1 counts losses since the node was linked: a fresh link starts a fresh count.

Why "Fibonacci" and not "golden ratio", and what the bound is worth

The structure is named for the lemma, not the constant: the minimum subtree sizes satisfy the Fibonacci recurrence exactly, because a degree-k node's children have degrees at least 0, 0, 1, 2, …, k−2 and the minimum sizes of those add up, by identity (I), to the next Fibonacci number. The constant φ is what falls out when the recurrence is solved. In practical terms the bound says that the trees may be about 1.44× taller in degree than binomial trees of the same size, so consolidate's degree table is 44% longer and extractMin's constant is correspondingly worse — one more entry on the ledger of why §23 finds the structure's practical performance disappointing despite its bounds. The proof itself is the durable thing: it is the template for every "lazy structure with a damage-limiting invariant" analysis, and the same shape of argument — bound the size from below by a recurrence the invariant enforces — reappears in the analysis of pairing heaps and of splay trees.

Why the Fibonacci heap loses the race it wins on paper

Three reasons, each of which the earlier sections set up. The bounds are amortized, so a single extractMin may take Θ(V) — harmless for a total running time but visible as latency. The constants are large: four pointers, a degree and a mark per node, a consolidate that walks a degree table 44% longer than a binomial heap's (§22), and every operation a pointer chase through separately allocated nodes, against a binary heap whose entire state is one array. And the operation it optimises is the one that matters least in practice: on many graph families met in practice the number of decreaseKeys that actually happen is far below E, because most relaxations do not improve on the current tentative distance and never reach the queue — so the term the Fibonacci heap optimises is smaller than the bound assumes. Published benchmarks comparing priority queues inside Dijkstra's algorithm consistently rank binary and d-ary heaps, and pairing heaps, ahead of Fibonacci heaps by constant factors that are not small; the specific ratios depend on the graph family and the hardware, and this page has not measured them, so it reports the ordering and not a number.

What is used instead

A 4-ary index heap is a common choice when decreaseKey is implemented: the four children of a node share a cache line (with the array padded so child groups are 4-aligned), the height is half a binary heap's, and the index map is a plain array indexed by vertex id (§16, §17). A binary heap with lazy deletion is what most library-based implementations do, because the library provides no decreaseKey: instead of lowering a vertex's key, push a fresh (distance, vertex) pair and, on extraction, discard any pair whose distance is stale; the heap grows to O(E) entries in the worst case, the log term becomes log E ≤ 2 log V, and no index map is needed — §24 spells out the mechanics. A pairing heap is the practical compromise for algorithms that genuinely need a fast decreaseKey with merging: a self-adjusting multiway tree with three pointers per node (child, sibling, and a back pointer — the third is what decreaseKey needs), O(log n) amortized extractMin, and a decreaseKey whose amortized cost is not O(1) — the proven bounds lie between Ω(log log n) and 2^O(√(log log n)) — but whose measured performance beats the Fibonacci heap on the workloads that matter. The pattern is the one Algorithm Analysis warns about: an asymptotic improvement on one term of a sum, purchased with constants that dominate the whole sum at every n anyone runs.

What a library heap is for, and the two ways people misuse it

The first misuse is treating the heap's array as sorted. It is not: iterating a heap yields keys in level order, which is sorted only along root-to-leaf paths, and "the second element of the heap array is the second smallest" is false as often as it is true. To read the k smallest in order you must pop k times, and to read all n in order you must pop n times — which is heapsort — or copy and sort. The second misuse is calling a linear-time "remove(x)" in a loop and expecting a logarithmic structure: a library that offers arbitrary removal without handles implements it by scanning, and n removals are Θ(n²). Lazy deletion is the answer to both: keep the heap append-only, keep the truth about each item outside it, and let stale entries surface and be discarded at pop time. The cost is the heap's size, bounded by the total number of pushes rather than by the number of live items, and the one discipline it requires is that every pop checks staleness before believing the result.

Why the libraries chose this and not a Fibonacci heap

The binary array heap is the structure whose worst case is a clean logarithm with no amortization small print, whose memory is a single growable block, and whose constant factors are the smallest of any structure on this page. A library that shipped a Fibonacci or pairing heap would give every user a slower push and pop in exchange for a decreaseKey most users never call and a merge most users never need. The design pattern is the same one behind the decision in Hash Tables §25 to ship one collision policy rather than all of them: the default serves the common case, and the extended operation is left to the user who needs it, with lazy deletion as the documented escape hatch. The build-from-sequence operation is the one to look for: a library that offers it is exposing the Θ(n) construction of §09, and using it instead of n pushes is a free log factor on setup.

25 Top-k and streaming: the k smallest of n, two algorithms with two different bounds

"The k smallest of n keys" has a heap solution that is O(n log k) and another that is O(n + k log n), and they are different algorithms with different memory requirements, not two bounds for one algorithm. The first keeps a max-heap of size k holding the k smallest seen so far, with the largest of them at the root as a threshold: each new key is compared against the root and either discarded in one comparison or swapped in with a sift-down of O(log k). The second min-heapifies all n in Θ(n) and pops k times at O(log n) each; it needs all n in memory and hands the results out in sorted order. Which is better depends on k, on whether the data fits in memory, and on whether the output must be sorted.

26 The running median with two heaps

A single heap knows one extreme. To know the middle of a growing multiset, use two: a max-heap of the smaller half and a min-heap of the larger half, kept so that every key in the first is ≤ every key in the second and their sizes differ by at most one. Then the median is the root of the larger heap when sizes differ, or the mean of the two roots when they are equal. Each arrival costs one comparison to decide which half it joins, one O(log n) insert, and — if the sizes have drifted apart by two — one move of a root from the heavy heap to the light one. That is O(log n) per element and O(1) per median query, against O(n) per query for a scan and O(n log n) for re-sorting.

A single min-heap of all n keys knows the smallest, and finding the ceil(n/2)-th smallest from it costs n/2 pops — Θ(n log n) per query, and destructive. It does not generalise to a sliding window without more machinery — removing an element that is no longer in the window is an arbitrary delete, which needs the handles of §16 or the lazy deletion of §24 — and for approximate quantiles over very large streams, sketch structures that use sublinear memory replace it entirely. Within its scope it is the canonical example of a heap used not for its minimum but for the partition it maintains: everything on one side beats everything on the other, and the roots are the two elements that touch the cut.

Why the heap is the right size and why k log k does not appear

The heap never holds more than one entry per list, so its size is bounded by k regardless of n, and every operation is O(log k). The build is k inserts, O(k log k), or a bottom-up construction in O(k) — either way it is dominated by the n·log k of the merge whenever n ≥ k, which is always, since every list has at least one element. It is worth seeing that a min-heap of all n elements would give the same output at O(n log n), and that the entire saving of the k-way merge is the exponent of the logarithm: it exploits the fact that the input is already partly sorted, which is exactly the information a heap of the whole input would throw away. The idea is a small instance of the general pattern in Recursion, Divide & Conquer: merging is cheap in proportion to how sorted the pieces already are.

External sorting, and where the heap sits in it

When the data does not fit in memory, the sort has two phases and the heap appears in both. In the run-formation phase, a heap-based technique called replacement selection produces sorted runs that are, for random input, on average about twice the size of memory rather than equal to it (the classical snowplow argument): keep a min-heap of the memory-resident keys, emit the minimum, read the next input key, and insert it into the heap if it is ≥ the last emitted key (it can still go in the current run) or set it aside for the next run if not; the run ends when the heap is empty. Longer runs mean fewer runs, which means fewer merge passes. In the merge phase, the k-way merge above reads one block from each run and refills as blocks empty, and the number of runs it can merge at once is bounded by memory divided by block size. The bound O((n/B)·log_(M/B)(n/B)) block transfers is the external analogue of n log n, and the heap is the in-memory workhorse at both stages of achieving it.

What "no search" really means

A heap cannot find a key k without a scan, and the reason is structural rather than an oversight: the heap property gives no information about which subtree a key is in. A BST's invariant — everything left is smaller, everything right is larger — is what prunes half the tree at each step; the heap's invariant says only that a subtree's keys are ≥ its root, which rules out a subtree when k < root and rules out nothing when k ≥ root. The consequence is every extended operation in §04: decreaseKey and delete need a handle, because "find the entry with key k" is not available and "find the entry for item x" needs the inverse map of §16. When the heap is the wrong structure

If the workload ever asks "what is the smallest key greater than k?", or "how many keys lie between a and b?", or needs to visit keys in order more than once, the heap is the wrong structure and a balanced tree or a sorted array is right, exactly as Hash Tables §26 concludes for the hash table on the same question. If the workload asks only "what is the smallest?" and "here is another one", the heap is right and a tree is paying for ordered structure it never uses. The Trees & BSTs page takes the other branch of this decision; the two pages together cover the whole spectrum of "keep the minimum available", from no order (the unsorted list) through partial order (the heap) to total order (the tree and the sorted array), and the cost of each operation moves monotonically along it: the less order a structure maintains, the cheaper its updates and the fewer questions it can answer, and the heap is the point on that spectrum where "the minimum" is still cheap and nothing else is.

30 Pitfalls

Heaps fail quietly. A wrong index formula, a sift in the wrong direction, a stale handle — each produces a structure that is almost a heap, passes small tests, and returns a non-minimum from extractMin at some later, unrelated moment. The defence is the property check the figures on this page run after every operation: for every i ≥ 1, a[parent(i)] beats-or-ties a[i]. The list below is ordered by how often each bites.

  • parent(i) = i/2 in 0-based code. Right for odd i, wrong for every even i ≥ 2 (2 → 1 instead of 0) — and it survives every insertion order of up to six keys before producing an invalid heap at seven. The 0-based parent is floor((i − 1)/2); the 1-based parent is floor(i/2). §02 derives both and the twin-view figure lets you check any index.
  • Sift-down that compares only the left child, or compares the two children but swaps with the wrong one. The routine must swap with the better child, which means comparing the children first; §07 shows why swapping with the worse child breaks an edge the routine never revisits.
  • Build-heap from the front. The loop must run from floor(n/2) − 1 down to 0; the forward loop is wrong on [1, 3, 2, 4] (§09). Also: starting at n/2 rather than n/2 − 1 is harmless, starting at n/2 − 2 skips a node.
  • Building by n inserts when the keys were all available. Costs O(n log n) worst case and a factor of about 1.2 even on random input, against Θ(n) bottom-up (§11). Use the library's heapify if it has one.
  • Assuming heapsort is fast on sorted input. It is not adaptive: sorted input costs about the same as random, and the only cheap input is all-equal keys (§13).
  • Assuming heapsort is stable. [2a, 2b, 1] is the three-element counterexample. Augment the key with the original index if stability matters, or use mergesort.
  • delete(handle) that only sifts down. The moved-in last key can be smaller than the new parent; compare with the parent first and sift in the right direction (§16). The failing input is the one where a small key lands under a large parent.
  • A stale inverse map. Every swap must update pos[] for both entries; forgetting one leaves a handle that names the wrong slot, and the next decreaseKey through it lowers a stranger's key. The figure in §16 checks pos[item[i]] = i for every i after every run; do the same in tests.
  • Mixing amortized and worst-case columns. A Fibonacci heap's O(1) insert is an amortized promise; a single extractMin can cost Θ(n). A table that lists it beside the binary heap's O(log n) without saying so is comparing two different kinds of statement (§04, §19).
  • Stating the d-ary trade as a typical-case saving. Insert is O(log_d n) in the worst case; on random keys it is a small constant at every d, and extract's d·log_d n decides. Wide heaps pay for long climbs and for cache lines, not for typical inserts (§17).
  • Reading the heap array as sorted. It is sorted along root-to-leaf paths only. To get k keys in order, pop k times; to get all of them, that is heapsort (§24).
  • Top-k with the heap the wrong way round. The k smallest need a max-heap (evict from the root); the k largest need a min-heap (§25). And the output is unsorted.
  • Lazy deletion without a staleness check on every pop. One pop that trusts a stale entry returns a key that was lowered or removed long ago; the check must run on every extraction, including peeks.
  • Negating keys to flip the orientation. Fine for integers away from the type's minimum; an overflow for the type's minimum value (and a wrap for unsigned types), and impossible for non-numeric keys; floats negate exactly, and NaN breaks a heap regardless of sign. A reversed comparator is the general answer.
  • A comparator that is not a total preorder. NaN, or a multi-field comparison that forgets a field, makes the heap property unsatisfiable, and the routines terminate with a structure that is not a heap (§04).
  • Expecting FIFO among equal priorities. The ADT does not promise it and the heap does not deliver it. Add a sequence number as a secondary key.
  • Calling parent(0). floor(−1/2) is −1 in floor division and 0 in truncating division; either way the loop must stop at i = 0 before computing it. Sentinel implementations that store +∞ at a[0] in 1-based layout avoid the test, and then must never let a real key into a[0].
