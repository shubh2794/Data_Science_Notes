24 What the heap buys Dijkstra and Prim — and why the theoretical winner rarely wins

The two classic greedy graph algorithms are the reason decreaseKey exists as a named operation. Both keep every unfinished vertex in a min-priority queue keyed by its best-known value — a tentative distance for Dijkstra, the lightest crossing edge for Prim — and each iteration extracts the minimum and relaxes its edges, which lowers keys. Over the whole run that is V extractMins and at most E decreaseKeys, and the total is V × (extract cost) + E × (decreaseKey cost) + O(V + E) for the scan. Every priority queue on this page plugs into that formula, and the table below is what comes out. Reading it correctly requires holding two facts at once: the Fibonacci heap has the best bound, and it is almost never the fastest.

Why the Fibonacci heap loses the race it wins on paper

Three reasons, each of which the earlier sections set up. The bounds are amortized, so a single extractMin may take Θ(V) — harmless for a total running time but visible as latency. The constants are large: four pointers, a degree and a mark per node, a consolidate that walks a degree table 44% longer than a binomial heap's (§22), and every operation a pointer chase through separately allocated nodes, against a binary heap whose entire state is one array. And the operation it optimises is the one that matters least in practice: on many graph families met in practice the number of decreaseKeys that actually happen is far below E, because most relaxations do not improve on the current tentative distance and never reach the queue — so the term the Fibonacci heap optimises is smaller than the bound assumes. Published benchmarks comparing priority queues inside Dijkstra's algorithm consistently rank binary and d-ary heaps, and pairing heaps, ahead of Fibonacci heaps by constant factors that are not small; the specific ratios depend on the graph family and the hardware, and this page has not measured them, so it reports the ordering and not a number.

What is used instead

A 4-ary index heap is a common choice when decreaseKey is implemented: the four children of a node share a cache line (with the array padded so child groups are 4-aligned), the height is half a binary heap's, and the index map is a plain array indexed by vertex id (§16, §17). A binary heap with lazy deletion is what most library-based implementations do, because the library provides no decreaseKey: instead of lowering a vertex's key, push a fresh (distance, vertex) pair and, on extraction, discard any pair whose distance is stale; the heap grows to O(E) entries in the worst case, the log term becomes log E ≤ 2 log V, and no index map is needed — §25 spells out the mechanics. A pairing heap is the practical compromise for algorithms that genuinely need a fast decreaseKey with merging: a self-adjusting multiway tree with three pointers per node (child, sibling, and a back pointer — the third is what decreaseKey needs), O(log n) amortized extractMin, and a decreaseKey whose amortized cost is not O(1) — the proven bounds lie between Ω(log log n) and 2^O(√(log log n)) — but whose measured performance beats the Fibonacci heap on the workloads that matter. The pattern is the one Algorithm Analysis warns about: an asymptotic improvement on one term of a sum, purchased with constants that dominate the whole sum at every n anyone runs.

25 The heap in practice: what the standard libraries give you, and what they leave out

The priority queue shipped in a general-purpose standard library is, as a rule, a binary heap in an array: it is the structure with O(log n) worst-case insert and extract, O(1) findMin, Θ(n) construction from a sequence, no allocation per element, and the fewest ways to go wrong. What such libraries typically do not provide is decreaseKey, arbitrary delete in logarithmic time, or merge — the extended operations of §04 — because each needs a handle or a linked representation that every user would pay for. The four conventions below are documented behaviour of widely used libraries as of this page's writing; the conditions attached to each are part of the claim.

What a library heap is for, and the two ways people misuse it

The first misuse is treating the heap's array as sorted. It is not: iterating a heap yields keys in level order, which is sorted only along root-to-leaf paths, and "the second element of the heap array is the second smallest" is false as often as it is true. To read the k smallest in order you must pop k times, and to read all n in order you must pop n times — which is heapsort — or copy and sort. The second misuse is calling a linear-time "remove(x)" in a loop and expecting a logarithmic structure: a library that offers arbitrary removal without handles implements it by scanning, and n removals are Θ(n²). Lazy deletion is the answer to both: keep the heap append-only, keep the truth about each item outside it, and let stale entries surface and be discarded at pop time. The cost is the heap's size, bounded by the total number of pushes rather than by the number of live items, and the one discipline it requires is that every pop checks staleness before believing the result.

Why the libraries chose this and not a Fibonacci heap

The binary array heap is the structure whose worst case is a clean logarithm with no amortization small print, whose memory is a single growable block, and whose constant factors are the smallest of any structure on this page. A library that shipped a Fibonacci or pairing heap would give every user a slower push and pop in exchange for a decreaseKey most users never call and a merge most users never need. The design pattern is the same one behind the decision in Hash Tables §25 to ship one collision policy rather than all of them: the default serves the common case, and the extended operation is left to the user who needs it, with lazy deletion as the documented escape hatch. The build-from-sequence operation is the one to look for: a library that offers it is exposing the Θ(n) construction of §09, and using it instead of n pushes is a free log factor on setup.

26 Top-k and streaming: the k smallest of n, two algorithms with two different bounds

"The k smallest of n keys" has a heap solution that is O(n log k) and another that is O(n + k log n), and they are different algorithms with different memory requirements, not two bounds for one algorithm. The first keeps a max-heap of size k holding the k smallest seen so far, with the largest of them at the root as a threshold: each new key is compared against the root and either discarded in one comparison or swapped in with a sift-down of O(log k). It needs k cells of memory and one pass, so it works on a stream. The second min-heapifies all n in Θ(n) and pops k times at O(log n) each; it needs all n in memory and hands the results out in sorted order. Which is better depends on k, on whether the data fits in memory, and on whether the output must be sorted.

Notice the max-heap of the SMALLEST: the orientation is the opposite of what the question sounds like, because the heap's root must be the element most likely to be evicted.

Why the orientation is reversed

To keep the k smallest, the structure must be able to answer "which of my current k is the largest, so I can throw it out if something smaller arrives?" — and that is a max-heap's root. A min-heap of the k smallest would know the smallest of them, which is never the one to evict. The same reversal holds for the k largest: keep a min-heap, evict from its root. Getting this backwards is the most common bug in top-k code, and it fails loudly (the answers are wrong), which is the kind of bug to prefer. The second-most common is forgetting that algorithm A's output is unsorted and returning the heap array as if it were the answer in order; the figure's readout measures what the extra sort costs.

27 The running median with two heaps

A single heap knows one extreme. To know the middle of a growing multiset, use two: a max-heap of the smaller half and a min-heap of the larger half, kept so that every key in the first is ≤ every key in the second and their sizes differ by at most one. Then the median is the root of the larger heap when sizes differ, or the mean of the two roots when they are equal. Each arrival costs one comparison to decide which half it joins, one O(log n) insert, and — if the sizes have drifted apart by two — one move of a root from the heavy heap to the light one. That is O(log n) per element and O(1) per median query, against O(n) per query for a scan and O(n log n) for re-sorting.

Why two heaps and not one heap plus a count

A single min-heap of all n keys knows the smallest, and finding the ceil(n/2)-th smallest from it costs n/2 pops — Θ(n log n) per query, and destructive. The two-heap structure keeps a boundary in the sorted order rather than an end, and the boundary is exactly what the median is. The same idea generalises to any fixed quantile: to track the p-th percentile, keep the sizes in ratio p : (1 − p) instead of 1 : 1, and the boundary sits at the percentile. It does not generalise to a sliding window without more machinery — removing an element that is no longer in the window is an arbitrary delete, which needs the handles of §16 or the lazy deletion of §25 — and for approximate quantiles over very large streams, sketch structures that use sublinear memory replace it entirely. Within its scope it is the canonical example of a heap used not for its minimum but for the partition it maintains: everything on one side beats everything on the other, and the roots are the two elements that touch the cut.

Note the asymmetry the invariant chooses: when the count is odd, the extra element lives in low, so the median is always max(low) — a convention, but one that must be applied consistently, because "which heap holds the extra one" is the difference between a correct median and an off-by-one on every odd step.

28 Merging k sorted lists in O(n log k), and external sorting

Merging two sorted lists is a single pass comparing heads. Merging k of them naively — compare all k heads, emit the smallest, advance that list — is O(k) per output element, O(nk) in all, where n is the total length. A min-heap of the k heads makes it O(log k) per element: the heap holds one entry per list, the current head tagged with its list number; pop the smallest, emit it, push the next element of the same list. Total O(n log k), with O(k) extra space. This is the merge step of external sorting — sort chunks that fit in memory, then merge the k sorted runs from disk in one pass — and it is the merge inside the multiway mergesorts that cache-aware sorting libraries use, and inside the merging of sorted index segments in search engines.

Why the heap is the right size and why k log k does not appear

The heap never holds more than one entry per list, so its size is bounded by k regardless of n, and every operation is O(log k). The build is k inserts, O(k log k), or a bottom-up construction in O(k) — either way it is dominated by the n·log k of the merge whenever n ≥ k, which is always, since every list has at least one element. It is worth seeing that a min-heap of all n elements would give the same output at O(n log n), and that the entire saving of the k-way merge is the exponent of the logarithm: it exploits the fact that the input is already partly sorted, which is exactly the information a heap of the whole input would throw away. The idea is a small instance of the general pattern in Recursion, Divide & Conquer: merging is cheap in proportion to how sorted the pieces already are.

External sorting, and where the heap sits in it

When the data does not fit in memory, the sort has two phases and the heap appears in both. In the run-formation phase, a heap-based technique called replacement selection produces sorted runs that are, for random input, on average about twice the size of memory rather than equal to it (the classical snowplow argument): keep a min-heap of the memory-resident keys, emit the minimum, read the next input key, and insert it into the heap if it is ≥ the last emitted key (it can still go in the current run) or set it aside for the next run if not; the run ends when the heap is empty. Longer runs mean fewer runs, which means fewer merge passes. In the merge phase, the k-way merge above reads one block from each run and refills as blocks empty, and the number of runs it can merge at once is bounded by memory divided by block size. The bound O((n/B)·log_(M/B)(n/B)) block transfers is the external analogue of n log n, and the heap is the in-memory workhorse at both stages of achieving it.

29 Locality: what in an array heap is actually contiguous, and what is not

"The array heap has good cache behaviour" is repeated often and is half true, and the half that is false is the half that matters at scale. What is contiguous: the two children of a node, always, at 2i+1 and 2i+2 — one cache line nearly always serves both comparisons of a sift-down step. What is not: a node and its child, whose distance in the array is about i+1 cells, which doubles at every level. A sift-down from the root visits indices 0, then 1 or 2, then 3 … 6, then 7 … 14, and by depth d it is at index ≈ 2ᵈ: the first few levels share a cache line, and every level after that is a new line, at an address the hardware cannot predict from the previous one. The heap's memory behaviour is therefore excellent while the heap fits in cache and poor once it does not, and the crossover is what the figure measures.

Why the pattern cannot be fixed by reordering the array

The level-order layout is forced by the completeness property: indices 0 … n−1 must be exactly the nodes of a complete tree, and the level-order layout puts each level in a contiguous block, so consecutive levels are necessarily far apart. The alternatives trade the formula's simplicity for locality: a van Emde Boas–style recursive layout or a B-heap groups a subtree of several levels into one block, so that a path of length h crosses about h / (levels per block) blocks instead of h lines. Those layouts work and are used in cache-sensitive priority queues, but the parent and child formulas become multi-step, insertion at "the next free slot" is no longer an append, and the code is several times longer. For the common case — a heap of a few thousand entries, which fits in a mid-level cache whole — the plain layout is the right choice and the scattered pattern costs little; the measurement below shows the number of distinct lines a sift touches growing linearly with the height, and it is that count, multiplied by the miss latency, that decides when the plain layout stops being cheap.

The sift is run on a random max-heap of n = 2¹⁴ keys with a −1 placed at the root, so it falls all the way to a leaf along a data-dependent path — 13 levels at the default, because n = 2¹⁴ has a single node on its fifteenth level and almost every leaf is at depth 13 — and every index it reads is recorded. The parent-to-child gaps double at every level — the readout checks each against its closed-form bracket [2^(d−1), 2^d], the shaded band — and the sibling gap is 1 at every level. With 16 keys per line the top four levels (indices 0 … 14, plus index 15) share one line and each level below is a fresh line: the readout counts the distinct lines touched by the one sift, and separately counts how many sibling pairs shared a line, predicting the exceptions exactly from "2i+2 is a multiple of 16" — the straddle that a 1-based layout would never produce. Slide n up to 2²⁰ and the line count grows by one per doubling; change the key size and the number of levels in the first line shifts by one for every factor of two. What the figure makes concrete is the split in the folklore claim: siblings are adjacent, and the comparison between them is nearly always one line; generations are adjacent only at the top, and a deep heap pays a cache miss per level below that.
