Data Structures

One question, asked seven ways: how should this data be arranged in memory, and what does that arrangement make cheap? A data structure is not a container — it is a cost contract. It promises certain operations are fast, and it pays for every promise with something else: memory, ordering, worst-case guarantees, or insert speed. This is the overview — the map, the one idea that runs through all seven parts, and a one-screen cost table. The notes live on seven sub-pages, ordered so each one only assumes what came before.

why The thread that runs through it

Every structure here is the same bargain struck at a different exchange rate: you pay in one operation to make another cheap. Naming which operation you actually perform most is the entire skill; the structure follows almost mechanically once you have.

the operations you actually run→their relative frequency→the invariant worth maintaining→the structure that maintains it cheaply→a cost contract
  • The abstract data type is not the implementation. A stack is a promise — last in, first out — and nothing more. It can be an array or a linked list, and the promise is identical either way; only the cost profile and the memory behaviour differ. Keeping the two levels separate is what lets you swap implementations without rewriting the code that uses them.
  • An invariant is what you are really paying for. A heap maintains "every parent ≤ its children"; a BST maintains "everything left is smaller"; a hash table maintains "this key lives at h(key)". Every operation costs whatever it takes to restore the invariant after the change — which is why insert and delete are the interesting operations and read is usually free.
  • Contiguous vs linked is the first fork. Contiguous storage buys O(1) indexing and excellent cache behaviour, and pays with O(n) middle insertion and resize copies. Linked storage buys O(1) splicing at a known position, and pays with pointer chasing, per-node overhead, and no indexing at all.
  • Ordering is the second fork. Hash tables and heaps are fast precisely because they refuse to maintain a total order — a hash table cannot answer "what is the next largest key?" at all, and a heap only knows its minimum. Search trees keep the order and pay O(log n) for it. If you never need ordered iteration, range queries or successor lookups, paying for a tree is waste.
  • Worst case and expected case are different products. A hash table is expected O(1) and worst-case O(n); a balanced tree is worst-case O(log n) with no expectation involved. For an interactive system with an adversary on the other end, the guarantee can be worth more than the average.
  • Asymptotics ignore the constant that your hardware charges. Big-O counts operations on a flat memory model. Real machines have caches, and a linear scan of a contiguous array routinely beats an asymptotically superior pointer structure at small and medium n. The growth rate tells you who wins eventually; measurement tells you whether you are there yet. Algorithm Analysis sets out both halves of that claim.
