Linked Lists, Stacks & Queues

One decision — hold each element in its own node and record where the next one is — and every cost here follows from it. Storing the address instead of computing it means a splice is a couple of field writes wherever it happens, and it means there is no arithmetic that can find element i, so reaching a position is a walk. That single inversion produces singly, doubly and circular lists, the sentinel trick that deletes every boundary case, the runner and cycle-detection patterns, and the two restricted-access types built on top: the stack, which is the shape of recursion, expression evaluation and depth-first search, and the queue, which is the shape of a circular buffer, a scheduler and a breadth-first frontier — together with the honest verdict on when a chain of nodes is actually the right answer.

01 What a linked structure is

A linked structure stores each element in its own separately allocated node, and stores alongside the element one or more references to other nodes. A reference is just a machine address — a fixed-width word naming a place in memory. The collection is not a region; it is a graph of nodes joined by those addresses, plus one external reference, conventionally called head, that names where to start. Nothing else is required, and nothing else is promised.

Why each part of the definition is load-bearing

  • Separately allocated. Each node is its own allocation, requested from the allocator when the element arrives and released when it leaves. Nothing is reserved in advance, nothing is copied when the collection grows, and the collection's memory is never one block — so it never has to be one block, which is precisely the constraint that forces a dynamic array to reallocate and copy. The cost is that the allocator is now on the critical path of every insertion, and that the nodes may land anywhere, in any order, arbitrarily far apart (§03).
  • Holds a reference. The link field is a fixed-width word regardless of how big the payload is, which is what makes the structure work uniformly for a 4-byte integer and a 4-kilobyte record. It is also pure overhead: on a 64-bit machine every node pays 8 bytes per link, before the allocator's own per-block bookkeeping and alignment rounding.
  • Named by an external reference. A list is its head pointer. Lose head and the entire chain is unreachable and — in a managed runtime — collected; there is no directory, no length field unless you keep one, and no way to rediscover the nodes. This is a real difference in failure mode from an array, where the block is either allocated or not and the elements are wherever they were put. Half the classic linked-list bugs in §29 are variants of "the head moved and nobody told anyone".
  • Null terminates. The last node's link is a distinguished non-address. That one value is what every traversal loop tests against, what every boundary case special-cases, and what sentinels exist to make unnecessary.

What the definition does not say

  • Nothing about the nodes being in order in memory. The chain order and the storage order are independent. They may coincide right after a list is built by repeated appends from a fresh allocator, and they diverge the moment anything is inserted, deleted, sorted or reallocated. Every performance claim on this page that is not an asymptotic one depends on which of the two is true at the time.
  • Nothing about there being exactly one link. One link forward gives a singly linked list; one forward and one back gives a doubly linked one; two children give a binary tree; a variable-length list of links gives the adjacency list of a graph. The node-and-reference discipline is the same in all four; only the arity of the link field changes. This page establishes the discipline, and the later parts spend it.
  • Nothing about a length. An array knows its length because the length was fixed at allocation. A chain does not, unless a count is maintained by hand on every insert and delete. A length() that walks the chain is Θ(n) — and a loop that calls it on every iteration is Θ(n²), which is the single commonest accidental quadratic in list code.
  • Nothing about being able to go backwards. With one forward link, a node cannot name the node that points at it. That asymmetry is not a detail; it is the source of the predecessor problem, which is the reason doubly linked lists exist at all.

The motivation, stated as the same cost argument the array page made

Every container has to answer "where is element i?", and there are only two families of answer: compute it, which demands uniform cells laid consecutively, or store it, which demands a reference per element and a traversal to reach that reference. Arrays & Strings takes the first answer to its conclusion. This page takes the second. Taking it means giving up the one thing the first answer is unbeatable at — constant-time access to an arbitrary position — in exchange for three things the first answer cannot offer: an insertion or deletion that moves nothing, a structure that grows one element at a time with no reallocation and no copy, and the ability to splice, split, join and reorder by rewriting links rather than relocating data. Whether that trade is worth taking is a question with a specific and often disappointing answer, which §28 gives without softening it.

A node, and what it costs to change one link step through the operation — the splice is a fixed number of writes; the walk to reach it is not

Two things are worth watching. First, the order of the two writes in an insertion: new.next = cur.next must happen before cur.next = new, because the other order overwrites the only reference to the rest of the list and loses every node after the insertion point. That is not a style rule; it is the difference between a correct splice and a leak. Second, switch the control to insert after position k and look at the shape of the picture afterwards: the new node sits below the row, and the chain now zig-zags. The drawing is honest — logical order and physical position have separated, and they stay separated for the life of the list. Everything §03 has to say about performance is a consequence of that picture.

The one-line version. A linked structure is what you get when you decide that position shall be stored rather than computed. Everything it is good at — splicing without moving, growing without copying — and everything it is bad at — finding anything, and touching memory efficiently — is downstream of that decision.

27 Priority queues: named here, built elsewhere

There is a third answer to "which element comes out next?", and it is neither "the newest" nor "the oldest" but "the most important". A priority queue supports insert(v, priority) and extractMin() (or extractMax()), and it is the ADT that completes the trio. It belongs on this page as a comparison and not as a construction, because the structure that implements it well is a heap, which is an array with a tree's shape encoded in its index arithmetic — a different design from anything here.

What a linked list can and cannot do here

Both linked implementations in the table above are genuinely used, and the choice between them is the classic time-trade. An unsorted linked list gives O(1) insertion and pays Θ(n) on every extraction; a sorted one pays Θ(n) on every insertion and extracts in O(1). Over n inserts and n extracts both are Θ(n²), so neither is a good general answer — but if one operation dominates heavily, the matching list is simpler than a heap and often faster at small n. Be precise about decreaseKey, which is the operation a priority queue inside Dijkstra's algorithm leans on, because the two list variants behave oppositely and the folklore answer ("lists are bad at it") is wrong for one of them. On an unsorted list, if the caller holds a handle to the node, lowering its key is a single field write — O(1), better than a binary heap's O(log n), because an unsorted list maintains no order to repair. On a sorted list, the node must be moved to its new place, which is a walk: Θ(n). What neither can do cheaply is extractMin and ordered access together, and what neither can do at all is reach a position in the middle without walking to it. The genuinely useful consequence is that an unsorted array or list gives Dijkstra Θ(V² + E), which beats the binary-heap O((V + E) log V) when the graph is dense enough that E approaches V². That is a real and not-uncommon case, and it is the first of two places on this page where the flat structure wins outright.

Where the sorted list does win

One structure on this page is genuinely the right priority queue in a specific setting: a sorted doubly linked list when priorities arrive in nearly sorted order and elements must be repriorised by splicing. The insertion walk is short when the new element belongs near one end, the splice is O(1), references to elements stay valid, and moving an element to a new priority is a remove-and-reinsert with no reallocation. That is the shape of a simple event queue in a discrete-event simulation where events are scheduled mostly in the near future — and it is why "use a heap" is a default rather than a law.

28 When a linked list is actually the right answer

The honest summary of the last twenty-seven sections is that a dynamic array beats a linked list for most general-purpose sequence work, often by a large constant factor, and the cases where the list wins are specific and identifiable. Being able to name them — and to recognise when none of them applies — is more useful than any amount of enthusiasm for either structure.

The five genuine wins

  • You already hold the node, and you splice a lot. This is the row of the §02 table that the "O(1) insertion" headline is really about, and the one no array layout can match at any size. An LRU cache moving an entry to the front of its recency list, a scheduler moving a task between run queues, an allocator moving a block between size classes, an intrusive list threading objects that already exist — all of these hold a pointer to the element and perform O(1) removal and reinsertion with no search and no copy. An array cannot do this at all without a Θ(n) shift.
  • References to elements must stay valid. Every insertion into a dynamic array may reallocate and invalidate every pointer, reference, iterator and index into it. A node's address never changes. When other data structures point at the elements — a hash map from key to node, a second list threading the same objects, a callback holding a handle — this is not a performance argument at all, it is a correctness one.
  • Worst-case latency matters more than throughput. Every list insertion, and every deletion at a node whose predecessor is reachable, is worst-case O(1) with no resize and no copy. (Reaching a position is still Θ(k) and searching still Θ(n) — the guarantee being bought here is about growth and splicing, not about lookup.) The array's append is O(1) amortized with Θ(n) spikes, which is unacceptable in a real-time audio callback, a control loop, or an interrupt handler. The caveat from §24 applies: the list's latency is then the allocator's latency, so real-time list code preallocates its nodes into a free list.
  • Constant-time splitting, joining and reordering of whole sequences. Concatenating two lists is one link write; splitting at a held node is one link write; moving a run of elements from one list to another is a constant number of writes with nothing copied. Arrays pay Θ(n) for each. This is why linked structures appear inside other structures — the child lists of a Fibonacci heap, the free lists of an allocator, the bucket chains of a hash table.
  • The elements are large, or the memory is fragmented. The link overhead is a fixed 8 or 16 bytes, so its relative cost falls as the payload grows — and a linked structure needs no contiguous block at all, so it can allocate when a large contiguous allocation would fail. For big records in a fragmented heap, the array's advantages largely evaporate.

The three arguments that are usually wrong

  • "Insertion is O(1)." Only at a node you already hold. Insertion at an index is Θ(k); insertion before a value is Θ(n). The §02 figure measures both and shows that for a uniformly random position the two structures touch the same n/2 elements on average — with the array's being a tight, prefetched block move.
  • "The array wastes memory on growth." It holds up to 100% slack; the list holds a link plus allocator overhead per element. For small payloads the list is the bigger waster, permanently, as the §03 figure quantifies — and the array's slack can be reclaimed by shrinking or by reserving the right capacity up front, where the list's overhead cannot be reclaimed at all.
  • "It avoids the copy." It avoids one copy and pays an allocation per element. The array's amortized copying is a handful of sequential memmoves over the whole lifetime of the structure; n allocator calls are not obviously cheaper, and they are certainly less predictable.

The decision procedure, compressed

ask these four, in order1. Do I index by position, or binary search, or scan a lot? → array. Stop. 2. Must references to elements survive insertions elsewhere? → linked. Stop. 3. Do I hold nodes and splice, or split and join whole sequences? → linked. Stop. 4. Is a Θ(n) latency spike unacceptable, even rarely? → linked, with preallocated nodes. otherwise→ array. It is the default for a reason, and the burden of proof is on the alternative. and separately, for the restricted ADTsstack, bounded → array or ring; stack, latency-critical → nodes + free list queue, bounded → circular buffer, every time queue, unbounded with hard latency → linked, head + tail deque → circular buffer if small elements, block-chain or doubly linked otherwise
Why the structure is still worth knowing cold. Even if you rarely reach for a bare linked list, you will use the discipline constantly: a tree is nodes with two links, a graph's adjacency list is nodes with many, a hash table's chains are lists, an allocator's free blocks are a list, and the call stack is a list of frames. The pointer discipline of §01 — save before you overwrite, maintain both directions, null the fields of anything you unlink — is the part that transfers, and it transfers everywhere.

29 Pitfalls

Every item here is a bug that compiles, passes a casual test, and fails on a boundary or under load. They are grouped by which structure produces them, and each one names the check that catches it.

Pointer discipline

  • Overwriting a link before saving what it pointed at. cur.next = prev before nxt = cur.next loses the entire rest of the list. Same bug as writing cur.next = new before new.next = cur.next. Check: after any routine that rewrites links, assert the node count is what it should be.
  • Losing the head. A routine that advances head as its working cursor returns a list that starts in the middle, and in a managed runtime the prefix is collected. Check: never use the external reference as the loop variable; copy it into a local cursor first.
  • Forgetting to update the auxiliary fields. A tail pointer left stale by a head-deletion on a one-element list, or a size counter not decremented, produces a structure that is internally inconsistent in a way no single operation reveals. Check: a debug-mode invariant routine that walks the list and re-derives size and tail from scratch, called after every mutation in tests.
  • Breaking the back-pointer symmetry. Updating next and not prev gives a list that is correct forwards and corrupt backwards. Check: walk forward collecting nodes, walk backward from the tail, assert the two sequences are exact reverses.
  • Leaving a deleted node pointing into the list. A stale reference to it walks back into a structure it is no longer part of, and a double removal rewrites its old neighbours' links with garbage. Check: null both fields of every unlinked node, or write a poison value.
  • The copy-the-successor trick at the tail, or with escaped references. §05 in full: it faults on the last node, and it destroys node identity everywhere else. Check: only use it on lists whose nodes never escape, and give the list a trailer sentinel.

Traversal and termination

  • Indexed access inside a loop. for i in 0…n−1: visit(get(i)) is Θ(n²) on a linked list, and it looks exactly like the linear array version. Check: the doubling-ratio experiment — quadruple n and see whether the operation count quadruples or goes up sixteenfold.
  • Calling length() in a loop condition on a structure that computes it by walking. Same quadratic, same test.
  • A while (p ≠ start) loop on a circular list, which terminates immediately because p = start on entry. Check: use do … while, and test the one-element ring.
  • An unbounded search on a circular list, which never returns when the value is absent. Check: bound every circular traversal by the start comparison or by a maintained count.
  • Assuming a list is acyclic. Any traversal over a list with a cycle runs forever. Check: Floyd's algorithm in a debug assertion, or make cycles unrepresentable by building lists only through an API that cannot close one.
  • Off-by-one in the runner setup. Advancing the lead pointer k−1 links instead of k returns the wrong node from the end, silently. Check: test k = 1 (the last node) and k = n (the first), and assert that k > n is an error rather than an answer.

Rings, queues and wraparound

  • back − front without the + capacity. Correct until the window splits, then negative. Check: a test that enqueues past the end of the block before measuring size — a test suite that never wraps will never see this.
  • Reading a wrapped ring as one contiguous slice. data[front … back] is empty or backwards once the window is split. Check: always read as two runs, and test with the front deliberately placed near the end of the block.
  • A negative modulus on the backwards step. (front − 1) mod capacity is −1 in several widely used languages. Check: write (front − 1 + capacity) mod capacity unconditionally, and test addFirst on a buffer whose front is at index 0.
  • Confusing full with empty. §23 in full. Check: test the three boundary states explicitly — empty, exactly one element, and exactly at capacity — and test them after a wraparound, not only from a fresh buffer.
  • A resize that block-copies a split window. Preserves positions rather than order, so the queue silently reorders. Check: fill, drain part way, wrap, then grow, then drain completely and compare with a reference FIFO — which is exactly the cross-check the §22 figure runs on every operation.
  • Shrinking at half full. Destroys the amortized bound under an alternating workload. Check: shrink at a quarter, to a half.

Stacks and recursion

  • Popping an empty stack. The precondition of §13, and the one that returns a null which is then used. Check: make the empty case raise, or return an option type the caller must unwrap.
  • The two pops in the wrong order in a postfix evaluator. The second pop is the left operand; getting it backwards is invisible for + and × and wrong for everything else. Check: test with a non-commutative operator, every time.
  • Assuming recursion is free. Depth × frame size is real memory, and a recursion linear in the input will overflow on a large one. Check: test at a size big enough to matter, not at ten; convert to an explicit stack when the depth is data-dependent.
  • Relying on tail-call elimination that the language does not guarantee. Check: read the language specification, not a blog post; and note that a call with work after it is not a tail call however it is written.
  • Using an unbounded stack or queue as a buffer. Turns a fast, visible rejection into slow, invisible memory growth. Check: bound it and choose a policy — block, reject, or overwrite.
The single highest-value habit. Write an invariant checker for every linked structure you build — walk it, count the nodes, re-derive every auxiliary field, verify the back-pointers mirror the forward ones, verify no node is reachable twice — and call it after every mutation in the test build. It costs an hour and it converts an entire category of silent corruption into a loud, immediate, precisely located failure.
