One decision — hold each element in its own node and record where the next one is — and every cost here follows from it. Storing the address instead of computing it means a splice is a couple of field writes wherever it happens, and it means there is no arithmetic that can find element i, so reaching a position is a walk. 01 What a linked structure is

A linked structure stores each element in its own separately allocated node, and stores alongside the element one or more references to other nodes. A reference is just a machine address — a fixed-width word naming a place in memory. The collection is not a region; it is a graph of nodes joined by those addresses, plus one external reference, conventionally called head, that names where to start. Nothing else is required, and nothing else is promised.

Why each part of the definition is load-bearing

  • Separately allocated. Each node is its own allocation, requested from the allocator when the element arrives and released when it leaves. Nothing is reserved in advance, nothing is copied when the collection grows, and the collection's memory is never one block — so it never has to be one block, which is precisely the constraint that forces a dynamic array to reallocate and copy. The cost is that the allocator is now on the critical path of every insertion, and that the nodes may land anywhere, in any order, arbitrarily far apart (§03).
  • Holds a reference. The link field is a fixed-width word regardless of how big the payload is, which is what makes the structure work uniformly for a 4-byte integer and a 4-kilobyte record. It is also pure overhead: on a 64-bit machine every node pays 8 bytes per link, before the allocator's own per-block bookkeeping and alignment rounding.
  • Named by an external reference. A list is its head pointer. Lose head and the entire chain is unreachable and — in a managed runtime — collected; there is no directory, no length field unless you keep one, and no way to rediscover the nodes. This is a real difference in failure mode from an array, where the block is either allocated or not and the elements are wherever they were put. Half the classic linked-list bugs in §28 are variants of "the head moved and nobody told anyone".
  • Null terminates. The last node's link is a distinguished non-address. That one value is what every traversal loop tests against, what every boundary case special-cases, and what sentinels exist to make unnecessary.

What the definition does not say

  • Nothing about the nodes being in order in memory. The chain order and the storage order are independent. They may coincide right after a list is built by repeated appends from a fresh allocator, and they diverge the moment anything is inserted, deleted, sorted or reallocated. Every performance claim on this page that is not an asymptotic one depends on which of the two is true at the time.
  • Nothing about there being exactly one link. One link forward gives a singly linked list; one forward and one back gives a doubly linked one; two children give a binary tree; a variable-length list of links gives the adjacency list of a graph. The node-and-reference discipline is the same in all four; only the arity of the link field changes. This page establishes the discipline, and the later parts spend it.
  • Nothing about a length. An array knows its length because the length was fixed at allocation. A chain does not, unless a count is maintained by hand on every insert and delete. A length() that walks the chain is Θ(n) — and a loop that calls it on every iteration is Θ(n²), which is the single commonest accidental quadratic in list code.
  • Nothing about being able to go backwards. With one forward link, a node cannot name the node that points at it. That asymmetry is not a detail; it is the source of the predecessor problem, which is the reason doubly linked lists exist at all.

The motivation, stated as the same cost argument the array page made

Every container has to answer "where is element i?", and there are only two families of answer: compute it, which demands uniform cells laid consecutively, or store it, which demands a reference per element and a traversal to reach that reference. Arrays & Strings takes the first answer to its conclusion. This page takes the second. Taking it means giving up the one thing the first answer is unbeatable at — constant-time access to an arbitrary position — in exchange for three things the first answer cannot offer: an insertion or deletion that moves nothing, a structure that grows one element at a time with no reallocation and no copy, and the ability to splice, split, join and reorder by rewriting links rather than relocating data. Whether that trade is worth taking is a question with a specific and often disappointing answer, which §27 gives without softening it.

A node, and what it costs to change one link step through the operation — the splice is a fixed number of writes; the walk to reach it is not

Two things are worth watching. First, the order of the two writes in an insertion: new.next = cur.next must happen before cur.next = new, because the other order overwrites the only reference to the rest of the list and loses every node after the insertion point. That is not a style rule; it is the difference between a correct splice and a leak. Second, switch the control to insert after position k and look at the shape of the picture afterwards: the new node sits below the row, and the chain now zig-zags. The drawing is honest — logical order and physical position have separated, and they stay separated for the life of the list. Everything §03 has to say about performance is a consequence of that picture.

The one-line version. A linked structure is what you get when you decide that position shall be stored rather than computed. Everything it is good at — splicing without moving, growing without copying — and everything it is bad at — finding anything, and touching memory efficiently — is downstream of that decision.

02 The cost contract, against the contiguous one

A data structure is a set of promises with a price list attached. Put the linked price list beside the contiguous one and every entry is either inverted or unchanged — there is no operation where linking wins on both access and locality, and no operation where contiguity wins on both splice cost and growth. The rows that get misquoted

  • "Linked lists have O(1) insertion." Only the insert after a held node row is true unconditionally, and read it carefully: it says at a node you already hold. If the caller supplies an index, the list must walk to it and the operation is Θ(k). If the caller supplies a value to insert before, the list must search and it is Θ(n). The O(1) is real but it is a claim about what you are holding, not about the operation.
  • "…and O(1) deletion, for the same reason." It does not follow, and the table now says so on its own row. Inserting after a held node touches only that node's link field, which you have; deleting a held node touches the link field of its predecessor, which a singly linked node cannot name. So deletion at a held node is Θ(k) on a singly linked list and O(1) only once a back-pointer exists. The two operations are constantly quoted as a pair and only one of them is free — which is the whole subject of §05.
  • "Deleting at the back is symmetric with deleting at the front." It is not, for a singly linked list, and a tail pointer does not fix it. Removing the last node requires writing null into the second-to-last node's link field, and the tail pointer cannot reach its own predecessor. So pop_back is Θ(n) on a singly linked list with a tail pointer and O(1) only once the list is doubly linked (§06). This asymmetry is why a singly linked list makes a fine stack and a poor deque.
  • "Arrays are O(n) to insert, so lists are faster for insert-heavy work." Compare the whole operation. Inserting at a random position costs the array a mean of n/2 element moves — a tight, prefetched, vectorisable memmove — and costs the list a mean of n/2 pointer chases, each a potential cache miss, plus an allocation. Same asymptotics, and the constant factor usually favours the array — by how much is a question about a particular machine, which §03 answers only as a memory-traffic ratio and explicitly declines to turn into a wall-clock number.
  • "Binary search on a sorted linked list is Θ(log n)." It is not, because computing a midpoint requires random access. Halving the index range still costs a walk to reach each midpoint, and the total is Θ(n) — worse in practice than a plain scan, because it walks the same prefix repeatedly. A sorted list gives you early termination on a failed search and nothing else; the Θ(log n) lookup on a linked structure has to be bought with extra links, which is what a balanced tree and a skip list both do.

The two rows the list wins, and what they are worth

The genuine wins are splice at a held node and structural rearrangement. Concatenating two lists is one link write if you kept a tail pointer, against copying n₁ + n₂ elements for arrays. Splitting a list at a held node is one link write, against a copy. Moving an element from one list to another — a scheduler moving a task between run queues, an LRU cache moving an entry to the front of its recency list — is a constant number of writes with no element ever copied and, crucially, no reference to the element invalidated. That last property is the one that most often decides the question in real code: pointers, iterators and references into a linked list stay valid across insertions and deletions elsewhere in the list, where every one of them into a dynamic array is invalidated the moment the array reallocates. The standard name for the failure is iterator invalidation, and it is worth knowing as a phrase because library documentation states its rules in exactly those terms — which operations invalidate which iterators is part of a container's published contract, not an implementation detail. When a design needs stable identity for its elements, the list is not winning on complexity at all — it is winning on a guarantee the array cannot make.

Reading a bound as a pair, not a number

Some entries in the table are written O(·) and others Θ(·), and the difference is not decoration. O(1) for the front insert is an upper bound that also happens to be tight, but writing it as O signals that the operation never does more than a constant amount of work — it is a guarantee. Θ(k) for reaching position k is a tight two-sided bound: the walk does at least k link reads and at most k, always, with no best case to hope for. And the array's amortized O(1) append is a third kind of claim entirely — a bound on a sequence, derived in Algorithm Analysis, where any single append may cost Θ(n). The list's growth needs no amortization argument at all: every insert is worst-case constant, which is why linked allocation appears in real-time systems where a doubling copy's latency spike is unacceptable even though its average is excellent.

The two bar series are mirror images, and their sum is constant — exactly n for the insert, since the array touches n − k and the list k: the array's cost falls as k rises and the list's rises with it, crossing at k = n/2 — or, when n is odd and there is no such index, at the first integer above it, which is where the violet marker actually sits. That is the whole cost contract in one picture. The mean readout is the sentence to take away — for insertion at a uniformly random position both structures touch about n/2 elements, so on average they are the same asymptotic class and the decision has to be made on the constant factor, on the access pattern of the surrounding code, or on the reference-stability guarantee of the previous subsection. Switch the control to read element k and the symmetry vanishes: the array bar is flat at zero touched elements for every k, because the address was computed rather than found. There is no crossover on that setting, at any n, ever.

Model discipline, carried over. Every bound in the table is a RAM-model bound, where any one memory access costs the same as any other. Every claim on this page that one structure is faster in practice than another with the same bound is a claim about the next section, which counts memory transactions rather than steps. Keep the two ledgers separate; mixing them is how people end up defending a chain of nodes that is asymptotically equal and four times slower.

03 The cache reality that asymptotics hide

Traversing an array of n elements and traversing a chain of n nodes are both Θ(n). They are commonly reported as being a factor of a few apart in wall-clock time; that figure is quoted often enough to count as folklore, and this section will deliberately not endorse it as a number. What it will do is locate the gap, which is not in the step count at all — it is in how many times the processor has to go and fetch a block of memory. This section prices that, under a model stated explicitly enough to be argued with.

The model, and why it has to be written down

The RAM model charges O(1) for any memory access, wherever the address points. That is the right abstraction for deriving a bound and the wrong one for predicting a runtime, because real memory moves in lines: an aligned block, typically 64 bytes, is the smallest unit transferred between DRAM and the processor. Touching one byte fetches the whole line containing it, and a small pool of recently used lines is kept in cache. So the quantity that predicts a traversal's speed is not "how many elements did you read" but how many distinct lines did you have to fetch, and how many did you have to fetch twice because they had been evicted in between. The figure below simulates exactly that, with the model printed in the panel: 64-byte lines, a fully associative cache of 64 lines holding 4 KB, least-recently-used eviction, cold start. Those are simplifications of a real hierarchy (which is multi-level and set-associative, and which prefetches), and they are deliberately conservative — a real machine's set associativity and limited prefetch make the scattered case worse, not better.

Two separate penalties, often confused

  • The size penalty is unconditional. Every node carries a link the array does not, and every allocation is rounded up to the allocator's grain and carries the allocator's own bookkeeping. With an 8-byte payload the node is at least twice the size of the array element, so even a perfectly laid out chain fetches twice as many lines. With a 4-byte payload it is four times. With a 32-byte record it is 1.5 times, and with a 64-byte one 1.25 times under the same 16-byte allocation grain — still a quarter more memory traffic, so call it small rather than gone. The smaller the payload, the worse linking looks, and that is the single most useful rule of thumb in this section.
  • The scatter penalty is conditional — and it is worth being exact about the condition. The figure models scatter the conservative way: the n nodes occupy one compact run of n × nodesize bytes and only the visit order is shuffled. Under that model, if the whole run fits in cache the visit order does not matter at all — every line is fetched once whatever the order, and a shuffled chain costs exactly what a packed one costs — and the penalty appears only once the footprint exceeds the cache, at which point a shuffled order starts re-fetching lines it has already evicted. The figure marks that threshold. This is why microbenchmarks of linked lists on small inputs are so often reported as "no slower than an array": at small n, for a chain whose nodes happen to be packed together, that is correct. It is not the general case. A chain whose nodes were allocated over a program's lifetime can be spread across the heap one node per line, and then n nodes cost up to n fetches at every n — with no threshold and no small-n reprieve. Which regime you are in is a fact about the allocator and the list's history, not about the data structure, which is precisely why the figure reports the floor rather than a number to quote.
  • The prefetcher is the third, unmodelled penalty. A constant-stride scan is recognised by hardware, which begins fetching the next line before it is requested and hides the latency of the fetch entirely. A pointer chase cannot be prefetched by stride, because the next address is not known until the current node has arrived — the dependency is serial. The model below does not simulate this at all, so its ratios understate the real gap; treat them as a floor.

What this does and does not license you to say

  • Licensed: "these two traversals are in the same complexity class and the array's is cheaper in memory traffic by a factor of at least nodesize / itemsize — a factor of two at an 8-byte payload, four at a 4-byte one, and 1.25 at a 64-byte one." That is a statement about a stated model, reproducible from the figure.
  • Licensed: "the gap shrinks as the payload grows." Set the payload control to 32 bytes and watch the ordered-node ratio fall from 2.00× to 1.50×; at a 64-byte payload it is 1.25×. Small, then — but say "small", not "gone".
  • Not licensed: any specific wall-clock multiplier on any specific machine. That depends on the cache sizes, the associativity, the prefetcher, the allocator's placement policy, whether the list was built in one burst or accumulated over a program's lifetime, and what else is competing for cache. The only way to get such a number is to measure it on the machine in question, and the measurement will not transfer to a different one.
  • Not licensed: "therefore never use a linked list." The structures in §27 are chosen for guarantees the array cannot make — stable references, worst-case constant growth, O(1) splice between containers — and those reasons survive this section intact.

04 Singly linked lists: the traversal loop and the four boundary cases

A singly linked list is the minimal linked structure: one node type with one link field, one external reference head, and null as the terminator. Everything else — tail pointers, counts, sentinels, back-pointers — is an optimisation layered on this, and each one is worth stating as what it buys and what it costs to maintain. Start with the loop that every list operation is a variation of.

the traversal — the shape of every singly linked algorithmcur ← head while cur ≠ null: visit(cur.data) cur ← cur.next loop invariantat the top of each iteration, every node strictly before cur has been visited exactly once, and cur is either null or the first unvisited node terminationeach iteration advances cur one link along a finite acyclic chain ⇒ cur reaches null in n iterations costn link reads, n visits, 1 null test per iteration plus the final one ⇒ Θ(n) time, O(1) extra space

Why the loop is written with the cursor and not an index

The natural-looking alternative — for i in 0 … n−1: visit(get(i)) — is a trap that costs a factor of n. Each get(i) restarts at the head and walks i links, so the total is 0 + 1 + 2 + ⋯ + (n−1) = n(n−1)/2 = Θ(n²) link reads to do what the cursor loop does in n. This is the same quadratic that repeated string concatenation produces, arising for the same reason: an operation that looks constant in the notation is linear in the structure. If a list type offers indexed access at all, treat every call as a fresh traversal, and never put one inside a loop over the same list.

The four positions, priced

  • Insert at the head — new.next = head; head = new. Two writes, no traversal, worst-case O(1). This is the operation the structure is for, and it is the reason a singly linked list is the natural node-backed stack.
  • Delete at the head — head = head.next. One write, no traversal, O(1). Must first check head ≠ null, which is boundary case number one.
  • Insert at the tail — Θ(n) with only a head pointer, because the last node must be found; O(1) if a tail reference is maintained. Maintaining it is three lines and two extra assignments per operation, and getting one of them wrong is boundary case number two: every insertion into an empty list must set tail as well as head — and that is true of the head-insert too, which otherwise never touches tail at all. It is exactly because the head-insert normally leaves tail alone that the empty case is the one people forget.
  • Delete at the tail — Θ(n), and a tail pointer does not help. The operation needs to write null into the second-to-last node's link field, and from tail there is no route backwards. You must walk from the head to find the predecessor. This single asymmetry is the strongest practical argument for the doubly linked list, and the reason a singly linked list makes a fine stack and a bad deque. Boundary case number three: deleting the last remaining node must reset tail to null as well as head.

Note also that the invariant above is what makes the loop obviously correct: each iteration visits one node and advances past it, the set of visited nodes grows by exactly one, and the loop cannot revisit a node because the chain is acyclic. Drop that assumption and the loop does not terminate — which is the entire subject of §10.

Building a list, and the order that surprises people

Repeatedly inserting at the head builds the list in reverse of the insertion order, in Θ(n) total. Repeatedly inserting at the tail preserves the order, in Θ(n) total if a tail pointer is kept and Θ(n²) if it is not — the classic accidental quadratic in list-building code, and the reason so many list routines build reversed and then reverse once at the end (§11), which is Θ(n) and needs no tail pointer at all. The same trick appears in recursive list code: build the result backwards on the way down, reverse once on the way out.

Maintenance cost is part of the price. Every auxiliary field — tail, a node count, a "last accessed" cursor — must be updated on every operation that could invalidate it, including the ones written months later by someone else. A list with three auxiliary fields has three invariants, and each one has an empty-list case and a one-element case. Most linked-list bugs in production code are a missed update to an auxiliary field, not a mistake in the splice.

05 The predecessor problem, and the trick that dodges it

The predecessor problem is the standing consequence of a one-way link: given a node, a singly linked list offers no way to find the node that points at it, short of searching for it from the head. Almost every awkward thing about singly linked lists is a restatement of that one sentence, and the sharpest version of it is a question. "Delete this node in O(1)" is one of the most-asked questions about linked lists, and the honest answer is that on a singly linked list it is impossible as stated — and that there is a trick which produces something almost as good, with a defect at exactly one position and a second defect that has nothing to do with position at all. Both are worth understanding precisely, because the trick is correct and useful in some designs and silently wrong in others.

Why the predecessor is needed

Removing a node from a chain means making the chain skip it, and "the chain" is a set of link fields living inside other nodes. The only field that has to change is the one in the node immediately before the target. A singly linked node holds no reference to whoever points at it — the link relation is one-way — so from the target alone that field is unreachable. The only way to find it is to start at head and walk until prev.next === target, which is Θ(k) for a target at position k and Θ(n) in the worst case. This is why the cost table in §02 splits insertion and deletion at a held node onto two rows rather than quoting them as a pair: O(1) deletion at a held node is a claim about a doubly linked list, or about a caller who happens to be holding the predecessor rather than the target, and it is false of a bare singly linked one.

the constraint, stated as a reachability factfrom a node x in a singly linked list, the reachable set is { x, x.next, x.next.next, … } the predecessor of x is NOT in that set (unless the list is circular — §08) thereforeremove(x) given only x requires a search from head Θ(position of x) unless you change what "remove" meansremove the VALUE at x, rather than the NODE x — which the successor trick does

The copy-the-successor trick

Given only a reference to node x, and provided x.next ≠ null: copy the successor's payload into x, then unlink the successor. Two writes, one payload copy, no traversal at any position. The list's sequence of values afterwards is exactly what deleting x would have produced, so from the outside — from anyone who only ever reads the list by traversing it — the operation is indistinguishable from a real deletion in O(1).

Three ways to remove a node you hold a reference to the third mode runs the trick where it does not work, and reports the fault

The two defects, in order of how often they bite

  • It cannot be applied to the tail. The trick works by sacrificing the successor, and the last node has none. Run the third mode of the figure and the routine faults on x.next.data. There is no patch inside the trick: any fix is structural — walk from the head after all (giving up the O(1) exactly where it was most wanted), keep a back-pointer (§06), or give the list a trailer sentinel so that no node holding real data is ever last. The third option is the cheapest, and it is one of the strongest arguments for sentinels.
  • It deletes the wrong object. The values are right; the identities are not. The node that survives is the one that held the deleted value, and the node that dies is the one that held the surviving value. Any reference held outside the list — an iterator, a cached pointer, an index in a hash map from key to node, another container's link to the same node — now points at a node that has been unlinked, or at a node whose payload has silently changed underneath it. Both are failures of aliasing discipline — two names for what the program believed was one object, which have quietly come to name different things — and the outside reference to the unlinked successor is a dangling one. In a language with manual memory management this is a use-after-free waiting to happen; in a managed one it is a quieter bug where an object that should have disappeared stays alive and an object that should have survived does not. The trick is safe exactly when no reference to any node escapes the list.

The cost, measured

The figure counts all three methods on the same six-node list. The walk to the predecessor of position k costs k − 1 cursor advances plus one link write; at k = 3 that is two advances. The trick costs zero advances, one payload copy and one link write at every interior position — it is genuinely constant, and the readout says so by measurement rather than assertion. And at the tail it costs one fault. Whether the difference between Θ(k) and O(1) is worth the identity hazard is a design question with a clear decision rule: if the nodes are private to the list, take the trick; if anything outside the list knows about a node, do not.

The general lesson, which recurs. When a structure cannot answer a question, you have three moves: search for the answer (pay time), store the answer (pay space, and pay to maintain it — this is the back-pointer), or change the question (this is the trick, and it works only if the weaker guarantee is genuinely enough). The whole of §07 is the second move applied to boundary conditions, and every index in a hash table or tree is the second move applied to lookup.

06 Doubly linked lists: what the back-pointer buys

A doubly linked list is a linked list whose nodes carry two links: one to the successor and one to the predecessor. Add that second field and the structure changes character. Every node now knows both of its neighbours, so every local operation becomes local: removal, insertion on either side, and traversal in either direction, all from a node reference alone, all in O(1), with no walk and no trick. The price is one extra word per node and one extra invariant to maintain on every single link write.

The four capabilities the second link buys

  • Removal from a held node, genuinely O(1), with correct identity. This is the row of the §02 table that the singly linked list could only fake. The node that dies is the node you asked to remove — so outside references behave as they should, and the copy-the-successor hazard disappears entirely. This capability, rather than the backwards traversal, is the usual reason a general-purpose list type in a library is doubly linked.
  • Insertion before a held node. Symmetric with insertion after, and the reason list APIs can offer insert_before(pos, v) without a linear search.
  • Backward traversal and a genuine O(1) pop_back. With a tail pointer, tail.prev is the new tail in one read. The asymmetry that made a singly linked list a bad deque is gone, and the doubly linked list becomes the natural node-backed deque.
  • A bidirectional iterator with a well-defined "one before". Iterators over a singly linked list can only advance; over a doubly linked list they can also retreat, which is what lets an algorithm back up one position without re-walking from the head.

What it costs, stated precisely

  • One extra word per node, unconditionally. With an 8-byte payload on a 64-bit machine, a singly linked node needs 16 bytes and a doubly linked one 24 — so by the argument of §03 a doubly linked traversal fetches 1.5× the lines of a singly linked one, and 3× the lines of a packed array of the same payloads. Doubling the links doubles neither the bound nor the constant, but it does move it in the wrong direction.
  • Two invariants instead of one, on every write. Every link change must be mirrored. A routine that updates next and forgets prev produces a list that traverses correctly forwards and is corrupt backwards — a bug that hides until something iterates in reverse, which may be months later and in different code. This is the single most valuable thing a debug-mode consistency check can assert: walk forward collecting nodes, walk backward from the tail, and require the two sequences to be exact reverses.
  • More boundary cases, not fewer. Each splice now has a null test at both ends rather than one, so the naive implementation has more case analysis than the singly linked one. That is exactly the problem the next section removes.

Step 4 is the one people omit. A deleted node that still points into the list is a live hazard: a stale iterator that dereferences it walks back into a structure it is no longer part of, and a second removal of the same node will happily rewrite a.next and b.prev with garbage — the double-free's structural equivalent. Nulling both fields turns that silent corruption into an immediate, obvious null dereference. Some implementations go further and write a poison value, so the failure names itself in a debugger.

Two links is not the last word. A node may carry any number of links, and each one buys a different question a cheap answer. A skip list gives some nodes extra forward links that jump ahead by powers of two, buying O(log n) expected search on a linked structure; a binary search tree gives each node two links interpreted as "smaller" and "larger"; an adjacency list gives each node a whole list of links. The design question is always the same one: which query is being paid for, and who maintains the extra links when the structure changes?

07 Sentinels: deleting the boundary cases rather than handling them

A sentinel is a node that holds no data and exists only so that the boundary of the structure is never null. A doubly linked list with a header before the first real node and a trailer after the last has no null link fields anywhere between them — so every real node has a real predecessor and a real successor, and every splice is the same three or four writes with no case analysis at all. That is the entire idea, and its effect on code quality is out of all proportion to its size.

the structureH ⇄ x₀ ⇄ x₁ ⇄ ⋯ ⇄ x₍ₙ₋₁₎ ⇄ T H = header, T = trailer, neither holds data an empty list is not a special case — it is thisH ⇄ T size = 0, and every routine still works the universal splice — every insertion in the whole implementation is a call to thisinsertBetween(p, q, v): y ← new node(v) ; y.prev ← p ; y.next ← q ; p.next ← y ; q.prev ← y and every insertion the ADT offers is one line on top of itaddFirst(v) = insertBetween(H, H.next, v) addLast(v) = insertBetween(T.prev, T, v) addBefore(x, v) = insertBetween(x.prev, x, v) addAfter(x, v) = insertBetween(x, x.next, v) the universal removal — no test for "is x first?" or "is x last?" exists anywhereremove(x): x.prev.next ← x.next ; x.next.prev ← x.prev the only tests left are genuine preconditions, not link casesisEmpty() ≡ H.next = T popFirst on an empty list is an ERROR, not a null link

Why this works: the invariant it establishes

The null tests in a boundary-free implementation exist to answer two questions — "is this node the first?" and "is this node the last?" — and both questions arise because the answer changes what has to be written. Sentinels make the answer always no. Every node the user can reach has a non-null prev and a non-null next; the header's prev and the trailer's next are the only nulls in the structure and no operation ever reads them. The invariant, stated once and then relied on everywhere, is: every node between H and T inclusive has both neighbours present, and H and T are never removed. Establishing an invariant so that downstream code can stop checking is the same move as a loop guard in a search, a padded border on an image convolution, or a bias term that removes a special case from a linear model — buy one piece of structure, delete a category of conditionals.

The write columns say the rest: sentinels are not buying speed. They are buying the deletion of a category of bug, at a cost of two nodes per list.

Where sentinels stop being worth it

  • Many small lists. Two sentinel nodes per list is a fixed overhead. A hash table with a hundred thousand buckets, each a list averaging one element, pays two hundred thousand empty nodes — often more memory than the data. This is the standard argument for null-terminated buckets, or for storing the first element inline in the bucket.
  • Singly linked lists. A header sentinel alone still removes the "insert or delete at the front" case, which is most of the benefit, and costs one node. A trailer sentinel buys less for the ordinary operations, because the front is where a singly linked list's boundary cases live — but it is not worthless: it is exactly what makes the copy-the-successor trick total, since with a trailer present no node holding real data is ever last. Which of the two is worth a node depends on which problem you have.
  • Where the sentinel can be mistaken for data. If a sentinel carries a payload field at all, some traversal somewhere will eventually read it. The standard discipline is that sentinel payloads are never valid, iteration is defined as stopping at the trailer rather than at null, and any public API that could hand a user a position pointing at a sentinel must return "no such element" instead.
  • A different use of the same word. "Sentinel" also names the trick of appending the search key to the end of an array so a linear scan needs no bounds check — the same idea, guaranteeing a loop terminates without testing a boundary, applied to contiguous storage. Both usages remove a conditional by adding an element.
Asymptotically nothing, practically a lot. Sentinels change no complexity bound on this page; they reduce constant factors slightly and reduce case analysis enormously. The right way to justify them is not "faster" but "there is no first-element case and no last-element case, because there is no first element and no last element" — a statement about the shape of the code rather than its speed.

08 Circular lists

Point the last node's link at the first instead of at null and the list becomes a ring. There is no end, so there is no terminator; there is no first node, only whichever node the external reference currently names; and a traversal must be told when to stop by something other than a null, because it will never find one. That last sentence is the whole design trade: circularity removes one class of boundary and introduces one class of non-termination.

What circularity buys

  • Both ends from one reference. A singly linked circular list with a tail pointer reaches the front in one read — tail.next — so it supports addFirst, addLast and removeFirst all in O(1) with a single external pointer, which a null-terminated singly linked list needs two pointers to do. (removeLast is still Θ(n); the predecessor problem does not care that the list is circular.)
  • Rotation for free. "Move the front element to the back" is tail ← tail.next, one assignment, no allocation, no copying, no element moved. That is the operation a round-robin scheduler performs on every quantum, and the reason circular lists are the textbook representation of a cyclic turn order — players in a game, buffers in a pool, processes sharing a CPU.
  • Concatenation in a constant number of writes. Two rings with tails t₁ and t₂ are joined by swapping the two next fields: t₁.next ↔ t₂.next, then the combined tail is t₁ (or t₂, depending on the order wanted). Splicing a ring into another ring at a held node is the same two writes. This is the operation that makes circular lists appear inside other structures — the child lists of a Fibonacci heap are circular doubly linked lists precisely so that merging and cutting are constant-time and case-free.
  • No null tests at all, once the empty case is handled. Combine circularity with a sentinel and you get the cleanest doubly linked list design in common use: a single dummy node whose next is the first element and whose prev is the last, so an empty list is the dummy pointing at itself and every operation — including on the empty list — is the same case-free splice. One extra node, no nulls, no head/tail pointers to keep in sync, and the list header itself can be the dummy, embedded in the owning object rather than allocated.

What it costs

Every traversal must carry its own stopping condition, and getting it wrong is an infinite loop rather than a null dereference — a failure mode that is harder to diagnose because it produces no exception and no stack trace, just a program that stops making progress. The two correct idioms are compare against the starting node (a do … while (p ≠ start), which visits every node exactly once and handles the one-element ring correctly) and count down from a maintained size (which requires the size to be accurate, and fails silently if it is not). The tempting third idiom — a while (p ≠ start) loop written head-first — visits nothing, because p = start on entry. Searching a circular list for a value that is not present must likewise be bounded by the start comparison, or it never returns.

Everything the linked ring gets free from its structure, the array ring has to pay for in index arithmetic, and everything the array ring gets free from contiguity, the linked ring pays for in cache misses.

09 The runner: two cursors at different speeds

The runner technique is a traversal that carries two cursors instead of one and maintains a fixed relationship between them — a ratio of speeds, or a constant separation — so that the relationship, at the moment the loop ends, is the answer. It exists because a linked list cannot answer "where is the middle?" or "what is the tenth node from the end?" by arithmetic, and the obvious algorithm — walk once to find the length, then walk again to the target — takes two passes. The runner answers both in one pass and O(1) extra space. It is the linked-list counterpart of the two-pointer pattern on arrays, and the difference between them is instructive: on an array the two pointers are indices whose difference is meaningful; on a list they are references whose separation exists only because the loop maintains it.

What else the pattern solves in one pass

  • Delete the k-th node from the end.   • Split a list in half. Run the fast runner with the first guard, keep the node before slow, cut its link — the ✓ pairing in the table above. The pattern behind the pattern. Both runners work by maintaining a relationship between two cursors that the loop body preserves — a ratio of speeds, or a constant separation — so that when the loop's termination condition fires, the relationship forces the answer. That is a loop invariant used constructively rather than defensively: you are not checking that the invariant holds, you are choosing an invariant whose truth at termination is the result you want.

10 Cycle detection, and the entry-point argument

A linked list with a cycle is one in which some node's link points at a node already on the path from the head — usually by accident, from a splice that closed a loop. Every traversal over such a list runs forever, so detecting the condition matters; and because the naive detection (record every node visited in a set) costs Θ(n) extra space, the constant-space alternative is one of the few genuinely clever small algorithms. It has two phases: the first proves a cycle exists and finds a node in it, the second finds the node where the cycle begins. The second phase's correctness is the part usually stated without proof, so it gets one here.

The shape, and the two parameters that describe it

Any list reachable from a single head has exactly one of two shapes: a straight chain ending in null, or the rho shape — a tail of μ nodes running into a cycle of λ nodes, so named because the picture is the Greek letter ρ. A node's position is then either an index i < μ in the tail, or a cycle offset (i − μ) mod λ. Both μ and λ are unknown to the algorithm; the point of the two phases is that phase one recovers a multiple of λ and phase two recovers μ, without ever computing either directly.

Step through phase 1 and watch the gap rather than the positions: once both cursors are on the ring, the fast one closes on the slow one by exactly one node per round, so it can never jump over it and a meeting is forced within λ rounds of both entering. Then switch attention to phase 2, where the surprise is that no arithmetic is performed at all — the algorithm never computes μ or λ, it just walks two cursors at the same speed and lets the congruence do the work. Set the tail length to 0 and the entry becomes the head itself, and phase 2 terminates in zero steps; set the cycle length to 2 and watch the meeting round jump to the next multiple of 2 at or above the tail length. Every one of those predictions is checked against the measured run in the readout.

The alternatives, and when each is right

  • A visited set. Walk the list, inserting each node's identity into a hash set and stopping when an insert finds a duplicate. O(n) expected time and Θ(n) space, and the first duplicate is the entry node directly — no second phase needed. Simpler to write and to read; use it unless the space matters.
  • Marking nodes. Set a visited flag in each node. Θ(n) time and O(1) auxiliary space, but it mutates the structure, needs a field the nodes may not have, and is not safe under concurrent readers or on a shared structure. Real cycle collectors do a version of this; general-purpose list code should not.
  • Brent's algorithm. A different constant-space cycle finder: keep one cursor fixed, advance the other, and teleport the fixed one to the moving one whenever the distance reaches the next power of two. It finds λ directly, typically performs fewer link traversals than Floyd's, and is the one to reach for when following a link is expensive. Floyd's stays the canonical exposition because the two-speed invariant is easier to state.
  • Nothing at all. The best answer in most production code is to make cycles impossible by construction — build lists through an API that cannot close a loop — rather than to detect them afterwards.
Where this generalises. Nothing in either phase uses the fact that the structure is a list. The argument applies to any functional graph — any iteration x ← f(x) on a finite set — because such an iteration is exactly a rho shape. That is why the same algorithm detects cycles in a pseudo-random number generator's sequence, finds the repeating part of a decimal expansion, and underlies Pollard's rho method for integer factorisation. The structure this page draws is a special case of the general one.

11 Reversal, iterative and recursive

Reversing a linked list is the canonical exercise for a reason: it cannot be done by moving data, only by rewriting links, and the loop that does it needs exactly three references and no extra memory. It is also the cleanest small demonstration of the difference between an O(1)-space iterative algorithm and an O(n)-space recursive one that looks like it uses no memory at all.

Why the save must come first

The line nxt ← cur.next looks like bookkeeping and is the entire algorithm. After cur.next ← prev executes, the only reference in the program to the rest of the list is whatever was saved beforehand; if nothing was, every node after cur is unreachable and gone. This is the same ordering constraint as the insertion in §01 and it has the same general form: when rewriting a link, read everything you still need through it before you overwrite it. Almost every "my list lost half its elements" bug is this rule violated.

The recursive version, and the space it does not admit to

The recursive formulation is shorter and, to many readers, clearer: reverse everything after the head, then make the old second node point back at the head and cut the head's own link. Its correctness argument is an induction — assume the recursive call returns the head of a correctly reversed suffix, and check that the two writes attach the current node to the end of it — and it performs 2(n−1) link writes rather than n, because each frame writes the flip and then nulls the old link. But the real difference is the one the source code does not mention: it holds a stack frame per node, so the space is Θ(n) rather than O(1), and on a long list it overflows the call stack. Switch the figure to the recursive mode and the column of live frames on the right is the measurement of exactly that. A list of ten million nodes reverses fine iteratively and crashes recursively, in a language without tail-call elimination — and this recursion is not tail-recursive anyway, because work happens after the recursive call returns.

What reversal is actually used for

  • Undoing a head-built list. Building by repeated head insertion is O(1) per element and produces the reverse order; one Θ(n) reversal at the end fixes it. Total Θ(n), no tail pointer needed — strictly better than maintaining a tail, and much better than the Θ(n²) of appending without one.
  • Palindrome and comparison checks in constant space, by reversing one half in place, as §09 describes.
  • Adding numbers stored least-significant-digit-first, and the other digit-list problems where the natural traversal direction is the opposite of the stored one.
  • As the model for every in-place pointer rewrite. Rotating a list by k, swapping adjacent pairs, partitioning around a value, merging two sorted lists — all of them are the same discipline of "save, rewrite, advance", and getting reversal exactly right is the cheapest way to learn it.
Reversal is O(1) in a doubly linked list — sort of. If a doubly linked list is implemented so that "forward" and "backward" are chosen by a flag rather than baked into the field names, reversing it is flipping the flag: one write, O(1). That is a genuine trick and it is also a warning about what "reverse" means — the nodes and links did not change at all, only the interpretation did. A structure's operations are only as cheap as the representation lets them be, and choosing the representation is the design.

12 What a stack is: the LIFO contract

A stack is a collection with one accessible end. Elements are added and removed at that end only, so the element removed is always the one most recently added — last in, first out. That is the entire specification. It says nothing about how the elements are stored, and the restriction is not a limitation that implementers work around; it is the point, because a structure that promises less can guarantee more: every operation a stack offers can be done in constant time, and on a node-backed implementation in worst-case constant time. (On an array-backed one push is O(1) amortized, with a Θ(n) resize hiding in it — a distinction §13 measures rather than asserts, and one worth keeping straight from the first sentence.)

Why the restriction is worth something

  • Every operation is worst-case constant. Not amortized, not expected — constant, on the node-backed implementation, with no resize and no rehash. That is a latency guarantee, and it is available because nothing may be asked of the middle.
  • The implementation is free to choose. Because the interface never mentions position, it can be satisfied by the end of a dynamic array or by the front of a singly linked list, and callers cannot tell which. Wrapping an existing container in the narrower interface is the adapter pattern, and it is exactly how standard libraries usually ship stack and queue — not as structures in their own right but as thin adapters over a deque or a vector, with the underlying container a parameter. §13 compares them; both are correct, and the choice is made purely on latency, memory and locality.
  • The restriction is a correctness tool. A routine that takes a stack cannot accidentally read the wrong element, because there is no way to name one. Shrinking an interface to what an algorithm actually needs is the cheapest way to make classes of bug unrepresentable — the same argument as passing a read-only view instead of a mutable one.
  • It matches the shape of a class of problems exactly. Whenever a problem says "the most recently started thing must be finished first", a stack is the problem's structure rather than a data structure chosen to solve it: nested delimiters, nested function calls, nested scopes, nested markup, backtracking through choices, undo of actions. §18 collects them.

The two preconditions, and what to do about them

pop and top are partial — undefined on an empty stack — and every implementation must decide what happens when the precondition is violated. The three standard answers are to raise an error (which makes the bug loud and is right when emptiness indicates a logic error), to return a sentinel value such as null (which is convenient and quietly conflates "empty" with "the top was null"), or to offer a total variant — tryPop returning a success flag, or a peek that returns an optional. There is no universally right answer, but there is a universally wrong pattern: returning a sentinel and never checking it. Note also the second precondition, usually unstated: a bounded stack can be full, and push on a full stack is the symmetric partial case — which is precisely what a stack overflow is.

Where the name comes from, and why it is worth taking literally

The picture is a spring-loaded stack of plates in a canteen: you put a plate on top and you take the top plate off, and no plate in the middle is reachable without removing everything above it. Two things in that image are accurate and worth keeping. First, the only observable element is the top — anything else requires destroying the state above it, which is why "find the maximum in a stack" is not a stack operation. Second, the stack has no intrinsic bottom from the user's point of view: the operations behave identically whether there is one element below or a million, which is exactly the property that makes recursion compose.

ADT versus implementation, again. "Stack" names a contract; "array-backed stack" and "node-backed stack" name two structures that satisfy it. The habit worth keeping — the same one Arrays & Strings §03 argues for — is to write algorithms against the contract and choose the implementation separately, on evidence. Almost all of this page's stack material is about the contract; only §13 is about the structures.

13 Array-backed against node-backed, measured

Both implementations give the contract of §12 in constant time per operation — worst-case constant for the nodes, amortized constant for the array, which is the first of the differences and not the last. Reading the figure: three different claims, all true at once

The two things the table says that the bars cannot

Reference stability is the row that most often decides real designs: a node's address never changes, so a pointer into a node-backed stack stays valid across any number of pushes, while a pointer into an array-backed one is invalidated by every resize. And memory cuts both ways — the array holds up to 100% slack after a doubling and the nodes hold a link plus allocator overhead per element, so which wastes more depends entirely on the payload size, exactly as in §03. Do the arithmetic rather than trusting the slogan: with an 8-byte payload the node pays 8 bytes of link — plus whatever the allocator's own header and grain rounding add — against an array slack of at most 8 bytes per element and, averaged over a doubling cycle, rather less, so the nodes lose but not by the factor people expect. With a 64-byte payload the node's fixed overhead is still about 16 bytes while the array's worst-case slack is 64, and the array is the bigger waster.

A hybrid beats both, and libraries know it. Allocate the stack as a chain of blocks — say 64 elements each — with the top block's fill index playing the role of size. Pushes are a write and an increment; a block boundary allocates one new block, which is O(1) worst case rather than Θ(n); elements are contiguous within a block, so the traversal locality is nearly the array's; and no element ever moves, so references stay stable. That is roughly the shape of a production deque, and it is the standard answer when neither pure implementation is acceptable.

14 The call stack: the stack you are already using

Function calls nest — a call that starts later must finish earlier — which is the LIFO property exactly. So the machinery that runs your programs is a stack, maintained by the compiler and the processor, and understanding its shape explains recursion depth, stack overflow, why local variables vanish on return, and why a recursive algorithm's space cost is so easy to forget. This section is not an aside about hardware; it is the most important application of §12 on the page.

The distinction the figure exists to make

At the default fib(4) the readout reports nine calls where the tower is never more than four frames tall; push n to 5 and it is fifteen calls against five frames. The number of calls is the time cost; the height of the tower is the space cost, and for fib the first is exponential in n while the second is linear. Confusing them leads to two opposite mistakes: fearing that a deeply branching recursion will exhaust memory (it will not, if it is shallow), and assuming that a cheap-looking linear recursion is free (it is not — Θ(n) frames on a list of ten million nodes will overflow before it finishes, which is exactly what §11's recursive reversal demonstrates).

Four consequences worth carrying around

  • Local variables are frame slots, so they die on return. Returning a pointer to a local is returning a pointer into space that the next call will reuse — the classic dangling-pointer bug in languages that allow it. Heap-allocated nodes, by contrast, outlive the call that made them, which is why a linked structure built in a recursive routine survives and an array declared locally does not.
  • Recursion can always be converted to an explicit stack. Anything the call stack does, a stack you allocate yourself can do — and then the depth is limited by the heap rather than by the thread's stack reservation, and the state you push is exactly the state you need rather than a whole frame. This is how iterative tree traversals and iterative depth-first search are written, and it is the standard fix for a recursion that overflows.
  • Tail calls are the special case where the frame is not needed. If the recursive call is the very last thing a function does, the caller's frame holds nothing that will be read again, so an implementation may reuse it rather than push — turning Θ(n) space into O(1). Whether this happens is a property of the language and the compiler, not of the code; do not rely on it unless the language guarantees it. And note that the recursive list reversal in §11 is not tail-recursive, because two writes happen after the call returns.
  • The stack is where the trace comes from. A stack trace is a walk down the live frames, possible because the return address into each caller is recorded somewhere the walker can find. Where exactly is a platform question — a chain of saved frame pointers when they are kept, and side tables generated by the compiler when they are not — but either way it is the same "store the reference rather than compute it" decision this page opened with, applied to control flow.
Two stacks, one idea. The call stack is the operating system's and the compiler's; the explicit stacks of §12 and §13 are yours. They have the same contract and are used for the same reason — LIFO is the shape of nested work — and the only real differences are who allocates the memory and how much of it there is. When a recursive algorithm is rewritten with an explicit stack, nothing about the algorithm has changed; only the ownership of the storage has.

15 Balanced delimiters: the smallest problem that needs a stack

Given a string containing ( ) [ ] { } among other characters, decide whether the delimiters are correctly nested. The interesting thing about this problem is not the algorithm — it is one pass and eight lines — but the fact that a running tally per bracket type is demonstrably not enough as soon as there is more than one kind of bracket, and the reason why is the clearest small argument for what a stack actually contributes.

Why counting fails, and what the stack adds

With one bracket type, a counter works: increment on an opener, decrement on a closer, reject if it ever goes negative, require zero at the end. With two types it does not, because ([)] and ()[] have identical counts for both symbols and only the second is correctly nested. What the counter has lost is which opener is currently innermost, and that is exactly what a stack preserves: the top of the stack is always the most recently opened, still-unclosed delimiter, which is the only one a closer is allowed to match. The invariant is worth stating explicitly, because it is what makes the one-pass algorithm obviously correct.

On the default string {[a+(b*c)]-d} the scan performs three pushes, three pops and three comparisons against the top, and the stack never holds more than three entries — which is the string's nesting depth, and also the algorithm's space. Switch to crossed nesting and the rejection happens at the first character that cannot be explained, with the stack still holding the opener that proves it; switch to an opener never closed and the failure happens only at end of input, because nothing before that point was locally wrong. That difference — reject-early versus reject-at-the-end — is characteristic of every stack-based parser, and it is why a good error message names both the offending closer and the index of the opener it failed to match, which the stack has right there.

Where the same algorithm reappears, essentially unchanged

  • Markup and tag nesting. <a><b></b></a> is the same problem with longer delimiters; every XML and HTML parser keeps this stack, and the error "unexpected closing tag, expected </b>" is the top of it being reported.
  • Block structure in compilers. begin/end, braces, and indentation-based blocks all push a scope on entry and pop it on exit; the symbol table of a lexically scoped language is a stack of scopes, so that a name lookup walks from the innermost outwards.
  • Editor bracket matching. Highlighting the partner of the bracket under the cursor is this scan run from the cursor outwards, and "jump to matching brace" is the same.
  • Well-formedness checks generally. Any grammar whose nesting is context-free but not regular needs this stack — and that is the formal version of the counting argument, stated carefully. The language of balanced brackets over two or more bracket types is context-free but not regular, so no finite-state machine recognises it; a pushdown automaton — a finite-state machine plus a stack — does, and the checker above is one. What that argument does not say is that "counters can never work": a machine with two unbounded counters is a strictly more powerful device than a finite-state machine (it is Turing-complete, in fact), so the impossibility is about finite state, not about arithmetic. The honest claim is the narrow one this section actually demonstrated — a tally per bracket type, updated once per symbol, cannot distinguish ([)] from ()[], because it has thrown away the one thing that matters: which opener is innermost.
The general shape. The stack here holds obligations — commitments made that must be discharged in reverse order. That framing transfers directly: the call stack holds pending returns, an undo stack holds reversible actions, a depth-first search stack holds vertices whose exploration is unfinished, and a backtracking search's stack holds choices that may need to be retracted. Whenever the obligations are discharged innermost-first, the structure is a stack, and the invariant is always "the stack holds the outstanding obligations, most recent on top".

16 Evaluating postfix with one stack

In postfix notation — also called reverse Polish — each operator is written after its operands: 3 4 + rather than 3 + 4. The notation needs no parentheses and no precedence rules, because the order of the tokens already determines the grouping completely, and it is evaluated by a loop over the tokens with a single stack of operands. That combination — no lookahead, no backtracking, no parse tree, one pass, Θ(n) — is why postfix is the internal form of so many calculators, virtual machines and bytecode instruction sets.

Prefix, infix, postfix — and which is easy for whom

  • Infix (a + b) is what people read. It requires precedence rules, associativity rules and parentheses to be unambiguous, and evaluating it directly needs either a parse tree or the stack pair of §17.
  • Postfix (a b +) is what machines evaluate. No parentheses, no precedence, one stack, one pass. It is a post-order walk of the expression tree written out linearly.
  • Prefix (+ a b), also called Polish notation, is a pre-order walk. It is evaluated by scanning right-to-left with the same one-stack loop, or by recursive descent left-to-right — which is exactly why languages built on prefix syntax parse so easily.
  • All three contain the same tree. Infix, prefix and postfix are the in-order, pre-order and post-order traversals of one expression tree, and the conversions between them are traversals of that tree. That is the single most useful thing to know about the three notations, and it makes the next section's algorithm feel less like a trick.
Where this lives in practice. A stack-based virtual machine — the execution model of several widely used bytecode formats — is this evaluator, generalised: instructions push operands and pop them, and a compiler emitting bytecode for an expression is emitting its postfix form. The same one-stack evaluator is what a spreadsheet uses on a formula, what a shell arithmetic expansion uses, and what most calculator firmware has used since long before either.

What the operator stack is holding

The same thing the delimiter stack held in §15: obligations. An operator on the stack is an operation that has been read but cannot yet be emitted, because a more tightly binding operation might still arrive to its right. The rule for popping is exactly the test "can this waiting operator no longer be overtaken?", and when the answer is yes it is emitted. Seen that way, the parenthesis barrier is not a special case at all — it is an obligation that can only be discharged by its matching closer, and it blocks everything beneath it because nothing outside the parentheses may be applied before what is inside.

Two stacks give direct evaluation. Run this algorithm with a second stack of operands and, instead of emitting an operator, apply it immediately to the top two values — and you have evaluated the infix expression in one pass without ever building the postfix string. That two-stack variant, and the precedence-climbing recursive parser that computes the same thing with the call stack doing the waiting, are the two standard ways real parsers handle expressions. They are the same algorithm with the obligations stored in different places.

18 The rest of the stack's job list

Every use of a stack is the same observation applied to a different domain: work that nests must be finished innermost-first, and the structure that enforces that is the one whose only reachable element is the most recent. Collecting the applications makes the pattern recognisable, which is the useful part — the goal is to see a new problem and notice that it is stack-shaped before reaching for anything else.

Backtracking and depth-first exploration

A search that makes a choice, explores its consequences, and retracts it on failure is a stack of choices: push the decision and the state needed to undo it, and pop on the way back. Written recursively the stack is the call stack; written iteratively it is explicit. Depth-first search is exactly this on a graph — push the start, then repeatedly pop a vertex and push its unvisited neighbours — and the single-line difference between DFS and breadth-first search is that BFS uses a queue instead. That substitution changes the shape of the exploration completely while changing nothing else in the code, which is the cleanest demonstration on this page that an ADT's contract is what determines an algorithm's behaviour. The same pattern is maze solving, N-queens, sudoku, constraint propagation with retraction, and the recursive enumeration that memoization later prunes.

Undo, redo, and history

An undo facility pushes a description of each action — enough to reverse it — and pops to undo. Redo is a second stack that the undo pops feed into, and performing a fresh action clears the redo stack, which is why you cannot redo after typing something new. The same pair of stacks is a browser's back and forward buttons. Two design notes that follow from the structure: the undo stack is usually bounded, which makes it a ring buffer of actions rather than an unbounded stack, and the pair of stacks only behaves correctly if every recorded action is genuinely invertible from what was stored — otherwise undo produces a state that never existed.

Evaluation, parsing and machine execution

  • Expression evaluation — §16 and §17.
  • Nesting checks in any language with matched delimiters — §15.
  • Scope handling. A compiler's symbol table is a stack of scopes; entering a block pushes, leaving pops, and a name lookup scans from the top down, which gives lexical shadowing for free.
  • Stack machines. Several widely used bytecode formats define their instruction set over an operand stack, so a compiler emitting code for an expression is emitting its postfix form and the interpreter is the evaluator of §16.

Reversal, and the two-stack idioms

Pushing a sequence and popping it yields the reverse — the simplest possible use, and the reason a stack turns up in any "process these in the opposite order" problem, including the post-order traversal trick of running a modified pre-order and reversing the result. Two stacks together buy more: a stack that also answers min() in O(1) keeps a parallel stack of running minima, pushing a new minimum alongside every push; a queue built from two stacks uses one for arrival order and one for departure order, with an amortization argument that §25 proves; and a stack that answers "where is the next element to my right that is smaller than this one?" in amortized O(1) per element is the monotonic-stack pattern. Note what that pattern does and does not give: the position of the next smaller element on each side, cheaply — not a count of how many later elements are smaller, which is the inversion-counting problem and needs a merge sort or a Fenwick tree, not a stack.

The monotonic stack

A stack kept in sorted order by construction — push, but first pop everything that violates the order — solves a family of array problems in Θ(n) that look quadratic: next greater element, largest rectangle in a histogram, daily temperatures, stock spans, and trapping rain water. The cost argument is the aggregate method: each element is pushed once and popped at most once, so however many pops one iteration performs, the total over the whole run is at most n. That is the same accounting that makes the sliding window linear, and recognising it is usually the moment a problem stops looking hard.

The test for stack-shapedness. Ask: when I finish with something, is it always the most recently started thing? If yes, the structure is a stack and the code will be short. If instead the thing finished is the one that has been waiting longest, it is a queue. If it is the one with the highest priority, it is a priority queue, and that needs a heap. Those three questions cover most of the ordering decisions in ordinary programs.

19 What a queue is: the FIFO contract

A queue is a collection with two accessible ends: elements are added at one and removed at the other. The element removed is therefore always the one that has been waiting longest — first in, first out. Like the stack, it is deliberately impoverished so that every operation can be constant-time — worst-case constant on a fixed-capacity ring or a linked queue, amortized constant once the storage has to grow; unlike the stack, its two ends are different, and that difference is what makes the implementation interesting rather than obvious.

Why the second boundary changes everything

A stack's occupied region always starts at a fixed place and grows and shrinks at one end. A queue's occupied region has both ends moving forward — enqueues push the back forward, dequeues push the front forward — so over a long run the occupied window marches steadily through the storage, leaving used-and-released space behind it. Every array-backed queue implementation is an answer to the question of what to do about that drift: shuffle the elements back to the start (§20, and it is quadratic), let the window run off the end and reallocate (unbounded memory for a bounded queue), or wrap the window around (§21, and this is the answer). A node-backed queue sidesteps the question entirely, because nodes have no positions to drift through.

Where the shape comes from, and the vocabulary that comes with it

  • Scheduling. Any resource shared by more requests than it can serve at once has a queue in front of it: a CPU run queue, a printer spool, a thread pool's work queue, a socket's accept backlog. FIFO here is a fairness property — no request is starved, because every earlier arrival is served first — which is a guarantee a stack conspicuously does not make.
  • Buffering between producers and consumers. A queue decouples the rate at which things are produced from the rate at which they are consumed, absorbing bursts. That is what a keyboard buffer, an audio ring, a network receive buffer and a message broker's topic partition all are, and the queue's capacity is the size of burst it can absorb before it must either block the producer or drop.
  • Breadth-first exploration. Breadth-first search is depth-first search with the stack replaced by a queue, and the consequence is that vertices are discovered in order of distance from the source — which is what makes BFS a shortest-path algorithm on unweighted graphs. The level-order traversal of a tree is the same algorithm.
  • Simulation. Discrete-event simulation of anything with waiting lines — tills, call centres, packets at a router — is a queue plus a clock, and the classical results about how waiting time blows up as utilisation approaches capacity are results about this structure.

The preconditions, and the bounded case

As with the stack, dequeue and front are partial: undefined on an empty queue, and each implementation must choose between raising, returning a sentinel, or offering a total variant. The bounded case is more consequential here than it is for stacks, because queues are so often used as buffers with a fixed capacity, and a full buffer needs a policy: block the producer until space appears (back-pressure — correct when the producer can be slowed), reject the new element (correct when dropping is better than delaying), or overwrite the oldest (correct for a telemetry ring where recent data matters more than complete data). Those three policies are the whole design space, and choosing between them is usually a more important decision than choosing the data structure.

The obvious array-backed queue keeps the front at index 0: enqueue appends at the end, dequeue takes data[0] and shifts everything down by one. The mistake, named

This is the same error as building a string by repeated concatenation or building a list by repeated tail-append without a tail pointer: a per-operation cost that is proportional to the collection's current size, inside a loop that runs once per element. The sum ∑ k is the signature. Whenever a profile shows a quadratic where the algorithm looks linear, the first thing to look for is an operation whose cost depends on size being called n times — and in a dynamic language it is very often a "remove from the front of a list" call that is documented, in small print, as linear.

Three repairs, in increasing order of cleverness

  • Do not shift; move the front index instead. Keep a front index and leave the departed elements where they are, dead. Now dequeue is O(1) — but the occupied window drifts to the right forever, so the array must keep growing even though the queue's size may stay tiny. A queue holding ten elements that has served a million would occupy a million cells. This is strictly better than the shift and still unacceptable.
  • Shift lazily, in batches. Let the front index drift and compact the array only when the wasted prefix exceeds half the capacity. Each compaction is Θ(n) but pays for at least n/2 dequeues, so the amortized cost per operation is O(1) by the aggregate argument. This works, and it is the same trade as dynamic-array doubling: constant on average, linear in the worst case.
  • Wrap the window around. Let the back index run off the end and reappear at index 0, reusing the space the front has vacated. No element ever moves, no compaction ever happens, the memory is exactly the capacity, and every operation is worst-case O(1) — not amortized. That is the circular buffer, and it is strictly better than the other two whenever the capacity can be fixed or grown by doubling.

And the node-backed queue, which has none of these problems

A singly linked list with both a head and a tail pointer implements a queue directly: enqueue is an insert at the tail (O(1), because tail is held) and dequeue is a delete at the head (O(1), because the head needs no predecessor). Note the happy accident — this is exactly the pairing of operations that a singly linked list does well, which is why the queue, unlike the deque, needs no back-pointers. The costs are the ones §03 priced: one allocation per element, a link per element, and no locality. For a queue whose maximum size is known, the circular buffer wins comfortably; for one that must grow without bound and where worst-case latency matters, the linked queue is the safer choice.

A test that catches this class of bug. Run the structure through n enqueues and n dequeues for n, 2n and 4n, and count the primitive operations rather than timing them. Linear work quadruples when n quadruples; quadratic work goes up sixteenfold. That ratio test is far more reliable than a stopwatch and it does not depend on the machine — it is the doubling-ratio experiment, and it is the cheapest way to find a hidden linear operation.

21 The circular buffer: wrapping the window instead of moving the data

A circular buffer — ring buffer, cyclic queue — is a fixed array plus two indices, in which "the next cell" means (i + 1) mod capacity rather than i + 1. The occupied region is a window that moves forward and wraps around the end of the block, so the space a dequeue frees at the front is reused by a later enqueue at the back. No element is ever moved, no memory is ever reallocated, and every operation is worst-case constant — as long as the capacity is fixed, which §23 is about giving up. It is the usual queue implementation in systems code, and it is the array-side dual of the circular list of §08.

Two of those lines are where implementations actually go wrong. The size formula must add capacity before taking the modulus, because back − front goes negative whenever the window has wrapped and the ring is not completely full — and a test suite that never fills the buffer past the end will never notice. (At completely full it does something worse than go negative: back = front, so the subtraction returns a perfectly plausible 0. And any code that reads the contents as a contiguous slice is wrong once the window wraps: data[front … back] is empty or backwards in that state. A bulk read must be done as two slices, data[front … capacity) followed by data[0 … back), which is exactly how a ring buffer hands a split region to a write system call.

Why the modulus is usually not a modulus

A division instruction is slow, and it is on the hot path of every operation. Two standard replacements: constrain the capacity to a power of two, in which case i mod capacity is the bitwise i & (capacity − 1) and costs one cycle; or replace the modulus with a conditional, i = i + 1; if (i == capacity) i = 0;, which is correct for any capacity because the index only ever advances by one and therefore can only overshoot by one. The power-of-two trick is why so many ring buffer APIs insist on a power-of-two capacity, and the conditional is why the ones that do not are still fast. Both are behaviour-preserving; neither changes anything in this section.

Where you have already used one. A ring buffer is the standard structure for a hardware device's transmit and receive descriptors, for an audio callback's sample buffer, for a lock-free single-producer single-consumer channel (where front is owned by the consumer and back by the producer, so the two never write the same word), for a bounded log or telemetry buffer that overwrites its oldest entries, and for the fixed-size sliding window over a stream. In every one of those, the property being bought is the same: bounded memory, no allocation after start-up, and no element ever moving.

22 The full-versus-empty ambiguity, and the ways out of it

A circular buffer holding only front and back has a genuine ambiguity: front = back means both completely empty and completely full, because the window that has wrapped all the way round ends exactly where it started. This is not a subtlety to be coded around carelessly — it is a real information deficit, and the fix is always the same in form: supply the missing bit. Three standard ways do that, each costing something, and production ring buffers use all three depending on what is scarce; a fourth sidesteps the deficit entirely by never throwing the information away. The three-plus-one is not a theorem, only an enumeration of what is actually used — but the counting argument below, that two mod-capacity indices cannot encode capacity + 1 sizes, is.

Choosing between them

  • Store the size when you want size() to be free and you do not mind one more word of state. It is the easiest to reason about — size is the queue's own count, not something derived — and it is the one to write first. Its cost is that two fields change on every operation, which matters in the concurrent case below.
  • Leave one cell empty when state must be minimal and losing a cell is acceptable. It is the traditional embedded-systems answer and it has the pleasing property that front and back each change on exactly one kind of operation. Its cost is the wasted cell, which is negligible at capacity 4096 and annoying at capacity 4.
  • Store a flag when you need the full capacity and one boolean is cheaper than a word. In practice this is the least used of the three, because the flag has to be updated in both operations and is easy to get wrong at exactly the states nobody tests.
  • Use unbounded counters when the buffer is concurrent. This is the version that matters most in real systems: with a monotonic head written only by the consumer and a monotonic tail written only by the producer, there is no shared mutable field at all, size = tail − head is exact, and a single-producer single-consumer ring becomes lock-free almost by accident. The wrap is confined to the indexing expression data[i mod capacity], and with a power-of-two capacity that is a bitwise and. The one caveat is counter overflow, which at 64 bits is not a practical concern.

What the figure shows when you switch the control

The three options in the §21 figure are three genuinely different implementations, not three labels on one. Switch to leave one cell permanently empty and the same scripted run reports the buffer full one element earlier and rejects one more enqueue, because its usable capacity is 7 rather than 8 — the wasted cell is visible as a rejection. Switch between the other two and the behaviour is identical, which is the point: they are two ways to store the same missing bit. In all three the readout confirms that zero elements were moved over the entire run, and that the contents read out by the modular walk match a reference FIFO at every single step.

A generalisable lesson about state. The ambiguity exists because two variables were being asked to encode more states than they can distinguish. The fix, in all three forms, is to add exactly the missing information — a count, a forbidden state, or a bit. When a data structure has a case that "cannot be distinguished", the right question is never "how do I work around it" but "how many states do I need, and how many does my representation have?" Counting those two numbers usually names the fix immediately.

A bounded ring buffer never grows — that is usually the point of choosing one. Three things the resize changes

  • The worst case stops being constant. A fixed-capacity ring has worst-case O(1) operations, full stop. A growable one has amortized O(1) with Θ(n) spikes, exactly like the array-backed stack of §13, and for exactly the same reason. If the ring was chosen because of the latency guarantee, making it growable throws away the reason it was chosen.
  • The copy is two block moves, not one. In practice the loop above is written as two memcpys — data[front … capacity) then data[0 … back) — because the split window is exactly two contiguous runs. Same result, and substantially faster on a real machine for the reasons §03 gives — two long sequential runs against a loop with a modulus in it — though how much faster is again a per-machine question and not a number to quote. It is the same two-slice decomposition that a bulk read of a wrapped ring needs.
  • Shrinking has the same trap as a dynamic array. If the buffer shrinks when it falls to half full, an alternating fill-and-drain sequence can force a resize on every operation and destroy the amortized bound. The standard fix carries over unchanged: shrink at one quarter full, and shrink to half the capacity, which leaves the new block half full and guarantees Θ(n) operations must pass before the next resize in either direction. That argument is derived in full on the Algorithm Analysis page.

When not to grow at all

A great many queues should be bounded, and treating "the buffer is full" as an error to be designed around rather than a limit to be raised is often the better engineering. An unbounded queue in front of a slow consumer does not fix the slow consumer; it converts a visible rejection into an invisible and unbounded memory growth, and turns a fast failure into a slow one. The three bounded-queue policies from §19 — block the producer, reject the element, overwrite the oldest — are all more honest than growing, and the first of them is the standard mechanism by which back-pressure propagates through a pipeline. Grow when the queue's size is genuinely data-dependent and unbounded; otherwise pick a capacity and a policy.

The linked queue's answer to the same problem. A node-backed queue never resizes, never copies and never rejects, because each element carries its own storage. The costs are the ones this page has priced repeatedly: an allocation per element, a link per element, and no locality. Which is better is a genuine trade — but note that the linked queue's worst case is the allocator, whose own latency is not constant when it has to ask the operating system for more memory. "No copy" is not the same as "predictable".

Three of the four operations are fine: addFirst and removeFirst are head operations, and addLast is a tail insert with a held tail pointer. The fourth, removeLast, needs to write null into the second-to-last node's link, and no amount of extra external pointers reaches it — tail cannot find its own predecessor. The two good implementations, compared

  • Doubly linked with sentinels. All four operations are insertBetween or remove from §07, with no case analysis whatsoever, worst-case O(1) with no resize, and references to elements stay valid forever. Costs: two links plus an allocator header per element, an allocation per insertion, and no locality. This is the right choice when elements are large, when references into the deque must stay valid, or when worst-case latency is the binding constraint.
  • Circular buffer. All four operations are one index step and one write, worst-case O(1) while the capacity holds, no allocation at all after construction, and the elements are contiguous and cache-friendly. Costs: a fixed capacity, or an amortized resize with the split-window subtlety of §23, and references invalidated by every resize. This is the right choice for small elements and a known or bounded size — which is most of the time.
  • The hybrid that most standard libraries actually ship. A deque of fixed-size blocks, indexed by a small array of block pointers: contiguous within a block, so traversal is nearly as fast as an array's; O(1) worst case at both ends, because growth allocates one block; and no element ever moves, so references stay stable even as the deque grows. It is the same block-chain design that §13 suggests for stacks, and it exists precisely because neither pure implementation is acceptable for a general-purpose container.

What deques are for

Beyond being the union of stack and queue, the deque earns its place in two specific patterns. The first is the monotonic deque behind the sliding-window maximum: keep indices in the deque in decreasing order of value, push new elements at the back after popping everything smaller, and pop from the front when an index leaves the window. Each index enters and leaves once, so the whole scan is Θ(n) — it is the monotonic stack argument with both ends in play, and it is the standard solution to a problem that looks like it needs a heap. The second is work stealing: each worker thread pushes and pops its own tasks at one end of its deque while idle threads steal from the other end, so the common case touches only the owner's end and contention is rare by construction. Both patterns need genuinely both ends; neither is expressible with a stack or a queue alone.

Name the operations, not the container. "I need a deque" is usually the conclusion of "I need to add here and remove there". Writing down the four operations a piece of code actually performs, and only then choosing the structure, is the habit that avoids both mistakes: reaching for a heavyweight container when a stack would do, and discovering three months later that the queue you chose cannot remove from the front in constant time.

The same bound by the accounting method, in one sentence

Charge every enqueue three coins: one pays for the push onto the inbox, and two are left on the element to prepay its eventual pop from the inbox and push onto the outbox. Charge every dequeue one coin, which pays for the pop off the outbox. Because an element crosses from inbox to outbox at most once, the two prepaid coins are always there when the transfer happens, and no operation is ever unable to pay. Since the credit on every element is non-negative, the total charged is an upper bound on the total spent — which is the whole of the accounting method, and it gives the same 3m.

Reading the two panels

The top panel is the reason amortized analysis is needed at all: the per-operation cost is emphatically not constant, and on the all enqueues then all dequeues sequence there is a single red spike whose height is the entire queue. The bottom panel is the resolution. The dashed cumulative-amortized line lies above the solid cumulative-actual line at every prefix, and the shaded gap between them is exactly the potential Φ = 2 × |inbox| — not approximately, exactly, and the readout verifies that identity at every one of the operations rather than at the end. That is what a potential function is: prepaid work, banked during the cheap operations, spent by the expensive one. Switch to the strictly alternating sequence and the spikes almost vanish, because the inbox never accumulates; switch to randomised and the spikes reappear at irregular intervals with the same total bound holding throughout.

What it is good for, and what it is not

  • It is the standard answer to "implement a queue using only stacks". Beyond the exercise, it is genuinely useful when the only primitive available is a stack — which happens in functional settings, where a queue is naturally a pair of immutable lists. Be careful with the amortization there, though: the argument above assumes each state of the queue is used once. If old versions of the structure are kept and re-used — which is the whole point of a persistent data structure — an adversary can dequeue repeatedly from the same expensive state and pay for the transfer every time, and the O(1) amortized bound collapses. Restoring it needs lazy evaluation plus memoization (the banker's queue) or an incremental rotation that moves a bounded amount of work per operation (a real-time queue). The plain eager pair-of-lists version is the right thing only when the queue is used single-threadedly, ephemerally, one version at a time.
  • The worst case is still Θ(n). Amortized does not mean the spike is gone; it means the spikes are rare enough to pay for. In a latency-sensitive setting the transfer is a real stall, and the fixes are the same as everywhere else on this page: use a structure with a worst-case bound, or spread the transfer out incrementally (which is exactly what a real-time functional queue does, moving a constant number of elements per operation).
  • The amortized bound is fragile if the pattern changes. The argument depends on elements crossing at most once. A variant that ever pushes elements back from the outbox into the inbox — a tempting way to implement "peek at the back" — destroys the bound completely and makes the structure quadratic.
  • It is a good introduction to the potential method, because the potential has a plain-English meaning — the work owed by the elements still sitting in the inbox — where the dynamic array's Φ = 2·num − size takes more staring at. Both are worked in full on the Algorithm Analysis page.
Amortized is not average-case. Nothing in this section mentions a probability distribution. The bound holds for every sequence of operations, including the worst one an adversary can construct, which is a strictly stronger guarantee than an expected-case bound. The distinction is drawn carefully in Algorithm Analysis, and it is the difference between "usually fast" and "cannot be made slow".

26 Priority queues: named here, built elsewhere

There is a third answer to "which element comes out next?", and it is neither "the newest" nor "the oldest" but "the most important". A priority queue supports insert(v, priority) and extractMin() (or extractMax()), and it is the ADT that completes the trio. It belongs on this page as a comparison and not as a construction, because the structure that implements it well is a heap, which is an array with a tree's shape encoded in its index arithmetic — a different design from anything here.

What a linked list can and cannot do here

Both linked implementations in the table above are genuinely used, and the choice between them is the classic time-trade. An unsorted linked list gives O(1) insertion and pays Θ(n) on every extraction; a sorted one pays Θ(n) on every insertion and extracts in O(1). Over n inserts and n extracts both are Θ(n²), so neither is a good general answer — but if one operation dominates heavily, the matching list is simpler than a heap and often faster at small n. Be precise about decreaseKey, which is the operation a priority queue inside Dijkstra's algorithm leans on, because the two list variants behave oppositely and the folklore answer ("lists are bad at it") is wrong for one of them. On an unsorted list, if the caller holds a handle to the node, lowering its key is a single field write — O(1), better than a binary heap's O(log n), because an unsorted list maintains no order to repair. On a sorted list, the node must be moved to its new place, which is a walk: Θ(n). What neither can do cheaply is extractMin and ordered access together, and what neither can do at all is reach a position in the middle without walking to it. The genuinely useful consequence is that an unsorted array or list gives Dijkstra Θ(V² + E), which beats the binary-heap O((V + E) log V) when the graph is dense enough that E approaches V². That is a real and not-uncommon case, and it is the first of two places on this page where the flat structure wins outright.

Where the sorted list does win

One structure on this page is genuinely the right priority queue in a specific setting: a sorted doubly linked list when priorities arrive in nearly sorted order and elements must be repriorised by splicing. The insertion walk is short when the new element belongs near one end, the splice is O(1), references to elements stay valid, and moving an element to a new priority is a remove-and-reinsert with no reallocation. That is the shape of a simple event queue in a discrete-event simulation where events are scheduled mostly in the near future — and it is why "use a heap" is a default rather than a law.

27 When a linked list is actually the right answer

The honest summary of the last twenty-six sections is that a dynamic array beats a linked list for most general-purpose sequence work, often by a large constant factor, and the cases where the list wins are specific and identifiable. Being able to name them — and to recognise when none of them applies — is more useful than any amount of enthusiasm for either structure.

The five genuine wins

  • You already hold the node, and you splice a lot. This is the row of the §02 table that the "O(1) insertion" headline is really about, and the one no array layout can match at any size. An LRU cache moving an entry to the front of its recency list, a scheduler moving a task between run queues, an allocator moving a block between size classes, an intrusive list threading objects that already exist — all of these hold a pointer to the element and perform O(1) removal and reinsertion with no search and no copy. An array cannot do this at all without a Θ(n) shift.
  • References to elements must stay valid. Every insertion into a dynamic array may reallocate and invalidate every pointer, reference, iterator and index into it. A node's address never changes. When other data structures point at the elements — a hash map from key to node, a second list threading the same objects, a callback holding a handle — this is not a performance argument at all, it is a correctness one.
  • Worst-case latency matters more than throughput. Every list insertion, and every deletion at a node whose predecessor is reachable, is worst-case O(1) with no resize and no copy. (Reaching a position is still Θ(k) and searching still Θ(n) — the guarantee being bought here is about growth and splicing, not about lookup.) The array's append is O(1) amortized with Θ(n) spikes, which is unacceptable in a real-time audio callback, a control loop, or an interrupt handler. The caveat from §23 applies: the list's latency is then the allocator's latency, so real-time list code preallocates its nodes into a free list.
  • Constant-time splitting, joining and reordering of whole sequences. Concatenating two lists is one link write; splitting at a held node is one link write; moving a run of elements from one list to another is a constant number of writes with nothing copied. Arrays pay Θ(n) for each. This is why linked structures appear inside other structures — the child lists of a Fibonacci heap, the free lists of an allocator, the bucket chains of a hash table.
  • The elements are large, or the memory is fragmented. The link overhead is a fixed 8 or 16 bytes, so its relative cost falls as the payload grows — and a linked structure needs no contiguous block at all, so it can allocate when a large contiguous allocation would fail. For big records in a fragmented heap, the array's advantages largely evaporate.

The three arguments that are usually wrong

  • "Insertion is O(1)." Only at a node you already hold. Insertion at an index is Θ(k); insertion before a value is Θ(n). The §02 figure measures both and shows that for a uniformly random position the two structures touch the same n/2 elements on average — with the array's being a tight, prefetched block move.
  • "The array wastes memory on growth." It holds up to 100% slack; the list holds a link plus allocator overhead per element. For small payloads the list is the bigger waster, permanently, as the §03 figure quantifies — and the array's slack can be reclaimed by shrinking or by reserving the right capacity up front, where the list's overhead cannot be reclaimed at all.
  • "It avoids the copy." It avoids one copy and pays an allocation per element. The array's amortized copying is a handful of sequential memmoves over the whole lifetime of the structure; n allocator calls are not obviously cheaper, and they are certainly less predictable.

The decision procedure, compressed

ask these four, in order1. Do I index by position, or binary search, or scan a lot? → array. Stop. 2. Must references to elements survive insertions elsewhere? → linked. Stop. 3. Do I hold nodes and splice, or split and join whole sequences? → linked. Stop. 4. Is a Θ(n) latency spike unacceptable, even rarely? → linked, with preallocated nodes. otherwise→ array. It is the default for a reason, and the burden of proof is on the alternative. and separately, for the restricted ADTsstack, bounded → array or ring; stack, latency-critical → nodes + free list queue, bounded → circular buffer, every time queue, unbounded with hard latency → linked, head + tail deque → circular buffer if small elements, block-chain or doubly linked otherwise
Why the structure is still worth knowing cold. Even if you rarely reach for a bare linked list, you will use the discipline constantly: a tree is nodes with two links, a graph's adjacency list is nodes with many, a hash table's chains are lists, an allocator's free blocks are a list, and the call stack is a list of frames. The pointer discipline of §01 — save before you overwrite, maintain both directions, null the fields of anything you unlink — is the part that transfers, and it transfers everywhere.

28 Pitfalls

Every item here is a bug that compiles, passes a casual test, and fails on a boundary or under load. They are grouped by which structure produces them, and each one names the check that catches it.

Pointer discipline

  • Overwriting a link before saving what it pointed at. cur.next = prev before nxt = cur.next loses the entire rest of the list. Same bug as writing cur.next = new before new.next = cur.next. Check: after any routine that rewrites links, assert the node count is what it should be.
  • Losing the head. A routine that advances head as its working cursor returns a list that starts in the middle, and in a managed runtime the prefix is collected. Check: never use the external reference as the loop variable; copy it into a local cursor first.
  • Forgetting to update the auxiliary fields. A tail pointer left stale by a head-deletion on a one-element list, or a size counter not decremented, produces a structure that is internally inconsistent in a way no single operation reveals. Check: a debug-mode invariant routine that walks the list and re-derives size and tail from scratch, called after every mutation in tests.
  • Breaking the back-pointer symmetry. Updating next and not prev gives a list that is correct forwards and corrupt backwards. Check: walk forward collecting nodes, walk backward from the tail, assert the two sequences are exact reverses.
  • Leaving a deleted node pointing into the list. A stale reference to it walks back into a structure it is no longer part of, and a double removal rewrites its old neighbours' links with garbage. Check: null both fields of every unlinked node, or write a poison value.
  • The copy-the-successor trick at the tail, or with escaped references. §05 in full: it faults on the last node, and it destroys node identity everywhere else. Check: only use it on lists whose nodes never escape, and give the list a trailer sentinel.

Traversal and termination

  • Indexed access inside a loop. for i in 0…n−1: visit(get(i)) is Θ(n²) on a linked list, and it looks exactly like the linear array version. Check: the doubling-ratio experiment — quadruple n and see whether the operation count quadruples or goes up sixteenfold.
  • Calling length() in a loop condition on a structure that computes it by walking. Same quadratic, same test.
  • A while (p ≠ start) loop on a circular list, which terminates immediately because p = start on entry. Check: use do … while, and test the one-element ring.
  • An unbounded search on a circular list, which never returns when the value is absent. Check: bound every circular traversal by the start comparison or by a maintained count.
  • Assuming a list is acyclic. Any traversal over a list with a cycle runs forever. Check: Floyd's algorithm in a debug assertion, or make cycles unrepresentable by building lists only through an API that cannot close one.
  • Off-by-one in the runner setup. Advancing the lead pointer k−1 links instead of k returns the wrong node from the end, silently. Check: test k = 1 (the last node) and k = n (the first), and assert that k > n is an error rather than an answer.

Rings, queues and wraparound

  • back − front without the + capacity. Correct until the window splits, then negative. Check: a test that enqueues past the end of the block before measuring size — a test suite that never wraps will never see this.
  • Reading a wrapped ring as one contiguous slice. data[front … back] is empty or backwards once the window is split. Check: always read as two runs, and test with the front deliberately placed near the end of the block.
  • A negative modulus on the backwards step. (front − 1) mod capacity is −1 in several widely used languages. Check: write (front − 1 + capacity) mod capacity unconditionally, and test addFirst on a buffer whose front is at index 0.
  • Confusing full with empty. §22 in full. Check: test the three boundary states explicitly — empty, exactly one element, and exactly at capacity — and test them after a wraparound, not only from a fresh buffer.
  • A resize that block-copies a split window. Preserves positions rather than order, so the queue silently reorders. Check: fill, drain part way, wrap, then grow, then drain completely and compare with a reference FIFO — which is exactly the cross-check the §21 figure runs on every operation.
  • Shrinking at half full. Destroys the amortized bound under an alternating workload. Check: shrink at a quarter, to a half.

Stacks and recursion

  • Popping an empty stack. The precondition of §12, and the one that returns a null which is then used. Check: make the empty case raise, or return an option type the caller must unwrap.
  • The two pops in the wrong order in a postfix evaluator. The second pop is the left operand; getting it backwards is invisible for + and × and wrong for everything else. Check: test with a non-commutative operator, every time.
  • Assuming recursion is free. Depth × frame size is real memory, and a recursion linear in the input will overflow on a large one. Check: test at a size big enough to matter, not at ten; convert to an explicit stack when the depth is data-dependent.
  • Relying on tail-call elimination that the language does not guarantee. Check: read the language specification, not a blog post; and note that a call with work after it is not a tail call however it is written.
  • Using an unbounded stack or queue as a buffer. Turns a fast, visible rejection into slow, invisible memory growth. Check: bound it and choose a policy — block, reject, or overwrite.
The single highest-value habit. Write an invariant checker for every linked structure you build — walk it, count the nodes, re-derive every auxiliary field, verify the back-pointers mirror the forward ones, verify no node is reachable twice — and call it after every mutation in the test build. It costs an hour and it converts an entire category of silent corruption into a loud, immediate, precisely located failure.
