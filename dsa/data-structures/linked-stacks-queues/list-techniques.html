08 Circular lists

Point the last node's link at the first instead of at null and the list becomes a ring. There is no end, so there is no terminator; there is no first node, only whichever node the external reference currently names; and a traversal must be told when to stop by something other than a null, because it will never find one. That last sentence is the whole design trade: circularity removes one class of boundary and introduces one class of non-termination.

the structure — singly linked, circularcur → n₀ → n₁ → ⋯ → n₍ₙ₋₁₎ → n₀ → ⋯ no null anywhere the traversal, which must count or compare rather than test for nullstart ← cur ; p ← cur repeat: visit(p) ; p ← p.next until p = start the standard external reference is the LAST node, not the first — and this is whygiven tail: first = tail.next so both ends are O(1) from one reference addLast(v): y.next ← tail.next ; tail.next ← y ; tail ← y O(1) addFirst(v): y.next ← tail.next ; tail.next ← y O(1), tail unchanged rotate(): tail ← tail.next O(1) — one assignment an empty ringtail = null the one case that survives; a sentinel node removes it too

What circularity buys

  • Both ends from one reference. A singly linked circular list with a tail pointer reaches the front in one read — tail.next — so it supports addFirst, addLast and removeFirst all in O(1) with a single external pointer, which a null-terminated singly linked list needs two pointers to do. (removeLast is still Θ(n); the predecessor problem does not care that the list is circular.)
  • Rotation for free. "Move the front element to the back" is tail ← tail.next, one assignment, no allocation, no copying, no element moved. That is the operation a round-robin scheduler performs on every quantum, and the reason circular lists are the textbook representation of a cyclic turn order — players in a game, buffers in a pool, processes sharing a CPU.
  • Concatenation in a constant number of writes. Two rings with tails t₁ and t₂ are joined by swapping the two next fields: t₁.next ↔ t₂.next, then the combined tail is t₁ (or t₂, depending on the order wanted). Splicing a ring into another ring at a held node is the same two writes. This is the operation that makes circular lists appear inside other structures — the child lists of a Fibonacci heap are circular doubly linked lists precisely so that merging and cutting are constant-time and case-free.
  • No null tests at all, once the empty case is handled. Combine circularity with a sentinel and you get the cleanest doubly linked list design in common use: a single dummy node whose next is the first element and whose prev is the last, so an empty list is the dummy pointing at itself and every operation — including on the empty list — is the same case-free splice. One extra node, no nulls, no head/tail pointers to keep in sync, and the list header itself can be the dummy, embedded in the owning object rather than allocated.

What it costs

Every traversal must carry its own stopping condition, and getting it wrong is an infinite loop rather than a null dereference — a failure mode that is harder to diagnose because it produces no exception and no stack trace, just a program that stops making progress. The two correct idioms are compare against the starting node (a do … while (p ≠ start), which visits every node exactly once and handles the one-element ring correctly) and count down from a maintained size (which requires the size to be accurate, and fails silently if it is not). The tempting third idiom — a while (p ≠ start) loop written head-first — visits nothing, because p = start on entry. Searching a circular list for a value that is not present must likewise be bounded by the start comparison, or it never returns.

Josephus, as a worked trace of the rotate-and-delete pattern

The classic use of a circular list is a repeated "advance k, delete, continue" loop. Take the ring 1 2 3 4 5 6 7 with k = 3, deleting every third node, starting the count at 1:

Two details in that trace are the ones to check any implementation against. In round 3 the count wraps past the end of the ring — 7, 1, 2 — which the circular structure handles with no arithmetic at all, where an array implementation needs an index modulo a length that is changing as elements are removed. And in round 6, with only two nodes left, the count reads 1, 4, 1 — node 1 is counted twice and is the one eliminated; a correct implementation counts advances, not distinct nodes, and the survivor is 4. (Cross-checked against the closed recurrence J(1) = 0, J(n) = (J(n−1) + k) mod n, which gives J(7) = 3, i.e. the fourth position, 4.) For a singly linked ring the loop must keep the predecessor rather than the victim, for the reason §05 gives; for a doubly linked ring it can keep the victim and splice it out directly.

The ring is the other structure in this page's title. A circular buffer — §22 — is this same idea implemented in a contiguous array, with (i + 1) mod capacity playing the part of the wrap-around link. The two are duals: the linked ring stores the wrap in a pointer, the array ring computes it with a modulo. Everything the linked ring gets free from its structure, the array ring has to pay for in index arithmetic, and everything the array ring gets free from contiguity, the linked ring pays for in cache misses.

09 The runner: two cursors at different speeds

The runner technique is a traversal that carries two cursors instead of one and maintains a fixed relationship between them — a ratio of speeds, or a constant separation — so that the relationship, at the moment the loop ends, is the answer. It exists because a linked list cannot answer "where is the middle?" or "what is the tenth node from the end?" by arithmetic, and the obvious algorithm — walk once to find the length, then walk again to the target — takes two passes. The runner answers both in one pass and O(1) extra space. It is the linked-list counterpart of the two-pointer pattern on arrays, and the difference between them is instructive: on an array the two pointers are indices whose difference is meaningful; on a list they are references whose separation exists only because the loop maintains it.

pattern A — the fast runner: one cursor moves twice as fastslow ← head ; fast ← head while fast ≠ null and fast.next ≠ null: slow ← slow.next ; fast ← fast.next.next invariant maintained at the top of every iterationslow has advanced s links ⇔ fast has advanced 2s links on exit, slow is at the middlen even ⇒ slow at index n/2 (the SECOND of the two middle nodes) n odd ⇒ slow at index (n−1)/2 (the unique middle) pattern B — the offset runner: one cursor starts k links aheadlead ← head ; advance lead k links (fail if it runs off the end — the list is shorter than k) trail ← head ; while lead ≠ null: lead ← lead.next ; trail ← trail.next invariantlead is always exactly k links ahead of trail on exitlead = null ⇒ trail is the k-th node FROM THE END (1-indexed from the last) cost, both patternsΘ(n) link reads, one pass, O(1) extra space — and the list is never traversed twice

Why "the middle" needs its definition pinned down

For odd n the middle is unambiguous. For even n there are two candidates, and which one the loop lands on is decided entirely by the loop condition, which is why implementations of this disagree. With the guard while fast ≠ null and fast.next ≠ null, on n = 6 the cursors go (0,0) → (1,2) → (2,4) → (3,6=null) and the loop exits with slow at index 3 — the second middle. With the guard while fast.next ≠ null and fast.next.next ≠ null the loop exits one step earlier, at index 2 — the first middle. Neither is more correct; they answer different questions. A merge sort that splits a list in half cares which, and the thing that actually bites is not the guard on its own but the pairing of the guard with the side you cut on. Take n = 2, the smallest case that still splits:

n = 2, and the four combinations — only two of them make progresssecond middle (slow at index 1), cut BEFORE slow → [0] | [1] ✓ both halves non-empty second middle (slow at index 1), cut AFTER slow → [0,1] | [ ] ✗ infinite recursion first middle (slow at index 0), cut AFTER slow → [0] | [1] ✓ both halves non-empty first middle (slow at index 0), cut BEFORE slow → [ ] | [0,1] ✗ infinite recursion the rule that falls outguard fast ≠ null and fast.next ≠ null ⇒ second middle ⇒ cut before slow guard fast.next ≠ null and fast.next.next ≠ null ⇒ first middle ⇒ cut after slow and the failure mode, so you recognise itan empty half means the recursive call gets the same list back, unchanged, forever — a stack overflow rather than a wrong answer, which is at least loud

Pin the definition, then write the guard to match it, then write the cut to match the guard, and test n = 1 and n = 2 explicitly. Those two sizes are where every version of this disagrees, and where every version of this is tested last.

What else the pattern solves in one pass

  • Delete the k-th node from the end. Run the offset runner with trail stopping one node earlier, so it ends at the predecessor of the target — the predecessor problem again, solved by shifting the invariant rather than by searching. A header sentinel removes the "the target is the head" case entirely.
  • Split a list in half. Run the fast runner with the first guard, keep the node before slow, cut its link — the ✓ pairing in the table above. This is how a merge sort on a linked list partitions — and it is why merge sort, not quicksort, is the sort for linked lists: merging needs only sequential access and splicing, where quicksort's partition wants random access to swap.
  • Detect a palindrome. Find the middle with the fast runner, reverse the second half in place (§11), compare the halves walking inwards from both ends, then reverse the second half back. Θ(n) time, O(1) extra space, and it is the standard way to do it without copying the list into an array. (The final re-reversal is not optional if the caller may look at the list again — a predicate that leaves its input mangled is a bug however fast it is.)
  • Detect a cycle. The fast runner's entire reason for existing, and the subject of the next section.
The pattern behind the pattern. Both runners work by maintaining a relationship between two cursors that the loop body preserves — a ratio of speeds, or a constant separation — so that when the loop's termination condition fires, the relationship forces the answer. That is a loop invariant used constructively rather than defensively: you are not checking that the invariant holds, you are choosing an invariant whose truth at termination is the result you want.

10 Cycle detection, and the entry-point argument

A linked list with a cycle is one in which some node's link points at a node already on the path from the head — usually by accident, from a splice that closed a loop. Every traversal over such a list runs forever, so detecting the condition matters; and because the naive detection (record every node visited in a set) costs Θ(n) extra space, the constant-space alternative is one of the few genuinely clever small algorithms. It has two phases: the first proves a cycle exists and finds a node in it, the second finds the node where the cycle begins. The second phase's correctness is the part usually stated without proof, so it gets one here.

The shape, and the two parameters that describe it

Any list reachable from a single head has exactly one of two shapes: a straight chain ending in null, or the rho shape — a tail of μ nodes running into a cycle of λ nodes, so named because the picture is the Greek letter ρ. A node's position is then either an index i < μ in the tail, or a cycle offset (i − μ) mod λ. Both μ and λ are unknown to the algorithm; the point of the two phases is that phase one recovers a multiple of λ and phase two recovers μ, without ever computing either directly.

phase 1 — why a meeting is forcedafter i rounds: slow has advanced i links, fast has advanced 2i once BOTH are inside the cycle, their cycle offsets are (i − μ) mod λ and (2i − μ) mod λ they coincide ⇔ 2i − μ ≡ i − μ (mod λ) ⇔ i ≡ 0 (mod λ) so the first meeting is ati = λ · max(1, ceil(μ / λ)) — always ≤ μ + λ, so phase 1 is O(μ + λ) = O(n) the intuitive version of the same factinside the cycle the gap fast − slow grows by exactly 1 link per round, modulo λ, so it takes every value in 0 … λ−1 and must hit 0 — fast cannot step OVER slow phase 2 — the entry point, and why it workslet i be the meeting round, so i ≡ 0 (mod λ) and the meeting node is at cycle offset (i − μ) mod λ restart p at the head; leave q at the meeting node; advance both one link per step after μ steps: p is at the entry, by definition of μ q is at cycle offset (i − μ + μ) mod λ = i mod λ = 0 — also the entry and they cannot have met earlierp is still in the tail for all steps < μ, and q is always in the cycle; a tail node is never a cycle node cost of the whole thingtime O(μ + λ) = O(n) · extra space O(1) — two references, no set, no marking

Floyd's two phases on a rho-shaped list set the tail and cycle lengths; the meeting round and the entry step are predicted and then measured

Step through phase 1 and watch the gap rather than the positions: once both cursors are on the ring, the fast one closes on the slow one by exactly one node per round, so it can never jump over it and a meeting is forced within λ rounds of both entering. Then switch attention to phase 2, where the surprise is that no arithmetic is performed at all — the algorithm never computes μ or λ, it just walks two cursors at the same speed and lets the congruence do the work. Set the tail length to 0 and the entry becomes the head itself, and phase 2 terminates in zero steps; set the cycle length to 2 and watch the meeting round jump to the next multiple of 2 at or above the tail length. Every one of those predictions is checked against the measured run in the readout.

The alternatives, and when each is right

  • A visited set. Walk the list, inserting each node's identity into a hash set and stopping when an insert finds a duplicate. O(n) expected time and Θ(n) space, and the first duplicate is the entry node directly — no second phase needed. Simpler to write and to read; use it unless the space matters.
  • Marking nodes. Set a visited flag in each node. Θ(n) time and O(1) auxiliary space, but it mutates the structure, needs a field the nodes may not have, and is not safe under concurrent readers or on a shared structure. Real cycle collectors do a version of this; general-purpose list code should not.
  • Brent's algorithm. A different constant-space cycle finder: keep one cursor fixed, advance the other, and teleport the fixed one to the moving one whenever the distance reaches the next power of two. It finds λ directly, typically performs fewer link traversals than Floyd's, and is the one to reach for when following a link is expensive. Floyd's stays the canonical exposition because the two-speed invariant is easier to state.
  • Nothing at all. The best answer in most production code is to make cycles impossible by construction — build lists through an API that cannot close a loop — rather than to detect them afterwards.
Where this generalises. Nothing in either phase uses the fact that the structure is a list. The argument applies to any functional graph — any iteration x ← f(x) on a finite set — because such an iteration is exactly a rho shape. That is why the same algorithm detects cycles in a pseudo-random number generator's sequence, finds the repeating part of a decimal expansion, and underlies Pollard's rho method for integer factorisation. The structure this page draws is a special case of the general one.

11 Reversal, iterative and recursive

Reversing a linked list is the canonical exercise for a reason: it cannot be done by moving data, only by rewriting links, and the loop that does it needs exactly three references and no extra memory. It is also the cleanest small demonstration of the difference between an O(1)-space iterative algorithm and an O(n)-space recursive one that looks like it uses no memory at all.

the iterative reversal — three references, one passprev ← null ; cur ← head while cur ≠ null: nxt ← cur.next ← save the rest of the list BEFORE destroying the link to it cur.next ← prev ← the flip: one link write prev ← cur ; cur ← nxt head ← prev loop invariant, at the top of each iterationprev is the head of the already-reversed prefix; cur is the head of the untouched suffix; the two sublists are disjoint and together contain every node exactly once termination and costcur advances one node per iteration ⇒ n iterations; exactly n link writes, 3n + 1 assignments Θ(n) time, O(1) extra space, 0 allocations, 0 payloads copied

Why the save must come first

The line nxt ← cur.next looks like bookkeeping and is the entire algorithm. After cur.next ← prev executes, the only reference in the program to the rest of the list is whatever was saved beforehand; if nothing was, every node after cur is unreachable and gone. This is the same ordering constraint as the insertion in §01 and it has the same general form: when rewriting a link, read everything you still need through it before you overwrite it. Almost every "my list lost half its elements" bug is this rule violated.

Reversal, step by step — and what the recursive version hides the same list, both algorithms; the result is read back and compared with the input reversed

The recursive version, and the space it does not admit to

The recursive formulation is shorter and, to many readers, clearer: reverse everything after the head, then make the old second node point back at the head and cut the head's own link. Its correctness argument is an induction — assume the recursive call returns the head of a correctly reversed suffix, and check that the two writes attach the current node to the end of it — and it performs 2(n−1) link writes rather than n, because each frame writes the flip and then nulls the old link. But the real difference is the one the source code does not mention: it holds a stack frame per node, so the space is Θ(n) rather than O(1), and on a long list it overflows the call stack. Switch the figure to the recursive mode and the column of live frames on the right is the measurement of exactly that. A list of ten million nodes reverses fine iteratively and crashes recursively, in a language without tail-call elimination — and this recursion is not tail-recursive anyway, because work happens after the recursive call returns.

What reversal is actually used for

  • Undoing a head-built list. Building by repeated head insertion is O(1) per element and produces the reverse order; one Θ(n) reversal at the end fixes it. Total Θ(n), no tail pointer needed — strictly better than maintaining a tail, and much better than the Θ(n²) of appending without one.
  • Palindrome and comparison checks in constant space, by reversing one half in place, as §09 describes.
  • Adding numbers stored least-significant-digit-first, and the other digit-list problems where the natural traversal direction is the opposite of the stored one.
  • As the model for every in-place pointer rewrite. Rotating a list by k, swapping adjacent pairs, partitioning around a value, merging two sorted lists — all of them are the same discipline of "save, rewrite, advance", and getting reversal exactly right is the cheapest way to learn it.
Reversal is O(1) in a doubly linked list — sort of. If a doubly linked list is implemented so that "forward" and "backward" are chosen by a flag rather than baked into the field names, reversing it is flipping the flag: one write, O(1). That is a genuine trick and it is also a warning about what "reverse" means — the nodes and links did not change at all, only the interpretation did. A structure's operations are only as cheap as the representation lets them be, and choosing the representation is the design.

12 The positional list ADT: naming a place in the list without counting to it

A positional list is a sequence ADT whose operations take and return positions — opaque, stable handles to individual elements — instead of integer indices. The doubly linked list with sentinels of §07 can insert, remove and step in either direction in O(1) from a node; what it lacks is a safe public way to hold on to a node. Exposing raw nodes leaks the implementation and lets a caller corrupt the links; exposing indices throws the O(1) away, because reaching index i is a Θ(i) walk. The position is the middle path: a small wrapper around a node that the caller can keep, pass back, compare and dereference, but cannot use to reach inside.

the positionp.element() the element stored at this position O(1) p = q true iff p and q refer to the same place O(1) the list — every operation O(1) on a doubly linked list with sentinelsfirst(), last() position of the first / last element, or none if empty before(p), after(p) the neighbouring position, or none at either end is_empty(), len() add_first(e), add_last(e) insert, and RETURN the new element's position add_before(p, e) = insertBetween(p.node.prev, p.node, e) (§07) add_after(p, e) = insertBetween(p.node, p.node.next, e) replace(p, e) store e at p, return the old element — the position is unchanged delete(p) unlink p's node, return its element — p is now INVALID the representationposition = ( container, node ) ← container: which list issued it before/after return "none" instead of a sentinel — H and T are never handed out validation, run at the top of every operation that takes a positionvalidate(p): p.container ≠ this list ⇒ error: position from another list p.node.next = null ⇒ error: position was deleted (see below) otherwise return p.node O(1)

Why a position survives what an index does not

An index is a derived, global quantity: element e's index is the number of elements before it, so it changes whenever anything is inserted or deleted anywhere earlier in the list. A position is a stored, local quantity: it is the identity of e's node, and nothing done to other nodes changes that identity. Take the list [A, B, C] and record both handles for C — index 2, position p. Now add_first(Z). The list is [Z, A, B, C]; index 2 now names B, silently, with no error anywhere, while p.element() is still C and after(p), add_before(p, …) and delete(p) still act on C. Insertions and deletions elsewhere are four and two link writes on other nodes (§06); none of them writes to p's node or to the wrapper. A position is invalidated by exactly one event: the deletion of its own element. That is the same design rule as storing a subtree size rather than a rank in an augmented search tree — keep what is local, derive what is global — met here from the other side.

Stale positions, and how they are caught

Two kinds of bad position reach a list in practice: one issued by a different list, whose use would splice nodes between two structures and corrupt both, and one whose element has already been deleted, whose use would rewrite the neighbours' links from the dead node's stale fields — the double-removal corruption described in §06. The first is caught by storing the issuing container in the position. The second is caught for free by the hygiene step §06 already recommends: delete sets the dead node's prev and next to null, and since no live node between the sentinels ever has a null next, "next is null" is an exact, O(1) test for "deleted". Both checks are constant time, so validation changes no bound, and it turns a silent corruption that surfaces far away into an error at the line that caused it. Two refinements matter in practice:

  • Equality by node, not by wrapper. before and after create a fresh wrapper each call, so two position objects for the same element are different objects. Position equality must compare the nodes they wrap, or after(p) = q is always false.
  • Where memory is reused, identity is not enough. In a language with manual memory management the dead node may be freed and its memory handed to a new node, and a stale handle then points at a live but unrelated element — the null test passes. The standard remedy is a generation count: the handle stores (slot, generation), each slot's counter is incremented when it is freed, and a handle whose generation does not match is stale. It is the same O(1) check, with a counter doing the job the null field did.

Positions, iterators, and the invalidation contract

An iterator is a position plus a direction of travel: it holds a current place and offers "advance", where a position offers before and after as separate list operations. The practical question about either is the same — which modifications invalidate it? — and the positional list gives the strongest answer a sequence can: only removing the element itself. An iterator into a dynamic array gives the weakest: any insertion that reallocates invalidates every iterator, and any insertion or deletion before an iterator shifts what it refers to. Library container documentation states these rules per operation, and they come straight from the representation: node-based containers keep iterators valid across unrelated splices, contiguous ones do not. A third policy is common for iterators that must not observe a structure mid-change: the container keeps a modification counter, the iterator records it at creation, and any mismatch on the next step raises an error — fail-fast iteration, which detects the problem rather than tolerating it.

What positions are for

  • Handles held by another structure. A hash map from key to position gives O(1) lookup and O(1) relocation of the element — the recency list of an LRU cache is exactly this: on access, delete(p) and add_first(e), and store the new position back in the map. The handles that make decreaseKey possible in an array heap (Heaps & Priority Queues, §16) are the same idea for a structure whose elements move.
  • Cursors. A text buffer's cursor, a playlist's "now playing", a scheduler's "next task" — places that must stay attached to their element while the sequence is edited around them.
  • Maintaining access frequencies. Keep a list of items with an access count each, to report the most-used ones. On every access, increment the count and move the item forward past any items with smaller counts. With a position for each item, finding it is O(1) and each step forward is an O(1) splice, so an access costs O(1 + d) for a move of d places, and the top k are always the first k positions. The cheaper heuristic is move-to-front: on access, move the item straight to the front, O(1) always, with no counts at all. Its list is no longer sorted by frequency, so reporting the top k needs a full scan — but its total access cost is provably within a constant factor of the best any reordering strategy could achieve, even one that knew the requests in advance. That guarantee is a result of online algorithm analysis, where move-to-front is the standard first example.
The ADT is the promise, not the list. Nothing in the positional-list interface says "doubly linked"; it says O(1) everything and stable handles, and the doubly linked list with sentinels is simply the representation that keeps that promise. An array could implement the same interface — positions as indices that are updated on every shift — and would break the O(1) bound the moment it did, which is the clearest statement of what the node-based representation is for.
