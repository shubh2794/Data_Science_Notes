20 What a queue is: the FIFO contract

A queue is a collection with two accessible ends: elements are added at one and removed at the other. The element removed is therefore always the one that has been waiting longest — first in, first out. Like the stack, it is deliberately impoverished so that every operation can be constant-time — worst-case constant on a fixed-capacity ring or a linked queue, amortized constant once the storage has to grow; unlike the stack, its two ends are different, and that difference is what makes the implementation interesting rather than obvious.

Why the second boundary changes everything

A stack's occupied region always starts at a fixed place and grows and shrinks at one end. A queue's occupied region has both ends moving forward — enqueues push the back forward, dequeues push the front forward — so over a long run the occupied window marches steadily through the storage, leaving used-and-released space behind it. Every array-backed queue implementation is an answer to the question of what to do about that drift: shuffle the elements back to the start (§21, and it is quadratic), let the window run off the end and reallocate (unbounded memory for a bounded queue), or wrap the window around (§22, and this is the answer). A node-backed queue sidesteps the question entirely, because nodes have no positions to drift through.

Where the shape comes from, and the vocabulary that comes with it

  • Scheduling. Any resource shared by more requests than it can serve at once has a queue in front of it: a CPU run queue, a printer spool, a thread pool's work queue, a socket's accept backlog. FIFO here is a fairness property — no request is starved, because every earlier arrival is served first — which is a guarantee a stack conspicuously does not make.
  • Buffering between producers and consumers. A queue decouples the rate at which things are produced from the rate at which they are consumed, absorbing bursts. That is what a keyboard buffer, an audio ring, a network receive buffer and a message broker's topic partition all are, and the queue's capacity is the size of burst it can absorb before it must either block the producer or drop.
  • Breadth-first exploration. Breadth-first search is depth-first search with the stack replaced by a queue, and the consequence is that vertices are discovered in order of distance from the source — which is what makes BFS a shortest-path algorithm on unweighted graphs. The level-order traversal of a tree is the same algorithm.
  • Simulation. Discrete-event simulation of anything with waiting lines — tills, call centres, packets at a router — is a queue plus a clock, and the classical results about how waiting time blows up as utilisation approaches capacity are results about this structure.

The preconditions, and the bounded case

As with the stack, dequeue and front are partial: undefined on an empty queue, and each implementation must choose between raising, returning a sentinel, or offering a total variant. The bounded case is more consequential here than it is for stacks, because queues are so often used as buffers with a fixed capacity, and a full buffer needs a policy: block the producer until space appears (back-pressure — correct when the producer can be slowed), reject the new element (correct when dropping is better than delaying), or overwrite the oldest (correct for a telemetry ring where recent data matters more than complete data). Those three policies are the whole design space, and choosing between them is usually a more important decision than choosing the data structure.

The same code, one word changed. Take a graph traversal, and replace "stack" with "queue" in one line. Nothing else changes — not the visited set, not the loop, not the neighbour expansion — and the algorithm goes from diving down one path to sweeping outwards in rings. That is worth internalising, because it is the sharpest possible demonstration that the choice of ADT is an algorithmic decision, not an implementation detail.

21 The naive array queue, and why it is quadratic

The obvious array-backed queue keeps the front at index 0: enqueue appends at the end, dequeue takes data[0] and shifts everything down by one. It is four lines, it is correct, and it turns a sequence of n enqueues and n dequeues from Θ(n) work into Θ(n²). It is worth deriving that number rather than just asserting it, because the same mistake — an O(1)-looking operation that is secretly linear — recurs in every structure on this page.

The mistake, named

This is the same error as building a string by repeated concatenation or building a list by repeated tail-append without a tail pointer: a per-operation cost that is proportional to the collection's current size, inside a loop that runs once per element. The sum ∑ k is the signature. Whenever a profile shows a quadratic where the algorithm looks linear, the first thing to look for is an operation whose cost depends on size being called n times — and in a dynamic language it is very often a "remove from the front of a list" call that is documented, in small print, as linear.

Three repairs, in increasing order of cleverness

  • Do not shift; move the front index instead. Keep a front index and leave the departed elements where they are, dead. Now dequeue is O(1) — but the occupied window drifts to the right forever, so the array must keep growing even though the queue's size may stay tiny. A queue holding ten elements that has served a million would occupy a million cells. This is strictly better than the shift and still unacceptable.
  • Shift lazily, in batches. Let the front index drift and compact the array only when the wasted prefix exceeds half the capacity. Each compaction is Θ(n) but pays for at least n/2 dequeues, so the amortized cost per operation is O(1) by the aggregate argument. This works, and it is the same trade as dynamic-array doubling: constant on average, linear in the worst case.
  • Wrap the window around. Let the back index run off the end and reappear at index 0, reusing the space the front has vacated. No element ever moves, no compaction ever happens, the memory is exactly the capacity, and every operation is worst-case O(1) — not amortized. That is the circular buffer, and it is strictly better than the other two whenever the capacity can be fixed or grown by doubling.

And the node-backed queue, which has none of these problems

A singly linked list with both a head and a tail pointer implements a queue directly: enqueue is an insert at the tail (O(1), because tail is held) and dequeue is a delete at the head (O(1), because the head needs no predecessor). Note the happy accident — this is exactly the pairing of operations that a singly linked list does well, which is why the queue, unlike the deque, needs no back-pointers. The costs are the ones §03 priced: one allocation per element, a link per element, and no locality. For a queue whose maximum size is known, the circular buffer wins comfortably; for one that must grow without bound and where worst-case latency matters, the linked queue is the safer choice.

A test that catches this class of bug. Run the structure through n enqueues and n dequeues for n, 2n and 4n, and count the primitive operations rather than timing them. Linear work quadruples when n quadruples; quadratic work goes up sixteenfold. That ratio test is far more reliable than a stopwatch and it does not depend on the machine — it is the doubling-ratio experiment, and it is the cheapest way to find a hidden linear operation.

22 The circular buffer: wrapping the window instead of moving the data

A circular buffer — ring buffer, cyclic queue — is a fixed array plus two indices, in which "the next cell" means (i + 1) mod capacity rather than i + 1. The occupied region is a window that moves forward and wraps around the end of the block, so the space a dequeue frees at the front is reused by a later enqueue at the back. No element is ever moved, no memory is ever reallocated, and every operation is worst-case constant — as long as the capacity is fixed, which §24 is about giving up. It is the usual queue implementation in systems code, and it is the array-side dual of the circular list of §08.

Two of those lines are where implementations actually go wrong. The size formula must add capacity before taking the modulus, because back − front goes negative whenever the window has wrapped and the ring is not completely full — and a test suite that never fills the buffer past the end will never notice. (At completely full it does something worse than go negative: back = front, so the subtraction returns a perfectly plausible 0. That is the ambiguity of §23, and it is why the formula is only safe on a ring that keeps a cell empty or keeps a count.) And any code that reads the contents as a contiguous slice is wrong once the window wraps: data[front … back] is empty or backwards in that state. A bulk read must be done as two slices, data[front … capacity) followed by data[0 … back), which is exactly how a ring buffer hands a split region to a write system call.

Why the modulus is usually not a modulus

A division instruction is slow, and it is on the hot path of every operation. Two standard replacements: constrain the capacity to a power of two, in which case i mod capacity is the bitwise i & (capacity − 1) and costs one cycle; or replace the modulus with a conditional, i = i + 1; if (i == capacity) i = 0;, which is correct for any capacity because the index only ever advances by one and therefore can only overshoot by one. The power-of-two trick is why so many ring buffer APIs insist on a power-of-two capacity, and the conditional is why the ones that do not are still fast. Both are behaviour-preserving; neither changes anything in this section.

Where you have already used one. A ring buffer is the standard structure for a hardware device's transmit and receive descriptors, for an audio callback's sample buffer, for a lock-free single-producer single-consumer channel (where front is owned by the consumer and back by the producer, so the two never write the same word), for a bounded log or telemetry buffer that overwrites its oldest entries, and for the fixed-size sliding window over a stream. In every one of those, the property being bought is the same: bounded memory, no allocation after start-up, and no element ever moving.

23 The full-versus-empty ambiguity, and the ways out of it

A circular buffer holding only front and back has a genuine ambiguity: front = back means both completely empty and completely full, because the window that has wrapped all the way round ends exactly where it started. This is not a subtlety to be coded around carelessly — it is a real information deficit, and the fix is always the same in form: supply the missing bit. Three standard ways do that, each costing something, and production ring buffers use all three depending on what is scarce; a fourth sidesteps the deficit entirely by never throwing the information away. The three-plus-one is not a theorem, only an enumeration of what is actually used — but the counting argument below, that two mod-capacity indices cannot encode capacity + 1 sizes, is.

the ambiguity, stated preciselythe pair (front, back) can take capacity² values, but the queue has capacity + 1 distinct sizes and (front, back) with front = back is reachable both at size 0 and at size = capacity resolution 1 — store the sizestate: front, size back = (front + size) mod capacity empty ⇔ size = 0 full ⇔ size = capacity usable = capacity resolution 2 — never let the buffer fill; keep one cell always emptystate: front, back empty ⇔ front = back full ⇔ (back + 1) mod capacity = front usable = capacity − 1 resolution 3 — store one extra bitstate: front, back, full empty ⇔ front = back and not full full ⇔ front = back and full usable = capacity resolution 4 — refuse to reduce mod capacity at all, and the ambiguity never ariseskeep head and tail as monotonically increasing 64-bit counters, never reduced mod capacity size = tail − head (exact, no ambiguity); the cell is data[head mod capacity]

Choosing between them

  • Store the size when you want size() to be free and you do not mind one more word of state. It is the easiest to reason about — size is the queue's own count, not something derived — and it is the one to write first. Its cost is that two fields change on every operation, which matters in the concurrent case below.
  • Leave one cell empty when state must be minimal and losing a cell is acceptable. It is the traditional embedded-systems answer and it has the pleasing property that front and back each change on exactly one kind of operation. Its cost is the wasted cell, which is negligible at capacity 4096 and annoying at capacity 4.
  • Store a flag when you need the full capacity and one boolean is cheaper than a word. In practice this is the least used of the three, because the flag has to be updated in both operations and is easy to get wrong at exactly the states nobody tests.
  • Use unbounded counters when the buffer is concurrent. This is the version that matters most in real systems: with a monotonic head written only by the consumer and a monotonic tail written only by the producer, there is no shared mutable field at all, size = tail − head is exact, and a single-producer single-consumer ring becomes lock-free almost by accident. The wrap is confined to the indexing expression data[i mod capacity], and with a power-of-two capacity that is a bitwise and. The one caveat is counter overflow, which at 64 bits is not a practical concern.

What the figure shows when you switch the control

The three options in the §22 figure are three genuinely different implementations, not three labels on one. Switch to leave one cell permanently empty and the same scripted run reports the buffer full one element earlier and rejects one more enqueue, because its usable capacity is 7 rather than 8 — the wasted cell is visible as a rejection. Switch between the other two and the behaviour is identical, which is the point: they are two ways to store the same missing bit. In all three the readout confirms that zero elements were moved over the entire run, and that the contents read out by the modular walk match a reference FIFO at every single step.

A generalisable lesson about state. The ambiguity exists because two variables were being asked to encode more states than they can distinguish. The fix, in all three forms, is to add exactly the missing information — a count, a forbidden state, or a bit. When a data structure has a case that "cannot be distinguished", the right question is never "how do I work around it" but "how many states do I need, and how many does my representation have?" Counting those two numbers usually names the fix immediately.

24 Growing a circular buffer, and why the copy is not a memcpy

A bounded ring buffer never grows — that is usually the point of choosing one. But an unbounded queue built on a ring must grow when it fills, and the resize is the one place where a circular buffer is harder than a plain dynamic array, because the window may be split across the end of the block and a straight block copy would scramble the order. The fix is three lines, and getting it wrong produces a queue that is correct until the first time it both wraps and resizes, which may be a long way into production.

Three things the resize changes

  • The worst case stops being constant. A fixed-capacity ring has worst-case O(1) operations, full stop. A growable one has amortized O(1) with Θ(n) spikes, exactly like the array-backed stack of §14, and for exactly the same reason. If the ring was chosen because of the latency guarantee, making it growable throws away the reason it was chosen.
  • The copy is two block moves, not one. In practice the loop above is written as two memcpys — data[front … capacity) then data[0 … back) — because the split window is exactly two contiguous runs. Same result, and substantially faster on a real machine for the reasons §03 gives — two long sequential runs against a loop with a modulus in it — though how much faster is again a per-machine question and not a number to quote. It is the same two-slice decomposition that a bulk read of a wrapped ring needs.
  • Shrinking has the same trap as a dynamic array. If the buffer shrinks when it falls to half full, an alternating fill-and-drain sequence can force a resize on every operation and destroy the amortized bound. The standard fix carries over unchanged: shrink at one quarter full, and shrink to half the capacity, which leaves the new block half full and guarantees Θ(n) operations must pass before the next resize in either direction. That argument is derived in full on the Algorithm Analysis page.

When not to grow at all

A great many queues should be bounded, and treating "the buffer is full" as an error to be designed around rather than a limit to be raised is often the better engineering. An unbounded queue in front of a slow consumer does not fix the slow consumer; it converts a visible rejection into an invisible and unbounded memory growth, and turns a fast failure into a slow one. The three bounded-queue policies from §20 — block the producer, reject the element, overwrite the oldest — are all more honest than growing, and the first of them is the standard mechanism by which back-pressure propagates through a pipeline. Grow when the queue's size is genuinely data-dependent and unbounded; otherwise pick a capacity and a policy.

The linked queue's answer to the same problem. A node-backed queue never resizes, never copies and never rejects, because each element carries its own storage. The costs are the ones this page has priced repeatedly: an allocation per element, a link per element, and no locality. Which is better is a genuine trade — but note that the linked queue's worst case is the allocator, whose own latency is not constant when it has to ask the operating system for more memory. "No copy" is not the same as "predictable".

25 Deques: both ends, and the structures that can do it

A deque — double-ended queue, pronounced "deck" — allows insertion and removal at both ends, and nothing in the middle. It generalises both previous ADTs: use one end only and it is a stack; add at one end and remove at the other and it is a queue. The interesting part is which implementations can support all four operations in O(1), because two of the structures on this page cannot.

Why a singly linked list cannot be a deque, restated

Three of the four operations are fine: addFirst and removeFirst are head operations, and addLast is a tail insert with a held tail pointer. The fourth, removeLast, needs to write null into the second-to-last node's link, and no amount of extra external pointers reaches it — tail cannot find its own predecessor. This is the same wall as §05 and §04, and it is why the deque is the operation set that forces the second link. A deque is exactly the ADT that distinguishes a singly from a doubly linked list.

The two good implementations, compared

  • Doubly linked with sentinels. All four operations are insertBetween or remove from §07, with no case analysis whatsoever, worst-case O(1) with no resize, and references to elements stay valid forever. Costs: two links plus an allocator header per element, an allocation per insertion, and no locality. This is the right choice when elements are large, when references into the deque must stay valid, or when worst-case latency is the binding constraint.
  • Circular buffer. All four operations are one index step and one write, worst-case O(1) while the capacity holds, no allocation at all after construction, and the elements are contiguous and cache-friendly. Costs: a fixed capacity, or an amortized resize with the split-window subtlety of §24, and references invalidated by every resize. This is the right choice for small elements and a known or bounded size — which is most of the time.
  • The hybrid that most standard libraries actually ship. A deque of fixed-size blocks, indexed by a small array of block pointers: contiguous within a block, so traversal is nearly as fast as an array's; O(1) worst case at both ends, because growth allocates one block; and no element ever moves, so references stay stable even as the deque grows. It is the same block-chain design that §14 suggests for stacks, and it exists precisely because neither pure implementation is acceptable for a general-purpose container.

What deques are for

Beyond being the union of stack and queue, the deque earns its place in two specific patterns. The first is the monotonic deque behind the sliding-window maximum: keep indices in the deque in decreasing order of value, push new elements at the back after popping everything smaller, and pop from the front when an index leaves the window. Each index enters and leaves once, so the whole scan is Θ(n) — it is the monotonic stack argument with both ends in play, and it is the standard solution to a problem that looks like it needs a heap. The second is work stealing: each worker thread pushes and pops its own tasks at one end of its deque while idle threads steal from the other end, so the common case touches only the owner's end and contention is rare by construction. Both patterns need genuinely both ends; neither is expressible with a stack or a queue alone.

Name the operations, not the container. "I need a deque" is usually the conclusion of "I need to add here and remove there". Writing down the four operations a piece of code actually performs, and only then choosing the structure, is the habit that avoids both mistakes: reaching for a heavyweight container when a stack would do, and discovering three months later that the queue you chose cannot remove from the front in constant time.

26 A queue from two stacks, and the amortization proved

Two stacks make a queue. Enqueue by pushing onto an inbox; dequeue by popping from an outbox, and whenever the outbox is empty, first pour the entire inbox into it — which reverses the order, turning LIFO into FIFO. A single dequeue can therefore cost Θ(n), and yet every sequence of operations averages O(1) per operation. That combination — expensive individual steps, cheap totals — is the definition of an amortized bound, and this is the cleanest small example of one that is not the dynamic array.

The same bound by the accounting method, in one sentence

Charge every enqueue three coins: one pays for the push onto the inbox, and two are left on the element to prepay its eventual pop from the inbox and push onto the outbox. Charge every dequeue one coin, which pays for the pop off the outbox. Because an element crosses from inbox to outbox at most once, the two prepaid coins are always there when the transfer happens, and no operation is ever unable to pay. Since the credit on every element is non-negative, the total charged is an upper bound on the total spent — which is the whole of the accounting method, and it gives the same 3m.

Reading the two panels

The top panel is the reason amortized analysis is needed at all: the per-operation cost is emphatically not constant, and on the all enqueues then all dequeues sequence there is a single red spike whose height is the entire queue. The bottom panel is the resolution. The dashed cumulative-amortized line lies above the solid cumulative-actual line at every prefix, and the shaded gap between them is exactly the potential Φ = 2 × |inbox| — not approximately, exactly, and the readout verifies that identity at every one of the operations rather than at the end. That is what a potential function is: prepaid work, banked during the cheap operations, spent by the expensive one. Switch to the strictly alternating sequence and the spikes almost vanish, because the inbox never accumulates; switch to randomised and the spikes reappear at irregular intervals with the same total bound holding throughout.

What it is good for, and what it is not

  • It is the standard answer to "implement a queue using only stacks". Beyond the exercise, it is genuinely useful when the only primitive available is a stack — which happens in functional settings, where a queue is naturally a pair of immutable lists. Be careful with the amortization there, though: the argument above assumes each state of the queue is used once. If old versions of the structure are kept and re-used — which is the whole point of a persistent data structure — an adversary can dequeue repeatedly from the same expensive state and pay for the transfer every time, and the O(1) amortized bound collapses. Restoring it needs lazy evaluation plus memoization (the banker's queue) or an incremental rotation that moves a bounded amount of work per operation (a real-time queue). The plain eager pair-of-lists version is the right thing only when the queue is used single-threadedly, ephemerally, one version at a time.
  • The worst case is still Θ(n). Amortized does not mean the spike is gone; it means the spikes are rare enough to pay for. In a latency-sensitive setting the transfer is a real stall, and the fixes are the same as everywhere else on this page: use a structure with a worst-case bound, or spread the transfer out incrementally (which is exactly what a real-time functional queue does, moving a constant number of elements per operation).
  • The amortized bound is fragile if the pattern changes. The argument depends on elements crossing at most once. A variant that ever pushes elements back from the outbox into the inbox — a tempting way to implement "peek at the back" — destroys the bound completely and makes the structure quadratic.
  • It is a good introduction to the potential method, because the potential has a plain-English meaning — the work owed by the elements still sitting in the inbox — where the dynamic array's Φ = 2·num − size takes more staring at. Both are worked in full on the Algorithm Analysis page.
Amortized is not average-case. Nothing in this section mentions a probability distribution. The bound holds for every sequence of operations, including the worst one an adversary can construct, which is a strictly stronger guarantee than an expected-case bound. The distinction is drawn carefully in Algorithm Analysis, and it is the difference between "usually fast" and "cannot be made slow".
