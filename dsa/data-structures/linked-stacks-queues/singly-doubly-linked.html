02 The cost contract, against the contiguous one

A data structure is a set of promises with a price list attached. Put the linked price list beside the contiguous one and every entry is either inverted or unchanged — there is no operation where linking wins on both access and locality, and no operation where contiguity wins on both splice cost and growth. Reading the table properly means reading the qualifier on each row, because the two structures' headline bounds are frequently quoted without the condition that makes them true.

The rows that get misquoted

  • "Linked lists have O(1) insertion." Only the insert after a held node row is true unconditionally, and read it carefully: it says at a node you already hold. If the caller supplies an index, the list must walk to it and the operation is Θ(k). If the caller supplies a value to insert before, the list must search and it is Θ(n). The O(1) is real but it is a claim about what you are holding, not about the operation.
  • "…and O(1) deletion, for the same reason." It does not follow, and the table now says so on its own row. Inserting after a held node touches only that node's link field, which you have; deleting a held node touches the link field of its predecessor, which a singly linked node cannot name. So deletion at a held node is Θ(k) on a singly linked list and O(1) only once a back-pointer exists. The two operations are constantly quoted as a pair and only one of them is free — which is the whole subject of §05.
  • "Deleting at the back is symmetric with deleting at the front." It is not, for a singly linked list, and a tail pointer does not fix it. Removing the last node requires writing null into the second-to-last node's link field, and the tail pointer cannot reach its own predecessor. So pop_back is Θ(n) on a singly linked list with a tail pointer and O(1) only once the list is doubly linked (§06). This asymmetry is why a singly linked list makes a fine stack and a poor deque.
  • "Arrays are O(n) to insert, so lists are faster for insert-heavy work." Compare the whole operation. Inserting at a random position costs the array a mean of n/2 element moves — a tight, prefetched, vectorisable memmove — and costs the list a mean of n/2 pointer chases, each a potential cache miss, plus an allocation. Same asymptotics, and the constant factor usually favours the array — by how much is a question about a particular machine, which §03 answers only as a memory-traffic ratio and explicitly declines to turn into a wall-clock number.
  • "Binary search on a sorted linked list is Θ(log n)." It is not, because computing a midpoint requires random access. Halving the index range still costs a walk to reach each midpoint, and the total is Θ(n) — worse in practice than a plain scan, because it walks the same prefix repeatedly. A sorted list gives you early termination on a failed search and nothing else; the Θ(log n) lookup on a linked structure has to be bought with extra links, which is what a balanced tree and a skip list both do.

The two rows the list wins, and what they are worth

The genuine wins are splice at a held node and structural rearrangement. Concatenating two lists is one link write if you kept a tail pointer, against copying n₁ + n₂ elements for arrays. Splitting a list at a held node is one link write, against a copy. Moving an element from one list to another — a scheduler moving a task between run queues, an LRU cache moving an entry to the front of its recency list — is a constant number of writes with no element ever copied and, crucially, no reference to the element invalidated. That last property is the one that most often decides the question in real code: pointers, iterators and references into a linked list stay valid across insertions and deletions elsewhere in the list, where every one of them into a dynamic array is invalidated the moment the array reallocates. The standard name for the failure is iterator invalidation, and it is worth knowing as a phrase because library documentation states its rules in exactly those terms — which operations invalidate which iterators is part of a container's published contract, not an implementation detail. When a design needs stable identity for its elements, the list is not winning on complexity at all — it is winning on a guarantee the array cannot make.

Reading a bound as a pair, not a number

Some entries in the table are written O(·) and others Θ(·), and the difference is not decoration. O(1) for the front insert is an upper bound that also happens to be tight, but writing it as O signals that the operation never does more than a constant amount of work — it is a guarantee. Θ(k) for reaching position k is a tight two-sided bound: the walk does at least k link reads and at most k, always, with no best case to hope for. And the array's amortized O(1) append is a third kind of claim entirely — a bound on a sequence, derived in Algorithm Analysis, where any single append may cost Θ(n). The list's growth needs no amortization argument at all: every insert is worst-case constant, which is why linked allocation appears in real-time systems where a doubling copy's latency spike is unacceptable even though its average is excellent.

Cost at every position: the shift against the walk both series are measured by running the real routines once per position — not plotted from a formula

The two bar series are mirror images, and their sum is constant — exactly n for the insert, since the array touches n − k and the list k: the array's cost falls as k rises and the list's rises with it, crossing at k = n/2 — or, when n is odd and there is no such index, at the first integer above it, which is where the violet marker actually sits. That is the whole cost contract in one picture. The mean readout is the sentence to take away — for insertion at a uniformly random position both structures touch about n/2 elements, so on average they are the same asymptotic class and the decision has to be made on the constant factor, on the access pattern of the surrounding code, or on the reference-stability guarantee of the previous subsection. Switch the control to read element k and the symmetry vanishes: the array bar is flat at zero touched elements for every k, because the address was computed rather than found. There is no crossover on that setting, at any n, ever.

Model discipline, carried over. Every bound in the table is a RAM-model bound, where any one memory access costs the same as any other. Every claim on this page that one structure is faster in practice than another with the same bound is a claim about the next section, which counts memory transactions rather than steps. Keep the two ledgers separate; mixing them is how people end up defending a chain of nodes that is asymptotically equal and four times slower.

03 The cache reality that asymptotics hide

Traversing an array of n elements and traversing a chain of n nodes are both Θ(n). They are commonly reported as being a factor of a few apart in wall-clock time; that figure is quoted often enough to count as folklore, and this section will deliberately not endorse it as a number. What it will do is locate the gap, which is not in the step count at all — it is in how many times the processor has to go and fetch a block of memory. This section prices that, under a model stated explicitly enough to be argued with.

The model, and why it has to be written down

The RAM model charges O(1) for any memory access, wherever the address points. That is the right abstraction for deriving a bound and the wrong one for predicting a runtime, because real memory moves in lines: an aligned block, typically 64 bytes, is the smallest unit transferred between DRAM and the processor. Touching one byte fetches the whole line containing it, and a small pool of recently used lines is kept in cache. So the quantity that predicts a traversal's speed is not "how many elements did you read" but how many distinct lines did you have to fetch, and how many did you have to fetch twice because they had been evicted in between. The figure below simulates exactly that, with the model printed in the panel: 64-byte lines, a fully associative cache of 64 lines holding 4 KB, least-recently-used eviction, cold start. Those are simplifications of a real hierarchy (which is multi-level and set-associative, and which prefetches), and they are deliberately conservative — a real machine's set associativity and limited prefetch make the scattered case worse, not better.

what a packed traversal costs, exactlyline fetches = ceil(n × bytes-per-element / linesize) the two layouts, 8-byte payload, 8-byte link, 16-byte allocator grain, 64-byte linearray element = 8 bytes ⇒ 8 elements per line list node = 8 + 8 = 16 bytes ⇒ 4 nodes per line, even when perfectly packed so, before a single node is misplacedratio of line fetches = nodesize / itemsize = 16 / 8 = 2× and once the chain outgrows the cache and the visit order is scatteredeach node can cost its own fetch ⇒ up to n fetches against ceil(n × itemsize / linesize)

Two separate penalties, often confused

  • The size penalty is unconditional. Every node carries a link the array does not, and every allocation is rounded up to the allocator's grain and carries the allocator's own bookkeeping. With an 8-byte payload the node is at least twice the size of the array element, so even a perfectly laid out chain fetches twice as many lines. With a 4-byte payload it is four times. With a 32-byte record it is 1.5 times, and with a 64-byte one 1.25 times under the same 16-byte allocation grain — still a quarter more memory traffic, so call it small rather than gone. The smaller the payload, the worse linking looks, and that is the single most useful rule of thumb in this section.
  • The scatter penalty is conditional — and it is worth being exact about the condition. The figure models scatter the conservative way: the n nodes occupy one compact run of n × nodesize bytes and only the visit order is shuffled. Under that model, if the whole run fits in cache the visit order does not matter at all — every line is fetched once whatever the order, and a shuffled chain costs exactly what a packed one costs — and the penalty appears only once the footprint exceeds the cache, at which point a shuffled order starts re-fetching lines it has already evicted. The figure marks that threshold. This is why microbenchmarks of linked lists on small inputs are so often reported as "no slower than an array": at small n, for a chain whose nodes happen to be packed together, that is correct. It is not the general case. A chain whose nodes were allocated over a program's lifetime can be spread across the heap one node per line, and then n nodes cost up to n fetches at every n — with no threshold and no small-n reprieve. Which regime you are in is a fact about the allocator and the list's history, not about the data structure, which is precisely why the figure reports the floor rather than a number to quote.
  • The prefetcher is the third, unmodelled penalty. A constant-stride scan is recognised by hardware, which begins fetching the next line before it is requested and hides the latency of the fetch entirely. A pointer chase cannot be prefetched by stride, because the next address is not known until the current node has arrived — the dependency is serial. The model below does not simulate this at all, so its ratios understate the real gap; treat them as a floor.

At the default settings — 8-byte payloads, n = 448 — the simulation returns 56 line fetches for the packed array, 112 for a chain of nodes laid out in visit order, and 270 for the same nodes visited in scattered order. The middle number is exactly twice the first, because the node is exactly twice the size of the element; it is a size effect and no amount of careful allocation removes it. The third is the scatter effect, and under this model it only exists to the right of the orange marker at n = 256, which is where 16-byte nodes stop fitting into a 4 KB cache — 256 × 16 = 4096 bytes, exactly 64 lines, so n = 256 is the last value that still fits. Drag n to or below that marker and the red curve lies exactly on the teal one — shuffling the visit order costs nothing while everything is resident. That is the caveat this section exists to make precise: the locality argument against linked lists is real, it is large, and as measured here it is conditional on the working set — with the second condition from the bullet above still attached, that the nodes are packed rather than strewn across the heap.

What this does and does not license you to say

  • Licensed: "these two traversals are in the same complexity class and the array's is cheaper in memory traffic by a factor of at least nodesize / itemsize — a factor of two at an 8-byte payload, four at a 4-byte one, and 1.25 at a 64-byte one." That is a statement about a stated model, reproducible from the figure.
  • Licensed: "the gap shrinks as the payload grows." Set the payload control to 32 bytes and watch the ordered-node ratio fall from 2.00× to 1.50×; at a 64-byte payload it is 1.25×. Small, then — but say "small", not "gone".
  • Not licensed: any specific wall-clock multiplier on any specific machine. That depends on the cache sizes, the associativity, the prefetcher, the allocator's placement policy, whether the list was built in one burst or accumulated over a program's lifetime, and what else is competing for cache. The only way to get such a number is to measure it on the machine in question, and the measurement will not transfer to a different one.
  • Not licensed: "therefore never use a linked list." The structures in §28 are chosen for guarantees the array cannot make — stable references, worst-case constant growth, O(1) splice between containers — and those reasons survive this section intact.
Carried over, not repeated. 04 Singly linked lists: the traversal loop and the four boundary cases

A singly linked list is the minimal linked structure: one node type with one link field, one external reference head, and null as the terminator. Everything else — tail pointers, counts, sentinels, back-pointers — is an optimisation layered on this, and each one is worth stating as what it buys and what it costs to maintain. Start with the loop that every list operation is a variation of.

the traversal — the shape of every singly linked algorithmcur ← head while cur ≠ null: visit(cur.data) cur ← cur.next loop invariantat the top of each iteration, every node strictly before cur has been visited exactly once, and cur is either null or the first unvisited node terminationeach iteration advances cur one link along a finite acyclic chain ⇒ cur reaches null in n iterations costn link reads, n visits, 1 null test per iteration plus the final one ⇒ Θ(n) time, O(1) extra space

Why the loop is written with the cursor and not an index

The natural-looking alternative — for i in 0 … n−1: visit(get(i)) — is a trap that costs a factor of n. Each get(i) restarts at the head and walks i links, so the total is 0 + 1 + 2 + ⋯ + (n−1) = n(n−1)/2 = Θ(n²) link reads to do what the cursor loop does in n. This is the same quadratic that repeated string concatenation produces, arising for the same reason: an operation that looks constant in the notation is linear in the structure. If a list type offers indexed access at all, treat every call as a fresh traversal, and never put one inside a loop over the same list.

The four positions, priced

  • Insert at the head — new.next = head; head = new. Two writes, no traversal, worst-case O(1). This is the operation the structure is for, and it is the reason a singly linked list is the natural node-backed stack.
  • Delete at the head — head = head.next. One write, no traversal, O(1). Must first check head ≠ null, which is boundary case number one.
  • Insert at the tail — Θ(n) with only a head pointer, because the last node must be found; O(1) if a tail reference is maintained. Maintaining it is three lines and two extra assignments per operation, and getting one of them wrong is boundary case number two: every insertion into an empty list must set tail as well as head — and that is true of the head-insert too, which otherwise never touches tail at all. It is exactly because the head-insert normally leaves tail alone that the empty case is the one people forget.
  • Delete at the tail — Θ(n), and a tail pointer does not help. The operation needs to write null into the second-to-last node's link field, and from tail there is no route backwards. You must walk from the head to find the predecessor. This single asymmetry is the strongest practical argument for the doubly linked list, and the reason a singly linked list makes a fine stack and a bad deque. Boundary case number three: deleting the last remaining node must reset tail to null as well as head.

Take the six-node list head → 31 → 7 → 19 → 4 → 23 → 12 → null and run the cursor loop, writing down the state at the top of each iteration:

That n + 1 is not pedantry: it is the extra test that a trailer sentinel converts from a branch into a comparison against a known node, and it is exactly the fencepost structure that half-open ranges formalise on the array side. Note also that the invariant above is what makes the loop obviously correct: each iteration visits one node and advances past it, the set of visited nodes grows by exactly one, and the loop cannot revisit a node because the chain is acyclic. Drop that assumption and the loop does not terminate — which is the entire subject of §10.

Building a list, and the order that surprises people

Repeatedly inserting at the head builds the list in reverse of the insertion order, in Θ(n) total. Repeatedly inserting at the tail preserves the order, in Θ(n) total if a tail pointer is kept and Θ(n²) if it is not — the classic accidental quadratic in list-building code, and the reason so many list routines build reversed and then reverse once at the end (§11), which is Θ(n) and needs no tail pointer at all. The same trick appears in recursive list code: build the result backwards on the way down, reverse once on the way out.

Maintenance cost is part of the price. Every auxiliary field — tail, a node count, a "last accessed" cursor — must be updated on every operation that could invalidate it, including the ones written months later by someone else. A list with three auxiliary fields has three invariants, and each one has an empty-list case and a one-element case. Most linked-list bugs in production code are a missed update to an auxiliary field, not a mistake in the splice.

05 The predecessor problem, and the trick that dodges it

The predecessor problem is the standing consequence of a one-way link: given a node, a singly linked list offers no way to find the node that points at it, short of searching for it from the head. Almost every awkward thing about singly linked lists is a restatement of that one sentence, and the sharpest version of it is a question. "Delete this node in O(1)" is one of the most-asked questions about linked lists, and the honest answer is that on a singly linked list it is impossible as stated — and that there is a trick which produces something almost as good, with a defect at exactly one position and a second defect that has nothing to do with position at all. Both are worth understanding precisely, because the trick is correct and useful in some designs and silently wrong in others.

Why the predecessor is needed

Removing a node from a chain means making the chain skip it, and "the chain" is a set of link fields living inside other nodes. The only field that has to change is the one in the node immediately before the target. A singly linked node holds no reference to whoever points at it — the link relation is one-way — so from the target alone that field is unreachable. The only way to find it is to start at head and walk until prev.next === target, which is Θ(k) for a target at position k and Θ(n) in the worst case. This is why the cost table in §02 splits insertion and deletion at a held node onto two rows rather than quoting them as a pair: O(1) deletion at a held node is a claim about a doubly linked list, or about a caller who happens to be holding the predecessor rather than the target, and it is false of a bare singly linked one.

the constraint, stated as a reachability factfrom a node x in a singly linked list, the reachable set is { x, x.next, x.next.next, … } the predecessor of x is NOT in that set (unless the list is circular — §08) thereforeremove(x) given only x requires a search from head Θ(position of x) unless you change what "remove" meansremove the VALUE at x, rather than the NODE x — which the successor trick does

The copy-the-successor trick

Given only a reference to node x, and provided x.next ≠ null: copy the successor's payload into x, then unlink the successor. Two writes, one payload copy, no traversal at any position. The list's sequence of values afterwards is exactly what deleting x would have produced, so from the outside — from anyone who only ever reads the list by traversing it — the operation is indistinguishable from a real deletion in O(1).

Three ways to remove a node you hold a reference to the third mode runs the trick where it does not work, and reports the fault

The two defects, in order of how often they bite

  • It cannot be applied to the tail. The trick works by sacrificing the successor, and the last node has none. Run the third mode of the figure and the routine faults on x.next.data. There is no patch inside the trick: any fix is structural — walk from the head after all (giving up the O(1) exactly where it was most wanted), keep a back-pointer (§06), or give the list a trailer sentinel so that no node holding real data is ever last. The third option is the cheapest, and it is one of the strongest arguments for sentinels.
  • It deletes the wrong object. The values are right; the identities are not. The node that survives is the one that held the deleted value, and the node that dies is the one that held the surviving value. Any reference held outside the list — an iterator, a cached pointer, an index in a hash map from key to node, another container's link to the same node — now points at a node that has been unlinked, or at a node whose payload has silently changed underneath it. Both are failures of aliasing discipline — two names for what the program believed was one object, which have quietly come to name different things — and the outside reference to the unlinked successor is a dangling one. In a language with manual memory management this is a use-after-free waiting to happen; in a managed one it is a quieter bug where an object that should have disappeared stays alive and an object that should have survived does not. The trick is safe exactly when no reference to any node escapes the list.

The cost, measured

The figure counts all three methods on the same six-node list. The walk to the predecessor of position k costs k − 1 cursor advances plus one link write; at k = 3 that is two advances. The trick costs zero advances, one payload copy and one link write at every interior position — it is genuinely constant, and the readout says so by measurement rather than assertion. And at the tail it costs one fault. Whether the difference between Θ(k) and O(1) is worth the identity hazard is a design question with a clear decision rule: if the nodes are private to the list, take the trick; if anything outside the list knows about a node, do not.

The general lesson, which recurs. When a structure cannot answer a question, you have three moves: search for the answer (pay time), store the answer (pay space, and pay to maintain it — this is the back-pointer), or change the question (this is the trick, and it works only if the weaker guarantee is genuinely enough). The whole of §07 is the second move applied to boundary conditions, and every index in a hash table or tree is the second move applied to lookup.

06 Doubly linked lists: what the back-pointer buys

A doubly linked list is a linked list whose nodes carry two links: one to the successor and one to the predecessor. Add that second field and the structure changes character. Every node now knows both of its neighbours, so every local operation becomes local: removal, insertion on either side, and traversal in either direction, all from a node reference alone, all in O(1), with no walk and no trick. The price is one extra word per node and one extra invariant to maintain on every single link write.

the node, and the invariant that defines the structurenode = ( payload , prev , next ) the symmetry invariant — must hold for every node at every quiescent momentx.next ≠ null ⇒ x.next.prev = x x.prev ≠ null ⇒ x.prev.next = x splice out x — two fields read, two written, no searchx.prev.next ← x.next x.next.prev ← x.prev (each guarded by a null test, unless sentinels — §07) splice in y between p and q (where q = p.next)y.prev ← p ; y.next ← q ; p.next ← y ; q.prev ← y four writes, O(1) space, payload p bytes, w-byte wordssingly: n × (p + w) doubly: n × (p + 2w) ⇒ +w bytes per element, forever

The four capabilities the second link buys

  • Removal from a held node, genuinely O(1), with correct identity. This is the row of the §02 table that the singly linked list could only fake. The node that dies is the node you asked to remove — so outside references behave as they should, and the copy-the-successor hazard disappears entirely. This capability, rather than the backwards traversal, is the usual reason a general-purpose list type in a library is doubly linked.
  • Insertion before a held node. Symmetric with insertion after, and the reason list APIs can offer insert_before(pos, v) without a linear search.
  • Backward traversal and a genuine O(1) pop_back. With a tail pointer, tail.prev is the new tail in one read. The asymmetry that made a singly linked list a bad deque is gone, and the doubly linked list becomes the natural node-backed deque.
  • A bidirectional iterator with a well-defined "one before". Iterators over a singly linked list can only advance; over a doubly linked list they can also retreat, which is what lets an algorithm back up one position without re-walking from the head.

What it costs, stated precisely

  • One extra word per node, unconditionally. With an 8-byte payload on a 64-bit machine, a singly linked node needs 16 bytes and a doubly linked one 24 — so by the argument of §03 a doubly linked traversal fetches 1.5× the lines of a singly linked one, and 3× the lines of a packed array of the same payloads. Doubling the links doubles neither the bound nor the constant, but it does move it in the wrong direction.
  • Two invariants instead of one, on every write. Every link change must be mirrored. A routine that updates next and forgets prev produces a list that traverses correctly forwards and is corrupt backwards — a bug that hides until something iterates in reverse, which may be months later and in different code. This is the single most valuable thing a debug-mode consistency check can assert: walk forward collecting nodes, walk backward from the tail, and require the two sequences to be exact reverses.
  • More boundary cases, not fewer. Each splice now has a null test at both ends rather than one, so the naive implementation has more case analysis than the singly linked one. That is exactly the problem the next section removes.

A hand-traced deletion, field by field

Take … ⇄ 19 ⇄ 4 ⇄ 23 ⇄ … and delete the node holding 4. Name the nodes a = node(19), x = node(4), b = node(23). Before the operation the four relevant fields are a.next = x, x.prev = a, x.next = b, b.prev = x.

step 1 — read what you need, before anything is destroyedp ← x.prev ( = a ) q ← x.next ( = b ) step 2 — reroute the forward linkp.next ← q a.next is now b (the forward chain already skips x) step 3 — reroute the backward linkq.prev ← p b.prev is now a (the backward chain now skips x too) state after — x is out of both chains; its own fields are untouched and now stalea.next = b b.prev = a x.prev = a x.next = b ← x still points INTO the list step 4 — hygiene, and it is not optional in every settingx.prev ← null ; x.next ← null so a stale reference to x cannot re-enter the list count2 reads, 2 writes (4 with hygiene), 0 traversal — independent of n and of x's position and the same trace run backwards — put a new node y holding 9 back between a and bp ← a q ← a.next ( = b ) 2 reads y.prev ← p y.prev is now a write 1 y.next ← q y.next is now b write 2 p.next ← y a.next is now y write 3 ← a's forward link now goes through y q.prev ← y b.prev is now y write 4 ← and b's backward link too check the symmetry invariant on all four affected fieldsa.next = y and y.prev = a ✓ y.next = b and b.prev = y ✓ … ⇄ 19 ⇄ 9 ⇄ 23 ⇄ … count2 reads, 4 writes, 0 traversal — insertion costs two more writes than removal, and for the same reason: the new node's own two fields have to be filled in, where a removed node's are simply abandoned

Step 4 is the one people omit. A deleted node that still points into the list is a live hazard: a stale iterator that dereferences it walks back into a structure it is no longer part of, and a second removal of the same node will happily rewrite a.next and b.prev with garbage — the double-free's structural equivalent. Nulling both fields turns that silent corruption into an immediate, obvious null dereference. Some implementations go further and write a poison value, so the failure names itself in a debugger.

Two links is not the last word. A node may carry any number of links, and each one buys a different question a cheap answer. A skip list gives some nodes extra forward links that jump ahead by powers of two, buying O(log n) expected search on a linked structure; a binary search tree gives each node two links interpreted as "smaller" and "larger"; an adjacency list gives each node a whole list of links. The design question is always the same one: which query is being paid for, and who maintains the extra links when the structure changes?

07 Sentinels: deleting the boundary cases rather than handling them

A sentinel is a node that holds no data and exists only so that the boundary of the structure is never null. A doubly linked list with a header before the first real node and a trailer after the last has no null link fields anywhere between them — so every real node has a real predecessor and a real successor, and every splice is the same three or four writes with no case analysis at all. That is the entire idea, and its effect on code quality is out of all proportion to its size.

Why this works: the invariant it establishes

The null tests in a boundary-free implementation exist to answer two questions — "is this node the first?" and "is this node the last?" — and both questions arise because the answer changes what has to be written. Sentinels make the answer always no. Every node the user can reach has a non-null prev and a non-null next; the header's prev and the trailer's next are the only nulls in the structure and no operation ever reads them. The invariant, stated once and then relied on everywhere, is: every node between H and T inclusive has both neighbours present, and H and T are never removed. Establishing an invariant so that downstream code can stop checking is the same move as a loop guard in a search, a padded border on an image convolution, or a bias term that removes a special case from a linear model — buy one piece of structure, delete a category of conditionals.

The write columns say the rest: sentinels are not buying speed. They are buying the deletion of a category of bug, at a cost of two nodes per list.

Where sentinels stop being worth it

  • Many small lists. Two sentinel nodes per list is a fixed overhead. A hash table with a hundred thousand buckets, each a list averaging one element, pays two hundred thousand empty nodes — often more memory than the data. This is the standard argument for null-terminated buckets, or for storing the first element inline in the bucket.
  • Singly linked lists. A header sentinel alone still removes the "insert or delete at the front" case, which is most of the benefit, and costs one node. A trailer sentinel buys less for the ordinary operations, because the front is where a singly linked list's boundary cases live — but it is not worthless: it is exactly what makes the copy-the-successor trick total, since with a trailer present no node holding real data is ever last. Which of the two is worth a node depends on which problem you have.
  • Where the sentinel can be mistaken for data. If a sentinel carries a payload field at all, some traversal somewhere will eventually read it. The standard discipline is that sentinel payloads are never valid, iteration is defined as stopping at the trailer rather than at null, and any public API that could hand a user a position pointing at a sentinel must return "no such element" instead.
  • A different use of the same word. "Sentinel" also names the trick of appending the search key to the end of an array so a linear scan needs no bounds check — the same idea, guaranteeing a loop terminates without testing a boundary, applied to contiguous storage. Both usages remove a conditional by adding an element.
Asymptotically nothing, practically a lot. Sentinels change no complexity bound on this page; they reduce constant factors slightly and reduce case analysis enormously. The right way to justify them is not "faster" but "there is no first-element case and no last-element case, because there is no first element and no last element" — a statement about the shape of the code rather than its speed.
