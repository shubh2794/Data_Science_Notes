Trees & Binary Search Trees

A tree is what you get when a linked node is allowed more than one forward link and forbidden from ever being pointed at twice: a hierarchy, with one root, no cycles, and a single path from the top to every node. That one restriction buys a great deal. It makes every question about the structure a recursion — a tree is a node plus smaller trees — so height, size, printing, evaluation and search all become three-line functions whose cost is the number of nodes they touch. It makes the shape of the tree, and specifically its height, the single number that governs the cost of everything that walks from the root down. And when the two links of a binary node are given a meaning — smaller keys this way, larger that way — the tree becomes a binary search tree: binary search made dynamic, with insert and delete alongside lookup, and with successor, range and sorted iteration thrown in, which is exactly the list of things a hash table cannot do. Every bound on this page is O(h), and the page ends where h stops being small on its own: with the measured collapse of a search tree fed sorted input, the theorem that says random input keeps it shallow, and the hand-off to the structures that enforce balance.

01 What a tree is

A rooted tree is a set of nodes in which one node is distinguished as the root and every other node has exactly one parent. That is the whole definition, and everything else — children, leaves, depth, height, subtrees, ancestors — is vocabulary for consequences of it. Because each non-root node has exactly one parent, following parent links from any node must end at the root without repeating (a repeat would mean some node had two parents, or the root had one), so there is exactly one path from the root to every node and no cycles. The same definition can be given recursively, and the recursive form is the one every algorithm on this page uses: a tree is either empty, or a root node together with a finite, possibly empty, list of disjoint trees, the subtrees, whose roots are the children of the root. Both definitions describe the same objects; the first is how you check something is a tree, the second is how you compute on one.

Why the recursive definition is the one that matters

The structural definition says what a tree is; the recursive one says how to take it apart, and every algorithm here is a case analysis on it: if the tree is empty, answer the base case; otherwise do something with the root and recurse on the subtrees. Size is 1 + ∑ size(subtrees); height is 1 + max height(subtrees); printing is "print the root, then print each subtree"; searching a search tree is "compare with the root, then recurse into exactly one subtree". The correctness of each of these is an induction on the size of the tree, and the induction goes through because the subtrees are strictly smaller and pairwise disjoint — which is precisely what the recursive definition guarantees and what a general graph does not. The theory of why such recursions terminate, how deep the call stack gets and when to replace it with an explicit stack lives on Recursion & Divide and Conquer; this page applies it to one family of structures and owns what is specific to them: the shapes, the traversal orders, the array and pointer layouts, and the search-tree invariant.

The conventions in the formula block are not the only possible ones, and it matters that a page picks one and sticks to it. Some treatments count height in nodes rather than edges, so that a single node has height 1 and the empty tree height 0; under that convention every "h" on this page becomes "h + 1" and the bound floor(log₂ n) of §03 becomes floor(log₂ n) + 1. The edge convention is used here because it makes height equal to the maximum depth, makes a leaf's height 0 match a leaf's "nothing below me", and matches the heap page's h = floor(log₂ n) exactly. The empty tree is given height −1 for one reason only: it makes the recursion height(v) = 1 + max(height(left), height(right)) correct without a special case for leaves, and it makes the counting bounds of §03 hold at n = 0 (with h = −1: h + 1 = 0 ≤ n = 0 ≤ 2⁰ − 1 = 0). Every formula on this page has been checked at n = 0, 1, 2 under these conventions.

The motivation: what hierarchy buys

  • A linked list with branching. A singly linked list is a tree in which every node has at most one child; the node-and-reference discipline is identical, and so is the danger — lose the root and you lose everything. What branching adds is the possibility of reaching any of n nodes in far fewer than n steps: a node at depth d is d links from the root, and a tree can hold 2ᵈ nodes at depth d, so n nodes can all sit within log₂ n links of the top. Whether they do is the shape question this page keeps returning to.
  • A model of things that are hierarchies. File systems, the document object model of a web page, the nesting of a JSON value, the call tree of a recursive program (Recursion §04), the parse tree of an expression or a sentence, an organisation chart, a taxonomy, the moves of a game explored from a position, the splits of a decision tree. For these the tree is not a clever encoding; it is the data. §13 collects them.
  • A vehicle for an ordering invariant. Give the two links of a binary node the meaning "smaller" and "larger", and a search becomes a walk down one path — the binary search tree, the second half of this page. Give the links the meaning "no smaller than me" and you get a heap. Give them the meaning "next character of the key" and you get a trie. The tree is the same; the invariant on it is what differs.
  • A connected acyclic graph, with a root. Seen from the graph side, a free tree is a connected graph with no cycles — n − 1 edges, exactly one path between any two vertices — and a rooted tree is a free tree with one vertex declared the root, which orients every edge away from it. The graph vocabulary and the breadth-first and depth-first searches that generalise this page's traversals are on Graph Representations & Traversal; here the root is always given and every edge already has a direction.
The one sentence to carry through the page. A tree is a recursive structure — a root and smaller trees — so every algorithm on it is a recursion whose cost is the number of nodes it touches, and every search on it is a walk down one path whose cost is the height. The first half of the page is about the shapes and the walks; the second half is about what happens when the walk is guided by keys.

02 Binary trees, and full, complete, perfect, degenerate

A binary tree is an ordered tree in which every node has at most two children, each labelled as the left child or the right child. The labelling is part of the structure, not a drawing convention: a node with one child that is a left child is a different tree from a node whose one child is a right child, and in a search tree the two mean opposite things. The recursive definition adjusts accordingly — a binary tree is empty, or a root with a left subtree and a right subtree, either or both of which may be empty — and the empty subtrees are real: they are where a search ends unsuccessfully, where an insertion attaches, and where the array layout of §05 wastes its space. Four named shapes recur, and because they are routinely confused and have different counting facts, they are separated here with their definitions side by side.

Full trees: leaves = internal + 1, proved

This identity is the one most often misapplied, so its hypothesis deserves emphasis: it holds for full binary trees — every node has zero or two children — and not for binary trees in general (the figure's degenerate chain has 1 leaf and h internal nodes, and its complete tree with an odd-sized last level fails it too whenever some node has exactly one child). The proof is a counting of edges two ways. Let a full tree have n_I internal nodes and n_E leaves, so n = n_I + n_E. Counting edges by their lower end, every node but the root is the child end of one edge: edges = n − 1 = n_I + n_E − 1. Counting edges by their upper end, every internal node is the parent end of exactly two (that is the fullness hypothesis) and leaves of none: edges = 2·n_I. Equating, 2·n_I = n_I + n_E − 1, so n_E = n_I + 1. The same double count with "exactly two" replaced by "at most two" gives only n − 1 ≤ 2·n_I, i.e. n_E ≤ n_I + 1, for a general binary tree — the identity becomes an inequality the moment a single one-child node exists. An equivalent removal argument — repeatedly delete a leaf together with its (internal) parent and reattach its sibling, which removes one of each kind and keeps the tree full, until one node is left — reaches the same conclusion and is the argument to remember if the edge count does not come to mind.

What the two extremes mean for cost

A binary tree of a million nodes can have height 19 (floor(log₂ 10⁶) = 19, since 2¹⁹ = 524 288 ≤ 10⁶ < 2²⁰) or height 999 999, and nothing in the definition of a binary tree prefers one to the other. Every operation whose cost is "walk one root-to-leaf path" — search, insert, delete, min, max in a search tree; sift-up and sift-down in a heap — is therefore either logarithmic or linear depending on a property the operation itself does not control. There are exactly three ways out, and this page and its neighbours take one each. Control the shape by construction: a heap is always complete because insertion and deletion are defined to keep it so, which is why its height is exactly floor(log₂ n) with no hypothesis. Rely on randomness: a search tree built from keys in random order has expected height O(log n) — a theorem with hypotheses, in §23. Rebalance: pay extra work on every update to keep h = O(log n) in the worst case — the AVL, red-black and B-tree families, which are built at Balanced & Multiway Trees and are only pointed at here from §22.

04 Representations: linked nodes, parent pointers, left-child / right-sibling

A tree in memory is a choice about which of its relations to store explicitly. The parent relation defines the tree, but almost every algorithm walks downward, so the standard representation stores the inverse: each node holds references to its children, and the parent is stored too only if some operation needs to climb. For binary trees that is two fields, left and right, and optionally parent; for general trees, whose nodes have any number of children, there are two honest layouts — a per-node list of child references, or the left-child / right-sibling trick, which encodes an arbitrary tree as a binary one with exactly two links per node and no lists at all.

The parent pointer: what it buys and what it costs

Without a parent link, a node knows nothing about where it sits; the only way to reach its parent is to search for it again from the root, remembering the previous node on the way — exactly the predecessor problem of a singly linked list, in two dimensions. Insertion into a search tree can live with that, because the insertion walk naturally has the parent in hand when it reaches the null it will replace (the trailing pointer of §18). Two operations cannot: the successor of a node with no right subtree is found by climbing (§16), and deletion of an arbitrary node must rewire the parent's link to it. Both can be written without parent pointers by re-searching from the root for the node's key — the cost stays O(h), since the re-search is one more root-to-node path — or by writing them recursively so that the recursion's return path plays the role of the parent chain. The parent pointer's price is a third reference per node (50% more link memory on a two-link node) and a third field to keep consistent on every structural change, which is where a large fraction of tree bugs live: the transplant operation of §20 exists precisely to update parent in exactly one place.

Left-child / right-sibling: an arbitrary tree with two links

A node with k children could store them in a list, but then the tree is a tree of lists — an extra allocation per internal node, a variable-size object, and an iteration protocol for "the children of v". The left-child / right-sibling representation removes all of it. Each node keeps only its first child and its next sibling; the children of v are recovered by taking v.firstChild and then following nextSibling links until null, which touches exactly k nodes for k children — linear in the number of children, never in n. What makes this more than a storage trick is that the result is a binary tree: rename firstChild to left and nextSibling to right and every binary-tree algorithm applies. A preorder traversal of the binary form visits the nodes in the general tree's preorder (root, then the first child's subtree, then the next sibling's — which is the rest of the children), as the figure's readout confirms on the 13-node sample. The costs shift in one visible way: sibling chains become depth in the binary form, so a general tree of height 3 with a node of three children becomes a binary tree of height 6, and the height of the binary form is bounded by the number of nodes on a root-to-leaf path counting siblings, not by the general height. Any algorithm whose cost is "the height of the binary form" is paying for that.

Where the array goes. The representations above are pointer-based and inherit the pointer-chasing cost of Linked Lists §03: each link followed is potentially a cache miss, and the nodes of a tree built over time are scattered wherever the allocator put them. The one representation that avoids all of it — a tree stored in a flat array with the structure in the index arithmetic — is the subject of the next section, and it is excellent for exactly one shape.

05 The array layout: level numbering, and why it is only for complete trees

Number the potential positions of a binary tree level by level, left to right, starting at 0 — the root is 0, its children 1 and 2, their children 3 … 6, and in general the children of position f are 2f + 1 and 2f + 2. Store the node at position f in slot f of an array and the tree needs no links at all: parent, left and right are arithmetic. For a complete tree the numbering is gap-free and the array has exactly n slots — that is the binary heap, whose index arithmetic, height and cache behaviour are derived in full on Heaps §02, §03 and §28 and are not repeated here. This section is about the other case: what the layout costs when the tree is not complete.

When the array layout is the right choice anyway

  • When the shape is complete by construction — the binary heap — and then it is not merely acceptable but the best representation available: n slots, no links, parent and children by shift-and-add, siblings adjacent in memory. The locality is genuinely good near the root and genuinely poor deep down, and the exact picture (Heaps §28) is that a root-to-leaf walk touches indices 0, 1–2, 3–6, 7–14, …, so the gap between a node and its child doubles at every level and only the top log₂ L levels share a cache line of L keys. "Trees have bad locality" is true of pointer trees and false of this one for its top levels; neither slogan survives without the shape it refers to.
  • When the tree is perfect and static — a tournament tree, a segment tree over a power-of-two range, the comparison tree of a binary search over a sorted array. A sorted array is a particular balanced search tree read in inorder rather than by level number, and the next part of the series makes that identity explicit for implicit search trees laid out in level order (Eytzinger layout), which trade the sorted array's simplicity for the heap's locality.
  • Never for a dynamic search tree, whose shape is dictated by the keys: the space is Θ(2ʰ) and a deletion that promotes a subtree must move every node in it. A dynamic tree is a pointer tree, and its locality problem is solved, when it must be, by making the nodes bigger — the B-tree of the next part — rather than by flattening the tree.

06 Computing depth and height, and the Θ(n²) trap

Depth and height are both defined recursively, and the two recursions run in opposite directions: depth is computed by climbing up parent links from a node to the root, height by descending down from a node to its leaves. Each is a one-line function with an obvious cost. The trap is in combining them. The definition "the height of a tree is the maximum depth of its leaves" is true, and implementing it literally — find every leaf, compute each one's depth by climbing, take the maximum — is correct and Θ(n²) on the wrong shape, while the direct recursion is Θ(n) on every shape. 07 The four traversals: preorder, inorder, postorder, level order

A traversal visits every node of a tree exactly once, and the traversal orders differ only in when a node is visited relative to its subtrees. Three of the four are depth-first — they finish a whole subtree before starting the next — and are distinguished by the position of the node among its children: preorder visits the node before its subtrees, postorder after them, and inorder, which is specific to binary trees, between the left subtree and the right. The fourth, level order (breadth-first), visits all nodes at depth 0, then all at depth 1, and so on, and is not a recursion at all but a queue. Which order you want is never a matter of taste: each corresponds to a different question about the tree, and the section lists them.

What each order is for

  • Preorder — copy, serialise, "process a node before its children". The node comes out before anything below it, so a preorder listing can be read back to rebuild the tree (given the null markers or the inorder sequence), a directory listing that prints a folder's name before its contents is a preorder, and any computation that hands a value down the tree — a node's depth is its parent's depth plus one, a node's path from the root is its parent's path plus itself — is a preorder with an extra argument. The prefix form of an expression is the preorder of its tree (§12).
  • Postorder — delete, size, height, evaluate, "process a node after its children". The node comes out after everything below it, so any computation that hands a value up — subtree size, height, the value of an expression, the total size of a directory tree — is a postorder. Freeing a tree's nodes must be postorder: free the children first, then the node, or the links to the children are gone before they are visited. The postfix form of an expression is its tree's postorder, which is why postfix evaluation needs only a stack.
  • Inorder — sorted order, infix notation. On a binary search tree the inorder sequence is the keys in sorted order (proved in §21), which is the single most used fact on this page. On an expression tree it is the infix form, which is what humans write, minus the parentheses that must be put back. On a general binary tree without an invariant it has no special meaning.
  • Level order — nearest first. Nodes come out in nondecreasing depth, so the first match found is a shallowest one, which is what a search that wants the closest answer needs; a game-tree search that must produce some answer within a time limit explores level by level so that it always has a complete shallow analysis; and the level numbering of §05 coincides with the level-order position for a COMPLETE tree (for others the level number skips the missing slots: node 9 of the sample BST is level number 21 but tenth in level order). It generalises to breadth-first search on graphs (Graph Representations & Traversal), where "depth" becomes "distance from the source" and the queue is what makes that true.

08 Recursive traversals: the Θ(n) proof and the stack depth

A recursive traversal of an n-node tree takes Θ(n) time and Θ(h) space. Both facts are usually asserted with "it visits each node once", and that phrase is true but not a proof: it does not account for the calls on empty subtrees, of which there are more than there are nodes, nor for the cost of returning. The honest proofs are short and are worth having exactly, because the same two arguments — count what happens per edge and the stack holds one frame per ancestor — are reused for every recursive tree algorithm on the page.

Why "each node once" is not enough, and why it does not matter here

The traversal makes 2n + 1 calls, not n: for the ten-node sample tree the counter reports 21, and on a chain of n nodes it would report the same 2n + 1, because the count depends on n only. The extra n + 1 calls are the ones that test x = null and return — they are the base cases of the recursion, they cost a constant each, and a proof that forgets them is off by a constant factor of about two, which is harmless for Θ(n) but would be fatal in an exact count (the kind the sorting page does for mergesort). The edge-counting proof avoids the issue by counting something structural — every edge is walked down once and up once — and it is the version that survives generalisation: to general trees, where a node's call loops over a list of children rather than making two fixed calls; to the Euler tour, which is literally the walk that crosses each edge twice; and to the successor-walk bound of §16, where the same "each edge at most twice" observation turns n − 1 calls of worst-case O(h) into Θ(n) in total.

The space bound is where the recursion's convenience is paid for. The stack holds one frame for every ancestor of the node being visited, so it is exactly as deep as the tree is, plus one; the recursion page derives the frame cost and its §06 the practical limits. On a balanced tree that is a few dozen frames and irrelevant. On a degenerate tree — which, for a search tree, is what sorted input produces (§22) — it is n frames, and a recursive traversal of a large chain is a stack overflow. The next section is the standard cure: own the stack.

09 Iterative traversals with an explicit stack, and the postorder trick

Every recursive traversal can be rewritten with a stack you allocate yourself, following the general recipe of Recursion §10: the stack holds what the call stack would have held, but only the part you need — a node reference rather than a whole frame — and its capacity is bounded by the heap rather than by the thread's stack reservation. The three orders need three slightly different loops, and inorder is the one to know cold, because it is the iterator over a search tree's keys (§17): it can be paused between visits, which a recursion cannot.

Recursion versus iteration for traversals: it depends, and on what. The iterative loop is not automatically faster. It does the same n pushes and pops the recursion does with frames, and a compiler's handling of a small recursive function is often as good as a hand-written loop. What the explicit stack buys is control: no overflow on a deep tree, the ability to stop and resume (an iterator), and the ability to store less than a frame per level. What it costs is clarity — the postorder loop in particular is easy to get subtly wrong — and the general trade-off is discussed on Recursion §08. Choose the recursion when the tree is known to be shallow and the traversal runs to completion; choose the loop when either fails.

10 Threaded trees and Morris traversal: inorder in O(1) extra space

The stack of the previous section exists to remember how to get back up. A tree has n + 1 null child links doing nothing, and a threaded tree spends them on exactly that memory: a null right link is replaced by a pointer to the node's inorder successor, so that "what comes next" is a pointer follow rather than a climb, and an inorder traversal needs neither recursion nor stack. Threads can be permanent — a design choice with a flag bit per link to say "this is a thread, not a child" — or, in Morris traversal, created on the fly and removed again as the walk passes, leaving the tree unmodified and the traversal in O(1) extra space and O(n) time.

11 The Euler tour: the one walk the three orders are views of

Draw a tree and walk around it keeping the edges always on your left, starting at the root, going down to the leftmost child and eventually coming back up to the root from the right. That walk — the Euler tour of the tree — passes each node three times in a binary tree: once on its left side on the way down, once underneath it between its two subtrees, and once on its right side on the way back up. Record only the left-side passes and you have the preorder; only the underneath passes, the inorder; only the right-side passes, the postorder. The three traversals are not three algorithms but three filters on one walk, and writing the walk once with three hooks — a "pre visit", an "in visit" and a "post visit" — is the template every nontrivial tree computation fits into.

13 Trees as the data itself: file systems, documents, parse trees, decisions, games

Before the search tree, which uses a tree as a device for finding keys, it is worth listing the cases where the tree is not a device but the shape of the data, because those are where the general-tree machinery of §01–§11 is used as is: variable numbers of children, preorder and postorder with hooks, level order for nearest-first, no ordering invariant on the keys. In every case below the question to ask is which traversal the common operations are — and it is almost always one of the four.

  • File systems. Directories are internal nodes, files are leaves, and the path /usr/local/bin is a root-to-node path written as the sequence of labels. Listing a directory recursively is a preorder (the directory's name before its contents); computing the total size of a directory tree is a postorder (children's sizes, then the sum); deleting a directory tree is a postorder (you cannot remove a directory that still has children). "Find the shallowest file with this name" is a level-order search. Hard links (to files — directories cannot be hard-linked on ordinary Unix filesystems) turn the tree into a DAG, so a naive postorder size sum double-counts unless it tracks inodes; symbolic links can even create cycles, which is why recursive tools refuse to follow them by default.
  • Structured documents: the DOM, JSON, XML. An HTML page is a tree of elements whose children are ordered; rendering is a preorder with the box-model state flowing down and a postorder with the computed sizes flowing up — the two directions of the Euler-tour hooks. A JSON value is a tree in which objects and arrays are internal nodes; a serialiser is a preorder with the punctuation emitted at the pre, between and post hooks ({, ,, }), which is the parenthesis printer of §12 with different brackets.
  • Parse trees and abstract syntax trees. A compiler front end builds a tree from source text — the expression tree of §12 is the smallest example — and every later phase is a traversal: type checking is a postorder (a node's type depends on its children's), code generation is a postorder (evaluate the operands, then apply the operator), pretty-printing is the inorder-with-precedence printer, constant folding is a postorder that replaces subtrees. The syntax trees of natural-language parsing are the same structure with a grammar's nonterminals as internal nodes.
  • Decision trees. Each internal node asks a question, each edge is an answer, each leaf a decision; classifying an example is a root-to-leaf walk, so its cost is the depth of the leaf reached — which is the height question of §03 in a different costume. In machine learning the tree is learned and the split questions are chosen to shorten the expected path; that is Decision Trees, and its "depth" and "number of leaves" hyperparameters are this page's vocabulary.
  • Game trees and search trees over states. Positions are nodes, moves are edges, and the tree is generated as it is explored rather than stored. Depth-first exploration with a depth cutoff is a bounded preorder; iterative deepening is a sequence of them; minimax is a postorder in which a node's value is the max or min of its children's. These trees are enormous and are never materialised, which is why the traversal's Θ(h) space bound rather than its Θ(n) time bound is the one that matters — the same trade the backtracking section of the recursion page makes.
  • The call tree. A recursive program's calls form a tree whose nodes are invocations; the running time is the size of the tree and the stack depth is its height, which is why the recursion page draws it and why the recursion-tree method of Algorithm Analysis sums work over its levels. That tree is walked in preorder — a call happens before its sub-calls — and unwound in postorder.
  • Hierarchies that are graphs in disguise. 14 What a binary search tree is: the invariant, exactly

A binary search tree is a binary tree with a key in every node such that, for every node x, every key in x's left subtree is less than x.key and every key in x's right subtree is greater. The word that carries the whole definition is subtree. The condition is not "the left child is smaller and the right child is larger" — that is a weaker statement, it is the one most people write down first, and a tree can satisfy it at every node while being useless for search. The correct invariant is what makes a search a single path: at any node, the key you want is either here, or entirely to one side, or absent; nothing anywhere in the other subtree can be it.

Why "subtree" and not "child"

A search compares the target with the root and then commits: if the target is smaller, it goes left and never looks at anything to the right again. That commitment is justified only if nothing in the right subtree could be the target, i.e. if every key there is larger than the root — the subtree condition. The child condition guarantees far less: it says the right child is larger, and says nothing about the right child's left subtree, which might contain a key smaller than the root. The counterexample in the figure is the smallest one: 12 is the right child of 5, correctly larger than 5, and is a descendant of 10 on the wrong side of it. A search for 12 compares with 10, goes right, finds 15, goes left into an empty subtree, and reports "absent" — correctly, in the sense that the algorithm did exactly what a search tree entitles it to do, and wrongly, because the tree lied. The checker that catches this is the interval form: each node receives the bounds its ancestors impose and tests its own key against them, so 12 is checked against (−∞, 10) and fails. A checker that only compares each node with its two children will pass this tree and every tree like it, and it is one of the most common wrong answers to "verify this is a BST".

Two invariants that look alike and are not. A heap requires each node to be no larger than its children — a child condition, which by transitivity becomes a subtree condition for free, because "no larger than" is the same relation on both sides. The search tree's condition has opposite relations on the two sides, and transitivity does not carry "left child smaller" past the child to the child's right subtree; that asymmetry is why the BST invariant must be stated over subtrees and why a heap gives no help at all in locating a key (Heaps §29).

16 Successor and predecessor: the two cases, and the amortised walk

The successor of a node x is the node with the next larger key — the one that follows x in inorder — and a search tree finds it without comparing any keys, from the structure alone. There are exactly two cases. If x has a right subtree, its successor is the smallest key there: go right once, then left to the bottom. If it has none, every larger key is above x: climb until the step just taken was from a left child, and the node arrived at is the successor; if the climb reaches the root without ever stepping up from a left child, x was the maximum and has none. Predecessor is the mirror image. Each call is O(h), and yet a full inorder walk by repeated successor calls is Θ(n), not O(n·h) — the two bounds are both true and the distinction is the first amortised argument on this page.

20 Deletion: the three cases, transplant, and the successor-or-predecessor choice

Deletion is the one operation on a plain search tree that has cases, and the reason is structural: removing a node with two children leaves a hole that must be filled by some key without violating the invariant, and only two keys can fill it — the node's successor or its predecessor, the two keys adjacent to it in sorted order. A node with no children is simply unlinked; a node with one child is replaced by that child; a node with two children is replaced by its successor, which has no left child (if it had one, that would be a smaller key still larger than the deleted one) and so can itself be removed by the one-child rule. 21 The inorder walk is sorted; tree sort, and its exact identity with quicksort

The inorder traversal of a search tree visits its keys in increasing order, in Θ(n) time — so a search tree is also a sorted sequence, and the operations that a sorted array supports by position (range queries, sorted iteration, "the k-th smallest") are all available, with the tree's dynamic insertion and deletion added. It also means that building a tree and walking it is a sorting algorithm, tree sort; and tree sort turns out to make exactly the same comparisons as quicksort with the first element as pivot and an order-preserving partition, which is why the two share every bound: Θ(n log n) expected on random input, Θ(n²) on sorted input, and the Ω(n log n) comparison lower bound in the worst case.

That is why "random insertion order" gives a good tree for the same reason "random pivot" gives a good sort, and why sorted insertion order is the same catastrophe as first-element pivoting on sorted input.

22 The cost is O(h): the degenerate case measured, and why balance matters

Every operation on a binary search tree — search, minimum, maximum, successor, predecessor, insert, delete — runs in O(h) time on a tree of height h. That is the theorem, and it is the whole theorem: nothing in the definition of a search tree bounds h by anything better than n − 1. The O(log n) that everyone associates with search trees is a corollary under a hypothesis — that h = O(log n) — and this section measures what happens when the hypothesis fails, which for a tree built by plain insertion it does the moment the keys arrive in sorted order. The next part of the series, Balanced & Multiway Trees, is about making the hypothesis true by force; this page ends by showing exactly what it has to prevent.

What balancing has to do, stated as a contract

A balanced search tree is one whose height is guaranteed to be O(log n) after every operation, in the worst case, for every input order. The guarantee is bought by extra work at insertion and deletion — some local restructuring near the modified path that keeps a shape invariant true — and the restructuring must itself cost only O(log n) (or amortised as much), or nothing has been gained. The classic invariants are of three kinds. Height balance: at every node the two subtree heights differ by at most one (AVL trees), which forces h < 1.44·log₂(n + 2). Colour balance: every root-to-null path has the same number of "black" nodes and no two consecutive "red" ones (red-black trees), which forces h ≤ 2·log₂(n + 1). Fan-out balance: every leaf at the same depth, with nodes holding between t − 1 and 2t − 1 keys (B-trees), which forces h ≤ log_t((n + 1)/2) and makes each node a disk block. Each is realised by rotations or splits — local operations that preserve the BST property while changing the shape — and each is the subject of the next part, which this page deliberately does not teach: it ends by handing over a tree whose only defect is that nothing stops h from reaching n − 1, and a chart of what that costs. The hand-off is Balanced & Multiway Trees.

The statement to never write. "Search in a BST is O(log n)." Without a qualifier it is false; the tree in the chart's red line is a BST and its search is Θ(n). Write "O(h)", or "O(log n) if balanced", or "O(log n) expected for random insertion order" — and mean the hypothesis you attached.

24 The deletion bias: why "no deletions" is in the hypothesis

The standard deletion of §20 replaces a two-child node with its successor, always. That is a fixed asymmetry — keys are promoted from the right subtree, never the left — and over a long sequence of random insertions and deletions it slowly reshapes the tree: the distribution stops being the randomly-built one, and the conjectured asymptotic behaviour — supported by an analytic model and by simulation, and proved for the variant in which the deleted key itself is re-inserted — is that the expected mean depth eventually grows like Θ(√n) rather than Θ(log n). The effect is slow to appear and modest at sizes a figure can run, and the figure reports what it actually measured rather than the asymptote; but it is real, it is the reason the random-tree theorem excludes deletions, and it has a one-line cure.

Reading the table

  • If nothing ever asks about order, hash. Every row where the tree wins is an order question — min, successor, range, sorted iteration, rank. A program that only ever does get and put by exact key pays a logarithm for nothing with a tree, and pays it on every access.
  • If the set is static, sort it. A sorted array beats every tree on every query row and on space and locality; it loses only on updates. Build once, binary-search forever — and the boundary variants of binary search give range queries and rank directly. Many "I need an ordered map" cases are this one in disguise.
  • If the set is dynamic and order matters, tree — and then almost always a balanced one, because the plain tree's O(h) is a promise about the input, not about the structure. The one honest use of a plain BST is when the insertion order is known to be random (or can be made so), in which case §23 applies and the simpler code wins.
  • The floor under everything. Sorted iteration from a hash table costs a sort, and a tree gives it in Θ(n) — but building the tree cost Ω(n log n) comparisons (§21), so over the lifetime of the data the logarithm was paid either way. The tree spreads it over the insertions; the hash-then-sort pays it at the end. Which is better depends on how many times the sorted order is wanted.

28 Trees in practice: which ordered maps are trees, and which are not

The plain binary search tree of this page is almost never what a library ships as its ordered map, for exactly the reason of §22: no library can promise its users random insertion order. What ships is a balanced variant, and — a point worth checking rather than assuming — not always a binary one, and sometimes not a tree at all. The list below is general practice as documented by the implementations themselves; it is the landscape the next part of the series maps in detail.

  • Red-black trees are the classic choice for an in-memory ordered map with per-node allocation: the C++ standard library's map/set in the common implementations, Java's TreeMap/TreeSet, and .NET's SortedDictionary/SortedSet are all red-black trees, and the Linux kernel uses an intrusive red-black tree in several subsystems (its process scheduler's run queue among them). The guarantee is h ≤ 2·log₂(n + 1) with O(1) rotations per update.
  • B-trees in memory are the newer answer to the locality row of §27: Rust's BTreeMap is a B-tree rather than a binary tree, storing several keys per node in a contiguous array so that one cache line serves several comparisons and the number of allocations drops by the node's fan-out. The designer of the C++ standard library has said he would choose a B-tree today for the same reason. Every database index of note — the B+-tree — is the on-disk version of the same idea, with the node sized to a page.
  • Skip lists get the same expected O(log n) from randomised linked lists and no rotations, and are chosen where simplicity or concurrency matters: the sorted-set type of a well-known in-memory data store is a skip list paired with a hash table, and the in-memory write buffer of a widely used embedded key-value store is a skip list because it must serve concurrent readers alongside a single writer without locking.
  • Python has no ordered map in its standard library. Its dict is a hash table that preserves insertion order, which is not sorted order; a sorted map comes from a third-party package whose implementation is, notably, a list of sorted lists rather than a tree — a reminder that "ordered map" is an interface and the tree is one implementation. Go's standard library likewise has no ordered map. JavaScript's Map is insertion-ordered, not sorted.
  • Where the plain BST does appear: as the internal structure of a treap (a BST whose shape is randomised by priorities — the next part), as the comparison structure that binary search over a sorted array implicitly follows, in textbooks, and in code that knows its keys are random or is willing to shuffle them. It is also, unfortunately, common in code that does not know its keys are sorted, and §22 is what that code does at scale.

Three systems claims, each with its condition

  • "Trees have bad locality." True of a pointer tree built over time: each level of a search is a dependent pointer load, likely a cache miss, and a lookup on a million-key balanced tree is roughly twenty misses. False of the array-encoded complete tree for its top levels (Heaps §28), false of a B-tree whose nodes are cache lines or pages, and much less true of a tree built from sorted input into contiguous memory in level order. The claim is about the representation, not the abstraction.
  • "Recursion is slower than iteration for traversals." Sometimes, marginally, and it depends on the compiler, the language runtime and whether the recursion is the tail-call kind. What is reliably different is the space bound — frames versus a node stack you size yourself — and the ability to pause. Choose by those, measure if the constant matters.
  • "A language's ordered map is a BST." Some are (balanced binary: red-black); some are B-trees; some are skip lists; some do not exist. All of them present the operations of §27's last column, and the choice of structure underneath is decided by memory layout and concurrency, not by asymptotics, which are the same for all of them.

29 Pitfalls

  • "O(log n) search in a BST." The theorem is O(h). Without "balanced" or "random insertion order" the statement is false, and sorted input — auto-increment ids, timestamps, log lines — is the common case, not the pathological one (§22).
  • Checking the invariant against children only. A validator that compares each node with its two children passes trees that are not search trees; the correct check passes bounds down or verifies that inorder is strictly increasing (§14).
  • Confusing full, complete and perfect. leaves = internal + 1 needs full; h = floor(log₂ n) needs complete; n = 2ʰ⁺¹ − 1 needs perfect. A complete tree can have a one-child node; a full tree can be a zig-zag of height (n − 1)/2 (§02).
  • Two height conventions. Height in edges (this page: leaf 0, empty −1) or in nodes (leaf 1, empty 0); every formula shifts by one between them. State which, and check n = 1.
  • The naive height is quadratic — on a comb, not on a chain. "Max depth over leaves, each by climbing" is Θ(n²) when there are many deep leaves; a chain has one leaf and is linear for it. The recursive height is 2n + 1 calls on every shape (§06).
  • The array layout for a non-complete tree. A right-going chain of 20 nodes needs 2²⁰ − 1 slots; the layout is Θ(2ʰ) space and is for complete trees only (§05).
  • Recursive traversal of a deep tree. The stack is h + 1 frames; on the degenerate tree that is n, and a large one overflows. Use the explicit stack or Morris (§09, §10).
  • Preorder + postorder do not determine a tree. A(B, ∅) and A(∅, B) have the same preorder and postorder. Inorder plus either does, for distinct keys (§07).
  • Postfix build pops in the wrong order. The top of the stack is the right operand; popping it second gives 4 − 7 for 7 4 −. Test on a non-commutative operator (§12).
  • Printing infix without the associativity clause. 8 / (4 / 2) must keep its parentheses, 9 − 3 − 2 must not; precedence alone gets one of them wrong (§12).
  • Deleting by copying the key. Copying the successor's key into the node and deleting the successor's node is simpler and leaves any outside reference to either node pointing at the wrong thing. Transplant deletes the node it was asked to delete (§20).
  • Forgetting the parent pointer in transplant. The replacing subtree's parent must be set, and it may be null. Every "the tree is corrupted after delete" bug is here or in the "successor is not the right child" case.
  • Always taking the successor on delete. Correct, and over a long stream of random updates it makes the tree drift toward Θ(√n) mean depth (conjectured for random replacement keys, proved when the same key returns). Alternate (§24).
  • Assuming the random-tree bounds after deletions, or on non-random input. Both hypotheses are load-bearing (§23). And the random-tree height constant 4.311 is a slow asymptote: at n = 1024 the measured height is about 3.0·ln n.
  • "Uniformly random BST" for "randomly built BST". Uniform over shapes gives Θ(√n) expected height; uniform over insertion orders gives Θ(log n). The Catalan count is over shapes (§25).
  • Equal keys sent to "either side". Then search cannot prune and every bound fails. Send them consistently to one side, or keep a count per node (§14).
  • Mutating a key in place. A key changed while in the tree silently breaks the invariant for every ancestor; remove, change, reinsert.
  • Building from sorted input node by node when you could build directly. Sorted input into a plain BST is Θ(n²); the same sorted input builds a minimum-height tree (height floor(log₂ n)) in Θ(n) by taking the middle element as root recursively (the median-first order of §18).
  • Using a search tree when no query involves order. Every access pays a logarithm the hash table would not; §27's first rule.
