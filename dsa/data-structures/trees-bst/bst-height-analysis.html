21 The inorder walk is sorted; tree sort, and its exact identity with quicksort

The inorder traversal of a search tree visits its keys in increasing order, in Θ(n) time — so a search tree is also a sorted sequence, and the operations that a sorted array supports by position (range queries, sorted iteration, "the k-th smallest") are all available, with the tree's dynamic insertion and deletion added. It also means that building a tree and walking it is a sorting algorithm, tree sort; and tree sort turns out to make exactly the same comparisons as quicksort with the first element as pivot and an order-preserving partition, which is why the two share every bound: Θ(n log n) expected on random input, Θ(n²) on sorted input, and the Ω(n log n) comparison lower bound in the worst case.

The order-preserving partition is essential to the pair-by-pair identity — an in-place Lomuto or Hoare partition (Sorting §12–13) reorders the sub-arrays and so changes which element becomes the next pivot, and Lomuto's partition gives exactly the same comparison-count distribution (verified by full enumeration at n ≤ 7) while Hoare's, which compares about n + 1 times per partition as the pointers cross, has a different one.

What the identity teaches. The root of a search tree partitions the keys exactly as a pivot does, and each subtree is the recursive sort of one side. A search tree is therefore a materialised quicksort: the recursion tree of the sort, kept in memory, with each pivot's comparisons paid once at insertion instead of once per partition pass. That is why "random insertion order" gives a good tree for the same reason "random pivot" gives a good sort, and why sorted insertion order is the same catastrophe as first-element pivoting on sorted input.

22 The cost is O(h): the degenerate case measured, and why balance matters

Every operation on a binary search tree — search, minimum, maximum, successor, predecessor, insert, delete — runs in O(h) time on a tree of height h. That is the theorem, and it is the whole theorem: nothing in the definition of a search tree bounds h by anything better than n − 1. The O(log n) that everyone associates with search trees is a corollary under a hypothesis — that h = O(log n) — and this section measures what happens when the hypothesis fails, which for a tree built by plain insertion it does the moment the keys arrive in sorted order. The next part of the series, Balanced & Multiway Trees, is about making the hypothesis true by force; this page ends by showing exactly what it has to prevent.

What balancing has to do, stated as a contract

A balanced search tree is one whose height is guaranteed to be O(log n) after every operation, in the worst case, for every input order. The guarantee is bought by extra work at insertion and deletion — some local restructuring near the modified path that keeps a shape invariant true — and the restructuring must itself cost only O(log n) (or amortised as much), or nothing has been gained. The classic invariants are of three kinds. Height balance: at every node the two subtree heights differ by at most one (AVL trees), which forces h < 1.44·log₂(n + 2). Colour balance: every root-to-null path has the same number of "black" nodes and no two consecutive "red" ones (red-black trees), which forces h ≤ 2·log₂(n + 1). Fan-out balance: every leaf at the same depth, with nodes holding between t − 1 and 2t − 1 keys (B-trees), which forces h ≤ log_t((n + 1)/2) and makes each node a disk block. Each is realised by rotations or splits — local operations that preserve the BST property while changing the shape — and each is the subject of the next part, which this page deliberately does not teach: it ends by handing over a tree whose only defect is that nothing stops h from reaching n − 1, and a chart of what that costs. The hand-off is Balanced & Multiway Trees.

The statement to never write. "Search in a BST is O(log n)." Without a qualifier it is false; the tree in the chart's red line is a BST and its search is Θ(n). Write "O(h)", or "O(log n) if balanced", or "O(log n) expected for random insertion order" — and mean the hypothesis you attached.

23 Randomly built search trees: expected depth ≈ 2·ln n, expected height ≈ 4.31·ln n

If the keys arrive in a uniformly random order, the tree is shallow with high probability: the expected depth of a node is about 2·ln n ≈ 1.39·log₂ n, and the expected height about 4.311·ln n ≈ 2.99·log₂ n. These are theorems with two hypotheses that are easy to lose — every insertion order is equally likely, and the tree was built by insertions only — and each hypothesis has a way of failing in practice: real key streams are not random permutations (§22), and deletions, done the standard way, break the distribution (§24). Within the hypotheses the results are exact enough to check by measurement, and the figure does.

At the default n = 1024 the measured mean depth over twenty trees is 11.03 and the exact expectation 2(1 + 1/1024)·H₁₀₂₄ − 4 is 11.03 — the theorem is exact and the Monte Carlo lands on it — while the rough 2·ln n = 13.9 overshoots because the constant 2γ − 4 ≈ −2.85 is not small at this n. The height markers tell the other half of the story: the measured mean height is 20.8 (range 18–25), the asymptotic 4.311·ln n = 29.9 is far to the right, and even with the second-order term (26.1) the law has not converged; the measured ratio height / ln n is 2.99 here and creeps upward as n grows — slide to 4096 and it reaches about 3.2. The constant 4.311 is a true limit and a poor estimate at any size a figure can build; the honest statement at practical sizes is "the height of a random BST is about three times ln n, rising slowly toward 4.3". The histogram's shape — a peaked bulk around the mean with a long right tail to the height — is the picture behind both numbers: most nodes are near 2·ln n, a few are much deeper, and the deepest decides the worst-case search.

Randomness as a design tool. Since the theorem needs only that the insertion order be random, an adversarial or sorted input can be rescued by shuffling it before insertion — when all keys are known up front, which is the situation in which one could simply sort and build a perfect tree instead. When keys arrive online the shuffle is unavailable, and the alternatives are to randomise the structure rather than the order (treaps and skip lists, in the next part) or to enforce balance deterministically (AVL, red-black, B-trees). The same fact under the same hypothesis is why randomised quicksort works, via the identity of §21.

24 The deletion bias: why "no deletions" is in the hypothesis

The standard deletion of §20 replaces a two-child node with its successor, always. That is a fixed asymmetry — keys are promoted from the right subtree, never the left — and over a long sequence of random insertions and deletions it slowly reshapes the tree: the distribution stops being the randomly-built one, and the conjectured asymptotic behaviour — supported by an analytic model and by simulation, and proved for the variant in which the deleted key itself is re-inserted — is that the expected mean depth eventually grows like Θ(√n) rather than Θ(log n). The effect is slow to appear and modest at sizes a figure can run, and the figure reports what it actually measured rather than the asymptote; but it is real, it is the reason the random-tree theorem excludes deletions, and it has a one-line cure.

What it does show is measurable and enough to justify the hypothesis: after deletions, a tree is no longer randomly built, and a one-line change to which neighbour replaces a deleted node decides whether it gets better or worse.

25 Counting search trees: the Catalan numbers, and why random order ≠ random shape

How many different binary search trees hold the same n distinct keys? The keys are forced into inorder, so the question is how many binary tree shapes there are on n nodes, and the answer is the n-th Catalan number: 1, 1, 2, 5, 14, 42, 132, …, growing like 4ⁿ / n^(3/2). Two facts follow that are easy to state wrongly. First, the count is of shapes with keys in sorted inorder, so it assumes distinct keys. Second, the n! insertion orders map onto those shapes very unevenly — balanced shapes are hit by many orders and chains by one each — so "a randomly built BST" (random insertion order, §23) and "a uniformly random BST" (each shape equally likely) are different distributions, and only the first is the one with logarithmic expected height.

26 Augmenting a search tree: subtree sizes for rank and select, and beyond

A search tree answers "is k here?" and "what is next after k?"; it does not, as built, answer "what is the 6th smallest key?" or "how many keys are below k?" — those need a count of what lies to the left, and a plain node knows nothing about the size of its subtrees. Store one extra integer per node, the size of its subtree, and both questions become one root-to-node walk. This is augmentation: attach to each node a summary of its subtree that can be recomputed from its children in O(1), keep it correct on the way back up from every insertion and deletion, and the tree answers a new class of query at the old O(h) cost.
