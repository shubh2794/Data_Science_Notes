Dynamic Programming

Data Structures & Algorithms Define the state, write the recurrence, fill in dependency order — how exponential recursion collapses into a polynomial table.

01 The two ingredients

Dynamic programming breaks a hard problem into smaller overlapping subproblems and caches each answer so it is computed exactly once. It is not a trick; it is a bookkeeping discipline applied to recursion.

  • Optimal substructure: an optimal solution is assembled from optimal solutions of its subproblems. Without it, a cached subanswer might be the wrong one to reuse.
  • Overlapping subproblems: naive recursion revisits the same subproblem many times. Without overlap there is nothing to save — that is plain divide-and-conquer, like mergesort.
  • Why caching wins: naive Fibonacci recursion makes 2·fib(n+1) − 1 calls, growing like φⁿ with φ ≈ 1.618. Yet only n + 1 distinct values exist. Storing each one collapses exponential work into Θ(n).
  • The cost formula: total work is the number of distinct states multiplied by the work per transition. Every complexity claim on this page is that product — quote it that way and the bound is never a guess.
From exponential to linearnaive: T(n) = T(n−1) + T(n−2) + Θ(1) ⇒ Θ(φⁿ), φ = (1+√5)/2 memoized: n+1 distinct states × Θ(1) transition ⇒ Θ(n) time, Θ(n) space general: cost = (# states) × (work per transition)
Takeaway: DP does not make the search space smaller — it makes you visit each point in it once. If the state space is exponential, so is the DP.

02 Top-down memoization vs bottom-up tabulation

Same recurrence, two ways to execute it: let recursion discover the order, or impose the order yourself.

  • Top-down: keep the natural recursion, add a cache, return early on a hit. It computes only the states actually reachable from the goal — a real saving when the reachable slice of the table is sparse.
  • Bottom-up: fill a table from the base cases upward in an order that guarantees every dependency is already resolved. No recursion, no stack limit, and it exposes the rolling-array space optimizations of section 09.

Takeaway: write it top-down first — the recurrence is easier to trust when it mirrors the recursion — then convert to a table if you need the constant factor or the space saving.

03 The recurrence-first method

The hard part of DP is never the code — it is deciding what a subproblem is. Answer five questions in order and the implementation is mechanical.

  • 1 · State. What exactly does dp[…] mean, in one sentence with every index pinned down? "The best value using the first i items with capacity w" is a state; "something about items" is not.
  • 2 · Transition. From that state, what choices exist, and which earlier states does each one consult? This is the recurrence.
  • 3 · Base cases. The smallest states, answered directly — usually empty prefixes, zero capacity, or single elements.
  • 4 · Evaluation order. An order in which every dependency is already computed. Bottom-up code is wrong the moment this is wrong, and it fails silently by reading a zero.
  • 5 · Answer. Which cell (or which maximum over cells) is the result? Not always the last one — LIS is a maximum over the whole table.
State must be sufficientthe state has to capture everything the future depends on if two paths reaching the same state can lead to different futures, the state is missing a dimension cost = (# states) × (transitions per state)
Takeaway: a state is sufficient when two different histories arriving at it are interchangeable from then on. Failing that test is the root cause of most wrong DP solutions — you add a dimension and the recurrence becomes correct.

04 One-dimensional families

The simplest DPs index a single position and look back a constant number of steps. Recognizing them is mostly pattern matching on the recurrence.

  • Climbing stairs / counting paths: to reach step i you came from i−1 or i−2, so the counts add. Identical to Fibonacci with different base cases — Θ(n) time, O(1) space once you keep only two values.
  • House robber: at each element, either skip it and keep the previous best, or take it and add the best from two back. The "cannot take neighbours" constraint is what forces the i−2 reference.
  • Maximum subarray: the best subarray ending at i either extends the previous one or restarts at i. The global answer is the maximum over all i — a linear scan, and a clean illustration of "the state is the best ending here, not the best so far".
Linear recurrencesstairs: f(i) = f(i−1) + f(i−2), f(0)=1, f(1)=1 house robber: f(i) = max( f(i−1), f(i−2) + a[i] ) max subarray: best(i) = max( a[i], best(i−1) + a[i] ), answer = maxi best(i) all three: Θ(n) time, O(1) space
Takeaway: when the answer is a maximum over states rather than the final state, say so explicitly — returning dp[n] out of habit is a classic off-by-one-idea bug.

05 The knapsack family

Two dimensions now: how far through the items you are, and how much budget remains. Almost every "choose a subset under a limit" problem is this table.

0/1 knapsack

  • State: dp[i][w] is the best value obtainable from the first i items with capacity w. Transition: skip item i, or take it and pay its weight — take the better.
  • Cost: n·W states, O(1) transition ⇒ Θ(n·W) time, reducible to O(W) space by keeping one row.
  • "Pseudo-polynomial" matters. W is written in log W bits, so n·W is exponential in the input length. Knapsack is NP-hard; the table is fast only when capacities are small numbers.

Unbounded knapsack and coin change

  • With unlimited copies the recurrence consults the same item count, so in the 1-D rolling form the capacity loop runs ascending — a cell may reuse an already-updated cell from this round. For 0/1, the same loop must run descending so each item is used at most once. One loop direction is the entire difference between the two problems.
  • Coin change is the same skeleton with a min instead of a max, and unreachable amounts held at infinity so they never win a comparison.
Knapsack recurrences0/1: dp[i][w] = max( dp[i−1][w], dp[i−1][w − wᵢ] + vᵢ ) for wᵢ ≤ w unbounded: dp[w] = maxi( dp[w − wᵢ] + vᵢ ) coin change: dp[a] = 1 + minc dp[a − c], dp[0] = 0 cost: Θ(n·W) time · O(W) space · pseudo-polynomial in W
Takeaway: in the space-optimized 1-D version, loop direction encodes reuse. Descending = each item once; ascending = unlimited copies. Get it backwards and you silently solve the other problem.

06 String and grid DP

Two sequences, two indices: dp[i][j] compares a prefix of one against a prefix of the other. The whole family — alignment, similarity, diffs — is one grid fill.

  • Longest common subsequence: if the current characters match, extend the diagonal by one; otherwise drop a character from one side or the other and keep the better. Θ(m·n) time.
  • Edit distance: the minimum inserts, deletes and substitutions turning one string into the other. Borders are dp[i][0] = i and dp[0][j] = j — the cost of deleting or inserting a whole prefix. On a match the cost carries from the diagonal; otherwise it is 1 plus the cheapest of the three neighbours, each neighbour naming one edit.
  • Reading the directions: diagonal = substitute (or free match), up = delete from the row string, left = insert from the column string. That mapping is what makes the table reconstructible into an actual edit script.
Grid recurrencesLCS: match → dp[i−1][j−1] + 1 · else → max( dp[i−1][j], dp[i][j−1] ) edit distance: match → dp[i−1][j−1] else → 1 + min( dp[i−1][j], dp[i][j−1], dp[i−1][j−1] ) borders → dp[i][0] = i, dp[0][j] = j cost: Θ(m·n) time · Θ(min(m,n)) space if only the value is needed
Edit-distance table, filled cell by cell Each step applies the recurrence and highlights the winning neighbor
Takeaway: watch the fill order in the visualization — every cell reads only its left, upper and diagonal neighbours, which is exactly why row-by-row is a valid evaluation order and why one row of memory suffices.

07 Longest increasing subsequence

The textbook O(n²) DP, and the rewrite that makes it O(n log n) by changing what the table stores.

  • Quadratic version: let dp[i] be the length of the longest increasing subsequence ending at i. Scan all earlier smaller elements and extend the best. n states with an O(n) transition ⇒ Θ(n²).
  • The patience trick: keep an array tails where tails[k] is the smallest possible tail among all increasing subsequences of length k+1. Invariant: tails is strictly increasing at all times, so it can be binary-searched. For each element, replace the first tail that is ≥ it, or append if none is — O(log n) per element.
  • Careful: tails is not itself an LIS, only its length is correct. Reconstructing the actual subsequence needs a predecessor index stored per element.
LISquadratic: dp[i] = 1 + max{ dp[j] : j < i and a[j] < a[i] }, answer = maxi dp[i] Θ(n²) tails invariant: tails[0] < tails[1] < … · tails[k] = smallest tail of a length-(k+1) subsequence binary search per element ⇒ Θ(n log n) time, Θ(n) space
Takeaway: the speed-up comes from re-choosing the state — from "best ending at i" to "best tail per length". Redefining the state is often worth more than optimizing the loop; the binary search itself is standard Sorting & Searching.

08 Interval, tree, and bitmask DP

When the state is a range, a subtree, or a subset, the same method applies — only the shape of the state changes.

  • Interval DP: dp[i][j] covers the segment from i to j and tries every split point k inside it. With Θ(n²) states and an O(n) transition the cost is Θ(n³) — matrix-chain ordering, optimal binary search trees, merging stones.
  • Tree DP: the state is a subtree, and the evaluation order is a post-order traversal, so children are solved before their parent. Usually dp[v][0/1] for "v excluded / included", giving Θ(n) over the whole tree.
  • Bitmask DP: the state is a subset encoded in the bits of an integer, for problems where order or membership among ≤ ~20 items matters. Shortest Hamiltonian path costs Θ(2ⁿ·n²) — still exponential, but a colossal improvement on n!.
  • Beyond puzzles: the Viterbi algorithm in hidden Markov models is DP over (position, hidden state) in Θ(T·|S|²), and all-pairs Floyd-Warshall in Trees & Graphs is DP over which vertices may be used as intermediates.
Shapes of stateinterval: dp[i][j] = mini ≤ k < j ( dp[i][k] + dp[k+1][j] + cost(i, j) ) Θ(n³) tree: dp[v] = combine over children c of v (post-order) Θ(n) bitmask: dp[mask][i] = best route covering set mask ending at i Θ(2ⁿ·n²)
Takeaway: "smaller subproblem" does not have to mean "shorter prefix". Ranges shrink inward, trees shrink toward leaves, subsets shrink by clearing bits — pick the ordering in which your state genuinely gets smaller.

09 Rolling arrays and reconstructing the answer

Two routine follow-ups: shrink the memory, and recover not just the optimal value but the choices that achieved it.

  • Rolling arrays: if dp[i][·] depends only on dp[i−1][·], keep two rows — or one, with the loop direction chosen so you never clobber a value you still need. Grid DPs drop from Θ(m·n) to Θ(n) space; linear DPs drop to O(1).
  • The trade-off: discarded rows cannot be walked backwards, so the compressed version returns the value but not the solution. Keep the full table when you need the path — or use a divide-and-conquer split that recovers an alignment in linear space at the cost of roughly doubling the time.
  • Reconstruction: either store a parent pointer per cell recording which choice won, or re-derive it by walking backwards from the answer cell and asking at each step which neighbour is consistent with the recorded value. The first costs memory, the second costs nothing but care.
Space compressionif dp[i][·] reads only dp[i−1][·]: Θ(m·n) space → Θ(n) if dp[i] reads only dp[i−1], dp[i−2]: Θ(n) space → O(1) time is unchanged · but the traceback path is lost
Takeaway: decide up front whether the question asks for the value or the solution. Compressing space first and being asked for the sequence afterwards means writing the whole thing twice.

10 Recognizing DP, and the usual mistakes

DP problems announce themselves. The signals are a sequence of choices, a best-or-count objective, and a state space small enough to enumerate.

Signals

  • "How many ways…", "minimum / maximum cost…", "is it possible to reach…" — counting and optimizing over choices, not reporting a fixed quantity.
  • Each choice constrains later choices, so a locally best pick can be globally wrong — which is exactly where greedy fails and DP succeeds. Greedy commits and never revisits; DP weighs all relevant subproblems first.
  • Brute-force recursion is obvious but retraces the same configurations, and the number of distinct configurations is polynomial.

Common mistakes

  • An insufficient state: two histories reach the same cell but face different futures. Add the missing dimension.
  • Wrong evaluation order: reading a cell that has not been filled. It does not crash — it returns a plausible wrong number.
  • Base cases and borders: confusing "index i" with "the first i items" is the source of nearly every off-by-one here.
  • Loop direction in a space-compressed 1-D table, which silently converts 0/1 into unbounded.
  • Reaching for DP when there is no overlap (that is divide-and-conquer) or when a proved greedy rule exists (that is cheaper).
  • Ignoring the recursion depth of a top-down solution over a long sequence.
Takeaway: state the state in one sentence, then the recurrence, then the order, then the cost as states × transition — and only then write code. The same discipline scales far beyond puzzles: the Bellman equations and value iteration of Reinforcement Learning are dynamic programming over states of a Markov decision process, and the bounds here are stated in the language of Big-O Complexity.
