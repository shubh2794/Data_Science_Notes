AI Engineering

The discipline of building, evaluating, and operating production AI/LLM applications — bridging the gap between a model that works in a notebook and a system that works for users. The core loop is: prompt it, evaluate it, guard it, ship it, watch it, improve it.

LLMs Production Evaluation Architecture

01 What is AI engineering

AI engineering is what happens after the model exists. Where ML engineering trains and serves models, AI engineering wraps a foundation model in context, guardrails, caches, routers, and feedback loops to produce a reliable application.

  • The shift: classical ML engineering owns the model (data collection, training, serving). AI engineering treats the model as a component and owns the application — the prompts, orchestration, evaluation, and operational envelope around it.
  • The 3-layer stack: (1) Model layer — foundation models, fine-tuning, alignment. (2) Application layer — prompting, RAG, agents, guardrails, caching, routing. (3) Infrastructure layer — serving, observability, cost control, feedback pipelines.
  • Why it emerged: foundation models made the model layer accessible via APIs. The hard engineering moved to the application layer — how to reliably extract value from a model you did not train.
  • Core activities: prompt engineering, evaluation pipeline design, context engineering, guardrail architecture, model selection and routing, caching, monitoring, cost optimization, and building data flywheels from production traffic.
  • Key difference from MLOps: MLOps automates training pipelines and model lifecycle. AI engineering focuses on inference-time orchestration and the evaluation-driven development loop. In practice they overlap heavily — see LLMOps.

02 The production architecture

A 5-step pipeline that wraps around every LLM call in a production system. Each step is independently valuable; together they form the standard AI engineering stack.

The 5-layer production architecture Click a layer to see details — each wraps the model call
  • Step 1 — Enhance context. Before the model sees the query, enrich it: retrieve documents (RAG), inject few-shot examples, prepend conversation memory, attach tool results. This is context engineering at the system level.
  • Step 2 — Guardrails. Validate inputs (injection screening, topic scope, PII detection) and outputs (schema conformance, policy compliance, citation presence). Deterministic rules first, model-based classifiers for the rest. Details in LLM Security.
  • Step 3 — Model router and gateway. Route requests by complexity: simple questions to a small/cheap model, hard ones to a frontier model. A gateway provides a unified API, rate limiting, retries, fallback chains, and usage logging.
  • Step 4 — Cache. Exact-match caching for repeated queries; semantic caching (embed the query, search by cosine similarity, return a cached answer if similarity exceeds a threshold). Also: KV cache reuse (prompt caching) to avoid re-processing shared prefixes.
  • Step 5 — Agent patterns. When the task requires multi-step reasoning, tool use, or dynamic control flow, add agent patterns — but only when the simpler layers are insufficient. See design patterns.

Cross-cutting concerns wrap around all five steps:

  • Monitoring and observability — trace every call, log token usage, measure latency, detect regressions. See monitoring and drift.
  • Orchestration — pipeline frameworks (LangChain, LlamaIndex, custom DAGs) wire the steps together; the orchestrator manages retries, fallbacks, and state.
  • User feedback — thumbs up/down, edits, regenerations, implicit signals. The data flywheel that turns production traffic into training and eval data.
Design principle: each layer should be independently bypassable. A request that needs no RAG skips step 1; a request that hits the cache skips steps 1–3. The architecture is a set of optional wrappers, not a mandatory pipeline.

03 Evaluation-driven development

Evaluation is the inner loop of AI engineering. You cannot improve what you cannot measure, and LLM outputs are hard to measure — so building the eval pipeline is typically the highest-leverage early investment.

Information-theoretic metrics

  • Entropy of a distribution p: the expected information content.
  • Cross entropy between true distribution p and model distribution q: measures how many bits the model needs.
  • Perplexity: the exponential of cross entropy — "how many tokens is the model effectively choosing between at each step."
  • Bits per character (BPC) / bits per byte (BPB): cross entropy normalized by character or byte count, enabling comparison across tokenizers.
cross entropy and perplexityH(p, q) = −∑x p(x) log q(x) PPL = exp(H(p, q)) = exp( −(1/N) ∑i log q(xi) )

Functional correctness and similarity

  • Exact match / pass@k: does the output exactly match (or functionally satisfy) the reference? Used in code generation (HumanEval), math, structured extraction.
  • Similarity to references: BLEU, ROUGE, BERTScore, semantic similarity. Useful when there is no single correct answer but a reference distribution exists.
  • Task-specific metrics: F1 for extraction, accuracy for classification, faithfulness for RAG (is the answer grounded in the retrieved context?).

LLM-as-a-Judge

  • Use a strong model to score or compare outputs against a rubric. Scales to thousands of examples where human eval cannot. Full details in LLM-as-a-Judge.
  • Limitations: position bias (prefers the first answer), self-preference (prefers its own outputs), verbosity bias, sensitivity to rubric wording. Calibrate against human judgments.
  • Comparative evaluation: pairwise comparison is more reliable than absolute scoring — ask "which is better?" rather than "rate 1–5."

The eval-first rule: before changing a prompt, a model, or a pipeline step, write the eval that would detect the improvement. If you cannot write the eval, you cannot tell whether the change helped.

04 Model selection & routing

No single model is optimal for all queries. Routing sends each request to the model that offers the best quality-per-dollar for that specific input.

  • Build vs. buy: use an API (fast start, pay per token, limited control) or self-host (high fixed cost, full control, lower marginal cost at scale). The decision depends on volume, latency requirements, data sensitivity, and customization needs.
  • Model selection workflow: (1) define evaluation criteria, (2) scan public benchmarks to shortlist, (3) run your own eval on your data, (4) compare on quality, cost, and latency together.
  • Routing by complexity: a small classifier or heuristic scores the input's difficulty. Simple queries go to a fast/cheap model; complex queries go to a frontier model. The router itself can be a small LLM, a logistic regression on input features, or a rule-based system.
  • Fallback chains: try the cheapest model first; if confidence is low or the output fails validation, escalate to a stronger model. Cost scales with difficulty, not with volume.
  • Model cascading: a generalization of fallback — route through a sequence of models of increasing cost, stopping when quality is sufficient.
  • Gateway pattern: a unified API layer in front of multiple providers. Handles routing, retries, rate-limit backoff, provider failover, usage logging, and key management. Examples: LiteLLM, Portkey, custom proxy.

The routing payoff: if 70% of queries are easy enough for a model that costs 10x less, routing saves roughly 63% of token spend with minimal quality loss — but only if the router itself is accurate.

05 Guardrails architecture

Guardrails enforce constraints that prompting alone cannot guarantee. The principle: deterministic rules wherever possible, model-based classifiers for everything else, defense in depth always.

Input guardrails

  • Injection screening: detect prompt-injection attempts — heuristic (regex for known patterns), embedding similarity to known attacks, or a fine-tuned classifier. See LLM Security for the attack taxonomy.
  • Scope enforcement: reject or redirect off-topic queries before they consume tokens. A topic classifier or embedding-based similarity check against allowed domains.
  • PII detection: scan inputs for personal data (names, emails, SSNs) and redact, mask, or reject before the data reaches the model or logs.

Output guardrails

  • Schema validation: enforce structured output via JSON schema, regex, or grammar-constrained decoding. Deterministic and cheap — always the first check.
  • Policy compliance: a content classifier checks for prohibited content, brand-safety violations, or harmful advice. Can be a dedicated small model or a rule set.
  • Citation and grounding: verify that claims in the output are supported by retrieved context. Reduces hallucination risk.
  • PII leakage: scan outputs for PII before returning to the user — the model may reproduce training data or user data from context.

Design principles

  • Deterministic before model-based: regex, schema checks, and allow-lists are fast, cheap, and predictable. Use model-based classifiers only for things that cannot be expressed as rules.
  • Defense in depth: layer input and output guardrails — catching at input is cheaper (avoids a model call), but output checks catch failures the input filter missed.
  • Fail safely: when a guardrail fires, return a graceful fallback (not a raw error), log the event, and alert if frequency spikes.
  • Budget guardrails: cap tokens per request, spend per user, and loop iterations per agent run. These are operational guardrails, not content guardrails, and they prevent runaway costs.
The layering rule: a guardrail in the prompt is a suggestion. A guardrail in the post-processing code is a rule. A guardrail enforced by the gateway before the model is ever called is a guarantee.

06 Caching strategies

LLM calls are expensive and often repetitive. Caching converts repeat or near-repeat queries from a cost problem into a latency win.

  • Exact-match caching: hash the full prompt (system + user + parameters); return the cached response on a hit. Simple, zero risk of wrong matches, and effective when the same query recurs (e.g., common customer questions).
  • Semantic caching: embed the query, search a vector store for cached queries above a cosine-similarity threshold, return the cached response. Catches paraphrases but introduces a false-positive risk — a query that sounds similar but means something different.
  • KV cache reuse (prompt caching): when multiple requests share a long system prompt or document prefix, cache the key-value states for that prefix so each new request only processes the unique suffix. Offered by API providers (e.g., cached tokens pricing) and self-hosted inference engines.
  • Cache invalidation: the hard part. Invalidate on: model version change, system-prompt change, retrieved-document update, time-based expiry. Semantic caches also need similarity-threshold tuning — too loose and stale answers slip through.
  • Cache hit rate drivers: traffic concentration (few queries repeated often), prompt stability (infrequent system-prompt changes), and query normalization (lowercasing, whitespace stripping) all improve hit rates.

07 Observability & monitoring

If you cannot see what the system is doing at the call level, you cannot debug it, cost-control it, or know when it degrades. LLM observability is the operational backbone of AI engineering.

  • Tracing LLM calls: log every call with: prompt (or hash), completion, model used, token counts (input/output), latency (TTFT, total), cost, temperature, and any tool calls. A trace ID links calls within one user request.
  • Chain and agent tracing: for multi-step pipelines, log the full DAG — which steps ran, in what order, what each produced, and where the pipeline branched or retried. Frameworks like LangSmith, Arize, and Braintrust provide this.
  • Token usage and cost tracking: aggregate by user, endpoint, model, and time window. Alert on sudden spikes (a runaway agent loop, a prompt that grew unexpectedly, a cache miss storm).
  • Latency tracking: measure time-to-first-token (TTFT), tokens-per-second, and end-to-end latency. Separate model latency from orchestration overhead. See model acceleration for serving optimization.
  • Quality monitoring: run lightweight auto-evals on a sample of production traffic — a small LLM judge scoring helpfulness, or a classifier detecting refusals, hallucination markers, or off-topic responses.
  • Drift detection: monitor input distribution (topic shift, query length, language mix) and output distribution (sentiment, refusal rate, avg response length). Drift signals that the eval set may no longer represent production. Cross-link: monitoring and drift.
  • Alerting rules (examples): cost per hour exceeds 2x baseline; p95 latency exceeds SLA; refusal rate jumps above threshold; error rate from a provider spikes.
The minimum viable stack: structured logging of every LLM call (prompt hash, tokens, latency, cost) + a dashboard that shows cost and latency over time + an alert on cost spikes. Everything else is incremental.

08 User feedback & the data flywheel

The highest-value data in an AI application is production user feedback — it is on-distribution, labeled by intent, and free. The flywheel: deploy → collect → evaluate → improve → redeploy.

Types of feedback

  • Explicit: thumbs up/down, star ratings, "was this helpful?", free-text corrections. High signal, low volume — most users do not click.
  • Implicit: copy/paste the answer (positive), regenerate (negative), edit the output (correction signal), abandon the conversation (negative), time-on-page, follow-up questions that rephrase the same intent (failure signal).
  • Conversational mining: extract preference pairs from chat logs — when a user rephrases and accepts the second answer, that is a (rejected, chosen) pair usable for DPO/RLHF. See preference optimization.

The flywheel

  • Step 1 — Collect: instrument the UI for explicit feedback; log implicit signals server-side. Tag every interaction with a trace ID so feedback connects to the full call chain.
  • Step 2 — Curate: filter noise, deduplicate, classify into failure modes (wrong answer, bad format, too slow, refused valid query, hallucinated). Build an eval set from the hardest cases.
  • Step 3 — Improve: fix the prompt, add a guardrail, update retrieved documents, add examples, or (if the pattern is systemic) fine-tune. Run the new version against the curated eval set before deploying.
  • Step 4 — Redeploy and A/B test: ship the improvement to a fraction of traffic, compare metrics, roll out or roll back. See A/B testing.
  • Compounding effect: each cycle tightens the distribution of queries the system handles well, surfaces new failure modes at the edges, and grows the eval set. Teams that run this loop weekly improve faster than teams that retrain monthly.
flywheel improvement rateΔquality ∝ feedback_volume · signal_quality · iteration_speed
The flywheel is the moat. The model is commoditized; the eval set and the feedback pipeline built from your users' data is not. Invest in instrumentation early — it compounds.

09 Cost optimization

Token spend is the cloud bill of AI engineering. The goal is not to minimize cost but to maximize quality per dollar — and to make cost visible and controllable.

  • Token budgeting: estimate tokens per request (input + output), multiply by expected volume, and model the monthly spend before launch. Track actual vs. budgeted daily.
  • Tiered model selection: route cheap queries to cheap models (Section 04). This is typically the single largest cost lever — if 70% of traffic can use a model at 1/10th the price, the bill drops by ~63%.
  • Caching: exact-match and semantic caching (Section 06) turn repeat queries from model calls into lookups. At high cache hit rates, the cost per query approaches zero for those queries.
  • Prompt compression: shorter prompts cost fewer input tokens. Techniques: remove redundant instructions, use concise few-shot examples, summarize retrieved documents before injection, use reference IDs instead of full text.
  • Batch vs. real-time: batch requests (where latency is not critical) can use lower-priority pricing tiers offered by some providers, sometimes at 50% discount.
  • Output length control: set max_tokens appropriately; instruct the model to be concise; use structured output to avoid verbose prose when a JSON object suffices.
  • Quantization and self-hosting: for high-volume applications, serving a quantized open model can be cheaper than API pricing. Break-even depends on volume, hardware cost, and engineering overhead. See model acceleration.
  • Fine-tuning for cost: a fine-tuned small model that handles your specific task well can replace a large general model at a fraction of the cost — especially for high-volume, narrow-domain applications.

10 Pitfalls & what to remember

Pitfalls

  • Shipping without evals. The most common failure: iterating on prompts by vibes instead of against a measured baseline. You cannot tell if you improved or regressed.
  • Over-engineering early. Adding agents, routers, and caches before understanding the basic failure modes. Start with a single prompt, a single model, and a good eval set.
  • Ignoring cost until the bill arrives. Token spend can grow 10x overnight when a feature goes viral or an agent loop runs away. Budget and alert from day one.
  • Guardrails only in the prompt. Telling the model "never reveal the system prompt" is a suggestion, not a guarantee. Enforce rules in code.
  • Evaluating on benchmarks, deploying on users. Public benchmarks measure general capability; your application has a specific distribution. Always eval on your own data.
  • Semantic caching with loose thresholds. Returning cached answers for queries that are similar but not equivalent. A paraphrase cache miss is invisible until a user gets a wrong answer.
  • Feedback without a loop. Collecting thumbs-up data that nobody looks at. Feedback is only valuable if it feeds back into the eval set and drives improvements.
  • Treating the model as fixed. Models get updated, deprecated, or repriced. Build abstractions (the gateway pattern) that let you swap models without rewriting the application.

What to remember

  • AI engineering is application engineering: the model is a component, the product is the system around it.
  • The 5-layer architecture: context → guardrails → router → cache → agents. Each layer is optional; add only when measured need demands it.
  • Evals are the inner loop. Build the eval pipeline before building the feature. If you cannot write the eval, you cannot tell whether the change helped.
  • Cost is a first-class metric. Report quality per dollar, not quality alone. A 2% quality gain at 3x cost is usually a loss.
  • The data flywheel — deploy, collect feedback, improve, redeploy — is the long-term moat. Invest in instrumentation early.
  • Neighbours: prompt engineering for the prompting techniques, context engineering for what fills the window, LLM fundamentals for the models themselves, LLMOps for the operational stack, agents for the agentic layer.
The whole page in one line: wrap the model in context, guardrails, routing, and caching; evaluate everything; collect feedback; optimize cost per quality — and iterate weekly.
