Structured & Constrained Generation

LLM output is stochastic — every sample is a roll of the dice over a vocabulary of tens of thousands of tokens. Downstream systems that need reliable structure (JSON, SQL, code, branded prose) cannot afford to hope the model formats things correctly. This page covers how to enforce structure at the token level: logits masking, grammar-constrained decoding, FSM-guided generation, style transfer, and the quality trade-offs that come with narrowing the beam.

01 Why constrain generation?

  • An LLM samples from P(token | context). With temperature > 0 and no intervention, any token with nonzero probability can appear — including tokens that break the JSON you asked for, insert a competitor's name, or produce an invalid SQL keyword.
  • Prompt engineering is necessary but not sufficient. You can instruct "respond in valid JSON" and that raises the probability of well-formed output, but it does not make it 1.0. Under distribution shift, long outputs, or low-probability paths, the model will occasionally violate the format. For mission-critical pipelines, "usually works" is not a spec.
  • Constrained decoding is deterministic. Instead of hoping the model obeys the format, you prevent non-conforming tokens from being sampled. The constraint acts at the logits level, before sampling, so the model physically cannot emit a disallowed continuation. The distribution is renormalised over the remaining valid tokens and generation proceeds normally.
  • Use cases: data extraction into typed schemas (medical records, legal clauses, financial reports), API-ready JSON/XML output, branding compliance (no competitor names, approved terminology only), code generation with syntax enforcement, SQL constrained to a database schema, and templated document generation where certain fields must come from a controlled vocabulary.
  • The spectrum ranges from soft (logit bias — nudge, don't force) through hard (logits mask — zero out forbidden tokens) to grammar (every generated prefix must be a valid partial parse of a formal grammar). Harder constraints give stronger guarantees but narrow the beam more.
One sentence: constrained decoding turns "the model usually produces valid JSON" into "the model can only produce valid JSON" — moving format correctness from probabilistic to deterministic.

02 Logits masking

Intercept the sampling stage and zero out probabilities of non-conforming tokens — the simplest and most flexible form of constrained decoding.

Logits masking in action Toggle the constraint to mask invalid tokens; remaining probabilities renormalise. Click Sample to pick a token.

How it works

  • At each decoding step the model produces raw logits z ∈ R|V| over the full vocabulary. A LogitsProcessor receives z and the tokens generated so far, checks each candidate continuation against the active rules, and sets z[t] = -inf for every token t that would violate a constraint. The softmax then assigns zero probability to masked tokens and renormalises over the rest.
  • Rules can be anything you can compute in a function: regex match on the decoded string so far, membership in a blocklist (competitor names, profanity), type checks (next token must start a number), or custom business logic.
  • Works with beam search: each beam is checked independently. Non-conforming beams are pruned; if all beams violate, the search backtracks one step and retries with stricter masking. After a maximum number of retries, return a refusal or fallback.
masking z'[t] = z[t] · 1[valid(t, context)] + (-∞) · 1[¬valid(t, context)] renormalised probability P'(t | ctx) = exp(z'[t]) / ∑t'∈V exp(z'[t']) (∑ only over valid tokens since exp(-∞) = 0)

The retry antipattern

  • The alternative to logits masking is the generate-check-retry loop: generate a full output, validate it, and if it fails, retry with a modified prompt. This is simpler to implement but far less efficient.
  • If the model produces valid output with probability p, the expected number of attempts is 1/p. At p = 90% you need 1.1 attempts on average — tolerable. At p = 50% you need 2 — costly. At p = 10% you need 10 — unacceptable. The retry loop is only viable when p > 90%.
  • Logits masking avoids this entirely: every generation is valid by construction. The cost is that you need access to the logits (local model or an API that exposes a logits processor hook), and the mask function must run fast enough per token.
retry cost E[attempts] = 1 / p p = P(output is valid) example p = 0.70 ⇒ E[attempts] ≈ 1.43 p = 0.30 ⇒ E[attempts] ≈ 3.33
Takeaway: logits masking is the token-level equivalent of input validation — prevent bad output at the source rather than catching it after the fact. Use it whenever you have logit access and a checkable rule.

03 Grammar-constrained decoding

Define an output schema — JSON Schema, BNF grammar, or regex — and the serving infrastructure constrains generation to conform, server-side.

  • The idea: instead of writing custom masking rules per use case, express the desired output format as a formal grammar and let the decoding engine enforce it. The engine compiles the grammar into an automaton, tracks the parse state at each step, and masks out tokens that would leave no valid completion.
  • JSON Schema mode is the most common variant. You provide a JSON Schema describing the desired output shape (types, required fields, enums, nested objects). The engine ensures every generated token is part of a string that will parse as valid JSON conforming to that schema. Supported by major API providers: OpenAI's response_format: {type: "json_schema", json_schema: {...}}, and Anthropic's tool use with input schemas.
  • BNF / EBNF grammars give full control. llama.cpp supports GBNF (a BNF variant) that can describe any context-free language — JSON, SQL subsets, custom DSLs. The grammar is compiled into a pushdown automaton that runs alongside generation.
  • Regex constraints force the output to match a regular expression, compiled to an FSM (see §06). Libraries like outlines support this natively.
  • Trade-off: more constraints = fewer valid tokens at each step = narrower beam. If the constraint is very tight (e.g., enum with 3 values), the model is basically a classifier with extra steps. If the constraint is too loose (any valid JSON), you get syntactic correctness but no semantic guarantees. The sweet spot is a schema tight enough to be useful downstream but loose enough that the model's distribution still has room to express quality.

04 Structured output formats

Each output format has different constraint mechanics. JSON needs bracket matching; SQL needs grammar compliance; code needs indent tracking.

  • JSON: the workhorse. Constraints enforce bracket/brace matching, correct string quoting, comma placement, and type conformance (string vs number vs boolean vs null). With a schema, additionally enforce field names, required fields, enum values, and nesting depth. JSON mode (without schema) guarantees syntactically valid JSON but not semantically correct output — the fields might be named wrong or the values meaningless.
  • XML / YAML: XML needs tag matching and attribute quoting; YAML needs consistent indentation. Both are less commonly constrained at the token level than JSON because their grammars are more complex, but template-based approaches (generate into predefined slots) work well.
  • Function calling / tool use: the model outputs a structured call — function name + arguments as a JSON object conforming to a per-tool schema. The API provider enforces the schema; the caller validates argument values. This is the standard pattern for agent tool invocation.
  • SQL generation: constrain to valid SQL grammar plus the target database's schema (table names, column names, types). Can be done with GBNF grammars or by fine-tuning on the schema and validating with a parser post-generation. Text-to-SQL systems often use constrained decoding to avoid hallucinating table or column names.
  • Code generation: syntax enforcement for a target language. Python needs indent tracking (a pushdown automaton tracking scope depth); languages with braces need brace matching. In practice, most code generation relies on model quality plus post-generation parsing rather than token-level constraints, because the grammar of a full programming language is large and slow to enforce per-token.
  • Markdown / templated prose: a lightweight constraint — force heading structure, bullet format, or section markers. Often done with template-based generation (§08) rather than grammar constraints.

Takeaway: match the constraint mechanism to the grammar class. Regular expressions for flat formats, context-free grammars for nested structures, and templates for lightly structured prose.

05 Style transfer for LLMs

Constraining what the model says is format enforcement. Constraining how it says it is style transfer — tone, register, sentence length, terminology, voice.

  • Few-shot style examples. The simplest approach: provide input→output pairs that demonstrate the target style. The model learns the mapping in-context. Works well when you have paired examples (original text + rewritten version). The number of examples needed depends on how distinctive the style is — a highly unusual register may need 5–10 examples; a minor tone adjustment may need 1–2.
  • Reverse neutralisation. When you have only reference content in the target style (not paired examples), a two-step approach works: (1) instruct the model to rewrite the reference into a neutral, plain style, producing synthetic pairs (neutral, styled); (2) use those pairs as few-shot examples to teach the style mapping. The model never sees the original input — it learns the style delta from the synthetic pairs.
  • Content optimisation via style. A/B test multiple style variants of the same content (email subject lines, ad copy, product descriptions) and pick the best-performing one. The key insight: you do not need to identify which stylistic factors (formality, urgency, length, emoji use) made the difference. You simply generate variations, test them, and keep the winners. The LLM is both the variation generator and, optionally, the predictor of which variation will perform best.
  • Style as a constraint. Style rules can be enforced at different levels: (1) prompt-level — "write in a formal, concise tone" in the system prompt; (2) example-level — few-shot demonstrations; (3) logit-level — boost/suppress tokens associated with a style (e.g., suppress casual contractions); (4) post-generation — a rewrite pass or classifier that flags off-style output.
  • Limitations. Style transfer is inherently soft — there is no grammar of "formal English" to enforce at the token level. The model's style compliance degrades with output length (style drift), with conflicting instructions, and when the content itself pushes toward a different register. Evaluation is subjective and best done with human raters or a calibrated LLM-as-a-Judge.
Takeaway: style transfer is the soft cousin of constrained decoding — use paired examples when available, reverse neutralisation when not, and A/B testing when you care about downstream outcomes more than stylistic theory.

06 Constrained decoding algorithms

The engine behind grammar-constrained generation: finite automata, pushdown automata, and constrained beam search.

FSM-guided generation

  • For regular languages (regex, enum lists, fixed patterns): compile the constraint to a deterministic finite automaton (DFA). At each decoding step, the current DFA state determines which tokens are valid — a token is valid if the characters it decodes advance the DFA to a non-dead state. Mask everything else.
  • The DFA state is updated after each token. Because BPE tokens can represent multiple characters, the transition may cross several DFA states in one step. The library precomputes, for each (DFA state, token) pair, whether the token leads to a live state — this lookup table makes per-token masking fast.
  • This is the core of the outlines library: compile a regex or JSON Schema (via a regex representation of valid JSON strings for each schema) into a DFA, build the token mask table, and use it as a logits processor. Generation speed overhead is small because the masks are precomputed.

Pushdown automata for context-free grammars

  • Nested structures (JSON objects inside arrays inside objects, recursive SQL subqueries, matched parentheses) require a pushdown automaton (PDA) — an FSM plus a stack. The stack tracks nesting depth and expected closing tokens.
  • At each step, the valid token set depends on both the current automaton state and the top of the stack. For example: if the stack says "inside an array, inside an object, two levels deep", then ] closes the array, , continues it, but } is invalid at this level.
  • llama.cpp's GBNF parser runs a PDA alongside generation. The grammar rules are compiled into a parse table, and each token is checked against the current parse state before being allowed.

Constrained beam search

  • Beam search with constraints scores each candidate continuation as a combination of the language model score and a constraint penalty:
beam score score(y1:t) = log PLM(y1:t) + λ · constraint_score(y1:t) hard constraint constraint_score = 0 if valid, -∞ if invalid (equivalent to masking) soft constraint constraint_score = -α · violations(y1:t) (penalise but don't forbid)
  • Hard constraints prune beams that violate the grammar. Soft constraints penalise violations, allowing the model to occasionally break a rule if the language model score is high enough — useful for style constraints where occasional deviation is acceptable.
  • Speculative constrained decoding: draft several tokens cheaply (small model or heuristic), then verify the draft against the constraint automaton in one pass. Valid prefixes are accepted; the first invalid token triggers rejection and re-generation from that point. This amortises the per-token constraint checking cost across a multi-token draft. Compatible with speculative decoding for speed.
Takeaway: FSM for regular constraints, PDA for context-free grammars, constrained beam search for combining model quality with rule compliance. The constraint automaton runs alongside decoding and determines the valid token set at each step.

07 Token healing & bias

BPE tokenisation creates subtle boundary problems for constrained generation. Token healing and logit bias are the fixes.

Token boundary issues

  • BPE tokenisation is context-dependent: the string {"name" might be tokenised as ["{", "\"name\""] or ["{\"", "name", "\""] depending on surrounding context. When a prompt ends mid-token (e.g., the system prompt ends with { and the model should continue with "name":), the model's BPE merges may not align with the constraint grammar's expectations.
  • Token healing addresses this by backing up to the last clean token boundary before starting constrained generation. The backed-up characters are prepended to the constraint automaton's initial state, ensuring the first generated token is compatible with both the BPE encoding and the grammar.
  • Without token healing, constrained generation can deadlock: the grammar expects " as the next character, but the model's BPE vocabulary has no token that starts with " in this context (because {" is a single token). The constraint masks out all tokens, and generation fails.

Logit bias

  • Logit bias adds a fixed value to specific token logits before softmax — a soft version of masking. Positive bias encourages a token; negative bias discourages it. Unlike masking (which sets probability to exactly 0), bias adjusts the probability smoothly.
  • Use cases: suppress specific words (competitor names, profanity) with a large negative bias (e.g., -100), or encourage specific tokens (brand terms, preferred phrasings) with a moderate positive bias (e.g., +5).
  • APIs that expose logit bias typically take a dictionary of {token_id: bias_value}. The bias is added before temperature scaling.
logit bias z'[t] = z[t] + bias[t] bias[t] ∈ R (0 for unbiased tokens) hard mask as limit limb→-∞ softmax(z + b · et)[t] = 0 (masking is the extreme of bias)

Temperature + constraints

  • Low temperature + hard constraints = most predictable output. Low temperature concentrates probability mass on the top tokens; hard constraints remove invalid ones. The combination makes the model nearly deterministic when the constraint is tight.
  • High temperature + hard constraints can produce surprisingly creative output within the constraint boundary — useful for brainstorming within a fixed schema, generating diverse valid JSON examples, or exploring the space of valid completions.
  • Temperature is applied before masking in most implementations: softmax(z / T) then mask. This means temperature affects the relative ranking of valid tokens but not which tokens are valid.
Takeaway: token healing prevents BPE boundary deadlocks, logit bias gives soft control, and temperature tunes diversity within the constraint boundary. All three interact — test the combination, not each in isolation.

Server-side / inference engines

  • vLLM supports guided decoding via outlines integration — pass a JSON Schema or regex with the request and the engine applies FSM-guided masking during generation. No client-side token manipulation needed.
  • TGI (Text Generation Inference) supports grammar-constrained generation with JSON Schema and regex constraints.
  • llama.cpp supports GBNF grammars natively — pass a grammar file and every generated token is checked against the parse state. Runs locally, no API needed.

Cloud API structured outputs

  • OpenAI: response_format: {type: "json_schema", json_schema: {name: "...", schema: {...}}} enforces JSON Schema compliance. Also supports json_object for unschema'd JSON. Function calling enforces per-tool schemas.
  • Anthropic: tool use with input_schema enforces JSON Schema for tool arguments. No standalone JSON mode as of late 2026 — structured output is routed through tool use.
  • Pattern: define a schema (Pydantic model, JSON Schema, or tool definition), pass it to the API, and the provider enforces it server-side. The instructor library wraps this pattern with validation and automatic retries for all major providers.

Template-based generation

  • The guidance library pioneered the pattern of interleaving fixed template text with generated segments. The template defines structure; generation fills slots. Example: {"name": "{{gen 'name' stop='"'}}", "age": {{gen 'age' pattern='[0-9]+'}}}. The fixed parts (braces, keys, colons) are written directly; only the values are generated, with per-slot constraints.
  • This avoids the problem of the model needing to "learn" JSON syntax in every generation — the structure is deterministic, and the model's capacity is spent entirely on the content.
Takeaway: for cloud APIs, use the provider's native schema mode (or tool use). For local models, use outlines (FSM) or llama.cpp (GBNF). For the template pattern, use guidance. For Pydantic integration with any provider, use instructor.

09 Quality vs constraint trade-off

Every constraint narrows the beam. The question is how much quality you lose for the guarantee you gain.

  • The fundamental trade-off: the model was trained to predict the next token over the full vocabulary. Constraining it to a subset changes the distribution. If the constraint aligns with what the model would have produced anyway (e.g., forcing JSON for a model fine-tuned on JSON), the quality loss is negligible. If the constraint fights the model's natural distribution (e.g., forcing SQL syntax from a model that rarely saw SQL), fluency degrades.
  • Measuring quality degradation: compare constrained vs unconstrained generation on the same prompts. Metrics: perplexity increase (how much more "surprised" the model is by its own constrained output), human preference scores (do raters prefer the unconstrained version?), and downstream task accuracy (does the constrained output actually perform better in the pipeline, even if less fluent?).
  • The paradox: constrained output often performs better downstream even when it is less fluent, because the downstream system can parse it reliably. A slightly awkward but parseable JSON response beats an eloquent but broken one.
  • Mitigation strategies:
  • (a) Use the minimum necessary constraints. Do not constrain what does not need constraining. If only the top-level structure must be JSON, let the string values inside be free-form.
  • (b) Prefer schema-level over token-level constraints when possible. A JSON Schema constraint lets the model choose among all valid JSON strings of that shape; a regex constraint on individual fields is tighter and may be unnecessarily restrictive.
  • (c) Fine-tune on constrained output. If your model will always generate in a specific format, include that format in the fine-tuning data. This aligns the model's distribution with the constrained space, reducing the quality gap. Models fine-tuned on JSON output lose little quality when constrained to JSON.
  • (d) Warm up with examples. Few-shot examples in the target format (prompt engineering) shift the model's distribution toward the constrained space before the constraint even kicks in, reducing conflicts.
quality gap ΔQ = Qunconstrained - Qconstrained ideal ΔQ → 0 when model distribution aligns with constraint space worst case ΔQ is large when constraint space ∩ model's high-probability region is small
Takeaway: constraints trade fluency for reliability. Minimise the trade-off by constraining only what matters, fine-tuning on the target format, and measuring downstream performance — not just generation quality in isolation.

10 Pitfalls & recap

Common mistakes and the one-line summary of each technique.

Pitfalls

  • Over-constraining kills quality. Forcing the model into a very narrow output space (e.g., only 3 possible responses) wastes the model's generative capacity and produces robotic output. Use the lightest constraint that meets the requirement.
  • Under-constraining fails downstream. JSON mode without a schema guarantees syntax but not semantics. The consumer crashes on an unexpected field name or type. Always validate generated output even with constraints — constraints guarantee syntax, not content.
  • Schema drift. The schema in the prompt, the schema in the constraint, and the schema the consumer expects can diverge over time. Version all three together and test their alignment.
  • Token boundary misalignment. Without token healing (§07), constrained generation can fail silently or deadlock at BPE boundaries. Use a library that handles healing, or test edge cases explicitly.
  • Assuming JSON mode = correct JSON. "Syntactically valid" does not mean "semantically correct". The JSON might have the right braces and quotes but contain hallucinated values, wrong types in string fields, or missing data. Structural correctness is necessary, not sufficient — see Hallucination & Factuality.
  • Not validating even with constraints. Constraints can have bugs. The grammar might not cover an edge case. The schema might be looser than intended. Always validate generated output with the same validator your consumer uses.
  • Latency impact of complex grammars. A large BNF grammar (full SQL, full Python) requires expensive per-token parse-state computation. For latency-sensitive applications, simplify the grammar or use a draft-and-verify approach. FSM-based approaches (regex, JSON Schema) are fast because the mask is precomputed; PDA-based approaches (full CFGs) are slower.
