Context Engineering

A model's behaviour is set by what's in its context window. Context engineering is the discipline of deciding — and budgeting — exactly what goes in there: instructions, examples, retrieved knowledge, tools, and memory.

LLMs & Generative AI Prompting LLM systems

01 Beyond prompt engineering

Prompt engineering tweaks the wording of one instruction. Context engineering designs the whole information payload the model sees at inference.

  • An LLM has no state between calls — the context window is the entire interface. Everything it "knows" for this turn is whatever you packed in. Weights supply general capability; context supplies the situation.
  • Because of in-context learning, changing the context changes behaviour with no retraining — which is exactly why getting the context right is so high-leverage. A context change ships in seconds; a fine-tune ships in days.
  • It spans more than a prompt string: system instructions, few-shot examples, retrieved documents, tool definitions and results, conversation history, and scratchpad/memory. Most of those are assembled by code at request time, not typed by a human — which makes context a piece of software, with versions, tests and regressions.
  • The job is therefore closer to information retrieval and caching than to copywriting: select, order, compress, cache, and evaluate.
One sentence: context engineering = assembling the right tokens, in the right order, within a finite budget, so the model can do the task.

02 The context window is a budget

Every component competes for a fixed number of tokens. Overspend and something gets truncated. Drag the controls and watch the budget fill.

Context window budget packer Components fill the window in order; past the capacity line, tokens are truncated

Three currencies, not one

The token count is only the visible cost. Behind it sit two others: compute and KV-cache memory. Prefill (reading the prompt) is quadratic in length because every token attends to every earlier one; decoding is linear per token but must hold the whole key/value cache in GPU memory, which grows linearly with context and is often the real limit on batch size.

what a long context actually costsprefill compute ∝ n² decode compute per token ∝ n price ∝ n kv-cache memory for n tokensmemKV = 2 · L · n · hkv · dhead · bytes (2 = keys + values · L layers · hkv kv-heads)
  • h_kv is why grouped-query and multi-query attention exist: shrinking the number of KV heads shrinks the cache linearly, which is what makes long contexts servable at all.
  • Modern windows are large, but never free — long contexts cost more, run slower, and dilute attention across more candidates. The budget is real even at 200k tokens.
  • A useful discipline: give every component an explicit token allowance and a truncation rule, rather than letting whichever section is generated last silently overflow. See Context-Length Extension for how the window gets big in the first place.
Takeaway: budget in tokens, but reason in three currencies — tokens billed, compute burned, and cache memory held. Only the first is on the invoice.

A useful frame: instructions say how, examples show how, retrieval supplies what, tools extend what it can do, memory supplies state. If a block doesn't answer one of those, cut it.

04 Prompting techniques

The classic levers that still live inside the context.

  • Zero-shot vs few-shot: describe the task, or include input→output examples and let the model infer the pattern. Examples win when the output format is idiosyncratic or the label boundary is hard to state in words; they lose when they are long enough to crowd out retrieval. Cover the edge cases and the label distribution, not just the easy middle.
  • Chain-of-thought: ask for step-by-step reasoning to unlock multi-step tasks (see Reasoning in LLMs). On reasoning-trained models this is often redundant — they already think — so explicit CoT instructions can just add latency.
  • Role & format: set a persona, and specify the exact output shape (schema, headings, field names) — constrain ambiguity before it becomes a parsing bug.
  • Delimiters & structure: fence sections (instructions / documents / query) with unambiguous markers so the model never confuses data for commands. Consistent tags also make the context diffable and testable — and are the first line of defence against prompt injection.
  • Positive over negative: "answer only from the documents" beats "don't make things up." Rules stated as behaviours are easier to follow than rules stated as prohibitions.
Takeaway: prompting is now a component of context engineering, not a rival to it. Wording matters least when the right facts are present and most when they aren't.

05 Bringing knowledge in

Most of the "what" in the window is retrieved, not written by hand.

  • RAG is the workhorse: embed the query, search a vector store, drop the top chunks into the context — grounding the answer and sidestepping the knowledge cutoff.
  • Retrieval quality is context quality: bad chunks waste budget and mislead. A cheap first-stage retriever pulling ~50 candidates followed by a cross-encoder re-ranker that keeps 3–5 is the standard shape — it spends tokens only on what survives a second, sharper look.
  • Hybrid retrieval (dense embeddings plus lexical/BM25) catches what pure vectors miss: exact identifiers, error codes, rare product names.

Chunking is a context decision

  • Chunk too small and each piece loses the context that makes it interpretable; too large and every hit drags in filler you pay for. Splitting on structure (headings, sections, function boundaries) beats splitting on a fixed character count.
  • Two patterns fix most of it: overlap between adjacent chunks so a fact spanning a boundary survives, and retrieve small, expand large — match on a precise sentence, then send its surrounding section to the model.
  • Always carry provenance (title, section, date, URL-free identifier) into the context. It lets the model cite, lets you debug, and lets conflicting sources be ranked by recency or authority.
  • Tool results — API calls, database queries, code execution — are another channel of fresh, grounded context fed back into the window, and need the same discipline: truncate, summarize, label.
Takeaway: retrieval decides what is in the window and chunking decides how legible it is. Both are worth more tuning than the prompt wrapped around them.

06 Memory & state

Conversations and agent runs outgrow the window — so we compress, externalize, or drop.

The three tiers

  • Short-term: the last few turns kept verbatim. Cheap, exact, and where nearly all the relevant detail actually lives.
  • Compaction / summarization: older history distilled into a running summary so it keeps informing the model without eating the budget. Trigger it on a threshold (say 70% of window), summarize the oldest span, and always keep the most recent turns raw — summarizing what just happened is where the worst information loss occurs.
  • Long-term: facts written out to an external store and retrieved when relevant. Once memory is external, memory becomes a retrieval problem — with all the same questions of recall, precision, staleness and conflict.

Externalizing state

  • A scratchpad — a file, a to-do list, a structured plan the agent rewrites each turn — keeps state out of the transcript. It survives compaction, is cheap to re-read, and is inspectable by a human.
  • Prefer pointers over payloads: keep an identifier and one-line description of a large artefact in context, and fetch the body only when a step needs it.
  • Memory needs a write policy as much as a read policy — what gets promoted to durable memory, what expires, and what happens when a new fact contradicts an old one. Without expiry, long-lived memories quietly poison later runs.
  • This matters most for agents, whose multi-step runs would otherwise blow the window in a few iterations.
Takeaway: the window is working memory, not storage. Anything that must survive belongs in a file, a database, or a summary you deliberately maintain.

07 Ordering & "lost in the middle"

Where you put something in the window matters as much as whether it's there.

  • Retrieval accuracy as a function of position is famously U-shaped: models use information at the start and end of a long context far more reliably than the same information buried in the middle. The effect persists in models whose windows are nominally long enough to hold everything.
  • So: put the most important instructions and the highest-relevance chunks near the edges. A common layout is stable instructions first, evidence in the middle ordered best-outward, and the actual question last.
  • Compress before you pad — a tight, relevant context beats a long, noisy one. More tokens is not more signal; every extra distractor is another candidate attention has to discount.
  • Re-ranking plus putting top results at the edges is the cheapest reliability win in a RAG pipeline — no retraining, no new infrastructure.
  • Related failure: context rot — accuracy degrades gradually as a window fills, even below the nominal limit. Treat "fits in the window" as a necessary, not sufficient, condition. Context-Length Extension covers why usable length trails advertised length.
Takeaway: a long window is a capacity, not a promise. Position is a free lever — use it before reaching for a bigger model.

08 Caching & the cost of re-reading

The same prefix is re-read on every turn. Caching its key/value tensors turns that quadratic re-read into a lookup.

How prefix caching works

  • Prefill computes a key/value pair per token per layer. If the next request begins with the byte-identical prefix, those tensors are still valid and can be reused instead of recomputed — cached reads are dramatically cheaper and faster than fresh prefill, at the cost of a small premium to write the cache and a short time-to-live.
  • The rule that follows: order the context stable → volatile. System prompt, tool schemas and long reference documents go first; retrieved chunks next; the user's new turn last. One edited character early in the prompt invalidates everything after it.
  • This puts genuine tension on §07: recency wants the important thing last, caching wants the stable thing first. The usual resolution is to keep the bulk stable and cheap, and re-state the few critical instructions in a short block right before the question.
  • Rotating a timestamp, a session id, or a shuffled example order into the system prompt is the classic own-goal — it silently destroys every cache hit.
why layout dominates cost in multi-turn usecostuncached ≈ T · nprefix costcached ≈ nprefix + T · ndelta (T turns, ndelta = new tokens per turn)
Takeaway: in a multi-turn or agentic loop, prompt layout is a performance decision. Sort by volatility and most of the bill disappears.

09 Tools, schemas & the agent loop

In an agent, the context is not written once — it is rewritten on every iteration of plan → act → observe.

Tool definitions are prompt

  • A tool schema — name, description, typed parameters — occupies real tokens and is read as instructions. Names and descriptions do most of the routing work, so vague or overlapping descriptions cause tool-selection errors that look like reasoning failures.
  • Fewer, sharper tools beat many overlapping ones. When the set grows large, retrieve the relevant tools per query rather than shipping the whole catalogue every turn — the same selection problem as document retrieval. Packaging instructions, schemas and resources as loadable units is the idea behind agent skills.
  • Structured outputs close the loop on the other side: constrained decoding against a schema masks invalid tokens at each step, so the result parses by construction. That converts a class of retry loops into a guarantee — and keeps tool results machine-readable when they are fed back in.

The loop is where context explodes

  • Every observation — a search result, a file, a stack trace — is appended, so context grows monotonically while the useful fraction shrinks. Truncate and summarize tool output at the boundary, before it enters the transcript.
  • Sub-agents are a context tactic as much as an architecture: give a child a clean window and a narrow brief, and return only its conclusion to the parent. Isolation stops one noisy sub-task from polluting the whole run. See Agents and Agentic Design Patterns.
  • Treat every tool result as untrusted data. Retrieved pages and API responses can carry instructions; fence them and never grant them the authority of the system block.
Takeaway: in agent loops, context management is the control loop. What you choose to append, summarize or discard each turn determines whether the run converges or drowns.

10 Evaluating context strategies

Context changes are code changes. They need a test suite, not a vibe check.

  • Separate the two failure sources. Score retrieval on its own (recall@k, precision, whether the answer-bearing chunk is present) before scoring the answer. If the fact never made it into the window, no prompt fix will help.
  • Fix the seed set. A few hundred representative prompts with expected answers or rubric criteria, versioned alongside the context template, so any edit can be A/B'd. Grade with a rubric-based model judge plus spot checks — see LLM-as-a-Judge.
  • Ablate. Drop one component at a time — the few-shot block, the summary, the last three chunks — and measure. Components that don't move the score are pure cost.
  • Probe position. Plant a needed fact at the start, middle and end of a filled window; the accuracy gap is your local "lost in the middle" curve and tells you where the good chunks belong.
  • Track cost and latency as first-class metrics next to quality, including cache-hit rate — most context wins are quality per token, not quality alone.

12 Pitfalls & what to remember

  • The context window is the interface — the model knows only what you pack in, and it's a finite budget in tokens, compute and KV memory.
  • Assemble, don't just prompt: instructions + examples + retrieval + tools + memory, each earning its tokens and each independently ablatable.
  • Order matters — edges over middle for attention, stable-before-volatile for caching. Reconcile the two deliberately.
  • Retrieval quality is context quality — hybrid search, re-rank, chunk on structure, carry provenance.
  • Manage state via compaction and external memory, with an explicit write-and-expire policy — especially for agents.
  • Longer is not better. Dilution, cost and latency all scale with length; a bigger window is the last resort, not the first.
  • Evaluate it like code: a fixed seed set, retrieval scored separately, ablations, and cost tracked next to quality.
