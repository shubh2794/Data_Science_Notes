Dataset Engineering for LLMs

Model performance depends as much on the data you feed as on the architecture you pick. This page covers building training and fine-tuning datasets for LLMs — data curation, quality filtering, synthetic data generation, deduplication, and data mixing — the full pipeline from raw crawl to tokenised batches.

01 Data-centric AI

  • The conventional ML loop iterates on the model (architecture, hyper-parameters, training tricks) while holding the data fixed. Data-centric AI flips this: hold the model fixed and iterate on the data — cleaning labels, removing noise, re-balancing domains, synthesising hard examples.
  • Both matter, but data improvements transfer across model sizes and architectures. A cleaned, deduplicated pre-training corpus benefits a 1B model and a 70B model alike; a better architecture only helps the checkpoint it ships in.
  • Benchmarks like DataComp (2023) make the shift explicit: contestants submit datasets, not models. The model, training recipe, and evaluation are locked — the only variable is which data you select from a fixed pool. Winners consistently beat the baseline by filtering and mixing, not by changing a single weight.
  • The organisational shift mirrors the technical one. Training runs now have dedicated data teams: data labellers, dataset creators, data quality engineers, and data tooling developers. Data curation is no longer a side-task on the way to training — it is a first-class role.
One sentence: improving the data is often higher-leverage than improving the model — and benchmarks that evaluate datasets, not models, prove it.

02 Data curation

What data you need depends on the training phase and the target behaviour.

Data by training phase

  • Pre-training needs raw tokens — web crawls, books, code repos, multilingual text. The format is simply long sequences of text, the objective is next-token prediction, and the main variable is what you include and how much.
  • Supervised fine-tuning (SFT) needs (instruction, response) pairs. Each pair teaches a target behaviour: a question and a correct answer, a task prompt and a tool call, a user message and a helpful reply. Format matters — single-turn or multi-turn chat, with system prompts, role tags, and tool-call schemas.
  • Preference alignment (RLHF / DPO) needs (instruction, chosen, rejected) triples. The model learns which of two responses is preferred — the signal is relative, not absolute. See Policy / Preference Optimization.

Curating for target behaviours

  • Training data should exhibit the behaviours you want. If you want chain-of-thought reasoning, include examples that reason step by step. If you want tool use, include action–observation pairs. If you want concise answers, include short, direct responses — not verbose essays.
  • Single-turn data (one instruction, one response) is simpler to collect and label. Multi-turn data (conversations with follow-ups, corrections, and context) teaches the model to track state across turns — essential for chat and agent loops.
  • Unlearning bad behaviours is as important as teaching good ones. If the model is arrogant, include humble examples. If it gives unsolicited advice, include examples that answer only what was asked. Preference data is especially useful here: chosen = appropriate, rejected = the bad habit.
Takeaway: pre-training wants volume, SFT wants demonstrations, alignment wants comparisons. In every phase, the data should look like the behaviour you want the model to produce.

03 Data quantity & scaling

  • More data generally helps, but with diminishing returns. Doubling the data does not halve the loss — the relationship is a power law.
  • Chinchilla scaling laws (2022) established a rule of thumb for compute-optimal training: the number of training tokens should be roughly 20 times the parameter count. A 7B model is compute-optimal at ~140B tokens; a 70B model at ~1.4T tokens.
  • Over-training: in practice, many teams train smaller models on far more tokens than compute-optimal (e.g. a 7B model on 1–2T tokens). The model is worse per training FLOP, but it is cheaper at inference — and inference cost dominates when you serve millions of requests. This is the Llama philosophy.
  • Data quantity by phase:
    Pre-training: trillions of tokens (1–15T is common as of 2024–2025).
    SFT: thousands to millions of examples (a few thousand high-quality examples can outperform millions of low-quality ones).
    Preference alignment: thousands to tens of thousands of comparisons.
chinchilla rule of thumb Dopt ≈ 20 × N N = parameter count, Dopt = compute-optimal token count power-law loss scaling L(D) ∝ D−α α ≈ 0.095 (more data → lower loss, but slowly)
Takeaway: pre-training needs trillions of tokens; SFT can get by with thousands of high-quality examples; and over-training small models past compute-optimal is a deliberate trade of training cost for inference savings.

04 Data quality signals

Not all data is worth training on. Quality signals separate signal from noise.

  • Length heuristics. Documents that are too short (a few words) carry almost no information. Documents that are too long (hundreds of pages of boilerplate) are often verbose, repetitive, or machine-generated. Keep the middle of the distribution.
  • Perplexity filtering. Score each document with a reference language model. High perplexity means the text is unusual — could be noise, encoding errors, non-natural-language content, or a foreign language the reference model was not trained on. Very low perplexity can indicate repetitive, formulaic text. Filter at both ends.
  • Classifier-based quality scoring. Train a binary classifier (e.g. a fastText model) on a small set of high-quality text (curated references, textbooks, well-edited articles) versus random web text. Score the full corpus and keep the top fraction. This is the core of the approach used in many major pre-training datasets.
  • Decontamination. Remove any text that overlaps with test/benchmark data from the training set. Without this, evaluation scores are inflated — the model has memorised the answers, not learned the skill. Use n-gram overlap to flag contamination; see Model Evaluation.
  • Domain balancing. Ensure representation across domains — not just web text, but also code, math, science, conversation, and multilingual sources. Under-representation of a domain means the model will be weak there; over-representation skews the model's default style and knowledge.
perplexity filter PPL(x) = exp( −(1/T) · ∑t=1T log p(xt | x<t) ) keep x if PPLlo < PPL(x) < PPLhi classifier filter keep x if P(high-quality | x) > τ τ tuned on held-out quality sample
Takeaway: filter by length, perplexity, classifier score, and benchmark contamination. Each signal catches a different kind of junk — use them together.

05 Deduplication

Duplicate data degrades training: it causes memorisation, skews the distribution, and wastes compute.

  • Why dedup matters. If the same passage appears 100 times, the model memorises it verbatim instead of learning the underlying pattern. The distribution shifts toward the duplicated content, and rare-but-important data gets proportionally down-weighted.
  • Exact dedup — hash every document (or paragraph, or n-gram) and remove exact matches. Fast and lossless: if the hashes match, the content is identical. Use SHA-256 or similar; normalise whitespace first.
  • Near-dedup: MinHash / LSH. Many duplicates differ by a header, a date, or minor edits. MinHash estimates Jaccard similarity between sets of n-grams; Locality-Sensitive Hashing (LSH) groups similar documents into the same bucket for efficient pairwise comparison. This catches near-duplicates that exact hashing misses.
  • Suffix array dedup. Build a suffix array over the concatenated corpus and find repeated substrings. This catches substring-level duplication — the same paragraph copied into hundreds of different pages — without requiring document-level similarity.
  • Granularity. Dedup at multiple levels: document (remove whole duplicate pages), paragraph (remove copied paragraphs within otherwise unique documents), and n-gram (remove repeated phrases). Each catches different duplication patterns.
  • When to dedup. For pre-training: before tokenisation, on the raw text. For synthetic data: after generation, to catch cases where the generator produced near-identical outputs. Cross-dataset dedup: always check training data against eval/benchmark data to prevent contamination.
jaccard similarity J(A, B) = |A ∩ B| / |A ∪ B| A, B = sets of n-grams from two documents minhash estimate P( min h(A) = min h(B) ) = J(A, B) h = random hash function; use k hash functions, average agreement lsh threshold P(candidate pair) ≈ 1 − (1 − Jr)b b bands × r rows per band; tune b, r for target similarity threshold
Takeaway: exact hashing catches copies, MinHash/LSH catches near-copies, suffix arrays catch repeated substrings. Dedup at every granularity, and always cross-check against eval data.

06 Synthetic data generation

Use a stronger model to generate training data for a weaker model — or for yourself.

  • The core idea: generating training data with a capable model is often cheaper and faster than human annotation. A frontier model can produce thousands of instruction-response pairs in hours; human annotators take weeks.
  • Self-Instruct. The model generates its own instruction–response pairs from a small seed set, bootstrapping a large dataset from minimal human input. The seed set defines the style and difficulty; the model extrapolates.
  • Evol-Instruct. Start with simple instructions and iteratively evolve them into more complex ones — adding constraints, nesting sub-tasks, requiring multi-step reasoning. This is how WizardLM-style datasets are built: breadth evolution (new topics) and depth evolution (harder variants).
  • Distillation via generation. A strong teacher model generates outputs; a smaller student model learns to imitate them. The student's training data is the teacher's outputs. This is knowledge distillation without access to the teacher's weights — only its generations.
  • Risks:
    Model collapse — training on the model's own outputs (or outputs from a model trained on synthetic data) can cause progressive degradation across generations, as the tails of the distribution are trimmed and the model converges to a narrower, blander distribution.
    Amplified biases — if the teacher has biases, the synthetic data inherits and may amplify them.
    Hallucinations in training data — the teacher may generate plausible but false content, which the student then treats as ground truth.
  • Quality control. Never use raw synthetic data without filtering. Common gates: LLM-as-judge scoring (see LLM-as-a-Judge), rule-based checks (format, length, language), human review on a sample, and deduplication of near-identical generations.
Takeaway: synthetic data is a force multiplier, but it must be filtered. Without quality gates, you get model collapse, amplified bias, and hallucinated training labels.

07 Data mixing

The mix ratio — how much web text, code, math, books, and conversation — is one of the most consequential hyper-parameters in pre-training.

Why the mix matters

  • Too much code and the model talks like a compiler — terse, unsocial, over-structured. Too little code and it cannot program. Too much conversation data and it becomes chatty and shallow on technical questions. The ratio shapes the model's personality, strengths, and weaknesses.
  • Domain weighting strategies:
    Proportional — weight each domain by its share of the raw corpus. Simple but lets web text dominate.
    Upweight high-quality — give books, textbooks, and curated sources higher weight than their raw size suggests. This is the most common adjustment.
    Curriculum learning — start with easy/general data and gradually increase the fraction of hard/specialised data (code, math, reasoning) as training progresses.
  • Epoch-level vs batch-level mixing. Epoch-level: train on all of domain A, then all of domain B (simple but causes forgetting). Batch-level: every batch is a mix of all domains (interleaved, stable). Batch-level mixing is standard for pre-training.
  • Data repeats. Repeating high-quality data (books, textbooks, curated text) 2–4 times generally helps more than adding an equivalent volume of low-quality data. Beyond ~4 epochs on the same data, diminishing returns set in and memorisation risk grows.
Takeaway: the mix ratio is a hyper-parameter with outsized impact. Upweight quality, interleave domains at the batch level, and repeat good data rather than padding with junk.

08 Data processing pipeline

An end-to-end pipeline turns a raw crawl into tokenised, shuffled, ready-to-train batches.

  1. Crawl / collect — web crawls (Common Crawl snapshots), code repositories, digitised books, curated datasets, internal corpora.
  2. Language / format filtering — keep target languages, strip HTML/boilerplate, handle encoding, discard binary and non-text content.
  3. Quality filtering — length heuristics, perplexity scores, classifier-based quality scoring (§04).
  4. Deduplication — exact hash, MinHash/LSH near-dedup, suffix-array substring dedup (§05).
  5. Decontamination — remove n-gram overlaps with eval/benchmark datasets.
  6. PII / safety filtering — redact or remove personally identifiable information, toxic content, and copyrighted material where required. See Data Quality & Governance.
  7. Domain classification & mixing — tag each document with its domain, apply the mix weights (§07).
  8. Tokenize — encode text into token IDs using the model's tokenizer (BPE, SentencePiece, etc.).
  9. Package — concatenate token sequences, split into fixed-length training sequences, shuffle, and write to an efficient format for the data loader.

Tools and formats

  • Pipeline frameworks: datatrove (HuggingFace), dolma (AI2), RedPajama (Together AI) — all implement the stages above with configurable filters, deduplication, and parallelism.
  • Processing at scale: distributed across many machines using map-reduce or streaming pipelines. A full Common Crawl snapshot is petabytes; each stage must be parallelisable and resumable.
  • Formats: JSONL for text (one JSON object per line, easy to stream), Parquet for structured/columnar data (efficient compression, random access), Arrow for in-memory processing. Final training data is often in a memory-mapped binary format for fast random access by the data loader.
Takeaway: the pipeline is crawl → filter → dedup → decontaminate → classify → mix → tokenize → package. Each stage is independently testable and should be versioned.

09 Data for specific capabilities

Different downstream capabilities require different data shapes.

  • Conversation data. Multi-turn chat with role tags (system, user, assistant). Formats like ChatML wrap each turn in role markers. Good conversation data includes follow-up questions, corrections, and clarifications — not just single Q&A pairs.
  • Tool-use data. Action–observation pairs in a multi-message chat format: the model outputs a tool call (function name + arguments), the system returns the result, and the model integrates it into the response. See Agents and Context Engineering.
  • Code data. Source code with repo-level context (file paths, imports, dependencies), docstrings, inline comments, and test files. Including tests alongside code teaches the model to verify its own outputs. Repo-level context (multiple files from the same project) teaches cross-file reasoning.
  • Math / reasoning data. Step-by-step solutions that show the work, not just the answer. Each step should be verifiable. Synthetic math data (generated and verified by symbolic engines) is particularly effective because correctness can be checked automatically.
  • Safety data. Refusal examples (the model declines harmful requests), red-teaming datasets (adversarial prompts the model must handle gracefully), and boundary examples (edge cases between harmful and benign). See LLM Security.
  • Multimodal data. Image-text pairs (captioning, VQA), interleaved documents (text with inline images), video-text, and audio-text. Quality varies enormously — alt-text from the web is noisy; human-written descriptions are expensive but far more informative. See Vision-Language Models.
Takeaway: each capability has its own data shape. Conversation needs turns, tools need action–observation loops, code needs repo context, math needs verifiable steps, and safety needs both good and bad examples labelled clearly.

10 Pitfalls & recap

Common pitfalls

  • Data contamination. Training on benchmark data inflates eval scores and hides real weaknesses. Always decontaminate, and check for n-gram overlap between training and test sets.
  • Ignoring provenance & licensing. Not tracking where data came from makes it impossible to debug quality issues or comply with licensing requirements. Version and document every data source.
  • Poor dedup → memorisation. Failing to deduplicate means the model memorises repeated content verbatim and can regurgitate it at inference — a privacy and quality problem.
  • Unfiltered synthetic data → model collapse. Using raw synthetic data without quality filtering degrades the model progressively. Each generation of synthetic-on-synthetic training narrows the distribution further.
  • Imbalanced domain mix. Letting web text dominate because it is plentiful, while starving code, math, and multilingual sources, produces a lopsided model.
  • Not versioning datasets. Training runs must be reproducible. If you cannot reconstruct the exact dataset a model was trained on, you cannot debug it, audit it, or improve it systematically.

Recap

  • Data quality > quantity. A smaller, cleaner dataset beats a larger, noisier one. Filter aggressively.
  • Dedup is essential — at document, paragraph, and substring levels, and cross-checked against eval data.
  • Synthetic data is powerful but needs filtering. LLM-as-judge, human review, and dedup are non-negotiable quality gates.
  • Mixing ratios are hyper-parameters. Treat them like learning rate — tune them, don't guess.
  • Pipeline reproducibility matters. Version the data, the filters, the mix config, and the random seeds.
