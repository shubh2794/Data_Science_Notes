QLoRA: Fine-Tuning on a 4-bit Base

Keep the frozen pretrained model in 4 bits, dequantize each weight matrix on the fly to 16-bit for the matmul, and backpropagate only into 16-bit LoRA adapters. This page follows the original study from the memory problem to the three pieces that make it work — the NormalFloat4 data type, double quantization of the scaling constants, and paged optimizers — then through the ablations showing it matches 16-bit fine-tuning, the instruction-tuning study built on top of it, and what that study found about data quality and about judging chatbots.

01 The memory wall: more than 780 GB down to under 48 GB

Regular 16-bit fine-tuning of a 65B-parameter model needs more than 780 GB of GPU memory. QLoRA fine-tunes the same model on a single 48 GB GPU, and the original study reports it does so without degrading runtime or predictive performance relative to a 16-bit fully fine-tuned baseline.

  • Where 780 GB comes from. The paper gives the total, not a breakdown. It is exactly what you get at 12 bytes per parameter — 2 for the 16-bit weight, 2 for its gradient, 8 for Adam's two 32-bit moments: 65 × 10⁹ × 12 B = 780 GB (our arithmetic), before any activations.
  • LoRA already removes most of it. Frozen weights need no gradient and no optimiser state (see LoRA §06). What remains is the frozen model itself: 2 bytes per parameter, about 130 GB at 65B in 16-bit — still several GPUs.
  • The frozen base only has to be read. It is never updated, so it does not need the precision an optimiser step would. That is the opening QLoRA uses: store the base in 4 bits (about 0.5 bytes per parameter) and keep everything that is trained — the adapters — in 16-bit.
the bet, in one line per tensorfrozen base W stored in 4-bit NF4, dequantized to BF16 when used, never updated adapters L₁, L₂ stored and trained in BF16, receive all the gradients optimizer state only for the adapters; paged to CPU memory on spikes

The study's three named contributions each attack one part of the footprint that is left once LoRA is used: NF4 (§03) makes 4-bit storage of the weights accurate enough; double quantization (§04) shrinks the per-block scaling constants that 4-bit storage needs; paged optimizers (§05) absorb the short memory spikes that would otherwise crash a run sized right at the limit. The method was used to train more than 1,000 models, across 8 instruction datasets, several model families and scales from 80M to 65B parameters.

02 Background: blockwise absmax quantization, and why blocks

To fit a real-valued tensor into k bits, rescale it so its largest magnitude lands on the edge of the target range, then round. One outlier sets that scale for everyone, so the tensor is cut into small blocks that are each scaled on their own.

absmax quantization to Int8 (the paper's worked example)c = 127 / absmax(X) the quantization constant (FP32) X_Int8 = round( c · X ) dequant : X ≈ X_Int8 / c blockwise: one constant per block of B valuesflatten X, cut into n = (number of values) / B contiguous blocks quantize each block b with its own c_b = 127 / absmax(block b) storage = k bits per value + 32 bits per block = k + 32/B bits per value
  • The outlier problem. If one value in the tensor is much larger than the rest, c is small, and nearly all values map onto the few codes nearest zero; the paper's wording is that the quantization bins are then "not utilized well", with few or no numbers in some bins. Every other value effectively loses bits.
  • Blocks contain the damage. Each block is normalized by its own absmax, so an outlier only coarsens the B − 1 values that share its block. Smaller blocks mean less damage and more constants to store — the trade-off double quantization (§04) addresses.
  • k = 4 has very little room. At 4 bits there are 16 codes for each block. Where those 16 levels sit inside [−1, 1] now matters a great deal, which is the question NF4 answers.
LoRA itself is not re-derived here. The adapter parameterisation h = W₀x + (α/r)·BAx, its zero initialisation and its scaling are on the LoRA deep dive. The paper writes the same thing as Y = XW + s·XL₁L₂ with L₁ ∈ ℝ^(h×r), L₂ ∈ ℝ^(r×o) and a scalar s; this page uses its notation. Quantization for inference (GPTQ, AWQ, Int8 serving) is on model acceleration.

03 NormalFloat4: put the 16 levels where normal weights are

Pretrained weights are roughly zero-centred and normally distributed. So choose the 16 levels as quantiles of a standard normal: then, in expectation, every code is used equally often. The paper calls the resulting NF4 data type information-theoretically optimal for normally distributed weights.

Quantile quantization

A k-bit quantile quantizer spaces its 2ᵏ levels so that each bin holds the same probability mass of the input distribution. Exact quantiles are expensive to estimate for an arbitrary tensor, but if the distribution is known up to a scale, the levels can be computed once. Weights normalized by absmax into [−1, 1] are then a fixed distribution, so one table serves every block.

levels from standard-normal quantiles (the paper's estimate)qᵢ = ½ · ( Q_X( i / (2ᵏ + 1) ) + Q_X( (i + 1) / (2ᵏ + 1) ) ) Q_X = quantile function (inverse CDF) of the standard normal N(0, 1) each level is the midpoint of two neighbouring quantiles the levels are then normalized into [−1, 1]

The asymmetric construction that gives an exact zero

A symmetric set of 16 quantiles has no level at zero — 8 negative, 8 positive. But zero matters: padding and other zero-valued elements must be represented without error. NF4 therefore builds the two halves separately: 2ᵏ⁻¹ levels for the negative side and 2ᵏ⁻¹ + 1 for the positive side, both including zero, then unifies them and drops one of the two zeros. For k = 4: 7 negative levels, zero, and 8 positive levels — one more on the positive side.

The published table is reproduced to within about 10⁻⁷ by taking, for the positive half, the normal quantiles at 8 evenly spaced probabilities from δ down to (but excluding) 0.5, for the negative half the negated quantiles at 7 evenly spaced probabilities from δ to 0.5 (excluding 0.5), adding 0, and dividing by Q_X(δ) — with δ = ½·((1 − 1/32) + (1 − 1/30)) ≈ 0.9677, the average of the outer probabilities implied by 2·16 and 2·15 bins. Is the normality assumption true?

The paper's appendix tests it per neuron: about 7.5% of neurons were non-normal at a 5% significance threshold, roughly 2.5 points above the 5% false-positive rate expected if all of them were normal. So the bulk of pretrained weights fit the assumption well, with a minority that does not.

  • The error numbers are simulated, not reported. The weights are a seeded Gaussian sample, quantized to the nearest level of each grid. The NF4 levels are computed from normal quantiles and checked against the paper's table; the Int4 grid is the 4-bit analogue of the paper's absmax formula (levels j/7, j = −7…7); the FP4 grid is a generic E2M1 layout (magnitudes 0, 0.5, 1, 1.5, 2, 3, 4, 6, scaled by 1/6). The paper does not list its FP4 values, so this grid is our choice.
  • What the simulation shows. On clean Gaussian blocks NF4 has the lowest error at every block size. At B = 64 the ordering is NF4, then FP4, then Int4 — the same order as the paper's perplexity table in §09 — but Int4 beats this FP4 grid at the smallest blocks. With outliers and large blocks, the normalized values pile up near zero and stop looking normal; there FP4's dense levels near zero catch up with and slightly pass NF4. NF4's advantage depends on the normalized block actually being bell-shaped, which small blocks help ensure.
  • "Optimal" here means equal-use codes, not minimum squared error. Equal-probability bins maximise the entropy of the code stream; a minimum-MSE (Lloyd–Max) quantizer would place levels differently. The code entropy in the readout gets close to the 4-bit maximum for NF4 on clean Gaussian data (Int4's 15 levels cap it at log₂ 15 ≈ 3.91 bits). (Our gloss on the term; the paper uses the phrase without the distinction.)

04 Double quantization: quantize the quantization constants

Small blocks are needed for accurate 4-bit storage, but each block carries a 32-bit constant. At block size 64 that is half a bit per parameter of pure overhead. Double quantization treats those constants as just another tensor and quantizes them too.

cost of the constants, block size 64 for the weightssingle quantization: 32 / 64 = 0.5 bits per parameter double quantization: first-level constants c₂ → 8-bit floats, blocks of 256 one FP32 second-level constant c₁ per 256 of them 8 / 64 + 32 / (64 · 256) = 0.127 bits per parameter saving 0.5 − 0.127 = 0.373 bits per parameter on a 65B model ≈ 3 GB (65 × 10⁹ × 0.373 / 8 bytes ≈ 3.03 GB, our arithmetic)
  • Centring first. The absmax constants are all positive. Before the second quantization the paper subtracts their mean, so the values are centred around zero and a symmetric quantizer can be used.
  • No accuracy cost found. The paper reports that double quantization reduces the memory footprint without degrading performance (§09: in the data-type comparisons NF4 with and without it behave the same, and it gives only minor further gains in zero-shot accuracy).
  • Why it matters at the margin. 3 GB is under 7% of a 48 GB card, but a run sized at the limit lives or dies by margins like that; the memory figure in §07 lets you switch it off and see the total move. Exact: 8/64 + 32/16384 = 0.126953…, which the paper rounds to 0.127.

05 Paged optimizers: survive the spikes

Gradient checkpointing keeps activation memory low on average, but a mini-batch with a long sequence can spike it past the GPU limit. Paged optimizers let optimizer state spill to CPU memory instead of crashing the run.

  • The mechanism. Optimizer states are allocated in GPU unified memory, which does automatic page-to-page transfers between CPU and GPU. In the paper's words, the states are "automatically evicted to CPU RAM when the GPU runs out-of-memory" and "paged back into GPU memory when the memory is needed in the optimizer update step" — the same idea as an operating system paging between RAM and disk.
  • Why the optimizer state is the thing to page. It is only touched once per step, in the update, whereas the weights and activations are needed throughout the forward and backward pass. Moving it out costs nothing until the update.
  • What was measured, and what was not. The paper made no hard measurements of the paging cost, because paging happens mainly with rare long-sequence mini-batches. It reports that for 65B models on 48 GB GPUs at batch size 16, training ran at the same speed as with regular optimizers, and leaves characterising when slowdowns occur to future work. It also notes the 33B model does not quite fit in 24 GB without paging.

06 One QLoRA layer: NF4 storage, BF16 compute

QLoRA has one low-precision storage type (NF4) and one computation type (BFloat16). Every time a weight matrix is used — forward or backward — it is dequantized to BF16 just for that matmul.

forward pass of one linear layer with one adapterY^BF16 = X^BF16 · doubleDequant( c₁^FP32, c₂^k-bit, W^NF4 ) + X^BF16 · L₁^BF16 · L₂^BF16 doubleDequant( c₁, c₂, W ) = dequant( dequant( c₁, c₂ ), W ) = W^BF16 c₂^k-bit the per-block absmax constants of W, themselves quantized (8-bit floats, block 256) c₁^FP32 the second-level constants that dequantize c₂ W^NF4 4-bit codes, block size 64 backward pass: which gradients existneeded: ∂E/∂L₁ , ∂E/∂L₂ the adapter weights (BF16) needed: ∂E/∂X to keep backpropagating through the layer — uses W, so W is dequantized to BF16 again not needed: ∂E/∂W W is frozen; no gradient, no optimizer state
  • Gradients flow through the 4-bit weights, not into them. The input gradient ∂E/∂X = (∂E/∂Y)·Wᵀ + … requires W, so the backward pass dequantizes it as the forward pass did. Only the adapters accumulate gradients.
  • Quantization error is a fixed offset the adapters can compensate for. The model being fine-tuned is the dequantized model W̃ ≈ W, and the adapters are trained against that model's loss — they learn on top of W̃, not of the 16-bit W. (This is our framing of why fine-tuning on a quantized base works; the paper's evidence is empirical, §08–§09.)
  • The adapters are a small share of memory but not of activations. The paper's 7B example (LLaMA on FLAN v2, batch size 1, LoRA weights about 0.2% of the model): LoRA parameters take 26 MB, but the LoRA input gradients take 567 MB, falling to about 18 MB per sequence with gradient checkpointing — still more than all the LoRA weights. The 4-bit base model takes 5,048 MB. The conclusion drawn there: adding more adapters barely changes total memory, which is why §08's "adapt every layer" is affordable.

08 The adapter ablation: every linear layer, and rank barely matters

The standard practice of applying LoRA only to the query and value projections does not replicate full fine-tuning for large base models. Applying it to all linear layers in the transformer block does — and once that is done, the rank r has little effect.

  • The experiment. LLaMA 7B fine-tuned on Alpaca, scored by RougeL, with several random seeds per configuration. The number of adapted layers was the most critical LoRA hyperparameter: LoRA on all linear transformer-block layers was required to match 16-bit full fine-tuning.
  • Rank. Searched over r ∈ {8, 16, 32, 64, 128, 256}; the paper reports r to be unrelated to final performance when LoRA is used on all layers. This is the same flatness the original LoRA rank ablation found — but here it holds only once the adapters are spread across every layer.
  • The baselines were tuned too. The study found the default full fine-tuning hyperparameters undertuned and searched learning rates from 1e-6 to 5e-5 and batch sizes from 8 to 128, so the comparison is against a strong 16-bit baseline. The LoRA α was held fixed while the learning rate was searched; LoRA dropout 0.05 helped the 7B and 13B models but not 33B and 65B.

10 The instruction-tuning study: Guanaco, and quality over size

With fine-tuning of 65B models now cheap, the study instruction-tuned LLaMA at every size on eight datasets. The chatbot it produced, Guanaco, came from fine-tuning on a small, high-quality dataset — about 9k examples — and reached 99.3% of ChatGPT's score on the Vicuna benchmark as judged by GPT-4, after about 24 hours of fine-tuning on a single professional GPU.

  • Training data. Guanaco is fine-tuned on a variant of OASST1, a crowd-sourced multi-turn conversation dataset, keeping only the top-ranked reply at each level of the conversation tree: 9,209 examples.
  • The Vicuna benchmark is 80 prompts; GPT-4 scores both a model's answer and ChatGPT's out of ten, and the result is the model's score as a percentage of ChatGPT's. A second benchmark, OA, uses 953 unique user queries from the OASST1 validation set.
  • Cost. The 65B result took about 24 hours of fine-tuning on a single professional GPU; the 33B Guanaco can be trained on 24 GB consumer GPUs in under 12 hours.

Data quality beats dataset size

OASST1's 9k examples beat FLAN v2 — a collection of over 15M examples, subsampled to 450k for this study — on chatbot performance at every size in the table above, and at 13B none of the other, larger sets (Unnatural Instructions 240,670; HH-RLHF 160,800; Self-Instruct 82,612; Alpaca 51,942 examples) comes close to it either. The paper's conclusion: for chatbot performance, dataset suitability and quality matter more than size. The general version of that argument — curation, quality signals, how much data is enough — is on dataset engineering.

Percent-of-ChatGPT scores depend on one reference model. The study also ran Elo tournaments: models compete in pairwise matches on the same prompt, judged either by GPT-4 or by human raters, and the ratings are compared.

  • Order bias. GPT-4 assigns higher scores to the system that appears first in its prompt. The paper's remedy is to score each pair in both orders and average — standard practice for pairwise judges since.
  • Self-preference. GPT-4 rates its own outputs far higher than humans do (Elo 1348 vs 1176), which the paper puts at roughly a 20% higher win probability.
  • The verdict. System-level rankings from GPT-4 are a cheap and reasonable alternative to human evaluation, but the paper is explicit about the uncertainty, and the failure cases are visible — Guanaco 7B is third for humans and last for GPT-4 on the same prompts. The general treatment of judge biases (position, verbosity, self-preference) and their mitigations is on LLM-as-a-judge.

14 Common misconceptions

"QLoRA trains a 4-bit model." No — it trains 16-bit adapters on a frozen 4-bit base. No gradient is ever taken with respect to the 4-bit weights, and no computation happens in 4 bits: weights are dequantized to BF16 for every matmul (§06).
"NF4 is optimal, so it has the lowest quantization error." It is optimal in the quantile sense: equal expected use of every code for normal data. That maximises the information per code, which is not the same objective as minimum mean-squared error, and the guarantee assumes normality, which most but not all neurons satisfy (§03).
"Double quantization halves the memory again." It saves 0.373 bits per parameter — the constants, not the weights: from 4.5 to about 4.127 bits per parameter at block size 64, about 3 GB on a 65B model (§04).
"LoRA on the query and value projections is enough, as in the original LoRA." Not to match full fine-tuning on large models. The study found all linear layers were required; with that done, rank matters little (§08).
"Guanaco proves 9k examples are enough for anything." It shows that for a chatbot benchmark, a small high-quality conversational set beat much larger ones. On MMLU the ordering reverses — FLAN v2 wins — so "best data" depends on the target (§10).
"Guanaco 65B beats ChatGPT." 99.3% ± 4.4% of ChatGPT on 80 prompts, judged by GPT-4. That interval includes 100%, the judge is biased by order and towards itself, and humans and GPT-4 only moderately agree (§10–§11).

15 Takeaways

  • Frozen means read-only, and read-only weights can be stored at low precision: NF4 base, BF16 compute, BF16 adapters that get all the gradients.
  • Blockwise absmax with block size 64 contains outliers; NF4 places the 16 levels at normal quantiles with an exact zero; double quantization cuts the constants from 0.5 to 0.127 bits per parameter; paged optimizers absorb memory spikes.
  • 65B in under 48 GB, against more than 780 GB for 16-bit full fine-tuning — about 0.5 bytes per base parameter instead of 12.
  • Adapt every linear layer to match 16-bit fine-tuning; after that, rank is a minor knob.
  • NF4 + DQ matches 16-bit: full fine-tuning on GLUE and Super-NaturalInstructions at smaller scales, 16-bit LoRA on MMLU up to 65B (53.1 vs 53.0); FP4 lags by about a point.
  • Data quality over size for chatbots (9k OASST1 beats 450k FLAN v2), and MMLU does not predict chatbot quality.
  • Model judges give reasonable system-level rankings cheaply, but are order-biased and self-preferring — score both orders and keep humans in the loop.
