Prompt Engineering

A frozen model can be steered into a classifier, an extractor, a planner or a formatter purely by what you write to it. Prompt engineering is the craft of writing that instruction — examples, structure, reasoning cues, output contracts — and then measuring whether it actually works.

01 What prompt engineering is — and where it stops

Prompt engineering crafts the instruction. Context engineering assembles everything that surrounds it. The two share a window but answer different questions.

  • A pretrained-then-instruction-tuned model is a conditional distribution P(output | prompt). The weights are fixed at inference; the prompt is the only control surface you own per call. Prompt engineering is the discipline of choosing that conditioning text so the distribution concentrates on what you want.
  • Prompt engineering asks: how should the task be stated? — the instruction wording, the role, the delimiters, the examples that demonstrate the pattern, the reasoning cue, the output contract. It is mostly authored by a person and changes slowly.
  • Context engineering asks: what else must be in the window, and in what order? — retrieved documents, tool schemas, history, memory, caching layout, token budgets. It is mostly assembled by code at request time. The instruction is one component of that payload (its §04).
  • The boundary matters because the fixes differ. If the model has the facts but answers in the wrong shape, that is a prompt problem. If the model lacks the facts, no rewording helps — that is retrieval and context. If the model can't do it reliably at any wording, that is a training problem (§12).
  • It is also an empirical craft, not a bag of magic phrases. Behaviour shifts across model versions, so every claim on this page should be read as "a strong default to test", and every prompt should ship with an eval set (§10).

One sentence: prompt engineering = stating the task so that the model's most likely continuation is the output you need, in a format your code can consume — and proving it with an eval.

02 Zero-shot, few-shot & in-context learning

Describe the task, or show it. Either way, nothing is trained — the model conditions on the prompt and the pattern emerges in the forward pass.

zero-shotŷ = argmaxy Pθ(y | I, x) k-shot in-context learningŷ = argmaxy Pθ(y | I, (x1, y1), …, (xk, yk), x) (I = instruction, θ frozen)
  • Zero-shot relies on instruction tuning: the model has seen millions of "do X to this input" pairs and generalises to a new X stated in words. It is the default for well-known tasks (summarise, translate, classify sentiment) on modern chat models.
  • Few-shot adds k demonstrations. It wins when the output format is idiosyncratic, the label boundary is hard to put into words, or the house style must be copied exactly. See In-context learning for where the ability comes from.
  • What the examples actually teach is mostly the format, label space and input distribution. A well-known ablation found that randomising the labels in demonstrations hurt far less than expected, while removing the format or the label vocabulary hurt a lot. Larger models are more sensitive to the labels themselves — they can learn genuinely new (even flipped) mappings in context — so "labels don't matter" is a small-model result, not a law.
  • One useful mental model: demonstrations locate a task the model already half-knows rather than teach a new one from scratch. That explains both why a handful of examples is enough and why ICL struggles on tasks truly absent from pretraining.
  • Returns diminish fast. Most of the gain arrives with the first few examples; beyond that, each extra demonstration costs tokens on every call (§11) and can crowd out retrieved context. Long-context models make "many-shot" (hundreds of examples) feasible, which sometimes rivals light fine-tuning — at a per-call price.
Takeaway: start zero-shot with a precise instruction; add examples when the shape of the answer is what's going wrong. Examples are the most expensive tokens in a prompt because they are paid for on every single call.

03 Anatomy of a prompt

A production prompt is a structured document, not a sentence. Each block has a job, and the boundaries between them should be unmistakable.

BlockLives inJobCommon mistake
Role / personaSystemSets register, expertise level, audienceExpecting a role to add knowledge it doesn't have
Task & success criteriaSystemWhat to do, for whom, what "good" meansVague goal ("make it better") with no criterion
Rules & constraintsSystemScope, refusals, tone, length, grounding policyLong lists of contradictory or negative-only rules
ExamplesSystem or early user turnDemonstrate format and edge casesAll easy cases; one label over-represented
Input dataUser turn, fencedThe document / record / question to processUnfenced, so data reads as instructions
Output contractEnd of prompt or schemaExact fields, types, allowed values"Return JSON" with no schema

System vs user instructions

  • Chat models are trained with a role hierarchy: the system message carries operator intent that persists across turns; user messages carry the per-turn request. Put stable policy, persona and output contract in the system block; put the variable input in the user turn. This also lines up with prefix caching (stable first, volatile last).
  • The hierarchy is a training-time tendency, not a security boundary. A forceful enough user message, or instructions smuggled into input data, can still override it — see LLM Security for prompt injection and its defences.

Delimiters and output-format constraints

  • Fence every piece of data with unambiguous markers — XML-style tags (<document>…</document>), triple-backtick blocks, or clearly headed sections. Then refer to them by name: "summarise the text inside <document>". This stops the model treating a pasted email's "ignore the above" as a command, and makes prompts diffable.
  • State the output shape concretely: field names, types, allowed enum values, length limits, what to emit when the answer is unknown. An explicit escape value (""label": "unsure"") is cheaper than a hallucinated guess — compare the abstention techniques in Hallucination & Factuality.
  • For long documents, a common layout is documents first, instruction and question last — the model reads the evidence, then the task, right before it starts writing.
Takeaway: separate instructions from data structurally, keep policy in the system block, and end with an output contract specific enough that a parser could be written from it.

04 Writing the instruction: roles, specificity, framing

Most prompt bugs are specification bugs. Write the instruction you would give a capable new colleague who has zero context on your project.

  • Role prompting ("You are a senior tax accountant reviewing…") reliably shifts register — vocabulary, assumed audience, level of caution, what counts as relevant. It does not reliably add knowledge or accuracy on factual benchmarks; treat it as a style and focus lever, and pair it with the actual criteria the role implies.
  • Say why. "Keep answers under 80 words — they are read aloud on a phone line" generalises better than "keep answers short", because the model can infer the cases you didn't enumerate (no tables, no URLs).
  • Positive over negative. "Answer only from the provided documents; if they don't contain the answer, say so" beats "don't make things up". Prohibitions name the unwanted behaviour without saying what to do instead.
  • Be explicit about scope and effort. Modern instruction-tuned models tend to do exactly what is asked; if you want them to go beyond the literal request (suggest fixes, cover edge cases), say so.
  • Decompose the criteria, not just the task. A numbered checklist of what the output must satisfy doubles as the rubric for your eval (§10) — write it once, use it twice.
  • Avoid emphasis inflation. Capitals and "CRITICAL" scattered through a prompt were a workaround for older models; on current ones they tend to cause over-application of the shouted rule. Use them for the one rule that truly dominates, if any.
Takeaway: roles set tone; criteria set quality. A prompt that states the goal, the audience, the reason behind each constraint and what to do when unsure needs far fewer clever tricks.

05 Choosing and ordering examples

With few examples, which ones and in what order can swing accuracy as much as the instruction itself. The figure is a toy model of those effects.

Few-shot sensitivity explorer (illustrative simulation) Each dot = one random draw of examples and order; the band is mean ± 1 sd across draws

The simulation encodes, qualitatively, the effects reported repeatedly in the in-context learning literature. The numbers are invented; the shape is the point.

What the figure is encoding

  • Diminishing returns in k. Mean accuracy rises steeply over the first few shots, then flattens.
  • High variance at small k. With 1–4 examples, a different draw or a different permutation of the same examples can move accuracy from near-chance to near-best. Variance shrinks with k but doesn't vanish — report a spread over several draws, never a single prompt's score.
  • Similarity-retrieved examples (embed the query, pull its nearest labelled neighbours from a pool) usually beat a fixed set: they demonstrate the edge case the current input actually resembles. The cost is a retrieval step per call and a prompt that no longer caches as a fixed prefix.
  • Majority-label bias. If most demonstrations carry one label, predictions drift toward it. Balance the label distribution (or match the expected test distribution deliberately).
  • Recency bias. Labels near the end of the prompt are over-predicted. A block of same-label examples right before the query is the worst ordering; interleaving labels is a cheap fix.
  • Contextual calibration estimates the model's prior bias by feeding a content-free input (e.g. "N/A") through the same prompt, then rescales the label probabilities so that input would come out uniform. It reduces both bias and spread — when you have access to label probabilities.
contextual calibration (per prompt)pcf = P(y | prompt, "N/A") W = diag(pcf)⁻¹ p̂ = softmax(log(W · p)) ≈ normalise(p ⊘ pcf) similarity-retrieved demonstrationsD(x) = top-k(xi, yi) ∈ pool cos(e(x), e(xi)) cos(a, b) = (a·b) / (‖a‖ ‖b‖)
  • Practical recipe: cover the edge cases (the boundary between labels, the empty input, the malformed record), keep examples diverse so the model doesn't copy one surface pattern, and check that no example leaks specifics (names, numbers) the model will paste into unrelated answers.
  • For generation tasks, three varied examples usually beat one perfect one — a single example is read as a template and copied too literally.
Takeaway: treat the example set as a hyper-parameter. Balance labels, interleave them, prefer retrieved neighbours when the input space is broad, and measure the spread across permutations before trusting any single score.

  • Separate thinking from answer. Ask for the reasoning inside one tagged block and the final answer inside another, so code can parse the answer without the rationale — and so the rationale never leaks into a user-facing field.
  • Reasoning-trained models change the calculus.   • A written rationale is not a faithful explanation of how the answer was computed. Use it for accuracy and debugging, not as an audit trail.
Takeaway: CoT buys accuracy with output tokens. Use it on genuinely multi-step problems, keep the answer in its own parseable slot, and drop explicit CoT cues on models that reason by default.

07 Prompt chaining: decompose into stages

One prompt that does five things does each of them worse. Split the job into a pipeline of narrow prompts whose outputs feed the next.

  • A typical chain: extract (pull the relevant clauses from a contract) → analyse (classify each clause's risk) → draft (write the summary) → check (verify the draft cites only extracted clauses). Each stage has one job, one output schema and its own eval.
  • Why it helps: every stage gets the model's full attention on a smaller problem; intermediate outputs are inspectable and testable; failures localise to a stage; and stages can use different models — a small, cheap one for extraction, a stronger one for the hard judgement.
  • Gates between stages turn a chain into a program: validate stage i's output (schema, non-empty, within bounds) before spending tokens on stage i+1, and route failures to a retry or a fallback.
  • The cost is latency and compounding error. If each stage succeeds independently with probability pᵢ, the chain succeeds with ∏ pᵢ — five 95% stages give ≈ 77%. Gates and retries are what claw that back.
  • Chaining is the simplest of the fixed-path agentic workflow patterns; when the next step depends on what was observed, you have crossed into agents.
end-to-end reliability of an ungated chainP(chain ok) = ∏i=1…m pi e.g. 0.95⁵ ≈ 0.77
Takeaway: decompose until each prompt has one job and one schema. You trade a little latency for stages you can test, swap and debug independently.

08 Output parsing & structured outputs

When the output feeds code, "usually valid JSON" is a bug. There are three tiers of guarantee.

TierMechanismGuaranteeResidual risk
Instructed formatDescribe the schema and show an example in the promptNone — usually worksStray prose, trailing commas, missing fields
Validate-and-retryParse; on failure, re-prompt with the error messageProbabilistic, bounded by retriesExtra latency and cost on failures
Constrained decodingAt each step, mask tokens that would violate a grammar / JSON schemaSyntactically valid by constructionContent can still be wrong; schema features may be limited
  • Constrained decoding compiles the schema to a grammar or finite-state machine; at each decoding step, logits for tokens that cannot extend a valid prefix are set to −∞ before sampling. The output parses by construction. Many APIs expose this as a "structured output" or strict tool-schema mode; with open models it is a library-level feature of the inference server.
  • Validity is not correctness. A schema guarantees "amount": number, not that the number is the one in the invoice. Keep semantic validators (ranges, cross-field consistency, "value appears in source") after the parser.
  • Field order is a reasoning order. Because the model generates left to right, putting a "reasoning" field before "answer" in the schema gives you CoT inside structured output; putting the answer first forces it to commit before thinking.
  • Heavily restrictive grammars can hurt quality slightly on reasoning-heavy tasks, since the model can't "think out loud". The common workaround is a free-text reasoning field, or a two-step chain: reason freely, then format.
  • On retries, feed back the specific validation error ("field date: expected YYYY-MM-DD, got 'next Tuesday'") rather than "invalid, try again".
validate-and-retry with per-attempt validity p and at most R attemptsP(valid within R) = 1 − (1 − p)R E[attempts] = (1 − (1 − p)R) / p (p = 0.9, R = 3 → 99.9% valid, ≈ 1.11 calls)
Takeaway: when output feeds code, use schema-constrained decoding if available, keep semantic validators after it, and order schema fields so the model reasons before it commits.

09 Sampling parameters and the prompt

The prompt shapes the distribution; sampling decides how much of it you see. The decoding mathematics is derived in Decoding: temperature, top-k, top-p and visualised in LLM decoding.

temperature rescales the logits; top-p truncates the tailPT(t) = softmax(z / T)t Vp = smallest set with ∑t ∈ Vp PT(t) ≥ p
  • Low temperature (≈ 0–0.3) for extraction, classification, code and anything you will evaluate for exact match. Higher (≈ 0.7–1) for brainstorming, diverse drafts, and for generating the N samples that self-consistency votes over.
  • Tune one knob. Temperature and top-p both control tail mass; adjusting both makes behaviour hard to reason about, and some APIs now reject or ignore setting both. Some reasoning-model APIs fix sampling parameters entirely.
  • T = 0 is not a determinism guarantee. Batched inference, floating-point non-associativity and server-side changes can still vary outputs. If an eval needs repeatability, measure the run-to-run spread rather than assuming zero.
  • A good prompt narrows the distribution so that sampling matters less. If quality swings wildly between samples at moderate temperature, the instruction is under-specified — fix the prompt before turning the temperature down to hide it.
  • Stop sequences and max-token limits are part of the contract too: a stop on the closing tag of your answer block saves tokens and prevents trailing commentary.
Takeaway: sampling settings are task-specific, not global. Low and fixed for anything evaluated by exact match; higher only where diversity is the goal.

10 Evaluating and iterating on prompts

A prompt edit is a code change. Without an eval set you cannot tell an improvement from noise — and small eval sets are much noisier than they feel.

The loop

  • Write success criteria first — specific, measurable (exact-match accuracy, schema validity, rubric score, latency, cost per call).
  • Build an eval set of representative inputs, deliberately over-sampling the hard and adversarial cases. Start with tens of examples to iterate fast; grow to hundreds before trusting small differences. Version it alongside the prompt.
  • Grade by code where possible (exact match, regex, parser, unit test); by an LLM judge with a written rubric for open-ended output — watching for its position, length and self-preference biases; and by humans on a sample to keep the judge honest.
  • Regression-test every change against the full set, not just the case that motivated it. Prompt fixes are notorious for repairing one failure and silently breaking three others. Re-run the suite when the underlying model version changes, too.
  • A/B in production for what offline evals can't see — user edits, task completion, escalations — with the prompt version logged on every request.

How big a difference is real?

standard error of an accuracy estimated on n itemsSE = √( p (1 − p) / n ) 95% CI ≈ p ± 1.96 · SE examplep = 0.80, n = 100 → SE = 0.04 → CI ≈ ±7.8 points n = 1000 → ±2.5 points
  • On 100 items, a 3-point gain between two prompts is well inside the noise. Compare prompts on the same items (a paired test such as McNemar's on the items where they disagree) — it is far more sensitive than comparing two independent accuracies.
  • Because of the variance in §05, also measure across a few example permutations or seeds; a prompt that wins on one ordering and loses on another hasn't won.
  • Automated prompt optimisation — having a model propose rewrites or select demonstrations and keeping whatever scores best on a dev set — works, but overfits small dev sets exactly like hyper-parameter search does. Hold out a test split.
Takeaway: criteria → eval set → graders → regression suite → A/B. Size the eval so the differences you care about exceed the confidence interval, and compare prompts paired on the same items.

11 Prompt compression, caching & API cost

A prompt is paid for on every call. A long system prompt that costs fractions of a cent once becomes a real line item at a million calls a day.

Prompt cost calculator (illustrative prices) Baseline vs optimised daily cost; prices are placeholders — substitute your provider's
cost per day, no cachingC = N · ( (ns + nd) · cin + nout · cout ) with a cached static prefix (price multipliers ρr for a cached read, ρw for a cache write; W writes per day)C = N · ( ns · ρr · cin + nd · cin + nout · cout ) + W · ns · (ρw − ρr) · cin
  • The figure's defaults are placeholders: input at $3 per million tokens, output at 5× input, cached reads at 0.1× and cache writes at 1.25× the input rate, refreshed 288 times a day (every 5 minutes). Real ratios vary by provider and model, but output priced several times above input and cached reads priced at a small fraction of input are common patterns.
  • Caching only works on a byte-identical prefix, so the static part must come first and contain nothing that changes per call — no timestamps, no per-user names, no shuffled examples. Similarity-retrieved examples (§05) belong after the cache boundary. Layout rules are in Context Engineering §08.
  • Compression comes in three flavours: editorial (delete redundant rules, merge overlapping examples — free and usually the biggest win), learned token pruning (a small model drops low-information tokens, with aggressive ratios reported on long retrieved contexts), and summarisation of history or documents. The last two trade accuracy for tokens: quality is flat at mild ratios and then falls off, with exact strings (IDs, numbers, code) the first casualties.
  • Output tokens are the expensive side per token and dominate latency; once the prefix is cached they often dominate the bill as well (in the figure's defaults, output goes from about a quarter of the baseline cost to well over half of the optimised one). CoT, verbose prose and repeated JSON keys all add up. Ask for concise output, set max-tokens and stop sequences, and prefer short enum values.
  • Model routing is a cost lever too: send easy calls to a small model and escalate only the hard ones, measured per route with the eval from §10.
Takeaway: cost ≈ calls × (input tokens × input price + output tokens × output price). Cache the static prefix, edit the prompt down before compressing it algorithmically, and watch output length — per token it is the more expensive side, and after caching it is often most of the bill.

12 Prompting vs RAG vs fine-tuning

Each fixes a different gap. Diagnose the gap first; then pick the cheapest tool that closes it.

The decision triangle (illustrative heuristic) Describe the gap; the point moves toward the approach that addresses it
PromptingRAGFine-tuning
FixesTask statement, format, tone, simple behaviourMissing, private or fresh knowledgePersistent skill, style or behaviour the prompt can't reliably induce
Does not fixFacts the model never sawStyle, format, reasoning skillFresh facts (frozen at training time); reliable recall of rare facts
Time to changeMinutesRe-index: minutes to hoursData collection + training: days
Per-call costGrows with prompt lengthRetrieval + longer contextShorter prompts; can use a smaller model
Upfront costAn eval setIndex, chunking, retriever evalLabelled data, training, serving the adapter
  • Always start with prompting plus an eval set — it is the baseline every other option must beat, and the eval is reused by all three.
  • Reach for RAG when failures trace to facts the model doesn't have: private documents, anything after the training cutoff, things that change. It also enables citations, which helps against hallucination.
  • Reach for fine-tuning (usually a parameter-efficient adapter) when a behaviour is needed consistently and a prompt only gets it most of the time, when the few-shot block has grown into thousands of tokens paid on every call, or when latency demands a smaller model distilled to the task. Fine-tuning is a poor way to inject facts.
  • They compose. A common mature stack is a fine-tuned model for format and domain register, RAG for facts, and a prompt that ties them together. The RAG vs fine-tuning comparison covers that pairing.
Diagnostic: show the model the right answer's evidence in the prompt. If it now succeeds, you had a knowledge gap → RAG. If it still fails with the evidence present and a clear instruction, you have a capability or behaviour gap → better examples, decomposition, a stronger model, or fine-tuning.

13 Limits, pitfalls & what to remember

Limits of prompting

  • Brittleness. Semantically equivalent prompts — reordered examples, a changed delimiter, different whitespace — can produce measurably different accuracy, especially on smaller models. Robustness has to be measured, not assumed.
  • Version drift. A prompt tuned for one model version is not portable; when the model changes, re-run the eval before redeploying.
  • No new knowledge, bounded new skill. Prompts surface what the weights can already do. They cannot add facts (that's retrieval) or reliably install skills far beyond the model's ability (that's training or a stronger model).
  • Not a security boundary. Instructions can be overridden by adversarial input; anything with side effects needs controls outside the prompt — see LLM Security.

What to remember

  • Instruction vs context: prompt engineering states the task; context engineering decides what surrounds it. Diagnose which one is failing.
  • Structure the prompt: role and policy in the system block, data fenced in tags, an explicit output contract with an "unsure" escape.
  • Examples are hyper-parameters: balanced, interleaved, diverse, edge-case heavy; retrieved per query when the input space is broad; variance measured across permutations.
  • CoT costs output tokens: use it for multi-step problems on non-reasoning models; keep the answer in its own slot. Details in Reasoning in LLMs.
  • Decompose: chains of narrow prompts with gates beat one prompt doing everything.
  • Outputs that feed code: constrained decoding plus semantic validation plus targeted retries.
  • Evaluate like code: criteria, eval set, paired comparisons, regression suite, confidence intervals.
  • Price it: cache the stable prefix, trim before compressing, cap output length.
  • Escalate deliberately: prompting → RAG for knowledge, → fine-tuning for persistent behaviour or cost at volume.
Threads to pull: the ability itself is in-context learning in Large Language Models; the window around the prompt is Context Engineering; reasoning prompts deepen into Reasoning in LLMs; knowledge gaps go to RAG, behaviour gaps to PEFT; grading prompts is LLM-as-a-Judge; and keeping them safe is LLM Security.
