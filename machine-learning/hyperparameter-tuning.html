Hyperparameter Tuning

Parameters are learned; hyperparameters (learning rate, depth, λ, k) are chosen — and choosing them is a second, outer optimization problem with no gradients, an expensive objective, and a noisy one at that. This page is about spending a fixed compute budget on that outer problem as well as possible, and about not fooling yourself with the result.

Machine Learning Optimization Practice

01 Parameters vs hyperparameters

Two nested optimizations: the inner one is solved by training, the outer one by search.

Parameters θ are the numbers the training algorithm fits — regression weights, split thresholds in a tree, network weights. Hyperparameters λ are everything you had to decide before training could start: learning rate, batch size, number of neighbours k, tree depth, regularization strength, kernel width, number of boosting rounds, even the choice of preprocessing. Training minimizes a loss on the training split for a fixed λ; tuning minimizes a validation loss over λ, where each evaluation costs a whole training run.

the bilevel probleminner: θ*(λ) = argmin_θ L_train(θ ; λ) ← solved by the learning algorithm outer: λ* = argmin_λ L_val( θ*(λ) ; λ ) ← solved by search final: refit on train ∪ val with λ*, then report once on the untouched test set
  • No gradient. L_val is usually not differentiable in λ (how do you differentiate through "max depth = 6"?), so you cannot do gradient descent on the outer level. The search is black-box.
  • Expensive. One evaluation = one full training run, possibly times K for cross-validation folds. Budgets are counted in trials, not in seconds.
  • Noisy. L_val is measured on a finite validation set with a random seed, so the same λ re-evaluated gives a different number. Differences smaller than that noise are not real.
  • Mixed types. Continuous (learning rate), integer (max_depth), categorical (kernel), and boolean knobs coexist — and some only exist conditionally on others.
  • Every hyperparameter is ultimately a bias-variance dial, which is why tuning can be the difference between a mediocre and a strong model without touching the algorithm.
Takeaway: tuning is derivative-free optimization of an expensive, noisy function. Every method below is a different answer to "given that, where should I spend my next trial?"

03 The methods

Six families, from "try everything" to "let configurations compete for compute".

Grid search

Enumerate a lattice: choose mᵢ values for each of k hyperparameters and run all ∏ mᵢ combinations. Exhaustive, trivially parallel, perfectly reproducible — and combinatorially doomed. Five hyperparameters at five values each is 3,125 trials; adding one more value per axis multiplies the cost. It is still the right tool when k ≤ 2, the axes are genuinely categorical, and you want a complete picture of the surface.

Random search

Sample each hyperparameter independently from a distribution you specify (uniform, log-uniform, categorical) and run n independent trials. It decouples the budget from the dimensionality — you choose n directly — and it probes n distinct values on every axis. It parallelizes perfectly, tolerates crashed trials, and is the sane default whenever you have more than two or three knobs. Its weakness is that it never learns: trial 60 is as uninformed as trial 1.

Bayesian optimization

Fit a cheap surrogate model of the score surface to the trials so far — a Gaussian process, a random forest, or a pair of density estimators (TPE) — then choose the next point by maximizing an acquisition function that balances exploiting a good predicted mean against exploring a large predicted uncertainty.

expected improvement, for a minimized loss (y* = best so far, Y ~ N(μ(λ), σ(λ)²))EI(λ) = E[ max(0, y* − Y) ] = (y* − μ)·Φ(z) + σ·φ(z) z = (y* − μ) / σ simpler alternativesLCB(λ) = μ(λ) − κ·σ(λ) κ ↑ ⟹ more exploration TPE: split trials at a quantile into good ℓ(λ) and bad g(λ), then maximize ℓ(λ)/g(λ)

Very sample-efficient once it has 10–30 observations to learn from, but it is inherently sequential (the next point depends on the last result), so large parallel fleets need batching tricks, and the surrogate itself has hyperparameters. Below roughly 20 trials it has not learned anything and random search is just as good.

Successive halving and Hyperband

The previous methods all train each configuration to completion. Successive halving instead treats compute as the scarce resource: start n configurations on a small budget r, throw away the worst (1 − 1/η) fraction, multiply the survivors' budget by η, and repeat. Each rung costs about the same total, so you get log_η n rungs for roughly log_η n times the cost of a single full run.

successive halving with reduction factor ηrung i: nᵢ = ⌈n · η⁻ⁱ⌉ configs, each given rᵢ = r · ηⁱ resource cost of rung i = nᵢ · rᵢ ≈ n · r rungs = ⌊log_η n⌋ + 1 example: n = 27, η = 3, r = 1 epoch ⟹ 27×1, 9×3, 3×9, 1×27 = 27+27+27+27 = 108 epoch-units vs 27 × 27 = 729 epoch-units to train them all fully → ≈ 6.75× cheaper

The catch is the slow-starter risk: a configuration that is behind at rung 0 but would have won at full budget gets killed. Hyperband hedges by running several brackets with different (n, r) pairs — one aggressive bracket with many cheap configs, one conservative bracket that is essentially plain random search. ASHA is the asynchronous variant: promote a configuration as soon as it is in the top 1/η of its rung rather than waiting for the whole rung to finish, which keeps a large cluster busy.

Population-based and evolutionary search

Population-based training runs a population of models in parallel and periodically has poor performers copy the weights of good ones and perturb their hyperparameters. Because weights are inherited, it effectively learns a hyperparameter schedule (a learning rate that changes over training) rather than a single fixed value — something no other method here can express. Evolutionary / CMA-ES approaches keep a population, mutate and recombine the best, and handle rugged, non-smooth surfaces well; they need many evaluations but parallelize beautifully.

04 Why random beats grid

Two short calculations: how many random trials you need, and why the grid wastes most of its own.

How many random trials?

Suppose the top q fraction of the search space (by volume) is "good enough". Each independent random draw lands in that region with probability q, so the chance that at least one of n draws does is 1 − (1 − q)ⁿ. Invert it and you get a budget rule that does not mention dimensionality at all.

coverage of the top-q regionP(at least one hit in n trials) = 1 − (1 − q)ⁿ n ≥ ln(1 − P) / ln(1 − q) workedq = 0.05, P = 0.95 ⟹ n ≥ ln(0.05)/ln(0.95) = (−2.996)/(−0.0513) = 58.4 ⟹ n = 59 n = 60 trials ⟹ P = 1 − 0.95⁶⁰ = 0.954 ← the familiar "about 60 random trials" rule q = 0.01, P = 0.95 ⟹ n ≥ 299 a tenfold-narrower optimum costs ~5× the budget, not 10×

Effective dimensionality

In almost every real problem only a couple of hyperparameters actually move the score; the rest are nearly flat. Grid search does not know which, so it spends its budget varying all of them equally. With k axes at m values each, a grid uses mᵏ trials but explores only m distinct settings of the one axis that matters — the other mᵏ⁻¹ trials per setting are near-duplicates. Random search with the same budget explores mᵏ distinct settings of every axis. That is the entire argument, and it gets stronger as k grows.

distinct values probed on the axis that matters, for a fixed budget ngrid (k axes, m per axis, n = mᵏ): n^(1/k) random: n k = 4, n = 81 ⟹ grid probes 3 values of the important axis; random probes 81
  • Corollary: adding an irrelevant hyperparameter multiplies a grid's cost but costs random search nothing. You can afford to be generous with what you include in a random space.
  • Corollary: a grid's resolution on the important axis is the k-th root of your budget, so refining a grid is exponentially expensive. Coarse-to-fine manual refinement is the usual workaround, and it is exactly what a Bayesian method automates.
  • Random search also degrades gracefully: kill it at any point and you still have an unbiased sample of the space, whereas a half-finished grid is systematically biased toward whichever corner it started in.
Takeaway: grid search's cost scales with the number of hyperparameters; random search's cost scales with how narrow the good region is. Only the second of those is a property of your problem.

06 Designing the search space

The search space is a modelling decision, and a bad one caps how good any strategy can be. No optimizer can find a value you never allowed.

Use the right scale

Quantities that act multiplicatively must be sampled on a log scale. A learning rate of 0.001 and 0.002 differ meaningfully; 0.501 and 0.502 do not. Sampling u ~ Uniform(log a, log b) and taking 10ᵘ puts equal probability on each decade, which is what you actually believe a priori. The same goes for λ, C, γ, weight decay, and anything expressed as a ratio. Counts like n_estimators or layer width are often best on a log-integer scale too.

log-uniform samplingu ~ U(log₁₀ a, log₁₀ b) λ = 10ᵘ e.g. a = 10⁻⁵, b = 10⁻¹ ⟹ equal mass in each of the four decades near-1 quantities: sample the distance from 1β₂ = 1 − 10ᵘ, u ~ U(−4, −1) ← 0.999 and 0.9999 are far apart in effect, adjacent on a linear scale

Ranges, conditionals, and types

  • Set ranges wide, then check the edges. If the best trial sits at a boundary of your range, the range was wrong — extend it and re-run rather than accepting the boundary value.
  • Conditional spaces. γ only exists if kernel = rbf; num_layers determines how many width parameters exist. Encode these as trees of choices, not as one flat product — otherwise most of your trials evaluate meaningless combinations. Tree-structured samplers (TPE) and most modern tooling support this directly.
  • Order-free categoricals (solver, kernel) should not be encoded as integers; distance between them is meaningless and will mislead a surrogate.
  • Couple what is coupled. Learning rate and batch size interact (larger batches tolerate larger rates); rounds and learning rate in boosting trade off almost exactly. Either tune them jointly or fix one by a rule (e.g. small η plus early stopping on rounds).
  • Prune the list. Tune the 3–6 knobs known to matter and leave the rest at defaults. Every added axis dilutes the budget.

Takeaway: most "tuning didn't help" stories are search-space stories — a linear scale on a multiplicative knob, a range that excluded the optimum, or twenty axes sharing a thirty-trial budget.

07 Validating honestly

Search is an optimizer; it will happily optimize your evaluation noise. Nested cross-validation is how you find out.

Selection bias and nested CV

If you run 500 trials and report the best validation score, that number is optimistically biased — you selected the maximum of 500 noisy estimates, and the maximum of noise is positive. The larger the search, the larger the bias. The fix is to separate choosing from estimating: an inner loop tunes λ on training folds, and an outer loop scores the whole tuning procedure on data the inner loop never saw. The outer number is what you report; the inner best is what you deploy.

nested cross-validationfor each of K_out outer folds: tune λ by K_in-fold CV inside the outer training part refit with the winning λ on that whole training part, score on the held-out outer fold report: mean ± sd of the K_out outer scores costfits = K_out · ( K_in · T + 1 ) e.g. K_out = 5, K_in = 5, T = 50 trials ⟹ 1255 fits cheaper approximation: one fixed outer test set, K_in-fold CV inside — biased less than a single split, costs K_in · T + 1

Leakage traps

  • Preprocessing outside the loop. Scaling, imputation, feature selection, target encoding, and SMOTE must be fitted inside each training fold. Fitting a scaler on all the data before splitting leaks the validation distribution into training and inflates every score.
  • Grouped or temporal data. Random K-fold splits leak when rows share a patient, a user, or a session — use grouped splits; for time series use forward-chaining so the model never sees the future.
  • Reusing the test set. Each peek is a search step. Look once, at the end. See Model Evaluation.
  • Ignoring seed variance. Re-run the top few configurations with different seeds. If the spread across seeds exceeds the gap between your top-10 configs, you have not actually found a winner — pick the simplest or most robust one.

Budget and workflow

  • Rules of thumb. Random search: roughly 15–25 trials per hyperparameter you are tuning, minimum ~30. Bayesian: seed with 10–20 random trials before the surrogate is worth trusting. Halving/ASHA: start with 4–10× more configurations than you could afford to train fully.
  • Coarse to fine. A wide log-scale sweep first; then a narrower space centred on the good region. Re-check that the new range does not clip the optimum.
  • Early stopping is free tuning. Monitor a validation fold and stop when it stops improving — it removes "number of epochs / rounds" from the search entirely and makes each trial cheaper.
  • Tune the cheap thing first. Better features, better splits, and more data usually beat a bigger search; tuning is the last few percent, not the first.
  • Log everything — config, seed, metrics, data version, code version. Otherwise the best run is unreproducible. See Experiment Tracking.
  • Tooling in one line: Optuna and Ray Tune cover define-by-run conditional spaces, TPE/Bayesian samplers, and ASHA pruning; scikit-learn ships grid, random, and halving searches for smaller jobs.
Takeaway: the honest question is not "what is my best validation score?" but "how well does this whole tuning procedure do on data it has never touched?" Nested CV is the only clean answer.

08 Pitfalls & what to remember

Pitfalls

  • Reporting the best validation score as the model's performance. It is the maximum of many noisy draws — biased upward, and the bias grows with the number of trials.
  • Linear scales on multiplicative knobs. A uniform sweep of the learning rate from 0 to 1 puts 90% of its trials in a range no one uses.
  • Chasing differences inside the noise. Estimate run-to-run variability first; only trust gaps larger than it.
  • Tuning twenty knobs on thirty trials. Dilution beats optimization. Cut the space.
  • Optimum on the boundary. Always a sign the range was too narrow, never a result.
  • Preprocessing fitted before the split. The most common silent leak in tuning pipelines.
  • Halving on a model with a long warmup. Early rankings mean nothing; raise the minimum resource r.
  • Optimizing a metric you don't care about. Accuracy on imbalanced data, or a metric with a threshold you will later change.

What to remember

  • Tuning is a bilevel, gradient-free, expensive, noisy optimization. Every method is a budget-allocation policy.
  • Random beats grid whenever few hyperparameters matter, because a grid's resolution on the important axis is only n^(1/k). About 60 random trials give ~95% odds of hitting the top 5% region.
  • Bayesian optimization when trials are precious; Hyperband/ASHA when training is iterative and you can cull early; population-based when you need a schedule rather than a constant.
  • Design the space carefully — log scales, honest ranges, conditional structure, few axes.
  • Validate with nested CV, keep preprocessing inside the folds, and touch the test set once.
