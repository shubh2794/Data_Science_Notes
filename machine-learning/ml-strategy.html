ML Strategy & Error Analysis

How to set technical direction for a machine learning project — the applied playbook for deciding what to work on next. Most ML problems leave clues that tell you whether to collect more data, build a bigger model, fix labels, or change your metric. Learning to read those clues saves months of wasted effort.

Machine Learning Project Strategy Error Analysis Diagnostics

01 Why strategy beats raw effort

Faced with a model that isn't good enough, a team has dozens of options — more data, a bigger net, more features, regularization, a new architecture. Pick well and you win; pick poorly and you waste months.

  • The goal of all the tools below is to direct the team toward the highest-value change instead of guessing.
  • Scale drives progress: the two biggest levers of modern ML are (i) training a large enough model and (ii) feeding it enough data. Classical algorithms plateau as data grows; large neural nets keep improving.
  • This is the applied counterpart to the theory in Bias-Variance Tradeoff and Model Evaluation — same concepts, framed as decisions.
A simple, reliable recipe gets you surprisingly far: if avoidable bias is high → grow the model; if variance is high → add data. With enough compute and data, many problems become solvable. Everything else is about diagnosing which applies.

02 Dev / test sets: aim at the right target

Your dev and test sets define the target your team optimizes toward. Choose them to reflect the data you expect in the future and want to do well on — not just whatever you happen to have.

  • Training set — what the algorithm learns from. Dev (hold-out) set — used to tune parameters, pick features, make decisions. Test set — used only to estimate final performance, never to make decisions.
  • Dev and test must come from the same distribution. If they differ, you can optimize the dev set for weeks only to be judged on a different test set — you won't know if gains will transfer.
  • The old 70/30 split is obsolete at scale. Dev/test just need to be big enough: dev large enough to detect the improvements you care about (often 1k–10k examples to see a 0.1% gain); test large enough for a confident final estimate.
  • Change them quickly when they mislead: if you overfit the dev set → get fresh dev data; if the real distribution shifted → re-sample; if the metric rewards the wrong thing → change the metric.

03 A single-number evaluation metric

One number lets you instantly rank every model and iterate fast. Two numbers (precision AND recall) leave you guessing which model is better.

  • Combine multiple goals into one number — e.g. F1 (harmonic mean of precision/recall), or a weighted average of per-market accuracies.
  • Optimizing vs satisficing metrics: when you can't merge criteria sensibly (e.g. accuracy and runtime), pick one to optimize and set the rest as satisficing thresholds ("good enough"). Maximize accuracy subject to runtime ≤ 100 ms.
  • With N criteria, make N−1 satisficing and 1 optimizing. (Wakeword example: minimize false negatives subject to ≤ 1 false positive per 24 h.)
F1 = 2 / ( 1/Precision + 1/Recall ) · maximize: Accuracy s.t. RunTime ≤ 100ms

04 Build fast, then iterate

Don't design the perfect system up front. Build a basic system in days, then let error analysis point you to what matters.

Idea ─▶ Code ─▶ Experiment ─┐ ▲ │ └──────────────────────────────┘ the faster this loop spins, the faster you learn
  • Even experts try dozens of ideas before one sticks. A dev set + metric is what makes each turn of the loop fast and measurable.
  • The first system is a clue generator, not the final product. Its mistakes reveal where to invest.

05 Error analysis: look at the mistakes

Before spending a month on an idea, estimate its ceiling. Manually inspect ~100 misclassified dev examples and count categories — two hours of looking can save a month of building.

  • Ceiling estimate: if only 5% of errors are dogs, fixing "dogs" can cut error from 10% to at best 9.5%. If 50% are dogs, the same fix could take you 10% → 5%.
  • Evaluate ideas in parallel with a spreadsheet: one row per misclassified image, one column per hypothesized cause (dog, great cat, blurry, Instagram filter…). New categories will emerge as you look. Percentages needn't sum to 100% (an image can hit several).
  • Mislabeled examples: add a column to track them. Fix labels only when they materially distort the comparison (e.g. when 30% of your remaining errors are just bad labels). Apply the same fix to dev and test so they stay matched.

06 Eyeball & Blackbox dev sets

Manually staring at examples overfits your intuition to them. Split the dev set so you can tell when that's happening.

  • Eyeball dev set — the slice you look at by eye for error analysis. Blackbox dev set — the slice you only ever measure error on (tuning, model selection), never inspect.
  • If Eyeball performance pulls far ahead of Blackbox, you've overfit the Eyeball set — refresh it with new examples.
  • Sizing: the Eyeball set should produce enough mistakes to analyze — ~50 errors gives a good sense, ~100 a very good one. A 5%-error classifier needs ~2,000 Eyeball examples to surface 100 errors. Blackbox of 1k–10k is plenty. With little data, use the whole dev set as Eyeball.

07 Bias & variance — and the decomposition diagnoser

Error splits into bias (training error) and variance (how much worse dev is than train). But the most useful version subtracts the optimal / Bayes error rate to separate avoidable bias from the unavoidable floor.

  • Optimal (Bayes) error rate = the best any classifier could do. For tasks humans do well, estimate it with human-level performance. Some problems (very noisy speech) have an optimal error well above 0%.
  • Avoidable bias = training error − optimal error. Variance = dev error − training error. Reduce the bigger one first.
  • When train and dev/test come from different distributions, a third bucket appears — data mismatch — measured with a held-out train-dev set (same distribution as training, never trained on). See §10.
dev error = optimal (unavoidable) + avoidable bias + variance [ + data mismatch ] └─ Bayes floor ─┘ └ train − opt ┘ └ traindev − train ┘ └ dev − traindev ┘

08 What to do about each

High avoidable bias (underfit)High variance (overfit)
Best leversBigger model (more layers/units); train longer; better architectureMore training data; regularization (L1/L2, dropout); early stopping
AlsoReduce/remove regularization; new features from error analysisFeature selection (small data only); better-suited architecture
Doesn't helpMore data — it can't lower training errorShrinking the model (prefer regularization unless compute-bound)
  • The modern tradeoff is softer: with big nets + regularization you can grow the model to cut bias without raising variance, and add data to cut variance without raising bias — so the classic bias↔variance seesaw is less binding than it was.
  • Run error analysis on the training set too when bias is high — it reveals which examples the model can't even fit.

09 Learning curves: should you collect more data?

Plot dev error and training error against training-set size. Their levels and gap tell you whether more data will actually get you to the goal — before you spend months collecting it.

  • Dev error falls as data grows; training error rises (it's harder to fit more examples). Dev sits above training.
  • High bias: training error has plateaued above the desired line and the train↔dev gap is small → more data won't reach the goal. Fix bias.
  • High variance: training error is below desired but dev error is much higher and still descending → more data will help close the gap.
  • Curves can be noisy on small/skewed sets — average several random subsets, or use class-balanced subsets, and space sizes log-style (1k, 2k, 4k…) to save compute.

10 Comparing to human-level performance

For tasks people do well, human performance is a practical proxy for the optimal error rate — and a powerful accelerator while the machine is still catching up.

  • Three reasons it helps: (1) easy to get high-quality labels from humans; (2) error analysis can borrow human intuition ("why did you hear it right?"); (3) it estimates the optimal error rate, setting a sensible avoidable-bias target.
  • Define "human-level" as the best feasible human for the purpose of estimating optimal error — e.g. a team of doctors (2%) over a junior doctor (10%). The optimal rate can't be higher than what a human team achieves.
  • Surpassing humans: once you beat average human performance, progress slows — the three levers fade. But as long as there's a subset where humans still beat the model, you can keep using them there.

11 Training & testing on different distributions

In the big-data era, your training set often includes lots of data from a different distribution than what you care about (e.g. 200k web images to help recognize 10k mobile-app images). That's usually worth it — but it adds a new failure mode.

  • Keep dev/test pure: they should be only the distribution you care about (mobile images), never a random shuffle of everything. Put extra-distribution data (and some target data) into training.
  • Use all the data — usually. With a big enough net there's almost no downside to adding loosely-related data: a single mapping x→y works for both. Drop data only when it's inconsistent (NYC vs Detroit house prices: same size, different price) or genuinely irrelevant (scanned documents for a cat detector).
  • Weighting: if the extra data dwarfs the target data (40:1) and compute is limited, down-weight it (factor β) so the model still cares about the distribution you ship on.
  • The train-dev set isolates the new failure mode. Hold out data from the training distribution that you don't train on:
    • train ≪ train-dev gap → variance;   • train-dev ≪ dev gap → data mismatch;   • opt ≪ train gap → avoidable bias.
  • Addressing data mismatch: error-analyze the difference between training and dev (e.g. dev clips are recorded in cars), then get/make more matching data. Artificial data synthesis (add car noise to clean speech; add motion blur to web images) can manufacture it — but beware synthesizing from too narrow a source (1 h of car noise, 20 car models) or the model overfits the synthetic quirks.

12 The Optimization Verification test

A common AI pattern: learn an approximate scoring function Scorex(y), then use an approximate search (beam search, RL) to find arg maxy Scorex(y). When output is wrong, who's to blame — the search or the score?

  • Let y* be the correct (or a known-better, e.g. human) output and yout the model's output. Compute both scores:
  • If Score(y*) > Score(yout): the score function was right but search picked the worse option → fix the search algorithm (e.g. widen the beam).
  • If Score(y*) ≤ Score(yout): the scoring function rated the wrong answer higher → fix how you learn the score (the objective).
  • Run it across the dev errors to get the split (e.g. "95% are scoring-function faults") and prioritize accordingly. Works for speech (transcript), translation (sentence), and RL (compare reward of the model's trajectory vs a human pilot's).
Score(y*) > Score(y_out) → search algorithm is at fault Score(y*) ≤ Score(y_out) → objective / scoring function is at fault

13 Takeaways

  • Set the target first: dev/test from the distribution you care about (same as each other) + a single-number metric → fast, honest iteration.
  • Build fast, then read the clues with error analysis on ~100 mistakes; estimate each idea's ceiling before investing.
  • Diagnose, don't guess: decompose error into unavoidable (Bayes) + avoidable bias + variance + data mismatch, then attack the biggest bucket — bigger model for bias, more data/regularization for variance, matching data for mismatch.
  • Learning curves tell you in advance whether more data can even reach the goal.
  • Human-level performance estimates the optimal error and accelerates progress while you're behind it.
  • Optimization Verification separates a broken search from a broken objective. Deep dive: Bias-Variance · Model Evaluation · Hyperparameter Tuning.
