Model Evaluation & Metrics

Evaluation Methodology A model's score is a measurement, and every measurement can be wrong. This page is about producing a number you would be willing to bet on: the right metric for the cost structure, an honest split, a threshold you chose deliberately, and an estimate of how much of the number is noise.

01 Overview: what an evaluation is for

Evaluation answers one question — if I ship this, what happens? Everything else (accuracy, AUC, RMSE) is a proxy, and proxies leak.

Three failure modes account for almost every misleading result. First, optimistic splits: the model was scored on data it had already seen, directly (training data) or indirectly (a feature computed using the future, a duplicated row, a hyperparameter tuned on the test set). Second, the wrong metric: accuracy on a dataset that is 99% negative is beaten by a constant, and a metric that ignores the asymmetric cost of a missed fraud case will happily pick the worse model. Third, noise mistaken for signal: a 0.3-point gain on a 2,000-row test set is usually a coin flip, not an improvement.

Takeaway: a metric is a compression of a confusion matrix (or an error distribution) into one number. Always know what the compression threw away before you trust it.

02 The confusion matrix and everything derived from it

For binary classification with a fixed decision threshold, every prediction lands in one of four buckets. The whole family of classification metrics is just different ratios of these four counts.

  • True Positive (TP): predicted positive, actually positive.
  • False Positive (FP): predicted positive, actually negative — a Type I error, a false alarm.
  • True Negative (TN): predicted negative, actually negative.
  • False Negative (FN): predicted negative, actually positive — a Type II error, a miss.

The core ratios

Read each formula by its denominator: that tells you which population the metric conditions on. Precision conditions on what the model said; Recall conditions on what is actually true. That single distinction explains why precision moves when class balance changes and recall does not.

column-wise (conditioned on the truth) — stable under class imbalance Recall = TPR = Sensitivity = TP / (TP + FN) Specificity = TNR = TN / (TN + FP) FPR = 1 − Specificity = FP / (FP + TN) row-wise (conditioned on the prediction) — moves with prevalencePrecision = PPV = TP / (TP + FP) NPV = TN / (TN + FN) overallAccuracy = (TP + TN) / (TP + TN + FP + FN) Balanced Accuracy = ½·(TPR + TNR)
F-score — harmonic mean of precision and recall; β > 1 weights recall F₁ = 2·(P·R)/(P + R) = 2TP / (2TP + FP + FN) F_β = (1 + β²)·P·R / (β²·P + R) Matthews correlation — uses all four cells, symmetric in the classesMCC = (TP·TN − FP·FN) / √( (TP+FP)(TP+FN)(TN+FP)(TN+FN) ) ∈ [−1, 1]

A worked example: 1,000 emails, 50 of them spam

The filter flags 60 messages; 40 of them really are spam. So TP = 40, FP = 20, FN = 10, TN = 930.

the four counts, unpacked Accuracy = 970/1000 = 0.970 Precision = 40/60 = 0.667 Recall = 40/50 = 0.800 F₁ = 2(0.667)(0.800)/1.467 = 0.727 F₂ = 0.769 Specificity = 930/950 = 0.979 Balanced Accuracy = ½(0.800 + 0.979) = 0.889 MCC = 37000/√(60·50·950·940) = 0.715

Now compare against the model that predicts "never spam": it scores 0.950 accuracy — better-looking than nothing and only two points below our classifier — while its recall, F₁ and MCC are all 0. Accuracy is not merely a weak metric here, it actively ranks the useless model near the top. Balanced accuracy (0.500) and MCC (0.000) both correctly flag it as worthless.

Multi-class: the averaging choice is a modelling decision

With C classes the matrix is C × C; per-class metrics are computed one-vs-rest and then pooled. Macro averaging takes the unweighted mean over classes, so a 10-sample rare class counts as much as a 10,000-sample common one — use it when rare classes matter. Micro averaging pools the counts first, so it is dominated by frequent classes (and in single-label problems micro-F₁ equals accuracy). Weighted averaging sits between them, weighting each class by its support. Reporting "F₁ = 0.82" without saying which average is not a number anyone can act on.

Takeaway: pick the metric from the cost of each cell, not from habit. If a FP costs €1 and a FN costs €200, optimise expected cost directly; F₁ is only a reasonable default when the two errors hurt roughly equally and the positive class is rare.

04 ROC/AUC versus PR/AP — and when each lies

Most classifiers emit a score, not a label. Sweeping the threshold from +∞ down to −∞ traces a curve of operating points, and summarising that curve gives a threshold-free measure of ranking quality.

ROC and AUC

The ROC curve plots TPR against FPR across all thresholds. The area under it, AUC, has an exact probabilistic meaning: it is the probability that a randomly drawn positive is scored above a randomly drawn negative (ties counting a half). That is the normalised Mann–Whitney U statistic, which is why AUC can be computed from ranks alone.

AUC as a ranking probability AUC = P( s(x⁺) > s(x⁻) ) + ½·P( s(x⁺) = s(x⁻) ) rank form over n₊ positives and n₋ negativesAUC = ( ∑ᵢ∈pos rank(sᵢ) − n₊(n₊+1)/2 ) / (n₊ · n₋) AUC = 1.0 → perfect separation AUC = 0.5 → chance (the diagonal) AUC < 0.5 → the scores are inverted

Precision–recall and average precision

The PR curve plots precision against recall. Its chance baseline is not a diagonal but the horizontal line precision = prevalence π, so on a 1%-positive problem a "good-looking" PR curve at 0.05 precision is barely above random. Average Precision (AP) summarises it as a recall-weighted mean of precision, which is the sample estimate of the area under the PR curve without the optimistic interpolation that trapezoids introduce.

average precision — Rₙ, Pₙ are recall/precision at the n-th threshold AP = ∑ₙ (Rₙ − Rₙ₋₁) · Pₙ baseline AP ≈ π (the positive rate) the exact link between precision, recall and prevalencePrecision = π·TPR / ( π·TPR + (1 − π)·FPR )

That last identity is the whole story: at π = 0.5 a classifier with TPR 0.8 and FPR 0.02 has precision 0.976; at π = 0.01 the same classifier — same ROC point, same model — has precision 0.008/(0.008 + 0.0198) = 0.288. Nothing about the model changed; only the base rate did.

Takeaway: AUC measures ranking, PR/AP measures ranking under scarcity, log loss measures probability quality. A single model can be excellent on one and mediocre on another — that is information, not contradiction.

05 Thresholds and calibration

A threshold-free metric defers a decision that eventually has to be made. Choosing the threshold is a separate optimisation problem, and 0.5 is almost never the right answer.

The cost-optimal threshold

Let a false positive cost c_FP and a false negative cost c_FN. If the model outputs a genuine probability p = P(y = 1 | x), the expected cost of saying "positive" is (1 − p)·c_FP and of saying "negative" is p·c_FN. Setting them equal gives the break-even point.

Bayes-optimal decision threshold under asymmetric costs (1 − p)·c_FP = p·c_FN ⟹ t* = c_FP / (c_FP + c_FN) example: a missed fraud costs 200, a false alarm costs 1t* = 1/201 ≈ 0.005 ← flag anything above half a percent

The formula assumes p is calibrated — apply it to uncalibrated scores and the threshold lands on the wrong scale. If costs are unknown, tune the threshold on a validation split against the operating metric (F_β, precision at fixed recall), never on the test set.

Calibration: does 0.7 mean 70%?

A model is calibrated when, among all cases it scores at p, a fraction p are actually positive. Rankers can be badly uncalibrated and still have AUC 0.95. Calibration is measured with the Brier score (mean squared error on probabilities), log loss, and expected calibration error, which bins predictions and compares average confidence to average accuracy per bin. A reliability diagram plots that per bin against the diagonal.

proper scoring rules — minimised only by the true probability Brier = (1/n)·∑ᵢ (pᵢ − yᵢ)² LogLoss = −(1/n)·∑ᵢ [ yᵢ·ln pᵢ + (1 − yᵢ)·ln(1 − pᵢ) ] expected calibration error over B binsECE = ∑_b (n_b / n)·| acc(b) − conf(b) |

Typical offenders: boosted trees and SVMs (scores pushed to the extremes or living on an arbitrary margin scale), over-parameterised networks (systematically over-confident), and anything trained on resampled data (up-sampling positives inflates every predicted probability). Fixes are cheap post-hoc maps fitted on held-out data: Platt scaling (a 1-D logistic regression on the scores), isotonic regression (non-parametric and monotone, but data-hungry), and temperature scaling for networks — divide the logits by one learned T, which changes no argmax and therefore no accuracy.

Takeaway: ranking quality and probability quality are different properties. If a downstream system multiplies your output by a euro amount, you need calibration; if a human just reads a sorted list, you need ranking.

06 Regression metrics

For continuous targets, the metric encodes which errors you are willing to tolerate. The choice is not cosmetic: each metric is minimised by a different statistic of the conditional distribution.

absolute vs squared error MAE = (1/n)·∑ᵢ |yᵢ − ŷᵢ| MSE = (1/n)·∑ᵢ (yᵢ − ŷᵢ)² RMSE = √MSE scale-free fit qualityR² = 1 − SS_res/SS_tot = 1 − ∑ᵢ(yᵢ − ŷᵢ)² / ∑ᵢ(yᵢ − ȳ)² R²_adj = 1 − (1 − R²)·(n − 1)/(n − p − 1) ← penalises the p predictors relative errorMAPE = (100/n)·∑ᵢ |yᵢ − ŷᵢ| / |yᵢ| sMAPE = (100/n)·∑ᵢ 2|yᵢ − ŷᵢ| / (|yᵢ| + |ŷᵢ|)

Which statistic each one is asking for

Minimising MSE pushes ŷ toward the conditional mean; minimising MAE pushes it toward the conditional median; minimising the pinball loss ρ_τ(e) = max(τe, (τ−1)e) targets the τ-quantile. So "MAE is more robust to outliers" is not a folk rule — it follows from the fact that the median is robust and the mean is not. RMSE is in the units of y (readable) but is always ≥ MAE, with the gap widening as the error distribution gets heavier-tailed; the ratio RMSE/MAE is a free outlier diagnostic.

Traps

R² is only "proportion of variance explained" relative to the mean of the evaluated set; computed on a test set it can be negative, which simply means you did worse than predicting the training mean. It also rises mechanically with every added predictor, hence the adjusted form. MAPE explodes when any yᵢ nears zero, is undefined at zero, and is asymmetric: it punishes over-prediction harder than under-prediction, which quietly biases forecasting models downward. For time series prefer a scaled error such as MASE, which divides the MAE by the MAE of a naïve seasonal forecast — values below 1 mean you beat "repeat last season".

Takeaway: choose the loss you evaluate with and the loss you train with to match. Training on MSE and reporting MAE means the model is optimising a target you are not measuring.

07 Splits and cross-validation schemes

The split's job is to simulate deployment. Whatever shift the model will face in production — new users, new time periods, new hospitals — the split should reproduce it. A random shuffle is the right choice only when production really does draw i.i.d. from the same pool.

The three-way split

Train fits parameters, validation selects hyperparameters, architecture and threshold, test is touched once to produce the number you report. Every time you look at the test set and change something it becomes a second validation set, and its estimate turns optimistic. With small data, replace the fixed validation split with cross-validation but keep the test set separate.

k-fold and its variants

Partition into k folds, train on k − 1, score on the held-out one, rotate, average. Every point is used for validation exactly once, and the standard deviation across folds gives a rough sense of stability. k = 5 or 10 is the usual compromise: larger k means less bias (more training data per fit) but higher variance and k times the compute.

Time series needs more than "don't shuffle"

Use an expanding window (train on everything up to time t, test on t+1…t+h, roll forward) or a sliding window if the process is non-stationary and old data hurts. When labels are built from a forward-looking horizon — "did this customer churn within 30 days?" — adjacent train and test rows share outcome periods, so add a purge (drop rows whose label window overlaps the test window) and an embargo (drop a further gap after it). Also match the horizon: if production predicts 7 days ahead, validate 7 days ahead, not 1.

Takeaway: nested CV exists because selection is also fitting. If you picked the best of 200 configurations by inner-fold score, that best score is biased upward by exactly the amount you searched.

08 Data leakage

Leakage is any path by which information unavailable at prediction time reaches the model during training. It is the single most common cause of a model that scores 0.99 offline and fails in production, and it is invisible to every metric on this page — leaked evaluations look excellent.

The recurring shapes

  • Preprocessing before splitting. Fitting a scaler, imputer, target encoder, feature selector or PCA on the full dataset lets test statistics into the training pipeline. Fit every transform inside the fold, on training rows only, and apply it to the validation rows.
  • Target leakage. A feature that is a consequence of the label rather than a cause: number_of_treatments for predicting diagnosis, refund_issued for predicting fraud, an ID assigned after the outcome. The tell is a single feature with implausible importance.
  • Temporal leakage. Aggregates computed over the whole history ("customer's average order value") that include future orders. Every feature needs an as-of timestamp.
  • Duplicate or near-duplicate rows split across train and test — common in scraped, augmented or oversampled data. Note that resampling before the split copies the same minority rows into both sides.
  • Group leakage. The same patient, user, session or product appearing on both sides. Split by group, not by row.

The structural defence is to express the entire pipeline — imputation, encoding, scaling, selection, model — as one object fitted only on training folds. A quick smell test: shuffle the labels and re-run. A clean pipeline collapses to chance; if it does not, information is arriving from somewhere it should not.

Takeaway: suspiciously good results are a bug report, not a success. Investigate every score that beats your expectation by a wide margin before you present it.

09 Comparing models, and the offline↔online gap

"Model B beat model A by 0.4 points" is a claim about a population made from a sample, so it needs an interval and a test, not just a comparison of two decimals.

Quantifying the uncertainty

The cheapest honest tool is the bootstrap: resample the test set with replacement B ≈ 1000 times, recompute the metric on each resample, and take the 2.5th and 97.5th percentiles as a 95% interval. Crucially, resample the same indices for both models and bootstrap the difference — the paired interval is far tighter than two separate ones because the two models make correlated errors on the same rows. For a rough sanity bound on accuracy, the binomial standard error is √(p(1−p)/n): at p = 0.9 and n = 1000 that is about 0.9 points, so a 0.4-point "win" is inside the noise.

McNemar's test on paired predictions — b = A right/B wrong, c = A wrong/B right χ² = ( |b − c| − 1 )² / (b + c) ≈ χ²₁ under H₀: the two models err equally binomial standard error of an accuracy estimateSE = √( p(1 − p) / n ) n = 1000, p = 0.90 ⟹ SE ≈ 0.0095

Only the discordant pairs carry information: rows both models get right, or both get wrong, say nothing about which is better. Comparing across CV folds is harder still, because folds share training data and are not independent — a naive paired t-test is badly anti-conservative, so use a variance-corrected resampled version. And when comparing many models, correct for multiple comparisons or you will "discover" a winner by chance.

Why the offline number does not survive contact with production

Offline evaluation scores a model on a logged distribution; production runs it on a distribution the model itself creates. A recommender trained on clicks from the old ranker only ever sees feedback about items the old ranker showed — confounded, partial-feedback data, which is why off-policy estimators exist. Add distribution shift between the log window and today, latency and fallback behaviour that never appear in a notebook, and the fact that the offline metric is a proxy for a business metric it may track only weakly.

The practical stance: treat offline evaluation as a filter that cheaply rejects bad candidates, and treat the online experiment as the decision. Before running the experiment, verify that the offline metric has historically moved in the same direction as the online one — if it has not, you are tuning the wrong proxy. See A/B Testing for randomisation, power and sequential-peeking hazards, and Monitoring & Drift for detecting when a shipped model's inputs stop resembling its training set.

Takeaway: report intervals, test paired differences, and never treat an offline improvement as a result — treat it as a hypothesis worth an experiment.

10 Pitfalls & what to remember

  • Accuracy on imbalanced data. Always compare against the majority-class baseline; if you cannot beat it convincingly, you have no model.
  • Reusing the test set. Every peek costs a little of its independence. Decide the metric and the split before you start.
  • Threshold left at 0.5. A default, not a decision. Tune it on validation data against your cost structure.
  • Resampling before splitting. SMOTE or up-sampling applied to the whole dataset duplicates minority rows into both train and test. It also shifts the base rate, so recalibrate before reading probabilities.
  • Comparing metrics across datasets. AUC 0.85 on one test set and 0.83 on another says nothing; difficulty and prevalence differ.
  • Single-number reporting. One aggregate hides subgroup failure. Slice by segment, class, time window and input length — a model can be fine overall and useless for the group that matters.
  • Ignoring variance. Retrain with a different seed. If the gain vanishes, it was seed noise.
  • Optimising a proxy to death. Once a metric becomes the target it stops being a good measure; keep at least one guardrail metric that you are not optimising.
The one idea: an evaluation is an experiment about the future. Build the split to imitate deployment, choose the metric from the decision it feeds, attach an interval to every number, and confirm online before you believe it.
