CI/CD for Machine Learning

Continuous integration and delivery make every change pass the same automated checks before it reaches users. ML adds two things that change independently of code — the data and the trained model — so the pipeline must test all three, version all three, and gate promotion on statistical evidence rather than a green unit-test run.

MLOps & Deployment Automation Testing Release engineering

01 Why ML pipelines need more than software CI/CD

In ordinary software, behaviour is a function of code. In ML, behaviour is a function of code, data, and the training process — and any of the three can break production without a single line changing.

what can change a deployed system's behavioursoftware: behaviour = f(code, config) ML: behaviour = f(code, config, data, trained weights, upstream features)
  • Silent failure is the default. A broken join that doubles a feature's scale still produces predictions, still passes type checks, and still returns HTTP 200. Only data and model tests catch it.
  • Tests are statistical. "Accuracy ≥ 0.91" on a finite evaluation set is a noisy measurement; a gate that ignores noise either blocks good models or ships bad ones (§06).
  • The pipeline is the product. In mature setups you deploy the training pipeline, which then produces models continuously; the model is an output of the deployed system, not a hand-made release.

Cheap, fast, numerous tests at the bottom; expensive, slow, few at the top. Ordering checks from cheap to expensive makes the pipeline fail fast.

Takeaway: data validation is the most under-built layer and the one that catches the most real incidents. A schema check running before training costs seconds and prevents a day of training on broken input.

04 Data validation as code

  • Express expectations declaratively and version them with the pipeline: a schema (column, type, nullable, allowed range or categories) plus statistical checks against a reference profile computed on training data.
  • Two thresholds per check: warn (log, notify, continue) and fail (stop the pipeline). Everything failing hard leads to people disabling the checks.
  • Validate at boundaries: on ingestion (reject bad batches early), before training (protect the model), and on serving traffic (the same checks become monitoring — see Monitoring & Drift).
  • Quarantine, don't drop: failing rows or batches go to a quarantine table for inspection, so the pipeline does not silently shrink the training set. The broader practice is in Data Quality & Governance.
typical check familynull_rate(col) = #null / n ≤ τ_null min ≤ col ≤ max PSI(col; reference) < 0.25 |n_batch − n_expected| / n_expected ≤ 20%

05 Model quality gates and behavioural tests

A gate is a decision rule: given the candidate's measurements, promote or block. Good gates are relative to the champion, aware of noise, and checked on slices.

  • Absolute floor: never ship below a minimum (e.g. recall ≥ 0.80 on the fraud class) regardless of the champion.
  • Relative to the champion, with a margin: require the candidate to be non-inferior — not worse than the champion by more than a margin δ — using the lower confidence bound, not the point estimate. Evaluate both on the same, fixed evaluation set (paired comparison) to cut variance.
  • Slice gates: an overall gain can hide a regression on a small segment (a country, a device type, a protected group). Gate on the worst slice as well as the aggregate.
  • Operational gates: p99 latency, model size, memory, and cost per prediction against budgets.
  • Behavioural tests catch what aggregate metrics miss: minimum functionality (simple cases must be right), invariance (irrelevant perturbations must not change output), directional expectation (a known-monotone input moves output the right way).
  • Golden set regression: a curated set of hard, important examples whose predictions must not flip without review.
non-inferiority gate on a paired metric differenceΔ̂ = m_candidate − m_champion promote iff Δ̂ − 1.96 · SE(Δ̂) ≥ −δ and every slice s: m_candidate,s ≥ m_champion,s − δ_slice

07 Gates are noisy: the operating characteristic

A quality gate is a hypothesis test. Its pass probability as a function of the candidate's true improvement is its operating characteristic — the same idea as a power curve in Hypothesis Testing.

probability the non-inferiority gate passesP(pass | Δ) = Φ( (Δ + δ) / SE − 1.96 ) SE ∝ 1 / √n_eval
Gate operating characteristic ideal gate = step function at −δ · illustrative SE = 0.3/√n · bigger evaluation sets sharpen it
  • Read the default: with 10,000 evaluation examples and δ = 0.005, a candidate exactly as good as the champion passes only about 38% of the time, because the lower-bound rule demands evidence of non-inferiority. A retrain that merely matches the champion will be blocked more often than not — either accept that (conservative), widen δ, or grow the evaluation set until the curve is steep.
  • Small evaluation sets make gates flaky: the same candidate passes on Monday and fails on Tuesday. Teams then rerun until green — which turns the gate into the winner's-curse selection described in Experiment Tracking.
  • Fix the evaluation set (versioned, refreshed on a schedule) and use paired comparisons, so run-to-run noise comes from the model, not from resampling the data.

08 Pipelines as code

  • Define the pipeline as a DAG of containerized steps in version-controlled code: ingest → validate → featurize → train → evaluate → register → deploy. The same definition runs locally, in CI on sample data, and in production on full data.
  • Steps are pure functions of their inputs. Each step reads versioned inputs and writes versioned outputs, which enables step caching: if nothing upstream changed, reuse the output.
  • Parameterize, don't fork: environment, data window, and hyperparameters are inputs, not copies of the pipeline file.
  • Separate definition from trigger: the same pipeline is triggered by a merge (CI), a schedule (CT), or an alert (drift-triggered retraining).
  • Orchestration, retries and backfills are shared with ETL Pipelines; ML pipelines are ETL pipelines whose final load step is a model.
step cache key — rerun only when something it depends on changedkey(step) = hash( step code · container digest · params · key(upstream₁) · … · key(upstreamₖ) )

  • Build once, promote many. The artifact tested in staging must be the bit-identical artifact deployed to production. Rebuilding per environment reintroduces every dependency-resolution risk.
  • Environments: dev → staging → production, differing only in config and data access. Staging needs production-like data volume and traffic replay to make performance gates meaningful.
  • Promotion is a recorded event: who or what moved which version to which environment, when, with links to the gate results. That record is the audit trail.
  • Deployment strategy after promotion — shadow, canary, blue-green, rollback — is covered in Model Deployment; statistical comparison of live variants in A/B Testing.

10 Continuous training: triggers and safeguards

TriggerProsCons
Schedule (daily, weekly)Predictable cost and cadence; simpleRetrains when nothing changed; too slow after sudden shifts

Drift alertReacts to changeMost alerts are pipeline bugs; retraining on broken data bakes the bug in
Performance drop (labelled outcomes)Directly targets qualityLabels arrive late; damage already done
  • Automate training, gate promotion. A retrained model enters the same validation gates as any candidate; automatic retraining without gates is how a corrupt data week reaches production.
  • Training-window choice (sliding vs expanding, sample weighting by recency) is a modelling decision; record it as a pipeline parameter.
  • Feedback loops: when a model's predictions influence the labels it is retrained on (recommendations, credit approvals), CT can amplify bias. Keep an exploration slice or holdout population that the model does not influence.
