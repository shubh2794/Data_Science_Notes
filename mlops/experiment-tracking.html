Experiment Tracking

Model development is a search through hundreds of runs that differ by one flag, one data snapshot, or one library version. Experiment tracking is the lab notebook that records every run in a queryable form — so a number on a slide can be traced back to the exact code, data, configuration, and environment that produced it, and reproduced on demand.

01 The problem: results without provenance

Without tracking, the best model is a file called final_v3_really_final.pt and nobody knows which learning rate or which week's data produced it.

  • ML code is data-dependent: the same commit trained on Tuesday's and Wednesday's snapshot gives two different models. Version control of code alone (see Git) is necessary but nowhere near sufficient.
  • Iteration is wide: a tuning sweep produces dozens to thousands of runs. Spreadsheets and filenames break at about the tenth one.
  • Three questions a tracker must answer instantly: What did I run? (configuration and inputs) What happened? (metrics, curves, outputs) Can I get it back? (artifacts plus everything needed to regenerate them).
  • Downstream consumers — reviewers, the deployment pipeline, auditors — need the same answers. Tracking is the foundation that the model registry, CI/CD promotion gates and monitoring baselines are built on.
Takeaway: a metric without lineage is an anecdote. The goal is not pretty charts; it is being able to answer "where did this number come from?" six months later.

  • Behind the scenes a tracker is two stores: a metadata store (a relational database holding runs, params, metrics, tags) and an artifact store (object storage holding blobs, referenced by URI). See §10.

03 Reproducibility: the five things a run is a function of

A trained model is the output of a function. To reproduce it you must pin every argument — and know which ones are silently nondeterministic.

  • Bitwise vs statistical reproducibility. GPU kernels that use atomic adds, autotuned convolution algorithms, and multi-worker data order make bitwise-identical results expensive or impossible. Frameworks expose a "deterministic" mode that trades speed for repeatability. The practical standard is usually statistical: re-running yields a metric inside the run-to-run noise band.
  • That means you must measure the noise band: train the same config with 3–5 seeds and report mean ± spread. A "+0.3%" improvement that sits inside a ±0.5% seed spread is not an improvement.
  • Data lineage extends upstream: the snapshot id should point back through the ETL pipeline run that built it and, for features, the feature store definitions and the point-in-time join used.

04 What and how to log

  • At launch: resolved config, data snapshot id, commit hash, environment digest, seed, hardware. These are cheap and are the ones people forget.
  • During training: loss and key metrics per step (or every N steps), learning-rate schedule, gradient norm, throughput (samples/s), accelerator memory and utilization. Log with both step and wall time so runs on different hardware stay comparable.
  • At the end: final metrics on validation and per-slice breakdowns, the model artifact with its input/output signature, an example input, evaluation plots, and the prediction file for error analysis.
  • Autologging hooks into framework training loops and captures params, metrics and the model with one line. Useful as a floor, but it does not know your data snapshot id or business metric — add those explicitly.
  • Operational hygiene: log asynchronously and buffer locally so a tracker outage never kills a multi-day training job; throttle per-step logging (millions of points per run make the UI unusable); keep naming conventions (val/auc, train/loss) consistent so cross-run queries work.
  • Log failures too. Crashed and diverged runs are evidence about the search space. Deleting them biases every later conclusion toward configurations that happened to be stable.

05 Comparing runs and reading a sweep

A run table answers "which run won"; overlaid curves answer "how did it get there"; parallel coordinates answer "which region of the search space is good".

  • Run table: one row per run, columns for chosen params and summary metrics, sortable and filterable. The minimal comparison view.
  • Overlaid learning curves: spot divergence, overfitting (train falls while validation rises), and runs stopped too early. Smooth with an exponential moving average but keep the raw series visible.
  • Parallel coordinates: one vertical axis per hyperparameter plus the metric; each run is a polyline. Brushing an interval on the metric axis reveals which parameter ranges the good runs share. Use a log axis for scale-like parameters (learning rate, weight decay).
  • Parameter importance: fit a quick surrogate (random forest or correlation) from params to metric to rank which knobs matter — a hint for narrowing the next sweep, not a causal claim.

06 Sweeps as tracked objects

  • A sweep is a search space + search strategy + objective + budget. Store all four with the parent run so the search itself is reproducible. Strategies (grid, random, Bayesian optimization, Hyperband-style early stopping) are covered in Hyperparameter Tuning.
  • Early-stopped trials must be marked as pruned, not deleted — their partial curves are what the scheduler used to decide.
  • Record the number of trials and total compute. Both are needed to interpret the winner (§07) and to compare methods fairly: a method that "wins" with ten times the trials has not won.
  • Parallel workers write to the same experiment concurrently; the tracker must handle concurrent appends and give each trial a unique id independent of worker hostname.

07 The pitfall: selection bias from many runs on one validation set

Every time you pick the best of N runs by validation score, you select partly on noise. The reported validation score of the winner is optimistically biased, and the bias grows with N.

  • Each validation score is v̂ᵢ = vᵢ + εᵢ: true quality plus sampling noise from a finite validation set. Taking the max picks runs whose noise happened to be positive — the winner's curse.
  • For accuracy on n validation examples the noise standard deviation is roughly √(p(1 − p)/n). With n = 2,000 and p ≈ 0.8 that is about 0.9 percentage points — larger than many claimed improvements.
  • When true qualities are close, the expected max of N noisy draws grows like the extreme-value rate below, so 200 runs can inflate the winner by two to three noise standard deviations.
noise per validation score, and the optimism of the best of Nσ̂ ≈ √( p(1 − p) / n_val ) E[ maxi≤N εᵢ ] ≈ σ̂ · √(2 ln N) (asymptotic; overstates the bias for small N — the simulation shows the exact value)
Winner's curse simulator N runs with nearly identical true accuracy, scored on a finite validation set

Remedies

  • A test set touched once. Select on validation, report on a held-out test set that never influenced any decision. If you look at test results and then change something, it has become a second validation set.
  • Re-evaluate the finalists. Retrain the top-k configs with fresh seeds and score them on fresh data; the ranking often reshuffles.
  • Nested cross-validation when data is small: the inner loop selects, the outer loop estimates (see Model Evaluation).
  • Report N. "Best of 300 runs" and "best of 3 runs" with the same score are different claims. Comparing many configurations is a multiple-comparisons problem — the same logic as in ANOVA & Multiple Comparisons.
  • Rotate or refresh validation data on long-lived projects; a validation set used for a year of decisions is overfit by the team, not just the model.

08 The model registry: from run to deployable version

The tracker records everything that was tried; the registry records the few things that are candidates for production, with an auditable lifecycle.

  • A registered model is a named entity (fraud-scorer); each registration of an artifact creates an immutable, monotonically numbered version that links back to its source run — and therefore to code, data, config and environment.
  • Lifecycle labels. The classic scheme uses fixed stages — None → Staging → Production → Archived. Newer registries favour free-form, movable aliases (@champion, @challenger) plus tags (validation_status=approved), because fixed stages cannot express "two production models in two regions" or shadow candidates.
  • Serving resolves an alias, not a version number. Promotion and rollback become a metadata update — point @champion at version 12 or back at 11 — with no rebuild. The rollout mechanics are in Model Deployment.
  • Gate the transitions. Moving an alias to production should require passing automated checks (quality vs the current champion, latency, data validation, fairness slices) and, for regulated domains, a human approval recorded with who and when. These gates are pipeline stages in CI/CD.
  • Model metadata travels with the version: input/output schema, intended use, training data window, evaluation per slice, known limitations — a model card. This is the governance record auditors ask for (see Data Quality & Governance).

09 Tracker architecture and failure modes

  • Clients (training scripts, notebooks) call a tracking API. The server writes run metadata to a relational metadata store and either uploads artifacts itself or hands clients signed URLs to write directly to an artifact store (object storage).
  • Scaling pressure is almost always metric points: 1,000 runs × 100k steps × 20 metrics is 2 billion rows. Downsample at log time, store summary metrics separately, and index the columns you filter on.
  • Artifacts dominate storage cost. Checkpoints every epoch for every sweep trial add up to terabytes. Apply retention policies: keep the best and last checkpoint, expire the rest, never expire anything a registry version references.
  • Access control and PII. Logged prediction samples and example inputs can contain personal data; the artifact store inherits the data's governance obligations.

11 Takeaways

  • Schema: experiments contain runs; runs carry write-once params, append-only metrics, immutable artifacts, and auto-captured system metadata.
  • Reproducibility means pinning code, data, config, environment and seed — and measuring the seed noise band, since bitwise determinism is often unaffordable.
  • Selecting the best of N on one validation set inflates the score by roughly σ̂·√(2 ln N); keep an untouched test set and report N.
  • The registry turns a run into a versioned, aliased, gated deployable; serving resolves aliases so promotion and rollback are metadata changes.
  • Lineage must be walkable from the live endpoint back to the data snapshot — that is the test of whether tracking is working.
