LLM Serving & Inference Optimization

A trained model is a file. Making it answer millions of requests per day at acceptable latency and cost is serving — a separate engineering discipline from training, with its own bottlenecks, metrics, and tricks. This page covers the full stack: hardware limits, quantization, memory management, batching, parallelism, frameworks, and scaling.

MLOps & Deployment Inference LLM Serving Efficiency

01 Why serving is its own problem

Training touches each example once; inference touches every user request forever. A 1% efficiency gain in serving compounds into millions of dollars saved per year.

  • Inference dominates lifetime cost. Training a frontier model is a one-time (or few-time) expense. Inference runs 24/7 at scale, and for popular models the cumulative inference spend vastly exceeds training spend within months.
  • Two computational bottlenecks. Every operation is either compute-bound (limited by FLOPS — the GPU cannot multiply fast enough) or memory-bandwidth-bound (limited by how fast you can read weights from HBM). The roofline model draws the boundary.
  • Arithmetic intensity is the ratio of operations to bytes transferred. If a workload's arithmetic intensity exceeds the hardware's ops-per-byte ceiling, it is compute-bound; below that ceiling, it is memory-bound.
  • Prefill phase — processes all input tokens in parallel. Large matrix multiplications with high arithmetic intensity → compute-bound. This is why longer prompts increase TTFT.
  • Decode phase — generates one token at a time, autoregressively. Each step loads the full weight matrices but performs relatively few operations per weight → memory-bandwidth-bound. This is the fundamental bottleneck for token throughput.
  • Online vs. batch. Online APIs optimize latency (respond fast). Batch APIs optimize cost (queue requests, fill GPU utilization — often ~50% cheaper). Many providers now offer both tiers.

Key insight: prefill and decode have fundamentally different hardware profiles. This asymmetry motivates almost every optimization on this page — from batching (raise decode's arithmetic intensity) to disaggregated serving (put each phase on its ideal hardware).

02 Performance metrics

You cannot optimize what you do not measure. LLM serving has its own metric vocabulary, distinct from training metrics.

  • TTFT (Time to First Token). How long the user waits before any output appears. Dominated by prefill time. Target: <500ms for interactive apps, <200ms for conversational feel.
  • TPOT (Time per Output Token). The interval between consecutive generated tokens. Dominated by decode speed. Target: <50ms for real-time streaming (>20 tokens/sec feels fluid).
  • End-to-end latency. TTFT + (n_output_tokens × TPOT). For a 500-token response: TTFT + 500 × TPOT.
  • Throughput. Tokens per second across the whole system (all concurrent requests). The primary cost metric — higher throughput means more work per GPU-hour.
  • Latency percentiles. p50 tells you the typical experience. p95 and p99 tell you the tail — which is what SLOs are usually written against. Head-of-line blocking in static batching makes tails worse.
  • Streaming. Return tokens as generated rather than waiting for the full response. Reduces perceived latency dramatically even if total latency is unchanged. Most production APIs default to streaming.
  • Goodput. Throughput of requests that actually meet the SLO. A system can have high raw throughput but low goodput if too many requests miss their latency target.
end-to-end latency Te2e = Tprefill + noutput × Tdecode_step
throughput tokens/sec = concurrent_requests × tokens_per_request / Te2e

03 Quantization for serving

The single biggest lever for serving cost. Fewer bits per weight means smaller models, less memory bandwidth consumed, and faster decode — often with negligible quality loss. See also Model Acceleration for the broader picture.

  • Why it helps decode so much. Decode is memory-bandwidth-bound: you load the entire weight matrix to produce one token. Halving weight precision roughly halves the bytes loaded per step → roughly 2x decode speedup.
  • GPTQ — post-training quantization using second-order (Hessian) information to minimize layer-wise reconstruction error. Processes one layer at a time, quantizes weights to 4-bit or 3-bit. Requires a small calibration set. Produces GPU-friendly quantized weights.
  • AWQ (Activation-Aware Weight Quantization) — observes that a small fraction of weight channels matter disproportionately (because their corresponding activations are large). Protects those salient channels with per-channel scaling before quantizing to 4-bit. Often better quality than GPTQ at the same bit width.
  • SmoothQuant — migrates the quantization difficulty from activations (which have outlier channels) to weights (which are easier to quantize) via mathematically equivalent per-channel scaling. Enables W8A8 (8-bit weights and activations) with minimal loss.
  • GGUF — the quantization format used by llama.cpp. CPU-optimized with various quantization levels (Q4_K_M, Q5_K_S, etc.). Popular for local/edge deployment. Supports mixed quantization: more bits for attention layers, fewer for FFN.
  • bitsandbytes — integrates directly with HuggingFace Transformers. LLM.int8() uses mixed-precision decomposition: outlier features stay in FP16, the rest go to INT8. NF4 (4-bit NormalFloat) quantizes weights to a 4-bit data type optimized for normally-distributed weights — the format behind QLoRA.
  • FP8 — native 8-bit floating point on NVIDIA Hopper (H100) and newer GPUs. Two variants: E4M3 (more precision, for weights/activations) and E5M2 (more range, for gradients). Hardware-accelerated — no custom kernels needed. The default for new deployments on Hopper.

04 KV cache & memory

During decode, the model recomputes attention over all previous tokens. The KV cache stores the key and value projections so they are computed once and reused. It is also the largest dynamic memory consumer — and the main bottleneck for concurrent requests. See also KV Cache & Generation.

For a 70B model (80 layers, 8 KV heads GQA, d=128, FP16, 4K context): 2 × 80 × 8 × 128 × 4096 × 2 bytes ≈ 1.3 GB per sequence. Serving 32 concurrent requests = ~42 GB just for KV cache.

  • Multi-Query Attention (MQA). All query heads share a single KV head. Reduces KV cache by n_heads× (e.g. 32x for a 32-head model). Used by PaLM, Falcon. Slight quality loss.
  • Grouped-Query Attention (GQA). A compromise: a few KV head groups (e.g. 8 groups for 32 query heads → 4x reduction). Used by Llama 2 70B, Llama 3, Mistral. Near-MHA quality with most of the MQA memory savings.
  • PagedAttention (vLLM). Instead of pre-allocating a contiguous KV cache for the maximum sequence length, PagedAttention manages KV cache in fixed-size blocks (like virtual memory pages). A block table per sequence maps logical positions to physical blocks. Benefits:
    • Eliminates internal fragmentation — near-zero wasted memory
    • Enables memory sharing — beam search candidates and parallel samples share common prefix blocks (copy-on-write)
    • Dynamic allocation — sequences only consume memory they actually need
    In practice, PagedAttention increases concurrent batch size by 2–4x over naive allocation, directly boosting throughput.
  • Token eviction / attention sinking. Drop KV entries for middle tokens, keeping the first few (attention sinks) and recent tokens (sliding window). StreamingLLM showed attention sinks are critical for stable perplexity on long sequences.
  • KV cache quantization. Quantize cached keys/values to INT8 or INT4, halving or quartering cache memory. Modest quality impact since the cache is used in attention softmax, which is somewhat robust to noise.
Why this matters for cost: KV cache memory directly limits how many requests you can serve concurrently. Halving KV cache size (via GQA, quantization, or paging) roughly doubles your throughput for the same GPU. Every optimization on this page is ultimately about fitting more concurrent sequences in memory.

05 Continuous batching

The difference between a GPU sitting 30% idle and one running at 90% utilization is usually just the batching strategy.

  • Static (naive) batching. Group N requests, run them together, return results when the slowest sequence finishes. Short sequences pad and waste compute. The batch cannot accept new requests until all sequences complete. GPU utilization drops as sequences finish at different times.
  • Continuous (in-flight) batching. Operate at the iteration level: after each decode step, evict finished sequences and insert waiting ones. Every decode iteration runs with the maximum feasible batch size. Pioneered by Orca (2022), now the default in all major serving frameworks.
  • Why it matters so much. In static batching, if one sequence generates 500 tokens and another generates 50, the 50-token sequence holds a GPU slot for 10x longer than it needs. Continuous batching reclaims that slot immediately. Throughput improvements of 2–8x over static batching are typical.
  • Iteration-level scheduling. The scheduler decides at each step: which sequences to continue, which new requests to admit (constrained by available KV cache memory), and which to preempt if memory runs low (swap KV cache to CPU or recompute later).
  • Prefill interference. A new request's prefill (compute-heavy) can stall ongoing decode steps (memory-bound) if they share the GPU. Solutions: chunked prefill (break prefill into smaller chunks interleaved with decode steps), or disaggregated serving (separate machines for prefill and decode).

Bottom line: continuous batching is free throughput. There is no reason to use static batching in production. Every modern serving framework (vLLM, TGI, TensorRT-LLM, SGLang) implements it by default.

06 Disaggregated serving

Prefill and decode have opposite hardware appetites. Why force them onto the same machine?

  • The mismatch. Prefill is compute-bound — it wants high FLOPS (dense matrix multiplies on all input tokens in parallel). Decode is memory-bandwidth-bound — it wants fast memory reads (loading full weight matrices for one token at a time). A single GPU configuration is a compromise for both.
  • Disaggregated architecture. Run prefill on compute-optimized machines (maybe fewer GPUs with higher FLOPS). Run decode on memory-bandwidth-optimized machines (maybe more GPUs with high HBM bandwidth). Transfer the KV cache from prefill to decode machines after the prefill completes.
  • Benefits. Each phase runs on ideal hardware. Prefill machines can use larger batch sizes (no decode contention). Decode machines are not stalled by prefill compute. Independent scaling: scale prefill and decode pools separately based on workload mix.
  • Chunked prefill (a lighter alternative): break the prefill into fixed-size chunks and interleave them with decode iterations on the same GPU. This smooths out latency spikes from long prompts arriving mid-decode. Used by Sarathi, vLLM, and SGLang.
  • Trade-offs. KV cache transfer introduces network latency and complexity. Requires a scheduler that routes requests through both pools. More operational surface area. Worthwhile at large scale when the efficiency gains exceed the overhead.
When to disaggregate: if your workload has high variance in prompt length (some requests have 100 tokens, others have 100K), disaggregation prevents long prefills from blocking decode. For uniform workloads on a few GPUs, chunked prefill is usually sufficient.

07 Model parallelism for inference

When the model does not fit on one GPU — or when you need lower latency than one GPU can deliver — you split it across multiple GPUs. See also Distributed Training for the training-side view.

  • Tensor parallelism (TP). Split individual layers (weight matrices) across GPUs. Each GPU computes part of the matrix multiply, then an all-reduce synchronizes. Reduces per-GPU memory and compute. Best within a node (needs fast interconnect — NVLink). Common: TP=2, 4, or 8 across GPUs in one node.
  • Pipeline parallelism (PP). Put different layers on different GPUs. Requests flow through the pipeline. Lower interconnect requirements (only activations between stages, not all-reduce). Higher latency due to pipeline bubbles. Best across nodes. Often combined with TP: TP within a node, PP across nodes.
  • Expert parallelism (EP). For Mixture-of-Experts models: distribute experts across GPUs. Each token is routed to its assigned expert's GPU. Reduces per-GPU memory proportional to the number of expert shards. Introduces all-to-all communication for token routing. Key for serving large MoE models like Mixtral and DeepSeek.
  • When to use what. TP for latency reduction on models that fit on a few GPUs. PP for models spanning multiple nodes. EP specifically for MoE architectures. In practice, large deployments combine all three.

08 Serving frameworks

You almost never write a serving stack from scratch. The frameworks below implement most of the optimizations on this page out of the box.

  • vLLM. The most widely adopted open-source LLM serving engine. Introduced PagedAttention. Continuous batching, tensor parallelism, quantization support (AWQ, GPTQ, FP8), OpenAI-compatible API. Strong community and ecosystem. The default starting point.
  • SGLang. Focuses on structured generation and multi-turn efficiency. RadixAttention for prefix caching (shared prefixes across requests). Compressed finite-state machines for constrained decoding. Fast for workloads with repeated system prompts or structured outputs.
  • TensorRT-LLM (NVIDIA). NVIDIA's optimized serving engine. Compiles models to TensorRT for maximum kernel efficiency on NVIDIA GPUs. FP8 support on Hopper. In-flight batching, paged KV cache. Highest raw throughput on NVIDIA hardware but less flexible and slower iteration cycle.
  • TGI (Text Generation Inference, HuggingFace). Production-ready serving with tight HuggingFace ecosystem integration. Continuous batching, tensor parallelism, quantization. Good for teams already in the HF ecosystem. Production-tested at HuggingFace's own inference endpoints.
  • llama.cpp / Ollama. CPU-first inference via GGUF quantization. llama.cpp is the engine; Ollama wraps it in a user-friendly CLI and API. Great for local development, edge deployment, and Apple Silicon (Metal acceleration). Not designed for high-throughput GPU serving.

09 Scaling & routing

A single GPU serving instance is a building block. Production systems need autoscaling, request routing, and queue management to handle variable load while meeting SLOs.

  • SLO-aware autoscaling. Scale on latency percentiles (p95 TPOT, p99 TTFT), not just CPU/GPU utilization. A GPU at 80% utilization might already be violating latency SLOs due to queuing delay. Scale up before the SLO is breached, not after.
  • Request routing. Route requests to replicas considering: current queue depth, model already loaded (avoid cold starts), GPU memory available for KV cache, and request characteristics (long prompts to machines with more prefill headroom). Shortest-queue routing is a reasonable default.
  • Queue management. When all replicas are at capacity: queue with bounded wait time, shed load gracefully (return 429 with retry-after), or degrade (route to a smaller, faster model). Never queue unboundedly — queuing delay compounds under load.
  • Prefix caching. Many requests share common system prompts. Cache their KV states and reuse across requests. SGLang's RadixAttention organizes this as a radix tree. vLLM also supports automatic prefix caching. This reduces redundant prefill work substantially for multi-turn conversations and shared-prompt deployments.
  • Cost optimization. Use spot/preemptible instances for batch workloads. Right-size GPU types (do not use H100s for a 7B model). Batch APIs for non-latency-sensitive workloads. Model routing: send simple queries to a small model, hard queries to the large one (a form of the routing pattern from agentic design patterns).
  • Multi-model serving. Load multiple models (or LoRA adapters) on the same GPU, swapping as needed. Reduces cost when serving many fine-tuned variants. vLLM and SGLang both support dynamic LoRA loading.
The operational reality: serving LLMs at scale is as much a systems engineering problem as an ML one. The difference between a demo and a production system is graceful degradation under load, observable metrics, and an autoscaler that acts on the right signal.

10 Pitfalls & what to remember

Pitfalls

  • Optimizing the wrong phase. If TTFT is fine but TPOT is slow, quantization helps (decode is memory-bound). If TTFT is slow but TPOT is fine, you need to speed up prefill (more compute, shorter prompts, prefix caching). Measure before you optimize.
  • Ignoring KV cache memory. Teams budget GPU memory for model weights and forget that KV cache scales with sequence length × batch size. A 128K context window can consume more memory than the model itself.
  • Benchmarking at low concurrency. A framework looks great serving one request at a time. Production means 50–500 concurrent requests. Always benchmark at realistic concurrency and measure tail latency.
  • Quantization without eval. "4-bit is fine" is true on average and false for specific tasks. Always run your evaluation suite on the quantized model. Watch for degradation on reasoning, math, and long-context tasks.
  • Over-parallelizing. Tensor parallelism across more GPUs than needed wastes interconnect bandwidth. A 13B model on 8 GPUs will be slower than on 2 GPUs because communication overhead dominates.
  • No graceful degradation. Without load shedding and queue bounds, a traffic spike turns latency violations into cascading timeouts across your whole system.

What to remember

  • Prefill is compute-bound; decode is memory-bandwidth-bound. This asymmetry drives every optimization on this page.
  • Quantization (4-bit or FP8) is the single biggest lever. Start here.
  • Continuous batching is free throughput — never use static batching.
  • KV cache is the memory bottleneck. GQA, PagedAttention, and cache quantization are the levers.
  • Speculative decoding speeds up decode without quality loss — a small model drafts, the big model verifies.
  • Measure at production concurrency with tail latency metrics before declaring victory.
  • Neighbours: Model Acceleration (broader compression), Speculative Decoding (decode speedup), LLMOps (operational lifecycle), KV Cache & Generation (attention mechanics).
The whole page in one line: LLM serving is a memory-bandwidth game — quantize the weights, page the KV cache, batch continuously, and scale on the right signal.
