LLMOps

Operating LLM applications in production. It inherits MLOps but adds new problems: prompts as artifacts, non-deterministic outputs, eval without ground truth, prompt-injection safety, and serious cost/latency management.

MLOps & Deployment LLM systems Production

01 How LLMOps differs from MLOps

  • The "model" is often a third-party API; the thing you own and version is the prompt, context, and tools — see Context Engineering. Classic ML ships a weights file; here the weights belong to a provider and your day-to-day artifact is the prompt template, retrieval config, tool schemas, and model+version pin.
  • Outputs are non-deterministic and open-ended, and there is usually no ground-truth label, so evaluation shifts from exact-match accuracy to graded, rubric- and judge-assisted scoring plus human review — and it must continue in production, not just before launch.
  • Cost & latency per call are first-class concerns: every call is a metered transaction costing real money per token and taking hundreds of ms to seconds, turning token budgets, caching, and latency percentiles into core SLOs.
  • The input channel is an attack surface: instructions and data share one text channel, so untrusted content (a user message, a retrieved page, a tool result) can hijack the model. Safety becomes a runtime concern on both ingress and egress.
LLMOps = MLOps + (prompts-as-artifacts) + (non-determinism) + (eval-without-ground-truth) + (runtime safety) + (token-cost economics)

02 Prompt & context management

  • Treat prompts as code: prompts, templates, few-shot examples, tool/function schemas, and the model+version pin are versioned artifacts — stored in version control, diffed on change, and attached to traces so any output is reproducible.
  • Environment aliases (dev / staging / prod) let a prompt be promoted or rolled back independently of app code — the prompt has its own release lifecycle.
  • Pin the provider model version explicitly. Silent provider model bumps are a real source of regressions: treat a model update like a dependency upgrade and re-run evals before adopting it.
  • The decision of where knowledge and behavior live is itself a managed surface — see the tuning ladder below and Context Engineering.

04 RAG / retrieval ops

  • In a RAG app the retrieval layer is part of the production surface: monitor retrieval quality (was the right context fetched?), context relevance, and faithfulness / groundedness (did the answer stick to the retrieved context?) — not just final answer quality. See Hallucination & Factuality.
  • Retrieval adds an attack surface (OWASP LLM08, vector & embedding weaknesses): embedding poisoning and access-control leakage across tenants. Untrusted retrieved text can also carry indirect prompt injection.
  • The retrieval config (chunking, top-k, similarity threshold, reranker, embedding model) is a versioned artifact like the prompt. Cross-link to Vector Databases rather than re-deriving ANN internals here.

05 Evaluation — the defining LLMOps problem

  • Offline (pre-merge): a curated eval set scored by deterministic checks (format / schema / regex), rubric scorers, and LLM judges — run in CI as regression tests so a prompt or model change can't silently degrade quality.
  • LLM-as-a-judge modes: pointwise (reference-free) for production monitoring, pairwise for A/B-style "which is better", reference-based for correctness/faithfulness. Calibrate against a small human-labeled set and watch for position, verbosity, and self-enhancement bias — a strong judge agrees with humans only ≈ 80%+ of the time, so treat it as a noisy classifier.
  • Online (in production): A/B tests, thumbs-up/down, and implicit signals (edits, retries, abandonment) catch drift, edge cases, abuse, and cost spikes that offline sets miss.
  • The mature pattern is all three layers: deterministic checks for objective constraints, judges for qualitative quality at scale, human annotation for calibration and edge cases. Track faithfulness and safety, not just helpfulness.

06 Cost & latency math

Per-call cost is metered on tokens; report latency as a distribution, never a mean.

cost_per_call = n_in × price_in + n_out × price_out ≈ tokens × price_per_token
cost_eff = h · c_hit + (1 − h) · c_miss ≈ (1 − h) · c_miss (when c_hit ≈ 0)
input_cost ≈ n_in · price_in · (1 − f · d) (prefix cache: fraction f of input billed at discount d)
total_latency = TTFT + (n_out − 1) × TPOT (streaming: time-to-first-token + decode loop)
  • The (1 − h) lever. A cache hit-rate of h gives roughly an (1 − h) cost multiplier: h = 0.6 ⇒ ≈ 40% of the uncached spend. The same form gives effective latency: latency_eff = h · L_hit + (1 − h) · L_miss.
  • Percentiles, not means. Track p₅₀ / p₉₅ / p₉₉ — a mean of ≈ 2 s can hide a p₉₉ of ≈ 45 s. For streaming, perceived responsiveness is mostly TTFT (the prefill pass); total cost/throughput is mostly the TPOT decode side.
  • Throughput vs latency. Higher batch size packs more requests' decode steps together ⇒ higher tokens/sec per GPU ⇒ lower cost-per-token, at the price of higher per-request latency — the central serving trade-off.

07 Caching — reported numbers

  • Exact / prefix caching (provider-side): caching a long fixed prefix (system prompt, few-shot, retrieved context) is lossless for the cached tokens. Reported ≈ 90% cost and ≈ 85% latency reduction on long prompts, and ≈ 50% input-cost savings from automatic caching — directional, workload-dependent.
  • Semantic caching (e.g. GPTCache / Redis vector cache): embed the query, return a stored response when within a similarity threshold. Reported cache hit-rates ≈ 61–69%, API-call reductions up to ≈ 68.8%, with hit latency dropping toward sub-100 ms. One cited figure: ≈ 31% of queries are semantically similar to a prior request.
  • The key knob is the similarity threshold. Too loose ⇒ confidently wrong false hits; too tight ⇒ low hit-rate. This is the failure mode to guard.
  • Caching, quantization, and speculative-decoding magnitudes are vendor/engineering figures, not peer-reviewed bounds — treat as reported ≈, not guarantees.

08 Inference serving & cost optimization

  • Continuous (in-flight) batching (vLLM / TGI / SGLang) is the foundation of modern serving: dynamically swap finished sequences out and new requests in mid-batch to keep the GPU busy.
  • Quantization: FP16 → INT8/INT4 cuts memory ≈ 2–4× and inference cost ≈ 50% while typically retaining ≈ 95–99% of quality. See Model Acceleration.
  • Speculative decoding: ≈ 2–3× decode speedup, lossless for the exact variant; effectiveness drops at high batch concurrency. See Speculative Decoding.
  • KV cache reuse and model routing (easy → small/cheap, hard → large) attack cost from multiple sides; stacking optimizations is reported at ≈ 5–8× better cost-efficiency than naive FP16 + static batching — a single H100-class vendor claim, directional only.
  • Build vs buy: self-hosting on your own GPUs gives control and can be cheaper at scale but adds ops burden; provider APIs are simpler but meter per token and update models under you.

09 Fine-tuning vs prompting vs RAG ladder

  • Default escalation order: prompt engineering → few-shot / better context → RAG (knowledge at runtime) → fine-tuning (PEFT / LoRA) → full fine-tune / continued pretraining.
  • Prompting and RAG are cheaper to iterate and easy to roll back; fine-tuning is justified for consistent format/style/behavior, lower latency from shorter prompts, or capability not reachable by context.
  • Heuristic: knowledge that changes often → RAG; behavior/format that must be reliable → fine-tune. See Context Engineering.

10 Guardrails & safety

  • Input guardrails: detect/block prompt injection and jailbreaks, scan and redact PII, and fence untrusted content (retrieved docs, tool outputs, user text) so it can't be read as instructions.
  • Output guardrails: validate format/schema, filter unsafe/toxic content, check grounding/faithfulness, and never execute LLM output without validation (OWASP LLM05, improper output handling).
  • Prefer established frameworks (NeMo Guardrails, LLM Guard) over hand-rolled checks; treat guardrails as defense-in-depth, not a single gate.

11 Governance & security

The OWASP Top 10 for LLM Applications (2025) is the security backbone.

  • LLM01 Prompt Injection (still #1) · LLM02 Sensitive Information Disclosure · LLM03 Supply Chain · LLM04 Data & Model Poisoning · LLM05 Improper Output Handling · LLM06 Excessive Agency (over-broad tool/permission scope) · LLM07 System Prompt Leakage · LLM08 Vector & Embedding Weaknesses (RAG) · LLM09 Misinformation · LLM10 Unbounded Consumption (denial-of-wallet / model extraction).
  • Prompt injection has two flavors: direct (the user manipulates the prompt) and indirect (malicious instructions arrive via retrieved or tool content). There is no complete fix today — manage with defense-in-depth: input filtering, system-prompt hardening, output validation, least-privilege tool scope, behavioral monitoring.
  • AI gateway as central control plane: key management, rate limiting, per-team cost tracking, and budget caps to bound LLM10 (denial-of-wallet). Keep audit trails of prompts and outputs for policy enforcement.

12 Observability & tracing

  • Tracing vs monitoring: monitoring answers "is it working?"; tracing/observability answers "why isn't it?". Capture each step — prompt, retrieved context, tool calls, completion, token counts, latency, cost — as a distributed trace so a bad output can be debugged end to end.
  • Instrument with OpenTelemetry-style conventions so LLM metrics live in the same stack as the rest of the system, with per-tenant / per-feature / per-model cost attribution.
  • Dashboard metrics: latency p₅₀ / p₉₅ / p₉₉ (and TTFT for streaming), error / timeout / rate-limit rates, prompt vs completion tokens, cost per request / per 1K tokens / per model / per tenant, cache hit ratio, and online eval quality/safety scores.
  • Monitor quality, cost, latency, and drift; capture feedback to improve prompts and eval sets.

13 Takeaways

  • LLMOps = MLOps + prompts, non-determinism, eval-without-truth, safety, and cost.
  • Version prompts/context like code and pin the provider model; evaluate offline (judges in CI) + online (A/B + implicit signals).
  • Cache, batch, quantize, and route to control cost and latency — and report percentiles (p₉₉), not means.
  • Guardrail inputs and outputs against the OWASP LLM Top 10; an AI gateway bounds spend and denial-of-wallet.
  • Trace every step for per-tenant cost attribution and end-to-end debugging.
