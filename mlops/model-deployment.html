Model Deployment

Deployment is where a trained artifact becomes a service with an interface, a latency budget, a cost, and an on-call rotation. The model is usually the easy part; the hard parts are choosing the serving pattern, packaging reproducibly, meeting tail latency under load, rolling out without breaking anything, and making sure the features seen in production are the features seen in training.

01 What "deploying a model" actually means

A deployment is four things bound together: an artifact, a runtime that executes it, an interface callers depend on, and a rollout that moves traffic onto it safely.

  • Artifact: weights plus the preprocessing that must run identically to training, an input/output signature, and a link back to its training run (see Experiment Tracking).
  • Runtime: a model server, a batch job, a stream processor, or an on-device library — chosen by the serving pattern (§02).
  • Interface: the contract — request schema, response schema, error semantics, latency SLO. Changing it breaks callers; changing the model behind it should not.
  • Rollout: how traffic moves from the incumbent to the candidate, and how it moves back (§07).
  • Neighbouring pages go deeper on parts of this: making models smaller and faster in Model Acceleration, serving large generative models in LLM Serving, statistically comparing variants in A/B Testing, and watching production in Monitoring & Drift.

02 Serving patterns: batch, online, streaming, edge

The first decision is when a prediction is computed relative to when it is needed. It sets the latency budget, the cost model, and which failures you will have.

Batch (offline)On a schedule over a whole table; results written to a store and looked up laterMinutes to hours for the job; lookup is fastCheap, simple, easy to rerun and audit; large models are fineStale predictions; wasted compute on entities never queried; new entities have no scoreChurn scores, nightly recommendations, risk tiers

  • Hybrid is normal. Precompute expensive embeddings in batch, combine with request-time features online; or run a small on-device model with a server fallback.
  • Streaming deployments sit on the infrastructure of Stream Processing and Message Queues; batch deployments are just another job in the ETL pipeline.
  • Rule of thumb: if predictions can be precomputed for every entity that matters and staleness of hours is acceptable, choose batch. It removes an entire class of on-call incidents.

03 Packaging: formats, containers, and servers

  • Framework-native formats (pickled estimators, framework checkpoints) are simplest but tie the runtime to the exact library version used in training. Unpickling untrusted files executes code — treat them as code, not data.
  • ONNX is an interchange format: a graph of standard operators plus weights, runnable by several runtimes on CPU, GPU and mobile. It decouples training framework from serving runtime and enables graph-level optimization. Caveats: custom ops and dynamic control flow may not export; always assert numerical parity (e.g. max absolute difference below a tolerance on a fixed test batch) after conversion.
  • Compiled engines specialize a graph for one hardware target and precision — the subject of Model Acceleration. Faster, but rebuilt per target and harder to debug.
  • Containers freeze the OS libraries, language runtime, and dependencies. Deploy by image digest, not a mutable tag, so what you tested is byte-for-byte what runs. Choose whether the model is baked into the image (immutable, larger, slower to build) or pulled at startup from the registry (smaller image, but startup depends on the artifact store).
  • Model server vs custom app. A dedicated model server gives batching, multi-model hosting, metrics, and health endpoints for free; a thin custom web app gives full control over pre/post-processing. A common split: a custom service for business logic calling a model server for inference.
  • Preprocessing belongs with the model. Shipping tokenizers, scalers, and encoders as part of the artifact (or the same library used offline) is the strongest single defence against training/serving skew (§10).

  • Version the contract, not just the model. A path or package version (/v2/score) lets old clients keep working while new ones migrate.
  • Timeouts and retries are part of the interface. A caller with a 200 ms timeout retrying three times can triple load on an already slow service. Use deadlines propagated across calls, bounded retries with jittered backoff, and idempotent requests.
  • Return metadata: model version, latency, and a request id in every response make debugging and attribution possible.

05 Latency budgets, tails, and queueing

Users feel the tail, not the mean. A budget is set on a percentile (p99 < 150 ms), and every hop in the request path consumes part of it.

end-to-end budget is a sum of hopsT_total = T_network + T_feature_fetch + T_queue + T_preprocess + T_inference + T_postprocess
  • Feature fetch is often the largest term, not inference: several lookups against a feature store or cache (see Caching), each with its own tail.
  • Fan-out amplifies tails. If a request waits on k parallel calls and each is slow with probability q, the request is slow whenever any is:
tail amplification under fan-outP(request slow) = 1 − (1 − q)ᵏ q = 1%, k = 100 → ≈ 63%
  • Queueing dominates near saturation. With arrival rate λ and service rate μ per server, utilization is ρ = λ/μ. In the simplest single-server queue, mean time in system blows up as ρ → 1, which is why services are provisioned for 50–70% utilization at peak, not 95%.
utilization, simple single-server queue, and little's lawρ = λ / μ W = 1 / (μ − λ) (ρ < 1) L = λ · W
  • Tail-cutting tactics: hedged requests (send a duplicate after the p95 delay, take the first answer), timeouts with fallbacks (cached or default prediction), load shedding of low-priority traffic, and keeping p99 feature lookups on a fast path.

06 Dynamic batching and replicas — interactive

Accelerators amortize a large fixed cost per call over every item in a batch, so batching multiplies throughput. The price is waiting: a request may sit in a queue until the batch fills or a timeout fires.

batch service time and per-replica capacitys(b) = s₀ + s₁ · b capacity(B) = B / (s₀ + s₁ · B) stable iff λ / replicas < capacity(B)
  • Max batch size caps both throughput gain and worst-case compute time per batch. Batch timeout bounds the wait at low load; at high load batches fill before the timeout, so it stops mattering.
  • Generative models batch differently — at the token level, admitting new sequences into a running batch every step (continuous batching). That is covered in LLM Serving.
Discrete-event simulation of a batched model server s₀ = 12 ms fixed · s₁ = 1.2 ms per item · Poisson arrivals · random routing
Try: at λ = 300 with max batch 1 the single replica is overloaded (capacity ≈ 76 req/s) and latency explodes. Raise max batch to 8 and the same hardware copes. Then push λ to 1500: either add replicas or raise max batch — and watch the timeout trade median latency for throughput at low load.

07 Autoscaling

  • Target tracking is the standard rule: keep a load metric near a target per replica by scaling the replica count proportionally.
proportional scaling ruledesired = ⌈ current · (observed metric / target metric) ⌉ clamped to [min, max] replicas
  • Pick the right signal. CPU utilization works for CPU-bound models. For accelerator serving, utilization is a poor signal (a batched GPU can be "busy" yet have headroom); scale on queue depth, in-flight requests per replica, or measured p95 latency instead.
  • Cold starts are the enemy: pulling a multi-gigabyte image and model, then warming up kernels, can take minutes. Mitigate with minimum replicas, pre-pulled images, smaller artifacts, and warm-up requests before marking a replica ready.
  • Asymmetric speed: scale up fast (traffic spikes hurt immediately), scale down slowly with a stabilization window (flapping wastes cold starts).
  • Scale to zero saves money for rarely used models but guarantees a cold start on the first request — acceptable for internal tools, rarely for user-facing paths.
  • Predictive / scheduled scaling for known daily peaks beats reactive scaling that always lags by one cold start.

08 Rollout strategies and rollback

Never move 100% of traffic to an unproven model in one step. Progressive delivery limits the blast radius — how many requests a bad model can harm before it is caught.

StrategyMechanismUsers exposed to candidateRollbackCatchesCost / caveat
ShadowMirror live requests to the candidate; log its outputs, serve the incumbent'sNoneNothing to roll backCrashes, latency, output distribution shifts, disagreement with incumbentDouble inference cost; cannot measure user response; side-effecting calls must be stubbed
CanaryRoute a small, growing fraction (1% → 5% → 25% → 100%) with automated checks at each stepSmall then growingRoute the fraction back to 0Error rate, latency, business guardrails at real loadSmall early fractions have low statistical power (see viz)
Blue-greenTwo full environments; switch the router from blue to green at onceAll, after switchInstant: switch back to blueDeployment and integration failuresDouble capacity during cutover; no gradual exposure
RollingReplace replicas a few at a timeGrowing with replicas replacedRoll forward or redeploy old versionCrashes on startupMixed versions serve simultaneously; slow rollback
A/B testRandomized split held fixed for a pre-planned durationFixed shareEnd the experimentCausal effect on product metricsNeeds sample size planning — see A/B Testing
  • A typical sequence chains them: shadow to prove the candidate is operationally safe, canary to prove it does not regress guardrails, A/B to prove it improves the product, then full rollout.
  • Rollback must be boring. Keep the previous version deployed (or instantly redeployable), make rollback a single config change — e.g. moving the registry alias back — and rehearse it. Models with schema changes need backward-compatible features or rollback breaks.
  • Automate the decision. Canary analysis compares candidate vs baseline during the same window (not candidate vs last week) and aborts automatically on a statistically significant regression or a hard threshold breach.

09 Canary analysis — interactive

Step a candidate through traffic fractions. At each step the canary and baseline error rates are compared with a one-sided two-proportion test. Small steps protect users but can only detect large regressions.

two-proportion z-test per step (one-sided, abort if z > 2.33)z = (p̂_c − p̂_b) / √( p̄(1 − p̄) · (1/n_c + 1/n_b) ) excess failures = n_c · (p_c − p_b)
Progressive canary: 1% → 5% → 25% → 50% → 100% baseline error 1.0% · 50,000 requests per step window
Notice: with a 1.3% candidate (30% relative regression) the 1% step usually passes — 500 requests cannot resolve 1.0% vs 1.3%. The regression is typically caught at 25% or 50%, by which point roughly 50 excess failures have reached users per 50,000-request window — multiply by real traffic volume to see the true blast radius. A 2.5% candidate is usually caught at the 1% or 5% step. Real canary systems therefore add hard absolute thresholds, longer early windows, and cumulative (sequential) tests rather than relying on early steps alone.

10 Training/serving skew

The model is evaluated on features computed one way offline and then served features computed another way online. Accuracy drops with no error in any log.

KindExampleDefence
Code-path skewOffline feature in SQL, online in a service language; different null handling, rounding, or tokenizationOne feature definition used by both paths; shared preprocessing library shipped in the artifact
Time / leakage skewTraining joined "latest" values that were not known at prediction timePoint-in-time-correct joins (a core job of Feature Stores)
Freshness skewTraining used features updated hourly; serving cache is a day staleMonitor feature age; set freshness SLOs
Distribution skewTraining sample filtered differently from live traffic (bots removed offline only)Apply the same filters; compare live vs training distributions (see Monitoring & Drift)
Environment skewDifferent library version changes a defaultPinned container digest; parity test in CI
  • Log what you served. Record the exact feature vector the model received at serving time, then train the next model on those logged features. This closes the skew loop by construction.
  • Parity test before rollout: replay a sample of logged requests through the offline feature pipeline and the online path; assert per-feature agreement within tolerance. Wire it in as a gate in CI/CD.
  • Cleaning and transformation choices made in Data Preprocessing are exactly what must be replicated online.

11 Running it: health, fallbacks, and observability

  • Liveness vs readiness. Liveness says "the process is not wedged"; readiness says "the model is loaded and warmed — send traffic". Conflating them sends requests to replicas still loading weights.
  • Fallback chain: candidate → incumbent → cached prediction → rule-based default. A ranking service that returns a popularity list when the model times out degrades gracefully instead of failing.
  • Circuit breakers and load shedding stop a slow model from exhausting caller thread pools and cascading the outage upstream.
  • The four golden signals per model version: latency (percentiles), traffic, errors, saturation — plus model-specific signals: prediction distribution, feature null rates, and outcome metrics once labels arrive (see Monitoring & Drift).
  • Cost per prediction is an operating metric: replicas × hourly price ÷ predictions served. It is what makes batch, quantization, or a smaller model the right call.

12 Takeaways

  • Choose the serving pattern first — batch when staleness is acceptable, online when context is needed, streaming for event-driven freshness, edge for privacy and offline use.
  • Package immutably: artifact with its preprocessing, container by digest, parity-checked conversions.
  • Budget the tail: feature fetches and queueing often cost more than inference; fan-out amplifies tails; provision below saturation.
  • Batching trades latency for throughput; replicas and autoscaling on queue depth handle the rest.
  • Shadow → canary → A/B → full, with automated analysis and a rehearsed one-step rollback.
  • Kill training/serving skew with shared feature definitions, point-in-time joins, and logging served features.
