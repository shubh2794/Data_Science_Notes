Document AI Models

Document AI models are neural networks that read visually rich documents — forms, receipts, invoices, scanned letters, scientific pages — and turn them into labels, extracted fields, answers or structured text, using not only the words but where the words sit on the page and what the page looks like. This hub is the note on the category itself: the design axes that separate its members, the split between models that consume an OCR engine's output and models that read pixels directly, how the families evolved from 2019 onward, a comparison of published configurations and scores, and how to choose. The two model pages under it are LayoutLM (the OCR-based line) and Donut (the OCR-free line).

01 What document AI models are

A document AI model is a network whose input is a page — an image of a document, optionally accompanied by the words an OCR engine read from it and their bounding boxes — and whose output is a document-level label, a label per word, a span answering a question, or a generated sequence such as a JSON record. What makes the category distinct from plain NLP is that two-dimensional position is part of the meaning: the number to the right of "Total" on a receipt is the total because of where it is, not because of any word near it in reading order.

what an OCR-based model consumes, per pageinput = { (wᵢ, bᵢ) }ᵢ₌₁ⁿ ∪ image I bᵢ = (x₀, y₀, x₁, y₁) normalised to 0…1000 what an OCR-free model consumesinput = image I ∈ ℝ^(3 × H × W) output = token sequence y₁ … yₘ (generated)

Three kinds of signal

  • Text — the words themselves, from an OCR engine, from the PDF's embedded text layer, or read by the model itself from pixels.
  • Layout — the coordinates of each word or text segment on the page. Most OCR-based models from LayoutLM onward scale box corners to integers in 0…1000 and look each coordinate up in an embedding table.
  • Appearance — the pixels: fonts, bold headings, table rules, logos, stamps, checkboxes, handwriting. Early models added it through a CNN; later ones through ViT-style patches; OCR-free models rely on it entirely.

Two families, one question

The members of this hub split along one question — who does the reading? In the OCR-based family (LayoutLM v1/v2/v3, LayoutXLM, LiLT, DocFormer, UDOP) an external engine produces words and boxes, and the model is a Transformer encoder (or encoder–decoder) over those tokens, usually with image features on the side. In the OCR-free family (Donut, Pix2Struct, Nougat, and, more recently, general vision-language models) a vision encoder reads the raw page and a text decoder writes the answer, so there is no separate recognition step to fail. In practice each family tends to be strong where the other is weak — a practitioner observation rather than a measured result — which helps explain why both remain in use.

Takeaway: a document AI model is defined by its input — a page, with its words, their positions and its pixels — rather than by one architecture. The single most useful classification is whether an external OCR engine supplies the text (OCR-based) or the model reads it from pixels itself (OCR-free).

02 The design axes that separate the members

Every model in this hub can be placed by answering six questions. The answers are not independent — choosing OCR-free, for example, has in every published model here come with a generative decoder and a high input resolution — and the matrix below shows which combinations the published models actually chose.

The six questions

  • Text source. External OCR / PDF text layer, or the model's own reading of pixels. This decides whether the system inherits OCR errors and whether it needs an OCR licence, latency budget and language support.
  • How layout enters. Absolute 2D position embeddings added to each token (LayoutLM v1), those plus a spatial-aware attention bias computed from relative box offsets (LayoutLMv2, LayoutLMv3), a separate layout stream that exchanges attention scores with the text stream (LiLT), or implicitly through pixel positions in a vision backbone (Donut, Pix2Struct, Nougat).
  • How appearance enters. None (LayoutLM v1 text + layout, LiLT), region features from a CNN such as Faster R-CNN on ResNet-101 (LayoutLM v1 with image), a pooled 7 × 7 CNN grid (LayoutLMv2: 49 visual tokens from ResNeXt-101-FPN), linear patch embeddings (LayoutLMv3: 16 × 16 patches of a 224 × 224 image, 196 tokens), or a full high-resolution vision encoder (Swin-B in Donut and Nougat).
  • Output head. Encoder with token-classification, span or [CLS] heads (the LayoutLM line, LiLT, DocFormer), or an encoder–decoder that generates the output (UDOP, Donut, Pix2Struct, Nougat).
  • Pretraining objective. Masked visual-language modelling, alignment tasks between text and image, masked image modelling, or "read the page aloud" (pseudo-OCR) objectives — compared in Pretraining objectives.
  • Input resolution. From 224 × 224 (LayoutLMv2/v3, whose text comes from OCR anyway) to 2560 × 1920 (Donut), because a model that must read 8-point text itself needs far more pixels than one that only needs the page's visual gist.

03 How layout enters the model

An OCR engine returns each word with a pixel bounding box. Pages come in every size and scan resolution, so the first step in the LayoutLM line is to divide each corner coordinate by the page width or height and scale to an integer between 0 and 1000. Those integers index learned embedding tables, exactly as a token id indexes the vocabulary table.

normalise a pixel box on a W × H pagex̂ = floor(1000 · x / W) ŷ = floor(1000 · y / H) LayoutLM v1 input embedding for word ieᵢ = Tok(wᵢ) + Pos(i) + X(x̂₀) + Y(ŷ₀) + X(x̂₁) + Y(ŷ₁) LayoutLMv2 spatial-aware attention for query i, key jα′ᵢⱼ = αᵢⱼ + b¹ᴰ(j − i) + b²ᴰˣ(x̂ⱼ − x̂ᵢ) + b²ᴰʸ(ŷⱼ − ŷᵢ)

Three ways the same boxes are used

  • Absolute 2D embeddings (LayoutLM v1). The paper adds four position embeddings for the box corners, with one table shared by the two x coordinates and one by the two y coordinates. The widely used open implementation also adds width and height embeddings, giving four tables of 1024 rows (a configuration field called max_2d_position_embeddings) — which is where the roughly 3M parameters LayoutLM adds on top of BERT come from (see the parameter count).
  • Relative spatial bias (LayoutLMv2, LayoutLMv3). Absolute embeddings tell a token where it is; the attention bias tells a pair of tokens how far apart they are. The bias is a learned scalar per bucketed offset, added to the attention logit before the softmax — the same device as relative position bias in text Transformers, applied in two dimensions.
  • Segment-level positions (LayoutLMv3, LiLT). Instead of giving each word its own box, every word in a text line or block shares the block's box (LiLT gives each token the box of the OCR text string it belongs to, because some OCR engines return no word-level boxes). The LayoutLMv3 paper argues this helps because words in one segment usually carry one meaning; it is the reason v3's FUNSD score is not strictly comparable with word-level models, a point that paper itself notes.
From pixel boxes to layout ids — a toy receipt click a word · change the scan resolution and watch pixels change while the ids stay fixed

The receipt is defined once in inches (a 3 × 5 inch slip); pixel boxes are that geometry multiplied by the scan resolution, and the 0–1000 ids are recomputed from the pixels with the floor formula above. Because both the box and the page scale by the same factor, the ids barely move across resolutions — only floor rounding can shift an id by one — which is the whole point of normalising.

What the normalisation does not fix

  • It removes page size and scan resolution, but not rotation, skew or perspective: a phone photo of a receipt still needs deskewing before its boxes mean anything consistent.
  • 1000 buckets across a page is roughly one bucket per 0.2 mm on A4 width — finer than the box accuracy typical OCR engines deliver, so the quantisation is unlikely to be a practical bottleneck.
  • Reading order is not in the boxes. The 1D position index still comes from the order the OCR engine emitted words in, and a bad reading order (two-column pages, tables) degrades the text stream even when every box is right.
Takeaway: layout enters OCR-based models as quantised coordinates looked up in embedding tables, optionally refined by a relative 2D attention bias. OCR-free models never see a coordinate: position is implicit in where a pixel sits in the vision encoder's grid.

04 The pipeline versus the end-to-end model

An OCR-based system is a pipeline: recognise words, order them, then classify or extract. An OCR-free system is one network from pixels to answer. The trade-off between them is the central design decision in the category, and it is mostly about where errors come from and who pays for them.

What the pipeline costs

  • Error propagation. The downstream model sees only what OCR produced. A misread digit in an invoice total cannot be fixed by the best extractor, and the benchmark scores in Tasks and benchmarks are mostly measured with provided or high-quality OCR, so they tend to overstate field accuracy on messy scans.
  • Latency and parameters outside the model. The Donut paper's tables count OCR as "+ α" parameters and time for every OCR-based baseline; its RVL-CDIP table reports 752 ms per page for Donut against 1,396–1,489 ms for LayoutLM and LayoutLMv2 including their OCR.
  • Language and script coverage is set by the OCR engine, not the model. LayoutXLM and LiLT were built partly to make the model side multilingual; the OCR side still has to be.

What end-to-end costs

  • Resolution and compute. To read small print the encoder needs thousands of pixels per side; Donut pretrains at 2560 × 1920 (see Token budgets for what that means in tokens).
  • Pretraining data. The model must learn to read, which needs text-dense images with transcriptions: Donut uses 11M IIT-CDIP pages with pseudo-labels from a commercial OCR API plus 2M synthetic pages from its generator SynthDoG (0.5M per language in four languages).
  • Hallucination. A generative reader can produce fluent text that is not on the page, and gives no box to check it against — a failure mode an extractive pipeline largely avoids, since every answer it gives is a span of the OCR output, though that span can itself be misread.
A toy model of error propagation drag the sliders · the curve is field accuracy against field length in words

Assumptions, stated so they can be disputed: OCR errors are independent across words, a field is correct only if all its words are read correctly and the extractor then labels it correctly, and the end-to-end model's accuracy does not depend on field length. Real OCR errors are correlated (a blurry region fails together) and real end-to-end models also degrade on long fields, so treat the crossover as an illustration of the mechanism, not a prediction.

Takeaway: the pipeline multiplies two accuracies, and the OCR factor compounds with the number of words per field. End-to-end removes the multiplication but pays in resolution, pretraining data and a new failure mode — unverifiable generated text.

05 Token budgets: OCR words versus image patches

A dense page holds several hundred words. An OCR-based encoder spends roughly one token per sub-word on them and a few dozen to a couple of hundred on the image; an OCR-free encoder spends its tokens on pixels, and needs enough of them to resolve small print. The arithmetic of those two budgets explains much of the category's engineering.

ViT-style patches of size P on an H × W imageM = (H / P) · (W / P) LayoutLMv3: (224 / 16)² = 196 Swin stages: patch size 4, then 2 × 2 merging three timesstage k tokens = (H / (4·2ᵏ⁻¹)) · (W / (4·2ᵏ⁻¹)), k = 1 … 4 Donut at 2560 × 1920 — tokens handed to the decoder(2560 / 32) · (1920 / 32) = 80 · 60 = 4800

Why the encoders differ so much

  • OCR-based encoders cap text at 512 tokens. LayoutLM v1–v3, LayoutXLM and LiLT inherit BERT/RoBERTa's 512-position limit, so a dense page may need to be split into windows. The image branch is kept small because it only has to supply appearance cues: 49 tokens in LayoutLMv2, 196 in LayoutLMv3.
  • Swin keeps high resolution affordable. Donut's first Swin stage at 2560 × 1920 has 307,200 patch tokens, but attention is computed inside 10 × 10 windows, so cost grows linearly with image area rather than quadratically; the decoder cross-attends only to the 4,800 final-stage tokens.
  • Pix2Struct keeps the aspect ratio. Instead of resizing to a fixed square, it scales the image so that the number of 16 × 16 patches fits a budget (2,048 in pretraining) and adds 2D position embeddings for row and column. Its appendix reports that DocVQA accuracy keeps rising with resolution and shows significantly diminishing returns only after about 1M pixels (4,096 patches of 16 × 16); its DocVQA fine-tuning uses 4,096 patches for the base model and 3,072 for the large.
  • General VLMs use a dynamic budget. Qwen2-VL, for example, uses 14-pixel patches and merges 2 × 2 neighbours, so one language-model token covers 28 × 28 pixels, with configurable minimum and maximum pixel counts per image.
Tokens per page, by model family set page size and words per page · bars are log scale

OCR-model bars stack text tokens (words × sub-words per word, capped at 512 per window) and image tokens; the readout reports how many 512-token windows the text needs. Donut and Nougat resize to their fixed training resolutions (2560 × 1920 and 896 × 672); Pix2Struct uses the aspect-preserving rule with a 2,048-patch budget; the Qwen2-VL bar uses 28 × 28 pixels per token and the pixel limits in the released checkpoints' preprocessor configuration (min_pixels 3,136 = 4 tokens, max_pixels 12,845,056 = 16,384 tokens); the Transformers image processor's own fallback maximum is lower, 28 × 28 × 1,280 pixels (1,280 tokens). The sub-words-per-word ratio is an assumption you can change, not a measured constant.

Takeaway: OCR-based models spend a few hundred tokens because recognition happened outside the network; OCR-free models spend thousands because recognition happens inside it. Windowed attention (Swin) and aspect-preserving patching (Pix2Struct) are the two main tricks for making that affordable.

06 Pretraining objectives compared

Every model here is pretrained on unlabelled or weakly labelled pages before fine-tuning, and the objective is where most of the families' ideas live. OCR-based models extend BERT's masked language modelling with tasks that tie words to their positions and pixels; OCR-free models are pretrained to read the page out as text or markup.

Patterns across the table

  • IIT-CDIP is the shared substrate. A collection of about 11M scanned tobacco-litigation document images (the LayoutLMv3 paper notes it splits into about 42M pages) is the pretraining corpus of almost every OCR-based model here, which makes their results comparable but also biased toward English office documents of that era.
  • Alignment tasks come in pairs. v2's TIA/TIM, LiLT's CAI and v3's WPA all exist because MLM alone lets a model ignore the image or the layout; each adds a loss that can only be minimised by relating two modalities.
  • OCR-free objectives are reading tasks. Donut, Pix2Struct and Nougat all learn to transcribe first. The Donut paper's ablation calls its text-reading pretraining the most simple yet effective of the pretraining tasks it compared, with general tasks such as image captioning giving little gain.
Takeaway: OCR-based pretraining extends masked language modelling with losses that force text, layout and image to be used together; OCR-free pretraining teaches the model to read. The same 11M-image IIT-CDIP corpus sits under most of the table.

07 Lineage and timeline

The category's history runs in two strands that start two years apart and then converge. The OCR-based strand begins in December 2019 with LayoutLM and adds image features, multilinguality and cleaner fusion; the OCR-free strand begins in November 2021 with Donut and scales resolution and pretraining data. General vision-language models, from 2023–2024 on, absorbed much of the OCR-free strand.

Dates are arXiv first-submission months (the identifier encodes year and month). Parameter counts are the largest variant each paper reports; the Qwen2-VL point marks the general-VLM era and uses its largest open size.

What each step changed

  • LayoutLM (Dec 2019) — BERT plus 2D position embeddings, pretrained on IIT-CDIP; image features only at fine-tuning time.
  • LayoutLMv2 (Dec 2020) — image tokens inside the Transformer from pretraining on, spatial-aware attention, TIA/TIM.
  • LayoutXLM (Apr 2021) — the v2 recipe in 53 languages, with the XFUND benchmark in 7.
  • DocFormer (Jun 2021) — separate visual and text streams with shared spatial embeddings in every layer.
  • Donut (Nov 2021) — Swin encoder + BART-style decoder, no OCR, SynthDoG synthetic pages.
  • LiLT (Feb 2022) — a small layout Transformer that can be paired with any RoBERTa-like text model, so layout knowledge transfers across languages.
  • LayoutLMv3 (Apr 2022) — CNN replaced by linear patch embeddings; unified text and image masking.
  • Pix2Struct (Oct 2022) and UDOP (Dec 2022) — screenshot-parsing pretraining at variable resolution; one encoder–decoder unifying vision, text and layout.
  • Nougat (Aug 2023) — Donut's architecture specialised to academic PDFs, producing Markdown and LaTeX.
Takeaway: the OCR-based strand moved the image from a side input to a first-class token stream and then made it cheap; the OCR-free strand made reading part of the model. The two strands meet in large general vision-language models that read pages at dynamic resolution.

Values are those in the comparison table. Bars are coloured by family (OCR-based blue, OCR-free amber); Donut's CORD bar is hatched because its field-level F1 is not the entity F1 the others report. The axis starts at 60, so bar lengths exaggerate differences; read the numbers in the readout.

What the metrics reward

  • FUNSD is tiny. 50 test forms means a one-point F1 difference can be a handful of entities; treat gaps below about a point as noise unless several seeds are reported.
  • ANLS gives partial credit for near-miss strings, which favours generative models whose answers are close but not verbatim, and does not penalise an extractive model's exact span over a paraphrase.
  • RVL-CDIP is near its ceiling. Most models since LayoutLMv2 sit between 95 and 96.2%, and an audit of the dataset ("On Evaluation of Document Classification using RVL-CDIP", arXiv 2306.12550) estimates its label noise at 8.1% overall (1.6% to 16.9% by category), so the last half-point is weak evidence.
Takeaway: FUNSD and CORD test extraction from OCR-provided words, RVL-CDIP tests page classification, DocVQA tests reading plus reasoning. Small test sets and differing protocols make many headline differences smaller than they look.

10 Reading the numbers without being misled

Document AI papers compare against each other in consolidated tables, and the same model often appears with different numbers in different papers. Most of the discrepancies are protocol differences rather than errors, but they are large enough to reverse a conclusion if ignored.

Four recurring traps

  • Protocol on CORD. The OCR-based rows use ground-truth OCR and entity-level F1; the Donut paper reruns OCR-based baselines under its own end-to-end protocol, where LayoutLMv2 scores 78.9 rather than the 94.95 of the LayoutLMv3 table. The two numbers measure different tasks.
  • Segment versus word positions on FUNSD. LayoutLMv3 and some later models use segment-level boxes; the LayoutLMv3 paper itself notes this may help and makes its FUNSD numbers not directly comparable to word-level models. The UDoc CORD result in the same table used a non-standard 626/247 split and is flagged by that paper as not directly comparable for that reason.
  • Extra training data on DocVQA. Many DocVQA numbers use train + dev, or extra question-generation data: LayoutLMv2 LARGE is 83.48 on train alone, 85.29 with dev, and 86.72 with dev plus generated questions.
  • Parameter counts with and without OCR. OCR-free papers have no external engine to leave out, while OCR-based baselines are counted without their OCR engine (the Donut paper writes "+ α"). Donut reports 143M in one table and 176M in another, depending on whether English token embeddings are included.

Numbers on this page that disagree with each other

  • LayoutLM LARGE on DocVQA: the LayoutLMv2 results table gives 0.7259 (train set). The 0.7295 in that paper's abstract can look like a conflicting LayoutLM figure, but the abstract's left-hand numbers are the prior best result per task, not LayoutLM rows; this page uses the table.
  • LayoutLM BASE on FUNSD: 78.66 (text + layout, from its own paper) versus 79.27 (with image features) — both are correct, for different variants, and consolidated tables sometimes list one under the other's parameter count.
  • LayoutLM LARGE: reported as 343M, while the configuration arithmetic in the parameter figure gives about 339M.
Takeaway: before comparing two document AI numbers, check four things — the OCR source, word or segment boxes, the fine-tuning data, and whether the parameter count includes the OCR engine or the vocabulary.

11 How to choose between them

The right model depends less on leaderboard position than on what the documents look like, whether good OCR is already available, what output format downstream code needs, and the latency and licensing budget. The questions below are ordered by how strongly they usually constrain the answer.

A decision sequence

  • Is there reliable text already? Born-digital PDFs usually have an embedded text layer with exact boxes. Then OCR errors are largely not a concern and an OCR-based encoder (LayoutLMv3, LiLT) is usually the cheapest accurate choice for labelling and extraction.
  • Is the output a label per word, or a structure? Token classification (which words are the total, the date, the vendor) fits an encoder. A nested record (line items with quantities and prices), a free-form answer or a full transcription fits a generative model (Donut, UDOP, Pix2Struct, Nougat, a general VLM).
  • How good is the scan? Low-quality photos, handwriting and unusual scripts are where OCR fails first. The Donut paper reports 72.1 ANLS on DocVQA's handwritten subset against 67.3 for LayoutLMv2-Large-QG, despite a lower overall score — a case where the end-to-end model is the more robust one.
  • How many languages? For multilingual forms with an OCR engine that covers the languages, LayoutXLM or LiLT paired with a multilingual text model; for OCR-free, Donut's SynthDoG route pretrains readers for new scripts from synthetic pages.
  • What is the budget? A 133M encoder at 224 × 224 plus an OCR call is far cheaper per page than a multi-billion-parameter VLM at full resolution; the VLM wins on zero-shot breadth and on questions that need reasoning over the whole page.

Rules of thumb (practitioner heuristics, not results)

  • Labelling fields on clean forms with training data: an OCR-based encoder.
  • Receipts and invoices to JSON, noisy captures, no OCR licence: an OCR-free encoder–decoder fine-tuned on the schema.
  • Academic PDFs to Markdown with equations: a Nougat-style transcriber.
  • Few or no labelled examples, open-ended questions: a general vision-language model, checked against the page, because it can generate answers that are not there.
Takeaway: choose by input quality, output shape and budget, in that order. OCR-based encoders remain strong when text is reliable and the task is labelling; OCR-free and general VLMs win when reading itself is the hard part or the output is structured or open-ended.

14 Takeaways

The category in eight statements, each backed by a section above. If only one thing is remembered, it should be the OCR divide and the fact that most of the comparison numbers were measured under protocols that assume good OCR.

The category in eight statements

  • The input defines the category: a page, with words, their positions and its pixels. Two-dimensional position carries meaning that reading order alone loses.
  • One question splits the family: does an external OCR engine read the text (LayoutLM line, LayoutXLM, LiLT, DocFormer, UDOP) or does the model read pixels (Donut, Pix2Struct, Nougat, general VLMs)?
  • Layout enters as quantised coordinates — boxes scaled to 0…1000 and looked up in embedding tables — refined by a relative 2D attention bias from LayoutLMv2 on. It costs about 3M parameters in LayoutLM BASE.
  • The pipeline multiplies accuracies; end-to-end models remove the multiplication and pay in resolution (2560 × 1920 for Donut, thousands of tokens) and in a new failure mode, fluent text that is not on the page.
  • IIT-CDIP's 11M scanned images underlie the pretraining of nearly every OCR-based model; OCR-free models add synthetic pages (SynthDoG), web screenshots (Pix2Struct) or aligned academic sources (Nougat).
  • Fusion appears to matter more than size in the OCR-based line: LayoutLMv3 BASE (133M) reports higher FUNSD F1 than LayoutLMv2 LARGE (426M), with the caveat that v3 uses segment-level boxes.
  • Numbers need their protocol: Donut's CORD 84.1 and LayoutLMv3's 96.56 measure different things; DocVQA results vary with fine-tuning data; parameter counts vary with what is counted.
  • Choose by input quality, output shape and budget. Clean text and a labelling task favour an OCR-based encoder; noisy scans, structured outputs and open questions favour OCR-free models and general VLMs.
Takeaway: document AI is a family of answers to "who reads the page, and how is its layout represented?" — with LayoutLM and Donut as the two clearest, best-documented answers.
