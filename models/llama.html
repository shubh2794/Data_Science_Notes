Llama

Meta's open-weight family of decoder-only language models — LLaMA (February 2023), Llama 2 and Llama 2-Chat (July 2023), Llama 3, 3.1, 3.2 and 3.3 (April–December 2024) and the mixture-of-experts Llama 4 (April 2025). The generic decoder-only story — next-token prediction, causal masking, the generation loop, KV-cache basics and decoding — is told on the GPT page and is not repeated here. This page owns what Llama changed: training small models far past compute-optimal on public data, the RMSNorm / SwiGLU / RoPE / bias-free block, grouped-query attention, the 128K vocabulary and 128K context, the Llama 2-Chat alignment recipe, the move to experts and interleaved NoPE layers, and every released configuration with its parameter, KV-cache and compute arithmetic recomputed from the configs.

01 What Llama is

Llama is a causal Transformer decoder trained on next-token cross-entropy — the same objective as GPT — with a block that swaps three GPT components for later alternatives and drops every bias. Its historical importance is less the block than the release: capable weights that anyone could download, fine-tune and quantise.

The four things that make a model "a Llama"

  • Pre-normalisation with RMSNorm instead of LayerNorm (§07).
  • SwiGLU feed-forward with a hidden width near 8d/3, rounded up (§08).
  • Rotary position embeddings applied to queries and keys in every layer, instead of a learned position table (§09).
  • No bias terms in any linear layer, and an untied output head (§10).

Everything else in the family's history — grouped-query attention, a bigger tokenizer, a larger RoPE base, a long-context stage, experts — was added on top of that template, one or two changes per generation.

Takeaway: Llama is GPT's objective with a modernised block, trained on far more tokens per parameter, and released as weights. The block became the default template for later open families (see LLM Families).

29 Pitfalls

Mistakes that recur when using, fine-tuning or reasoning about Llama models.

Prompting and tokens

  • Wrong or missing chat template. Llama 2-Chat uses [INST] / <<SYS>>; Llama 3 uses header tokens and <|eot_id|>; Llama 4 uses a different set again. A base-model prompt sent to an instruct model (or the reverse) still produces text, usually worse. Use apply_chat_template.
  • Double begin-of-text. The template already emits <s> or <|begin_of_text|>; tokenising its output again with special tokens added gives two. Nothing errors.
  • Not stopping at end-of-turn. Llama 3 instruct turns end with <|eot_id|> (128009), not the base model's <|end_of_text|> (128001). If only the latter is a stop token, the model keeps writing past its turn.
  • No pad token. The original models use pad_id = −1. For batching, add a pad token and resize embeddings (the documented route), or reuse an existing token; pad on the left for generation, and make sure padding is masked out of the loss.

Positions and context

  • Dropping rope_scaling. Loading a Llama 3.1 checkpoint with code or configs that ignore the llama3 scaling reproduces Llama 3 positions; quality degrades beyond 8K with no error.
  • Assuming the advertised window is usable. 128K or 10M is what the positions support; retrieval and reasoning quality at that length must be measured.
  • Porting raw weights without the Q/K permutation between adjacent-pair and half-split RoPE layouts (§09).

Numerics and arithmetic

  • fp16 for training. Use bf16; fp16 fine-tuning of these models can overflow to NaN.
  • Quoting labels as sizes. "70B" is 69.0B (Llama 2) or 70.6B (Llama 3); "1B" is 1.24B. Use the config.
  • Comparing token counts across tokenizers. 2T Llama 2 tokens and 15T Llama 3 tokens are different units (§05).
  • Reading MoE totals as compute. Llama 4 Maverick is 400B to store but about 17B per token to run; memory planning uses the first number, FLOP planning the second.
Takeaway: most Llama failures are silent format errors — template, special tokens, padding, RoPE scaling — rather than exceptions. Check the rendered prompt and the config before debugging the model.

32 What to remember

Ten statements that summarise the family, each backed by a section above.

  • Same objective as GPT, modernised block: pre-norm RMSNorm, SwiGLU, RoPE, no biases, untied head.
  • Trained for inference. LLaMA's small models saw 77–148 tokens per parameter, Llama 3 8B about 1,900; the 405B was sized near compute-optimal.
  • Public data first, then less disclosure. LLaMA 1 published its per-source mix; later generations published less, and Llama 4 includes Meta product data.
  • The FFN width is a rounding rule, not 8d/3: floor, optional multiplier, round up.
  • RoPE makes scores relative; the base sets reach. 10,000 → 500,000, plus the code-only llama3 rescaling for 128K.
  • GQA with 8 KV heads arrived at Llama 2 70B and became universal in Llama 3 — an 8× smaller cache at 70B.
  • The tokenizer changed once in the dense era (32K → 128K), improving English compression by about 24% and making token counts incomparable across it.
  • Alignment moved from rejection sampling + PPO with two reward models (Llama 2) to rejection sampling + DPO in rounds (Llama 3) to SFT → online RL → DPO (Llama 4).
  • Llama 4 is a different architecture: top-1 MoE with a shared expert, NoPE every fourth layer, early fusion; 17B active of 109B or 400B.
  • Open weights, custom licence. Downloadable and fine-tunable, but not open source and not reproducible without the data.
Takeaway: Llama's technical contribution was a clean, reusable decoder recipe trained on many more tokens than was fashionable; its larger effect was making that recipe's weights available to everyone else.
