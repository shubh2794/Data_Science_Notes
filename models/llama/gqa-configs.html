12 Llama 2: what changed

The Llama 2 paper keeps "most of the pretraining setting and model architecture from Llama 1". The pretraining changes fit in one sentence — 40% more data, twice the context, GQA on the larger models — and most of the paper is about the chat model.

The two ablations behind the changes (appendix A.2.1)

  • Context 2k → 4k, both trained for 150B tokens: large gains on long-context tasks (NarrativeQA F1 0.21 → 17.26, Qasper 0.71 → 18.52) and no loss on general tasks such as HellaSwag (75.1 → 74.8, within noise).
  • MHA vs MQA vs GQA at 30B, 150B tokens each: GQA "performs comparably to the MHA baseline on most evaluation tasks and is better than the MQA variant on average". To keep total parameters constant, the FFN was widened by 1.3× for GQA and 1.33× for MQA — the origin of the 1.3 multiplier in the 70B config (§08).
  • Deployment reason: the largest models were served on 8 GPUs with tensor parallelism; with MQA's single KV head there is nothing to shard across GPUs, so the KV values would have to be duplicated on every GPU (making the cache as large as GQA's) or sharded by batch instead. Eight KV heads divide evenly across the eight GPUs of a node.
Takeaway: Llama 2 pretraining is LLaMA 1 with more tokens, a longer window and GQA. Its lasting contributions are GQA as the default for large open models, a commercial-use licence, and a documented chat-alignment recipe (§18–§19).

13 Grouped-query attention in Llama

GQA keeps all query heads but lets groups of them share one key head and one value head. The KV cache and the K/V projection weights shrink by the group size; the attention computation per query head is unchanged. General mechanics: Attention — GQA.

headsh query heads, n_kv key/value heads, group size g = h / n_kv attention weights per layer (bias-free)W_Q, W_O: 2 · d · h · d_h W_K, W_V: 2 · d · n_kv · d_h KV cache per token2 · L · n_kv · d_h · bytes
Query heads sharing key/value heads choose a model · slide the number of KV heads through the divisors of its query-head count · cache and weights recomputed

Where Llama uses it

  • Llama 2: only 34B and 70B (64 query heads, 8 KV heads, group of 8). The 7B and 13B stay multi-head.
  • Llama 3 onward: 8 KV heads at every size, including 8B (32 query heads, group of 4), 405B (128 query heads, group of 16), 3.2 1B (32 query heads of dimension 64) and Llama 4 (40 query heads, group of 5).
  • Converting a multi-head checkpoint to GQA is possible by mean-pooling the heads in each group and continuing training briefly (the GQA paper's "uptraining"); Llama's GQA models were trained with GQA from scratch.
Takeaway: with 8 KV heads, a 70B Llama caches as much per token as a multi-head model an eighth its width would. That — not the few percent of saved weights — is why every Llama since 3 uses it.

15 Counting the parameters from the config

Llama's count differs from GPT's 12·L·d² in three places: attention is smaller under GQA, the FFN has three matrices of width f, and the embedding is counted twice when untied. Norms add 2d per block and there are no biases or position tables.

per blockattention 2·d·h·d_h + 2·d·n_kv·d_h SwiGLU 3·d·f RMSNorm 2·d whole modelN = L·(attention + SwiGLU + 2d) + d + V·d · (1 if tied, else 2) MoE layer (Llama 4): E routed experts, one shared expert, a routerFFN_moe = (E + 1) · 3·d·f_e + d·E active: (k + 1) · 3·d·f_e + d·E

Llama 2 70B, by hand

  • Attention: 2 · 8192 · 8192 + 2 · 8192 · 1024 = 134,217,728 + 16,777,216 = 150,994,944.
  • SwiGLU: 3 · 8192 · 28672 = 704,643,072. Norms: 16,384. Per block 855,654,400; × 80 = 68,452,352,000.
  • Embeddings: 2 · 32,000 · 8192 = 524,288,000; final norm 8,192. Total 68,976,648,192 ≈ 69.0B — "70B" is a rounded label, about 1.5% high.
  • The same arithmetic gives Llama 3 70B 70.55B: identical block, but a four-times-larger vocabulary adds 1.58B of embeddings.

Takeaway: the configs land within 4% of every label except the small Llama 3.2 models, whose labels round down (1B is 1.24B, 3B is 3.21B); the Llama 4 text decoders fall about 1% short of 109B because the vision encoder is not counted. Active parameters for both Llama 4 models come out at about 17.2B, matching "17B active".

16 KV-cache bytes per token, per model

How a KV cache works is on the GPT page. What is Llama-specific is how much each release caches: GQA cut it by 8× at 70B, and long contexts then multiplied it back up.

bytes per token, one sequenceKV/token = 2 · L · n_kv · d_h · bytes_per_element worked, 16-bitLLaMA 65B 2 · 80 · 64 · 128 · 2 = 2,621,440 B = 2.5 MiB Llama 2 70B 2 · 80 · 8 · 128 · 2 = 327,680 B = 320 KiB Llama 3.1 8B 2 · 32 · 8 · 128 · 2 = 131,072 B = 128 KiB Llama 3.1 405B 2 · 126 · 8 · 128 · 2 = 516,096 B = 504 KiB
KV cache against context length set precision, batch and context · open circles are beyond a model's released window · Scout can use its chunked-attention cache

Scout's chunked cache follows the Transformers implementation (attention_chunk_size 8,192 on the RoPE layers, a full cache on every fourth, NoPE, layer); Meta's launch material describes the interleaving but not the chunking.

  • At 128K tokens, Llama 3.1 8B caches 16 GiB per sequence — about as much memory as its 16 GB of bf16 weights. Llama 3.1 405B caches 63 GiB per sequence.
  • LLaMA 65B at its full 2,048 tokens needed 5 GiB per sequence; Llama 2 70B at 4,096 tokens needs 1.25 GiB — twice the context, a quarter of the memory.
Takeaway: per token, a Llama 3.1 8B caches a quarter of a Llama 2 7B (8 KV heads vs 32), yet its 128K window makes the per-sequence cache larger than the model. Long context is a memory problem before it is a compute problem.

17 Training compute: 6·N·D against reported GPU-hours

The 6·N·D estimate is derived on the GPT page. Llama's papers and model cards report GPU-hours, which lets the estimate be turned into an implied per-GPU throughput.

training FLOPs (dense; MoE uses active parameters)C ≈ 6 · N · D implied sustained throughputFLOP/s per GPU ≈ C / (GPU-hours · 3600) Llama 3.1 405B6 × 405.85 × 10⁹ × 15.6 × 10¹² ≈ 3.80 × 10²⁵ (report: 3.8 × 10²⁵)
Compute and hardware across the family switch between 6·N·D, reported GPU-hours, implied TFLOP/s per GPU and implied utilisation

GPU-hours: LLaMA paper Table 15, Llama 2 paper Table 2, Llama 3.1 and Llama 4 model cards (H100-80GB). Llama 3 (April 2024) models have no separate figure. Peak figures are dense bf16: 312 TFLOP/s (A100), 989 TFLOP/s (H100 SXM).

  • The Llama 3 report calls its budget "almost 50× more than the largest version of Llama 2"; the ratio of the two 6·N·D values is about 46×.
  • The report's own measured rate for the 405B was 380–430 TFLOP/s per GPU (38–43% of peak) depending on the stage (Table 4); the lower rate implied by the model card's 30.84M GPU-hours presumably includes interruptions and non-training time.
  • Over a 54-day snapshot the 405B run had 466 job interruptions, 419 unexpected, about 78% attributed to confirmed or suspected hardware issues.
Takeaway: 6·N·D reproduces the one compute figure Meta published (3.8 × 10²⁵ for the 405B). Dividing by GPU-hours gives plausible utilisation — about 43% of A100 peak for Llama 2 70B — which is a useful sanity check on any claimed budget.
