03 LLaMA 1: public data, trained past compute-optimal

The LLaMA paper's argument was about inference, not training. The compute-optimal recipe (roughly 20 training tokens per parameter) minimises the cost of training a model of given quality; if the model will then serve many requests, a smaller model trained longer is cheaper overall.

lifetime compute of a dense modelC_life ≈ 6·N·D (train) + 2·N·Q (serve Q tokens) compute-optimal size for a training budget C (≈20 tokens per parameter)D ≈ 20·N ⇒ N_opt ≈ √(C / 120)

What the paper claimed and showed

  • The inference-budget argument, in the paper's words: the compute-optimal work "disregards the inference budget"; given a target level of performance, "the preferred model is not the fastest to train but the fastest at inference". It sets the compute-optimal recommendation of a 10B model on 200B tokens against its own finding that a 7B model "continues to improve even after 1T tokens".
  • Public data only. Every source in the mix (§04) was publicly available, in contrast to the undocumented corpora of GPT-3, Chinchilla and PaLM — which made the recipe reproducible in principle.
  • Headline results: LLaMA-13B "outperforms GPT-3 (175B) on most benchmarks" despite being more than ten times smaller, and LLaMA-65B is "competitive with" Chinchilla-70B and PaLM-540B. On MMLU (5-shot) the 65B scored 63.4, and a briefly instruction-tuned variant (LLaMA-I) 68.9.
  • Where the tokens-per-parameter lever actually applies. The 7B and 13B saw 1.0T tokens (about 148 and 77 per parameter); the 33B and 65B saw 1.4T (about 43 and 21). The 65B is therefore close to compute-optimal; the "trained far past optimal" story is about the small models.

Parameters from the configs; tokens from the papers and model cards (Llama 3.1 8B/70B use the model card's ~15T, 405B the report's 15.6T; Llama 4 uses the model card's ~40T and ~22T). The compute-optimal comparison uses the 20-tokens-per-parameter rule of thumb, not a fitted scaling law.

Takeaway: LLaMA made "train the small model much longer" the default for open models. By Llama 3 the 8B saw about 1,900 tokens per parameter, while the report sized its 405B to be roughly compute-optimal for the flagship budget.

05 Tokenizers: 32K SentencePiece, then 128K tiktoken, then 202K

Llama 1 and 2 share one 32,000-entry SentencePiece BPE; Llama 3 replaced it with a 128K byte-level BPE built on the tiktoken library; Llama 4's config has 202,048 embedding rows. General BPE theory is in Tokenization — BPE.

Why the vocabulary grew

  • Compression. The Llama 3 report measures English compression rising from 3.17 to 3.94 characters per token — about 24% more text per token, so the same training compute "reads" more text and the same context window holds more.
  • Multilinguality. The 28K extra tokens were chosen for non-English languages, improving compression and downstream scores "with no impact on English tokenization".
  • The cost is at small scale. Embedding matrices grow as V·d. For Llama 3.2 1B the (tied) embedding is 21% of all parameters; for Llama 3.1 405B the two untied matrices are about 1% (use the calculator in §15). This is part of why the smallest Llama 3.2 models tie their embeddings.
  • A tiktoken detail. The Transformers documentation notes the Llama 3 tokenizer "ignores BPE merge rules when an input token is part of the vocab": if a whole word is itself a vocabulary entry it is emitted directly, even if no merge sequence would produce it.
Takeaway: Llama 3's biggest single change apart from data volume was the tokenizer. Token counts before and after it are not comparable: "2T tokens" of Llama 2 and "15T tokens" of Llama 3 are measured in different units.

07 RMSNorm, worked by hand

LayerNorm subtracts the mean, divides by the standard deviation, then applies a gain and a bias. RMSNorm skips the mean and the bias: it divides by the root-mean-square and applies a gain. The placement (pre-norm, plus a final norm) is the same as GPT-2's; see Transformers — norms for the general comparison.

LayerNorm (GPT)LN(x) = γ ⊙ (x − μ) / √(σ² + ε) + β μ = mean(x), σ² = mean((x − μ)²) RMSNorm (Llama)RMSNorm(x) = g ⊙ x / √(mean(x²) + ε) epsilon in the released configsrms_norm_eps = 1e-6 (LLaMA 7B/13B/33B) · 1e-5 (LLaMA 65B, Llama 2 onward)

A four-number example

Why the simpler norm is enough

  • The RMSNorm paper argued that LayerNorm's benefit comes mainly from re-scaling invariance, not re-centring, and reported similar quality with less computation. RMSNorm needs one reduction per token instead of two.
  • One learned vector per norm instead of two: a Llama block has 2d norm parameters, a GPT block 4d. At any real width this is negligible; the saving that matters is the reduction, which is memory-bound on accelerators.
  • Because the residual stream is not mean-centred, a constant offset in the stream is not removed by the norm. Nothing in Llama relies on it being removed.
Takeaway: RMSNorm is LayerNorm without the mean and the bias. It removes scale but not shift, costs one reduction instead of two, and has one gain vector per norm.

08 SwiGLU and the (2/3)·4d hidden size

A SwiGLU feed-forward multiplies a SiLU-activated projection element-wise by a second, linear projection before projecting back. Three weight matrices instead of two, so the hidden width is cut by a third to keep the parameter count — then rounded up by the reference code.

SwiGLU FFN (three matrices, no biases)FFN(x) = W₂ · ( SiLU(W₁x) ⊙ W₃x ) SiLU(z) = z · sigmoid(z) parameter match with a 4d GELU FFN3 · d · f = 2 · d · 4d ⇒ f = 8d/3 ≈ 2.667·d the width rule in the reference codef₀ = ⌊2 · 4d / 3⌋ f₁ = ⌊ffn_dim_multiplier · f₀⌋ (if a multiplier is set) f = multiple_of · ⌈f₁ / multiple_of⌉

The gate, by hand

  • If for one hidden unit W₁x = 1.0 and W₃x = 2.0: SiLU(1.0) = 1.0 × 0.731 = 0.731, times 2.0 gives 1.462.
  • If instead W₁x = −2.0: SiLU(−2.0) = −2.0 × 0.119 = −0.238, times 2.0 gives −0.477. The gate is smooth and lets a small negative value through, unlike ReLU.
  • For LLaMA 7B (d = 4096): 4d = 16,384, ⌊2·16,384/3⌋ = 10,922, rounded up to a multiple of 256 gives 11,008 — the intermediate_size in the config, 2.6875·d.

09 RoPE, worked by hand

Rotary position embedding splits each query and key head vector into two-dimensional pairs and rotates pair i by an angle proportional to the token's position. The dot product of a rotated query and a rotated key then depends only on their relative offset. General theory and alternatives: Transformers — RoPE.

frequency of pair i (head dimension d_h, base θ)ωᵢ = θ^(−2i / d_h) i = 0, 1, …, d_h/2 − 1 rotation of a pair at position mR(mωᵢ) = [ cos mωᵢ −sin mωᵢ ] [ sin mωᵢ cos mωᵢ ] why only the offset matters(R(mω)q) · (R(nω)k) = qᵀ R(mω)ᵀ R(nω) k = qᵀ R((n − m)ω) k

A hand-worked pair

  • Pair i = 0 has ω₀ = θ⁰ = 1 radian per token for any base. Let q = k = (1, 0).
  • Query at m = 2: R(2)q = (cos 2, sin 2) = (−0.416, 0.909). Key at n = 0: unchanged, (1, 0). Score −0.416 = cos 2.
  • Move both by five tokens (m = 7, n = 5): q = (cos 7, sin 7), k = (cos 5, sin 5), score cos 7·cos 5 + sin 7·sin 5 = cos 2 = −0.416 again. Absolute position has cancelled.
  • The last pair (i = 63 of a 128-dimensional head) rotates at θ^(−126/128): with θ = 10,000 its wavelength is about 54,000 tokens; with θ = 500,000 about 2.56 million. Slow pairs carry long-range position; fast pairs carry local order.
Rotate one pair, check the score depends only on m − n choose the pair and base · move the two positions · the button shifts both by 10 tokens

Implementation facts that matter when porting weights

  • Only Q and K are rotated; V is not, so positions affect where attention goes but are not written into the values.
  • The rotation is applied in every layer, after the Q/K projections and before the dot product — a GQA key head is rotated once and shared by its query group.
  • Meta's reference code pairs adjacent dimensions (it views each head as complex numbers); the Transformers implementation pairs dimension j with j + d_h/2 (rotate_half). The two are equivalent only because the conversion script permutes the rows of the Q and K projection weights. Loading raw reference weights into the Transformers module without that permutation produces wrong outputs without an error (§30).
Takeaway: RoPE turns absolute positions into relative ones inside the attention score, with no learned table and no row limit. Its reach is set by the base θ: Llama 3 raised it from 10,000 to 500,000 so that more pairs have wavelengths longer than the training context (§20).

10 No biases, untied embeddings

Two small choices that the LLaMA paper does not discuss but the released weights make explicit: no linear layer has a bias, and the output projection is a separate matrix from the input embedding.

Biases

  • Every Llama config sets attention_bias = false and mlp_bias = false; the RMSNorms have no bias either. In a GPT block the biases total 13d per block — at d = 8192 about 106k parameters, 0.01% of a block. The saving is not the point.
  • The reasons usually given are simplicity and stability at scale (PaLM also dropped biases, reporting better training stability for large models). The Llama papers themselves do not state a reason.
  • Later families differ: Qwen kept Q/K/V biases through Qwen2.5, which is one of the few block-level differences from Llama (see LLM Families).

Untied output head

  • GPT ties W_out = W_embᵀ. Llama keeps two V × d matrices, so its embedding cost is 2·V·d: for Llama 3.1 8B that is 1.05B of 8.03B parameters (13%), for 405B 4.2B of 405.9B (1%).
  • Llama 3.2 1B and 3B tie (tie_word_embeddings = true). At 1.24B total, an untied 128,256 × 2048 head would add another 263M parameters — 21% more.
  • Llama 4 Scout and Maverick are untied again.
Takeaway: no biases anywhere and a separate output head, except where the embedding would be too large a share of a small model. Both show up only in the configs, which is why parameter counts should be computed from those, not from the papers' prose.

11 Optimisation and training efficiency

The optimiser settings were set in LLaMA 1 and barely changed through Llama 2. What changed from Llama 3 is batch-size and context scheduling at much larger scale.

LLaMA 1's efficiency work

  • A memory-efficient causal attention (from the xformers library) that neither stores attention weights nor computes scores for masked positions.
  • Hand-written backward passes so that activation checkpointing saves the expensive activations (linear-layer outputs) and recomputes only cheap ones; model and sequence parallelism; overlapping GPU communication with computation.
  • Result reported for the 65B: about 380 tokens per second per GPU on 2,048 A100-80GB GPUs, so 1.4T tokens took about 21 days. That rate times 6·N is about 149 TFLOP/s per GPU — consistent with the GPU-hours in §17.
Takeaway: the recipe is plain AdamW with β₂ = 0.95, cosine decay and weight decay 0.1. Llama 3 added the practices that matter at 16K GPUs: growing batch and sequence length early, a separate long-context stage, and an annealing phase with checkpoint averaging.
