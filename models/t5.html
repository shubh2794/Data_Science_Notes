T5 — the Text-to-Text Transfer Transformer

T5 is an encoder–decoder Transformer from Google that casts every text task — translation, summarisation, classification, regression, question answering — as "read a string, write a string", and a 2019 study that used that single interface to compare, one factor at a time, the architectures, pretraining objectives, datasets, transfer strategies and scaling choices of the time. This note covers it in detail: the text-to-text format and its task prefixes, the architecture (pre-norm RMS-style layer norm, bias-free dense layers, the bucketed relative position bias, tied embeddings, ReLU feed-forward in the original and GEGLU in v1.1), every released configuration with parameter counts recomputed from the configurations, the SentencePiece vocabulary and its sentinels, how the C4 corpus was filtered, the span-corruption objective worked by hand with its length arithmetic, the systematic study table by table, the pretraining and fine-tuning schedule with Adafactor, the headline results, the successors T5 v1.1, mT5, ByT5, Flan-T5, UL2 and T5Gemma, the compute arithmetic of encoder–decoder against decoder-only models, and practical use with pitfalls.

01 What T5 is

T5 ("Exploring the Limits of Transfer Learning with a Unified Text-to-Text Transformer", arXiv 1910.10683, JMLR 2020) is two things at once: a family of encoder–decoder Transformers, released at five sizes from 60M to 11B parameters, and a large controlled study of transfer learning for NLP. Both rest on one decision — every task is text in, text out — so the same model, loss, optimiser and decoding procedure serve all of them.

every task, pretraining included: maximise the likelihood of the target string given the input string (teacher forcing)L(θ) = − Σₜ₌₁ᵐ log p_θ(yₜ | y₁ … yₜ₋₁, Enc_θ(x)) wherex = task prefix + input text, y = target text + </s> pretraining input and target come from unlabeled text by span corruptionx = "Thank you <X> me to your party <Y> week." y = "<X> for inviting <Y> last <Z>" inference: decode the target string, then read the answer out of it"mnli hypothesis: … premise: …" → "entailment"; "stsb sentence1: … sentence2: …" → "3.8"

What goes in and what comes out

  • Input: a string that begins with a short task prefix — translate English to German:, summarize:, cola sentence: — tokenized with a 32,000-piece SentencePiece model; up to 512 tokens during pretraining.
  • Output: a string generated token by token: a translation, a summary, a class name such as entailment, a number such as 3.8, or an answer span.
  • Training: pretraining with span corruption on C4 (about 750 GB of filtered English web text), then fine-tuning on each task with the same cross-entropy loss. The released v1.0 checkpoints were pretrained on a mixture of C4 and the supervised tasks (final recipe).

02 Text-to-text: every task as a string, named by a prefix

To tell the model which task to perform, T5 prepends a task-specific text prefix to the input. Classification labels become words, regression becomes a number written as text, and reference-resolution tasks become "name the noun". The paper found the exact wording of the prefix had limited impact and treated it as a hyperparameter.

03 Architecture at a glance

T5 follows the original Transformer encoder–decoder closely. The paper lists three departures: layer normalisation without a bias and without mean-centring, applied to the input of each sub-layer (pre-norm) with the residual path left un-normalised; a simplified relative position scheme in place of sinusoidal embeddings; and no additive biases. The output softmax shares its weights with the input embedding.

encoder block (N blocks), then a final norm and dropouth ← h + Dropout(SelfAttn_full(LN(h), bias_enc)) h ← h + Dropout(FF(LN(h))) decoder block (N blocks), then a final norm and dropouth ← h + Dropout(SelfAttn_causal(LN(h), bias_dec)) h ← h + Dropout(CrossAttn(LN(h), z)) h ← h + Dropout(FF(LN(h))) output distribution: the tied embedding E; the Hugging Face code rescales by d_model^(−1/2) when tiedp(yₜ | y<ₜ, x) = softmax( E · (d_model^(−1/2) · hₜ) ), E ∈ ℝ^(32,128 × d_model)

What is and is not in a block

  • Attention has four bias-free projections: W_Q, W_K, W_V ∈ ℝ^(d_model × h·d_kv) and W_O ∈ ℝ^(h·d_kv × d_model). The inner width h·d_kv need not equal d_model — T5-3B and T5-11B make it 4× and 16× larger (configurations).
  • Feed-forward is dense–ReLU–dense with no biases (v1.0), or a GEGLU with three matrices (v1.1).
  • Position enters only through the bias added to attention logits, computed in the first layer of each stack and reused by every layer of that stack. Cross-attention has no position bias.
  • Dropout (0.1 in the study) is applied inside the feed-forward network, on each residual branch, on the attention weights, and at the input and output of each stack.

04 The simplified layer norm (RMS-style) and pre-norm residuals

T5's layer normalisation only rescales: it divides each vector by its root-mean-square and multiplies by a learned gain, with no mean subtraction and no additive bias. This is the operation later named RMSNorm; the Hugging Face implementation says so in its comments, and computes the mean square in 32-bit floats even for half-precision inputs.

standard LayerNorm, for comparisonLN(x) = g ⊙ (x − μ) / √(σ² + ε) + b, μ = (1/d) Σᵢ xᵢ, σ² = (1/d) Σᵢ (xᵢ − μ)² T5 layer norm: no centring, no biasT5LN(x) = g ⊙ x / √( (1/d) Σᵢ xᵢ² + ε ), g ∈ ℝ^d initialised to 1, ε = 10⁻⁶ pre-norm residual: the skip path is never normalisedh ← h + F(T5LN(h)) (post-norm would be h ← LN(h + F(h)))

Worked example

Take x = (2, 4, 6, 8). Its mean square is (4 + 16 + 36 + 64)/4 = 30, so T5LN(x) = x / √30 = (0.365, 0.730, 1.095, 1.461) with g = 1. Standard LayerNorm would first subtract the mean 5, giving (−3, −1, 1, 3) / √5 = (−1.342, −0.447, 0.447, 1.342). Adding a constant c to every coordinate changes T5LN's output (the mean is not removed) but leaves LayerNorm's unchanged; scaling x by any positive factor leaves both unchanged (up to ε).

  • Parameters. One gain vector of d_model per norm: two per encoder block, three per decoder block, plus one final norm per stack — 768 × (2·12 + 3·12 + 2) = 47,616 parameters in T5-Base, 0.02% of the model.
  • Why pre-norm. With the norm inside the branch, the residual stream is a sum of branch outputs plus the embedding; gradients reach early layers through the identity path undisturbed, which is generally credited with making deep pre-norm stacks such as T5's 24 + 24 layers easier to train than post-norm ones.
  • A consequence for half precision. Because nothing normalises the residual stream until the final norm, its magnitude can grow with depth — one ingredient of the fp16 overflow problem in pitfalls.
Takeaway: T5's norm is RMSNorm before it had a name: cheaper than LayerNorm (no mean, no bias) and, in the pre-norm position, friendly to deep stacks. Loading T5 weights into a LayerNorm-based implementation silently changes the network.

05 Relative position bias: 32 log-spaced buckets

T5 has no position embeddings on its tokens. Instead, each attention head adds a learned scalar to every query–key logit, chosen by the bucketed offset between the key's and the query's positions. There are 32 buckets per head; small offsets get their own bucket, larger ones share logarithmically wider buckets, and everything beyond the last boundary shares one. The table is learned once per stack — in the first layer — and reused by all layers of that stack; the encoder's and the decoder's tables are separate.

attention logits of head h: no 1/√d_kv scaling in T5 (see the next section)sᵢⱼ = qᵢ · kⱼ + B_h[ bucket(j − i) ], B ∈ ℝ^(32 × heads) per stack bidirectional (encoder): half the buckets for keys after the query, half for keys at or before itn = 32 / 2 = 16, offset r = j − i, base = 16 · [r > 0], a = |r| causal (decoder): future offsets never occur; all 32 buckets measure the distance into the pastn = 32, base = 0, a = max(0, −r) exact buckets for small distances, logarithmic above, capped at the last bucket (max_distance D = 128)e = n / 2; bucket = base + a if a < e bucket = base + min( n − 1, e + ⌊ ln(a / e) / ln(D / e) · (n − e) ⌋ ) otherwise

For the encoder, a = 20 is not exact (20 ≥ 8), so bucket = 8 + ⌊ln(20/8)/ln(16) · 8⌋ = 8 + ⌊0.3305 · 8⌋ = 8 + 2 = 10, the bucket that starts at 16. The formula would reach 16 — one past the last bucket — at a = 128, which is where "max distance 128" comes from; but the cap at n − 1 means the last bucket already starts at 91 in the encoder and 113 in the decoder. The paper's sentence "ranges that increase in size logarithmically up to an offset of 128 beyond which we assign all relative positions to the same embedding" is therefore true but loose: offsets from 91 (encoder) or 113 (decoder) upward already share one value. One more quirk of the encoder: offset 0 goes to bucket 0 and a key after the query has distance at least 1, so bucket 16 ("after, distance 0") can never be selected — the encoder uses 31 of its 32 buckets.

Consequences

  • Cheap and length-agnostic. The whole position mechanism of T5-Base is 32 × 12 = 384 numbers per stack. Nothing ties the model to 512 positions; the n_positions: 512 in the v1.0 configs is informational. Beyond the training length quality is not guaranteed, and attention cost still grows quadratically.
  • A single layer is blind beyond the last boundary — it cannot tell a key 200 tokens away from one 2,000 away — but, as the paper notes, stacked layers can combine local information to build sensitivity to larger offsets.
  • Padding side does not matter for the encoder, because nothing depends on absolute position (the library documentation says left or right padding both work).

06 Attention details: no √d_kv scaling, and the initialisation that replaces it

T5's attention does not divide the logits by √d_kv. The released code (Mesh TensorFlow, and the Hugging Face port, whose comment reads "T5 folds the relative position bias into the attention scores and does not scale the query/key dot product") instead initialises W_Q with a smaller standard deviation so the logits start at the same scale. The paper does not mention this; it is a code-level detail that matters if you port weights.

standard scaled dot-product attentionA = softmax( Q Kᵀ / √d_kv + mask ) V T5 attention: no scaling, position bias addedA = softmax( Q Kᵀ + B + mask ) V initialisation in the released code (factor 1): W_Q absorbs the missing 1/√d_kvW_Q ~ N(0, (d_model · d_kv)^(−1)), W_K, W_V ~ N(0, d_model^(−1)) W_O ~ N(0, (h · d_kv)^(−1)), E ~ N(0, 1) feed-forward initialisationW_in ~ N(0, d_model^(−1)), W_out ~ N(0, d_ff^(−1))

Why the two are equivalent at initialisation

With inputs of unit RMS, a query component qₐ = Σᵢ xᵢ W_Q,ᵢₐ has variance d_model · Var(W_Q) = 1/d_kv under T5's initialisation, versus 1 under the usual one. A logit q · k sums d_kv products, so its variance is d_kv · (1/d_kv) · 1 = 1 — the same as the standard √d_kv-scaled logit. The difference is what happens during training: T5's effective scale is a learned property of W_Q, not a fixed constant.

The tied output projection

Because the embedding E is initialised with unit variance and shared with the softmax layer, v1.0 multiplies the final decoder state by d_model^(−1/2) before the tied projection (768^(−1/2) = 0.0361 for T5-Base). T5 v1.1 unties the two matrices and drops this rescaling; the Hugging Face code decides which to do from the checkpoint's tie_word_embeddings flag. Mixing up the two is a silent error: logits come out √d_model = 27.7 times too large or too small.

Takeaway: when porting T5 to another codebase, three things have no counterpart in a textbook Transformer and each changes outputs silently: no 1/√d_kv in attention, the d_model^(−1/2) rescale before a tied output layer, and the scale-only norm.

07 The feed-forward layer: ReLU in T5, GEGLU in v1.1

The original T5 feed-forward network is two bias-free matrices with a ReLU between them. T5 v1.1 replaces it with GEGLU, from Shazeer's "GLU Variants Improve Transformer" (2020): the hidden layer is the elementwise product of a GELU-activated projection and a second, linear projection. The gate adds a third matrix, so v1.1 shrinks d_ff to keep sizes comparable.

T5 v1.0: W₁ is d × d_ff, W₂ is d_ff × d — 2 · d · d_ff parametersFF_ReLU(x) = max(0, x W₁) W₂ T5 v1.1 (feed_forward_proj = "gated-gelu", tanh approximation of GELU): W₀, W₁ are d × d_ff′ — 3 · d · d_ff′ parametersFF_GEGLU(x) = ( GELU(x W₀) ⊙ x W₁ ) W₂ same parameter count when3 · d · d_ff′ = 2 · d · d_ff ⇒ d_ff′ = (2/3) · d_ff applied to the released shapesBase: 3,072 → 2,048 (released 2,048); Large: 4,096 → 2,730.7 (released 2,816)

What the gate changes

  • A ReLU unit's output depends on one projection and is exactly zero for half its input range. A GEGLU unit multiplies a smooth, mostly-positive GELU of one projection by an unbounded linear value of another, so it can output either sign and its magnitude is modulated by a second direction of the input.
  • The GLU-variants paper reported lower pretraining perplexity for GEGLU and SwiGLU than for ReLU at matched parameters and compute on the T5 setup, and gains on downstream fine-tuning; SwiGLU is the variant most later decoder-only LLMs adopted.
  • The released v1.1 shapes are not all "2/3 of v1.0": Base matches (2,048), Large uses 2,816, and Small changes shape entirely (d_ff 1,024, 6 heads, 8 + 8 layers).

Reading the odd shapes

  • T5-3B projects 1,024-wide states to a 4,096-wide attention space (32 heads of 128) and back; each attention layer has 4 · 1,024 · 4,096 = 16.8M parameters, four times a d = 1,024 layer's. Its feed-forward layer is 16 · d_model wide.
  • T5-11B goes further: 128 heads of 128 (inner width 16,384) and a 65,536-wide feed-forward layer, 64 · d_model. A single feed-forward matrix is 1,024 × 65,536 = 67.1M parameters; the two of them in one block hold more than all of T5-Small's non-embedding weights.
  • v1.1 reverses the trade. XL and XXL widen d_model (2,048 and 4,096) and use ordinary 64-wide heads — "larger d_model and smaller num_heads and d_ff", as the release notes put it. The residual stream, and hence the embedding, gets wider: XXL's two 32,128 × 4,096 embedding tables (untied) are 263M parameters against 11B's single 32.9M.
  • Size labels are rounded loosely. "Large ≈ 770M" overstates the configuration by 4.4%; "3B" is 2.85B. The paper's own Section 3.7 text says "around 2.8 billion".
Takeaway: the five v1.0 sizes are not one shape scaled up — above Large, only the attention inner width and d_ff grow. Any calculation that assumes inner width = d_model or d_ff = 4·d_model is wrong for T5-3B, T5-11B and v1.1 Small.

10 The SentencePiece vocabulary: 32,000 pieces and 100 sentinels

T5 uses one SentencePiece model of 32,000 pieces for inputs and outputs, trained on 10 parts English C4 to 1 part each of German, French and Romanian Common Crawl text so that the translation targets can be spelled. The released tokenizer adds 100 sentinel tokens for span corruption, for 32,100 ids; the checkpoints' embedding tables have 32,128 rows, the last 28 unused.

ids in the released tokenizer<pad> = 0 (also the decoder start token), </s> = 1, <unk> = 2, pieces 3 … 31,999 sentinels count down from the top of the id range<extra_id_0> = 32,099, <extra_id_1> = 32,098, …, <extra_id_99> = 32,000 id(<extra_id_k>) = 32,099 − k embedding rows32,128 = 251 · 128 ≥ 32,100 (28 rows padding)

What the vocabulary cannot represent

The piece inventory was learned mostly from C4 (whose cleaning removed pages with a curly brace in their prose lines) plus some German, French and Romanian, so some common characters are not in it and become <unk> (id 2): {, }, ~, < (although > is in the vocabulary), most CJK characters, and some accented letters such as ï. The normaliser also collapses runs of whitespace and turns newlines into spaces. A fine-tuned T5 therefore cannot copy code or JSON braces from its input to its output, and it cannot preserve line structure.

Takeaway: the vocabulary is English-centred with just enough German, French and Romanian for WMT. Anything else — code, braces, CJK, line breaks — loses information before the model sees it; mT5's 250k vocabulary and ByT5's bytes exist to fix exactly this.

11 C4: the Colossal Clean Crawled Corpus and its filters

C4 is the April 2019 Common Crawl "web extracted text" after a set of line- and page-level heuristics, English-language detection and deduplication — about 750 GB of text (745 GB in the paper's Table 8), released through TensorFlow Datasets. The paper describes it as "reasonably clean and natural English text", large enough that the study's 34B-token pretraining never repeats data.

The filters, as the paper lists them

  1. Keep only lines that end in a terminal punctuation mark (period, exclamation mark, question mark, end quotation mark).
  2. Discard pages with fewer than 3 sentences; keep only lines with at least 5 words.
  3. Remove any page containing a word from the "List of Dirty, Naughty, Obscene or Otherwise Bad Words".
  4. Remove any line containing the word "Javascript".
  5. Remove any page containing "lorem ipsum".
  6. Remove any page containing a curly bracket "{".
  7. Remove citation markers such as [1] and [citation needed].
  8. Remove lines containing "terms of use", "privacy policy", "cookie policy", "uses cookies", "use of cookies" or "use cookies".
  9. Deduplicate: "discarded all but one of any three-sentence span occurring more than once".
  10. Keep pages that langdetect classifies as English with probability at least 0.99.

What the released code does differently

The TensorFlow Datasets implementation (c4_utils.py) applies the line rules in a fixed order, and three details differ from the paper's description:

  • Page-killing tests only see surviving lines. The "lorem ipsum" and "{" checks run inside the line loop after the terminal-punctuation and five-word checks, so a brace in a short or unpunctuated line (a code fragment, a menu) is dropped with that line and does not remove the page. The paper says any page containing a brace is removed.
  • Extra line rules. The code also drops lines ending in an ellipsis "…" (three periods) and lines containing any "word" longer than 1,000 characters; neither is in the paper.
  • Deduplication is by line, not three-sentence span. The code hashes each lower-cased line, keeps it in one page only, and then re-applies the 3-sentence minimum to the page that remains.

What the study found about C4 itself

Pretraining the baseline on "C4, unfiltered" (6.1 TB, language detection only) was worse on every task — GLUE 81.46 against 83.28, SuperGLUE 68.04 against 71.36 (data study). Later audits of C4 (not part of the T5 paper) found that the bad-words filter disproportionately removed text about and by some minority groups and that benchmark text leaked into the corpus, which is worth remembering when C4 is used as "clean" data.

Takeaway: C4 is a handful of cheap, transparent heuristics applied at web scale. They helped measurably, but the code is the specification — and the code's order of operations makes the "{" and "lorem ipsum" rules weaker than the paper's wording.

12 Span corruption, worked by hand

T5's pretraining objective removes about 15% of the tokens of a text in contiguous spans averaging 3 tokens, replaces each span with a unique sentinel token, and trains the decoder to output only the removed spans, each introduced by its sentinel (plus a closing sentinel when the text ends with kept tokens, as in the paper's example). Only the corrupted tokens are predicted, which keeps targets short.

for a text of T tokens, noise density r = 0.15, mean span length m = 3 (the released random_spans_noise_mask)noise = round(r · T), spans S = round(noise / m), non-noise = T − noise span lengths: a random split of the noise tokens into S non-empty parts, and of the rest into S parts; the text alternates kept / dropped, starting with keptT = k₁ + n₁ + k₂ + n₂ + … + k_S + n_S, Σ nᵢ = noise, kᵢ, nᵢ ≥ 1 sequence lengths, counting one sentinel per span and the end-of-sequence token|input| = (T − noise) + S + 1, |target| = noise + S + 1

Worked example: the paper's sentence

"Thank you for inviting me to your party last week." is 11 pieces for the T5 tokenizer (every word one piece, plus "."). Suppose "for inviting" and "last" are dropped (the paper's Figure 2):

The final sentinel <extra_id_2> marks the end of the last span (the paper's <Z>); it appears because the sentence ends with kept tokens ("week ."). In the released pipeline the mask always ends with a dropped span (spans alternate kept, dropped, starting with kept, and are not rolled), so real pretraining inputs end with a sentinel and real targets have none trailing — which is why the length formula above has exactly S sentinels on each side. The same sentence under the BERT-style objective would need an 11-token target — the whole text — and under "drop corrupted tokens" an input with no sentinels.

Baseline objective versus final objective

  • The study's baseline (Section 3.1.4) chooses tokens i.i.d. with probability 0.15 and merges consecutive dropped tokens into one sentinel. Spans are then usually length 1: with independent choices the expected run length is 1/(1 − 0.15) ≈ 1.18.
  • The released models (Section 3.7) use explicit span corruption with mean span length 3, which Table 7 found "slightly (but significantly)" better than i.i.d. on most non-translation benchmarks, and slightly cheaper because there are fewer sentinels.

20 The schedule: steps, tokens, the inverse-square-root rate and Adafactor

Pretraining in the study runs 2¹⁹ steps of 128 sequences of 512 tokens, packed so each batch holds about 2¹⁶ tokens — 2³⁵ ≈ 34B tokens in all, a small fraction of C4, so nothing repeats. The learning rate is 1/√max(n, k) with k = 10⁴ warm-up steps; the optimiser is Adafactor; decoding during the study is greedy.

Notes on the schedule

  • "Exponentially decays". The paper describes the post-warm-up phase as exponential decay; 1/√n is a power law — from step 10⁴ to 2¹⁹ the rate falls by √52.4 = 7.24×, not by an exponential factor. The formula, not the adjective, is what the code implements.
  • Why not a triangular schedule? It scored slightly better but needs the total step count in advance; the study varied step counts, so it used the schedule that does not.
  • BERT comparison. 34B tokens is about 1/4 of BERT's roughly 137B and 1/64 of RoBERTa's 2.2T; the final models' 1T is about 32× the baseline.
  • Adafactor (Shazeer and Stern 2018) keeps, for each weight matrix, row and column statistics of the squared gradients instead of a full second-moment matrix, and in its memory-saving configuration no momentum. The paper names only the optimiser and does not say which configuration it used; the memory saving matters most at 11B parameters (see the figure).

Takeaway: T5's recipe is simple and scale-free — a warm-up constant, then 1/√n, no knowledge of the total length needed — with an optimiser whose state for T5-11B is millions of numbers rather than tens of billions.

21 Putting it together: the recipe behind the released models

For the released T5 models the authors changed the baseline in six ways: span corruption (mean length 3) instead of i.i.d. noise; 1 million steps at 2¹¹ sequences of 512 (about 1T tokens); five sizes; multi-task pretraining; fine-tuning on individual GLUE and SuperGLUE tasks with small batches; and beam search for long outputs.

  • Multi-task pretraining. The unsupervised task was mixed with the supervised ones by examples-proportional mixing, with artificial sizes for the unlabeled data of 710,000 (Small), 2,620,000 (Base), 8,660,000 (Large), 33,500,000 (3B) and 133,000,000 (11B), and WMT En–Fr and En–De capped at 1M examples. This is why the released v1.0 checkpoints respond to translate English to German: before any fine-tuning.
  • Per-task GLUE / SuperGLUE fine-tuning with a batch of 8 sequences instead of 2¹¹ (so small tasks are not repeated within a batch) and checkpoints every 1,000 steps.
  • Decoding. Beam width 4 with length penalty 0.6 for WMT and CNN/DM; greedy elsewhere.
  • Test sets through the GLUE and SuperGLUE servers, standard CNN/DM test, newstest2014 / 2015 / 2016 for En–De / En–Fr / En–Ro; SQuAD on the validation set because the server could not run the largest models.

24 mT5: 101 languages

mT5 ("mT5: A Massively Multilingual Pre-trained Text-to-Text Transformer", arXiv 2010.11934) applies the T5 v1.1 recipe to mC4, a Common Crawl corpus covering 101 languages, with a 250,000-piece SentencePiece vocabulary. Sizes run from Small (≈ 300M) through Base (580M), Large (1.2B) and XL (3.7B) to XXL (13B), each pretrained for 1M steps on batches of 1,024 length-1,024 inputs — about 1T input tokens, the same amount as T5.

  • A slip in the ByT5 paper. ByT5 describes mT5-Base's "vocabulary and softmax output matrices" as "256 million parameters, or about 66% of the total".   • Classification cost. The mT5 paper points out that an encoder–decoder classifies at about the cost of T + 2 tokens (input, label, end) against T + 1 for an encoder-only model with a [CLS] token, despite twice the parameters.
Takeaway: mT5 is T5 v1.1 with a multilingual corpus and a vocabulary eight times larger; at small sizes most of its parameters are embeddings.

25 ByT5: bytes instead of pieces

ByT5 ("ByT5: Towards a Token-Free Future with Pre-trained Byte-to-Byte Models", arXiv 2105.13626) removes the tokenizer: text is fed as UTF-8 bytes, with 256 byte ids plus 3 special ids (padding, end-of-sequence, and an unused unknown). Sentinels reuse the final 100 byte ids, the mean masked span grows to 20 bytes, and the encoder is three times as deep as the decoder.

26 Flan-T5: instruction-tuned T5

Flan-T5 ("Scaling Instruction-Finetuned Language Models", arXiv 2210.11416) fine-tunes T5 models on 1,836 tasks (473 datasets, 146 task categories) phrased as instructions, with and without chain-of-thought exemplars, so that one checkpoint follows unseen instructions zero-shot. The released checkpoints share T5 v1.1's architecture (GEGLU, untied output layer) at five sizes: 80M, 250M, 780M, 3B and 11B.

27 UL2: a mixture of denoisers

UL2 ("UL2: Unifying Language Learning Paradigms", arXiv 2205.05131) keeps the T5 framework but pretrains on a mixture of seven denoising tasks in three families, each announced to the model by a mode token, [R], [S] or [X]. Its 20B encoder–decoder (19.5B parameters, 32 + 32 layers, d_model 4,096, d_ff 16,384, 16 heads of 256, the T5 32k vocabulary) was trained on 1T C4 tokens and later instruction-tuned as Flan-UL2.

Takeaway: UL2 is the T5 study's objective axis revisited: instead of picking one point on the denoising plateau, mix distant points — short spans, long spans, and prefix-LM — and let a mode token select the behaviour.

28 T5Gemma: encoder–decoders adapted from decoder-only models

T5Gemma ("Encoder-Decoder Gemma: Improving the Quality-Efficiency Trade-Off via Adaptation", arXiv 2504.06225) builds encoder–decoder models by initialising both stacks from a pretrained decoder-only Gemma 2 model and continuing pretraining with prefix-LM (with distillation) or UL2 objectives, on up to 2T tokens. Despite the name, the blocks are Gemma 2's (rotary position embeddings and its other components), not T5's.

  • Balanced and unbalanced pairs. 2B-2B and 9B-9B pair an encoder and decoder of the same size; 9B-2B pairs a large encoder with a small decoder to keep generation cheap.
  • Reported results. After instruction tuning, Gemma 2B-2B outperforms the decoder-only Gemma 2B by about 7%, and 9B-2B surpasses 2B-2B by more than 3%; adaptation reaches its decoder-only counterpart's quality after only tens of billions of tokens.
  • Why it connects to T5. It revisits the T5 study's architecture finding under modern conditions: at similar inference cost, an encoder–decoder with a bidirectional encoder fine-tunes better.
Takeaway: the encoder–decoder idea survives into the decoder-only era by adaptation: reuse a strong decoder-only model's weights, then pay for bidirectional reading only where it helps.

29 Encoder–decoder versus decoder-only: the compute arithmetic

An L + L encoder–decoder has roughly the parameters of a 2L-layer decoder-only model but the per-example compute of an L-layer one, because each token passes through only one stack. That is the equivalence the study used; it also has consequences at inference, where the encoder runs once and the decoder's cache holds only target tokens plus a fixed cross-attention cache.

One encoder layer processes 512 tokens: 512 · (4 · 768 · 768 + 2 · 768 · 3,072) = 3.62 × 10⁹ multiply–accumulates in its matrices plus 2 · 512² · 768 = 0.40 × 10⁹ in attention. One decoder-only layer of the same width on 640 tokens needs 640 · 7.08 × 10⁶ = 4.53 × 10⁹ plus 2 · 640² · 768 = 0.63 × 10⁹. The figure sums these over all layers for the three models of the paper's comparison.

Compute counts the matrix multiplications and attention products of one forward pass over an (input, target) pair, as in training, and excludes the embedding and softmax layers, norms and the causal-mask saving (full n² products are counted, as a plain implementation computes them). The decoder-only models take the chosen config's block shape: N layers (same compute) or 2N layers (same parameters). The cache assumes 16-bit values.

  • When the input is long and the output short (classification, extraction, summarisation), the encoder–decoder does the bulk of its work once, bidirectionally, and decodes against a fixed cross-attention cache.
  • When outputs are long and inputs short (open-ended generation, chat with growing context), the split buys less, and a single stack reuses one cache for the whole conversation — one reason decoder-only models took over general-purpose LLMs.
  • Parameters are not compute. Matching an encoder–decoder by parameters (2N decoder layers) doubles the decoder-only model's compute; matching by compute halves its parameters. The study's Table 2 reports both.
Takeaway: an encoder–decoder buys twice the parameters per FLOP and a bidirectional reading of the input; a decoder-only model buys one uniform stack and cache. Which is cheaper depends on the ratio of input to output length.

30 Using T5 with the Hugging Face Transformers library

All T5-family checkpoints load as T5ForConditionalGeneration (or through AutoModelForSeq2SeqLM) with a SentencePiece-based T5 tokenizer: google-t5/t5-small … t5-11b (v1.0), google/t5-v1_1-*, google/flan-t5-*, google/mt5-* and google/byt5-* (the last with a byte tokenizer). Correct use comes down to prefixes, the decoder start token, label masking, learning rate and precision.

The steps

  1. Inputs. tokenizer("translate English to French: The weather is nice today.", return_tensors="pt"). For v1.0 checkpoints use the paper's prefixes; for v1.1 the documentation notes there is "no real advantage" to a prefix in single-task fine-tuning, but prefixes should be used for multi-task fine-tuning. Flan-T5 takes natural-language instructions.
  2. Targets. Tokenize the target text as labels; replace padding ids in the labels by −100 so the loss ignores them. The model builds decoder_input_ids by shifting the labels right and inserting the decoder start token, which for T5 is the pad token (id 0).
  3. Loss. model(input_ids=…, attention_mask=…, labels=…).loss is the mean token cross-entropy over non-ignored positions — the paper's objective.
  4. Generation. model.generate(**inputs, max_new_tokens=…); greedy by default, beam 4 with length penalty 0.6 reproduces the paper's WMT and CNN/DM decoding.
  5. Span-corruption inputs use the sentinel strings directly: input "The <extra_id_0> walks in <extra_id_1> park", labels "<extra_id_0> cute dog <extra_id_1> the <extra_id_2>" (the library's own example).

31 Pitfalls

T5's failures are mostly silent: a wrong prefix, a label that tokenizes differently, an fp16 overflow that produces NaN only on some inputs, a brace that became <unk>. The list below is grouped by where they occur.

Numerics and precision

  • fp16 overflow. T5 was trained on TPUs, where the reduced-precision format is bfloat16, which has fp32's exponent range. In fp16 (maximum 65,504) the un-normalised residual stream and feed-forward activations of some checkpoints — v1.1, mT5 and Flan-T5 in particular — can overflow to inf and then NaN. The library's own code shows the workaround: it clamps hidden states to just below the fp16 maximum inside each block when running in fp16, and keeps the feed-forward output projection wo in fp32 (_keep_in_fp32_modules = ["wo"]). Use bf16 or fp32 when you can.
  • Porting to another implementation without the three T5 specifics — no 1/√d_kv, d_model^(−1/2) rescale before a tied output, scale-only norm — gives wrong logits with no error.

Inputs and targets

  • Prefix and field order. v1.0 checkpoints expect the Appendix D forms (mnli hypothesis: … premise: …, stsb sentence1: … sentence2: …); a different order or wording is a different input.
  • Label strings. "entailment" is 4 pieces (▁ · en · tail · ment) and "not_entailment" 5; compare decoded strings, and restrict or validate outputs for classification.
  • Unrepresentable characters. { } ~ <, most CJK characters and newlines do not survive the T5 tokenizer; use mT5 or ByT5, or escape them, for code, JSON or line-structured text.
  • STS-B-style regression needs the 0.2-grid quantisation and a parser for the generated number.

Training

  • Forgetting −100. Padding ids left as 0 in the labels teaches the model to predict padding.
  • v1.1 without dropout overfits small data sets; enable it.
  • Assuming v1.1 works zero-shot. It was never trained on supervised tasks; it must be fine-tuned (or use Flan-T5).
  • Span-corruption lengths. Continuing pretraining with inputs and targets not sized by the helper (568 → 512 / 114 at the defaults) pads or truncates every example.

Reading the paper's numbers

  • Validation versus test. Tables 1–13 and 15 are validation scores of the 34B-token baseline family; Table 14 is test scores of the 1T-token models. Do not mix them.
  • Noise. Differences under 2σ (0.47 GLUE, 0.83 SuperGLUE) are within the paper's own noise estimate.
  • Table 10's d = 2048 adapter row is a copy of the d = 128 row; use Table 16.
Takeaway: the checklist is short — right checkpoint for the job, right prefix and label strings, −100 in labels, bf16 not fp16, a tokenizer that can spell your data.

33 Takeaways

T5 made "every task is text-to-text" the default framing for transfer learning and produced a large controlled comparison of pretraining choices. Its largest model set the state of the art on GLUE and SuperGLUE in 2019, and its successors — v1.1, mT5, ByT5, Flan-T5, UL2 — remained standard encoder–decoder checkpoints for years.

What to remember

  • Design: the 2017 encoder–decoder with scale-only pre-norm, no biases, bucketed relative position biases and a tied (v1.0) or untied (v1.1) output layer.
  • Objective: span corruption — short targets, sentinels, 15% at mean length 3 — chosen from a plateau of similar denoising objectives on cost grounds.
  • Data: C4, cleaned by simple heuristics whose code differs in detail from their description; large enough, per the paper, to train on 1T tokens without repeating data.
  • Evidence: one-factor-at-a-time comparisons with a measured noise floor; read them with the 2σ rule and remember they were run at Base size.
  • Practice: use v1.0 for its built-in prefixes, v1.1 to fine-tune from scratch, Flan-T5 for instructions, mT5 or ByT5 beyond English; bf16, labels with −100, a tokenizer that can spell your data.
Takeaway: read the NLP Models hub for where T5 sits among encoders and encoder–decoders, BERT for the encoder-only recipe it compared against, and GPT for the decoder-only branch that its architecture study found weaker for fine-tuned transfer and that later dominated prompting.
