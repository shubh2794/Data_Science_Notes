10 Tokenizer and vocabulary layout

English-only checkpoints use GPT-2's byte-level BPE unchanged. The multilingual checkpoints use a vocabulary refitted on multilingual text but kept the same size, "to avoid excessive fragmentation on other languages since the GPT-2 BPE vocabulary is English only". Special tokens are appended after the BPE ranks in a fixed order, so every id is predictable from the family.

  • The no-speech token has two names. The paper and the current code call it <|nospeech|>; the vocabulary files published with the original checkpoints (and on the Hub for tiny … large-v2) call the same id <|nocaptions|>. The paper's <|endoftranscript|> is <|endoftext|> in the code.
  • Fragmentation still differs by script. The paper lists Hebrew, Telugu, Chinese and Korean among the worst outliers relative to their data and suggests the byte-level BPE may be "a poor match for these languages" as one possible cause.
Takeaway: read special-token ids from the tokenizer, never from memory; the three families disagree by one position in several places.

11 The multitask token format

Every training target, and every inference prompt, starts with the same small grammar: an optional block of previous text, the start-of-transcript token, a language tag, a task token, and optionally a flag that turns timestamps off. After that the output begins. Language identification, voice-activity detection, transcription and translation are all positions in this one sequence.

the grammar (paper Figure 1)[ <|startofprev|> previous text ] <|startoftranscript|> ( <|lang|> ( <|transcribe|> | <|translate|> ) [ <|notimestamps|> ] output | <|nospeech|> ) <|endoftext|> language identification = the decoder's distribution at the position after the start token, restricted to language tagslang* = argmax over ℓ ∈ languages of p(<|ℓ|> | <|startoftranscript|>, H)
Build a decoder sequence choose family, language and task · toggle timestamps, previous text, no speech

Token ids are computed from the order in which get_encoding in the released tokenizer.py appends special tokens after the BPE ranks (EOT, SOT, the language list, six control tokens, 1,501 timestamps), which reproduces the added_tokens.json files on the Hub. Text is shown as words, not BPE ids. The example sentences are for display.

Details that matter

  • Loss masking. Only the previous-text block is excluded from the loss; the language tag, the task token, timestamps and the end token are all predicted and trained. The language targets came from the VoxLingua107-tuned language detector used in filtering.
  • Previous text was added "with some probability" during training — 50% according to the hyperparameter table — so the model learns both to use context and to work without it. At inference it is how long-form transcription carries context across windows, and how a user can prompt vocabulary or style (initial_prompt, prompt_ids).
  • English-only checkpoints take no language or task token: the released tokenizer sets both to None, so their prompt is <|startoftranscript|> (plus <|notimestamps|>). They cannot translate.
  • No-speech detection reads the probability of the no-speech token at the first position after the start token — the same position where the language is predicted.
Takeaway: Whisper's "tasks" are prefixes. Forcing a prefix fixes the task; leaving a slot open lets the model classify (language, speech versus silence) by predicting it. The same idea — task as tokens — is what later instruction-following language models generalised.

12 Timestamps as tokens

When timestamps are on, the decoder writes a start-time token before each caption segment and an end-time token after it. Times are relative to the start of the current 30-second window and quantised to the nearest 20 ms — the encoder's native resolution — giving 1,501 tokens from <|0.00|> to <|30.00|>.

quantisation and idk = round(t / 0.02), token = <|0.02·k|>, id = timestamp_begin + k, k = 0 … 1,500 a segment that runs past the window end: only its start is emitted, and the next window begins there… <|t_a|> text <|t_b|> <|t_c|> <|endoftext|> → next window starts at t_c
Quantising time and writing the target drag a time · toggle a segment that crosses 30 s

Segment boundaries are an example. Token strings, ids and rounding errors are computed with the 20 ms step and the family's first timestamp id (tokenizer). The rule for a segment that runs past the window is the paper's Section 2.3: in timestamp mode only its start time is predicted, "to indicate that the subsequent decoding should be performed on an audio window aligned with that time".

Why tokens rather than a regression head

  • Timestamps come from the same softmax as text, so the model decides when a segment ends jointly with what it says, and no separate aligner is needed for segment-level times.
  • The price is resolution and reliability: times are segment boundaries on a 20 ms grid, predicted by a language model, and they can drift, overlap or be skipped. Word-level times come from a separate mechanism (cross-attention alignment heads with dynamic time warping), and precise alignment still usually calls for a forced aligner.
Takeaway: timestamp tokens do two jobs: they give users segment times, and they tell the long-form algorithm how far to move the window. A wrong timestamp is therefore not just a wrong time — it can make the next window skip or repeat audio.

13 Decoding constraints: suppression and timestamp rules

The released decoder does not sample from the raw softmax. A chain of logit filters removes tokens that are grammatically impossible or known to be harmful, and enforces the timestamp grammar. These rules are part of how Whisper behaves in practice, even though the paper mentions only one of them.

Takeaway: "the model's output" in practice is the model plus these filters. Reimplementations that skip them — a plain generate() without the timestamp processor, or without suppression — produce different and usually worse transcripts from the same weights.

15 Where the compute goes: one encoder pass, many decoder passes

Per 30-second window the encoder runs once over 1,500 positions; the decoder runs once per generated token (times the beam width). Counting operations shows the encoder dominating the FLOPs for short outputs, but the decoder's passes are sequential and small, which makes them slow on accelerators out of proportion to their FLOPs.

encoder, per window (multiply–accumulates)MAC_enc ≈ stem + Le · (12·1500·d² + 2·1500²·d) decoder, per generated token at position t, per beamMAC_tok ≈ Ld · (14d² + 2td + 2·1500·d) + V·d (+ once per window: Ld · 2·1500·d² for cross-attention K and V)
FLOPs per window: encoder versus decoder drag the number of output tokens · switch greedy / beam 5

Counts are computed layer by layer from each checkpoint's configuration: attention projections, attention scores and mixing, the MLP, the vocabulary projection, and the conv stem; LayerNorms, softmax and GELU are ignored; FLOPs = 2 × multiply–accumulates. The beam setting multiplies decoder work only. About 100 tokens is typical for 30 s of fluent English; the released decoder stops at 224 sampled tokens per window. FLOPs are not latency — measure on your hardware.

  • Why the decoder is slow anyway. Each decoder step reads all decoder weights and caches to produce one token; at batch size 1 that is memory-bandwidth bound. A 32-layer decoder does this 32 layers deep, sequentially, for every token. Cutting the decoder to 4 layers (turbo) or 2 (Distil-Whisper) removes most of that serial work while leaving the encoder untouched.
  • README speeds. OpenAI's README reports relative transcription speeds on an A100 of about 10× (tiny), 7× (base), 4× (small), 2× (medium), 1× (large) and 8× (turbo), with approximate VRAM of 1, 1, 2, 5, 10 and 6 GB — turbo is rated faster than base despite keeping the whole large-v3 encoder.
Takeaway: Whisper's cost has two shapes: a fixed, parallel encoder cost per window, and a serial decoder cost per token. Batching many windows helps the first; shrinking the decoder, speculative decoding or fewer beams help the second.

16 Training recipe

All sizes were trained with the same schedule: AdamW, a 2,048-update linear warm-up then linear decay to zero, batches of 256 30-second segments, and 2²⁰ = 1,048,576 updates — "between two and three passes over the dataset". Because training runs for so few epochs, the original models used no data augmentation and no regularisation.

Takeaway: nothing in the recipe is unusual. The one design decision that looks surprising — no regularisation — is a consequence of scale: with fewer than four epochs of highly diverse data, over-fitting was not the constraint, until large-v2 trained longer and added it back.

17 Multitask and multilingual transfer; the English-only models

Does training on 99 languages and two tasks hurt English? The paper compares English-only models with multitask multilingual ones at matched compute spent on English (only 65% of a joint model's compute goes to English transcription). Small models show negative transfer; the largest show positive transfer.

  • Figure 9's result. At low training compute, joint models are worse on English than English-only models given the same English FLOPs; the curves cross as compute grows, and for the largest experiments joint models are better "even when not adjusting for compute spent per task".
  • The released .en models follow the same pattern. The README says English-only models "tend to perform better, especially for the tiny.en and base.en models", with the difference becoming "less significant" for small.en and medium.en. Table 8's greedy WERs agree: tiny.en beats tiny on LibriSpeech test-clean (5.6 vs 7.6), medium beats medium.en (2.9 vs 3.1). There is no large.en.
  • What the tasks share. Translation data is non-English audio, so it trains the encoder on those languages even when the target is English — one reason the paper sees benefits from joint training at scale.
Takeaway: capacity decides whether multitask training helps. For a small model on English only, pick the .en checkpoint; at medium size and above, the multilingual model gives up little or nothing on English.
