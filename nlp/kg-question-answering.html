KG Question Answering

Let non-technical users query a knowledge graph in plain language. Instead of writing Cypher or SPARQL, the user asks a question; the system detects intent, extracts the relevant schema, generates a formal query, executes it, and summarises the result — an end-to-end pipeline that moves beyond RAG to structured query generation over graphs.

01 Beyond RAG for structured data

  • RAG excels at unstructured document retrieval: embed chunks, find the nearest neighbours, and feed them to an LLM. But when your data lives in a knowledge graph, many questions need graph traversals, aggregations, or multi-hop joins that nearest-neighbour search cannot express.
  • "How many suppliers in region X have overdue contracts?" — this requires a filtered traversal, a date comparison, and a count. No amount of chunk retrieval will reliably produce the exact number.
  • "Show the shortest path between company A and person B" — a graph algorithm, not a text-similarity lookup.
  • The core insight: when data is structured, the question-answering task is NL → query, not NL → retrieval. The user asks in English; the system writes Cypher or SPARQL, executes it against the graph database, and returns exact results.
  • RAG and KG-QA are complementary, not competing. Use RAG for unstructured corpora, KG-QA for structured knowledge, and hybrid systems when both coexist.
Question shapeRAG (vector retrieval)KG-QA (query generation)
Single fact in one passageStrong — cheap, robustOverkill — write a triple lookup
Multi-hop joinWeak — each hop needs a lucky retrievalStrong — follow the path
Aggregation / countWeak — top-k truncates; LLM guessesStrong — query returns exact answer
Exhaustive listWeak — top-k misses long tailsStrong — query returns all matches
Nuance / tone / exact wordingStrong — returns source textWeak — triples drop qualifiers
Key idea: when your data is a graph, generate a graph query — do not flatten structured knowledge into chunks and hope vector similarity recovers it.

02 Intent detection & routing

  • Before generating a query, classify the user's question to decide the output format and the downstream pipeline. Intent = visualization type + query complexity.
  • Typical intents and their target formats:
    • Graph canvas — "Show me connections between X and Y" → return nodes and edges for a visual graph.
    • Table — "List all suppliers in region R" → return rows and columns.
    • Chart — "Revenue trend for entity X" → return time-series data for a bar/line chart.
    • Map — "Where are our offices?" → return geo-coordinates for plotting.
    • Narrative — "Summarise what we know about X" → return text summary.
  • Use LLM-based classification with few-shot examples. The classification prompt should: (a) define each category clearly with one-line descriptions, (b) include boundary-case examples that sit between two intents, and (c) have a fallback category for ambiguous or out-of-scope questions.
  • Keep the classifier cheap and fast — it runs on every query. A small model or a cached few-shot prompt is usually sufficient; fine-tuning a lightweight classifier on logged queries is even better when you have enough data.
  • The detected intent propagates downstream: it determines which schema subset to expose (section 03), how to format the generated query's results (section 06), and whether to trigger summarization (section 07).
# Intent classification prompt sketch
system: """You classify user questions about a knowledge graph.
Return JSON: {"intent": <one of: graph, table, chart, map, narrative, unknown>,
              "complexity": <one of: simple, multi-hop, aggregate>}
If unsure, return intent "unknown" so the system can ask for clarification."""

# Few-shot examples
user: "Show connections between Acme Corp and Jane Doe"
assistant: {"intent": "graph", "complexity": "multi-hop"}

user: "How many open contracts do we have per region?"
assistant: {"intent": "chart", "complexity": "aggregate"}
Takeaway: intent detection is the router — get it wrong and the rest of the pipeline produces the right answer in the wrong shape, or follows the wrong code path entirely.

03 Schema extraction

  • An LLM cannot write valid Cypher or SPARQL without knowing the schema — which node labels, relationship types, and property keys exist in the graph.
  • Schema serialization: convert the graph schema into an LLM-friendly textual representation. For a property graph (Neo4j), extract the output of CALL db.schema.visualization() or apoc.meta.schema() and format it as a structured listing:
    • Node labels with their properties and types: (:Person {name: String, birthDate: Date})
    • Relationship types with source → target and properties: (:Person)-[:WORKS_FOR {since: Date}]->(:Organization)
  • Schema filtering is critical. A production KG may have hundreds of labels and thousands of properties. Exposing the full schema to the LLM: (a) blows up prompt size and cost, (b) increases hallucination of irrelevant types, and (c) confuses the model with unrelated options.
  • Filter strategies: keyword matching (match entities mentioned in the question to labels), embedding similarity (embed question and schema elements, keep the top-k closest), or graph-distance pruning (start from matched labels, include only their 1–2 hop neighbourhood in the schema graph).
  • The filtered schema goes into the prompt as structured context — the LLM's "data dictionary" for query generation.
# Schema context (filtered for a question about people and organisations)
Node labels:
  (:Person {name: String, role: String, birthDate: Date})
  (:Organization {name: String, founded: Int, sector: String})
  (:Contract {id: String, status: String, value: Float})

Relationships:
  (:Person)-[:WORKS_FOR {since: Date}]->(:Organization)
  (:Person)-[:MANAGES]->(:Person)
  (:Organization)-[:HAS_CONTRACT]->(:Contract)
Takeaway: the schema is the LLM's map of the graph. Expose too much and it hallucinates; expose too little and it cannot reach the answer. Filter to the question's neighbourhood.

04 Text-to-Cypher / Text-to-SPARQL

The core translation: an LLM converts a natural-language question into a formal graph query, using the schema (section 03), the detected intent (section 02), and any additional context.

  • The prompt for query generation includes:
    • Schema — the filtered node labels, relationships, and properties.
    • Intent — the detected output format and complexity.
    • User context — any selected nodes (e.g. the user clicked an entity on a canvas), conversation history, or domain constraints.
    • Annotation / domain rules — business logic the query must respect: "always filter by active status", "dates are stored as ISO strings", "use case-insensitive matching for names".
  • The LLM should return both the query and its reasoning (chain-of-thought or structured explanation). The reasoning helps with debugging and allows downstream agents to validate the approach before execution.
  • Few-shot examples in the prompt are essential — they anchor the model to valid syntax and idiomatic patterns for the target query language. Include examples that cover common patterns: simple lookups, multi-hop traversals, aggregations, and optional matches.
  • Cypher (property graph, Neo4j style) uses ASCII-art path patterns: MATCH (p:Person)-[:WORKS_FOR]->(o:Org) WHERE o.name = "Acme" RETURN p.
  • SPARQL (triple store) uses triple patterns with variables: SELECT ?person WHERE { ?person ex:worksFor ex:Acme }.
  • The choice between them depends on the backing store, not the LLM — the prompt template switches the target language and examples accordingly.
translation f( question, schema, intent, context ) → ( query, reasoning ) objective query must be syntactically valid ∧ schema-faithful ∧ semantically equivalent to question
# Example: text-to-Cypher generation
Question: "Who manages people working at Acme Corp?"
Schema:   (filtered — Person, Organization, WORKS_FOR, MANAGES)
Intent:   {intent: "table", complexity: "multi-hop"}

Generated Cypher:
  MATCH (mgr:Person)-[:MANAGES]->(emp:Person)-[:WORKS_FOR]->(o:Organization)
  WHERE o.name = "Acme Corp"
  RETURN DISTINCT mgr.name AS manager, collect(emp.name) AS employees

Reasoning: Two-hop traversal — start from Organisation, find employees via
WORKS_FOR, then find their managers via MANAGES. Aggregate employees per manager.
Takeaway: the LLM is the translator, not the executor. Its job is to produce a valid, schema-faithful query — the database does the actual computation.

05 Expert emulation

Instead of generic retrieval, mimic how a domain expert would query the KG — the pipeline encodes their reasoning chain.

  • A domain expert answering a KG question follows a predictable sequence:
    1. Understand the intent — what is the user really asking? What format do they expect?
    2. Know the schema — which entities, relations, and properties are relevant? What are the naming conventions?
    3. Write a precise query — translate the question into the graph's query language, using idiomatic patterns and respecting domain constraints.
    4. Execute and inspect — run the query, check the results for plausibility, handle edge cases (empty results, unexpected cardinality).
    5. Interpret contextually — explain the results in domain terms, highlight what matters, and flag anomalies.
  • The KG-QA pipeline encodes this exact chain: intent detection (step 1) → schema extraction (step 2) → text-to-query (step 3) → query execution (step 4) → result summarization (step 5).
  • The advantage over a single monolithic prompt ("answer this question using the graph") is decomposition: each step has a focused prompt, can be debugged independently, and can be swapped or improved without touching the others.
  • This mirrors the expert emulation pattern in agentic design: rather than trying to be a general assistant, the system emulates one specific expert persona — the person who knows the graph schema by heart and writes queries all day.
Key idea: design the pipeline as the reasoning steps a human expert would follow — each agent step corresponds to a cognitive step in the expert's workflow.

06 Query execution & error recovery

  • Run the generated query against the graph database (Neo4j, a SPARQL endpoint, or any graph store). The execution is deterministic — unlike LLM generation, the database returns exact results.
  • Errors are expected. LLM-generated queries frequently contain:
    • Syntax errors — missing parentheses, incorrect keywords, wrong clause order.
    • Schema mismatches — hallucinated node labels or relationship types that do not exist in the graph.
    • Runtime errors — queries that are syntactically valid but hit execution limits (unbounded traversals, cartesian products).
  • Error recovery loop: when execution fails, feed the error message back to the LLM along with the original question and schema, and ask it to fix the query. Use a retry budget (e.g. 3 attempts) to prevent infinite loops.
  • Result formatting depends on the detected intent:
    • Graph intent → parse returned nodes and relationships into a canvas-ready structure (node list + edge list).
    • Table intent → format records as rows and columns (DataFrame).
    • Chart intent → extract numeric series for plotting.
    • Map intent → extract coordinates and labels.
  • Empty results are not necessarily errors — the answer may genuinely be "none". But they are worth a sanity check: re-examine the query for overly restrictive filters or misspelled literals.
retry loop for attempt = 1 … N: result = execute( queryᵢ ) if success: return format( result, intent ) queryᵢ₊₁ = LLM( question, schema, queryᵢ, error_msg ) if all attempts fail: return fallback_message
Takeaway: treat query execution as a feedback loop, not a one-shot call. The LLM-database pair converges on a valid query within a few retries — but always cap the attempts.

07 Result summarization

  • Raw query results (JSON records, node-edge lists, tabular rows) are not user-friendly. A post-query LLM call transforms them into an actionable narrative.
  • Graph results: highlight key entities, notable paths, and structural features (hubs, bridges, clusters). "Person A is connected to Organisation B through two intermediaries: C and D."
  • Tabular results: surface trends, outliers, and aggregates. "15 of 23 contracts are overdue; the largest (USD 4.2M) belongs to Acme Corp."
  • Summary analysis flag: not every result needs summarization. A simple lookup ("What is X's role?") returns one value — summarization adds latency and cost for no benefit. Use a heuristic or the intent classification to decide:
    • Result set has > N records → summarize.
    • Intent is "narrative" → always summarize.
    • Intent is "graph" or "chart" → summarize as a caption; the visualization is the primary output.
    • Simple single-value lookup → skip summarization.
  • The summary prompt includes the original question, the executed query (for transparency), and the raw results. Ask the LLM to be concise, cite specific values, and flag caveats (e.g. "results limited to active contracts only").
Takeaway: summarization is the last-mile UX — it bridges the gap between database output and human understanding. But skip it when it adds nothing.

08 Agentic QA pipeline

Orchestrate the full flow as a stateful agent graph — each step is an agent that reads and writes a shared state, with dynamic edges for retry logic and conditional paths. This pattern aligns with agentic design patterns.

Agentic KG-QA pipeline Click "Run query" to animate the pipeline; execution may succeed or trigger a retry loop
  • Shared state (a typed dictionary) carries all intermediate data: the original question, detected intent, filtered schema, generated query, execution result, error messages, retry count, and final summary.
  • Agent nodes:
    1. Intent Detection — classifies question → writes intent to state.
    2. Schema Extraction — reads intent + question → writes schema.
    3. Text-to-Query — reads intent, schema, question, and optionally error_msg → writes query + reasoning.
    4. Query Execution — reads query → writes result or error_msg + increments retry_count.
    5. Post-Query Routing — reads result and intent → formats output and decides whether to summarize.
    6. Summary Generation — reads question, result, query → writes summary.
  • Dynamic edges handle conditional routing:
    • Execute → success → Route → Summary (or skip summary).
    • Execute → error and retry_count < max → loop back to Text-to-Query.
    • Execute → error and retry_count ≥ max → Route (with fallback message).
  • This is a directed graph of agents — naturally expressed using an agent orchestration framework. Each node is a pure function of the shared state; side-effects (LLM calls, database queries) happen inside the node.
# Shared state schema (TypedDict-style)
class KGQAState:
    question: str
    intent: dict               # {intent: str, complexity: str}
    schema: str                # filtered schema text
    query: str                 # generated Cypher/SPARQL
    reasoning: str             # LLM's chain-of-thought
    result: Any                # query result (records, graph, etc.)
    error_msg: str | None      # execution error, if any
    retry_count: int           # 0..max_retries
    formatted_output: Any      # intent-appropriate output
    summary: str | None        # narrative summary, if generated
Takeaway: the agentic pipeline is a state machine with LLM-powered transitions. Each node has one job, state is explicit, and the retry loop is a first-class edge — not an afterthought.

09 Graph feature engineering for QA

  • Graph-structural features can be pre-computed and exposed to the LLM as additional context, helping it reason about node importance, community structure, and connectivity.
  • Manual / classical features:
    • Degree centrality — how many connections a node has. High-degree nodes are hubs.
    • Betweenness centrality — how often a node lies on shortest paths between others. High betweenness = bridge or bottleneck.
    • Clustering coefficient — how connected a node's neighbours are to each other. Measures local community density.
    • PageRank — importance based on the structure and quality of incoming links (recursive: a link from an important node counts more).
    • Community labels — which cluster or community a node belongs to (from Louvain, Leiden, or label propagation).
  • These features are stored as node properties in the graph and exposed in the schema (section 03). The LLM can then reference them: "Return the top 10 people by PageRank in the finance community."
  • Semi-automated features bridge interpretability and scalability: use graph neural networks or KG embeddings to generate dense node representations, then cluster or project them into human-interpretable dimensions.
  • Pre-computed features are also useful for LLM-autonomous graph reasoning: instead of the LLM traversing the graph step by step, it reads pre-computed summaries ("node X has PageRank 0.034, betweenness 0.12, belongs to community 'finance'") and reasons over them directly.
degree deg(v) = |{ u : (v, r, u) ∈ G or (u, r, v) ∈ G }| PageRank PR(v) = (1 − d) / N + d · ∑u→v PR(u) / degout(u) d ≈ 0.85 clustering C(v) = 2 · |{ (u, w) ∈ E : u, w ∈ N(v) }| / ( deg(v) · (deg(v) − 1) )
Takeaway: graph features let the LLM reason about structure without traversing. Pre-compute degree, centrality, PageRank, and community labels; expose them as properties the generated query can filter and sort on.

10 Pitfalls & recap

Common pitfalls

  • Schema drift — the KG schema changes (new labels, renamed properties) but the prompts still reference the old schema. The LLM generates queries against a stale map. Fix: extract the schema dynamically at query time, or version it and validate on startup.
  • Hallucinated types — the LLM invents node labels or relationship types that do not exist in the graph. Fix: validate the generated query against the schema before execution; reject or retry if unknown types appear.
  • Over-complex queries — the LLM generates deeply nested subqueries or cartesian products that time out or return nonsensical results. Fix: set query complexity limits, use execution timeouts, and prompt for simple patterns first.
  • Single point of failure on the LLM — if the LLM is down, the whole pipeline stops. Fix: cache common query templates; fall back to a template-matching system for frequent question types.
  • Missing retry logic — the first query attempt fails, and the system returns an error to the user. Fix: always implement the retry loop (section 06) with error feedback.
  • Ignoring user context — the user has selected nodes on the canvas, but the query does not filter to them. Fix: pass selection state into the query generation prompt.
  • No pre-execution validation — running queries without checking them against the schema first. Fix: parse the query AST and check every label, type, and property against the known schema.
  • Treating all questions as RAG — routing every question through vector retrieval when some clearly need structured query. Fix: implement intent detection (section 02) as the first step.

Recap

  • When data is a graph, generate a query — not a retrieval. RAG is for unstructured text; KG-QA is for structured knowledge.
  • Intent detection routes the question to the right pipeline and output format.
  • Schema extraction gives the LLM a map — filtered to the question's neighbourhood to reduce hallucination.
  • Text-to-Cypher/SPARQL is the core translation; prompt it with schema + intent + context + few-shot examples.
  • Expert emulation — design the pipeline as the reasoning chain a domain expert would follow.
  • Error recovery with a retry loop is essential; LLM-generated queries frequently need correction.
  • Summarization is the last mile — transform raw results into narrative, but skip it when it adds nothing.
  • Orchestrate as an agent graph — explicit state, focused nodes, dynamic edges for retries and conditionals.
  • Graph features (degree, PageRank, communities) give the LLM structural context without traversal.
