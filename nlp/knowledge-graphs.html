Knowledge Graphs

Represent facts as a network of entities connected by typed relations. A knowledge graph stores "who/what relates to what, how" — structured, queryable knowledge that grounds search, reasoning, and retrieval. This page goes from the triple, through the ontology that gives triples meaning, to building a graph from tables and text, linking mentions to the right entity, embedding the graph, and retrieving from it. (This very site is one.)

NLP Knowledge representation Graphs Ontologies Entity linking

01 Facts as a graph

  • Nodes are entities (people, places, things, concepts); edges are typed relations between them.
  • Knowledge is stored as triples — (head, relation, tail) — the atom of a knowledge graph.
  • Unlike free text, it's structured: you can query it, traverse it, and reason over it precisely.
  • Two layers sit on top of each other: a schema that says which kinds of things and relations exist (§03), and the instance facts that populate it. Most of the engineering effort goes into getting real data into that shape — from tables (§04) and from text, where every name must first be resolved to the right entity (§05).
One sentence: a knowledge graph turns scattered facts into a connected, queryable network of entities and relations.

Each fact is a subject-predicate-object triple. Pick a sentence to see its triples become a graph.

Notice what the toy graph glosses over: "Apple" here is a string, not yet an identifier, and nothing says that founded by must connect an organisation to a person. Standards for triples, an ontology for the allowed types and relations, and a query language fill those gaps — §03.

03 Ontologies: the schema and the instance layer

A bag of triples is just data. An ontology gives it meaning: which classes of thing exist, which relations may connect them, and what follows logically from what is stated.

Intuition: a schema you can reason with

  • An ontology is a formal, shared vocabulary for a domain. It declares classes (Person, Organization, City), properties (worksFor, locatedIn, birthDate), and the rules that tie them together.
  • Subclass hierarchies organise classes into a taxonomy: Scientist ⊑ Person ⊑ Agent. Anything stated about a superclass applies to every subclass member.
  • Domain and range say what kinds of subject and object a property connects: worksFor has domain Person and range Organization; birthDate has a date-valued literal as its range.
  • Constraints go further: cardinality ("exactly one birth date"), disjointness ("nothing is both a Person and a City"), functional properties (at most one value per subject), and keys.
  • The difference from a database schema: a relational schema rejects non-conforming rows; an ontology also lets you derive facts nobody wrote down. That is both its power and its most common source of surprise.

The triple model, formally

  • The standard web data model for graphs (RDF) fixes what each position may hold. Identifiers are IRIs — globally unique, web-style names such as ex:person/101, so two sources that use the same IRI are talking about the same thing. Literals are values: a lexical form plus a datatype ("1984-03-02"^^xsd:date) or a language tag ("Paris"@fr). Blank nodes are local, anonymous nodes for things that exist but have no global name.
  • Subjects are IRIs or blank nodes; predicates are always IRIs; objects may be any of the three. Literals can only appear as objects — a value cannot have outgoing edges.
  • Named graphs extend triples to quads (s, p, o, g): the fourth slot names the graph a triple belongs to, which is the usual place to hang provenance, versioning, or access control on whole batches of facts. A newer revision of the standard (in late-stage standardisation as of 2026) also adds triple terms, letting a triple be the object of another triple, so that statements can be made about statements without the verbose classic reification pattern.
graph G ⊆ ( I ∪ B ) × I × ( I ∪ B ∪ L ) I = IRIs, B = blank nodes, L = literals dataset D = { G₀ } ∪ { ( gᵢ , Gᵢ ) } a default graph plus named graphs → quads (s, p, o, g)

Schema vocabulary and reasoning

  • A light schema layer (RDFS) adds subClassOf, subPropertyOf, domain, and range. A richer ontology language (OWL, built on description logics) adds class axioms — equivalence, disjointness, intersections, restrictions such as "a Parent is a Person with at least one hasChild" — and property characteristics: inverse (employs is the inverse of worksFor), transitive (partOf, locatedIn), symmetric (marriedTo), and functional.
  • Entailment is what a reasoner computes: every triple that must hold in every interpretation consistent with the stated facts and axioms. The core rules are mechanical and worth memorising:
subclass ( C ⊑ D ) ∧ ( x : C ) ⟹ ( x : D ) domain dom(p) = C ∧ ( x, p, y ) ⟹ ( x : C ) range range(p) = D ∧ ( x, p, y ) ⟹ ( y : D ) transitive ( x, p, y ) ∧ ( y, p, z ) ⟹ ( x, p, z ) inverse p = q⁻¹ ∧ ( x, p, y ) ⟹ ( y, q, x ) entailment K ⊨ α ⟺ α holds in every model of K
  • The domain/range trap. In these languages domain and range are inference rules, not checks. State (Paris, worksFor, Orbital Labs) with domain Person and the reasoner does not complain — it concludes that Paris is a Person. Pair this with the open-world assumption (a missing fact is unknown, not false) and the lack of a unique-name assumption (two IRIs may denote the same thing until proven otherwise), and you see why ontology reasoning cannot be used as validation.
  • Validation is a separate, closed-world layer: shape languages (such as SHACL) declare "every Person must have exactly one birthDate of type date" and report violations against the data as it is. Production graphs typically use both — reasoning to enrich, shapes to reject.
  • Cost. Full ontology reasoning is expensive (worst-case intractable for the most expressive language), so practice uses tractable profiles tuned to one job: large class hierarchies, query rewriting over databases, or forward-chaining rules. Many industrial graphs use only subclass, domain/range, inverse, and transitive closure — computed once and materialised.

TBox vs ABox

  • Description logic splits a knowledge base into the TBox (terminological box: classes, properties, axioms — Scientist ⊑ Person, dom(worksFor) = Person) and the ABox (assertional box: facts about individuals — Curie : Scientist, (Curie, won, NobelPhysics)). Property axioms are sometimes separated into an RBox.
  • The TBox is small, curated, and slow-changing — it is designed by people. The ABox is huge and fast-changing — it is extracted by pipelines. Most of the rest of this page is about filling the ABox without corrupting it.
  • Standard reasoning tasks map onto the split: consistency (does the ABox contradict the TBox?), classification (compute the full subclass hierarchy of the TBox), and instance checking / retrieval (which individuals belong to a class, including inferred members).
knowledge base K = ( 𝒯 , 𝒜 ) 𝒯 : C ⊑ D , dom(p) = C , p⁻¹ = q … 𝒜 : x : C , ( x, p, y ) …

Property graphs vs RDF

Two data models dominate. They can represent the same knowledge, but they make different things cheap.

Querying at a glance

Both languages are graph pattern matching: write a small graph with variables, and the engine returns every binding that matches. "Which scientists won a prize in physics?"

# triple-pattern query (SPARQL)
PREFIX ex: <http://example.org/>
SELECT ?person ?prize WHERE {
  ?person a ex:Scientist ;          # 'a' = rdf:type, matches inferred types too
          ex:won ?prize .
  ?prize  ex:field ex:Physics .
}

# path-pattern query (Cypher / GQL style)
MATCH (p:Scientist)-[:WON]->(z:Prize)-[:FIELD]->(:Field {name: "Physics"})
RETURN p.name, z.name
  • Variable-length paths express transitive questions directly: ?city ex:locatedIn+ ex:Europe in the triple language, -[:LOCATED_IN*1..]-> in the path language. That one operator is the difference between a graph query and a fixed chain of SQL joins.
  • Property-graph querying was standardised as an international language (GQL) in 2024; the path-pattern syntax above is the common core.
  • Whether ?person a ex:Scientist also returns members inferred through subClassOf depends on whether the store materialised entailments or rewrites queries — a frequent cause of "the query misses rows I can see".
Takeaway: the TBox is the contract, the ABox is the data. Use reasoning to add what the contract implies, use closed-world shapes to reject what violates it, and never confuse the two.

04 Building one: from tables, text, and LLMs

Ontology-driven construction means the schema comes first, and every source — a relational table, a JSON feed, a paragraph of prose — is mapped into it, then checked against it.

Structured sources: mapping tables into an ontology

  • The core correspondence is simple: a row → an entity (its IRI minted from the primary key), the table → a class, a value column → a datatype property with a literal object, and a foreign key → an object property pointing at another entity's IRI. Join tables (many-to-many) become edges; a nullable column that is null produces no triple, which under the open-world assumption means "unknown", not "none".
  • A direct mapping does this mechanically, using table and column names as the vocabulary. It is lossless but table-shaped — you get person#works_for, not a shared worksFor. An ontology mapping instead names the target class, property, and datatype for each column, and may split, merge, or compute values (concatenate a name, parse a date, mint an IRI from two keys).
  • Mapping languages make those rules declarative data rather than ETL code: a standard one exists for relational sources, and a generalisation of it covers CSV, JSON, and XML via iterators (one entity per array element or per path match). The mapping can be run eagerly (materialise triples) or virtually (rewrite graph queries into SQL against the live tables).
  • JSON nests: a nested object becomes either its own entity (if it has an identity, like an address with an ID) or a blank node, and arrays become repeated triples — order is lost unless modelled explicitly.
row → triples s = iri( T , pk(r) ) ( s , rdf:type , class(T) ) ( s , prop(c) , literal( r[c] , dtype(c) ) ) for each value column c with r[c] ≠ null ( s , rel(fk) , iri( T′ , r[fk] ) ) for each foreign key fk → T′

Schema alignment and ontology matching

  • When sources come with their own schemas, you must decide that employee.org_id, staff.company, and a third vocabulary's memberOf all mean worksFor. Ontology matching produces correspondences (e₁, e₂, relation, confidence) where the relation is equivalence (≡) or subsumption (⊑).
  • Matchers combine signals: lexical (label and synonym similarity), structural (matching parents, children, and domain/range), instance-based (two classes whose members overlap heavily are probably the same), and embedding / LLM-based (compare natural-language descriptions). A final step repairs the alignment so that it does not make the merged ontology inconsistent.
  • The instance-level twin is entity resolution (record linkage): deciding that two rows from different sources are the same real-world entity. The standard recipe is blocking (cheap keys to avoid comparing all pairs) → pairwise matching (a classifier over field similarities) → clustering (transitively merge matches, then break up implausible clusters). The output is an identity link between IRIs.

Unstructured sources: the text pipeline

  1. Entity recognition (NER) — find the mention spans and coarse types.
  2. Entity linking — resolve each mention to a canonical node, e.g. "Apple" to the company or the fruit, or declare it new (NIL). This is its own hard problem: §05.
  3. Relation extraction — classify the relation between pairs of linked entities ("founded by", "located in"), typically restricted to relations in the TBox whose domain and range fit the two entity types.
  4. Canonicalisation — map surface relation phrases ("was started by", "co-founded") onto schema properties, normalise literal values (dates, units, currencies), and merge NIL mentions that refer to the same new entity.
  5. Deduplication / fusion — merge facts about the same entity across sources and resolve conflicts, preferring fresher or more trusted sources.
  6. Validation against the schema — run shape checks, reject or quarantine violations, and record provenance (source document, span, extractor, confidence, timestamp) for every surviving triple.

LLM-based triple extraction

  • Instruction-tuned LLMs collapse steps 1–4 into one call: give the model the passage plus the allowed classes and relations (the relevant TBox slice, with one-line definitions and domain/range), and ask for triples as JSON. Schema-constrained prompting and structured decoding fix the shape of the output.
  • They do not fix the content. Typical failures: hallucinated relations (a fact plausible from world knowledge but absent from the passage), schema drift (inventing a relation name not in the list, or a near-synonym of one), wrong direction ((Jobs, foundedBy, Apple)), and ungrounded entities (normalised names that do not appear in the text and link to nothing). See Hallucination & Factuality.
  • So every extracted triple goes through deterministic gates before it touches the graph: the relation must exist in the schema, both endpoint types must satisfy its domain and range, the evidence span the model cites must actually occur in the source, and the entities must link (§05) or be explicitly minted as new.
  • Provenance per triple is non-negotiable: store the source, the quoted evidence span, the model and prompt version, and a confidence. It makes errors auditable and reversible — you can retract everything one bad prompt version produced.
  • A practical division of labour: LLMs for the long tail of relations and for bootstrapping silver training data; smaller fine-tuned extractors for high-volume, stable relations where cost and determinism matter.
accept a triple accept( h, r, t ) ⟺ r ∈ R𝒯 ∧ type(h) ⊑ dom(r) ∧ type(t) ⊑ range(r) ∧ evidence ⊂ source ∧ link(h), link(t) ≠ ⊥
// one extracted triple, as stored — the evidence makes it checkable

  "tail": "ex:person/steve-jobs",
  "evidence": "Apple was founded by Steve Jobs",

Takeaway: construction is mapping into a contract and then enforcing it. Tables map deterministically; text needs NER, linking, extraction, and canonicalisation; LLMs speed up the text path but must be fenced in by schema checks, evidence checks, and per-triple provenance.

05 Entity linking & named entity disambiguation

A mention is a string; a node is an identity. Entity linking maps each mention to its knowledge-base entry — or to NIL when the entity is not in the graph — and it is the step that decides whether your graph has one "Paris" or five.

The task

  • Input: a document with mentions m₁ … mn (from NER) and a knowledge base of entities ℰ, each with a name, aliases, a type, a short description, and graph neighbours. Output: for each mention an entity e ∈ ℰ ∪ { NIL }.
  • Two kinds of ambiguity: one name, many entities ("Jordan" — a country, a river, an athlete) and one entity, many names ("the Big Apple", "NYC", "New York"). Disambiguation handles the first; alias tables and canonicalisation handle the second.
  • The standard decomposition is candidate generation → local ranking → (optional) collective ranking → NIL decision. Each stage bounds the next: if the right entity is not in the candidate set, nothing downstream can recover it.

Candidate generation

  • Alias tables / surface-form dictionaries map each string to the entities it has been used for, with counts — mined from hyperlink anchor text, redirects, disambiguation pages, and synonym lists. Lookup is a hash probe after normalisation (case, punctuation, diacritics).
  • Fuzzy matching (character n-grams, edit distance, phonetic keys) catches typos, transliterations, and partial names ("Okonkwo" for a full name).
  • Dense retrieval embeds the mention-in-context and every entity description into one vector space and takes the nearest neighbours — high recall for paraphrased or rare mentions with no alias entry, the same machinery as RAG retrieval.
  • Keep the top k (often 10–100). The metric that matters here is candidate recall — the share of mentions whose gold entity survives into the set.

Local ranking: prior plus context

  • The prior P(e | m) is how often the string m refers to e across a large linked corpus. It is a remarkably strong baseline — on news text, most mentions refer to their most popular sense — and it is exactly what fails on the interesting cases.
  • Context similarity compares the words around the mention with the entity's description: "flew to Amman" fits the country; "scored 40 points" fits the athlete. Classically a TF-IDF or embedding cosine; today a learned encoder.
  • A local score blends the two with a weight λ. In practice the features are standardised and the weights learned, often alongside type compatibility (does the NER type agree with the entity's class?) and string similarity.
prior P(e | m) = count(m → e) ⁄ ∑e′ count(m → e′) context sim( ctx(m), desc(e) ) = ( a · b ) ⁄ ( ‖a‖ ‖b‖ ) a = enc(ctx(m)), b = enc(desc(e)) local score φ(m, e) = λ · log P(e | m) + ( 1 − λ ) · sim( ctx(m), desc(e) ) 0 ≤ λ ≤ 1 decision ê(m) = argmaxe ∈ C(m) φ(m, e) ê(m) = NIL if maxe φ(m, e) < τ

NIL detection

  • Many mentions — new employees, small companies, people in local news — have no entry. A linker that always returns its argmax will attach them to the nearest famous namesake, quietly corrupting the graph.
  • Two standard mechanisms: a threshold τ on the best score (tuned on held-out data for the precision/recall trade you want), or NIL as a candidate — an extra option in the candidate list with its own learned score, so the ranker can prefer "none of these".
  • NIL mentions are not discarded: they are clustered across documents (all mentions of the same new person grouped together) and become candidates for new nodes — the bridge from linking back to graph growth.

Collective disambiguation

  • Mentions in one document are about related things. If "Chicago" and "Boston" appear next to a basketball player, the teams are more likely than the cities — even though each city alone has the higher prior. Collective (joint) linking chooses all entities together to maximise local fit plus pairwise relatedness between the chosen entities.
  • Relatedness is measured from the graph itself: shared neighbours or shared inbound links (two entities linked from many of the same pages are related), embedding similarity, or path distance.
  • The exact joint problem is NP-hard in general (it is MAP inference in a fully connected model), so systems approximate: iterative / greedy refinement, dense-subgraph extraction on a mention–candidate graph (repeatedly drop the weakest-connected candidate), loopy belief propagation, or a random walk with restart from the document's mentions — candidates that a walk keeps returning to are the coherent ones.
collective objective ( e₁*, …, en* ) = argmaxeᵢ ∈ C(mᵢ) ∑i φ(mᵢ, eᵢ) + β · ∑i < j rel(eᵢ, eⱼ) inlink relatedness rel(a, b) = 1 − [ log max(|A|, |B|) − log |A ∩ B| ] ⁄ [ log |W| − log min(|A|, |B|) ] A, B = entities linking to a, b; W = all entities random walk π = α · s + ( 1 − α ) · Pᵀ π s = restart mass on the document's mentions; rank candidates by π
Linking ambiguous mentions: prior vs context vs coherence λ weighs the prior against context; coherence adds support from the other chosen entities; below τ a mention is NIL

Try the first sentence: with coherence off and λ = 0.5, "Jordan" goes to the athlete on prior alone; lower λ to about 0.3, or switch coherence on, and Amman pulls it to the country. In the second sentence the reverse happens — context and coherence pull "Chicago" and "Boston" from the cities to the teams. In the last, the person's name has no alias entry, every candidate is a weak fuzzy match, and the threshold correctly returns NIL; drag τ down far enough and the linker confidently attaches a stranger to a fictional character. (Set λ = 0 to see the opposite failure: with the prior ignored, a weak context match alone clears the threshold.)

Neural entity linking

  • Bi-encoder retrieval. One encoder embeds the mention with a marked span and its context, another embeds each entity's name and description; the score is a dot product. Entity vectors are precomputed, so candidate generation over millions of entities is an approximate nearest-neighbour search — and because entities are represented by their descriptions, the model links to entities never seen in training (zero-shot linking).
  • Cross-encoder re-ranking. The top-k candidates are re-scored by a single encoder that reads mention context and entity description together, so attention can compare them token by token. Far more accurate, far more expensive — the same retrieve-then-rerank shape as RAG re-ranking.
  • Generative linking has a model output the entity's unique name token by token, with decoding constrained to a prefix tree of valid names so that it can only produce existing entities.
  • Training uses in-batch and hard negatives (wrong candidates that share the alias), which is what teaches the model the fine distinctions the prior cannot.
bi-encoder sbi(m, e) = encm( [ctxleft ⟨m⟩ ctxright] ) · ence( [name ; desc] ) cross-encoder scross(m, e) = w · enc( [ctx(m) ; SEP ; name ; desc] )CLS training ℒ = − log [ exp s(m, e⁺) ⁄ ∑e ∈ {e⁺} ∪ N exp s(m, e) ] N = in-batch + hard negatives

LLM-assisted disambiguation

  • An LLM is a strong re-ranker: give it the passage, the mention, and the top candidates as (id, name, type, one-line description), and ask it to return one id or NIL. It brings world knowledge and reads long context well, which helps on rare entities and subtle cues.
  • Fence it in: the answer must be one of the listed ids (validate, or constrain decoding); NIL must be an explicit option, or the model will always pick something; and ask for the evidence phrase that justified the choice. Never let it invent an identifier — models will produce plausible-looking ids that do not exist.
  • Cost and latency make it a second tier: the classical or bi-encoder pipeline handles the confident majority, and the LLM sees only low-margin or high-value mentions.

Evaluation

  • In-KB accuracy: over mentions whose gold entity exists in the KB, the fraction linked correctly. Candidate recall bounds it from above; reporting accuracy only over mentions where the gold survived candidate generation (sometimes called normalised accuracy) isolates the ranker.
  • NIL handling is scored separately: precision and recall of NIL predictions, or an overall accuracy that counts a correct NIL as a hit. A system tuned only for in-KB accuracy can look excellent while linking every out-of-KB mention to a wrong entity.
  • Micro accuracy averages over all mentions (dominated by long documents and frequent entities); macro averages per document (or per entity), exposing failures on short texts and rare entities. Report both.
  • End-to-end evaluation includes mention detection: a link counts only if the span is also right, scored as precision/recall/F1 like NER.
in-KB accuracy AccKB = |{ m ∈ MKB : ê(m) = e*(m) }| ⁄ |MKB| micro vs macro micro = ∑d correctd ⁄ ∑d |Md| macro = (1 ⁄ |D|) ∑d correctd ⁄ |Md|
Takeaway: generate candidates for recall, rank locally with prior plus context, let the document vote through coherence, and keep an honest NIL. Every error here becomes a wrong edge in the graph — linking is where knowledge-graph quality is won or lost.

06 Knowledge-graph embeddings

  • Embed entities and relations as vectors so that valid triples score high — e.g. TransE: head + relation ≈ tail.
  • Enables link prediction (inferring missing edges) and similarity over entities — which also feeds the relatedness signal of collective linking (§05).
  • Bridges symbolic graphs with the vector world of embeddings and GNNs.

TransE models a relation as a translation in vector space: starting at the head entity h and moving by the relation vector r should land near the tail t. Plausibility is the negative distance — lower distance means a more plausible triple.

geometry h + r ≈ t distance d(h, r, t) = ‖ h + r − t ‖₂ score f(h, r, t) = − ‖ h + r − t ‖ (higher = more plausible)
Equation decoder — f(h, r, t) = − ‖ h + r − t ‖
Say it
“f of h, r, t equals minus the norm of h plus r minus t” — start at the head's vector, step by the relation's vector, measure how far you landed from the tail, and negate that distance so closer means a higher score.
Shapes
h, r, t ∈ ℝᵈ — one learned row each from the entity table and the relation table, all the same width d. h + r − t ∈ ℝᵈ is a residual vector; the norm ‖·‖ reduces it to a non-negative scalar, so f(h, r, t) ≤ 0 is a scalar with 0 as the perfect score.
Scope
The norm runs over the d coordinates of the single residual vector — here the Euclidean ‖·‖₂ of the distance line (TransE is also used with the L1 norm). The ∑ in the margin loss below ranges over every true triple (h, r, t) in the training graph paired with its corrupted triples (h′, r, t′), made by swapping in a random head or tail; nothing sums across relations inside one score.
Plain words
Each relation is a fixed arrow in embedding space. A fact is believable when following the relation's arrow from the head lands you on (or near) the tail; the score is just how close you got, with a minus sign so bigger is better.
Tiny example
d = 2, h = [1, 0], r = [0, 1] → h + r = [1, 1] true t = [0.9, 1.2]: h+r−t = [0.1, −0.2] ‖·‖₂ = 0.2236 f = −0.2236 corr t′ = [−1, 0.5]: h+r−t′ = [2, 0.5] ‖·‖₂ = 2.062 f = −2.062 → true triple ranks first (L1 norm instead: 0.3 vs 2.5 — same order) hinge, γ = 1: max(0, 1 + 0.2236 − 2.062) = 0 hinge, γ = 2: max(0, 2 + 0.2236 − 2.062) = 0.1621
Why it's here
It is the concrete instance of the knowledge-graph embedding idea in §06: the triples of §02 become vector arithmetic, and ranking every candidate tail by this score is exactly the link prediction the §07 viz draws. It is the simplest translation model in the field — the baseline later embedding models are measured against — and the bridge from symbolic facts to the vector world, which is what lets a graph fill in missing edges before serving the retrieval and multi-hop uses of §08–§09.

Training uses a margin ranking loss: real triples should score better than corrupted ones (h′, r, t′) by at least a margin γ.

loss L = ∑ max( 0, γ + d(h, r, t) − d(h′, r, t′) )

07 TransE scoring & link prediction

Pick a head entity and a relation; the target point h + r is drawn, and every candidate tail is ranked by distance to it. The closest is TransE's predicted answer — link prediction in 2-D.

h + r ≈ t in 2-D embedding space The star marks h + r; bars rank candidate tails by −distance

This is the same idea as the king − man + woman ≈ queen arithmetic on the Embeddings page — relations become consistent offset directions.

08 GraphRAG: retrieving from a graph

Vector RAG retrieves chunks that look like the question. Graph retrieval follows the relations the question is about — and can summarise a whole corpus in a way nearest-neighbour search cannot.

Local search: entity-centric retrieval

  1. Link the query. Run NER and entity linking (§05) on the question to find seed nodes — the same linker that built the graph, so query and graph agree on identities.
  2. Expand a subgraph. Collect the seeds' k-hop neighbourhood (usually 1–2 hops), filtered to relation types relevant to the question. Hubs explode the frontier — a country node has millions of edges — so expansion is pruned by relation type, by edge weight, or by personalised PageRank from the seeds (keep the top-scoring nodes, not the full ball).
  3. Assemble context. Serialise the subgraph as triples or short sentences, attach each entity's description and the source text chunks it was extracted from (provenance pays off here), and put it in the prompt — see Context Engineering.
  4. Generate with citations to triples and chunks, so an answer can be traced to edges rather than to a fuzzy passage.
seeds S = { link(m) : m ∈ mentions(q) } subgraph Gq = top-Kv πS(v) πS = α · 1S ⁄ |S| + ( 1 − α ) · Pᵀ πS (personalised PageRank) context ctx(q) = serialise( Gq ) ⊕ desc(v ∈ Gq) ⊕ chunks(provenance(Gq))

Global search: community summaries

  • Some questions have no seed entity: "What are the main themes across these 5,000 reports?" No single chunk contains the answer, so top-k similarity retrieval returns an arbitrary sample.
  • The community approach, at indexing time: (1) LLM-extract entities and relations from every chunk into a graph; (2) run hierarchical community detection (modularity-based clustering) to partition the graph into nested clusters of densely connected entities; (3) have an LLM write a summary of each community at each level.
  • At query time a global question is answered map-reduce over the summaries: each community summary produces a partial answer with a relevance rating, and a final call merges the highest-rated partials. The hierarchy level trades breadth for cost.
  • Lighter variants (2024–2026 practice) skip the up-front summarisation and build or summarise communities lazily at query time, cutting indexing cost substantially at some cost in query latency.

Fast-changing corpusEasy — embed new chunksCostly — re-extract, re-link, re-cluster

Costs and pitfalls

  • Indexing cost. LLM extraction over every chunk plus community summaries costs far more than embedding the same chunks — often by one or more orders of magnitude in model calls. Budget it before committing.
  • Graph quality caps answer quality. Missed links split one entity into several weak nodes; wrong links merge strangers; hallucinated triples become confident "facts". The construction and linking gates of §04–§05 matter more here than any retrieval trick.
  • Maintenance. Incremental updates are easy for triples but hard for community structure and summaries, which drift as the graph changes.
  • The common production answer is hybrid: vector retrieval for passages, graph expansion around linked entities for structure, and a re-ranker over the union — evaluated with the same faithfulness and context-recall metrics as plain RAG evaluation.
Takeaway: use the graph when the question is about relations, completeness, or the whole corpus; use vectors when it is about what a passage says. Most real systems do both, and both depend on the entity linker agreeing with itself at index and query time.

09 Why they matter

  • Grounding & retrieval: structured facts back search and RAG — GraphRAG (§08) traverses relations, not just similar chunks — and give a fact-checking target for LLM outputs.
  • Reasoning: multi-hop questions follow explicit relation paths (see Question Answering); ontology entailment adds facts nobody wrote down.
  • Enterprise knowledge: unify entities across siloed databases — schema alignment plus entity resolution, with the ontology as the shared contract.
  • Search and recommendation: entity cards, faceted navigation, and "related items" are graph neighbourhoods; KG embeddings power similarity and link prediction.

10 Takeaways

  • KG = entities + typed relations, stored as (head, relation, tail) triples with global identifiers and typed literals.
  • Ontology = TBox (classes, properties, domain/range, axioms) over an ABox of facts; reasoning infers under the open world, shapes validate under a closed one.
  • Build by mapping tables (row → entity, column → property, foreign key → relation) and text (NER → linking → relation extraction → canonicalisation → validation); fence LLM extraction with schema and evidence checks and keep per-triple provenance.
  • Entity linking = candidates → prior + context → collective coherence → NIL; it decides graph quality.
  • KG embeddings (TransE) enable link prediction and connect to GNNs.
  • GraphRAG wins on multi-hop, exhaustive, and global questions; vectors win on passage lookup; hybrid is the default.
