Named Entity Recognition

NER finds and classifies the spans of text that name real-world things — people, places, organizations, dates — turning free text into structured entities. It is the first step of most information-extraction pipelines, and the classic testbed for every sequence-labeling idea from gazetteers to transformers.

01 The task

Input a sentence; output a set of typed spans. Two decisions per entity — where it starts and stops, and what kind of thing it is — and both are harder than they look.

  • Formally: given tokens x = (x₁ … x_T), return a set of triples (i, j, type) meaning "tokens i through j name an entity of this type". Typical type sets are small — PER, LOC, ORG, MISC in general-domain corpora; hundreds of types in fine-grained or biomedical schemes.
  • Why it is hard. Entities are ambiguous in type (Apple the company vs the fruit, Washington the person, city, or state), multi-word with fuzzy boundaries (is the part of The New York Times? is Inc. part of the org?), and open-class — new names appear every day, so memorisation cannot work.
  • Context does the disambiguation. "…shares of Apple fell" versus "…ate an apple" differ only in surrounding words, which is precisely why contextual encoders transformed the task.
  • Two framings. Cast it as token labeling (a tag per token, decoded into spans) or as span classification (enumerate candidate spans, classify each). The first dominates historically; the second handles overlap, and both appear in §05.
two framings of the same tasktoken labeling: x → y ∈ ST , then decode spans from y span classification: { (i, j) : 1 ≤ i ≤ j ≤ T, j − i < L } → type ∪ { none }
One idea: NER is boundary detection plus typing. Most systems are good at typing and lose their points on boundaries — which is why the metric in §07 is unforgiving about exactly where a span begins and ends.

02 Tag schemes: BIO & BIOES

To turn spans into per-token labels you need a scheme that marks where each entity begins, so that two adjacent entities of the same type do not silently merge into one.

BIO and its variants

  • BIO (also called IOB2) uses three prefixes: B- begins an entity, I- continues it, O is outside any entity. For k entity types the tag set has 2k + 1 labels.
  • The B- prefix is the entire reason the scheme exists. Without it (the older IO scheme), Paris London tagged I-LOC I-LOC is indistinguishable from the single two-word location Paris London. IO has only k + 1 labels and is simpler to learn, but cannot represent adjacent same-type entities at all.
  • BIOES (equivalently BILOU) adds E- for the last token of a multi-token entity and S- for a single-token entity, giving 4k + 1 labels. The extra labels make boundaries explicit rather than implicit, which usually buys a small F1 gain — at the cost of more classes and sparser training signal per class.
  • Every scheme induces illegal transitions: under BIO, O → I-PER and B-LOC → I-PER are ill-formed. A CRF layer or constrained decoding enforces these; a plain softmax merely learns to avoid them most of the time.
tag-set size and legalityIO: k + 1 labels BIO: 2k + 1 BIOES: 4k + 1 legal(yt−1 → I-X) ⟺ yt−1 ∈ { B-X , I-X } spans(y) = { (i, j, X) : yi = B-X , yi+1…j = I-X , yj+1 ≠ I-X }
BIO tags & entity spans B- starts an entity, I- continues it, O is non-entity

BIO lets a token classifier represent multi-word and adjacent entities unambiguously, and it makes span extraction a deterministic post-processing pass over the tag sequence. Note the asymmetry the readout exposes: a single wrong tag in the middle of a four-token organisation destroys the whole entity at evaluation time, because scoring is per span, not per token.

Takeaway: the tag scheme is a lossless encoding of a set of spans as a sequence of labels — provided the sequence is well-formed. Choosing BIO vs BIOES is a bias/variance trade: more labels means sharper boundary signal but fewer examples per label.

03 Approaches, old to new

Four eras, each removing the previous era's manual labour: hand-written rules → hand-engineered features → learned word features → pretrained contextual features.

Rules and gazetteers

  • Regular expressions over word shape (Xxxxx Xxxxx), trigger words (Mr., Inc., said), and gazetteers — curated lists of known names. High precision on the covered vocabulary, poor recall on everything else, and enormous maintenance cost per domain.
  • Gazetteers never fully disappeared: they survive as features inside statistical models and as post-hoc validators in production systems, where a lookup against a customer list is often more reliable than a model.

Statistical, neural, and pretrained

  • CRFs replaced rules with weighted feature functions over the whole sequence, decoded with Viterbi — see HMMs & CRFs. Features were still hand-designed (capitalisation, suffix, gazetteer hit, neighbouring words), but weights were learned and globally normalised.
  • BiLSTM-CRF replaced feature engineering with learned representations: pretrained word embeddings plus a character-level encoder (for morphology and unseen-word shape), a bidirectional LSTM for context, and a CRF layer for valid transitions.
  • Transformer token classification is the current default: fine-tune a pretrained encoder such as BERT with a linear head over the tag set. Subword-level contextual vectors handle unseen names gracefully, and the pretraining does the work that gazetteers used to.

Generative LLM prompting

  • An instruction-tuned LLM can be asked to return entities directly as JSON, zero-shot or with a handful of demonstrations. This is unbeatable for cold-start work: a new entity type with no training data, or a one-off extraction over a few thousand documents.
  • The weaknesses are structural. Output is generated, not aligned — the model may return a normalised string ("New York City") that does not occur verbatim in the text, so offsets must be recovered by fuzzy matching and sometimes cannot be. Long documents strain recall, output is non-deterministic, and cost per document is orders of magnitude above a fine-tuned encoder. Constrained/structured decoding fixes the JSON shape but not the grounding.
  • The practical pattern is hybrid: use an LLM to bootstrap silver labels or handle rare types, then distil into a small encoder for volume.

04 The token-classification head

Fine-tuning an encoder for NER is a two-line change — a linear layer and a cross-entropy loss. The subtlety is entirely in aligning word-level labels to sub-word tokens.

The head itself

  • The encoder returns a contextual vector ht ∈ ℝd per token. A shared linear layer projects each to |S| logits, and a softmax gives a distribution over tags at that position. Loss is the mean cross-entropy over labelled positions.
  • Crucially there is no interaction between positions in the head — all context comes from the encoder. That is why a CRF layer (a learned |S| × |S| transition matrix, plus Viterbi) is an optional add-on, not a redesign.
per-token softmax headht = Encoder(x)t ∈ ℝd zt = W ht + b , W ∈ ℝ|S| × d P(yt = s | x) = softmax(zt)s = exp(zt,s) ⁄ ∑s′ exp(zt,s′) ℒ = −(1 ⁄ |M|) ∑t ∈ M log P(yt = y*t | x) M = positions that carry a label

Sub-word alignment

  • Labels are annotated on words; the model consumes sub-words (see Tokenization). Lovelace may become Love ##lace, so one gold label must be distributed over two positions.
  • The standard convention is first-subword labelling: the first piece of a word carries the word's tag; every continuation piece, plus special tokens such as [CLS] and [SEP], is assigned the ignore index (conventionally −100) and excluded from both loss and prediction. At inference, the tag of the first piece is the tag of the whole word.
  • The alternative — propagating B-X to the first piece and I-X to the rest, and supervising every piece — trains on more positions but must then reconcile disagreements between pieces of one word at decode time. First-subword labelling avoids that entirely, which is why it is the default.
  • Two failure modes to watch: offset drift, where reconstructed character offsets no longer match the source text (always carry the tokenizer's offset mapping rather than re-finding strings), and truncation, where entities past the model's maximum length are silently unlabelled. Use overlapping windows with a stride and merge, rather than plain truncation.

Takeaway: almost every silent NER bug lives in the alignment layer, not the model. Keep the tokenizer's offset mapping end-to-end and treat character offsets — not strings — as the ground truth for a span.

05 Nested & discontinuous entities

BIO can only express a flat, contiguous partition of the tokens. Real annotation guidelines — especially biomedical and legal ones — routinely break both assumptions.

Where flat tagging breaks

  • Nested entities. In "the University of Washington", the organisation contains a location; in "Bank of China employees", an ORG contains a LOC. A token can belong to two entities at once, and BIO gives it only one tag. Fine-grained corpora contain a substantial minority of such cases, so ignoring them caps recall.
  • Discontinuous entities. "left and right ventricles" encodes two entities sharing one head word; "pain in the neck and shoulder" splits one mention around intervening text. No contiguous span captures these.
  • Overlapping types. The same span may be legitimately typed twice (a person's name that is also a product name), which flat single-label tagging cannot express.

Span-based models

  • Enumerate every candidate span up to a maximum width L, build a span representation from its endpoints (and optionally a pooled interior), and classify it into types ∪ {none}. Because spans are scored independently, overlap and nesting are free — the model can accept two spans that share tokens.
  • The biaffine formulation scores a span by combining a start representation and an end representation through a bilinear form, producing a T × T × |types| table; the upper triangle is exactly the set of valid spans. It is elegant and strong, but costs O(T²) candidates — hence the width cap.
  • Other framings: machine-reading-comprehension NER asks a question per type ("find all locations") and predicts start/end pointers, which transfers well to unseen types because the type name is in the prompt; seq2seq NER generates a linearised list of spans, handling nesting and discontinuity uniformly at the cost of exposure to generation errors; and hypergraph / transition-based parsers build nested structures directly.
biaffine span scoringsi = MLPstart(hi) , ej = MLPend(hj) score(i, j) = si⊤ U ej + W [ si ; ej ] + b ∈ ℝ|types|+1 candidates: O(T · L) spans with width cap L , O(T²) without
Takeaway: choose the framing from the annotation, not from habit. Flat and contiguous → token labeling, which is cheaper and usually stronger. Nested or overlapping → span classification. Discontinuous → span classification plus an explicit combination step, or generation.

06 From mentions to entities

NER returns mentions — pieces of text. Downstream systems need entities — stable identifiers. Bridging the two is entity linking, and it is a separate, harder problem.

The linking pipeline

  • Mention detection (this page) → candidate generation → disambiguation → NIL handling. Candidate generation uses an alias table (surface form → plausible identifiers, mined from redirects, anchor text, and synonym lists) or a dense retriever over entity descriptions; it must be high-recall, since disambiguation can only pick from what it is given.
  • Disambiguation ranks candidates using three signals: prior popularity of each identifier for that surface form, local compatibility between the mention's context and the entity's description, and global coherence — the candidates chosen for all mentions in a document should be topically consistent with each other. Global coherence is what resolves "Paris" to the city in a travel article and to the person in a celebrity one.
  • NIL prediction is mandatory in practice: many mentions refer to entities absent from the knowledge base, and a linker that always emits its best guess will confidently attach them to the wrong node.
  • Modern linkers are bi-encoders — mention-in-context and entity-description embedded into a shared space for fast retrieval — optionally followed by a cross-encoder re-ranker over the top candidates. The same retrieve-then-rerank shape as RAG.
bi-encoder linking scorescore(m, e) = cos( f(mention m + context) , g(description of e) ) = (a · b) ⁄ (‖a‖ ‖b‖) ê = argmaxe ∈ C(m) score(m, e) predict NIL if max score < τ

Coreference and downstream use

  • Within a document, the same entity appears as Tim Cook, Cook, and he. Coreference resolution groups those mentions into one chain; NER only labels the ones that are names. Aggregating attributes per entity without coreference systematically under-counts.
  • Linked, coreferent entities are what make knowledge graphs possible: entities become nodes, and relation extraction over the linked mentions supplies the edges. Without linking you have strings, not a graph.
Takeaway: "Apple" is a mention; Q312 is an entity. NER stops at the string — anything that needs to join across documents needs linking, and linking needs a knowledge base plus an honest NIL threshold.

07 Evaluation

NER is scored at the entity level, not the token level — and that single choice explains most of the gap between a model that looks good and one that is good.

Entity-level precision, recall, F1

  • Predictions and gold annotations are both sets of (start, end, type) triples. Under the standard exact-match criterion, a prediction counts as a true positive only if both boundaries and the type match; otherwise it is a false positive, and the missed gold span is also a false negative.
  • That double penalty is severe. A four-token organisation with one token clipped off scores zero, and simultaneously costs a false positive — even though token-level accuracy for that entity was 75%. Token-level accuracy is therefore always flattering and should never be reported alone; the abundant O class also inflates it toward 95%+ regardless of skill.
  • Report micro-averaged F1 across all entities (the conventional headline number), and per-type F1 alongside it, since rare types are invisible in the micro average.
entity-level scoringTP = |{ predicted spans that exactly match a gold span, type included }| P = TP ⁄ |predicted| , R = TP ⁄ |gold| , F1 = 2PR ⁄ (P + R) micro-F1: pool TP/FP/FN over all types before dividing

Exact vs partial match

  • Exact match is harsh in domains where boundaries are genuinely conventional (should a job title be inside the person span? is the trailing Ltd. part of the org?). Relaxed criteria exist: type match credits any overlap with the right type; partial match awards half credit for an overlapping span with the correct type; boundary match ignores type and scores boundaries alone.
  • Decomposing errors this way is diagnostically valuable — it separates "the model found the right thing and mislabelled it" from "the model found the wrong extent" from "the model missed it entirely" — but the numbers are not comparable to exact-match figures. Always state which criterion you used.
  • Sanity checks that catch real bugs: does the evaluator ignore illegal tag sequences or silently repair them? Are offsets character-based or token-based on both sides? Were truncated documents scored as missed entities or dropped from the denominator?

08 Domains & where it's used

General-domain NER is close to saturated; almost all real work is domain adaptation, where the type inventory, the text, and the conventions all differ from anything pretrained.

Domain adaptation

  • Specialised text breaks general models in specific ways: biomedical and chemical names are long, hyphenated, and non-capitalised; legal text has bespoke party and citation types; clinical notes are ungrammatical and abbreviation-dense; user-generated text abandons capitalisation entirely, removing a feature general models lean on heavily.
  • The reliable ladder, cheapest first: (1) continued pretraining of the encoder on unlabelled in-domain text, which is nearly always the largest single win; (2) fine-tune on a few hundred to a few thousand in-domain annotations; (3) add gazetteer features or a dictionary post-filter for closed sub-vocabularies such as product codes; (4) use an LLM to produce silver labels that a human corrects, rather than annotating from scratch.
  • Test on capitalisation-perturbed and lowercased inputs before shipping. A drop of 20+ F1 points when case is stripped is common and reveals a model that has learned orthography instead of semantics.

Applications

  • Information extraction and search indexing — entities are the facets users filter by, and the anchors that make retrieval precise.
  • Redaction and compliance: detecting PII before storage or before sending text to a third-party model. Note that recall matters far more than precision here — a missed name is a breach, an over-redaction is an inconvenience.
  • Structured extraction from forms and contracts, where NER supplies the values that document intelligence attaches to fields.
  • Building knowledge graphs, and feeding relation extraction, event extraction, and question answering — all of which take entity spans as their input.
Takeaway: the benchmark number tells you almost nothing about your corpus. Budget for in-domain annotation and continued pretraining, and pick the operating point (precision- or recall-heavy) from the consequence of each error type.

09 Pitfalls & what to remember

The mistakes that cost real F1, and the lines worth carrying away.

Pitfalls

  • Reporting token accuracy. Inflated by the dominant O class and blind to boundary errors. Report entity-level F1 and name the match criterion.
  • Broken sub-word alignment. Labelling every piece, forgetting the −100 ignore index, or losing the offset mapping. The model trains fine and the spans come out wrong.
  • Silent truncation. Entities past the maximum sequence length disappear without error. Use a sliding window with overlap and merge spans across windows.
  • Forcing nested annotations into BIO. If the guidelines allow nesting, flat tagging silently discards the inner or outer mention and caps achievable recall. Switch framings instead of tolerating the loss.
  • Relying on capitalisation. Works on newswire, collapses on lowercased queries, transcripts, and chat. Augment training data with case perturbation.
  • Trusting LLM output as spans. Generated strings are not grounded offsets. Always verify the returned text occurs in the source, and treat anything unmatched as a failure rather than a paraphrase.

What to remember

  • NER = find + type entity spans, framed either as token labeling or as span classification.
  • BIO/BIOES encode spans as per-token tags; the B- prefix is what separates adjacent same-type entities.
  • Lineage: rules → CRFs → BiLSTM-CRF → fine-tuned transformer heads, with LLM prompting for cold start.
  • Subword alignment (first-piece labelling, ignore index for continuations) is where the bugs live.
  • Exact-match entity F1 is the metric, and boundaries are the hard part.
  • Mentions are not entities — linking and coreference turn spans into identifiers.
