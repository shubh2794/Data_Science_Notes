Retrieval-Augmented Generation

Give the model an open book: retrieve relevant documents at query time, stuff them into the prompt, and generate a grounded, citable answer — instead of relying on what's baked into the weights.

NLP LLM systems Retrieval

01 Why RAG exists

An LLM's knowledge is frozen in its weights. RAG gives it a live, external memory it can read from.

Parametric vs non-parametric memory

  • Parametric — knowledge baked into the weights during training. Fixed; updating it means retraining.
  • Non-parametric (RAG) — knowledge stored outside the model in a searchable index, fetched at inference and updated anytime without touching the weights.

What it fixes

  • Knowledge cutoff — retrieve current information the model never saw.
  • Hallucination — answering from retrieved evidence, not vibes, reduces confident falsehoods.
  • Proprietary / domain knowledge — your internal docs, never in any public training set.
  • Traceability — retrieved sources give you citations and explainability.
One sentence: RAG = retrieve relevant text → augment the prompt with it → generate a grounded answer.

02 The end-to-end pipeline

Two halves: an offline indexing phase, and an online query phase. Run the demo to watch a query score the docs and assemble a grounded answer.

Indexing (offline)

Document → parse → chunk → embed each chunk → store vectors in a vector DB

Query-time (online)

Query → embed → similarity search (top-k) → [optional re-rank] → prompt = context + query → LLM → answer

03 Chunking

Documents are too big to embed whole, so we split them. How you split decides what you can retrieve.

  • Fixed-size — split every N tokens (e.g. 256–512) with some overlap. Cheap, but blindly cuts across sentences and ideas.
  • Context-aware — split on sentences, document structure (Markdown/HTML headings), or recursively; semantic chunking starts a new chunk when adjacent-sentence similarity drops.
  • Late chunking — embed the whole document with a long-context model first, then pool into chunks, so each chunk keeps full-document context.
  • Late interaction (ColBERT) — keep token-level embeddings and score with MaxSim; very precise but storage-heavy.
Rule of thumb: if a chunk makes sense to a human without the surrounding text, it will to the LLM. Too small → no context; too large → noise dilutes the match.

04 Embeddings & similarity

Dense retrieval turns text into vectors where "related" means "close."

Each chunk and the query map to a vector; relevance is geometric proximity, usually cosine similarity:

cos(q, d) = (q · d) / (‖q‖ ‖d‖)
  • Bi-encoder (dual-encoder): query and document encoded independently, so all document vectors are precomputed offline. Fast — embed the query once, then search. This is what makes RAG tractable.
  • Sentence-BERT (SBERT): fine-tunes BERT with a Siamese/triplet setup so a single pooled vector captures sentence meaning. Raw BERT [CLS]/mean vectors are poor for similarity; SBERT turns a 65-hour pairwise search into a ~5-second one.
  • Trained with a contrastive objective — pull the query toward its relevant doc, push it from irrelevant ones.

See Embeddings for the representation details.

05 Sparse vs dense retrieval

Lexical matching and semantic matching fail in opposite situations — which is why hybrid wins.

Sparse / lexical (exact term overlap)

TF-IDF(t, d) = TF(t, d) · log(N / DF(t)) BM25(q, d) = Σ_t IDF(t) · ( f(t,d)·(k₁+1) ) / ( f(t,d) + k₁·(1 − b + b·|d|/avgdl) ) k₁ ≈ 1.2–2.0 b ≈ 0.75

Fast, deterministic, unbeatable for exact identifiers, codes, proper nouns, and jargon — but blind to synonyms and paraphrase. BM25 is the production default.

Dense / semantic (vector proximity)

Handles paraphrase, synonymy, and natural-language intent, and works cross-lingually — but is heavier, degrades on domain mismatch, and can miss exact rare terms.

Sparse (BM25)Dense (embeddings)
Matches onExact termsMeaning
Strong atIDs, codes, rare/exact termsParaphrase, synonyms, intent
Weak atSynonymy, paraphraseExact constraints, novel terms
CostCheap, no modelEmbedding + ANN index

06 Vector search (ANN)

Exact nearest-neighbour over millions of vectors is too slow — so we approximate.

  • Exact search scores every vector: O(n) per query, infeasible at scale.
  • Approximate Nearest Neighbour (ANN) trades a tiny bit of recall for orders-of-magnitude speed.
  • HNSW — navigable small-world graph; very low latency, the common default.
  • IVF — inverted-file + quantization; scales to huge corpora.
  • FAISS — Facebook's library implementing many of these; Pinecone / Weaviate / Qdrant / Chroma / Milvus are managed vector DBs built on the same ideas.

07 Hybrid search & re-ranking

Retrieve wide and cheap, then re-score the shortlist precisely.

Two-stage retrieval (the production standard)

Stage 1 BM25 / dense → top 100–1000 candidates (recall-safe, cheap) Stage 2 cross-encoder re-ranker → reorder, keep top-k (precise)

A cross-encoder reads query and document together in one forward pass, so it models their interaction directly — far more accurate than a bi-encoder, but O(candidates), hence used only on the shortlist.

Fusing multiple retrievers

Run lexical and dense in parallel and merge. Reciprocal Rank Fusion needs no score normalization — it just combines ranks:

RRF(d) = Σ_i 1 / (k + rank_i(d)) k ≈ 60

Robust to retrievers on totally different score scales; a doc ranked high by both retrievers floats to the top.

08 Generation & context injection

How the retrieved chunks actually reach the model — and the trap in long contexts.

prompt = [system: "answer only from the context"] + [retrieved chunks] + [user query]

"Lost in the middle"

LLMs attend most to the start and end of a long context and gloss over the middle. So:

  • Put the highest-relevance chunks first (this is what re-ranking buys you).
  • Keep the context tight — more chunks isn't better if they bury the answer.
  • Instruct the model to ground its answer in the context and cite sources.

09 Advanced RAG

Naive RAG is one retrieve-then-read. The hard queries need more.

  • Query rewriting / expansion — rephrase or add synonyms so retrieval matches better.
  • HyDE — have the LLM write a hypothetical answer document, embed that, and search near it. A guessed answer often sits closer to the real passage than the question does.
  • Multi-hop — decompose a question that needs chained facts ("the CEO of X who studied at Y") into sub-queries, retrieving and reasoning iteratively.
  • RAG-Fusion — generate several query variants, retrieve for each, fuse with RRF.
  • Parent-document / small-to-big — embed small chunks for precise matching, but return the larger parent for generation context.
  • Sentence-window / auto-merging — retrieve fine-grained, then expand to a surrounding window or merge sibling chunks into their parent.
  • Contextual retrieval (Anthropic) — prepend an auto-generated context blurb to each chunk before embedding ("This is from Acme's Q3 2024 report…"); cut failed retrievals by ~49% (≈67% with re-ranking).
Maturity ladder: Naive (retrieve → read) → Advanced (pre/post-retrieval tricks: rewriting, re-ranking, contextual chunks) → Modular / agentic (planning, tools, iterative retrieval).

10 Evaluation

Score the retriever and the generator separately — a great LLM can't fix bad retrieval, and vice versa.

Retrieval metrics

Precision@k = (relevant in top-k) / k Recall@k = (relevant in top-k) / (all relevant) MRR = (1/N) Σ 1 / rank_of_first_relevant nDCG@k = DCG@k / IdealDCG@k, DCG@k = Σᵢ relᵢ / log₂(i+1)

Generation metrics

  • Faithfulness / groundedness — is the answer actually supported by the retrieved context?
  • Answer relevance — does it address the question?
  • Context precision / recall — was the retrieved context on-point and complete?
  • RAGAS — a framework bundling these (context precision/recall, faithfulness, answer relevance) into an automated, reference-light score.

11 RAG vs fine-tuning

They solve different problems — knowledge vs behaviour — and pair well.

AspectRAGFine-tuning
Updating knowledgeDynamic — re-index, no retrainingExpensive retraining cycle
Current infoRetrieved at inferenceFrozen at training cutoff
Style / tone / formatNot really changedAdapts vocabulary & style
InterpretabilityCitations availableBlack-box weights
CostLower (no training)High (compute + labeled data)
Default: RAG for knowledge, fine-tuning for behaviour. Start with RAG; add fine-tuning when you need a specific style or domain vocabulary. Often both.

13 Takeaways

  • RAG = retrieve → augment → generate. External, updatable memory instead of frozen weights — fixing cutoff, hallucination, and private-data gaps.
  • Retrieval quality is the ceiling. Chunking, embeddings, and re-ranking matter as much as the LLM.
  • Hybrid + two-stage (BM25/dense recall → cross-encoder re-rank) is the robust production pattern.
  • Mind the prompt — best chunks first to dodge "lost in the middle," and instruct for grounded, cited answers.
  • Evaluate both halves — retrieval (P@k, recall@k, MRR, nDCG) and generation (faithfulness, answer relevance, RAGAS).
  • RAG vs fine-tuning — knowledge vs behaviour; usually start with RAG. Builds on Embeddings and Language Models.
