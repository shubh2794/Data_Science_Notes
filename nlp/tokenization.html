Tokenization

Cutting text into the discrete pieces a model can count — the boundary between language and tensors.

NLP Sub-words Fundamentals

01 What tokenization is

A neural network can't ingest a string — it ingests integers. Tokenization is the function that turns raw text into a sequence of IDs drawn from a fixed vocabulary, and back again.

  • It is a deterministic map text → [id₁, id₂, …, idn], where each ID indexes a row of the model's embedding table.
  • The unit isn't a word and isn't a character — it's a token: a sub-word chunk learned from a corpus so that frequent strings stay whole and rare ones split into reusable pieces.
  • The tokenizer is trained once, before the model, and then frozen. Its vocabulary is part of the model's contract: the same string must always produce the same IDs.
  • Every downstream cost — sequence length, attention compute, context-window budget, and API price — is denominated in tokens, not words or characters.
tokenize : Σ* → Vn detokenize ∘ tokenize = id |V| ≈ 30k – 256k
One idea: a token is the atom of cost and meaning for a language model. Pick the atoms well and short, common text becomes cheap while rare or unseen text still survives — never an out-of-vocabulary crash.

02 The granularity spectrum

Where you cut decides everything. There are three natural grain sizes — and sub-word is the engineered compromise between the two extremes.

Characters — tiny vocab, long sequences

  • Vocabulary is just the alphabet (≈100 symbols). Never any OOV — every string is representable.
  • But sentences explode into long sequences, and the model must relearn spelling from scratch. Self-attention is O(n²) in sequence length, so long sequences are expensive.

Words — short sequences, brittle vocab

  • One token per word: short sequences, intuitive units.
  • But the vocabulary must be enormous to cover a language, the long tail is always incomplete, and any unseen word ("antidisestablishmentarianism", a typo, a new product name) becomes an <UNK> — information destroyed.

Sub-words — the sweet spot

  • Keep frequent whole words as single tokens; split rare words into morpheme-like pieces (tokenization → token + ization).
  • A modest vocabulary (30k–256k) covers any string with no OOV, because the fallback is always smaller pieces, down to single bytes.

The spectrum is a single knob: shrink the vocabulary and sequences lengthen; grow it and sequences shorten but the embedding table balloons. Sub-word tokenizers learn where to sit on that knob from data.

03 Byte-Pair Encoding (BPE)

The dominant recipe. Start from characters and greedily merge the most frequent adjacent pair, over and over, until the vocabulary hits its target size.

The algorithm

  • Begin with every word as a sequence of single characters (plus an end-of-word marker).
  • Count all adjacent symbol pairs across the corpus. Find the most frequent pair, merge it into one new symbol, and record that merge as a rule.
  • Repeat. Each merge adds exactly one token to the vocabulary, so after k merges the vocab is base + k.
  • At inference, apply the learned merge rules in the order they were learned — that ordering is the whole tokenizer.
repeat until |V| = target: (x, y) = argmax(a,b) count( a · b ) ⟵ most frequent adjacent pair merge x · y → z , add z to V , record rule (x, y) → z

Why it works: frequency is a proxy for usefulness. The pairs worth a vocabulary slot are exactly the ones that recur — common morphemes and whole words earn their place; rare strings stay decomposed.

04 WordPiece & Unigram

BPE merges by raw frequency. Two alternatives merge by likelihood instead — they ask which vocabulary best explains the corpus, not which pair is simply most common.

WordPiece — merge by likelihood gain

  • Like BPE, it merges pairs greedily, but the score isn't raw count — it's the gain in corpus likelihood from the merge, which favours pairs whose co-occurrence is more than coincidence.
  • Marks continuation pieces with ## (so playing → play + ##ing). This is BERT's tokenizer.
score(a, b) = count(a · b) / ( count(a) · count(b) ) ⟵ merge by mutual association, not just count

Unigram — prune, don't grow

  • Works top-down: start with a large candidate vocabulary, then iteratively remove the tokens that hurt corpus likelihood least, until the target size remains.
  • Each word can be segmented many ways; the model assigns a probability to each token and picks the most probable segmentation (it can even sample alternatives — useful as regularization during training).
P(segmentation) = ∏i p(ti) seg* = argmaxseg ∏i p(ti)

SentencePiece — the language-agnostic wrapper

  • SentencePiece is the library, not an algorithm: it runs BPE or Unigram directly on raw Unicode, treating the space as an ordinary symbol (▁). No language-specific pre-tokenization, so it works the same for English, Japanese, or code.

05 Byte-level BPE & special tokens

Two engineering details make tokenizers bulletproof in production: a byte fallback so nothing is ever unrepresentable, and special tokens that carry structure the text alone can't.

Byte-level BPE

  • Run BPE over the 256 raw UTF-8 bytes rather than Unicode characters. The base alphabet is then exactly 256 symbols — so any byte sequence (emoji, rare scripts, malformed input, binary) is always tokenizable.
  • Guarantees a truly closed vocabulary: there is no <UNK> at all, because the worst case is falling back to individual bytes. This is why GPT-2 and most modern LLMs adopted it.

Special tokens

  • Sentinels & structure: [CLS] (a pooled-sentence slot) and [SEP] (segment boundary) in BERT; <|endoftext|> as a document separator in GPT.
  • Sequence boundaries: <BOS> / <EOS> mark where a generation starts and stops — sampling halts when <EOS> is produced.
  • Padding & masking: <PAD> fills short sequences to a uniform length for batching (and is masked out of attention); [MASK] is the prediction target in masked-language-model pretraining.
  • Chat models add role/turn tokens (system / user / assistant delimiters) so the model can tell who is speaking — these are reserved IDs the user's text can never collide with.
Special tokens are real vocabulary entries with reserved IDs. They are how a flat token stream encodes hierarchy — turns, segments, document edges — that raw characters can't express.

06 Vocabulary size as a trade-off

Choosing |V| is a balancing act between three competing costs. There is no free lunch — every gain on one axis is paid for on another.

  • Embedding & output table: grows linearly with |V| — each token needs an input-embedding row and an output-projection column, both of width d. A 256k vocab at d=4096 is billions of parameters before any layer.
  • Tokens per sentence: a bigger vocabulary fuses more text into single tokens, so the same passage uses fewer tokens — shorter sequences, less attention compute, more text per context window.
  • Compute / context budget: attention is O(n²) in token count, and API billing is per token. Fewer tokens means cheaper inference and longer effective context.
paramsembed ≈ 2 · |V| · d compute ∝ n² cost ∝ n (n = tokens)

So a larger vocabulary trades a one-time parameter cost (the embedding table) for a per-sentence saving (fewer tokens forever). Modern multilingual LLMs push |V| up (128k–256k) precisely to keep n small across many languages.

Rule of thumb: grow the vocabulary until the embedding-table cost stops paying for itself in shorter sequences. The crossover depends on model width d and how multilingual your text is.

07 Pitfalls & the tokenization tax

Tokenization quietly shapes what a model can and can't do well. Most "weird" LLM failures trace back to how the text was cut.

Numbers & arithmetic

  • A number like 12345 may split into arbitrary chunks (123 + 45) that don't align with place value, which is part of why naïve LLMs struggle with multi-digit arithmetic. Many modern tokenizers now split digits individually to fix this.

Whitespace, code & formatting

  • Leading spaces are usually part of the token ("hello" ≠ " hello"), so the same word can have different IDs depending on context.
  • Code is space- and indentation-heavy; tokenizers tuned for prose waste tokens on runs of spaces, which is why code-focused models add whitespace-run tokens.

Multilingual text — the tokenization tax

  • A tokenizer trained mostly on English fragments other languages into many more pieces. The same sentence in Hindi or Thai can cost 2–5× the tokens of its English translation.
  • That is a real, unequal tax: non-English users pay more (longer sequences, higher cost, less fits in the context window) for identical content — a key motivation for large multilingual vocabularies.

Cost & context follow tokens, not words

  • Context windows, rate limits, and pricing are all measured in tokens. A 100k-word document is not 100k tokens — roughly ~1.3 tokens per English word, and far more for other scripts or dense code.
  • This is why prompt size estimates must count tokens, not characters or words — see the cost relation in §06.
The tokenization tax: every quirk above is invisible in the prose but very visible on the bill and in the context budget. Knowing your tokenizer is knowing your true input length.

08 Takeaways

  • Tokens are the atoms. Models read integer IDs, not text; the tokenizer is the frozen map between them.
  • Sub-word wins. It dodges both the huge vocabulary of word-level and the long sequences of character-level, while eliminating OOV.
  • BPE = merge frequent pairs; Unigram = prune unlikely tokens; WordPiece = merge by likelihood. Byte-level BPE makes the vocabulary truly closed.
  • Vocabulary size is a three-way trade-off between embedding-table parameters, tokens-per-sentence, and compute/cost.
  • The cut has consequences: arithmetic, code, and especially non-English text all pay a hidden tokenization tax.
