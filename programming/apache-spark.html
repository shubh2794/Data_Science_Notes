Apache Spark

A distributed engine for data that does not fit on one machine. You describe a computation over a partitioned table; Spark builds a lazy plan, optimises it, cuts it into stages at every shuffle, and runs one task per partition across a cluster — keeping intermediate data in memory where it can. Most performance problems reduce to three words: shuffles, skew, and partitions.

01 Why Spark exists

  • One machine stops working somewhere between "doesn't fit in RAM" and "takes hours to scan". pandas is single-threaded and in-memory; Spark is the same tabular mental model spread across many machines.
  • It replaced MapReduce by generalising its two-phase job into an arbitrary DAG and by keeping data in executor memory between steps instead of writing every intermediate result to replicated storage.
  • Architecture. A driver process holds your program, builds the plan and schedules work; executors on worker machines run tasks and hold cached partitions. A cluster manager (standalone, YARN, or Kubernetes) hands out the executors.
UnitWhat it is
ApplicationOne driver + its executors (one SparkSession).
JobTriggered by one action (count, write, collect).
StageA run of operations with no shuffle inside; ends at a shuffle boundary.
TaskOne stage applied to one partition, on one executor core. The unit of parallelism and of retry.

  • An RDD is defined by five things: partitions, a compute function per partition, dependencies on parent RDDs, an optional partitioner, and preferred locations. The dependencies are the lineage — the recipe for rebuilding any lost partition.
  • A DataFrame and a SQL query compile to the same plan. df.groupBy("k").sum("v") and SELECT k, SUM(v) … GROUP BY k have identical performance — pick whichever reads better (see SQL).

03 Lazy evaluation and the DAG

Transformations return a new (lazy) DataFrame immediately and do no work. Only an action makes Spark plan and execute everything upstream of it.

Transformations (lazy)Actions (trigger a job)
select, filter, withColumn, join, groupBy().agg, orderBy, repartition, unioncount, show, collect, take, write…save, toPandas, foreach
  • Why lazy? Seeing the whole pipeline before running it lets the optimiser push filters below joins, read only the needed columns, and fuse many operations into one pass.
  • The trap: because nothing is materialised, every action recomputes the whole lineage from source. Two actions on an uncached DataFrame = two full reads (§08).
  • Errors surface late. A typo in a column name fails at analysis (immediately, since the schema is known); a bad value or a division by zero only fails when an action finally runs the task. Since Spark 4.0, ANSI SQL mode is on by default, so overflows and invalid casts raise errors instead of silently returning null.

05 Partitions, parallelism, and skew

  • A stage runs one task per partition, at most one task per executor core at a time. Too few partitions leave cores idle and make each task spill; too many add scheduling overhead and produce thousands of tiny output files. A common target is 100–200 MB of input per partition and 2–4× as many partitions as total cores.
  • Input partitions follow the files (roughly one per ~128 MB split). After a shuffle, the count is spark.sql.shuffle.partitions (200 by default) unless Adaptive Query Execution (on by default since 3.2) coalesces small post-shuffle partitions at runtime.
  • Skew — one key holding a big share of rows — makes one task run far longer than the rest. The stage time is the max, not the mean.
stage time is set by the largest partitionTstage ≥ c · maxᵢ rowsᵢ balanced: Tstage ≈ ⌈P / cores⌉ · c · (N / P) skew ratio = maxᵢ rowsᵢ / meanᵢ rowsᵢ c = cost per row · P = partitions · N = total rows salting a hot key k into S sub-keysk′ = (k, rand ∈ {0, …, S−1}) → aggregate on k′, then aggregate the S partials on k

  • AQE also handles the join case automatically: it detects skewed partitions in a sort-merge join from shuffle statistics and splits them into sub-tasks. Manual salting is still needed for skewed aggregations with custom logic and for older clusters.

08 Caching, persistence, and checkpointing

  • df.cache() marks a DataFrame for storage at level MEMORY_AND_DISK; it is itself lazy and is filled by the next action. Partitions that do not fit spill to local disk.
  • Cache when a DataFrame is reused by several actions or in a loop (iterative ML, an exploratory session, a dimension joined many times). Don't cache something used once — it costs memory that execution needs for shuffles and joins.
  • unpersist() explicitly when done. Executor memory is shared between storage and execution; cached blocks get evicted (LRU) when execution needs room.
  • Checkpointing writes the data to reliable storage and truncates the lineage. Use it when a lineage grows very long (hundreds of iterative steps), where a single lost partition would otherwise trigger a huge recomputation and planning itself gets slow.
MechanismSurvives executor loss?Keeps lineage?
cache() / persist()No — lost blocks are recomputed from lineageYes

10 Structured Streaming

The same DataFrame API over an unbounded table: each micro-batch appends new rows, and Spark incrementally updates the result as if the query were re-run over all data so far.

  • Execution: micro-batches by default (triggered on a fixed interval or as fast as possible), giving latencies from roughly a hundred milliseconds to seconds. availableNow triggers process everything pending then stop — handy for cheap scheduled incremental jobs.
  • Fault tolerance: source offsets and operator state are written to a checkpoint location each batch; with a replayable source (a durable log) and an idempotent or transactional sink, this yields end-to-end exactly-once results.
  • Event time: withWatermark("ts", "10 minutes") bounds how long state for a window is kept waiting for late events. Without a watermark, aggregation state grows forever.
  • Output modes: append (emit finalised rows only, needs a watermark for aggregations), update (emit changed rows), complete (re-emit the whole result; small aggregates only).

Windows, watermarks, and the durable log are covered in depth in Stream Processing.

11 MLlib

  • Pipeline API. A Transformer maps DataFrame → DataFrame (VectorAssembler, a fitted model); an Estimator has fit(df) → Transformer (StandardScaler, LogisticRegression). A Pipeline chains them so the same fitted preprocessing is replayed at scoring time — the same leakage discipline as in Data Preprocessing.
  • What it's good at: linear models, trees and gradient-boosted trees, ALS for recommendations, k-means, feature hashing and tokenising — algorithms that decompose into per-partition statistics plus a reduce.
  • What it isn't: a deep-learning trainer. For neural nets, Spark usually does the feature engineering and writes Parquet or tensor shards; a separate framework trains (see Distributed Training). Distributed batch inference via pandas UDFs is a common, well-suited pattern.
  • A frequent sweet spot: Spark aggregates terabytes into a feature table of millions of rows, then a single machine trains on it. Scale only the part that needs it.
