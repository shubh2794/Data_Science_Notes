Git & Version Control

Git is usually taught as a list of commands. It is easier to learn as one data structure and a few pointers into it. The history of a project is a directed acyclic graph of immutable snapshots. Every file, directory and commit is stored under the hash of its own contents, so the object store is a content-addressed key–value store. Branches, tags, HEAD and the staging area are small, cheap, movable pointers into that graph. Almost every command either adds objects to the store or moves a pointer, and once you can say which one a command does you can predict what it will do to your work. This page builds that model and uses it to explain commits, branching, three-way merge and rebase, undoing safely, remotes, searching history (including bisect as binary search over commits), and the parts of git that cause data scientists the most trouble: notebooks, large data, and what reproducibility needs beyond a commit hash. Every command output shown was produced by running real git (version 2.54) in throwaway repositories, and every figure that displays a hash computes it the same way git does.

01 What version control is, and what git actually stores

A version control system records the states a set of files has been in, who produced each state and why, and how the states relate. It lets you go back to any recorded state, compare two states, develop several lines of work at once and combine them later. Git records each state as a complete snapshot of the project, links every snapshot to the one or more snapshots it was made from, and never changes a snapshot once it exists. The history is therefore a directed acyclic graph (DAG) whose nodes are snapshots. Nearly every git command is a query on that graph or a change to a pointer into it.

Snapshots, not diffs

A common belief is that git stores each version as a list of changes from the version before. It does not. Each commit names one tree object that describes every file in the project at that moment. A file that did not change is not copied: the new tree points at the same stored file object as the old one, because the file's content, and therefore its name in the store, is the same (§02). So a snapshot costs only the objects that are actually new.

Widely repeated: "git stores diffs between versions, and git diff shows you what it stored." What git actually does: a commit points at a full snapshot. git diff computes a diff on demand by comparing two snapshots, which is why you can diff any two commits, including two that are not related by a single step. Deltas do appear on disk, but only as a compression detail inside packfiles, and the delta base is chosen by size and similarity, not by history order (§13). The model you program against is snapshots.

The snapshot model has practical consequences. Checking out an old commit does not replay hundreds of patches; git reads one tree. Comparing two branches does not depend on the path between them. Two people who independently produce the same file content produce the same stored object.

Distributed: every clone is the whole history

In a centralised system the history lives on a server and each developer holds only a working copy. In git every clone holds the complete object store: every commit, tree and file version that is reachable from the branches it fetched. Committing, branching, merging, viewing the log, diffing and bisecting are all local operations that need no network. A server such as a hosted GitHub or GitLab repository is, technically, just another clone that the team agrees to treat as the shared one. Collaboration consists of copying objects between object stores and moving pointers (§09).

About the hashes on this page. Every example was run in a scratch repository with author and committer set to Student <student@example.com> and with both dates pinned (starting at 2026-01-01 09:00 UTC), so the hashes printed here are reproducible. A commit's hash depends on its author, committer, both timestamps and its message as well as its content, so the same commands run on your machine will produce different commit hashes. Blob and tree hashes depend only on content, so those will match.

14 Common claims about git, checked against git

Much of what people "know" about git is a simplification that was once true, is true only by default, or was never quite true. Every row below was tested in a scratch repository while this page was written, and the section it links to shows the real output.

ClaimWhat git actually didShown in
"Git stores diffs between versions."Each commit points at a full snapshot (a tree). Diffs are computed on demand; deltas exist only as compression inside packfiles.§02, §13
"Git stores the newest version whole and older ones as deltas."The delta base is chosen largest-first. In a repository whose file shrank, the oldest version was stored whole; when the file grew, the newest was.§13
"Git records renames."No commit, tree or blob holds a rename. git mv is rm plus add; cleaning.py => clean_utils.py in git show --stat is computed at display time by content similarity (50% by default), and --follow uses the same kind of detection, which in one test followed a file into another file it had been partly copied from.§11
"Git can track an empty directory."It cannot: a directory exists in git only as a tree with entries. An empty directory did not even appear in git status. (A placeholder file such as .gitkeep is the usual workaround.)§02
"A branch is a 41-byte file."True for loose refs. After git gc the files were gone, folded into packed-refs; in a reftable repository there are no per-branch files at all.§03
"Changes on different lines always merge cleanly."Changes on adjacent lines (no unchanged line between them) conflicted; one unchanged line between them was enough to merge cleanly.§06
"A rebase replays the same patches."The same changes (zero-context patch ids matched), but different diffs (the context lines changed) and new hashes for every replayed commit, including ones whose change was untouched.§07
"'Ours' is always my branch."During a rebase, --ours gave the upstream's version and --theirs the commit being replayed.§07
"reset --hard deletes commits."The commits stayed in the store and in the reflog and were restored with one command. What it did destroy was an unstaged edit to a tracked file; a staged new file came back via fsck --lost-found; an untracked file was not touched.§08
"Re-merging a branch after reverting its merge brings the work back."It brought only the commits made after the revert. Reverting the revert was needed.§08
"git stash saves all my uncommitted work."Untracked files stayed in the working tree; only git stash -u included them.§08
"git pull = fetch + merge."With diverged branches and no configured preference, git pull stopped with fatal: Need to specify how to reconcile divergent branches.§09
"origin/main is the branch on the server."It is a ref in your own repository that only moves when you fetch, pull or push; it was stale until Bob fetched.§09
"--force-with-lease can't overwrite someone else's work."After a plain git fetch, it force-pushed over Alice's commit. Adding --force-if-includes rejected the same push.§09
"A...B means the same in log and diff."log: commits on exactly one side. diff: changes from the merge base to B. Two dots differ in the same way.§11
"-S finds every commit that touched a string."-S"lr =" missed the commit that changed lr = 0.1 to lr = 0.01, because the count of occurrences did not change; -G found it.§11
"Bisect takes exactly log₂ n steps."Between ⌊log₂ N⌋ and ⌈log₂ N⌉ tests for N candidates on a linear history; its "roughly k steps" message counts the steps remaining.§11
"Once I delete the big file, the repository shrinks."The pack stayed 4.77 MiB after deleting a 5 MB file, and a fresh clone downloaded all of it.§12
"Adding a file to .gitignore stops git tracking it."The tracked file kept appearing as modified until git rm --cached, and it remained in the old commit.§04
"SHA-1 is broken, so git's hashes are meaningless."Collisions can be manufactured at great cost, which matters for adversarial settings; git detects the known attack patterns and offers SHA-256 repositories. Accidental collisions remain negligible.§02

15 Summary

The mental model on one screen. (1) The object store is a content-addressed, append-only map from hash to bytes holding blobs (file contents), trees (directories), commits (tree + parents + who/when/why) and annotated tags; changing anything makes new objects, so nothing in it is ever edited. (2) History is the DAG formed by commits' parent links; branching is a fork in it, merging adds a node with two parents, rebasing copies a chain of nodes to a new base. (3) Four pointers make up all the state you feel: the working tree (your files), the index (the next snapshot), HEAD (where you are, usually via a branch) and branch refs (names for commits). For any command, ask: which objects does it add, and which pointers does it move? If it only adds objects or moves refs, the reflog can undo it; if it overwrites the working tree or index, uncommitted work is at risk.

For data-science repositories

  • Commit code, configs, lockfiles and data-version metafiles; keep data and model weights out of git and address them by hash (LFS for a few large files, a data-versioning tool for datasets).
  • Strip notebook outputs at staging time or pair notebooks with plain scripts; move logic that matters into modules.
  • Record four things with every result: commit, data hash, environment lock, seed. Commit before launching runs you intend to keep, and let the experiment tracker record the commit.
  • Use bisect with a deterministic metric check to find the commit that made a model worse.
