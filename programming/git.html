Git & Version Control

Git is usually taught as a list of commands. It is easier to learn as one data structure and a few pointers into it. The history of a project is a directed acyclic graph of immutable snapshots. Every file, directory and commit is stored under the hash of its own contents, so the object store is a content-addressed key–value store. Branches, tags, HEAD and the staging area are small, cheap, movable pointers into that graph. Almost every command either adds objects to the store or moves a pointer, and once you can say which one a command does you can predict what it will do to your work. This page builds that model and uses it to explain commits, branching, three-way merge and rebase, undoing safely, remotes, searching history (including bisect as binary search over commits), and the parts of git that cause data scientists the most trouble: notebooks, large data, and what reproducibility needs beyond a commit hash. Every command output shown was produced by running real git (version 2.54) in throwaway repositories, and every figure that displays a hash computes it the same way git does.

01 What version control is, and what git actually stores

A version control system records the states a set of files has been in, who produced each state and why, and how the states relate. It lets you go back to any recorded state, compare two states, develop several lines of work at once and combine them later. Git records each state as a complete snapshot of the project, links every snapshot to the one or more snapshots it was made from, and never changes a snapshot once it exists. The history is therefore a directed acyclic graph (DAG) whose nodes are snapshots. Nearly every git command is a query on that graph or a change to a pointer into it.

Snapshots, not diffs

A common belief is that git stores each version as a list of changes from the version before. It does not. Each commit names one tree object that describes every file in the project at that moment. A file that did not change is not copied: the new tree points at the same stored file object as the old one, because the file's content, and therefore its name in the store, is the same (§02). So a snapshot costs only the objects that are actually new.

Widely repeated: "git stores diffs between versions, and git diff shows you what it stored." What git actually does: a commit points at a full snapshot. git diff computes a diff on demand by comparing two snapshots, which is why you can diff any two commits, including two that are not related by a single step. Deltas do appear on disk, but only as a compression detail inside packfiles, and the delta base is chosen by size and similarity, not by history order (§13). The model you program against is snapshots.

The snapshot model has practical consequences. Checking out an old commit does not replay hundreds of patches; git reads one tree. Comparing two branches does not depend on the path between them. Two people who independently produce the same file content produce the same stored object.

Distributed: every clone is the whole history

In a centralised system the history lives on a server and each developer holds only a working copy. In git every clone holds the complete object store: every commit, tree and file version that is reachable from the branches it fetched. Committing, branching, merging, viewing the log, diffing and bisecting are all local operations that need no network. A server such as a hosted GitHub or GitLab repository is, technically, just another clone that the team agrees to treat as the shared one. Collaboration consists of copying objects between object stores and moving pointers (§09).

02 The object model: blobs, trees, commits, tags

Git stores exactly four kinds of object, each identified by the hash of its own bytes. A blob is the contents of one file. A tree is one directory listing. A commit is a pointer to one tree plus metadata. An annotated tag is a named, signed-or-unsigned pointer to another object. There is nothing else in the object store. Branches, HEAD and the staging area live outside it, as pointers (§03).

How the name is computed

An object's name is the hash of a short header followed by its body: the type, a space, the body length in bytes as decimal text, a zero byte, then the body. You can reproduce git's hash for hello with an ordinary SHA-1 tool:

Two consequences follow directly. First, the store is a content-addressed key–value map: the key is computed from the value, so inserting the same value twice is a no-op, and the lookup structure is a hash table in exactly the sense of Hash Tables · hashing beyond the table, except that the hash is cryptographic so that collisions are not expected to happen at all. Second, a parent's hash is written inside the child commit's bytes, so a commit's hash depends on its parent's hash, which depends on its parent's, and so on to the root. A commit hash is therefore a fingerprint of the whole history behind it, which is the same structure as a Merkle tree (here a Merkle DAG).

SHA-1, collisions, and SHA-256

Git was built on SHA-1. In 2017 researchers published two different PDF files with the same SHA-1 hash, and in 2020 a cheaper chosen-prefix collision followed, so SHA-1 no longer has the collision resistance it was chosen for. Git responded in two ways. Since version 2.13 (2017) it has computed SHA-1 with a collision-detecting implementation that recognises the known attack patterns while hashing and refuses objects that show them, so the published attacks cannot be smuggled into a repository. And git now supports a second object format: git init --object-format=sha256 creates a repository whose ids are 64 hex digits (the SHA-256 blob id for hello is 2cf8d83d…, which shasum -a 256 reproduces from the same blob 6\0hello\n bytes). The honest limits as of git 2.54: a SHA-256 repository cannot yet exchange objects with a SHA-1 repository, support across hosting platforms and tools is still uneven, and the project has announced that git 3.0 will make SHA-256 (and the reftable ref format, and main as the initial branch name) the default for new repositories, with no release date announced. For everyday integrity against accidents, either hash is effectively perfect: the chance of an accidental collision among even billions of objects is astronomically small (the birthday bound for a 160-bit hash puts it near n²/2¹⁶¹).

03 The four pointers: working tree, index, HEAD, branch

The object store only grows. Everything you experience as "state" in git (which branch you are on, what will go into the next commit, which files look modified) is held in four places outside it. The working tree is the ordinary files you edit. The index (also called the staging area) is the snapshot that the next commit will record. HEAD says which commit you are on, normally by naming a branch. A branch ref names one commit. Learning git commands mostly means learning which of these four each command moves.

Detached HEAD, demystified

"Detached HEAD" sounds like an error. It means only that .git/HEAD holds a commit hash instead of the name of a branch. You are still on a perfectly good commit; you can look around, build, run tests, even commit. What changes is that new commits are not recorded on any branch, so nothing will point at them once you switch away.

$ cat .git/HEAD
ref: refs/heads/main
$ git switch --detach 290ee3c
HEAD is now at 290ee3c Add data loader
$ cat .git/HEAD
290ee3cd6b786aaa5ebe5e51c76404fb961319bb
$ git commit -qm "Experiment on old version"     # works: 42092df
$ git switch main
Warning: you are leaving 1 commit behind, not connected to
any of your branches:

  42092df Experiment on old version

If you want to keep it by creating a new branch, this may be a good time
to do so with:

 git branch <new-branch-name> 42092df

Switched to branch 'main'
$ git switch 290ee3c                      # switch refuses to detach implicitly
fatal: a branch is expected, got commit '290ee3c'
hint: If you want to detach HEAD at the commit, try again with the --detach option.

So detached HEAD is harmless: git tells you exactly which commit you are leaving behind, it stays in the reflog for weeks (§08), and git switch -c name at any point turns the detached work into a branch. You land in it whenever you check out a tag, a specific commit, or a remote-tracking branch directly, and during every rebase and bisect. The older all-purpose git checkout detaches silently when given a commit; the newer pair git switch (move HEAD) and git restore (copy file contents), added in 2019, split its two jobs and make detaching explicit.

A branch, in this classic "files" layout, is a text file of 41 bytes: 40 hex digits and a newline. That is the precise sense in which branches are free. Two honest qualifications, both verified: after git gc the per-branch files disappear and the same information moves into one .git/packed-refs file (a loose file reappears for a branch the next time it moves, and overrides the stale packed line); and a repository created with --ref-format=reftable (the planned future default) has no per-branch files at all, only a compact binary table under .git/reftable/. In every layout a branch is still just a name for one commit hash.

04 Recording changes well

A commit is permanent once shared, it is read far more often than it is written, and it is the unit that later tools operate on: revert undoes one commit, cherry-pick copies one, bisect blames one. So the craft is to make each commit one coherent change with a message that explains it. The index exists to make that possible: it lets you choose exactly what goes into the next snapshot instead of committing whatever happens to be in your files.

Staging part of a file

Staging is per path (git add src/) and, with git add -p, per hunk: git walks through each changed region and asks whether to stage it. This is how one editing session that fixed a bug and also renamed a variable becomes two commits. In a ten-line file where line 1 and line 10 were both edited, answering y to the first hunk and n to the second leaves:

$ printf 'y\nn\n' | git add -p f.txt
$ git diff --staged | grep '^[-+][^-+]'     # will be committed
-a
+A
$ git diff | grep '^[-+][^-+]'              # still only in the working tree
-j
+J

Undoing staging is git restore --staged f.txt (index ← HEAD; your edits stay in the file). Discarding the edits themselves is git restore f.txt (working tree ← index), which is one of the few commands that destroys work git never saw (§08).

.gitignore: what it does and what it does not

A .gitignore file lists patterns for untracked paths that git should not offer to add. Patterns are matched relative to the file's directory; a trailing / matches directories only; a leading / anchors to that directory; * does not cross / but ** does; a leading ! re-includes something an earlier pattern excluded; later lines win. Private patterns that should not be committed go in .git/info/exclude. git check-ignore -v path names the exact file and line that ignores a path. Two behaviours trip almost everyone, and both were reproduced here:

# gotcha 1: ignoring a file that is already tracked does nothing
$ git add model.pkl && git commit -qm "Oops: commit a model binary"
$ printf 'data/\n!data/README.md\n*.pkl\n.env\n' > .gitignore
$ echo y >> model.pkl ; git status --short
 M model.pkl                                  # still tracked, still reported
?? .gitignore
# gotcha 2: you cannot re-include a file inside an excluded directory
$ git check-ignore -v data/README.md
.gitignore:1:data/	data/README.md               # the "!data/README.md" line had no effect
$ printf 'data/*\n!data/README.md\n*.pkl\n.env\n' > .gitignore    # exclude the contents, not the directory
$ git status --short --untracked-files=all
 M model.pkl
?? .gitignore
?? data/README.md                             # now re-included
# the fix for gotcha 1: stop tracking, keep the file on disk
$ git rm --cached -q model.pkl ; git check-ignore -v model.pkl
.gitignore:3:*.pkl	model.pkl
$ git commit -qm "Ignore data and model artifacts; stop tracking model.pkl"
$ git show HEAD~1:model.pkl                    # but the old commit still contains it, forever
x

The reason for gotcha 2 is efficiency: once git decides a directory is ignored it never looks inside it, so a negation for a file inside can never be consulted. The last line is the important one for data work (§12): untracking a file does not remove it from history. Every commit that ever contained it still does, in every clone.

What a good commit looks like

  • Atomic. One logical change: it builds and passes tests on its own, and reverting it undoes exactly one thing. A refactor and a behaviour change are two commits. Atomic commits are what make revert, cherry-pick and bisect precise.
  • Subject line in the imperative, about 50 characters. "Fix off-by-one in train/test split", not "fixed stuff" or "changes". The imperative reads as the completion of "If applied, this commit will …", and it is the form git itself uses ("Merge branch …", "Revert …").
  • Blank line, then a body that explains why. The diff already says what changed. The body says why it was needed, what was considered and rejected, and anything surprising, wrapped at about 72 columns so it reads well in a terminal. For a data change this is where the reason for a new threshold or a dropped feature belongs.
  • Structured prefixes are optional. Some teams use a machine-readable convention such as feat: / fix: / docs: subject prefixes (the "Conventional Commits" style) so release notes and version bumps can be generated automatically. Its value is consistency, not the particular words.
  • Never commit secrets. A key committed and then deleted is still in history (gotcha 1 above). Treat any secret that reached a pushed commit as leaked and rotate it.

Amend replaces the tip

git commit --amend does not edit the last commit; it cannot (§02). It builds a new commit from the current index, with the old commit's parents, and moves the branch to it. The old commit still exists and the reflog records the swap:

$ git rev-parse --short HEAD
9cbeab8
$ git commit -q --amend -m "Add f.txt"
$ git rev-parse --short HEAD
5d4dbb5
$ git reflog -2
5d4dbb5 HEAD@{0}: commit (amend): Add f.txt
9cbeab8 HEAD@{1}: commit: Add f.txt

Because amend produces a different commit, amending a commit you have already pushed rewrites shared history, with the consequences described in §07 and §09.

05 Branching

A branch is a movable name for a commit. Creating one writes a 41-byte file (§03) and copies nothing else. When you commit while on a branch, the new commit's parent is the commit the branch named, and the branch moves forward to the new commit. Two branches that started at the same commit and each received commits have diverged: the DAG now has a fork.

Creating, switching and growing

Switching branches rewrites the working tree and index to the target branch's snapshot. If you have uncommitted edits to a file that differs between the two branches, git refuses rather than overwrite them. Edits to files that are the same on both branches are carried across untouched, which surprises people but follows from the model: the working tree is not part of any branch.

Fast-forward: when "merging" only moves a pointer

If the branch you are on is an ancestor of the branch you merge, there is nothing to combine: every commit on your side is already in the other's history. Git simply moves your branch forward to the other tip. This is a fast-forward, and it creates no commit. After rebasing tune onto main (§07), merging it into main is a fast-forward:

$ git switch main ; git merge tune
Updating 7a583f0..64f3344
Fast-forward
 config.py | 4 ++--
 1 file changed, 2 insertions(+), 2 deletions(-)

Why free branches change how you work

  • A branch per question. Trying a different feature set, a different loss, a refactor you are not sure about: each gets a branch. Abandoning it costs one git branch -D.
  • The main line stays releasable. Unfinished work lives on branches, so main can always be built, tested and deployed (§10).
  • Review happens at the branch boundary. A pull request is a proposal to merge one branch into another (§09).
  • Branches are local until pushed. Nobody else sees your experimental branches unless you publish them, so you can rewrite them freely (§07).

The sandbox

A live repository you can drive. Each commit adds one new file (C1.txt containing C1, and so on), so merges never conflict and the tree of every commit is known exactly. The hash under each commit is the one real git computes for the same operations, with this page's pinned author and a clock that advances one minute per new commit. 06 Merging: the three-way merge and its base

Merging two diverged branches means producing one snapshot that contains the work of both. Comparing the two tips directly cannot do it: if a line differs between them, you cannot tell which side changed it. Git therefore finds a third snapshot, the merge base, the most recent commit both branches descend from, and compares each tip against it. A line changed on one side only takes that side's version; a line changed identically on both is fine; a region changed differently on both sides is a conflict for a human to resolve.

The merge base is a lowest common ancestor

A commit B is a common ancestor of X and Y if both can reach it by following parent edges. A best common ancestor is one that is not an ancestor of another common ancestor: nothing closer to both tips is shared. In a tree there is exactly one such node, the lowest common ancestor (LCA). In a DAG with merges there can be several, which is the criss-cross case below. git merge-base X Y returns one; git merge-base --all X Y returns all of them.

  1. Edit the file into the state you want, deleting all marker lines. To take one side wholesale for a file, git checkout --ours config.py or --theirs (or git restore --ours/--theirs).
  2. Run the tests. A merge that applies cleanly can still be semantically wrong (one branch renamed a function that the other branch started calling), so "no conflict" is not "correct".
  3. git add config.py marks the path resolved (it collapses the three stages to one).
  4. git commit (or git merge --continue) records the merge commit. To give up instead, git merge --abort restores the pre-merge state.

Trivial merges, hard merges, and --no-ff

  • Mechanically trivial: fast-forwards, and merges where the two sides touched different files or well-separated parts of the same file. Git does these without asking, and they are the vast majority.
  • Genuinely needs a human: the same region edited two ways; one side deleted or renamed a file the other edited; both sides added a file at the same path; binary files (git cannot merge bytes, so a changed .pkl or image on both sides is always a conflict); generated files such as lockfiles and notebooks, where it is usually better to regenerate than to hand-merge (§12).

  • --no-ff forces a merge commit even when a fast-forward was possible. 07 Rebase: replaying changes onto a new base

Merge combines two diverged lines by adding a commit with two parents. Rebase combines them differently: it takes the commits that are on your branch but not on the target, computes the change each one made relative to its parent, and re-applies those changes one at a time on top of the target. Since a commit's hash covers its parent (§02), every replayed commit is a new commit with a new hash, even when its change is identical. The originals are not modified, only abandoned.

Neither is "correct". The common compromise in teams is: rebase your private branch onto main as often as you like while you work, tidy it with interactive rebase before asking for review, then integrate into main with a merge commit or a squash merge, never rewriting main itself.

The golden rule: never rewrite history other people have

Once a commit has been pushed to a branch someone else may have fetched, replacing it with a rebased or amended version means their repository and yours now contain two different commits for "the same" work. If they merge or pull, both copies end up in history; if they had built on the old commit, they must now rebase their work onto your replacement by hand; and if you force-push over a branch that has gained commits you did not have, those commits are deleted from the shared branch (§09 shows this happening). The rule is about shared history: rewriting your own local or private-branch commits is normal and encouraged.

Interactive rebase: editing history before you share it

git rebase -i <base> opens a to-do list of the commits it is about to replay, oldest first. You can reorder lines, and change each line's verb: pick (keep), reword (keep, edit message), edit (stop to amend), squash (fold into the previous commit and merge the messages), fixup (fold in and discard this message), drop (remove). "Ours" and "theirs" swap during a rebase

During a merge, "ours" is the branch you are on. During a rebase, git is building on top of the target and replaying your commits onto it, so HEAD is the target and "ours" means the upstream while "theirs" means your commit being replayed. Verified on a conflicting rebase of tune onto a main that had set lr = 0.05: git checkout --ours config.py produced lr = 0.05 (main's value), --theirs produced lr = 0.01 (tune's). The markers say so too: <<<<<<< HEAD above main's line, >>>>>>> cdc6627 (Lower learning rate) below yours. Resolve, git add, then git rebase --continue; or git rebase --abort to return to where you started.

Cherry-pick: rebase for one commit

git cherry-pick <commit> applies one commit's change on top of HEAD as a new commit, keeping its message and author. It is exactly one step of a rebase. Picking 4955287 ("Add F1 metric") onto main produced 219dcea: the same change, a new parent, a new hash. Typical uses: bringing a bug fix from main onto a release branch, or rescuing one good commit from an abandoned branch. If the same change later arrives through a merge, git usually recognises the duplicate content, but the history will show the change twice.

The reflog: why "git lost my work" is almost always false

Every time HEAD or a branch moves, git appends a line to a reflog (.git/logs/): old value, new value, and what moved it. Unreachable objects are only deleted by garbage collection after that. Stash, honestly

git stash saves your uncommitted changes as special commits on a hidden ref (refs/stash) and resets your files to HEAD; git stash pop reapplies and drops the latest entry. It is handy for a quick context switch. Its weaknesses are real, though: stash entries have no branch and only an automatic message, they are easy to forget, pop can conflict, and by default untracked files are not stashed (verified: after git stash the new file was still sitting in the working tree; git stash -u includes it). Many experienced users prefer a WIP commit on the current branch (git commit -am "WIP"), which is visible in the log, survives anything, and is undone later with git reset HEAD~1 or folded away with interactive rebase. For working on two branches at once, git worktree add ../other-dir other-branch checks out a second branch into a second directory that shares the same object store, avoiding the stash dance entirely.

09 Remotes and collaboration

A remote is a named URL of another repository. Collaboration is two operations on the object store: fetch copies objects you lack from the remote and updates your record of where its branches are; push copies your objects to the remote and asks it to move one of its branches. Everything else (clone, pull, pull requests) is built from those two plus the merge and rebase you already know.

Remote-tracking branches are local, read-only bookmarks

origin/main is not "the branch on the server". It is a ref in your repository, refs/remotes/origin/main, recording where main was on origin the last time you fetched. It only moves when you fetch, pull or push. You cannot commit to it (checking it out gives a detached HEAD). Your local main is configured to track it, which is what makes git status report "ahead" and "behind". Right after cloning:

$ git clone origin.git bob ; cd bob
$ git branch -a

  remotes/origin/HEAD -> origin/main
  remotes/origin/main
$ cat .git/packed-refs

Running git fetch followed by an explicit merge or rebase is equivalent and makes each step visible.

Force-push, and how to do it without deleting a colleague's work

After rebasing or amending a branch you have already pushed, your branch no longer contains the remote tip, so a normal push is rejected. git push --force overwrites the remote branch unconditionally, deleting from it any commits you did not have. --force-with-lease adds a check: it overwrites only if the remote branch is still where your origin/main says it is. Three real runs in the Alice/Bob repository, after Bob amended his pushed commit and Alice pushed "Alice: tune":

$ git push --force-with-lease origin main        # Bob has not fetched Alice's new commit
 ! [rejected]        main -> main (stale info)     # good: the lease protected Alice
$ git fetch                                      # an editor's background fetch would do this silently
$ git push --force-with-lease origin main
 + eef75dd...146d3ae main -> main (forced update)  # bad: the lease now matches, and "Alice: tune" is gone
$ git push --force-with-lease --force-if-includes origin main    # same situation, recreated
 ! [rejected]        main -> main (remote ref updated since checkout)

The second run is the trap: --force-with-lease checks against your remote-tracking ref, so anything that refreshes that ref without you looking at the new commits (a plain git fetch, an IDE that fetches in the background) defeats the protection. --force-if-includes (git 2.30+) closes the gap by also requiring that the remote tip appears somewhere in your local branch's reflog, that is, that you actually integrated it at some point. The safe habit is git push --force-with-lease --force-if-includes, and only on branches that are yours.

Forks and pull requests

A pull request (GitHub) or merge request (GitLab) is not a git object; it is a hosting-platform record that says "please merge branch X into branch Y", with a discussion, review approvals and CI results attached. In the shared-repository model every contributor pushes branches to the one repository. In the fork model (usual for open source) you push to your own server-side copy and open the request against the original. Locally you then have two remotes, conventionally origin (your fork) and upstream (the original): fetch from upstream to stay current, push to origin, and the platform moves commits between the two server-side copies when the request is merged. Platforms usually offer three ways to land a request: a merge commit (--no-ff), a squash merge (all the branch's changes become one new commit on the target; the branch's own commits never enter main), or a rebase merge (each commit replayed onto the target). After a squash or rebase merge, your local branch's commits are not ancestors of main, so git branch -d will say the branch is not fully merged; that is expected.

10 Workflows that scale

Git does not prescribe how a team should use branches. A workflow is a convention about which branches exist, how long they live, and how work moves into the branch that gets deployed. The conventions differ mainly in how long work stays apart from the main line, because the cost of integrating grows with the time two lines of work have been diverging.

For a web service or an ML pipeline that deploys from one branch, teams have largely converged on the middle row kept short: short-lived branches, pull-request review, a required CI pass, merge to a protected main, deploy from main. Long-lived release branches remain right when you genuinely maintain several versions at once, as a library with a supported 1.x and 2.x does.

Protected branches and CI gates

Hosting platforms let you protect a branch: forbid direct pushes and force-pushes to it, require a pull request with a minimum number of approvals, require named status checks (tests, linters, data validation) to pass, and optionally require the branch to be up to date with main before merging so that CI tested the actual merge result. That turns the conventions of this section into rules the server enforces. The checks themselves are the subject of CI/CD in the MLOps notes: a pipeline triggered by each push or pull request that builds the code, runs the tests and, for ML, can run data checks and a small training or evaluation smoke test before anything merges. Locally, git hooks (scripts in .git/hooks, such as pre-commit) can run the fast checks before a commit is even created; they are not cloned with the repository, so teams distribute them through a hook-manager configuration that is committed.

Semantic versioning in one paragraph

Release tags usually follow semantic versioning, MAJOR.MINOR.PATCH: increment PATCH for backward-compatible bug fixes, MINOR for backward-compatible new functionality, MAJOR for any incompatible change to the public interface; pre-releases append a suffix such as 2.0.0-rc.1. Version 0.y.z signals that anything may change. The scheme is a promise to the people who depend on you, so it only works if "public interface" is defined. For a model artifact, that interface is the input schema, the output schema and the meaning of the outputs, so retraining that changes predictions but not the contract is a MINOR or PATCH bump, while changing the feature schema is MAJOR.

11 Searching history

Because history is a DAG of snapshots, questions about the past are graph queries. git log selects a set of commits by reachability and then filters and prints them. Ranges are set operations on ancestor sets; the pickaxe searches the changes; blame walks backwards line by line; and bisect runs a binary search over commits to find the one that introduced a bug.

Ranges are set algebra on ancestor sets

bisect: binary search over history

Something worked at an old commit and is broken now. Between them are n commits, and exactly one of them is the first bad one (assuming the bug, once introduced, stays). Testing commits one by one costs up to n tests. Because "is this commit bad?" is monotone along a linear history (good, good, …, good, bad, bad, …, bad), you can instead test the middle and discard half of the candidates each time. That is exactly binary search for a boundary, as in Sorting & Searching · binary search, applied to commits instead of array cells.

costcandidates N = commits in good..bad (bad included) tests ≈ log₂ N, always between ⌊log₂ N⌋ and ⌈log₂ N⌉ on a linear history N = 31 → 4 or 5 tests N = 1000 → about 10 tests N = 1 000 000 → about 20 tests invariantthe first bad commit is always in (last known good, first known bad] — each test shrinks that interval to about half

For data science the test is often a metric threshold: check out, run a short deterministic evaluation, exit non-zero if validation accuracy is below the known-good value minus a tolerance. 12 Git for data science

Git was designed for source code: many small text files, edited by hand, merged line by line. A data-science project also contains notebooks (JSON documents that embed their own outputs), datasets and model files (large binaries), and results that depend on things no file in the repository records (library versions, random seeds, hardware). Each of these breaks one of git's assumptions, and the fixes are all versions of one idea: keep in git the small, text, human-authored description of a thing, and keep the large or generated thing elsewhere, addressed by its hash.

Notebooks diff badly, and why

An .ipynb file is a JSON document. Each code cell stores its source, an execution_count, and its outputs: printed text, tables rendered as HTML, and plots embedded as base64-encoded PNG. So simply re-running a notebook, without changing a single line of code, changes the file. A real example: one cell, re-run, printing a slightly different number.

With real notebooks the effect compounds: one plot is tens of kilobytes of base64 that changes on every run, diffs become unreadable, review is impossible, merges of two people's edits to one notebook conflict inside JSON structure, and the repository grows with every committed re-run (history is immutable, so every version of every plot is kept forever). There are three families of fix, and they combine:

  • Do not commit outputs. Clear outputs and execution counts before committing. The robust way is a git clean filter: a command git runs on a file's content as it is staged, so the blob stored in history is the cleaned version while your working copy keeps its outputs. The nbstripout tool installs exactly this. The mechanism was verified with a five-line Python filter (below). The trade-off is real: someone opening the notebook on a hosting site sees no results.
  • Pair the notebook with a plain-script twin. The jupytext tool keeps a .py file (cells marked with # %% comments) or a Markdown file synchronised with the .ipynb. You commit the script, which diffs, reviews and merges like any code, and either do not commit the .ipynb or commit it only for its outputs.
  • Diff notebooks as notebooks. nbdime parses both versions and shows cell-level changes, source separately from outputs, and can be registered as git's diff and merge driver for *.ipynb through .gitattributes. Hosting platforms increasingly render notebook-aware diffs in pull requests.
$ cat strip.py                                 # reads a notebook on stdin, writes it without outputs
import json, sys
nb = json.load(sys.stdin)
for c in nb["cells"]:
    if c["cell_type"] == "code":
        c["outputs"] = []; c["execution_count"] = None
json.dump(nb, sys.stdout, indent=1); sys.stdout.write("\n")
$ git config filter.nbstrip.clean "python3 strip.py"
$ git config filter.nbstrip.smudge cat
$ echo '*.ipynb filter=nbstrip' > .gitattributes
$ git add .gitattributes eda.ipynb
$ grep -c '0.8123' eda.ipynb                    # your working copy still has its output

   "outputs": [],
$ git commit -qm "Strip notebook outputs via clean filter"
$ …re-run the notebook (count 9, output 0.8130)…
$ git status --short                            # nothing: a re-run is no longer a change

Three caveats from the mechanism itself. When a re-run changes the raw file’s size, git status takes a stat-cache shortcut and may still flag the path as modified without ever running the filter — git diff is empty, and a commit would be a no-op; a git add clears the flag without changing the stored blob. The filter is configured in .git/config, which is not cloned, so each collaborator must install it (the .gitattributes line is committed, the command is not). And notebooks should hold exploration and presentation, not the only copy of logic other code needs; once a function matters, move it into a module that is imported, tested and diffed normally.

Data does not belong in git

Git keeps every version of every file in every clone, forever. That is a feature for code and a disaster for a 2 GB parquet file retrained weekly. Deleting a large file in a later commit does not help, because the earlier commit still contains it. Verified with a 5 MB file:

$ git add train.parquet ; git commit -qm "Add data (mistake)"      # 5 000 000 random bytes
$ git rm -q train.parquet ; git commit -qm "Remove data"
$ git gc -q ; git count-objects -vH | grep size-pack
size-pack: 4.77 MiB                                               # still there
$ git clone -q file://$PWD ../fresh ; cd ../fresh ; git count-objects -vH | grep size-pack
size-pack: 4.77 MiB                                               # and every clone downloads it

The only way out is to rewrite history so that no commit contains the file (the separate git filter-repo tool is the modern way), which gives every later commit a new hash and requires every collaborator to re-clone or hard-reset: the golden rule of §07 broken on purpose. Prevention is far cheaper. Hosting platforms add hard limits on top: GitHub, for example, warns when a pushed file exceeds 50 MiB, rejects files over 100 MiB, and recommends keeping repositories under about 1 GB (5 GB at most). Random or already-compressed bytes (parquet, images, model weights) also defeat git's delta compression (§13), so every version costs its full size.

Git LFS: pointer files instead of content

Git LFS (Large File Storage) keeps large files out of the object store using the same clean/smudge filter mechanism as the notebook stripper. When you stage a tracked file, the clean filter stores the real bytes in a separate LFS store and gives git a tiny pointer file instead; when you check out, the smudge filter swaps the pointer back for the real file, downloading it from the LFS server if needed. LFS is the right tool when large binaries are part of the project in the ordinary sense: assets, a handful of model checkpoints, test fixtures. Its costs: every collaborator needs LFS installed (without it they check out pointer files), hosting platforms meter LFS storage and bandwidth, binary files still cannot be merged (LFS offers file locking for that), and it versions files, not datasets with lineage.

Data versioning: git's object model applied to data

Tools such as DVC take the idea one step further. The data is hashed and stored in a content-addressed cache that is laid out exactly like .git/objects; a small text metafile recording the hash goes into git; the cache is synchronised with cheap object storage (S3, GCS, Azure, a shared drive) instead of the git server. So a git commit pins a dataset version the same way a tree pins a blob, without the data ever entering git. A real run:

To reproduce an old experiment you git checkout its commit, which restores the old metafile, then dvc checkout restores the bytes with that hash from the local cache (dvc pull first downloads them if the cache does not have them). Such tools also record pipelines (which script turned which input hashes into which output hashes), so a stage is re-run only when one of its inputs changed: the same content-addressing logic as a build system. The same pattern appears in table formats with time travel and in lakehouse storage, which version data at the storage layer instead.

Reproducibility needs four versions, not one

what reproduces a resultresult = f( code @ commit, data @ hash, environment @ lockfile or image digest, randomness @ seed ) a commit hash pins the first. a data-version metafile in that commit pins the second. a committed lockfile pins the third. a recorded seed pins the fourth.
  • Environment. A requirements.txt with loose specifiers (pandas>=2) installs different versions on different days. A lockfile pins the full resolved dependency set, transitive dependencies included, usually with hashes of the package files; commit it. Pip-compiled requirement files, uv.lock, poetry.lock and conda lock files all do this; for system libraries, CUDA versions and the interpreter itself, a container image referenced by its digest (content hash again) pins more. The environment tools themselves are covered in Python · environments & the import system.
  • Randomness. Weight initialisation, shuffling, augmentation and dropout all draw random numbers; record the seed with the run and set it everywhere it is needed. The detailed discipline, and why identical seeds can still diverge on GPUs, is in Deep Learning in Practice · reproducibility.
  • Data. "the training CSV" is not a version. A hash is.
  • Data governance. Recording where data came from and how it was transformed (lineage) is the governance side of the same requirement; see Data Quality & Governance.

13 Internals in practice: snapshots, stored smart

If every commit is a full snapshot, why is a repository with years of history small? Because snapshots are only the logical model. Physically, git first shares unchanged objects between snapshots (§02), then compresses each object, and finally packs objects together and stores most of them as deltas against similar objects. This is where diffs actually live in git: as a storage optimisation inside packfiles, invisible to every command you run.

Loose objects and packfiles

A newly written object is a loose object: one zlib-compressed file under .git/objects/xx/. Periodically (git gc, which git also triggers automatically, or the scheduled git maintenance), loose objects are gathered into a packfile (.git/objects/pack/pack-….pack) with an index (.idx) for lookup by hash. Inside a pack, an object can be stored whole or as a delta: instructions to rebuild it by copying ranges from a base object and inserting new bytes. A real repository: a 187 KB Python file with 4000 lines, committed ten times with one line changed each time.

Ten versions, 1.87 MB of raw content, became 520 KiB of individually compressed loose objects and then a 39.7 KiB packfile (41.6 KiB counting its .idx, which is what size-pack reports): one blob stored whole (38 KB compressed) and nine stored as deltas of 29 to 51 bytes of delta instructions (the third column), occupying 42 to 56 bytes each in the pack once headers and compression are included (the fourth column). Rebuilding the newest version (af97595, depth 7) means applying seven deltas in sequence, which is why delta chains are capped (pack.depth, default 50) and why git caches recently rebuilt bases.

Widely repeated: "git stores the newest version whole and older versions as deltas, so recent checkouts are fastest." What this repository shows: here the oldest version (128a5c9, v1) is stored whole and the newest is a depth-7 delta. Git chooses bases by a heuristic: it sorts candidates by type, by a hash of the path name, and then by size, largest first, because a delta that deletes bytes is cheaper to encode than one that inserts them; the order in which objects appear (roughly recency) only breaks ties, and the search then tries each object against a sliding window of its neighbours in that order (pack.window, default 10). Each edit in this experiment replaced a long line with a shorter one, so v1 was the largest version. A second experiment in which each commit appended a line (so the newest version was largest) gave the opposite: newest stored whole, all nine older versions as depth-1 deltas against it (13 bytes of instructions, 25 or 26 bytes in the pack). Recency is a tie-breaker, not the rule.

Why clones and fetches are fast

When you fetch, your git and the server's negotiate: you list commits you have, the server walks the DAG from the commits you want until it reaches ones you have, and sends a single pack containing exactly the missing objects, usually reusing deltas already computed in its own packs. Because objects are named by content, "do you have this?" is a hash lookup and nothing is ever sent twice. Everything after the transfer (log, diff, blame, bisect, checkout) is local disk work.

Shallow and partial clones for huge repositories

When a repository's history is too large, you can ask for less of it. A shallow clone (--depth 1) fetches only the most recent commits: in the bloated repository of §12, it was 1.37 KiB instead of 4.77 MiB, with git log showing a single commit; the price is that operations needing older history (log beyond the cut, blame, bisect, merge-base with old branches) are limited until you git fetch --unshallow. A partial clone (--filter=blob:none) fetches every commit and tree but no file contents except those needed for the checkout, then downloads other blobs on demand when a command needs them: the same repository came to 2.81 KiB with the full three-commit log intact, and the 5 MB blob listed as missing until requested. Partial clones (often with git sparse-checkout to materialise only some directories) are the usual answer for monorepos and for repositories that once committed data.

15 Summary

The mental model on one screen. (1) The object store is a content-addressed, append-only map from hash to bytes holding blobs (file contents), trees (directories), commits (tree + parents + who/when/why) and annotated tags; changing anything makes new objects, so nothing in it is ever edited. (2) History is the DAG formed by commits' parent links; branching is a fork in it, merging adds a node with two parents, rebasing copies a chain of nodes to a new base. (3) Four pointers make up all the state you feel: the working tree (your files), the index (the next snapshot), HEAD (where you are, usually via a branch) and branch refs (names for commits). For any command, ask: which objects does it add, and which pointers does it move? If it only adds objects or moves refs, the reflog can undo it; if it overwrites the working tree or index, uncommitted work is at risk.

For data-science repositories

  • Commit code, configs, lockfiles and data-version metafiles; keep data and model weights out of git and address them by hash (LFS for a few large files, a data-versioning tool for datasets).
  • Strip notebook outputs at staging time or pair notebooks with plain scripts; move logic that matters into modules.
  • Record four things with every result: commit, data hash, environment lock, seed. Commit before launching runs you intend to keep, and let the experiment tracker record the commit.
  • Use bisect with a deterministic metric check to find the commit that made a model worse.
