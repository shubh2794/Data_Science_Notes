Pandas & NumPy

The in-memory data stack: NumPy gives one contiguous, single-dtype array that the CPU can grind through in a tight compiled loop, and pandas wraps those arrays in labelled, aligned tables. This is the overview: why whole-array thinking wins, and the performance ladder that applies to both. The library-specific notes live on two sub-pages.

01 Why vectorization wins

A NumPy ndarray is a fixed-size, single-dtype, contiguous typed memory buffer. A Python list is a resizable array of boxed pointers to scattered heap objects. That one structural difference is the whole performance story.

  • No per-element boxing. A list element is a full Python object — a header, a type pointer, a refcount, then the value. The interpreter must unbox each one on every touch. An array knows its dtype once; the raw values sit back-to-back with no per-element overhead.
  • Cache-friendly compiled loop. Because the bytes are contiguous and homogeneous, the addition a + b runs as a single C loop that the compiler can auto-vectorize to SIMD (one instruction over several lanes), and linear-algebra ops dispatch to a tuned BLAS kernel. The Python interpreter is entered once per array op, not once per element.
  • The payoff: a whole-array a + b is typically ≈10–100× faster than the equivalent for-loop. Treat that as a workload- and dtype-dependent range, not a guarantee — float-heavy arithmetic on large contiguous arrays sits at the top end; branchy, object-dtype, or tiny-array work sits at the bottom.
  • This contiguous, integer-indexed layout is the same idea behind arrays & strings — O(1) random access by computing an address — and the matrix engine that linear algebra rides on.
total bytes = s · ∏ᵢ shapeᵢ (s = itemsize in bytes, e.g. float64 → 8)
Mental model: the interpreter is expensive; the CPU is cheap. Vectorization moves the loop out of Python and into C. Every "loop over rows" you delete is the interpreter stepping aside so the silicon can do its job.

11 Performance, anti-patterns & when to graduate

Most pandas performance problems are one mistake: doing in Python what NumPy could do in C. The cure is to climb the speed ladder and stop dropping back into per-row loops.

The speed ladder (fastest → slowest)

ApproachWhy
Pure vectorized column ops (df.a + df.b, masks)One C loop over contiguous memory — top speed.
Built-in vectorized methods (.str, .dt, .where, .clip)Compiled, whole-column — still no Python loop.
groupby().agg / transformHashed split + compiled reducers.
itertuples()A real per-row loop, but lightweight named tuples.
apply(axis=1)A disguised loop — a Python call per row. Not vectorized.
iterrows()Slowest — boxes each row into a Series every iteration.
  • apply(axis=1) is not magic. It calls your Python function once per row — convenient, but it is a loop with extra steps. Reserve it for genuinely row-local logic that has no vectorized form.
  • Illustrative figure: summing across rows of a 1M-row frame via iterrows can take ≈47 s versus ≈0.03 s vectorized — a ≈1000× gap. Treat this as one illustrative measurement, not a fixed constant; the ratio swings with dtype and operation.

Memory levers

  • Downcast dtypes: float64 → float32 halves memory; int64 → int32/int16 quarters or eighths it — when the value range allows.
  • category for low-cardinality columns (countries, status flags) — store int codes instead of repeated strings.
  • Prefer nullable / string / Arrow-backed dtypes over object — contiguous, vectorizable storage instead of scattered boxed pointers.

Anti-patterns

  • concat/append in a loop is quadratic — each step copies the whole accumulator. Build a list and concat once at the end.
  • Merging without checking key uniqueness → silent many-to-many blow-up. Use validate=.
  • Relying on == for NaN → silent wrong results. Use isna().
  • Mutating a frame while iterating over it → undefined behaviour. Compute into a new column instead.
concat-in-loop: Θ(n²) (copies the accumulator each step) build list → concat once: Θ(n) iterrows ≈ 47 s vs vectorized ≈ 0.03 s on 1M rows (≈1000×, illustrative)

When to graduate

  • Pandas & NumPy fit when the working set fits in RAM — roughly up to a few GB, with headroom left for intermediates (a join can momentarily multiply your footprint).
  • Graduate to a chunked / columnar / distributed engine when the data exceeds memory or a single core becomes the bottleneck — the natural bridge to Apache Spark, which keeps this same split-apply-combine and join vocabulary but spreads it across a cluster.
The discipline: write the whole-array version first; reach for a loop only when the logic truly cannot be expressed as array operations — and reach for a bigger engine only when one machine genuinely can't hold the data.
