06 pandas core — Series, DataFrame & the Index

A Series is a 1-D array of values plus an Index. A DataFrame is an ordered set of columns — each a Series — sharing one Index: conceptually a dict of equal-length, individually-typed columns, i.e. columnar NumPy arrays wearing name tags.

  • The Index is the superpower. It gives label-based alignment: arithmetic and joins line up by label, not by position. Add two Series and matching labels combine while non-matching labels yield NaN — alignment, not silent misregistration.
  • The same Index powers selection, joins, group-by, and reshaping — it is the spine the whole library hangs on.
  • Columns are typed independently (a numeric column next to a string column next to a datetime column) — which is exactly why a DataFrame is "a dict of arrays" and not one 2-D array.
  • pandas is the workhorse of data preprocessing and exploratory data analysis — the layer where raw data is cleaned, reshaped, and made model-ready before it ever reaches a learning algorithm.

Copy-on-Write — the modern default

  • CoW is on by default in pandas 3.x. Any DataFrame derived from another (a slice, a filter, a subset) behaves as if it were independent: writing into the child never propagates back to the parent. You get predictable copy-on-write semantics with no aliasing surprises.
  • Legacy note: before pandas 3.0 the ambiguous SettingWithCopyWarning warned that a chained assignment might hit a view or a copy. Under CoW that ambiguity is effectively retired — treat the old warning as history.
  • Correct single-step assignment is still df.loc[mask, "col"] = value — one indexing operation that writes in place, rather than chained df[mask]["col"] = value.
  • Call .copy() when you explicitly want a detached frame to document intent (though under CoW a derived frame is already write-isolated).
The mental upgrade in pandas 3.x: "is this a view or a copy?" stops being a guessing game. A child frame is logically its own data; the library lazily shares memory until the moment you write, then quietly copies. You reason about values, not buffers.

07 groupby — split, apply, combine

The most important pattern in tabular analysis: split rows into groups by a key, apply a function to each group, then combine the results back into one frame.

  • Split — partition rows by one or more key columns.
  • Apply — one of three shapes: aggregate (each group → one value, e.g. .agg("sum")), transform (each group → same-shaped output, e.g. group-mean broadcast back per row), or filter (drop whole groups by a predicate).
  • Combine — stitch the per-group results into a single output indexed by the group keys.
  • Cost: grouping hashes the keys into buckets, so it runs in ≈ Θ(n) on average rather than sorting — this mirrors SQL's GROUP BY and the same operation in a distributed engine like Apache Spark.
df.groupby("k")["v"].agg("sum") split → aggregate → combine df.groupby("k")["v"].transform("mean") group mean, broadcast back to every row groupby ≈ Θ(n) average (hash keys → buckets, one pass)

Rows are coloured by key. Press group to bucket them, then sum each bucket and combine.

Split → apply → combine watch rows partition by key
Aggregate vs transform: aggregate shrinks (one row per group); transform preserves shape (one row per original row). Reach for transform whenever you want a group statistic written back beside each row — e.g. "this value minus its group's mean."

08 merge, join & concat

merge is the relational join — combine rows from two frames on matching keys. concat just stacks frames (along rows or columns) with no key matching.

  • how= mirrors SQL JOIN: inner (keys in both), left / right (keep all of one side), outer (union of keys, fill gaps with NaN). This is exactly SQL's JOIN family.
  • Algorithm — hash join: build a hash table on one side's keys, then probe it with the other side. Average cost ≈ Θ(n + m), far better than a nested-loop join.
  • The many-to-many trap: if a key is duplicated on both sides, each matching pair produces a row — a near-Cartesian blow-up, ≈ Θ(n · m). A merge can produce vastly more rows than either input.
  • Guardrail: pass validate= (e.g. "one_to_many") so pandas raises if the key uniqueness you assumed is wrong — cheap insurance against silent row explosions.
  • concat ≠ merge: concat stacks frames positionally/by-index (no key logic); merge is relational. For pure stacking, concat; for "look up matching rows," merge.
  • These are the same joins you write in SQL and run at scale on Apache Spark — the relational model travels across all three.
merge ≈ hash-join: build table on one side, probe with the other → Θ(n + m) average many-to-many on duplicated keys → near Θ(n · m) row blow-up (Cartesian) how ∈ { inner, left, right, outer } ↔ SQL JOIN

09 Reshaping — wide ↔ long

Tabular data lives in two shapes. Wide spreads a variable across many columns; long (tidy) stacks it into one value column plus a variable column. Reshaping moves between them.

  • melt — wide → long. Unpivot many columns into two: a variable column and a value column. The standard route to "tidy" data for plotting and grouping.
  • pivot / pivot_table — long → wide. Spread a key column out across new columns; pivot_table additionally aggregates when there are duplicate index/column pairs.
  • stack / unstack — the MultiIndex pair: stack pushes a column level down into the row index (wide → long), unstack pulls a row level up into columns (long → wide).
melt: wide → long (columns → rows) stack: columns level → index level pivot: long → wide (rows → columns) unstack: index level → columns level pivot_table = pivot + aggregation over duplicate (index, column) cells
Tidy heuristic: reach for long when each row should be one observation (best for groupby and plotting), and wide when you want a human-readable matrix (one entity per row, one feature per column). Most analysis flows melt → group → pivot.

10 Missing data

Missing values have one famous quirk: NaN is a float, and NaN ≠ NaN. Equality comparison against it always fails — so you must detect it with dedicated functions.

  • Never use == NaN. It is always False (even NaN == NaN). Detect with isna() / notna() instead.
  • Reductions skip NaN by default (skipna=True): Series([1, NaN, 3]).mean() divides by the 2 present values → 2.0, not NaN. Pass skipna=False to make missing values propagate.
  • Float NaN vs nullable NA: classic float columns use NaN; nullable dtypes (Int64, string, …) carry a real NA mask so integers and booleans can be missing without being promoted to float.
  • Handling: dropna() removes them, fillna(v) / forward-fill imputes them. Choosing how to treat missingness is a core data preprocessing decision, not an afterthought.
NaN == NaN → False ✗ never test equality isna(x) / notna(x) ✓ the only reliable detectors Series([1, NaN, 3]).mean() = (1 + 3) / 2 = 2.0 (skipna=True default)
The bug this prevents: filtering with df[df.col == np.nan] silently returns zero rows — never an error, just wrong. Always df[df.col.isna()].
