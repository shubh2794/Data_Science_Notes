Python

The language that won data science not by being fast, but by being the universal front-end to fast native code. You write the what in readable, dynamically-typed Python; tuned C, Fortran, and CUDA kernels do the how. The craft is knowing how the interpreter actually works — names binding to objects, the data model, the GIL, where the interpreter overhead hides — so you can stay in the expressive layer and drop into the fast layer exactly where it pays. For the array and dataframe stack that does the heavy lifting, see Pandas & NumPy.

01 Why Python for DS/ML

Python's value is not raw speed — pure-Python is one of the slowest mainstream languages. Its value is that it lowers the cost of thought and sits as the readable control layer on top of compiled numerical engines.

  • Readability lowers the cost of thought. Clean syntax means more of your attention goes to the model and the data and less to the language. In exploratory work — where you rewrite the same analysis ten times — that compounds.
  • The REPL → notebook loop. Type an expression, see the result, adjust, repeat. The tight feedback loop of an interactive interpreter (and notebooks built on it) matches how analysis actually proceeds: incrementally, with constant inspection.
  • Python is GLUE. You write the what in Python; compiled C / Fortran / CUDA kernels do the how. A line like a + b over two arrays enters the interpreter once and runs a tight C loop — see how vectorization moves the loop out of Python. The same idea underpins the matrix engine of linear algebra: BLAS/LAPACK kernels do the arithmetic, Python only orchestrates.
  • Ecosystem gravity / network effects. Because everyone targets Python, every new library, model, and tutorial lands in Python first. Each addition makes the next person more likely to choose Python — a self-reinforcing flywheel that, more than any feature, is why ML runs here. (Its long-standing partner for the data half of the work, SQL, completes the daily DS language pair.)
cost(analysis) ≈ cost(think) + cost(write) + cost(run) Python: minimizes think + write · delegates run → native kernels
Mental model: Python is a high-level remote control for fast machinery. The skill is to keep your code in the readable control layer and let C/CUDA do the numeric work — never hand-write the inner loop in Python when a library already runs it in C.

02 Execution model & the data model

CPython — the reference implementation you almost certainly run — compiles your source to bytecode, then executes that bytecode on a stack-based virtual machine. There is no separate compile step you invoke; it happens on import.

  • Source → bytecode → VM. .py text is parsed and compiled to compact bytecode instructions, cached as .pyc, and run by the CPython evaluation loop one instruction at a time on a value stack. "Interpreted" really means "compiled to bytecode, then interpreted."
  • Dynamic typing. Types attach to objects, not to names. The same name can point at an int now and a list next line — the type is checked at runtime, every time.
  • Everything is an object. Integers, functions, classes, modules — all are first-class objects with a type, an identity (id()), and attributes. There are no primitives sitting outside the object system.
  • The data model & dunder methods. Built-in syntax delegates to "double-underscore" methods on the object: len(x) calls x.__len__(), x[i] calls x.__getitem__(i), for v in x calls x.__iter__(), repr(x) calls x.__repr__(). Implement the right dunders and your own class behaves like a built-in — this is how the whole language is extensible.
len(x) → x.__len__() x[i] → x.__getitem__(i) for v in x → it = x.__iter__(); it.__next__() … a + b → a.__add__(b) (else b.__radd__(a))
Why dunders matter for DS: a NumPy array or a pandas Series feels native — arr[mask], len(df), for col in df — precisely because those libraries implement the data-model protocols. You are speaking the same object language the interpreter speaks.

03 Names, binding, mutability & aliasing

Python has no "variables" in the C sense of typed boxes that hold values. A name is a label bound to an object. Two names can label the same object — that is aliasing, and it is the source of the most common surprises in the language.

  • x = [1,2,3] creates a list object and binds the name x to it. y = x binds a second name to the same object — it does not copy. Now x and y are aliases.
  • Rebinding vs mutating. y = [4,5] rebinds y to a brand-new object — x is untouched. y.append(99) mutates the shared object in place — and the change is visible through x too, because they point at the same thing.
  • Mutable vs immutable. Lists, dicts, and sets are mutable (can change in place). Ints, floats, strings, and tuples are immutable — "changing" one always produces a new object and rebinds the name.
  • To break an alias, make a copy: y = x.copy() (shallow) or copy.deepcopy(x) (recursive). Now mutating one cannot affect the other.
y = x → alias (one object, two names) y.append(99) → mutate (visible through x AND y) y = [4,5] → rebind (new object; x unchanged) y = x.copy() → detach (independent object)

The mutable-default-argument gotcha

  • Default values are evaluated ONCE, at def-time — not on each call. So def f(x, acc=[]) creates a single list that persists across every call and silently accumulates.
  • The fix is the None sentinel: default to None and build a fresh object inside the body. This is one of the most-tested Python interview traps and a real production bug.
def f(x, acc=[]): # BUG: one shared list, evaluated once at def-time acc.append(x); return acc f(1) → [1] f(2) → [1, 2] f(3) → [1, 2, 3] ✗ shared! def f(x, acc=None): # FIX: fresh list each call if acc is None: acc = [] acc.append(x); return acc
Why these are the same bug: both come from forgetting that an assignment binds a name to an existing object rather than copying a value. The default list and the aliased list are one object seen through two doors. Once "name → object" is your mental model, both surprises evaporate.

04 The GIL & the concurrency choice

CPython has one Global Interpreter Lock. It protects the interpreter's internal state — most importantly the per-object reference counts — by allowing only one thread to execute Python bytecode at a time. That single fact dictates how you parallelize.

  • Why it exists. CPython manages memory with reference counting; updating a refcount from two threads at once without locking would corrupt it. One coarse lock is far simpler (and faster single-threaded) than locking every object.
  • The consequence. On the default build, CPU-bound threads do not scale across cores — they take turns holding the GIL. Adding threads to a number-crunching loop buys you roughly 1×, plus overhead.
  • The GIL is released during I/O waits (disk, network, sleeps) and inside many C extensions (NumPy releases it for big array ops). So I/O-bound work overlaps beautifully even with threads.

Decision rule

WorkloadToolWhy
I/O-bound (web, DB, files)threading or asyncioGIL released while waiting → real overlap; asyncio does it in one thread, cooperatively.
CPU-bound (default build)multiprocessingSeparate processes = separate interpreters = separate GILs → true multi-core.
CPU-bound (free-threaded build)threadingNo GIL → threads run bytecode in parallel across cores.
Heavy numericsvectorize / native kernelsThe C kernel sidesteps the question — see Pandas & NumPy.

Free-threading (no-GIL): PEP 703 / PEP 779

  • Status. Free-threading was experimental in 3.13 and became officially supported in 3.14 (PEP 779, "Phase II") — but it is still not the default build. The standard interpreter ships with the GIL; a separate build (configured with --disable-gil) removes it.
  • Identify what you are running. The free-threaded interpreter is named python3.13t / python3.14t. Check the build with python -VV, and at runtime ask sys._is_gil_enabled().
  • Single-thread cost. Removing the GIL once carried a steep single-threaded penalty (~40% in early 3.13); in 3.14 it has fallen to roughly 1–8% — present as a range, workload-dependent.
  • The horizon. A future "Phase III" would make the free-threaded build the default, but no version is committed — it depends on how fast the library ecosystem adopts it.
default build: one GIL → CPU-bound threads ≈ 1× (serialized bytecode) free-threaded: no GIL → CPU-bound threads ≈ N× (parallel across N cores) detect: python -VV · sys._is_gil_enabled() → True / False

05 Built-in data structures & complexity

Four built-in collections cover most code: list, dict, set, tuple. Choosing the right one is usually choosing the right complexity class — and the gap between O(n) and O(1) lookups is the difference between code that scales and code that doesn't.

TypeWhat it isMutable?Key trait
listDynamic array of boxed pointersYesOrdered; O(1) index; amortized O(1) append
dictHash table (key → value)YesO(1) average get/set; insertion-ordered
setHash table of keys onlyYesO(1) average membership; deduplicates
tupleImmutable listNoHashable → usable as a dict key / set element
  • A list is a dynamic array of boxed pointers — the same structure behind arrays & strings: O(1) random access by computing an address. append is amortized O(1): it occasionally over-allocates and grows the backing buffer (an O(n) resize), but averaged over many appends the cost is constant.
  • Inserting or popping at the front is O(n) — every later element must shift. For a queue, reach for collections.deque (O(1) at both ends).
  • Membership: x in list is O(n) (linear scan) but x in set / x in dict is O(1) average (hash lookup). Worst case is O(n) only under pathological hash collisions.
  • The killer lesson: doing n membership tests against a list is O(n²); against a set it is O(n). Converting a list to a set before a dedup/filter loop is the single most common easy speedup. See Big-O complexity and data structures & algorithms.
list: index O(1) · append O(1) amortized · insert(0)/pop(0) O(n) · x in list O(n) dict/set: get / set / del / membership → O(1) average (O(n) worst, pathological) n lookups in a list → O(n²) n lookups in a set → O(n) tuple = immutable list (hashable → dict key, set member)
Default to a dict/set when you ask "is it in there?" or "what maps to what?" — that question is what hash tables are for. Default to a list when order and indexing matter and you mostly append.

06 Comprehensions, generators & iterators

Comprehensions are Python's compact, readable way to build a collection from an iterable. The crucial choice is eager (a list comprehension that materializes everything) versus lazy (a generator that produces values one at a time).

  • List comprehension — [f(x) for x in xs if p(x)] — builds the whole result in memory: O(n) live memory. Fast and clear when the result fits.
  • Generator expression — (f(x) for x in xs) — is lazy: it yields one value per next() and holds essentially O(1) live memory. Perfect for streaming a huge file or a pipeline where you never need all values at once.
  • The iterator protocol. Anything iterable implements __iter__() (returns an iterator); an iterator implements __next__() (returns the next value or raises StopIteration). A for loop is sugar over exactly this. A function with yield becomes a generator — a paused-and-resumable iterator that keeps its local state between values.
[f(x) for x in xs] → list · O(n) memory · all values now (f(x) for x in xs) → generator · O(1) memory · one value at a time for v in obj ≡ it = iter(obj); while: v = next(it) … until StopIteration
Rule of thumb: if you will consume the values once, in order — especially over data too big for RAM — use a generator. If you need random access, length, or repeated passes, materialize a list.

07 First-class functions, closures & decorators

Functions in Python are ordinary objects: you can assign them to names, pass them as arguments, return them, and store them in lists or dicts. This first-class status is what makes closures and decorators possible.

  • First-class functions. sorted(xs, key=len) passes a function as data; a dict of {"sum": np.sum, "mean": np.mean} stores functions as values. This is the backbone of callbacks, strategy dispatch, and the key=/apply idioms throughout the data stack.
  • Closures. A function defined inside another captures the enclosing scope's variables — it "closes over" them and remembers them after the outer function returns. This is how you build configured functions (a multiplier-by-k maker, a parametrized validator) without classes.
  • Decorators. A decorator is a function that takes a function and returns a (usually wrapped) replacement. @timer above a definition is just f = timer(f). Common uses: timing, caching (functools.lru_cache), logging, registration, retry. Use functools.wraps inside the wrapper to preserve the original's name and docstring.
@decorator def f(...): ... ≡ f = decorator(f) def make_mul(k): # closure: captures k def mul(x): return x * k return mul times3 = make_mul(3) # times3(10) → 30
Where you meet these in DS: @lru_cache to memoize an expensive feature computation, framework decorators that register a function as a route / task / model, and passing reducers as key= arguments. The pattern is always "a function operating on a function."

08 Typing — dynamic with gradual hints

Python is and stays dynamically typed. Type hints (PEP 484) layer an optional, gradual annotation system on top — and crucially, those hints are erased at runtime. The interpreter does not enforce them; their value is entirely in tooling.

  • Hints are optional and erased. def mean(xs: list[float]) -> float: runs exactly the same whether or not the annotations are correct — passing a list of strings raises no type error from Python itself. Annotations are metadata, not checks.
  • The value is tooling, not enforcement. Static checkers (mypy, pyright) read the hints and catch type mismatches before you run; the IDE uses them for autocomplete and refactoring; and a typed signature is self-documenting — the clearest comment is the type.
  • Adopt gradually. The pragmatic pattern on DS teams: type the stable library / interface layer (functions other code calls) and leave exploratory notebook code untyped. You get the safety where it matters without slowing down the rapid-iteration layer.
def mean(xs: list[float]) -> float: ... # hint = documentation + tooling runtime: annotations erased → no type check, Python stays dynamic mypy / pyright: read hints → flag mismatches BEFORE running
The right expectation: type hints are not a switch that makes Python statically typed. They are a static-analysis aid you opt into, paid for in a little extra writing and repaid in fewer "wrong shape passed three calls down" bugs.

09 The performance story & escape hatches

Pure-Python loops are slow for two structural reasons. Understanding them tells you exactly which escape hatch to reach for — and why "just vectorize it" is almost always the first answer.

  • (a) Interpreter overhead. Every step of a Python loop does dynamic dispatch and type lookups: figure out what + means for these objects, find the method, check types — for every single element. The bytecode VM pays this tax per operation.
  • (b) Boxing. Every int and float is a full heap object — a header, a type pointer, a refcount, then the value — scattered across memory. Walking a list of them thrashes the cache: the CPU stalls fetching pointers to objects that aren't adjacent.

Escape hatches, in order of effort

ApproachWhat it doesWhen
Vectorize (Pandas & NumPy)Move the loop into C over contiguous typed memoryFirst resort — most numeric work
Numba (@njit)JIT-compiles numeric Python to machine codeLoop-heavy numeric code that's hard to vectorize
CythonCompiles annotated Python to a C extensionHot paths needing C-level control
C / C++ / Rust extensionHand-written native module called from PythonMaximum control / existing native code
multiprocessing / free-threadedTrue multi-core for CPU-bound workEmbarrassingly parallel, can't vectorize away
  • The interpreter itself got faster. The Faster-CPython effort (driven by PEP 659's specializing adaptive interpreter, which learns runtime type patterns and skips redundant checks) made 3.11 ≈ 1.25× over 3.10 (roughly 10–60% depending on workload), and 3.14 ≈ 40–50% over 3.10. Treat these as directional ranges, not pinned guarantees.
  • The 3.13 JIT (a copy-and-patch experimental JIT) so far adds only a few percent — present it as early and unverified in magnitude, not a promised win.
  • None of this closes the gap to native code. A 40–50% interpreter speedup is real, but vectorized C is still ≈10–100× a Python loop. Faster CPython makes the glue layer cheaper; it does not replace native kernels.
slow loop = interpreter overhead (dispatch + type lookups / step) + boxing (heap object per number → cache thrash) faster-cpython: 3.11 ≈ 1.25× vs 3.10 · 3.14 ≈ 40–50% vs 3.10 (ranges, directional) vectorized C ≈ 10–100× a Python loop (the real win lives in native kernels)
The discipline: reach down the ladder only as far as you must. Vectorize first; profile; only then introduce Numba/Cython/native code or parallelism — each step costs build complexity and readability, the very things Python bought you in section 01.

10 Modern features worth knowing

A handful of newer language features show up constantly in modern DS code. Each is tagged with the version it landed in.

  • f-strings (3.6). f"acc={score:.3f}" — inline, formatted interpolation. The f"{x=}" debug form (3.8) prints both the expression and its value: x=42. The fastest, clearest way to log during experiments.
  • dataclasses (3.7). @dataclass auto-generates __init__, __repr__, and __eq__ from annotated fields — ideal for config objects, hyperparameter bundles, and small typed records without boilerplate.
  • Walrus := (3.8). Assignment expression — bind and use a value in one place, e.g. while (line := f.readline()): or capturing a length inside a comprehension's filter.
  • Structural pattern matching match/case (3.10). Not a plain switch — it matches and destructures shapes: tuples, sequences, mappings, and class patterns, binding parts as it goes. Great for dispatching on the structure of parsed data or message types.
  • Exception groups + except* (3.11). Raise and selectively handle multiple concurrent exceptions at once — designed for the era of concurrent tasks (asyncio, parallel workers) where several can fail together.
f"{score:.3f}" · f"{x=}" → "x=42" (3.6 / 3.8 debug form) @dataclass → auto __init__/__repr__/__eq__ (3.7) n := len(xs) → assign + use in one expression (3.8) match cmd: case ("move", x, y): ... (3.10 destructuring) except* ValueError: ... (3.11 exception groups)
Match is matching, not switching. The win over an if/elif chain is the destructuring — case Point(x=0, y=y) tests the shape and binds y in one line. Reach for it when you branch on the structure of data, not just on a scalar value.

11 Environments & the import system

Isolated environments keep each project's dependencies from colliding. Three tools cover most workflows — and the import system is just a search-and-cache over sys.path.

ToolManagesNote
venvAn isolated set of Python packagesStdlib, lightweight; uses the Python you already have
condaPackages + non-Python binary deps + Python itselfSolves native libraries (CUDA, MKL, compilers); common in DS
pipInstalls Python packages from the indexThe package installer; runs inside venv or conda
  • The import system searches the directories in sys.path for the named module, then caches the compiled bytecode as a .pyc file (in __pycache__) so the next import skips recompilation. import x runs the module's top-level code once and binds the name x in your namespace.
  • Reproducibility belongs elsewhere. Pinning exact versions with lockfiles, building container images, and managing environments across a fleet are operational concerns — they live in the MLOps notes, not the language itself. Here, just remember: isolate per project, and record what you installed.
import x → search sys.path → run module top-level once → cache .pyc → bind name x venv ⊂ Python packages conda ⊂ Python packages + binary deps + Python pip install → fetch + install into the active environment
Practical default: one isolated environment per project, never the system Python. Use conda when you need native/GPU libraries it can solve for you; use venv + pip when pure-Python deps are enough. Either way, treat "what's installed" as something you record, not something you remember.
