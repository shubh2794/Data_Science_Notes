SQL

The declarative query language for tabular data — and the other half of the daily data-science language pair. You describe what set of rows you want; a cost-based query optimizer decides how to get them (which scans, which join algorithm, which index). The craft is thinking in sets, not rows: filter, join, aggregate, and reshape whole tables at once, push the heavy lifting down to a warehouse, and hand a compact, analysis-ready table to the in-memory stack. For the array-and-dataframe side of that handoff — and the SQL↔pandas dictionary — see Pandas & NumPy.

01 The relational model & the declarative paradigm

A relation R is a set of tuples over attributes A₁…Aₙ. A SQL table is the same idea with one relaxation: it is a multiset (a bag), so duplicate rows are allowed unless a key or DISTINCT forbids them. SQL is declarative — you state the what, the engine plans the how.

  • Declarative, not imperative. You do not write the loops, the index lookups, or the join order. You describe the result set; the planner/optimizer enumerates physical plans (sequential scan vs index scan, hash vs merge vs nested-loop join) and picks the one with the lowest estimated cost from table statistics.
  • Set-based, not row-by-row. One statement operates on whole relations at once — the same mental shift as vectorizing instead of looping. Walking rows one at a time with a cursor (the SQL analogue of iterrows) is an anti-pattern: it discards the optimizer and runs at interpreted speed.
  • Relational algebra under the hood. Every SQL clause maps to an algebraic operator. Learning the algebra is learning what the engine actually composes — selections (σ), projections (π), joins (⋈), and set operations (∪ ∩ −).
  • Where the internals live. How rows are physically stored, how transactions stay consistent, and how a B-tree index is laid out are database-internals concerns (the relational-engine, indexing, and OLTP-vs-OLAP topics in the databases domain). This page stays on SQL as a query language for data work — extract, filter, aggregate, reshape, and prep features.
σ_predicate (R) → WHERE predicate π_cols (R) → SELECT cols (+ DISTINCT for a true set projection) R ⋈ S on θ → R JOIN S ON θ (inner) R ⟕ S / R ⟖ S → LEFT / RIGHT OUTER JOIN R ⟗ S → FULL OUTER JOIN R × S → CROSS JOIN (Cartesian product) R ∪ S / R ∩ S / R − S → UNION / INTERSECT / EXCEPT
Mental model: SQL is a high-level specification of a result set; the optimizer is a compiler that turns it into a physical plan. Your job is to describe the answer clearly and give the planner good statistics and the right indexes — not to micro-manage how it runs. Fight the urge to loop.

02 Query anatomy & logical execution order

A query is written SELECT … FROM … WHERE …, but it is logically evaluated in a different order. Internalizing that order explains nearly every "why can't I reference that here?" error in SQL.

  • The logical pipeline (what the result is defined to be — the optimizer may physically reorder as long as the answer is identical):
FROM / JOIN → build the working row set (combine tables) WHERE → filter ROWS (before grouping) GROUP BY → collapse rows into groups HAVING → filter GROUPS (after aggregation) SELECT → compute output columns (incl. window functions) DISTINCT → drop duplicate output rows ORDER BY → sort the result LIMIT / OFFSET → truncate to a page
  • WHERE vs HAVING. WHERE filters individual rows before grouping; HAVING filters whole groups after aggregation. An aggregate predicate like count(*) > 5 must go in HAVING — the count does not exist yet at WHERE-time.
  • Aliases. A column alias defined in SELECT is not visible in WHERE, GROUP BY, or HAVING (those run first), but is visible in ORDER BY (which runs after SELECT). Many engines extend this leniency, but the portable rule follows the logical order.
  • Window functions run in the SELECT step — after GROUP BY/HAVING. So you cannot put a window function in WHERE or HAVING; to filter on one (e.g. "keep row_number() = 1"), wrap the query in a subquery or CTE and filter the outer level.
The alias trap, stated once: SELECT price*qty AS total FROM s WHERE total > 100 fails — at WHERE-time the name total does not exist yet. Repeat the expression in WHERE, or wrap it in a subquery/CTE. The viz below fires exactly this error when you try it.

03 JOINs & the fan-out gotcha

A join combines rows from two tables on a predicate. The type decides which non-matching rows survive; the key cardinality decides how many rows come out — and getting that wrong silently double-counts every aggregate downstream.

JoinKeepsAlgebra
INNER JOINOnly matched pairsR ⋈ S
LEFT JOINAll left rows; right NULL-filled when unmatchedR ⟕ S
RIGHT JOINAll right rows; left NULL-filled when unmatchedR ⟖ S
FULL OUTER JOINAll rows from both; NULL-filled where unmatchedR ⟗ S
CROSS JOINEvery pair (no predicate)R × S → |R|·|S| rows
  • Semi-join — "left rows that have a match," with no columns from the right and no row multiplication: WHERE EXISTS (…) or WHERE x IN (…).
  • Anti-join — "left rows that have no match": WHERE NOT EXISTS (…), or the classic LEFT JOIN … WHERE right.key IS NULL pattern.
  • Fan-out. If each left row matches mᵢ right rows, the inner-join output has Σᵢ mᵢ rows. A unique right key gives 1:1 or many:1 (safe — one output row per left row). Duplicate keys on both sides give many:many — a per-key Cartesian product that can dwarf either input.
  • Why it bites: aggregating after a fan-out join double-counts. If an order row matches three shipment rows, summing the order amount counts it three times.
  • Fixes: pre-aggregate to one row per entity before joining; use a window / ROW_NUMBER() to pick exactly one row; or join on the true unique key. The portable safeguard is to verify key uniqueness on the side you expect to be unique — the SQL counterpart of pandas' validate= on merge.
inner-join rows = Σᵢ mᵢ (mᵢ = right matches for left row i) unique right key → mᵢ ∈ {0,1} → no blow-up (1:1 / many:1, safe) dup keys both sides → many:many → per-key Cartesian (≫ inputs) CROSS JOIN size = |R| · |S| aggregate AFTER fan-out → double-count

04 Aggregation & GROUP BY

GROUP BY partitions rows into buckets by distinct key combinations and collapses each bucket to one output row. The result has exactly as many rows as there are distinct key combinations — this is SQL's split-apply-combine.

  • The cardinality rule: result rows = number of distinct grouping-key combinations. Group by one column → one row per distinct value; group by two → one row per distinct pair.
  • The SELECT-list rule: every selected column must be either a grouping key or wrapped in an aggregate (sum, count, avg, min, max). A bare non-grouped column has no single value per group — standard SQL rejects it.
  • COUNT(*) vs COUNT(col): COUNT(*) counts rows; COUNT(col) counts rows where col is not NULL. AVG, SUM, and the rest also ignore NULLs — so an average is over the present values, not the row count.
  • This is the exact same operation as pandas' groupby().agg() and the GROUP BY of a distributed engine — hash the keys into buckets, reduce each bucket. The vocabulary travels.
result rows = # distinct (key₁, …, keyₖ) combinations SELECT list ⊆ { grouping keys } ∪ { aggregate(col) } COUNT(*) = rows COUNT(col) = rows where col IS NOT NULL AVG / SUM / MIN / MAX → computed over NON-NULL values only
The collapse is the point. GROUP BY trades detail for summary: you get one row per group and lose the individual rows. When you want a group statistic but want to keep every row, that is a window function (next) — not GROUP BY.

05 Window functions

A window function computes a value per row over a related set of rows (the "window") — and crucially does not collapse the result. Every input row survives, gaining a new computed column. The slogan: GROUP BY collapses; WINDOW keeps.

f(args) OVER ( PARTITION BY p ORDER BY o [frame] ) ─ split into groups ─ │ ─ order within ─ │ ─ row range ─ ROW_NUMBER() → 1,2,3,4 (no ties) RANK() → 1,2,2,4 (gaps after ties) DENSE_RANK() → 1,2,2,3 (no gaps) LAG(x,k) / LEAD(x,k) → value k rows back / ahead (period-over-period) SUM(x) OVER (ORDER BY o ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) → running total
  • The frame default matters. With an ORDER BY and no explicit frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — i.e. a cumulative window (running total). With no ORDER BY, the frame is the whole partition (e.g. the partition average repeated on every row).
  • Ranking family: ROW_NUMBER breaks ties arbitrarily (always 1,2,3,4); RANK leaves gaps after ties; DENSE_RANK does not. Choose by whether ties should share a rank and whether gaps are acceptable.
  • Offset family: LAG/LEAD reach to neighboring rows in the ordered partition — the idiom for deltas, growth rates, and "compared to last period."
  • Where it runs: the SELECT step, after GROUP BY/HAVING — which is why you cannot filter on a window result in WHERE/HAVING (wrap in a subquery/CTE).
Use casePattern
Top-N per groupROW_NUMBER() OVER (PARTITION BY g ORDER BY v DESC) then keep ≤ N
Deduplicatekeep rows where ROW_NUMBER() … = 1
Running totalSUM(v) OVER (ORDER BY t)
Period-over-periodv − LAG(v) OVER (ORDER BY t)
Moving average (time features)AVG(v) OVER (ORDER BY t ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)

06 Subqueries vs CTEs

Deeply nested subqueries read inside-out and are hard to follow. A CTE (WITH name AS (…)) flattens that nesting into named, top-to-bottom steps — each reusable and testable, like assigning intermediate dataframes to variables.

  • CTEs are for readability. WITH a AS (…), b AS (… a …) SELECT … FROM b reads as a linear pipeline. The same logic as a stack of subqueries, but legible and DRY (define once, reference by name).
  • Materialization is engine- and version-dependent [unverified — depends on engine/version]. A common pattern: a single-reference, side-effect-free CTE is often inlined (folded into the outer query), while a multiply-referenced CTE is typically materialized once into a temp result. Some engines have historically treated a CTE as an optimization fence (older PostgreSQL always materialized). Modern PostgreSQL inlines single-reference CTEs by default and lets you force the choice with MATERIALIZED / NOT MATERIALIZED. Treat all of this as "check your engine," not a universal rule.
  • Recursive CTEs (WITH RECURSIVE) walk hierarchies and graphs: a base term (the anchor rows) UNION [ALL] a recursive term that references the CTE itself, iterating until no new rows appear. Use them for org charts, bills of materials, and path-finding.
WITH a AS ( … ), -- named step 1 b AS ( … FROM a … ) -- step 2 reuses a SELECT … FROM b; -- linear pipeline, not inside-out nesting WITH RECURSIVE t AS ( SELECT … -- base term (anchor) UNION ALL SELECT … FROM t … -- recursive term (references t) ) SELECT * FROM t; -- hierarchy / graph traversal
Don't assume a CTE is free or fenced. Whether it is inlined or materialized changes the plan — and the answer differs across engines and versions. When performance matters, read the EXPLAIN output (§10) rather than trusting folklore.

07 Set operations

Set operations stack the results of two queries that have matching column count and compatible types (columns align by position, not name). They are the direct SQL realization of relational ∪, ∩, and −.

OperatorReturnsNote
UNIONRows in either, de-duplicatedImplies a distinct pass — extra cost
UNION ALLRows in either, keeps duplicatesCheaper — no dedup; prefer when you know rows are disjoint
INTERSECTRows in bothDistinct by default
EXCEPTRows in the first but not the secondCalled MINUS in some dialects
A UNION B → A ∪ B (distinct) A UNION ALL B → bag union (keeps dups, cheaper) A INTERSECT B → A ∩ B A EXCEPT B → A − B (MINUS in some dialects) columns align by POSITION + type — not by name
Default to UNION ALL unless you actually need dedup. Plain UNION silently adds a distinct pass over the combined result — a real cost on large inputs. Reach for it only when duplicates across the two branches are possible and unwanted.

08 NULL & three-valued logic

NULL means "unknown," and it turns Boolean logic into three-valued logic: every predicate is TRUE, FALSE, or UNKNOWN. Any comparison to NULL yields UNKNOWN — including NULL = NULL. This is the source of more silent wrong answers than any other SQL feature.

  • Never test = NULL. x = NULL is UNKNOWN (not TRUE), and so is NULL = NULL. Use IS NULL / IS NOT NULL — the only operators that return a real Boolean against NULL.
  • WHERE keeps a row only when the predicate is TRUE. UNKNOWN is dropped exactly like FALSE — so a comparison against a NULL column quietly removes that row.
  • Aggregates ignore NULLs (§4), and COALESCE(x, default) substitutes a value — the standard way to handle the NULLs an outer join introduces.
NULL = NULL → UNKNOWN NULL = 5 → UNKNOWN (use IS NULL / IS NOT NULL) TRUE AND UNKNOWN → UNKNOWN TRUE OR UNKNOWN → TRUE FALSE AND UNKNOWN → FALSE FALSE OR UNKNOWN → UNKNOWN NOT UNKNOWN → UNKNOWN WHERE keeps a row ⇔ predicate is TRUE (UNKNOWN dropped, like FALSE)
The NOT IN trap: x NOT IN (a, b, NULL) expands to x≠a AND x≠b AND x≠NULL. That last term is UNKNOWN, so the whole AND can never be TRUE → the query returns zero rows, silently. Prefer NOT EXISTS, or explicitly exclude NULLs from the subquery, whenever the inner list might contain one.

09 SQL ↔ pandas — the same operations, two paradigms

Almost every SQL clause has a one-line pandas equivalent — they are two front-ends to the same relational operations. The difference is where and how the work runs. Rather than re-teach the dataframe side, see Pandas & NumPy; this is the dictionary.

The real trade-off: pandas is imperative + in-memory — you control each step and the whole frame must fit in RAM. SQL is declarative + optimizer-driven — you describe the result and the engine scales it across warehouse-sized data without loading it into your process. The practical division of labour: do the heavy filter/join/aggregate in SQL, then hand a compact table to pandas for the last-mile, row-local work.

10 Indexes & reading EXPLAIN

Because SQL is declarative, the optimizer chooses the access path. It estimates each plan's cost from table statistics (row counts, value distributions) and picks the cheapest. Two access paths dominate: scan the whole table, or jump in via an index.

  • Sequential scan reads every row — cost grows as Θ(N). It is actually the right choice when most rows qualify or the table is small: there is nothing to skip.
  • Index scan can locate matching rows without reading the whole table. As an order-of-magnitude intuition only [unverified; depends on index type and engine], finding k matches costs on the order of Θ(log N + k). The big win appears only when the query is selective — k ≪ N. Pull back most of the table and an index scan can be slower than a plain scan.
  • Indexes are not free. Each one must be updated on every insert/update/delete (write-throughput cost) and consumes storage. Index the columns you filter and join on; don't index everything.
  • EXPLAIN prints the chosen plan and its estimated cost without running the query. EXPLAIN ANALYZE actually runs it and prints actual rows and time per node — the way to catch a planner whose row estimate was wildly off (usually stale statistics), which is the root of most "why is this slow?" cases.
  • Data-structure internals are out of scope here. How a B-tree, hash, or columnar index is built and traversed belongs to the databases-domain Indexing topic — this page only cares that an index gives you a sub-linear lookup when the predicate is selective.
optimizer: cost(plan) from statistics → pick min seq scan ≈ Θ(N) best when most rows qualify / table is small index scan ≈ Θ(log N + k) [intuition only] big win only when selective (k ≪ N) EXPLAIN → chosen plan + ESTIMATED cost (no run) EXPLAIN ANALYZE → runs it + ACTUAL rows/time (exposes bad estimates)
Read the plan, don't guess. When a query is slow, run EXPLAIN ANALYZE and compare estimated vs actual rows at each node. A large gap means stale statistics misled the optimizer — refresh them (or add the missing index) rather than rewriting the SQL by superstition.

12 SQL's role in DS, analytics & feature engineering

SQL is the front of the data pipeline. Analytical SQL runs in OLAP warehouses and lakehouses, does the heavy reduction over huge row ranges, and emits a compact, analysis-ready table that the in-memory and ML stack takes over.

  • OLAP vs OLTP, briefly. Warehouses and lakehouses (Snowflake, BigQuery, Redshift, Databricks SQL, DuckDB) are OLAP — typically columnar, tuned for wide aggregations scanning huge row ranges. That contrasts with OLTP row stores built for high-QPS point reads and writes. (The OLTP/OLAP storage distinction itself is databases-domain context — mentioned here only to place SQL's analytical role.)
  • The handoff pattern. Warehouse SQL does the heavy filter → join → aggregate over billions of rows; the result — small enough to fit in memory — flows to pandas, a distributed dataframe engine, or an ML training job. Push computation to the data; move only the summary.
  • SQL is the start of feature engineering. Window functions build time features (lags, rolling aggregates), GROUP BY builds rollups and counts, and joins enrich entities with attributes from other tables. This is the layer that feeds downstream ETL pipelines and feature stores.
  • SQL-on-big-data. Engines like Spark SQL, Trino/Presto, and Hive expose the same declarative SQL surface over data spread across a cluster — the relational model and your SELECT … GROUP BY … OVER (…) vocabulary travel unchanged from a single warehouse to a distributed lake. (Exploratory analysis, large-scale Spark processing, and the ETL/feature-store layer each have their own treatment in this collection.)
warehouse SQL (OLAP, columnar): filter → join → aggregate over huge row ranges ↓ compact, analysis-ready table (fits in memory) pandas / Spark / ML takes over → modeling, last-mile transforms SQL = front of the feature pipeline: window fns (time features) · GROUP BY rollups · joins (enrich)
The division of labour: let the warehouse do what it is built for — scan, join, and aggregate enormous tables in parallel — and reserve the in-memory tools for the small, model-shaped result. The biggest analytics speedups usually come not from faster pandas, but from doing more of the reduction in SQL before the data ever leaves the warehouse.
